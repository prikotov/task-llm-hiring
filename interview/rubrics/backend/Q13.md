# Q13 — Агрегат в DDD

## 🟢 Зелёный свет: чек-лист сильного ответа
- [ ] Определение: кластер объектов-сущностей и VO с единым корнем,
  воспринимаемый как единое целое с точки зрения изменений данных
- [ ] Транзакционная граница: инварианты консистентны внутри агрегата после
  каждой транзакции; один агрегат = одна транзакция
- [ ] Доступ к дочерним объектам только через корень (корень контролирует
  инварианты)
- [ ] Ссылки на другие агрегаты — по идентификатору, не по объектной ссылке
- [ ] Выбор границ: по бизнес-инвариантам и потребностям консистентности,
  а не по структуре таблиц или удобству ORM
- [ ] Принцип «агрегат меньше — лучше» (consistency boundary, small aggregates)
- [ ] Пример: Заказ + строки заказа (один агрегат) vs Заказ + Клиент
  (разные агрегаты, ссылка по Id)
- [ ] Типовая ошибка: гигантский агрегат «на всю ER-модель» → блокировки,
  конфликты параллельных правок, тяжёлые загрузки; либо случайные границы
- Бонус: связь с eventual consistency между агрегатами через доменные события

## 🚩 Красные флаги
- «Агрегат = таблица/JOIN ради производительности БД» — подмена понятия
- «Доступ к детям напрямую — нормально» без оговорок — потеря инвариантов
- Перепутаны агрегат и репозиторий/контекст
- Определение есть, но практики выбора границ нет вообще (уровень 2)

## Образец сильного ответа
«Агрегат — граница консистентности: всё внутри сохраняется одной транзакцией,
инварианты защищает корень, наружу — только идентификаторы других агрегатов.
Границы провожу по вопросу "какие данные должны меняться атомарно, чтобы
инвариант не нарушался". Пример: в заказе строки заказа и итоговая сумма —
один агрегат, корень Order запрещает менять строки напрямую; клиент — другой
агрегат, в заказе живёт customerId. Типовая ошибка — слить заказ, клиента и
склад в один агрегат "для удобства": получаем блокировки и гонки там, где
достаточно ссылки по Id. Мелкие агрегаты предпочтительнее; между агрегатами —
eventual consistency через события».

## Шкала 0–4
- 0 — определение неверное или ответ не про DDD
- 1 — «кластер объектов с корнем» без понимания, зачем это нужно
- 2 — верное определение + транзакционная граница, но без практики выбора границ
- 3 — как «2» + правила выбора границ, корректный пример, типовая ошибка
- 4 — как «3» + нюансы: eventual consistency, связь с конкурентностью,
  антипаттерн «агрегат на всю модель», здравый вкус в примере
