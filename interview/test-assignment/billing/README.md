# Тестовое задание «биллинг LLM-токенов» — методика этапа 2

Этап 1 мерил знания «из базы» без харнеса (сырой промпт → ответ).
Этап 2 меряет **агентное программирование в минимальном харнесе**: модель
получает репозиторий с заданием и сама доводит его до сдачи. Харнес —
`pi` в стандартной поставке (read/bash/edit/write), без настроек и
подсказок.

## Состав каталога

| Путь | Что это |
|---|---|
| `skeleton/` | скелет для кандидата: Symfony 8 console (framework-bundle 8.0, http-kernel 7.4 LTS — чистая резолвиция без advisory-игноров), Doctrine ORM, миграции, docker compose PostgreSQL 17, PHPUnit, `TASK.md`, `AGENTS.md` (минимальная памятка — практики модель выбирает сама, чекер и ревью наблюдают), sample-фикстуры. Vendor в git не входит (один composer install), прогоны самодостаточны |
| `sample/` | те же sample-фикстуры отдельно (в скелет скопированы) |
| `fixtures/` | **скрытые** фикстуры чекера (кандидату не показывать) + `golden/` |
| `reference_calc.py` | референс арифметики: правила TASK.md на Decimal; генерирует `fixtures/golden/*` и числа worked example |
| `checker/check.py` | ярус 0 — функциональный чекер (docker, чистая БД, сравнение с golden) |
| `checker/metrics.py` | ярус 0.5 — phpstan/phpmd/phpcs/scc + AST-метрики coding-standard |
| `RUBRIC.md` | рубрика ревью (ярус 1) и описание всех ярусов |

Golden пересоздаются: `python3 reference_calc.py` (из этого каталога).
Менять формулы — только синхронно в TASK.md и reference_calc.py, затем
перегенерировать golden и перепрогнать чекер на референсном решении.

## Прогон кандидата

Скелет в git без `vendor/` (политика репо). Один раз подготовить его
(сеть нужна только здесь; в прогонах сеть не обязательна — vendor уже в копии):

```bash
cd interview/test-assignment/billing/skeleton && composer install
```

Каждый прогон — изолированная копия скелета **вне** дерева Models
(иначе pi увидит AGENTS.md рабочего репозитория):

```bash
RUN=/tmp/billing-<model>-run<N>
RESULTS=models/<модель>/test-assignment/run-XX && mkdir -p "$RESULTS"
cp -r interview/test-assignment/billing/skeleton "$RUN"
cd "$RUN" && cp .env.example .env
timeout 5400 pi -p --session-dir "$RESULTS/pi-session" --model <тег> \
  "Прочитай TASK.md в корне репозитория и выполни задание." 2>&1 | tee "$RESULTS/pi-run.log"
```

**На практике прогон делается раннером** — `runner_pi.py` (из каталога
billing/):

```bash
python3 runner_pi.py --model qwen3.8:27b-pi-100k \
  --results models/qwen3.8-27b-pi-100k/test-assignment/backend/run-01
```

Раннер **не использует глобальный конфиг pi** (`~/.pi/agent` не читается):
каждый прогон получает собственный `PI_CODING_AGENT_DIR` во временном
каталоге, `models.json` на единственную модель собирается на лету, адрес
сервера — только из env `OLLAMA_BASE_URL` (в git его нет). Уровень
размышлений `--thinking max` по умолчанию, контекст `--context 102400`.
Быстрая проверка сантехники: `--smoke`.

Сессия pi (JSONL — полный след размышлений и действий) пишется в
каталог результатов, вне копии репозитория: и `diff.patch` остаётся
чистым, и материал для анализа агентного поведения сохраняется.

- один запуск = один прогон; никаких follow-up'ов от нас — итерации
  (тесты, правки) модель делает сама в своём цикле;
- время: стартовый бюджет 90 минут на прогон (`timeout 5400`),
  калибруется пилотом;
- сеть не обязательна (vendor уже в скелете); AGENTS.md — памятка,
  не предписывает практик: выбор способа управления схемой, изменения
  каркаса и зависимости фиксируются чекером как наблюдения, «зачем» —
  оценивает судья по PR_DESCRIPTION;
- до серии убедиться, что pi умеет целиться в нужную модель
  (ollama-теги — через `--provider`/`--model`; на пилоте).

## Проверка и результаты

```bash
RESULTS=models/<модель>/test-assignment/run-XX && mkdir -p "$RESULTS"

# прогон pi: stdout — финальный ответ; сессия (JSONL с полным следом
# размышлений и действий: вызовы инструментов, промежуточные ответы,
# thinking) пишется в каталог результатов — вне копии репозитория,
# чтобы diff.patch оставался чистым
timeout 5400 pi -p --session-dir "$RESULTS/pi-session" --model <тег> \
  "Прочитай TASK.md в корне репозитория и выполни задание." 2>&1 | tee "$RESULTS/pi-run.log"

# ярус 0 — функциональные сценарии (docker, ~2 мин)
python3 interview/test-assignment/billing/checker/check.py --repo "$RUN" \
  > "$RESULTS/check.json"

# ярус 0.5 — метрики качества (сеть, ставит тула в одноразовую копию)
python3 interview/test-assignment/billing/checker/metrics.py --repo "$RUN" \
  > "$RESULTS/metrics.json"

# дифф для ревью
diff -ru interview/test-assignment/billing/skeleton "$RUN" > "$RESULTS/diff.patch"
```

Результаты складываются в `models/<модель>/test-assignment/<роль>/run-XX/`
(роль — как у собесов: `backend`, дальше — по мере появления заданий
других ролей):

- `solution/` — **само дерево решения** (весь репозиторий результата без
  vendor/var): код можно смотреть, ревьюить и показывать напрямую;
- `pi-session/` — сессия pi (JSONL): полный след размышлений и действий
  модели — основной материал для анализа агентного поведения; для
  удобного чтения: `pi --export pi-session/<file>.jsonl out.html`;
- `pi-run.log` — stdout прогона (финальный ответ, ход по времени);
- `diff.patch` — компактное «что изменилось против скелета»;
- `check.json`, `metrics.json` — ярусы 0/0.5;
- `scorecard.md` — ревью по `RUBRIC.md`, оси A/B + лист конвенций из
  `interview/conventions-probe.md`.

Сводные таблицы этапа — в `reports/` (по аналогии с этапом 1; формат
зафиксируем по данным пилота).

## Валидированность

- golden-выходы посчитаны независимо дважды: `reference_calc.py`
  (Python Decimal) и референсным PHP-решением на Symfony/Doctrine/bcmath
  (обе стороны сошлись байт-в-байт по всем трём отчётам, unrated-строке
  и выводу reprice);
- чекер прогнан на референсном решении: 11/11 обязательных, 2/2 бонусных;
  fallback-путь проверен на копии без миграций (method=schema_update,
  verdict pass); референсное решение в репо не попадает (только у судьи
  локально);
- `make db-up && make migrate` и worked example из TASK.md
  воспроизводятся на чистой БД.

## План прогона (после мержа)

1. **Пилот**: 3 модели разного калибра × 1 прогон — например
   `qwen3.8:27b`, `gemma4:31b-it-qat`, `gemma4:e2b`. Калибровка:
   хватает ли 90 минут, где модели застревают, различает ли чекер.
2. По разбросу пилота — решение о полной сетке (все 16 локальных +
   облачные) и числе прогонов (3 против 5: функциональная ось
   детерминирована чекером, 5 нужны только для устойчивости
   архитектурных решений).
3. Отчёт этапа — по аналогии с этапом 1: `models/*/test-assignment/`
   → сводный `REPORT.md` (доля чекера, метрики, оси A/B, дефолты
   конвенций).

## Секретность

`fixtures/` (скрытый набор и golden) в скелет не копируются и модели
не показываются; чекер и метрики запускает судья по завершении прогона.
Если скрытые фикстуры попадут в контекст модели — прогон считается
скомпрометированным.
