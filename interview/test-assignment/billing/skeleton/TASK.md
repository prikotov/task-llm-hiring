# Тестовое задание: учёт расходов на LLM-токены

Задание проверяет умение проектировать доменную логику и писать рабочий код
бэкенда. Мы ожидаем осмысленное предметное моделирование (DDD приветствуется),
аккуратную работу с деньгами и временем, и код, функциональный на базовом
уровне. Ориентир по времени — 4–6 часов; лучше меньше, но работающее, чем
больше и неработающее.

Всё выполняется офлайн: зависимости уже в `vendor/`, сеть не нужна
(и не доступна). Как поднять окружение — `README.md` в корне.

## Контекст

Сервис перепродаёт доступ к LLM: он платит провайдерам за токены и должен
знать свои расходы в разрезе пользователей и моделей. Данные приходят двумя
потоками:

- **история цен** — справочник: провайдеры, их модели и цены, действовавшие
  с определённых моментов времени;
- **события использования** — журнал фактических запросов к моделям
  (сколько каких токенов израсходовано), поставляемый провайдерами.

Нужно консольное приложение, которое принимает эти данные и считает расходы.
Реальность вносит тонкости — все они зафиксированы в требованиях ниже:

- у провайдеров **разные схемы тарификации** (per-token с разбивкой по видам
  токенов у одного, единая цена за любой токен у другого);
- **цены меняются во времени**: событие тарифицируется ценой, действовавшей
  в его момент, а не текущей;
- у одного провайдера есть **оф-пиковая скидка** в фиксированном окне UTC;
- провайдеры **присылают дубли** событий — двойного списания быть не должно;
- деньги считаются только **точной десятичной арифметикой** (float для
  денег запрещён).

## Входные данные

### История цен — JSON-файл

Пример (сокращённый; полный рабочий пример — `fixtures/prices.json`):

```json
{
  "providers": [
    {
      "code": "prism",
      "name": "Prism AI",
      "off_peak": {
        "window_start": "16:30",
        "window_end": "00:30",
        "multiplier": "0.5"
      }
    },
    { "code": "sfera", "name": "Sfera Cloud", "off_peak": null }
  ],
  "models": [
    { "provider": "prism", "code": "lumen-8" },
    { "provider": "sfera", "code": "gyro-pro" }
  ],
  "prices": [
    {
      "provider": "prism",
      "model": "lumen-8",
      "valid_from": "2026-08-01T00:00:00Z",
      "currency": "USD",
      "unit": "per_1m_tokens",
      "rates": {
        "input": "3.000000",
        "output": "12.000000",
        "cache_read": "0.300000",
        "cache_write": "3.750000"
      }
    },
    {
      "provider": "sfera",
      "model": "gyro-pro",
      "valid_from": "2026-08-01T00:00:00Z",
      "currency": "USD",
      "unit": "per_1m_tokens_unified",
      "rates": { "any": "2.400000" }
    }
  ]
}
```

Пояснения:

- `unit` задаёт схему тарификации:
  - `per_1m_tokens` — цена за 1 000 000 токенов отдельно для каждого вида:
    `input`, `output`, `cache_read`, `cache_write`;
  - `per_1m_tokens_unified` — единая цена за 1 000 000 токенов любого вида.
- `off_peak` — окно скидки провайдера по времени суток UTC:
  `window_start` включительно, `window_end` исключительно; окно может
  переходить через полночь (`16:30`–`00:30`); `multiplier` — множитель
  стоимости события, попавшего в окно. `null` — скидки нет.
- у одной модели может быть несколько строк цен с разными `valid_from`;
- `rates` — десятичные строки (не числа JSON), 6 знаков после точки;
- `currency` везде `USD` (поле зарезервировано на будущее).

### События использования — JSONL-файл

Одно событие на строку:

```json
{"provider": "prism", "provider_request_id": "e1", "model": "lumen-8", "user": "u-alice", "ts": "2026-09-15T11:00:00Z", "tokens_input": 1200000, "tokens_output": 800000, "tokens_cache_read": 2500000, "tokens_cache_write": 83333}
```

- `ts` — момент запроса, ISO-8601, всегда UTC (`Z`);
- `user` — идентификатор пользователя (строка), домена пользователей нет;
- `provider_request_id` — идентификатор запроса **со стороны провайдера**;
  вместе с `provider` образует естественный ключ события;
- количество токенов — целые ≥ 0, любые могут быть нулевыми (в т.ч. все).

## Правила тарификации

1. **Выбор цены.** Событие тарифицируется строкой цен своей модели с
   наибольшим `valid_from` ≤ `ts` события (`valid_from` включительно).
   Если такой строки нет — событие **unrated** (см. п. 7).
2. **Схема `per_1m_tokens`** — сумма по видам токенов:
   `cost = Σ tokens_вид × rate_вид / 1 000 000`.
   **Схема `per_1m_tokens_unified`**:
   `cost = (tokens_input + tokens_output + tokens_cache_read + tokens_cache_write) × rate_any / 1 000 000`.
3. **Оф-пик.** Если время суток `ts` (UTC) попадает в окно `[window_start, window_end)`
   провайдера события — стоимость всего события умножается на `multiplier`.
   Окно задаётся на уровне провайдера и действует для всех его моделей;
   отсутствие `off_peak` означает отсутствие скидки.
4. **Точность вычислений.** Все промежуточные вычисления — без округления
   (десятичная арифметика с запасом точности, например bcmath с масштабом
   ≥ 16). Округление ровно одно: итоговая стоимость **события** округляется
   до 6 знаков после точки по правилу HALF_UP (2.5 → 3). Суммы отчёта —
   сумма уже округлённых стоимостей событий, без повторного округления
   слагаемых. Тип float для денег использовать запрещено.
5. **Идемпотентность приёма.** События дедуплицируются по ключу
   `(provider, provider_request_id)`: повторная доставка уже известного
   события целиком игнорируется (никаких обновлений, никаких доначислений).
   Одинаковые `provider_request_id` у разных провайдеров — это разные
   события.
6. **Период отчёта.** `--from` включительно, `--to` исключительно.
7. **Unrated-события.** Не считаются ошибкой: не тарифицируются, в отчёт
   не попадают. Каждый запуск тарификации повторяет попытку для всех
   ещё не рассчитанных событий (цены могли подтянуться позже).

## Команды

Все команды — через `bin/console`. Вывод отчёта — строго в stdout,
служебные сообщения — в stderr.

### `app:prices:import <file>`

Загружает провайдеров, модели и строки цен. Идемпотентный upsert:
провайдеры — по `code`; модели — по `(provider, code)`; строки цен — по
`(provider, model, valid_from)` (повторная загрузка тех же сумм — не
изменяет данных). Код выхода 0. Некорректный JSON — ошибка, код 1.

### `app:usage:import <file>`

Загружает события по правилу п. 5. Код выхода 0 даже если все строки —
дубли. Некорректная строка JSONL — ошибка, код 1.

### `app:billing:rate`

Тарифицирует все ещё не рассчитанные события (включая повторные попытки
unrated). В stdout — сводка одной строкой: `RATED=<n> UNRATED=<m>`, где
n и m — количества событий, рассчитанных и оставшихся unrated **в этом
запуске**. Для каждого unrated-события этого запуска — строка в stderr:
`UNRATED <provider>/<provider_request_id> <ts> no_price`. Код выхода 0.

### `app:billing:report [--from=<iso>] [--to=<iso>]`

CSV в stdout (кодировка UTF-8, разделитель `,`, перевод строки `\n`):

```
user,model,tokens_input,tokens_output,tokens_cache_read,tokens_cache_write,cost_usd
u-alice,prism/lumen-8,1200000,800000,2500000,83333,14.262499
u-alice,sfera/gyro-pro,3000000,500000,0,0,8.400000
u-bob,prism/lumen-8,2000000,1000000,0,0,11.000000
TOTAL,,6200000,2300000,2500000,83333,33.662499
```

Требования к формату:

- первая строка — заголовок, точно как в примере;
- строки данных — по одной на пару (user, model), отсортированные по
  `user`, затем по `model` (лексикографически, по возрастанию);
- `model` — `<provider>/<code>` (например `prism/lumen-8`);
- количества токенов — суммы по событиям группы, целые без разделителей;
- `cost_usd` — сумма стоимостей событий группы, ровно 6 знаков после
  точки;
- последняя строка — `TOTAL` с пустым полем `model` и суммами по отчёту;
- unrated-события в отчёт не попадают никогда.

`--from`/`--to` — ISO-8601 (UTC), применяются к `ts` событий по п. 6;
без опций отчёт покрывает все события.

## Пример расчёта

Файлы этого примера лежат в `fixtures/` (`prices.json`, `usage.jsonl`) —
воспроизведите его сами. Три события:

| id | событие | разбор |
|----|---------|--------|
| e1 | prism/lumen-8, alice, `2026-09-15T11:00:00Z`, in 1 200 000, out 800 000, cr 2 500 000, cw 83 333 | цена — строка с 2026-08-01 (смена цены в 12:00 ещё не наступила); 11:00 — пик. Точная стоимость: `1.2M×3 + 0.8M×12 + 2.5M×0.3 + 83333×3.75/1M = 3.6 + 9.6 + 0.75 + 0.31249875 = 14.26249875` → округление события → **14.262499** |
| e2 | prism/lumen-8, bob, `2026-09-15T12:00:00Z`, in 2 000 000, out 1 000 000 | `12:00:00` — момент смены цены, действует новая строка (`valid_from` включительно): `2M×1.5 + 1M×8 = 11.000000` |
| e3 | sfera/gyro-pro, alice, `2026-09-20T17:10:00Z`, in 3 000 000, out 500 000 | unified: `3.5M×2.4 = 8.400000`; у sfera нет оф-пик — время суток не важно |

Отчёт за сентябрь (`--from 2026-09-01T00:00:00Z --to 2026-10-01T00:00:00Z`)
должен выдать в точности:

```
user,model,tokens_input,tokens_output,tokens_cache_read,tokens_cache_write,cost_usd
u-alice,prism/lumen-8,1200000,800000,2500000,83333,14.262499
u-alice,sfera/gyro-pro,3000000,500000,0,0,8.400000
u-bob,prism/lumen-8,2000000,1000000,0,0,11.000000
TOTAL,,6200000,2300000,2500000,83333,33.662499
```

## Требования

- PHP 8.3+, Symfony, PostgreSQL 17, Doctrine ORM. Каркас приложения уже
  настроен (`bin/console` работает, докер- compose для PostgreSQL — в
  `docker-compose.yml`, `Makefile` — типовые операции).
- Схема БД — только через Doctrine-миграции: на пустой базе
  `doctrine:database:create` + `doctrine:migrations:migrate` должны давать
  рабочую схему. Никаких `doctrine:schema:update` в решении.
- Архитектура, разбиение на слои/модули, именование — на ваше усмотрение
  (это предмет оценки). Тесты (в `vendor/` есть PHPUnit) — плюс, но не
  обязательны.
- Не изменять: `TASK.md`, `fixtures/`, `composer.json` / `composer.lock`,
  `docker-compose.yml`, `Makefile`, `AGENTS.md`. Если для решения объективно
  нужно — не меняйте, а зафиксируйте это как допущение в `PR_DESCRIPTION.md`.
- Неоговорённые детали — принимайте решения самостоятельно и фиксируйте
  допущения там же.

## Бонус (по желанию, оценивается отдельно)

**Ретро-коррекция цены.** Провайдер сообщил, что цена, действовавшая с
некоторого `valid_from`, была неверной, и присылает исправленную строку
(файл того же формата). Уже рассчитанные события трогать молча нельзя —
расходы показаны пользователю. Реализуйте команду:

```
bin/console app:billing:reprice <file>
```

Она применяет исправленные строки (upsert по `(provider, model, valid_from)`,
суммы заменяются), пересчитывает события, тарифицировавшиеся заменёнными
строками, и печатает в stdout ровно две строки:

```
REPRICED_EVENTS=<n>
REPRICE_DELTA_USD=<x.xxxxxx>
```

`n` — число пересчитанных событий, дельта — новая минус старая сумма их
стоимостей, 6 знаков. Механизм пересчёта (перезапись с журналом
корректировок, компенсирующие записи и т.п.) — на ваше усмотрение; итоговый
`app:billing:report` после reprice должен показывать пересчитанные суммы
без задвоений.

## Приёмка (самопроверка)

1. `make db-up && make migrate` — чистая база поднимается, миграции
   накатываются.
2. `app:prices:import fixtures/prices.json && app:usage:import fixtures/usage.jsonl && app:billing:rate` — без ошибок.
3. `app:billing:report --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z` — вывод байт-в-байт совпадает с примером выше.
4. Повторный импорт тех же файлов + rate + report — результат не меняется.
