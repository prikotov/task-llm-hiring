# Датчик конвенций: выявление врождённых предпочтений моделей

## Цель

Модели приходят «из коробки» с собственными дефолтами: как назвать класс,
где поставить flush, как оформить коммит. Сопоставление этих дефолтов с
конвенциями TasK отвечает на два вопроса:

1. **Что в конвенции можно не писать** — все модели и так делают одинаково
   (это «общее на базовом уровне»).
2. **Что писать обязательно** — модели расходятся между собой или систематически
   делают не то, что нужно проекту (правила обязательны, и их надо держать
   в контексте агента).

Это ось «возможности и риски» принципа интервью: возможности — совпадающие
дефолты, риски — систематические расхождения.

## Принцип

**Наблюдаем действия, не декларации.** Вопрос «какие у тебя предпочтения
naming'а?» даёт текст, не поведение. Модель раскрывает дефолты, когда
пишет код по требованиям, не зная конвенций проекта.

## Датчики

| # | Датчик | Что раскрывает | Статус |
|---|---|---|---|
| 1 | **Тестовое задание** (`test-assignment/`) — полный доменный код по требованиям | Главный датчик: naming, слои, иммутабельность, границы транзакций, исключения, типизация, тесты | главный |
| 2 | **Мини-код-ревью** (backend Q27, Q28 и аналоги других ролей) | Рефакторинг = целевое состояние модели: как она переименует, куда вынесет, где хочет flush | встроен |
| 3 | **Код в ответах теоретических вопросов** (Q01, Q04, Q09, Q13 backend) | Спонтанные привычки в малом коде | встроен |
| 4 | **Процессные датчики** в тестовом: написать commit message и описание PR к сделанному | Формат коммитов/PR без подсказки | добавить при адаптации тестового |

## Лист наблюдений

Заполняется судьёй по каждому датчику (одна строка = одно наблюдение
на модель). Формат значения: что сделала модель + цитата-доказательство.

| # | Точка наблюдения | Что фиксируем |
|---|---|---|
| 1 | Naming сущностей | суффикс: `Model` / `Entity` / без суффикса |
| 2 | Naming Value Object | `Vo` / `Value` / доменное имя без суффикса |
| 3 | Naming DTO | `Dto` / `DTO` / `Request`/`Response` / без суффикса |
| 4 | Naming интерфейсов | суффикс `Interface` / префикс `I` / без пометки |
| 5 | `declare(strict_types=1)` | ставит ли сам |
| 6 | `final` | помечает ли классы final |
| 7 | Иммутабельность | `readonly` у VO/DTO/свойств — по своей инициативе? |
| 8 | Валидация домена | в конструкторе/методах домена / внешний validator / нигде |
| 9 | Граница транзакции | кто вызывает flush: handler / репозиторий / сущность; persist+flush вместе |
| 10 | Слои | делит ли код на слои сам; куда кладёт Doctrine |
| 11 | Интерфейсы | выносит ли контракт без подсказки |
| 12 | Исключения | свои иерархии? оборачивает ли чужие? имена исключений |
| 13 | Типизация | типы свойств/методов/аргументов; nullable; массивы vs коллекции |
| 14 | Именование методов | глаголы; get/find/save/create; чёткость |
| 15 | PHPDoc и комментарии | пишет ли сам; дублирует ли очевидное |
| 16 | Тесты | пишет ли без требования; стиль имён тестов; моки |
| 17 | Commit message | формат: conventional? с scope? язык, регистр, точка |
| 18 | Описание PR | структура: что/зачем/как проверено; чек-листы |
| 19 | Обработка ошибок | try/catch дисциплина; что логирует; возврат ошибок |
| 20 | Уведомления/побочные эффекты | синхронно в коде / события / очередь — что выбирает без подсказки |

## Интерпретация (после прогона датчиков на всех моделях)

Для каждой строки листа:

- **Все модели делают одинаково и это совпадает с проектом** → в конвенции
  можно не писать (или одна строка «по умолчанию»).
- **Все делают одинаково, но не так, как нужно проекту** → правило писать
  обязательно + проверять валидатором (модели «стайерно» нарушат).
- **Модели расходятся между собой** → правило писать обязательно и держать
  в контексте агента; в собесе-агенте — контроль соблюдения.

Результат: отчёт «дефолты моделей vs конвенции TasK» (таблица по всем
моделям × лист наблюдений) — вход для доработки конвенций проекта.
