## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

Выберу возможности, которые реально помогают писать надёжный код: типизацию, неизменяемость, явное моделирование состояний и выразительную обработку ошибок.

**1. Union и nullable-типы, `mixed`, строгая типизация**

Типы на границах функций позволяют ловить ошибки ещё до выполнения логики.

```php
declare(strict_types=1);

function findUserName(int $id): ?string
{
    // null означает «пользователь не найден», а не «ошибка»
    return $id === 1 ? 'Alice' : null;
}

function formatId(int|string $id): string
{
    return (string) $id;
}
```

**2. Конструкторное продвижение свойств (PHP 8.0)**

Сокращает шаблонный код и делает зависимости явными.

```php
final class OrderService
{
    public function __construct(
        private PaymentGateway $payments,
        private OrderRepository $orders,
    ) {}
}
```

**3. `readonly`-свойства (PHP 8.1)**

Неизменяемые объекты-значения защищают инварианты и упрощают рассуждения о коде.

```php
final class Money
{
    public function __construct(
        public readonly int $amount,
        public readonly string $currency,
    ) {}

    public function add(self $other): self
    {
        if ($this->currency !== $other->currency) {
            throw new InvalidArgumentException('Currency mismatch');
        }
        return new self($this->amount + $other->amount, $this->currency);
    }
}

$price = new Money(100, 'RUB');
// $price->amount = 200; // Error: Cannot modify readonly property
```

**4. Enum (PHP 8.1)**

Заменяет «магические строки» и константы, а также позволяет описывать поведение.

```php
enum OrderStatus: string
{
    case Pending = 'pending';
    case Paid = 'paid';
    case Cancelled = 'cancelled';

    public function isFinal(): bool
    {
        return match ($this) {
            self::Paid, self::Cancelled => true,
            self::Pending => false,
        };
    }
}

$status = OrderStatus::from('paid');
var_dump($status->isFinal()); // bool(true)
```

**5. `match` (PHP 8.0)**

В отличие от `switch`, использует строгое сравнение, не проваливается между ветками и выбрасывает исключение при отсутствии подходящей ветки.

```php
$message = match ($status) {
    OrderStatus::Pending => 'Ожидает оплаты',
    OrderStatus::Paid => 'Оплачен',
    OrderStatus::Cancelled => 'Отменён',
};
```

**6. Named arguments (PHP 8.0)**

Делают вызовы с большим количеством опциональных параметров читаемыми и защищают от перепутанного порядка.

```php
$response = new JsonResponse(
    data: $payload,
    status: 201,
    headers: ['X-Request-Id' => $requestId],
);
```

**7. Nullsafe-оператор (PHP 8.0)**

Убирает вложенные проверки на `null`.

```php
$city = $user?->getAddress()?->getCity()?->getName();
```

**8. First-class callable syntax (PHP 8.1)**

```php
$normalize = strtolower(...);
$names = array_map($normalize, ['ALICE', 'BOB']);
```

**9. Атрибуты (PHP 8.0)**

Заменяют docblock-аннотации типизированными метаданными, которые проверяются компилятором и читаются через Reflection. В Symfony и Doctrine используются повсеместно:

```php
#[ORM\Entity]
#[ORM\Table(name: 'orders')]
class Order
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private int $id;
}
```

**10. Типы `never`, `static` в возвращаемом значении, интерсекции (PHP 8.1)**

```php
function fail(string $message): never
{
    throw new RuntimeException($message);
}

function process(Countable&Traversable $items): void
{
    foreach ($items as $item) {
        // ...
    }
}
```

**Что важно на практике**

Самая большая польза достигается сочетанием: строгие типы, `readonly`-объекты-значения, enum для состояний и `match` для логики. Это уменьшает количество мест, где можно получить неконсистентное состояние, и делает код предсказуемым.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

PHP с версии 7 имеет скалярные типы в объявлениях параметров и возвращаемых значений, а с 7.4 и 8.x добавились типизированные свойства, union-типы и другие конструкции. При этом язык остаётся динамическим, и многие поведения унаследованы от старых версий.

## 1. Два режима: coercive и strict

По умолчанию PHP работает в **coercive-режиме** (приведение скаляров). Если передать значение не того скалярного типа, интерпретатор попытается его привести:

```php
function add(int $a, int $b): int
{
    return $a + $b;
}

var_dump(add("5", "3"));   // int(8): строки приведены к int
var_dump(add(5.0, true));  // int(6): float без дробной части и bool тоже приводятся
var_dump(add("abc", 1));   // TypeError: "abc" нельзя привести к int
```

С `declare(strict_types=1);` приведение скаляров запрещено:

```php
declare(strict_types=1);

add("5", "3"); // TypeError
add(5.0, 1);   // TypeError: float нельзя передать в int
```

Важные детали:

- **Директива действует на вызовы, сделанные из файла, где она объявлена.** Она определяет, как проверяется вызов, а не то, как объявлена функция. Если файл A со `strict_types` вызывает функцию из файла B без директивы, проверка всё равно строгая, потому что строгость задаёт вызывающий код.
- **Разрешено расширение int до float.** `function f(float $x)` принимает `f(5)`, и в `$x` окажется `5.0`.
- **Строгость распространяется и на возвращаемые значения** в файле, где объявлена функция.
- **Встроенные функции тоже подчиняются `strict_types`** для вызовов из этого файла.
- **Директиву нужно ставить в каждом файле**, она не наследуется. Это частая причина «не работает»: файл без неё молча принимает приведения.

## 2. Приведения в тех местах, где вы их не ждёте

Часть ловушек связана с явными приведениями и неявными преобразованиями:

```php
var_dump((int) "12abc");  // int(12): мусор отбрасывается без ошибки
var_dump((int) null);     // int(0)
var_dump((int) 3.99);     // int(3): усечение, а не округление
var_dump((bool) "0");     // bool(false)
var_dump((bool) "0.0");   // bool(true)
var_dump((bool) []);      // bool(false)
var_dump(empty("0"));     // bool(true)
```

`(bool) "0"` и `empty("0")` возвращают `false`/`true`, что часто удивляет при проверке пользовательского ввода.

## 3. Ловушки сравнения

Нестрогое сравнение `==` использует приведение типов, и результаты бывают неочевидными:

```php
var_dump("1" == "01");     // true: обе строки числовые
var_dump("10" == "1e1");   // true: научная нотация
var_dump(null == false);   // true
var_dump([] == false);     // true
var_dump(0 == "a");        // false в PHP 8 (раньше было true)

in_array("abc", [0]);      // true в PHP < 8, нестрогое сравнение по умолчанию
```

Правило: всегда используйте `===` и `!==`. Для `in_array` и `array_search` передавайте третий аргумент `true`.

Отдельно: `switch` сравнивает нестрого, а `match` строго. В современном коде предпочитайте `match`.

## 4. Ключи массивов

Ключи тоже приводятся:

```php
$a = [];
$a["1"] = 'a';   // ключ станет int 1
$a["01"] = 'b';  // ключ останется строкой "01"
$a[true] = 'c';  // ключ 1, перезапишет 'a'
$a[1.7] = 'd';   // ключ 1, с PHP 8.1 выдаётся deprecation
```

Это ломает код, который считает, что ключ всегда имеет один тип, например при работе с ID из HTTP-запросов.

## 5. Арифметика и числа

```php
var_dump(PHP_INT_MAX + 1);       // float(9.2233720368547758E+18): переполнение молча переходит во float
var_dump(0.1 + 0.2 == 0.3);      // false
var_dump(10 / 4);                // float(2.5)
var_dump(10 % 0);                // DivisionByZeroError
var_dump(intdiv(10, 4));         // int(2)
```

Переполнение int молча превращается во float, и если ожидается int (например, ID или сумма в копейках), это тихая порча данных. Для денег используйте целые числа в минимальных единицах или библиотеку decimal, а не float.

Также `json_decode` превращает слишком большие целые числа во float, что стоит учитывать при работе с 64-битными ID из внешних API.

## 6. Где типизация спасает

**Ловим ошибку на границе, а не глубоко в логике.**

```php
declare(strict_types=1);

final class Order
{
    public function __construct(
        public readonly int $id,
        public readonly int $amountInCents,
    ) {}
}

// Ошибка будет сразу на вызове, а не при подсчёте итогов через три слоя
new Order("42", 1000); // TypeError
```

**Union-типы сохраняют точный тип.** В `int|string` значение `"5"` остаётся строкой, потому что совпадение точное и приведение не нужно:

```php
function normalizeId(int|string $id): string
{
    return (string) $id;
}
```

**`readonly` и типизированные свойства закрывают целые классы багов:**

```php
class Invoice
{
    private int $total; // до инициализации обращение даст Error, а не null
}

$i = new Invoice();
// echo $i->total; // Error: must not be accessed before initialization
```

**`never` и `void` задают контракт явно:**

```php
function fail(string $msg): never
{
    throw new RuntimeException($msg);
}
```

## 7. Где типизация удивляет

**Implicit nullable.** Параметр `int $x = null` неявно становится `?int`. Это работает, но создаёт путаницу. Пишите явно `?int $x = null`. (В PHP 8.4 неявный nullable помечен как устаревший.)

**`int|float` и строки.** Для `"1.5"` при `int|float` выберется `float`, а для `"15"` выберется `int`. Тип результата зависит от содержимого строки.

**Доктрина и гидрация.** Doctrine и драйверы БД возвращают значения, которые могут не совпадать с ожидаемым PHP-типом. Например, `decimal` часто приходит строкой, а результаты агрегатов (`SUM`, `COUNT` в зависимости от драйвера) могут быть строками. Если объявить `int $total`, в `strict_types` получите TypeError, а без него молчаливое приведение. Нужно явно приводить или использовать `DTO` с правильными типами.

**Типы в `iterable`.** До PHP 8.2 `iterable` включал массивы и `Traversable`, в 8.2 его разложили на `array|Traversable`. Правила проверки зависят от версии.

**`mixed` не равно «всё что угодно без проверки».** Это верхний тип, который принимает всё, но проверки внутри функции всё равно нужны.

**Разные значения `null` для свойств.** Типизированное свойство `?string $x` без значения по умолчанию всё равно нужно инициализировать явно, иначе доступ к нему до присваивания даёт Error, а не `null`.

## 8. Практические рекомендации

- Включайте `declare(strict_types=1);` во всех файлах проекта и проверяйте это линтером или PHP-CS-Fixer.
- Типизируйте всё: параметры, возвращаемые значения, свойства. Используйте `readonly` для объектов-значений.
- Вместо `==` пишите `===`, а в `in_array` и `array_search` передавайте `true`.
- Границы системы (HTTP, БД, внешние API, JSON) приводите к типам явно и в одном месте, например в DTO или мапперах.
- Для денег и больших целых чисел не используйте float.
- Включайте максимальный уровень ошибок и обрабатывайте предупреждения как исключения в тестах.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

Важно прояснить, что я отвечаю как ИИ-ассистент, поэтому «как я проектирую» означает, какие подходы я считаю правильными и как бы их применял. Ниже — рекомендации, которые опираются на широко принятые практики PHP и Symfony.

## 1. Исключение как часть контракта

Исключение — это такой же элемент контракта, как возвращаемый тип. Если метод может не выполнить свою задачу, это нужно отразить в его документации (`@throws`) и в именовании. Разделяю два типа ситуаций:

- **Ошибка программиста** (нарушение предусловия, невалидные аргументы, баг): это `LogicException` и его потомки. Их обычно не перехватывают, их исправляют в коде.
- **Ожидаемый отказ среды или бизнес-правила** (нет пользователя, недостаточно средств, таймаут API): это `RuntimeException` или собственные доменные исключения. Их можно и нужно обрабатывать.

Важно: `null` или `false` в качестве «ошибки» — тоже контракт. Выбирайте один стиль внутри слоя. Если метод ищет сущность, `find` возвращает `null`, а `get` выбрасывает исключение; это читается лучше, чем смешение.

## 2. Своя иерархия исключений

Иерархия нужна, чтобы вызывающий код ловил нужный уровень, не зная внутренностей:

```php
namespace App\Shared\Exception;

// Общий корень для всех исключений приложения
abstract class ApplicationException extends \RuntimeException {}

// Доменные ошибки: нарушение бизнес-правил
abstract class DomainException extends ApplicationException {}

final class InsufficientFundsException extends DomainException
{
    public function __construct(
        public readonly int $requested,
        public readonly int $available,
    ) {
        parent::__construct(sprintf(
            'Requested %d, available %d', $requested, $available
        ));
    }
}

// Инфраструктурные ошибки: внешние системы
abstract class InfrastructureException extends ApplicationException {}

final class PaymentGatewayUnavailable extends InfrastructureException {}
```

Замечания:

- Не называйте свой класс `DomainException` без необходимости: в PHP уже есть одноимённый класс из SPL. Используйте namespace или префикс.
- Типизированные поля в исключении (`requested`, `available`) лучше, чем разбор сообщения.
- Иерархия должна отражать то, что будет ловить вызывающий код, а не все возможные причины.

## 3. Оборачивание чужих исключений

Исключения внешних библиотек (Doctrine, HTTP-клиент, драйвер БД) не должны утекать наружу слоя. Оборачивайте их на границе и сохраняйте цепочку через `previous`:

```php
final class OrderRepository
{
    public function save(Order $order): void
    {
        try {
            $this->em->persist($order);
            $this->em->flush();
        } catch (\Doctrine\DBAL\Exception\UniqueConstraintViolationException $e) {
            throw new OrderAlreadyExists($order->getId(), previous: $e);
        } catch (\Doctrine\DBAL\Exception $e) {
            throw new PersistenceFailure('Не удалось сохранить заказ', previous: $e);
        }
    }
}
```

Правила:

- Перехватывайте конкретные типы, а не `\Throwable` или `\Exception` целиком.
- Всегда передавайте `previous`, чтобы не терять стек исходной ошибки.
- Перевод в доменное исключение делайте там, где известен смысл операции.

## 4. Что считать контрактом метода

Контракт описывает:

- какие исключения метод выбрасывает в штатных и нештатных ситуациях (`@throws` и имена классов);
- какие состояния объекта остаются после ошибки (атомарность: либо операция выполнена целиком, либо состояние не изменилось);
- что гарантируется при ошибке: не происходит ли частичной записи в БД, не остаются ли открытые ресурсы.

Пример с транзакцией:

```php
/**
 * @throws InsufficientFundsException если на счёте недостаточно средств
 * @throws PersistenceFailure при ошибке записи; транзакция откатывается
 */
public function withdraw(AccountId $id, Money $amount): void
{
    $this->tx->run(function () use ($id, $amount): void {
        $account = $this->accounts->get($id);
        $account->withdraw($amount); // может выбросить InsufficientFundsException
        $this->accounts->save($account);
    });
}
```

## 5. Антипаттерны

- **Проглатывание исключений:** `catch (\Throwable) {}` без логирования и реакции. Ошибка исчезает, и диагностировать её невозможно.
- **Слишком широкий catch:** `catch (\Exception $e)` в середине бизнес-логики маскирует баги программиста.
- **Исключения для управления потоком:** использование исключения там, где достаточно `null` или результата-объекта, например для «пользователь не найден» при обычном поиске.
- **Потеря цепочки:** `throw new X($e->getMessage())` без `previous`. Исходный стек теряется.
- **Утечка инфраструктуры:** `PDOException` или `Doctrine\...` долетают до контроллера и до ответа API.
- **Сообщение без данных:** `throw new Exception('Error')`. Нужны идентификаторы и контекст, но без чувствительных данных.
- **Разбор сообщения вместо типа:** `if (str_contains($e->getMessage(), 'duplicate'))`. Сообщения меняются, типы стабильны.
- **Исключения в конструкторе, оставляющие объект в полуинициализированном состоянии,** и `finally`, который подавляет исходное исключение через `return`.
- **Смешение `Error` и `Exception`:** ловить `\Error` (ошибки программы вроде `TypeError`) как обычную бизнес-ошибку.
- **Логирование и повторный выброс на каждом слое:** одна ошибка попадает в лог пять раз. Логируйте один раз, на границе приложения.

## 6. Обработка на границе

Централизуйте преобразование в HTTP-ответ, например через `kernel.exception` listener в Symfony. Доменные исключения маппятся в коды 404, 409, 422, а неизвестные превращаются в 500 с общим сообщением. Внутренние детали, стек и SQL в ответ не попадают; полная информация уходит в лог с идентификатором запроса.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

Важно напомнить, что у меня нет личного опыта работы с реальными кодовыми базами, поэтому «по моему опыту» означает, что я опираюсь на типичные паттерны, которые описаны в литературе и встречаются в обзорах и публичных проектах. По этим источникам чаще всего нарушается **принцип единственной ответственности (SRP)**.

## Почему именно SRP

- Класс растёт постепенно: сначала один метод, потом «ещё одна небольшая проверка», и через полгода сервис отвечает за валидацию, расчёт, запись в БД, отправку писем и формирование ответа.
- Нарушение незаметно при код-ревью, потому что каждое изменение выглядит разумным по отдельности.
- Последствия проявляются при тестировании: для проверки одной логики приходится поднимать всю инфраструктуру и мокать десять зависимостей.

## Типовой пример нарушения

```php
final class OrderService
{
    public function __construct(
        private \PDO $pdo,
        private \Swift_Mailer $mailer,
    ) {}

    public function placeOrder(array $data): int
    {
        // Валидация
        if (empty($data['email']) || !filter_var($data['email'], FILTER_VALIDATE_EMAIL)) {
            throw new \InvalidArgumentException('Invalid email');
        }
        if (empty($data['items'])) {
            throw new \InvalidArgumentException('Empty order');
        }

        // Расчёт стоимости
        $total = 0;
        foreach ($data['items'] as $item) {
            $total += $item['price'] * $item['qty'];
        }
        if (($data['promo'] ?? null) === 'SALE10') {
            $total = (int) round($total * 0.9);
        }

        // Сохранение
        $stmt = $this->pdo->prepare('INSERT INTO orders (email, total) VALUES (?, ?)');
        $stmt->execute([$data['email'], $total]);
        $orderId = (int) $this->pdo->lastInsertId();

        // Уведомление
        $message = (new \Swift_Message('Заказ #' . $orderId))
            ->setTo($data['email'])
            ->setBody("Сумма: $total");
        $this->mailer->send($message);

        return $orderId;
    }
}
```

Класс валидирует, считает, сохраняет в БД, отправляет письмо и знает формат входных данных. Изменение любой из этих частей требует правки одного и того же класса.

## Рефакторинг

Разделяем ответственности и связываем части через интерфейсы и объекты-значения:

```php
final readonly class OrderRequest
{
    /** @param list<OrderItem> $items */
    public function __construct(
        public string $email,
        public array $items,
        public ?string $promoCode = null,
    ) {}
}

final class OrderPricer
{
    public function price(OrderRequest $request): Money
    {
        $total = array_reduce(
            $request->items,
            fn (Money $sum, OrderItem $item): Money => $sum->add($item->lineTotal()),
            Money::zero('RUB'),
        );

        return $request->promoCode === 'SALE10'
            ? $total->multiply(0.9)
            : $total;
    }
}

final class OrderRepository
{
    public function __construct(private \PDO $pdo) {}

    public function save(Order $order): int
    {
        $stmt = $this->pdo->prepare('INSERT INTO orders (email, total) VALUES (?, ?)');
        $stmt->execute([$order->email, $order->total->amount]);

        return (int) $this->pdo->lastInsertId();
    }
}

final class OrderConfirmationSender
{
    public function __construct(private MailerInterface $mailer) {}

    public function send(Order $order): void
    {
        $this->mailer->send(new OrderConfirmationEmail($order));
    }
}

final class OrderService
{
    public function __construct(
        private OrderValidator $validator,
        private OrderPricer $pricer,
        private OrderRepository $orders,
        private OrderConfirmationSender $confirmation,
    ) {}

    public function placeOrder(OrderRequest $request): int
    {
        $this->validator->validate($request);

        $order = Order::create($request->email, $this->pricer->price($request));
        $orderId = $this->orders->save($order);

        $this->confirmation->send($order);

        return $orderId;
    }
}
```

## Что изменилось

- **Валидация** вынесена в `OrderValidator`, её можно тестировать без БД и почты.
- **Расчёт** отделён в `OrderPricer`: правила скидок меняются независимо от хранения.
- **Хранение** и **отправка** заменяемы: в тестах подставляются заглушки, а `OrderService` теперь только координирует шаги.
- **Вход** типизирован через `OrderRequest`, поэтому `array $data` больше не нужен в сервисе.

## Оговорки

- SRP не означает «по классу на каждую строку». Дробление без реальной причины для изменения даёт лишние абстракции. Ориентир: класс меняется по одной причине, и эта причина бизнес-смысловая или инфраструктурная.
- Часто следующим по частоте нарушением называют принцип открытости/закрытости (OCP), например когда новый вид скидки требует правки `if`-цепочки. Его решают стратегиями, но и здесь важно не вводить интерфейсы заранее, без второго реального варианта.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Да, можно, и это не ошибка. SOLID, как и любой набор принципов, описывает направление, а не закон. Каждое применение абстракции имеет цену: дополнительные файлы, интерфейсы, косвенность, которую нужно держать в голове. Если выгода от принципа в конкретном месте меньше этой цены, нарушение оправдано. Главное требование: нарушение должно быть осознанным и локальным, а не следствием того, что никто не подумал.

Есть несколько типичных случаев, когда отступление от SOLID разумно:

- **Код, который не меняется и не будет переиспользоваться.** Скрипт миграции данных или одноразовая команда не требует интерфейсов.
- **Простой внутренний объект без реальной вариативности.** Интерфейс с единственной реализацией и без планов на вторую часто только добавляет шум. Если тестам нужна подмена, можно тестировать через реальный объект или использовать финальный класс с поведением, которое легко проверить напрямую.
- **Производительность в горячем пути.** Лишняя косвенность и аллокации объектов иногда недопустимы, например в обработчике, который вызывается миллионы раз.
- **Ранняя стадия продукта.** Когда модель ещё не понятна, преждевременное разбиение на классы по ответственностям закрепляет неверные границы.

## Пример оправданного нарушения

Допустим, есть небольшой внутренний сервис, который раз в сутки формирует CSV-отчёт по продажам. Он используется одним администратором, меняется редко, а его логика короткая.

Строгое применение SRP и DIP дало бы такой набор: `ReportDataProvider` (интерфейс и реализация), `CsvFormatter` (интерфейс и реализация), `ReportWriter`, `ReportStorage`, фабрика и конфигурация DI. Для 60 строк логики это перебор.

Оправданная версия — один класс, который знает про PDO и файловую систему:

```php
final class DailySalesReport
{
    public function __construct(
        private \PDO $pdo,
        private string $outputDir,
    ) {}

    public function generate(\DateTimeImmutable $day): string
    {
        $stmt = $this->pdo->prepare(
            'SELECT product, SUM(qty) AS qty, SUM(total) AS total
             FROM sales WHERE sold_on = ? GROUP BY product ORDER BY product'
        );
        $stmt->execute([$day->format('Y-m-d')]);

        $path = sprintf('%s/sales-%s.csv', $this->outputDir, $day->format('Y-m-d'));
        $fh = fopen($path, 'w');
        fputcsv($fh, ['product', 'qty', 'total']);
        while ($row = $stmt->fetch(\PDO::FETCH_ASSOC)) {
            fputcsv($fh, [$row['product'], $row['qty'], $row['total']]);
        }
        fclose($fh);

        return $path;
    }
}
```

Нарушены SRP (класс и читает данные, и форматирует, и пишет файл) и DIP (зависит от конкретного PDO и файловой системы). Но класс короткий, понятный, покрывается интеграционным тестом на тестовой БД, а изменения в нём затрагивают один файл.

## Когда нарушение перестаёт быть оправданным

Сигналы, что пора рефакторить:

- появляется вторая реализация (например, отчёт в Excel или выгрузка в S3);
- класс начинает обрастать ветвлениями по типу отчёта;
- тесты становятся медленными или хрупкими из-за того, что нельзя подменить внешнюю систему;
- несколько разработчиков постоянно конфликтуют в одном файле.

Тогда выделяем границы: отделяем запрос данных, форматирование и запись. Принцип здесь работает как инструмент, а не как обязанность в каждом классе.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Открытость/закрытость (OCP) означает, что поведение модуля можно расширять без правки его существующего кода. Наследование — лишь один из способов. В PHP-проектах чаще используют следующие.

## 1. Полиморфизм через интерфейс (стратегия)

Вместо `if`-цепочки внутри класса выносим вариант поведения за интерфейс. Новый вариант — это новый класс, а не правка старого.

```php
interface DiscountPolicy
{
    public function apply(Money $total): Money;
}

final class PromoCodeDiscount implements DiscountPolicy
{
    public function __construct(private string $code) {}

    public function apply(Money $total): Money
    {
        return $total->multiply(0.9);
    }
}

final class OrderPricer
{
    /** @param iterable<DiscountPolicy> $discounts */
    public function __construct(private iterable $discounts) {}

    public function price(Money $subtotal): Money
    {
        foreach ($this->discounts as $discount) {
            $subtotal = $discount->apply($subtotal);
        }
        return $subtotal;
    }
}
```

Новая скидка добавляется реализацией интерфейса и регистрацией в DI, а `OrderPricer` не меняется. Здесь важно не вводить интерфейс заранее, а делать это, когда появляется второй реальный вариант.

## 2. Композиция и декораторы

Поведение добавляется оборачиванием объекта в другой объект с тем же интерфейсом:

```php
final class CachedProductCatalog implements ProductCatalog
{
    public function __construct(
        private ProductCatalog $inner,
        private CacheInterface $cache,
    ) {}

    public function find(ProductId $id): Product
    {
        return $this->cache->get(
            'product_' . $id->value,
            fn () => $this->inner->find($id),
        );
    }
}
```

Кэширование, логирование, retry и метрики добавляются новыми декораторами, без изменения исходного каталога.

## 3. Событийная модель (события и слушатели)

Ядро публикует событие, а дополнительные реакции подписываются на него. В Symfony это `EventDispatcher` и Messenger:

```php
final class OrderPlaced
{
    public function __construct(public readonly int $orderId) {}
}

// Ядро
$this->dispatcher->dispatch(new OrderPlaced($orderId));

// Новая реакция добавляется отдельным слушателем
#[AsEventListener]
final class SendOrderToWarehouse
{
    public function __invoke(OrderPlaced $event): void
    {
        // постановка задачи в очередь склада
    }
}
```

Подходит, когда реакций на событие много и они не должны знать друг о друге.

## 4. Конфигурация и данные вместо кода

Правила, которые меняются часто (тарифы, пороги, список способов доставки), можно хранить в конфигурации или таблице и читать при работе. Тогда новое правило — это запись в данных, а не новый `if`. Важно не превратить конфигурацию в скрытый язык программирования.

## 5. Тегированные сервисы и реестры

В Symfony можно пометить классы тегом и собрать их в коллекцию:

```yaml
services:
    _instanceof:
        App\Pricing\DiscountPolicy:
            tags: ['app.discount_policy']
```

```php
final class DiscountRegistry
{
    /** @param iterable<DiscountPolicy> $policies */
    public function __construct(
        #[AutowireIterator('app.discount_policy')] private iterable $policies,
    ) {}
}
```

Новая реализация автоматически попадает в реестр. Это удобная форма стратегии, когда набор вариантов определяется регистрацией, а не кодом ядра.

## 6. Паттерны с функциями и замыканиями

В PHP замыкания и callable часто заменяют небольшие интерфейсы. Передача `callable` или first-class callable (`$this->normalize(...)`) даёт расширяемость без отдельных классов, но для сложного поведения лучше интерфейс.

## Что выбрать

- Для ветвления по варианту поведения — стратегия или тегированная коллекция.
- Для добавления сквозного поведения — декоратор или middleware.
- Для побочных реакций — события.
- Для часто меняющихся правил — данные.

Оговорка: OCP полностью не достижим. Любое расширение предполагает, что изменения предвидены. Закрывать код стоит там, где изменения действительно ожидаются, а не везде сразу.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Нет, не только. SRP изначально сформулирован Робертом Мартином для классов, но принцип в целом говорит о причинах для изменения: у каждого элемента системы должна быть одна причина меняться. Поэтому его применяют на нескольких уровнях.

**Функции и методы.** Метод, который одновременно валидирует, считает и сохраняет, нарушает SRP так же, как класс. Признак нарушения: в названии метода приходится использовать «и» или «затем».

```php
// Два несвязанных дела в одной функции
function processAndSaveAndNotify(array $data): void { /* ... */ }
```

**Модули и пакеты.** Модуль должен отвечать за одну область: например, `Billing` не должен заодно хранить шаблоны писем и настройки интеграции с курьерскими службами. Здесь причинами для изменения выступают бизнес-области.

**Микросервисы и сервисы.** Сервис, который одновременно управляет заказами, платежами и уведомлениями, меняется по трём разным причинам и деплоится вместе с ними, что повышает риски. Это тот же принцип, только на уровне системы.

**Файлы и конфигурация.** Один файл с маршрутами, настройками БД, бизнес-константами и утилитами будет конфликтовать в git и трудно читаться. Разделение по назначению снижает конфликты.

**Слои архитектуры.** Контроллер отвечает за HTTP, сервис приложения за сценарий использования, домен за правила, репозиторий за хранение. Смешение этих ответственностей обычно и даёт «божественные» классы.

**Тесты.** Тест, проверяющий сразу расчёт, сохранение и письмо, ломается по любой из трёх причин и плохо диагностируется. Тест с одной причиной падения понятнее.

Важная оговорка: принцип масштабируется, но его смысл сохраняется только при правильном определении «причины для изменения». Если делить слишком мелко, например метод на строки или модуль на функции, появляется избыточная косвенность. Ориентир тот же, что и для классов: меняется ли этот элемент по одной причине, которая имеет смысл для бизнеса или инфраструктуры.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

Контейнер в Symfony проходит три стадии: сборка определений на этапе компиляции, кэширование в виде PHP-кода и ленивое создание экземпляров во время выполнения. Ниже подробно по каждой.

## 1. Компиляция контейнера

Symfony не хранит конфигурацию в памяти в исходном виде. При первой загрузке (или после сброса кэша в dev-режиме при изменении ресурсов) выполняется `ContainerBuilder` и серия compiler passes.

**Сбор определений.** Загружаются файлы `services.yaml`, `config/packages/*.yaml`, а также расширения бандлов (`Extension`), которые регистрируют свои сервисы. Каждый сервис превращается в объект `Definition`: класс, аргументы, вызовы методов, теги, фабрики, scope и флаги вроде `public`, `lazy`, `shared`.

**Autowiring как проход компилятора.** Автосвязывание не происходит во время запроса. Его выполняет `AutowirePass`: он читает конструкторы и сеттеры через Reflection, смотрит на типы параметров и подбирает сервисы из контейнера. Результат записывается в `Definition` как готовые ссылки (`Reference`). Поэтому ошибки автосвязывания возникают при компиляции, а не на первом запросе.

**Другие проходы.** Среди прочих выполняются:
- `ResolveInvalidReferencesPass` и проверки циклических зависимостей;
- `RemoveUnusedDefinitionsPass`, который удаляет сервисы, на которые никто не ссылается и которые не публичны;
- `ResolveTaggedIteratorArgumentPass` и `ResolveServiceSubscribersPass`, которые собирают теги в коллекции;
- `AutowireAttributePass`, обрабатывающий атрибуты вроде `#[Autowire]` и `#[AutowireIterator]`.

**Дамп в PHP.** Готовое определение сохраняется через `PhpDumper` в файл `var/cache/<env>/<Name>Container.php`. Это класс, наследующий `Container`, где каждый сервис представлен методом-фабрикой. Поэтому при production-работе контейнер не разбирает YAML и не использует Reflection, а просто выполняет готовый код.

## 2. Autowiring подробнее

Для каждого параметра конструктора компилятор делает примерно следующее:

1. Если параметр явно задан в `arguments` или атрибутом `#[Autowire]`, используется это значение.
2. Если тип — класс или интерфейс, ищется сервис с таким id. Для интерфейса Symfony использует алиас: если в проекте один реализующий класс, Symfony может автоматически сделать его алиасом интерфейса.
3. Если несколько реализаций, компилятор не угадывает. Нужен алиас, атрибут или `#[AutowireLocator]`, иначе будет ошибка неоднозначности.
4. Для скаляров (`string $dir`) без явного значения сборка падает, если нет `bind`. Типичное решение:

```yaml
services:
    _defaults:
        autowire: true
        autoconfigure: true
        bind:
            string $projectDir: '%kernel.project_dir%'
            iterable $discounts: !tagged_iterator app.discount_policy
```

`autoconfigure` добавляет теги по интерфейсам, например для `EventSubscriberInterface` или `Command`, а `bind` задаёт значения по имени параметра.

## 3. Что происходит при первом запросе сервиса

Когда код вызывает `$container->get('app.order_service')` или приложение получает сервис через конструктор контроллера, происходит следующее.

1. **Поиск в карте сервисов.** Сгенерированный контейнер знает id и соответствующий метод-фабрику.
2. **Проверка `shared`.** Если сервис общий (по умолчанию да), сначала проверяется, не создан ли он уже в этом запросе. При повторном запросе возвращается тот же объект.
3. **Вызов фабрики.** Метод `getAppOrderServiceService()` в дампе сначала получает зависимости, рекурсивно запрашивая их у контейнера. Каждая зависимость проходит ту же процедуру (включая `shared`).
4. **Создание объекта.** Вызывается конструктор с готовыми аргументами, затем методы из `calls` и настройка свойств, если она задана.
5. **Сохранение экземпляра.** Объект помещается во внутреннюю карту созданных сервисов, после чего возвращается вызывающему коду.

Если сервис помечен `lazy: true`, на шаге 3 вместо реального объекта создаётся прокси-класс, который инициализирует настоящий сервис только при первом обращении к методу. Это полезно для тяжёлых зависимостей, например клиента внешнего API.

Для сервисов с `public: false` доступ через `$container->get()` запрещён: они доступны только как зависимости других сервисов. Это позволяет компилятору удалить их, если они не используются.

## 4. Практические следствия

- Ошибки конфигурации (нет сервиса, неоднозначный интерфейс, цикл) видны на `cache:clear` или `debug:container`, а не в середине запроса.
- `bin/console debug:autowiring` показывает, какие типы контейнер может подставить.
- `bin/console debug:container App\\Pricing\\OrderPricer` показывает итоговые аргументы после компиляции.
- Вызов `$container->get()` напрямую из сервиса считается антипаттерном (service locator). Зависимости лучше получать через конструктор.
- Если сервис должен создавать другие объекты по требованию, используйте фабрику или `ServiceLocator`, а не сам контейнер.

Если хотите, могу разобрать конкретный пример: как Symfony собирает тегированную коллекцию стратегий и почему порядок в ней зависит от приоритетов.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

Циклическая зависимость возникает, когда сервис A требует B, а B требует A (напрямую или через цепочку). В конструкторной инъекции это невозможно создать: чтобы построить A, нужен готовый B, а для B нужен A. Symfony на этапе компиляции или при первом создании выбрасывает `ServiceCircularReferenceException`. Поэтому сначала стоит ответить на вопрос: цикл — это симптом плохой границы, или реальная двусторонняя связь?

## 1. Сначала проверить, нужен ли цикл

Чаще всего цикл говорит, что ответственность распределена неверно. Типичные случаи:

- `OrderService` вызывает `PaymentService`, а тот обратно вызывает `OrderService` для обновления статуса. Решение: `PaymentService` возвращает результат, а `OrderService` сам обновляет статус.
- Два сервиса обмениваются данными, потому что у них общая сущность или общее правило. Решение: выделить третий сервис или объект-значение, от которого зависят оба.

Если после переосмысления связь двусторонняя и естественная, переходите к техническим приёмам.

## 2. Сделать одну из зависимостей ленивой

Самый простой способ — `lazy: true` или атрибут `#[Lazy]` (в Symfony 6.3+). Symfony создаёт прокси, который инициализирует реальный сервис при первом вызове метода:

```php
use Symfony\Component\DependencyInjection\Attribute\Lazy;

final class OrderService
{
    public function __construct(
        #[Lazy] private PaymentService $payments,
    ) {}
}
```

Прокси создаётся без инициализации второго сервиса, поэтому цикл при конструировании разрывается. Ограничение: прокси работает только с классами, которые можно унаследовать, то есть не `final`, и с публичными методами. Для `final`-классов или интерфейсов нужна другая стратегия.

## 3. Отложить получение через ServiceLocator или фабрику

Вместо прямой зависимости внедряем объект, который получает сервис по требованию:

```php
use Symfony\Component\DependencyInjection\Attribute\AutowireLocator;
use Symfony\Component\DependencyInjection\ServiceLocator;

final class OrderService
{
    public function __construct(
        #[AutowireLocator(PaymentService::class)]
        private ServiceLocator $locator,
    ) {}

    public function cancel(int $orderId): void
    {
        $this->locator->get(PaymentService::class)->refund($orderId);
    }
}
```

Это не отменяет связи, но переносит момент создания. Минус: зависимость становится скрытой, поэтому используйте её аккуратно и только там, где цикл действительно нужен.

## 4. Событие вместо прямого вызова

Если один сервис нужен другому только для реакции на изменение, разорвите связь через события:

```php
// PaymentService после оплаты публикует событие
$this->dispatcher->dispatch(new PaymentConfirmed($orderId));

// OrderService подписан на него и сам меняет свой статус
#[AsEventListener]
final class MarkOrderPaid
{
    public function __invoke(PaymentConfirmed $event): void
    {
        // обновление заказа
    }
}
```

Теперь `PaymentService` не знает о `OrderService`, а цикла в графе зависимостей нет. Это, пожалуй, самый чистый вариант для реакций, но он делает поток управления менее очевидным, поэтому важно документировать события.

## 5. Интерфейс и инверсия зависимости

Если цикл возникает из-за того, что один модуль зависит от конкретной реализации другого, введите интерфейс в том модуле, который его использует, а реализацию оставьте в другом. Тогда зависимость направлена в одну сторону: от конкретного к абстракции.

## Что не стоит делать

- Не подменять цикл вызовом `$container->get()` внутри сервиса: это тот же service locator, только скрытый.
- Не использовать сеттерную инъекцию как обходной путь без понимания того, что объект может оказаться в неполном состоянии.
- Не делать все сервисы ленивыми «на всякий случай»: это усложняет отладку и не решает проблему проектирования.

Практический порядок: сначала пересмотреть границы, затем выбрать событие или интерфейс, и только если связь действительно двусторонняя и естественная, использовать `#[Lazy]` или локатор.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

Задача типичная: регистрация должна завершиться быстро, а побочные действия (письмо, индекс) выполняются отдельно и могут падать независимо. Варианты отличаются тем, где находится очередь, насколько надёжна доставка и сколько инфраструктуры нужно.

## Вариант 1. Синхронно в том же запросе

Самый простой вариант: после `flush()` контроллер сам вызывает почту и индексацию. Пользователь ждёт SMTP и HTTP-запрос к поисковому движку.

- Плюсы: минимум кода, сразу видна ошибка, транзакционная картина простая.
- Минусы: ответ замедляется, а сбой почты или поиска либо ломает регистрацию (если исключение не перехвачено), либо тихо теряется.
- Подходит только для быстрых и надёжных операций и для прототипов.

## Вариант 2. `kernel.terminate` или `kernel.response`

Symfony позволяет выполнить код после отправки ответа через событие `kernel.terminate` (`#[AsEventListener(event: KernelEvents::TERMINATE)]`). Ответ уходит клиенту, а PHP-процесс доделывает работу.

- Плюсы: без инфраструктуры очередей, пользователь не ждёт.
- Минусы: работа привязана к конкретному PHP-процессу; при падении воркера или таймауте задача теряется; под PHP-FPM это зависит от `fastcgi_finish_request`. Нагрузка на тот же пул процессов растёт. Повторы и мониторинг не предусмотрены.
- Подходит для необязательных действий, потери которых допустимы (например, метрики, прогрев кэша).

## Вариант 3. Symfony Messenger с асинхронным транспортом (рекомендуемый)

Регистрация публикует сообщение, обработчики выполняются в воркере (`bin/console messenger:consume`):

```php
final readonly class UserRegistered
{
    public function __construct(public int $userId) {}
}

#[AsMessageHandler]
final class SendWelcomeEmail
{
    public function __invoke(UserRegistered $message): void { /* ... */ }
}

#[AsMessageHandler]
final class IndexUser
{
    public function __invoke(UserRegistered $message): void { /* ... */ }
}
```

В контроллере или сервисе регистрации: `$this->bus->dispatch(new UserRegistered($user->getId()));`

Настройка транспорта (например, Doctrine или Redis) в `messenger.yaml`, retry-политика и failure transport.

- Плюсы: ответ быстрый, отдельные обработчики падают и повторяются независимо, есть failed-очередь, масштабирование воркеров, стандартные инструменты (`messenger:failed:retry`).
- Минусы: нужна инфраструктура воркеров и мониторинг; доставка «как минимум один раз», поэтому обработчики должны быть идемпотентны (например, индексация по ID — безопасна, письмо может уйти дважды без дедупликации); нет гарантий порядка без дополнительных мер.

## Вариант 4. Outbox-паттерн

Сообщение записывается в таблицу `outbox` в той же транзакции, что и пользователь. Отдельный процесс читает таблицу и отправляет события.

- Плюсы: нет расхождения «пользователь создан, а событие потерялось» — запись и событие атомарны. Это самый надёжный вариант при строгих требованиях.
- Минусы: больше кода и таблиц, задержка доставки, нужен механизм очистки и ретраев.
- Подходит, когда потеря события недопустима (например, интеграция с биллингом), а не для простой индексации.

Важно: сообщение лучше отправлять после коммита транзакции. Иначе воркер может начать обработку до того, как пользователь виден в БД. Для этого у Messenger есть `DispatchAfterCurrentBusMiddleware` в связке с транзакцией, а у Doctrine — `doctrine_transaction` middleware, либо просто диспетчеризация после `flush()` вне транзакции.

## Практическая рекомендация

Для этой задачи обычно выбирают Messenger (вариант 3): передаётся только идентификатор пользователя, обработчики получают актуальные данные из БД, а не из сообщения, что снижает риск устаревших данных. Дополнительно:

- настроить retry с экспоненциальной задержкой и `failure_transport`;
- сделать обработчики идемпотентными (проверка «письмо уже отправлено», upsert в индекс);
- мониторить длину очереди и failed-сообщения;
- логировать с идентификатором сообщения для трассировки.

Если письмо и индекс критичны настолько, что потеря недопустима, добавить outbox между регистрацией и Messenger. Вариант с `kernel.terminate` оставить только для несущественных задач.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

Symfony разделяет три задачи: кто пользователь (аутентификация), что ему разрешено в общем виде (роли) и можно ли выполнить конкретное действие над конкретным объектом (voters). Эти уровни работают вместе, но решают разные вопросы.

## 1. Аутентификация

Аутентификация отвечает на вопрос «кто это». Через `security.yaml` настраивается firewall: какой механизм применяется к каким маршрутам (форма входа, JSON-логин, API-токен, OAuth и т. д.).

```yaml
security:
    providers:
        app_user_provider:
            entity:
                class: App\Entity\User
                property: email
    firewalls:
        main:
            lazy: true
            provider: app_user_provider
            custom_authenticator: App\Security\ApiTokenAuthenticator
    access_control:
        - { path: ^/admin, roles: ROLE_ADMIN }
        - { path: ^/api, roles: IS_AUTHENTICATED_FULLY }
```

Провайдер загружает пользователя, а аутентификатор проверяет учётные данные или токен и возвращает объект `Passport`. Результат — объект, реализующий `UserInterface`, который хранится в токене безопасности (`TokenStorage`).

## 2. Роли

Роли — строки вида `ROLE_ADMIN`, которые присваиваются пользователю методом `getRoles()`. Проверка выполняется через `access_control` для путей или через `#[IsGranted('ROLE_ADMIN')]` и `$this->isGranted()` в коде.

```php
#[IsGranted('ROLE_ADMIN')]
public function dashboard(): Response { /* ... */ }
```

Иерархия ролей задаётся в конфигурации:

```yaml
security:
    role_hierarchy:
        ROLE_ADMIN: [ROLE_EDITOR, ROLE_USER]
```

Роли хороши, когда права зависят только от того, кто пользователь, а не от того, над чем он работает.

## 3. Voters

Voter решает задачу с учётом объекта: например, «может ли пользователь редактировать именно этот заказ». Voter реализует `VoterInterface` (обычно через `Voter` с методами `supports` и `voteOnAttribute`):

```php
final class OrderVoter extends Voter
{
    public const EDIT = 'ORDER_EDIT';

    protected function supports(string $attribute, mixed $subject): bool
    {
        return $attribute === self::EDIT && $subject instanceof Order;
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token): bool
    {
        $user = $token->getUser();
        if (!$user instanceof User) {
            return false;
        }

        /** @var Order $subject */
        return $subject->getOwner() === $user || $user->hasRole('ROLE_MANAGER');
    }
}
```

Использование:

```php
#[IsGranted(OrderVoter::EDIT, subject: 'order')]
public function edit(Order $order): Response { /* ... */ }

// или в коде
$this->denyAccessUnlessGranted(OrderVoter::EDIT, $order);
```

Стратегия принятия решения (`affirmative`, `consensus`, `unanimous`, по умолчанию `affirmative`) задаётся в `access_decision_manager`. Важно помнить, что voter может возвращать `ACCESS_ABSTAIN`, если он не поддерживает атрибут, и тогда решение принимают другие voter'ы.

## Когда что выбирать

**Достаточно ролей**, если:
- права не зависят от конкретного объекта (доступ в админку, к отчётам, к функциям «для всех»);
- набор ролей небольшой и стабильный;
- проверка выполняется по пути или по простому атрибуту.

**Нужен voter**, если:
- решение зависит от владельца или связи с объектом (автор статьи, участник проекта, менеджер команды);
- одно и то же правило нужно в контроллере, шаблонах Twig, сервисах и командах;
- правило сложнее «роль есть или нет», например учитывает статус объекта или время;
- хочется протестировать правило изолированно.

**Типичная ошибка:** создавать роль на каждый объект (`ROLE_ORDER_42_EDITOR`) или проверять владельца прямо в контроллере через `if`. Первое быстро раздувает пользователя и не масштабируется, второе разбрасывает правила по коду и ломает единообразие. Для таких случаев правильный инструмент — voter.

Практический ориентир: роли описывают «что пользователь за человек в системе», voters описывают «что он может сделать с этим объектом». Большинство приложений используют оба механизма вместе.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

Value Object в Doctrine — задача с известным напряжением: ORM по умолчанию ожидает изменяемые сущности с конструктором без аргументов и записью полей через рефлексию, а домену нужны неизменяемость и инварианты в конструкторе. Ниже основные способы, от простого к более строгому.

## 1. Embeddable

Самый естественный вариант для Doctrine ORM: объект-значение помечается `#[ORM\Embeddable]`, а его поля попадают в таблицу владельца с префиксом.

```php
#[ORM\Embeddable]
final readonly class Money
{
    #[ORM\Column(type: 'integer')]
    private int $amount;

    #[ORM\Column(length: 3)]
    private string $currency;

    public function __construct(int $amount, string $currency)
    {
        if ($amount < 0) {
            throw new \InvalidArgumentException('Amount must be non-negative');
        }
        if (!preg_match('/^[A-Z]{3}$/', $currency)) {
            throw new \InvalidArgumentException('Invalid currency code');
        }
        $this->amount = $amount;
        $this->currency = $currency;
    }

    public function amount(): int { return $this->amount; }
    public function currency(): string { return $this->currency; }
}

#[ORM\Entity]
class Order
{
    #[ORM\Embedded(class: Money::class, columnPrefix: 'total_')]
    private Money $total;
}
```

Плюсы: простая схема, загрузка вместе с сущностью, поиск и индексы по полям, стандартная поддержка.

Минусы и подводные камни:
- Гидрация создаёт объект через рефлексию и **не вызывает конструктор**, поэтому инварианты в конструкторе при загрузке из БД не проверяются. Данные в БД должны быть корректны изначально, а миграции — аккуратны.
- `readonly` на классе с приватными полями у Doctrine иногда требует версии, где поддерживается инициализация readonly-свойств через рефлексию. Проверьте версию ORM и DBAL.
- Nullable-embeddable: если все колонки NULL, Doctrine возвращает `null` вместо объекта, поэтому поведение при частично пустых данных нужно проверять тестом.
- Изменение значения через новый объект требует явного присваивания `$order->setTotal(new Money(...))`; Doctrine отслеживает замену, а не мутацию, что и нужно домену.

## 2. Custom DBAL Type

Значение хранится в одной колонке, а преобразование описывается классом типа. Удобно для `Email`, `Money` в виде строки, `Uuid`-подобных значений.

```php
final class EmailType extends \Doctrine\DBAL\Types\StringType
{
    public const NAME = 'email';

    public function convertToPHPValue($value, AbstractPlatform $platform): ?Email
    {
        return $value === null ? null : new Email($value);
    }

    public function convertToDatabaseValue($value, AbstractPlatform $platform): ?string
    {
        return $value?->value();
    }

    public function getName(): string { return self::NAME; }
}
```

Регистрация в `doctrine.yaml` под `types`. В маппинге: `#[ORM\Column(type: 'email')]`.

Плюсы: одна колонка, преобразование в одном месте, сущность видит объект сразу.
Минусы: `convertToPHPValue` вызывает конструктор, поэтому инварианты проверяются при загрузке (это плюс), но ошибка некорректных данных в БД проявится как исключение во время чтения, а не раньше. Сложные объекты с несколькими полями в одной колонке тяжелее запрашивать.

## 3. Relation к отдельной сущности

Иногда value object выглядит как сущность с собственным id, например `Address` в отдельной таблице. Тогда это уже не чистое значение: появляется идентичность и жизненный цикл. Если значение должно быть неизменяемым, удобнее хранить его в embeddable, а не связывать через `OneToOne`, иначе возникают дыры в инвариантах (объект можно изменить через другую ссылку).

## 4. Хранение в JSON-колонке

Подходит для сложных структурированных значений, которые не запрашиваются по полям. Преобразование через кастомный тип или `json`-колонку с сериализацией в DTO.

Минусы: нет валидации схемы на уровне БД, сложно индексировать и искать, при изменении структуры нужна миграция данных. Гарантии инвариантов целиком лежат на приложении.

## Общие подводные камни

- **Гидрация обходит конструктор** (для embeddable). Решение: в тестах проверяйте, что загруженные данные проходят те же правила, или дублируйте критичные ограничения CHECK-констрейнтами в миграции.
- **Мутация через геттер.** Если объект содержит массив или изменяемый вложенный объект, неизменяемость нарушается. Используйте `readonly`, иммутабельные коллекции или копирование.
- **Сравнение.** Doctrine сравнивает embeddable по ссылке при изменении. Для равенства по значению реализуйте `equals()` и используйте его в бизнес-логике, а не `==` над объектами.
- **Сериализация для кэша и событий.** Value object должен корректно сериализоваться, иначе неизменяемость и инварианты при восстановлении не сохраняются.
- **Enum как value object.** Для ограниченного набора значений enum PHP часто лучше любого маппинга: Doctrine умеет хранить backed enum напрямую.

## Что выбрать

- По умолчанию: **Embeddable** для составных значений и **custom DBAL type** для одноколоночных (email, телефон, идентификатор).
- JSON — только если структура не запрашивается и меняется редко.
- Отдельную таблицу — только если у значения появилась собственная идентичность, и тогда это уже сущность, а не value object.

Главный принцип: инвариант должен защищаться в конструкторе объекта, а БД — хотя бы базовыми CHECK и NOT NULL, потому что гидрация может обходить проверки приложения.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

Возьмём агрегат `Order` с корнем и коллекцией `OrderLine`. Правило домена: строки заказа меняются только через корень, инвариант (например, не более 20 позиций и сумма положительная) проверяется в корне.

## 1. Доменная модель

```php
#[ORM\Entity]
#[ORM\Table(name: 'orders')]
class Order
{
    #[ORM\Id, ORM\Column(type: 'uuid')]
    private Uuid $id;

    #[ORM\Column(length: 20, enumType: OrderStatus::class)]
    private OrderStatus $status;

    /** @var Collection<int, OrderLine> */
    #[ORM\OneToMany(
        mappedBy: 'order',
        targetEntity: OrderLine::class,
        cascade: ['persist'],
        orphanRemoval: true,
    )]
    private Collection $lines;

    public function __construct(Uuid $id)
    {
        $this->id = $id;
        $this->status = OrderStatus::Draft;
        $this->lines = new ArrayCollection();
    }

    public function addLine(ProductId $product, int $qty, Money $price): void
    {
        if ($this->status !== OrderStatus::Draft) {
            throw new \DomainException('Order is not editable');
        }
        if ($this->lines->count() >= 20) {
            throw new \DomainException('Too many lines');
        }
        $this->lines->add(new OrderLine($this, $product, $qty, $price));
    }

    public function removeLine(OrderLine $line): void
    {
        if ($this->status !== OrderStatus::Draft) {
            throw new \DomainException('Order is not editable');
        }
        $this->lines->removeElement($line);
    }

    /** @return list<OrderLine> */
    public function lines(): array
    {
        return $this->lines->toArray();
    }
}

#[ORM\Entity]
#[ORM\Table(name: 'order_lines')]
class OrderLine
{
    #[ORM\Id, ORM\Column(type: 'uuid')]
    private Uuid $id;

    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'lines')]
    #[ORM\JoinColumn(nullable: false, onDelete: 'CASCADE')]
    private Order $order;

    #[ORM\Column(type: 'product_id')]
    private ProductId $product;

    #[ORM\Column]
    private int $qty;

    #[ORM\Embedded(class: Money::class, columnPrefix: 'price_')]
    private Money $price;

    public function __construct(Order $order, ProductId $product, int $qty, Money $price)
    {
        if ($qty <= 0) {
            throw new \DomainException('Quantity must be positive');
        }
        $this->id = Uuid::v7();
        $this->order = $order;
        $this->product = $product;
        $this->qty = $qty;
        $this->price = $price;
    }
}
```

Ключевые решения маппинга:

- `OrderLine` вне агрегата не должна иметь публичного репозитория и не создаётся извне. Доступ только через `Order`.
- `cascade: ['persist']` и `orphanRemoval: true` делают строки частью жизненного цикла корня. Удаление строки из коллекции приводит к её удалению в БД.
- Коллекция приватна, наружу отдаётся копия через `lines()`, чтобы инвариант нельзя было обойти через `$order->lines()->add(...)`.
- Двусторонняя связь (`inversedBy`/`mappedBy`) нужна, чтобы строка знала владельца и не могла существовать без него (`nullable: false`).

## 2. Репозиторий работает с агрегатом целиком

```php
final class OrderRepository
{
    public function __construct(private EntityManagerInterface $em) {}

    public function get(Uuid $id): Order
    {
        $order = $this->em->find(Order::class, $id);
        if ($order === null) {
            throw new OrderNotFound($id);
        }
        return $order;
    }

    public function add(Order $order): void
    {
        $this->em->persist($order);
    }
}
```

Репозиторий не вызывает `flush()`. Он только регистрирует изменения в Unit of Work. Поиск по строкам без корня не делаем: это нарушает границы агрегата (для отчётов используется отдельный read-model).

## 3. Граница транзакции: сценарий в application service

```php
final class AddLineHandler
{
    public function __construct(
        private OrderRepository $orders,
        private TransactionalRunner $tx,   // обёртка над EntityManager::wrapInTransaction
    ) {}

    public function __invoke(AddLineCommand $cmd): void
    {
        $this->tx->run(function () use ($cmd): void {
            $order = $this->orders->get($cmd->orderId);
            $order->addLine($cmd->product, $cmd->qty, $cmd->price);
            // flush выполняется внутри run() после выхода из замыкания
        });
    }
}
```

Правила:

- **Одна транзакция на один агрегат и один вызов use case.** Агрегат меняется целиком и атомарно.
- **`flush()` вызывает application service (или обёртка транзакции), а не домен и не репозиторий.** Домен не знает о БД, репозиторий не должен фиксировать чужие изменения.
- **Контроллер не вызывает `flush()`.** Он вызывает команду или handler.
- **Один `flush()` на use case.** Unit of Work собирает все изменения агрегата и выполняет их в правильном порядке (вставки до обновлений, удаления в конце).

## 4. Подводные камни

- **Загрузка коллекции лениво (lazy)**. При `lines()` в обработчике коллекция догружается отдельным запросом. Для N+1 при чтении используйте fetch join в специальном запросе, но не меняйте им состояние агрегата.
- **Сохранение чужих агрегатов.** Если в одной транзакции меняются два агрегата, Doctrine зафиксирует оба. Это признак, что граница выбрана неверно или нужны доменные события с отдельными транзакциями.
- **Конкурентные изменения.** Два запроса могут изменить один заказ. Используйте `#[ORM\Version]` (оптимистическая блокировка) на корне, тогда конфликт даст `OptimisticLockException`, а не потерю данных.
- **`flush()` внутри домена или репозитория.** Ломает транзакционные границы и делает тесты медленными.
- **`cascade: ['remove']` на большой коллекции.** Может загрузить всё в память; для массовых удалений лучше DQL DELETE, но тогда нужно учитывать, что доменные правила обходятся.
- **Инварианты на уровне агрегата.** Проверка «не более 20 строк» должна быть в корне, а не в контроллере; и она работает только если коллекцией управляет корень.
- **Изменение строки без корня.** Если `OrderLine` меняется напрямую и затем `flush`, инвариант корня может быть нарушен. Поэтому `OrderLine` лучше делать неизменяемой или менять через методы корня.

Итог: корень загружается целиком через репозиторий, все изменения проходят через его методы, транзакцию и `flush` держит application service, а версионирование корня защищает от гонок.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

Сначала важно убедиться, что проблема действительно в N+1, а не в чём-то другом (медленный внешний API, отсутствующий индекс, тяжёлый рендеринг). Подозрение нужно подтвердить измерением.

## 1. Диагностика

**Профилировщик Symfony.** В панели Doctrine (Web Profiler) видно число запросов и их время. Если на одной странице сотни однотипных `SELECT ... WHERE id = ?` с разными параметрами, это почти всегда N+1.

**Логи запросов.** В dev-окружении можно включить логирование SQL через `doctrine.dbal.logging` или посмотреть `bin/console doctrine:query:sql` для проверки конкретного запроса. Полезно смотреть `EXPLAIN` для тяжёлых запросов, чтобы отделить N+1 от плохого плана.

**Счётчик запросов в тестах.** Надёжный способ закрепить результат, например через middleware или `Doctrine\DBAL\Logging\Middleware`, который считает запросы. Тест проверяет, что страница делает не более N запросов при фиксированном числе сущностей. Это защищает от регрессий.

**Важно воспроизвести на разном объёме данных.** Если число запросов растёт линейно с количеством записей, диагноз подтверждён.

Типичный источник проблемы: цикл по коллекции, где в шаблоне или в геттере обращаются к связи (`$order->getCustomer()->getName()`), либо Twig вызывает ленивую загрузку в `for`.

## 2. Способы решения

### a) Fetch join в DQL / QueryBuilder

Загрузка связи одним запросом вместе с основной сущностью:

```php
$orders = $this->em->createQueryBuilder()
    ->select('o', 'c', 'l')
    ->from(Order::class, 'o')
    ->join('o.customer', 'c')
    ->leftJoin('o.lines', 'l')
    ->where('o.status = :status')
    ->setParameter('status', OrderStatus::Paid)
    ->getQuery()
    ->getResult();
```

- **Плюсы:** один запрос на всё, явно, под конкретный сценарий, не меняет маппинг.
- **Минусы:** при нескольких `to-many` JOIN даёт декартово произведение строк (раздувание результата); Doctrine при этом дедуплицирует сущности, но данные передаются полностью. Для пагинации с `to-many` нужен `Paginator` и аккуратная работа с `setMaxResults`: без него лимит применяется к строкам JOIN, а не к сущностям.

### b) Batch fetching (пакетная загрузка)

Для `to-one` и ленивых коллекций Doctrine умеет загружать связи пачкой по `IN (...)` при обращении к первой из них. Это включается через `#[ORM\OneToMany(fetch: 'EXTRA_LAZY')]` для коллекций или через явную загрузку `UnitOfWork` в сервисе.

- **Плюсы:** минимум изменений, сохраняется ленивость, нет декартова произведения.
- **Минусы:** число запросов равно `ceil(N / batch)`, а не 1; поведение менее очевидно; `EXTRA_LAZY` не загружает коллекцию при `count()` и `contains()` без обращения к БД, что удобно, но легко забыть.

### c) Отдельный read-model / DTO-запрос

Для страницы-списка часто достаточно выбрать только нужные поля в DTO через `NEW`-конструкцию или `Partial`:

```php
$rows = $this->em->createQuery(
    'SELECT NEW App\Dto\OrderRow(o.id, c.name, o.total)
     FROM App\Entity\Order o JOIN o.customer c'
)->getResult();
```

- **Плюсы:** минимум данных, никаких сущностей в памяти, нет ленивых загрузок и нет проблем с Unit of Work, быстро и предсказуемо.
- **Минусы:** дублирование запросов, отдельный класс под каждый экран, сущности нельзя изменять по этим данным.

Для списков и отчётов это обычно лучший выбор. Для страниц, где нужна модификация агрегата, он не подходит.

### d) Кэширование

Second-level cache Doctrine или кэш результатов запроса (`setResultCacheId`) уменьшают повторные обращения к БД.

- **Плюсы:** ускоряет чтение, не меняет код запросов.
- **Минусы:** инвалидация становится главной сложностью; данные могут быть устаревшими; второй уровень сложно настроить правильно, и он маскирует проблему, а не решает её.

Кэш полезен как дополнение, но не как замена исправлению запросов.

### e) Оптимизация на уровне шаблона

Если проблема в Twig (вызовы связей в циклах), можно предварительно передать в шаблон уже загруженные данные (DTO или массивы), а не сущности с ленивыми связями.

## 3. Как выбирать

- Список или таблица без изменений: **read-model/DTO** (c).
- Один сценарий с известной связью и нужной сущностью: **fetch join** (a), с осторожностью при нескольких `to-many`.
- Связи загружаются непредсказуемо, а менять код сложно: **batch fetching** (b).
- Горячие данные, редко меняющиеся: **кэш** (d) поверх исправленных запросов.

Практический порядок: подтвердить число запросов в профилировщике, найти место обращения к связи, выбрать минимально достаточное решение и закрепить его тестом на количество запросов, чтобы проблема не вернулась.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

Код приложения — не единственный участник, который пишет в базу. Миграции, ручные правки через psql, другие сервисы, фоновые скрипты, баги в путях, которые обходят домен, и гонки между параллельными запросами могут нарушить инварианты, даже если каждая проверка в коде корректна. Проверка «сначала SELECT, потом INSERT» в приложении не защищает от гонки: два запроса одновременно проходят проверку и оба записывают. Ограничение в БД — единственная гарантия, которая действует при любом способе записи.

Поэтому разделение такое: приложение даёт понятные сообщения об ошибках и сложные правила, а БД защищает инварианты, которые должны держаться всегда.

## Средства PostgreSQL

**NOT NULL.** Самое простое и самое полезное. Если поле обязательно по смыслу, объявите его так.

```sql
ALTER TABLE orders ALTER COLUMN customer_id SET NOT NULL;
```

**UNIQUE и уникальные индексы.** Защищают от дублей и гонки при проверке «уже существует».

```sql
ALTER TABLE users ADD CONSTRAINT users_email_key UNIQUE (email);

-- Уникальность только для неудалённых записей
CREATE UNIQUE INDEX users_email_active_uniq ON users (email) WHERE deleted_at IS NULL;
```

**CHECK.** Простые инварианты на значения одной строки.

```sql
ALTER TABLE order_lines
    ADD CONSTRAINT qty_positive CHECK (qty > 0),
    ADD CONSTRAINT price_non_negative CHECK (price_amount >= 0);
```

Важно: CHECK не должен дублировать сложную бизнес-логику, он нужен для базовых гарантий.

**FOREIGN KEY.** Ссылочная целостность. Выбирайте `ON DELETE` осознанно: `CASCADE` для строк агрегата, `RESTRICT` или `NO ACTION` для связей между агрегатами, `SET NULL` только если это допустимо домену.

```sql
ALTER TABLE order_lines
    ADD CONSTRAINT order_lines_order_fk
    FOREIGN KEY (order_id) REFERENCES orders (id) ON DELETE CASCADE;
```

**EXCLUDE-ограничения.** Самый мощный инструмент для «не пересекаются» (бронирование, расписания). Требует расширения `btree_gist` для сочетания с обычными типами.

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE room_bookings
    ADD CONSTRAINT no_overlapping_bookings
    EXCLUDE USING gist (room_id WITH =, during WITH &&);
```

Здесь `during` — тип `tstzrange`. Такое правило невозможно выразить через UNIQUE, и проверка в коде при параллельных запросах не даст гарантии.

**Триггеры.** Нужны, когда правило зависит от нескольких таблиц или требует вычислений, которые CHECK выразить не может. Использовать их стоит осторожно: логика уходит из кода в БД, её сложнее тестировать и понимать, и она скрыто выполняется при любой записи. Обычно я выбираю триггер только для инвариантов, которые действительно должны срабатывать всегда, например аудит или согласованность денормализованных счётчиков.

**Ограничения на состояние через enum или справочник.** Для статусов можно использовать внешний ключ на справочную таблицу или CHECK со списком значений. Для PHP-enum это дублирование, поэтому выбирайте одно: либо справочник, либо CHECK, синхронизированный с enum тестом.

## Как это связано с Doctrine

Атрибуты `#[ORM\UniqueConstraint]`, `#[ORM\Index]`, `nullable: false` попадают в миграции, так что часть ограничений можно описывать в маппинге. Но EXCLUDE, частичные индексы (`WHERE`), сложные CHECK и триггеры обычно добавляются вручную в миграции через `$this->addSql(...)`. Doctrine их не отслеживает, поэтому при изменениях схемы стоит проверять, что они не потерялись (например, `doctrine:schema:validate` и тесты на ограничения).

## Когда что использовать

- Значение обязательно по смыслу — NOT NULL.
- Уникальность сущности или ключа — UNIQUE (с условием, если есть soft delete).
- Простое условие на значения строки — CHECK.
- Связь между таблицами — FOREIGN KEY с продуманным ON DELETE.
- Непересечение диапазонов — EXCLUDE.
- Сложное правило на несколько строк или таблиц — сначала пересмотреть модель, и только потом триггер или блокировку (`SELECT ... FOR UPDATE`, оптимистическая блокировка через `#[ORM\Version]`).

Итог: проверки в приложении отвечают за понятность и сценарии, ограничения в БД — за гарантию. Если инвариант важен, он должен быть защищён в обоих местах, а БД — последним барьером.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

Диагностику я начинаю с измерения, а не с догадок: сначала нужно понять, медленный ли именно этот запрос, как часто он вызывается и что именно в нём тормозит.

## 1. Воспроизведение и сбор данных

- Фиксирую точный SQL, который уходит из приложения. В Doctrine это можно увидеть в профилировщике Symfony или через логирование DBAL. Важно взять реальные параметры, потому что план зависит от значений.
- Проверяю, медленный ли запрос сам по себе или медленно всё приложение. Для этого смотрю `pg_stat_statements`: он показывает суммарное время, среднее время, число вызовов и число прочитанных блоков. Запрос, который занимает 50 мс, но вызывается 100 000 раз в минуту, может быть главной проблемой.

```sql
SELECT calls, mean_exec_time, total_exec_time, rows, query
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

- Смотрю на объём данных в таблицах и на статистику: `pg_stat_user_tables` (seq scan против index scan, дата последнего `ANALYZE`), размер таблиц и индексов.

## 2. Анализ плана

Основной инструмент — `EXPLAIN (ANALYZE, BUFFERS)`. Без `ANALYZE` видна только оценка планировщика, а с ним — реальное время и реальное число строк.

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT o.id, o.total_amount
FROM orders o
WHERE o.customer_id = $1 AND o.status = 'paid'
ORDER BY o.created_at DESC
LIMIT 20;
```

Что смотрю в плане:

- **Оценки против факта.** Если `rows=10` в оценке и `rows=250000` по факту, статистика устарела или корреляция колонок не учтена. Лечится `ANALYZE` таблицы или расширенной статистикой `CREATE STATISTICS`.
- **Seq Scan** на большой таблице при селективном условии: нужен индекс. Seq Scan на маленькой таблице или при выборке большой части строк — нормален.
- **Большой Rows Removed by Filter**: индекс не покрывает условие, фильтр читает лишнее.
- **Сортировка (Sort) с внешней памятью** (`Sort Method: external merge`): не хватает `work_mem` или нужен индекс под `ORDER BY`.
- **Nested Loop с большим числом итераций** по внутренней стороне: часто признак неверной оценки и отсутствия индекса на join-колонке.
- **Buffers: shared read** много по сравнению с `hit`: данные не в кэше, запрос читает диск.
- **Heap Fetches** в Index Only Scan: нужен `VACUUM`, иначе visibility map не обновлена.

## 3. Типовые причины и решения

**Отсутствует индекс.** Самая частая причина. Индекс под фильтр, join и сортировку, порядок колонок важен: сначала равенство, потом диапазон и сортировка.

```sql
CREATE INDEX CONCURRENTLY orders_customer_status_created_idx
    ON orders (customer_id, status, created_at DESC);
```

`CONCURRENTLY` не блокирует запись на время создания. Частичный индекс подходит, если нужна только часть строк: `WHERE status = 'paid'`.

**Индекс есть, но не используется.** Причины: функция над колонкой (`WHERE lower(email) = ...` без функционального индекса), неявное приведение типов (`varchar` сравнивается с `int`), `LIKE '%xxx'` без `pg_trgm`, низкая селективность, устаревшая статистика.

**Устаревшая статистика.** Решение: `ANALYZE`, проверка работы autovacuum, для сильно коррелированных колонок — `CREATE STATISTICS`.

**Пагинация через OFFSET.** Чем дальше страница, тем больше строк читается и отбрасывается. Лучше keyset-пагинация по индексированному ключу (`WHERE (created_at, id) < (...)`).

**N+1 со стороны приложения.** Тысячи одинаковых быстрых запросов. Это не проблема плана, а проблема обращения, и решается на уровне кода.

**Неэффективные join и подзапросы.** Коррелированный подзапрос в `SELECT` на каждую строку, `NOT IN` с NULL, которые блокируют использование индекса; часто помогает переписывание в `JOIN` или `NOT EXISTS`.

**Bloat и устаревшие данные.** Много мёртвых строк после массовых UPDATE/DELETE раздувает таблицу. Смотрю `n_dead_tup` и настройки autovacuum.

**Блокировки.** Запрос «медленный», но план хороший: ждёт блокировку. Проверяю `pg_stat_activity` и `pg_locks`, особенно длинные транзакции в приложении (`idle in transaction`).

**Настройки памяти.** `work_mem` для сортировок и хешей, `shared_buffers` и `effective_cache_size` для планировщика. Меняю их осторожно и обычно после того, как исправил запрос.

## 4. Порядок действий

1. Подтвердить, что запрос главный по суммарному времени (`pg_stat_statements`).
2. Получить реальный план с `ANALYZE` и `BUFFERS` на продовых параметрах (или на копии).
3. Найти главный узел по времени и сравнить оценки с фактом.
4. Исправить причину: индекс, переписывание, статистика, пагинация, приложение.
5. Проверить план ещё раз и сравнить время и буферы до и после.
6. Закрепить результат: миграция с индексом, при необходимости тест на производительность или мониторинг `pg_stat_statements` на регрессии.

Главная мысль: оптимизация начинается с плана и числа чтений, а не с добавления индексов «на всякий случай». Каждый индекс замедляет запись и занимает место, поэтому его добавление должно опираться на измеренную пользу.

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

Агрегат в DDD — это кластер связанных объектов (сущностей и объектов-значений), который рассматривается как единое целое с точки зрения изменений данных. У него есть один вход — корень агрегата (aggregate root), через который извне меняется состояние, и набор инвариантов, которые должны выполняться после каждой операции. Агрегат — единица транзакционной согласованности: в одной транзакции меняется один агрегат, а внешние ссылки на его внутренности не хранятся.

## Как определяю границы

Исхожу из вопросов, которые задаёт бизнес, а не из структуры таблиц:

1. **Какие инварианты должны держаться строго, в одной транзакции?** Если два объекта обязаны быть согласованы мгновенно, они кандидаты в один агрегат. Если согласованность может быть eventual, им место в разных агрегатах.
2. **Что меняется вместе?** Объекты, которые почти всегда изменяются в одном сценарии, стоит объединять; то, что меняется независимо, лучше разделять.
3. **Насколько велик кластер?** Агрегат должен быть небольшим. Коллекции без верхней границы — признак ошибки.
4. **Нужна ли ссылка по идентификатору?** Между агрегатами связи хранятся по ID, а не по прямым ссылкам на объекты.

## Пример

Интернет-магазин, сущности `Order`, `OrderLine`, `Customer`, `Product`.

- `Order` и `OrderLine` — один агрегат с корнем `Order`. Инвариант «не более 20 позиций, сумма положительная, заказ редактируется только в статусе Draft» должен проверяться атомарно при любом изменении строк. Строки без заказа смысла не имеют.
- `Customer` — отдельный агрегат. Его данные (имя, адрес, лимиты) меняются независимо от заказов. В `Order` хранится только `CustomerId`.
- `Product` — отдельный агрегат, с каталогом и ценой. Заказ фиксирует цену на момент покупки внутри `OrderLine` как объект-значение `Money`, а не ссылается на живой товар.

```php
final class Order
{
    private OrderId $id;
    private CustomerId $customerId;   // ссылка по идентификатору
    /** @var list<OrderLine> */
    private array $lines = [];        // внутренности доступны только через корень

    public function addLine(ProductId $product, int $qty, Money $price): void
    {
        if (count($this->lines) >= 20) {
            throw new DomainException('Too many lines');
        }
        $this->lines[] = new OrderLine($product, $qty, $price);
    }
}
```

## Типовая ошибка

**Границы по таблицам или по ORM-связям, а не по инвариантам.** Классическая картина: «у заказа есть клиент, значит `Customer` вложен в `Order`», или «все сущности, связанные внешними ключами, образуют один агрегат». В результате:

- одна транзакция тянет за собой огромный граф и блокирует лишние строки;
- конкурентные изменения разных частей сталкиваются с оптимистичными блокировками на корне, хотя конфликта по смыслу нет;
- загрузка агрегата тянет десятки связанных объектов, и появляется N+1 и медленные страницы;
- любая связь по объекту, а не по ID, позволяет менять чужие данные через «случайную» ссылку.

Признак ошибки: агрегат нельзя сохранить без загрузки половины базы, или два пользователя постоянно получают конфликты при работе с разными полями одного объекта. Исправление — пересмотреть инварианты, разорвать связи на уровне ID и связать части доменными событиями с eventual consistency там, где строгая согласованность не нужна.

Итог: граница агрегата определяется тем, какие инварианты должны выполняться атомарно, а не тем, какие таблицы связаны внешними ключами.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

Без защиты возникает классическая проблема lost update: оба процесса читают одну версию агрегата, каждый применяет свои изменения в памяти, и последний `flush()` молча перезаписывает результат первого. Инварианты при этом могут нарушиться: например, два процесса одновременно добавляют строки, и каждый видит, что их ещё меньше 20, хотя вместе получается 21.

В Doctrine без явной блокировки UnitOfWork обновляет строки по первичному ключу без проверки предыдущего состояния, поэтому конфликт не обнаруживается.

## Что происходит по шагам

1. Процесс A загружает `Order` (версия 5).
2. Процесс B загружает `Order` (версия 5).
3. A вызывает `addLine`, B тоже, оба делают `flush()`.
4. Второй `flush` перезаписывает изменения первого, либо инвариант нарушен на уровне данных.

## Варианты проектирования

### 1. Оптимистичная блокировка (основной вариант)

Корень агрегата получает счётчик версии, Doctrine при каждом `UPDATE` проверяет, что версия в БД совпадает с загруженной:

```php
#[ORM\Entity]
class Order
{
    #[ORM\Version]
    #[ORM\Column(type: 'integer')]
    private int $version;
}
```

Doctrine формирует `UPDATE orders SET ..., version = version + 1 WHERE id = ? AND version = ?`. Если строка не обновилась, бросается `OptimisticLockException`. Обработка: повторить use case с перезагрузкой агрегата (retry) или показать пользователю конфликт (HTTP 409).

Плюсы: нет блокировок на время чтения, хорошо масштабируется, подходит для веб-интерфейсов с редкими конфликтами. Минусы: при частых конфликтах растёт число повторов; нужна логика retry; версия должна обновляться и для изменений дочерних сущностей. Важно: изменение строки `OrderLine` без изменения корня не увеличит версию, поэтому корень нужно помечать как изменённый (например, `$order->touch()` внутри методов, меняющих коллекцию), иначе конфликт не будет обнаружен.

### 2. Пессимистичная блокировка

Загрузка с `LockMode::PESSIMISTIC_WRITE` (`SELECT ... FOR UPDATE`) внутри транзакции:

```php
$order = $this->em->find(Order::class, $id, LockMode::PESSIMISTIC_WRITE);
```

Плюсы: конфликтов нет в принципе, retry не нужен, подходит для сценариев с высокой конкуренцией (например, резервирование остатка). Минусы: блокировка держится до конца транзакции, поэтому транзакция должна быть короткой и без внешних вызовов (HTTP, отправка писем); при неаккуратности возникают deadlock'и и очереди ожидания.

### 3. Атомарные операции на уровне БД

Если изменение сводится к арифметике (списать 1 единицу со склада), можно выполнить условный `UPDATE ... SET qty = qty - 1 WHERE id = ? AND qty >= 1` и проверить число затронутых строк. Это быстро и без блокировки на чтение, но вне агрегатной модели, и инварианты описываются SQL, а не доменом. Подходит для простых счётчиков, а не для сложных корней.

### 4. Сериализация через очередь или единственного обработчика

Команды на один агрегат направляются в одну очередь с ключом (partition key = id агрегата), и обрабатываются последовательно. Конкуренции нет по построению, но растёт задержка и сложность инфраструктуры. Оправдано для высоконагруженных потоков.

### 5. Ограничения в БД как последний барьер

Для инвариантов, которые можно выразить через уникальность или CHECK, добавляются ограничения, чтобы даже при ошибке в коде БД не приняла нарушение. Например, уникальный индекс `(order_id, product_id)` для запрета дублей строк.

## Как выбираю

- По умолчанию: **оптимистичная блокировка на корне** агрегата плюс retry на уровне application service. Конфликты в типичном веб-приложении редки, а код простой.
- Если конфликты частые и потеря пересчёта дорога: **пессимистичная блокировка** на короткой транзакции.
- Если изменение — счётчик или остаток: **атомарный UPDATE** с условием.
- Если важна строгая очерёдность и нагрузка высокая: **сериализация по ключу**.
- Всегда дополнять **ограничением в БД** инварианты, которые можно выразить декларативно.

Итог: защита от гонок должна стоять на границе агрегата, а не разбрасываться по коду; версия корня — главный механизм, а блокировки и ограничения БД — дополнение для особых случаев.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

Доменное событие — это факт, который произошёл в домене и уже не может быть отменён: `UserRegistered`, `OrderPaid`, `StockReserved`. Имя пишу в прошедшем времени, а содержимое — минимальное: идентификаторы и данные, нужные для реакции. Я опираюсь на принципы из литературы по DDD и на практики Symfony; собственного эксплуатационного опыта у меня нет.

## Когда публикую

Событие фиксирую внутри агрегата, когда меняется его состояние значимым для других частей образом. Агрегат накапливает события в списке и не отправляет их сам:

```php
final class Order
{
    /** @var list<object> */
    private array $events = [];

    public function pay(): void
    {
        if ($this->status !== OrderStatus::Draft) {
            throw new \DomainException('Order cannot be paid');
        }
        $this->status = OrderStatus::Paid;
        $this->events[] = new OrderPaid($this->id, $this->total);
    }

    /** @return list<object> */
    public function pullEvents(): array
    {
        $events = $this->events;
        $this->events = [];
        return $events;
    }
}
```

Так домен остаётся без зависимости от шины и БД, а решение «отправлять или нет» принимает application service после успешного сохранения.

## Как обрабатываю

Обработка выполняется после того, как изменение состояния уже зафиксировано:

```php
final class PayOrderHandler
{
    public function __invoke(PayOrderCommand $cmd): void
    {
        $order = $this->orders->get($cmd->orderId);
        $order->pay();

        $this->tx->run(fn () => $this->orders->save($order));

        foreach ($order->pullEvents() as $event) {
            $this->bus->dispatch($event);
        }
    }
}
```

Реакции обычно асинхронные через Messenger: письмо, обновление отчётов, вызов склада. Синхронные подписчики допустимы только для того, что должно сработать в той же операции и не требует внешних вызовов.

## Какие проблемы решают

- Разделение: `Order` не знает о письмах, складе и аналитике.
- Расширяемость: новая реакция — новый обработчик, без правки агрегата.
- Понятный журнал бизнес-фактов, который удобно логировать и аудировать.
- Ослабленная связность между агрегатами: вместо прямых вызовов — eventual consistency.

## Какие проблемы создают

- Неявный поток управления: сложно понять, что случится после `pay()`. Нужна документация списка событий и их подписчиков.
- Порядок и повторы: доставка обычно «как минимум один раз», обработчики должны быть идемпотентными.
- Эволюция схемы события: поля меняются, старые сообщения остаются в очереди. Нужно версионирование или только добавление полей.
- Отладка распределённых сбоев: часть реакций прошла, часть упала.
- Соблазн вызывать через события всё подряд, включая то, что должно быть в одной транзакции.

## Связь с транзакциями

Ключевое правило: **публиковать событие нужно только после успешного коммита**. Иначе обработчик может увидеть состояние, которого в БД ещё нет, либо событие уйдёт, а транзакция откатится, и реакция случится для несуществующего факта.

Есть три варианта:

1. **Диспатч после коммита** (как в примере выше). Просто, но если процесс упадёт между `commit` и `dispatch`, событие потеряется.
2. **Outbox.** Событие записывается в таблицу `outbox` в той же транзакции, что и агрегат; отдельный воркер публикует его и помечает как отправленное. Гарантирует согласованность ценой инфраструктуры и задержки.
3. **Синхронные подписчики внутри транзакции** для того, что обязано откатиться вместе с агрегатом (например, запись в журнал аудита той же БД). Цена — длинная транзакция и связность.

В Doctrine удобно слушать `postFlush`, но это место, где легко ошибиться: событие уходит до того, как доменная логика завершилась, либо при вложенных транзакциях. Поэтому я предпочитаю явный диспатч в application service, а для надёжности добавляю outbox, если потеря события недопустима.

Итог: событие — это факт, записанный в агрегате; публикуется он после коммита, а если потеря недопустима, его доставку гарантирует outbox, а обработчики делаю идемпотентными.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

Сущность (Entity) определяется идентичностью: два объекта с одинаковыми атрибутами, но разными ID — разные сущности. Она изменяема, и её жизненный цикл важен: `Order` с номером 42 остаётся тем же заказом, даже если поменялся статус или состав строк.

Объект-значение (Value Object) определяется только значениями своих атрибутов. `Money(100, 'RUB')` равен любому другому `Money(100, 'RUB')`. Он неизменяем, не имеет идентификатора и заменяется целиком: вместо изменения суммы создаётся новый объект.

```php
// Value Object: равенство по значению, неизменяемость
final readonly class Money
{
    public function __construct(
        public int $amount,
        public string $currency,
    ) {
        if ($amount < 0) {
            throw new \DomainException('Amount must be non-negative');
        }
    }

    public function equals(self $other): bool
    {
        return $this->amount === $other->amount
            && $this->currency === $other->currency;
    }
}

// Entity: идентичность важнее атрибутов
final class Customer
{
    public function __construct(
        private readonly CustomerId $id,
        private string $name,
    ) {}

    public function id(): CustomerId { return $this->id; }

    public function rename(string $name): void { $this->name = $name; }
}
```

Два `Customer` с одинаковым именем — разные люди. Два `Money` с одинаковой суммой и валютой — одна и та же сумма.

## Как решаю, к чему отнести концепцию

Задаю несколько вопросов:

1. **Нужно ли отслеживать, «тот же это объект» после изменений?** Да — сущность. Нет, важно только значение — объект-значение.
2. **Меняется ли он во времени или создаётся заново?** Если изменение означает смену значения (новый адрес доставки), это, скорее, значение. Если объект живёт и эволюционирует (клиент, заказ) — сущность.
3. **Есть ли у него собственный жизненный цикл и бизнес-идентификатор?** Номер заказа, номер договора — признаки сущности.
4. **Можно ли заменить одно другим без потери смысла?** Да — значение.
5. **Есть ли инварианты, которые защищает именно эта единица?** Они подсказывают границы и роль в агрегате.

Типичная ошибка — делать сущностью всё, что имеет поля, включая `Address`, `Price`, `Email`. Это приводит к лишним таблицам, идентификаторам и проблемам с равенством. Обратная ошибка — делать значением то, что нужно отслеживать (например, `Account` с балансом, у которого есть история и владелец).

## Единый язык

Ubiquitous language — общий словарь, которым говорят разработчики, аналитики и бизнес. Термины из него попадают в имена классов, методов и событий. Если бизнес говорит «резервирование», в коде будет `reserve()`, а не `setStatus(2)`; если говорят «списание», не `decreaseQuantity()`.

Влияние на код:

- **Имена отражают смысл.** `order->confirm()` вместо `order->setStatus('confirmed')`: метод выражает правило, а не механику.
- **Модель ловит противоречия.** Когда разработчик и эксперт расходятся в термине, это видно сразу, и часто выявляется неверная граница контекста.
- **Разные контексты — разные словари.** «Клиент» в продажах и «клиент» в бухгалтерии могут быть разными моделями. Единый язык действует внутри ограниченного контекста (bounded context), а не во всей компании.
- **Код становится документацией.** Новый человек понимает домен по классам и методам, а не по таблицам БД.

Практически это означает: вместе с экспертом фиксируем глоссарий, его термины используем в коде, тестах, событиях и обсуждениях, а расхождения обсуждаем сразу, а не маскируем техническими названиями.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

Ниже структура, которую я считаю разумной для Symfony-приложения. Опираюсь на принципы Мартина и практики DDD, собственного проектного опыта у меня нет.

## Слои и правило зависимостей

Ядро правила: **зависимости направлены только внутрь**. Внешний слой знает о внутреннем, но не наоборот. Внутренние слои определяют интерфейсы, которые реализуют внешние.

```
Infrastructure  →  Application  →  Domain
(Symfony, Doctrine,   (сценарии,       (сущности, VO,
 HTTP, очереди,        порты,           доменные события,
 адаптеры)             команды)         правила)
```

Интерфейс (контроллер, консольная команда, обработчик очереди) тоже относится к внешнему кольцу и только вызывает application-слой.

## Что где лежит

**Domain (ядро).** Агрегаты, сущности, объекты-значения, доменные события, доменные сервисы, интерфейсы репозиториев (без реализации). Никаких зависимостей от Symfony, Doctrine, PSR-интерфейсов, HTTP, `\PDO`. Чистый PHP, даже атрибуты маппинга сюда не попадают.

**Application (сценарии использования).** Команды и их обработчики (`PayOrderHandler`), запросы и read-модели, порты наружу (интерфейсы почтовика, платёжного шлюза, поискового индекса), транзакционная граница, диспетчеризация событий после коммита. Знает домен, но не знает, как именно выполняются запросы.

**Infrastructure (адаптеры).** Реализации репозиториев на Doctrine, маппинг (атрибуты или XML), реализации портов (`SymfonyMailer`, HTTP-клиент поиска), транспорты Messenger, кэш, файловая система.

**Presentation / Interface (вход).** Symfony-контроллеры, консольные команды, обработчики HTTP-запросов, маппинг DTO в команды и обратно, перевод исключений в коды ответа, сериализация.

Иногда Presentation выделяют отдельно, иногда объединяют с Infrastructure. Для небольшого проекта достаточно трёх каталогов, для большого полезно разделить.

## Куда попадают конкретные вещи

**Doctrine.** Сами сущности в Domain пишутся без зависимости от ORM. Маппинг либо живёт в Infrastructure (XML или YAML рядом с ORM-конфигурацией), либо атрибутами на доменных классах: это компромисс, который допустим, но он нарушает строгую чистоту. Реализации репозиториев, `EntityManager`, DQL, кастомные DBAL-типы — только в Infrastructure. Интерфейс `OrderRepository` в Domain, `DoctrineOrderRepository` в Infrastructure.

**Symfony-контроллер.** В Presentation. Он принимает запрос, валидирует форму, создаёт команду, вызывает handler через шину и возвращает ответ. Бизнес-правил в нём нет. Ошибки домена перехватываются на границе и маппятся в 404, 409, 422.

**Обработчик очереди.** Тоже вход, в Presentation (или в отдельном слое Messaging внутри Infrastructure, если хотите отделить). Он получает сообщение, восстанавливает нужные данные и вызывает application-сценарий. Не содержит логики, кроме разбора сообщения и повторных попыток.

Типичная структура каталогов:

```
src/
  Domain/
    Order/        Order.php, OrderLine.php, OrderRepository.php (интерфейс), OrderPaid.php
  Application/
    Order/
      PayOrder/   PayOrderCommand.php, PayOrderHandler.php
    Port/         PaymentGateway.php, Mailer.php
  Infrastructure/
    Persistence/Doctrine/  DoctrineOrderRepository.php, Mapping/
    Mail/          SymfonyMailer.php
    Messaging/     OutboxPublisher.php
  Presentation/
    Http/Order/    PayOrderController.php
    Messaging/     OrderPaidConsumer.php
```

## Как следить за границами

1. **Правила зависимостей в инструментах.** Deptrac (или аналоги) описывает слои и запрещённые зависимости, например `Domain` не может ссылаться на `Doctrine` и `Symfony`. Запускается в CI и падает при нарушении.
2. **Статический анализ.** PHPStan или Psalm с настройками, а для домена — проверка отсутствия `use` из чужих namespace.
3. **Архитектурные тесты.** PHPat (или самописные тесты на Reflection) фиксируют правило текстом, чтобы его было видно в коде.
4. **Ревью.** Инструменты ловят прямые `use`, но не ловят утечку смысла, например логику скидки в контроллере. Это проверяется на код-ревью по вопросу «где здесь правило?».
5. **Тесты домена без инфраструктуры.** Если тесты домена и application-слоя запускаются без БД и Symfony-kernel, граница держится естественно. Медленные тесты обычно признак того, что домен зависит от инфраструктуры.

Оговорка: чистая архитектура — инструмент против связности, а не самоцель. Для простого CRUD-модуля ценой многослойности может стать лишний код. Границы стоит вводить там, где есть реальная сложность домена и ожидаемая смена технологий или интеграций.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

Стратегия строится вокруг простого правила: максимум уверенности при минимуме медленных и хрупких тестов. Для Symfony с PostgreSQL это обычно пирамида с акцентом на быстрые unit-тесты домена и реальную БД в интеграционных тестах. Опыт у меня теоретический, опираюсь на общепринятые практики.

## Пирамида

- **Unit-тесты домена (основа, тысячи).** Агрегаты, объекты-значения, доменные сервисы, инварианты. Без kernel, без БД, без моков инфраструктуры. Миллисекунды.
- **Unit-тесты application-слоя (много).** Обработчики команд с фейковыми портами (in-memory репозиторий, фейковый mailer). Быстрые, проверяют сценарий и порядок действий.
- **Интеграционные тесты (средний слой).** Doctrine-репозитории и маппинг против реального PostgreSQL, миграции, ограничения БД, EXPLAIN-проверки для критичных запросов, сериализация, Messenger с транспортом in-memory.
- **Функциональные тесты (мало).** HTTP-сценарии через `WebTestCase`: регистрация, оплата, проверка кодов ответа и прав доступа. Покрывают маршрутизацию, security, обработку исключений.
- **E2E (единицы).** Небольшой набор критичных пользовательских путей, если есть фронтенд, например через Playwright. Запускаются отдельно, не блокируют каждый коммит.

## Что мокаем, а что нет

**Мокаем (или подменяем фейком):**
- внешние HTTP-сервисы (платёжный шлюз, поисковый индекс), через порты и заглушки;
- почту (`MailerInterface` с `TestMailer`/`InMemoryTransport`);
- часы (`ClockInterface`) и генераторы случайных значений;
- очереди: в тестах Messenger с синхронным или in-memory транспортом.

**Не мокаем:**
- PostgreSQL в интеграционных тестах: поведение SQL, индексов, `NULL`, ограничений и уровней изоляции на SQLite не воспроизвести, поэтому фейк БД даёт ложное чувство безопасности;
- Doctrine-маппинг и репозитории: моки EntityManager проверяют реализацию, а не поведение;
- собственные доменные объекты: мок `Money` или `Order` почти всегда признак неверной границы.

Моки уместны на границах системы, а не внутри домена.

## Как сделать быстро и стабильно

**Быстрота**
- Большинство проверок вынести в unit-уровень, интеграционные оставлять для того, что реально зависит от БД.
- Не поднимать kernel там, где он не нужен; в интеграционных тестах кэшировать контейнер и переиспользовать его.
- Для тестов БД: миграции применяются один раз, а изоляция достигается транзакцией, которая откатывается после теста (`DAMA\DoctrineTestBundle` или аналог с savepoint'ами). Удаление и пересоздание схемы на каждый тест слишком медленны.
- Параллельный запуск (`paratest`) с отдельной БД на процесс, если набор вырос.
- Не тестировать одно и то же на всех уровнях.

**Стабильность**
- Детерминированность: фиксированные часы, фиксированные ID (или подменяемый генератор UUID), сортировка в ассертах, где порядок не гарантирован.
- Изоляция данных: никаких зависимостей между тестами, никакого порядка выполнения.
- Не полагаться на автоинкрементные ID и на порядок строк без `ORDER BY`.
- Ошибки PHP (deprecation, notice) превращать в исключения, как я упоминал ранее, чтобы не пропускать предупреждения.
- Проверять количество запросов к БД в ключевых сценариях, это защищает от N+1 регрессий.
- Флаки-тесты не игнорировать: помечать, находить причину, а не ставить повторный запуск «до зелёного».

**Поддержка**
- Тестовые builders/фабрики для агрегатов вместо громоздких фикстур: меняется одно место при изменении модели.
- Фикстуры минимальные, у каждого теста — только то, что ему нужно для проверки.
- Имена тестов описывают поведение: `pay_fails_when_order_is_already_paid`.
- Архитектурные тесты (Deptrac, PHPat) запускаются в том же наборе, чтобы границы слоёв не размывались.

## Что запускать когда

- На каждый коммит: unit и быстрые интеграционные тесты, статический анализ, архитектурные правила.
- На merge в main: полный интеграционный и функциональный набор, проверки миграций.
- По расписанию или перед релизом: E2E, нагрузочные и EXPLAIN-проверки ключевых запросов на данных, близких к продовым.

Итог: тесты домена быстрые и без инфраструктуры, интеграционные — с настоящим PostgreSQL, моки только на внешних границах, а стабильность держится на изоляции, детерминированности и контроле времени выполнения.

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Это классическая задача конкурентного доступа. Без защиты возможны несколько типов проблем, и не все они очевидны.

## Какие проблемы возможны

**Lost update (потерянное обновление).** Оба пользователя читают запись, каждый меняет своё поле или весь объект, и последняя запись молча перезаписывает предыдущую. Например, оба редактируют заказ: один меняет адрес, другой комментарий, и если сохраняется весь объект, изменение первого теряется.

**Нарушение инварианта (write skew).** Каждый процесс проверяет условие на своих данных, и оба проходят проверку, но вместе нарушают правило. Например, два администратора одновременно уменьшают остаток на складе с 1 до 0 при условии «остаток не отрицательный», и остаток уходит в минус.

**Dirty read, non-repeatable read, phantom read.** Зависят от уровня изоляции. В PostgreSQL по умолчанию `READ COMMITTED`: грязного чтения нет, но два одинаковых SELECT внутри транзакции могут вернуть разные данные. Поведение при `REPEATABLE READ` и `SERIALIZABLE` отличается: `SERIALIZABLE` может откатить транзакцию с ошибкой сериализации, её нужно повторять.

**Взаимная блокировка (deadlock).** Пессимистичные блокировки в разном порядке дают ситуацию, когда A ждёт B, а B ждёт A. PostgreSQL обнаруживает это и откатывает одну транзакцию.

**Устаревшие данные в интерфейсе.** Пользователь видит версию, которая уже не актуальна, и принимает решение на её основе.

## Способы защиты

### 1. Оптимистичная блокировка (версия или timestamp)

В записи хранится version. При обновлении проверяется, что версия не изменилась:

```sql
UPDATE orders SET status = $1, version = version + 1
WHERE id = $2 AND version = $3;
-- затронуто 0 строк: конфликт
```

В Doctrine это `#[ORM\Version]`, исключение `OptimisticLockException`.

- Плюсы: без блокировок на время чтения, хорошо масштабируется, понятный механизм, легко работает с HTTP (версию можно передать в форме, ETag, If-Match).
- Минусы: при частых конфликтах растёт число повторов; нужна логика обработки конфликта (повтор или 409 пользователю); защищает только от конфликтов, которые видит сама запись, инварианты между записями не покрывает.

**Выбираю:** для редактирования через веб-интерфейс, когда конфликты редки, а пользователь должен видеть, что данные изменились.

### 2. Пессимистичная блокировка (SELECT ... FOR UPDATE)

```sql
SELECT * FROM stock WHERE product_id = $1 FOR UPDATE;
```

В Doctrine: `LockMode::PESSIMISTIC_WRITE`.

- Плюсы: конфликтов нет, второй процесс ждёт, retry не нужен, защищает и от write skew, если блокируется нужная строка.
- Минусы: блокировка держится до конца транзакции; долгие транзакции и внешние вызовы внутри них дают очереди и deadlock'и; при высокой нагрузке падает пропускная способность.

**Выбираю:** когда конфликт частый и дорогой (резервирование остатка, списание баланса), а транзакция короткая.

### 3. Атомарное условное обновление

```sql
UPDATE stock SET qty = qty - 1
WHERE product_id = $1 AND qty >= 1;
-- затронуто 0 строк: товара нет
```

- Плюсы: одна команда, быстро, без явной блокировки, инвариант держится в самой БД.
- Минусы: логика выражается SQL, а не доменом; сложные правила так не записать.

**Выбираю:** для счётчиков и остатков с простым условием.

### 4. Уровни изоляции SERIALIZABLE

БД сама обнаруживает конфликты зависимостей и откатывает одну из транзакций с ошибкой сериализации.

- Плюсы: защищает даже от write skew без явных блокировок в коде.
- Минусы: нужно повторять транзакции при ошибке; производительность ниже; ошибки непредсказуемы для разработчика, если не обработаны.

**Выбираю:** редко, для узких критичных операций, где логика сложна и явные блокировки не покрывают все случаи. Для всего приложения включать не стоит.

### 5. Ограничения в БД

UNIQUE, CHECK, FOREIGN KEY не дадут нарушить инвариант независимо от того, как прошла проверка в коде. Например, `CHECK (qty >= 0)` ловит уход в минус даже при гонке, хотя ошибка будет исключением, а не понятным ответом.

**Выбираю всегда** как последний барьер для инвариантов, которые выражаются декларативно.

### 6. Сериализация через очередь

Команды над одной сущностью идут в одну очередь с ключом по её ID. Конфликтов нет по построению, но растёт задержка и сложность.

**Выбираю** для высоконагруженных потоков, где порядок важнее мгновенного ответа.

## Как выбирать

1. Конфликты редкие, пользователь интерактивно редактирует: **оптимистичная версия** + понятный ответ 409.
2. Конфликты частые, операция короткая, важна гарантия: **пессимистичная блокировка** `FOR UPDATE`.
3. Счётчик или остаток с простым условием: **условный UPDATE**.
4. Инвариант нужно защитить всегда: **CHECK/UNIQUE/FK** в дополнение к любому из выше.
5. Сложная логика на нескольких строках, где ничего из перечисленного не покрывает: **SERIALIZABLE** с повтором транзакции или пересмотр границ агрегата.

Итог: сначала определить, что именно может разойтись (поле записи, инвариант между записями, очередность), затем выбрать самый лёгкий механизм, который это закрывает, и всегда дополнить его ограничением в БД.

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

У меня нет собственного опыта работы в команде, поэтому ниже описан процесс, который я считаю разумным для PHP/Symfony-проекта с трунк-ориентированным подходом. Он опирается на общепринятые практики, а не на личную историю.

## 1. Постановка задачи

Задача описывается так, чтобы её можно было проверить: какое поведение нужно получить, какие инварианты важны, что считается готовым. Если задача затрагивает модель домена, сначала фиксирую термины с бизнесом (единый язык), чтобы имена в коде совпадали с решением.

Почему так: дешевле уточнить требования до кода, чем переписывать ветку через неделю.

## 2. Ветвление

Основная ветка `main` всегда зелёная и готова к выпуску. Работа ведётся в коротких ветках от `main`:

- `feature/order-payment-retry`, `fix/stock-negative-qty`, `chore/upgrade-symfony-7-4`;
- ветка живёт от одного дня до нескольких дней. Если дольше, задачу стоит разрезать.

Git Flow с `develop` и долгими `release/*` я обычно не выбираю: он создаёт расхождения между ветками и откладывает интеграцию. Исключение, если продукт поставляется версиями нескольким клиентам и нужна поддержка старых версий. Тогда ветки `release/x.y` оправданы.

Почему: короткие ветки означают частую интеграцию и меньше конфликтов. Конфликты и так дорогие, а долгая ветка их только накапливает.

## 3. Коммиты

Формат Conventional Commits, с понятным заголовком в повелительном наклонении и телом, если нужен контекст:

```
fix(order): prevent negative stock on concurrent reservation

Use conditional UPDATE with qty >= 1 and check affected rows.
Refs: #482
```

Правила:
- один коммит — одно логическое изменение, которое проходит тесты;
- рефакторинг и изменение поведения в разных коммитах;
- миграции и код, который от них зависит, в одном PR, но миграция должна быть обратно совместимой для текущего релиза;
- без сообщений вида «fix», «wip», «правки».

Почему: история читается как журнал решений, по ней удобно делать `git bisect` и формировать changelog.

Перед отправкой я привожу историю в порядок интерактивным rebase, чтобы убрать промежуточные «починил опечатку».

## 4. Pull request

Содержит:
- описание: что сделано, зачем, как проверить;
- ссылку на задачу;
- отдельно отмеченные риски: миграции, изменения в публичном API, влияние на производительность (с ссылкой на EXPLAIN, если трогаем запрос);
- результаты локальных проверок.

Размер ориентирую на несколько сотен строк. Большой PR разбиваю на цепочку зависимых PR или выношу подготовительный рефакторинг отдельно.

Почему: ревьюер тратит внимание на то, что понятно из описания, и быстрее находит проблемы в маленьком диффе.

## 5. Автоматические проверки

Пайплайн на каждом PR:
- установка зависимостей и `composer validate`;
- PHP-CS-Fixer или PHP_CodeSniffer;
- PHPStan или Psalm на высоком уровне;
- Deptrac для границ слоёв;
- unit, интеграционные тесты с реальным PostgreSQL;
- проверка миграций на чистой и на предыдущей схеме;
- `doctrine:schema:validate`.

Ревью начинается, когда пайплайн зелёный. Человек не должен ловить то, что ловит машина.

## 6. Ревью

Ревьюер проверяет:
- соответствует ли решение задаче и модели домена (есть ли правило, где оно должно быть);
- инварианты и транзакционные границы;
- обработку ошибок и контракты исключений;
- безопасность: доступы через voters, валидация входа, утечки данных в ответах и логах;
- производительность: число запросов, индексы под новые запросы;
- читаемость и тесты, которые проверяют поведение, а не реализацию.

Стиль и форматирование не обсуждаются вручную, для этого есть линтер.

Правила процесса: минимум один апрувер, автор не мержит свой PR без ревью, комментарии разделяются на блокирующие и рекомендательные. Спорные места решаем созвоном или письменно, но не бесконечной перепиской.

Почему: ревью нужно прежде всего для знания кода и для ловли ошибок, которые тесты не видят (неверная граница, утечка смысла).

## 7. Слияние

Squash merge для коротких веток (история в `main` становится одним коммитом на задачу с понятным заголовком) или rebase merge, если коммиты в ветке осмысленны. Merge-коммиты в ветках фичей не нужны: они усложняют историю.

Почему: линейная история проще для bisect и отката.

## 8. Выкладка

Каждый коммит в `main` собирается в артефакт (образ или архив) с тегом версии. Деплой:
- на staging автоматически;
- на production по кнопке после проверки, с возможностью отката к предыдущему артефакту;
- миграции выполняются отдельным шагом, и каждая миграция обратно совместима с предыдущей версией кода, чтобы откат кода не требовал отката схемы.

Опасные миграции (переименование колонок, удаление данных) разбиваются на несколько релизов: сначала добавить новое, затем перенести, затем удалить старое.

## 9. Релизы и версии

Тег в формате SemVer, если есть внешние потребители API или библиотека. Для внутреннего сервиса достаточно дат или номеров сборок, но тег на каждый деплой обязателен.

Changelog формируется из заголовков коммитов Conventional Commits. Breaking changes помечаются явно (`feat!:` или поле `BREAKING CHANGE` в теле).

Hotfix: ветка от тега продакшена, минимальное исправление, PR в `main` и в ветку релиза, если она есть. Так исправление не теряется при следующем релизе.

## 10. Почему так

- Короткие ветки и частая интеграция снижают стоимость конфликтов.
- Зелёный `main` позволяет выпускать в любой момент.
- Проверки машины освобождают ревью для смысла, а не для стиля.
- Обратно совместимые миграции делают откат безопасным.
- История коммитов служит документацией и инструментом диагностики.

Оговорка: процесс должен соответствовать размеру команды. Для одного разработчика достаточно коротких веток, тестов в CI и тегов. Полный набор ревью и правил имеет смысл, когда в проекте несколько людей и есть риск дорогих ошибок.

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

Важная оговорка: у меня нет собственного опыта ревью в команде, поэтому ниже описан подход, который я считаю разумным и который опирается на общепринятые практики.

## Что такое хорошее ревью

Ревью нужно, чтобы ошибку поймали до продакшена, а знание о коде распространилось по команде. Хорошее ревью делает автора лучше и не тормозит поставку без причины. Плохое ревью либо придирается к стилю, либо пропускает неверную границу, потому что ревьюер «доверяет» автору.

## В первую очередь

Порядок важен: сначала то, что дорого исправлять потом.

1. **Соответствие задаче и домену.** Решает ли PR нужную проблему, и есть ли правило там, где оно должно быть. Частая находка: скидка посчитана в контроллере, а не в агрегате.
2. **Инварианты и транзакции.** Не нарушаются ли инварианты агрегата, не ушёл ли `flush` в домен, не смешаны ли в одной транзакции чужие агрегаты, защищена ли запись от гонок (версия, условный UPDATE).
3. **Контракты и ошибки.** Какие исключения выбрасываются, не проглочено ли что-то, не утекает ли инфраструктура в API.
4. **Безопасность.** Проверяются ли права через voters на объекте, а не только роль, валидируется ли вход, не попадают ли персональные данные в ответы и логи.
5. **Производительность.** Не появился ли N+1, есть ли индекс под новый запрос, не грузится ли коллекция целиком.
6. **Тесты.** Проверяют ли они поведение, а не внутреннюю реализацию, покрывают ли граничные случаи и инварианты.
7. **Читаемость.** Имена из единого языка, понятный поток, отсутствие лишней абстракции.

Стиль, форматирование и порядок импортов ревьюер не обсуждает вручную: это делает линтер.

## Как маркирую замечания

Каждый комментарий помечаю явно, чтобы автор понимал, что обязательно, а что нет:

- **blocker:** ошибка, нарушение инварианта, уязвимость, потеря данных. PR не мержится, пока не исправлено.
- **issue:** проблема, которая не обязательно ломает прод сейчас, но должна быть решена. Можно согласовать сроки, но не молча игнорировать.
- **suggestion:** предложение по улучшению. Автор решает сам, отказ без аргументации нормален.
- **question:** непонимание. Это не критика, а запрос объяснения; иногда ответ показывает, что код нужно переписать понятнее.
- **nit:** мелочь. Не блокирует и не обязательна.

Комментарий формулирую конкретно: что вижу, почему это проблема, как можно иначе. Например, не «плохо», а «здесь скидка считается в контроллере, поэтому её не проверит тест домена; предлагаю перенести в `OrderPricer`, он уже покрыт тестами».

## Разногласия с автором

1. **Сначала понять.** Спрашиваю, почему выбрано такое решение. Часто у автора есть контекст, которого нет в диффе (ограничения, договорённости, нагрузка).
2. **Аргументировать фактами.** Ссылка на инвариант, замер, план запроса, существующую практику в проекте, а не «мне так не нравится».
3. **Различать блокер и вкус.** Если спор о предпочтении, а решение работает и покрыто тестами, уступаю. Если спор о риске, настаиваю.
4. **Не затягивать в переписку.** Больше трёх раундов в комментариях — повод для короткого созвона или письменного решения с указанием, кто принимает финальное слово (обычно владелец модуля).
5. **Если решение принято и оно не нарушает инвариантов, безопасности или договорённостей,** не возвращаюсь к вопросу в каждом PR. Лучше зафиксировать решение в документации или ADR.

## Со стороны автора

Тоже важно: не принимать ревью на личный счёт, отвечать по сути, помечать, что исправлено, и просить повторный просмотр только по изменённым местам. Если замечание непонятно, лучше спросить, чем молча исправить по-своему.

Итог: ревью про риски и смысл, а не про стиль; замечания маркируются так, чтобы было ясно, что блокирует; разногласия решаются фактами и, если нужно, решением владельца модуля.

1. В разделе «Мои заказы» список поддерживает постраничный просмотр всех заказов пользователя, отсортированных по дате создания по убыванию.

Здесь важно, чтобы исполнитель мог решить без вопросов, поэтому указываю ограничения: время ответа, изоляция, отсутствие полнотекстового поиска в этой версии.

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

В PostgreSQL конструкции `FORCE INDEX` нет. Это синтаксис MySQL и MariaDB (`SELECT ... FROM orders FORCE INDEX (idx_name)`), а также похожие `USE INDEX` и `IGNORE INDEX`. Если вы видели его в PostgreSQL-запросе, это либо ошибка синтаксиса, либо код, перенесённый из MySQL.

## Почему в PostgreSQL этого нет

PostgreSQL принципиально не даёт прямых подсказок планировщику в SQL. Выбор плана делает оптимизатор на основе статистики и стоимостной модели, а не по указаниям в запросе. Причины:

- Подсказки быстро устаревают: данные меняются, индекс перестаёт быть оптимальным, а подсказка продолжает его навязывать.
- Они скрывают реальную причину проблемы, обычно устаревшую статистику или неверную оценку селективности.
- Они усложняют переносимость и поддержку запросов.

## Как добиться аналогичного эффекта

Если нужно повлиять на план, в PostgreSQL используют такие средства:

- **Исправить причину.** Обновить статистику через `ANALYZE`, при необходимости создать расширенную статистику `CREATE STATISTICS` для коррелированных колонок, проверить, что autovacuum работает.
- **Правильный индекс.** Составной, частичный или функциональный индекс под конкретный запрос часто решает задачу лучше подсказки.
- **Переписать запрос.** Например, условие без функции над колонкой, без неявного приведения типов, `EXISTS` вместо `NOT IN`.
- **Настройки на уровне сессии** для диагностики, а не для продакшена: `SET enable_seqscan = off;` временно запрещает последовательное сканирование, чтобы проверить, даст ли индекс лучший план. Это инструмент исследования, а не постоянное решение.
- **Параметры стоимости** (`random_page_cost`, `effective_cache_size`), если планировщик систематически ошибается из-за неверных предположений о диске и кэше.
- **Расширение `pg_hint_plan`**, которое даёт подсказки через комментарии в запросе. Используется редко, требует установки, и я бы применял его только после того, как исчерпаны все остальные варианты.

## Итог

`FORCE INDEX` в PostgreSQL не существует. Вместо принудительного выбора индекса стоит проверить план через `EXPLAIN (ANALYZE, BUFFERS)`, понять, почему оптимизатор не выбирает индекс, и устранить причину: статистику, индекс или сам запрос.

Опыта измерений у меня нет, поэтому не могу назвать процент «по моему опыту». Могу объяснить, что известно о механизме, и что важно помнить при оценке.

## Что делает strict_types

Директива влияет на то, как проверяются аргументы при вызове функции и возвращаемые значения, а не на скорость работы всего кода. Для вызова из файла с `strict_types=1` движок проверяет тип без приведения: если пришла строка вместо `int`, сразу `TypeError`. В нестрогом режиме он попытался бы привести значение, а это дополнительная работа. Но разница в том, что в строгом режиме проверка не делает лишней работы при успешном вызове, потому что совпадение типов и так обнаруживается.

Поэтому накладные расходы сводятся к небольшой разнице в обработке вызова, а не к отдельной проверке, которую добавляет директива. На практике в строгом режиме иногда даже меньше преобразований, чем в обычном.

## Почему измерять процент бессмысленно

- Директива не меняет поведение оптимизатора и JIT-компилятора заметно для типичного кода.
- Время запроса в веб-приложении определяется БД, сетью, сериализацией, рендерингом, а не проверкой скалярных аргументов. Доля вызовов с приведением типов в таком коде ничтожна.
- Эффект проявляется только в очень горячих циклах с миллионами вызовов функций с приведением типов, и там вопрос решается профилированием конкретного места.

## Как проверить на своём коде

- Запустить бенчмарк (например, PhpBench) на реальном горячем пути, с и без директивы, с несколькими прогонами и доверительным интервалом.
- Смотреть профилировщик (Xdebug profiler, Blackfire, Tideways), а не общее время запроса.
- Учитывать, что различие касается только вызовов из файла с директивой, и если в нём много приведений, которые раньше молча работали, код сломается, это большая цена, чем микросекунды.

Итог: `strict_types=1` почти не влияет на производительность, и в типичном приложении его стоит включать ради корректности. Точный процент можно получить только замером на конкретной нагрузке.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

В Doctrine ORM составные первичные ключи поддерживаются. Ограничение, которое иногда путают с отсутствием поддержки, касается генерации значений: автогенерация (`IDENTITY`, sequence) работает только для одиночного ключа, поэтому составной ключ заполняется приложением.

## Как это выглядит

Ключ объявляется несколькими полями с `#[ORM\Id]`:

```php
#[ORM\Entity]
#[ORM\Table(name: 'order_lines')]
class OrderLine
{
    #[ORM\Id]
    #[ORM\ManyToOne(targetEntity: Order::class)]
    #[ORM\JoinColumn(name: 'order_id', nullable: false, onDelete: 'CASCADE')]
    private Order $order;

    #[ORM\Id]
    #[ORM\Column(type: 'integer')]
    private int $lineNumber;

    #[ORM\Column]
    private int $qty;

    public function __construct(Order $order, int $lineNumber, int $qty)
    {
        $this->order = $order;
        $this->lineNumber = $lineNumber;
        $this->qty = $qty;
    }
}
```

Здесь ключ — пара `(order_id, line_number)`. Полезные детали:

- `ManyToOne` в составном ключе допустим, и тогда связь участвует в идентичности. Ключ `order_id` при этом тоже становится частью первичного ключа.
- Значение `lineNumber` задаёт агрегат. Его нужно вычислять в корне (`max + 1`), а при гонке защищаться версией корня, как обсуждалось ранее, иначе два процесса получат одинаковый номер и упадут на уникальном ключе.
- `find()` принимает массив: `$em->find(OrderLine::class, ['order' => $orderId, 'lineNumber' => 3])`. Для связи можно передать объект или идентификатор.
- Для `ManyToOne` в ключе лучше использовать `#[ORM\Id]` вместе с явным `JoinColumn`, и не забывать, что при загрузке Doctrine создаёт прокси `Order`.

## Как с этим живут в реальных проектах

Обычно выбирают один из трёх вариантов:

1. **Суррогатный ключ (UUID или bigint) плюс уникальный индекс** на бизнес-комбинацию. Самый распространённый вариант в Symfony-проектах. Удобно для связей, URL, API и `find()`, а уникальность держится ограничением в БД. Минус: лишняя колонка и индекс.
2. **Составной ключ как есть**, когда сущность по природе зависит от родителя и не имеет самостоятельной идентичности (строки заказа, теги у товара, связи многие-ко-многим с атрибутами). Подходит для таблиц-связок, где нужна скорость и естественная идентичность.
3. **Составной ключ с идентификатором-значением** (`Embeddable` для id), если комбинация полей сама является понятием домена. Аккуратно: равенство и сериализация идентификатора должны быть продуманы.

Практические подводные камни:

- Вложенные ключи усложняют маршруты: в URL приходится передавать несколько параметров или кодировать ключ.
- Каскады и `orphanRemoval` работают, но удаление родителя тянет за собой детей через FK `ON DELETE CASCADE`. Это лучше дублировать в БД.
- Doctrine не умеет `IDENTITY`-генерацию для составного ключа, поэтому `persist` без заполненных полей даст ошибку или пустой ключ. Значения должны быть известны до `flush`.
- Сравнение сущностей и кэширование второго уровня работают по составному ключу, но в логах и профилировщике идентификатор выглядит менее удобно.

## Итог

Составной ключ в Doctrine — рабочая возможность, а не ограничение. Выбирать его стоит, когда дочерняя сущность не имеет смысла без родителя и её естественная идентичность состоит из нескольких полей. Если же нужны удобные связи, API и независимость от родителя, надёжнее суррогатный ключ и уникальное ограничение в PostgreSQL.

## Q27 · Мини-код-ревью

**Интервьюер:** Посмотри на этот код:

```php
class OrderController
{
    public function pay(Request $req): Response
    {
        $id = $req->get('order_id');
        $pdo = DB::connect();
        $order = $pdo->query("SELECT * FROM orders WHERE id = $id")->fetch();
        if (!$order) {
            return new Response('not found', 404);
        }
        $order['status'] = 'paid';
        $pdo->exec("UPDATE orders SET status = 'paid' WHERE id = $id");
        Mailer::send($order['email'], 'Ваш заказ оплачен');
        (new Logger())->log('paid ' . $id);
        return new Response('ok');
    }
}
```

Какие проблемы ты видишь и как бы ты этот код переделал? С чего начал бы и почему?

**Кандидат:**

Начну с самого опасного: этот код уязвим для SQL-инъекции. `$id` берётся из запроса и подставляется в строку SQL без экранирования, поэтому `order_id=1 OR 1=1` вернёт заказ, а `1; DROP TABLE orders` может уничтожить данные (PDO в обычном `query()` допускает стэкинг). Это блокер, и с него надо начинать.

## Что видно в коде

**Безопасность**
- SQL-инъекция через `$id` в `query()` и `exec()`.
- Нет проверки прав: любой, кто знает ID, может оплатить чужой заказ. Нет проверки владельца и текущего статуса.
- Ответ `not found` без проверки формата `order_id`.
- Персональные данные (`email`) читаются, хотя нужны только для письма.

**Бизнес-логика и домен**
- Статус меняется напрямую через SQL, минуя доменные правила: можно «оплатить» отменённый заказ или уже оплаченный.
- Нет доменного события `OrderPaid`, поэтому логика почты и логирования разбросана по контроллеру.
- Заказ загружается как массив, а не как агрегат, поэтому инварианты не проверяются.

**Транзакции и согласованность**
- Чтение, обновление и отправка письма не в одной транзакции. Гонка: два запроса оба пройдут проверку статуса.
- Письмо отправляется синхронно внутри HTTP-запроса: медленный SMTP тормозит ответ, и при сбое письма статус уже изменён, а пользователь получает 500 или, что хуже, молча теряет уведомление.
- Нет блокировки или версии, lost update возможен.

**Ошибки и наблюдаемость**
- `Mailer::send` и `Logger` — статические или самодельные вызовы, их нельзя подменить в тестах.
- Логируется `'paid ' . $id` без контекста и без обработки ошибок.
- Не исключений, а строки `'not found'` и `'ok'` в ответе; нет кодов ошибок в API-стиле.
- `DB::connect()` создаётся прямо в методе: соединение не управляется контейнером.

**Архитектура**
- Контроллер делает всё: HTTP, SQL, бизнес-правило, почту, лог.

## Как переделал бы

Порядок такой: сначала безопасность и корректность, потом архитектура, потом производительность.

**Шаг 1. Закрыть инъекцию и права.** Это можно сделать немедленно, даже до рефакторинга. Минимальный вариант на PDO с параметрами:

```php
$stmt = $pdo->prepare('SELECT * FROM orders WHERE id = :id');
$stmt->execute(['id' => $id]);
```

Но правильнее сразу перейти на Doctrine и проверку владельца, например через voter.

**Шаг 2. Переложить логику в домен и application-слой.**

```php
#[IsGranted('ORDER_PAY', subject: 'order')]
public function pay(Order $order, PayOrderHandler $handler): Response
{
    $handler(new PayOrderCommand($order->getId()));

    return $this->json(['status' => 'paid'], Response::HTTP_OK);
}
```

Route с `Order` через ParamConverter/`#[MapEntity]` (ID валидируется как UUID или int). Контроллер не меняет статус и не знает про SMTP.

**Шаг 3. Агрегат меняет своё состояние.**

```php
public function pay(): void
{
    if ($this->status !== OrderStatus::Draft) {
        throw new OrderNotPayable($this->id, $this->status);
    }
    $this->status = OrderStatus::Paid;
    $this->events[] = new OrderPaid($this->id);
}
```

**Шаг 4. Обработчик с транзакцией и версией.** Загрузка, `pay()`, `flush()` в одной транзакции, версия корня защищает от гонки, после коммита публикуются события.

**Шаг 5. Письмо и лог — асинхронно.** Обработчик `OrderPaid` через Messenger отправляет письмо. Email загружается уже там, по ID. Логирование через PSR-3 `LoggerInterface`, внедряется через конструктор, с контекстом: `['order_id' => $id]`.

**Шаг 6. Ответ и ошибки.** Доменные исключения маппятся в 404/409/422 на границе. Внутренние детали не попадают в ответ.

**Шаг 7. Тесты.** Unit-тест `Order::pay` (из Draft проходит, из Paid падает), тест обработчика с фейковым mailer, функциональный тест: чужой заказ даёт 403, повторная оплата 409, инъекция `1 OR 1=1` даёт 404 или 422.

## Почему с этого порядка

Сначала безопасность, потому что инъекция и отсутствие проверки прав — то, что можно эксплуатировать прямо сейчас, и это важнее любой архитектуры. Затем корректность статуса, потому что без неё рефакторинг будет переносить ошибку. Архитектуру и асинхронность делаю после, когда поведение зафиксировано тестами. И обязательно сообщил бы команде о том, что уязвимость уже в проде: нужно проверить логи на подозрительные запросы и, возможно, сбросить доступы к БД.

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Главная проблема: сущность `User` знает о инфраструктуре. Она хранит `EntityManagerInterface` и сама вызывает `flush()`. Это нарушает почти все правила, которые мы обсуждали.

## Что не так

**Нарушение правила зависимостей.** Домен зависит от Doctrine. Тесты `changeEmail` потребуют БД или мок EntityManager, что делает домен медленным и хрупким. Сущность нельзя использовать вне Doctrine без подмены инфраструктуры.

**Домен сохраняет сам себя.** Агрегат не должен фиксировать транзакции. Это задача application-слоя: он решает, когда и в каком контексте сохранять изменения. Вызов `flush()` внутри метода модели делает невозможным объединение нескольких изменений в одну транзакцию и ломает границы, которые мы выстраивали.

**Нет валидации и инвариантов.** `changeEmail` принимает любую строку: пустую, без `@`, с пробелами, в верхнем регистре. Email должен быть объектом-значением, который гарантирует корректность при создании.

**Нет события и идентичности.** Смена email — значимый факт (например, нужно подтвердить новый адрес, отправить уведомление на старый). Сейчас об этом ничего не известно домену. Нет `id`, без которого нельзя говорить о сущности как о сущности.

**Конструктор принимает инфраструктуру.** Создать `User` в тесте или в миграции данных без EntityManager невозможно. Конструктор также не гарантирует, что пользователь создан в валидном состоянии.

**Тип `string` вместо понятия домена.** Email — не просто строка, а понятие с правилами.

## Как бы исправил

**1. Объект-значение для email.**

```php
final readonly class Email
{
    private string $value;

    public function __construct(string $value)
    {
        $normalized = strtolower(trim($value));
        if (!filter_var($normalized, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidEmail($value);
        }
        $this->value = $normalized;
    }

    public function value(): string
    {
        return $this->value;
    }

    public function equals(self $other): bool
    {
        return $this->value === $other->value;
    }
}
```

**2. Чистая сущность без инфраструктуры.** Идентичность и инварианты в конструкторе, мутация через метод с доменным событием.

```php
final class User
{
    /** @var list<object> */
    private array $events = [];

    public function __construct(
        private readonly UserId $id,
        private Email $email,
    ) {}

    public function id(): UserId
    {
        return $this->id;
    }

    public function email(): Email
    {
        return $this->email;
    }

    public function changeEmail(Email $newEmail): void
    {
        if ($this->email->equals($newEmail)) {
            return;
        }
        $old = $this->email;
        $this->email = $newEmail;
        $this->events[] = new UserEmailChanged($this->id, $old, $newEmail);
    }

    /** @return list<object> */
    public function pullEvents(): array
    {
        $events = $this->events;
        $this->events = [];

        return $events;
    }
}
```

**3. Сохранение и транзакции вынесены наружу.** Use case в application-слое:

```php
final class ChangeUserEmailHandler
{
    public function __construct(
        private UserRepository $users,
        private TransactionalRunner $tx,
        private EventDispatcher $events,
    ) {}

    public function __invoke(ChangeUserEmailCommand $cmd): void
    {
        $user = $this->users->get($cmd->userId);
        $user->changeEmail(new Email($cmd->email));

        $this->tx->run(fn () => $this->users->save($user));

        foreach ($user->pullEvents() as $event) {
            $this->events->dispatch($event);
        }
    }
}
```

**4. Маппинг переезжает в Infrastructure.** Doctrine-маппинг либо в XML/YAML рядом с инфраструктурой, либо в отдельном маппере, который преобразует `User` в запись. Если используются атрибуты, это компромисс, который стоит осознанно зафиксировать. Email сохраняется через кастомный DBAL-тип, как обсуждали раньше. Интерфейс `UserRepository` лежит в домене, реализация `DoctrineUserRepository` в инфраструктуре.

## Что проверить после рефакторинга

- Unit-тест `User::changeEmail` без БД и kernel: смена на тот же адрес ничего не меняет, смена на новый порождает событие.
- Тест `Email`: нормализация регистра, отказ от невалидного формата.
- Интеграционный тест репозитория на PostgreSQL: сохранённый и загруженный email совпадают.
- Уникальность email через UNIQUE-ограничение в БД, а не только проверку в коде.

## С чего начал бы

Сначала вынес бы `flush()` из сущности: это самое вредное и самое простое исправление, оно сразу разрывает связь домена с инфраструктурой. Затем ввёл бы `Email` как объект-значение, потому что это снимает целый класс ошибок во всех местах, где используется email. И только потом перенёс бы сохранение в application-слой и добавил события. Так каждый шаг можно проверить тестами, а поведение не меняется неожиданно.

**Интервьюер:** Тебе нужно решить техническую проблему на незнакомых тебе технологии или стеке. Опиши последовательность своих действий от первого взгляда на задачу до уверенного ответа о сроках решения. Когда, по-твоему, нужно просить помощи у команды, а когда разбираться самому?

**Кандидат:**

Ниже описан подход, который я считаю разумным. Личного опыта работы с незнакомым стеком в команде у меня нет, поэтому это методика, а не воспоминание.

## 1. Первый взгляд: зафиксировать задачу

Прежде чем трогать технологию, отвечаю на вопросы, которые определяют, что вообще считается решением:

- Какой симптом и какое ожидаемое поведение? Что воспроизводится, при каких условиях, кто затронут?
- Что уже пробовали и какие данные есть (логи, метрики, версии)?
- Что будет считаться готовым: конкретный тест, замер, поведение в staging?

Записываю это в задаче, чтобы не уйти в исследование ради исследования.

## 2. Оценить незнакомое, не погружаясь сразу

Для стека, который не знаю, сначала составляю карту, а не читаю всё подряд:

- официальная документация по нужной части (а не по всему фреймворку);
- как устроен механизм, который участвует в проблеме, в 2–3 абзацах своими словами;
- как технология обычно ломается и какие диагностические инструменты у неё есть (логи, профилировщики, `--help`, режимы отладки);
- похожие проблемы в issue-трекере проекта, отличая актуальные от устаревших версий.

Цель: за короткое время понять, где искать причину, а не выучить стек целиком.

## 3. Воспроизвести и сузить

Самый важный шаг. Строю минимальный воспроизводящий пример: отключаю всё лишнее, меняю по одному параметру, сравниваю «работает» и «не работает». Бинарный поиск по изменениям (`git bisect`, откат конфигурации, по половине модулей) часто быстрее, чем чтение кода.

Записываю гипотезы и проверяю каждую измерением. Решение без воспроизведения я не считаю решением.

## 4. Найти причину и проверить исправление

- Причина подтверждается: изменение одного фактора меняет результат.
- Исправление проверяется тестом, который падал до правки.
- Нет побочных эффектов: прогоняю соседние сценарии.

## 5. Оценка сроков

Срок оцениваю не по ощущению, а по этапам, каждый из которых имеет условие завершения:

- понимание механизма и воспроизведение (часть дня, если стек простой; несколько дней, если он сложный);
- поиск причины (зависит от того, насколько быстро сужается пространство гипотез);
- исправление и тесты;
- ревью и выкатка.

Для каждого этапа указываю неопределённость и сигнал, что оценка пересматривается. Например: «если к концу второго дня не воспроизвели проблему, меняем стратегию и подключаем эксперта». Так вместо одной цифры человек получает диапазон и понимает, от чего он зависит.

## 6. Когда просить помощи

Просить помощи стоит раньше, чем кажется неловко, если:

- прошло заметно больше отведённого времени без подтверждённой гипотезы;
- проблема в production, затрагивает пользователей или данные, и нужны права или знание инфраструктуры;
- речь о части системы, за которую отвечает другой человек, и правильное решение зависит от его договорённостей;
- не хватает доступа к данным или окружению, которые есть только у команды;
- есть риск сделать необратимое изменение, а контекст неполный.

Просьба должна быть конкретной: что уже проверено, какая гипотеза, что нужно от собеседника. Это экономит время и обоим.

## 7. Когда разбираться самому

Самостоятельно стоит идти, если:

- задача ограничена и воспроизводится в изолированном окружении;
- вопрос в документации и механизме, который можно понять за разумное время;
- помощь потребует от другого человека больше времени, чем сам разбор;
- речь о понимании, которое в любом случае пригодится мне дальше.

Но и тогда я ставлю временной лимит и сигнал: если лимит прошёл, спрашиваю.

Итог: сначала фиксирую, что считать решением, затем воспроизвожу и сужаю, оцениваю сроки по этапам с условиями, а помощь прошу рано, когда риск, доступ или чужой контекст важнее самостоятельного поиска.
