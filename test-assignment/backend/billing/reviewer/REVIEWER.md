# Этап 3 — код-ревью локальными моделями (reviewer/)

Место в системе: этап 1 — знания «из базы» (собес без харнеса), этап 2 —
агентное программирование (тестовое задание в pi), этап 3 — **ревью чужого
кода**: модель-ревьюер получает решение другого прогона этапа 2 и проводит
код-ревью в среде pi. Код не правит и не исполняет — только читает и судит.

Это отдельная способность, которую этапы 1–2 не меряют: писать код и судить
код — разные навыки. Этап 3 отвечает и на прикладной вопрос: коррелирует ли
«умеет писать» с «умеет ревьюить» (модели, сами писавшие на 2/11 — смогут ли
разглядеть дефекты у других?).

## Что меряем

1. **Функциональное соответствие заданию** — видно ли по коду (без запуска),
   что сделано по TASK.md, а что сломано или отсутствует.
2. **Качество суждения** — оси A/B рубрики в сравнении с эталоном
   (замороженные вердикты ярусов 3/4 по этому же коду).
3. **Работа с метриками** — метрики даны как запахи (указатели, где смотреть,
   по Фаулеру), а не вердикт: ревьюер должен проверить их по коду, а не
   пересказать. В реальности ревью работает так же.
4. **Слепое пятно** — каверзное решение, которое слепой судья яруса 4
   переоценил (4.0 при задвоенных суммах отчётов): заметит ли ревьюер то,
   что не увидел судья?

## Слепой протокол

Ревьюер **не получает**: результат чекера, golden, fixtures, чекер,
scorecard'ы, имя модели-автора, путь к прогону (провенанс вырезается даже из
metrics.json). Знание вердикта чекера превратило бы ревью в пересказ —
измеряли бы пересказ, а не ревью.

Ревьюер **получает** (рабочая копия вне дерева Models):

| Файл | Что это |
|---|---|
| `TASK.md` | задание |
| `AGENTS.md` | памятка, которую получал кандидат (нужна для оси B) |
| `solution/` | дерево решения (полный репозиторий результата без vendor/var) |
| `diff.patch` | дифф решения против каркаса |
| `metrics.json` | санированные метрики качества (phpstan/phpmd/phpcs/psalm/scc/AST) |
| `MANIFEST.txt` | список файлов solution/ с размерами (для навигации) |

## Объекты ревью

Четыре решения этапа 2 (полный выбор — в `references/README.md`):

| Слаг | Прогон-источник | Чекер | Ярус 3 (A/B) | Ярус 4 (A) | Роль |
|---|---|---|---|---|---|
| `good` | huihui-ai-pi-100k run-02 | 13/13 | 3.5/4.0 | 3.5 | эталон полного зачёта |
| `mid` | muse-glimmer run-03 | 11/11+0б | 2.5/2.5 | 2.5 | всё работает, архитектурно слабое |
| `tricky` | qwen3.8-27b-pi-100k run-03 | 9/11 | 2.5/3.0 | **4.0** | слепое пятно: суммы задвоены |
| `bad` | gemma4-31b-it-qat-pi-100k run-02 | 8/11 | 1.5/1.0 | 2.5 | усечение вместо HALF_UP, дубли, нет артефактов |

Принцип пары: «плохое» — не трэш (команды и сущности на месте, дефекты в
арифметике и дедупликации), «хорошее» — не идеальное (N+1, память вместо
GROUP BY, phpstan 49). Различение тонкое — вот что меряем. `mid` отделяет
«работает» от «качественно», `tricky` — главный тест на слепое пятно.

Эталон-карточки (`references/*.json`) заморожены 2026-10-30; после старта
прогонов не меняются.

## Что делает ревьюер

1. Читает TASK.md, AGENTS.md, metrics.json, MANIFEST.txt, diff.patch и код
   в solution/ — **единственный инструмент: read**.
2. Проверяет функциональное соответствие по коду: импорт с идемпотентностью,
   тарификация (valid_from, оф-пик через полночь, cache-цены, одно округление
   HALF_UP, деньги без float), unrated, три отчёта, эксклюзивность --to,
   артефакты.
3. Проверяет сигналы метрик по коду: реальный дефект или ложное срабатывание;
   отсутствие тестов и неотрефлексированные ошибки статики — минус процессу.
4. Финальное сообщение — **JSON одной строкой** (машиночитаемая сверка без LLM):

```json
{"axis_a": 3.5, "axis_b": 4.0, "functional": 4.0,
 "defects": [{"file": "...", "lines": "10-15", "severity": "critical|major|minor", "desc": "..."}],
 "note": "сильные стороны, что подтвердилось/опроверглось из метрик, бонус, итог"}
```

Оси A/B — дескрипторы рубрики яруса 3 (`../RUBRIC.md`), переписанные под
слепой протокол (без ссылок на чекер). Шкала `functional`: 0 — не выполнено;
1 — меньшая часть; 2 — около половины; 3 — большинство (1–2 обязательных
сломаны); 4 — всё обязательное; бонус не добавляет и не штрафует.
Каждый дефект — с файлом и строками; неуверенность — severity minor и
формулировка «подозрение»; верить коду, а не PR-описаниям.

## Изоляция и целостность

- **инструменты ограничены структурно**: `pi --tools read` — edit/write/bash
  отключены флагом, а не инструкцией;
- рабочая копия материалов — во временном каталоге **вне дерева Models**
  (pi не видит AGENTS.md рабочего репозитория);
- `PI_CODING_AGENT_DIR` изолирован, models.json на одну модель (код
  `runner_pi.py` переиспользуется);
- **манифест sha256** всех файлов рабочей копии до и после прогона: любое
  изменение = прогон compromised, в свод не попадает;
- fixtures/checker/golden в копию не попадают физически; vendor отсутствует —
  код нечем исполнить даже случайно.

## Прогон

```bash
cd test-assignment/backend/billing/reviewer

python3 runner_reviewer.py --model qwen3.8:27b-pi-100k \
  --target models/huihui-ai-pi-100k/backend/test-assignment/run-02 \
  --results models/qwen3.8-27b-pi-100k/backend/review/run-01
```

- `--target` обязан быть объектом эталон-сетки (иначе сверка невозможна);
- теги без `pi-100k` — через серверные алиасы `-ctx100k` (как в этапе 2);
- параметры: thinking max, контекст 102400, таймаут 3600 с;
- опции: `--thinking`, `--context`, `--timeout`, `--max-tokens`, `--smoke`,
  `--keep`; провайдер `--provider deepseek` — для будущего сравнения
  (облачные в эту серию не входят);
- результат в `models/<модель-ревьюер>/backend/review/run-XX/`:
  `run.json` (параметры, целостность, токены, parse_ok), `pi-session/`,
  `pi-run.log`, `review.json` (распарсенный вердикт), `review.md` (сырой
  финальный ответ).

## Сверка с судьёй (эталоном)

```bash
python3 score_review.py models/qwen3.8-27b-pi-100k/backend/review/run-01 [...]
```

- автоматически: |ΔA|, |ΔB|, |ΔF| против `references/*.json`; черновик
  зачёта (калибруется пилотом): |Δ| ≤ 0.5 — зачёт, ≤ 1.0 — частично, больше —
  промах. Результат — `review-score.json` рядом с вердиктом;
- вручную на пилоте: **recall** — какие известные дефекты эталона ревьюер
  нашёл (сверка списков печатается скриптом), и **precision** — какие из его
  дефектов выдуманы. Позже эти две ручные операции можно отдать скрипту-судье
  (паттерн `judge_tier3.py`);
- отдельная метрика «поймал слепое пятно»: нашёл ли ревьюер задвоение сумм
  на `tricky` (D1) — то, что пропустил ярус 4.

## План

1. **Пилот (методика)**: qwen3.8:27b-pi-100k (сильная) + gemma4:e2b-ctx100k
   (слабая) × 4 решения × 1 прогон = 8 сессий. Отладка промпта, JSON-контракта,
   целостности; калибровка порогов зачёта.
2. **Сетка**: 14 локальных моделей × 4 решения × 3 прогона. Облачные — не в
   этой серии (максимум deepseek для сравнения, отдельным решением).
3. **Свод** (`reports/`): матрица ревьюеров × решения (Δ-баллы, recall,
   пойманные ловушки), корреляция «пишет ↔ ревьюит» (итоги этапа 2 против
   этапа 3).

## Правила валидности прогона ревью

Прогон засчитывается, только если:
1. **целостность ok** (манифест до/после совпал);
2. **есть чтение** (`tool_calls > 0` в run.json): вербальный вердикт без
   единого tool-call — выдумка, а не ревью (e2b на пилоте выдала три таких
   вердикта подряд, с ссылками на несуществующие файлы);
3. **JSON-вердикт распарсен** (`parse_ok`); экстрактор устойчив к типовым
   поломкам (markdown-обрамление, невалидные `\`-эскейпы — qwen ломает JSON
   путями вида `\Что-то`).

## Уроки пилота (2026-10-31)

Пилот: qwen3.8:27b-pi-100k + gemma4:e2b-ctx100k × 4 решения (по 1 прогону).

1. **Эталон ошибается — и независимое ревью это находит.** Механизм дефекта
   «плохого» решения из вердикта яруса 3 («усечение вместо HALF_UP») был
   опровергнут рантайм-проверкой php 8.5, на которую вышло ревью qwen
   самостоятельным пересчётом; версия «задвоение учёта» для tricky тоже
   оказалась ошибкой чтения судейского диффа (токены в отчётах совпадают с
   golden, расходятся только стоимости — тарифное правило, не дубли).
   Эталон-карточки исправлены (поле changelog в каждой); ожидаемые баллы не
   двигались — якорь тот же (факты чекера). Вывод методики: |Δ| от эталона —
   не «ошибка ревьюера», а повод для разбора; верифицировать спор — кодом.
2. **e2b не способна к агентному ревью** (0 tool-calls в 3 прогонах из 4,
   fabricated-вердикты). В сетку такие модели включать бессмысленно — гейт
   п.2 отсекает; дискриминативность шкалы на ревью для слабых моделей не
   измеряется этим этапом.
3. **Ложные срабатывания — главная статья промахов qwen**: Observation
   «метода нет на OutputInterface → PHP fatal» оказалось неверной (Symfony
   передаёт ConsoleOutput, у которого метод есть; чекер это и подтвердил) —
   из-за неё занижено functional на «mid». Показательный тип ошибки: поверить
   статической сигнатуре против рантайм-полиморфизма.
4. **Слепое пятно яруса 4 не преодолено чтением кода**: на tricky ревью qwen
   просчитало worked example (он сходится!), поверило и поставило F=4 —
   дефект живёт в больших фикстурах (данные-зависимый). Слепая ревью-сессия
   повторяет судьбу слепого судьи, если не проверить границы данных. Заодно
   qwen-ревью выдало правдоподобную гипотезу настоящего механизма
   (квантование DATETIME на границах окна) — кандидат на отдельную проверку.
5. **Сильное ревью — это независимая проверка, а не чтение списком**: лучшая
   сессия (qwen × good) пересчитала worked example, сверила phpunit-счётчик
   с PR-заявкой, опровергла запах LCOM4 («артефакт value-объектов») и нашла
   фактические ошибки в PR_DESCRIPTION (ссылка на несуществующий файл).

## Ограничения валидности

- эталон — тоже LLM-вердикты (ярусы 3/4), а не абсолютная истина; расхождение
  ревьюера с эталоном может быть находкой, а не ошибкой (note'ы смотрим
  вручную, особенно на `tricky`);
- статическое ревью без запуска кода — осознанный выбор (изоляция,
  воспроизводимость); запускающее ревью — возможное расширение v2;
- слабая модель может не выдержать JSON-контракт: `parse_ok=false` фиксируется
  в run.json, сырой ответ остаётся в review.md.
