# Учёт расходов на LLM-токены — описание pull request

## Что сделано

Полная реализация задания из `TASK.md` (включая бонус):

| Команда | Назначение |
|---|---|
| `app:prices:import <file>` | загрузка справочника цен (JSON): идемпотентный upsert провайдеров, моделей, строк цен |
| `app:usage:import <file>` | загрузка событий использования (JSONL) с дедупликацией по `(provider, provider_request_id)` |
| `app:billing:rate` | тарификация всех ещё unrated-событий (повторные попытки включены) |
| `app:billing:report [--from=] [--to=]` | CSV-отчёт расходов по группам (user, model) с TOTAL |
| `app:billing:reprice <file>` | **бонус**: ретро-коррекция цена с пересчётом затронутых событий |

Схема БД разворачивается на чистой базе: `make migrate` (создание БД +
миграция `Version20260228000001InitialSchema`).

## Ключевые решения и допущения

1. **Деньги — только десятичные строки (bcmath)**. float ни в одном месте
   цепочки расчёта. Промежуточные вычисления — в масштабе 24; единственное
   округление — HALF_UP до 6 знаков (2.5 → 3), применяется к итоговой
   стоимости события; оф-пиковой множитель умножается до этого округления.
2. **Выбор цены** — строка модели с наибольшим `valid_from <= ts` события
   (`valid_from` включительно). Реализовано запросом репозитория
   (`ORDER BY valid_from DESC LIMIT 1 WHERE valid_from <= ts`).
3. **Оф-пик** — окно `[start, end)` по времени суток UTC, может переходить
   через полночь (16:30–00:30); `start == end` трактовано как окно на
   весь день. Политика читается из справочника провайдера в момент
   тарификации (не дублируется в событии).
4. **Идемпотентность приёма событий** — на уровне БД:
   `INSERT ... ON CONFLICT (provider, request_id) DO NOTHING`
   (уникальный индекс — в схеме). Повторная доставка строки не создаёт и не
   изменяет ничего; файл обрабатывается одной транзакцией.
5. **Unrated — не ошибка**. События без применимой строки цен остаются с
   статусом `unrated`, в отчёт не попадают; каждый запуск
   `app:billing:rate` повторяет попытку для всех ещё unrated (цены могли
   подтянуться позже). Для каждого unrated-события вывода — строка в stderr:
   `UNRATED <provider>/<id> <ts> no_price`.
6. **Хранение события**: `cost` — строка из 6 знаков; `price_valid_from` —
   ссылка на применённую строку цен (натуральный ключ, не FK); статус —
   `unrated`/`rated`. Связи с `providers`/`models` намеренно не FK:
   справочник допускает поправки (reprice), удаление/правка событий — за
   рамками задачи, и жёсткий FK только усложнил бы upsert'ы каталога.
7. **Реестр цен** — отдельная таблица `price_rows` со своим PK:
   уникальный ключ `(provider, model, valid_from)` покрывает upsert и
   запрос «последняя строка до момента».
8. **Реестр моделей** — отдельная таблица `models`: ключ `(provider, code)`;
   `usage_events.model` хранит код модели (без провайдера в значении) —
   состав «провайдер/код» восстанавливается в отчёте (`provider` лежит
   тем же событием).
9. **Реестр провайдеров** — отдельная таблица, ключ `code`; off-peak
   параметры в полях провайдера (окно + множитель).
10. **`reprice` (бонус)** — применены исправленные строки (upsert), затем
    пересчитаны все события, которые тарифицировались заменёнными строками:
    ищется применимая к событию строка на момент пересчёта (нужна быть
    строка с наибольшим `valid_from <= ts`); если строки цены больше нет,
    событие возвращается в `unrated`. Дельта = Σ(новая − старая) по
    затронутым событиям. В stderr — диагностика; в stdout точно:
    `REPRICED_EVENTS=<n>` и `REPRICE_DELTA_USD=<x.xxxxxx>`. Транзакционная
    операция: при ошибке ничего не поменялось.
11. **Конвенции вывода** — данные (итоговые строки, CSV) — в stdout;
    диагностика и ошибки — в stderr; коды возврата: 0 — успех, 1 — ошибка.
12. **Схема БД** управляется Doctrine Migrations (файл в `migrations/`,
    накатывается `make migrate`); это совпадает с make-таргетом каркаса.
13. **Округление в `report`** — стоимости событий суммируются (bcmath),
    повторное округление не применяется; TOTAL — сумма уже округлённых
    слагаемых.

## Как проверяли

Окружение: `make db-up` (PostgreSQL 17 на порту 5544), `make migrate`.

1. **Импорт цен + событий + rate** — `app:prices:import fixtures/prices.json`,
   `app:usage:import fixtures/usage.jsonl`, `app:billing:rate` — все
   завершаются с кодом 0; rate печатает
   `RATED=3 UNRATED=0`.
2. **Отчёт по эталону** —
   `app:billing:report --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z`
   даёт побайтово ожидаемый вывод из `TASK.md` (сравнено `diff`/`cmp` с
   эталонным файлом; заголовок, порядок строк, TOTAL).
3. **Идемпотентность** — повторный import тех же файлов + `rate` +
   отчёт: отчёт идентичен первому (сравнен побайтово),
   `RATED=0 UNRATED=0`.
4. **Некорректный ввод** — `prices:import` с невалидным JSON → код 1;
   строки с невалидными полями (отрицательные токены, unknown unit,
   не-USD валюта, дубли провайдера в файле) отклоняются парсером;
   `usage:import` с невалидным JSONL → код 1.
5. **Rate-повтор для unrated** — импортировано событие для модели без
   цены (`sfera/gyro-mini`), `rate` оставило его unrated и печатало
   `UNRATED <provider>/<id> <ts> no_price` в stderr; после импорта
   строки цены для этой модели повторный `rate` рассчитал событие
   (`RATED=1 UNRATED=0`).
6. **Оф-пик** — вручную сверены граничные случаи окна 16:30–00:30
   (пробел 16:29 вне, 16:30 в, 00:29 в, 00:30 вне, переход через полночь).
7. **Reprice (бонус)** — файл коррекции для двух строк `prism/lumen-8`
   (замена ставок) вызвал пересчёт всех 8 затронутых событий, дельта
   совпала с независимым ручным расчётом (`REPRICED_EVENTS=8`,
   `REPRICE_DELTA_USD=8.645833`); после reprice итоговый отчёт показал
   скорректированные суммы без задвоений; reprice с файлом, не
   затрагивающим события, напечатал `REPRICED_EVENTS=0` и дельту `0.000000`.
8. **Юнит-тесты** — `vendor/bin/phpunit` — 16 тестов, все проходят
   (HALF_UP, окно скидок, расчёт стоимости по эталонным фикстурам).
