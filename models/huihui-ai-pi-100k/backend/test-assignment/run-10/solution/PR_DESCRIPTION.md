# PR: Учёт расходов на LLM-токены

Реализован полный цикл биллинга по Taks.md: импорт истории цен и событий
потребления, расчёт стоимости «по цене на момент события», CSV-отчёт и
бонус — ретро-коррекция цен. Цель — корректность денег (без float),
воспроизводимость (идемпотентность импортов) и детерминированный отчёт.

## Что сделано

Команды (все через `bin/console`, `App\` в `src/`):

| Команда | Назначение |
|---|---|
| `app:prices:import <file>` | Импорт провайдеров/моделей/строк цен (JSON). Сравнение по естественным ключам: провайдер — `code`, модель — `(provider, code)`, строка — `(provider, model, valid_from)`. Повторная загрузка тех же сумм не дублирует данные. |
| `app:usage:import <file>` | Импорт событий (JSONL) с дедупликацией по `(provider, provider_request_id)`. Повторная доставка молча пропускается; код 0 даже если все строки дубли. |
| `app:billing:rate` | Расчёт стоимости pending-событий по цене на момент `ts`. В stdout — `RATED=<n> UNRATED=<m>`, unrated — по строке в stderr; код 0. |
| `app:billing:report [--from --to]` | CSV (UTF-8, `,`, `\n`) по (user, model) с заголовком, сортировкой user→model и итоговой строкой `TOTAL`; ровно 6 знаков; unrated не попадают. |
| `app:billing:reprice <file>` *(бонус)* | Ретро-коррекция: upsert строки цены по `(provider, model, valid_from)` на основе уже загруженного справочника (секции `providers`/`models` в файле коррекции не обязательны), пересчёт затронутых событий и вывод `REPRICED_EVENTS=<n>` и `REPRICE_DELTA_USD=<x.xxxxxx>` (новая минус старая сумма, 6 знаков). |

## Архитектура и ключевые решения

Слои (PSR-4 `App\` → `src/`):
- **`App\Domain`** — чистая предметная логика без зависимостей от ORM/фреймворка: `Decimal` (обёртка bcmath), `CostCalculator`, `OffPeak`, `TokenCounts`, `RateUnit`, `EventStatus`. Удобно покрывать юнит-тестами (`App\Tests\Domain`).
- **`App\Dto`** — типизированные DTO (Provider/Model/Price/UsageEvent), отдельно от ORM-сущностей.
- **`App\Entity`** — ORM-сущности: `Provider`, `Model`, `PriceRow`, `UsageEvent`.
- **`App\Repository`** — кастомные репозитории с бизнес-запросами (например, `PriceRowRepository::findForModelAt` — строка с наибольшим `valid_from <= ts`).
- **`App\Service`** — импорт (Parser + Importer), расчёт (`RateRunner`), отчёт (`ReportRenderer`), ретро-коррекция (`RepriceService`), `Parsing` (валидация полей).
- **`App\Command`** — тонкий CLI-слой над общей базой `AppCommand`.

Денежные расчёты:
- **Без float**: всё — десятичные строки + bcmath с масштабом 20 (запас >= 16 по требованию). Тип `float` в деньгах не используется.
- **Единственное округление — HALF_UP, 6 знаков, только итоговой стоимости события** (`Decimal::roundHalfUp`). Промежуточные суммы/делимые сохраняются с запасом знаков; слагаемые в отчёте не перекругляются.
- **Оф-пик** — множитель применяется ко всему событию *до* округления; окно `[start, end)` (включительно start, исключительно end), корректный переход через полночь.
- **Цена — на момент события**: выбирается строка с наибольшим `valid_from <= event.ts`; `valid_from` включительно (поэтому e2 на `12:00:00` получает новую строку).

Оформление (stdout/stderr, код выхода):
- **stdout** — публичный результат (отчёт, сводка `RATED=...`, строки `REPRICED...`). **stderr** — служебное (статус импорта, unrated, ошибки). **Код**: `0` — успех, `1` — ошибка.
- **Идемпотентность импортов**: цены — upsert по естественным ключам (в рамках одной транзакции); события — дедупликация по `(provider, provider_request_id)`.
- **БД**: миграция `migrations/Version20261027100109.php` (таблицы `providers`, `models`, `price_rows`, `usage_events`). Управление схемой — штатное `make db-up` / `make migrate` (Doctrine Migrations), как в каркасе.

## Допущения

- **Валюта** строки: поле `currency`, если отсутствует — `USD` (в фикстурах `currency` присутствует; при отсутствии валидируется как трёхбуквенный код).
- **Диапазон отчёта** `--from/--to`: полуинтервал `[from, to)` — `from` включительно, `to` исключительно; сравнение по `ts` (UTC).
- **Reprice**: стоимость события *перезаписывается* (не доначисляется), поэтому итоговый `report` после reprice показывает пересчитанные суммы без задвоения; повторное применение той же коррекции даёт `REPRICE_DELTA_USD=0.000000` (идемпотентно).
- **Отчёт** группирует события с одним и тем же (user, model) в одной строке, суммы токенов — по событиям группы, `cost_usd` — сумма стоимостей событий группы.
- **UNRATED**: для события, по которому нет цены на момент `ts`, в stderr — строка вида `UNRATED prism/e0-early 2026-07-01T10:00:00Z no_price` (провайдер/запрос, UTC-ISO-8601, причина `no_price`).

неизвестные провайдер/модель в коррекции (код 1), повторные применения reprice.

## Отступления от каркаса (с обоснованием)

- **Добавлены файлы** (никакие каркасные файлы не изменены):
  - всё содержимое `src/` (кроме `Kernel.php` из каркаса), `tests/Domain/*Test.php`,
    `migrations/Version20261027100109.php`;
  - вспомогательный `fixtures/reprice_correction.json` — пример коррекции цен для
    бонус-команды (`providers`/`models` там намеренно отсутствуют, чтобы проверить
    требование «секции могут отсутствовать или быть пустыми»).
- **Зависимости**: новых пакетов не добавлено. Используется `ext-bcmath` (уже
  в `composer.json`), а для unit-тестов — `phpunit/phpunit` (уже в `require-dev`).
- **Альтернативные решения** (детали, принятые по ходу):
  - В ORM-атрибутах `#[ORM\Column(name: 'user_name')]`, а не `column:` — в установленном
    `doctrine/orm` у `Column` параметр именно `name` (проверено через reflection).
  - Сортировка/запросы по «минуте в сутки UTC» для правила оф-пика берутся из `ts`
    (UTC) напрямую — правило по моменту времени события.
  - `UsageEvent.user` физически хранится в столбце `user_name`, чтобы избежать
    конфликта с зарезервированным словом `user` в PostgreSQL при генерации SQL.
  - `Provider::$models` типизирован как интерфейс `Doctrine\Common\Collections\Collection`
    (не конкретный `ArrayCollection`), так как ORM гидратирует один-ко-многим
    коллекцией `PersistentCollection`.
  - Тесты сфокусированы на чистом предметном слое (без БД) — это быстрый и
    воспроизводимый якорь для проверки денег/округлений/оф-пика; интеграционные
    сценарии проверяются CLI-командами (см. выше).
  - Все `throw` в парсерах/сервисах — `InputError` (универсальный
    исключительный тип для ошибок входных данных), перехватываются в командах
    через `AppCommand::fail()` → stderr + код 1.
  - Слой `App\Dto` отделён от ORM-сущностей: парсеры формируют DTO, а сервисы
    импорта уже их «привязывают» к сущностям; это упрощает unit-тестирование
    логики и не заставляет тесты тянуть за собой ORM.
