## Descripción PR: Система учёта расходов на LLM-токены

### Что сделано
Реализован бэкенд для учёта стоимости использования LLM-токенов с поддержкой различных схем тарификации и временем действия цен.

**Основные возможности:**
- **Импорт данных**:
    - `app:prices:import`: Загрузка провайдеров, моделей и цен из JSON. Реализован идемпотентный upsert.
    - `app:usage:import`: Загрузка событий использования из JSONL. Дедупликация по `(provider, provider_request_id)`.
- **Тарификация**:
    - `app:billing:rate`: Расчёт стоимости для всех нерасчитанных событий.
    - Поддержка схем `per_1m_tokens` (разные ставки для типов токенов) и `per_1m_tokens_unified` (единая ставка).
    - Учёт оф-пиковых скидок в UTC окнах (включая окна, переходящие через полночь).
    - Высокая точность вычислений с использованием `bcmath` и округление стоимости события до 6 знаков после запятой по правилу HALF_UP.
- **Отчётность**:
    - `app:billing:report`: Генерация CSV-отчёта по пользователям и моделям за выбранный период.
- **Бонус**:
    - `app:billing:reprice`: Возможность корректировки цен с пересчетом уже тарифицированных событий.

### Ключевые решения и допущения
1. **Точность вычислений**: Для всех денежных операций использовался `bcmath` с промежуточной точностью 16 знаков. Округление до 6 знаков выполняется один раз в конце расчёта стоимости одного события.
2. **Хранение данных**:
    - Суммы стоимостей хранятся в БД как строки (`DECIMAL(18,6)`) для предотвращения потерь точности floating point.
    - Ставки цен хранятся в JSON-поле для гибкости поддержки разных схем тарификации.
3. **Оптимизация**:
    - `UsageEvent` содержит ссылку на `Price` (ManyToOne), что позволяет быстро находить события для пересчёта при изменении цены.
4. **Обработка reserved keywords**: Поле `user` в таблице `usage_events` переименовано в `user_id` на уровне БД, так как `USER` является зарезервированным словом в PostgreSQL.

### Как проверяли
1. Развёрнута чистая база данных через `make db-up` и `make migrate`.
2. Загружены тестовые данные из `fixtures/`.
3. Выполнена тарификация `app:billing:rate`.
4. Сгенерирован отчёт `app:billing:report`, вывод которого полностью совпадает с примером из `TASK.md`.
5. Проверена идемпотентность повторным импортом данных и запуском тарификации.
