# Учёт расходов на LLM-токены

## Что сделано

Реализованы все обязательные команды и бонус:

- `app:prices:import <file>` — идемпотентный upsert справочника и истории цен;
- `app:usage:import <file>` — потоковый приём JSONL, первый вариант события
  побеждает, дубли не обновляют данные;
- `app:billing:rate` — тарификация ещё не рассчитанных событий с повторными
  попытками для unrated;
- `app:billing:report [--from=…] [--to=…]` — CSV с детерминированной сортировкой,
  точными суммами и итоговой строкой;
- `app:billing:reprice <file>` — исправление цен с пересчётом связанных событий
  и денежным журналом корректировок.

CSV и сводки выводятся только в stdout; ошибки и диагностика unrated — в stderr.
Импорт при успехе ничего не печатает. Ошибки возвращают код 1.

## Устройство и ключевые решения

- `src/Domain/`: сущности `Provider`, `Model`, `Price`, `UsageEvent`,
  `PriceAdjustment`, значение `TokenUsage`, окно `OffPeak`, калькулятор
  `CostCalculator`. Изменения состояния событий выполняются доменными методами;
  поля сущностей доступны для чтения, но не для внешней записи.
- `src/Application/`: сценарии импорта, тарификации, коррекции и построения
  отчёта. Консольные адаптеры в `src/Command/` отвечают за аргументы, потоки и
  коды завершения.
- `src/Infrastructure/`: проверка входных данных, поиск временной цены,
  транзакции и тип времени Doctrine.
- Справочник, расчёты событий и корректировки сохраняются через Doctrine ORM.
  Для массового приёма событий используется DBAL и PostgreSQL
  `INSERT … ON CONFLICT DO NOTHING`: это настоящий запрет обновления дубля,
  подкреплённый уникальным индексом. Агрегация отчёта также выполнена через DBAL:
  `SUM(BIGINT)` и `SUM(NUMERIC)` не требуют загрузки событий в PHP и не используют
  float.
- Событие хранит строковые коды провайдера и модели независимо от справочника.
  Поэтому использование можно принимать до загрузки цен. У рассчитанного
  события сохраняются ссылка на выбранную строку цены, стоимость и фактически
  применённый множитель оф-пика. `NULL` стоимости означает unrated;
  `0.000000` — полноценное рассчитанное событие.
- Цена выбирается по максимальному `valid_from <= ts`. Период отчёта —
  `[from, to)`. Оф-пик проверяется в UTC, включая переход через полночь.
- Все денежные операции выполняются BCMath над строками. Для ставок с шестью
  дробными знаками произведение на целые токены точно при масштабе 6,
  деление на миллион — при масштабе 12. При умножении на оф-пиковый множитель
  масштаб увеличивается на всю его дробную часть, поэтому промежуточного
  округления нет даже для длинного множителя. Единственное округление события —
  `bcround(..., 6, RoundingMode::HalfAwayFromZero)` (HALF_UP для неотрицательных
  расходов). Ставки канонизируются BCMath и сравниваются как строки, без
  неявного преобразования больших чисел в float. Отчёт суммирует уже
  округлённые стоимости.
- Любая изменяющая команда атомарна, включая весь JSONL-файл. При ошибке
  откатываются и ранее обработанные записи этого файла. Транзакционный advisory
  lock PostgreSQL сериализует изменяющие команды: два одновременных `rate` или
  `reprice` не выполняют двойное начисление. Это намеренно простой компромисс
  для консольного приложения, а не высоконагруженная архитектура с воркерами.
- Тарификация и коррекция обходят события пакетами по 200 с очисткой ORM и
  продвижением по ID; unrated внутри пакета не зацикливают обход.
- В БД есть уникальные индексы естественных ключей, внешние ключи и CHECK для
  неотрицательных токенов и согласованного состояния тарификации.
- Сортировка отчёта использует `COLLATE "C"`, а не локаль БД. CSV кодируется
  стандартным `fputcsv` с отключённым нестандартным escape и явным `\n`.
  Кавычки, запятые, переводы строк и похожие на console-разметку пользовательские
  идентификаторы сохраняются корректно.

### Время и миграция

Схема разворачивается штатным **`make migrate`**. Миграция
`migrations/Version20261018124834.php` содержит прямой и обратный переходы.

Для временных полей добавлен DBAL-тип `utc_instant` и домен PostgreSQL
`billing_utc_instant` поверх `TIMESTAMP(6) WITHOUT TIME ZONE`. Запись и чтение
всегда в UTC. Это сохраняет микросекунды, которые стандартный тип Doctrine
теряет при записи. Отдельное имя домена обеспечивает корректную обратную
интроспекцию схемы, не переопределяя обычные timestamp-поля, в том числе таблицу
служебных версий миграций. `doctrine:schema:validate` проходит без расхождений.
Для создания схемы нужен именно запуск миграций, а не `doctrine:schema:create`,
который сам не создаёт PostgreSQL-домен и дополнительные CHECK-ограничения.

### Ретро-коррекция

`reprice` использует только существующих в БД провайдеров и модели. Секции
`providers`/`models` могут отсутствовать; если переданы, они не создают и не
обновляют справочник. Изменённые существующие строки цен определяют набор
событий по сохранённой ссылке `rated_price_id`.

Для каждого такого события стоимость пересчитывается из исходных токенов
с **первоначально применённым множителем**. В
`billing_price_adjustment` сохраняются событие, старая и новая стоимость,
время корректировки. Обновление цены, пересчёт и журнал фиксируются одной
транзакцией. Отчёт читает текущую стоимость события и не прибавляет журнал
повторно. Повтор той же коррекции даёт нулевые счётчик и дельту.

Новая историческая строка цены может быть вставлена через `reprice`, но сама
по себе не меняет уже рассчитанные события, связанные с другими строками.
Unrated пересчитываются следующей командой `rate`.

## Допущения и границы

- Временные значения принимаются в формате `YYYY-MM-DDTHH:MM:SS[.ffffff]Z`,
  с точностью до микросекунд. Невозможные календарные даты отвергаются, а не
  нормализуются. Диагностика печатает нормализованное UTC-время.
- Отсутствующий `off_peak` и `null` означают отсутствие скидки. Окно с равными
  границами считается пустым. Множитель — неотрицательная десятичная строка;
  он не ограничен сверху единицей.
- Ставки неотрицательны, заданы строками ровно с шестью дробными знаками;
  валюта — USD. Поддерживаются только две схемы из задания. Ведущие нули и
  порядок ключей ставок не создают ложную коррекцию цены.
- Текстовые идентификаторы и имя провайдера — непустые UTF-8 строки до 255
  символов без NUL. Каждое отдельное количество токенов должно помещаться
  в неотрицательный PHP int / PostgreSQL BIGINT на 64-битной платформе;
  суммы отчёта могут выходить за этот диапазон. Стоимость события хранится
  в `NUMERIC(50,6)` (до 44 цифр целой части).
- Каждая строка JSONL валидируется, в том числе дубли; пустая строка — ошибка.
  CRLF и последний перевод строки поддерживаются, пустой файл допустим.
- Повторяющиеся естественные ключи внутри JSON цен нормализуются до последней
  записи, а в JSONL побеждает первое принятое событие.
- Обычный импорт цен обновляет справочник, но не пересчитывает уже рассчитанные
  события. Исправления, требующие пересчёта, следует подавать сразу в `reprice`,
  а не предварительно в `prices:import`: идентичная текущей строка не считается
  новой коррекцией. Изменение настройки оф-пика влияет только на последующую
  тарификацию, отдельной истории оф-пика в задании нет.
- Если `from == to`, отчёт пуст; `from > to` — ошибка аргументов.

## Как проверено

Окружение: PHP 8.5.11, PostgreSQL 17.11 из предоставленного compose,
Doctrine ORM 3.7.5 / DBAL 4.5.0. Зависимости использованы из `vendor/`.

### Развёртывание и приёмка

Проверка выполнена на отдельной первоначально чистой БД, чтобы не затрагивать
существующие данные окружения:

```bash
make db-up
export DATABASE_URL='postgresql://app:app@127.0.0.1:5544/billing_check_pi?serverVersion=17&charset=utf8'
make migrate
bin/console
bin/console doctrine:schema:validate
bin/console app:prices:import fixtures/prices.json
bin/console app:usage:import fixtures/usage.jsonl
bin/console app:billing:rate
bin/console app:billing:report \
  --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z
```

Получены `RATED=3 UNRATED=0` и CSV из задания, включая
`TOTAL,,6200000,2300000,2500000,83333,33.662499`.
В интеграционном тесте весь отчёт сравнивается с эталоном как строка,
включая заголовок, порядок строк и завершающий LF.

Повторены оба импорта: `RATED=0 UNRATED=0`; отчёты до и после повторения
сохранены в файлы и сравнены `cmp` без отличий. Также проверены откат
миграции до `0`, повторный `make migrate` и валидация схемы.

### Автоматические тесты

```bash
# Только модульные проверки; интеграционные явно пропускаются без URL:
make test

# Полный набор, включая настоящие CLI-процессы и PostgreSQL:
TEST_DATABASE_URL='postgresql://app:app@127.0.0.1:5544/app?serverVersion=17&charset=utf8' make test

bin/console lint:container
find src tests migrations -name '*.php' -print0 | xargs -0 -n1 php -l
```

Полный прогон: **54 теста, 241 проверка — успешно**, без пропусков.
Проверки синтаксиса и контейнера также проходят.

Интеграционный набор создаёт отдельную БД со случайным именем, накатывает
миграцию и удаляет эту БД после завершения. Данные БД из `TEST_DATABASE_URL`
не очищаются и не используются для тестовых событий; роли требуется `CREATEDB`.

Покрыты: эталонный отчёт, идемпотентность, изменение содержимого дубля,
одинаковый request ID у разных провайдеров, обе схемы тарификации, точные
границы смены цены и оф-пика, переход через полночь, микросекунды, нулевое
событие, HALF_UP и суммирование после округления, большие числа, длинные
множители, CSV-экранирование, пустой отчёт, временные фильтры, unrated и поздние
цены, ошибочные файлы и атомарный откат, коррекции с положительной и
отрицательной дельтой, журнал, повтор коррекции, сохранение исходного оф-пика,
историческая вставка, обработка 405 событий и параллельные `rate`/`reprice`.

## Изменения каркаса и зависимости

Единственный изменённый существующий файл конфигурации —
**`config/packages/doctrine.yaml`**: регистрация `utc_instant` и отображения
PostgreSQL-домена, необходимая для точного хранения времени и согласованной
интроспекции.

Добавлены реализация в `src/{Domain,Application,Infrastructure,Command}/`,
миграция в `migrations/`, тесты в `tests/{Unit,Integration}/`,
`COMMIT_MESSAGE.md` и это описание. Миграция размещена в штатном каталоге
Doctrine, а не в `src/`, согласно настройкам каркаса.

Новые зависимости **не добавлялись**. `TASK.md`, `AGENTS.md`, `README.md`,
`fixtures/`, `composer.json`, `composer.lock`, `docker-compose.yml`, `Makefile`,
`phpunit.xml.dist`, `src/Kernel.php`, `bin/console` и `.env` не изменялись.
Альтернативы чистому ORM для приёма/отчёта и стандартному типу времени
обоснованы выше; альтернативного способа запуска приложения или миграций нет.
