# Учёт расходов на LLM-токены

## Что сделано

Консольное приложение (Symfony 8, Doctrine ORM, PostgreSQL 17), которое
принимает историю цен и журнал событий использования и считает расходы по
пользователям и моделям.

Команды:

| Команда | Назначение |
|---|---|
| `app:prices:import <file>` | upsert провайдеров, моделей и строк цен |
| `app:usage:import <file>` | загрузка JSONL-событий с дедупликацией |
| `app:billing:rate` | тарификация всех нерассчитанных событий, `RATED=n UNRATED=m` |
| `app:billing:report [--from] [--to]` | CSV-отчёт по (user, model) с TOTAL |
| `app:billing:reprice <file>` (бонус) | ретро-коррекция цен и пересчёт затронутых событий |

Структура (`src/Billing/`):

- `Domain/Shared` — `Decimal` (bcmath, единственное округление события), `Time` (строгий разбор ISO-8601 с `Z`/смещением).
- `Domain/Catalog` — `Provider`, `OffPeakWindow`, `Model`, `Price`, `PricingUnit`, `CostAdjustment`.
- `Domain/Usage` — `UsageEvent` (агрегат события с расчётом), `TokenUsage` (value object).
- `Application/` — парсеры и импортёры, `RatingService`, `UsageReportBuilder`, `RepriceService`.
- `Infrastructure/Persistence/` — Doctrine-репозитории.
- `UI/Console/` — команды.

## Ключевые решения

1. **Стоимость события — в `Price::charge()`.** Все промежуточные значения — bcmath со шкалой 30; округление до 6 знаков HALF_UP выполняется один раз (`Decimal::roundEvent`). Оф-пик применяется к уже посчитанной (несокращённой) стоимости, множитель — из `OffPeakWindow`.
2. **Оф-пик.** Окно `[start, end)` по UTC-минутам; при `start > end` — через полночь. Граница `end` исключена, `start` включён (покрыто тестами: 23:59, 00:29:59 — внутри; 00:30 — снаружи).
3. **Выбор цены.** `PriceRepository::findActiveFor` — строка с наибольшим `valid_from <= ts`. Значение `valid_from` хранится как `timestamptz`, сравнение в БД.
4. **Unrated.** Событие без цены хранит `price_id = NULL`; каждый `rate` перебирает все такие события заново. В отчёт попадают только события с `price_id IS NOT NULL` (фильтр в SQL).
5. **Дедупликация событий.** Уникальный индекс `(provider_code, provider_request_id)` + проверка `existsByKey` перед вставкой. Дубли внутри одного файла отсекаются в памяти. Файл разбирается целиком до записи: при ошибке в любой строке ничего не сохраняется (код выхода 1).
6. **Импорт цен не перезаписывает историю.** Если строка `(provider, model, valid_from)` уже есть с другими ставками, импорт завершается ошибкой (код 1) с подсказкой использовать `reprice`. Так повторная загрузка тех же сумм — no-op, а молчаливое изменение уже рассчитанной истории невозможно. Альтернатива (перезапись с пересчётом) отвергнута: это скрытая правка расходов, которые уже показаны пользователю.
7. **Ретро-коррекция (бонус).** Исправленные строки применяются upsert'ом (модель обязана существовать в БД). Затем пересчитываются все рассчитанные события модели с `ts >= valid_from` и для изменившихся записывается `CostAdjustment` (старое/новое значение, причина). Сами события не удаляются и не дублируются — отчёт показывает пересчитанные суммы без задвоения. `REPRICED_EVENTS` — число событий, пересчитанных заменёнными строками (включая те, чья сумма не изменилась в результате округления; в этом случае `CostAdjustment` не пишется). `REPRICE_DELTA_USD` — сумма (новое − старое) по этим событиям.
8. **Время.** Все `ts` и даты параметров парсятся строго: ISO-8601 с обязательным смещением, результат — в UTC.
9. **Ошибки.** Все ожидаемые ошибки входных данных — `InvalidInputException` → сообщение в stderr и код 1. Отчёт и сводки — в stdout, служебные сообщения — в stderr.

## Допущения

- Идентификатор `provider` в событии/модели ссылается на `code` провайдера; модели сопоставляются по `(provider, code)`.
- Поле `currency` сохраняется, но не используется в расчётах (все суммы — USD по ТЗ).
- Если в `prices` встретилась модель, которой нет в `models`, она создаётся (upsert справочника). В `reprice` модель обязана существовать.
- `--from/--to` принимаются только в формате ISO-8601 с суффиксом `Z` или смещением.
- Отрицательные токены и нецелые значения в событиях — ошибка импорта.
- Итоговое `cost_usd` по группе — сумма уже округлённых стоимостей событий (без повторного округления).

## Как проверял

```bash
cp .env.example .env          # уже было
make db-up                    # PostgreSQL 17 поднят
bin/console doctrine:database:drop --force --if-exists -n
make migrate                  # чистая база, схема накатывается
bin/console doctrine:schema:validate   # OK: маппинги и схема совпадают
bin/console app:prices:import fixtures/prices.json      # exit 0
bin/console app:usage:import fixtures/usage.jsonl       # exit 0
bin/console app:billing:rate                            # RATED=3 UNRATED=0
bin/console app:billing:report --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z
# вывод байт-в-байт совпадает с примером из TASK.md (проверено cmp)
```

Повторный импорт тех же файлов + rate + report — отчёт побайтно тот же
(`Новых событий: 0, дублей пропущено: 3`, `RATED=0 UNRATED=0`).

Дополнительно проверено вручную:
- unrated-событие (цена с 2026-07-01 отсутствует) — строка в stderr, `UNRATED=1`, повтор rate не падает;
- одинаковый `provider_request_id` у разных провайдеров — два разных события;
- оф-пик на границах (23:59, 00:29:59 — со скидкой; 00:30 — без);
- некорректный JSON / JSONL — код 1;
- reprice: дельта +1.000000 у `u-bob` и `u-o` совпала с ручным расчётом; повторный reprice той же коррекции даёт `REPRICE_DELTA_USD=0.000000`; итоговый отчёт без задвоений; повторный импорт исходного `prices.json` после коррекции отказывает (код 1), как и задумано.

Unit-тесты: `make test` — 5 тестов, 12 проверок (пример из ТЗ, оф-пик через полночь и полуоткрытость окна, unified-схема, нулевые токены, HALF_UP на уровне события).

## Что не покрыто / известные ограничения

- Интеграционных тестов с БД нет, проверка сценариев — ручная (см. выше).
- Тарификация событий одним пакетом с `flush` в конце: на очень больших объёмах стоит перейти на батчи с `clear()`.
- `UsageEventImporter` загружает весь файл в память до записи (осознанно — атомарность). Для больших файлов нужен поточный режим с транзакцией на батч.
- `reprice` перебирает все рассчитанные события модели с `ts >= valid_from` (не только затронутые диапазоны); для текущих объёмов достаточно, на больших нужен индекс по `(provider_code, model_code, ts)`.
