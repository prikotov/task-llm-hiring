## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

Для чистого и надёжного кода я бы выделил шесть возможностей. Ниже каждая с коротким примером.

## 1. Типы: union, nullable, `mixed`, `never`, `static` (PHP 8.0+, `never` с 8.1)

Типы описывают контракт прямо в сигнатуре, и ошибки ловятся раньше.

```php
function findUserId(string|int $identifier): ?int
{
    return is_numeric($identifier) ? (int) $identifier : null;
}

function fail(string $message): never
{
    throw new RuntimeException($message); // функция никогда не возвращает управление
}
```

## 2. Конструкторное продвижение свойств (PHP 8.0)

Убирает шаблонный код и делает зависимости очевидными.

```php
final class OrderService
{
    public function __construct(
        private OrderRepository $orders,
        private PaymentGateway $payments,
        private LoggerInterface $logger,
    ) {}
}
```

## 3. Readonly-свойства и классы (PHP 8.1 / 8.2)

Иммутабельность защищает объекты-значения и доменные сущности от случайных изменений.

```php
final readonly class Money
{
    public function __construct(
        public int $amount,
        public string $currency,
    ) {}

    public function add(self $other): self
    {
        if ($this->currency !== $other->currency) {
            throw new InvalidArgumentException('Валюты не совпадают');
        }
        return new self($this->amount + $other->amount, $this->currency);
    }
}
```

## 4. Enum (PHP 8.1)

Заменяет константы-строки и делает набор допустимых значений закрытым.

```php
enum OrderStatus: string
{
    case New = 'new';
    case Paid = 'paid';
    case Shipped = 'shipped';

    public function canBeCancelled(): bool
    {
        return match ($this) {
            self::New, self::Paid => true,
            self::Shipped => false,
        };
    }
}

$status = OrderStatus::from('paid');
```

## 5. `match` (PHP 8.0)

В отличие от `switch`, работает строго (`===`), возвращает значение и выбрасывает `UnhandledMatchError`, если ветка не найдена.

```php
$discount = match ($customerType) {
    'vip' => 0.2,
    'regular' => 0.05,
};
```

## 6. Named arguments и атрибуты (PHP 8.0)

Именованные аргументы делают вызовы самодокументируемыми. Атрибуты заменяют аннотации в docblock и поддерживаются парсером.

```php
$user = new User(
    email: 'a@example.com',
    isActive: true,
);

#[Route('/orders/{id}', methods: ['GET'])]
public function show(int $id): Response
{
    // ...
}
```

## Дополнительно

- **First-class callable syntax** (8.1): `$fn = strlen(...);`
- **Pure intersection types** (8.1): `Countable&Iterator $items`
- **Fibers** (8.1): низкоуровневые примитивы для асинхронности; в повседневном коде используются редко, зато важны для фреймворков и библиотек.

Если выбрать три самых важных, то это **типы, readonly-объекты и enum**: они вместе сильнее всего снижают количество ошибок на этапе написания кода.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

# Система типов в PHP

PHP использует гибридную систему: объявленные типы проверяются во время выполнения, а без `strict_types` движок пытается привести значение к нужному типу. Ниже разберём режимы, приведения и ловушки.

## 1. Что даёт `declare(strict_types=1)`

Директива действует на **вызовы функций, объявленные в файле, где она стоит**. Проверяется тип аргумента на стороне вызывающего кода.

```php
// file: a.php
declare(strict_types=1);

function double(int $n): int
{
    return $n * 2;
}

echo double(5);      // 10
echo double('5');    // TypeError: Argument #1 ($n) must be of type int, string given
```

Без `strict_types` строка `'5'` молча превращается в `5`, и ошибка не возникает.

**Важно:** директива не влияет на то, как проверяется возвращаемое значение внутри функции. Она действует только на тот файл, из которого происходит вызов. Вызов из файла без `strict_types` в функцию, объявленную в файле со `strict_types`, всё равно идёт в слабом режиме, так как строгость определяется файлом вызова.

```php
// file: b.php (без strict_types)
require 'a.php';
echo double('5'); // 10: вызов из нестрогого файла, приведение разрешено
```

Ещё один нюанс: в строгом режиме разрешено только расширение `int` до `float`:

```php
declare(strict_types=1);
function half(float $x): float { return $x / 2; }
echo half(5); // 2.5, int расширяется до float, это разрешено
```

## 2. Как ведут себя приведения (слабый режим)

В слабом режиме скалярные типы (`int`, `float`, `string`, `bool`) приводятся по правилам движка.

```php
function takesInt(int $n): int { return $n; }

takesInt('42');     // 42
takesInt('42abc');  // 42 с Warning/Notice в PHP 8: "A non-numeric..." -> в PHP 8 это TypeError для нечисловых строк
takesInt(4.0);      // 4
takesInt(4.7);      // 4 с Deprecated в PHP 8.1: implicit conversion loses precision
takesInt(true);     // 1
takesInt(null);     // TypeError: null нельзя передать в не-nullable int
```

Точнее по PHP 8.x: строка с мусором вроде `'42abc'` даёт `int` с предупреждением (`A well formed numeric value...`), а полностью нечисловая строка `'abc'` вызывает `TypeError`. Поведение зависит от версии, поэтому полагаться на «молчаливое» приведение не стоит.

## 3. Ловушки

### Ловушка 1: `null` и скаляры
```php
function greet(string $name): string { return "Hi, $name"; }
greet(null); // TypeError в PHP 8 (в PHP 7 null приводился к '' только для внутренних функций)
```
Для внутренних функций (`strlen`, `str_contains`) поведение с `null` в PHP 8.1+ даёт `Deprecated`.

### Ловушка 2: сравнение `==` и приведение
```php
var_dump(0 == 'a');        // PHP 8: false (раньше было true)
var_dump('1' == '01');     // true
var_dump('10' == '1e1');   // true
var_dump(100 == '1e2');    // true
var_dump(null == false);   // true
var_dump(null === false);  // false
```
Правило: в коде всегда используйте `===`.

### Ловушка 3: `int` на 32-битной системе и переполнение
```php
var_dump(PHP_INT_MAX + 1); // float(9.2233720368547758E+18): тип молча меняется на float
```
Арифметика не выбрасывает исключение при переполнении, а переходит во float. Для денег это опасно, поэтому храните суммы в минимальных единицах (копейках) и проверяйте диапазон.

### Ловушка 4: `array` без содержимого
```php
/** @param int[] $ids */
function sumIds(array $ids): int { return array_sum($ids); }
sumIds(['1', 'x']); // array_sum даёт 1, молча пропуская проблемы
```
Тип `array` не проверяет элементы. Нужны generics в статанализаторе (PHPStan, Psalm) или value objects.

### Ловушка 5: возврат `false` вместо `null`
```php
function findAge(string $name): int|false
{
    return $name === 'Ann' ? 30 : false;
}
if (findAge('Bob')) { ... } // 0 тоже ложно: возраст 0 будет принят за отсутствие
```
Используйте `?int` или исключения, а проверку делайте через `!== false`.

### Ловушка 6: свойства и `readonly` до инициализации
```php
class User {
    public int $id;
}
$u = new User();
echo $u->id; // Error: must not be accessed before initialization
```
Типизированные свойства без значения по умолчанию не имеют `null`. Обращение до инициализации даёт `Error`.

### Ловушка 7: `int|float` и `number_format`
Смешение `int` и `float` в денежных расчётах даёт ошибки округления. `0.1 + 0.2 !== 0.3`. Для денег используйте целые числа или `bcmath`/`brick/money`.

## 4. Где типизация спасает

- `declare(strict_types=1)` ловит неверные аргументы на границах модулей, пока код не ушёл в продакшен.
- Union-типы и `never` делают контракт явным, а статанализатор (PHPStan уровень 8-9) ловит расхождения.
- `readonly` и типизированные свойства не позволяют объекту оказаться в невалидном состоянии.
- Enum и `match` без ветки дают `UnhandledMatchError`, так что новый случай не потеряется молча.

## 5. Практический совет

1. Во всех файлах ставьте `declare(strict_types=1);`.
2. Включите PHPStan или Psalm на максимальном уровне.
3. Не используйте `==`, `switch` с нестрогим сравнением и возврат `false` как «отсутствие значения».
4. Для денег, идентификаторов и статусов используйте value objects и enum, а не голые скаляры.

Если хотите, разберу, как strict_types работает с методами Symfony Serializer и параметрами из HTTP-запроса, где строки приходят всегда.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

Ниже то, как я бы проектировал обработку ошибок в PHP-приложении. Опыт работы в продакшене у меня теоретический, поэтому опираюсь на общепринятые практики и известные библиотеки.

## 1. Базовая иерархия

Создайте один корневой интерфейс приложения. Тогда можно поймать все ошибки домена одной строкой, но не перехватывать чужие исключения вроде `PDOException` случайно.

```php
interface DomainException extends \Throwable {}

abstract class OrderException extends \RuntimeException implements DomainException {}

final class OrderNotFound extends OrderException
{
    public static function withId(OrderId $id): self
    {
        return new self(sprintf('Заказ %s не найден', $id->value));
    }
}

final class OrderCannotBeCancelled extends OrderException
{
    public function __construct(public readonly OrderStatus $status)
    {
        parent::__construct("Заказ в статусе {$status->value} нельзя отменить");
    }
}
```

Разделяйте две группы:
- **Ошибки бизнес-правил** (заказ нельзя отменить): ожидаемые, их можно показать пользователю или обработать.
- **Ошибки инфраструктуры** (БД, сеть): неожиданные, обычно логируются и превращаются в 500.

## 2. Оборачивание чужих исключений

Чужие исключения не должны протекать через границы слоёв. Например, `Doctrine\DBAL\Exception` не должен попадать в контроллер. Оборачивайте на границе адаптера, сохраняя причину через `previous`.

```php
final class DoctrineOrderRepository implements OrderRepository
{
    public function __construct(private EntityManagerInterface $em) {}

    public function get(OrderId $id): Order
    {
        try {
            $order = $this->em->find(Order::class, $id->value);
        } catch (\Doctrine\ORM\ORMException $e) {
            throw new OrderStorageFailure('Не удалось загрузить заказ', 0, $e);
        }

        return $order ?? throw OrderNotFound::withId($id);
    }
}
```

`previous` сохраняет цепочку: в логах видно и доменное сообщение, и первопричину.

## 3. Что считается контрактом метода

Контракт описывается не только типами, но и тем, какие исключения метод может выбросить.

- Задокументируйте в PHPDoc: `@throws OrderNotFound`.
- Различайте **ожидаемые** исключения (часть API) и **непредвиденные** (баги и сбои инфраструктуры).
- Не меняйте набор исключений без изменения контракта: новый тип исключения для вызывающего кода может стать поломкой.
- `Throwable` и `Exception` в сигнатурах документации не пишите: это слишком широко.

```php
/** @throws OrderNotFound если заказа нет */
public function get(OrderId $id): Order
```

## 4. Антипаттерны

1. **Проглатывание исключения**: `catch (\Throwable $e) {}`. Ошибка исчезает, и баг найти нельзя.
2. **Лог и повторный бросок без контекста**: логировать на каждом уровне, и в логах появляется дубль.
3. **Потеря цепочки**: `throw new Exception($e->getMessage())` без `$e` в `previous`.
4. **Исключения для потока управления**: `try { find() } catch (NotFound) { create() }` вместо проверки или явного метода.
5. **Слишком широкий catch**: `catch (\Exception $e)` ловит и баги (`TypeError` и подобные наследуют `Error`, но `Exception` тоже слишком широк), и ожидаемые ошибки вперемешку.
6. **Исключения с `null` или `false` как сигналом**: смешивание стилей. Выберите одно: либо исключения, либо явный результат.
7. **Утечка деталей наружу**: SQL, стек-трейсы и внутренние имена классов в HTTP-ответе.
8. **Информативность без данных**: `throw new \Exception('Ошибка')`. Лучше передать id и состояние.
9. **Глобальный обработчик как единственная защита**: контроллеры оборачивают всё подряд. Лучше ловить конкретное на нужном уровне.

## 5. Обработка на границе

Преобразование в HTTP-ответ делайте в одном месте: в Symfony это `ExceptionListener` или `kernel.exception` через `#[AsEventListener]`, либо `ErrorHandler` в API Platform. Доменные исключения маппятся в 404, 409, 422, а всё неизвестное становится 500 с логированием и без деталей для клиента.

```php
#[AsEventListener]
final class DomainExceptionListener
{
    public function __invoke(ExceptionEvent $event): void
    {
        $e = $event->getThrowable();
        if ($e instanceof OrderNotFound) {
            $event->setResponse(new JsonResponse(['error' => $e->getMessage()], 404));
        } elseif ($e instanceof OrderCannotBeCancelled) {
            $event->setResponse(new JsonResponse(['error' => $e->getMessage()], 409));
        }
    }
}
```

Если хотите, могу разобрать, как это ложится на чистую архитектуру: какие исключения живут в домене, а какие в адаптерах.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

Я не работал над реальными проектами, поэтому опираюсь на типичные наблюдения из открытого кода и обсуждений. По моей оценке, чаще всего нарушается **принцип единственной ответственности (SRP)**. Классы быстро обрастают обязанностями: сервис заказов сам валидирует, считает скидки, пишет в БД, отправляет письма и логирует. Причина в том, что добавить метод в существующий класс проще, чем продумать новый, и на небольших задачах это кажется безопасным.

## Пример нарушения

```php
final class OrderService
{
    public function __construct(private \PDO $pdo) {}

    public function placeOrder(array $data): int
    {
        // валидация
        if (empty($data['email']) || !filter_var($data['email'], FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException('Некорректный email');
        }
        if (empty($data['items'])) {
            throw new InvalidArgumentException('Пустой заказ');
        }

        // расчёт суммы и скидки
        $total = 0;
        foreach ($data['items'] as $item) {
            $total += $item['price'] * $item['qty'];
        }
        if ($data['customer_type'] === 'vip') {
            $total *= 0.9;
        }

        // сохранение в БД
        $stmt = $this->pdo->prepare('INSERT INTO orders (email, total) VALUES (?, ?)');
        $stmt->execute([$data['email'], $total]);
        $id = (int) $this->pdo->lastInsertId();

        // уведомление
        mail($data['email'], 'Заказ принят', "Номер заказа: $id");

        // логирование
        error_log("Order $id created");

        return $id;
    }
}
```

Класс валидирует, считает деньги, работает с БД, шлёт письмо и пишет лог. Изменение любой из этих частей требует правки и тестирования всего класса. Тестировать без реальной БД и почты тоже сложно. Кроме того, `mail()` и `error_log()` — жёсткие зависимости.

## Рефакторинг

Разделяем обязанности и вводим зависимости через интерфейсы.

```php
final readonly class PlaceOrderCommand
{
    /** @param list<OrderLine> $lines */
    public function __construct(
        public Email $email,
        public array $lines,
        public CustomerType $customerType,
    ) {}
}

final class PricingService
{
    public function total(array $lines, CustomerType $type): Money
    {
        $total = Money::zero('RUB');
        foreach ($lines as $line) {
            $total = $total->add($line->subtotal());
        }
        return $type === CustomerType::Vip ? $total->multiply(0.9) : $total;
    }
}

interface OrderRepository
{
    public function save(Order $order): OrderId;
}

interface OrderNotifier
{
    public function orderPlaced(Order $order): void;
}

final class PlaceOrderHandler
{
    public function __construct(
        private PricingService $pricing,
        private OrderRepository $orders,
        private OrderNotifier $notifier,
        private LoggerInterface $logger,
    ) {}

    public function __invoke(PlaceOrderCommand $command): OrderId
    {
        // валидация уже выполнена типами value objects при создании команды
        $order = Order::place(
            $command->email,
            $command->lines,
            $this->pricing->total($command->lines, $command->customerType),
        );

        $id = $this->orders->save($order);
        $this->notifier->orderPlaced($order);
        $this->logger->info('Order created', ['id' => $id->value]);

        return $id;
    }
}
```

Что изменилось:
- **Валидация** переехала в value objects (`Email`), которые не позволяют создать невалидное состояние.
- **Расчёт** отделён в `PricingService`, его можно тестировать без БД.
- **Хранение и уведомление** скрыты за интерфейсами. Реализация с `PDO` и с `mail()` живёт в адаптерах, а в тестах подставляются заглушки.
- **Вход** типизирован (`PlaceOrderCommand`) вместо `array $data`.

Этот пример заодно показывает связь с **DIP** (зависимость от абстракций) и **OCP** (новый тип скидки добавляется через стратегию, без правки обработчика), но чаще всего нарушение начинается именно с SRP.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Да, SOLID это не законы, а эвристики. Они помогают держать код поддерживаемым, но у каждого принципа есть цена: больше классов, интерфейсов и косвенности. Если в конкретной ситуации эта цена выше пользы, отступать от принципа разумно. Важно только понимать, что именно нарушаешь и почему.

Критерии, когда нарушение оправдано:
- код короткий и живёт недолго (скрипт миграции, одноразовая утилита);
- абстракция появилась бы раньше второй реализации или реального изменения (правило «rule of three»);
- требование пока не меняется, и гибкость никому не нужна;
- производительность критична, и косвенность заметно дорожает (горячий путь, большие циклы);
- нарушение локализовано и задокументировано, а не расползается по проекту.

## Пример оправданного нарушения

Допустим, есть небольшой внутренний CLI-скрипт, который раз в месяц выгружает заказы за период в CSV. Он один, его поддерживает один человек, формат фиксирован.

```php
declare(strict_types=1);

// Нарушение SRP и DIP намеренно: скрипт одноразовый, абстракции не окупятся.
$pdo = new PDO($_ENV['DATABASE_URL']);
$from = new DateTimeImmutable($argv[1]);
$to   = new DateTimeImmutable($argv[2]);

$stmt = $pdo->prepare(
    'SELECT id, email, total FROM orders WHERE created_at BETWEEN ? AND ? ORDER BY id'
);
$stmt->execute([$from->format('Y-m-d'), $to->format('Y-m-d')]);

$out = fopen('php://stdout', 'w');
fputcsv($out, ['id', 'email', 'total']);
while ($row = $stmt->fetch(PDO::FETCH_ASSOC)) {
    fputcsv($out, $row);
}
```

Здесь выборка, форматирование и вывод смешаны в одном месте, и зависимости создаются прямо внутри. Для скрипта на 15 строк это нормально: разнесение по классам, интерфейсам и тестовым двойникам добавит файлов и церемоний, но не добавит безопасности. Если позже скрипт начнёт расти (появятся другие форматы, фильтры, отправка на почту), это станет сигналом к рефакторингу.

Оправданность зависит от контекста и срока жизни кода. Неоправданное нарушение выглядит иначе: тот же приём в ядре сервиса заказов, который меняется каждую неделю и тестируется в CI.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Открытость/закрытость (OCP) означает, что поведение можно расширять без правки существующего кода. Наследование здесь не единственный путь. Чаще используют следующие приёмы.

## 1. Полиморфизм через интерфейс (стратегия)

Вместо `if` по типу клиента выносим правило в реализации интерфейса. Новый тип скидки добавляется новым классом.

```php
interface DiscountPolicy
{
    public function apply(Money $total): Money;
}

final class NoDiscount implements DiscountPolicy
{
    public function apply(Money $total): Money { return $total; }
}

final class VipDiscount implements DiscountPolicy
{
    public function apply(Money $total): Money { return $total->multiply(0.9); }
}

final class PricingService
{
    public function __construct(private DiscountPolicy $discount) {}

    public function total(Money $subtotal): Money
    {
        return $this->discount->apply($subtotal);
    }
}
```

Добавление «праздничной» скидки не требует правки `PricingService`: достаточно нового класса `HolidayDiscount`.

## 2. Композиция декораторов

Новое поведение оборачивает существующее, не меняя его.

```php
final class LoggingOrderRepository implements OrderRepository
{
    public function __construct(
        private OrderRepository $inner,
        private LoggerInterface $logger,
    ) {}

    public function save(Order $order): OrderId
    {
        $id = $this->inner->save($order);
        $this->logger->info('Order saved', ['id' => $id->value]);
        return $id;
    }
}
```

Кэш, метрики, повторные попытки и логирование добавляются таким же способом. В Symfony это часто делают через декорирование сервисов (`#[AsDecorator]`).

## 3. Диспетчеризация событий

Ядро публикует событие, а новые реакции подписываются на него. Код ядра не меняется.

```php
final readonly class OrderPlaced
{
    public function __construct(public OrderId $orderId) {}
}

// Ядро
$this->dispatcher->dispatch(new OrderPlaced($id));

// Новое поведение добавляется отдельным слушателем
#[AsEventListener]
final class SendOrderEmail
{
    public function __invoke(OrderPlaced $event): void
    {
        // отправка письма
    }
}
```

## 4. Тегированные сервисы и реестры

Набор реализаций собирается контейнером. Например, все экспортёры CSV, JSON, XML регистрируются тегом, и фабрика выбирает нужный по формату. Новый формат подключается без изменения фабрики.

```php
final class ExporterRegistry
{
    /** @param iterable<Exporter> $exporters */
    public function __construct(private iterable $exporters) {}

    public function for(string $format): Exporter
    {
        foreach ($this->exporters as $exporter) {
            if ($exporter->supports($format)) {
                return $exporter;
            }
        }
        throw new UnsupportedFormat($format);
    }
}
```

## 5. Замыкания и функции как стратегии

Для простых случаев интерфейс избыточен, достаточно передать callable или `Closure`.

```php
final class Pipeline
{
    /** @param list<callable(Order): Order> $steps */
    public function __construct(private array $steps) {}

    public function process(Order $order): Order
    {
        return array_reduce($this->steps, fn (Order $o, callable $step) => $step($o), $order);
    }
}
```

## 6. Цепочка обязанностей (middleware)

Обработчики выстраиваются в цепочку, и новый шаг добавляется в её конфигурацию. Так устроены HTTP middleware и Symfony Messenger.

## 7. Конфигурация и данные вместо кода

Правила хранятся в конфигурации или таблице, а не в ветках `if`. Например, процент скидки по типу клиента лежит в YAML или в БД. Это расширяет поведение без изменения кода, но усложняет валидацию конфигурации, поэтому подходит не для всего.

## Что выбрать

- Для одного варианта поведения, который может меняться: интерфейс-стратегия.
- Для сквозных задач (логирование, кэш): декоратор.
- Для реакций на факты в системе: события.
- Для набора однотипных плагинов: тегированные сервисы.

Не стоит вводить эти механизмы заранее: OCP окупается там, где изменения действительно ожидаются. Иначе получится переусложнённый код, за который платит команда.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Нет, SRP не ограничен классами. Принцип говорит об ответственности модуля, и класс здесь лишь самая частая единица. Формулировка Роберта Мартина звучит так: модуль должен иметь одну причину для изменения, то есть один источник требований, которым он обязан отвечать.

Под «модулем» можно понимать:

- **Метод или функцию.** Функция, которая одновременно валидирует, считает и сохраняет, нарушает SRP так же, как класс с тремя обязанностями.
- **Пространство имён или пакет.** Пакет `Billing`, который одновременно отвечает за счета, отчёты для маркетинга и интеграцию с почтой, будет меняться по трём разным причинам.
- **Микросервис или приложение.** Сервис, который отвечает и за заказы, и за пользователей, и за уведомления, вынуждает команды координировать релизы, потому что у него несколько причин для изменения.
- **Файл или конфигурацию.** Один огромный `services.yaml` со всем подряд и конфиг, где смешаны окружение, бизнес-правила и инфраструктура, тоже страдают от этой проблемы.
- **Слой в архитектуре.** Контроллер, который сам ходит в БД и считает скидки, смешивает HTTP-адаптер с доменной логикой.

Пример на уровне функции:

```php
// Одна функция: разбор, проверка и отправка CSV-отчёта
function exportAndMailReport(string $path, string $recipient): void
{
    $rows = array_map('str_getcsv', file($path));
    foreach ($rows as $row) {
        if (count($row) !== 3) {
            throw new RuntimeException('Bad row');
        }
    }
    mail($recipient, 'Report', implode("\n", array_map('implode', $rows)));
}
```

Здесь три причины для изменения: формат CSV, правила валидации и способ доставки. Разделение выглядит так:

```php
function parseReport(string $path): array { /* только чтение и разбор */ }
function validateReport(array $rows): void { /* только правила */ }
function sendReport(array $rows, string $recipient): void { /* только доставка */ }
```

Практический вывод: спрашивайте не «это класс или нет», а «какие разные заинтересованные стороны или причины могут заставить меня менять этот код». Если ответов больше одного, стоит разделить, на каком бы уровне это ни происходило. При этом дробить до бесконечности тоже вредно: SRP не требует, чтобы каждый метод жил в отдельном модуле, и слишком мелкие единицы усложняют навигацию по коду.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

Ниже описано устройство DI-контейнера Symfony в современных версиях (5.x–7.x). Детали могут отличаться между версиями, поэтому для точных ссылок смотрите документацию конкретного релиза.

## 1. Что такое контейнер

Контейнер — это объект, который знает, как создавать сервисы и какие зависимости им нужны. Вместо `new OrderService(new PdoOrderRepository(...))` в коде вы просите контейнер получить готовый сервис, а он собирает граф объектов сам.

В Symfony контейнер строится из описаний: определения сервисов (`ContainerBuilder`) формируются из `services.yaml`, атрибутов вроде `#[AsEventListener]` и `#[AsDecorator]`, а также из пакетов (bundles) и расширений. Всё это описывается в объекте `ContainerBuilder`.

## 2. Что происходит при компиляции контейнера

Компиляция выполняется на этапе `cache:warmup` (или при первом запуске в `dev`, если кэш устарел). Результат — PHP-класс в `var/cache/.../App_KernelDevDebugContainer.php` или аналогичный файл.

Основные шаги, которые выполняет `ContainerBuilder::compile()` и набор compiler passes:

1. **Загрузка конфигурации.** Расширения (`Extension`) читают настройки пакетов и регистрируют определения сервисов.
2. **Compiler passes.** Это проходы по графу определений, например:
   - `AutowirePass` вычисляет аргументы конструкторов по типам (подробнее ниже);
   - `ResolveNamedArgumentsPass`, `ResolveInstanceofConditionalsPass` и другие нормализуют определения;
   - `DecoratorServicePass` подставляет декораторы;
   - `RemoveUnusedDefinitionsPass` удаляет сервисы, на которые никто не ссылается (кроме публичных);
   - `CheckCircularReferencesPass` и `CheckExceptionOnInvalidReferenceBehaviorPass` ищут циклы и несуществующие зависимости.
3. **Проверка ошибок.** Если зависимость не найдена или есть цикл, компиляция падает с понятным исключением. Поэтому ошибки DI в Symfony обычно видны сразу, а не на первом запросе.
4. **Дамп.** `PhpDumper` превращает определения в PHP-код: для каждого сервиса генерируется метод вида `getOrderServiceService()`, который вызывает нужные конструкторы. Для ленивых сервисов создаются прокси.

Важно: в production-режиме контейнер компилируется один раз и кэшируется. Сгенерированный код работает без рефлексии и почти без накладных расходов.

## 3. Как работает autowiring

Autowiring — это автоматическое связывание аргументов конструктора с сервисами по типу.

```php
final class OrderService
{
    public function __construct(
        private OrderRepository $orders,      // интерфейс
        private LoggerInterface $logger,
    ) {}
}
```

`AutowirePass` делает примерно следующее:

1. Для каждого сервиса с включённым autowiring читает параметры конструктора через рефлексию (на этапе компиляции, не на каждом запросе).
2. Для каждого параметра с типом-классом или интерфейсом ищет сервис с таким идентификатором. Идентификатор — полное имя класса или интерфейса.
3. Если интерфейс реализован одним сервисом, он подставляется автоматически. Если реализаций несколько, нужен явный алиас:

```yaml
services:
    App\Domain\OrderRepository: '@App\Infrastructure\DoctrineOrderRepository'
```

4. Скалярные параметры (`string $dsn`) не связываются по типу. Их задают явно через `arguments` или через `bind`:

```yaml
services:
    _defaults:
        autowire: true
        autoconfigure: true
        bind:
            $projectDir: '%kernel.project_dir%'
            string $stripeKey: '%env(STRIPE_KEY)%'
```

5. Если зависимость не удалось определить, компиляция завершается ошибкой с подсказкой, какие варианты доступны.

Сервисы, которые не запрошены явно, по умолчанию приватны и могут быть удалены, если на них никто не ссылается. Это ускоряет контейнер.

## 4. Что происходит при первом запросе сервиса

Допустим, вы вызываете `$container->get(OrderService::class)` или контроллер получает его через аргумент. Далее происходит следующее:

1. **Поиск метода.** Сгенерированный класс контейнера содержит `get()`, который по идентификатору находит нужный метод-фабрику. Если сервис уже создан, экземпляр возвращается из кэша `$services` (это shared-сервис, по умолчанию так и есть).
2. **Рекурсивное получение зависимостей.** Фабрика сервиса сначала запрашивает аргументы: `$this->get(OrderRepository::class)` и `$this->get(LoggerInterface::class)`. Каждая из этих зависимостей создаётся по той же схеме, рекурсивно.
3. **Создание объекта.** Вызывается конструктор с уже готовыми аргументами.
4. **Конфигурация после создания.** Если сработали configurator, вызовы методов (`calls` в определении) или `autoconfigure`-правила (например, интерфейс `EventSubscriberInterface` автоматически получает тег), они применяются к объекту.
5. **Сохранение в кэш.** Экземпляр записывается в контейнер, чтобы следующие обращения получили тот же объект.
6. **Возврат.** Вызывающий код получает готовый сервис.

### Ленивые сервисы

Если сервис помечен как `lazy: true` (или зависимость через ленивый прокси), контейнер вместо реального объекта передаёт прокси. Настоящий сервис создаётся только при первом обращении к методу прокси. Это полезно для тяжёлых зависимостей, которые нужны не всегда.

### Что важно знать на практике

- **Сервисы shared по умолчанию.** Один экземпляр на весь запрос (в PHP-FPM — на процесс, но каждый HTTP-запрос стартует с нуля). В Messenger-воркерах и долгоживущих процессах состояние сервисов может сохраняться между сообщениями, поэтому держите их без изменяемого состояния или сбрасывайте его.
- **Циклические зависимости** обнаруживаются на этапе компиляции. Их решают разрывом цикла, сеттер-инъекцией или ленивыми прокси.
- **Container как Service Locator.** Инъекция самого контейнера в сервис антипаттерн: зависимости становятся невидимыми. Лучше внедрять конкретные сервисы, а в контроллерах использовать `ServiceSubscriber`, если нужен набор ленивых зависимостей.
- **Отладка.** Команды `php bin/console debug:container OrderRepository` и `debug:autowiring` показывают, какой сервис будет подставлен и почему.

## Итог

Компиляция превращает описания сервисов в PHP-код фабрик с проверками графа; autowiring сопоставляет типы аргументов с сервисами на этапе сборки; при первом запросе фабрика рекурсивно создаёт зависимости, применяет конфигурацию и кладёт экземпляр в кэш. Поэтому в production-окружении DI почти не стоит по производительности, а ошибки конфигурации обычно обнаруживаются ещё до запуска приложения.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

Циклическая зависимость возникает, когда сервис A требует B, а B требует A (напрямую или через цепочку). Контейнер Symfony находит такие циклы на этапе компиляции (`CheckCircularReferencesPass`), и обычно сигнал о проблеме в дизайне. Сначала стоит спросить себя, почему зависимость пошла по кругу, и только потом выбирать технический приём.

## 1. Сначала проверить дизайн

Чаще всего цикл говорит о том, что граница ответственности проведена неверно:

- **Выделить общую логику** в третий сервис, от которого зависят оба.
- **Перенести метод** туда, где он логичнее: если `OrderService` вызывает `PaymentService`, который обратно вызывает `OrderService` для обновления статуса, часто достаточно вынести обновление статуса в событие или в доменный метод агрегата.
- **Заменить прямой вызов событием.** `PaymentService` публикует `PaymentCompleted`, а `OrderService` (или отдельный слушатель) реагирует на него. Направление зависимости становится односторонним.

```php
// Было: цикл OrderService <-> PaymentService
// Стало: PaymentService только публикует факт, слушатель обновляет заказ
final readonly class PaymentCompleted
{
    public function __construct(public OrderId $orderId) {}
}

#[AsEventListener]
final class MarkOrderPaid
{
    public function __construct(private OrderRepository $orders) {}

    public function __invoke(PaymentCompleted $event): void
    {
        $order = $this->orders->get($event->orderId);
        $order->markPaid();
        $this->orders->save($order);
    }
}
```

## 2. Разорвать цикл на уровне интерфейса

Если цикл остаётся, один из участников может зависеть не от конкретного класса, а от узкого интерфейса, который другой сервис реализует. Направление зависимости при этом не меняется, но граф в контейнере перестаёт быть циклическим, потому что ссылка идёт на абстракцию, а не на сервис-инстанс.

## 3. Ленивый сервис (`lazy: true`)

Контейнер передаёт прокси вместо реального объекта. Реальный создаётся при первом вызове метода, и цикл на этапе создания разрывается.

```php
use Symfony\Component\DependencyInjection\Attribute\Lazy;

final class OrderService
{
    public function __construct(
        #[Lazy] private PaymentService $payments,
    ) {}
}
```

Ленивые прокси полезны, но имеют цену: прокси — это подклассы (или интерфейсные прокси), поэтому `final` класс для ленивой инъекции не подойдёт. Ещё важно: ошибка в зависимости всплывёт не при создании, а при первом вызове.

## 4. Сеттер-инъекция

Один из сервисов получает зависимость через метод `setX()`, который вызывается после конструктора. Это разрывает цикл при создании, но делает зависимость необязательной на момент конструирования, то есть объект может оказаться в неполном состоянии. Использовать стоит осторожно, и лучше сочетать с проверкой в методе.

```yaml
services:
    App\Payment\PaymentService:
        calls:
            - setOrderService: ['@App\Order\OrderService']
```

Для уже существующих сервисов в Symfony также используют `#[Required]` на сеттере, но это тот же компромисс: инициализация не гарантирована конструктором.

## 5. Что не стоит делать

- **Внедрять контейнер** (`ContainerInterface`) и доставать сервис вручную. Это скрывает зависимость и обходит проверки компиляции.
- **Использовать `ServiceLocator` как обходной путь** без необходимости. Допустимо, когда нужен ленивый набор сервисов, но не как способ замолчать цикл.
- **Отключать проверку циклов** или переписывать код так, чтобы цикл стал невидимым.

## Итог

Порядок такой: сначала пересмотреть границы и заменить прямой вызов событием или выделенным сервисом; если цикл всё ещё оправдан, разорвать его через интерфейс, затем через `lazy`; сеттер-инъекцию оставить на крайний случай. Цикл, который не получилось убрать, обычно означает, что два сервиса на самом деле одна сущность с разными обязанностями.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

Задача делится на две части: разорвать связь между регистрацией и побочными действиями, и вынести их из цикла HTTP-запроса. Варианты отличаются тем, где именно происходит асинхронность и насколько надёжна доставка. Опыта эксплуатации этих схем у меня нет, поэтому опираюсь на документацию Symfony и типичные практики.

## Вариант 1. Синхронные слушатели события

Регистрация публикует `UserRegistered`, слушатели выполняют работу в том же запросе.

```php
#[AsEventListener]
final class SendWelcomeEmail
{
    public function __invoke(UserRegistered $event): void
    {
        $this->mailer->send(/* ... */);
    }
}
```

- **Плюсы:** просто, нет инфраструктуры, легко отлаживать.
- **Минусы:** ответ пользователю ждёт SMTP и индексатора. Если письмо падает, регистрация может откатиться или ответ станет 500, если исключение не перехвачено. Это прямо противоречит требованию.

Подходит только для быстрых и надёжных действий в памяти, но не для внешних сервисов.

## Вариант 2. Отложенная отправка после ответа (kernel.terminate)

Слушатель на `kernel.terminate` выполняется после отправки ответа клиенту, но в том же PHP-процессе.

```php
#[AsEventListener(event: KernelEvents::TERMINATE)]
final class IndexUser { /* ... */ }
```

- **Плюсы:** не нужна очередь и воркеры, ответ уходит быстрее.
- **Минусы:** процесс PHP-FPM занят дольше, нагрузка на воркеры растёт при пике. Если процесс упадёт, задача потеряется. Повторных попыток нет. Для письма и индекса это слабая гарантия доставки.

Подходит для лёгких побочных эффектов, например, сброса кэша или записи метрики.

## Вариант 3. Асинхронная очередь через Symfony Messenger (рекомендуемый)

Регистрация отправляет команду или сообщение в транспорт, а отдельный воркер выполняет обработчики.

```php
final readonly class SendWelcomeEmailMessage
{
    public function __construct(public UserId $userId) {}
}

#[AsMessageHandler]
final class SendWelcomeEmailHandler
{
    public function __invoke(SendWelcomeEmailMessage $message): void
    {
        // загрузить пользователя, отправить письмо
    }
}
```

В `messenger.yaml` указывается маршрут: `App\Message\SendWelcomeEmailMessage: async`. Транспорт может быть Doctrine (таблица в PostgreSQL), Redis, RabbitMQ или Amazon SQS. Воркер запускается командой `bin/console messenger:consume async`.

- **Плюсы:** ответ не ждёт внешних систем, повторные попытки и `failure_transport` встроены, сообщения переживают перезапуск, воркеры масштабируются отдельно.
- **Минусы:** нужна инфраструктура и мониторинг воркеров. Появляется eventual consistency: письмо придёт через секунды или минуты. Обработчики должны быть идемпотентными, потому что при повторе сообщение может прийти дважды. Сообщения лучше передавать id, а не сущности, иначе обработчик получит устаревшие данные.

Для письма и индексации это обычно лучший выбор.

## Вариант 4. Событие + асинхронный слушатель

Сочетание: регистрация публикует доменное событие, а слушатель ставит команду в Messenger. Так ядро не знает про очередь.

```php
#[AsEventListener]
final class DispatchWelcomeJob
{
    public function __construct(private MessageBusInterface $bus) {}

    public function __invoke(UserRegistered $event): void
    {
        $this->bus->dispatch(new SendWelcomeEmailMessage($event->userId));
        $this->bus->dispatch(new IndexUserMessage($event->userId));
    }
}
```

- **Плюсы:** доменный код не зависит от транспорта, добавить новый побочный эффект можно слушателем.
- **Минусы:** косвенность, сложнее проследить цепочку вызовов.

## Вариант 5. Transactional outbox

Если важно, чтобы событие гарантированно попало в очередь только при успешном сохранении пользователя, событие записывается в таблицу в той же транзакции, а отдельный процесс переносит его в брокер.

- **Плюсы:** нет потери событий при падении между `commit` и отправкой в очередь.
- **Минусы:** дополнительная таблица, фоновый процесс, сложнее поддержка. Оправдано, когда потеря события недопустима.

Для письма и индекса обычно хватает Messenger с Doctrine-транспортом, а outbox нужен, если сбой между сохранением и отправкой критичен.

## Итог

- Для ответа без ожидания внешних систем: **Messenger** (вариант 3 или 4).
- `kernel.terminate` годится только для лёгких задач без требований к надёжности.
- Синхронные слушатели подходят для внутренней логики, но не для письма и индекса.
- Outbox добавляйте, если нельзя терять события даже при сбое между транзакцией и очередью.

Практический минимум: передавать в сообщение идентификатор, сделать обработчики идемпотентными, настроить retry и `failure_transport`, а также мониторить очередь и время обработки.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

Ниже описано устройство безопасности Symfony 5.x–7.x. Детали конфигурации меняются между версиями, поэтому для точных ссылок смотрите документацию конкретного релиза.

## 1. Два разных вопроса: кто и что можно

Symfony Security делит работу на две части:

- **Аутентификация** отвечает на вопрос «кто это». Она создаёт объект `UserInterface` и кладёт его в токен (`TokenInterface`), который хранится в `TokenStorage`.
- **Авторизация** отвечает на вопрос «что ему можно». Проверка идёт через `AuthorizationChecker`: `isGranted('EDIT', $order)`.

## 2. Аутентификация

В `security.yaml` задаётся firewall, а в нём — один или несколько аутентификаторов (authenticators). Современный способ — классы, реализующие `AuthenticatorInterface` (или готовые: `form_login`, `json_login`, `access_token`).

Жизненный цикл запроса:

1. Firewall проверяет, подходит ли запрос (`supports()`).
2. Аутентификатор извлекает учётные данные (`Passport`) и проверяет их через провайдер пользователей и хешер паролей.
3. При успехе создаётся `Token` с пользователем и ролями, и он сохраняется в сессии (для stateful) или используется только для текущего запроса (для stateless API).
4. При неудаче вызывается обработчик ошибки, и пользователь получает 401 или редирект.

```yaml
security:
    firewalls:
        api:
            pattern: ^/api
            stateless: true
            custom_authenticators: [App\Security\ApiKeyAuthenticator]
```

Провайдер пользователей загружает пользователя по идентификатору, например через Doctrine `entity` provider.

## 3. Роли

Роль — строка вида `ROLE_ADMIN`, которая прикрепляется к пользователю через `getRoles()`. Иерархия задаётся в конфигурации:

```yaml
security:
    role_hierarchy:
        ROLE_ADMIN: [ROLE_MANAGER, ROLE_USER]
```

Роли проверяются через `access_control` (по путям) или `isGranted('ROLE_ADMIN')` в коде.

Роли хороши для вопроса «какая часть приложения доступна этому типу пользователя». Они не знают, к какому объекту относится право.

## 4. Voters

Voter — класс, который отвечает за решение по конкретному атрибуту и, при необходимости, по конкретному объекту. Он реализует три метода:

- `supports(string $attribute, mixed $subject): bool` — понимает ли он этот атрибут и объект;
- `voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token): bool` — решение;
- стратегия агрегации задаётся в `security.yaml` (`affirmative`, `consensus`, `unanimous`, по умолчанию `affirmative`).

```php
final class OrderVoter extends Voter
{
    public const EDIT = 'ORDER_EDIT';

    protected function supports(string $attribute, mixed $subject): bool
    {
        return $attribute === self::EDIT && $subject instanceof Order;
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token): bool
    {
        $user = $token->getUser();
        if (!$user instanceof User) {
            return false;
        }

        /** @var Order $subject */
        return $subject->ownerId()->equals($user->id());
    }
}
```

Использование в контроллере или сервисе:

```php
$this->denyAccessUnlessGranted(OrderVoter::EDIT, $order);
```

Voter также может учитывать роли: например, администратор редактирует любой заказ. Для этого в `voteOnAttribute` вызывают `$this->security->isGranted('ROLE_ADMIN')` или сверяют роли из токена.

## 5. Когда выбираю voter, а когда достаточно ролей

**Достаточно ролей**, если:
- правило касается типа пользователя, а не конкретного объекта («только админ открывает раздел отчётов»);
- доступ задаётся по маршруту через `access_control`;
- нет зависимости от владельца, статуса или других данных.

**Нужен voter**, если:
- решение зависит от объекта: владелец, статус, принадлежность к организации;
- правило сложнее одного условия и должно тестироваться отдельно;
- одно и то же правило используется в нескольких местах: контроллере, шаблоне Twig, сервисе, команде;
- нужно сочетать роли и данные: «менеджер видит заказы своего отдела, а админ всех».

Практически: роли выражают грубые границы, voters — правила на уровне бизнес-сущностей. Если на проекте начинают появляться проверки вида `if ($order->getOwner() === $user || in_array('ROLE_ADMIN', ...))` в разных местах, это сигнал вынести их в voter.

## Типичные ошибки

- Проверять владельца вручную в контроллере вместо voter: правило дублируется и легко забывается.
- Строить иерархию из большого числа ролей вместо атрибутов с объектами.
- Забывать, что `voteOnAttribute` вызывается и для анонимного пользователя: `$token->getUser()` может быть строкой `anon.`, поэтому проверяйте тип.
- Полагаться только на `access_control` для защиты данных: он работает по URL, а объект можно получить и другими путями, например через сервис или команду.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

Главная сложность в том, что Doctrine по умолчанию рассчитана на изменяемые сущности с сеттерами и гидрирует объекты через рефлексию, минуя конструктор. Поэтому неизменяемость и инварианты нужно обеспечить самостоятельно. Ниже варианты маппинга, от простого к сложному.

## Вариант 1. Embeddable

Doctrine поддерживает `#[ORM\Embeddable]`: значение встраивается в колонки таблицы владельца.

```php
#[ORM\Embeddable]
final readonly class Money
{
    public function __construct(
        #[ORM\Column(type: 'integer')]
        public int $amount,
        #[ORM\Column(type: 'string', length: 3)]
        public string $currency,
    ) {
        if ($amount < 0) {
            throw new InvalidArgumentException('Сумма не может быть отрицательной');
        }
    }
}

#[ORM\Entity]
class Order
{
    #[ORM\Embedded(class: Money::class, columnPrefix: 'total_')]
    private Money $total;
}
```

- **Плюсы:** стандартный механизм, данные в колонках, удобно для запросов и индексов, `readonly` работает.
- **Минусы и подводные камни:** Doctrine гидрирует объект через рефлексию, минуя конструктор. Инварианты в конструкторе не срабатывают при загрузке из БД, а значит, и поврежденные данные в БД пройдут молча. `readonly` на свойствах может мешать гидрации в некоторых версиях, поэтому проверяйте совместимость своей версии ORM. Обновление значения делается заменой целого объекта, а не изменением полей.

## Вариант 2. Custom Type

Значение сериализуется в один скаляр (строку, int, JSON) через собственный `Type`.

```php
final class MoneyType extends Type
{
    public const NAME = 'money';

    public function getSQLDeclaration(array $column, AbstractPlatform $platform): string
    {
        return $platform->getStringTypeDeclarationSQL(['length' => 20]);
    }

    public function convertToPHPValue($value, AbstractPlatform $platform): ?Money
    {
        if ($value === null) {
            return null;
        }
        [$amount, $currency] = explode(' ', $value);
        return new Money((int) $amount, $currency); // конструктор проверяет инварианты
    }

    public function convertToDatabaseValue($value, AbstractPlatform $platform): ?string
    {
        return $value === null ? null : "{$value->amount} {$value->currency}";
    }

    public function getName(): string { return self::NAME; }
}
```

- **Плюсы:** при гидрации вызывается конструктор, поэтому инварианты действуют всегда. Одна колонка.
- **Минусы:** значение нельзя эффективно искать по частям (`WHERE amount > 100` не работает без функций БД). Формат строки становится контрактом: смена формата требует миграции данных. Тип нужно зарегистрировать в конфигурации.

## Вариант 3. Маппинг через DTO или фабрику на уровне репозитория

Сущность хранит примитивы, а value object собирается в геттере или репозитории.

- **Плюсы:** полный контроль, никакой магии Doctrine.
- **Минусы:** код маппинга дублируется, сущность теряет явность типов, легко забыть пересборку и получить несогласованность.

## Вариант 4. Отдельная таблица (связь OneToOne)

Value object выносится в связанную сущность. Формально это уже не value object для Doctrine, а сущность с идентичностью.

- **Плюсы:** можно хранить сложные значения и историю.
- **Минусы:** лишние JOIN, сложнее согласованность, избыточность. Оправдано редко.

## Подводные камни, общие для всех вариантов

1. **Сравнение.** Doctrine при `flush` сравнивает значения, а для объектов сравнивает по ссылке. Замена `Money` новым объектом с теми же данными считается изменением, и это безопасно, но лишние UPDATE возможны. Для embeddable это обычно нормально.
2. **Мутирующие методы.** Если в value object есть `setAmount()`, неизменяемость рушится. Не используйте сеттеры, возвращайте новые экземпляры: `$money->add($other)`.
3. **Гидрация минует конструктор** (для embeddable и для сущностей). Поэтому инварианты нельзя проверять только в конструкторе. Для custom type конструктор вызывается, для embeddable нет. Учтите это при выборе.
4. **Null-значения.** Embeddable с `null` в колонках Doctrine может вернуть `null` вместо объекта, если все колонки пусты. Для обязательных значений задайте `nullable: false` и проверяйте.
5. **Запросы.** DQL работает с полями embeddable через путь `o.total.amount`, а custom type ограничен сравнением целиком. Продумайте, по каким полям нужны фильтрация и сортировка.
6. **Миграции.** Смена формата custom type или добавление колонок в embeddable требует миграции и backfill данных.
7. **Невалидные данные в БД.** Если в таблице оказалась запись, которую конструктор не пропустит, гидрация упадёт с исключением. Это полезно (проблема видна), но требует стратегии исправления данных.

## Практический выбор

- Простые значения, по которым нужны запросы и индексы (деньги, координаты, адрес): **embeddable**, плюс проверки в конструкторе и тесты на загрузку.
- Значения, для которых критичны инварианты при любой загрузке, а поиск по частям не нужен (идентификаторы вроде `Email`, сложные коды): **custom type**, поскольку конструктор вызывается всегда.
- Сложные структуры со своей историей: отдельная сущность, а не value object.

Важно: в обоих случаях покройте тестами цикл «сохранить, загрузить, сравнить», иначе ошибка маппинга обнаружится только в продакшене.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

Возьму пример агрегата «Заказ» (`Order`) с дочерними позициями (`OrderLine`). Корень `Order` — единственная точка входа: позиции не загружаются и не сохраняются отдельно, все изменения идут через него.

## 1. Маппинг коллекции

Дочерние сущности имеют идентичность внутри агрегата, но не существуют без корня. Поэтому связь делается через `OneToMany` с `cascade` и `orphanRemoval`.

```php
#[ORM\Entity]
#[ORM\Table(name: 'orders')]
class Order
{
    #[ORM\Id]
    #[ORM\Column(type: 'uuid')]
    private Uuid $id;

    #[ORM\Column(type: 'string', enumType: OrderStatus::class)]
    private OrderStatus $status;

    /** @var Collection<int, OrderLine> */
    #[ORM\OneToMany(
        targetEntity: OrderLine::class,
        mappedBy: 'order',
        cascade: ['persist'],
        orphanRemoval: true,
    )]
    private Collection $lines;

    public function __construct(Uuid $id)
    {
        $this->id = $id;
        $this->status = OrderStatus::New;
        $this->lines = new ArrayCollection();
    }

    public function addLine(ProductId $product, int $qty, Money $price): void
    {
        $this->assertModifiable();
        $this->lines->add(new OrderLine(Uuid::v7(), $this, $product, $qty, $price));
    }

    public function removeLine(Uuid $lineId): void
    {
        $this->assertModifiable();
        foreach ($this->lines as $line) {
            if ($line->id()->equals($lineId)) {
                $this->lines->removeElement($line); // orphanRemoval удалит строку
                return;
            }
        }
        throw new LineNotFound($lineId);
    }

    public function total(): Money
    {
        return array_reduce(
            $this->lines->toArray(),
            fn (Money $sum, OrderLine $l) => $sum->add($l->subtotal()),
            Money::zero('RUB'),
        );
    }

    private function assertModifiable(): void
    {
        if ($this->status !== OrderStatus::New) {
            throw new OrderNotModifiable($this->status);
        }
    }
}

#[ORM\Entity]
class OrderLine
{
    #[ORM\Id]
    #[ORM\Column(type: 'uuid')]
    private Uuid $id;

    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'lines')]
    #[ORM\JoinColumn(nullable: false, onDelete: 'CASCADE')]
    private Order $order;

    #[ORM\Column(type: 'uuid')]
    private Uuid $productId;

    #[ORM\Column(type: 'integer')]
    private int $qty;

    #[ORM\Embedded(class: Money::class, columnPrefix: 'price_')]
    private Money $price;

    public function __construct(Uuid $id, Order $order, Uuid $productId, int $qty, Money $price)
    {
        if ($qty <= 0) {
            throw new InvalidArgumentException('Количество должно быть положительным');
        }
        $this->id = $id;
        $this->order = $order;
        $this->productId = $productId;
        $this->qty = $qty;
        $this->price = $price;
    }

    public function id(): Uuid { return $this->id; }
    public function subtotal(): Money { return $this->price->multiply($this->qty); }
}
```

Ключевые моменты маппинга:
- `orphanRemoval: true` удаляет строку, когда её убрали из коллекции. Без него останутся «висящие» записи.
- `cascade: ['persist']` сохраняет новые позиции вместе с корнем. Каскад `remove` на коллекции обычно не нужен: удаление агрегата целиком лучше делать явно.
- Коллекция `lines` приватна, наружу отдаётся только чтение (`toArray()` или `Collection` через `readonly`-обёртку). Прямой `$order->getLines()->add(...)` обходит инварианты.
- `Uuid` для id позиций позволяет создавать их до `flush`.

## 2. Границы транзакции

Правило: **одна транзакция = один агрегат**. Изменяется ровно один корень, и всё, что относится к инвариантам, сохраняется атомарно. Связи между агрегатами не должны требовать одновременного изменения в одной транзакции. Если, например, нужно списать остаток на складе, это отдельный агрегат, и согласованность достигается событием, а не общей транзакцией.

## 3. Кто и когда вызывает flush

- **Flush вызывает прикладной слой** (обработчик команды, application service), а не доменные объекты. Домен не знает о `EntityManager`.
- **Один flush на одну команду.** Обработчик загружает агрегат, вызывает методы корня, и `flush` выполняется один раз в конце. Это и есть граница транзакции.
- **Транзакцию оборачивает инфраструктура.** Симфони-обёртка `Doctrine\ORM\EntityManager::wrapInTransaction()` или middleware Messenger (`doctrine_transaction`) открывает транзакцию вокруг обработчика и делает `flush`.

```php
#[AsMessageHandler]
final class AddLineHandler
{
    public function __construct(
        private OrderRepository $orders, // абстракция над Doctrine
    ) {}

    public function __invoke(AddLineCommand $cmd): void
    {
        $order = $this->orders->get($cmd->orderId); // загрузка агрегата целиком
        $order->addLine($cmd->productId, $cmd->qty, $cmd->price); // все инварианты в корне
        $this->orders->save($order); // внутри: $em->persist($order); без flush
    }
}
```

Репозиторий отвечает за `persist`, а коммит делает middleware. Так обработчик не знает о транзакции, и её легко проверить в тестах.

## 4. Подводные камни

1. **Ленивая загрузка и N+1.** Обход `lines` без подготовки даёт запрос на каждый заказ. Для чтения используйте `JOIN FETCH` в отдельном запросе или read model, а не агрегат.
2. **Загрузка огромного агрегата.** Если позиций тысячи, агрегат тяжёлый. Это сигнал пересмотреть границы: возможно, коллекция не часть инварианта.
3. **Конкурентные изменения.** Два процесса меняют один заказ. Используйте optimistic locking: `#[ORM\Version]` на корне. Иначе последняя запись молча перетрёт предыдущую.
4. **Flush внутри доменного метода или репозитория с flush.** Тогда транзакция раскрывается наружу и частичные изменения могут закоммититься.
5. **Изменение позиций мимо корня.** Если где-то есть прямой `EntityManager::persist(OrderLine)`, инварианты корня обходятся.
6. **Доменное событие до flush.** Если событие отправляется до коммита, слушатель может увидеть несохранённое состояние. Публикуйте события после успешного flush или через outbox.
7. **Каскад remove** на `OneToMany` удаляет дочерние записи по одной, что дорого. Для больших коллекций удаляйте агрегат через DQL или отдельную команду.

Итог: корень — единственная точка входа, коллекция маппится с `orphanRemoval`, транзакция покрывает один агрегат, а `flush` вызывается один раз в прикладном слое через обёртку транзакции, а не из домена.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

Диагностику и решение я описываю по документации Doctrine и Symfony и типичной практике. Опыта разбора реальных инцидентов у меня нет.

## 1. Как подтвердить проблему

Сначала нужно убедиться, что дело действительно в N+1, а не в медленном запросе или сериализации.

**Профилировщик Symfony (Web Profiler).** Вкладка Doctrine показывает число запросов и их время. Если на одну страницу приходится, например, 1 запрос на список заказов и ещё 50 одинаковых по структуре запросов на `customer` или `lines`, это N+1.

**Логирование SQL в dev-окружении:**
```yaml
# config/packages/doctrine.yaml (только dev)
doctrine:
    dbal:
        logging: true
```

**Счётчик запросов в тестах.** Удобно зафиксировать ожидаемое число запросов, чтобы регрессия ловилась в CI. Например, через middleware логгера DBAL или `Doctrine\DBAL\Logging\Middleware`, который считает вызовы, и assert на результат.

**EXPLAIN на стороне PostgreSQL.** Если много одинаковых запросов с разными id в `WHERE`, это типичный признак. Медленный отдельный запрос видно через `pg_stat_statements`.

Признаки N+1: число запросов растёт линейно с числом записей на странице; запросы отличаются только параметрами; время складывается из множества мелких обращений, а не одного тяжёлого.

## 2. Способы решения

### Способ 1. JOIN FETCH в DQL

```php
$orders = $em->createQuery(
    'SELECT o, c FROM App\Entity\Order o JOIN o.customer c WHERE o.status = :s'
)->setParameter('s', 'paid')->getResult();
```

- **Плюсы:** один запрос, явно, легко читать, работает с `ManyToOne` и `OneToOne`.
- **Минусы:** при `JOIN FETCH` коллекции (`OneToMany`) строки декартово умножаются, пагинация через `setMaxResults` ломается: Doctrine предупреждает и грузит всё в память. Для коллекций нужен отдельный приём (см. пункт 4).

### Способ 2. Пакетная загрузка (batch fetching)

Doctrine при обращении к одной из ленивых связей подгружает сразу пачку родственных сущностей. Настраивается через `fetch: EXTRA_LAZY` или батч-размер на уровне маппинга / `#[ORM\BatchSize]`.

- **Плюсы:** не нужно менять запросы, хорошо работает с коллекциями и пагинацией.
- **Минусы:** число запросов всё равно растёт, но медленнее (N/batch). Поведение неявное, сложнее объяснить, что происходит.

### Способ 3. Отдельный запрос с IN

Загрузить связанные сущности одним запросом по списку id, затем собрать карту вручную.

```php
$customerIds = array_unique(array_map(fn ($o) => $o->customerId(), $orders));
$customers = $em->getRepository(Customer::class)->findBy(['id' => $customerIds]);
```

- **Плюсы:** полный контроль, предсказуемые запросы, подходит для read-сценариев.
- **Минусы:** больше кода, легко забыть и вернуться к ленивой загрузке, сложнее поддерживать.

### Способ 4. Два запроса вместо JOIN для коллекций

Сначала выбрать корни с пагинацией, затем загрузить коллекции для их id с `JOIN FETCH`. Так пагинация не ломается.

- **Плюсы:** корректная пагинация и отсутствие дубликатов.
- **Минусы:** два запроса, логика разнесена по коду.

### Способ 5. Read model / DTO-проекция

Для списков и отчётов агрегат не нужен. Запрос выбирает только нужные поля в DTO через `NEW` или Partial.

```php
$rows = $em->createQuery(
    'SELECT NEW App\Dto\OrderRow(o.id, o.total, c.name)
     FROM App\Entity\Order o JOIN o.customer c'
)->getResult();
```

- **Плюсы:** минимум данных, самый быстрый вариант, не загружает агрегат и его инварианты.
- **Минусы:** отдельный код для чтения, дублирование моделей, нужно поддерживать синхронизацию с записью (для сложных случаев CQRS).

### Способ 6. Нативный SQL или оптимизированный запрос на уровне БД

Для сложных выборок — `JSON_AGG`, оконные функции, `LATERAL` в PostgreSQL.

- **Плюсы:** максимальная производительность, полный контроль над планом.
- **Минусы:** привязка к диалекту PostgreSQL, сложнее тестировать и поддерживать.

## 3. Что выбрать

- Простая связь `ManyToOne` в списке: **JOIN FETCH**.
- Коллекция с пагинацией: **два запроса** (способ 4).
- Нужен только набор полей для вывода: **DTO-проекция** (способ 5).
- Много разных связей, не хочется переписывать код: **batch fetching** как временное решение.
- Сложная аналитика: **нативный SQL**.

Важно: не «исправлять вслепую». После изменения снова считайте запросы в профилировщике и зафиксируйте их число тестом, иначе N+1 вернётся при следующей доработке.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

Код приложения проверяет инварианты до записи, но у него есть пределы. Ограничения в БД — последняя линия защиты, которая работает независимо от того, как именно данные попали в таблицу.

## Почему одной валидации в коде недостаточно

- **Гонки.** Два запроса одновременно проверяют, что email свободен, и оба проходят проверку. Без `UNIQUE` в БД оба записываются. Проверка `SELECT` перед `INSERT` этого не предотвращает.
- **Другие пути записи.** Миграции, скрипты, административные инструменты, прямой SQL, второе приложение или сервис, который пишет в ту же базу, обходят доменные классы.
- **Ошибки в коде.** Баг в одном месте, забытая проверка в новом эндпоинте, `UPDATE` в DQL мимо агрегата.
- **Эволюция.** Через год правило меняется, старые строки не проходят новую проверку, но остаются в таблице. БД покажет это при миграции, а код молча примет.
- **Гидрация минует конструктор.** Как обсуждали ранее, Doctrine может загрузить состояние, которое конструктор не пропустил бы.

Ограничения в БД не заменяют код, а дополняют его: код даёт понятные ошибки пользователю, БД гарантирует, что невалидное состояние не попадёт в хранилище.

## Инструменты PostgreSQL

### 1. NOT NULL
Самое дешёвое и самое важное. Обязательные поля должны быть `NOT NULL`, иначе `null` проникнет в любую выборку.

### 2. UNIQUE и уникальные индексы
Для гарантии уникальности, включая частичные индексы:
```sql
CREATE UNIQUE INDEX uniq_user_email ON users (lower(email));
-- уникальность только для активных записей
CREATE UNIQUE INDEX uniq_active_slug ON products (slug) WHERE deleted_at IS NULL;
```
Выражения в индексе (`lower(email)`) позволяют проверять регистронезависимо.

### 3. CHECK
Простые инварианты строки:
```sql
ALTER TABLE order_lines ADD CONSTRAINT qty_positive CHECK (qty > 0);
ALTER TABLE orders ADD CONSTRAINT total_non_negative CHECK (total_amount >= 0);
```
CHECK не работает с другими таблицами, поэтому подходит для правил внутри одной строки.

### 4. FOREIGN KEY
Гарантирует ссылочную целостность. Выбор `ON DELETE` важен:
```sql
ALTER TABLE order_lines
  ADD CONSTRAINT fk_line_order FOREIGN KEY (order_id)
  REFERENCES orders(id) ON DELETE CASCADE;
```
`CASCADE` согласован с `orphanRemoval` из агрегата. `RESTRICT` лучше там, где удаление родителя должно быть осознанным.

### 5. EXCLUDE (пересечения)
Запрещает пересекающиеся диапазоны, например бронирование одного номера на перекрывающиеся даты:
```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE bookings ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (room_id WITH =, during WITH &&);
```
Это то, что в коде почти не выразить без гонок.

### 6. Enum-подобные типы и домены
`CREATE TYPE order_status AS ENUM (...)` или `DOMAIN` с CHECK для повторно используемых правил (например, валидный email или код валюты). Минус: изменение ENUM требует миграции, поэтому часто проще `VARCHAR` с CHECK.

### 7. Триггеры
Для сложных межстрочных правил и аудита. Используйте осторожно: логика уходит из кода, её сложнее найти и тестировать, и она может неожиданно срабатывать в миграциях.

### 8. Ограничения отложенной проверки
`DEFERRABLE INITIALLY DEFERRED` откладывает проверку FK или UNIQUE до коммита. Нужно для вставки взаимно ссылающихся строк в одной транзакции.

## Когда что использовать

- Обязательность и формат одной строки: `NOT NULL`, `CHECK`.
- Уникальность, включая гонки при параллельной регистрации: `UNIQUE` индекс (код-проверка только для понятного сообщения).
- Связи между таблицами: `FOREIGN KEY`.
- Непересекаемость интервалов: `EXCLUDE`.
- Правила между таблицами или сложная логика: триггер или, лучше, код с блокировкой (`SELECT ... FOR UPDATE`) или optimistic locking.

Практическое правило: всё, что является инвариантом данных и не зависит от внешнего контекста, фиксируйте в схеме. Всё, что зависит от сценария, пользовательских сообщений и внешних систем, оставляйте в коде. Обе стороны должны выполнять одни и те же правила, иначе схема и код быстро разойдутся: поэтому в Doctrine ограничения описываются в маппинге (`#[ORM\UniqueConstraint]`, `#[ORM\Index]`) и в миграциях, а не только вручную.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

Опыта разбора реальных медленных запросов у меня нет, поэтому ниже процесс, который соответствует документации PostgreSQL и общепринятой практике.

## 1. Сначала измерить, а не гадать

Прежде чем менять запрос или индексы, выясняю, какой именно запрос медленный и насколько. Иначе легко оптимизировать то, что занимает 2% времени.

- **`pg_stat_statements`**: показывает суммарное время, число вызовов и среднее время по нормализованным запросам. Смотрю по `total_exec_time`, потому что быстрый запрос, выполняемый миллион раз, может быть важнее одного тяжёлого.
- **Логи медленных запросов**: `log_min_duration_statement = 200` (мс) в `postgresql.conf` покажет запросы, превышающие порог.
- **Продакшен-метрики и APM**: показывают, в какое время деградация и совпадает ли она с нагрузкой или деплоем.
- **На стороне приложения**: профилировщик Symfony / логи Doctrine показывают, какой именно SQL уходит из кода. Иногда «медленный запрос» на самом деле N+1, как обсуждали выше.

## 2. Посмотреть план

Основной инструмент:

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE) SELECT ...;
```

Что смотрю в плане:
- **Тип доступа**: `Seq Scan` на большой таблице с селективным фильтром — подозрительно; `Index Scan` или `Bitmap Index Scan` — обычно лучше.
- **Расхождение оценок и факта**: `rows=10` при `actual rows=500000` означает устаревшую статистику или неподходящий тип оценки. Лечится `ANALYZE` или `ALTER TABLE ... SET STATISTICS`.
- **`BUFFERS`**: много `shared read` указывает на чтение с диска; высокий `temp read/written` — сортировка или хэш не умещаются в `work_mem`.
- **Узлы сортировки и `Sort Method: external merge`**: признак нехватки памяти для сортировки.
- **Вложенные циклы (`Nested Loop`) с большим числом итераций**: часто приводит к квадратичной стоимости, особенно если внутренняя сторона без индекса.
- **Фильтр после JOIN**: условие применилось поздно, и лишние строки читались зря.
- **`Rows Removed by Filter`**: большое значение означает, что индекс не покрывает условие.

Важно: `EXPLAIN ANALYZE` реально выполняет запрос. Для записи используйте его в транзакции с откатом или на реплике.

## 3. Типовые причины

1. **Нет подходящего индекса** или индекс не используется из-за типа выражения. Например, `WHERE lower(email) = ?` не использует обычный индекс по `email`; нужен индекс по выражению.
2. **Функции или неявное приведение типов** в условии: `WHERE created_at::date = ...`, сравнение `int` с `text`. Индекс обходится.
3. **Лидирующий `%` в `LIKE`**: `LIKE '%abc'` не использует B-tree. Нужен `pg_trgm` с GIN.
4. **Неэффективная пагинация** через `OFFSET` на больших значениях: читается и отбрасывается всё до смещения. Лучше keyset-пагинация (`WHERE id > :last ORDER BY id LIMIT 50`).
5. **Устаревшая статистика** после массовых изменений: планировщик выбирает плохой план. Помогает `ANALYZE`, в крайнем случае расширенная статистика.
6. **Лишние колонки и широкие выборки**: `SELECT *` мешает index-only scan и тянет лишнее по сети.
7. **Избыточные или неиспользуемые индексы**: замедляют `INSERT`/`UPDATE`. Проверяю через `pg_stat_user_indexes` (`idx_scan = 0`).
8. **Коррелированные подзапросы** и `NOT IN` с `NULL`, которые переписываются в `EXISTS`, `NOT EXISTS` или `JOIN`.
9. **Блокировки и ожидания**: запрос медленный не потому, что считает, а потому что ждёт блокировку. Смотрю `pg_stat_activity` и `pg_locks`.
10. **Недостаточный `work_mem` или плохие настройки** памяти и планировщика. Меняю осторожно, после анализа, а не как первое действие.

## 4. Оптимизация по шагам

1. Зафиксировать текущее время и план (`EXPLAIN ANALYZE`).
2. Выделить главную причину в плане (чаще всего одна).
3. Внести одно изменение: индекс, переписанный запрос или статистику.
4. Снова снять план и время на реальных или похожих данных.
5. Проверить, что другие запросы не замедлились из-за нового индекса.

Типичные варианты исправлений:

```sql
-- составной индекс под фильтр и сортировку
CREATE INDEX CONCURRENTLY idx_orders_status_created ON orders (status, created_at DESC);

-- частичный индекс для горячего подмножества
CREATE INDEX CONCURRENTLY idx_orders_unpaid ON orders (created_at) WHERE status = 'new';

-- индекс под LIKE '%...%'
CREATE INDEX CONCURRENTLY idx_products_name_trgm ON products USING gin (name gin_trgm_ops);
```

`CONCURRENTLY` не блокирует запись на время создания индекса, но не работает внутри транзакции и требует аккуратности при откате неудачного построения (`INVALID` индекс нужно удалить).

## 5. Что не делаю сразу

- Не добавляю индексы «на всякий случай»: каждый индекс замедляет запись и занимает место.
- Не меняю глобальные настройки PostgreSQL без доказательств.
- Не переписываю запрос, не понимая, почему план плохой.

Итог: сначала измерить через `pg_stat_statements` и логи, затем разобрать план `EXPLAIN (ANALYZE, BUFFERS)`, найти одну главную причину, исправить её минимальным изменением и проверить результат на похожих данных.

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

Агрегат в DDD — это кластер связанных объектов (сущностей и value objects), который рассматривается как единое целое для изменения данных. У него есть один **корень агрегата** (aggregate root): через него извне обращаются ко всем внутренним объектам, и только он гарантирует выполнение **инвариантов** — правил, которые должны выполняться всегда, после каждой операции.

Ключевые свойства:
- **Инварианты** — отправная точка. Агрегат нужен там, где есть правило, которое нельзя нарушить даже на мгновение, например «в заказе не больше 50 позиций» или «сумма оплат не превышает итог».
- **Транзакционная граница.** Один агрегат меняется в одной транзакции.
- **Ссылки между агрегатами** делаются по идентификатору, а не по объекту. Так граница остаётся явной, а загрузка не тянет за собой весь граф.
- **Маленький агрегат.** Чем меньше объектов внутри, тем проще согласовать инварианты и тем меньше конфликтов при параллельных изменениях.

## Пример: интернет-магазин

Есть правила:
1. Позиции заказа не могут меняться после оплаты.
2. Количество товара в позиции больше нуля.
3. Заказ не может содержать одинаковый товар дважды (позиции объединяются).

Инварианты 1 и 3 касаются только позиций и статуса самого заказа, значит, они живут в одном агрегате:

```php
final class Order // корень агрегата
{
    private array $lines = []; // OrderLine, доступны только через корень
    private OrderStatus $status;

    public function __construct(
        private OrderId $id,
        private CustomerId $customerId, // ссылка на другой агрегат по id
    ) {
        $this->status = OrderStatus::New;
    }

    public function addProduct(ProductId $productId, int $qty, Money $price): void
    {
        if ($this->status !== OrderStatus::New) {
            throw new OrderNotModifiable();
        }
        if ($qty <= 0) {
            throw new InvalidArgumentException('Количество должно быть положительным');
        }
        $key = $productId->value;
        $this->lines[$key] = isset($this->lines[$key])
            ? $this->lines[$key]->increase($qty)
            : new OrderLine($productId, $qty, $price);
    }
}
```

Что здесь важно:
- `Customer` — отдельный агрегат. `Order` хранит только `CustomerId`, а не объект покупателя. Баланс клиента, его адрес и история живут своими правилами.
- `Product` и остаток на складе — тоже отдельные агрегаты. Списание остатка происходит реакцией на событие `OrderPlaced` в собственной транзакции, а не внутри заказа.
- `OrderLine` существует только внутри `Order`. Снаружи его не создают и не меняют напрямую.

## Типовая ошибка: границы по таблицам или по UI

Частый сценарий: агрегат «Заказ» начинают проектировать по схеме БД или по экрану. Тогда в агрегат тянут `Customer` (чтобы показать имя), `Product` (чтобы показать название), `Warehouse` (чтобы проверить остаток), историю платежей и доставку. Получается огромный объект:

- любое изменение любого поля конфликтует с параллельным изменением другого;
- при загрузке тянется весь граф, и появляются N+1 и тяжёлые запросы;
- инварианты «остаток не меньше нуля» и «заказ не больше 50 позиций» нельзя одновременно гарантировать в одной транзакции без блокировок на весь граф;
- границы определяются тем, что удобно показать на экране, а не тем, что должно меняться атомарно.

Исправление: спросить, какие правила должны выполняться **атомарно**. Всё, что можно согласовать событием или проверить eventual consistency, выносится в другой агрегат. Для отображения имени покупателя достаточно хранить id и читать через отдельный read model, а не держать его в корне заказа.

## Как я определяю границы на практике

1. Найти инварианты и отметить, какие данные нужны, чтобы их проверить.
2. Спросить: нужна ли согласованность прямо сейчас или достаточно «скоро»?
3. Проверить, меняются ли объекты вместе и вызывает ли их изменение один и тот же бизнес-процесс.
4. Ссылаться на другие агрегаты по идентификатору.
5. Проверить на практике: если для одной операции приходится грузить и менять несколько корней, границы, скорее всего, проведены неверно.

Итог: агрегат задаётся инвариантами и транзакционной границей, а не таблицами, экранами или связями в ORM.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

Без защиты результат предсказуем: последняя запись молча перетирает предыдущую, и часть изменений теряется. Если процессы работают с разными полями, потеря может быть незаметной. Если они меняют связанные инварианты (например, один добавляет позицию, а второй меняет статус на «оплачен»), можно получить состояние, которое правила домена не допускают.

Типичный сценарий: процесс A загружает заказ (версия 5), процесс B загружает его же (версия 5). A добавляет позицию и сохраняет (версия 6). B меняет статус и сохраняет, записывая поверх версии 6 и затирая позицию из A. Ни одна из операций не выбросила ошибку.

## Стратегии

### 1. Оптимистичная блокировка (основной вариант)

Процессы не блокируют друг друга при чтении. При записи проверяется, что версия не изменилась с момента загрузки. Если изменилась, запись отклоняется.

В Doctrine это делается атрибутом `#[ORM\Version]` на корне агрегата:

```php
#[ORM\Entity]
class Order
{
    #[ORM\Version]
    #[ORM\Column(type: 'integer')]
    private int $version;
}
```

При `flush` Doctrine добавляет условие `WHERE version = :expected` и увеличивает версию. Если строк обновлено 0, бросается `OptimisticLockException`.

Что делаю дальше:
- ловлю исключение на границе (обработчик команды или middleware) и либо повторяю команду с перезагрузкой агрегата (ограниченное число раз), либо возвращаю конфликт клиенту (HTTP 409);
- повтор допустим только для идемпотентных или переформулируемых команд. Команду «списать 1 шт. с остатка» повторять можно только с перезагрузкой, иначе списание пройдёт дважды;
- версию учитываю и в API: клиент передаёт ETag или версию, и сервер сравнивает её при изменении.

Плюсы: дёшево, нет блокировок в БД, хорошо для большинства сценариев, где конфликты редки. Минусы: при частых конфликтах много повторов и недовольных пользователей.

### 2. Пессимистичная блокировка

Загрузка с блокировкой строки: `SELECT ... FOR UPDATE` (в Doctrine `LockMode::PESSIMISTIC_WRITE`). Второй процесс ждёт, пока первый закоммитит.

```php
$order = $em->find(Order::class, $id, LockMode::PESSIMISTIC_WRITE);
```

Использую, когда конфликты частые и дорогие для повтора, например при списании ограниченного остатка. Нужно держать транзакцию короткой, иначе очередь ожидания растёт, и учитывать риск взаимных блокировок (deadlock), поэтому блокировать несколько агрегатов стоит в одном заранее заданном порядке.

### 3. Сериализация через очередь или партиционирование

Все команды для одного агрегата направляются в одну очередь или к одному воркеру (например, по ключу `orderId` в Messenger с транспортом, который сохраняет порядок). Конкуренции нет по построению, но появляется задержка и сложность масштабирования.

Подходит, когда команд много и они быстрые, а блокировки в БД нежелательны.

### 4. Дополнительные ограничения в БД

Если конфликт касается инварианта, который можно выразить в схеме (уникальность, `CHECK qty >= 0` для остатка), он не даст записать невалидное состояние даже при гонке. Это страховка, а не замена блокировки: сообщение об ошибке получится хуже.

### 5. Проектирование команд, снижающее конфликты

- Делать агрегат меньше: чем меньше корень, тем реже конфликты.
- Выносить независимые данные в отдельные агрегаты (например, счётчики просмотров, флаги уведомлений).
- Использовать команды-операции (`addLine`, `markPaid`), а не «сохранить весь объект целиком».

## Что выбираю

- По умолчанию: оптимистичная блокировка с `#[ORM\Version]`, конфликт возвращается как 409 или повторяется с перезагрузкой.
- Для ограниченных ресурсов с частыми конфликтами: пессимистичная блокировка на короткой транзакции.
- Для потока команд с высокой нагрузкой на один агрегат: сериализация через очередь.
- Всегда: инварианты в схеме там, где это возможно, и тесты на параллельное выполнение (два процесса, один агрегат), чтобы проверить, что конфликт обнаруживается.

Итог: без явной стратегии конкурентные изменения молча портят данные. Я закладываю версию в агрегат с самого начала, обрабатываю конфликт осознанно и выбираю пессимистичную блокировку только там, где оптимистичная даёт неприемлемое число повторов.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

Доменное событие фиксирует факт, который уже произошёл в домене: `OrderPlaced`, `PaymentCompleted`, `UserRegistered`. Оно описывает прошедшее время, поэтому называю его в прошедшем времени. Опыта эксплуатации у меня нет, поэтому опираюсь на документацию Symfony и практики DDD.

## Когда публикую

- Событие появляется внутри агрегата, когда он меняет состояние и это значимо для других частей системы. Агрегат записывает событие в свой внутренний список (`recordThat`), а не отправляет его сразу.
- Публикация происходит на уровне прикладного сервиса или обработчика команды, после успешного изменения агрегата и до коммита или сразу после него, в зависимости от стратегии ниже.

```php
final class Order
{
    private array $events = [];

    public function markPaid(): void
    {
        $this->assertCanBePaid();
        $this->status = OrderStatus::Paid;
        $this->events[] = new OrderPaid($this->id, $this->total());
    }

    /** @return list<object> */
    public function pullEvents(): array
    {
        $events = $this->events;
        $this->events = [];
        return $events;
    }
}
```

Агрегат не знает о шине и инфраструктуре. Он только фиксирует, что произошло, и отдаёт события наружу.

## Как обрабатываю

Обработчик команды делает три вещи: меняет агрегат, сохраняет его и забирает события.

```php
final class MarkOrderPaidHandler
{
    public function __invoke(MarkOrderPaid $cmd): void
    {
        $order = $this->orders->get($cmd->orderId);
        $order->markPaid();
        $this->orders->save($order);
        // события уходят в механизм публикации после сохранения
        foreach ($order->pullEvents() as $event) {
            $this->eventBus->dispatch($event);
        }
    }
}
```

Слушатели делятся на два типа:
- **Синхронные внутренние** (в той же транзакции): для инвариантов, которые должны быть атомарны с изменением. Использую редко.
- **Асинхронные** через Messenger: отправка письма, обновление индекса, интеграции. Сообщение содержит id и тип события, обработчик загружает свежие данные сам.

## Что решает подход

- **Развязка.** Ядро не знает, кто реагирует на факт. Новая реакция добавляется слушателем, без правки агрегата (это связано с OCP).
- **Ограничение связности между агрегатами.** Вместо того чтобы `Order` вызывал склад, склад реагирует на `OrderPlaced` в своей транзакции.
- **Журнал фактов.** События можно логировать, использовать для аудита и построения read model.
- **Eventual consistency** там, где атомарность не нужна, без распределённой транзакции.

## Что создаёт

- **Косвенность.** Цепочка «событие → слушатель → команда → событие» трудно проследить. Нужны логи с correlation id.
- **Порядок и повторы.** Асинхронные события могут прийти не по порядку и дважды. Обработчики должны быть идемпотентными, а агрегаты устойчивыми к запоздалым событиям.
- **Устаревшие данные.** Слушатель, получивший событие позже, видит уже другое состояние. Не передавайте в событие всё состояние как истину, передавайте факт и идентификатор.
- **Эволюция схемы события.** Переименование или изменение полей ломает подписчиков, особенно при асинхронной обработке очередей со старыми сообщениями.
- **Потеря события.** Если событие отправлено, но транзакция откатилась, подписчики получили несуществующий факт. Или наоборот: транзакция закоммитилась, а отправка упала.

## Связь с транзакциями БД

Это главный подводный камень. Есть три варианта:

1. **Публикация до коммита.** Слушатель может прочитать ещё не закоммиченное состояние или событие уйдёт для откатившейся транзакции. Так делать нельзя для асинхронных подписчиков.
2. **Публикация после коммита** (например, через Messenger-middleware, который отправляет сообщения после успешной транзакции, или `kernel.terminate`-подобная схема). Событие не уйдёт для откатившейся записи, но если процесс упадёт между `commit` и отправкой, событие потеряется.
3. **Transactional outbox.** Событие записывается в таблицу `outbox` в той же транзакции, что и агрегат. Отдельный процесс читает таблицу и публикует события. Гарантия «ровно то, что закоммитилось, будет опубликовано хотя бы раз». Цена: таблица, фоновый процесс и идемпотентные подписчики.

Практически: для внутренней логики домена события в памяти и синхронные слушатели внутри одной транзакции, для интеграций и писем — асинхронная шина с публикацией после коммита, а если потеря события недопустима — outbox. Doctrine-транзакцию и публикацию связываю в одном месте (middleware или обёртка обработчика), чтобы не разъехались.

Итог: события фиксируют факты внутри агрегата, публикуются после успешного сохранения, и их надёжность определяется тем, как они связаны с коммитом. Вопрос «что будет, если транзакция откатится» нужно задавать для каждого события.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

Entity определяется **идентичностью**: два объекта с одинаковыми атрибутами, но разными id — разные сущности. Их состояние меняется со временем, и мы отслеживаем, что это тот же самый заказ или тот же пользователь. Value Object определяется **значением**: два объекта с одинаковыми полями взаимозаменяемы, он неизменяем и не имеет собственного id. Деньги «100 RUB» из одного места равны деньгам «100 RUB» из другого.

```php
// Value Object: равенство по значению, неизменяем
final readonly class Money
{
    public function __construct(public int $amount, public string $currency)
    {
        if ($amount < 0) {
            throw new InvalidArgumentException('Сумма не может быть отрицательной');
        }
    }

    public function add(self $other): self
    {
        $this->assertSameCurrency($other);
        return new self($this->amount + $other->amount, $this->currency);
    }

    public function equals(self $other): bool
    {
        return $this->amount === $other->amount && $this->currency === $other->currency;
    }

    private function assertSameCurrency(self $other): void
    {
        if ($this->currency !== $other->currency) {
            throw new InvalidArgumentException('Валюты не совпадают');
        }
    }
}

// Entity: идентичность важнее атрибутов, состояние меняется
final class Order
{
    public function __construct(private OrderId $id, private OrderStatus $status) {}

    public function id(): OrderId { return $this->id; }

    public function markPaid(): void
    {
        $this->status = OrderStatus::Paid;
    }
}
```

## Как решаю, что является чем

Задаю несколько вопросов:

1. **Нужно ли отслеживать «этот же самый» объект во времени?** Если да (заказ, клиент, счёт), это Entity. Если важно только значение (сумма, адрес, диапазон дат, цвет), это Value Object.
2. **Можно ли заменить объект на равный без последствий?** Если можно, это VO. Заменить «мой заказ № 42 на другой с теми же полями» нельзя, а заменить «адрес доставки на такой же адрес» можно.
3. **Есть ли у объекта собственный жизненный цикл и инварианты, которые меняются?** Если да, скорее Entity. Если у него только правила проверки значения, скорее VO.
4. **Как его будут искать?** Поиск по идентификатору указывает на Entity, поиск по содержимому или сравнение значений на VO.
5. **Проверка через поведение:** если в коде появляется `$a->setX(...)` для изменения «части» объекта, часто это VO, которое стоило заменить новым экземпляром.

Типичная ошибка: делать из всего Entity с `id` и сеттерами, включая деньги, адрес и email. Тогда инварианты размазываются по сеттерам, а сравнение становится сравнением по ссылке. Обратная ошибка: сделать VO то, что реально меняется и должно отслеживаться (например, статус заказа как «значение» без идентичности заказа).

## Единый язык (Ubiquitous Language)

Это общий словарь, на котором говорят разработчики, аналитики, бизнес и эксперты предметной области. Термины из него попадают в код без перевода: если бизнес говорит «отменить резерв», в коде будет `cancelReservation()`, а не `releaseStock()` или `updateStatusTo(3)`.

Влияние на код:
- **Имена классов и методов** совпадают с терминами бизнеса. Код читается как описание процесса, и разработчик может спросить у эксперта «правильно ли я понял».
- **Разные значения одного слова разделяются по контекстам.** «Клиент» в продажах и «клиент» в доставке могут быть разными моделями, и это нормально (ограниченные контексты).
- **Инварианты и правила** записываются в терминах домена, а не технических флагов. Вместо `if ($order->status === 2)` появляется `if ($order->isAwaitingPayment())`.
- **Ошибки и исключения** называются бизнес-языком: `OrderCannotBeCancelled`, а не `InvalidStateException`.
- **Тесты** описывают сценарии словами предметной области, и их может читать не только программист.

Признак проблемы: в коде и в разговорах с бизнесом используются разные слова для одного понятия. Тогда стоит остановиться и уточнить термин, иначе расхождение превратится в баги, которые никто не заметит, пока они не попадут в продакшен.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

Опыта поддержки такой структуры в продакшене у меня нет, поэтому описываю типичную схему, которая соответствует общепринятым практикам и идеям Robert C. Martin и Hexagonal Architecture.

## 1. Слои и правило зависимостей

Главное правило: **зависимости направлены внутрь**. Внешние слои знают о внутренних, но не наоборот. Домен не знает ни о Doctrine, ни о Symfony, ни о HTTP.

```
Инфраструктура (адаптеры)  ──►  Приложение (use cases)  ──►  Домен (ядро)
  Doctrine, Symfony, HTTP,        обработчики команд,         сущности, VO,
  Messenger, API-клиенты          порты (интерфейсы)          события, правила
```

### Домен (Domain)
- Entity, Value Object, агрегаты, доменные события, доменные исключения, доменные сервисы (правила, которые не принадлежат одной сущности).
- Чистый PHP: без `use Doctrine\...`, `use Symfony\...`, без `Request`, без `EntityManager`.
- Интерфейсы репозиториев описываются здесь же или в слое приложения (порты).

### Приложение (Application)
- Use cases: обработчики команд и запросов, которые оркеструют домен.
- Порты: интерфейсы для внешнего мира (`OrderRepository`, `PaymentGateway`, `Clock`, `EventPublisher`).
- DTO команд и запросов. Транзакционная граница обычно здесь (через middleware или обёртку).
- Зависит только от домена.

### Инфраструктура (Infrastructure / Adapters)
- Реализации портов: `DoctrineOrderRepository`, `StripePaymentGateway`, `MessengerEventPublisher`.
- Конфигурация фреймворка, маппинг Doctrine, миграции, сериализация.
- Зависит от приложения и домена, реализуя их интерфейсы.

### Презентация / вход (Presentation, Delivery)
- Symfony-контроллеры, CLI-команды, консьюмеры очередей, формы, API-ресурсы.
- Превращает HTTP-запрос или сообщение в команду, вызывает use case, превращает результат в ответ.
- Не содержит бизнес-правил.

## 2. Куда попадают конкретные вещи

| Элемент | Слой | Почему |
|---|---|---|
| Doctrine-маппинг (атрибуты на сущностях) | Инфраструктура | Сущность в домене без атрибутов ORM; маппинг выносят в XML/YAML или отдельные классы конфигурации. Практически компромисс: атрибуты ORM часто оставляют на домене, и это принимают осознанно. |
| `DoctrineOrderRepository` | Инфраструктура | Реализация порта `OrderRepository` |
| Symfony-контроллер | Презентация | Принимает HTTP, валидирует форму, вызывает use case |
| Обработчик команды (`MarkOrderPaidHandler`) | Приложение | Оркестрирует агрегат, репозиторий, события |
| Обработчик очереди (Messenger `#[AsMessageHandler]`) | Презентация (вход) или приложение | Это входящий адаптер: распаковывает сообщение и вызывает use case. Бизнес-логики внутри быть не должно. |
| `Order::markPaid()` | Домен | Правило состояния заказа |
| `StripePaymentGateway` | Инфраструктура | Реализация порта `PaymentGateway` |
| `EventPublisher` интерфейс | Приложение | Порт; реализация через Messenger в инфраструктуре |

Пример слоёв для одного сценария:

```php
// Презентация: контроллер только переводит HTTP в команду
final class MarkPaidController
{
    public function __construct(private MessageBusInterface $bus) {}

    #[Route('/orders/{id}/pay', methods: ['POST'])]
    public function __invoke(string $id): Response
    {
        $this->bus->dispatch(new MarkOrderPaid($id));
        return new Response(status: 202);
    }
}

// Приложение: use case
final class MarkOrderPaidHandler
{
    public function __construct(
        private OrderRepository $orders,
        private EventPublisher $events,
    ) {}

    public function __invoke(MarkOrderPaid $cmd): void
    {
        $order = $this->orders->get(OrderId::fromString($cmd->orderId));
        $order->markPaid();
        $this->orders->save($order);
        $this->events->publish(...$order->pullEvents());
    }
}

// Домен: правило
final class Order
{
    public function markPaid(): void
    {
        if ($this->status !== OrderStatus::AwaitingPayment) {
            throw new OrderCannotBeMarkedPaid($this->status);
        }
        $this->status = OrderStatus::Paid;
        $this->events[] = new OrderPaid($this->id);
    }
}
```

Обработчик очереди устроен так же, как контроллер: `#[AsMessageHandler]` на классе, который вызывает тот же use case. Поэтому один и тот же сценарий можно запустить из HTTP, из консоли или из очереди, не дублируя логику.

## 3. Как следить за границами

1. **Статический анализ архитектуры.** Инструменты `deptrac` (PHP) задают правила: `Domain` не может зависеть от `Infrastructure` и `Symfony`. Нарушение ломает CI.
2. **Правила PHPStan / Psalm** и запрет `use` определённых пространств имён в домене через кастомные правила.
3. **Структура каталогов и пространств имён** отражает слои (`Domain/`, `Application/`, `Infrastructure/`, `UI/`), и отклонения видны в ревью.
4. **Тесты домена без фреймворка.** Если тесты домена и приложения запускаются без ядра Symfony и без БД, граница соблюдается сама. Медленный или сложный тест домена часто признак утечки зависимостей.
5. **Code review с чек-листом:** нет ли `EntityManager` или `Request` в домене, бизнес-правил в контроллере, `new` инфраструктурных классов внутри use case.

Типичные нарушения: контроллер, который сам считает скидку и пишет через `EntityManager`; доменная сущность, вызывающая `Mailer`; обработчик очереди с логикой, которая не доступна из HTTP.

Итог: зависимости направлены внутрь, домен чистый, порты описывают потребности приложения, адаптеры их реализуют, а `deptrac` в CI не даёт границам размыться.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

Опыта ведения большого тестового набора в продакшене у меня нет, поэтому описываю стратегию, которая соответствует общепринятым практикам Symfony и PHPUnit.

## 1. Пирамида тестов

Основа — быстрые unit-тесты домена, посередине — интеграционные тесты приложения и инфраструктуры с реальной PostgreSQL, сверху — несколько функциональных (HTTP) тестов на ключевые сценарии.

- **Unit (большинство, миллисекунды):** агрегаты, value objects, доменные сервисы, правила состояний. Без Symfony, без БД, без моков инфраструктуры.
- **Интеграционные (средне):** обработчики команд с реальным Doctrine и PostgreSQL, маппинг (сохранить–загрузить–сравнить), кастомные запросы репозиториев, миграции.
- **Функциональные / HTTP (мало):** `WebTestCase` для критических путей: регистрация, оплата, доступ по voter. Проверяют связку маршрутов, безопасности, сериализации и ответов.
- **E2E (единицы или ноль в самом приложении):** если нужны, то во внешнем стенде с реальными соседними сервисами.

Ориентир: если функциональных тестов больше интеграционных, а тех больше unit, пирамида перевёрнута, и набор станет медленным и хрупким.

## 2. Что мокаю, а что нет

**Мокаю:**
- внешние API и платёжные шлюзы (`PaymentGateway` через порт, в тесте фейк с предсказуемыми ответами);
- почту, HTTP-клиенты, часы (`Clock`), генераторы id, если результат должен быть детерминированным;
- порты приложения в unit-тестах обработчиков, если важна только логика оркестрации.

**Не мокаю:**
- PostgreSQL в интеграционных тестах. Мок `EntityManager` или репозитория не проверяет запросы, маппинг, индексы и `UNIQUE`-ограничения. Тесты с SQLite дают ложное ощущение: различия диалектов и типов (`jsonb`, `uuid`, `citext`, exclude-ограничения) ломают правду.
- собственные value objects и агрегаты: их создают настоящими, мок VO бессмысленен.
- Doctrine в тесте маппинга: если мокнуть `EntityManager`, маппинг не проверен.

Правило: мокать то, что находится за границей системы или недетерминировано. Внутреннее поведение использовать настоящим.

## 3. Изоляция данных с PostgreSQL

- Каждый тест выполняется в транзакции с откатом (`dama/doctrine-test-bundle` или аналогичный подход). Это быстро и не требует пересоздания схемы.
- Схема создаётся один раз миграциями, а не `schema:update` на каждом запуске.
- Для тестов, которые сами требуют коммита (проверка обработки после commit, `UNIQUE` при гонке), используйте отдельную очистку через `TRUNCATE` и помечайте такие тесты группой, чтобы они не замедляли остальные.
- Отдельная база под тесты, которую можно поднять в Docker одной командой.

## 4. Быстрота

- Unit-тесты не поднимают ядро Symfony (`KernelTestCase` только когда нужен контейнер).
- Кэшировать контейнер тестового окружения: `cache:warmup --env=test`.
- Не грузить фикстуры целиком: строить минимальные данные в каждом тесте через фабрики (Foundry или собственные билдеры).
- Параллельный запуск (`paratest`), если набор растёт, но только при изолированных данных.
- Не спать (`sleep`) и не ждать реальных таймеров: используйте внедрённые часы.

## 5. Стабильность

- **Недетерминированность:** фиксировать время, id, порядок выборки (всегда `ORDER BY` в ожидаемых результатах).
- **Общее состояние:** никаких статических кешей и глобальных переменных между тестами; проверять, что тесты проходят в случайном порядке (`--order-rand`).
- **Внешние сервисы:** в CI не ходить в интернет; фейки вместо реальных шлюзов.
- **Флаки-тесты** не игнорировать: помечать, разбирать причину и либо чинить, либо удалять.
- **Тесты параллельности** (два процесса, один агрегат) держать отдельным набором, с контролируемым таймингом, иначе они станут флаки.
- **Сообщения об ошибках:** проверять поведение и состояние, а не конкретный текст исключения, если он может меняться.

## 6. Что проверять в CI

- Unit и интеграционные тесты на каждом коммите; функциональные тоже, но на небольшом наборе.
- Покрытие смотреть как индикатор, а не как цель: важнее покрытие инвариантов домена.
- Статанализ (PHPStan) и `deptrac` вместе с тестами, чтобы архитектурные границы проверялись так же строго.
- Время прогона отслеживать: если набор замедляется, это сигнал пересмотреть уровни тестов, а не терпеть.

Итог: много быстрых unit-тестов домена, реальный PostgreSQL в интеграционных тестах с откатом транзакций, мало HTTP-тестов на критичные пути, мокаются только внешние и недетерминированные зависимости.

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Этот вопрос близок к тому, что мы уже обсуждали для агрегатов, поэтому здесь сосредоточусь на общей картине: проблемы на уровне одной строки в БД и способы их решения. Опыта эксплуатации этих схем у меня нет, опираюсь на документацию PostgreSQL, Doctrine и типичные практики.

## 1. Какие проблемы возникают

- **Lost update (потерянное обновление).** Оба процесса прочитали значение, каждый изменил своё поле, и последний `UPDATE` перезаписал всё целиком. Пример: два оператора меняют поля одной карточки клиента, и один из них молча теряет свою правку.
- **Нарушение инварианта при гонке.** Оба проверили «остаток ≥ 1», оба списали единицу, остаток ушёл в минус. Проверка в коде без блокировки не спасает.
- **Dirty read и неповторяемое чтение.** Процесс видит незакоммиченные или меняющиеся между двумя чтениями данные. Зависит от уровня изоляции; в PostgreSQL грязного чтения нет, но неповторяемое и фантомное возможны при `READ COMMITTED`.
- **Взаимная блокировка (deadlock).** Два процесса берут блокировки в разном порядке. PostgreSQL обнаруживает это и откатывает одну транзакцию с ошибкой.
- **Тихая потеря ошибки.** Если конфликт не обнаружен, пользователь видит «успех», а данных нет.

## 2. Способы защиты

### Вариант 1. Оптимистичная блокировка через версию

Строка содержит `version`. `UPDATE ... WHERE id = ? AND version = ?`, при нулевом количестве затронутых строк конфликт. В Doctrine это `#[ORM\Version]`.

- **Плюсы:** без блокировок в БД, хорошо масштабируется, понятно для API (ETag, 409).
- **Минусы:** при частых конфликтах много повторов; нужна обработка исключения и решение, повторять или сообщить пользователю; не защищает от инвариантов между несколькими строками.

### Вариант 2. Пессимистичная блокировка строки

`SELECT ... FOR UPDATE` (в Doctrine `LockMode::PESSIMISTIC_WRITE`). Второй процесс ждёт коммита первого.

- **Плюсы:** конфликт исключён, логика простая, подходит для ограниченных ресурсов (остаток, места, номера).
- **Минусы:** ожидание и падение пропускной способности при горячих строках; риск deadlock; транзакция должна быть короткой; `FOR UPDATE` не работает с оптимистичной логикой и требует дисциплины.

Вариант `FOR UPDATE SKIP LOCKED` подходит для очередей задач: воркеры берут разные строки и не ждут друг друга.

### Вариант 3. Атомарное обновление на стороне БД

Не читать, а менять условно одной командой:

```sql
UPDATE products SET stock = stock - 1 WHERE id = ? AND stock >= 1;
-- затронуто 0 строк => товара нет
```

- **Плюсы:** минимум кода, гонка невозможна, блокировка на время одного оператора.
- **Минусы:** логика правил переезжает в SQL, сложнее сложные инварианты, сложнее тестировать через домен.

### Вариант 4. Ограничения в схеме

`CHECK (stock >= 0)`, `UNIQUE`, `EXCLUDE`. Они не дают записать невалидное состояние даже при гонке.

- **Плюсы:** последняя линия защиты, работает для любых путей записи.
- **Минусы:** ошибка приходит как исключение БД, сообщение для пользователя надо переводить; не заменяет предотвращение конфликта.

### Вариант 5. Сериализация через очередь

Все изменения одной сущности направляются в один обработчик (партиционирование по ключу). Конкуренции нет по построению.

- **Плюсы:** без блокировок в БД, хорошо для потоков команд.
- **Минусы:** задержка, сложность, не подходит для синхронного ответа пользователю.

### Вариант 6. Уровни изоляции SERIALIZABLE

PostgreSQL при `SERIALIZABLE` отслеживает опасные зависимости и откатывает одну из транзакций (ошибка сериализации, код 40001), приложение должно повторить транзакцию.

- **Плюсы:** защищает и от аномалий между несколькими строками, без явных блокировок в коде.
- **Минусы:** частые откаты и повторы, нагрузка на CPU, обязательная логика повтора в приложении.

## 3. Когда что выбираю

- **Редактирование карточки человеком, конфликты редки:** оптимистичная блокировка с версией и ответом 409.
- **Ограниченный ресурс с горячей строкой (остаток, последнее место):** атомарный `UPDATE ... WHERE stock >= 1` или пессимистичная блокировка на короткой транзакции; плюс `CHECK` в схеме.
- **Очередь задач:** `FOR UPDATE SKIP LOCKED`.
- **Инвариант между несколькими строками или агрегатами:** `SERIALIZABLE` с повтором или пессимистичная блокировка в фиксированном порядке.
- **Уникальность (email, slug):** `UNIQUE` индекс всегда, проверка в коде только ради сообщения.
- **Всегда:** тест, который запускает два процесса на одну строку и проверяет, что конфликт обнаружен или инвариант сохранён.

Итог: сначала определить, что именно нельзя потерять или нарушить. Lost update лечится версией или блокировкой, инвариант на ресурсе лечится атомарной операцией или `CHECK`, а многострочные инварианты требуют `SERIALIZABLE` или явного порядка блокировок. Схема БД остаётся страховкой в любом случае.

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

Честно: у меня нет собственного опыта работы в команде и продакшен-релизов, поэтому описываю процесс, который я считаю разумным и который соответствует распространённым практикам (trunk-based или упрощённый GitHub Flow с короткими ветками). Ниже — что и почему.

## 1. Ветвление

- **Основная ветка `main`** всегда в состоянии, готовом к деплою. Прямые коммиты в неё запрещены защитой ветки.
- **Короткоживущие ветки от `main`**: `feature/…`, `fix/…`, `chore/…`. Живут от нескольких часов до пары дней.
- **Без долгоживущих `develop` и веток релизов** в типичном проекте. Git-flow оправдан, когда одновременно поддерживаются несколько версий продукта, а для одного сервиса с непрерывным деплоем он создаёт лишние слияния и расхождения.

Почему: чем дольше ветка, тем больше конфликтов и тем позже обнаруживаются интеграционные проблемы. Короткие ветки дешевле интегрировать.

Если задача большая, я разбиваю её на несколько маленьких PR, которые можно слить по очереди, часто за флагом функциональности (feature flag), чтобы неготовый код не попадал пользователям.

## 2. Формат коммитов

Использую Conventional Commits:

```
feat(orders): добавить отмену заказа в статусе Paid

Отмена требует возврата платежа, поэтому вызывает RefundService
через событие OrderCancellationRequested.

Refs: TASK-142
```

- Тип: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`.
- Заголовок в императиве, до ~72 символов, описывает **что** и по возможности **зачем**.
- Тело объясняет **почему**, потому что диф уже показывает, что изменилось.
- Ссылка на задачу в футере.

Почему: история читается как changelog, по ней можно автоматически генерировать релиз-ноты и определять версию (semver), а `git log` и `git blame` отвечают на вопрос «почему так сделано».

Коммиты делаю атомарными: один логический шаг (например, рефакторинг отдельно от изменения поведения). Перед PR привожу историю в порядок через interactive rebase, но не переписываю уже опубликованную и чужую ветку.

## 3. Pull request

Состав PR:
- Описание: проблема, решение, как проверено, что важно проверить ревьюеру, ссылка на задачу.
- Размер: стараюсь держать до нескольких сотен строк изменений. Большой PR ревьюят поверхностно.
- Тесты и миграции в том же PR, что и код, который их требует.
- Скриншоты или примеры ответа API, если меняется внешнее поведение.

Перед открытием запускаю локально линтеры, PHPStan, `deptrac`, тесты. В CI те же проверки обязательны, и merge без зелёного пайплайна запрещён.

Почему: автоматика дешевле ревьюера. Ревьюер должен думать о логике и архитектуре, а не о пробелах.

## 4. Ревью

Что проверяю в чужом PR:
- соответствует ли решение задаче и инвариантам домена;
- границы слоёв (нет ли Doctrine или Symfony в домене, бизнес-логики в контроллере);
- миграции: обратная совместимость, блокировки на больших таблицах (`CREATE INDEX CONCURRENTLY`), наличие отката;
- тесты: проверяют ли они поведение, а не реализацию, нет ли флаки-признаков;
- обработка ошибок, логирование без утечки данных, безопасность (voters, валидация входа);
- читаемость: имена из единого языка.

Комментарии разделяю на блокирующие и рекомендательные (например, префиксом `nit:`). Автор отвечает на каждый, ревьюер отмечает решение явно.

Почему: ревью нужно прежде всего для знания кода в команде и поимки ошибок, которые тесты не покрывают. Строгость к блокирующим и мягкость к стилю экономят время обеих сторон.

## 5. Релизы и продакшен

- Merge в `main` через squash или rebase-merge по политике команды; squash даёт один коммит на задачу, rebase сохраняет атомарность. Я склоняюсь к squash для небольших задач и к rebase для серий осмысленных коммитов.
- Каждый merge в `main` автоматически уходит на staging. Продакшен деплоится по тегу (`v1.4.0`), который ставится после проверки на staging.
- Версии по semver, changelog генерируется из Conventional Commits.
- Миграции БД выкатываются отдельно и заранее, если они несовместимы: сначала добавить колонку и код, который её поддерживает, потом удалять старое. Это позволяет откатить приложение без отката схемы.
- Откат: тег предыдущей версии и деплой; `git revert` коммита предпочтительнее, чем force-push в `main`.
- Hotfix: ветка от тега продакшена, минимальный фикс, PR в `main` и в нужные релизные ветки.

Почему так: главное свойство процесса — предсказуемость. Защищённый `main`, короткие ветки и автоматические проверки делают так, что проблемы ловятся до продакшена, а откат занимает минуты.

## Что не делаю

- Не переписываю историю общих веток (`force-push` только в свою ветку и только с `--force-with-lease`).
- Не коммичу секреты и не полагаюсь на то, что `.gitignore` спасёт: проверяю `git diff --staged` и использую хук или сканер секретов.
- Не мержу собственный PR без ревью, даже в маленьких проектах.

Итог: короткие ветки от `main`, Conventional Commits, небольшие PR с автоматической проверкой, содержательное ревью и деплой по тегам. Каждый элемент уменьшает стоимость ошибки и делает историю полезной для команды.

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

Честно: у меня нет собственного опыта ревью в команде, поэтому описываю подход, который считаю разумным и который соответствует распространённым практикам.

## Что такое хорошее ревью

Цель ревью — не найти все ошибки (это задача тестов и статанализа), а убедиться, что код решает правильную задачу, не ломает инварианты и будет понятен через полгода. Хорошее ревью быстрое, конкретное и доброжелательное к коду, а не к автору.

## Маркировка замечаний

Каждое замечание явно помечаю, чтобы автор понимал, что обязательно, а что нет:

- **блокирующее** (без префикса или `blocker:`) — ошибка, нарушение инварианта, утечка данных, проблема безопасности, сломанная обратная совместимость миграции. Без исправления или явного обоснования не апрувлю;
- **вопрос** (`question:`) — мне непонятно, почему так сделано. Это не обязательно означает проблему: часто ответ автора показывает, что решение обдуманное, и тогда стоит добавить комментарий в код;
- **предложение** (`suggestion:`) — лучший вариант, но текущий тоже приемлем. Автор решает сам;
- **мелочь** (`nit:`) — стиль, именование, опечатка. Не блокирует merge, и если линтер умеет это проверять, я не трачу на это время людей.

Пример:

```
blocker: здесь `findOne` без блокировки, два процесса могут списать остаток дважды. Нужен `LockMode::PESSIMISTIC_WRITE` или версия агрегата.

question: почему обработка ошибки здесь проглатывается? Если это намеренно, поясните комментарием.

nit: `$d` лучше назвать `$deliveryDate`.
```

## На что смотрю в первую очередь

1. **Корректность и инварианты.** Правильно ли решается задача, не обходит ли код доменные правила (прямой `persist` строки агрегата, `UPDATE` мимо корня, проверка «до» без блокировки).
2. **Безопасность и данные.** Проверки доступа (voters, а не только скрытые кнопки), валидация входа, отсутствие секретов в логах и ответах, SQL без конкатенации.
3. **Границы и архитектура.** Нет ли Doctrine или `Request` в домене, бизнес-логики в контроллере, зависимостей, которые ломают правило направления.
4. **Миграции и совместимость.** Блокировки на больших таблицах, обратимость, совместимость со старым кодом во время выката.
5. **Тесты.** Проверяют ли они поведение, а не внутреннюю реализацию; есть ли тест на сам баг или на граничный случай.
6. **Читаемость и единый язык.** Имена из терминов предметной области, понятные ошибки.

Только после этого смотрю на форматирование и стиль, и то в основном там, где его не проверяет автоматика.

## Разногласия с автором

Исхожу из того, что у автора может быть контекст, которого у меня нет.

- Сначала уточняю: задаю вопрос, а не утверждаю «это неправильно». Часто выясняется, что решение обоснованно.
- Если спор о вкусе или о равноценных вариантах, я не настаиваю: решает автор, а я фиксирую мнение как `suggestion:`.
- Если спор о корректности, привожу конкретный сценарий, который ломается (последовательность действий, входные данные, тест), а не ссылаюсь на «так принято». Лучше всего написать падающий тест.
- Если договориться не получается, выношу вопрос на синхронный разговор или к владельцу модуля, а не затягиваю переписку на десятки комментариев.
- Принятое решение фиксирую в PR или в документации, если оно повлияет на будущий код.

## Чего избегаю

- Ревью на десятки «nit»-замечаний, которые скрывают один серьёзный баг.
- Переписывание чужого решения под свой стиль без причины.
- Апрув без чтения, «потому что срочно» и «потому что автор старший».
- Личные формулировки («ты не подумал») вместо фактов о коде.

Итог: блокирующие замечания — только о корректности, безопасности и инвариантах; остальное помечаю как вопрос, предложение или мелочь; разногласия решаю фактами и тестами, а не авторитетом.

Сырая жалоба вида «не могут найти заказы из прошлого» ничего не говорит о том, что именно сломано. Прежде чем писать задачу, я бы уточнил у бизнеса несколько фактов, но ниже сформулирую задачу так, чтобы исполнитель мог начать работу без дополнительных вопросов. Допущения, которые я сделал, явно выписаны, и при их расхождении с реальностью задачу надо скорректировать.

## Задача

**Название:** Поиск исторических заказов в личном кабинете пользователя

**Проблема.** Пользователи не могут найти свои заказы, совершённые более 30 дней назад, через личный кабинет (раздел «Мои заказы»). За последний месяц поддержка получила N обращений (N подставить из тикетов), большинство связано с отсутствием заказов в списке. *Допущение: проблема в разделе «Мои заказы», а не в email-уведомлениях или в оформлении.*

**Цель.** Пользователь в разделе «Мои заказы» может найти любой свой заказ независимо от давности, а количество обращений в поддержку по этой теме снижается. Метрика: доля обращений с темой «не найден заказ» падает до согласованного уровня в течение двух недель после релиза.

**Что нужно сделать.**
1. Воспроизвести проблему: найти заказ старше 30 дней через личный кабинет на staging и зафиксировать, на каком шаге он пропадает.
2. Определить причину: фильтр по дате, лимит выборки, пагинация без перехода на следующую страницу, сортировка, отсутствие поиска по номеру, права доступа или что-то другое. Для этого проверить запрос в репозитории и логи.
3. Исправить причину. Если проблема в пагинации или сортировке, использовать keyset-пагинацию или корректный `ORDER BY` с индексом. Если нужен поиск, добавить фильтр по номеру заказа и дате.

1. **Проверяю противоречие фактами, а не интуицией.** Замеряю: что даёт текущий план, что даёт вариант с индексом, каков реальный объём данных. Часто оказывается, что конфликт мнимый.

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

В PostgreSQL конструкции `FORCE INDEX` нет. Её используют в MySQL и MariaDB (`SELECT ... FROM orders FORCE INDEX (idx_status)`), а также там есть `USE INDEX` и `IGNORE INDEX`. Если вы видели её в PostgreSQL-запросе, это либо синтаксис из другой СУБД, либо ошибка в коде, который не выполнится.

## Что делает PostgreSQL вместо этого

Планировщик PostgreSQL сам выбирает план, и вмешиваться в него напрямую можно двумя способами, оба в основном для диагностики:

- **Параметр сессии `enable_*`.** Например, `SET enable_seqscan = off;` запрещает последовательное сканирование, и планировщик вынужден брать индекс, если он подходит. Это не гарантия: если индекс неприменим, будет выбран другой медленный план. Параметр действует на текущую сессию или транзакцию (`SET LOCAL`), поэтому его удобно проверить в `EXPLAIN`, но в продакшен-коде его не оставляют.
- **Расширение `pg_hint_plan`.** Даёт комментарии-подсказки вида `/*+ IndexScan(orders idx_orders_status_created) */`. Требует установки расширения и считается крайней мерой, потому что подсказка переживает изменение данных и схемы, но перестаёт быть правильной.

## Когда это действительно нужно

Вмешательство в план оправдано редко. Сначала я проверяю причину плохого плана:

1. **Устаревшая статистика.** `ANALYZE` на таблице, при необходимости `ALTER TABLE ... SET STATISTICS`.
2. **Неподходящий индекс.** Нет индекса, индекс не покрывает фильтр или сортировку, выражение в условии отличается от выражения в индексе.
3. **Несоответствие типов.** Неявное приведение, из-за которого индекс не используется.
4. **Неверные оценки из-за корреляции колонок.** Помогает расширенная статистика `CREATE STATISTICS`.

Если после этого план всё равно неудачен, а данные и запрос стабильны, можно рассмотреть `pg_hint_plan` с комментарием в коде и задачей на пересмотр. В задаче про поиск заказов я бы сначала добавил составной индекс и проверил план, а не стал что-либо форсировать.

Итог: `FORCE INDEX` в PostgreSQL не существует. Аналог для диагностики — `enable_*` в сессии, для продакшена — правильный индекс и статистика, а подсказки планировщика — последнее средство.

## Что делает strict_types

Директива меняет только правило проверки аргументов при вызове функций, объявленных в этом файле. Без неё движок при несоответствии типа пытается привести значение (`'5'` в `int`), с ней такое приведение запрещено и бросается `TypeError`.

## Почему влияние обычно мало

- **Проверка типа дешёвая.** Сравнение типа zval с ожидаемым выполняется в одну-две инструкции. Приведение (`'5'` → `5`) тоже не бесплатно, так что в слабом режиме иногда работа даже больше, а не меньше.
- **Она не меняет количество вызовов и логику.** Строгий режим не добавляет циклов, аллокаций и обращений к памяти на горячем пути в типичном коде.
- **Это компиляционный признак файла.** Флаг применяется при компиляции opcache, поэтому в продакшене, где opcache включён, стоимость проверки уже учтена в скомпилированном коде.
- **Реальные узкие места в другом:** запросы к БД, сериализация, HTTP, N+1, плохие алгоритмы. Они на порядки дороже проверки типов.

## Когда разница может стать заметной

Теоретически, на микробенчмарке с миллионами вызовов очень маленькой функции, разница может быть измеримой в процентах. Но это то, что проверяется профилировщиком, а не предположением: нужно замерить на реальном коде через Xdebug/Blackfire или `hyperfine` до и после.

## Практический вывод

Не отключать `strict_types` ради скорости: он ловит ошибки на границах модулей, а выигрыш почти наверняка не будет заметен в общем времени ответа. Если вопрос всё же возникает, измеряйте на своём коде и смотрите на долю времени функции в профиле, а не на абстрактный процент.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

Утверждение неверно: Doctrine ORM поддерживает составные первичные ключи. Пометив несколько свойств атрибутом `#[ORM\Id]`, вы получаете составной ключ. Ограничения есть, но не отказ от поддержки.

## Как это выглядит

```php
#[ORM\Entity]
#[ORM\Table(name: 'order_lines')]
class OrderLine
{
    #[ORM\Id]
    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'lines')]
    #[ORM\JoinColumn(name: 'order_id', nullable: false, onDelete: 'CASCADE')]
    private Order $order;

    #[ORM\Id]
    #[ORM\Column(type: 'integer')]
    private int $position;

    #[ORM\Column(type: 'integer')]
    private int $qty;
}
```

В таблице получается `PRIMARY KEY (order_id, position)`. Для связи через ключевую ассоциацию (`order` как `#[ORM\Id]`) Doctrine требует, чтобы родительская сущность была загружена или создана до дочерней, потому что её идентификатор участвует в ключе.

## Почему это иногда кажется проблемой

- **Идентичность составная.** `find()` принимает массив: `$em->find(OrderLine::class, ['order' => $order, 'position' => 3])`. Сравнение и поиск по нескольким полям неудобны в коде и в API.
- **Сущность с идентификатором-связью.** Пока родитель не сохранён, у дочерней сущности нет полного ключа, и `persist` с последующим `flush` требует аккуратного порядка.
- **Изменение ключевого поля** по сути создаёт другую сущность. Doctrine такое не поддерживает как обычное обновление.
- **Сгенерированные id** в составном ключе не работают стандартно: `#[ORM\GeneratedValue]` допустим только для одного поля.
- **Сериализация и URL.** Для API составной ключ обычно превращают в суррогатный id или строку вида `order-uuid:3`, что требует маппинга.

## Как с этим живут в реальных проектах

1. **Суррогатный ключ.** Добавляют `id` (UUID или bigint) как единственный `#[ORM\Id]`, а составной набор делают `#[ORM\UniqueConstraint]`. Это самый частый выбор: проще работать с `find`, URL и связями, а уникальность гарантирует схема.
2. **Составной ключ, когда он естественный.** Таблицы связей многие-ко-многим с дополнительными атрибутами, справочники по паре ключей. Здесь ключ несёт смысл, и его оставляют, а доступ строят через репозиторий с явными методами.
3. **Идентичность через агрегат.** Для дочерних сущностей агрегата (как `OrderLine`) часто не нужен отдельный ключ вовсе: они доступны только через корень, и идентификатор внутри агрегата может быть обычным `id`, уникальным в пределах заказа.
4. **Value object для ключа.** Составной идентификатор оформляют как VO (`OrderLineId(orderId, position)`) и маппят через custom type или embeddable, чтобы остальной код работал с одним объектом.

## Итог

Doctrine поддерживает составные ключи, и они корректны в схеме. На практике чаще выбирают суррогатный `id` плюс уникальное ограничение в БД, потому что он проще в коде, API и миграциях. Составной ключ оправдан, когда сама пара значений является идентичностью, и тогда стоит заранее продумать поиск, создание и сериализацию.

## Q27 · Мини-код-ревью

**Интервьюер:** Посмотри на этот код:

```php
class OrderController
{
    public function pay(Request $req): Response
    {
        $id = $req->get('order_id');
        $pdo = DB::connect();
        $order = $pdo->query("SELECT * FROM orders WHERE id = $id")->fetch();
        if (!$order) {
            return new Response('not found', 404);
        }
        $order['status'] = 'paid';
        $pdo->exec("UPDATE orders SET status = 'paid' WHERE id = $id");
        Mailer::send($order['email'], 'Ваш заказ оплачен');
        (new Logger())->log('paid ' . $id);
        return new Response('ok');
    }
}
```

Какие проблемы ты видишь и как бы ты этот код переделал? С чего начал бы и почему?

**Кандидат:**

Начал бы с безопасности и целостности данных, потому что здесь есть то, что может навредить прямо сейчас, а уже потом архитектура и стиль.

## Проблемы, по приоритету

**1. SQL-инъекция.** `$id` берётся из запроса и подставляется в SQL без параметризации. Атакующий передаёт `order_id=1 OR 1=1` или `1; DROP TABLE orders` (зависит от драйвера) и читает или портит любые данные. Это блокер.

**2. Нет проверки прав.** Любой, кто знает или перебирает id, может пометить чужой заказ оплаченным. Нужна проверка, что текущий пользователь имеет право оплачивать этот заказ (voter).

**3. Гонка и нет атомарности.** Статус читается и меняется отдельно. Два параллельных запроса оба пройдут, а если оплата проходит через платёжный шлюз, он может быть вызван дважды. Нет транзакции: если письмо или лог упадут после UPDATE, заказ уже оплачен, а пользователь получит ошибку.

**4. Нет проверки бизнес-правил.** Заказ можно оплатить из любого статуса: уже оплаченный, отменённый, отгруженный. Правило «оплатить можно только новый заказ» отсутствует.

**5. Побочные эффекты внутри контроллера.** Отправка письма синхронно блокирует ответ, а при сбое почты пользователь видит 500 после уже выполненной оплаты. Логика живёт в контроллере, нельзя переиспользовать и протестировать.

**6. Смешаны слои.** Контроллер работает с БД напрямую, знает про SQL, `Mailer` и `Logger`. Зависимости создаются через `new`, поэтому тестировать без реальной БД и почты нельзя.

**7. Утечка и грубость ответа.** Ответ `'not found'` без разделения на «нет заказа» и «нет доступа» позволяет перебором определять существование заказов. Лог `'paid ' . $id` не структурирован и не содержит пользователя или времени.

**8. Мелочи.** `SELECT *` вытягивает всё, включая лишнее. Статус в массиве меняется, но это не влияет на БД и вводит в заблуждение. Нет типов, нет `declare(strict_types=1)`, `$id` не проверен на число.

## Как бы переделал

Сначала закрыл бы инъекцию и права, это минимальный безопасный шаг, который можно выкатить сразу. Затем вынес бы логику в use case.

```php
declare(strict_types=1);

final class PayOrderController
{
    public function __construct(private MessageBusInterface $bus) {}

    #[Route('/orders/{id}/pay', methods: ['POST'])]
    #[IsGranted('ORDER_PAY', subject: 'order')] // проверка прав через voter
    public function __invoke(Order $order): Response
    {
        $this->bus->dispatch(new PayOrder($order->getId()));
        return new Response(status: 202);
    }
}
```

`Order $order` ParamConverter загружает заказ по id безопасно, без SQL-склейки; если id нет, Symfony вернёт 404. Права проверяет voter.

```php
final class PayOrderHandler
{
    public function __construct(
        private OrderRepository $orders,
        private EventPublisher $events,
    ) {}

    public function __invoke(PayOrder $cmd): void
    {
        $order = $this->orders->get($cmd->orderId);
        $order->markPaid(); // правило статуса внутри агрегата, бросает исключение при недопустимом переходе
        $this->orders->save($order);
        $this->events->publish(...$order->pullEvents());
    }
}
```

Транзакция и `flush` оборачиваются инфраструктурой. Письмо и лог больше не в этом пути: `OrderPaid` уходит в очередь, и отдельный слушатель отправляет письмо. Сбой почты не откатывает оплату и не даёт 500 клиенту. Версия агрегата (`#[ORM\Version]`) защищает от двойной оплаты при гонке: второй запрос получит конфликт.

Предупреждение: если оплата реально списывает деньги через шлюз, вызов шлюза не должен быть внутри транзакции БД, а сохранение результата и идемпотентность (ключ идемпотентности от клиента или внутренний `paymentId`) обязательны. Это отдельная тема, и без неё переписывание не закрывает риск двойного списания.

## Итог

Начал бы с инъекции и проверки прав, потому что это уязвимости, которые опасны прямо сейчас и не требуют рефакторинга. Затем перенёс бы правило статуса в домен, операцию в use case с транзакцией и версией, а побочные эффекты отправил бы асинхронно. Логику переделывать последней, потому что безопасный минимум ничего не ломает.

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Главная проблема: сущность зависит от инфраструктуры. `EntityManagerInterface` — это деталь Doctrine, и домен не должен её знать. Из этого следуют остальные проблемы.

## Что не так

**1. Сущность сама сохраняет себя.** `flush()` внутри доменного метода раскрывает транзакционную границу наружу. Вызывающий код не контролирует, когда и что коммитится. Если сущность меняется в составе команды из нескольких шагов, часть изменений может закоммититься раньше времени.

**2. Нарушено правило зависимостей.** Домен зависит от Doctrine. Тест `new User($em, 'a@b.c')` требует мок `EntityManager`, а сам домен без фреймворка не работает. Это то, что `deptrac` должен запрещать.

**3. Инвариант не защищён.** `changeEmail` принимает любую строку: пустую, без `@`, с пробелами, в другом регистре. Email — кандидат на value object (`Email`), который проверяет формат при создании. Сейчас правило вообще отсутствует.

**4. Нет бизнес-смысла.** Смена email обычно требует подтверждения нового адреса, уведомления старого, проверки уникальности. Сейчас всё это молча пропускается. Метод называется `changeEmail`, но делает только присваивание.

**5. Уникальность не проверяется.** Два пользователя могут получить один email. Проверка в домене без запроса в БД невозможна, поэтому нужен `UNIQUE` индекс в схеме, а для понятной ошибки, возможно, проверка в прикладном слое.

**6. Изменение без событий.** Другие части системы не узнают, что email сменился.

**7. Мелочь:** геттер `email()` без `get` — допустимо по стилю, но важнее, что он не возвращает VO.

## Как бы исправил

Домен чистый, без `EntityManager`, с value object и доменным событием:

```php
declare(strict_types=1);

final readonly class Email
{
    public string $value;

    public function __construct(string $value)
    {
        $normalized = strtolower(trim($value));
        if (!filter_var($normalized, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidEmail($value);
        }
        $this->value = $normalized;
    }

    public function equals(self $other): bool
    {
        return $this->value === $other->value;
    }
}

final class User
{
    /** @var list<object> */
    private array $events = [];

    public function __construct(
        private UserId $id,
        private Email $email,
        private bool $emailConfirmed = false,
    ) {}

    public function requestEmailChange(Email $newEmail): void
    {
        if ($this->email->equals($newEmail)) {
            return; // идемпотентно, лишних событий нет
        }
        $this->events[] = new EmailChangeRequested($this->id, $this->email, $newEmail);
    }

    public function confirmEmailChange(Email $newEmail): void
    {
        // вызывается, когда пользователь подтвердил ссылку из письма
        $this->email = $newEmail;
        $this->emailConfirmed = true;
        $this->events[] = new EmailChanged($this->id, $newEmail);
    }

    /** @return list<object> */
    public function pullEvents(): array
    {
        $events = $this->events;
        $this->events = [];
        return $events;
    }
}
```

Обработчик команды в приложении:

```php
final class ChangeEmailHandler
{
    public function __construct(
        private UserRepository $users,
        private EmailUniqueness $uniqueness, // порт, реализуется через запрос к БД
        private EventPublisher $events,
    ) {}

    public function __invoke(ChangeEmail $cmd): void
    {
        $newEmail = new Email($cmd->email);
        if (!$this->uniqueness->isFree($newEmail)) {
            throw new EmailAlreadyTaken($newEmail);
        }
        $user = $this->users->get($cmd->userId);
        $user->requestEmailChange($newEmail);
        $this->users->save($user);
        $this->events->publish(...$user->pullEvents());
    }
}
```

Что здесь изменилось:
- `flush` ушёл из домена. Сохраняет репозиторий, коммит делает инфраструктура.
- `Email` сам проверяет формат и нормализует значение, `User` получает уже валидный объект.
- Смена email стала процессом: запрос, подтверждение, событие. Это ближе к реальным правилам, а не к присваиванию.
- Уникальность проверяется в приложении через порт, а `UNIQUE` индекс в БД остаётся обязательной страховкой от гонки.
- Домен не знает про Doctrine. Маппинг уехал в инфраструктуру: XML/YAML или отдельную конфигурацию. Если атрибуты ORM остаются на классе, это компромисс, который стоит явно признать в проекте.

Итог: сущность не должна ни сохранять себя, ни зависеть от `EntityManager`. Инварианты вынесены в value object, сохранение и уникальность — в приложение и инфраструктуру, а изменения домена выражаются событиями.

## Q29 · Процесс и рассуждение

**Интервьюер:** Тебе нужно решить техническую проблему на незнакомых тебе технологии или стеке. Опиши последовательность своих действий от первого взгляда на задачу до уверенного ответа о сроках решения. Когда, по-твоему, нужно просить помощи у команды, а когда разбираться самому?

## 1. Первый взгляд: понять, что именно нужно

Прежде чем трогать технологию, фиксирую в одной-двух фразах:
- что за симптом или требование, и кто от этого страдает;
- что уже известно: логи, текст ошибки, воспроизводимость, когда началось;
- что считается решением (критерий «готово»).

Если на этом шаге не получается ответить, значит, задача не готова, и её надо уточнить, а не гадать.

## 2. Освоить минимум за пределами интереса

Не читаю всю документацию. Ищу:
- официальный «Getting started» и раздел про то, что я пытаюсь сделать;
- версию стека, которая реально используется в проекте (не последнюю из головы);
- как технология обычно ломается: типичные ошибки, известные ограничения, issue трекер.

Параллельно смотрю, как устроен этот стек в самом проекте: конфиги, существующие примеры, тесты. Чужой рабочий код обычно дешевле любой статьи.

## 3. Воспроизвести в изоляции

Минимальный эксперимент вне основного кода: маленький скрипт, тест, локальный контейнер. Цель не решение, а проверка гипотезы «я понимаю, как это работает». Каждое предположение проверяю одним запуском, а не рассуждением.

Веду короткий журнал: что пробовал, что ожидал, что получил. Это экономит время и не даёт ходить по кругу.

## 4. Найти причину, а не симптом

Сужаю область бисекцией: отключаю половину системы, откатываю версию, упрощаю входные данные. Так быстрее всего доходим до места, где поведение расходится с ожиданием.

## 5. Оценить сроки

Срок оцениваю не по ощущению, а по известным этапам:
- сколько неизвестного осталось (если гипотез много, оценка размытая);
- есть ли уже работающий путь решения или только направление;
- сколько займут проверка, тесты и ревью.

Говорю диапазон и условие: «если причина в конфиге, то за полдня; если в библиотеке, то до двух дней, и тогда нужен вопрос к автору». Уверенный ответ о сроках появляется, когда известна причина, а не когда начата работа.

## Когда просить помощь, а когда разбираться самому

**Разбираюсь сам, пока:**
- есть конкретный следующий шаг, который дешёво проверить;
- вопрос можно найти в документации или в коде проекта за разумное время (ориентир 30–60 минут без прогресса для простого, около двух часов для сложного);
- проблема локальная и не блокирует других.

**Прошу помощь сразу, если:**
- затрагивается безопасность, данные или деньги, и я не уверен в последствиях;
- проблема связана с инфраструктурой или правами, которых у меня нет;
- есть знакомый в команде, который знает стек, а мои гипотезы не сходятся;
- я хожу по кругу: повторяю одни и те же попытки или трачу время на поиск того, что знает владелец модуля.

**Как просить правильно:** с описанием того, что уже проверено, воспроизводимым минимумом, ожидаемым и фактическим поведением, и конкретным вопросом. «Не работает, помогите» почти никогда не даёт ответа; «вот минимальный пример, ожидаю X, получаю Y, проверил версии A и B, подозреваю Z — верно ли?» решается за минуты.

Итог: сначала понять задачу, затем минимально освоить стек, проверять гипотезы в изоляции и оценивать сроки по оставшейся неопределённости. Помощь просить рано, если есть дешёвый следующий шаг, и поздно, если я трачу время на то, что знает другой человек.

## Q30 · Процесс и рассуждение

**Интервьюер:** Ты пообещал сделать задачу к завтрашнему дню, но по ходу работы понял, что это два дня работы. Что делаешь?

**Кандидат:**

Сразу сообщаю о сдвиге, а не жду дедлайна. Сроки в команде держатся на том, что все знают о рисках заранее: если заказчик узнаёт о проблеме в день дедлайна, решений остаётся меньше всего.

## Что делаю в первую очередь

1. **Проверяю оценку фактами.** Два дня — это моя текущая гипотеза. Уточняю, что именно займёт время: неизвестная причина, миграция, медленные тесты или ревью. Если выясняется, что основная часть сделана и осталось проверить одно, оценка может сократиться, и тогда сообщаю об этом так же явно.

2. **Сообщаю сразу, а не завтра утром.** Пишу тому, кто ждёт результат, примерно так: «По задаче обнаружил, что для полного решения нужно два рабочих дня, а не один. Причина: X. Текущий статус: Y. Сегодня и завтра сделаю Z».

3. **Предлагаю варианты, а не только новый срок.** Обычно их несколько:
   - сдать к завтрашнему дню частичный результат, который уже можно проверить (например, диагностику и воспроизведение с первым исправлением без миграции);
   - сохранить срок, но сузить задачу, вынеся побочную часть в отдельный PR;
   - сдвинуть срок на два дня, если ценность задачи это оправдывает;

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

Честно: у меня нет собственного опыта выпуска кода в живом продукте под давлением сроков, поэтому описываю подход, который считаю разумным и который соответствует распространённой практике.

## Главная идея

«Достаточно хорошо» определяется не абстрактным идеалом, а тем, что код должен делать сейчас, как его будут менять дальше и какой ценой ошибка. Качество — не одна шкала. Есть минимум, который не обсуждается, и есть уровень, который растёт вместе с задачей.

## Что обязательно, независимо от срока

- **Корректность в проверенных сценариях.** Основной путь и известные граничные случаи покрыты тестами.
- **Инварианты и безопасность.** Права доступа, валидация входа, защита от гонок там, где данные или деньги. Здесь не экономлю никогда.
- **Обратимость.** Миграции откатываемы, изменение можно выкатить и откатить без ручной уборки.
- **Наблюдаемость.** Ошибки логируются с контекстом, есть что посмотреть, если станет плохо.
- **Понятность для следующего человека.** Имена из единого языка, без «магии», которую нужно объяснять устно.

Это не «полировка», а условие, при котором вообще можно отдавать код.

## Что зависит от контекста

- **Стиль, мелкий рефакторинг, идеальная структура** — допустимо отложить, если код работает и покрыт тестами. Фиксирую долг в задаче, а не в голове.
- **Производительность** — оптимизирую, когда есть замер или признак проблемы, а не заранее.
- **Абстракции** — не вношу, пока нет второго случая использования.
- **Полнота покрытия** — важнее покрытие инвариантов, чем процент строк.

## Сигналы, что пора отдавать

- Обязательный минимум выполнен, и оставшиеся улучшения не меняют поведение.
- Дальнейшая полировка не даёт обратной связи: мы спорим о вкусе, а не о результате.
- Пользователь или бизнес ждёт, и задержка стоит больше, чем вероятная проблема в будущем.
- Код можно быстро поправить после выката, и это дешевле, чем держать его в ветке.

## Сигналы, что пора продолжать

- Нарушены инварианты, безопасность или данные, даже если «работает в основном сценарии».
- Тесты зелёные, но покрывают не то, что важно.
- Код трудно объяснить: если автор не может сказать, почему сделано именно так, ревьюер тем более.
- Изменение затрагивает общий компонент, который будут менять многие, и долг быстро размножится.
- Нужен откат, а его нет.

## Как держу баланс на практике

1. **Маленькие порции.** Небольшой PR проще довести до качества, чем огромный. Качество держится на размере изменения.
2. **Долг фиксирую явно.** Если что-то сознательно отложено, это задача с описанием, а не комментарий `TODO` без владельца.
3. **Качество измеряю автоматикой.** PHPStan, `deptrac`, тесты в CI решают большую часть споров заранее.
4. **Сроки обсуждаю заранее.** Если компромисс нужен, говорю о нём вслух: что сокращаем, что остаётся, какой риск.
5. **Выкатываю за флагом** (feature flag), когда код готов технически, но бизнес-поведение ещё не согласовано.

Итог: отдавать можно, когда выполнен обязательный минимум и оставшиеся улучшения не влияют на корректность, безопасность и обратимость. Всё остальное — задача с явным владельцем, а не причина держать код в ветке.
