Связанность классов: Ce, Ca, нестабильность I

Ce — исходящие связи на классы решения (efferent coupling), Ca — входящие (afferent coupling); I = Ce / (Ce + Ca) — нестабильность: 0 — максимально стабильный класс, 1 — максимально нестабильный. Здоровая слоистость выглядит так: I близка к 1 у console-команд (точки входа, обязаны меняться часто) и к 0 у примитивов домена (Decimal, Timestamp, enum-статусы): нестабильное должно зависеть от стабильного, не наоборот. Обоснование

ревьюер яруса 3
Решение в целом рабочее и правильно спроектировано: чёткие слои (Domain без Doctrine-логики — EventCostCalculator, Money на bcmath\Number с SCALE=24 и одним округлением HALF_UP), все 5 команд, бонус reprice реализован, приёмка по фикстурам байт-в-байт. Деньги везде строковые/decimal, float не используется — ключевое требование соблюдено. Дедупликация по (provider, provider_request_id) с unique constraint, окно оф-пика с переходом через полночь [start, end) — корректно (Provider::isInOffPeak). Дефекты: 1) единственный обязательный провал чекера — формат timestamp в stderr UNRATED выводится как 2026-07-31T23:00:00+00:00 вместо ожидаемого Z (BillingRateCommand: format('c') вместо format с 'Z'); 2) в Money::toFixedSix для неокруглённых значений >6 знаков дробная часть отбрасывается без округления — сейчас компенсируется тем, что дельта reprice складывается из уже округлённых cost, но toFixedSix хрупок; 3) N+1 на каждый flush в saveUsageEvent внутри цикла импорта и по-событийный findProvider/findModel в rate — не «дёшево»; 4) unrated-событие, для которого провайдер не найден, неотличимо от отсутствия цены (в stderr всегда no_price, а не отдельная причина); 5) знаковое качество процессов: PR_DESCRIPTION подробный (решения, допущения, шаги проверки), но статанализ явно не прогонялся (141 psalm, 32 phpstan, 43 phpcs), тестов нет, метод roundHalfUp написан вручную со сложной строковой арифметикой вместо аудита; граней (дубли с изменённым payload, граница valid_from == ts) в артефактах не проверены.
