# Учёт расходов на LLM-токены

Консольное приложение на PHP 8.4 / Symfony 8 / Doctrine + PostgreSQL 17, которое
принимает справочник исторических цен (JSON) и события потребления (JSONL),
тарифицирует события по цене, действовавшей в момент запроса, применяет
оф-пиковую скидку провайдера и формирует CSV-отчёт по пользователям и моделям.
Все деньги считаются точно (bcmath), float не используется.

## Что сделано

Команды (все — через `bin/console`):

| Команда | Назначение |
|---|---|
| `app:prices:import <file>` | Идемпотентный upsert провайдеров, моделей и строк цен. `providers`/`models`/`prices` — по своим ключам; повторная загрузка не изменяет данные. Код 0; некорректный JSON — ошибка, код 1. |
| `app:usage:import <file>` | Импорт событий JSONL. Дедупликация по `(provider, provider_request_id)` через `ON CONFLICT DO NOTHING`. Код 0, даже если все строки — дубли; некорректная строка — код 1. |
| `app:billing:rate` | Тарификация всех ещё unrated-событий. В stdout — ровно `RATED=<n> UNRATED=<m>`; по каждому unrated — строка в stderr `UNRATED <provider>/<id> <ts> no_price`. Повторные попытки для уже unrated выполняются на каждом запуске (п. 7). |
| `app:billing:report [--from --to]` | CSV в stdout: заголовок, строки по (user, `<provider>/<model>`) с суммами токенов и стоимости, `TOTAL`. Период `[from,to)`. Unrated в отчёт не попадают. |
| `app:billing:reprice <file>` | **Бонус.** Ретро-коррекция: upsert исправленных строк цен (провайдер/модель обязаны быть уже в БД, секции `providers`/`models` в файле могут отсутствовать) и пересчёт событий, тарифицированных именно этой строкой, с журналом корректировок. В stdout ровно 2 строки `REPRICED_EVENTS=<n>` / `REPRICE_DELTA_USD=<x.xxxxxx>`. |

## Архитектура

```
src/
  Domain/
    Decimal.php         # обёртка над bcmath: add/sub/mul/div/roundHalfUp/format (масштаб 20)
    TokenUsage.php      # value object: input/output/cache_read/cache_write, total, byKind
    OffPeakWindow.php   # окно [start,end) по UTC, переход через полночь, apply(cost,ts)
  Application/
    PriceFileParser.php     # разбор+валидация JSON-справочника -> нормализованные строки
    PriceImportService.php  # upsert провайдеров/моделей/ценок
    UsageImportService.php  # разбор+валидация JSONL, вставка с ON CONFLICT
    RatesCalculator.php     # чистая функция: baseCost + оф-пик + единственное округление
    RatingService.php       # выбор исторической цены, тарификация unrated
    ReportService.php       # группировка + суммирование, строка TOTAL
    RepriceService.php      # upsert исправлений, пересчёт, журнал reprice_corrections
  Command/                  # 5 консольных команд (тонкий слой, перевод ошибок в код выхода)
  Entity/                   # ORM-сущности: Provider, Model, PriceLine, UsageEvent
migrations/
  Version20260915120000.php # схема: все деньги NUMERIC, rates JSON со строками, unique-ключи
tests/
  DecimalTest.php           # HALF_UP, арифметика bcmath
  RatesCalculatorTest.php   # обе схемы, оф-пик, нулевые токены, округление событий
```

Тарификация вынесена в чистую функцию `RatesCalculator` (без БД) — её тестируют
единичными тестами. Команды — тонкий адаптер Symfony Console. Доменные типы
(`Decimal`, `TokenUsage`, `OffPeakWindow`) не зависят от инфраструктуры.

## Ключевые решения

1. **Выбор цены** — строка цен модели с наибольшим `valid_from <= ts`
   (включительно). Реализовано запросом на максимум по `valid_from`.

2. **Схемы расчёта** (п. 2)
   - `per_1m_tokens`: `Σ tokens_вид × rate_вид / 1e6` (по 4 видам);
   - `per_1m_tokens_unified`: `(Σ всех токенов) × rate_any / 1e6`.

3. **Оф-пик** — накладывается *на стоимость события целиком* (после baseCost,
   до единственного округления), если `ts` попадает в `[start,end)`. Окно на
   уровне провайдера, может переходить через полночь (`16:30–00:30`); `end`
   исключительно. `null` — без скидки.

4. **Точность** (п. 4) — промежуточные вычисления в `Decimal` (bcmath,
   масштаб 20, т.е. без округления). Единожды окр. итог события до 6 знаков
   HALF_UP. Суммы отчёта = точное сложение уже округлённых event-cost.
   float не используется нигде для денег (в схемах — NUMERIC, в JSON — строки).

5. **Идемпотентность** (п. 5) — уникальность на `(provider_code,
   provider_request_id)` + `ON CONFLICT DO NOTHING`: повтор доставляемого
   события целиком игнорируется (никаких UPDATE/доначислений); одинаковый
   `provider_request_id` у разных провайдеров — разные строки.

6. **Период отчёта** (п. 6) — `ts >= from AND ts < to`.

7. **Unrated** (п. 7) — не ошибка: событие остаётся со статусом `unrated`,
   в отчёт не попадает; каждый запуск `app:billing:rate` повторяет попытку
   для всех ещё unrated (цены могли подтянуться позже).

8. **Бонус — ретро-коррекция.** Исправленные строки upsert'ятся по
   `(provider, model, valid_from)`. Пересчитываются только уже rating'нутые
   события, чья `price_line_id` указывает на заменённую строку; события по
   другим строкам не трогаются. Каждая правка фиксируется в
   `reprice_corrections` (event, old_cost, new_cost, created_at) — журнал
   для аудита/компонования. Отчёт после reprice показывает пересчитанные
   суммы без задвоений. Новые строки для ранее unrated-событий подхватываются
   `app:billing:rate`.

## Допущения (неоговорённые ТЗ детали)

- **`ts` в БД хранится в UTC с точностью до секунды.** Микросекунды событий
  в fixture отсутствуют и на выбор цены/оф-пик не влияют.
- **`price_line_id` у rated-событий** — ссылка на строку цен, которой оно
  рассчитано. Используется для точной ретро-коррекции и аудита.
- **Journal корректировок** (`reprice_corrections`) пишется в той же
  транзакции, что и пересчёт. Альтернатива (компенсирующие записи) отклонена
  как более сложная и менее прозрачная для «показать, что было».
- **Время оф-пика** считается по моменту `ts` (UTC), а не по `now()` —
  тарификация ретро-справедлива.
- **`report`** группирует по `(user, provider/model)`; `TOTAL` — сумма по
  всем группам отчёта (не по БД целиком).
- **Валидация** JSON/JSONL строга (типы, неотрицательность, ISO-8601);
  ошибки — в stderr, код 1.
- **`currency`** всегда `USD` — поле сохраняется, но не участвует в расчётах.

## Управление схемой БД

Схема — Doctrine migration (`migrations/Version20260915120000.php`).
Разворачивается на чистой базе типовым вызовом:

```
make db-up     # поднять PostgreSQL 17
make migrate   # применить миграции
```

(Способ управления — дефолтный `make migrate`, как в ТЗ — отдельного
описания не требуется.)

## Как проверяли (команды/шаги)

```
make db-up && make migrate

# 3) импорт + rate
bin/console app:prices:import fixtures/prices.json
bin/console app:usage:import fixtures/usage.jsonl
bin/console app:billing:rate                # -> RATED=3 UNRATED=0

# 4) отчёт (байт-в-байт сверка с примером ТЗ)
bin/console app:billing:report --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z
# -> совпадает с эталоном ТЗ (diff пуст)

# 5) повторный импорт + rate + report
# -> результат не меняется (дубли проигнорированы, idempotency)

# Бонус: ретро-коррекция
bin/console app:billing:reprice <файл_с_исправленными_ценой>
# -> REPRICED_EVENTS=<n> ; REPRICE_DELTA_USD=<x.xxxxxx>
# -> повторный report показывает пересчитанные суммы без задвоений

# Ед. тесты
vendor/bin/phpunit   # 23 ассерта, всё зелёное
```

- Импорт некорректного JSON/JSONL → код 1 (проверено).
- Повторный импорт тех же событий → `duplicates_ignored=N`, данные не меняются.
- `app:billing:rate` повторно для unrated → попытка повторяется.

## Отступления от каркаса

- **Добавлены новые файлы** (домен, application, команды, миграция, тесты) —
  каркас (`TASK.md`, `README.md`, `docker-compose.yml`, `Makefile`,
  `composer.json`, `phpunit.xml.dist`, `fixtures/`) **не изменялся**.
- **Зависимости** — не добавлены (используются уже установленные
  symfony/console, doctrine/orm, doctrine/dbal, bcmath — расширение PHP).
- **Схема БД** — создана миграцией (в каркасе её не было).
- **`user` в БД** — колонка названа `user_id` (избирательное слово SQL);
  наружу в отчёте отдаётся как `user`.
- Альтернативные механизмы отклонены: вместо компенсирующих записей — журнал
  корректировок; вместо float — бcmath; вместо «текущая цена» — исторический
  выбор строки цен.
