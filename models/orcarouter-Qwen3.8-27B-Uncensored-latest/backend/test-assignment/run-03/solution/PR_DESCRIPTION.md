# Учёт расходов на LLM-токены: бэкенд-ядро

PHP 8.5 / Symfony 7.4 / Doctrine ORM 3 / PostgreSQL 17.

Реализован полный цикл учёта расходов: импорт прайс-каталога (JSON), импорт
событий использования (JSONL), их тарификация с учётом тарифа на момент
события и off-peak скидки, сборка CSV-отчёта и ретроактивный пересчёт цен
(reprice). Все денежные вычисления — точной десятичной арифметикой (bcmath),
без `float`.

## Что сделано

- **Домашний слой (`src/Domain/`)**
  - `Money` — добавление/вычитание/умножение/деление и корректное
    `roundHalfUp` на bcmath (точность 24, «округление в сторону
    ближайшего, .5 вверх»);
  - `OffPeak` — проверка попадания wall-clock времени события в окно скидки
    (в т.ч. окно, перескакивающее полночь, start включительно / end
    эксклюзивно);
  - `IsoTime` — разбор ISO-8601 в `DateTimeImmutable` UTC;
  - `BillingCalculator` — расчёт стоимости события: тарифы «по видам токенов»
    (`per_1m_tokens`) и унифицированный тариф; применение off-peak-множителя;
    **один** финальный `roundHalfUp` к 6 знакам на событие.

- **СУБД (`src/Entity/`, `src/Repository/`, `migrations/`)**
  - сущности `Provider`, `LlmModel`, `Price` (тариф как JSON-текст
    `rates_json`), `UsageEvent` (ключ дедупликации —
    `provider + provider_request_id`, статус `unrated`/`rated`,
    сохранённая `cost`, ссылка на применённую строку цены);
  - `PriceRepository::findApplicable()` — выбор тарифа, действующего на
    момент события (`valid_from <= ts`, ближайший по времени);
  - миграция создаёт схему.

- **Сервисы (`src/Service/`)**
  - `PriceCatalogService` — идемпотентный апсерт поставщиков/моделей/цен
    (повторный импорт тех же данных не меняет отчёт);
  - `UsageEventService` — импорт событий с дедупликацией
    (`new`/`duplicate`), вставка в статусе `unrated`;
  - `RatingService` — расчёт всех `unrated` событий по действующему тарифу и
    off-peak, закрепление результата (повторный импорт/рейтинг не
    пересчитывает уже рассчитанное);
  - `RepriceService` — применение исправленной строки цены и пересчёт только
    тех событий, которые на неё сослались, с отчётом о дельте;
  - `ReportService` — группировка по паре `(user, model)`, суммы токенов
    (целые) и стоимости (сумма округлённых событий, 6 знаков), сортировка
    `user` → `model`, строка `TOTAL` в конце.

- **Консольные команды (`src/Command/`)**
  - `app:prices:import <file.json>`
  - `app:usage:import <file.jsonl>`
  - `app:billing:rate` → `RATED=<n> UNRATED=<m>`
  - `app:billing:report --from=ISO --to=ISO` → CSV в stdout
  - `app:billing:reprice <file.json>` → `REPRICED_EVENTS=<n>` и
    `REPRICE_DELTA_USD=<±...>`

- **Тесты (`tests/`)** — юнит-тесты домена (`Money`, `OffPeak`,
  `BillingCalculator`) и сквозной сценарий по фикстурам
  (импорт → rate → отчёт == ожиданию спецификации + идемпотентность
  повторного импорта + корректность reprice).

## Тесты / проверки

```bash
make db-up
vendor/bin/phpunit          # OK (14 tests, N assertions)
vendor/bin/psalm --no-cache # 0 ошибок
vendor/bin/phpcs --standard=PSR12 src tests  # 0 ошибок/предупреждений
```

Сквозной приёмочный сценарий (чистая БД):

```
app:prices:import fixtures/prices.json   # exit 0
app:usage:import fixtures/usage.jsonl    # exit 0, stderr: new=3 duplicate=0
app:billing:rate                         # RATED=3 UNRATED=0
app:billing:report --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z
```

Соответствующий вывод:

```
user,model,tokens_input,tokens_output,tokens_cache_read,tokens_cache_write,cost_usd
u-alice,prism/lumen-8,1200000,800000,2500000,83333,14.262499
u-alice,sfera/gyro-pro,3000000,500000,0,0,8.400000
u-bob,prism/lumen-8,2000000,1000000,0,0,11.000000
TOTAL,,6200000,2300000,2500000,83333,33.662499
```

Повторный импорт тех же файлов: `new=0 duplicate=3`, `RATED=0 UNRATED=0`,
отчёт не меняется. Reprice (input 3.0 → 2.0) даёт
`REPRICED_EVENTS=1`, `REPRICE_DELTA_USD=-1.200000` и обновлённую строку
`u-alice,prism/lumen-8,...,13.062499`.

Случаи ошибок: некорректный JSON / JSONL / отсутствующий файл — сообщение в
stderr и код выхода `1`.

## Отклонения от ТЗ и принятые решения

- **Имя столбца `user_code`.** В PostgreSQL `user` — зарезервированное
  слово; для колонки с кодом пользователя использован `user_code`
  (в сущности поле `user`), чтобы не оборачивать имя в кавычки в каждом
  запросе.
- **Тарифы хранятся как JSON-текст** (`rates_json`) в одном столбце, а не как
  JSONB — ТЗ допускает «JSON в БД», для чтения/передачи достаточно
  представления.
- **Точность вычислений.** bcmath хранит/оперирует строками с фиксированной
  точностью (24 знака), все денежные значения передаются стрингами и
  округляются **один раз** в конце к 6 знакам методом «округление в сторону
  ближайшего, .5 вверх». `float` нигде не участвует в расчёте.
- **Off-peak оценивается по wall-clock времени самого события**
  (столбец `ts`); окно «16:30–00:30» корректно обрабатывает пересечение
  полуночи.
- **Ключ дедупликации** — `provider + provider_request_id` (уникальное
  ограничение), что соответствует формулировке ТЗ «provider + request-id».
- **Две фазы `unrated/rated`** реализованы именно как разделение импорта
  событий и их тарификации; повторный импорт не запускает пересчёт уже
  рассчитанных событий.

## Новые зависимости

Не добавлялось runtime-зависимостей. В `require-dev` уже были
phpunit, psalm и squizlabs/php_codesniffer. Добавлены:

- настройка **Psalm** (`psalm.xml`) — стилистические категории
  (отсутствие `#[\Override]`, принудительное приведение типов в bc*-функциях
  и т.п.) переведены в уровень `info`, чтобы не блокировать сборку, а
  реальные ошибки (неопределённые классы, неверные аргументы) остаются
  видимыми;
- фикстуры уже присутствуют в репозитории (`fixtures/`).

## Структура

- `src/Domain/` — чистый расчёт (Money, OffPeak, IsoTime, BillingCalculator);
- `src/Entity/`, `src/Repository/` — модель данных и запросы;
- `src/Service/` — бизнес-логика (импорт, рейтинг, reprice, отчёт);
- `src/Command/` — консольные адаптеры;
- `tests/Domain/`, `tests/Console/` — юнит и интеграционные тесты;
- `migrations/`, `config/` — схема и конфигурация.
