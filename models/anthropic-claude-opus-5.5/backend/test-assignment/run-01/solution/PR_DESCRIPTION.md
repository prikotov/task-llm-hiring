# Учёт расходов на LLM-токены

## Что сделано

Команды `bin/console`:
- `app:prices:import <file>` — upsert провайдеров (по `code`), моделей (по `(provider, code)`), строк цен (по `(model, valid_from)`).
- `app:usage:import <file>` — приём JSONL с дедупликацией.
- `app:billing:rate` — тарификация нерассчитанных событий, `RATED=n UNRATED=m` в stdout, `UNRATED ...` в stderr.
- `app:billing:report [--from] [--to]` — CSV в stdout.
- `app:billing:reprice <file>` (бонус).

## Структура (`src/`)

- `Shared/` — `Decimal` (обёртка над bcmath, float не используется), `UtcTime`, `InvalidInput`.
- `Pricing/Domain` — `Provider`, `LlmModel`, `PriceRow` (сущности), объекты-значения `Rates`, `PricingUnit`, `OffPeakWindow`, `TokenUsage`. Расчёт стоимости события — `PriceRow::costOf()`: точная стоимость по схеме → множитель оф-пика → единственное округление HALF_UP до 6 знаков.
- `Pricing/Application` — `PriceList` (парсинг/валидация JSON), `PriceImporter`.
- `Usage/` — `UsageEvent` (сущность), разбор строки и импорт.
- `Billing/` — `RatingService`, `CostReport`, `RepricingService`, `CostAdjustment` (журнал корректировок).
- `Ui/Console` — тонкие команды.

## Ключевые решения и допущения

- **Деньги**: bcmath, масштаб промежуточных вычислений 24; в БД `NUMERIC(30,6)`; ставки хранятся строками в JSON. Округление `bcround(..., HalfAwayFromZero)` (стоимости неотрицательны, т.е. это HALF_UP).
- **Отчёт**: суммы считаются в PostgreSQL по `NUMERIC` (точно) по уже округлённым стоимостям событий; TOTAL — сумма строк через bcmath. Сортировка — в PHP через `strcmp` (байтовая лексикографика, не зависит от collation БД).
- **Дедупликация** — на уровне БД (уникальный индекс + `ON CONFLICT DO NOTHING`): работает и для дублей внутри одного файла, и при конкурентных загрузках. Дубль никак не изменяет существующее событие.
- **Событие хранит коды провайдера/модели**, а не FK: событие может прийти до появления модели в справочнике — тогда оно unrated и тарифицируется при следующем `rate`.
- **Атомарность импорта**: файл сначала полностью валидируется, затем пишется в одной транзакции; некорректная строка → код 1 без частичной загрузки.
- **Изменение сумм уже применённой строки цены через `app:prices:import` запрещено** (ошибка, код 1) — иначе рассчитанные события молча разошлись бы со справочником; для этого есть `reprice`. Изменение неиспользованной строки — обычный upsert. Повторная загрузка тех же сумм ничего не меняет.
- **Оф-пик**: окно `[start, end)` по времени суток UTC с точностью до секунды; `start == end` трактуется как пустое окно. Параметры окна берутся из текущих данных провайдера (истории окон нет — в задаче не требуется).
- `currency` принимается только `USD`.
- Время хранится в `TIMESTAMPTZ(0)` — дробные секунды в `ts` отбрасываются (во входных данных их нет).
- `--from/--to` в отчёте: некорректная дата → код 2 (`INVALID`), сообщение в stderr.
- CSV-поля с `,`/`"`/переводом строки экранируются по RFC 4180 (на случай необычных user id).

### Reprice (бонус)

Строки из файла upsert-ятся по уже существующим в БД провайдеру/модели (секции `providers`/`models` игнорируются). Для каждой созданной/изменённой строки берутся рассчитанные события этой модели с `ts >= valid_from`; пересчитываются те, у которых старая или новая эффективная строка — изменённая (т.е. и исправление сумм, и вставка новой строки, «вытесняющей» прежнюю). Стоимость события перезаписывается, а в `cost_adjustment` пишется старая/новая стоимость и строка цены — история изменений сохраняется, отчёт показывает новые суммы без задвоений. Повторный reprice тем же файлом даёт `REPRICED_EVENTS=0`.

## Как проверял

```bash
make db-up
bin/console doctrine:database:drop --force && make migrate
bin/console app:prices:import fixtures/prices.json
bin/console app:usage:import fixtures/usage.jsonl
bin/console app:billing:rate          # RATED=3 UNRATED=0
bin/console app:billing:report --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z  # байт-в-байт с TASK.md (cmp)
# повтор импорта + rate + report — результат идентичен, RATED=0 UNRATED=0
make test                             # юнит-тесты: расчёт, HALF_UP, окно через полночь
```
Дополнительно вручную: unrated (неизвестная модель, ts раньше первой цены) и повтор rate; одинаковый `provider_request_id` у разных провайдеров; некорректный JSON/JSONL → код 1; reprice строки с 2026-09-15T12:00 (`input` 1.5→2.0) → `REPRICED_EVENTS=1`, `REPRICE_DELTA_USD=1.000000`, отчёт u-bob = 12.000000.
