# Учёт расходов на LLM-токены

## Что сделано

Консольное приложение на Symfony/Doctrine/PostgreSQL по `TASK.md`:

| Команда | Назначение |
|---|---|
| `app:prices:import <file>` | upsert провайдеров, моделей и строк цен |
| `app:usage:import <file>` | приём JSONL-событий с дедупликацией |
| `app:billing:rate` | тарификация нерассчитанных событий |
| `app:billing:report [--from] [--to]` | CSV-отчёт в stdout |
| `app:billing:reprice <file>` | ретро-коррекция цен (бонус) |

## Архитектура и слои

```
src/
  Domain/            чистая логика, без Doctrine и I/O
    Money/           Decimal — деньги поверх bcmath
    Pricing/         Provider, Model, PriceRow, PricingUnit, OffPeakWindow, CostAdjustment
    Usage/           UsageEvent, TokenUsage
    Billing/         CostCalculator — единственное место расчёта стоимости
  Application/       сценарии: ImportPriceList, ImportUsageEvents,
                     RateUsageEvents, BuildReport, RepriceEvents
  Infrastructure/
    Doctrine/        сущности, репозитории, EntityManager
    Json/            чтение и валидация prices.json / usage.jsonl
  UI/Console/Command/  команды Symfony
```

Домен ничего не знает о БД: Doctrine-сущности конвертируются в доменные
объекты (`toDomain()` / `fromDomain()`) на границе persistence-слоя.
Контроллеры/HTTP отсутствуют — только консоль.

## Ключевые решения

**Деньги.** `App\Domain\Money\Decimal` — неизменяемая обёртка над bcmath
с рабочим масштабом 30. Float не используется нигде: ставки из JSON
берутся как строки, `cost_usd` в БД — `NUMERIC(24,6)`, агрегаты
отчёта складываются в `Decimal` и форматируются один раз.
Округление ровно одно — `roundHalfUp(6)` итоговой стоимости события.
Правило HALF_UP реализовано прибавлением половины младшего разряда
с последующим усечением; знак обрабатывается отдельно (2.5 → 3, −2.5 → −3).

**Выбор цены.** Для события берётся строка своей модели с наибольшим
`valid_from <= ts` (`valid_from` включительно). Нет строки — событие
остаётся `unrated`, не считается ошибкой и повторяется при следующем
запуске `app:billing:rate`.

**Оф-пик.** Окно хранится как минуты от полуночи UTC; поддерживается
переход через полночь (`[start, 24:00) ∪ [00:00, end)`), начало
включительно, конец исключительно, пустое окно (`start == end`)
не срабатывает. Множитель применяется к стоимости всего события.

**Идемпотентность.** Уникальный индекс
`(provider_code, provider_request_id)`; при приёме ключи сначала
проверяются пачкой, дубли (в том числе внутри одного файла)
пропускаются, повторная доставка не изменяет данных. Строки цен
upsert-ятся по `(provider, model, valid_from)`, повторная загрузка
тех же сумм ничего не меняет.

**Время.** Все моменты — UTC. В БД `TIMESTAMP(0) WITHOUT TIME ZONE`
(всегда UTC), на входе строгий разбор `YYYY-MM-DDTHH:MM:SS[.ffffff]Z`
с проверкой на «залипание» даты (30 февраля отклоняется).

**Ретро-коррекция.** Строка цены обновляется на месте, затем
пересчитываются уже рассчитанные события затронутых моделей с
`ts >= min(исправленных valid_from)`. Каждая переоценка пишется в
журнал `cost_adjustments` (старая стоимость, новая, причина), а в
событии остаётся одна актуальная `cost_usd`. Поэтому отчёт читает
только актуальные значения и не задваивает суммы; `REPRICED_EVENTS`
считает события, чья стоимость реально изменилась, — повторный запуск
того же файла даёт `0` и дельту `0.000000`.

**Отчёт.** Группировка по (user, provider/model) выполняется в SQL,
сортировка — в PHP через `strcmp` (лексикографически по байтам,
не зависит от коллации БД). CSV пишется в stdout с `\n`, служебные
сообщения — в stderr. Unrated-события в отчёт не попадают.

## Схема БД

Одна миграция `migrations/Version20260101000000.php` (чистый SQL,
разворачивается на пустой базе через `make migrate`). Таблицы:
`providers`, `models`, `price_rows`, `usage_events`, `cost_adjustments`.
CHECK-ограничения на неотрицательность токенов и стоимости, на
согласованность полей оф-пика и на допустимые значения `unit`.

## Отступления от каркаса

- **`src/` и `migrations/` заполнены** — это и есть реализация задания.
- **Файлы каркаса не менялись**: `TASK.md`, `AGENTS.md`, `README.md`,
  `fixtures/`, `composer.json`/`composer.lock`, `docker-compose.yml`,
  `Makefile`, `phpunit.xml.dist` остались как были. Новых зависимостей
  нет — bcmath и всё нужное уже объявлено в `composer.json`.
- **`config/` не менялся**: маппинг Doctrine уже нацелен на `src/`
  (`auto_mapping` + атрибуты), команды подхватываются `autoconfigure`
  через `#[AsCommand]`, репозитории — обычные autowired-сервисы.
- **Сессионная таймзона**: приложение полагается на UTC-контракт
  входных данных и не задаёт `date_default_timezone`, так как
  явных преобразований зон в коде нет (все моменты приводятся к UTC
  при разборе и при записи в БД).

## Допущения

- `currency` поддерживается как поле, но расчёты всегда в USD
  (конвертации нет — по условию везде `USD`).
- Время хранится с точностью до секунды: события и строки цен в
  контракте задаются с точностью до секунды, дробные секунды на входе
  допускаются и усекаются.
- Модель события ищется в справочнике по `(provider, model)`; если
  провайдера/модели нет в базе — событие `unrated` с причиной `no_price`.
- `app:prices:import` требует, чтобы используемые в `prices` и `models`
  провайдеры были объявлены в том же файле (иначе ошибка, код 1):
  частично применять некорректный справочник нельзя.
- Файл принимается целиком или не принимается вовсе: ошибка любой
  строки JSONL отменяет весь файл (код 1).
- `REPRICED_EVENTS` считает события с изменившейся стоимостью;
  события, пересчитанные в ту же сумму, не учитываются (иначе повторная
  загрузка того же файла давала бы ненулевой счётчик).
- `cost_adjustments.event_id` — ссылка на событие без FK: события
  не удаляются, а внешний ключ только усложнил бы миграции.
- Тарификация идёт батчами по 500 событий с пагинацией по `id`
  (unrated-события остаются с `cost_usd IS NULL`, поэтому без курсора
  они возвращались бы в каждом батче).

## Тесты и проверка

31 unit-тест (`make test`): точность и округление Decimal, окно оф-пика
(включая переход через полночь и границы), расчёт по обеим схемам,
переключение цены на `valid_from`, разбор JSONL и отказ на некорректном
времени. Тесты не требуют БД.

Ручная проверка приёмки:

```bash
make db-up
make migrate

bin/console app:prices:import fixtures/prices.json
bin/console app:usage:import fixtures/usage.jsonl
bin/console app:billing:rate
# RATED=3 UNRATED=0

bin/console app:billing:report --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z
# вывод байт-в-байт совпадает с примером из TASK.md

# повторный импорт тех же файлов + rate + report — вывод не меняется
```

Дополнительно проверялись: off-peak на границах 16:30/00:30 и в
00:29, unified-схема, нулевые токены, unrated для отсутствующего
провайдера и для события раньше первой цены, ошибки импорта
(некорректный JSON/JSONL — код 1), двойные доставки и дубли внутри
файла, reprice с пустыми секциями providers/models и его идемпотентность.

Схема БД проверена `doctrine:schema:update --dump-sql` — расхождений
с маппингом нет.
