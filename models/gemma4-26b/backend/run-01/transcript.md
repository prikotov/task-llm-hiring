## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

Я считаю, что главная ценность новых версий PHP — это **усиление системы типов** и **сокращение бойлерплейта** (шаблонного кода). Это позволяет переносить часть ответственности за проверку корректности данных с рантайма (когда ошибка уже случилась у пользователя) на стадию написания кода и статического анализа.

Вот 5 возможностей, которые я считаю наиболее критичными для чистого и надёжного кода:

### 1. Constructor Property Promotion (PHP 8.0)
Это радикально сокращает количество кода в DTO и сервисах. Раньше нам приходилось объявлять свойство, принимать его в конструкторе и присваивать вручную. Теперь это делается одной строкой.

```php
// До PHP 8.0
class UserRegistrationService {
    private UserRepository $repository;
    private LoggerInterface $logger;

    public function __construct(UserRepository $repository, LoggerInterface $logger) {
        $this->repository = $repository;
        $this->logger = $logger;
    }
}

// PHP 8.0+
class UserRegistrationService {
    public function __construct(
        private UserRepository $repository,
        private LoggerInterface $logger,
    ) {}
}
```

### 2. Union Types и Intersection Types (PHP 8.0 / 8.1)
Это позволяет делать сигнатуры методов честными. Мы не просто говорим «здесь какой-то объект», мы четко описываем допустимые варианты, что делает контракт метода прозрачным.

```php
// Union Types: переменная может быть либо Int, либо Float
public function calculateArea(int|float $radius): float {
    return pi() * ($radius ** 2);
}

// Intersection Types (PHP 8.1): объект должен реализовывать ОБА интерфейса
public function process(Iterator & Countable $collection): void {
    // Мы гарантированно можем и итерироваться, и вызывать count()
}
```

### 3. Readonly Properties (PHP 8.1)
Это фундаментальный инструмент для реализации **immutability** (неизменяемости). В DDD это критически важно для Value Objects. Если объект создан — его состояние не должно меняться.

```php
readonly class Money {
    public function __construct(
        public int $amount,
        public string $currency,
    ) {}
}

$price = new Money(100, 'USD');
// $price->amount = 200; // Fatal Error: Cannot modify readonly property
```

### 4. Match Expression (PHP 8.0)
В отличие от `switch`, `match` является выражением (возвращает значение) и использует строгое сравнение (`===`). Это исключает классические ошибки, когда забыт `break` или когда типы данных не совпадают.

```php
// Чистый и безопасный код
$statusColor = match ($userStatus) {
    Status::Active   => 'green',
    Status::Pending  => 'yellow',
    Status::Inactive => 'red',
    default          => 'grey', // Обязателен, если не покрыты все Enum
};
```

### 5. Nullsafe Operator (PHP 8.0)
Этот оператор позволяет избежать "ада из if-проверок" при работе с цепочками объектов, которые могут быть `null`. Это делает код чище, не жертвуя безопасностью.

```php
// Без nullsafe:
$country = null;
if ($user !== null) {
    if ($user->getAddress() !== null) {
        $country = $user->getAddress()->getCountry();
    }
}

// С nullsafe:
$country = $user?->getAddress()?->getCountry();
```

**Итог:** Использование этих инструментов делает код более "самодокументированным". Когда я вижу `readonly` или `int|string`, мне не нужно лезть в документацию или дебажить код, чтобы понять, что ожидается на вход и что может случиться на выходе.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

Это отличный вопрос, который затрагивает фундаментальную разницу между «гибким» скриптовым языком и современным языком с системой типов.

### 1. Как устроена система типов в PHP
PHP — это язык с **динамической типизацией**, но с поддержкой **строгой типизации на уровне сигнатур**. Это значит, что тип переменной может меняться в процессе выполнения, но типы аргументов функций и возвращаемых значений могут быть жестко заданы.

### 2. Роль `declare(strict_types=1);`
По умолчанию PHP работает в **coercive mode** (режим приведения типов). Если вы передадите строку `"5"` в функцию, ожидающую `int`, PHP молча превратит её в `5`.

`strict_types=1` переключает интерпретатор в режим, где **типы должны строго соответствовать объявленным**. Если тип не совпадает (и не является подтипом/интерфейсом), PHP выбросит `TypeError`.

**Важно:** `strict_types` действует на **файл, в котором написан вызов функции**, а не на файл, где функция объявлена. Это часто путает разработчиков.

---

### 3. Типичные ловушки и примеры

#### Ловушка №1: Неявное приведение (Coercive mode)
В обычном режиме PHP пытается быть "слишком умным".

```php
declare(strict_types=0); // По умолчанию

function add(int $a, int $b): int {
    return $a + $b;
}

echo add(5, "10"); // Результат: 15. PHP молча привел строку к числу.
echo add(5, null); // Результат: 5. PHP привел null к 0 (в зависимости от версии/контекста).
```
*Почему это плохо:* Вы можете получить некорректные данные в расчетах (например, `"10 apples"` превратится в `10`), и ошибка проявится гораздо позже в бизнес-логике.

#### Ловушка №2: Проблема `strict_types` при вызовах из разных файлов
Это самая частая причина "странного" поведения.

```php
// File A.php
function process(int $val) { return $val; }

// File B.php
declare(strict_types=1);
require 'A.php';

process("5"); // TypeError! Потому что strict_types включен в B.php
```

#### Ловушка №3: Потеря точности при приведении (Float vs Int)
```php
function setAge(int $age) {}

setAge(25.9); // В coercive mode превратится в 25. В strict mode — TypeError.
```

---

### 4. Где типизация спасает

Типизация — это ваш первый эшелон обороны. Она работает как контракт.

**Пример: Защита доменной логики**
Представьте, что у нас есть метод удаления пользователя.

```php
class UserService {
    public function deleteUser(int $userId): void {
        // Если сюда попадет null или строка, система упадет сразу, 
        // не доходя до выполнения SQL-запроса.
    }
}

// Без типов:
// $userId может быть "admin", и запрос может либо упасть в БД, 
// либо (что хуже) сработать непредсказуемо.

// С типами:
$service->deleteUser("not_an_id"); // TypeError: Argument 1 must be of type int, string given.
```
**Спасение:** Ошибка возникает мгновенно, в месте вызова, с понятным traceback. Мы не пытаемся обрабатывать "мусор".

---

### 5. Где типизация удивляет (Нюансы)

#### Нюанс №1: Массивы (Array vs Generic Collections)
PHP не поддерживает дженерики на уровне ядра. Вы можете типизировать аргумент как `array`, но вы не можете сказать «массив только из объектов `User`».

```php
/** @param User[] $users */
function processUsers(array $users) { 
    // Статический анализатор (PHPStan) скажет, что все ок.
    // Но в рантайме я могу передать [1, "hello", null], и PHP это пропустит.
}
```
*Удивление:* Типизация массива в PHP — это лишь "обещание" для разработчика, а не гарантия для процессора.

#### Нюанс №2: Сравнение `0`, `false` и `null`
До появления строгих типов и `match`, сравнение часто приводило к сюрпризам из-за слабого сравнения (`==`).

```php
$val = 0;
if ($val == false) { /* Сработает */ }
if ($val === false) { /* Не сработает */ }

// С использованием match (PHP 8) и strict types:
$result = match ($val) {
    0 => 'zero',
    false => 'boolean false',
}; // Выберет 'zero', так как match использует строгое сравнение.
```

### Резюме для интервью:
Я всегда пишу `declare(strict_types=1);` во всех своих файлах. Это делает поведение системы предсказуемым. Я дополняю это использованием **статических анализаторов (PHPStan или Psalm)**, чтобы закрыть пробелы, которые PHP не может закрыть сам (например, содержимое массивов), превращая PHP из "гибкого скриптового языка" в инструмент с мощной статической проверкой типов.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

Проектирование обработки исключений — это не про то, как «поймать ошибку», а про то, как **передать информацию о сбое на нужный уровень абстракции**. Мой подход базируется на принципе: *исключение должно быть информативным, типизированным и находиться в правильном слое архитектуры*.

### 1. Иерархия собственных исключений
Я никогда не использую базовый `\Exception` для бизнес-логики. Я строю иерархию, которая отражает архитектуру приложения.

Обычно я создаю корневой интерфейс или абстрактный класс для всего приложения, а далее разделяю их по слоям:
* `App\Exception\DomainException` (ошибки бизнес-логики: `InsufficientFundsException`, `UserAlreadyExistsException`).
* `App\Exception\InfrastructureException` (ошибки внешних систем: `RepositoryException`, `ExternalApiTimeoutException`).
* `App\Exception\ApplicationException` (ошибки координации: `CommandValidationException`).

**Зачем это нужно?** Это позволяет на верхнем уровне (например, в Kernel или Middleware) решать, как реагировать: `DomainException` превращаем в `400 Bad Request` с понятным сообщением, а `InfrastructureException` — в `500 Internal Server Error` и логируем её для дебага.

### 2. Оборачивание (Exception Wrapping)
Это один из важнейших принципов для сохранения чистоты архитектуры. Мы не должны пробрасывать низкоуровневые ошибки (например, `PDOException`) через слои доменной логики.

**Плохо:** Доменная логика узнает, что у нас PostgreSQL, потому что ей прилетел `PDOException`.
**Хорошо:** Мы перехватываем инфраструктурную ошибку и оборачиваем её в свою, сохраняя оригинальный контекст.

```php
try {
    $this->db->query("...");
} catch (PDOException $e) {
    // Мы оборачиваем исключение, сохраняя $e как "previous"
    throw new RepositoryException("Failed to fetch user", 0, $e);
}
```
*Почему это важно:* Слой `Service` теперь зависит от `RepositoryException`, а не от деталей реализации БД. Мы сохраняем цепочку вызовов (`$e->getPrevious()`), чтобы при дебаге видеть корень проблемы.

### 3. Контракт метода
Контракт метода — это не только то, что он возвращает, но и то, **что он может выбросить**.

Если метод может выбросить исключение, которое является частью логики приложения (например, `UserNotFoundException`), это **часть контракта**. Это должно быть задокументировано (через PHPDoc `@throws`), чтобы вызывающий код знал: «Я должен либо обработать это, либо пробросить выше».

Однако, если метод выбрасывает `RuntimeException` из-за того, что пропал интернет — это не контракт, это непредвиденное состояние среды.

### 4. Антипаттерны

#### А. "Catch-all" (Поглощение исключений)
```php
try {
    $this->doSomething();
} catch (\Exception $e) {
    // Пусто или просто log
}
```
Это самый опасный антипаттерн. Он скрывает ошибки, делает отладку невозможной и оставляет приложение в непредсказуемом состоянии (например, транзакция не откатилась, а код пошел дальше).

#### Б. Использование исключений для управления потоком (Flow Control)
Использование `try-catch` вместо `if` в обычных условиях (например, проверка существования файла или валидация email).
*Исключения — это дорого (создание stack trace) и они предназначены для **исключительных** ситуаций.* Если ошибка ожидаема — используйте возвращаемые значения (например, `null` или специальный Result Object).

#### В. Перехват слишком широких типов
```php
catch (\Throwable $e) // Плохо
```
Ловить `Throwable` в середине бизнес-логики — значит мешать системе падать при критических ошибках (типа `Error` или `TypeError`), которые нужно исправлять в коде, а не обрабатывать в `catch`.

#### Г. "Exception Swallowing" с потерей контекста
Когда разработчик ловит `PDOException` и выбрасывает `new \Exception("Error")`, теряя оригинальный объект исключения. Без `$e` в качестве `previous` мы теряем SQL-запрос, который вызвал ошибку, и саму причину (например, нарушение уникальности ключа).

---

**Резюме моего подхода:**
1. **Типизация:** Всегда свои классы исключений.
2. **Абстракция:** Оборачиваем низкоуровневые ошибки в высокоуровневые.
3. **Цепочка:** Всегда передаем `$previous` исключение.
4. **Предсказуемость:** Исключение — это сигнал о нарушении контракта, а не способ сказать "пользователь ввел не то".

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

По моему опыту, чаще всего в реальных проектах нарушается **Single Responsibility Principle (SRP)** — Принцип единственной ответственности.

### Почему это происходит?
Разработчики (особенно на ранних этапах или в условиях жесткого дедлайна) склонны создавать так называемые **«Божественные объекты» (God Objects)**. Логика кажется линейной: «Мне нужно зарегистрировать пользователя, отправить ему письмо и создать запись в логах». Кажется проще сделать это в одном методе или одном сервисе, чем плодить новые классы. 

В итоге получается класс, который знает слишком много: как работать с БД, как формировать Email, как общаться с внешним API и как хранить конфигурацию. Такой код крайне сложно тестировать и невозможно менять, не сломав что-то в другом месте.

---

### Типовой пример нарушения (God Service)

Представь сервис регистрации. Он делает всё: валидирует, сохраняет, шлет почту и логирует.

```php
class UserService {
    public function register(array $data): void {
        // 1. Валидация (Нарушение: сервис знает о правилах валидации)
        if (empty($data['email']) || !filter_var($data['email'], FILTER_VALIDATE_EMAIL)) {
            throw new \InvalidArgumentException("Invalid email");
        }

        // 2. Работа с БД (Нарушение: сервис знает о SQL/Eloquent/Doctrine)
        $user = new User();
        $user->setEmail($data['email']);
        $user->save(); 

        // 3. Отправка Email (Нарушение: сервис знает о протоколах почты/SMTP)
        mail($user->getEmail(), "Welcome!", "Thanks for joining.");

        // 4. Логирование (Нарушение: сервис знает о механизме логов)
        file_put_contents('app.log', "User {$user->getId()} registered\n", FILE_APPEND);
    }
}
```

**Проблемы этого кода:**
1. **Тестирование:** Чтобы протестировать регистрацию, тебе нужно настроить и БД, и почтовый сервер, и файловую систему.
2. **Хрупкость:** Если мы решим сменить `mail()` на `Mailgun`, нам придется менять `UserService`.
3. **Дублирование:** Если нам понадобится регистрация через API, нам придется либо копировать этот код, либо вызывать этот тяжелый сервис.

---

### Рефакторинг (Соблюдение SRP и Dependency Injection)

Мы разделяем ответственности, делегируя каждую задачу специализированному объекту.

```php
// 1. Интерфейсы для гибкости (DIP)
interface UserRepositoryInterface {
    public function save(User $user): void;
}

interface MailerInterface {
    public function sendWelcomeEmail(User $user): void;
}

// 2. Специализированные сервисы
class UserService {
    public function __construct(
        private UserRepositoryInterface $userRepository,
        private MailerInterface $mailer,
        private LoggerInterface $logger // Используем стандартный PSR-3
    ) {}

    public function register(UserRegistrationDto $dto): void {
        // Валидация теперь вынесена в DTO или отдельный Validator
        $user = User::fromDto($dto); 
        
        $this->userRepository->save($user);
        $this->mailer->sendWelcomeEmail($user);
        $this->logger->info("User {$user->getId()} registered");
    }
}
```

### Что изменилось?

1.  **Single Responsibility:** `UserService` теперь отвечает **только за координацию** процесса регистрации. Он не знает, *как* сохраняется пользователь и *как* отправляется письмо. Он просто говорит: «Сохрани это» и «Отправь это».
2.  **Testability:** Теперь мы можем легко написать Unit-тест для `UserService`, подставив **Mock**-объекты для репозитория и почтовика. Тест будет выполняться за миллисекунды и не потребует реальной БД.
3.  **Extensibility:** Если завтра мы перейдем с MySQL на MongoDB или с `mail()` на `SendGrid`, мы просто создадим новую реализацию интерфейса и подменим её в контейнере (DI Container). Сам `UserService` не изменится ни на одну строчку.

**Вывод:** Соблюдение SRP превращает «спагетти-код» в конструктор, где детали реализации легко заменяются, не нарушая целостность системы.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Короткий ответ: **Да, можно.** 

В инженерии существует понятие **Engineering Trade-offs** (инженерные компромиссы). Любое решение в разработке — это баланс между чистотой кода, скоростью разработки, стоимостью поддержки и производительностью. Принципы SOLID — это не законы физики, а рекомендации, которые помогают управлять сложностью. Если сложность не угрожает проекту, иногда стоит пожертвовать идеальной архитектурой.

Вот три основные ситуации, когда нарушение SOLID может быть оправданным:

### 1. MVP (Minimum Viable Product) и прототипирование
Когда задача стоит «проверить гипотезу за неделю» или «выкатить прототип до инвесторов», написание идеальной иерархии интерфейсов и внедрение множества паттернов может привести к **Overengineering** (избыточному проектированию).

*   **Пример:** Вы пишете небольшой скрипт для разового импорта данных из CSV в БД. 
*   **Нарушение:** Вы нарушаете SRP и DIP, написав один монолитный скрипт с жестко прописанными SQL-запросами.
*   **Почему это оправдано:** Если этот скрипт будет запущен один раз и больше никогда не изменится, создание полноценного слоя репозиториев и интерфейсов — это пустая трата денег компании.

### 2. Проекты с очень низким уровнем сложности и малым сроком жизни
Если вы пишете микросервис, который выполняет одну простую функцию (например, просто перекладывает сообщение из очереди в базу) и который не будет поддерживаться годами, избыточная архитектура создаст больше проблем, чем решит.

*   **Пример:** Нарушение Open/Closed Principle (OCP). Вместо создания интерфейсов для разных типов уведомлений, вы используете простой `switch` внутри метода.
*   **Почему это оправдано:** Если вероятность появления новых типов уведомлений в ближайшие 2 года равна нулю, то `switch` читается проще и понятнее, чем дерево классов с паттерном «Стратегия».

### 3. Критическая производительность (Highload)
Иногда следование SOLID (особенно Dependency Injection и использование множества абстракций) вносит накладные расходы на память и процессорное время (вызовы методов через таблицы виртуальных функций, создание множества объектов в контейнере).

*   **Пример:** В высоконагруженном цикле обработки миллионов пакетов данных вы решаете не использовать абстрактные обертки и интерфейсы, а работать с «голыми» примитивами и конкретными классами.
*   **Почему это оправдано:** В экстремальных условиях (например, обработка трафика в real-time) лишний уровень абстракции может стать узким местом (bottleneck).

---

### Золотое правило: "Rule of Three" (Правило трех)

Чтобы не превратить нарушение в хроническую болезнь, я рекомендую использовать подход: **«Не делай абстракцию, пока не увидишь необходимость трижды».**

1.  **Первый раз:** Пишем быстро и «грязно» (нарушаем SRP/OCP).
2.  **Второй раз:** Копируем код или чуть-чуть меняем. Начинаем чувствовать легкий дискомфорт.
3.  **Третий раз:** Когда приходят изменения в третий раз, мы видим четкую закономерность. Только в этот момент мы проводим рефакторинг и внедряем SOLID.

**Резюме:** Нарушение SOLID оправдано, если **стоимость написания чистого кода выше, чем стоимость его потенциального исправления в будущем.** Если риск «грязного» кода минимален, а время на «чистый» слишком велико — выбирайте скорость.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Это отличный вопрос, который бьет прямо в цель одной из главных проблем объектно-ориентированного программирования: **наследования**. 

Наследование часто называют «сильным» или «жестким» связыванием (tight coupling), потомуная оно нарушает инкапсуляцию (подкласс зависит от деталей реализации родителя). В современном PHP (и в ООП в целом) для реализации **Open/Closed Principle (OCP)** гораздо эффективнее использовать **композицию** и **полиморфизм через интерфейсы**.

Вот основные способы реализации OCP без использования наследования:

### 1. Композиция и паттерн «Стратегия» (Strategy)
Это самый распространенный способ. Вместо того чтобы расширять класс через наследование, мы передаем ему объект, который реализует нужный интерфейс. Мы «открыты» для новых алгоритмов (через новые реализации интерфейса), но «закрыты» для изменений в самом классе-контексте.

**Пример:** Система расчета стоимости доставки.

```php
// Интерфейс — наш контракт
interface ShippingStrategy {
    public function calculate(float $weight): float;
}

// Конкретные реализации (новые стратегии легко добавлять)
class FedexStrategy implements ShippingStrategy {
    public function calculate(float $weight): float { return $weight * 1.5; }
}

class DHLStrategy implements ShippingStrategy {
    public function calculate(float $weight): float { return $weight * 2.0; }
}

// Класс-контекст (Закрыт для изменений, открыт для новых стратегий)
class ShippingCalculator {
    private ShippingStrategy $strategy;

    public function __construct(ShippingStrategy $strategy) {
        $this->strategy = $strategy;
    }

    public function setStrategy(ShippingStrategy $strategy): void {
        $this->strategy = $strategy;
    }

    public function getCost(float $weight): float {
        return $this->strategy->calculate($weight);
    }
}

// Использование:
$calculator = new ShippingCalculator(new FedexStrategy());
echo $calculator->getCost(10); // 15

// Добавляем новую службу, не меняя ShippingCalculator!
$calculator->setStrategy(new DHLStrategy());
echo $calculator->getCost(10); // 20
```

### 2. Использование паттерна «Декоратор» (Decorator)
Декоратор позволяет динамически добавлять новую функциональность объекту, не меняя его исходный код и не используя наследование для расширения поведения.

**Пример:** Логирование или кэширование данных.

```php
interface DataProvider {
    public function getData(): string;
}

class SimpleDataProvider implements DataProvider {
    public function getData(): string {
        return "Some data";
    }
}

// Декоратор, который добавляет логирование
class LoggingDecorator implements DataProvider {
    public function __construct(
        private DataProvider $wrapped
    ) {}

    public function getData(): string {
        echo "Log: Fetching data...\n";
        return $this->wrapped->getData();
    }
}

// Использование:
$provider = new LoggingDecorator(new SimpleDataProvider());
echo $provider->getData(); 
```
Здесь мы "открыты" для добавления новых функций (кэширование, сжатие, шифрование) через новые декораторы, но "закрыты" для изменения `SimpleDataProvider`.

### 3. Паттерн «Наблюдатель» (Observer)
Этот паттерн позволяет реализовать OCP на уровне событий. Объект (Subject) не знает, кто на него подписан, он просто уведомляет подписчиков о событии.

**Пример:** После регистрации пользователя нужно отправить email и создать бонусный счет.

```php
interface EventSubscriber {
    public function handle(User $user): void;
}

class UserRegistrationSubject {
    private array $subscribers = [];

    public function subscribe(EventSubscriber $subscriber): void {
        $this->subscribers[] = $subscriber;
    }

    public function register(User $user): void {
        // Логика регистрации...
        echo "User registered!\n";

        // Оповещение всех подписчиков
        foreach ($this->subscribers as $subscriber) {
            $subscriber->handle($user);
        }
    }
}

// Мы можем добавлять любое количество новых действий, не меняя UserRegistrationSubject
class EmailSubscriber implements EventSubscriber {
    public function handle(User $user): void { echo "Sending email...\n"; }
}

class BonusSubscriber implements EventSubscriber {
    public function handle(User $user): void { echo "Adding bonus points...\n"; }
}
```
Класс `UserRegistrationSubject` **закрыт** для изменений (нам не нужно лезть в него, чтобы добавить новую акцию), но **открыт** для расширения (мы просто подписываем нового слушателя).

### 4. Dependency Injection (DI) и Service Container
Хотя DI — это механизм, он является ключевым инструментом для реализации OCP. С помощью DI мы можем менять поведение приложения, просто меняя конфигурацию в контейнере. Мы подменяем одну реализацию интерфейса на другую, не трогая код, который этот интерфейс использует.

### Итог: почему это лучше наследования?
1.  **Меньше связности (Low Coupling):** Мы зависим от абстракций (интерфейсов), а не от конкретных реализаций.
2.  **Гибкость в рантайме:** Наследование работает только на этапе компиляции/написания кода. Композиция (Strategy/Decorator) позволяет менять поведение программы прямо во время её выполнения.
3.  **Избегание проблемы «хрупкого базового класса»:** При наследовании изменение в родителе может непредсказуемо сломать десятки потомков. При композиции каждый объект автономен.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Короткий ответ: **Нет, не только.**

Хотя в учебниках по ООП принцип единственной ответственности (Single Responsibility Principle) чаще всего объясняют на примере классов, в современной разработке он распространяется на **любой уровень абстракции**, где существует логика.

Если мы говорим шире, SRP — это принцип **минимизации когнитивной нагрузки**. Любой элемент системы должен отвечать за одну концепцию (один «принцип изменения»).

Вот уровни, на которых применяется SRP:

### 1. Уровень функций и методов (самый прикладной)
Метод должен выполнять одну операцию. Если в методе вы видите слова «и», «затем», «а также» — скорее всего, он нарушает SRP.

*   **Нарушение:** Метод `saveUser()`, который одновременно валидирует данные, сохраняет в БД и отправляет уведомление.
*   **Соблюдение:** Метод `validate()`, метод `save()`, метод `notify()`.

### 2. Уровень модулей и пакетов (Composer packages / Namespaces)
Модуль (или библиотека) должен решать одну задачу. 

*   **Нарушение:** Пакет, который умеет и работать с изображениями, и отправлять SMS, и генерировать PDF-отчеты. 
*   **Соблюдение:** Разделение на специализированные пакеты: `image-processor`, `sms-gateway`, `pdf-generator`. Это позволяет пользователям устанавливать только то, что им нужно, не таща за собой лишние зависимости.

### 3. Уровень микросервисов (Архитектурный уровень)
Это SRP, возведенный в абсолют. Микросервис должен отвечать за один **Bounded Context** (ограниченный контекст) в терминах DDD.

*   **Нарушение:** «Монолитный микросервис», который управляет и пользователями, и заказами, и складом, и доставкой. Если изменения в логике склада заставляют переделывать сервис заказов — это нарушение SRP.
*   **Соблюдение:** Отдельный сервис `OrderService`, отдельный `StockService`.

### 4. Уровень системных компонентов (Инфраструктура)
Даже на уровне железа или ОС есть подобие SRP. Например, ядро ОС отвечает за управление ресурсами, а драйвер — за специфику работы с конкретным устройством.

---

### Как понять, что уровень (класс, метод или сервис) нарушает SRP?

Существует отличный критерий — **«Причина для изменения» (Reason to change)**. 

Задайте себе вопрос: *«Сколько разных людей или отделов могут попросить меня изменить этот компонент?»*

1.  Если вы измените **метод** `processData()`, потому что изменился формат даты — это одна причина. 
2.  Если вы измените тот же метод, потому что изменился способ записи в БД — это **вторая** причина.
3.  Если вы измените его, потому что изменился формат логов — это **третья** причина.

**Если у одного компонента три разные причины для изменения — он нарушает SRP.**

### Резюме
SRP — это не «правило для классов», это **философия управления сложностью**. 
*   На уровне **метода** мы боремся с запутанным кодом.
*   На уровне **класса** — с жесткой связностью.
*   На уровне **модуля/сервиса** — с масштабируемостью и сложностью развертывания.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

Это отличный вопрос, который отделяет простого пользователя фреймворка от инженера, понимающего, как работает магия под капотом. 

В Symfony DI Container — это не просто «склад объектов», это мощный механизм, который проходит через два принципиально разных этапа: **Compile Time** (сборка) и **Runtime** (использование).

---

### 1. Этап компиляции (Compile Time)
Когда вы очищаете кэш или запускаете приложение в режиме `prod`, Symfony запускает процесс компиляции контейнера. Это происходит **один раз**.

**Что происходит на этом этапе:**
1.  **Загрузка конфигурации:** Symfony собирает все файлы `services.yaml`, конфигурации из бандлов и атрибуты классов.
2.  **Построение графа зависимостей:** Контейнер анализирует, какой сервис от чего зависит. Он строит дерево: «Сервис А нужен Сервису Б, а Сервису Б нужен Сервис В».
3.  **Прохождение Compiler Passes:** Это «магия» Symfony. Существуют специальные классы (Compiler Passes), которые могут изменять конфигурацию контейнера «на лету». 
    *   *Пример:* Пасс находит все сервисы, помеченные тегом `kernel.event_subscriber`, и автоматически регистрирует их в `EventDispatcher`. Вам не нужно прописывать их вручную — контейнер сам «находит» их во время компиляции.
4.  **Оптимизация и генерация PHP-кода:** Это самый важный момент. Symfony не читает YAML-файлы во время запроса пользователя. Вместо этого она генерирует **чистый PHP-класс** (обычно в папке `var/cache/.../App_KernelDevDebugContainer.php`). 
    *   Этот сгенерированный класс содержит методы вроде `getServiceA()`, которые по сути являются набором инструкций `new ServiceA(new ServiceB(...))`.

**Итог компиляции:** У вас есть максимально оптимизированный, плоский PHP-класс, который знает всё о связях ваших сервисов.

---

### 2. Как работает Autowiring
Autowiring — это не магия во время выполнения запроса, это **магия во время компиляции**.

Когда Symfony видит ваш класс:
```php
public function __construct(UserRepository $repository) {}
```
Во время компиляции (этап 1) она использует **Reflection API**, чтобы прочитать типы аргументов конструктора. 

1.  Контейнер видит: «Ага, методу нужен объект типа `UserRepository`».
2.  Он ищет в своем графе зависимостей: «Есть ли у меня сервис, который реализует или является `UserRepository`?».
3.  Если находит, он записывает в сгенерированный PHP-класс инструкцию: «При создании этого сервиса, передай в конструктор результат вызова `get(UserRepository::class)`».

**Важно:** Если вы допустите ошибку (например, два сервиса реализуют один интерфейс и контейнер не знает, какой выбрать), ошибка вылетит **на этапе компиляции**, а не когда пользователь нажмет на кнопку.

---

### 3. Момент запроса сервиса (Runtime)
Когда в коде вызывается `$container->get(MyService::class)` (или это происходит автоматически через внедрение в контроллер), происходит следующее:

1.  **Проверка Shared (Singleton) состояния:** В Symfony по умолчанию все сервисы являются **shared** (синглтонами внутри одного запроса). Контейнер проверяет: «Создавал ли я этот объект ранее в этом запросе?».
2.  **Если сервис уже создан:** Контейнер просто возвращает уже существующий экземпляр из внутреннего массива (кеша объектов). Это очень быстро.
3.  **Если сервис еще не создан (First time):**
    *   Вызывается сгенерированный метод из скомпилированного класса (например, `getMyService()`).
    *   Этот метод выполняет цепочку `new ...` для всех зависимостей, которые были прописаны в графе.
    *   Объект создается, помещается в массив внутри контейнера (чтобы при следующем запросе отдать тот же экземпляр) и возвращается вам.

### Итоговая схема:

| Этап | Когда | Что делает | Результат |
| :--- | :--- | :--- | :--- |
| **Compile Time** | При деплое / очистке кэша | Reflection, Compiler Passes, анализ YAML | Оптимизированный PHP-класс с готовыми `new` |
| **Runtime (First call)** | При первом обращении | Вызов метода из сгенерированного класса | Создание объекта и сохранение в кеш (shared) |
| **Runtime (Subsequent)** | При повторном обращении | Возврат из внутреннего массива | Мгновенная отдача готового объекта |

**Почему это круто?** Потому что мы получаем удобство декларативного описания (YAML/Attributes) и мощь Autowiring, но при этом в рантайме получаем производительность обычного PHP-кода без лишних раздумий и парсинга конфигов.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

Циклические зависимости (Circular Dependencies) — это ситуация, когда `ServiceA` требует `ServiceB`, а `ServiceB` требует `ServiceA`. В Symfony это приводит к фатальной ошибке при попытке создания объектов, так как контейнер попадает в бесконечную рекурсию.

Я подхожу к решению этой проблемы в три этапа: сначала пытаюсь **исправить архитектуру** (потому что цикл — это симптом болезни), затем использую **инструменты фреймворка**, и в крайнем случае — **дизайнерские паттерны**.

---

### 1. Архитектурное исправление (Правильный путь)

Чаще всего циклическая зависимость — это признак того, что ваши сервисы слишком «толстые» или их обязанности размыты.

**А) Выделение третьего сервиса (Extract Class)**
Если `A` и `B` зависят друг от друга, значит, у них есть общая логика, которая не принадлежит ни одному из них. Я выделяю эту логику в `ServiceC`.
*   *Было:* `A <-> B`
*   *Стало:* `A -> C` и `B -> C`. Теперь `A` и `B` независимы.

**Б) Пересмотр границ ответственности (Refactoring)**
Иногда цикл возникает, потому что сервис делает слишком много. Например, `UserService` вызывает `OrderService`, а `OrderService` хочет проверить статус пользователя через `UserService`. 
*   *Решение:* Я переношу проверку статуса в более низкий слой (например, в `UserRepository` или отдельный `UserPolicy`), который не зависит от заказов.

---

### 2. Инструменты Symfony (Быстрый путь)

Если архитектурно изменить всё прямо сейчас невозможно (например, при рефакторинге легаси), я использую встроенные возможности DI.

**А) Lazy Services (Ленивые сервисы)**
Это самый элегантный способ в Symfony. Вместо того чтобы внедрять реальный объект, Symfony внедряет **Proxy-объект**. Этот прокси выглядит как ваш сервис, но он не инициализирует реальный объект до тех пор, пока вы не вызовете у него первый метод.

```yaml
# services.yaml
App\Service\ServiceA:
    lazy: true

App\Service\ServiceB:
    lazy: true
```
*Как это работает:* Контейнер создает «пустышку». `ServiceA` получает этот прокси и успешно создается. Когда вы позже вызовете `$serviceA->doSomething()`, прокси внутри себя обратится к контейнеру, создаст реальный `ServiceA` и передаст вызов ему. Цикл разорван.

**Б) Использование Setter Injection вместо Constructor Injection**
Конструктор требует объект *в момент создания*. Сеттер позволяет создать объект, а потом «доставить» ему зависимость.
*   *Минус:* Это делает объект менее надежным (состояние может быть неполным в момент создания), поэтому я использую это только как временную меру.

---

### 3. Паттерны проектирования (Дизайнерский путь)

Если архитектура требует сложной логики, я применяю паттерны, которые естественным образом разрывают связи.

**А) Паттерн «Событие/Слушатель» (Event Dispatcher)**
Это мой фаворит. Вместо того чтобы `ServiceA` вызывал `ServiceB` напрямую, `ServiceA` просто генерирует событие: *"Я сделал что-то!"*.
*   `ServiceA` не знает о существовании `ServiceB`.
*   `ServiceB` подписан на это событие.
*   **Цикл разорван полностью**, так как прямой связи между ними больше нет.

**Б) Паттерн «Команда» (Command Bus / Messenger)**
Вместо того чтобы один сервис вызывал метод другого, он отправляет **Command** (объект-команду) в шину (Bus).
*   `ServiceA` отправляет `CreateOrderCommand`.
*   `CommandHandler` получает команду и вызывает `ServiceB`.
*   Связь идет не между сервисами, а через посредника (Bus), что делает их абсолютно независимыми.

### Резюме моего алгоритма:
1.  **Попробовать вынести общую логику** в третий сервис (лучшее решение).
2.  **Использовать Event Dispatcher**, чтобы превратить прямую зависимость в реактивную (самое чистое решение).
3.  Если нужно быстро «заткнуть дыру» без изменения логики — использовать **`lazy: true`** в Symfony.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

Для решения этой задачи я буду использовать **асинхронную обработку задач**. Главная цель — минимизировать время ответа сервера (Response Time), выполнив тяжелые операции (почта, API поисковика) в фоновом режиме.

В экосистеме Symfony для этого есть стандартный и мощный инструмент — **Symfony Messenger**.

Вот три варианта реализации, от простого к профессиональному, с их плюсами и минусами.

---

### Вариант 1: Symfony Messenger + Транспорт (RabbitMQ / Redis / Doctrine)
Это «золотой стандарт» для современных Symfony-приложений. Мы разделяем процесс на **Dispatching** (отправка команды) и **Handling** (выполнение).

**Как это работает:**
1. В контроллере или сервисе после сохранения пользователя я вызываю `$bus->dispatch(new UserRegisteredEvent($userId));`.
2. Messenger берет это событие, сериализует его и отправляет в «транспорт» (например, в очередь RabbitMQ или Redis).
3. Пользователь сразу получает ответ `201 Created`.
4. В это время отдельный процесс (**Worker**) в фоновом режиме слушает очередь, забирает сообщение и выполняет два хендлера: `SendWelcomeEmailHandler` и `UpdateSearchIndexHandler`.

**Trade-offs:**
*   **Плюсы:** 
    *   **Надежность:** Если почтовый сервис упадет, сообщение останется в очереди и будет обработано позже (Retry mechanism).
    *   **Масштабируемость:** Можно запустить 10 воркеров на разных серверах, если очередь растет.
    *   **Скорость:** Пользователь не ждет сетевых задержек от внешних API.
*   **Минусы:** 
    *   **Сложность инфраструктуры:** Нужно разворачивать и поддерживать брокер сообщений (RabbitMQ/Redis).
    *   **Мониторинг:** Нужно следить за тем, чтобы воркеры не «упали» и очередь не переполнилась.

---

### Вариант 2: Использование Doctrine Transport (Low-overhead)
Если мы не хотим внедрять RabbitMQ, Symfony Messenger позволяет использовать **базу данных (PostgreSQL/MySQL)** в качестве транспорта.

**Как это работает:**
Сообщения сохраняются в специальную таблицу в нашей текущей БД. Воркер (команда `messenger:consume doctrine`) читает их оттуда.

**Trade-offs:**
*   **Плюсы:**
    *   **Простота:** Не нужно устанавливать новый софт, всё уже есть в проекте.
    *   **Транзакционность:** Можно сделать так, чтобы сообщение попадало в очередь только в рамках той же БД-транзакции, что и регистрация пользователя (атомарность).
*   **Минусы:**
    *   **Нагрузка на БД:** Постоянные запросы `SELECT/UPDATE` от воркеров создают лишнюю нагрузку на основную базу данных.
    *   **Производительность:** База данных не предназначена для работы в качестве высокоскоростной очереди сообщений.

---

### Вариант 3: FastCGI Finish Request (Quick & Dirty)
Если проект очень маленький и мы не хотим возиться с очередями, можно использовать функцию `fastcgi_finish_request()`.

**Как это работает:**
Эта функция говорит веб-серверу (Nginx + PHP-FPM): «Отправь клиенту ответ и закрой соединение, но не завершай выполнение PHP-скрипта».

```php
// В контроллере
$user = $repository->save($user);
echo json_encode(['status' => 'ok']);

if (function_exists('fastcgi_finish_request')) {
    fastcgi_finish_request(); // Клиент получил ответ и закрыл вкладку
}

// Дальше идет тяжелый код, который клиент уже не видит
$mailer->sendWelcomeEmail($user);
$searchIndexer->update($user);
```

**Trade-offs:**
*   **Плюсы:**
    *   **Максимальная скорость внедрения:** Не нужно ничего настраивать.
*   **Минусы:**
    *   **Никакой надежности:** Если скрипт упадет на этапе отправки письма, пользователь об этом не узнает, а письмо не уйдет. Мы не сможем его перезапустить.
    *   **Блокировка ресурсов:** PHP-процесс остается занятым и не может обрабатывать новые запросы, пока не доделает фоновую работу. Это быстро «съест» все доступные воркеры PHP-FPM.
    *   **Зависимость от среды:** Работает только в связке Nginx + PHP-FPM.

---

### Мой выбор и вердикт

Для реального продакшн-приложения я выберу **Вариант 1 (Messenger + RabbitMQ или Redis)**. 

**Почему:**
1.  **Гарантия доставки:** Регистрация пользователя — критическое событие. Мы не можем позволить себе «потерять» отправку письма или обновление индекса.
2.  **Разделение ответственности:** Использование `UserRegisteredEvent` позволяет легко добавлять новые действия (например, отправку данных в CRM или аналитику) без изменения кода регистрации.
3.  **Устойчивость к нагрузкам:** В моменты пикового трафика очередь просто вырастет, но система не упадет, а воркеры постепенно разберут задачи.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

В Symfony контроль доступа разделяется на два четких этапа: **«Кто ты?» (Authentication)** и **«Что тебе можно?» (Authorization)**. Это фундаментальное различие важно понимать для проектирования безопасности.

### 1. Аутентификация (Authentication) — «Кто ты?»
Это процесс идентификации пользователя. В Symfony за это отвечают **Authenticators**.

*   **Как это работает:** Когда приходит запрос, цепочка аутентификаторов (настраивается в `security.yaml`) проверяет учетные данные (логин/пароль, JWT-токен, OAuth-токен и т.д.).
*   **Результат:** Если данные верны, создается объект `Token` (обычно `PostAuthenticationToken`), который содержит информацию о пользователе и его правах. Этот токен кладется в `TokenStorage`, и он становится доступен на протяжении всего жизненного цикла запроса.

### 2. Авторизация (Authorization) — «Что тебе можно?»
Когда мы уже знаем, кто перед нами, в дело вступает компонент `AccessDecisionManager`. Он решает, разрешить доступ или выдать `AccessDeniedException`.

Здесь есть три уровня проверки:

#### А) Роли (Roles) — Статический уровень
Роли — это простые строки (например, `ROLE_USER`, `ROLE_ADMIN`).
*   **Как работают:** Это иерархическая система. Если у вас настроена `role_hierarchy`, то `ROLE_ADMIN` может автоматически включать в себя `ROLE_USER`.
*   **Где используются:** В `security.yaml` для ограничения доступа к целым разделам (URL-адресам) или в аннотациях/атрибутах контроллеров: `#[IsGranted('ROLE_ADMIN')]`.

#### Б) Voter-ы — Динамический уровень
Voter (избиратель) — это класс, который реализует логику проверки доступа на основе бизнес-правил.
*   **Как работают:** Когда вы вызываете `$this->denyAccessUnlessGranted('EDIT', $article)`, Symfony опрашивает все зарегистрированные Voter-ы. Каждый из них говорит: «Я могу это проверить» или «Это не ко мне». Если Voter сказал «Да», доступ разрешен.

---

### Когда выбирать Role, а когда Voter?

Это ключевой вопрос архитектуры. Выбор зависит от того, **насколько проверка зависит от данных (контекста)**.

#### Выбираю ROLE, если:
Проверка **статична** и не зависит от конкретного объекта в базе данных. Это проверка «социального статуса» пользователя.
*   *Примеры:* 
    *   «Только администраторы могут заходить в панель управления».
    *   «Только платные подписчики могут смотреть видео».
    *   «Только модераторы могут удалять комментарии».
*   **Плюс:** Очень высокая производительность, простота настройки в конфиге.

#### Выбираю VOTER, если:
Проверка **динамична** и требует знания **владельца объекта** или его состояния. Это проверка «прав на конкретный ресурс».
*   *Примеры:*
    *   «Пользователь может редактировать статью, **только если он её автор**». (Нужно сравнить `user.id` и `article.author_id`).
    *   «Пользователь может просматривать документ, **только если у него есть статус 'Approved'** в этом документе».
    *   «Доступ разрешен, **только если сейчас рабочее время**».
*   **Плюс:** Позволяет реализовать сложнейшую бизнес-логику, инкапсулированную в одном месте.

---

### Пример реализации Voter (кратко)

Если бы я писал проверку на владение статьей, мой Voter выглядел бы так:

```php
class ArticleVoter extends Voter
{
    const EDIT = 'ARTICLE_EDIT';

    protected function supports(string $attribute, mixed $subject): bool
    {
        // Проверяем, что атрибут верный и subject — это объект Article
        return $attribute === self::EDIT && $subject instanceof Article;
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token): bool
    {
        $user = $token->getUser();
        if (!$user instanceof User) {
            return false;
        }

        /** @var Article $article */
        $article = $subject;

        // Логика: только автор может редактировать
        return $article->getAuthor() === $user;
    }
}
```

### Резюме для собеседования:
1.  **Authentication** — идентификация (кто ты).
2.  **Authorization** — проверка прав (что можно).
3.  **Roles** — для глобальных прав доступа (админ/пользователь), проверяются быстро.
4.  **Voters** — для прав на конкретные сущности (автор/владелец), позволяют внедрять сложную бизнес-логику.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

Это отличный вопрос, который затрагивает стык чистого DDD и ограничений ORM. Проблема в том, что Doctrine — это Data Mapper, который через Reflection пытается управлять состоями объектов, а Value Object (VO) по определению должен быть **immutable** (неизменяемым) и **валидным** с момента создания.

Если просто объявить свойства как `readonly` (в PHP 8.1+) или приватные без сеттеров, Doctrine может столкнуться с трудностями при восстановлении объекта из базы.

Вот три основных способа решения этой задачи:

---

### 1. Использование Embeddables (Рекомендуемый способ)
Это нативный механизм Doctrine для работы с Value Objects. Он позволяет «встроить» поля VO в таблицу основной сущности.

**Как это выглядит:**
```php
#[ORM\Embeddable]
readonly class Money {
    public function __construct(
        #[ORM\Column(type: 'int')]
        private int $amount,
        #[ORM\Column(type: 'string', length: 3)]
        private string $currency,
    ) {
        if ($amount < 0) throw new \InvalidArgumentException("Amount cannot be negative");
    }
}

#[ORM\Entity]
class Product {
    #[ORM\Embedded(class: Money::class)]
    private Money $price;
}
```

**Плюсы:**
* **Нативность:** Это стандартный путь Doctrine.
* **Простота:** Данные хранятся в той же таблице, что и сущность (нет лишних JOIN).
* **Валидация:** Конструктор VO гарантирует, что объект никогда не будет в невалидном состоянии.

**Минусы и подводные камни:**
* **Связанность с БД:** VO начинает «знать» о типах колонок Doctrine.
* **Отсутствие переиспользования:** Вы не можете легко использовать Embeddable как отдельную сущность с собственным ID.

---

### 2. Custom Types (Типизированные столбцы)
Вы можете создать свой собственный тип данных для Doctrine, который будет заниматься сериализацией/десериализацией вашего VO в строку (например, JSON или строку через разделитель).

**Как это выглядит:**
В базе хранится строка `100|USD`. В `MoneyType` вы прописываете логику преобразования.

**Плюсы:**
* **Изоляция:** Сущность вообще не знает, что это VO, она просто видит тип данных.
* **Чистота БД:** Все VO одного типа хранятся в одной колонке в едином формате.

**Минусы и подводные камни:**
* **Проблема поиска (Querying):** Если вы храните VO в формате JSON в одной колонке, вам будет крайне сложно (или невозможно на уровне стандартного SQL) делать запросы типа `WHERE money.amount > 100`.
* **Производительность:** Постоянная сериализация/десериализация при каждом чтении/записи.

---

### 3. Использование Lifecycle Callbacks или `__construct` (Manual Mapping)
Если вы не хотите использовать Embeddables, вы можете хранить поля VO отдельно в сущности, но при чтении/записи «собирать» их.

**Как это выглядит:**
В сущности хранятся `$priceAmount` и `$priceCurrency`. В методе `getPrice()` вы создаете новый объект `new Money($this->priceAmount, $this->priceCurrency)`.

**Плюсы:**
* Полный контроль над тем, как данные попадают в VO.

**Минусы и подводные камни:**
* **Раздувание сущности:** Сущность превращается в «свалку» из примитивных полей, которые на самом деле являются частями одного объекта. Это нарушает инкапсуляцию.

---

### Главные подводные камни при работе с VO и Doctrine

#### 1. Проблема "Identity" и сравнения
Value Object определяется своими значениями, а не ID. В Doctrine, если вы достанете один и тот же VO из разных сущностей, это будут разные экземпляры в памяти. При сравнении `$vo1 === $vo2` вы получите `false`, даже если значения идентичны. 
* **Решение:** Всегда переопределяйте методы `equals(ValueObject $other): bool` и используйте их вместо строгого сравнения.

#### 2. Инициализация через Reflection
Doctrine использует Reflection для обхода конструктора при загрузке данных из БД. Это может привести к тому, что **валидация в конструкторе будет проигнорирована**, если данные в БД по какой-то причине стали некорректными (например, кто-то поправил их вручную через SQL).
* **Решение:** Если данные критически важны, стоит добавить проверку валидности в метод `postLoad` или убедиться, что на уровне БД стоят `CHECK constraints`.

#### 3. Immutability vs Doctrine Proxy
Если вы используете прокси-объекты (Lazy Loading), Doctrine может попытатить «подменить» части объекта. Для VO это не критично, так как они не имеют своей жизненной очереди (Identity Map), но важно помнить: **VO не должен иметь своего жизненного цикла (ID, CreatedAt и т.д.)**.

### Мой выбор:
Для 90% задач я выбираю **Embeddables**. Это дает лучший баланс между чистотой доменной модели, производительностью запросов (отсутствие JOIN и возможность фильтрации по колонкам) и простотой поддержки.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

Это фундаментальный вопрос проектирования. В DDD **Агрегат** — это граница согласованности (Consistency Boundary). Все изменения внутри агрегата должны быть атомарными, а доступ к дочерним элементам должен осуществляться **только через Корень Агрегата (Aggregate Root)**.

Разберем это на примере агрегата **`Order` (Заказ)**, который содержит коллекцию **`OrderItem` (Позиции заказа)**.

---

### 1. Маппинг коллекции (Doctrine Mapping)

Чтобы соблюсти принцип инкапсуляции, мы не должны позволять внешнему коду напрямую манипулировать коллекцией `items`.

**Правила маппинга:**
*   Используем `orphanRemoval: true`. Если мы удаляем позицию из коллекции заказа, Doctrine должна автоматически удалить запись из таблицы `order_items`.
*   Используем `cascade: ['persist', 'remove']`. Изменения в позициях должны автоматически «протекать» в корень при сохранении корня.

```php
#[ORM\Entity]
class Order {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    /** @var Collection<int, OrderItem> */
    #[ORM\OneToMany(
        targetEntity: OrderItem::class, 
        mappedBy: 'order', 
        cascade: ['persist', 'remove'], 
        orphanRemoval: true
    )]
    private Collection $items;

    public function __construct() {
        $this->items = new ArrayCollection();
    }

    // ВАЖНО: Мы не возвращаем саму коллекцию для изменения!
    // Мы возвращаем только итерируемый объект или копию.
    public function getItems(): array {
        return $this->items->toArray();
    }

    // Единственный способ изменить коллекцию — через метод агрегата
    public function addItem(Product $product, int $quantity): void {
        $item = new OrderItem($this, $product, $quantity);
        $this->items->add($item);
    }

    public function removeItem(OrderItem $item): void {
        $this->items->removeElement($item);
    }
}

#[ORM\Entity]
class OrderItem {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'items')]
    #[ORM\JoinColumn(nullable: false)]
    private Order $order;

    // ... остальные поля
}
```

---

### 2. Границы транзакции и вызов `flush()`

Это самая частая точка ошибки. В DDD существует строгое правило: **Один агрегат — одна транзакция.**

#### Кто вызывает `flush()`?
`flush()` **никогда** не должен вызываться внутри доменного сервиса или внутри самого Агрегата. Агрегат — это чистая бизнес-логика, он не должен знать о существовании БД или Unit of Work.

`flush()` должен вызываться на уровне **Application Service (Use Case)**.

#### Как это работает (сценарий: добавление товара в заказ):

1.  **Application Service** открывает транзакцию (или полагается на то, что Doctrine обернет `flush` в транзакцию).
2.  Загружает **Aggregate Root** из репозитория.
3.  Вызывает **бизнес-метод** агрегата (`$order->addItem(...)`).
4.  Сохраняет агрегат через репозиторий (`$orderRepository->save($order)`).
5.  Вызывает `entityManager->flush()`.

**Пример Application Service:**

```php
class AddItemToOrderService {
    public function __construct(
        private OrderRepository $orderRepository,
        private ProductRepository $productRepository,
        private EntityManagerInterface $entityManager
    ) {}

    public function execute(int $orderId, int $productId, int $qty): void {
        // 1. Загружаем агрегат (целиком!)
        $order = $this->orderRepository->find($orderId);
        $product = $this->productRepository->find($productId);

        // 2. Выполняем бизнес-логику внутри агрегата
        // Внутри addItem() может быть проверка: "не превышен ли лимит веса заказа"
        $order->addItem($product, $qty);

        // 3. Сохраняем изменения
        // Repository внутри может просто делать $this->em->persist($order)
        $this->orderRepository->save($order);

        // 4. Фиксируем изменения в БД (атомарно для всего агрегата)
        $this->entityManager->flush();
    }
}
```

---

### 3. Почему это важно? (Анализ рисков)

**Риск 1: Нарушение инкапсуляции (Коллекция снаружи)**
Если вы сделаете `public function getItems(): Collection`, то любой разработчик напишет `$order->getItems()->add($newItem)`. Это обойдет бизнес-логику агрегата (например, пересчет общей суммы заказа), и состояние агрегата станет невалидным. **Всегда возвращайте `array` или `ReadOnlyCollection`.**

**Риск 2: Вызов `flush()` внутри цикла**
Если вы будете вызывать `flush()` для каждой позиции товара, вы создадите десятки мелких транзакций вместо одной большой. Это убьет производительность и нарушит атомарность (если на 5-м товаре произойдет ошибка, первые 4 уже будут в базе).

**Риск 3: Изменение дочерних сущностей без корня**
Если вы попытаетесь загрузить `OrderItem` напрямую и изменить его, минуя `Order`, вы нарушаете границы агрегата. Все изменения должны проходить через `Order`.

### Резюме:
*   **Маппинг:** `OneToMany` с `orphanRemoval` и `cascade`.
*   **Доступ:** Коллекция скрыта, изменение только через методы корня.
*   **Транзакция:** Весь агрегат (корень + дети) сохраняется одним вызовом `flush()` в Application Service.
*   **Граница:** Агрегат — это единица работы. Если вы меняете `OrderItem`, вы меняете `Order`.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

Проблема N+1 — это классическая ловушка ORM. Она возникает, когда вы загружаете список основных сущностей (1 запрос), а затем в цикле обращаетесь к их связанным объектам, что провоцирует еще по одному запросу для каждой записи (N запросов).

Вот мой алгоритм действий.

---

### 1. Диагностика

Прежде чем оптимизировать, нужно доказать наличие проблемы.

1.  **Symfony Profiler (самый быстрый путь):** В разделе "Doctrine" профилировщика я смотрю на количество запросов. Если я вижу десятки почти одинаковых запросов к одной и той же таблице (например, `SELECT ... FROM user WHERE id = ?`), — это оно.
2.  **SQL Log / Debug Bar:** Проверка через логирование SQL запросов в реальном времени.
3.  **Инструменты мониторинга (APM):** Если проблема на продакшене, я использую **New Relic** или **Blackfire.io**. Blackfire особенно хорош тем, что строит визуальный граф вызовов и сразу подсвечивает "горячие" участки, где тратится время на выполнение SQL.

---

### 2. Способы решения и их Trade-offs

#### Способ А: Eager Loading через `JOIN FETCH` (в DQL/QueryBuilder)
Это самый эффективный способ. Вместо того чтобы грузить сущности по одной, мы просим Doctrine вытащить их одним тяжелым запросом с использованием `JOIN`.

```php
// В репозитории
public function findAllWithUsers(): array {
    return $this->createQueryBuilder('o')
        ->leftJoin('o.user', 'u') // Присоединяем пользователя
        ->addSelect('u')          // ГОВОРИМ Doctrine: "Заполни объект пользователя данными из этого JOIN"
        ->getQuery()
        ->getResult();
}
```

*   **Плюсы:** Решает проблему за **1 запрос**. Очень высокая производительность.
*   **Минусы:** 
    *   **Проблема декартова произведения (Cartesian Product):** Если вы сделаете `JOIN FETCH` для двух разных коллекций (например, `orders` -> `items` И `orders` -> `tags`), количество строк в результате запроса вырастет экспоненциально (`orders * items * tags`), что перегрузит память и CPU.
    *   **Сложность запроса:** SQL становится тяжелее.

#### Способ Б: Использование `fetch="EAGER"` в маппинге
Можно настроить сущность так, чтобы она всегда подгружала связанные данные.

```php
#[ORM\ManyToOne(targetEntity: User::class, fetch: 'EAGER')]
private User $user;
```

*   **Плюсы:** Решает проблему "автоматически" для всего приложения.
*   **Минусы (Огромные):** Это **антипаттерн** в большинстве случаев. Теперь, когда вам в другом месте приложения нужен *просто* пользователь (без его заказов), Doctrine все равно будет делать лишний JOIN. Это превращает "точечные" проблемы в глобальную проблему производительности.

#### Способ В: Использование `Partial Objects` (редко и опасно)
Выбор только нужных полей.

*   **Плюсы:** Экономия трафика между БД и приложением.
*   **Минусы:** Очень опасно. Если вы подгрузили "частичный" объект, а потом попытались обратиться к полю, которое не загрузили — вы получите ошибку или `null`. Это нарушает целостность сущности.

#### Способ Г: Использование DTO (Data Transfer Objects)
Если вам нужно просто вывести список (например, таблицу в админке) и вам не нужны методы сущности, я не использую сущности вообще. Я пишу SQL/DQL запрос, который возвращает плоские DTO.

```php
// Возвращает массив объектов UserListDto, а не сущностей User
return $this->createQueryBuilder('u')
    ->select('new App\Dto\UserListDto(u.id, u.email, r.name)')
    ->leftJoin('u.role', 'r')
    ->getQuery()
    ->getResult();
```

*   **Плюсы:** 
    *   **Максимальная скорость:** Нет накладных расходов на создание тяжелых объектов Doctrine и управление ими в Unit of Work.
    *   **Никаких N+1:** Все данные приходят в одном плоском запросе.
*   **Минусы:** 
    *   **Read-only:** DTO нельзя сохранить обратно в базу через `flush()`. Это только для чтения.
    *   **Дублирование кода:** Приходится описывать DTO для разных экранов.

---

### Итоговая стратегия выбора:

1.  **Для отображения списков (Read-only):** Я выбираю **DTO**. Это самый быстрый и чистый способ для отображения данных в таблицах.
2.  **Для работы с бизнес-логикой (Write/Read):** Я использую **Eager Loading через `JOIN FETCH`** в конкретном репозитории, чтобы подгрузить только те связи, которые реально нужны для выполнения задачи.
3.  **Никогда** не использую `fetch="EAGER"` в маппинге сущностей, так как это создает скрытые проблемы в будущем.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

Это отличный вопрос, который часто вызывает споры: «Зачем дублировать логику?». Но в серьезных системах это не дублирование, а **эшелонированная оборона (Defense in Depth)**.

Бизнес-валидация в коде (PHP) — это **первая линия обороны**. Она быстрая, дает понятные сообщения пользователю и позволяет работать с логикой, которую БД не поймет.
Ограничения в БД — это **последняя линия обороны**. Она защищает данные от ошибок в коде, багов в миграциях, ручных правок администратора через консоль и ошибок в параллельных процессах.

Вот почему нельзя полагаться только на PHP:

### 1. Почему кода недостаточно?

*   **Race Conditions (Состояние гонки):** Две параллельные транзакции могут проверить одно и то же условие в PHP (например, «хватит ли денег на счету») и обе пройдут проверку, так как на момент проверки данные еще не зафиксированы. БД (с правильными уровнями изоляции) поймает это.
*   **Человеческий фактор:** Кто-то зашел в базу через `psql` или `pgAdmin`, чтобы "быстро поправить баг", и случайно удалил обязательное поле или вставил дубликат. Без ограничений в БД данные будут испорчены.
*   **Другие потребители данных:** Ваше приложение — не единственный, кто пишет в базу. Это могут быть микросервисы на Python, ETL-скрипты, системы аналитики или интеграционные шины. У них нет вашего PHP-кода с его валидацией.
*   **Целостность при миграциях:** При изменении структуры данных ошибки в скриптах миграции могут привести к нарушению логики.

---

### 2. Какие средства я использую в PostgreSQL

Я разделяю ограничения на три уровня:

#### А) Структурная целостность (Обязательно всегда)
Это база, которая гарантирует, что данные физически корректны.
*   **`NOT NULL`**: Гарантирует наличие обязательных полей.
*   **`PRIMARY KEY` / `UNIQUE`**: Гарантирует уникальность (например, `email` пользователя или `slug` статьи). Это защищает от дублей даже при ошибках в коде.
*   **`FOREIGN KEY`**: Гарантирует, что вы не создадите заказ для несуществующего пользователя и не удалите пользователя, у которого есть активные заказы.

#### Б) Доменная целостность (Domain Constraints)
Когда бизнес-правило простое и статистическое.
*   **`CHECK constraints`**: Идеально для диапазонов и простых условий.
    *   *Пример:* `CHECK (price > 0)`, `CHECK (status IN ('pending', 'active', 'canceled'))`, `CHECK (end_date > start_date)`.
*   **`ENUM` (или Check на строках)**: Для жестко заданных типов.

#### В) Сложная целостность (Advanced)
Когда правила выходят за рамки одной строки.
*   **Триггеры (Triggers)**: Для автоматического обновления полей (например, `updated_at`) или ведения аудиторского лога (history tables).
*   **Исключающие ограничения (Exclusion Constraints)**: В PostgreSQL это киллер-фича. Позволяет запретить пересечение периодов (например, нельзя забронировать один и тот же отель на пересекающиеся даты).

---

### 3. Примеры и стратегии применения

| Ситуация | Где валидация | Почему |
| :--- | :--- | :--- |
| **Формат email** | PHP (Symfony Validator) | Нужно вернуть пользователю красивую ошибку: "Email не валиден". |
| **Уникальность Email** | **БД (UNIQUE constraint)** | Только БД может гарантировать уникальность при одновременной регистрации двух людей. |
| **Сумма заказа > 0** | PHP + БД (CHECK) | В PHP — для UI, в БД — как страховка от ошибок в расчетах. |
| **Связь Заказ -> Юзер** | **БД (FOREIGN KEY)** | Чтобы не допустить "сиротских" записей в базе. |
| **Бронирование дат** | БД (Exclusion Constraint) | Чтобы исключить пересечение интервалов на уровне движка. |

### Резюме:
Я придерживаюсь правила: **«PHP — для удобства пользователя и UX, PostgreSQL — для неизменности и правды данных».** 

Бизнес-валидация в коде делает систему **дружелюбной**, а ограничения в БД делают систему **надежной**. Если вы уберете одно из двух, вы либо получите плохой UX, либо испорченную базу данных.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

Когда запрос выполняется медленно, моя задача — перейти от догадок к доказательствам. Я не начинаю менять индексы наугад, а использую итеративный процесс: **Анализ → Идентификация → Тестирование → Валидация**.

---

### 1. Инструментарий диагностики

Мой «джентльменский набор» включает:

1.  **`EXPLAIN (ANALYZE, BUFFERS)`**: Это мой главный инструмент. 
    *   `EXPLAIN` показывает **план** (как БД *планирует* выполнить запрос).
    *   `ANALYZE` выполняет запрос и показывает **реальное время** и количество строк.
    *   `BUFFERS` показывает, сколько данных было прочитано из памяти (shared buffers), а сколько — с диска. Это критично для понимания того, упираемся ли мы в I/O.
2.  **`pg_stat_statements`**: Расширение, которое позволяет увидеть статистику по всем запросам, выполненным на сервере. Я использую его, чтобы найти самые «дорогие» запросы (по общему времени выполнения или количеству чтений).
3.  **`pg_stat_user_tables`**: Помогает понять, насколько активно используются индексы и как часто происходит `seq_scan` (полное сканирование таблицы) вместо `index_scan`.
4.  **Внешние APM (New Relic / Blackfire)**: Чтобы понять, где именно затык — в самом SQL, в сетевой задержке или в подготовке данных на стороне PHP.

---

### 2. Процесс диагностики (Step-by-Step)

**Шаг 1: Получение плана выполнения.**
Я запускаю запрос с `EXPLAIN (ANALYZE, BUFFERS)`. Я ищу в выводе три вещи:
*   **Seq Scan**: Если я вижу сканирование всей таблицы вместо использования индекса.
*   **Costly Nodes**: Узлы с самым высоким `actual time` (например, тяжелые `Sort` или `Hash Join`).
*   **Rows mismatch**: Если `rows` в плане сильно отличается от `actual rows`. Это значит, что статистика БД устарела и планировщик строит неверный план.

**Шаг 2: Анализ работы с памятью.**
Смотрю на `Buffers`. Если `Read` (чтение с диска) значительно больше, чем `Hit` (чтение из кэша), значит, либо данных слишком много для текущего `shared_buffers`, либо запрос делает неэффективные случайные прыжки по диску.

**Шаг 3: Проверка статистики.**
Если план выглядит странно, я проверяю актуальность статистики командой `ANALYZE <table_name>`.

---

### 3. Типовые причины и способы решения

Я разделяю их на уровни:

#### А) Проблемы с индексами (Самое частое)
*   **Отсутствие индекса:** Запрос делает `Seq Scan`. 
    *   *Решение:* Создать B-tree индекс.
*   **Неэфновенный индекс (SARGability):** Использование функций над колонкой в `WHERE`.
    *   *Пример:* `WHERE DATE(created_at) = '2023-01-01'` убивает индекс.
    *   *Решение:* Переписать на диапазон: `WHERE created_at >= '2023-01-01' AND created_at < '2023-01-02'`.
*   **Неподходящий тип индекса:** Поиск по тексту через `LIKE '%word%'`.
    *   *Решение:* Использовать `GIN` индекс с расширением `pg_trgm`.
*   **Низкая селективность:** Индекс есть, но планировщик его игнорирует, потому что колонка содержит мало уникальных значений (например, `is_active`).

#### Б) Проблемы структуры запроса
*   **N+1 запросы:** (Уже обсуждали). 
    *   *Решение:* `JOIN FETCH` или сбор данных через `IN (...)`.
*   **Слишком много JOIN-ов:** Приводит к взрывному росту промежуточных данных.
    *   *Решение:* Разбить запрос на два или использовать временные таблицы.
*   **Неоптимальные сортировки (`Sort`):** Если данных много, сортировка может вытесняться из памяти на диск (`External merge Disk`).
    *   *Решение:* Увеличить `work_mem` или добавить индекс, который уже содержит данные в нужном порядке.

#### В  Проблемы конфигурации БД
*   **Малый `work_mem`:** Сортировки и Join-ы тормозят, так как постоянно пишут во временные файлы на диске.
*   **Малый `shared_buffers`:** Слишком много чтений с диска.
*   **Устаревшая статистика:** Планировщик выбирает плохой план.
    *   *Решение:* Регулярный `autovacuum` и `analyze`.

---

### Мой алгоритм действий (Резюме):
1.  **Найти** медленный запрос через `pg_stat_statements`.
2.  **Понять**, почему он медленный, через `EXPLAIN ANALYZE`.
3.  **Если это сканирование таблицы** $\rightarrow$ добавить индекс или переписать `WHERE` (SARGability).
4.  **Если это тяжелый Join/Sort** $\rightarrow$ проверить `work_mem` или переписать запрос.
5.  **Если это много мелких запросов** $\rightarrow$ оптимизировать ORM (N+1).
6.  **Проверить**, не помогает ли `ANALYZE`.
7.  **Замерить результат** после изменений.

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

В Domain-Driven Design (DDD) **Агрегат (Aggregate)** — это кластер связанных объектов (сущностей и Value Objects), которые рассматриваются как единое целое для обеспечения **целостности данных (Invariants)**.

Если говорить проще: Агрегат — это граница, внутри которой бизнес-правила (инварианты) всегда должны выполняться атомарно.

### 1. Как определять границы агрегата?

Границы агрегата определяются не тем, что «логично сгруппировать», а тем, **какие правила должны соблюдаться одновременно**.

При поиске границ я задаю себе три вопроса:
1.  **Какие правила требуют атомарности?** (Если я изменю А, должен ли я немедленно изменить Б, чтобы система осталась валидной?)
2.  **Какова минимальная единица транзакции?** (Что должно быть сохранено в БД за один `commit`?)
3.  **Как объекты взаимодействуют друг с другом?** (Нужно ли мне знать внутреннее состояние объекта Б, чтобы выполнить операцию в объекте А?)

**Главное правило:** Внутри агрегата изменения происходят мгновенно и синхронно. Между разными агрегатами — через **доменные события (Domain Events)** или **Eventual Consistency** (согласованность в конечном счете).

---

### 2. Пример: Система заказа (E-commerce)

Представим процесс оформления заказа. У нас есть `Order` (Заказ), `OrderItem` (Позиция заказа) и `Product` (Товар).

#### Правильный подход:
**Агрегат: `Order`**
*   **Корень (Root):** `Order`.
*   **Внутри агрегата:** `OrderItem` (Entity) и `Money` (Value Object).
*   **Инвариант:** "Общая сумма заказа не может быть отрицательной" и "Количество позиций не может быть нулевым при переходе в статус 'Оплачен'".

**Почему `Product` — не часть агрегата `Order`?**
Товар существует сам по себе. Если мы изменим цену товара, заказ не должен измениться магическим образом (заказ фиксирует цену на момент покупки). Если мы сделаем `Product` частью агрегата `Order`, то при изменении описания товара нам придется пересоздавать все заказы, где он участвует. Это нарушение границ.

**Как это работает:**
*   Вы взаимодействуете только с `Order`.
*   Чтобы добавить товар, вы вызываете `$order->addItem($productId, $quantity)`.
*   `Order` сам находит цену товара (через доменный сервис) и создает внутри себя `OrderItem`.

---

### 3. Типовая ошибка: «Слишком большой агрегат» (The Fat Aggregate)

Это самая распространенная ошибка. Разработчик пытается включить в агрегат всё, что кажется «связанным».

**Пример ошибки:**
Попытаться включить `Product` в агрегат `Order`.

**Почему это плохо:**
1.  **Конфликты блокировок (Concurrency):** Если два клиента одновременно покупают разные товары, они оба попытаются заблокировать (Lock) один и тот же агрегат `Order` (если бы он включал товары). Это убьет производительность.
2. much **Нарушение инкапсуляции:** Агрегат становится слишком тяжелым. Чтобы просто проверить статус заказа, вам придется подгружать из базы дерево всех товаров, их описаний, остатков на складах и т.д.
3.  **Трудности с масштабированием:** Вы не сможете легко разнести заказы и товары по разным микросервисам, так как они связаны жесткой связью в рамках одной транзакции.

**Признак ошибки:** Если для изменения одного маленького поля вам приходится загружать из базы огромный граф объектов — ваш агрегат слишком велик.

---

### Резюме: Золотые правила границ

1.  **Маленькие агрегаты лучше больших.** Лучше иметь два маленьких агрегата, связанных через ID и события, чем один гигантский.
2.  **Ссылайтесь на другие агрегаты только по ID.** Не держите объект другого агрегата внутри себя как прямую ссылку (Entity Reference). Используйте `productId`, а не `Product $product`.
3.  **Соблюдайте инварианты.** Если правило требует, чтобы два объекта всегда были синхронны (например, `Balance` и `TransactionHistory`), они должны быть в одном агрегате. Если они могут быть синхронизированы с задержкой в 1 секунду — разделите их.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

Это классическая проблема конкурентного доступа (Race Condition). Если два процесса одновременно прочитают агрегат, изменят его в памяти и попытаются сохранить, возникнет ситуация **"Lost Update"** (потерянное обновление): тот, кто сохранит вторым, просто перезапишет изменения первого, и данные первого процесса будут безвозвратно утеряны.

В проектировании я рассматриваю три стратегии решения, выбирая подходящую в зависимости от требований к производительности и консистентности.

---

### 1. Оптимистичная блокировка (Optimistic Locking) — мой основной выбор

Это подход, основанный на предположении, что конфликты случаются редко. Мы не блокируем базу данных, а просто проверяем, не изменился ли объект, пока мы с ним работали.

**Как это работает:**
В таблицу агрегата добавляется специальная колонка `version` (integer).

1.  **Процесс А** читает `Order` (version = 1).
2.  **Процесс Б** читает `Order` (version = 1).
3.  **Процесс А** меняет статус на `Paid` и делает `UPDATE ... SET status='paid', version=2 WHERE id=1 AND version=1`. Успешно.
4.  **Процесс Б** меняет количество товаров и делает `UPDATE ... SET quantity=5, version=2 WHERE id=1 AND version=1`.
5.  **Результат:** БД вернет `0 rows affected`, потому что `version` уже равна 2. Doctrine выбросит `OptimisticLockException`.

**Плюсы:**
*   Максимальная производительность (нет реальных блокировок в БД).
*   Отлично подходит для веб-приложений с высокой нагрузкой.

**Минусы:**
*   Нужно обрабатывать исключение на уровне приложения (например, просить пользователя обновить страницу или делать автоматический retry).

---

### 2. Пессимистичная блокировка (Pessimistic Locking)

Этот подход используется, когда конфликты происходят часто или когда цена ошибки слишком высока (например, в банковских транзакциях).

**Как это работает:**
Мы используем механизмы БД (`SELECT ... FOR UPDATE`), чтобы заблокировать строку на уровне базы данных с момента чтения до момента завершения транзакции.

1.  **Процесс А** делает `SELECT ... FOR UPDATE`. БД ставит блокировку на строку.
2.  **Процесс Б** пытается сделать такой же `SELECT ... FOR UPDATE`, но база заставляет его **ждать**, пока Процесс А не сделает `COMMIT` или `ROLLBACK`.
3.  **Процесс А** завершает работу.
4.  **Процесс Б** "просыпается", читает уже обновленные данные и продолжает работу.

**Плюсы:**
*   Гарантированная консистентность.
*   Процесс не падает с ошибкой, а просто ждет.

**Минусы:**
*   **Риск Deadlocks:** Если два процесса заблокируют разные ресурсы в разном порядке, они могут заблокировать друг друга навсегда.
*   **Низкая масштабируемость:** Пока строка заблокирована, другие процессы простаивают. Это может привести к исчерпанию пула соединений к БД.

---

### 3. Дизайн через событийную консистентность (Eventual Consistency)

Если конфликты происходят постоянно, это признак того, что **агрегат слишком большой**. Вместо того чтобы пытаться защитить его одним огромным замком, я перепроектирую систему.

**Как это работает:**
Я разбиваю один большой агрегат на несколько маленьких. Вместо того чтобы менять состояние одного объекта, процессы генерируют **команды** или **события**, которые обрабатываются последовательно через очередь (Messenger).

**Пример:** Вместо изменения баланса пользователя в одном агрегате, я создаю записи о транзакциях (Immutable Ledger). Баланс — это просто сумма всех записей. Записи добавляются без конфликтов, так как они только `INSERT`, а не `UPDATE` старой строки.

---

### Мой алгоритм выбора:

1.  **Если конфликты редкие (99% случаев):** Использую **Optimistic Locking** (`version` column). Это стандарт для большинства бизнес-приложений.
2.  **Если критически важно избежать ошибок без переповторов (финансы):** Использую **Pessimistic Locking** (`FOR UPDATE`), но строго ограничиваю время жизни транзакции.
3.  **Если конфликты — это норма (высоконагруженные системы):** Я пересматриваю границы агрегата и ухожу в сторону **Event Sourcing** или **Command Sourcing**, чтобы превратить `UPDATE` в серию `INSERT` событий.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

Доменные события (**Domain Events**) — это мощный инструмент для реализации слабой связанности (loose coupling). Они позволяют объектам сообщать о том, что в их мире произошло что-то значимое, не зная о том, кто на это отреагирует.

### 1. Когда публиковать события?
Событие должно публиковаться **только тогда, когда агрегат перешел в новое, валидное состояние**.

**Правило:** Событие — это не "команда к действию", а "факт, который уже случился". 
*   **Плохо:** `OrderWasCreatedEvent` (публикуется до того, как транзакция зафиксирована).
*   **Хорошо:** `OrderPaidEvent` (публикуется внутри метода агрегата после изменения его внутреннего состояния).

**Техническая реализация:** Я не публикую событие мгновенно через шину (Messenger) внутри метода агрегата. Вместо этого агрегат накапливает события в своей внутренней коллекции (массив `$events`), а публикация происходит **после** успешного завершения транзакции в Application Service.

---

### 2. Как обрабатывать события?

Я разделяю обработчики на два типа в зависимости от их природы:

1.  **Внутрипроцессные (In-Memory/Synchronous):** Обработчики, которые выполняются в том же потоке и в той же транзакции. Используются для поддержанных инвариантов внутри одного контекста.
2.  **Внешние (Asynchronous/Out-of-process):** Обработчики, которые запускаются через очередь (RabbitMQ/Redis). Они используются для связи между агрегатами или между микросервисами (например, отправка Email, обновление индекса поиска).

---

### 3. Связь с транзакциями (Проблема "Dual Write")

Это самая тонкая часть. Возникает риск: **мы сохранили данные в БД, но упали до того, как отправили событие в очередь.** Или наоборот: событие ушло, а транзакция в БД откатилась.

Чтобы избежать этого, я использую один из двух подходов:

#### А) Transactional Outbox Pattern (Самый надежный)
Вместо прямой отправки в RabbitMQ, я записываю событие в специальную таблицу `outbox` **в той же транзакции**, что и изменения агрегата.
1.  `BEGIN TRANSACTION`
2.  `UPDATE orders SET status = 'paid' ...`
3.  `INSERT INTO outbox (event_type, payload) VALUES ('OrderPaid', '{...}')`
4.  `COMMIT`
5.  Отдельный процесс (Relay) читает таблицу `outbox` и перекладывает сообщения в RabbitMQ.

**Результат:** Гарантированная доставка (At-least-once delivery).

#### Б) Post-Commit Dispatching (Проще)
Я использую механизм, который гарантирует, что `Messenger->dispatch()` вызовется только **после успешного COMMIT** транзакции в БД. В Symfony это можно реализовать через `DoctrineTransactionMiddleware` или кастомный слушатель событий `onFlush`/`postFlush`.

---

### 4. Плюсы и минусы

#### Какие проблемы решает:
*   **Слабая связанность (Decoupling):** `OrderService` не должен знать о `EmailService` или `SearchIndexer`. Он просто говорит: "Заказ оплачен".
*   **Соблюдение SRP:** Логика отправки писем выносится из основного бизнес-процесса.
*   **Масштабируемость:** Мы можем вынести тяжелые задачи (генерация PDF, интеграция с API) в отдельные воркеры.

#### Какие проблемы создаёт:
*   **Eventual Consistency (Согласованность в конечном счете):** Система перестает быть мгновенно согласованной. Пользователь может нажать "Оплатить", получить ответ "Ок", но статус в поиске обновится только через 2 секунды. Это требует изменения UX (скелетоны, уведомления "обновляем...").
*   **Сложность отладки:** Путь выполнения запроса становится нелинейным. Трудно проследить цепочку: "Событие А $\rightarrow$ Обработчик Б $\rightarrow$ Событие В".
*   **Риск дублирования (Idempotency):** Из-за особенностей сетей и стратегии "At-least-once", обработчик может получить одно и то же событие дважды.
    *   *Решение:* Все обработчики **должны быть идемпотентными** (повторный вызов с тем же ID события не должен приводить к дублированию действий, например, двойному списанию денег).

### Итоговый принцип:
Используйте события для **связи между контекстами**, но всегда помните про **идемпотентность** и **атомарность записи события вместе с данными**.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

Это фундаментальные вопросы, которые отделяют «просто программирование» от «проектирования предметной области».

### 1. Entity vs Value Object

Главное различие заключается в том, **как мы определяем идентичность объекта**.

| Характеристика | Entity (Сущность) | Value Object (Объект-значение) |
| :---    | :--- | :--- |
| **Идентичность** | Определяется уникальным ID, который не меняется. | Определяется набором своих свойств (значений). |
| **Жизненный цикл** | Имеет историю изменений. Объект может меняться, оставаясь тем же самым. | Неизменяем (Immutable). Если нужно изменить — создаем новый объект. |
| **Сравнение** | `A === B`, если у них одинаковые ID. | `A === B`, если все их поля идентичны. |
| **Пример** | `User` (ID 1), `Order` (ID 500). | `Money(100, 'USD')`, `Address`, `Email`. |

**Пример для наглядности:**
Два пользователя с одинаковыми именами и датами рождения — это **разные** сущности (у них разные ID). Но две купюры по 100 рублей — это **одинаковые** Value Objects (их ценность и свойства идентичны, нам не важно, какая именно это купюра).

---

### 2. Как я принимаю решение: что есть что?

Когда я проектирую новую концепцию, я задаю себе следующие вопросы:

1.  **Есть ли у этого объекта жизненный цикл?** Если объект проходит через состояния (`New` $\rightarrow$ `Active` $\rightarrow$ `Archived`), это **Entity**.
2.  **Важна ли мне уникальность в рамках системы?** Если я могу отличить два объекта только по ID, это **Entity**. Если я могу отличить их только по составу полей — это **Value Object**.
3.  **Могу ли я менять его свойства?** Если изменение свойства (например, смена города в адресе) означает создание "нового" понятия — это **Value Object**. Если изменение свойства (например, смена фамилии пользователя) — это модификация того же самого человека — это **Entity**.

**Мой чек-лист при проектировании:**
*   Если это просто набор атрибутов $\rightarrow$ **Value Object**.
*   Если это "субъект" действия $\rightarrow$ **Entity**.
*   Если это описание состояния $\rightarrow$ **Value Object**.

### 3. Единый язык (Ubiquitous Language)

**Ub ubiquitous language** — это общий язык, который используют разработчики, эксперты предметной области (Domain Experts), менеджеры и аналитики. Это не "сленг программистов", а терминология, которую используют люди, решающие бизнес-задачи.

#### Как он влияет на код?

В классическом подходе (Anemic Domain Model) код выглядит так:
`$order->setStatus(OrderStatus::PAID);` — это техническое действие.

В DDD, благодаря Ubiquitous Language, код выглядит как **описание бизнес-процесса**:
`$order->markAsPaid();` — это доменное действие.

**Влияние на проектирование:**

1.  **Имена классов и методов:** Если бизнес говорит: "Мы *подтверждаем* заказ", то в коде должен быть метод `confirm()`, а не `updateStatus(1)`.
2.  **Устранение ментального перевода:** Разработчик не должен в голове переводить "бизнес-термин" в "название таблицы" или "название метода". Код должен читаться как текст на языке бизнеса.
3.  **Снижение риска ошибок:** Когда терминология в коде и в требованиях совпадает, риск того, что разработчик неверно понял суть процесса, сводится к минимуму.

#### Как я внедряю Ubiquitous Language:
*   **Активное слушание:** На встречах с бизнесом я записываю не только "что нужно сделать", а именно те слова и термины, которые они используют.
*   **Рефакторинг имен:** Если я вижу, что в коде метод называется `process()`, а бизнес называет это `validateShipment()`, я немедленно переименовываю метод.
*   **Словарь (Glossary):** В сложных проектах я поддерживаю небольшой документ (или Wiki), где зафиксированы определения ключевых терминов, чтобы у всех участников процесса было единое понимание.

**Итог:** Ubiquitous Language превращает код из "инструкции для машины" в "документацию бизнес-логики", которую может понять даже не технический специалист.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

Чистая архитектура (Clean Architecture) в PHP-приложении строится вокруг идеи **инверсии зависимостей**. Главная цель — сделать ядро приложения (бизнес-логику) независимым от внешнего мира (БД, фреймворка, API, очереди).

### 1. Слои архитектуры

Я разделяю приложение на четыре основных слоя.

#### А) Domain Layer (Ядро / Домен)
Это самый внутренний слой. Он не знает ни о чем, кроме правил бизнеса.
*   **Что внутри:** Entities (Агрегаты), Value Objects, Domain Exceptions, Domain Services (если логика не влезает в сущность), Domain Events.
*   **Зависимости:** **Ни от кого**. Этот слой не должен импортировать ничего из Symfony, Doctrine или сторонних библиотек (кроме базовых типов PHP).

#### Б) Application Layer (Слой приложения / Use Cases)
Этот слой оркестрирует выполнение конкретных задач пользователя.
*   **Что внутри:** Use Case классы (или Command Handlers), DTO (Data Transfer Objects), интерфейсы репозиториев (Repository Interfaces).
*   **Зависимости:** Только от **Domain Layer**. Он знает, *что* нужно сделать, но не знает, *как* данные сохраняются.

#### В) Infrastructure Layer (Слой инфраструктуры)
Слой реализации деталей. Здесь живет всё, что касается "внешнего мира".
*   **Что внутри:** Реализации репозиториев (Doctrine), клиенты API (Guzzle), отправка почты (Mailer), работа с очередями, реализация интерфейсов из Application слоя.
*   **Зависимости:** От **Application Layer** и **Domain Layer**.

#### Г) Presentation / UI Layer (Слой представления)
Точка входа в приложение.
*   **Что внутри:** Symfony Controllers, CLI Commands, API Resources (JSON/XML).
*   **Зависимости:** От **Application Layer**. Контроллер не должен содержать бизнес-логику, он только принимает запрос, вызывает Use Case и возвращает ответ.

---

led
### 2. Правило зависимостей (Dependency Rule)

**Зависимости всегда направлены внутрь, к центру (к Domain).**

*   `Presentation` $\rightarrow$ `Application` $\rightarrow$ `Domain`
*   `Infrastructure` $\rightarrow$ `Application` $\rightarrow$ `Domain`

**Никогда** не должно быть зависимости: `Domain` $\rightarrow$ `Infrastructure`. 
*Например: Ваш `User` (Entity) не должен иметь аннотацию `#[ORM\Entity]`, если вы хотите абсолютной чистоты. Но на практике в PHP часто допускают "грязный" Domain, где Entity помечены атрибутами Doctrine, чтобы не писать сложные маппинги. Это компромисс между чистотой и скоростью разработки.*

---

### 3. Куда попадут компоненты?

| Компонент | Слой | Почему? |
| :--- | :--- | :--- |
| **Symfony Controller** | **Presentation** | Это интерфейс взаимодействия с HTTP-протоколом. |
| **Doctrine Entity/Repository** | **Infrastructure** | Это деталь реализации хранения данных. Интерфейс репозитория — в Application, реализация — в Infrastructure. |
| **Message Handler (Queue)** | **Infrastructure** | Это механизм доставки сообщения. Сам Handler вызывает Use Case из Application слоя. |

---

### 4. Как следить за границами слоёв?

Соблюдать границы "силой воли" невозможно, нужны инструменты.

1.  **Статический анализ (PHPStan / Psalm):** 
    Я настраиваю правила, которые запрещают использование определенных пространств имен в определенных директориях. Например, запретить использование `App\Infrastructure\*` внутри `App\Domain\*`.

2.  **Архитектурные тесты (Deptrac):**
    Это специализированный инструмент для PHP, который позволяет описать слои и правила зависимостей в YAML-файле. При запуске тестов Deptrac проверит, не импортировал ли кто-то `Doctrine` в `Domain`. Если нарушение есть — билд упадет.

3.  **Code Review:** 
    Это последний и самый важный рубеж. На ревью я смотрю не только на алгоритмы, но и на импорты (`use` statements) в начале файла. Если я вижу в Domain-классе `use Symfony\Component\...`, я сразу отклоняю PR.

4.  **Dependency Injection (DI) Container:**
    Правильное использование DI гарантирует, что слои не знают друг о друге. Мы внедряем `UserRepositoryInterface` (из Application), а контейтнер подставляет `DoctrineUserRepository` (из Infrastructure). Это позволяет менять реализацию, не трогая бизнес-логику.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

Для Symfony-приложения я придерживаюсь классической **Пирамиды Тестирования**, но с учетом специфики веб-разработки. Главная цель — найти баланс между уверенностью в коде и скоростью обратной связи (feedback loop).

### 1. Пирамида тестов в моем исполнении

#### **A. Unit Tests (Основание — 70-80%)**
Это тесты на изоляции. Мы тестируем чистую логику без обращения к БД или сети.
*   **Что тестируем:** Value Objects, Domain Entities (их методы), Domain Services, простые Utility-классы.
*   **Что мокаем:** Вообще всё, что не является частью тестируемого объекта.
*   **Инструмент:** `PHPUnit`.
*   **Цель:** Проверить все граничные условия и сложные алгоритмы максимально быстро.

#### **Б. Integration Tests (Середина — 15-20%)**
Здесь мы проверяем, как наши компоненты работают вместе.
*   **Что тестируем:** Репозитории (взаимодействие с БД), взаимодействие сервисов, работу с файловой системой или кэшем.
*   **Что мокаем:** Внешние API (через `MockHttpClient`), но **не мокаем базу данных**.
*   **Инструмент:** `PHPUnit` + реальная база данных (PostgreSQL) в Docker.
*   **Цель:** Убедиться, что SQL-запросы верны и интеграция с БД работает.

#### **В. Functional / API Tests (Вершина — 5-10%)**
Проверка всего пути запроса от контроллера до БД.
*   **Что тестируем:** Контроллеры, обработку HTTP-запросов, работу Middleware, Security (права доступа), работу очереди (через синхронный транспорт).
*   **Что мокаем:** Внешние сервисы (платежные шлюзы, почтовые сервера).
*   **Инструмент:** `Symfony WebTestCase` (BrowserKit).
*   **Цель:** Проверить, что "склеенное" приложение работает как единое целое.

---

### 2. Что мокать, а что нет? (Золотое правило)

Моя стратегия: **Мокаем внешние границы, не мокаем внутренние компоненты.**

*   **МОКАЕМ (Mock/Stub):**
    *   Внешние HTTP-сервисы (API сторонних компаний).
    *   Почтовые серверы (чтобы не спамить).
    *   Системы очередей (если мы не тестируем сам механизм доставки).
    *   *Важно:* Я использую `MockHttpClient` в Symfony, чтобы имитировать ответы внешних API без реальных сетевых вызовов.

*   **НЕ МОКАЕМ:**
    *   **Базу данных (PostgreSQL).** Использование моков для репозиториев — это путь к "тестам, которые проходят, но код падает в проде". Я использую реальную БД в Docker.
    *   **Value Objects и Entities.** Это часть доменной модели, их нужно проверять реально.
    *   **Внутренние доменные сервисы.** Если мы тестируем Use Case, мы должны использовать реальные сервисы, чтобы проверить интеграцию логики.

---

### 3. Как поддерживать тесты быстрыми и стабильными?

Медленные тесты — это тесты, которые перестают запускать. Я борюсь с этим так:

#### **Для скорости:**
1.  **Database Isolation (Transactions):** Для интеграционных и функциональных тестов я использую паттерн "тестовая транзакция". Каждый тест оборачивается в транзакцию, которая откатывается (`rollback`) в конце теста. Это в разы быстрее, чем `TRUNCATE` или `DROP/CREATE` таблиц перед каждым тестом.
2.  **Parallel Testing:** Использование `Paratest` для запуска тестов в несколько потоков.
3.  **Memory DB (для простых случаев):** Если проект позволяет, для некоторых тестов можно использовать SQLite в памяти, но для PostgreSQL-специфичных функций (JSONB, полнотекстовый поиск) я всегда использую настоящий Postgres в Docker.

#### **Для стабильности (Flakiness prevention):**
1.  **Deterministic Data:** Я не использую `rand()` или текущее время `now()` внутри тестов. Я всегда использую фиксированные даты (через `ClockInterface` в PHP 8.3+) и предсказуемые фабрики данных.
2.  **Data Builders / Factories:** Вместо того чтобы вручную создавать объекты, я использую **AliceBundle** или **FactoryMuffin**. Это гарантирует, что каждый тест получает чистый, валидный набор данных.
3.  **Изоляция окружения:** Каждый запуск тестов должен происходить в чистом Docker-контейнере с идентичной конфигурацией БД и PHP.
4.  **Idempotency в тестах:** Каждый тест должен быть независимым. Результат теста А не должен влиять на тест Б.

**Мой девиз:** "Тест должен быть быстрым как Unit, но надежным как Integration".

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Это классическая проблема конкурентного доступа в многопользовательских системах. Если два процесса прочитают состояние объекта, изменят его в памяти и попытаются записать обратно, возникнет ситуация **"Lost Update" (Потерянное обновление)**: изменения первого пользователя будут просто перезаписаны изменениями второго, и данные первого процесса будут потеряны.

Я разделяю способы защиты на три основные стратегии: **Оптимистичную**, **Пессимистичную** и **Конфликтную (через архитектуру)**.

---

### 1. Оптимистичная блокировка (Optimistic Locking)
Мы предполагаем, что конфликты случаются редко. Мы не блокируем запись, а проверяем версию объекта в момент сохранения.

**Механизм:**
В таблицу добавляется колонка `version` (integer).
1. Процесс А читает запись (`version = 5`).
2. Процесс Б читает ту же запись (`version = 5`).
3. Процесс А сохраняет изменения: `UPDATE ... SET ..., version = 6 WHERE id = 1 AND version = 5`. Успех.
4. Процесс Б пытается сохранить: `UPDATE ... SET ..., version = 6 WHERE id = 1 AND version = 5`.
5. **Результат:** БД возвращает `0 rows affected`, так как `version` уже стала `6`. Doctrine выбрасывает `OptimisticLockException`.

**Trade-offs:**
*   **Плюсы:** Максимальная производительность, отсутствие блокировок (deadlocks), отлично масштабируется.
*   **Минусы:** При конфликте пользователю нужно либо повторить действие, либо разрешить ручное слияние изменений.

---

### 2. Пессимистичная блокировка (Pessimistic Locking)
Мы исходим из того, что конфликт неизбежен. Мы блокируем строку в БД в момент чтения, чтобы никто другой не мог даже начать работу с ней.

**Механизм:**
Использование SQL-команды `SELECT ... FOR UPDATE`.
1. Процесс А читает запись с `FOR UPDATE`. БД ставит эксклюзивную блокировку.
2. Процесс Б пытается прочитать ту же запись с `FOR UPDATE`. БД заставляет его **ждать** (он зависает на этом запросе).
3. Процесс А завершает транзакцию (`COMMIT`). Блокировка снимается.
4. Процесс Б получает данные, которые уже обновил Процесс А, и продолжает работу.

**Trade-offs:**
*   **Плюсы:** Гарантированная целостность, пользователь не получает ошибок "попробуйте еще раз", всё происходит прозрачно.
*   **Минусы:** 
    *   **Низкая производительность:** Другие процессы стоят в очереди.
    *   **Риск Deadlocks:** Если два процесса заблокируют разные строки в разном порядке, они заблокируют друг друга навсегда.
    *   **Риск исчерпания ресурсов:** Если транзакции долгие, пул соединений к БД быстро закончится.

---

### 3. Конфликтная стратегия (Архитектурная/Eventual Consistency)
Если конфликты происходят постоянно (например, при массовом обновлении остатков на складе), блокировки не помогут — система просто встанет. В этом случае я меняю саму модель данных.

**Механизм:**
Вместо одного поля `balance` (которое мы постоянно обновляем), я использую **Immutable Ledger (Журнал операций)**.
*   Вместо `UPDATE accounts SET balance = balance - 10` я делаю `INSERT INTO transactions (account_id, amount) VALUES (1, -10)`.
*   Текущий баланс — это сумма всех записей.

**Trade-offs:**
*   **Плюсы:** Никаких блокировок на `UPDATE`, никакой потери данных, идеальный аудит.
*   **Минусы:** Сложность чтения (нужно агрегировать данные), необходимость использования Materialized Views или кэширования для быстрого получения текущего баланса.

---

### Итоговая сравнительная таблица и мой выбор

| Критерий | Optimistic Locking | Pessimistic Locking | Immutable Ledger |
| :--- | :--- | :--- | :--- |
| **Когда применять** | Редкие конфликты, высокая нагрузка. | Редкие, но критичные конфликты (финансы). | Постоянные конфликты (высокий нагруз). |
| **Производительность** | Высокая | Низкая | Очень высокая (на запись) |
| **Сложность кода** | Средняя (обработка исключений) | Низкая (на уровне БД) | Высокая (новая модель данных) |
| **UX** | "Ошибка, попробуйте снова" | "Загрузка..." (ожидание) | "Ваша операция в очереди" |

**Мой выбор:**
1.  Для **90% веб-приложений** (админки, профили, заказы) — **Optimistic Locking**. Это стандарт индустрии.
2.  Для **критичных финансовых операций** (перевод денег между счетами) — **Pessimistic Locking** на очень короткий период.
3.  Для **высоконагруженных счетчиков/балансов** (биржи, системы лояльности) — **Immutable Ledger** (Append-only).

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

Мой процесс работы с Git строится вокруг принципа **стабильности основной ветки** и **максимальной прозрачности изменений**. Я не сторонник хаотичного коммита в `main`. Мой стандарт — это использование **GitFlow** (или его облегченной версии **GitHub Flow**) в сочетании с жестким процессом Code Review.

Вот как выглядит мой жизненный цикл задачи:

### 1. Ветвление (Branching Strategy)
Я использую модель, где `main` всегда представляет собой стабильный, готовый к релизу код.

*   **`main`**: Только стабильный код, который сейчас на продакшене.
*   **`develop`**: Интеграционная ветка. Сюда сливаются все завершенные задачи перед релизом.
*   **`feature/TASK-123-description`**: Ветки для новых фич. Название всегда содержит ID задачи из Jira/YouTrack.
*   **`bugfix/TASK-123-description`**: Ветки для исправления багов.
*   **`hotfix/issue-name`**: Ветки для критических исправлений на `main`.

**Почему так?** Это разделяет "рабочую грязь" (фичи в разработке) и "стабильный продукт". Разработчик никогда не мешает коллеге, работая в своей ветке.

---

### 2. Коммиты (Commit Messages)
Я придерживаюсь стандарта **Conventional Commats**. Это делает историю понятной и позволяет автоматизировать генерацию Changelog.

**Формат:** `<type>(<scope>): <description>`

*   `feat:` — новая функциональность.
*   `fix:` — исправление ошибки.
*   `refactor:` — изменение кода, не меняющее логику.
*   `test:` — добавление тестов.
*   `docs:` — изменение документации.
*   `chore:` — обновление зависимостей, конфигов (не касающихся бизнес-логики).

**Пример:** `feat(order): add validation for discount code application`

**Почему так?** Это превращает `git log` в читаемую историю изменений. Если через полгода нужно будет найти, когда изменилась логика скидок, я сделаю `git log --grep="feat(order)"` и мгновенно найду нужный коммит.

---

### 3. Pull Request (PR) и Code Review
PR — это не просто "просьба влить код", это инструмент обмена знаниями.

**Мой процесс создания PR:**
1.  **Self-Review:** Перед тем как позвать коллег, я сам просматриваю свой Diff. Это позволяет убрать забытые `dd()`, `var_dump()` и лишние комментарии.
2.  **Описание:** В описании PR я всегда указываю:
    *   **Что сделано** (краткое резюме).
    *   **Зачем это сделано** (ссылка на задачу).
    *   **Как протестировать** (step-by-step инструкции для ревьюера).
    *   **Риски** (на что обратить внимание).

**Процесс ревью:**
*   Я ожидаю минимум одного одобрения (`Approve`) от коллеги.
*   **Критерии ревью:** не только "работает/не работает", но и соблюдение архитектуры (SOLID, Clean Architecture), читаемость имен, покрытие тестами и отсутствие утечек памяти.
*   **Общение:** Критика должна быть конструктивной. Вместо "Это плохо", я пишу "Как ты думаешь, не приведет ли этот подход к проблеме N+1 в будущем?".

---

### 4. Релизы (Releases)
Когда ветка `develop` накапливает достаточно изменений, происходит релиз.

1.  **Release Branch:** Создается ветка `release/v1.2.0`. Здесь проводятся финальные тесты (QA, Smoke tests).
2.  **Merge to Main:** После успешных тестов `release` сливается в `main` с тегом (Git Tag).
3.  **Back-merge:** `main` сливается обратно в `develop`, чтобы все последующие фичи базировались на релизном коде.
4.  **Deployment:** Из `main` код деплоится на продакшен.

**Почему так?** Это позволяет изолировать процесс подготовки релиза. Если в процессе тестирования `release`-ветки найдется баг, мы правим его в ней, не блокируя работу других разработчиков в `develop`.

---

### Резюме: Почему мой процесс именно такой?

*   **Предсказуемость:** Любой член команды понимает, где находится код и что он делает.
*   **Безопасность:** Запрет на прямой пуш в `main` и обязательный Review минимизируют риск "сломать продакшен".
*   **Прослеживаемость (Traceability):** Благодаря Conventional Commits и привязке к ID задач, мы всегда можем понять контекст любого изменения.
*   **Масштабируемость:** Такая структура позволяет команде расти с 3 до 30 человек без хаоса в репозитории.

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

Для меня Code Review — это не «экзамен» и не поиск ошибок, а **инструмент обеспечения качества и обмена знаниями**. Хороший ревью помогает команде расти, а не превращается в инструмент подавления или токсичности.

Вот как я выстраиваю этот процесс:

### 1. На что я смотрю в первую очередь (Приоритеты)

Я разделяю замечания на три уровня важности, чтобы не перегружать автора мелкими придирками.

**Уровень 1: Критические ошибки (Blockers)**
Это то, что нельзя пропускать в продакшен.
*   **Нарушение бизнес-логики:** Код делает не то, что требует задача.
*   **Безопасность:** SQL-инъекции, отсутствие проверки прав доступа, утечка чувствительных данных.
*   **Производительность:** Проблемы N+1, тяжелые циклы, отсутствие индексов, утечки памяти.
*   **Нарушение архитектуры:** Нарушение границ слоев (например, Entity обращается к Repository), нарушение принципов SOLID.
*   **Ошибки надежности:** Отсутствие обработки исключений там, где они неизбежны, или «проглатывание» ошибок.

**Уровень 2: Качество и поддерживаемость (Suggestions)**
То, что не сломает систему прямо сейчас, но создаст проблемы в будущем.
*   **Чистота кода:** Плохие имена переменных, слишком длинные методы (нарушение SRP), избыточная вложенность.
*   **Тестируемость:** Сложно ли протестировать этот код? Можно ли его легко переиспользовать?
*   **Стиль:** Несоответствие принятому в команде стандарту (PSR).

**Уровень 3: Мелочи (Nitpicks)**
*   Опечатки в комментариях, лишние пробелы, стиль именования, который «просто не нравится».

---

### 2. Как я маркирую замечания

Чтобы автор понимал серьезность моих слов, я использую префиксы. Это избавляет от двусмысленности и эмоционального напряжения.

*   **`[BLOCKER]`** — Критическая ошибка. PR не может быть принят, пока это не будет исправлено.
*   **`[QUESTION]`** — Я не уверен, что здесь всё верно. Прошу автора объяснить логику (возможно, я чего-то не понимаю).
*   **`[SUGGESTION]`** — Предложение по улучшению. Это не обязательно делать, но стоит обдумать.
*   **`[NITPICK]`** — Мелочь. Можно проигнорировать, если автор не хочет тратить время. Не блокирует PR.
*   **`[PRAISE]`** — Обязательно! Если я вижу изящное решение или отличный подход, я пишу об этом. Это поддерживает мотивацию.

---

### 3. Как поступать при разногласиях

Разногласия — это нормальная часть процесса. Моя цель — найти **лучшее техническое решение**, а не доказать свою правоту.

**Мой алгоритм действий:**

1.  **Сначала — аргументация через «Почему»:** Я никогда не говорю «сделай так». Я говорю: «Если мы сделаем это через цикл, то при росте таблицы до 10к записей мы получим проблему N+1. Что ты об этом думаешь?». Я апеллирую к принципам (SOLID, производительность, надежность).
2.  **Если аргументы не принимаются:**
    *   Если это вопрос стиля или «вкусовщины» — я **отступаю**. Если код работает, он чистый и не нарушает архитектуру, я не буду тратить время команды на споры о названиях.
    *   Если это вопрос архитектуры или безопасности — я предлагаю **дискуссию в офлайне** (созвон или живое обсуждение). В комментариях к PR легко запутаться и начать конфликтовать.
3.  **Escalation (Эскалация):** Если мы зашли в тупик и не можем договориться, я предлагаю привлечь третьего человека (Team Lead или Tech Lead) в качестве арбитра. Мы выносим спор на обсуждение команды, чтобы выработать единый стандарт.

**Главное правило:** Мы критикуем **код**, а не **автора**. Я всегда стараюсь сохранять профессиональный и уважительный тон.

## Q22 · Работа с задачами

**Интервьюер:** Ты выполняешь задачу с чёткими критериями приёмки. По ходу работы выясняется: а) нашёл попутный баг, не связанный с задачей; б) понял, что один из критериев приёмки противоречит цели задачи. Что делаешь в каждом случае и почему?

**Кандидат:**

Это классическая ситуация, которая проверяет не только технические навыки, но и профессиональную зрелость (Seniority). Моя стратегия строится на принципе: **«Не усложняй задачу, но не игнорируй риски»**.

---

### Случай А: Нашёл «попутный» баг (Side-effect / Opportunistic bug)

Здесь важно не впасть в ловушку «расширения области видимости» (Scope Creep). Если я начну исправлять всё, что кажется мне некрасивым, я никогда не закончу текущую задачу.

**Мои действия:**

1.  **Оценка критичности:**
    *   Если баг **критический** (data loss, security breach, crash): Я немедленно останавливаюсь и сообщаю об этом. Это приоритет №1. Исправление такого бага может быть вынесено в отдельный экстренный тикет, но работа над текущей задачей может быть приостановлена.
    *   Если баг **незначительный** (UI-глюк, опечатка, неоптимальный код в соседнем методе): Я **не исправляю его в рамках текущей задачи**.

2.  **Регистрация:**
    Я создаю новый тикет (Jira/GitHub Issue) на этот баг, описываю шаги для воспроизведения и прикладываю приоритет.

3.  **Коммуникация:**
    В описании текущего Pull Request я оставляю комментарий: *"В процессе работы обнаружил баг [ссылка на новый тикет]. Он не относится к текущей задаче, но может повлиять на стабильность. Исправлять в этом PR не буду, чтобы не раздувать scope, но зафиксировал"*.

**Почему именно так?**
Исправление «попутных» багов в рамках одной задачи нарушает принцип **атомарности изменений**. Если мой PR будет содержать и фичу, и исправление чужого бага, его будет в три раза сложнее ревьюить. Если мой фикс бага приведет к регрессии, будет невозможно понять, что именно сломалось.

---

### Случай Б: Критерий приёмки противоречит цели задачи

Это ситуация «конфликта требований». Например: *Цель — сделать поиск мгновенным, а критерий — «поддержка сложных полнотекстовых запросов с регулярными выражениями»*.

**Мои действия:**

1.  **Никакой самодеятельности:** Я **никогда** не принимаю решение о нарушении критериев самостоятельно. Это ответственность Product Owner-а или архитектора.
2.  **Сбор доказательств (Evidence-based approach):** Я не просто иду к заказчику с фразой «это не сработает». Я готовлю техническое обоснование:
    *   «Если мы реализуем критерий №3 (сложные Regex), время ответа вырастет с 200 мс до 5 секунд, что противоречит цели (быстрый поиск)».
    *   Я привожу цифры, примеры запросов и показываю альтернативы.
3.  **Предложение альтернатив (Trade-offs):** Вместо того чтобы просто сказать «нет», я предлагаю компромисс:

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

Важное уточнение: в PostgreSQL **не существует прямой команды `FORCE INDEX`**, как это реализовано в MySQL. В MySQL вы можете явно сказать: «Используй этот индекс, несмотря на свои планы». В PostgreSQL управление планом выполнения работает иначе.

Однако концептуально задача «заставить БД использовать конкретный индекс» в PostgreSQL решается через другие механизмы.

### 1. Как это работает в PostgreSQL (Механизмы)

Если планировщик (Query Planner) выбирает неэффективный план (например, делает `Seq Scan` вместо `Index Scan`), у нас есть три пути:

#### А) Настройка стоимости (Cost Constants)
Планировщик выбирает план на основе оценки «стоимости» (cost). Если он не использует индекс, значит, он считает, что чтение индекса будет дороже, чем сканирование всей таблицы. Мы можем подправить параметры сессии, чтобы изменить его «взгляд на мир»:
*   `SET random_page_cost = 1.1;` — по умолчанию в Postgres значение `4.0`. Снижая его, мы говорите планировщику: «Слушай, чтение по случайным адресам (индексу) почти такое же дешевое, как последовательное чтение. Используй индексы чаще».
*   `SET effective_cache_size = '4GB';` — сообщаем планировщику, сколько памяти доступно для кэша, чтобы он понимал, что индекс может целиком поместиться в RAM.

#### Б) Использование расширения `pg_hint_plan`
Если вам действительно нужно поведение как в MySQL (явно указать индекс для конкретного запроса), в PostgreSQL используется расширение `pg_hint_plan`. Оно позволяет добавлять подсказки прямо в SQL-запрос.

```sql
/*+ IndexScan(users user_email_idx) */
SELECT * FROM users WHERE email = 'test@example.com';
```

#### В) Создание функциональных индексов
Часто индекс не используется, потому потому что запрос написан так, что индекс не может быть применен (например, `WHERE UPPER(email) = '...'`). Вмеме того чтобы «заставлять» индекс, мы создаем индекс, который соответствует запросу.

---

### 2. Когда это стоит применять (Use Cases)

Я применяю эти методы только в трех случаях:

1.  **Статистика устарела (Самый частый случай):**
    Если план запроса внезапно изменился на плохой, скорее всего, планировщик опирается на старую статистику.
    *   *Решение:* `ANALYZE <table_name>`. Это не «форсирование», это восстановление нормальной работы планировщика.

2.  **Неправильные параметры конфигурации:**
    Если база работает на SSD, а настройки `random_page_cost` остались от старых HDD.
    *   *Решение:* Настройка параметров сервера под современное железо.

3.  **Специфические сложные запросы:**
    Когда планировщик «тупит» на очень сложном запросе с множеством джойнов и подзапросов, выбирая неверный порядок объединения.
    *   *Решение:* Использование `pg_hint_plan` или переписывание запроса (например, использование CTE или подзапросов).

---

### 3. Почему нельзя использовать "Force" постоянно?

Использование подсказок (hints) — это **"технический долг"**, который вы берете у базы данных.

*   **Хрупкость:** Если вы принудительно заставили индекс `idx_user_email` работать сегодня, а завтра вы удалили этот индекс или пересоздали его с другими параметрами, ваш запрос упадет или станет еще медленнее.
*   **Негибкость:** Данные меняются. Сегодня индекс эффективен, а завтра, когда таблица разрастется или распределение данных изменится, этот же индекс станет обузой. Планировщик PostgreSQL — это очень умный математический движок, и если он не использует индекс, у него обычно есть на то веские причины (например, он считает, что данные распределены так, что `Seq Scan` будет быстрее).

**Мой принцип:** Сначала исправляю статистику (`ANALYZE`), затем структуру запроса, затем конфигурацию сервера, и только в самом крайнем случае — использую `pg_hint_plan`.

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

Это отличный вопрос, который проверяет понимание того, как работает движок PHP (Zend Engine) «под капотом».

Короткий ответ: **В современных версиях PHP (8.x) влияние `strict_types=1` на производительность практически равно нулю (менее 0.1% в большинстве сценариев).**

Более того, в некоторых специфических случаях использование строгой типизации может даже **помочь** оптимизации, хотя это и не является прямой целью.

### Почему это не замедляет код?

Многие ошибочно полагают, что `strict_types` заставляет PHP выполнять дополнительные проверки при каждом вызове функции, что должно замедлять работу. Но реальность иная:

1.  **Проверки происходят в момент вызова, а не во время выполнения логики:**
    Когда вы вызываете функцию, PHP проверяет типы аргументов один раз в момент входа в функцию. Если типы не совпадают, выбрасывается `TypeError`. Это происходит на уровне опкодов (opcodes) и не добавляет накладных расходов на саму работу внутри функции.

2.  **Оптимизации JIT (Just-In-Time Compilation):**
    В PHP 8 появился JIT-компилятор. Для него строгая типизация — это подарок. Когда JIT видит, что типы жестко заданы и не изменятся (благодаря `strict_types` и типизированным свойствам), он может генерировать гораздо более эффективный машинный код. Ему не нужно генерировать проверки на случай, если вместо `int` придет `string`, потому Because он **уверен**, что придет `int`.

3.  **Уменьшение "Internal Coercion" (внутреннего приведения типов):**
    В режиме `coercive mode` (когда `strict_types=0`), PHP постоянно выполняет неявные преобразования (например, превращает `"5"` в `5`). Это требует процессорного времени. В режиме `strict_types=1` эти преобразования исключены на уровне логики приложения, так как вы обязаны передавать правильный тип.

---

### Когда задержка может возникнуть (Теоретические кейсы)

Замедление может появиться только в одном сценарии: если ваше приложение **массово и намеренно** использует несогласованные типы, и вы заставляете PHP постоянно выбрасывать и ловить исключения (что является ужасной практикой).

Если вы переходите с `strict_types=0` на `strict_types=1` и у вас начинают сыпаться ошибки — это не «замедление», это **исправление ошибок проектирования**.

### Итог

Если вы будете замерять производительность через `microbenchmark`, разница будет находиться в пределах погрешности измерения.

**Мой вердикт:** Никогда не отказывайтесь от `strict_types=1` ради производительности. Выигрыш в скорости будет мизерным, а выигрыш в **надежности, читаемости и стоимости поддержки кода** — колоссальным. В современном PHP типизация — это не "налог на скорость", а фундамент стабильной системы.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

Это один из самых обсуждаемых вопросов в сообществе Doctrine. Важно понимать, что утверждение «Doctrine не поддерживает составные ключи» — это **полуправда**. Технически Doctrine *может* работать с ними, но она делает это крайне неохотно, и архитектурно это считается «антипаттерном» в рамках философии библиотеки.

### Почему Doctrine "сопротивляется" составным ключам?

Основная причина кроется в архитектурной философии **Data Mapper** и концепции **Identity Map**.

1.  **Identity Map (Карта идентичности):**
    Doctrine использует внутренний реестр (Identity Map), чтобы гарантировать, что для одной и тойтой записи в БД в рамках одного сеанса (Unit of Work) существует только один объект в памяти. Для этого Doctrine нужно однозначно идентифицировать объект. Проще всего это сделать через один столбец `id`. При использовании составных ключей логика сравнения и поиска объектов в мапе усложняется.

2.  **Сложность жизненного цикла (Lifecycle):**
    Многие функции Doctrine (связи `ManyToOne`, `OneToOne`, работа с `Proxy`-объектами) жестко завязаны на наличие одного уникального идентификатора. Если у сущности составной ключ, то при создании связи (например, `Order -> OrderItem`) Doctrine должна будет прокидывать не одно значение, а целую композицию ключей, что сильно усложняет генерацию SQL и работу прокси-объектов.

3.  **Упрощение маппинга:**
    Разработчики Doctrine сознательно пошли по пути упрощения. Вместо того чтобы поддерживать бесконечное количество комбинаций составных ключей, они сделали ставку на **Surrogate Keys (суррогатные ключи)** — простые `id` (UUID или Auto-increment), которые гарантируют уникальность и упрощают все внутренние механизмы.

---

### Как с этим живут в реальных проектах?

В проектировании БД составные ключи часто встречаются (например, в таблицах связей Many-to-Many или в legacy-системах). Вот три стратегии, которые я использую:

#### 1. Стратегия "Surrogate Key" (Рекомендуемый подход)
Это самый чистый способ с точки зрения DDD и Doctrine. Мы добавляем в таблицу искусственный первичный ключ (например, `id` типа `UUID` или `BIGINT`), который не несет бизнес-смысла, но служит техническим идентификатором.

*   **Как это выглядит:** У вас есть таблица `user_roles`. Вместо составного ключа `(user_id, role_id)`, мы добавляем колонку `id`.
*   **Плюсы:** Полная совместимость с Doctrine, легкость работы с связями, отсутствие проблем с Identity Map.
*   **Минусы:** Небольшое увеличение объема данных (лишняя колонка) и необходимость следить за уникальностью пары `(user_id, role_id)` через `UNIQUE constraint` на уровне БД.

#### 2. Использование Value Objects для связи (Entity $\leftrightarrow$ Entity)
Если составной ключ — это просто комбинация двух внешних ключей (как в таблице связей Many-to-Many), я не пытаюсь превратить эту таблицу в полноценную Entity. Я использую коллекции в родительском агрегате.

*   **Пример:** `User` имеет `ManyToMany` связь с `Role`. Doctrine сама создавит скрытую таблицу связи, и нам не нужно думать о её ключе.

#### 3. Использование Embeddables (Если ключ — это бизнес-сущность)
Если составной ключ — это не просто два ID, а реальный объект (например, `CompositeKey` из `CountryCode` и `AreaCode`), я использую `Embeddable`.

*   **Как это выглядит:** Я создаю `Value Object`, который содержит оба поля, и мапплю его как `Embedded` в основную сущность. Однако, чтобы это работало как первичный ключ, мне все равно придется добавить технический `id`, так как Doctrine не умеет использовать `Embeddable` в качестве `@Id`.

---

### Итоговый совет (Best Practice)

Если вы проектируете систему с нуля: **всегда используйте суррогатные ключи (Surrogate Keys)**. 

Используйте `UUID` (v4 или v7 для сортировки), если вам нужна распределенная система, или `BigInt Auto-increment`, если вам нужна максимальная простота. А для обеспечения бизнес-правил (например, чтобы у пользователя не было двух одинаковых ролей) используйте **Unique Constraints** на уровне базы данных. 

Это позволит вам наслаждаться всеми преимуществами Doctrine, не борясь с ограничениями её архитектуры.

## Q27 · Мини-код-ревью

**Интервьюер:** Посмотри на этот код:

```php
class OrderController
{
    public function pay(Request $req): Response
    {
        $id = $req->get('order_id');
        $pdo = DB::connect();
        $order = $pdo->query("SELECT * FROM orders WHERE id = $id")->fetch();
        if (!$order) {
            return new Response('not found', 404);
        }
        $order['status'] = 'paid';
        $pdo->exec("UPDATE orders SET status = 'paid' WHERE id = $id");
        Mailer::send($order['email'], 'Ваш заказ оплачен');
        (new Logger())->log('paid ' . $id);
        return new Response('ok');
    }
}
```

Какие проблемы ты видишь и как бы ты этот код переделал? С чего начал бы и почему?

**Кандидат:**

Этот код — классический пример «антипаттерна» в веб-разработке. Он нарушает почти все принципы, о которых мы говорили ранее: безопасность, архитектуру, надежность и тестируемость.

### 1. Анализ проблем (Что не так?)

Я бы разделил проблемы на три уровня:

**Уровень А: Критические уязвимости (Безопасность)**
*   **SQL Injection:** Переменная `$id` вставляется напрямую в строку запроса. Злоумышленник может передать `1 OR 1=1` и манипулировать всей базой. Это критическая дыра.
*   **Отсутствие авторизации:** Код не проверяет, принадлежит ли этот заказ текущему пользователю. Любой может оплатить (или «оплатить» несуществующий) чужой заказ, просто подставив ID.

**Уровень Б: Архитектурные ошибки (Чистота кода)**
*   **Нарушение SRP (Single Responsibility Principle):** Контроллер делает **всё**: обрабатывает HTTP, работает с БД, управляет бизнес-логикой (смена статуса), отправляет почту и логирует.
*   **Нарушение слоев:** Бизнес-логика (статус заказа) перемешана с инфраструктурой (SQL, Mailer).
*   **Tight Coupling (Жесткая связанность):** Использование статических методов `DB::connect()`, `Mailer::send()` и `new Logger()` делает этот код **невозможным для Unit-тестирования**. Мы не можем подменить почтовый сервер или БД на моки.

**Уровень В: Надежность и UX (Бизнес-логика)**
*   **Отсутствие транзакционности:** Если `Mailer::send()` упадет с ошибкой, статус в БД уже будет `paid`, но пользователь не получит подтверждения. Состояние системы станет противоречивым.
*   **Отсутствие обработки ошибок:** Нет `try-catch` блоков. Любой сбой (БД недоступна, почта не ушла) вызовет `500 Internal Server Error` без внятного объяснения.

### 2. Как бы я это переделал?

Я бы начал с **декомпозиции**. Моя цель — превратить этот «спагетти-код» в четкую цепочку: 
`Контроллер (HTTP) -> Use Case (Бизнес-логика) -> Репозиторий (Данные)`.

#### Шаг 1: Создание Доменной модели и Репозитория

#### Шаг 3: Реализация через Dependency Injection
Мы убираем статические вызовы и внедряем зависимости через конструктор.

### Итоговый (рефакторенный) код

**Domain Layer:**
```php
readonly class Order {
    public function __construct(
        public int $id,
        public string $email,
        public string $status
    ) {}

    public function markAsPaid(): self {
        return new self($this->id, $this->email, 'paid');
    }

```

**Application Layer:**
```php
class PayOrderUseCase {
    public function __construct(
        private OrderRepositoryInterface $repository,
        private MailerInterface $mailer,
        private LoggerInterface $logger,
        private TransactionManager $transactionManager // Для атомарности
    ) {}

    public function execute(int $orderId, int $currentUserId): void {
        $this->transactionManager->transactional(function() use ($orderId, $currentUserId) {
            $order = $this->repository->findById($orderId);

            if (!$order) throw new OrderNotFoundException($orderId);
            if ($order->getUserId() !== $currentUserId) throw new AccessDeniedException();

            $updatedOrder = $order->markAsPaid();
            $this->repository->save($updatedOrder);

            $this->mailer->send($order->getEmail(), 'Ваш заказ оплачен');
            $this->logger->info("Order {$orderId} marked as paid");
        });
    }
}
```

**Presentation Layer (Controller):**
```php
class OrderController extends AbstractController 
{
    public function pay(Request $request, PayOrderUseCase $useCase): Response 
    {
        $orderId = (int) $request->get('order_id');
        $userId = $this->getUser()->getId();

        try {
            $useCase->execute($orderId, $userId);
            return new JsonResponse(['status' => 'ok']);
        } catch (OrderNotFoundException $e) {
            return new JsonResponse(['error' => 'Not found'], 404);
        } catch (AccessDeniedException $e) {
            return new JsonResponse(['error' => 'Forbidden'], 403);
        } catch (\Exception $e) {
            return new JsonResponse(['error' => 'Internal error'], 500);
        }
    }
}
```

### Почему это решение лучше?
1.  **Безопасность:** SQL Injection невозможен (используются подготовленные выражения в репозитории). Добавлена проверка прав доступа.
2.  **Атомарность:** Благодаря `transactional()`, если почта не отправится, статус заказа в БД не изменится.
3.  **Тестируемость:** Теперь я могу написать Unit-тест на `PayOrderUseCase`, подставив моки для репозитория и почты.
4.  **Чистота:** Контроллер стал тонким. Он только принимает запрос и возвращает ответ. Вся «магия» скрыта в слое приложения.

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Этот код — классический пример того, как разработчик пытается «упростить» жизнь, но на самом деле нарушает все фундаментальные принципы проектирования. В этом классе смешано всё: данные, поведение, инфраструктура и управление состоянием.

### Что не так с этой сущностью?

**1. Нарушение ответственности (SRP) и утечка инфраструктуры:**
Сущность `User` (Domain Layer) не должна знать о существовании `EntityManagerInterface` (Infrastructure Layer). Это самая грубая ошибка. Сущность должна описывать **бизнес-правила**, а не способ их сохранения в базу данных. Теперь ваш домен жестко привязан к Doctrine.

**2. Нарушение принципа инкапсуляции и чистоты Domain Layer:**
В конструктор внедрен сервис. Это делает создание сущности крайне сложным. Чтобы просто создать объект `new User(...)`, вам нужно прокинуть в него тяжелый объект `EntityManager`, что делает невозможным создание сущностей в Unit-тестах без огромного количества моков.

**3. Проблема "Side Effects" (Побочных эффектов):**
Метод `changeEmail` делает две вещи: меняет состояние объекта и вызывает `flush()`. 
*   Это нарушает предсказуемость: вызывая метод, я не ожидаю, что в этот же момент в базу данных полетит запрос.
*   Это мешает работе Unit of Work: если я меняю email в цикле для 10 пользователей, я сделаю 10 запросов к базе вместо одного эффективного `flush()` в конце транзакции.

**4. Невозможность тестирования:**
Вы не можете протестировать логику смены email без инициализации всего контейнера Doctrine. Это превращает Unit-тесты в тяжелые интеграционные тесты.

---

### Как бы я это исправил?

Я разделю ответственность: `User` будет отвечать только за изменение своего состояния, а сохранением будет заниматься репозиторий или сервис приложения.

#### 1. Чистая доменная сущность (Domain Layer)

```php
#[ORM\Entity] // Допускается, если мы смиренно принимаем Coupling с Doctrine
class User
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 255, unique: true)]
    private string $email;

    public function __construct(string $email)
    {
        // Здесь может быть валидация формата email
        if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
            throw new \InvalidArgumentException("Invalid email format");
        }
        $this->email = $email;
    }

    public function changeEmail(string $newEmail): void
    {
        if ($this->email === $newEmail) {
            return;
        }

        if (!filter_var($newEmail, FILTER_VALIDATE_EMAIL)) {
            throw new \InvalidArgumentException("Invalid email format");
        }

        $this->email = $newEmail;
        // НИКАКИХ $this->em->flush() здесь!
    }

    public function getEmail(): string
    {
        return $this->email;
    }

    public function getId(): ?int
    {
        return $this->id;
    }
}
```

#### 2. Слой приложения (Application Layer)

Здесь происходит оркестрация: мы берем сущность, меняем её и просим репозиторий сохранить результат.

```php
class ChangeUserEmailService
{
    public function __construct(
        private UserRepositoryInterface $userRepository,
        private EntityManagerInterface $entityManager
    ) {}

    public function execute(int $userId, string $newEmail): void
    {
        $user = $this->userRepository->find($userId);
        if (!$user) {
            throw new UserNotFoundException($userId);
        }

        // 1. Меняем состояние в памяти
        $user->changeEmail($newEmail);

        // 2. Сохраняем изменения в БД одной транзакцией
        $this->entityManager->flush();
    }
}
```

### Итог изменений:
1.  **Тестируемость:** Теперь я могу протестировать `User->changeEmail()` простым `new User(...)` без всякой магии с базой.
2.  **Чистота:** Доменная модель ничего не знает о базе данных и способах её сохранения.
3.  **Производительность:** Мы контролируем момент `flush()`, что позволяет группировать изменения и минимизировать количество запросов к БД.
4.  **Предсказуемость:** Метод `changeEmail` теперь делает ровно одну вещь — меняет состояние объекта.

## Q29 · Процесс и рассуждение

**Интервьюер:** Тебе нужно решить техническую проблему на незнакомых тебе технологии или стеке. Опиши последовательность своих действий от первого взгляда на задачу до уверенного ответа о сроках решения. Когда, по-твоему, нужно просить помощи у команды, а когда разбираться самому?

**Кандидат:**

Это ситуация, в которой проверяется не только технический кругозор, но и **инженерная зрелость**. Главная ошибка здесь — либо «закопаться» в решении на три дня, либо бежать к коллегам с вопросом «как это работает?» через 5 минут после получения задачи.

Мой процесс состоит из четырех четких этапов.

---

### 1. Этап исследования (Discovery & Investigation)

Прежде чем оценивать сроки, я должен понять объем «неизвестного».

1.  **Понимание контекста:** Я изучаю задачу не как «написать код», а как «решить проблему бизнеса». Что должно измениться? Каков ожидаемый результат?
2.  **Чтение документации (Deep Dive):** Я иду в официальную документацию технологии. Я не ищу ответы на StackOverflow в первую очередь — я стараюсь понять фундаментальные принципы (ментальную модель) этой технологии. Если это новый фреймворк, я смотрю его архитектурные гайды.
3.  **Создание "Sandbox" (Песочницы):** Я создаю минимальный, изолированный проект (PoC — Proof of Concept), где пробую базовые возможности технологии. Моя цель — не решить задачу, а проверить, *способна ли эта технология в принципе решить мою задачу*.
4.  **Анализ текущей реализации:** Я смотю, как эта технология уже используется в нашем проекте. Какие паттерны мы применяем? Какие у нас уже есть обертки или конфигурации?

### 2. Этап декомпозиции и оценки (Spike & Estimation)

Когда я понял, как работает технология, я перехожу к самой задаче.

1.  **Декомпозиция на подзадачи:** Я разбиваю задачу на мелкие, понятные шаги (например: «настроить конфиг», «реализовать интерфейс», «написать тесты»).
2.  **Оценка рисков:** Я ищу «узкие места». Где может возникнуть неопределенность? (Например, «не знаю, как эта библиотека взаимодействует с нашими транзакциями»).
3.**Формирование оценки:** Я даю оценку по методу **PERT** (три числа: оптимистичный, наиболее вероятный и пессимистичный сценарий). Это позволяет мне сказать: «Я планирую закончить за 3 дня, но если возникнет проблема с X, это может занять до 5 дней».

---

### 3. Когда разбираться самому, а когда просить помощи?

Я использую правило **«Таймера и прогресса»**.

**Разбираться самому, если:**
*   Я нахожусь в фазе «понимания документации».
*   Я пробую разные подходы в песочнице, и они не работают.
*   Проблема решается поиском в документации или StackOverflow (но не более 30-60 минут на одну конкретную подзадачу).
*   *Моя цель на этом этапе:* пройти путь от «я не знаю, что это» до «я понимаю, почему это не работает».

**Просить помощи (Escalation), если:**
*   **Тупик (Stuck):** Я потратил фиксированное время (например, 1-2 часа) на одну и ту же подзадачу, перепробовал все очевидные подходы, но прогресса ноль.
*   **Архитектурный риск:** Я нашел решение, но оно кажется мне «костылем» или нарушает наши внутренние стандарты. Мне нужно подтверждение от лида.
*   **Неизвестная инфраструктура:** Проблема не в коде, а в том, как работает наш CI/CD, Docker или деплой. Это не моя зона ответственности, и я не должен тратить время на дебаг инфраструктуры.
*   **Блокировка:** Моя работа стоит, потомуp я жду ответа от другой команды или документации.

**Как я прошу помощи:**
Я никогда не прихожу с вопросом «Как это сделать?». Я прихожу с фразой:
> «Я решаю задачу X. Я изучил документацию, попробовал подходы А и Б в песочнице. Подход А не работает, потому потому что [причина]. Подход Б кажется рискованным из-за [причина]. Как ты считаешь, какой путь лучше или я что-то упускаю?»

### Итог
Мой подход позволяет мне **сохранять автономность**, но при этом **не подводить команду** непредсказуемыми задержками. Я превращаю «незнание» в «процесс исследования», а «проблему» — в «структурированный вопрос».

## Q30 · Процесс и рассуждение

**Интервьюер:** Ты пообещал сделать задачу к завтрашнему дню, но по ходу работы понял, что это два дня работы. Что делаешь?

**Кандидат:**

Это критический момент, который проверяет мою профессиональную честность и умение управлять ожиданиями (Stakeholder Management). 

**Главное правило: никогда не скрывать проблему и не пытаться «проскочить» на авось.** Если я промолчу и в дедлайн принесу пустой результат, я подорву доверие к себе и заблокирую работу всей команды.

Вот мой алгоритм действий:

### 1. Немедленное уведомление (Communication)
Как только я понял, что не укладываюсь в срок, я **немедленно** сообщаю об этом. Не нужно ждать завтрашнего утра или момента дедлайна. Чем раньше я сообщу, тем больше у бизнеса будет времени на перестроение планов.

### 2. Формат сообщения (Проблема + Причина + Решение)
Я не прихожу с проблемой «я не успеваю». Я прихожу с анализом ситуации. Мой отчет будет состоять из трех частей:

*   **Что произошло (The Reality):** «При реализации задачи X я обнаружил, что оценка была занижена. Объем работы оказался больше, чем ожидалось».
*   **Почему так случилось (The Root Cause):** Я даю техническое обоснование, чтобы это не выглядело как «я ленился».
    *   *Пример:* «В процессе реализации выяснилось, что текущая архитектура репозитория не поддерживает нужный фильтр, и мне необходимо провести рефакторинг слоя данных, чтобы задача была выполнима».
*   **Предложение вариантов (The Options):** Я не просто кидаю проблему на стол, а предлагаю пути решения.

---

### 3. Предложение вариантов (Trade-offs)

Я предложу менеджеру на выбор три стратегии:

**Вариант А: Сдвиг дедлайна (Quality First)**
«Если нам важно реализовать задачу полностью и правильно (с учетом рефакторинга), мне потребуется еще один рабочий день. Срок сдвигается на послезавтра».
*   *Когда выбирать:* Если задача критична для стабильности системы и «костыль» принесет больше вреда, чем задержка.

**Вариант Б: Сокращение объема (Scope Cutting)**
«Мы можем успеть к завтрашнему дню, если мы временно ограничим функционал. Например, я сделаю базовую реализацию без сложной фильтрации, а расширенную часть вынесу в отдельный тикет на следующую неделю».
*   *Когда выбирать:* Если дедлайн жесткий (например, релиз или презентация клиенту) и нам нужен хотя�режим MVP.

**Вариант В: Приоритизация (Re-prioritization)**
«Если этот дедлайн критичен, я могу бросить текущую задачу и заняться другой, более приоритетной. Но тогда текущая задача будет отложена».
*   *Когда выбирать:* Если у меня в работе несколько задач и менеджер должен решить, что важнее для бизнеса прямо сейчас.

---

### Резюме: почему я действую именно так?

1.  **Прозрачность (Transparency):** Я минимизирую неопределенность для бизнеса.
2.  **Управление рисками:** Я даю менеджеру возможность самому выбрать уровень риска (задержка vs неполный функционал).
3.  **Профессионализм:** Я показываю, что я контролирую ситуацию, понимаю причины проблем и умею предлагать варианты решения, а не просто констатирую факт неудачи.

**Мой принцип:** «Лучше плохие новости сегодня, чем катастрофа завтра».

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

Это вопрос о поиске баланса между **инженерным совершенством** и **бизнес-ценностью**. В индустрии есть понятие «Overengineering» (избыточное проектирование) — это когда разработчик строит космический корабль там, где достаточно велосипеда.

Мой подход базируется на принципе: **«Код должен быть достаточно хорошим, чтобы быть безопасным, тестируемым и понятным, но не настолько идеальным, чтобы он не приносил денег»**.

Вот как я соблюдаю этот баланс:

### 1. Критерии «Достаточно хорошего кода» (Definition of Done)

Для меня задача считается выполненной и готовой к отдаче, если она соответствует следующим четырем критериям:

1.  **Корректность (Correctness):** Код решает поставленную бизнес-задачу и проходит все утвержденные сценарии (Acceptance Criteria).
2.  **Надежность (Reliability):**
    *   Написаны Unit и интеграционные тесты, покрывающие основные пути (Happy Path) и критические ошибки.
    *   Нет явных уязвимостей (SQLi, XSS) и утечек памяти.
3.  **Читаемость и поддерживаемость (Maintainability):**
    *   Код соответствует принятому в команде стилю (PSR).
    *   Имена переменных и методов отражают доменную логику (Ubiquitous Language).
    *   Сложность методов находится в разумных пределах (нет «спагетти»).
4.  **Предсказуемость (Predictability):** Код не ломает существующий функционал (пройдено регрессионное тестирование).

Если эти четыре пункта соблюдены — **код готов к релизу**.

---

### <li>2. Когда стоит продолжать улучшать (Refactoring)

Я не занимаюсь «рефакторингом ради рефакторинга». Я иду вглубь кода только в двух случаях:

1.  **Обнаружение «запаха кода» (Code Smell), мешающего текущей задаче:** Если я пишу фичу и вижу, что текущий класс слишком раздут и мешает мне писать тесты — я провожу локальный рефакторинг. Это называется **«Правило бойскаута»**: оставь место стоянки чуть чище, чем оно было до тебя.
2.  **Технический долг, блокирующий развитие:** Если я вижу, что архитектурная проблема (например, отсутствие абстракции) будет постоянно замедлять разработку новых задач в ближайшие недели, я выношу это в отдельный тикет и предлагаю менеджеру запланировать его в спринт.

---

### 3. Моя стратегия баланса: «Прагматичный инженер»

В реальном проекте я использую три инструмента для управления балансом:

#### А) Оценка стоимости изменений (Cost-Benefit Analysis)
Перед тем как начать глубокий рефакторинг, я спрашиваю себя:
*   *«Сколько времени это займет?»*
*   *«Насколько это снизит вероятность багов в будущем?»*
*   *«Насколько это ускорит разработку новых фич?»*
Если затраты на рефакторинг превышают выгоду от упрощения кода — я оставляю код как есть, но фиксирую это как техдолг.

#### Б) Управление техническим долгом (Technical Debt Management)
Я рассматриваю техдолг не как грех, а как **кредит**.
*   Иногда мы берем кредит (пишем чуть менее идеальный код), чтобы быстрее выкатить фичу к дедлайну.
*   Но я всегда веду учет этих «кредитов» (создаю тикеты в бэклоге). Если мы будем только брать кредиты и никогда не возвращать их (рефакторить), проект «оббанкротится» — разработка станет невозможной из-за сложности кода.

#### В) Приоритет тестирования над перфекционизмом
Если время поджимает, я лучше напишу чуть меньше тестов, но сделаю их на критические пути, чем буду пытаться добиться 100% покрытия, тратя время на проверку тривиальных геттеров и сеттеров.

### Резюме
Мой подход: **«Сначала работающий код, затем надежный код, затем чистый код»**. 
Я не трачу время на полировку деталей, которые не влияют на стабильность и скорость доставки ценности. Но я никогда не игнорирую фундаментальные проблемы, которые могут разрушить систему в будущем.
