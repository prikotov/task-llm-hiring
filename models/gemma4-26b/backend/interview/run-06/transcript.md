## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

### Рассуждение

Когда звучит вопрос о «самых важных» возможностях, я сразу разделяю их на две категории: **синтаксический сахар** (который делает код красивее) и **инструментарий для повышения надежности** (который уменьшает количество runtime-ошибок). 

Если говорить о «чистом и надежном» коде, то мой фокус смещается с эстетики на **строгость типов** и **явность намерений**. 

Я рассмотрю следующие возможности:
1. **Union Types & Intersection Types:** Это фундаментальный сдвиг. Раньше мы использовали PHPDoc для описания типов, что было «честным словом» разработчика. Теперь это контракт, который проверяет сам движок.
2. **Constructor Property Promotion:** Это про чистоту. Это убирает огромный пласт шаблонного кода (boilerplate), который раньше замусоривал классы, мешая видеть суть логики.
3. **Readonly Properties & Classes:** Это про иммутабельность (неизменяемость). В DDD и чистой архитектуре это критически важно: объект (Value Object или DTO) не должен меняться после создания. Это избавляет от побочных эффектов.
4. **Match Expression:** Это про чистоту и безопасность. В отличие от `switch`, `match` возвращает значение и требует исчерпывающего покрытия (exhaustive checking), что снижает риск пропустить кейс.
5. **Attributes:** Это замена аннотациям в комментариях. Теперь метаданные — это часть языка, а не просто текст, который парсится регулярками.

Я намеренно не буду упоминать JIT или Enumerations (хотя они важны), так как они больше про производительность или структурирование данных, а не про фундаментальную надежность и чистоту архитектуры.

---

### Ответ

Для меня «чистый и надежный» код — это код, который максимально явно описывает свои правила игры и минимизирует пространство для ошибок. Вот мой топ возможностей:

#### 1. Строгая типизация (Union & Intersection Types)
Это база. Раньше мы часто использовали `mixed` или полагались на комментарии. Теперь мы заставляем PHP проверять типы на уровне ядра. Intersection types (PHP 8.1) позволяют описывать объекты, которые должны реализовывать сразу несколько интерфейсов, что крайне полезно для соблюдения принципов интерфейсов.

```php
// Union Types: четко говорим, что может быть на входе
public function process(string|int $id): void { ... }

// Intersection Types: объект ДОЛЖЕН быть и LoggerInterface, и FlushableInterface
public function execute(LoggerInterface&FlushableInterface $service): void { ... }
```

#### 2. Constructor Property Promotion & Readonly (PHP 8.0/8.1)
Это киллер-фича для написания DTO и Value Objects. Она убирает визуальный шум и позволяет легко создавать неизменяемые объекты. В чистой архитектуре это критично: если объект создан, его состояние не должно меняться «под капотом».

```php
// Было: 20 строк кода (свойства, конструктор, присваивания)
// Стало: одна строка
readonly class UserDto
{
    public function __construct(
        public int $id,
        public string $email,
        public DateTimeImmutable $createdAt,
    ) {}
}
```

#### 3. Match Expression (PHP 8.0)
`match` — это эволюция `switch`. Он возвращает значение и, что самое важное, выбрасывает ошибку, если ни одно условие не подошло (в отличие от `switch`, который просто пропустит выполнение). Это делает код предсказуемым.

```php
$status = match($response->getStatusCode()) {
    200, 201 => 'success',
    404      => 'not_found',
    500      => 'server_error',
    default  => throw new \Exception('Unexpected status'), // Безопасная обработка
};
```

#### 4. Enums (PHP 8.1)
Хотя я не включил их в основной список «архитектурных» фич, невозможно говорить о надежности без перечислений. Enums заменяют магические строки и константы, превращая их в полноценные объекты первого класса. Это исключает передачу невалидных значений в методы.

```php
enum OrderStatus: string 
{
    case Pending = 'pending';
    case Shipped = 'shipped';
    case Delivered = 'delivered';
}

// Теперь метод принимает только валидный статус, а не любую строку
public function updateStatus(OrderStatus $status): void { ... }
```

**Итог:** Эти инструменты позволяют мне перенести проверку логики с этапа «надеюсь, я не забыл обработать этот случай» на этап «код просто не запустится, если условие не соблюдено». Это и есть надежность.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

### Рассуждение

Это вопрос с подвохом, потомуy многие разработчики (даже уровня Middle) путают **weak typing** (слабую типизацию) PHP с тем, как он работает по умолчанию в режиме **coercive mode** (режим приведения типов).

Прежде чем отвечать, я разберу три уровня понимания этого вопроса:
1. **Поведение по умолчанию (Coercive mode):** PHP пытается «помочь» разработчику, превращая типы на лету. Это удобно для маленьких скриптов, но смертельно для Enterprise-систем.
2. **Строгий режим (`declare(strict_types=1)`):** Это не изменение работы самого языка, это изменение правил проверки типов *только для текущего файла* при вызове функций. Это критически важный нюанс.
3. **Ловушки:** Я выделю проблемы с `null` (до появления nullable-типов), проблемы с `float/int` при сравнении и специфику работы с объектами и массивами.

Я должен четко разграничить: `strict_types` влияет на **вызов** функции, а не на то, как данные хранятся внутри неё. Если я передаю строку в функцию, которая ожидает int, и в файле, где вызывается функция, стоит `strict_types=1`, я получу `TypeError`. Если нет — PHP попытается сделать `(int) "123"`.

---

### Ответ

Система типов в PHP — это гибридная модель. По умолчанию PHP работает в режиме **coercive mode** (приведение типов), стараясь сделать вызов функции «успешным» любой ценой.

#### 1. Что дает `strict_types=1`?
Важно понимать: эта директива работает **на стороне вызывающей стороны**. Она говорит интерпретатору: «В этом файле не пытайся угадать типы, если они не совпадают с сигнатурой функции — сразу кидай `TypeError`».

Это ключевой инструмент для обеспечения контрактов в DDD. Без него ваш Domain Service может случайно получить строку вместо числа, и ошибка всплывет гораздо позже, когда данные попадут в БД или лог.

#### 2. Приведение типов: как это работает
В обычном режиме PHP делает неявное приведение. 

```php
declare(strict_types=0); // Режим по умолчанию

function add(int $a, int $b): int {
    return $a + $b;
}

echo add(5, "10"); // Выведет 15. PHP молча привел "10" к int.
echo add(5, "abc"); // Выведет 5 (приведет "abc" к 0), если не было ошибок, но это опасно.
```

Если мы добавим `declare(strict_types=1);`, то `add(5, "10")` немедленно выбросит `Fatal error: Uncaught TypeError`.

#### 3. Типичные ловушки на практике

**Ловушка №1: "Странное" поведение при передаче типов между файлами**
Это самая частая причина багов. Если `FileA.php` вызывает функцию из `FileB.php`, то поведение зависит от того, какой `strict_types` прописан в `FileA.php`, а не в `FileB.php`.

```php
// FileB.php
function calculate(int $val) { return $val * 2; }

// FileA.php
require 'FileB.php';
declare(strict_types=1); 

calculate("10"); // TypeError! (потому что strict_types в FileA)
```

**Ловушка №2: Проблема `null`**
До PHP 7.1, если вы указали тип `int`, вы не могли передать `null`. Это заставляло разработчиков использовать `mixed` или делать проверки внутри, что замусоривало код. Сейчас мы используем nullable-типы (`?int`), но часто забываем про них, получая ошибки на неявных `null` из БД.

**Ловушка №3: Сравнение Float и Int**
Из-за особенностей представления чисел с плавающей точкой, типизация может «удивлять» при проверках.

```php
function check(float $val) { ... }
check(1); // Работает (приведение int -> float)
```

#### 4. Примеры: спасение vs удивление

**Где типизация спасает (Clean Architecture / DDD):**
Когда мы проектируем Value Object. Типизация гарантирует, что в метод `Order::ship(DateTimeImmutable $date)` не придет строка или `null`. Это гарантирует, что состояние системы всегда валидно.

```php
public function transitionToStatus(StatusEnum $status): void 
{
    // Мы на 100% уверены, что $status — это объект Enum, 
    // а не строка 'shipped', которую кто-то прислал из API.
    $this->status = $status;
}
```

**Где типизация удивляет (Legacy/Coercive mode):**
Когда вы ожидаете, что тип данных будет строго контролироваться, а PHP «проглатывает» ошибку, превращая мусор в `0` или `false`.

```php
declare(strict_types=0);

function processId(int $id) {
    return "Processing ID: " . $id;
}

// Мы ожидаем ошибку, если пришла пустая строка из API, 
// но PHP превратит её в 0 и "продолжит" работу.
echo processId(""); // "Processing ID: 0" — это логическая ошибка, которую трудно отловить.
```

**Мой вердикт как инженера:** В современном PHP-бэкенде использование `declare(strict_types=1)` в каждом файле должно быть стандартом де-факто. Это превращает PHP из «гибкого языка для скриптов» в предсказуемый инструмент для построения надежных систем.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

### Рассуждение

Вопрос об исключениях — это вопрос о **стратегии обработки ошибок** и о том, как мы сообщаем вызывающему коду о том, что что-то пошло не так. Плохая работа с исключениями превращает проект в «угадайку»: разработчик никогда не знает, нужно ли ему оборачивать вызов метода в `try-catch` или он может просто пробросить исключение выше.

Я подхожу к этому вопросу через призму **слоев архитектуры**. Исключение — это не просто ошибка, это инструмент передачи информации о нарушении инвариантов системы.

Я выделяю три ключевых аспекта:
1. **Иерархия:** Исключения должны быть структурированы так, чтобы вызывающий код мог обрабатывать их на разных уровнях абстракции (общий catch для группы ошибок или специфичный для конкретной ситуации).
2. **Контракт:** Исключение — это часть сигнатуры метода, даже если оно не указано в Type Hinting (так как PHP не поддерживает `throws` в сигнатуре на уровне языка).
3. **Обертывание (Wrapping):** Это способ сохранить контекст, не раскрывая детали реализации (например, не пробрасывать `PDOException` из репозитория в контроллер).

Я также отмечу, что использование исключений для управления логикой потока (Flow Control) — это классическая ошибка, которую я пресекаю на код-ревью.

---

### Ответ

Проектирование исключений для меня — это проектирование **языка ошибок** вашего приложения.

#### 1. Иерархия исключений
Я никогда не использую стандартные `\Exception` или `\RuntimeException` напрямую в бизнес-логике. Я создаю свою иерархию, которая отражает суть проблем.

Обычно структура выглядит так:
* `App\Exception\DomainException` (базовый класс для всех ошибок домена).
    * `App\Exception\Domain\EntityNotFoundException`
    * `App\Exception\Domain\InsufficientFundsException`
* `App\Exception\InfrastructureException` (ошибки внешних систем).
    * `App\Exception\Infrastructure\ExternalApiTimeoutException`

Это позволяет на верхнем уровне (например, в Symfony Kernel Exception Listener) решить: если это `DomainException`, мы возвращаем пользователю красивое сообщение (4xx), если это `InfrastructureException` — мы логируем критическую ошибку и отдаем 500.

#### 2. Контракт метода и «невидимые» исключения
Поскольку PHP не заставляет нас объявлять `throws` в сигнатуре, я считаю, что **документация (PHPDoc) и чистота кода обязаны это компенсировать**.

Если метод `UserRepository::findById(int $id)` может не найти пользователя, у меня есть два пути:
1. **Вернуть `?User` (Nullable):** Если отсутствие пользователя — это нормальный, ожидаемый сценарий (например, при поиске в поиске). Это **не** исключение.
2. **Бросить `EntityNotFoundException`:** Если метод по контракту *обязан* вернуть пользователя (например, при получении профиля текущего авторизованного юзера), и его отсутствие — это нарушение бизнес-логики.

**Контракт метода включает в себя все исключения, которые он может выбросить.** Я приучаю команду документировать их в PHPDoc.

#### 3. Оборачивание (Exception Wrapping)
Это важнейший принцип для сохранения чистоты архитектуры. Мы не должны позволять деталям реализации «протекать» в другие слои.

**Плохо:** Репозиторий пробрасывает `PDOException` в Сервис. Теперь Сервис знает, что мы используем SQL.
**Хорошо:** Репозиторий ловит `PDOException` и выбрасывает `Infrastructure\DatabaseException`.

```php
// Repository layer
try {
    $this->connection->executeStatement(...);
} catch (\PDOException $e) {
    // Мы оборачиваем исключение, сохраняя оригинальное (previous) для отладки
    throw new DatabaseException("Failed to update user", 0, $e);
}
```

#### 4. Антипаттерны

Я выделяю три главных антипаттерна, которые встречал в 15-летней практике:

1. **Exceptions for Flow Control (Исключения для управления логикой):**
   Использование `try-catch` там, где можно использовать простой `if`. 
   *Пример:* Проверка прав доступа через выброс `AccessDeniedException` вместо `if (!$user->hasPermission(...))`. Исключения — это дорогостоящая операция для CPU, и они должны использоваться только для *исключительных* ситуаций.

2. **Generic Exceptions (Универсальные исключения):**
   Когда везде кидают `\Exception`. Это делает невозможным точечную обработку ошибок. Вы либо ловите всё (и замалчиваете важные баги), либо не ловите ничего.

3. **Silent Catch (Глотание исключений):**
   ```php
   try {
       $this->doSomething();
   } catch (\Exception $e) {
       // Пусто. Ошибки больше нет, а система в невалидном состоянии.
   }
   ```
   Это самый опасный антипаттерн. Если вы ловите исключение, вы должны либо обработать его, либо залогировать и пробросить выше. «Замалчивание» ошибки — прямой путь к повреждению данных в БД.

**Итог:** Мой подход — исключения должны быть типизированными, иерархичными, не раскрывать детали реализации через обертывание и использоваться только для действительно исключительных случаев, а не для проверки условий `if/else`.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

### Рассуждение

Вопрос о «самом часто нарушаемом» принципе всегда субъективен, так как зависит от уровня команды. Однако, если говорить о реальных проектах средней и высокой сложности, я выделю два главных кандидата: **SRP (Single Responsibility Principle)** и **DIP (Dependency Inversion Principle)**.

Но если нужно выбрать один, который «отравляет» код сильнее всего и встречается чаще всего — это **SRP (Принцип единственной ответственности)**.

Почему это происходит? 
1. **Скорость разработки:** Проще написать один класс, который делает всё, чем проектировать взаимодействие нескольких мелких.
2. **Естественное стремление человека:** Мы мыслим сущностями. «Класс Пользователь» кажется логичным, и мы начинаем добавлять туда и смену пароля, и отправку Email, и сохранение в БД, и генерацию PDF-отчетов.
3. **Эволюция кода:** Проект начинается чисто, но со временем класс обрастает «полезными» методами, превращаясь в **God Object** (Божественный объект).

Нарушение SRP влечет за собой цепочку проблем: нарушение OCP (при добавлении новой фичи нужно править старый класс), нарушение LSP (класс становится слишком сложным и начинает вести себя непредсказуемо) и, конечно, ад в тестировании.

Я покажу нарушение SRP на примере типичного сервиса заказов.

---

### Ответ

Чаще всего в реальной разработке нарушается **SRP (Single Responsibility Principle)**. Классы часто превращаются в «швейцарские ножи», которые знают слишком много о разных аспектах системы.

#### Типовое нарушение (God Service)

Представь сервис `OrderService`. В нем собрана и бизнес-логика, и работа с БД, и отправка уведомлений, и даже формирование чеков.

```php
class OrderService
{
    public function createOrder(array $data): void
    {
        // 1. Валидация (Бизнес-логика)
        if (empty($data['items'])) {
            throw new \Exception("Order must have items");
        }

        // 2. Расчет стоимости (Бизнес-логика)
        $total = 0;
        foreach ($data['items'] as $item) {
            $total += $item['price'] * $item['quantity'];
        }

        // 3. Работа с БД (Инфраструктура)
        // Представим, что здесь прямой вызов SQL или тяжелый репозиторий
        $this->db->query("INSERT INTO orders (total) VALUES ($total)");

        // 4. Отправка Email (Внешний сервис)
        $mail = new PHPMailer();
        $mail->Body = "Your order total is: " . $total;
        $mail->send();

        // 5. Генерация PDF (Внешний сервис/библиотека)
        $pdf = new PDFGenerator();
        $pdf->generate($total);
    }
}
```

**Почему это плохо?**
*   **Трудно тестировать:** Чтобы протестировать расчет суммы, тебе нужно поднять БД, настроить почтовый сервер и библиотеку PDF.
*   **Хрупкость:** Если изменится формат Email, тебе придется менять `OrderService`. Если изменится схема БД — снова `OrderService`.
*   **Дублирование:** Если нам нужно создать заказ через API или консольную команду, нам придется либо дублировать логику, либо тащить за собой весь этот тяжелый сервис.

#### Рефакторинг (Разделение ответственности)

Я разделю этот процесс на специализированные компоненты. Сервис заказов будет только **координировать** выполнение процесса, делегируя детали реализации другим объектам.

```php
// 1. Интерфейсы для обеспечения гибкости (DIP)
interface OrderRepositoryInterface { public function save(Order $order): void; }
interface NotificationServiceInterface { public function notify(Order $order): void; }
interface InvoiceGeneratorInterface { public function generate(Order $order): void; }

// 2. Чистый доменный сервис
class OrderService
{
    public function __construct(
        private OrderRepositoryInterface $repository,
        private NotificationServiceInterface $notifier,
        private InvoiceGeneratorInterface $invoiceGenerator,
        private OrderCalculator $calculator // Отдельный сервис для расчетов
    ) {}

    public function createOrder(OrderData $data): void
    {
        // Создаем доменный объект (Entity)
        $order = new Order($data->items);
        
        // Используем специализированный сервис для расчетов
        $order->setTotal($this->calculator->calculate($order->getItems()));

        // Делегируем сохранение репозиторию
        $this->repository->save($order);

        // Делегируем уведомления и счета
        $this->notifier->notify($order);
        $this->invoiceGenerator->generate($order);
    }
}
```

**Что изменилось?**
1.  **SRP соблюден:** `OrderService` теперь отвечает только за *процесс* создания заказа. Он не знает, как работает SQL, как работает SMTP или как генерируется PDF.
2.  **Тестируемость:** Теперь я могу легко написать Unit-тест для `OrderService`, подставив `Mock` для всех интерфейсов. Тест будет выполняться миллисекунды и не потребует внешних зависимостей.
3.  **Расширяемость (OCP):** Если завтра мы захотим отправлять уведомления не через Email, а через Telegram, я просто создам `TelegramNotificationService`, реализующий `NotificationServiceInterface`, и передам его в конструктор. Сам `OrderService` менять не придется.
4.  **Читаемость:** Код стал декларативным. Глядя на метод `createOrder`, я сразу понимаю бизнес-процесс, не отвлекаясь на детали реализации.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

### Рассуждение

Это отличный вопрос, который отделяет «академического» разработчика от «инженерного». В учебниках SOLID преподносится как незыблемый закон, но в реальной жизни инженер всегда работает в условиях **ограничений**: времени, бюджета, сложности задачи и требований к производительности.

Если я буду слепо следовать всем принципам в каждом микросервисе или маленьком скрипте, я превращу разработку в бесконечный процесс проектирования (overengineering), который никогда не принесет бизнес-ценности.

Я рассматриваю SOLID не как набор догм, а как **инструмент управления сложностью**. Если сложность системы на данном этапе низка, то применение всех принципов может создать *избыточную* сложность. 

Я выделяю два критерия, когда нарушение оправдано:
1. **Масштаб и жизненный цикл проекта:** Если это прототип (PoC), скрипт миграции или инструмент, который будет написан один раз и удален через неделю, SOLID — это лишняя трата денег компании.
2. **Производительность и технические ограничения:** Иногда абстракции (DIP/ISP) вносят накладные расходы, которые недопустимы в высоконагруженных узлах (hot paths).

---

### Ответ

Да, нарушать принципы SOLID можно и иногда даже нужно. Инженерная задача — это всегда поиск баланса между **гибкостью (flexibility)** и **прагматичностью (pragmatism)**. 

Слепое следование SOLID там, где оно не требуется, приводит к «архитектурному ожирению» — когда кода становится в 10 раз больше, а пользы от него нет, потому что проект никогда не вырастет до масштабов, где эти абстракции пригодятся.

#### Пример оправданного нарушения: Принцип единственной ответственности (SRP) в рамках одной сущности (Value Object или маленького DTO)

Представь, что нам нужно создать простой класс для валидации и хранения данных о цвете (RGB).

**Вариант 1: Строгое соблюдение SRP (Overengineering)**
Мы создаем:
1. `Color` (Entity/Value Object).
2. `ColorValidator` (Service для валидации).
3. `ColorFactory` (Service для создания объекта через валидацию).
4. `ColorFormatter` (Service для преобразования в Hex/RGBA).

Для маленького проекта это превращается в катастрофу: чтобы просто передать цвет из формы в базу, мне нужно прокинуть через DI контейнер четыре разных класса.

**Вариант 2: Прагматичное нарушение (Оправданное)**
Мы объединяем логику в один компактный класс.

```php
readonly class Color
{
    public function __construct(
        public int $r,
        public int $g,
        public int $b,
    ) {
        // Мы нарушаем SRP, так как класс и хранит данные, и валидирует их
        $this->validate();
    }

    private function validate(): void
    {
        if ($this->r < 0 || $this->r > 255) {
            throw new \InvalidArgumentException("R must be 0-255");
        }
        // ... и так далее
    }

    public function toHex(): string
    {
        // Мы также нарушаем SRP, добавляя метод форматирования
        return sprintf("#%02x%02x%02x", $this->r, $this->g, $this->b);
    }
}
```

**Почему это оправдано?**
1. **Связность (Cohesion):** Валидация цвета и его форматирование — это неотъемлемые свойства самого понятия «Цвет». Разделение их на разные сервисы не упрощает код, а размазывает его по проекту.
2. **Снижение когнитивной нагрузки:** Разработчику проще понять один класс `Color`, чем прыгать по пяти файлам, чтобы понять, как работает простейшая структура данных.
3. **Экономия ресурсов:** Мы не тратим время на написание тестов для трех пустых классов-прослоек.

#### Когда нарушение становится опасным?
Нарушение оправдано только тогда, когда **стоимость абстракции выше, чем стоимость потенциальных изменений**. 

Если я нарушаю SRP в маленьком `Value Object` — это нормально. Но если я нарушаю SRP в `OrderService`, который является ядром системы и будет расширяться ближайшие два года — это технический долг, который я обязан зафиксировать и запланировать его погашение.

**Мой принцип:** Нарушай SOLID, если это экономит время сейчас и не создаст проблем при масштабировании завтра. Если сомневаешься — проектируй по SOLID.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

### Рассуждение

Когда говорят об Open/Closed Principle (OCP), классический пример из учебников — это наследование (полиморфизм через подклассы). Однако в современной разработке (особенно в PHP/Symfony) полагаться только на наследование — значит создавать жесткие иерархии, которые крайне трудно поддерживать (проблема «хрупкого базового класса»).

Я рассматриваю OCP как задачу: **«Как добавить новое поведение, не меняя существующий код?»**. 

Если мы не используем наследование (is-a), у нас остаются два мощных архитектурных пути:
1. **Композиция (has-a):** Мы не меняем класс, а меняем его «внутренности» через внедрение зависимостей. Это основа Dependency Injection.
2. **Делегирование/Событийная модель:** Мы позволяем внешнему коду «подписываться» на процессы внутри нашего класса.

Я рассмотрю эти подходы, так как именно они лежат в основе расширяемых систем вроде Symfony.

---

### Ответ

Наследование — это самый «грубый» способ реализации OCP. В реальных Enterprise-системах мы предпочитаем более гибкие механизмы, которые позволяют расширять функционал, не создавая глубоких иерархий классов.

Вот основные способы:

#### 1. Композиция и паттерн «Стратегия» (Strategy)
Это самый распространенный способ. Вместо того чтобы наследоваться от базового класса, чтобы изменить алгоритм, мы передаем этот алгоритм в конструктор через интерфейс.

**Пример:** У нас есть сервис оплаты. Вместо создания `PaypalOrderService` и `StripeOrderService` (наследование), мы используем композицию.

```php
interface PaymentStrategy {
    public function pay(int $amount): void;
}

class OrderService 
{
    // Мы закрыты для изменений (не меняем этот класс), 
    // но открыты для расширения (добавляем новые стратегии)
    public function __construct(
        private PaymentStrategy $paymentStrategy 
    ) {}

    public function process(int $amount): void 
    {
        $this->paymentStrategy->pay($amount);
    }
}
```
*Чтобы добавить новый способ оплаты, нам не нужно трогать `OrderService`, мы просто создаем новый класс, реализующий интерфейс.*

#### 2. Паттерн «Декоратор» (Decorator)
Декоратор позволяет добавлять ответственности объекту «на лету», не меняя его код и не используя наследование для расширения функционала. Это классический способ соблюдения OCP для добавления сквозной логики (логирование, кэширование, валидация).

**Пример:**
```php
interface RepositoryInterface {
    public function find(int $id): array;
}

class SqlRepository implements RepositoryInterface {
    public function find(int $id): array { /* SQL запрос */ return []; }
}

// Декоратор, который добавляет кэширование, не меняя SqlRepository
class CachedRepository implements RepositoryInterface 
{
    public function __construct(
        private RepositoryInterface $innerRepository,
        private CacheInterface $cache
    ) {}

    public function find(int $id): array {
        return $this->cache->get($id) ?? $this->innerRepository->find($id);
    }
}
```

#### 3. Событийная модель (Observer / Event Dispatcher)
Это самый мощный способ реализации OCP в крупных фреймворках (как Symfony). Мы превращаем класс в «излучатель» событий. Мы не знаем, кто нас слушает, но мы позволяем любому количеству сторонних модулей вмешаться в процесс.

**Пример:**
Вместо того чтобы в методе `registerUser()` прописывать отправку письма, создание профиля и выдачу бонуса, мы просто кидаем событие.

```php
class UserService 
{
    public function __construct(private EventDispatcherInterface $dispatcher) {}

    public function register(User $user): void 
    {
        // Логика регистрации...
        
        // Мы закрыты для изменений. Если завтра нужно будет добавить 
        // отправку SMS, мы не будем менять этот класс.
        $this->dispatcher->dispatch(new UserRegisteredEvent($user));
    }
}
```
*Любой новый функционал (SMS, аналитика, интеграция с CRM) реализуется как отдельный `EventListener`, который не знает о существовании `UserService`.*

#### 4. Использование Traits (с осторожностью)
Хотя Trait — это не совсем композиция (это горизонтальное копирование кода), он позволяет расширять функциональность классов без создания иерархии наследования. Однако я считаю это скорее инструментом повторного использования кода, а не чистым способом реализации OCP, так как Trait жестко «вшивается» в класс в момент написания.

**Резюме:**
Если вам нужно изменить **алгоритм** — используйте **Стратегию**.
Если нужно добавить **поведение поверх** существующего — используйте **Декоратор**.
Если нужно добавить **реакцию на действие** — используйте **События (Event Dispatcher)**.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

### Рассуждение

Это отличный вопрос, который проверяет, понимает ли разработчик суть принципа или просто зазубрил определение «один класс — одна ответственность». 

Если отвечать поверхностно, то многие учебники говорят: «Класс должен иметь только одну причину для изменения». Но это узкое определение. На самом деле, **SRP — это принцип управления сложностью на любом уровне абстракции.**

Я должен разобрать этот вопрос на трех уровнях:
1. **Уровень кода (Классы/Функции):** Это то, о чем говорят все.
2. **Уровень модулей/компонентов:** Как мы разделяем целые библиотеки или микросервисы.
3. **Уровень архитектуры (Слои/Bounded Contexts):** Как мы разделяем доменные области.

Если мы будем применять SRP только к классам, мы получим «микро-классы» (classlets) — мелкие обрывки кода, которые по отдельности ничего не значат, но вместе создают невыносимую сложность при навигации. Настоящий SRP — это про **когерентность (связность) ответственности**, а не про количество строк в файле.

---

### Ответ

**Нет, SRP не ограничивается только классами.** 

Принцип единственной ответственности применим к любому элементу системы, который можно выделить как самостоятельную единицу. Если мы будем применять его только к классам, мы рискуем попасть в ловушку «атомарного проектирования», когда у нас сотни крошечных классов, но при этом вся логика системы всё равно размазана по всему проекту.

Вот где еще должен применяться SRP:

#### 1. Уровень функций и методов
Функция должна выполнять одну задачу. Если метод называется `saveAndSendEmail()`, он уже нарушает SRP. 
* **Плохо:** Метод, который делает запрос в БД, обрабатывает результат, форматирует его и отправляет в лог.
* **Хорошо:** Маленькая функция, которая делает только одну трансформацию или только одно действие.

#### 2. Уровень модулей и пакетов (Composer packages)
В PHP-экосистеме мы часто собираем компоненты. Модуль должен иметь одну четкую цель. 
* **Нарушение:** Библиотека, которая одновременно занимается и работой с очередями (RabbitMQ), и парсингом XML, и валидацией почты. 
* **Решение:** Разделение на специализированные пакеты (`symfony/messenger`, `symfony/validator`). Это позволяет пользователю установить только то, что ему нужно, не раздувая зависимости.

#### 3. Уровень микросервисов и сервисов (Infrastructure)
В распределенных системах SRP проявляется на уровне **Bounded Contexts** (ограниченных контекстов) из DDD.
* **Нарушение:** «Монолитный микросервис», который отвечает и за склад (Inventory), и за заказы (Orders), и за пользователей (Users). Если склад упадет, заказы тоже не смогут работать.
* **Решение:** Каждый микросервис должен владеть своей областью ответственности и своими данными.

#### 4. Уровень слоев архитектуры (Layers)
Даже внутри одного приложения слои должны соблюдать SRP. 
* **Слой Domain** отвечает только за бизнес-правила.
* **Слой Infrastructure** отвечает только за реализацию (БД, API, File System).
* **Слой Application** отвечает только за координацию.
Если вы начнете писать SQL-запросы прямо в Domain-сущностях, вы нарушите SRP на уровне архитектурных слоев.

**Итог:**
SRP — это принцип **разделения ответственности по смыслу (семантике)**, а не по синтаксису. Важно не то, сколько классов вы создали, а то, насколько четко каждая единица вашей системы (будь то метод, класс, пакет или сервис) отвечает за одну конкретную бизнес-задачу.

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

Вопрос касается «сердца» Symfony. Чтобы ответить на него глубоко, я не должен ограничиваться описанием «он просто кладет объекты в корзину». Я должен объяснить разницу между **Runtime** (когда работает приложение) и **Compile-time** (когда собирается контейнер), потому что именно в этом кроется секрет производительности Symfony.

Я разделю ответ на три этапа, соответствующих вопросу:
1. **Compile-time (Компиляция):** Здесь происходит магия оптимизации. Я объясню концепцию `ContainerBuilder`, процесс обхода конфигураций и роль `CompilerPasses`.
2. **Autowiring (Автоматическое внедрение):** Я разберу, как Symfony использует Reflection API, чтобы сопоставить типы в конструкторах с доступными сервисами.
3. **Runtime (Первый запрос):** Я объясню принцип **Lazy Loading** (ленивой загрузки) и то, как сервис превращается из описания в живой объект.

Важный нюанс: многие думают, что контейнер «ищет» сервисы в момент запроса. Это не так. В продакшене контейнер — это уже скомпилированный PHP-файл, где всё прописано жестко.

---

### Ответ

Работа DI-контейнера в Symfony делится на два принципиально разных этапа: сборка (компиляция) и выполнение (runtime).

#### 1. Компиляция контейнера (Compile-time)
Когда вы очищаете кэш или запускаете приложение в режиме `dev`, Symfony запускает процесс сборки контейнера. Это происходит один раз и результат сохраняется в кэш в виде готового PHP-класса.

**Что происходит в этот момент:**
1. **Загрузка конфигурации:** Symfony собирает все определения (definitions) из YAML, XML, PHP файлов и атрибутов. Каждое определение — это не сам объект, а «рецепт» его создания.
2. **Обработка Autowiring:** Symfony анализирует конструкторы ваших классов через **Reflection API**. Она смотрит на type-hints (например, `UserRepository $repo`) и ищет в своих «рецептах» сервис, который соответствует этому типу.
3. **Compiler Passes (Проходы компиляции):** Это самый важный этап. Контейнер проходит по всем своим определениям несколько раз. На этом этапе происходят оптимизации:
    * **Dependency Resolution:** Проверка, что все зависимости существуют и нет циклических ссылок.
    * **Service Decoration:** Если вы используете декораторы, именно здесь они «оборачиваются».
    * **Removing unused services:** Если сервис не используется ни одним другим сервисом, он может быть удален из контейнера для экономии памяти.
4. **Генерация PHP-файла:** В итоге Symfony берет все эти выводы и записывает их в один огромный PHP-файл в директории `var/cache/...`. Этот файл содержит методы, которые просто создают объекты через `new`.

#### 2. Как работает Autowiring
Autowiring — это не магия, а умное сопоставление типов во время компиляции.

* Когда Symfony видит в конструкторе `public function __construct(LoggerInterface $logger)`, она лезет в свой реестр сервисов.
* Она ищет сервис, который помечен как реализующий `LoggerInterface`.
* Если найдено несколько (например, `MonologLogger` и `NullLogger`), и вы не указали конкретный, Symfony выдаст ошибку на этапе компиляции.
* **Важно:** Autowiring работает на этапе **компиляции**, а не в момент выполнения запроса. В итоговом скомпилированном контейнере никакой рефлексии уже нет — там просто написано: `return new MyService(new MonologLogger());`.

#### 3. Момент запроса сервиса (Runtime)
Когда вы впервые вызываете `$container->get(MyService::class)` (или когда сервис запрашивается через injection в контроллере), происходит следующее:

1. **Проверка наличия:** Контейнер проверяет, был ли этот сервис уже создан.
2. **Создание (Instantiating):** Если сервис еще не создан, контейнер берет «рецепт» из скомпилированного файла. 
3. **Построение графа зависимостей:** Он идет по цепочке: чтобы создать `MyService`, ему нужен `Repository`, а для `Repository` нужен `Connection`. Он создает их в правильном порядке.
4. **Singleton (Shared services):** По умолчанию все сервисы в Symfony являются **Shared** (синглтонами). Это значит, что после того, как сервис создан первый раз, он сохраняется внутри контейнера в приватном массиве. При втором запросе тот же самый экземпляр будет отдан мгновенно.

**Резюме процесса:**
* **Компиляция:** Из кучи конфигов и рефлексии создается один оптимизированный PHP-файл.
* **Autowiring:** Происходит во время компиляции, связывая типы с именами сервисов.
* **Runtime:** Контейнер просто берет готовый «рецепт» из файла, создает объект (если его еще нет) и кэширует его. Это делает Symfony невероятно быстрой даже при огромном количестве сервисов.

### ↳ Углубление

### Рассуждение

Циклические зависимости (Circular Dependencies) — это ситуация, когда Сервис А требует Сервис Б, а Сервис Б требует Сервис А. В классическом DI-контейнере это приводит к бесконечной рекурсии при попытке создать любой из них: `A -> B -> A -> B...` и, в конечном итоге, к `Fatal error: Allowed memory size exhausted` или переполнению стека.

Прежде чем предлагать решение, я должен проанализировать **причину** появления цикла. Цикл — это почти всегда симптом архитектурной ошибки. Обычно это происходит в двух случаях:
1. **Нарушение SRP:** Два сервиса слишком тесно связаны, потому что они пытамысь делать одну и ту же работу или знают слишком много друг о друге.
2. **Неправильное распределение ответственности:** Логика, которая должна принадлежать третьему, нейтральному сервису, размазана между А и Б.

Я не считаю правильным просто «заткнуть дыру» техническим костылем, не разбираясь в архитектуре. Однако, в реальной разработке бывают ситуации (например, при рефакторинге legacy-кода), когда нужно быстро решить проблему.

Поэтому я разделяю свои ответы на две категории: **«Исправление архитектуры»** (правильный путь) и **«Технические приемы»** (путь спасения).

---

### Ответ

Я подхожу к решению этой проблемы поэтапно: от поиска архитектурной ошибки до применения технических инструментов.

#### 1. Архитектурное решение (Первый приоритет)

Прежде чем внедрять костыли, я задаю вопрос: «Почему они зависят друг от друга?».

*   **Выделение третьего сервиса (Extraction):** Если А и Б зависят друг от друга, значит, у них есть общая логика. Я выделяю эту логику в новый Сервис В, который оба сервиса будут использовать.
    * *Пример:* `OrderService` требует `EmailService`, а `EmailService` требует `OrderService` для получения данных о заказе. **Решение:** Создать `OrderDataFormatter`, который будет подготавливать данные для письма, и использовать его в обоих местах.
*   **Перенос ответственности:** Возможно, один из сервисов слишком «раздут». Я смотрю, можно ли перенести часть методов из одного сервиса в другой, чтобы разорвать цикл.
*   **Использование событий (Event Dispatcher):** Это лучший способ разорвать жесткую связь. Вместо того чтобы Сервис А вызывал метод Сервиса Б, Сервис А должен просто выбросить событие `SomethingHappened`. Сервис Б подпишется на это событие. Теперь А ничего не знает о Б, и цикл разорван.

#### 2. Технические решения (Если архитектуру менять нельзя/нельзя сейчас)

Если архитектурное исправление невозможно (например, мы работаем с чужим кодом или жестким дедлайном), я использую следующие инструменты:

*   **Lazy Services (Ленивые прокси):** В Symfony это стандартный способ. Вместо реального объекта в конструктор подставляется «прокси-объект» (Proxy object). Этот прокси выглядит как ваш сервис, но он не инициализирует реальный объект, пока вы не вызовете у него какой-либо метод.
    * *Как это работает:* Контейнер создает «пустышку». Цикл обрывается, так как создание `Service A` завершается созданием «пустышки» `Service B`, не запуская создание реального `Service B`.
    * *В Symfony:* Это делается через тег `lazy: true` в конфигурации сервиса.

*   **Setter Injection (Внедрение через сеттер):** Вместо того чтобы требовать сервис в конструкторе (Constructor Injection), я позволяю внедрить его позже через метод.
    * *Как это работает:* Мы создаем `Service A` (без `Service B`), затем создаем `Service B` (без `Service A`), а потом вызываем `$serviceA->setServiceB($serviceB)`. Это разрывает цикл при создании объектов.
    * *Минус:* Это нарушает принцип неизменяемости (immutability) и делает объект потенциально невалидным до вызова сеттера.

*   **Интерфейс вместо реализации:** Иногда цикл возникает из-за того, что мы пытаемся внедрить слишком тяжелую реализацию. Если я внедрю только узкий интерфейс, это не уберет цикл физически, но поможет сделать зависимости более прозрачными и иногда упрощает переход на ленивую загрузку.

**Мой алгоритм действий:**
1. Попытаться разорвать цикл через **Event Dispatcher** (самый чистый способ).
2. Если не помогает — выделить общую логику в **третий сервис**.
3. Если это невозможно — применить **Lazy Services** (проксирование).
4. В крайнем случае (если это legacy и нельзя использовать прокси) — использовать **Setter Injection**.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

### Рассуждение

Эта задача — классический пример разделения **синхронного** (критичного для пользователя) и **асинхронного** (фонового) выполнения. 

Главная цель: минимизировать время ответа (Latency) и обеспечить надежность (Reliability). Если мы будем отправлять письмо и обновлять индекс прямо в контроллере, то:
1. Пользователь будет ждать, пока почтовый сервер ответит (а это может занять секунды).
2. Если индекс поиска упадет, регистрация тоже может завершиться ошибкой (хотя пользователь уже создан).
3. При высокой нагрузке синхронные задачи «забьют» PHP-FPM воркеры, и сайт перестанет отвечать.

Я буду рассматривать три варианта реализации: от самого простого до промышленного стандарта.

---

### Ответ

Я буду строить решение на основе разделения ответственности: контроллер (или Application Service) только сохраняет пользователя и инициирует события, а всё остальное происходит «за кулисами».

#### Вариант 1: Symfony Messenger + Транспорт (Промышленный стандарт)

Это наиболее правильный и масштабируемый подход для Enterprise-разработки.

**Как это устроено:**
1. В `UserService::register()` после успешного сохранения пользователя в БД я отправляю **Message** (простой DTO, например, `UserRegisteredEvent`) в шину сообщений (Message Bus).
2. Symfony Messenger перехватывает это сообщение и отправляет его в **Transport** (очередь).
3. Отдельный процесс (Worker), запущенный в консоли, слушает очередь и вызывает соответствующие **Handlers** (обработчики): `SendWelcomeEmailHandler` и `UpdateSearchIndexHandler`.

**Транспорты (где хранить очередь):**
* **Doctrine (Database):** Сообщения хранятся в таблице БД. Хорошо для начала, не требует новой инфраструктуры.
* **Redis/RabbitMQ:** Идеально для высокой нагрузки. Очень быстрые, поддерживают сложные сценарии.

**Trade-offs:**
* **Плюсы:** Максимальная скорость ответа пользователю; высокая надежность (если письмо не ушло, Messenger попробует еще раз — механизм **Retry**); возможность масштабировать воркеры независимо от веб-сервера.
* **Минусы:** Усложнение инфраструктуры (нужно следить за воркерами, настраивать RabbitMQ/Redis); риск «состояния гонки» (race condition), если воркер попытается найти пользователя в БД раньше, чем транзакция регистрации завершится.

#### Вариант 2: Symfony Messenger + `sync` транспорт (Быстрый прототип)

Если проект на ранней стадии и мы хотим использовать архитектуру Messenger, но не хотим настраивать RabbitMQ.

**Как это устроено:**
Мы настраиваем шину так, чтобы сообщения отправлялись в транспорт `sync`. В этом случае обработчики вызываются **сразу же** в том же процессе.

**Trade-offs:**
* **Плюсы:** Архитектура уже готова к переходу на RabbitMQ (нужно только поменять конфиг); код чистый и разделенный.
* **Минусы:** **Это не решает проблему задержки.** Пользователь всё равно будет ждать завершения отправки письма и обновления индекса. Это лишь «обертка» над синхронным кодом.

#### Вариант 3: Использование Symfony Workflow (Если есть сложный жизненный цикл)

Если регистрация пользователя — это не просто действие, а процесс (например, «регистрация -> подтверждение почты -> активация»), я бы использовал компонент **Workflow**.

**Как это устроено:**
Мы определяем переходы (transitions) между состояниями пользователя. Переходы могут триггеть события, которые затем подхватываются Messenger.

**Trade-offs:**
* **Плюсы:** Позволяет визуализировать и строго контролировать бизнес-процесс.
* **Минусы:** Избыточно для простой задачи «зарегистрировал и забыл».

---

### Мой итоговый выбор и архитектурный план

Для реального продакшн-приложения я выберу **Вариант 1 (Messenger + RabbitMQ/Redis)**. 

**Мой план реализации:**

1.  **Транзакционная целостность (Важно!):** Я оберну сохранение пользователя в БД и отправку сообщения в очередь в одну транзакцию (или использую паттерн **Outbox**). Это гарантирует, что мы не отправим письмо о регистрации, если транзакция создания пользователя откатилась.
2.  **Слой Application:**
    ```php
    public function register(UserDto $dto): void 
    {
        $this->entityManager->wrapInTransaction(function() use ($dto) {
            $user = $this->userFactory->create($dto);
            $this->userRepository->save($user);
            
            // Отправляем сообщение в шину. Оно уйдет в RabbitMQ.
            $this->messageBus->dispatch(new UserRegisteredEvent($user->getId()));
        });
    }
    ```
3.  **Слой Handlers:** Создам два независимых хендлера. Это позволит, например, при сбое обновления индекса (Search Index Down) не мешать отправке писем.
4.  **Настройка Retry:** В конфиге Symfony настрою `retry_strategy` (например, 3 попытки с экспоненциальной задержкой), чтобы кратковременные сбои внешних API не приводили к потере данных.

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

### Рассуждение

Вопрос затрагивает три фундаментальных уровня безопасности в Symfony: **кто** пользователь (Authentication), **что** ему разрешено в общих чертах (Roles) и **может ли он** совершить конкретное действие над конкретным объектом (Voters/Authorization).

Многие разработчики путают эти понятия, пытаяясь решить задачу через роли, что приводит к «взрыву» количества ролей в системе (например, `ROLE_EDIT_POST_1`, `ROLE_EDIT_POST_2`). 

Я разделяю этот процесс на три этапа:
1. **Authentication (Личность):** Проверка учетных данных (пароль, токен, OAuth). Результат — объект `User`.
2. **Role-Based Access Control (RBAC):** Грубая фильтрация на уровне доступа к URL или группам функций.
3. **Attribute-Based Access Control (ABAC) через Voters:** Тонкая настройка прав на основе логики и контекста (владелец ли это объекта? активен ли он?).

---

### Ответ

В Symfony контроль доступа разделен на две четкие области: **Authentication** (кто ты?) и **Authorization** (что тебе можно?).

#### 1. Authentication (Аутентификация)
Это процесс подтверждения личности. Symfony использует систему `Authenticators`. Когда приходит запрос, соответствующий `Firewall`, Symfony запускает цепочку аутентификаторов.
* Если данные верны, создается `Token` (внутри `TokenStorage`), который связывает текущий запрос с объектом `User`.
* Это происходит до того, как мы начнем проверять права.

#### 2. Roles (Роли)
Роли — это простая иерархическая система прав. Это «грубый инструмент».
* Мы используем роли для доступа к разделам приложения (например, `/admin` доступен только `ROLE_ADMIN`).
* Роли хорошо работают, когда права зависят только от статуса пользователя, а не от данных.

#### 3. Voters (Вотеры)
Voters — это механизм реализации сложной логики авторизации. Это классы, которые реализуют интерфейс `VoterInterface` и отвечают на вопрос: «Разрешено ли этому пользователю выполнить это действие (`attribute`) над этим объектом (`subject`)?».

Внутри вотера мы получаем:
* `TokenInterface` (текущий пользователь).
* `attribute` (например, `'POST_EDIT'`).
* `subject` (сам объект, например, экземпляр `Post`).

---

### Когда выбирать Roles, а когда Voters?

Это ключевой архитектурный вопрос. Мой критерий выбора — **зависимость от контекста (данных)**.

#### Выбирай ROLES, если:
Доступ зависит **только от типа пользователя** и не зависит от того, над каким именно объектом совершается действие.
* *Пример:* «Только администратор может зайти в панель управления».
* *Пример:* «Только менеджеры могут видеть отчеты».
* *Код:* `#[IsGranted('ROLE_ADMIN')]` в контроллере.

#### Выбирай VOTERS, если:
Доступ зависит от **состояния объекта** или **связи между пользователем и объектом**. Как только в условии появляется слово **«свой»**, **«созданный в это время»** или **«в статусе X»** — это работа для вотера.
* *Пример:* «Пользователь может редактировать пост, **только если он его автор**». (Нужно сравнить `user.id` и `post.author_id`).
* *Пример:* «Редактировать статью можно, **только если она находится в черновике**». (Нужно проверить `post.status`).
* *Пример:* «Просматривать документ можно, **только если у организации пользователя есть подписка**». (Нужно проверить связь через сервис).

#### Сравнительная таблица

| Критерий | Roles (RBAC) | Voters (ABAC) |
| :--- | :--- | :--- |
| **Объект** | Нет (только тип пользователя) | Да (обязательно проверяется `subject`) |
| **Сложность** | Низкая | Средняя/Высокая |
| **Гибкость** | Низкая (статично) | Высокая (динамически) |
| **Типичный кейс** | Доступ к `/admin` | "Могу ли я нажать кнопку 'Удалить' на этом конкретном товаре?" |

**Мой совет:** Если вы начинаете плодить роли типа `ROLE_OWNER_OF_POST`, вы нарушаете архитектуру. Немедленно создавайте Voter. Роли — это для структуры, вотеры — для бизнес-логики.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

### Рассуждение

Это фундаментальный вопрос при проектировании доменного слоя с использованием Doctrine. Проблема в том, что Doctrine — это **Data Mapper**, который ориентирован на работу с «плоскими» данными и жизненным циклом сущностей (Entities), в то время как **Value Objects (VO)** по своей природе — это неизменяемые (immutable) объекты, которые не имеют своего ID и не живут независимо от сущности.

Когда мы говори Immutability и валидность, мы сталкиваемся с конфликтом: Doctrine хочет «втихую» менять свойства объекта через рефлексию (setters или direct property access), а VO должен менять состояние только через создание нового экземпляра.

Я рассмотрю три основных спосо never-ending debate в сообществе:
1. **Embeddables** (родной механизм Doctrine).
2. **Custom Types** (создание своего типа данных).
3. **Serialization (JSON/String)** (хранение как строка или JSON).

Также я затрону проблему **"Leakage of Doctrine into Domain"** — когда детали маппинга начинают диктовать правила домена.

---

### Ответ

Для хранения Value Object в Doctrine существует три основных подхода. Выбор зависит от того, насколько сложен ваш VO и как вы планируете его использовать в запросах.

#### 1. Doctrine Embeddables (Рекомендуемый путь для простых VO)
Это встроенный механизм, который позволяет маппить VO как набор колонок в той же таблице, где находится Entity.

*   **Как это работает:** Вы помечаете класс атрибутом `#[Embeddable]`, а в Entity используете `#[Embedded]`.
*   **Пример:** `Address` (city, street, zip). В БД это будут колонки `address_city`, `address_street` и т.д.

**Плюсы:**
*   **Queryability:** Вы можете легко искать по полям VO в DQL/SQL (`WHERE a.address.city = :city`).
*   **Типизация:** Все поля остаются типизированными колонками БД.

**Минусы и подводные камни:**
*   **Сложность:** Если VO очень сложный (содержит коллекции), Embeddables не подойдут.
*   **Валидация:** Важно, чтобы валидация происходила в конструкторе VO, а не в Entity. Doctrine при загрузке из БД вызывает конструктор (или заполняет свойства через рефлексию), поэтому VO должен быть готов к работе сразу.

#### 2. Custom Doctrine Types (Для атомарных VO)
Если ваш VO — это что-то однородное (например, `Money`, `Email`, `Color`), лучше всего создать свой тип данных.

*   **Как это работает:** Вы реализуете `Doctrine\DBAL\Types\Type` и переопределяете методы `convertToDatabaseValue` и `convertToPHPValue`.
*   **Пример:** VO `Money(amount, currency)` может храниться в одной колонке как строка `100_USD`.

**Плюсы:**
*   **Чистота Entity:** В Entity это выглядит как обычное поле: `private Money $price;`.
*   **Атомарность:** Объект хранится как одна единица в БД.

**Минусы и подводные камни:**
*   **Потеря Queryability:** Вы не сможете легко написать запрос «найти все товары дороже 100 рублей», если цена лежит в колонке-строке `100_USD`. Вам придется использовать сложные SQL-функции парсинга строк.
*   **Сложность реализации:** Нужно корректно обрабатывать преобразование типов и ошибки.

#### 3. JSON Serialization (Для сложных, иерархических VO)
Если VO представляет собой сложную структуру или древовидный объект.

*   **Как это работает:** Вы используете тип `json` в Doctrine и в Entity используете `json_encode`/`json_decode` (или интеграцию с Symfony Serializer) в методах доступа.

**Плюсы:**
*   **Гибкость:** Можно хранить любую структуру без изменения схемы БД.

**Минусы и подводные камни:**
*   **Полная потеря типизации на уровне БД:** БД видит только текст.
*   **Тяжелые запросы:** Поиск внутри JSON — это всегда удар по производительности (даже с поддержкой JSONB в PostgreSQL, это сложнее, чем обычные колонки).

---

### Сводная таблица и вердикт

| Метод | Когда использовать | Поиск (Query) | Сложность VO |
| :--- | :--- | :--- | :--- |
| **Embeddables** | Когда у VO есть несколько полей (Address, Period) | **Отлично** | Средняя |
| **Custom Types** | Когда VO — это одна сущность (Money, Email) | **Плохо** | Низкая |
| **JSON** | Когда VO — это глубокая структура/дерево | **Средне/Плохо** | Высокая |

**Мой профессиональный выбор:**

1. Если VO состоит из нескольких логически связанных полей (как `Address`) — я всегда использую **Embeddables**. Это дает лучший баланс между чистотой домена и возможностью делать эффективные SQL-запросы.
2. Если VO — это атомарное значение (как `Email` или `Color`) — я использую **Custom Types**.
3. **Главный совет по неизменяемости:** Чтобы гарантировать неизменяемость, я всегда использую `readonly` свойства в PHP 8.2+ для классов VO. Это гарантирует на уровне языка, что даже если Doctrine попытается что-то изменить через рефлексию, она столкнется с ошибкой, что заставит нас проектировать систему правильно.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

### Рассуждение

Это вопрос о том, как подружить паттерн **Aggregate** из DDD с реализацией **Data Mapper** в Doctrine. Это классическая точка конфликта. 

В DDD **Агрегат** — это граница целостности. Все изменения внутри агрегата должны проходить через **Aggregate Root (AR)**. Никто не должен менять дочерние сущности напрямую, минуя корень.
В Doctrine же всё работает через `Unit of Work`: вы можете достать любую сущность из репозитория и изменить её, и Doctrine это «проглотит».

Я выделяю три критические проблемы, которые нужно решить:
1. **Инкапсуляция коллекции:** Как запретить внешнему коду делать `$aggregate->getItems()->add($item)`, тем самым обходя правила агрегата?
2. **Границы транзакции:** Как гарантировать, что всё, что касается агрегата, сохранится атомарно?
3. **Управление жизненным циклом:** Кто «владеет» процессом сохранения?

Я возьму для примера агрегат `Order` (Корень) и коллекцию `OrderItem` (Дочерние сущности).

---

### Ответ

#### 1. Маппинг и инкапсуляция коллекции
Главная ошибка — возвращать из агрегата обычную `ArrayCollection`. Это дает доступ к методам `add()` и `remove()` извне, что разрушает инкапсуляцию.

**Как делать правильно:**
* В маппинге используем `orphanRemoval: true`. Это критически важно: если мы удаляем элемент из коллекции в коде, Doctrine должна физически удалить строку из БД.
* Из агрегата мы возвращаем коллекцию только для чтения (через `ArrayIterator` или преобразование в массив).

```php
#[ORM\Entity]
class Order // Aggregate Root
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    /** @var Collection<int, OrderItem> */
    #[ORM\OneToMany(mappedBy: 'order', targetEntity: OrderItem::class, cascade: ['persist', 'remove'], orphanRemoval: true)]
    private Collection $items;

    public function __construct() {
        $this->items = new ArrayCollection();
    }

    // Метод для добавления (бизнес-логика внутри корня)
    public function addItem(Product $product, int $quantity): void 
    {
        if ($quantity <= 0) throw new \InvalidArgumentException("Quantity must be > 0");
        
        // Проверка бизнес-правила: нельзя добавить один и тот тот же товар дважды
        // Вместо этого мы обновляем количество существующего
        $existing = $this->items->filter(fn(OrderItem $item) => $item->getProduct()->equals($product))->first();
        
        if ($existing) {
            $existing->addQuantity($quantity);
        } else {
            $this->items->add(new OrderItem($this, $product, $quantity));
        }
    }

    // Возвращаем только для чтения!
    /** @return array<int, OrderItem> */
    public function getItems(): array 
    {
        return $this->items->toArray();
    }
}
```

#### 2. Границы транзакции
Транзакция должна охватывать весь процесс изменения агрегата. В Symfony/Doctrine это реализуется на уровне **Application Service**. 

Агрегат не должен знать о транзакциях. Транзакция — это инфраструктурная деталь.

#### 3. Кто и когда вызывает `flush()`?
Это самый частый спор. 
* **Антипаттерн:** Вызывать `flush()` внутри методов агрегата или репозитория. Это делает систему непредсказуемой.
* **Правильный подход:** `flush()` вызывается один раз в конце операции в **Application Service** (или через Middleware/Event Listener).

---

### Полная схема работы (Пример)

**Application Service (Координатор):**

```php
class PlaceOrderService
{
    public function __construct(
        private OrderRepositoryInterface $orderRepository,
        private EntityManagerInterface $entityManager, // Используем для управления транзакцией
    ) {}

    public function execute(OrderDto $dto): void
    {
        // 1. Открываем транзакцию
        $this->entityManager->wrapInTransaction(function() use ($dto) {
            
            // 2. Загружаем или создаем агрегат
            $order = new Order(); 

            // 3. Выполняем бизнес-действия через корень
            foreach ($dto->items as $itemDto) {
                $product = $this->productRepository->find($itemDto->productId);
                $order->addItem($product, $itemDto->quantity);
            }

            // 4. Сохраняем агрегат. 
            // Благодаря cascade: ['persist'], Doctrine сама увидит новые OrderItem
            $this->orderRepository->save($order);
            
            // При выходе из wrapInTransaction автоматически вызовется flush() 
            // и commit() транзакции.
        });
    }
}
```

### Итоговые правила проектирования:

1.  **Инкапсуляция:** Коллекция внутри агрегата — `ArrayCollection`, снаружи — `array`. Изменения — только через методы корня (`addItem`, `removeItem`).
2.  **Маппинг:** Всегда используйте `orphanRemoval: true` для дочерних сущностей, иначе удаление из коллекции не удалит запись из БД.
3.  **Cascade:** Используйте `cascade: ['persist', 'remove']`, чтобы управлять жизненным циклом детей через корень.
4.  **Транзакции:** Граница транзакции — это один Use Case (один метод Application Service).
5.  **Flush:** Вызывается один раз в конце Use Case. Никогда не вызывайте `flush()` внутри доменного слоя.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

### Рассуждение

Проблема N+1 — это классическая ловушка ORM. Она возникает, когда мы загружаем коллекцию сущностей одним запросом, а затем в цикле обращаемся к связанным объектам, заставляя Doctrine делать отдельный SQL-запрос для каждой итерации.

Прежде чем бросаться исправлять код, я должен следовать инженерному подходу: **«Не оптимизируй то, что не доказано»**. Я не буду менять код, основываясь на «ощущении», что страница тормозит.

Мой план действий:
1. **Диагностика:** Точное определение количества и типа запросов.
2. **Классификация:** Понимание, где именно происходит «взрыв» запросов (в репозитории, в Twig-шаблоне или в сериализаторе).
3. **Решение:** Выбор метода в зависимости от контекста (Eager Loading, Join, DTO).

---

### Ответ

#### 1. Диагностика

Первым делом я должен увидеть реальные SQL-запросы, которые генерирует приложение.

*   **Symfony Profiler (самый быстрый способ):** Я открываю вкладку **Doctrine** в профилировщике. Там есть раздел "Queries", где я сразу увижу дублирующиеся запросы. Если я вижу 50 одинаковых запросов к таблице `user`, значит, у меня N+1.
*   **Logging:** В локальной разработке я включаю логирование SQL в консоль или файл.
*   **Blackfire.io / Tideways:** Если проблема на стейджинге или сложнее, чем просто N+1 (например, тяжелая гидратация), я использую профайлеры, которые показывают дерево вызовов и время, затраченное на каждый запрос.

#### 2. Способы решения и их Trade-offs

Я выделяю три основных метода решения, каждый из которых имеет свои нюансы.

##### Способ А: Fetch Join (Eager Loading через DQL)
Это самый распространенный метод. Вместо того чтобы просто делать `findAll()`, мы пишем запрос, который явно присоединяет (JOIN) нужные сущности и выбирает их сразу.

```php
// В репозитории
public function findAllWithUsers(): array
{
    return $this->createQueryBuilder('o')
        ->addSelect('u') // Важно! Мы говори Selct-им связанные сущности
        ->leftJoin('o.user', 'u')
        ->getQuery()
        ->getResult();
}
```

*   **Плюсы:** Решает проблему одним запросом; данные сразу попадают в Identity Map Doctrine.
*   **Минусы:** 
    *   **Cartesian Product (Декартово произведение):** Если вы делаете `leftJoin` сразу на несколько коллекций (например, `orders` и `items`), количество строк в результате запроса растет экспоненциально, что убивает память и производительность.
    *   **Тяжелая гидратация:** Чем больше данных мы тянем одним запросом, тем больше времени Doctrine тратит на превращение строк SQL в объекты PHP.

##### Способ Б: Entity Graphs / Batch Loading (через Fetch Mode)
В маппинге можно указать `fetch="EAGER"`.

*   **Плюсы:** Удобно, если связь используется почти всегда.
*   **Минусы:** **Очень опасно.** Это делает загрузку «всегда жадной». Если в одном месте вам нужны только `Order`, а в другом — `Order + User`, то при использовании `EAGER` вы будете всегда тянуть `User`, даже когда он не нужен. Это создает скрытые проблемы с производительностью в других частях системы. **Я практически никогда не использую этот способ в Enterprise-проектах.**

##### Способ В: Использование DTO (Data Transfer Objects)
Если нам не нужны полноценные объекты с методами и жизненным циклом, а нужно просто вывести список данных на страницу, я отказываюсь от гидратации сущностей в пользу DTO.

```php
// В репозитории
public function findOrderSummaries(): array
{
    return $this->createQueryBuilder('o')
        ->select(sprintf('new %s(o.id, u.email, o.total)', OrderSummary::class))
        ->join('o.user', 'u')
        ->getQuery()
        ->getResult();
}
```

*   **Плюсы:** 
    *   **Невероятная скорость:** Мы не тратим ресурсы на создание тяжелых объектов `Entity` и отслеживание их изменений (Unit of Work).
    *   **Минимальный объем памяти:** Мы тянем только те поля, которые реально нужны для отображения.
*   **Минусы:** 
    *   **Отсутствие функционала:** Полученный DTO — это просто набор данных, вы не сможете вызвать на нем метод `order->cancel()`.
    *   **Дублирование кода:** Приходится создавать классы DTO.

#### Резюме: когда и что выбирать?

1.  Если мне нужны **полноценные сущности** для дальнейшей работы (изменение, удаление) $\rightarrow$ использую **Fetch Join** в конкретном методе репозитория.
2.  Если мне нужно просто **отобразить список** (Read-only) $\rightarrow$ я выбираю **DTO**. Это самый эффективный способ для высоконагруженных страниц.
3.  Если я вижу **Cartesian Product** (слишком много Join-ов) $\rightarrow$ я разделяю загрузку на два запроса: первый загружает основные сущности, второй — связанные коллекции (Doctrine эффективно «подтянет» их в Identity Map при втором запросе).

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

### Рассуждение

Этот вопрос проверяет понимание концепции **«Defense in Depth» (эшелонированная оборона)**. 

Многие разработчики попадают в ловушку мышления: «Раз у меня есть валидация в доменном слое (Entity/Value Object) и в Application Service, то база данных — это просто хранилище». Это опасное заблуждение. 

Я рассматриваю валидацию на двух уровнях:
1. **Бизнес-валидация (Application/Domain level):** Она отвечает на вопрос «Корректно ли это с точки зрения бизнес-процесса?». Она богатая, она может обращаться к внешним API, к другим сервисам, она понимает контекст.
2. **Техническая целостность (Database level):** Она отвечает на вопрос «Могут ли данные в этой таблице нарушить физическую или логическую структуру системы?».

**Почему нельзя полагаться только на код?**
* **Множественность точек входа:** Приложение — это не единственный способ попасть в БД. Есть миграции, есть аналитические скрипты, есть прямые правки от DBA, есть другие микросервисы (на Python, Go и т.д.). Если логика только в PHP, любой другой клиент может «сломать» данные.
* **Race Conditions (Состояние гонки):** Код приложения работает в изолированных процессах. Два параллельных запроса могут пройти бизнес-валидацию одновременно (например, проверка остатка товара), а затем оба попытаются списать товар, приведя к отрицательному балансу. БД — единственный компонент, имеющий глобальное знание о состоянии через транзакции и блокировки.
* **Производительность:** База данных гораздо эффективнее находит нарушения структуры (например, дубликаты) на уровне движка, чем приложение на уровне перебора объектов.

---

### Ответ

Я придерживаюсь принципа: **Бизнес-логика живет в коде, а правила целостности — в базе данных.** 

Я использую ограничения PostgreSQL как «последний рубеж обороны», который гарантирует, что даже при баге в коде или стороннем доступе данные не превратятся в мусор.

#### Какие средства я использую и когда:

**1. Primary Keys и Unique Constraints (Уникальность)**
Это база. Если поле должно быть уникальным (email, slug, артикул), я **обязательно** вешаю `UNIQUE` индекс.
* *Зачем:* Защита от Race Condition. Код может проверить `if (!$userRepository->findByEmail($email))`, но в миллисекунду между проверкой и сохранением придет второй такой же запрос. Только `UNIQUE` constraint на уровне БД гарантирует, что второй запрос упадет с ошибкой.

**2. Foreign Key Constraints (Ссылочная целостность)**
Я всегда использую `FOREIGN KEY` со строгим определением поведения (`ON DELETE RESTRICT` или `ON DELETE CASCADE`).
* *Зачем:* Чтобы не возникло ситуации «сиротских» записей (например, заказ без существующего пользователя), что является фатальным для аналитики и логики приложения.

**3. NOT NULL Constraints (Обязательность)**
Все поля, которые не могут быть пустыми по логике, должны иметь `NOT NULL`.
* *Зачем:* Чтобы избежать `NullPointerException` (или `TypeError` в PHP) в самых неожиданных местах, когда код ожидает объект, а получает `null` из-за ошибки в миграции или стороннего скрипта.

**4. Check Constraints (Проверка диапазонов и форматов)**
Это мощный инструмент PostgreSQL, который часто игнорируют.
* *Зачем:* Если у нас есть поле `price` или `age`, я вешаю `CHECK (price > 0)`.
* *Пример:* Даже если в коде случится баг и в поле цены запишется `-100`, база просто отклонит транзакцию. Это гарантирует, что финансовые отчеты никогда не «поплывут».

**5. Domain-specific Constraints (Сложные правила)**
Для очень критичных вещей я использую триггеры или сложные ограничения, хотя стараюсь их избегать, чтобы не усложнять логику. Но если правило должно соблюдаться *всегда и везде* (например, сумма строк в инвойсе должна быть равна итогу в инвойсе), я рассмотрю возможность реализации этого на уровне БД.

#### Резюме (Trade-offs)

| Уровень | Что проверяет | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Код (Domain/App)** | Бизнес-смыслы, сложные связи, контекст | Гибкость, понятные ошибки для пользователя, легкая поддержка | Уязвимость к Race Conditions и внешним клиентам |
| **База (PostgreSQL)** | Структура, уникальность, математическая корректность | Абсолютная надежность, защита от параллелизма, универсальность | Сложность отладки, "дорогая" ошибка (нужно обрабатывать исключения БД) |

**Мой подход:** Я пишу подробную валидацию в PHP, чтобы давать пользователю красивые сообщения об ошибках, но я дублирую критические правила (Unique, Not Null, Check) в схеме БД, чтобы спать спокойно.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

### Рассуждение

Когда я слышу «запрос тормозит», я не бросаюсь сразу добавлять индексы. Это самая частая ошибка — «лечение симптомов вместо болезни». Добавление лишних индексов может замедлить вставку (INSERT/UPDATE) и только запутать планировщик запросов.

Мой процесс всегда строится на переходе от **наблюдения** к **гипотезе** и затем к **проверке**. Я делю процесс на три этапа:
1. **Локализация:** Понять, это медленный запрос, медленная БД, проблемы с сетью или неэффективная гидратация в PHP.
2. **Анализ плана выполнения:** Понять, как именно PostgreSQL «думает» об этом запросе.
3. **Оптимизация:** Выбор конкретного инструмента (индексы, переписывание запроса, изменение структуры).

---

### Ответ

Процесс оптимизации для меня — это детективная работа. Я иду по пути от внешних симптомов к внутренним механизмам.

#### 1. Диагностика (Где проблема?)

Первым делом я должен понять, на чьей стороне затык.

*   **Инструменты:**
    *   **`EXPLAIN ANALYZE`:** Мой главный инструмент. Без него любая оптимизация — это гадание. Он показывает не только план, но и реальное время выполнения каждого узла.
    *   **`pg_stat_statements`:** Расширение, которое показывает статистику по всем запросам в базе. Помогает найти «самые тяжелые» запросы в системе (top CPU/IO consumers), а не только тот, который я тестирую вручную.
    *   **PostgreSQL Logs:** Проверяю параметры `log_min_duration_statement`, чтобы увидеть медленные запросы в логах сервера.
    *   **Application Profiling (Blackfire/Tideways):** Чтобы исключить ситуацию, когда тормозит не SQL, а Doctrine при попытке превратить 10 000 строк в объекты (проблема гидратации).

#### 2. Анализ плана (Что делает база?)

Когда я нашел проблемный запрос, я запускаю `EXPLAIN (ANALYZE, BUFFERS)`. Я смотрю на:
*   **Sequential Scan vs Index Scan:** Если я вижу `Seq Scan` на огромной таблице там, где должен быть индекс — это первая точка роста.
*   **Cost vs Actual Time:** Если планировщик ошибается в оценке стоимости (Cost), значит, у него устаревшая статистика.
*   **Rows (Estimated vs Actual):** Если база ожидает 1 строку, а получает 1 000 000 — это проблема со статистикой или очень сложным Join.
*   **Buffers:** Смотрю, сколько данных читается с диска (Read) и сколько из кэша (Hit). Если `Read` очень много — нам не хватает оперативной памяти (shared_buffers) или индексов.

#### 3. Типовые причины и способы решения

Я выделяю четыре основные группы проблем:

**А. Отсутствие или неэффективность индексов**
*   *Причина:* Запрос идет по полю, на котором нет индекса, или индекс не подходит (например, поиск по `LIKE '%value%'` не использует обычный B-tree индекс).
*   *Решение:* Добавить индекс. Если это поиск по части строки — использовать `pg_trgm` (trigram index). Если это поиск по диапазону дат — проверить, не мешает ли другой индекс.

**Б. Проблема «раздувания» таблиц (Bloat)**
*   *Причина:* В PostgreSQL `UPDATE` — это фактически `DELETE` + `INSERT`. Если в таблице много обновлений, старые версии строк (dead tuples) копятся, и `Seq Scan` начинает читать «мусор».
*   *Решение:* Проверить работу `Autovacuum`. Если он не справляется, нужно оптимизировать частоту обновлений или настроить параметры вакуума более агрессивно.

**В. Неправильное планирование из-за устаревшей статистики**
*   *Причина:* Планировщик выбирает плохой план, потому что думает, что данных мало, а их много.
*   *Решение:* Запустить `ANALYZE <table_name>`, чтобы обновить статистику.

**Г. Проблемы на стороне приложения (Doctrine/ORM)**
*   *Причина:* **N+1 запросов** или **Over-fetching** (выборка всех колонок `SELECT *`, когда нужны только две).
*   *Решение:* Использовать `JOIN FETCH` в DQL или переписать запрос на использование DTO, чтобы не тянуть лишние данные и не нагружать память.

#### Итоговый алгоритм:
1. Замерить время в приложении.
2. Найти запрос через `pg_stat_statements`.
3. Прогнать `EXPLAIN (ANALYZE, BUFFERS)`.
4. Если `Seq Scan` на большой таблице $\rightarrow$ **Индексы**.
5. Если `Rows Estimated` сильно отличается от `Actual` $\rightarrow$ **ANALYZE / Статистика**.
6. Если много `Read` из диска $\rightarrow$ **Индексы или увеличение RAM**.
7. Если запрос быстрый в консоли, но медленный в PHP $\rightarrow$ **Оптимизация гидратации (DTO)**.

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

### Рассуждение

Вопрос об агрегатах — это вопрос о том, как мы управляем **состоянием** и **согласованностью** (consistency) в сложной системе. 

Многие разработчики ошибочно полагают, что Агрегат — это просто «связка таблиц в БД». Это не так. Агрегат — это концепция из области проектирования бизнес-логики. Если мы будем ошибаться с границами агрегатов, мы получим либо «распределенную транзакцию» (когда изменение одной вещи ломает всё), либо «несогласованную систему» (когда бизнес-правила нарушаются из-за того, что части системы живут своей жизнью).

Я буду структурировать ответ так:
1. **Определение:** Что такое Агрегат, Корень (Root) и инвариант.
2. **Критерии границ:** Как я решаю, где заканчивается один агрегат и начинается другой.
3. **Пример:** Наглядная модель (Заказ и Позиции заказа).
4. **Типовая ошибка:** «Раздутый агрегат» (God Aggregate).

---

### Ответ

**Агрегат (Aggregate)** — это кластер связанных объектов (сущностей и Value Objects), который рассматривается как единая единица при изменении данных. 

У агрегата есть две важнейшие составляющие:
1. **Aggregate Root (Корень):** Единственная точка входа. Все внешние объекты могут ссылаться только на Корень. Никто не имеет права менять внутренности агрегата, минуя Корень.
2. **Инварианты:** Это бизнес-правила, которые должны быть всегда истинными внутри агрегата. Например: «Сумма позиций в заказе не может быть отрицательной». Корень отвечает за то, чтобы ни одно действие не нарушило этот инвариант.

#### Как я определяю границы агрегата?

Я использую три правила:

1.  **Правило транзакционной согласованности:** Если изменение объекта А требует немедленного (синхронного) изменения объекта Б, чтобы бизнес-логика оставалась верной — они должны быть в одном агрегате. Если допустима «согласованность в конечном счете» (eventual consistency) — это разные агрегаты.
2.  **Правило минимальной связности:** Агрегат должен быть как можно меньше. Маленькие агрегаты легче масштабировать, они меньше блокируют базу данных и их проще тестировать.
3.  **Правило идентификаторов:** Внутри агрегата объекты могут иметь ссылки на другие объекты (объекты). Но между разными агрегатами связь должна быть **только через ID** (Identity), а не через прямые ссылки на объекты.

#### Пример: Система заказов (E-commerce)

Представим процесс оформления заказа.

* **Агрегат `Order` (Корень):**
    * Содержит `OrderId`, `CustomerId`, `Status`, `TotalAmount`.
    * Содержит коллекцию `OrderItem` (дочерние сущности).
* **Инвариант:** Сумма всех `OrderItem` должна всегда совпадать с `TotalAmount`.

**Как это работает:**
Если клиент хочет добавить товар, он не вызывает `$orderItem->setQuantity()`. Он вызывает `$order->addItem($product, $quantity)`. Внутри этого метода `Order` пересчитывает `TotalAmount`. Таким образом, корень гарантирует, что инвариант не нарушен.

**Граница:** `OrderItem` не может существовать без `Order`. Он — часть агрегата. Но `Product` — это другой агрегат. `Order` хранит только `productId`, а не ссылку на объект `Product`.

#### Типовая ошибка: "Раздутый агрегат" (God Aggregate)

Самая частая ошибка — попытка запихнуть в один агрегат слишком много сущностей, которые связаны между собой.

**Ошибка:** Решить, что `Order` (Заказ), `Customer` (Клиент), `Product` (Товар) и `Warehouse` (Склад) — это один огромный агрегат, потому что «при заказе нужно проверить склад и списать товар у клиента».

**К чему это приведет:**
1. **Проблемы с производительностью:** Каждый раз, когда вы просто хотите сменить статус заказа, вам придется загружать из базы огромный граф объектов (клиента, товары, склад), что создаст гигантскую нагрузку на память и БД.
2. **Блокировки (Concurrency):** Если один менеджер обновляет адрес клиента, а в этот же момент другой менеджер оформляет заказ этому же клиенту, они оба будут пытаться заблокировать одну и ту же строку в БД (или одну и ту же транзакцию), вызывая Deadlocks или ошибки ожидания.
3. **Сложность тестирования:** Чтобы протестировать простой метод заказа, вам придется настраивать моки для всего мира (склад, клиент, товары).

**Правильный путь:** Сделать `Customer`, `Product` и `Warehouse` отдельными агрегатами. Связать их через `Id`. Если при заказе нужно проверить склад — обратитесь к `WarehouseService`, который работает с агрегатом `Warehouse`. Обновление склада произойдет либо в той же транзакции (если это критично), либо через асинхронное событие.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

### Рассуждение

Этот вопрос бьет в самую суть проблем распределенных систем и конкурентного доступа. Когда два процесса одновременно пытаются изменить один и тот тот же агрегат, возникает состояние **Race Condition** (состояние гонки).

Прежде чем отвечать, я должен уточнить: результат зависит от того, как настроена база данных и как реализован уровень доступа к данным. Если мы ничего не предпримем, возникнет ситуация **Lost Update** (потерянное обновление):
1. Процесс А прочитал агрегат (баланс = 100).
2. Процесс Б прочитал агрегат (баланс = 100).
3. Процесс А вычитает 10 и сохраняет (баланс = 90).
4. Процесс Б вычитает 20 и сохраняет (баланс = 80).
**Итог:** Мы потеряли списание в 10 единиц, хотя должно было остаться 70.

Я рассматриваю два основных стратегических подхода для решения этой проблемы: **Optimistic Locking** (Оптимистичная блокировка) и **Pessimistic Locking** (Пессимистичная блокировка). Также я упомяну архитектурный подход через **Event Sourcing**.

---

### Ответ

В проектировании систем я всегда исхожу из того, что конкурентные изменения — это не исключение, а норма. Я выбираю стратегию защиты в зависимости от частоты конфликтов и требований к бизнес-процессу.

#### 1. Optimistic Locking (Оптимистичная блокировка)
Это мой основной выбор для большинства бизнес-процессов. Мы предполагаем, что конфликты случаются редко.

**Как это работает:**
Мы добавляем в агрегат поле `version` (integer). При каждом обновлении мы проверяем, не изменилась ли версия с момента чтения.
* Процесс А читает `version: 1`.
* Процесс Б читает `version: 1`.
* Процесс А сохраняет: `UPDATE ... SET version = 2 WHERE id = 1 AND version = 1`. Успех.
* Процесс Б пытается сохранить: `UPDATE ... SET version = 2 WHERE id = 1 AND version = 1`. **0 строк затронуто**, так как версия уже 2.

**В Symfony/Doctrine:** Это реализуется одной аннотацией `#[ORM\Version]` над полем. Doctrine сама выбросит `OptimisticLockException`.

* **Плюсы:** Не блокирует базу данных, высокая производительность, масштабируемость.
* **Минусы:** Если конфликты происходят часто, пользователю придется постоянно переделывать действия (Retry).
* **Когда использовать:** Когда конфликты редки (например, редактирование профиля пользователя).

#### 2. Pessimistic Locking (Пессимистичная блокировка)
Мы предполагаем, что конфликты неизбежны, и «запираем» ресурс на время работы.

**Как это работает:**
На уровне БД выполняется запрос `SELECT ... FOR UPDATE`. Это блокирует строки до завершения текущей транзакции. Второй процесс будет буквально «стоять и ждать» у входа в БД, пока первый не сделает `COMMIT`.

**В Symfony/Doctrine:** Используется через `$entityManager->lock($entity, LockMode::PESSIMISTIC_WRITE)`.

* **Плюсы:** Гарантирует, что конфликт не возникнет (процесс просто подождет).
* **Минусы:** 
    * **Риск Deadlocks:** Если два процесса заблокируют разные ресурсы в разном порядке.
    * **Снижение throughput:** Процессы стоят в очереди, база данных нагружается ожиданием.
* **Когда использовать:** В критических финансовых операциях, где потеря данных недопустима, а конкуренция за одну и ту же запись (например, остаток товара на складе в «черную пятницу») очень высока.

#### 3. Архитектурный подход: Event Sourcing
Если бизнес требует абсолютной прозрачности и невозможности потери данных, я проектирую систему на основе событий.

**Как это работает:**
Мы не храним текущее состояние (баланс = 70). Мы храним последовательность событий: `MoneyDeposited(100)`, `MoneyWithdrawn(10)`, `MoneyWithdrawn(20)`. Текущее состояние — это проекция этих событий.

**Решение конфликтов:**
При записи нового события мы проверяем, не изменился ли "Sequence Number" (порядковый номер) последнего события. Если пришел параллельный поток, его событие будет отклонено, так как номер последовательности уже не актуален.

* **Плюсы:** Полный аудит, идеальная история изменений, отсутствие классических Race Conditions при правильной реализации.
* **Минусы:** Огромная сложность реализации и изменения ментальной модели разработки.

---

### Мой итоговый алгоритм выбора:

1. **По умолчанию:** Использую **Optimistic Locking** (`version`). Это дешево, безопасно и покрывает 95% кейсов.
2. **При высокой конкуренции (Hot spots):** Если я вижу, что пользователи часто получают ошибки версий (например, в аукционах или при массовых закупках), я перехожу на **Pessimistic Locking** на уровне БД.
3. **Если важна история:** Если бизнес требует знать, *почему* баланс стал таким, я проектирую систему через **Event Sourcing**.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

### Рассуждение

Вопрос о доменных событиях (Domain Events) — это вопрос о том, как управлять **связанностью (coupling)** в системе. Если один процесс в коде начинает напрямую вызывать методы другого процесса, мы получаем «спагетти-код», где изменение одного модуля ломает пять других.

Доменные события позволяют перейти от модели **"Я делаю это и потом заставляю тебя сделать то"** (Command-driven) к модели **"Я сделал это, а кто хочет — пусть реагирует"** (Event-driven).

Я разделяю использование событий на три уровня:
1. **Внутри агрегата:** Для поддержания инвариантов.
2. **Между агрегатами (синхронно):** Для поддержания связи внутри одной транзакции.
3. **Между подсистемами (асинхронно):** Для интеграции с другими сервисами или модулями.

Самая большая ловушка здесь — это **связь событий с транзакциями**. Если мы опубликуем событие, а транзакция откатится, мы получим «фантомное» событие (система будет думать, что действие совершено, хотя в БД ничего не изменилось).

---

### Ответ

#### 1. Когда публиковать события?
Я публикую события в тот момент, когда **бизнес-состояние изменилось и стало валидным**. Событие — это факт, который уже произошел.

* **Внутри агрегата:** Событие фиксируется внутри метода агрегата (просто записывается в массив `$recordedEvents`). Это позволяет агрегату оставаться «чистым» и не зависеть от шины событий.
* **В Application Service:** Именно здесь происходит «выстрел» (dispatch) накопленных событий из агрегата в шину (Message Bus).

#### 2. Как обрабатывать?
Я разделяю обработчики на два типа:
1. **Синхронные (Internal Handlers):** Выполняются в той же транзакции. Используются, когда действие *обязательно* должно завершиться для соблюдения целостности (например, обновление счетчика в другом агрегате, если это критично).
2. **Асинхронные (External Handlers):** Выполняются в фоновом процессе (чеer Messenger + RabbitMQ). Используются для побочных эффектов: отправка Email, обновление поискового индекса, уведомление в Telegram.

#### 3. Связь с транзакциями БД (Критический момент)
Это самая важная часть. Существует два подхода, и я выбираю их исходя из задачи:

**Подход А: "Publish inside transaction" (Рискованный)**
Мы вызываем `dispatch()` внутри транзакции.
* **Проблема:** Если `dispatch()` отправит сообщение в RabbitMQ, а через миллисекунду БД сделает `ROLLBACK`, обработчик сообщения получит сигнал, попробует найти данные в базе, а их там **нет**. Это классический баг несогласованности.

**Подход Б: "Transactional Outbox Pattern" (Надежный)**
Я использую этот паттерн, если мне нужна гарантированная доставка.
1. Вместо отправки в RabbitMQ, мы сохраняем событие в специальную таблицу `outbox` в **той же транзакции**, что и основное изменение.
2. Отдельный процесс (Relay) читает таблицу `outbox` и перекладывает сообщения в реальную очередь.
* **Результат:** Событие гарантированно появится в очереди только если транзакция в БД прошла успешно.

#### 4. Какие проблемы решает и какие создаёт?

**Проблемы, которые решаются:**
* **Слабая связанность (Low Coupling):** Сервис заказов больше не знает о существовании сервиса почты. Он просто говорит: "Заказ создан".
* **Масштабируемость:** Тяжелые задачи (индексация, генерация PDF) выносятся из основного потока запроса.
* **Расширяемость:** Чтобы добавить новую реакцию на событие (например, отправку SMS), мне не нужно менять код старого сервиса. Я просто пишу новый `EventListener`.

**Проблемы, которые создаются (но ими нужно управлять):**
* **Сложность отладки:** Поток управления становится нелинейным. Ты не можешь просто проследить стек вызовов в IDE, чтобы понять, почему ушел Email. Нужно смотреть логи всей системы.
* **Eventual Consistency (Согласованность в конечном счете):** Мы должны смириться с тем, что данные в поиске обновятся не мгновенно, а через 200 мс. Это требует изменения UX (например, показывать пользователю статус "обновляется").
* **Проблема дубликатов (Idempotency):** В распределенных системах сообщение может прийти дважды. **Все обработчики должны быть идемпотентными** — повторный вызов с тем же ID события не должен приводить к повторному списанию денег.

**Итог:** Я использую доменные события как основной механизм коммуникации между модулями, всегда применяя паттерн **Transactional Outbox** для критически важных интеграций, чтобы избежать расхождения данных между шиной событий и базой данных.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

### Рассуждение

Это фундаментальные вопросы проектирования. Если здесь допустить ошибку, вся последующая архитектура (агрегаты, репозитории, сервисы) будет построена на ложном фундаменте.

Я разделяю эти понятия не по «количеству полей» в классе, а по **природе их идентичности** и **способу управления состоянием**.

1.  **Entity vs Value Object:** Это вопрос о том, *кто* этот объект. Если важна история изменений и уникальный след в системе — это Entity. Если важна только суть (значение) — это Value Object.
2.  **Метод принятия решения:** Я использую «тест на идентичность» и «тест на мутацию».
3.  **Ubiquitous Language:** Это не просто «словарь терминов». Это мост между миром бизнеса и миром кода. Если бизнес говорит «заказ аннулирован», а в коде метод называется `setStatus(0)`, — связь разорвана, и это ведет к ошибкам.

---

### Ответ

#### 1. Entity vs Value Object

Главное различие заключается в **идентичности (Identity)**.

* **Entity (Сущность):** Обладает уникальным идентификатором, который остается неизменным на протяжении всего жизненного цикла. Даже если все свойства сущности изменятся, она останется той же самой сущностью.
    * *Пример:* `User`. Если пользователь сменил имя, почту и адрес, он всё равно остается тем же пользователем (ID: 42).
    * *Свойства:* Имеет жизненный цикл, меняет состояние (mutable), управляется через репозиторий.

* **Value Object (Объект-значение):** Описывает характеристику или свойство. Он не имеет идентификатора. Два объекта считаются равными, если все их свойства идентичны.
    * *Пример:* `Money(100, 'USD')`. Если я создам другой объект с теми же 100 долларами, для системы это будет то же самое значение.
    * *Свойства:* Всегда неизменяем (immutable). Любое изменение — это создание нового экземпляра. Не имеет жизненного цикла.

#### 2. Как я решаю, к чему отнести концепцию?

Когда я проектирую новую модель, я задаю себе три вопроса:

1.  **«Если я изменю все поля этого объекта, останется ли он тем же самым?»**
    * Да $\rightarrow$ Entity.
    * Нет $\rightarrow$ Value Object.
2.  **«Нужен ли мне уникальный ID для этого объекта в базе данных или для отслеживания его истории?»**
    * Да $\rightarrow$ Entity.
    * Нет $\rightarrow$ Value Object.
3.  **«Должен ли этот объект быть неизменяемым?»**
    * Если я хочу избежать побочных эффектов и гарантировать валидность — я делаю его Value Object.

#### 3. Единый язык (Ubiquitous Language)

**Ubiquitous Language** — это общий язык, на котором общаются разработчики, аналитики, менеджеры и доменные эксперты (бизнес). Этот язык должен пронизывать всё: от обсуждений в Zoom до названий классов, методов и колонок в БД.

**Как он влияет на код?**
В плохом коде мы видим «перевод» с человеческого на технический:
* Бизнес: «Клиент отменил заказ».
* Код: `$order->setStatus(4);` (Где 4 — это статус отмены). Это плохой код, он не отражает смысл.

В коде с применением Ubiquitous Language мы видим:
* Код: `$order->cancel();`

**Преимущества влияния языка на код:**
1.  **Снижение когнитивной нагрузки:** Когда я читаю метод `order->cancel()`, я сразу понимаю бизнес-смысл, не заглядывая в константы или документацию.
2.  **Минимизация ошибок перевода:** Когда разработчик и эксперт используют одни и те же термины, вероятность того, что «заказ» в коде будет обрабатываться не так, как «заказ» в бизнесе, стремится к нулю.
3.  **Самодокументированный код:** Код становится живой документацией бизнес-процесса.

**Мой принцип:** Если бизнес-эксперт не может прочитать ваш код (или его высокоуровневое описание) и понять, что там происходит, — вы не внедрили Ubiquitous Language, и ваша архитектура рискует стать оторванной от реальности.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

### Рассуждение

Когда я проектирую приложение по принципам **Clean Architecture**, моя главная цель — защитить бизнес-логику от внешнего мира. В классическом PHP-приложении «внешним миром» являются фреймворк (Symfony), база данных (Doctrine), API сторонних сервисов и консольные команды.

Я использую **Dependency Inversion Principle (DIP)** как основной инструмент. Бизнес-логика не должна зависеть от деталей реализации. Это значит, что если завтра мы заменим Doctrine на другой инструмент или перейдем с Symfony на другой фреймворк, я не должен переписывать ядро приложения.

Я разделяю приложение на слои, где каждый слой имеет строго определенную зону ответственности и направление зависимостей.

---

### Ответ

В моей архитектуре выделяются четыре основных слоя. Главное **правило зависимостей**: зависимости направлены только **внутрь**, к центру (к бизнес-логике). Слои не знают о существовании слоев, которые находятся «снаружи» них.

#### 1. Слои архитектуры

**A. Domain Layer (Центр: Ядро)**
Это самый чистый слой. Здесь нет ни одной зависимости от сторонних библиотек (кроме базовых типов PHP).
* **Что внутри:** Entity (агрегаты), Value Objects, Domain Exceptions, Domain Services (если логика не влезает в агрегат), интерфейсы репозиториев.
* **Зависимости:** Ни от кого.

**B. Application Layer (Сценарии использования / Use Cases)**
Этот слой оркеструет выполнение бизнес-задач. Он не знает, *как* данные сохраняются, он знает только, *что* нужно сделать.
* **Что внутри:** Use Case классы (или Command Handlers), DTO (Data Transfer Objects), интерфейсы для внешних сервисов (например, `EmailServiceInterface`).
* **Зависимости:** Только на Domain Layer.

**C. Infrastructure Layer (Детали реализации)**
Здесь живут все технические подробности. Это реализация интерфейсов, определенных в слоях выше.
* **Что внутри:** Реализации репозиториев (Doctrine), реализации почтовых сервисов (Mailgun/Symfony Mailer), клиенты для внешних API, работа с очередями.
* **Зависимости:** На Domain и Application слоях.

**D. Presentation/User Interface Layer (Входные точки)**
Слой, который принимает ввод от пользователя или внешних систем и передает его в Application Layer.
* **Что внутри:** Symfony Controllers, CLI Commands, API Endpoints.
* **Зависимости:** На Application слое.

---

#### 2. Размещение компонентов (Где они живут?)

Согласно этой структуре, ваши компоненты распределяются так:

* **Symfony-контроллер** $\rightarrow$ **Presentation Layer**. Его задача: принять Request, превратить его в DTO и вызвать нужный Use Case из Application Layer.
* **Doctrine (Repository Implementation)** $\rightarrow$ **Infrastructure Layer**. В Domain слое лежит только *интерфейс* репозитория, а сама реализация с SQL/DQL живет в Infrastructure.
* **Обработчик очереди (Message Handler)** $\rightarrow$ **Application Layer** (логика) + **Infrastructure** (механизм доставки). Сам хендлер вызывает Use Case из Application слоя, а инфраструктурный транспорт (Messenger) лишь доставляет сообщение.

---

#### 3. Как следить за соблюдением границ?

Соблюдать границы «на честном слове» невозможно — это ведет к деградации архитектуры. Я использую три уровня контроля:

1.  **Static Analysis (PHPStan/Psalm):**
    Я настраиваю строгую проверку типов. Но для архитектуры я использую расширения (например, `phpstan-deprecation-rules` или кастомные правила), которые запрещают, например, использование классов `Doctrine\ORM` внутри папки `Domain`.

2.  **Архитектурные тесты (ArchUnit / PHPArkitect):**
    Это мой любимый инструмент. Я пишу Unit-тесты, которые проверяют архитектуру.
    * *Пример теста:* «Классы в папке `Domain` не должны иметь `use` инструкций, указывающих на `Infrastructure` или `Symfony`». Если кто-то случайно импортирует `EntityManager` в сущность — тест упадет при CI.

3.  **Code Review:**
    Ни один PR не проходит без проверки на «протекание» деталей реализации. Если я вижу в Domain-слое аннотации Doctrine или использование `Symfony\Component\HttpFoundation\Request`, я возвращаю задачу на рефакторинг.

**Итог:** Чистая архитектура — это не про то, как разложить файлы по папкам, а про то, как **направить стрелки зависимостей** так, чтобы бизнес-логика оставалась изолированной, тестируемой и защищенной от изменений в инфраструктуре.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

### Рассуждение

Выбор стратегии тестирования — это всегда поиск баланса между **уверенностью (confidence)** и **скоростью обратной связи (feedback loop)**. Если мы будем писать только тяжелые интеграционные тесты, разработка станет мучительной из-за долгого ожидания. Если только Unit-тесты — мы рискуем получить работающие в изоляции компоненты, которые «взрываются» при встрече в реальной среде.

Я придерживаюсь классической **Пирамиды Тестирования**, но с поправкой на специфику PHP и Symfony. В PHP сложность часто кроется в интеграции с БД и внешними API, поэтому «тестовый колокол» (Test Bell) — это важная надстройка.

Мой подход строится на трех столпах:
1. **Разделение по уровню ответственности.**

**А. Тестирование БД (PostgreSQL):**

**Б. Тестирование очередей:**
* Вместо реального RabbitMQ я использую транспорт `doctrine` или `sync` для тестов. Это позволяет проверять, что сообщение *было отправлено*, не запуская полноценный брокер сообщений.

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

### Рассуждение

Это классическая проблема конкурентного доступа в многопользовательских системах. Когда два процесса считывают одни и те же данные, изменяют их и пытаются сохранить, возникает риск нарушения целостности данных.

Главная проблема здесь — **Lost Update (Потерянное обновление)**. 
Представь сценарий:
1. Пользователь А читает баланс счета (100$).
2. Пользователь Б читает тот же баланс (100$).
3. Пользователь А снимает 10$ и записывает в БД (90$).
4. Пользователь Б снимает 20$ и записывает в БД (80$).
**Итог:** Мы потеряли списание пользователя А. Баланс стал 80$, хотя должен быть 70$.

Я рассматриваю три основных стратегии решения: **Optimistic Locking**, **Pessimistic Locking** и **Atomic Operations**.

---

### Ответ

Я разделяю стратегии защиты на три категории в зависимости от того, как мы управляем конфликтами.

#### 1. Optimistic Locking (Оптимистичная блокировка)
Мы предполагаем, что конфликты случаются редко. Мы не блокируем запись при чтении, но при попытке записи проверяем, не изменил ли кто-то данные, пока мы работали.

* **Механизм:** В таблицу добавляется колонка `version` (integer). При каждом `UPDATE` мы добавляем условие `WHERE version = :old_version` и инкрементируем версию. Если `affected_rows == 0`, значит, кто-то успел обновиться первым.
* **В Symfony/Doctrine:** Реализуется через атрибут `#[ORM\Version]`. Doctrine сама выбросит `OptimisticLockException`.

**Trade-offs:**
* **Плюсы:** Не блокирует базу данных, не снижает пропускную способность (throughput), отлично масштабируется.
* **Минусы:** Если конфликты происходят часто, пользователю придется постоянно получать ошибку и повторять действие (Retry).
* **Когда выбирать:** В 90% случаев в веб-приложениях (редактирование профиля, посты, заказы), где вероятность того, что два админа одновременно нажмут «Сохранить» на одном объекте, крайне мала.

#### 2. Pessimistic Locking (Пессимистичная блокировка)
Мы предполагаем, что конфликт неизбежен, и «захватываем» ресурс заранее.

* **Механизм:** При чтении данных мы используем SQL-команду `SELECT ... FOR UPDATE`. База данных ставит блокировку на эти строки. Второй процесс, попытавшийся прочитать те же строки с `FOR UPDATE`, будет **стоять в очереди** и ждать, пока первый процесс не сделает `COMMIT` или `ROLLBACK`.
* **В Symfony/Doctrine:** Реализуется через `$em->lock($entity, LockMode::PESSIMISTIC_WRITE)`.

**Trade-</strong>offs:**
* **Плюсы:** Гарантирует целостность без необходимости повторных попыток со стороны пользователя.
* **Минусы:** 
    * **Риск Deadlocks:** Если два процесса блокируют разные ресурсы в разном порядке, они могут заблокировать друг друга навсегда.
    * **Снижение производительности:** Процессы выстраиваются в очередь, растет время ответа (latency).
* **Когда выбирать:** В критических финансовых операциях или системах с высокой конкуренцией за один ресурс (например, бронирование последнего места в самолете или списание денег со счета в высоконагруженном сервисе).

#### 3. Atomic Operations (Атомарные операции на уровне БД)
Вместо того чтобы «прочитать $\rightarrow$ посчитать в PHP $\rightarrow$ записать», мы делегируем вычисление самой базе данных.

* **Механизм:** Использование SQL-выражений вида `UPDATE accounts SET balance = balance - 10 WHERE id = 1`.
* **В Symfony/Doctrine:** Можно использовать `QueryBuilder` для выполнения арифметических операций прямо в SQL.

**Trade-offs:**
* **Плюсы:** Самый быстрый и надежный способ для простых инкрементов/декрементов. Полностью исключает Race Condition на уровне логики «чтения-записи».
* **Минусы:** Мы теряем возможность выполнить сложную бизнес-валидацию в PHP (например, проверку лимитов, которая требует данных из других таблиц), так как изменения происходят внутри БД.
* **Когда выбирать:** Для простых счетчиков, балансов или инкремента просмотров.

## Q19 · Git и процесс

Я базируюсь на принципах **GitFlow** (в упрощенном виде) или **GitHub Flow**, в зависимости от частоты релизов, но с упором на автоматизацию.

### Ответ

Мой процесс построен вокруг идеи **непрерывной интеграции (CI)** и **контролируемого слияния**. Я сторонник подхода, где `main` всегда находится в релизном состоянии.

#### 1. Начало работы: Ветвление (Branching)
Я использую стратегию **Feature Branches**. 

* **Как это выглядит:** Каждая задача (Task/Story) из Jira/Linear порождает свою ветку. Название ветки должно быть информативным: `feature/JIRA-123-user-registration` или `fix/JIRA-456-broken-login`.
* **Почему так:** Это позволяет изолировать работу. Я могу переключаться между задачами, не смешивая незавершенный код. Это также критично для CI/CD: каждая ветка может иметь свой пайплайн проверки.

#### 2. Разработка и коммиты (Commits)
Я придерживаюсь стандарта **Conventional Commits**.

* **Формат:** `type(scope): description` (например, `feat(auth): add OAuth2 support` или `fix(api): resolve null pointer in user profile`).
* **Почему так:** 
    1. **Автоматизация:** Это позволяет автоматически генерировать `CHANGELOG.md` при релизе.
    2. **Читаемость:** Коллегам и мне через месяц будет понятно, *зачем* был сделан этот коммит, не заглядывая в Jira.
    3. **Атомарность:** Один коммит — одна логическая правка. Это упрощает `git revert`, если что-то пошло не так.

#### 3. Pull Request (PR) и Code Review
PR — это не просто просьба «влить мой код», это точка контроля качества.

* **Процесс:** Когда задача готова, я создаю PR. В описании я обязательно указываю: **что** сделано, **как** это протестировано (скриншоты, если это UI) и **какие** есть риски.
* **Review:** Я приветствую конструктивное ревью. Основной фокус — не на стиле кода (это должен делать линтер), а на:
    * Архитектурных решениях (не нарушен ли SRP/DIP?).
    * Пограничных случаях (edge cases) и безопасности.
    * Тестовом покрытии.
* **Почему так:** Ревью — это способ обмена знаниями в команде. Это предотвращает появление «bus factor» (когда только один человек знает, как работает модуль).

#### 4. CI/CD и Автоматизация (The Gatekeeper)
Ни один PR не может быть влит в `main`, пока не пройден автоматический пайплайн:
1. **Static Analysis:** PHPStan (на максимальном уровне), Psalm, PHP-CS-Fixer.
2. **Tests:** Unit, Integration и Functional тесты.
3. **Security Scan:** Проверка на уязвимые зависимости (Composer audit).

Если пайплайн упал — PR блокируется. Это гарантирует, что `main` всегда стабилен.

#### 5. Релизы (Releases)
Я предпочитаю **Continuous Deployment** (если проект позволяет) или **Continuous Delivery**.

* **Как это выглядит:** После слияния ветки в `main`, запускается процесс сборки артефакта (Docker-образ) и его деплоя на стейджинг. После успешных тестов на стейджинге, деплой на продакшн происходит либо автоматически, либо нажатием одной кнопки (Manual Approval).
* **Tagging:** Каждый релиз помечается Git-тегом (например, `v1.2.0`) в соответствии с **SemVer** (Semantic Versioning).
* **Почему так:** Это минимизирует риск «релизного ада», когда раз в месяц команда сидит ночами, пытаясь выкатить огромный пакет изменений. Релизы должны быть маленькими, частыми и незаметными.

## Q20 · Git и процесс

### Рассуждение

Для меня код-ревью — это не инспекция или «экзамен», а **инструмент обеспечения качества и обмена знаниями**. Если ревью превращается в поиск опечаток или споры о стиле, оно перестает приносить пользу.

Я разделяю ревью на две плоскости: **техническую** (чтобы код работал и был поддерживаемым) и **коммуникативную** (чтобы команда росла и не чувствовала токсичности). 

Прежде чем отвечать, я обозначу свою философию: **«Будь строг к коду, но добр к человеку»**. Моя цель — не «победить» автора, а сделать продукт лучше.

---

### Ответ

#### 1. На что я смотрю в первую очередь (Приоритеты)

Я не трачу время на обсуждение пробелов или скобок (это работа линтеров и PHP-CS-Fixer). Мой фокус смещается от поверхностного к глубокому:

1.  **Архитектура и дизайн (High Level):**
    *   Не нарушен ли **SRP**? Не превратился ли этот класс в «божественный объект»?
    *   Соблюден ли **DIP**? Не зависит ли домен от инфраструктуры (например, SQL-запроса внутри Entity)?
    *   Правильно ли выбрана граница **Агрегата**?
2.  **Бизнес-логика и корректность:**
    *   Покрывает ли этот код требования задачи?
    *   Неты ли здесь «дыр» в логике (edge cases)? Что будет, если придет `null`, пустой массив или отрицательное число?
    *   Соблюдены ли инварианты домена?
3.  **Безопасность и производительность:**
    *   Нет ли здесь потенциальных SQL-инъекций или уязвимостей?
    *   Нет ли здесь проблемы **N+1** или тяжелых циклов, которые положат сервер под нагрузкой?
4.**Тесты:**
    *   Есть ли тесты на новый функционал?
    *   Тестируют ли тесты именно поведение (behavior), а не реализацию?

#### 2. Как я маркирую замечания (Коммуникация)

Чтобы автор не гадал, насколько критична моя правка, я использую систему уровней (аналог [Conventional Comments](https://conventionalcomments.org/)):

*   **[BLOCKER] / [CRITICAL]:** Ошибка, которая приведет к багу, дыре в безопасности или поломке системы. Этот PR **не может** быть влит, пока не будет исправлено.
*   **[SUGGESTION] / [QUESTION]:** «Мне кажется, здесь можно сделать проще, но это не критично». Это не обязательное исправление, а предложение для обсуждения.
*   **[NIT] (Nitpick):** Мелочи, касающиеся стиля или чистоты (например, слишком длинная строка). Я пишу: «NIT: можно сократить, но на твое усмотрение». Это сигнализирует автору: «Можешь проигнорировать, если спешишь».
*   **[CHALLENGE]:** Когда я не согласен с подходом и хочу, чтобы автор аргументировал свое решение.

#### 3. Как я поступаю при разногласиях

Конфликты — это нормально. Если мы не можем прийти к согласию, я следую алгоритму:

1.  **Смена контекста (Offline):** Если дискуссия в комментариях к PR затягивается (больше 3-4 реплик без прогресса), я предлагаю: *«Давай созвонимся на 5 минут или обсудим это в Slack/личном разговоре»*. Текст часто лишен интонации, и дискуссия может превратиться в срач. Живой разговор решает 90% споров.
2.  **Аргументация через "Почему":** Я никогда не говорю «сделай так». Я говорю: «Если мы сделаем так, то в будущем нам будет сложно добавить X, потому что...». Я апеллирую к принципам (SOLID, KISS, DRY) и бизнес-рискам.
3.  **Принцип "Disagree and Commit":** Если мы зашли в тупик, а решение не является критической ошибкой (не ломает систему), я предлагаю: *«Давай оставим как есть, но зафиксируем это как технический долг (Technical Debt) в бэклоге»*. 
4.  **Эскалация (крайний случай):** Если спор касается фундаментальных архитектурных решений, которые могут повлиять на всё приложение, я привлекаю техлида или архитектора как арбитра.

**Мой девиз в ревью:** Мы оба работаем на одну цель — качественный продукт. Если я нашел ошибку, я не «поймал» коллегу, я помог ему не выкатить баг в продакшн.

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

### Рассуждение

Здесь я должен сразу внести важную техническую ясность: **в PostgreSQL нет команды `FORCE INDEX`**. 

Если вы встретите такую команду в контекте PostgreSQL, это либо ошибка, либо использование специфического расширения, либо (что чаще всего) человек перепутал PostgreSQL с **MySQL**. В MySQL `FORCE INDEX` — это хинт (hint), который принудительно заставляет оптимизатор использовать конкретный индекс, даже если планировщик считает, что последовательное сканирование (`Seq Scan`) будет быстрее.

В PostgreSQL философия управления планом выполнения иная. PostgreSQL — это самонастраивающаяся система, и она «не любит», когда ей навязывают конкретные индекты напрямую через SQL-синтаксис. Вместо этого в Postgres используются другие механизмы управления планом.

Поэтому я отвечу на вопрос так: **как в PostgreSQL добиться того же эффекта, для которого в MySQL используют `FORCE INDEX`, и почему это делается иначе.**

---

### Ответ

Поскольку прямой команды `FORCE INDEX` в PostgreSQL не существует, инженеры используют альтернативные способы «подсказать» планировщику, что текущий план выполнения неоптимален.

#### 1. Почему планировщик может игнорировать нужный индекс?
Прежде чем «принуждать» базу, нужно понять, почему она его не берет. Основные причины:
* **Низкая селективность:** Если индекс по полю `status` покрывает 90% строк таблицы, планировщик решит, что проще прочитать всю таблицу целиком (`Seq Scan`), чем прыгать по индексу и постоянно обращаться к основной куче (Heap).
* **Устаревшая статистика:** Планировщик думает, что в таблице 100 строк, хотя там 1 000 000. Он выбирает неверный план.
* **Типы данных (Type Mismatch):** Если вы сравниваете `integer` с `text`, индекс по `integer` не будет использован из-за неявного приведения типов.

#### 2. Способы управления планом в PostgreSQL (Альтернативы FORCE INDEX)

**А. Обновление статистики (`ANALYZE`)**
Это первое, что я сделаю. Если статистика устарела, планировщик «слеп».
* **Действие:** `ANALYZE VERBOSE table_name;`. Это заставит базу пересчитать распределение данных.

**Б. Создание расширенных индексов (Partial & Expression Indexes)**
Вместо того чтобы заставлять базу использовать индекс, я создам индекс, который *идеально подходит* под запрос.
* **Partial Index:** Если мы часто ищем только «активные» заказы, я создам индекс `CREATE INDEX ... WHERE status = 'active'`. Он будет крошечным и супер-быстрым.
* **Expression Index:** Если мы ищем по `lower(email)`, обычный индекс не сработает. Я создам индекс по выражению: `CREATE INDEX ... ON users (lower(email));`.

**В. Использование `pg_hint_plan` (Для экстремальных случаев)**
Если я работаю в среде, где критически важно управлять планом (например, высоконагруженный Enterprise), и стандартных средств не хватает, я использую расширение `pg_hint_plan`.
* **Как это работает:** Оно позволяет писать хинты прямо в комментариях к SQL-запросу, имитируя поведение Oracle или MySQL.
* **Пример:** `/*+ IndexScan(table_name index_name) */ SELECT ...`
* **Когда использовать:** Только если `ANALYZE` и создание правильных индексов не помогли, а стоимость неоптимального плана слишком велика.

**Г. Изменение параметров сессии (Для отладки)**
Если мне нужно проверить, станет ли запрос быстрее с индексом, я могу временно «запретить» последовательное сканирование в текущей сессии:
`SET enable_seqscan = off;`
Это не «форсирует» индекс, но заставляет планировщик искать альтернативы, кроме `Seq Scan`. Это отличный инструмент для диагностики.

#### Резюме и мой подход:

Если я вижу, что запрос тормозит:
1. Я запускаю `EXPLAIN ANALYZE`.
2. Если вижу `Seq Scan` там, где ожидаю индекс — проверяю **типы данных** (нет ли неявного приведения) и **селективность**.
3. Я проверяю актуальность статистики через `ANALYZE`.
4. Если проблема в специфическом условии (например, поиск по части строки) — я создаю **Partial** или **GIN/GIST** индекс.
5. Я **избегаю** использования хинтов типа `pg_hint_plan` в рабочем коде, так как это делает систему хрупкой и привязывает её к конкретным планам, которые могут сломаться при обновлении версии PostgreSQL или изменении объема данных.

## Q25 · Провокации

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

### Рассуждение

Это вопрос с подвохом, который проверяет понимание того, как работает движок PHP (Zend Engine). 

Если отвечать на него прямо: **влияние `strict_types=1` на скорость выполнения практически равно нулю.**

Многие разработчики ошибочно полагают, что «строгость» требует от PHP выполнения дополнительных проверок «на лету» при каждом вызове функции, что должно замедлять код. Однако на самом деле механизм работы `strict_types` реализован на уровне компиляции в опкоды (opcodes) и работает иначе.

Я должен разобрать этот вопрос через три аспекта:
1. **Механизм работы (Runtime vs Compile-time).**
2. **Влияние на оптимизацию (JIT и OpCache).**
3. **Реальный профиль нагрузки (где на самом деле теряется время).**

---

### Ответ

Если говорить о цифрах, то в типичном приложении разница в производительности между `strict_types=1` и `strict_types=0` составляет **менее 0.1%**, что в рамках прикладной разработки считается статистической погрешностью.

Вот почему это так:

#### 1. Механизм работы (Type Checking)
Когда вы используете `strict_types=1`, PHP не «начинает проверять типы» в смысле выполнения тяжелых алгоритмов. На самом деле, в режиме `strict_types=0` (coercive mode) PHP **тоже делает проверки**, но он делает их более «широкими» и сложными.

* **В режиме `strict_types=0`:** Если вы передаете строку `"10"` в функцию `int $x`, PHP должен: 1) Понять, что пришла строка. 2) Попробовать преобразовать её в `int`. 3) Проверить, не потеряется ли информация (например, если это `"10.5"`). Это активный процесс преобразования (coercion).
* **В режиме `strict_types=1`:** Если вы передаете строку вместо `int`, PHP просто видит несоответствие типов и мгновенно выбрасывает `TypeError`. 

То есть, «строгий» режим на самом деле **легче** для процессора, потому لأنه просто отсекает неверные типы, вместо того чтобы пытаться их «починить» через приведение типов.

#### 2. Влияние на OpCache и JIT
Современный PHP (особенно 8.0+) очень сильно полагается на оптимизации.
* **Type Hinting как подсказка:** Когда типы объявлены строго, оптимизатору (Zend VM) проще генерировать эффективный байт-код. Он точно знает, с каким типом данных будет работать регистр процессора.
* **JIT (Just-In-Time compilation):** Строгая типизация — лучший друг JIT. Чем меньше неопределенности в типах (Type Uncertainty), тем эффективнее JIT компилирует PHP-код в машинный код. В режиме `strict_types=1` JIT может генерировать более оптимизированные инструкции, так потому что ему не нужно вставлять проверки на возможную трансформацию типов.

#### 3. Где на самом самом деле теряется время?
В любом реальном приложении (Symfony, Laravel) 99% времени тратится не на выполнение базовых операций процессора (вроде сравнения типов), а на:
* **I/O операции:** Запросы к PostgreSQL, чтение файлов, запросы к Redis.
* **Сложные алгоритмы:** Сериализация JSON, работа с большими массивами.
* **Memory Management:** Выделение памяти под объекты и их уничтожение (Garbage Collection).

На фоне сетевого запроса к базе данных, который длится 2-10 мс, наносекундные задержки от проверки типов просто невозможно измерить.

**Мой вердикт:**
Использовать `strict_types=1` нужно **всегда**. Это не вопрос производительности, это вопрос **безопасности, предсказуемости и качества кода**. Выигрыш в производительности от его использования может быть даже положительным за счет упрощения работы JIT-компилятора, а риск возникновения ошибок из-за неявного приведения типов в «слабом» режиме несоизмеримо выше любой возможной выгоды.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

### Рассуждение

Вопрос содержит в себе техническую неточность, которую важно прояснить сразу: **Doctrine ORM на самом деле поддерживает составные первичные ключи (Composite Primary Keys)**. Вы можете объявить их через несколько атрибутов `#[ORM\Id]`.

Однако, когда люди говорят, что «Doctrine не поддерживает их», они имеют в виду, что поддержка этих ключей в Doctrine — это **«грабель»**, а не полноценная фича. Использование составных ключей в Doctrine приносит столько боли в проектировании и эксплуатации, что опытные архитекторы стараются их избегать.

Я разберду, почему это «плохо», в чем реальные технические сложности и какие архитектурные паттерны мы используем, чтобы этого избежать.

---

### Ответ

Технически составные ключи поддерживаются, но на практике они ломают многие удобства, которые делает за нас ORM.

#### Почему это «проблема» (проблемы реализации)

1.  **Сложность работы с Identity Map:** Doctrine полагается на идентификатор объекта, чтобы понимать, является ли загруженный объект тем же самым, что уже есть в памяти. С составными ключами логика сравнения становится сложнее, и это увеличивает риск ошибок в Unit of Work.
2.  **Сложность в связях (Associations):** Если сущность `A` имеет составной ключ, то любая сущность `B`, которая ссылается на `A` через `ManyToOne`, должна будет хранить **все** поля составного ключа как Foreign Key. Это раздувает таблицы, усложняет JOIN-ы и делает маппинг очень громоздким.
3.  **Проблемы с Generic-кодом и рефлексией:** Многие инструменты (библиотеки для API, мапперы, генераторы кода), которые ожидают, что у сущности есть один `id`, начинают ломаться или требовать написания кастомных адаптеров.
4.  **Сложность в работе с Repository:** Методы вроде `find($id)` теперь требуют передачи массива `['id_part1' => 1, 'id_part2' => 2]`, что менее удобно и более подвержено ошибкам.

#### Как с этим «живут» в реальных проектах (Best Practices)

В современной разработке на Symfony/Doctrine мы используем три стратегии, чтобы избежать составных ключей:

**1. Использование Surrogate Key (Суррогатный ключ) — мой основной выбор**
Вместо того чтобы использовать естественный составной ключ (например, `order_id` + `product_id`), мы добавляем к таблице один технический столбец: `id` (UUID или Auto-increment BIGINT).

*   **Как это работает:** Составной ключ (бизнес-ключ) остается в таблице, но он помечается как `UNIQUE CONSTRAINT`.
*   **Почему это лучше:** 
    *   У каждой сущности есть один простой `id`.
    *   Все связи (`ManyToOne`) работают по одному полю.
    *   Doctrine работает идеально и быстро.
    *   Бизнес-логика (уникальность пары полей) всё еще защищена базой данных.

**2. Использование Value Objects (для логики)**
Если составной ключ — это не просто ID, а смысловая сущность (например, `Period(startDate, endDate)`), я не мапплю его как первичный ключ. Я мапплю его как **Embeddable**.

*   **Как это работает:** `Period` — это Value Object. В базе это две колонки. Но в коде я работаю с одним объектом.
*   **Почему это лучше:** Это сохраняет чистоту доменного слоя (DDD) и избавляет от проблем с идентификацией.

**3. Использование UUID (UUID v4 или v7)**
В распределенных системах вместо составных ключей часто используют UUID.

*   **Почему это лучше:** UUID дает уникальность «из коробнуть» без необходимости проверять наличие записи в БД или строить сложные составные индексы. Это упрощает шардирование и синхронизацию данных между микросервисами.

#### Резюме: мой подход

Если я проектирую систему:
1. **Никогда** не использую составные первичные ключи как `#[ORM\Id]`. Это создает технический долг в инфраструктуре.
2. Всегда использую **суррогатный ключ** (`id` типа `UUID` или `bigint`) для идентификации сущности.
3. Если мне нужна уникальность комбинации полей (например, «один пользователь — один профиль»), я накладываю **`#[ORM\UniqueConstraint]`** на эти поля. 

Это дает нам: **чистый код, предсказуемый ORM и надежную целостность данных.**

### Рассуждение

Этот код — классический пример «антипаттерна», который часто встречается в старых PHP-проектах или в коде, написанном без понимания архитектурных слоев. Если я получу такой код на ревью, я не просто попрошу его переписать — я поставлю под сомнение безопасность и надежность всего модуля.

Я разделяю проблемы на три критических уровня: **Безопасность**, **Надежность (Reliability)** и **Архитектура**.

#### 1. Проблемы (Что здесь не так?)

**А. Критическая уязвимость: SQL Injection**
Это самая страшная ошибка. Переменная `$id` берется напрямую из запроса (`$req->get('id')`) и вставляется в строку запроса. Злоумышленник может передать `1; DROP TABLE users;`, и база данных выполнит это. Это катастрофа.

**Б. Нарушение транзакционности (Atomicity)**
Процесс оплаты состоит из двух действий: изменение статуса в БД и отправка письма. Если база обновится, а почтовый сервис упадет (или PHP упадет из-за нехватки памяти), заказ останется в статусе `paid`, но пользователь не получит подтверждения. Или наоборот: если мы сначала отправим письмо, а база упадет — пользователь получит письмо, что заказ оплачен, хотя в БД он остался «неоплаченным».

**В. Нарушение ответственности (SRP/Layering)**
Контроллер делает **всё**:
* Работает с HTTP (Request/Response).
* Работает с БД напрямую (PDO).
* Содержит бизнес-логику (изменение статуса).
* Интегрируется с внешними сервисами (Mailer, Logger).
Это делает код невозможно тестировать (нужно поднимать БД, почту и логгер для одного теста) и невозможно переиспользовать.

**Г. Отсутствие обработки ошибок и типов**
Нет проверок на валидность `$id` (это число или строка?), нет обработки исключений от `Mailer` или `PDO`.

---

#### 2. Как я бы это переделал

Я начну не с переписывания кода, а с **определения границ**. Я разделю этот процесс на три слоя:
1. **Presentation Layer** (Контроллер): только принимает запрос и вызывает Use Case.
2. **Application Layer** (Use Case): управляет транзакцией и координацией.
3. **Domain Layer** (Entity/Service): содержит бизнес-правила.

**Мой план рефакторинга:**
1. Вынести бизнес-логику в `OrderService` или `PlaceOrderUseCase`.
2. Использовать **Prepared Statements** (чечерез Doctrine или чистый PDO) для защиты от SQL Injection.
3. Обернуть всё в **Транзакцию**.
4. Вынести отправку письма в **Асинхронный обработчик** (чеize Messenger), чтобы ошибка почты не откатывала оплату.

---

#### 3. Итоговый код (Refactored)

**Domain Layer (Сущность):**
```php
class Order 
{
    // ... свойства, конструктор
    public function markAsPaid(): void 
    {
        if ($this->status === Status::PAID) {
            throw new OrderAlreadyPaidException();
        }
        $this->status = Status::PAID;
    }
}
```

**Application Layer (Use Case):**
```php
class PayOrderUseCase
{
    public function __construct(
        private OrderRepositoryInterface $repository,
        private MessageBusInterface $eventBus, // Для асинхронных событий
        private EntityManagerInterface $entityManager
    ) {}

    public function execute(int $orderId): void
    {
        // Используем транзакцию для обеспечения атомарности
        $this->entityManager->wrapInTransaction(function() use ($orderId) {
            $order = $this->repository->find($orderId);
            
            if (!$order) {
                throw new OrderNotFoundException($orderId);
            }

            $order->markAsPaid();
            $this->repository->save($order);

            // Вместо прямой отправки письма — отправляем событие в шину
            // Это решит проблему "письмо ушло, а БД упала"
            $this->eventBus->dispatch(new OrderPaidEvent($order->getId()));
        });
    }
}
```

**Presentation Layer (Контроллер):**
```php
class OrderController extends AbstractController
{
    public function pay(int $orderId, PayOrderUseCase $useCase): Response
    {
        try {
            $useCase->execute($orderId);
            return new JsonResponse(['status' => 'ok']);
        } catch (OrderNotFoundException $e) {
            return new JsonResponse(['error' => 'Not found'], 404);
        } catch (OrderAlreadyPaidException $e) {
            return new JsonResponse(['error' => 'Already paid'], 400);
        } catch (\Exception $e) {
            $this->logger->error($e->getMessage()); // Логируем системную ошибку
            return new JsonResponse(['error' => 'Internal error'], 500);
        }
    }
}
```

### Что изменилось?
1. **Безопасность:** SQL Injection невозможен благодаря использованию ORM/Prepared Statements.
2. **Надежность:** Благодаря транзакции и асинхронным событиям (Outbox pattern), данные в БД и статус в почте будут согласованы.
3. **Тестируемость:** Я могу написать Unit-тест на `Order::markAsPaid()` за миллисекунды, не подключая базу.
4. **Чистота:** Контроллер стал "тонким", он только переводит HTTP в доменные команды.

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

### Рассуждение

Этот код — классический пример нарушения всех фундаментальных принципов проектирования доменного слоя. Перед нами не «сущность», а «объект, который пытается управлять своей собственной сохранностью».

Я выделяю три критические архитектурные ошибки:

1.  **Нарушение чистоты домена (Dependency Leakage):** Сущность (Domain Layer) зависит от `EntityManagerInterface` (Infrastructure Layer). Это грубейшее нарушение правила зависимости: домен должен быть «чистым» и не знать о том, как он сохраняется.
2.  **Нарушение ответственности (SRP):** Сущность отвечает и за бизнес-логику (`changeEmail`), и за инфраструктурную операцию (`flush`). Это делает сущность «умной» в худшем смысле этого слова.
3.  **Нарушение инкапсуляции и управления состоянием:** Вызов `flush()` внутри метода сущности превращает её в инструмент управления базой данных. Это делает невозможным предсказать, когда именно данные будут записаны в БД, и лишает нас контроля над транзакциями.

---

### Ответ

#### Что именно здесь не так?

1.  **Зависимость от инфраструктуры:** `EntityManagerInterface` — это деталь реализации Doctrine. Если вы захотите протестировать эту сущность или перенести её в другой контекст (например, в микросервис без Doctrine), вы не сможете этого сделать без подкладывания тяжелых моков.
2.  **Скрытые побочные эффекты (Side Effects):** Когда разработчик вызывает `$user->changeEmail('new@email.com')`, он ожидает изменения состояния объекта. Он **не ожидает**, что в этот же момент в базу данных полетит `UPDATE` запрос. Это делает поведение кода непредсказуемым.
3.  **Проблемы с транзакциями:** Если в рамках одного бизнес-процесса (Use Case) мне нужно изменить двух пользователей и один заказ, я не смогу сделать это атомарно. Каждый вызов `changeEmail` будет принудительно фиксировать изменения в БД (commit), и если третий шаг упадет, первые два уже нельзя будет откатить.

#### Как бы я это исправил?

Я разделю ответственность: сущность будет управлять только **состоянием**, а сохранением будет заниматься **Application Layer** через репозиторий.

**1. Чистая доменная сущность (Domain Layer):**

```php
#[ORM\Entity]
class User
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 255, unique: true)]
    private string $email;

    public function __construct(string $email)
    {
        // Здесь может быть валидация email
        $this->email = $email;
    }

    public function changeEmail(string $newEmail): void
    {
        // Только бизнес-логика: проверка формата, проверка, не совпадает ли с текущим
        if ($this->email === $newEmail) {
            return;
        }
        
        $this->email = $newEmail;
    }

    public function getEmail(): string
    {
        return $this->email;
    }

    public function getId(): ?int
    {
        return $this->id;
    }
}
```

**2. Слой приложения (Application Layer / Use Case):**

```php
class ChangeUserEmailUseCase
{
    public function __construct(
        private UserRepositoryInterface $userRepository,
        private EntityManagerInterface $entityManager,
    ) {}

    public function execute(int $userId, string $newEmail): void
    {
        // Управление транзакцией и сохранением происходит здесь
        $this->entityManager->wrapInTransaction(function() use ($userId, $newEmail) {
            $user = $this->userRepository->find($userId);
            
            if (!$user) {
                throw new UserNotFoundException($userId);
            }

            $user->changeEmail($newEmail);

            // Мы явно говорим, когда данные должны уйти в базу
            $this->userRepository->save($user);
        });
    }
}
```

**Что изменилось?**
*   **Тестируемость:** Теперь я могу протестировать `User::changeEmail` обычным Unit-тестом без всяких моков и БД.
*   **Предсказуемость:** Изменение состояния объекта больше не вызывает внезапных сетевых запросов.
*   **Атомарность:** Теперь я могу гарантировать, что если что-то пойдет не так в середине процесса, транзакция откатит всё, и данные останутся консистентными.
*   **Чистота:** Доменный слой больше не знает о существовании Doctrine.

* **Формирование ответа:** Мой ответ звучит так: «Я изучил задачу. Основная сложность в [X]. Я планирую сделать PoC за 4 часа, после чего смогу дать точную оценку по срокам».

#### 4. Когда просить помощи, а когда разбираться самому?

Я использую правило **«Time-boxing»** и **«Value of help»**.

**Я разбираюсь сам, если:**
* Я нахожусь в фазе «понимания концепций» (чтение документации, изучение кода). Это инвестиция в мой рост.

* Я трачу время, но вижу прогресс (пусть даже медленный).

**Я иду к команде, если:**
* **Правило 1 часа (Time-box):** Если я бьюсь над конкретной ошибкой или багом больше часа и у меня нет ни одной новой гипотезы — я иду к коллеге. Время команды дороже моей гордости.

* **Неопределенность требований:** Если задача сформулирована так, что я не могу определить критерии приёмки.

**Моя коммуникация при помощи:**
Я никогда не прихожу с вопросом: «Как это работает?». Я прихожу с вопросом: *«Я пытаюсь сделать X, уже пробовал подходы A и B, столкнулся с ошибкой C. У меня есть гипотеза D, но я не уверен. Можешь подсказать, в ту ли сторону я думаю?»*. Это показывает, что я проделал работу и ценю время коллеги.

## Q30 · Процесс и рассуждение

**Интервьюер:** Ты пообещал сделать задачу к завтрашнему дню, но по ходу работы понял, что это два дня работы. Что делаешь?

**Кандидат:**

### Рассуждение

Это критический момент для профессиональной репутации. В разработке часто возникает ситуация, когда первоначальная оценка (Estimation) оказывается неверной из-за скрытых сложностей или «кроличьих нор». 

Главная ошибка здесь — **продолжать молчать и пытаться «дожать» задачу в срок**, надеясь на чудо. Это приводит к двум негативным сценариям:
1. Вы сдаете некачественный, сырой код, потому_то спешили.
2. Вы срываете дедлайн в последний момент, когда бизнес уже построил планы на ваш результат.

Мой подход базируется на принципах **прозрачности (Transparency)** и **управления ожиданиями (Expectation Management)**. Я считаю, что плохая новость, сказанная заранее, гораздо лучше, чем плохая новость, сказанная в момент дедлайна.

---

### Ответ

Если я понял, что не укладываюсь в срок, я буду действовать по следующему алгоритму:

#### 1. Немедленная коммуникация (Stop the bleeding)
Как только я осознал масштаб проблемы, я не жду завтрашнего дня. Я иду к менеджеру (PM) или заказчику **сразу**. 
* **Плохо:** Ждать завтрашнего утра и сказать: «Извините, я не успел».
* **Хорошо:** Сказать в середине текущего дня: «Я обнаружил проблему, которая увеличивает объем работ».

#### 2. Структурированный отчет (Context, Reason, Solution)
Я не просто говорю «мне нужно больше времени». Я предоставляю аргументацию, чтобы заказчик понимал, *почему* это произошло. Мой отчет состоит из трех частей:

1.  **Что пошло не так (The "Why"):** Я объясняю техническую причину без лишнего жаргона. 
    * *Пример:* «В процессе реализации выяснилось, что структура данных в стороннем API отличается от документации, и мне нужно написать дополнительный слой трансформации данных».
2.  **Что уже сделано (Progress):** Я показываю, что я не бездельничал.
    * *Пример:* «Базовая логика и интеграция с нашей БД уже готовы и протестированы».
3.  **Новый план (The "New Timeline"):** Я предлагаю конкретные варианты решения.

#### 3. Предложение вариантов (Trade-offs)
Я не просто приношу проблему, я приною **варианты выбора**. Это переводит меня из позиции «проблемного сотрудника» в позицию «партнера, решающего задачу».

Я предложу три пути:
* **Вариант А: Полноценное решение (Quality First).** «Если мы сделаем всё по плану, включая трансформацию данных, мне понадобится еще один полный рабочий день. Это будет надежное и чистое решение».
* **Вариант Б: MVP / Облегченная версия (Speed First).** «Мы можем выкатить задачу завтра, если мы уберем функционал [X] или сделаем его в упрощенном виде. Это позволит закрыть основной кейс, но потребует доработки позже».
* **Вариант В: Декомпозиция (Scope Management).** «Я могу завтра сдать первую часть задачи (например, только чтение данных), а вторую часть (запись) доделать послезавтра».

#### 4. Резюме моего подхода

Моя цель — не «отмазаться», а помочь бизнесу принять **обоснованное решение**. 

Если бизнес выберет вариант Б (срезать функционал), я сделаю это и зафиксирую это как техдолг. Если выберет вариант А (подождать), я буду работать над качественным решением. В обоих случаях я сохраняю доверие, потомут я предоставил им **информацию для принятия решения вовремя**.

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

Мой подход базируется на понятии **«Достаточное качество» (Good Enough)**. Я не ищу «идеальный» код, я ищу код, который:
1. Корректен (выполняет бизнес-задачу).
2. Безопасен (не имеет дыр).
3. Поддерживаем (другой разработчик сможет его понять и изменить без страха).

Я использую три фильтра для принятия решения: **Тип задачи**, **Стоимость изменения** и **Риск**.

---

### Ответ

Для соблюдения баланса между качеством и скоростью я использую следующие критерии и стратегии:

#### 1. Классификация задач (Context Matters)

Я подхожу к коду по-разному в зависимости от того, какую роль он играет в системе:

* **Core Domain (Ядро):** Если это код, описывающий бизнес-логику (например, расчет стоимости заказа или правила начисления бонусов), я буду фанатично следить за чистотой, тестами и соблюдением паттернов. Здесь цена ошибки — деньги и репутация. **Здесь качество приоритетнее скорости.**
* **Infrastructure/Glue Code (Связующий код):** Если это контроллер, который просто пробрасывает данные, или простой маппинг, я не буду строить там сложную иерархию классов. Достаточно того, чтобы код был читаемым и тестируемым. **Здесь скорость приоритетнее идеальной архитектуры.**
* **Experimental/Prototype:** Если это PoC (Proof of Concept) или задача «проверить гипотезу», я пишу максимально просто, даже если это нарушает некоторые принципы. **Здесь скорость — единственный приоритет.**

#### 2. Мои критерии «Достаточного качества»

Я считаю код готовым к релизу (Definition of Done), если он проходит чек-лист:
1. **Корректность:** Он решает поставленную задачу и проходит все Unit/Integration тесты.
2. **Читаемость:** Я могу прочитать свой код спустя месяц и понять, что он делает, без долгого раздумья.
3. **Тестируемость:** Код не написан так, что его невозможно протестировать без запуска всего приложения.
4. **Отсутствие явных «запахов» (Code Smells):** В коде нет явных дублирований, огромных методов или жестких зависимостей (Hardcoded dependencies).

#### 3. Управление техническим долгом (The Debt Strategy)

Я осознаю, что иногда мы **намеренно** идем на компромисс. Это не «плохой код», это **«взятый кредит»**. 

Мой алгоритм действий при осознанном ухудшении качества:
1. **Фиксация:** Я создаю задачу в бэклоге (Jira) с тегом `technical-debt`. Я описываю, что именно мы сделали «быстро» и почему это может стать проблемой в будущем.
2. **Прозрачность:** Я сообщаю команде: «Мы сейчас делаем это быстро, чтобы успеть к релизу, но я завел задачу на рефакторинг, чтобы не накопить долг».
3. **Планирование:** Я стараюсь закладывать время на рефакторинг в следующие спринты (например, правило 20% времени на техдолг).

#### Резюме: Как я соблюдаю баланс?

Я не стремлюся к «чистоте ради чистоты». Мой баланс — это:
* **Приоритет качества** там, где ошибка стоит дорого (Core Domain).
* **Приоритет скорости** там, где мы проверяем гипотезу или пишем вспомогательный код.
* **Управление долгом** там, где мы осознанно выбрали скорость ради бизнеса, но обязались вернуться и исправить это позже.

**Моя цель — не написать самый красивый код в мире, а приносить бизнесу ценность, создавая систему, которую можно менять без боли.**
