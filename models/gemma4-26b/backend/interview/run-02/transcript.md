## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

Для меня важно, что возможности PHP 8+ направлены на две ключевые цели: **уменьшение шаблонного кода (boilerplate)** и **усиление строгой типизации**. Чем меньше «шума» в коде, тем легче читать бизнес-логику, и чем строже типы, тем меньше ошибок достигает продакшена.

Вот мой топ наиболее важных возможностей:

### 1. Constructor Property Promotion (PHP 8.0)
Это, пожалуй, самое заметное улучшение для чистоты кода. Оно избавляет от необходимости дублировать свойства в объявлении класса и в конструкторе. Это делает Dependency Injection (DI) максимально лаконичным.

**Как было раньше:**
```php
class UserService {
    private UserRepository $repository;
    private LoggerInterface $logger;

    public function __construct(UserRepository $repository, LoggerInterface $logger) {
        $this->repository = $repository;
        $this->logger = $logger;
    }
}
```

**Как сейчас:**
```php
class UserService {
    public function __construct(
        private UserRepository $repository,
        private LoggerInterface $logger,
    ) {}
}
```

### 2. Union Types и Intersection Types (PHP 8.0 / 8.1)
Это критически важно для **надёжности**. Раньше, чтобы принимать несколько типов, приходилось использовать PHPDoc, который не проверяется рантаймом. Теперь мы можем явно заявить, что метод принимает конкретные типы.

*   **Union Types (`|`)**: «Или этот, или тот».
*   **Intersection Types (`&`)**: «Должен быть и тем, и другим одновременно» (очень полезно для работы с интерфейсами).

```php
// Union Type: метод принимает либо строку, либо число
public function processId(string|int $id): void { ... }

// Intersection Type (PHP 8.1): объект должен реализовывать оба интерфейса
public function execute(Iterator & Countable $collection): void { ... }
```

### 3. Match Expression (PHP 8.0)
В отличие от `switch`, `match` является выражением (возвращает значение) и использует строгое сравнение (`===`). Это делает код предсказуемым и исключает ошибки, связанные с неявным приведением типов.

```php
$status = match ($httpCode) {
    200, 201 => 'Success',
    404      => 'Not Found',
    500      => 'Server Error',
    default  => 'Unknown Status',
};
```

### 4. Readonly Properties (PHP 8.1 / 8.2)
Это важнейшая фича для реализации **Value Objects** и обеспечения **неизменяемости (immutability)**. Если объект не должен меняться после создания, `readonly` гарантирует это на уровне языка.

```php
readonly class Money {
    public function __construct(
        public int $amount,
        public string $currency,
    ) {}
}

$m = new Money(100, 'USD');
// $m->amount = 200; // Ошибка: Cannot modify readonly property
```

### 5. Attributes (PHP 8.0)
Замена аннотациям в комментариях. Это делает метаданные частью языка, а не просто строками в комментариях, которые парсятся через рефлексию. Это делает код чище, так как конфигурация (например, валидация или маршрутизация) находится рядом с кодом, но не загромождает его синтаксически.

```php
#[Route('/api/users/{id}', methods: ['GET'])]
public function getUser(int $id): Response { ... }
```

### Резюме
Если объединить эти фичи, то современный PHP позволяет писать код, который выглядит почти как в Java или C#, но сохраняет гибкость скриптового языка, при этом обеспечивая уровень защиты данных (через `readonly` и типы), который раньше был недоступен.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

Система типов в PHP — это гибридная модель. Она сочетает динамическую типизацию (переменная может менять тип на лету) и строгую типизацию (ограничение типов для аргументов, возвращаемых значений и свойств классов).

### 1. Что дает `declare(strict_types=1);`

По умолчанию PHP работает в **косвенном (weak) режиме**. Это значит, что если вы передадите строку `"5"` в функцию, ожидающую `int`, PHP молча попытается привести её к числу.

Включение `strict_types=1` меняет это поведение **только для текущего файла**. Это заставляет PHP выбрасывать `TypeError`, если переданный тип не соответствует объявленному (без попыток автоматического приведения).

**Важный нюанс:** `strict_types` влияет на то, как вызывающий код передает данные в функцию, а не на то, как функция возвращает данные.

### 2. Приведения типов (Coercion)

В «мягком» режиме PHP использует правила приведения типов.
* **Приведение к числам:** `"10" + 5` даст `15`.
* **Приведение к bool:** Любое непустое значение (кроме `0`, `"0"`, `[]`, `null`) — это `true`.
* **Приведение к string:** Объект превращается в строку, если у него есть метод `__toString()`.

### 3. Типичные ловушки

#### Ловушка №1: "Магическое" приведение в Switch/If
В слабом режиме сравнение `==` часто приводит к неожиданным результатам.

```php
// Слабый режим (без strict_types)
if ("0" == false) { /* Это сработает (true) */ }
if ("foobar" == 0) { /* Это сработает (true) в старых версиях PHP, 
   в PHP 8.0+ поведение изменилось, но это все еще опасная зона */ }

// Решение: Всегда использовать === (строгое сравнение)
```

#### Ловушка №2: Nullable типы и отсутствие проверки
Частая ошибка — забыть, что тип может быть `null`, если не использовать знак `?` (или union type `|null`).

```php
function getName(User $user): string { ... }

// Если метод вернет null, а в сигнатуре не указано ?string, будет фатальная ошибка.
```

#### Ловушка №3: Массивы и их содержимое
PHP позволяет типизировать переменную как `array`, но **нельзя** типизировать содержимое массива (например, нельзя сказать «массив только из объектов User» на уровне синтаксиса языка). Это решается только через PHPDoc и статический анализ (PHPStan/Psalm).

---

### 4. Примеры: Где типизация спасает и где удивляет

#### Где типизация СПАСАЕТ (Prevention of Logic Errors)

Представьте работу с деньгами. Без строгой типизации легко передать строку или float вместо целого числа (копеек).

```php
declare(strict_types=1);

class Wallet {
    // Используем int для копеек, чтобы избежать проблем float
    public function addMoney(int $amount): void {
        // ...
    }
}

$wallet = new Wallet();

// ОШИБКА: PHP не даст передать строку или float, предотвращая потерю точности
// $wallet->addMoney(100.50); // TypeError!
// $wallet->addMoney("100");  // TypeError!
```
*Здесь типизация выступает как «предохранитель», не давая неверным данными испортить состояние системы.*

#### Где типизация УДИВЛЯЕТ (The "Surprise" Factor)

Самое частое удивление связано с тем, что `strict_types` работает **локально** для файла.

```php
// Файл A.php
function process(int $id) { return $id; }

// Файл B.php
require 'A.php';

function caller() {
    return process("123"); // В B.php нет strict_types=1, поэтому PHP приведёт "123" к 123.
}

// Файл C.php
declare(strict_types=1);
require 'A.php';

function callerStrict() {
    return process("123"); // В C.php ЕСТЬ strict_types=1, будет TypeError!
}
```

**Итог:** 
Для написания надежного кода я всегда:
1. Использую `declare(strict_types=1);` во всех файлах.
2. Использую строгое сравнение `===`.
3. Опираюсь на статический анализ (PHPStan), чтобы «закрыть» дыры в типизации массивов и коллекций.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

Проектирование обработки исключений — это не просто использование `try-catch`, это проектирование **поведения системы при ошибках**. Я придерживаюсь принципа: исключение — это не способ управления логикой (не `goto`), а сигнал о том, что текущий поток выполнения прерван из-за нарушения бизнес-правил или технических сбоев.

Вот мой подход:

### 1. Иерархия исключений
Я никогда не использую базовый `\Exception` или `\RuntimeException` напрямую в бизнес-логике. Я создаю собственную иерархию, разделяя их на два больших ветви:

*   **Domain Exceptions (Business Logic Errors):** Это ошибки, которые «ожидаемы» в контексте бизнеса. Например, `InsufficientFundsException` или `UserAlreadyExistsException`. Они не являются системным сбоем; это штатная ситуация, на которую приложение должно отреагировать (например, показать пользователю красивое сообщение).
*   **Infrastructure Exceptions (Technical Errors):** Ошибки внешнего мира. `DatabaseConnectionException`, `ExternalApiTimeoutException`. Они обычно сигнализируют о том, что что-то сломалось «под капотом».

**Пример структуры:**
```text
App\Exception\
├── Domain\
│   ├── DomainExceptionInterface (маркерный интерфейс)
│   ├── Order\
│   │   └── OrderNotFoundException
│   └── User\
│       └── InvalidEmailException
└── Infrastructure\
    ├── Persistence\
    │   └── RepositoryException
    └── ExternalApi\
        └── ServiceUnavailableException
```

### 2. Оборачивание (Exception Wrapping)
Это критически важный момент для соблюдения слоистости архитектуры (Clean Architecture). **Слой приложения не должен знать о деталях реализации инфраструктуры.**

Если `Doctrine` выбрасывает `UniqueConstraintViolationException`, мой репозиторий не должен пробрасывать его выше. Это «протекающая абстракция». Вместо этого я ловлю техническое исключение и оборачиваю его в свое доменное.

```php
// Внутри Repository
public function save(User $user): void {
    try {
        $this->entityManager->persist($user);
        $this->entityManager->flush();
    } catch (UniqueConstraintViolationException $e) {
        // Оборачиваем: сохраняем контекст ошибки, но меняем тип на понятный домену
        throw new UserAlreadyExistsException("User with email {$user->getEmail()} exists", 0, $e);
    }
}
```
*Зачем это нужно?* Если завтра мы заменим Doctrine на чистый SQL или MongoDB, вызывающий код (Service/Controller) не изменится, так как он ожидает `UserAlreadyExistsException`, а не специфичный для ORM класс.

### 3. Контракт метода
Контракт метода состоит из двух частей:
1.  **Что он возвращает (Success path).**
2.  **Что он выбрасывает (Error path).**

Если метод может выбросить исключение, которое является частью бизнес-логики, это **обязательно** должно быть зафиксировано в PHPDoc. Это часть документации для разработчика.

```php
/**
 * @throws InsufficientFundsException Если на счету недостаточно средств
 * @throws AccountLockedException Если аккаунт заблокирован
 */
public function withdraw(int $amount): void;
```

### 4. Антипаттерны

1.  **Exception as Flow Control (Исключение как управление потоком):**
    Использование `try-catch` для проверки условий.
    *Плохо:* `try { $user->login(); } catch (InvalidCredentialsException $e) { ... }` — если это ожидаемое поведение, лучше использовать возвращаемый объект-результат или проверку `if`.
    *Правило:* Исключение должно быть «дорогим» и редким событием.

2.  **Catching Generic Exceptions (Ловля всего подряд):**
    `catch (\Exception $e)` или `catch (\Throwable $e)` без последующего логирования или специфической обработки. Это «заглатывание» ошибок, которое делает отладку невозможной.

3.  **Missing Context (Потеря контекста):**
    Создание нового исключения без передачи предыдущего (`$previous`).
    *Плохо:* `throw new MyException("Error");`
    *Хорошо:* `throw new MyException("Error", 0, $originalException);` (сохранение Stack Trace оригинала).

4.  **Leaking Implementation Details (Утечка деталей реализации):**
    Когда контроллер ловит `PDOException`. Это нарушает инкапсуляцию и заставляет верхние слои зависеть от низкоуровневых драйверов БД.

### Итог моего подхода:
*   **Слой Domain** определяет свои ошибки.
*   **Слой Infrastructure** оборачивает свои ошибки в ошибки Domain или Infrastructure-слоя.
*   **Слой Application** (Use Cases) управляет транзакциями и решает, прервать выполнение или продолжить.
*   **Слой UI (Controller/CLI)** — это последнее звено, которое ловит исключения и превращает их в HTTP-ответы (400, 404, 500) или вывод в консоль.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

По моему опыту, чаще всего в реальном коде нарушается принцип **Single Responsibility Principle (SRP)** — Принцип единственной ответственности.

### Почему это происходит?
Разработчики (особенно в условиях горящих дедлайнов) склонны идти по пути наименьшего сопротивления. Проще всего добавить еще одну проверку, еще один запрос в БД или еще одну отправку письма в тот же класс, который уже делает основную работу. В итоге класс превращается в «Божественный объект» (God Object), который знает и делает слишком много.

### Типовой пример нарушения (SRP)

Представим сервис для регистрации пользователя. В плохом примере он делает всё: сохраняет в БД, отправляет email и логирует действия.

```php
class UserRegistrationService {
    public function register(array $data): void {
        // 1. Валидация (бизнес-логика или инфраструктура?)
        if (!isset($data['email']) || !filter_var($data['email'], FILTER_VALIDATE_EMAIL)) {
            throw new \InvalidArgumentException("Invalid email");
        }

        // 2. Работа с БД (инфраструктура)
        $user = new User($data['email'], $data['password']);
        // Представим, что здесь прямой вызов PDO или Doctrine
        $db->query("INSERT INTO users ..."); 

        // 3. Отправка уведомления (внешний сервис)
        $mail = new Mailer();
        $mail->send($data['email'], "Welcome!");

        // 4. Логирование (инфраструктура)
        file_put_contents('app.log', "User registered: " . $data['email'], FILE_APPEND);
    }
}
```

**Проблемы этого кода:**
1.  **Сложность тестирования:** Чтобы протестировать регистрацию, вам нужно имитировать и БД, и почтовый сервер, и файловую систему.
2.  **Хрупкость:** Если формат логов изменится или мы перейдем с почты на SMS, нам придется менять класс `UserRegistrationService`.
3.  **Дублирование:** Если нам понадобится регистрация через API, нам придется либо дублировать код, либо тащить этот тяжелый класс.

---

### Рефакторинг (Применение SRP и DI)

Мы разделяем ответственности, делегируя работу специализированным сервисам.

```php
// 1. Интерфейсы для абстракции (Dependency Inversion тоже в помощь)
interface UserRepositoryInterface {
    public function save(User $user): void;
}

interface NotificationServiceInterface {
    public function sendWelcomeEmail(User $user): void;
}

// 2. Чистый сервис, отвечающий ТОЛЬКО за процесс регистрации (оркестрация)
class UserRegistrationService {
    public function __construct(
        private UserRepositoryInterface $userRepository,
        private NotificationServiceInterface $notificationService,
        private LoggerInterface $logger // Стандартный PSR-3 логгер
    ) {}

    public function register(UserRegistrationDto $dto): void {
        // DTO (Data Transfer Object) берет на себя ответственность за структуру данных
        $user = new User($dto->email, $dto->password);

        // Оркестрация шагов
        $this->userRepository->save($user);
        $this->notificationService->sendWelcomeEmail($user);
        
        $this->logger->info("User registered: {email}", ['email' => $user->getEmail()]);
    }
}
```

### Что изменилось?

1.  **Single Responsibility:** `UserRegistrationService` теперь не знает, *как* сохраняется пользователь или *как* отправляется письмо. Он знает только *последовательность* действий.
2.  **Тестируемость:** Теперь я могу легко написать Unit-тест, подставив "заглушки" (Mocks) для репозитория и почтовика. Мне не нужна реальная БД.
3.  **Гибкость:** Если завтра мы решим использовать `Mailgun` вместо `SMTP` или `Redis` вместо `MySQL`, мы просто создадим новую реализацию интерфейса, не меняя ни строчки в `UserRegistrationService`.
4.  **Типобезопасность:** Вместо массива `$data`, где может не быть ключа `email`, мы используем `UserRegistrationDto`, что исключает ошибки на входе.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Короткий ответ: **Да, можно.**

SOLID — это не догма и не закон физики, а набор инженерных рекомендаций. В проектировании программного обеспечения всегда существует фундаментальный компромисс (trade-off) между **чистотой архитектуры** и **стоимостью разработки** (временем, сложностью и ресурсами).

Нарушение принципов оправдано, когда цена «соблюдения правил» превышает ценность, которую они приносят.

### Когда нарушение оправдано?

1.  **Proof of Concept (PoC) или прототипирование:** Когда ваша задача — быстро проверить гипотезу или показать работающий макет заказчику. Здесь скорость важнее масштабируемости.
2.  **Малые скрипты и утилиты:** Если вы пишете скрипт на 50 строк, который запускается раз в месяц для миграции данных, внедрять туда интерфейсы, DTO и цепочки сервисов — это **Overengineering** (избыточное проектирование).
3.  **Legacy-код и жесткие сроки:** Если код работает, а задача — поправить опечатку в тексте, переписывание всего модуля по SOLID может привести к регрессии и неоправданным затратам.
4.  **Микросервисы с очень узкой зоной ответственности:** Если сервис делает ровно одну вещь (например, только конвертирует валюту) и никогда не будет расширяться, избыточная абстракция может только усложнить чтение кода.

---

### Пример оправданного нарушения: Принцип Interface Segregation (ISP) или Dependency Inversion (DIP)

Представьте, что вы пишете очень простой внутренний инструмент для админов, который просто выгружает список пользователей в CSV.

**Вариант "По SOLID" (Overengineering):**
Вы создаете `UserExporterInterface`, `CsvExporterAdapter`, `UserProviderInterface`, `DatabaseUserProvider`, внедряете их в `ExportService`. Кода — 200 строк, тестов — 100 строк.

**Вариант "Оправданное нарушение":**
Вы пишете один простой класс, который делает всё за один проход.

```php
// Это нарушение DIP и ISP, так как класс жестко привязан к БД и формату CSV
class SimpleUserExporter {
    public function exportToCsv(PDO $pdo, string $filename): void {
        $users = $pdo->query("SELECT email FROM users")->fetchAll();
        $fp = fopen($filename, 'w');
        foreach ($users as $user) {
            fputcsv($fp, [$user['email']]);
        }
        fclose($fp);
    }
}
```

**Почему это оправдано?**
*   **Сложность:** Этот скрипт — «одноразовый» инструмент.
*   **Риски:** Внедрение интерфейсов создаст иллюзию гибкости там, где она не нужна. Мы потратим 2 часа на архитектуру, которую никогда не будем расширять.
*   **Поддержка:** Другому разработчику проще прочитать один линейный скрипт, чем прыгать по пяти файлам интерфейсов, чтобы понять, как работает простейшая выгрузка.

### Золотое правило инженера:
**«Не усложняй, пока не возникнет необходимость в усложнении»** (YAGNI — *You Ain't Gonna Need It*).

Нарушать SOLID нужно осознанно, понимая, что вы осознанно создаете **технический долг**, и понимая, когда этот долг станет слишком дорогим и когда его нужно будет вернуть (рефакторить).

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Вы абсолютно правы. Наследование — это самый старый и прямолинейный способ реализации **Open/Closed Principle (OCP)**, но в современном объектно-ориентированном программировании оно считается «тяжелым» и хрупким (проблема хрупкого базового класса).

На практике OCP реализуется через **композицию** и **делегирование**. Основная идея: мы не меняем существующий класс, а меняем *поведение*, которое он использует.

Вот основные способы:

### 1. Композиция и паттерн «Стратегия» (Strategy)
Это самый распространенный способ. Вместо того чтобы наследовать класс, чтобы изменить один метод, мы выносим это поведение в отдельный объект (стратегию) и передаем его в основной класс через конструктор.

**Пример:** Система оплаты.
*   **Плохо (через наследование):** Создавать `PayPalOrder`, `StripeOrder`, `CryptoOrder` через наследование от `Order`. При добавлении нового метода оплаты придется плодить классы.
*   **Хорошо (OCP через композицию):**

```php
interface PaymentStrategy {
    public function pay(int $amount): void;
}

class StripePayment implements PaymentStrategy {
    public function pay(int $amount): void { /* логика Stripe */ }
}

class Order {
    public function __construct(private PaymentStrategy $paymentStrategy) {}

    public function process(int $amount): void {
        // Класс Order закрыт для изменений, но открыт для новых способов оплаты
        $this->paymentStrategy->pay($amount);
    }
}
```

### 2. Паттерн «Декоратор» (Decorator)
Декоратор позволяет динамически добавлять объекту новые обязанности, не меняя его код и не используя наследование. Мы «оборачиваем» базовый объект в новый объект, который расширяет функционал.

**Пример:** Логирование или кэширование.
Вместо того чтобы создавать `LoggedUserRepository` и `CachedUserRepository`, мы создаем декораторы.

```php
interface UserRepository {
    public function find(int $id): User;
}

class BaseUserRepository implements UserRepository {
    public function find(int $id): User { /* запрос в БД */ }
}

// Декоратор для логирования
class LoggingUserRepository implements UserRepository {
    public function __construct(private UserRepository $inner) {}

    public function find(int $id): User {
        echo "Log: Searching for user $id\n";
        return $this->inner->find($id);
    }
}

// Использование:
$repo = new LoggingUserRepository(new BaseUserRepository());
$repo->find(1);
```

### 3. Паттерн «Наблюдатель» (Observer / Event Dispatcher)
Этот способ реализует OCP на уровне системы событий. Основной объект просто «кричит» в пространство: *«Что-то произошло!»*, а другие объекты (слушатели) реагируют на это.

**Пример:** Регистрация пользователя.
Чтобы после регистрации отправить Email, отправить SMS и начислить бонусы, нам **не нужно** менять класс `UserRegistrationService`. Мы просто подписываем новых слушателей на событие `UserRegistered`.

```php
class UserRegistrationService {
    public function __construct(private EventDispatcher $dispatcher) {}

    public function register(User $user): void {
        // ... логика регистрации ...
        $this->dispatcher->dispatch(new UserRegisteredEvent($user));
    }
}

// Новые функции добавляются внешними слушателями, не трогая сервис регистрации.
```

### 4. Использование Callbacks (Замыканий)
В PHP (и других языках) можно передать поведение прямо в метод в виде анонимной функции. Это самый простой и быстрый способ реализации OCP для небольших задач.

**Пример:**
```php
class DataProcessor {
    public function process(array $data, callable $transformation): array {
        $result = [];
        foreach ($data as $item) {
            $result[] = $transformation($item);
        }
        return $result;
    }
}

$processor = new DataProcessor();
// Мы расширяем логику обработки, не меняя DataProcessor
$upperCase = $processor->process(['a', 'b'], fn($s) => strtoupper($s));
```

### Резюме: что выбрать?

| Способ | Когда использовать |
| :--- | :--- |
| **Стратегия** | Когда у вас есть несколько алгоритмов одной задачи (оплата, сортировка). |
| **Декоратор** | Когда нужно добавить поведение (логи, кэш, валидация) к существующему объекту, не меняя его. |
| **Observer** | Когда одно действие в системе должно запускать цепочку независимых реакций. |
| **Callbacks** | Для простых, разовых трансформаций данных внутри метода. |

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Короткий ответ: **Нет.**

Хотя в контекстe объектно-ориентированного программирования (ООП) мы чаще всего говорим о классах, принцип единственной ответственности (SRP) является более фундаментальным. Он относится к **любому модулю системы**, который имеет границы ответственности.

Вот где еще он применяется:

### 1. Функции и методы (в процедурном и функциональном стиле)
Это самый первый уровень SRP. Функция должна делать одну вещь и делать её хорошо.
*   **Нарушение:** Функция `processData()`, которая читает файл, парсит его, считает сумму, сохраняет в базу и отправляет Email.
*   **Соблюдение:** Одна функция читает, вторая парсит, третья считает.

### 2. Модули и пакеты (Packages/Libraries)
На уровне архитектуры приложения модули (или микросервисы) должны иметь одну зону ответственности.
*   **Нарушение:** Модуль `Billing`, который помимо управления счетами, еще и занимается управлением профилями пользователей и хранением контента.
*   **Соблюдение:** Модуль `Billing` отвечает только за деньги. Если ему нужны данные пользователя, он запрашивает их у модуля `UserManagement` через API или события.

### 3. Микросервисы (Microservices)
В распределенных системах SRP превращается в принцип **Bounded Context** (Ограниченный контекст) из DDD.
*   **Нарушение:** «Распределенный монолит», где один сервис пытается обслуживать все потребности компании, становясь узким местом и чрезмерно сложным.
*   **Соблюдение:** Каждый микросервис отвечает за свою бизнес-область (например, сервис заказов, сервис каталога, сервис доставки).

### 4. Файлы и структура проекта
Даже структура папок в вашем проекте должна следовать SRP.
*   **Нарушение:** Один огромный файл `utils.php`, в котором лежат и функции для работы с датами, и функции для работы с текстом, и функции для работы с БД.
*   **Соблюдение:** Разделение на `DateUtils.php`, `StringUtils.php`, `DbUtils.php`.

### 5. Базы данных (Таблицы и Схемы)
Даже на уровне проектирования БД есть подобие SRP.
*   **Нарушение:** Таблица `users`, в которой хранятся и данные профиля, и настройки уведомлений, и история последних покупок, и технические метаданные логов.
*   **Соблюдение:** Нормализация данных. Таблица `users` (основные данные), `user_profiles` (доп. информация), `user_settings` (настройки).

---

### Почему важно понимать это шире, чем просто "классы"?

Если вы будете применять SRP только к классам, вы можете создать идеально чистые классы, которые при этом будут объединены в один гигантский, запутанный и неповоротливый модуль (или микросервис). 

**Настоящий мастер архитектуры применяет SRP на всех уровнях абстракции:**
1.  **Метод** (микро-уровень)
2.  **Класс** (уровень объектов)
3.  **Модуль/Пакет** (уровень компонентов)
4.  **Микросервис** (уровень системы)

**Резюме:** SRP — это принцип **разделения ответственности**, а не принцип «одного класса». Любой компонент системы должен иметь одну четкую цель.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

Это глубокий вопрос, который затрагивает внутреннюю «магию» Symfony. Чтобы понять, как это работает, нужно разделить жизненный цикл контейнера на два этапа: **Компиляция** (build time) и **Работа** (runtime).

### 1. Этап компиляции (Compilation Phase)
В Symfony контейнер не создается «с нуля» при каждом запросе. Он проходит стадию сборки, которая происходит один раз (при очистке кэша или установке нового кода).

**Что происходит в этот момент:**
1.  **Сбор конфигурации:** Symfony проходит по всем файлам конфигурации (`services.yaml`, аннотациям/атрибутам, параметрам) и собирает «чертежи» всех сервисов.
2.  **Регистрация Definition:** Для каждого сервиса создается объект `Definition`. Это не сам сервис, а «рецепт»: какой у него класс, какие аргументы нужны в конструктор, какие методы вызвать (calls).
3.  **Проход компилятора (Compiler Passes):** Это самый важный этап. Symfony запускает цепочку «компиляторов», которые модифицируют `Definition`.
    *   Они ищут реализации интерфейсов.
    *   Они находят все сервисы, помеченные тегами (например, `kernel.event_listener`), и собирают их в специальные коллекции.
    *   Они могут изменять определения (например, заменять один сервис другим в зависимости от среды `dev/prod`).
4.  **Генерация оптимизированного PHP-кода:** После того как все `Definition` обработаны, Symfony берет этот «план» и генерирует на его основе один огромный, максимально оптимизированный PHP-файл (обычно в `var/cache/.../App_KernelDevDebugContainer.php`).

**Результат компиляции:** Вместо того чтобы на лету парсить YAML-файлы, PHP просто подключает один готовый файл, где все связи уже прописаны в виде чистого кода. Это делает контейнер невероятно быстрым.

---

### 2. Как работает Autowiring
Autowiring — это не магия во время работы приложения, это **магия во время компиляции**.

Когда вы помечаете сервис как `autowire: true`, происходит следующее:
1.  В процессе компиляции Symfony использует **Reflection API**, чтобы посмотреть на конструктор вашего класса.
2.  Она видит: «Ага, этому классу нужен `UserRepositoryInterface`».
3.  Она ищет в контейнере сервис, который реализует этот интерфейс.
4.  Если находит (и если нет конфликтов — например, двух реализаций одного интерфейса), она **автоматически записывает** этот сервис в `Definition` вашего класса.

**Важно:** В момент выполнения (runtime) никакого рефлексирования не происходит. В сгенерированном PHP-файле уже жестко прописано: `new MyService(new UserRepository())`.

---

### 3. Момент запроса сервиса (Runtime: Lazy Loading)
Когда вы вызываете `$container->get(MyService::class)` (или когда сервис запрашивается через DI в контроллере), происходит следующее:

1.  **Проверка в кэше (Singleton pattern):** Контейнер проверяет, был ли этот сервис уже создан ранее. В Symfony все сервисы по умолчанию являются **shared** (синглтонами) в рамках одного жизненного цикла запроса.
2.  **Если сервис уже есть:** Он просто возвращается из внутреннего массива `$this->services`.
3.  **Если сервиса еще нет (First call):**
    *   Контейнер берет `Definition` этого сервиса.
    *   Он смотрит на список аргументов, которые были определены/вычислены на этапе компиляции.
    *   Он **рекурсивно** вызывает создание всех зависимостей (если для `A` нужен `B`, он сначала создаст `B`).
    *   Вызывает конструктор класса.
    *   Применяет дополнительные настройки (например, `set` методы, если были `calls`).
    *   Сохраняет созданный объект в массив `$this->services` и возвращает его.

#### Особый случай: Lazy Services
Если сервис помечен как `lazy`, то в момент первого запроса Symfony не создает реальный объект, а создает **Proxy-объект** (с помощью библиотеки `ocramius/proxy-manager` или встроенных средств).
*   Этот прокси выглядит как ваш класс, но он пустой.
*   Реальный объект будет создан только в тот момент, когда вы вызовете у прокси **первый реальный метод**. Это позволяет не инициализировать тяжелые сервисы, если они не понадобились в текущем сценарии.

### Итог (коротко):
*   **Компиляция:** Превращает кучу YAML/атрибутов в один быстрый PHP-файл с готовыми связями.
*   **Autowiring:** Это автоматическое заполнение связей в `Definition` через Reflection на этапе компиляции.
*   **Первый запрос:** Рекурсивное создание объектов по «рецепту» из сгенерированного файла и кэширование результата.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

Циклические зависимости (Circular Dependency) — это ситуация, когда `ServiceA` требует `ServiceB`, а `ServiceB` требует `ServiceA`. Это классическая проблема проектирования, которая говорит о том, что границы ответственности размыты.

Я подхожу к решению этой проблемы в три этапа: **анализ причин**, **архитектурное исправление** (предпочтительно) и **технические «костыли»** (если исправить архитектуру невозможно).

---

### 1. Архитектурное исправление (Правильный путь)
Прежде чем лезть в настройки контейнера, я пытаюсь понять, почему они зависят друг от друга. Обычно это признак того, что оба сервиса пытаются делать слишком много.

#### А) Выделение третьего сервиса (Extract Third Service)
Если `A` и `B` зависят друг от друга, скорее всего, есть какая-то общая логика, которая принадлежит обоим. Я выделяю эту логику в новый `ServiceC`, и теперь `A` и `B` зависят от `C`, но не друг от друга.

*   **Было:** `A <-> B`
*   **Стало:** `A -> C` и `B -> C`

#### Б) Пересмотр иерархии (Inversion of Control)
Иногда циклическая зависимость возникает из-за того, что высокоуровневый сервис пытается вызвать низкоуровневый, а низкоуровневый хочет сообщить о чем-то высокоуровневому.
Вместо того чтобы вызывать высокоуровневый сервис напрямую, я использую **событийную модель (Event Dispatcher)**.

*   **Пример:** `OrderService` (высокий уровень) вызывает `PaymentService` (низкий уровень). А `PaymentService` хочет вызвать `OrderService`, чтобы обновить статус заказа.
*   **Решение:** `PaymentService` просто кидает событие `PaymentCompletedEvent`. `OrderService` слушает это событие. Цикл разорван.

#### В) Перенос метода
Иногда один из методов, вызывающих цикл, просто не должен находиться в этом классе. Я переношу этот метод в другой сервис, где он будет уместен.

---

### 2. Технические решения (Если архитектуру менять нельзя)

Если я работаю с Legacy-кодом или сторонней библиотекой, где рефакторинг невозможен или слишком рискован, я использую возможности Symfony.

#### А) Lazy Services (Ленивая инициализация)
Это самый чистый из «технических» способов. Если я помечу один из сервисов в цикле как `lazy`, Symfony подставит вместо него **Proxy-объект**.

```yaml
# services.yaml
App\Service\ServiceA: ~
App\Service\ServiceB:
    lazy: true  # Теперь ServiceA может зависеть от ServiceB без цикла
```
**Как это работает:** `ServiceA` создается сразу. `ServiceB` не создается, вместо него подкладывается «пустышка». Реальный `ServiceB` будет создан только тогда, когда вы впервые вызовете метод у этого прокси. Цикл в момент инициализации разрывается.

#### Б) Setter Injection вместо Constructor Injection
Конструктор — это жесткое требование. Если мы используем внедрение через методы (`setServiceB`), мы можем сначала создать `ServiceA`, а затем «доложить» в него `ServiceB`.

```php
class ServiceA {
    private $serviceB;

    public function setServiceB(ServiceB $serviceB) {
        $this->serviceB = $serviceB;
    }
}
```
*Примечание: В современном Symfony/PHP это считается менее предпочтительным, так как объект может оказаться в невалидном состоянии (null в поле), пока метод не будет вызван.*

---

### Мой алгоритм действий:

1.  **Попробовать выделить `ServiceC`** (самый надежный метод).
2.  **Заменить прямой вызов на `EventDispatcher`** (лучший способ для развязки логики).
3.  Если ничего не помогает и это оправдано — **использовать `lazy: true`**.

**Чего я никогда не делаю:** Я не оставляю циклы «как есть», полагаясь на то, что «оно как-то заработает», и не использую `ServiceLocator` (пробрасывание всего контейнера в сервис), так как это скрывает зависимости и делает код нетестируемым.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

Для решения этой задачи необходимо перенести выполнение тяжелых или внешних задач из основного потока (Request-Response cycle) в фоновый режим. В Symfony для этого есть три основных подхода, различающихся по сложности и надежности.

---

### Вариант 1: Symfony Messenger + Транспорт (Рекомендуемый)

Это стандарт индустрии для Symfony. Мы используем компонент **Messenger**, который разделяет отправку команды и её выполнение.

**Как это устроено:**
1.  В сервисе `UserRegistrationService` мы не вызываем `Mailer` напрямую, а отправляем **Message** (простой DTO) в шину (Bus).
2.  Шина пересылает это сообщение в **Transport** (очередь).
3.  В фоновом процессе (Worker) работает потребитель, который забирает сообщение из очереди и выполняет его.

**Пример реализации:**
```php
// 1. Message (DTO)
class UserRegisteredEvent {
    public function __construct(public int $userId) {}
}

// 2. В сервисе регистрации
public function register(UserRegistrationDto $dto): void {
    $user = $this->userRepository->save($dto);
    // Отправляем сообщение в шину, это происходит мгновенно
    $this->messageBus->dispatch(new UserRegisteredEvent($user->getId()));
}

// 3. Handler (Выполняется в фоне)
class UserRegisteredHandler implements MessageHandlerInterface {
    public function __invoke(UserRegisteredEvent $event) {
        $user = $this->userRepository->find($event->userId);
        $this->mailer->sendWelcomeEmail($user);
        $this->searchIndexer->updateIndex($user);
    }
}
```

**Транспорты (где хранить очередь):**
*   **Doctrine:** Хранит сообщения в таблице БД. (Просто настроить, не нужно новых инструментов).
*   **Redis/RabbitMQ:** Профессиональные брокеры сообщений. (Очень быстро, высокая надежность).

**Trade-offs:**
*   ✅ **Плюсы:** Высокая надежность, автоматические повторы при ошибках (retry strategy), возможность масштабирования воркеров.
*   ❌ **Минусы:** Требует инфраструктуры (Redis/RabbitMQ) и отдельного процесса (supervisor), который будет держать воркеров запущенными.

---

### Вариант 2: FastCGI Finish Request (Быстрый "костыль")

Если мы используем PHP-FPM, можно использовать функцию `fastcgi_finish_request()`. Она позволяет закрыть HTTP-соединение с клиентом, но продолжить выполнение PHP-скрипта на сервере.

**Как это устроено:**
```php
public function register(UserRegistrationDto $dto): Response {
    $user = $this->userRepository->save($dto);
    
    // Отправляем ответ клиенту немедленно
    $response = new Response('User registered');
    $response->send(); 
    
    if (function_exists('fastcgi_finish_request')) {
        fastcgi_finish_request(); // Клиент видит страницу, но PHP еще работает
    }

    // Тяжелые задачи выполняются "в пустоту"
    $this->mailer->sendWelcomeEmail($user);
    $this->searchIndexer->updateIndex($user);
}
```

**Trade-offs:**
*   ✅ **Плюсы:** Не требует никакой дополнительной инфраструктуры. Очень легко внедрить.
*   ❌ **Минусы:** 
    *   **Нет отказоустойчивости:** Если скрипт упадет во время отправки письма, пользователь об этом не узнает, а письмо никогда не уйдет (нет повторов).
    *   **Занимает воркер PHP-FPM:** Пока выполняется фоновая задача, PHP-воркер занят и не может обрабатывать новые HTTP-запросы. При нагрузке это быстро "положит" сайт.

---

### Вариант 3: Реактивные системы / Go/Node.js sidecars (Архитектурный уровень)

В очень высоконагруженных системах задачи могут выноситься на уровень инфраструктуры. Например, PHP-приложение пишет событие в Kafka или Redis, а отдельный микросервис на Go/Python подхватывает его и делает работу.

**Trade-offs:**
*   ✅ **Плюсы:** Максимальная производительность и изоляция.
*   ❌ **Минусы:** Огромная сложность поддержки и развертывания.

---

### Итоговое сравнение и мой выбор

| Критерий | Messenger (RabbitMQ/Redis) | FastCGI Finish | Свой скрипт/Cron |
| :--- | :--- | :--- | :--- |
| **Надежность** | ⭐⭐⭐⭐⭐ (есть Retries) | ⭐ (упал — пропало) | ⭐⭐ |
| **Скорость ответа** | ⭐⭐⭐⭐⭐ (мгновенно) | ⭐⭐⭐⭐⭐ (мгновенно) | ⭐⭐⭐ (зависит от логики) |
| **Сложность внедрения** | ⭐⭐⭐ (нужен брокер) | ⭐ (одна строка) | ⭐⭐ |
| **Масштабируемость** | ⭐⭐⭐⭐⭐ | ⭐ (плохо для CPU/RAM) | ⭐⭐ |

**Мой выбор:** 
Для серьезного Enterprise-приложения я всегда выбираю **Symfony Messenger с транспортом Redis или RabbitMQ**. Это дает предсказуемость: я знаю, что если почтовый сервис упадет, сообщение не потеряется, а через 5 минут будет повторно отправлено воркером. Это обеспечивает гарантию доставки (at-least-once delivery).

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

В Symfony безопасность строится на четком разделении двух понятий: **«Кто ты?»** (Authentication) и **«Что тебе можно?»** (Authorization).

### 1. Аутентификация (Authentication) — «Кто ты?»
Это процесс проверки личности пользователя. В Symfony за это отвечает компонент `Security`.

*   **Firewalls:** В `security.yaml` мы определяем «фаерволы» — области приложения (например, `/api` или `/admin`), к которым применяются определенные правила.
*   **Authenticators:** Это классы, которые реализуют логику входа. Например, `FormLoginAuthenticator` для формы, `JWTAuthenticator` для API или `OAuthAuthenticator`.
*   **User Provider:** Механизм, который загружает данные пользователя (из БД через Doctrine, из памяти или из LDAP) на основе предоставленных учетных данных.
*   **Token Storage:** После успешного входа Symfony создает `Token` (содержащий объект `User`) и сохраняет его в `TokenStorage`. Это позволяет в любой части приложения узнать, кто сейчас авторизован.

### 2. Авторизация (Authorization) — «Что тебе можно?»
Когда мы знаем, кто пользователь, нужно решить, имеет ли он доступ к ресурсу. Здесь работают три уровня:

#### А) Роли (Roles)
Это самый простой уровень. Роли — это просто строки (например, `ROLE_USER`, `ROLE_ADMIN`).
*   **Как работают:** Проверка идет по принципу иерархии (можно настроить `role_hierarchy` в конфиге, где `ROLE_ADMIN` автоматически включает в себя `ROLE_USER`).
*   **Где используются:** В `access_control` (на уровне URL) или через аннотацию `#[IsGranted('ROLE_ADMIN')]`.

#### Б) Voters (Голосующие) — Самый мощный инструмент
Voter — это класс, который реализует логику проверки прав на основе **конкретного объекта** и **конкретного действия**.

**Как работает Voter:**
Когда вы вызываете `$this->denyAccessUnlessGranted('EDIT', $post)`, Symfony опрашивает все зарегистрированные Voter-ы.
1.  Каждый Voter получает `Token` (пользователя) и `Subject` (объект `$post`).
2.  Voter отвечает одним из трех состояний:
    *   `ACCESS_GRANTED`: Доступ разрешен.
    *   `ACCESS_DENIED`: Доступ запрещен.
    *   `ACCESS_ABSTAIN`: Я не знаю, что это за объект, пропустите меня.
3.  Если хотя бы один Voter сказал `GRANTED` (и нет запрещающих), доступ разрешен.

---

### 3. Когда выбирать Роли, а когда Voter?

Это ключевой вопрос архитектуры.

#### Используй РОЛИ, когда:
*   **Доступ зависит только от статуса пользователя.** (Например: «Только администраторы могут видеть страницу настроек»).
*   **Проверка идет на уровне URL/Маршрута.** (Например: доступ к `/admin` требует `ROLE_ADMIN`).
*   **Логика универсальна для всех.** (Например: «Любой залогиненный пользователь может смотреть ленту»).

**Минус ролей:** Они не знают о данных. Роль `ROLE_USER` не может сказать: «Ты можешь редактировать этот пост, только если ты его автор».

#### Используй VOTER, когда:
*   **Доступ зависит от владельца объекта (Ownership).** (Например: «Пользователь может редактировать только *свои* статьи»).
*   **Доступ зависит от состояния объекта (State).** (Например: «Статью нельзя редактировать, если она уже опубликована»).
*   **Нужна сложная бизнес-логика.** (Например: «Доступ разрешен, если пользователь из отдела продаж И у него есть статус 'Senior' И текущее время — рабочий час»).
*   **Проверка происходит внутри кода (в контроллере или сервисе) над конкретным объектом.**

---

### Пример для закрепления

Представим блог.

1.  **Роли:** Мы ставим `access_control` на `/admin`, чтобы только `ROLE_ADMIN` мог туда зайти. Это проверка «паспорта».
2.  **Voter:** Мы создаем `PostVoter`. Когда пользователь нажимает «Редактировать», мы вызываем `isGranted('POST_EDIT', $post)`.
    *   Voter смотрит: `if ($user === $post->getAuthor()) return GRANTED;`
    *   Voter смотрит: `if ($user->hasRole('ROLE_ADMIN')) return GRANTED;`
    *   В противном случае — `DENIED`.

**Резюме:** Роли — это про **статус** (кто ты в системе), Voter — это про **бизнес-правила** (что ты можешь делать с конкретным ресурсом).

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

Хранение Value Objects (VO) — это классическая проблема разрыва между чистой архитектурой (где VO неизменяемы и инкапсулируют логику) и реляционными БД (где данные лежат в плоских колонках).

Поскольку Doctrine по умолчанию маппит только примитивы, для VO есть три основных пути.

---

### 1. Embeddables (Встроенные объекты) — Стандартный путь
Это официальный способ Doctrine для реализации паттерна **Embedded**. VO рассматривается не как отдельная сущность, а как набор колонок внутри таблицы основной сущности.

**Пример:**
```php
#[ORM\Embeddable]
class Money {
    public function __construct(
        #[ORM\Column(type: 'int')]
        private int $amount,
        #[ORM\Column(type: 'string', length: 3)]
        private string $currency,
    ) {
        // Валидация прямо в конструкторе гарантирует валидность
        if ($amount < 0) throw new \InvalidArgumentException();
    }
    // Геттеры, методы (только без сеттеров!)
}

#[ORM\Entity]
class Order {
    #[ORM\Embedded(class: Money::class)]
    private Money $totalPrice;
}
```

**Плюсы:**
*   **Простота:** Не нужны дополнительные таблицы или сложные маппинги.
*   **Производительность:** Все данные в одной таблице, один SQL-запрос.
*   **Целостность:** Валидация в конструкторе гарантирует, что в БД не попадет «битый» объект.

**Минусы и подводные камни:**
*   **Дублирование колонок:** Если у вас 10 сущностей используют `Money`, в каждой таблице будут колонки `amount` и `currency`.
*   **Сложность запросов:** Если нужно найти все заказы с определенной валютой, придется писать `WHERE totalPrice_currency = 'USD'`.

---

### 2. Custom Mapping Types (Собственные типы) — Путь сериализации
Вы можете создать свой тип данных (чеlрез `Type`), который будет превращать объект в строку (например, JSON или строку с разделителем) при сохранении и обратно при чтении.

**Пример:** Хранение `Money` как строка `100|USD` в одной колонке.

**Плюсы:**
*   **Чистота схемы:** Одна колонка вместо нескольких.
*   **Универсальность:** Легко переиспользовать тип по всему проекту.

**Минусы и подводные камни:**
*   **Невозможность фильтрации:** Вы не сможете эффективно сделать запрос `WHERE amount > 100` на уровне SQL, так как значение лежит внутри строки/JSON. Это убивает производительность на больших данных.
*   **Потеря типизации в БД:** База данных видит просто `string` или `text`, а не число и код валюты.

---

### 3. Entity mapping (Связь One-to-One) — Путь сущностей
Вы можете превратить VO в полноценную `Entity` и связать её с основной сущностью через `OneToOne`.

**Плюсы:**
*   **Полноценные запросы:** Можно строить сложные SQL-запросы по полям VO.
*   **Переиспользование:** Объект может существовать независимо.

**Минусы и подводные камни:**
*   **Нарушение сути VO:** Value Object по определению не имеет ID и жизненного цикла. Превращение его в Entity с `id` нарушает принципы DDD.
*   **Проблема производительности (N+1):** Чтобы получить `Order` и его `Money`, Doctrine придется сделать дополнительный JOIN или отдельный запрос, если не настроен `fetch="EAGER"`.

---

### Как обеспечить неизменяемость (Immutability)

Чтобы VO был по-настоящему неизменяемым, нужно соблюдать три правила:

1.  **Запрет сеттеров:** В классе VO не должно быть методов `set...`.
2.  **Конструктор как единственный вход:** Все данные передаются только при создании.
3.  **Методы, возвращающие новый экземпляр:** Если нужно «изменить» значение, метод должен вернуть новый объект.

```php
public function add(int $extra): self {
    return new self($this->amount + $extra, $this->currency);
}
```

### Итоговая рекомендация

1.  **Если VO — это логическая часть сущности** (адрес, деньги, координаты) $\rightarrow$ используйте **Embeddables**. Это самый сбалансированный путь для производительности и чистоты.
2.  **Если VO — это очень мелкая, простая строка/массив** и вам **не нужно** по нему фильтровать в SQL $\rightarrow$ используйте **Custom Mapping Type** (сериализация в JSON).
3.  **Никогда** не превращайте VO в Entity только ради того, чтобы не возиться с Embeddables — это создаст архитектурный долг и проблемы с производительностью.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

Это один из самых важных вопросов при переходе от «Data-Driven» к «Domain-Driven» подходу. Главная цель — сделать так, чтобы **Агрегат был единицей целостности**. Это значит, что внешние объекты не могут менять дочерние элементы напрямую, минуя Корень Агрегата (Aggregate Root).

Разберем на примере агрегата **Заказ (Order)**, который содержит коллекцию **Позиций заказа (OrderItem)**.

---

### 1. Маппинг коллекций (Encapsulation)

В Doctrine мы используем `OneToMany` для связи. Но чтобы соблюсти инкапсуляцию, мы **не должны** давать доступ к коллекции через геттер, который возвращает саму коллекцию Doctrine (`ArrayCollection`). Если мы это сделаем, любой сервис сможет вызвать `$order->getItems()->add($item)`, нарушив правила бизнеса (например, добавив товар в закрытый заказ).

**Правильный подход:**
*   Коллекция в классе должна быть `private`.
*   Геттер должен возвращать либо `ReadOnlyArray`, либо (что проще и чаще) возвращать копию или итератор.
*   Изменение коллекции происходит только через методы самого Корня.

```php
#[ORM\Entity]
class Order {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    /** @var Collection<int, OrderItem> */
    #[ORM\OneToMany(mappedBy: 'order', targetEntity: OrderItem::class, cascade: ['all'], orphanRemoval: true)]
    private Collection $items;

    public function __construct() {
        $this->items = new ArrayCollection();
    }

    // Запрещаем прямой доступ к коллекции!
    public function getItems(): array {
        return $this->items->toArray();
    }

    // Единственный способ изменить состав — через метод Агрегата
    public function addItem(Product $product, int $quantity): void {
        if ($this->isClosed()) {
            throw new OrderClosedException();
        }
        
        $item = new OrderItem($this, $product, $quantity);
        $this->items->add($item);
    }
}
```
*Важно: `orphanRemoval: true` критичен. Если мы удалим элемент из коллекции `$items`, Doctrine должна автоматически удалить его из БД.*

---

### 2. Границы транзакции (Transaction Boundaries)

Согласно правилам DDD, **одна транзакция = один Агрегат**. 

Это значит, что если вам нужно обновить `Order` и одновременно `UserBalance`, это должно происходить в одной транзакции, но это сигнал о том, что либо ваши границы агрегатов размыты, либо вам нужно использовать **Eventual Consistency** (через Messenger/события).

В рамках одного Агрегата (`Order` + `OrderItem`):
*   Любые изменения внутри `Order` (добавление товара, смена статуса) должны быть атомарными. 
*   Doctrine делает это автоматически, если мы вызываем `flush()` один раз в конце операции.

---

### 3. Кто и когда вызывает `flush()`?

Это вечный спор, но в современной Symfony-архитектуре есть золотой стандарт.

**Антипаттерн: `flush()` внутри сервиса или репозитория.**
Если `OrderRepository->save($order)` внутри вызывает `flush()`, то вы теряете контроль над транзакцией. Если вы захотите в одном бизнес-процессе сохранить два агрегата, вы не сможете откатить первый, если второй упадет.

**Правильный паттерн: `flush()` на уровне Application Service (Use Case).**

Слой приложения (Application Layer) управляет процессом. Он открывает транзакцию, вызывает методы доменных моделей и в самом конце фиксирует изменения.

```php
class PlaceOrderService { // Это Application Service
    public function __construct(
        private OrderRepository $orderRepository,
        private EntityManagerInterface $entityManager,
        private PaymentGateway $paymentGateway
    ) {}

    public function execute(OrderData $data): void {
        // 1. Начинаем транзакцию
        $this->entityManager->beginTransaction();

        try {
            // 2. Работаем с Агрегатом
            $order = new Order($data->customerId);
            foreach ($data->items as $itemData) {
                $order->addItem($itemData->product, $itemData->qty);
            }

            $this->orderRepository->save($order);

            // 3. Внешние действия (Side effects)
            $this->paymentGateway->charge($order->getTotal());

            // 4. Фиксируем всё одним махом
            $this->entityManager->flush();
            $this->entityManager->commit();

        } catch (\Exception $e) {
            // 5. В случае ошибки — откатываем всё
            $this->entityManager->rollback();
            throw $e;
        }
    }
}
```

### Итоговая схема:

1.  **Mapping:** Используем `cascade: ['all']` и `orphanRemoval: true`. Доступ к коллекции только через методы `add/remove`.
2.  **Transaction:** Одна транзакция на один бизнес-процесс (один или несколько агрегатов).
3.  **Flush:** Вызывается строго в **Application Service** после завершения всех доменных операций. Репозиторий только подготавливает состояние (через `persist`), но не "закрывает" сделку.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

Проблема N+1 — это классическая ошибка, когда вместо одного запроса с `JOIN` Doctrine делает один запрос для получения основных сущностей, а затем еще $N$ запросов для получения связанных данных для каждой из них.

### 1. Диагностика

Прежде чем чинить, нужно подтвердить проблему.

*   **Symfony Profiler (лучший способ):** Открываем вкладку **Doctrine**. Там наглядно показано количество запросов. Если я вижу 50 одинаковых запросов к таблице `comments` для одного запроса к `posts` — это оно. Профайлер также подсвечивает дубликаты.
*   **SQL Log (в разработке):** Включение логирования SQL (через `doctrine/sql-logger`) позволяет видеть поток запросов в консоли или логах.
*   **Инструменты APM:** В продакшене использую **New Relic** или **Sentry**. Они строят "Trace", где видно дерево вызовов и аномально длинные цепочки SQL-запросов.

---

### 2. Способы решения и их Trade-offs

#### Способ А: Eager Loading через JOIN (Query Builder / DQL)
Это основной способ. Мы явно говорим Doctrine: «Когда будешь доставать сущность А, сразу подтяни сущность Б одним запросом».

```php
// В репозитории
return $this->createQueryBuilder('p')
    ->leftJoin('p.comments', 'c')
    ->addSelect('c') // Ключевой момент: выбираем данные комментариев
    ->getQuery()
    ->getResult();
```

*   **Плюсы:** Решает проблему в корне. Один запрос вместо $N+1$. Очень высокая производительность.
*   **Минусы/Риски:** 
    *   **Cartesian Product (Декартово произведение):** Если у одного поста 100 комментариев, а у него еще 10 тегов, `JOIN` создаст огромное количество строк в результирующей таблице, которые Doctrine будет мучительно парсить.
    *   **Сложность:** Нужно писать специфичные методы в репозитории под каждый конкретный случай использования.

#### Способ Б: Fetch Mode `EAGER` (Mapping level)
Можно настроить маппинг в аннотациях/атрибутах так, чтобы связь всегда загружалась сразу.

```php
#[ORM\ManyToOne(targetEntity: User::class, fetch: 'EAGER')]
private User $author;
```

*   **Плюсы:** Проще в написании, не нужно менять каждый запрос в репозитории.
*   **Минусы/Риски:** 
    *   **Глобальность:** Это "ядерный" вариант. Связь будет подтягиваться **всегда**, даже там, где она не нужна (например, в админке для списка, где имя автора не отображается). Это приводит к избыточной нагрузке на память и БД.
    *   **Антипаттерн:** Обычно это считается плохой практикой, так как нарушает предсказуемость нагрузки.

#### Способ В: Использование `Partial Objects` или `DTO` (Data Transfer Objects)
Вместо того чтобы загружать тяжелые объекты со всеми их связями, мы выбираем только нужные поля прямо в SQL.

```php
// Выбираем только ID и имя, не загружая сущности целиком
return $this->createQueryBuilder('p')
    ->select('NEW App\Dto\PostSummaryDto(p.id, p.title, u.username)')
    ->join('p.author', 'u')
    ->getQuery()
    ->getResult();
```

*   **Плюсы:** Максимальная производительность. Минимальное потребление памяти (не создаются объекты Entity с их UnitOfWork).
*   **Минусы/Риски:** Полученные объекты — это просто данные (DTO), у них нет методов доменной модели. Их нельзя сохранить обратно в БД через `flush()`.

#### Способ Г: Использование `Batch Processing` (для фоновых задач)
Если проблема N+1 возникла не в контроллере, а в консольной команде, которая обрабатывает 10 000 записей.

*   **Решение:** Загружать данные пачками (например, по 100 штук) и периодически делать `$entityManager->clear()`, чтобы очистить память от обработанных объектов.

---

### Итоговая стратегия (мой алгоритм):

1.  **По умолчанию:** Всегда использую `fetch: 'LAZY'` (стандарт Doctrine).
2.  **Если вижу N+1 в профайлере:** Иду в репозиторий и переписываю метод, используя `leftJoin` + `addSelect` (**Способ А**). Это мой основной инструмент.
3.  **Если данных слишком много и они "тяжелые":** Перехожу на выборку через **DTO** (**Способ В**), чтобы не нагружать память и не забивать UnitOfWork.
4.  **Никогда** не использую `fetch: 'EAGER'` в маппинге, если не уверен на 100%, что это нужно везде.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

Это отличный вопрос, который часто вызывает споры между разработчиками. Короткий ответ: **Бизнес-валидация в коде отвечает за пользовательский опыт и правила домена, а ограничения в БД отвечают за сохранность и целостность данных как физического актива.**

Никакой код приложения не может гарантировать 100% целостность данных. Ошибки в логике, баги в конкурентном доступе или прямые правки в БД администратором могут нарушить правила, заложенные в PHP. База данных — это **последний рубеж обороны**.

Вот почему я использую оба уровня и как это разделяю.

---

### 1. Зачем нужны ограничения в БД (Layer of Defense)

1.  **Конкурентный доступ (Race Conditions):**
    Бизнес-валидация в PHP часто страдает от состояния гонки.
    *Пример:* Два параллельных запроса проверяют баланс пользователя (`if ($balance >= 100)`). Оба видят, что денег хватает. Оба списывают деньги. Итог: баланс ушел в минус. 
    *Решение:* `CHECK (balance >= 0)` в PostgreSQL предотвратит это на уровне транзакции, даже если PHP-код «ошибся».

2.  **Целостность связей (Referential Integrity):**
    Если мы удалим пользователя, у которого есть активные заказы, и в коде забудем обработать это, мы получим «сиротские» записи.
    *Решение:* `FOREIGN KEY` с правилами `ON DELETE RESTRICT` или `CASCADE` гарантирует, что связи не будут разорваны.

3.  **Защита от "человеческого фактора":**
    Администратор или аналитик может зайти в консоль `psql` и поправить данные. Без ограничений в БД он может легко нарушить бизнес-логику (например, поставить некорректный статус).

---

### 2. Какие средства я использую и когда

Я разделяю ограничения на три категории:

#### А. Ограничения целостности (Обязательно)
Это то, что должно быть в БД **всегда**.
*   **`NOT NULL`**: Если поле обязательно для бизнеса, оно обязательно и в БД.
*   **`PRIMARY KEY` / `UNIQUE`**: Гарантирует уникальность (email, slug, UUID). Это база.
*   **`FOREIGN KEY`**: Гарантирует, что связи между сущностями не превращаются в мусор.

#### Б. Ограничения доменных правил (Выборочно)
Это правила, которые можно проверить в коде, но которые критичны для безопасности данных.
*   **`CHECK constraints`**: Для простых проверок диапазонов или форматов.
    *   *Пример:* `CHECK (price > 0)`, `CHECK (status IN ('pending', 'paid', 'cancelled'))`.
    *   **Когда использовать:** Когда нарушение этого правила означает катастрофическую ошибку в данных.
*   **`EXCLUDE constraints`**: Для предотвращения наложений (например, бронирование отеля на одни и те же даты).

#### В. Бизнес-валидация (В коде PHP)
Это сложные правила, которые требуют обращения к внешним сервисам, сложной математики или контекста.
*   *Пример:* «Пользователь может купить этот товар, только если он прошел верификацию и его кредитный рейтинг выше X».
*   **Почему здесь:** БД не может сходить в сторонний API или проверить сложную цепочку условий, зависящую от множества таблиц и внешних факторов.

---

### 3. Сводная таблица: Разделение ответственности

| Характеристика | Валидация в PHP (Domain/App) | Ограничения в PostgreSQL |
| :--- | :--- | :--- |
| **Цель** | Обратная связь пользователю, UX, сложные правила. | Гарантия того, что данные никогда не станут «битыми». |
| **Сложность** | Любая (API, сложные расчеты). | Только простые, атомарные проверки. |
| **Скорость** | Быстро (в памяти). | Быстро (на уровне движка БД). |
| **Ошибка** | Выбрасывает `Exception` для обработки в UI. | Выбрасывает `PDOException` (нужно ловить). |
| **Пример** | "Пароль должен содержать спецсимвол". | `UNIQUE (email)`, `CHECK (age >= 18)`. |

### Мой подход в работе:
Я проектирую систему так: **«Валидируй максимально рано (в коде), чтобы дать быстрый ответ пользователю, но защищайся максимально поздно (в БД), чтобы данные остались верными при любом сценарии».**

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

Когда запрос в PostgreSQL начинает тормозить, я не гадаю на кофейной гуще, а следую методологии: **«Измерить $\to$ Понять план $\to$ Найти причину $\to$ Исправить $\to$ Проверить»**.

Вот мой пошаговый процесс.

### 1. Сбор метрик и диагностика (Инструменты)

Первым делом мне нужно понять масштаб проблемы: это один «тяжелый» запрос или общая деградация всей базы?

*   **`EXPLAIN (ANALYZE, BUFFERS)`**: Это мой главный инструмент. Я не просто смотрю план (`EXPLAIN`), а выполняю запрос (`ANALYZE`), чтобы увидеть реальное время выполнения и то, сколько данных было прочитано из памяти (`BUFFERS`) и с диска.
*   **`pg_stat_statements`**: Если проблема плавающая и я не могу поймать её руками, я смотрю эту расширение. Оно хранит статистику по всем выполненным запросам: среднее время, количество вызовов, количество чтений с диска. Это помогает найти «самые дорогие» запросы в системе.
*   **`pg_stat_activity`**: Помогает увидеть, что происходит прямо сейчас: завис ли запрос в состоянии `Lock` (ожидание блокировки) или он потребляет слишком много CPU.
*   **Внешние инструменты**: Если инфраструктура позволяет, использую **New Relic** или **Sentry** для отслеживания медленных запросов в контексте работы приложения.

---

### 2. На что я смотю в `EXPLAIN ANALYZE`?

Я ищу аномалии в плане выполнения:

1.  **Seq Scan (Sequential Scan)**: Вместо использования индекса база читает всю таблицу целиком. Это главная причина тормозов на больших таблицах.
2.  **Index Scan vs Index Only Scan**: Если я вижу `Index Scan`, значит, базе приходится лезть в саму таблицу (Heap), чтобы забрать данные. Если `Index Only Scan` — данные взяты прямо из индекса, это максимально быстро.
3.  **Cost vs Actual Time**: Если планировщик ожидает, что вернется 10 строк (`rows=10`), а на деле возвращается 1 000 000 — значит, статистика базы устарела, и план выбран неверно.
4.  **Hash Join / Nested Loop**: Я смотрю, как соединяются таблицы. Если при большом количестве строк я вижу `Nested Loop`, это часто признак отсутствия подходящего индекса.
5.  **External Merge (Disk Sort)**: Если в плане вижу `Sort Method: external merge Disk`, значит, памяти (work_mem) не хватило для сортировки, и она пошла на медленный диск.

---

### 3. Типовые причины и способы решения

#### Проблема №1: Отсутствие или неэффективный индекс
*   **Симптом:** `Seq Scan` на большой таблице.
*   **Решение:** Создать индекс. Если фильтрация идет по части значения или по функции (например, `WHERE LOWER(email) = ...`), обычный индекс не поможет.
*   **Решение 2:** Создать **Partial Index** (индекс по части таблицы, например `WHERE status = 'active'`) или **Expression Index** (`CREATE INDEX ... ON table (LOWER(email))`).

#### Проблема №2: Устаревшая статистика
*   **Симптом:** Планировщик делает неверный выбор (например, выбирает `Nested Loop` там, где нужен `Hash Join`), потомуs что думает, что в таблице 10 строк, а их миллион.
*   **Решение:** Запустить `ANALYZE` для этой таблицы, чтобы обновить статистику.

#### Проблема №3: Избыточное чтение данных (Over-fetching)
*   **Симптом:** Высокий `Buffers: shared read` (много чтений с диска).
*   **Причина:** `SELECT *` вместо выбора конкретных колонок или слишком много `JOIN`.
*   **Решение:** Оптимизировать запрос, выбирая только нужные поля, или использовать `Covering Index` (индекс, содержащий все необходимые поля, чтобы избежать обращения к таблице).

#### Проблема №4: Блокировки (Locks/Contention)
*   **Симптом:** Запрос висит в `pg_stat_activity` в состоянии `WaitEvent: Lock`.
*   **Причина:** Другой процесс держит транзакцию и обновляет ту же строку или таблицу.
*   **Решение:** Оптимизировать длительность транзакций в коде приложения, избегать `SELECT ... FOR UPDATE` там, где это не критично.

#### Проблема №5: Нехватка ресурсов (Memory/Disk)
*   **Симптом:** `Sort Method: external merge Disk`.
*   **Решение:** Увеличить `work_mem` для конкретной сессии или на уровне сервера, чтобы сортировка происходила в оперативной памяти.

---

### Мой алгоритм действий (Summary)

1.  **Запускаю `EXPLAIN (ANALYZE, BUFFERS)`**.
2.  **Ищу `Seq Scan`** $\to$ создаю индекс (возможно, функциональный или частичный).
3.  **Ищу несовпадение ожидаемых и реальных строк** $\to$ делаю `ANALYZE`.
4.  **Ищу `Disk Sort`** $\to$ увеличиваю `work_mem`.
5.  **Ищу `JOIN` на огромных объемах** $\to$ пересматриваю структуру запроса или добавляю покрывающие индексы.
6.  **Проверяю код приложения** $\to$ убираю лишние `SELECT *` и лишние циклы запросов (N+1).

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

**Агрегат (Aggregate)** в Domain-Driven Design — это кластер связанных объектов, которые рассматриваются как единое целое для изменения данных. 

Главная цель агрегата — **поддержание инвариантов** (бизнес-правил, которые всегда должны быть истинными). Вместо того чтобы позволить любому сервису менять любую часть системы, мы разрешаем изменения только через **Корень Агрегата (Aggregate Root)**.

### Как я определяю границы агрегата?

Я не рисую границы вокруг «сущностей», я рисущу их вокруг **правил**. Мой алгоритм:

1.  **Найти инварианты:** Какие правила должны соблюдаться одновременно? Если изменение объекта А требует немедленного изменения объекта Б, чтобы система осталась в валидном состоянии — они должны быть в одном агрегате.
2.  **Определить транзакционную границу:** Агрегат — это единица атомарности. В одной транзакции мы должны иметь возможность гарантировать выполнение всех правил внутри этого агрегата.
3.  **Оценить частоту изменений:** Если два объекта часто меняются вместе — это один агрегат. Если они меняются независимо — это разные агрегаты.
4.  **Связь через ID, а не через объект:** Объекты внутри агрегата связаны ссылками на объекты, а объекты *между* разными агрегатами связаны только через их `Identity` (ID).

---

### Пример: Система онлайн-заказов

#### Правильный подход (Разделение на агрегаты)

У нас есть два агрегата: **Order (Заказ)** и **Product (Товар)**.

*   **Агрегат Order:**
    *   *Корень:* `Order`.
    *   *Вложенные элементы:* `OrderItem` (позиция заказа).
    *   *Инвариант:* «Общая сумма заказа должна соответствовать сумме цен всех позиций» и «Заказ не может быть изменен, если он переведен в статус `Shipped`».
    *   *Связь:* `OrderItem` не может существовать без `Order`. Мы меняем состав заказа только через `Order::addItem()`.

*   **Агрегат Product:**
    *   *Корень:* `Product`.
    *   *Инвариант:* «Цена товара не может быть отрицательной» и «Количество остатков на складе не может быть меньше нуля».
    *   *Связь:* `Order` не содержит объект `Product` целиком. Он хранит `productId`.

**Почему это хорошо?** Когда мы меняем цену товара, нам не нужно пересчитывать все заказы в системе (это было бы невозможно). Мы просто меняем цену в `Product`. Если нам нужно применить скидку к заказу, мы делаем это в рамках транзакции `Order`.

---

### Типовая ошибка: "Слишком большой агрегат" (Big Aggregate)

Это самая частая ошибка — попытка объединить всё, что хоть как-то связано, в один огромный граф объектов.

**Пример ошибки:** Попытка сделать `Customer` (Клиент) корнем агрегата, который включает в себя все его `Order` (Заказы), а заказы включают в себя все `OrderItem` (Позиции).

**Почему это плохо (последствия):**
1.  **Конфликты блокировок (Concurrency):** Если клиент делает новый заказ, система блокирует объект `Customer`. В это же время, если менеджер пытается обновить адрес доставки в старом заказе этого же клиента, он получит ошибку или будет ждать. Два разных бизнес-процесса мешают друг другу.
2.  **Производительность:** Чтобы просто проверить статус клиента, Doctrine придется подгружать (или даже затронуть) огромную историю его заказов.
3.  **Нарушение SRP:** Агрегат становится слишком сложным, его инварианты размываются, и он превращается в "Божественный объект".

**Как исправить:** Нужно разбить его. `Customer` — это один агрегат. `Order` — другой. Связь между ними — только через `customerId`.

---

### Резюме: Золотые правила границ
*   **Маленькие агрегаты лучше больших.** (Small aggregates lead to better scalability and concurrency).
*   **Внутри агрегата:** Полная согласованность (Strong Consistency) через транзакцию.
*   **Между агрегатами:** Согласованность в конечном счете (Eventual Consistency) через события (Domain Events).

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

Если два процесса одновременно пытаются изменить один и тот тот же агрегат, возникает ситуация **состояния гонки (Race Condition)**. 

В классической реляционной БД (PostgreSQL) и ORM (Doctrine) результат зависит от уровня изоляции транзакций, но без специальной защиты произойдет одно из двух:
1.  **Lost Update (Потерянное обновление):** Процесс А прочитал данные, Процесс Б прочитал те же данные, Процесс А сохранил изменения, а затем Процесс Б сохранил свои. Изменения Процесса А будут просто стерты (перезаписаны) изменениями Процесса Б. Это катастрофа для целостности данных.
2.  **Deadlock (Взаимная блокировка):** Если оба процесса пытаются обновить одни и те же строки в разном порядке, база данных может обнаружить взаимную блокировку и принудительно завершить одну из транзакций.

---

### Как я проектирую систему с учетом этого?

Я использую три основных стратегии, выбирая подходящую в зависимости от бизнес-задачи.

#### 1. Optimistic Locking (Оптимистичная блокировка) — Мой стандарт
Это лучший выбор для большинства систем, где конфликты случаются редко. Мы предполагаем, что конфликтов не будет, но проверяем это в момент сохранения.

**Как это работает:**
В таблицу агрегата добавляется поле `version` (целое число). 
1. Процесс А читает объект (version = 1).
2. Процесс Б читает объект (version = 1).
3. Процесс А сохраняет изменения. SQL делает: `UPDATE table SET ..., version = 2 WHERE id = 1 AND version = 1`. Успех.
4. Процесс Б пытается сохранить. SQL делает: `UPDATE table SET ..., version = 2 WHERE id = 1 AND version = 1`. **Ничего не происходит (0 строк затронуто)**, потому что версия уже стала 2.
5. Doctrine выбрасывает `OptimisticLockException`.

**Плюсы:** Высокая производительность (нет реальных блокировок в БД), масштабируемость.
**Минусы:** При конфликте приложению нужно уметь обрабатывать ошибку (например, попросить пользователя обновить страницу или автоматически повторить попытку/retry).

#### 2. Pessimistic Locking (Пессимистичная блокировка) — Для критических операций
Используется, когда цена ошибки слишком высока или конфликты происходят постоянно (например, списание денег со счета в высоконагруженной системе).

**Как это работает:**
Мы используем SQL-команду `SELECT ... FOR UPDATE`.
1. Процесс А читает объект и база данных **блокирует** эту строку на уровне БД.
2. Процесс Б пытается прочитать тот же объект с `FOR UPDATE`, но база заставляет его **ждать**, пока Процесс А не завершит транзакцию (commit или rollback).

**Плюсы:** Гарантированная целостность, никакой потери данных.
**Минусы:** 
*   Сильно снижает пропускную способность системы (Concurrency $\to$ 0).
*   Риск возникновения Deadlocks.
*   Пользователи могут испытывать задержки (зависание запроса).

#### 3. Решение на уровне архитектуры (Idempotency & Eventual Consistency)
Если агрегат слишком "горячий" (его все пытаются менять одновременно), я стараюсь уйти от прямой модификации.

*   **Append-only (Immutable Logs):** Вместо изменения поля `balance` в таблице `accounts`, я записываю новые транзакции в таблицу `transactions`. Текущий баланс — это сумма всех записей. Это исключает конфликты обновления одной строки.
*   **Event Sourcing:** Состояние агрегата восстанавливается из последовательности событий. Конфликты решаются на этапе принятия решения о приеме нового события.

---

### Итоговый алгоритм выбора:

1.  **Конфликты редкие?** $\to$ **Optimistic Locking** (через `version` в Doctrine). Это мой выбор по умолчанию.
2.  **Конфликты частые и критичные (деньги)?** $\to$ **Pessimistic Locking** (`SELECT FOR UPDATE`) или переход на модель **Append-only**.
3.  **Нужна сверхвысокая нагрузка?** $\to$ **Event Sourcing** или декомпозиция агрегата на более мелкие части.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

Доменные события (Domain Events) — это способ сообщить остальной части системы, что «внутри агрегата что-то произошло». Это ключевой инструмент для реализации **слабой связанности (loose coupling)**.

### 1. Когда публиковать события?

Событие должно публиковаться **только тогда, когда агрегат перешел в новое валидное состояние**. 

**Правило:** Событие — это свершившийся факт в прошлом. Мы не публикуем «заказ будет создан», мы публикуем «заказ создан». 

**Важный нюанс:** Событие должно генерироваться **внутри** метода агрегата, но публиковаться (dispatch) **снаружи**, после успешного завершения транзакции. Если мы опубликуем событие внутри метода `order->pay()`, а транзакция потом упадет с ошибкой, мы отправим письмо о платеже, которого не было. Это ведет к рассинхрону данных.

---

### 2. Как обрабатывать события?

Я разделяю обработчики на два типа:

1.  **Синхронные (Internal):** Выполняются в той же транзакции, что и основной процесс. Используются для поддержания инвариантов внутри одного Bounded Context (например, обновление агрегата-проекции для поиска).
2.  **Асинхронные (External):** Выполняются через шину сообщений (Messenger + RabbitMQ/Redis). Используются для связи с другими микросервисами или для тяжелых задач (отправка Email, генерация PDF, синхронизация с ElasticSearch).

---

### 3. Связь событий с транзакциями (Transactional Outbox)

Это самая сложная техническая часть. Как гарантировать, что событие будет доставлено, если БД обновилась, а шина сообщений упала?

Существует два подхода:

#### А) Плохой подход: "Publish then Commit"
Мы сначала отправляем сообщение в RabbitMQ, а потом вызываем `$em->flush()`.
*   **Риск:** Если `flush()` упадет, сообщение уже улетело. Мы получили «фантомное» событие.

#### Б) Хороший подход: Transactional Outbox Pattern
Мы не отправляем сообщение в RabbitMQ напрямую. Вместо этого мы сохраняем событие в **таблицу `outbox` в той же самой БД**, в той же самой транзакции, что и основной агрегат.

1.  Начинаем транзакцию.
2.  Меняем `Order` (статус = `PAID`).
3.  Добавляем запись в таблицу `outbox` (событие `OrderPaid`).
4.  `COMMIT`. Теперь данные и событие гарантированно сохранены вместе.
5.  Отдельный процесс (Relay) читает таблицу `outbox` и перекладывает сообщения в RabbitMQ.

В Symfony это часто реализуется через интеграцию **Doctrine + Symfony Messenger**, где сообщения сохраняются в БД (транспорт `doctrine`) и обрабатываются воркером.

---

### 4. Проблемы и их решение

| Проблема | Описание | Как я с этим борюсь |
| :--- | :--- | :--- |
| **Дублирование событий** | Из-за ретраев воркера одно и то же событие может прийти дважды. | **Идемпотентность:** Обработчик должен уметь обрабатывать одно и то же событие много раз без побочных эффектов. |
| **Порядок событий** | Событие "Заказ доставлен" может прийти раньше, чем "Заказ создан". | Использование последовательных ID или временных меток (timestamps) и проектирование логики так, чтобы она не зависела от строгого порядка. |
| **Сложность отладки** | Трудно проследить цепочку: "Событие А $\to$ Handler $\to$ Событие Б". | **Distributed Tracing:** Использование `Correlation ID`, который пробрасывается через все события и логи, позволяя построить сквозной путь запроса. |

---

### Резюме (Summary)

**Зачем это нужно?**
*   **Decoupling:** `OrderService` не должен знать о существовании `EmailService`.
*   **Scalability:** Тяжелые задачи выносятся в фон.
*   **Extensibility:** Мы можем добавить новый функционал (например, отправку SMS), просто добавив новый слушатель, не меняя старый код.

**Мой принцип:** Агрегат порождает событие $\to$ Транзакция фиксирует агрегат и событие в БД $\to$ Воркер доставляет событие миру.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

Это фундаментальные вопросы, которые отделяют «просто программиста» от «проектировщика систем».

### 1. Entity vs Value Object

Главное различие — в том, **как мы определяем идентичность объекта**.

#### Entity (Сущность)
Сущность определяется своим **идентификатором (ID)**. Она обладает жизненным циклом: она создается, меняется, перемещается и в конце концов удаляется.
*   **Идентичность:** Даже если два пользователя имеют одинаковые имена и возраст, они — разные люди, потому что у них разные `user_id`.
*   **Изменяемость (Mutability):** Состояние сущности может меняться со временем, но она остается той же самой сущностью.
*   **Пример:** `User`, `Order`, `Product`.

#### Value Object (Объект-значение)
Value Object определяется своими **атрибутами (свойствами)**. У него нет ID. Если два объекта имеют одинаковые значения всех полей, они **равны**.
*   **Идентичность:** Если у нас есть два объекта `Money(100, 'USD')`, это один и тот же объект. Нам не важно, «какой именно» это стодолларовый билет, нам важна его ценность.
*   **Неизменяемость (Immutability):** Это критически важно. Вы не меняете свойства VO, вы создаете новый экземпляр с новыми значениями.
*   **Пример:** `Money`, `Address`, `Email`, `DateRange`.

**Краткая шпаргалка:**
*   Если у объекта есть `id` $\to$ **Entity**.
*   Если объект можно заменить другим с теми же данными без потери смысла $\to$ **Value Object**.

---

### 2. Как я принимаю решение (Процесс классификации)

Когда я проектирую новую модель, я задаю себе три вопроса:

1.  **«Нужен ли этому объекту жизненный цикл?»**
    Если объект просто описывает характеристику чего-то (например, цвет или координаты), это **Value Object**. Если объект будет эволюционировать (заказ переходит из `New` в `Paid`), это **Entity**.

2.  **«Важна ли мне история изменений этого объекта?»**
    Если мне важно знать, что этот конкретный объект изменился, мне нужен ID (**Entity**). Если мне важно только текущее состояние — это **Value Object**.

3.  **«Могу я заменить один экземпляр другим без последствий?»**
    Если я заменю один адрес на другой с такими же улицами и домом — ничего не изменится. Значит, это **Value Object**.

---

### 3. Единый язык (Ubiquitous Language)

**Ubiquitous Language** — это общая терминология, которую используют **разработчики** и **бизнес-эксперты** (Domain Experts) для описания предметной области. Это не просто «словарь», это живой язык, который пронизывает всё: от разговоров в Zoom до названий классов и методов в коде.

#### Как он влияет на код?

Если бизнес-эксперт говорит: *"Мы **аннулируем** заказ, если клиент **не подтвердил** оплату"*, то в коде я не должен писать `deleteOrder()` или `cancelOrder()`. Я должен написать `order->void()` или `order->cancel()`.

**Влияние проявляется в трех аспектах:**

1.  **Именование (Naming):**
    *   *Плохо:* `updateStatus(1)` (непонятно, что происходит).
    *   *Хорошо:* `shipOrder()` (сразу понятно, какое бизнес-событие произошло).
    *   Имена методов в коде должны быть точными терминами из бизнеса.

2.  **Структура (Modeling):**
    Если бизнес говорит, что «Скидка» — это не просто число, а сложная сущsть со сроком действия и условиями, я не создаю в `Order` поле `discount_amount: int`. Я создаю `Discount` как полноценный **Value Object** или **Entity**.

3.  **Снятие ментального барьера:**
    Когда разработчик и бизнес-эксперт смотрят на код (или на схему БД), они должны говорить на одном языке. Это минимизирует риск того, что программист реализует «технически правильную, но фактически неверную» фичу.

**Главный признак успеха:** Когда бизнес-эксперт смотрит на ваш метод `$order->applyDiscount($coupon)` и говорит: «Да, именно так это работает в реальности», — значит, вы успешно внедрили Ubiquitous Language.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

Применение Чистой Архитектуры (Clean Architecture) в PHP-приложении направлено на то, чтобы **бизнес-логика не зависела от фреймворка, базы данных или внешних API**.

Главное правило — **Dependency Rule (Правило зависимостей)**: зависимости направлены только внутрь, к центру (к бизнес-логике). Внутренние слои ничего не знают о внешних.

Вот как я структурирую типичное приложение:

---

### 1. Слои приложения

#### Layer 1: Domain (Ядро / Центр)
Это самый чистый слой. Здесь живет "сердце" системы.
* **Что внутри:** Entity (Агрегаты), Value Objects, Domain Exceptions, Domain Services (если логика не влезает в одну сущность), интерфейсы репозиториев.
* **Зависимости:** **Ноль**. Этот слой не зависит ни от чего. Он содержит только чистый PHP.

#### Layer 2: Application (Use Cases / Сценарии использования)
Этот слой координирует выполнение задач, реализуя конкретные сценарии использования приложения.
* **Что внутри:** Use Case классы (или Command Handlers), DTO (Data Transfer Objects), интерфейсы для внешних сервисов (например, `MailerInterface`).
* **Зависимости:** Только на слой **Domain**. Он не знает о БД или HTTP.

#### Layer 3: Infrastructure (Внешний мир / Реализация)
Здесь реализуются все технические детали.
* **Что внутри:** Реализации репозиториев (Doctrine), реализация отправки Email (Symfony Mailer), клиенты для внешних API, работа с очередями (Messenger).
* **Зависимости:** На слой **Application** (чтобы реализовать интерфейсы) и на слой **Domain** (чтобы маппить данные).

#### Layer 4: Presentation / UI (Точка входа)
Слой, через который пользователь взаимодействует с системой.
* **Что внутри:** Symfony Controllers, CLI Commands, API Resource classes.
* **Зависимости:** На слой **Application** (чтобы вызвать нужный сценарий).

---

### 2. Куда попадут компоненты?

| Компонент | Слой | Обоснование |
| :--- | :--- | :--- |
| **Doctrine ORM** | **Infrastructure** | Это инструмент хранения данных. Бизнес-логика не должна знать, что данные лежат в SQL. |
| **Symfony Controller** | **Presentation** | Это способ доставки запроса к приложению. Его можно заменить на консольную команду или RabbitMQ consumer, не меняя логику. |
| **Queue Handler** | **Presentation / Application** | Обработчик очереди — это такой же "вход" в систему, как и контроллер. Он вызывает `UseCase` из слоя Application. |

---

### 3. Визуализация потока данных (Request Flow)

1.  **HTTP Request** $\to$ **Controller** (Presentation).
2.  **Controller** $\to$ преобразует запрос в **DTO** $\to$ вызывает **UseCase** (Application).
3.  **UseCase** $\to$ загружает **Aggregate** через **Repository Interface** (Domain).
4.  **UseCase** $\to$ вызывает метод на **Aggregate** (Domain) $\to$ меняет состояние.
5.  **UseCase** $\to$ вызывает `Repository->save()` (Infrastructure реализует этот интерфейс).
6.  **UseCase** $\to$ возвращает результат в **Controller**.
7.  **Controller** $\to$ отдает **Response**.

### 4. Как следить за соблюдением границ?

Нарушение границ (например, когда контроллер делает запрос к БД напрямую) — это "архитектурный рак". Я использую три уровня защиты:

#### А) Статический анализ (Инструменты)
Это самый эффективный метод.
*   **PHPStan / Psalm:** Я настраиваю их на строгий режим.
*   **Deptrac:** Это специализированный инструмент для проверки архитектуры. Я пишу конфиг, где явно указываю: *"Слой Domain не может зависеть от слоя Infrastructure"*. Если кто-то добавит `use Doctrine\ORM\...` в класс из Domain, Deptrac выдаст ошибку при CI/CD.

#### Б) Code Review (Человеческий фактор)
При ревью я смотрю на импорты (`use` statements) в верхней части файла. Если в папке `Domain` я вижу импорт `Symfony\Component\...` или `Doctrine\...`, это автоматический Reject.

#### В) Тестирование
*   **Unit-тесты для Domain:** Они должны быть экстремально быстрыми, так как им не нужны БД или фреймворк. Если для теста доменного метода нужно поднять контейнер Symfony — значит, границы нарушены.
*   **Интеграционные тесты для Infrastructure:** Проверяют, что маппинг Doctrine работает правильно.

**Итог:** Чистая архитектура — это не про то, чтобы сделать "сложно", а про то, чтобы сделать **"заменяемо"**. Мы строим систему так, чтобы замена базы данных или фреймворка была лишь технической задачей, а не переписыванием всей бизнес-логики.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

Для Symfony-приложения я придерживаюсь классической **Пирамиды Тестирования**, но с поправкой на современную разработку (включая упор на интеграционные тесты для проверки правильности маппинга БД).

### 1. Уровни тестирования (Пирамида)

#### **Bottom: Unit Tests (Основание — 70-80%)**
*   **Что тестируем:** Чистую бизнес-логику. Value Objects, Domain Entities, Domain Services, простые Utility-классы.
*   **Что мокаем:** **Всё.** Здесь не должно быть ни БД, ни Symfony, ни файловой системы. Все зависимости передаются через интерфейсы и подменяются моками (PHPUnit Mock или Mockery).
*   **Цель:** Проверить краевые случаи (edge cases) логики мгновенно.

#### **Middle: Integration Tests (Середина — 15-20%)**
*   **Что тестируем:** Взаимодействие компонентов. Правильность работы репозиториев с БД, работу Middleware, интеграцию слоев.
*   **Что мокаем:** Внешние API (через `MockHttpClient`), сторонние сервисы (че way `MockObject`), но **НЕ** саму базу данных.
*   **Цель:** Убедиться, что SQL-запросы корректны, маппинг Doctrine работает, и интеграция слоев (Application $\to$ Domain) не сломана.

#### **Top: Functional/E2E Tests (Вершина — 5%)**
*   **Что тестируем:** Полный жизненный цикл запроса. От HTTP-запроса до ответа.
*   **Что мокаем:** Только самые тяжелые и нестабильные внешние системы (платежные шлюзы, SMS-сервисы).
*   **Инструмент:** `Symfony WebTestCase`.
*   **Цель:** Проверить, что вся "труба" (Routing $\to$ Controller $\to$ Service $\to$ DB) работает как единое целое.

---

### 2. Что мокать, а что нет? (Золотое правило)

Моканье — это палка о двух концах.

*   **МОКАЙ:**
    *   **Внешние API:** Чтобы не зависеть от интернета и сторонних сервисов.
    *   **Посылку сообщений (Messenger):** Чтобы не запускать реальных воркеров в Unit-тестах.
    *   **Случайные факторы:** Время (`ClockInterface`), генераторы случайных чисел.

*   **НЕ МОКАЙ:**
    *   **Свою бизнес-логику:** Если ты мокаешь `OrderService` внутри теста другого сервиса, ты тестируешь не систему, а свои предположения о том, как работает сервис. Это ведет к "зеленым тестам при сломанном коде".
    *   **Базу данных (в интеграционных тестах):** Тестировать репозиторий с моком репозитория — бессмысленно.

---

### 3. Как поддерживать тесты быстрыми и стабильными?

Медленные тесты — это тесты, которые разработчики перестают запускать.

#### **Для скорости:**
1.  **Использование SQLite в памяти (`:memory:`) для Unit/Integration:** Это очень быстро, но **опасно**, так как синтаксис SQLite отличается от PostgreSQL.
    *   *Мой выбор:* Использовать **реальный PostgreSQL в Docker**. Благодаря возможности быстрого поднятия контейнеров, это почти так же быстро, как SQLite, но на 100% надежно.
2.  **Очистка состояния (Database Isolation):**
    *   Использовать `DAMADoctrineTestBundle`. Он оборачивает каждый тест в транзакцию и делает `rollback` в конце. Это позволяет не пересоздавать схему базы перед каждым тестом, что экономит уйму времени.
3.  **Параллельный запуск:** Использование `Paratest` для запуска тестов в несколько потоков.

#### **Для стабильности (Flakiness prevention):**
1.  **Изоляция данных:** Каждый тест должен создавать свои данные. Никогда не полагайся на то, что в базе что-то уже лежит (используй `DataFixtures`).
2.  **Избегай Race Conditions в тестах:** Если тест зависит от времени, всегда внедряй `ClockInterface` (из PSR-20), чтобы ты мог "заморозить" время в тесте.
3.  **Чистота окружения:** Тесты должны запускаться в чистом Docker-контейнере, чтобы исключить влияние "мусора" на локальной машине разработчика.

### Итоговая стратегия:
Я строю систему так: **Unit-тесты** проверяют логику за миллисекунды, **Integration-тесты** с реальной PostgreSQL проверяют маппинг и SQL, а **WebTestCase** проверяет, что пользователь действительно сможет нажать кнопку и получить результат. При этом `DAMADDoctrineTestBundle` обеспечивает скорость за счет транзакционного отката.

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Это классическая проблема **конкурентного доступа (Concurrency Control)**. Когда два процесса читают одни и те же данные, изменяют их в памяти и пытаются записать обратно, возникает риск нарушения целостности данных.

### Основные проблемы

1.  **Lost Update (Потерянное обновление):** Самая частая проблема.
    *   *Сценарий:* Пользователь А и Б читают баланс $100. А вычитает $20, Б вычитает $30. Оба сохраняют результат. Если Б сохранит последним, баланс станет $70, а изменения пользователя А ($80) просто исчезнут.
2.  **Dirty Read (Грязное чтение):** Процесс А читает данные, которые изменил процесс Б, но процесс Б еще не зафиксировал (commit) транзакцию. Если Б сделает rollback, процесс А будет работать с "несуществующими" данными.
3.  **Non-repeatable Read (Неповторяющееся чтение):** В рамках одной транзакции процесс А читает строку, затем процесс Б меняет её и фиксирует. Процесс А читает ту же строку снова и видит уже другие данные.
4.  **Phantom Read (Фантомное чтение):** Процесс А читает набор строк по условию (например, `count(*) where status='new'`). Процесс Б добавляет новую строку. Процесс А делает повторный запрос и видит "фантомную" строку.

---

### Способы защиты

Я разделяю стратегии на две большие группы: **Оптимистичные** и **Пессимистичные**.

#### 1. Optimistic Locking (Оптимистичная блокировка)
Мы предполагаем, что конфликты редки. Мы не блокируем базу, а просто проверяем, не изменил ли кто-то запись, пока мы с ней работали.

*   **Как реализовать:** Добавить в таблицу колонку `version` (integer). При каждом `UPDATE` мы проверяем: `WHERE id = :id AND version = :old_version`.
*   **Механизм:** Если версия в БД уже изменилась, `UPDATE` затронет 0 строк. Doctrine выбросит `OptimisticLockException`.
*   **Когда выбирать:**
    *   Когда конфликты случаются редко.
    *   Когда транзакции "длинные" (например, пользователь открыл форму редактирования и ушел пить кофе). Пессимистичная блокировка в этом случае заблокировала бы базу на 10 минут.
    *   В высоконагруженных системах с большим количеством чтений.

#### 2. Pessimistic Locking (Пессимистичная блокировка)
Мы предполагаем, что конфликт неизбежен, и блокируем данные в самом начале.

*   **Как реализовать:** Использовать SQL-команду `SELECT ... FOR UPDATE`.
*   **Механизм:** Когда процесс А делает такой запрос, база данных вешает "замок" на эту строку. Процесс Б, попытавшись прочитать эту строку с таким же флагом, будет **ждать** (зависнет), пока Процесс А не сделает `COMMIT` или `ROLLBACK`.
*   **Когда выбирать:**
    *   В критических финансовых операциях (списание денег, резервирование билетов).
    *   Когда конфликт почти гарантирован (очень горячие данные).
    *   Когда цена ошибки выше, чем цена ожидания пользователя.

#### 3. Database-level Constraints (Атомарные операции)
Вместо "считать в PHP $\to$ записать в БД", мы переносим логику в сам SQL.

*   **Пример:** Вместо `UPDATE accounts SET balance = 80 WHERE id = 1` (вычисленный в PHP), мы делаем `UPDATE accounts SET balance = balance - 20 WHERE id = 1`.
*   **Когда выбирать:** Для простых арифметических операций или изменения статусов. Это самый быстрый и надежный способ, так как БД сама гарантирует атомарность на уровне одной инструкции.

---

### Сравнительная таблица

| Критерий | Optimistic Locking | Pessimistic Locking | Atomic SQL Update |
| :--- | :--- | :--- | :--- |
| **Производительность** | ⭐⭐⭐⭐⭐ (Высокая) | ⭐⭐ (Низкая) | ⭐⭐⭐⭐⭐ (Максимальная) |
| **Сложность кода** | Средняя (нужен retry) | Средняя (нужно управлять транзакцией) | Низкая |
| **Риск Deadlock** | Нет | **Высокий** | Низкий |
| **UX (User Experience)** | Пользователь может увидеть ошибку "Данные устарели" | Пользователь может увидеть "зависание" страницы | Прозрачно для пользователя |

### Мой выбор (Decision Matrix)

1.  **Нужно просто обновить профиль пользователя или описание товара?** $\to$ **Optimistic Locking**. Это стандарт для веб-приложений.
2.  **Нужно списать деньги со счета или забронировать последнее место в самолете?** $\to$ **Pessimistic Locking** (через `SELECT FOR UPDATE`) или **Atomic SQL**.
3.  **Нужно просто инкрементировать счетчик просмотров?** $\to$ **Atomic SQL** (`SET views = views + 1`).
4.  **Нужно обрабатывать очереди задач?** $\to$ **Optimistic Locking** (через состояние `version` или статус задачи).

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

Мой Git-процесс строится вокруг принципов **предсказуемости, атомарности и безопасности**. Я сторонник модели, близкой к **GitHub Flow**, но с четким разделением на стабилизацию и релизы, что критично для Enterprise-разработки.

Вот мой цикл:

### 1. Ветвление (Branching Model)

Я использую модель, где `main` — это всегда стабильный, готовый к продакшену код.

*   **`main`**: Стабильная ветка. Сюда попадают только протестированные и прошедшие ревью изменения.
*   **`feature/task-id-description`**: Ветки для новых задач. Короткоживущие.
*   **`bugfix/task-id-description`**: Ветки для исправления ошибок.
*   **`hotfix/description`**: Ветки для экстренных правок на продакшене.

**Почему так?** Это исключает ситуацию, когда "грязный" код из недоделанной фичи попадает в `main`. Каждая ветка изолирована.

---

### 2. Формат коммитов (Conventional Commats)

Я придерживаюсь стандарта **Conventional Commits**. Это делает историю понятной и позволяет автоматизировать версионирование.

**Формат:** `<type>(<scope>): <description>`
*   `feat`: Новая функциональность.
*   `fix`: Исправление ошибки.
*   `refactor`: Изменение кода без изменения логики.
*   `docs`: Изменения в документации.
*   `test`: Добавление или исправление тестов.
*   `chore`: Обновление зависимостей, конфигов (не касающихся кода).

**Пример:** `feat(order): add discount calculation to checkout process`

**Почему так?**
1.  **Читаемость:** По логу сразу понятно, что произошло.
2.  **Автоматизация:** Можно автоматически генерировать `CHANGELOG.md` и определять версию (SemVer) на основе типов коммитов.
3.  **Атомарность:** Один коммит = одна логическая операция. Это упрощает `cherry-pick` и `revert`.

---

### 3. Pull Request (PR) и Code Review

PR — это не просто "просьба влить код", это этап **контроля качества и обмена знаниями**.

**Мой процесс создания PR:**
1.  **Self-Review:** Перед тем как позвать коллег, я сам прохожу по своему Diff. Это помогает найти забытые `dd()`, лишние пробелы или закомментированный код.
2.  **Описание:** В PR я пишу: **Что** сделано, **Зачем** (ссылка на задачу), **Как** это протестировано.
3.  **Code Review:**
    *   Я смотю не только на "работает/не работает", но и на архитектурную чистоту (SOLID, паттерны).
    *   Смотрю на тесты: покрыли ли они новые сценарии?
    *   Если замечаю архитектурную ошибку — прошу рефакторинга. Если мелкую опечатку — пишу комментарий.

**Почему так?** Ревью распределяет ответственность. Команда знает о коде, который вошел в систему, и это предотвращает появление "Bus Factor" (когда только один человек знает, как работает модуль).

---

### 4. Релизы (Releases)

Я использую **Semantic Versioning (SemVer)**: `MAJOR.MINOR.PATCH`.

*   **Patch (1.0.1):** Исправление багов (backward compatible).
*   **Minor (1.1.0):** Новый функционал (backward compatible).
*   **Major (2.0.0):** Ломающие изменения (breaking changes).

**Процесс выкатки:**
1.  После того как все PR в `main` прошли проверку, создается **Release Tag**.
2.  Запускается CI/CD пайплайн.
3.  **Автоматизация:** CI запускает тесты, линтеры (PHPStan, PHP-CS-Fixer) и собирает артефакты.
4.  **Deployment:** Деплой происходит либо через Blue-Green, либо через Canary, чтобы минимизировать риск простоя при ошибке.

---

### Резюме: Почему этот процесс эффективен?

*   **Предсказуемость:** Благодаря Conventional Commits и SemVer мы знаем, что прилетит в следующем обновлении.
*   **Безопасность:** `main` всегда в порядке, а ошибки отлавливаются на этапе CI и Code Review до того, как попадут к пользователю.
*   **Масштабируемость:** Такой процесс позволяет работать команде из 5, 50 или 100 человек, не превращая репозиторий в хаос.

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

Для меня хороший Code Review — это не «полиция кода», а **инструмент обеспечения качества и обмена знаниями**. Если ревью превращается в поиск опечаток или спор о стиле, оно теряет свою ценность.

### 1. На что я смотрю в первую очередь (Приоритеты)

Я делю замечания на три уровня приоритетности, чтобы автор понимал серьезность проблемы.

**Уровень 1: Критические ошибки (Blockers)**
Это вещи, которые нельзя пропускать в `main`.
*   **Нарушение логики и бизнес-правил:** Ошибка в расчете скидки, неверное состояние заказа.
*   **Безопасность:** SQL-инъекции, отсутствие проверки прав доступа (Authorization), утечка чувствительных данных.

**Уровень 3: Стиль и мелочи (Nitpicks)**

*   **`[PRAISE]`** — Обязательно! Если я вижу изящное решение или хорошую архитектурную мысль, я это отмечаю. Это поддерживает позитивную атмосферу в команде.

### А) Нашёл «попутный» баг (не связанный с задачей)

**Почему?**
1.  **Размытие контекста (Scope Creep):** Если я исправлю баг в другом модуле внутри PR по моей задаче, я нарушу атомарность изменений. Если мой основной код окажется проблемным, откатить его будет невозможно, не откатив вместе с исправлением чужого бага.

3.  **Сложность тестирования:** Тесты моей задачи пройдут успешно, но я не смогу гарантировать, что исправленный баг не сломал другие части системы.

1.  **Зафиксировать баг:** Я создам отдельную задачу (Issue/Ticket) в бэклоге, максимально подробно описав шаги воспроизведения.
2.  **Оценить критичность:**
    *   Если это **Blocker** (например, дыра в безопасности или падение системы), я немедленно сообщу об этом лиду или менеджеру. Мы решим: либо бросать текущую задачу и чинить это, либо делать это отдельным быстрым патчем.

**Почему?**
Выполнение заведомо плохого ТЗ — это создание технического долга, который рано или поздно «взорвется». Моя роль как инженера — предупредить об этом на этапе проектирования, а не констатировать факт катастрофы после релиза.

**Мои действия:**
1.  **Не начинать реализацию:** Не стоит тратить время на написание кода, который всё равно придётся переделывать.
2.  **Собрать доказательства:** Я подготовлю аргументы. Если это производительность — я покажу план запроса (`EXPLAIN ANALYZE`) или замеры. Если это логика — я опишу сценарий, где это приведет к ошибке.

Хороший PR-отчёт состоит из четырех ключевых блоков:

#### **А) Summary (Что сделано)**
Краткое, человекочитаемое описание изменений. Не «добавил метод `getOrders`», а «реализовал возможность фильтрации заказов по дате, чтобы пользователи могли находить старые покупки».

Если мои изменения затронули что-то еще (например, увеличили размер таблицы или изменили формат ответа API), я обязан об этом заявить. Это дает сигнал команде быть внимательнее при деплое.

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

Важное уточнение: в PostgreSQL **нет прямой команды `FORCE INDEX`**, как в MySQL. Если вы попытаетесь написать `SELECT * FROM table FORCE INDEX (idx_name)`, вы получите синтаксическую ошибку.

В PostgreSQL управление выбором индекса реализовано иначе. Вместо явного принуждения, разработчики используют **настройку параметров планировщика** или **создание специфических индексов**.

Однако, суть вопроса подразумевает: «Как заставить базу использовать конкретный индекс, если она упорно этого не делает?».

### Почему планировщик может игнорировать индекс?

Прежде чем «заставлять» базу, нужно понять, почему она этого не делает. Основные причины:
1.  **Низкая селективность:** Планировщик считает, что данных, подходящих под условие, слишком много (например, более 20-30% всей таблицы), и ему дешевле просканировать всю таблицу целиком (`Seq Scan`), чем прыгать по дереву индекса и потом лезть в кучу страниц данных (Heap).
2.  **Устаревшая статистика:** Таблица изменилась, а `ANALYZE` еще не запускался. Планировщик думает, что в таблице 10 строк, а там миллион.
3.  **Неподходящий тип данных:** Вы сравниваете `integer` с `text` (неявное приведение типов), из-за чего индекс становится бесполезным.
4. way **Функции в условии:** `WHERE LOWER(email) = ...` не использует обычный индекс по `email`.

---

### Как «принудить» PostgreSQL использовать индекс?

Если вы уверены, что индекс будет работать быстрее, но планировщик ошибается, есть три пути:

#### 1. Настройка параметров сессии (Самый близкий аналог `FORCE INDEX`)
Вы можете временно «обмануть» планировщик, сказав ему, что сканирование таблицы — это очень дорого, а индекс — очень дешево.

```sql
-- Увеличиваем стоимость последовательного сканирования
SET seq_page_cost = 10.0; 
-- Уменьшаем стоимость чтения по индексу
SET index_page_cost = 0.1; 

-- Теперь планировщик с большой вероятностью выберет индекс
SELECT * FROM users WHERE email = 'test@example.com';

-- Возвращаем всё как было
RESET seq_page_cost;
RESET index_page_cost;
```
*Этот метод используется для отладки или в очень специфических процедурах, но его опасно использовать глобально.*

#### 2. Создание функциональных или частичных индексов (Правильный путь)
Вместо того чтобы заставлять базу использовать индекс, нужно сделать индекс, который **идеально подходит** под запрос.

*   **Функциональный индекс:** Если запрос использует функцию.
    `CREATE INDEX idx_users_lower_email ON users (LOWER(email));`
*   **Частичный индекс (Partial Index):** Если вы часто ищете только активных пользователей.
    `CREATE INDEX idx_active_users ON users (id) WHERE status = 'active';` (Это сделает индекс крошечным и сверхбыстрым).

#### 3. Использование CTE (Common Table Expressions) или подзапросов
Иногда можно «подсказать» планировщику, ограничив область поиска.
```sql
WITH filtered_ids AS (
    SELECT id FROM users WHERE status = 'active' -- Здесь сработает индекс
)
SELECT * FROM users WHERE id IN (SELECT id FROM filtered_ids);
```

---

### Резюме: когда и что применять?

| Ситуация | Что делать | Почему |
| :--- | :--- | :--- |
| **Планировщик ошибается из-за статистики** | Запустить `ANALYZE table_name` | Обновить данные для планировщика. |
| **Нужен поиск по функции (`LOWER`, `date_trunc`)** | Создать **Functional Index** | Индекс должен соответствовать выражению. |
| **Нужен поиск по подмножеству данных** | Создать **Partial Index** | Индекс будет меньше и быстрее. |
| **Нужно "протолкнуть" индекс в экстренном случае** | `SET seq_page_cost = ...` | Временная манипуляция стоимостью операций. |

**Мой профессиональный совет:** Если вам постоянно приходится использовать методы «принуждения», значит, у вас либо **проблема с дизайном индексов**, либо **проблема с устаревшей статистикой**. В 99% случаев правильный `CREATE INDEX` лучше, чем манипуляции с `cost` параметров.

## Q25 · Провокации

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

Если отвечать прямо: **влияние `strict_types=1` на производительность практически равно нулю (менее 1%).**

В современных версиях PHP (8.x) эта директива не является «накладным расходом» в привычном понимании. Она не заставляет интерпретатор делать дополнительные тяжелые проверки на каждом шагу.

Вот детальный разбор, почему это так и откуда берутся мифы о замедлении.

### 1. Почему это НЕ замедляет код?

**Внутренняя оптимизация (OpCache):**
Когда вы используете `strict_types=1`, PHP при компиляции в опкод (Opcode) заранее знает, какие типы ожидаются в функциях. В режиме `coerce` (по умолчанию) PHP вынужден при каждом вызове функции выполнять проверку: *«Так, мне прислали строку "5", а я жду int. Могу ли я безопасно превратить её в число?»*. Это требует операций сравнения и приведения типов.

В режиме `strict` PHP просто проверяет: *«Тип совпадает? Да. Идем дальше»*. Это максимально дешевая операция на уровне процессора.

**На самом деле, `strict_types` может даже немного УСКОРИТЬ код:**
Поскольку PHP не нужно тратить циклы процессора на проверку правил приведения типов (например, превращение `float` в `int` или `string` в `int`), выполнение некоторых участков кода может стать чуть более прямолинейным.

---

### 2. Откуда взялся миф о замедлении?

Замедление может наблюдаться только в одном специфическом сценарии: **массовое несоответствие типов в высоконагруженных циклах**.

Если ваш код написан в стиле «все типы — это строки», а вы внезапно включили `strict_types`, PHP начнет выбрасывать `TypeError` на каждой итерации. Но это не «замедление выполнения», это **остановка программы из-за ошибки**.

Иногда разработчики путают производительность с **издержками на обработку исключений**. Если ваш код спроектирован так, что из-за нестрогих типов он постоянно «проскакивает» ошибки, которые вы подавляете через `try-catch`, то включение `strict_types` заставит вас исправить архитектуру, и вы увидите разницу в скорости. Но это разница между «работой с ошибками» и «правильной работой».

---

### 3. Реальные факторы, влияющие на скорость (что важнее)

Если вы беспокоитесь о микросекундах, то `strict_types` — это последнее, о чем стоит думать. Гораздо больше на производительность влияют:

1.  **Аллокация памяти:** Создание тысяч объектов в цикле.
2.  **I/O операции:** Запросы к БД, обращения к файловой системе или API.
3.  **Сложность алгоритмов:** $O(n^2)$ против $O(n \log n)$.
4.  **Работа с OpCache:** Насколько эффективно код закэширован.

### Мой вердикт

Я использую `declare(strict_types=1);` в **100% своих проектов**. 

**Причина не в скорости, а в надежности.** Выигрыш в безопасности (предотвращение багов, связанных с неявным приведением типов) несопоставим с ничтожным (если он вообще есть) влиянием на производительность. В современной разработке мы оптимизируем алгоритмы и запросы к БД, а не экономим на проверке типов.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

Это один из самых обсуждаемых вопросов в сообществе Doctrine. Важно сразу прояснить технический нюанс: **Doctrine поддерживает составные первичные ключи (Composite Primary Keys), но делает это крайне ограниченно и с большими неудобствами.**

На самом деле, документация говорит, что это возможно, но на практике вы столкнетесь с тем, что многие функции (например, работа с `OneToMany` связями или некоторые методы `UnitOfWork`) работают некорректно или требуют костылей.

### Почему это «не поддерживается» (Проблема архитектуры)

Проблема не в том, что разработчики Doctrine «не смогли», а в самой философии **Data Mapper** и реализации **Identity Map**.

1.  **Identity Map (Карта идентичности):** Внутри `EntityManager` есть массив, где ключом является уникальный идентификатор сущности. Если у сущности нет одного уникального `id`, а есть набор полей, Doctrine должно храть ключ как массив или строку. Это усложняет внутреннюю логику сравнения объектов и управления их состоянием.
2.  **Сложность связей (Associations):** В реляционных БД связь `ManyToOne` указывает на первичный ключ целевой таблицы. Если у целевой таблицы составной ключ, то в дочерней таблице вам нужно храть **несколько колонок** для внешней связи. Это делает маппинг связей в Doctrine невероятно громоздким и хрупким.
3.  **Смена парадигмы:** Doctrine создавалась с расчетом на то, что каждая сущность — это независимый объект со своим уникальным `surrogate key` (суррогатным ключом, например, `id`).

---

### Как с этим живут в реальных проектах?

Когда бизнес-логика требует составного ключа (например, в таблицах связей many-to-many или в legacy-базах), разработчики используют три стратегии:

#### 1. Введение суррогатного ключа (Лучший способ)
Это самый надежный и рекомендуемый способ. Даже если в базе данных логически ключом является пара `(order_id, product_id)`, мы добавляем в таблицу колонку `id` (автоинкремент или UUID).

*   **Как это выглядит:** Мы сохраняем составной ключ как обычные колонки (`order_id`, `product_id`), но для Doctrine первичным ключом является наш новый `id`.
*   **Плюсы:** Полная поддержка всех фич Doctrine, простота связей, отсутствие проблем с UnitOfWork.
*   **Минусы:** Небольшое дублирование данных (наличие и `id`, и составного набора колонок).

#### 2. Использование Embeddables (Для Value Objects)
Если составной ключ — это просто группа атрибутов, описывающих сущность (например, `CompositeId` из `street` и `house_number`), мы оформляем его как `Embeddable`.

*   **Как это выглядит:** Мы создаем класс `CompositeId` и используем его как поле в основной сущности.
*   **Плюсы:** Чистый код, соблюдение DDD.
*   **Минусы:** Это не делает набор полей первичным ключом на уровне БД в полной мере (нужно вручную вешать `UniqueConstraint`), и это все равно не решает проблему, если этот ключ должен быть внешним (FK) для других таблиц.

#### 3. Принятие боли (Mapping Composite Keys)
Если вы работаете с Legacy-базой, которую **нельзя менять** (нельзя добавить `id`), вы вынуждены настраивать маппинг через несколько `@Id` полей.

*   **Как это выглядит:**
    ```php
    #[ORM\Id, ORM\Column]
    private int $orderId;

    #[ORM\Id, ORM\Column]
    private int $productId;
    ```
*   **Плюсы:** Не нужно менять структуру БД.
*   **Минусы:** Вы становитесь «заложником» Doctrine. Вы не сможете использовать некоторые стандартные методы, у вас будут проблемы с `ManyToMany`, и вы постоянно будете натыкаться на ошибки при попытке связать эту сущность с другими.

---

### Мой вердикт

В 99% случаев в новых проектах я выбираю **первый вариант: добавление суррогатного ключа (`id`)**. 

Это может показаться нарушением нормализации БД, но в мире ORM **удобство управления жизненным циклом объекта и предсказуемость работы UnitOfWork важнее, чем идеальная нормализация таблиц**. Если вам нужно соблюдать уникальность пары полей, вы просто вешаете `#[UniqueConstraint]` на эти две колонки. Это дает вам и чистоту кода, и целостность данных на уровне БД.

## Q27 · Мини-код-ревью

**Интервьюер:** Посмотри на этот код:

```php
class OrderController
{
    public function pay(Request $req): Response
    {
        $id = $req->get('order_id');
        $pdo = DB::connect();
        $order = $pdo->query("SELECT * FROM orders WHERE id = $id")->fetch();
        if (!$order) {
            return new Response('not found', 404);
        }
        $order['status'] = 'paid';
        $pdo->exec("UPDATE orders SET status = 'paid' WHERE id = $id");
        Mailer::send($order['email'], 'Ваш заказ оплачен');
        (new Logger())->log('paid ' . $id);
        return new Response('ok');
    }
}
```

Какие проблемы ты видишь и как бы ты этот код переделал? С чего начал бы и почему?

**Кандидат:**

Этот код — классический пример «антипаттерна», который в реальной среде приведет к взлому системы, потере данных и невозможности её тестирования.

### Анализ проблем

Я бы разделил их на три уровня:

#### 1. Критические (Безопасность и целостность)
*   **SQL Injection:** Переменная `$id` вставляется напрямую в строку запроса. Злоумышленник может передать `1; DROP TABLE users;`, и база будет уничтожена.
*   **Race Condition (Состояние гонки):** Между `SELECT` и `UPDATE` проходит время. Если два процесса одновременно вызовут `pay`, оба могут пройти проверку, и мы получим двойное списание или некорректные действия (хотя здесь статус просто перезаписывается, в логике списания денег это будет катастрофой).
*   **Отсутствие транзакционности:** Если `UPDATE` прошел успешно, а `Mailer::send` упал с ошибкой, заказ останется в статусе `paid`, но пользователь не получит подтверждения. Система окажется в несогласованном состоянии.

#### 2. Архитектурные (Чистота кода)
*   **Нарушение SRP (Single Responsibility Principle):** Контроллер делает всё: парсит запрос, работает с БД, отправляет почту, логирует. Он знает слишком много о деталях реализации.
*   **Нарушение слоев:** Бизнес-логика (смена статуса) перемешана с транспортным уровнем (HTTP). Мы не сможем вызвать оплату из консольной команды или очереди, не имитируя `Request`.
*   **Жесткая зависимость (Tight Coupling):** Использование статических методов `DB::connect()`, `Mailer::send()` и `new Logger()` делает код невозможно протестировать через Unit-тесты (нельзя подменить их моками).

#### 3. Качество кода
*   **Слабая типизация:** Нет типов аргументов и возвращаемых значений.
*   **Массив вместо объекта:** Работа с `$order['email']` — это риск опечатки. Лучше использовать объект `Order`.

---

### Как бы я это переделал?

Я бы начал **не с переписывания кода, а с проектирования слоев**. Я бы разделил эту задачу на:
1.  **Domain Layer:** Сущность `Order` с методом `pay()`.
2.  **Application Layer:** `PayOrderUseCase` (или Command Handler), который оркеструет процесс.
3.  **Infrastructure Layer:** Репозиторий для БД, Mailer для почты и Logger для логов.

#### Рефакторинг (Целевой вид)

**1. Доменная сущность (Domain):**
```php
class Order {
    private int $id;
    private string $status;
    private string $email;

    public function pay(): void {
        if ($this->status === 'paid') {
            throw new OrderAlreadyPaidException();
        }
        $this->status = 'paid';
    }
    // геттеры...
}
```

**2. Прикладной сервис (Application):**
```php
class PayOrderUseCase {
    public function __construct(
        private OrderRepositoryInterface $repository,
        private MailerInterface $mailer,
        private LoggerInterface $logger
    ) {}

    public function execute(int $orderId): void {
        // Используем транзакцию для атомарности
        $this->repository->transactional(function() use ($orderId) {
            $order = $this->repository->findById($orderId);
            if (!$order) {
                throw new OrderNotFoundException();
            }

            $order->pay();
            $this->repository->save($order);

            // Событие для внешних систем
            $this->mailer->send($order->getEmail(), 'Ваш заказ оплачен');
            $this->logger->info("Order paid: " . $order->getId());
        });
    }
}
```

**3. Контроллер (Presentation):**
```php
class OrderController extends AbstractController {
    public function __construct(private PayOrderUseCase $useCase) {}

    public function pay(Request $req): Response {
        try {
            $id = (int) $req->get('order_id');
            $this->useCase->execute($id);
            return new Response('ok');
        } catch (OrderNotFoundException $e) {
            return new Response('not found', 404);
        } catch (\Exception $e) {
            return new Response('error', 500);
        }
    }
}
```

### Почему именно так?

1.  **Безопасность:** SQL-инъекции исключены (используем prepared statements в репозитории).
2.  **Атомарность:** Благодаря `transactional()`, если почта не отправится, статус заказа не изменится в базе.
3.  **Тестируемость:** Я могу написать Unit-тест на `PayOrderUseCase`, подсунув ему моки репозитория и почты, и не подключаться к реальной БД.
4.  **Масштабируемость:** Если завтра мы захотим отправлять почту через очередь (Messenger), я просто заменю реализацию `MailerInterface` в DI-контейнере, не меняя ни одной строчки в `PayOrderUseCase`.

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Эта сущность нарушает практически все фундаментальные принципы чистой архитектуры и DDD. Она превращает доменную модель в «толстый» объект, который слишком много знает о внешнем мире.

### Что не так?

**1. Нарушение Dependency Rule (Зависимость от инфраструктуры)**
Это самая грубая ошибка. Сущность (`User`) зависит от `EntityManagerInterface` (инфраструктурный слой Doctrine). Доменная сущность должна быть «чистой» — она должна состоять только из бизнес-логики и не знать о том, как, где или когда она будет сохранена в базу данных.

**2. Нарушение Single Responsibility Principle (SRP)**
Сущность отвечает за две разные вещи:
*   Хранение состояния пользователя (бизнес-логика).
*   Управление жизненным циклом сохранения (инфраструктурная логика).

**3. Нарушение инкапсуляции и чистоты транзакций**
Вызов `$this->em->flush()` внутри метода `changeEmail` — это катастрофа. 
*   **Непредсказуемость:** Вызов метода сущности внезапно инициирует запись в базу. Это делает поведение объекта неявным.
*   **Проблема транзакций:** Если внутри `changeEmail` произойдет еще что-то (например, вы захотите обновить профиль и сменить email в одном бизнес-процессе), вы не сможете объединить это в одну атомарную транзакцию, так как `flush()` сработает преждевременно.

**4. Нарушение концепции Identity Map**
Сущность сама управляет своим сохранением. В DDD за это отвечает Репозиторий, а за координацию процесса — Application Service.

---

### Как бы я это исправил?

Нужно разделить **состояние** (Domain) и **действие по сохранению** (Infrastructure/Application).

#### 1. Чистая доменная сущность (Domain Layer)
Она теперь максимально простая, не знает о базе и просто меняет свое внутреннее состояние.

```php
// src/Domain/Entity/User.php

#[ORM\Entity]
class User
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(unique: true)]
    private string $email;

    public function __construct(string $email)
    {
        // Здесь можно добавить валидацию email
        $this->email = $email;
    }

    public function changeEmail(string $newEmail): void
    {
        // Бизнес-логика: например, проверка на валидность или запрет на смену
        if ($this->email === $newEmail) {
            return;
        }
        
        $this->email = $newEmail;
    }

    public function getEmail(): string
    {
        return $this->email;
    }
    
    public function getId(): ?int
    {
        return $this->id;
    }
}
```

#### 2. Прикладной сервис (Application Layer)
Он оркеструет процесс: достает сущность, вызывает её метод и просит репозиторий сохранить результат.

```php
// src/Application/UseCase/ChangeUserEmailUseCase.php

class ChangeUserEmailUseCase
{
    public function __construct(
        private UserRepositoryInterface $userRepository,
        private EntityManagerInterface $entityManager // Для управления транзакцией
    ) {}

    public function execute(int $userId, string $newEmail): void
    {
        // 1. Находим пользователя
        $user = $this->userRepository->findById($userId);
        
        if (!$user) {
            throw new UserNotFoundException();
        }

        // 2. Выполняем бизнес-действие
        $user->changeEmail($newEmail);

        // 3. Сохраняем изменения (Unit of Work)
        // Здесь flush() вызывается один раз на всю операцию
        $this->entityManager->flush();
    }
}
```

### Итог изменений:
1.  **Тестируемость:** Теперь я могу написать Unit-тест на `User::changeEmail`, не создавая подключение к базе и не подменяя `EntityManager`.
2.  **Предсказуемость:** Метод `changeEmail` больше не делает "магических" запросов в БД. Он просто меняет данные в памяти.
3.  **Чистота:** Доменная модель полностью изолирована от фреймворка и инфраструктуры. Мы можем заменить Doctrine на что угодно, не меняя ни строчки в `User.php`.

## Q29 · Процесс и рассуждение

**Интервьюер:** Тебе нужно решить техническую проблему на незнакомых тебе технологии или стеке. Опиши последовательность своих действий от первого взгляда на задачу до уверенного ответа о сроках решения. Когда, по-твоему, нужно просить помощи у команды, а когда разбираться самому?

**Кандидат:**

Это ситуация, с которой сталкивается любой Senior-разработчик. Мой подход базируется на принципе **минимизации неопределенности** и **эффективного управления временем компании**.

Вот мой алгоритм действий:

### 1. Фаза исследования (Discovery) — «Понять, что я не знаю»
Прежде чем заявлять о сроках, я должен провести «разведку боем».

1.  **Изучение контекста (Reading the Docs):** Я начинаю с официальной документации и архитектурных схем. Моя цель — понять ментальную модель технологии (как она мыслит, как управляет состоянием, как работает жизненный цикл объектов).
2.  **Анализ существующего кода (Code Archeology):** Я смотрю, как эта технология уже используется в текущем проекте. Это лучший способ понять «местный» стандарт и избежать конфликтов с архитектурой.
3.  **Создание изолированного Proof of Concept (PoC):** Я создаю крошечный, максимально упрощенный проект (sandbox), где пытаюсь воспроизвести проблему или реализовать базовый функционал. Это позволяет проверить гипотезы, не рискуя основным кодом.
4.  **Поиск паттернов (StackOverflow, GitHub Issues, Reddit):** Я ищу, сталкивался ли кто-то с похожей проблемой. Я ищу не просто «код-костыль», а объяснение причин ошибки.

### 2. Фаза оценки (Estimation)
Только после того, как я «потрогал» технологию руками в PoC, я перехожу к оценке.

1.  **Декомпозиция:** Я разбиваю задачу на мелкие подзадачи (например: «настроить конфиг», «реализовать базовый маппинг», «написать тесты»).
2.  **Оценка рисков:** Я задаю себе вопрос: «Где здесь самое тонкое место?». Если я не понимаю, как работает интеграция с внешней системой, я закладываю буфер на исследование этой части.
3.  **Формулирование срока:** Я даю не одну цифру, а **диапазон (Range)** с пояснением. 
    *   *Плохо:* «Сделаю за 2 дня».
    *   *Хорошо:* «Если проблема в конфигурации, сделаю за 4 часа. Если проблема в архитектуре интеграции, потребуется 2 дня. Я дам точный прогноз после этапа прототипирования».

---

### 3. Когда разбираться самому, а когда просить помощи?

Это вопрос баланса между моей самодостаточностью и стоимостью времени команды.

#### **Разбираться самому (Deep Dive), если:**
*   Я нахожусь в фазе **исследования (PoC)**. Это мое время, я учусь.
*   Проблема локальна и я вижу путь решения, но мне не хватает знаний синтаксиса или конкретного API.
*   Я застрял, но у меня есть четкий план действий, и мне просто нужно время на «прогрев» мозга.
*   *Правило:* Я выделяю на самостоятельный поиск фиксированное время (**Time-box**). Например, «Я буду копать это сам 2 часа. Если не сдвинусь — иду к команде».

#### **Просить помощи (Escalation), если:**
*   **Я уперся в стену (The Wall):** Я потратил выделенное время (Time-box), перерыл документацию и StackOverflow, но всё еще не понимаю фундаментальную причину проблемы.
*   **Риск для проекта:** Я вижу, что решение задачи может потребовать масштабного рефакторинга, который затронет другие команды. Это архитектурное решение, которое я не имею права принимать в одиночку.
*   **Неопределенность требований:** Я понимаю, *как* реализовать, но не понимаю *что* именно нужно бизнесу.
*   **Проблема в инфраструктуре/окружении:** Если баг не в коде, а в конфигурации CI/CD или настройках сервера, которые я не контролирую.

**Мой подход к просьбе о помощи:**
Я никогда не прихожу с вопросом «Почему это не работает?». Я прихожу с форматом:
> *"Я решаю задачу X. Попробовал подходы А и Б, вот что изучил, вот что получил в итоге (ошибка/результат). Я застрял на этапе Y. Есть ли у тебя идеи или ты можешь подсказать, в какую сторону копать?"*

Это показывает, что я проделал работу, ценю время коллеги и пришел не за готовым ответом, а за **направлением**.

## Q30 · Процесс и рассуждение

**Интервьюер:** Ты пообещал сделать задачу к завтрашнему дню, но по ходу работы понял, что это два дня работы. Что делаешь?

**Кандидат:**

Это критическая ситуация, которая проверяет профессиональную честность и умение управлять ожиданиями (Stakeholder Management). Самая большая ошибка здесь — продолжать молчать, надеясь «героически» доделать задачу ночью, и в итоге в очередной раз сорвать дедлайн.

Мой алгоритм действий:

### 1. Немедленная коммуникация (Fail Fast)
Как только я осознал, что срок нереалистичен, я **немедленно** сообщаю об этом. Чем раньше я скажу, тем больше у команды будет пространства для маневра (перестроить план спринта, перераспределить задачи).

**Принцип:** Плохие новости должны доставляться как можно раньше.

### 2. Анализ и подготовка аргументации
Я не прихожу с фразой «я не успеваю». Я прихожу с **фактами и вариантами решения**. Перед разговором я должен четко понимать:
*   **Почему возникла задержка?** (Обнаружена скрытая сложность, изменились требования, возникла техническая проблема с архитектурой). Это не оправдание, а контекст.
*   **Что уже сделано?** (Показать прогресс, чтобы было видно, что я не бездельничал).
*   **Что именно занимает время?** (Разбить оставшуюся работу на части).

### 3. Предложение вариантов (Trade-offs)
Я не просто переношу дедлайн, я предлагаю варианты решения проблемы. У бизнеса всегда есть выбор между **временем, объемом и качеством**.

**Вариант А: Сдвиг срока (Scope stays, Time increases)**
*   *«Я понял, что задача требует больше времени из-за сложности интеграции с API. Мне нужно еще один день. Это позволит сделать всё качественно и с тестами».*
*   **Когда:** Когда задача критически важна и её нельзя упрощать.

**Вариант Б: Сокращение объема (Scope decreases, Time stays)**
*   *«Я не успею сделать всё к завтра, но я могу выкатить базовый функционал (MVP) завтра, а второстепенные фичи (например, логирование или расширенные фильтры) доделать послезавтра».*
*   **Когда:** Когда есть жесткий дедлайн (например, релиз или презентация клиенту) и нам нужно «что-то работающее» прямо сейчас.

**Вариант В: Помощь команды (Resources increase)**
*   *«Задача оказалась сложнее из- чем ожидалось. Если мы подключим еще одного разработчика на вторую половину дня, мы успеем к завтрашнему дню».*
*   **Когда:** Если задача критична и ресурсы команды позволяют.

---

### Пример того, как я это скажу (в Slack или на стендапе):

> «Коллеги, по задаче с рефакторингом модуля оплаты: я обнаружил, что при изменении логики расчетов нам нужно переписать еще и интеграцию с платежным шлюзом, о чем не было сказано в описании.
>
> На текущий момент готово 60% (базовая логика). Если я буду делать всё по плану, задача будет готова только послезавтра.
>
> **Предлагаю два варианта:**
> 1. Мы сдвигаем дедлайн на завтрашний вечер, чтобы я сделал всё чисто и с тестами.
> 2. Я завтра выкатываю только базовый функционал (смена статуса), а интеграцию с шлюзом сделаю вторым этапом в следующий день.
>
> Что скажете?»

### Почему это правильно?
1.  **Я сохраняю доверие:** Я не обманываю и не пытаюсь «спрятать» проблему.
2.  **Я даю выбор:** Я не навязываю свое решение, а даю бизнесу инструменты для принятия управленческого решения.
3.  **Я проявляю ответственность:** Я показываю, что я контролирую ситуацию и понимаю последствия.

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

Это вопрос о поиске баланса между **инженерным совершенством** и **бизнес-целесообразностью**. В разработке существует концепция «золотой середины»: если тратить всё время на идеальный код, продукт никогда не выйдет на рынок. Если гнаться только за скоростью — проект превратится в «спагетти», который невозможно поддерживать.

Мой подход базируется на трех принципах: **оценка стоимости, анализ рисков и понимание контекста.**

---

### 1. Когда код «достаточно хорош» (Definition of Done)

Я считаю код готовым к сдаче, когда он соответствует трем критериям:

1.  **Он решает бизнес-задачу (Correctness):** Код работает именно так, как описано в требованиях. Все граничные случаи обработаны.
2.  **Он безопасен и стабилен (Reliability):** Он покрыт тестами, не ломает существующий функционал (нет регрессии) и не содержит очевидных уязвимостей.
3.  **Он понятен и поддерживаем (Maintainability):** Он соответствует принятым в команде стандартам (PSR, Style Guide), не содержит «магических» чисел и имеет понятные имена.

**Если код прошел эти три фильтра — он готов.** Дальнейшее улучшение (например, переход от `foreach` к `array_map` или разделение класса на еще более мелкие части) — это уже работа над техническим долгом.

---

### 2. Когда стоит продолжать улучшать (Refactoring)

Я продолжаю улучшать код, если я вижу **«точку невозврата»** или **высокую стоимость владения**:

*   **Запах кода (Code Smells):** Если я вижу, что новая задача требует внесения изменений в уже написанный код, и это вызывает «боль» (сложно добавить новое поле, нужно менять 10 мест) — это сигнал, что текущий код **недостаточно хорош**. Нужно провести рефакторинг.
*   **Критический путь:** Если код находится в самом часто используемом или самом нагруженном месте системы (например, ядро обработки заказов), я буду инвестировать в него гораздо больше времени на чистоту и производительность, чем в код админки для генерации отчетов.
*   **Технический долг становится дорогим:** Если скорость разработки новых фич замедляется из-за сложности старого кода — это время платить по долгам.

---

### 3. Как я соблюдаю баланс в реальном проекте

Чтобы не превратиться в «вечного рефакторинга», я использую следующие стратегии:

#### А) Правило бойскаута (Boy Scout Rule)
*«Оставь место стоянки чуть чище, чем оно было до тебя»*.
Я не пытаюсь переписать весь проект за один раз. Но если я работаю над задачей и вижу мелкий, некритичный запах кода в этом же модуле — я исправляю его сразу. Это позволяет плавно и незаметно улучшать качество системы без остановки разработки.

#### Б) Оценка стоимости vs Ценность (Cost vs Value)
Перед любым крупным рефакторингом я задаю вопрос: **«Сколько времени это займет и что это даст бизнесу?»**
*   Если рефакторинг займет 3 дня, а ускорит работу модуля на 5 мс — я **не буду** этого делать.
*   Если рефакторинг займет 3 дня, но позволит нам внедрять новые фичи в два раза быстрее в следующем месяце — я **предложу** это бизнесу.

#### В) Стратегия «Технический долг как инструмент»
Я осознаю, что технический долг — это не всегда плохо. Иногда это **инструмент**, позволяющий выпустить продукт вовремя (Time-to-Market).
*   Я могу сознательно написать менее идеальный код, чтобы успеть к релизу.
*   **Но:** Я обязан зафиксировать этот долг (создать задачу в бэклоге) и обсудить с командой, когда мы будем его возвращать.

#### Г) Использование CI/CD и автоматизации
Чтобы не тратить время на обсуждение «стиля кода» на ревью, я выношу всё, что можно автоматизировать, в пайплайн (PHPStan, PHP-CS-Fixer). Это освобождает время разработчиков для обсуждения **архитектуры и логики**, а не пробелов и скобок.

### Итог
Моя цель — не написать «идеальный код», а создать **здоровую систему**, которая позволяет бизнесу быстро развиваться, не превращаясь в неподъемную гору технического долга.

Если бы мне пришлось выбирать стек для нового проекта и защищать его перед командой, я бы не просто назвал технологии, а представил бы **архитектурно обоснованное решение**, исходя из трех критериев: **Time-to-Market (скорость выхода на рынок)**, **Reliability (надежность)** и **Maintainability (стоимость поддержки)**.

Вот мой выбор и аргументация:

---

### 1. Язык и фреймворк: PHP 8.3 + Symfony
**Почему:**
*   **Скорость разработки (Productivity):** Symfony предоставляет готовые, протестированные компоненты для всего: от безопасности до работы с очередями. Это позволяет команде фокусироваться на **бизнес-логике**, а не на написании «велосипедов» для работы с HTTP или сессиями.
*   **Типизация и надежность:** Благодаря PHP 8, мы имеем строгую типизацию, readonly свойства и атрибуты. Это делает код самодокументированным и снижает количество runtime-ошибок.
*   **Экосистема:** Огромное количество готовых библиотек (Composer) и отличная документация.

### 2. База данных: PostgreSQL
**Почему:**
*   **Мощность и функциональность:** PostgreSQL — это не просто хранилище, это полноценный движок. Поддержка JSONB (для полуструктурированных данных), сложные оконные функции, отличная работа с индексами (GIN, GiST) и поддержка полнотекстового поиска делают её универсальной.
*   **Целостность:** Строгие ограничения (constraints), поддержка сложных транзакций и ACID-комплаентность гарантируют, что данные в системе не превратятся в хаос.
*   **Масштабируемость:** Она отлично справляется с нагрузками и имеет богатый инструментарий для репликации и шардирования.

### 3. Архитектурный паттерн: Clean Architecture + DDD
**Почему:**
*   **Защита от изменений:** Мы отделяем ядро (бизнес-правила) от деталей реализации (БД, API, очереди). Если через два года мы захотим заменить PostgreSQL на MongoDB или перейти с REST на GraphQL, нам не придется переписывать всю систему — мы просто напишем новые адаптеры в слое Infrastructure.
*   **Тестируемость:** Разделение на слои позволяет писать быстрые Unit-тесты для бизнес-логики без необходимости поднимать тяжелую инфраструктуру.

### 4. Инфраструктура и коммуникация: Docker + Messenger + RabbitMQ
**Почему:**
*   **Консистентность окружения:** Docker гарантирует, что «у меня на машине работает» будет означать «работает и в продакшене».
*   **Асинхронность (Scalability):** Использование Symfony Messenger и RabbitMQ позволяет развязать тяжелые процессы (отправка писем, генерация отчетов, интеграции) от основного цикла запроса. Это делает систему отзывчивой для пользователя и устойчивой к пиковым нагрузкам.
