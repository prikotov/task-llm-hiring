## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

### Рассуждение

Когда мы говорим о «чистом и надежном коде» в контексте PHP, мы подразумеваем две вещи: **снижение когнитивной нагрузки** (код должен быть понятным и предсказуемым) и **минимизацию runtime-ошибок** (код должен быть защищен на уровне типов).

До PHP 8.0 язык часто критиковали за избыточность (boilerplate) и «рыхлость» типизации. Современные версии (8.0, 8.1, 8.2, 8.3) фактически превратили PHP в более строгий и выразительный язык. 

Если анализировать мой опыт, я бы выделил четыре ключевых направления:
1.  **Строгость типов и защита состояния:** Это уменьшает количество `null` проверок и невалидных состояний объектов.
2.  **Синтаксический сахар для уменьшения бойлерплейта:** Чем меньше «мусорного» кода, тем проще видеть бизнес-логику.
3.  **Улучшение работы с данными:** Новые структуры данных делают код более семантичным.
4.  **Pattern Matching:** Возможность выразительно обрабатывать разные состояния данных.

Я не буду перечислять всё подряд (вроde JIT, который больше про производительность, а не про чистоту), а сосредоточусь именно на инженерных аспектах качества кода.

---

### Финальный ответ

Я выделяю четыре ключевых нововведения, которые кардинально изменили подход к написанию чистого кода в PHP.

#### 1. Constructor Property Promotion & Readonly Properties
Это уничтожило необходимость дублировать свойства в объявлении класса, параметрах конструктора и теле самого конструктора. В сочетании с `readonly` это позволяет создавать неизменяемые (immutable) объекты — золотой стандарт для Value Objects в DDD.

**Было:**
```php
class UserRegistrationRequest {
    private string $email;
    private string $password;

    public function __construct(string $email, string $password) {
        $this->email = $email;
        $this->password = $password;
    }

    public function getEmail(): string { return $this->email; }
    public function getPassword(): string { return $this->password; }
}
```

**Стало (PHP 8.2+):**
```php
readonly class UserRegistrationRequest {
    public function __construct(
        public string $email,
        public string $password,
    ) {}
}
```
*Результат: Код стал компактным, а объект защищен от случайного изменения состояния после создания.*

#### 2. Enums (Перечисления)
До появления Enums мы использовали константы, что было небезопасно: в метод можно было передать любое целое число или строку, даже если она не является «валидным состоянием». Enums дают строгую типизацию на уровне значений.

**Пример:**
```php
enum OrderStatus: string {
    case Pending = 'pending';
    case Shipped = 'shipped';
    case Delivered = 'delivered';
}

class Order {
    public function transitionTo(OrderStatus $status): void {
        // Мы на 100% уверены, что сюда не придет "something_else"
        $this->status = $status;
    }
}
```
*Результат: Исключены ошибки передачи невалидных состояний, код самодокументирован.*

#### 3. Match Expression
`match` — это не просто «улучшенный switch». Это выражение, которое возвращает значение и использует строгое сравнение (`===`). Это делает логику ветвления более предсказуемой и уменьшает вероятность ошибки из-за забытого `break`.

**Пример:**
```php
$message = match ($status) {
    OrderStatus::Pending => 'Ваш заказ ожидает обработки',
    OrderStatus::Shipped => 'Заказ уже в пути',
    OrderStatus::Delivered => 'Заказ доставлен',
    // Если значение не покрыто, PHP выбросит UnhandledMatchError, что лучше, чем молчаливый провал
};
```
*Результат: Исчезает риск забыть `break` и упрощается обработка исключительных случаев.*

#### 4. Union Types & Intersection Types
Это позволяет точно описывать контракты методов. Union types (`string|int`) расширяют гибкость, а Intersection types (`Iterator&Countable` — PHP 8.1) позволяют описывать объекты, которые должны удовлетворять нескольким интерфейсам одновременно, что критично для сложных систем.

**Пример:**
```php
// Intersection types позволяют требовать строгого соответствия нескольким контрактам
public function process(LoggerInterface&FlushableInterface $logger): void 
{
    $logger->log('Processing...');
    $logger->flush();
}
```
*Результат: Типизация становится максимально точной, что позволяет инструментам статического анализа (PHPStan, Psalm) находить ошибки еще до запуска кода.*

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

### Рассуждение

Вопрос о системе типов в PHP — это классический вопрос на понимание того, насколько разработчик осознает «подводные камни» языка. 

Для начала стоит прояснить одну важную деталь: в PHP существует два разных уровня типизации. Первый — это **внутренняя типизация языка** (как значения хранятся в памяти и как они преобразуются при операциях). Второй — это **типизация на уровне сигнатур функций и методов** (Type Hinting). Проблема в том, что по умолчанию PHP ведет себя как язык с «мягкой» типизацией (coercive mode), пытаясь «помочь» разработчику, приводя типы автоматически.

Когда мы говорим о `declare(strict_types=1);`, мы не меняем движок PHP, мы меняем **правила проверки типов при вызове функций** в текущем файле.

Основные зоны риска, которые я выделяю:
1. **Coercive mode (режим по умолчанию):** когда строка `"10"` превращается в `int(10)` без предупреждений.
2. **Nullability:** попытка передать `null` туда, где ожидается тип, но не указано `?Type`.
3. **Область действия `strict_types`:** это самая большая «ловушка». Она работает только на *вызов* функции из того файла, где она объявлена.

---

### Финальный ответ

Система типов PHP — это гибридная модель. По умолчанию она работает в режиме **coercive mode** (приведение типов), но мы можем принудительно переключить её в **strict mode**.

#### 1. Что дает `strict_types=1`?
Эта директива отключает автоматическое приведение типов при передаче аргументов в функцию. Если функция ожидает `int`, а вы передаете `string`, PHP выбросит `TypeError`.

**Важно:** `strict_types` действует на стороне **вызывающего** кода. Если в `file_a.php` стоит `strict_types=1`, а в `file_b.php` нет, то вызов функции из `file_a` будет строгим, а из `file_b` — мягким. Это часто путает разработчиков.

#### 2. Типичные ловушки и поведение

**Ловушка №1: Неявное приведение (Coercive mode)**
В режиме по умолчанию PHP пытается «угадать» намерение.

```php
declare(strict_types=0); // По умолчанию

function add(int $a, int $b): int {
    return $a + $b;
}

echo add(5, "10"); // Выведет 15. PHP тихо привел "10" к int.
```
*Проблема: Это скрывает баги. Если в функцию пришла строка `"10abc"`, PHP может выдать предупреждение или превратить её в `10`, что приведет к непредсказуемому бизнес-результату.*

**Ловушка №2: Nullable-типы**
Многие забывают, что в PHP тип `string` и `?string` — это разные вещи.

```php
function process(string $name) { /*...*/ }

process(null); // TypeError, даже если в базе данных это поле может быть NULL.
```

**Ловушка №3: Магические преобразования при сравнении**
Это не совсем про сигнатуры, но про систему типов в целом. Оператор `==` (loose comparison) — источник огромного количества багов.

```php
if (0 == "foobar") { 
    // В старых версиях PHP (до 8.0) это было true! 
    // В PHP 8.0+ это false, так как логика сравнения изменилась.
}
```

#### 3. Где типизация спасает

Типизация спасает в **архитектурных границах**. Когда я проектирую Domain Layer, я использую строгие типы, чтобы гарантировать, что в бизнес-логику не попадет «мусор».

**Пример «спасения»:**
Представим метод перевода денег.
```php
declare(strict_types=1);

class Wallet {
    public function deposit(int $amount): void {
        // ...
    }
}

$wallet = new Wallet();
$amountFromRequest = $_GET['amount']; // Это всегда string

// Ошибка вылетит НЕМЕДЛЕННО при вызове, а не внутри метода,
// где мы можем случайно потерять точность или совершить ошибку.
$wallet->deposit($amountFromRequest); 
```
*Здесь типизация заставляет разработчика явно привести строку к числу (`(int)$amount`), делая намерение явным.*

#### 4. Где типизация удивляет (и мешает)

Типизация может «удивлять» при работе с полиморфизмом и сложными структурами данных, если не понимать разницы между интерфейсами и конкретными классами.

**Пример «удивления»:**
```php
interface UserInterface {}
class Admin implements UserInterface {}
class Guest implements UserInterface {}

function register(UserInterface $user) { /*...*/ }

// Если я передам объект, который реализует интерфейс, но 
// является анонимным классом или прокси-объектом (как в Doctrine),
// иногда возникают проблемы с проверкой типов в сложных иерархиях,
// особенно если используются сторонние библиотеки с их собственной типизацией.
```

**Итог:**
Я всегда использую `declare(strict_types=1);` во всех своих проектах. Это переносит обнаружение ошибок с этапа «неожиданного поведения в продакшене» на этап «ошибки при запуске теста/скрипта». Мой золотой стандарт: **Явное лучше, чем неявное.**

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

### Рассуждение

Вопрос об исключениях — это вопрос о том, как приложение управляет **непредвиденными состояниями** и как оно сообщает о них вызывающему коду. 

Главная проблема начинающих разработчиков в том, что они либо используют исключения для управления потоком программы (Control Flow), либо вообще игнорируют их, полагаясь на `return false` или `null`. Оба подхода ошибочны.

При проектировании я опираюсь на три принципа:
1. **Исключение — это исключительная ситуация**, а не ожидаемый сценарий (для ожидаемых сценариев есть `Result` объекты или `null`).
2. **Иерархия должна отражать бизнес-смыслы**, а не техническую реализацию.
3. **Границы (Boundaries) — это места трансформации**. Когда исключение пересекает границу слоя (например, из Infrastructure в Domain), оно должно быть преобразовано.

Разберем это подробнее.

---

### Финальный ответ

Я подхожу к проектированию исключений системно, разделяя их на технические и бизнес-исключения.

#### 1. Иерархия исключений
Я никогда не выбрасываю базовый `\Exception`. Я всегда создаю свою иерархию, начиная от общего интерфейса или абстрактного класса приложения.

*   **Domain Exceptions:** Отражают нарушение бизнес-правил (например, `InsufficientFundsException`). Они важны, потому что именно на них строится логика обработки ошибок на уровне пользователя.
*   **Application Exceptions:** Отражают ошибки использования приложения (например, `UserNotFoundException` в контексте Use Case).
*   **Infrastructure Exceptions:** Отражают технические сбои (например, `DatabaseConnectionException`).

**Пример структуры:**
```text
App\Exception\DomainExceptionInterface (маркерный интерфейс)
├── App\Exception\Domain\InsufficientFundsException
└── App\Exception\Domain\AccountIsLockedException
```

#### 2. Оборачивание (Exception Wrapping)
Это критически важный аспект при соблюдении чистой архитектуры. Если мой репозиторий (Infrastructure слой) использует Doctrine, он может выбросить `Doctrine\DBAL\Exception`. Я **не имею права** пробрасывать это исключение в Domain слой. Почему? Потому что тогда мой Domain станет зависимым от реализации (Doctrine).

**Правильный подход:** Перехватить техническое исключение и обернуть его в наше доменное/прикладное.

```php
// В слое Infrastructure (Repository)
try {
    $this->connection->executeQuery($sql);
} catch (\PDOException $e) {
    // Мы оборачиваем низкоуровневую ошибку в наш контекстный класс
    // Передаем $e как $previous, чтобы сохранить Stack Trace
    throw new RepositoryException("Failed to fetch user", 0, $e);
}
```
*Это позволяет слою Application обрабатывать ошибку через `RepositoryException`, не зная ничего о PDO или Doctrine.*

#### 3. Контракт метода
Контракт метода — это не только типы возвращаемых значений и аргументов. Это еще и **обещание относительно исключений**.

Если я пишу метод:
`public function withdraw(int $amount): void`

Я должен четко понимать:
1. Выбрасывает ли он исключение, если денег недостаточно? (Это часть контракта).
2. Выбрасывает ли он исключение, если база данных упала? (Это техническая деталь, которую лучше скрыть или обернуть).

В хорошей документации (или в понимании команды) должно быть ясно: «Этот метод гарантирует либо успешное выполнение, либо выбрасывает `InsufficientFundsException`».

#### 4. Антипаттерны

Я выделяю четыре главных антипаттерна, которые я пресекаю на Code Review:

1.  **Exceptions for Control Flow (Исключения для управления логикой):**
    *   *Пример:* Использование `try-catch` для проверки, существует ли файл или пользователь. 
    *   *Почему это плохо:* Исключения — дорогая операция (сбор Stack Trace). Это делает код запутанным и медленным. Вместо этого используйте `if ($user === null)`.

2.  **Catch-and-Log-and-Silence (Поймал, записал и забыл):**
    *   *Пример:* `catch (\Exception $e) { $this->logger->error($e); }` без дальнейших действий.
    *   *Почему это плохо:* Это создает «молчаливые ошибки». Система продолжает работать в невалидном состоянии, и проблему невозможно отследить.

3.  **Generic Exception Catching (Ловля общего исключения):**
    *   *Пример:* `catch (\Exception $e)` или `catch (\Throwable $e)` в середине бизнес-логики.
    *   *Почему это плохо:* Вы можете случайно поймать `TypeError` или `DivisionByZeroError`, которые являются багами в коде, а не ожидаемыми ошибками, и пропустить их.

4.  **Missing Previous Exception (Потеря исходного исключения):**
    *   *Пример:* `throw new MyException("Error occurred");` без передачи `$e`.
    *   *Почему это плохо:* Вы теряете первопричину (Root Cause). Когда через месяц вы будете дебажить лог, вы увидите только `MyException`, но не узнаете, что на самом деле упал сокет или закончилась память. Всегда передавайте `$previous`.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

### Рассуждение

Если анализировать реальные проекты (от стартапов до крупного энтерпрайза), я бы выделил одного главного «виновника». Это не нарушение Single Responsibility (хотя оно встречается повсеместно), и не Liskov Substitution (который часто является следствием архитектурных ошибок).

Самый массовый и разрушительный нарушаемый принцип — это **Dependency Inversion Principle (DIP)**.

**Почему именно он?**
Разработка на PHP часто идет по пути наименьшего сопротивления. Проще создать экземпляр класса прямо внутри другого класса (`new UserService()`), чем проектировать интерфейс, регистрировать его в DI-контейнере и внедрять через конструктор. 

Нарушение DIP ведет к жесткой связности (Tight Coupling). Как только вы начинаете создавать объекты внутри методов, ваш код становится:
1. **Нетестируемым:** вы не можете подменить реальный сервис моком (Mock) в юнит-тестах.
2. **Хрупким:** изменение в одном классе неизбежно ломает цепочку зависимых объектов.
3. **Сложным для расширения:** вы не можете заменить реализацию (например, с MySQL на PostgreSQL или с Mailchimp на SendGrid) без переписывания бизнес-логики.

---

### Финальный ответ

Чаще всего нарушается **Dependency Inversion Principle (Принцип инверсии зависимостей)**.

#### Типовой пример нарушения (Tight Coupling)

Представьте сервис, который регистрирует пользователя и отправляет ему приветственное письмо. Разработчик решает «ускорить» процесс и делает так:

```php
class UserRegistrationService {
    public function register(array $userData): void {
        // 1. Работа с БД (напрямую создаем зависимость)
        $repository = new MySQLUserRepository(); 
        $repository->save($userData);

        // 2. Работа с почтой (напрямую создаем зависимость)
        $mailer = new SendGridMailer('api-key-123');
        $mailer->sendWelcomeEmail($userData['email']);
        
        echo "User registered!";
    }
}
```

**В чем проблема здесь?**
*   `UserRegistrationService` жестко привязан к `MySQLUserRepository` и `SendGridMailer`. 
*   Если я захочу написать Unit-тест на этот сервис, он реально пойдет в базу данных и реально попытается отправить письмо через API. Это уже не юнит-тест, а интеграционный, и он будет медленным и нестабильным.
*   Если завтра бизнес скажет: «Переходим на Amazon SES», мне придется править бизнес-логику сервиса.

---

#### Рефакторинг (Применение DIP)

Чтобы исправить это, мы должны внедрять зависимости через интерфейсы (абстракции), а не через конкретные реализации.

**Шаг 1: Создаем интерфейсы (абстракции)**

```php
interface UserRepositoryInterface {
    public function save(array $data): void;
}

interface MailerInterface {
    public function sendWelcomeEmail(string $email): void;
}
```

**Шаг 2: Реализуем конкретные классы**

```php
class MySQLUserRepository implements UserRepositoryInterface {
    public function save(array $data): void { /* SQL logic */ }
}

class SendGridMailer implements MailerInterface {
    public function sendWelcomeEmail(string $email): void { /* API logic */ }
}
```

**Шаг 3: Рефакторим основной сервис (Dependency Injection)**

```php
class UserRegistrationService {
    // Мы зависим от интерфейсов, а не от реализаций
    public function __construct(
        private UserRepositoryInterface $userRepository,
        private MailerInterface $mailer
    ) {}

    public function register(array $userData): void {
        $this->userRepository->save($userData);
        $this->mailer->sendWelcomeEmail($userData['email']);
        
        echo "User registered!";
    }
}
```

**Что мы получили в итоге?**
1.  **Тестируемость:** В тестах я могу легко передать `new MockUserRepository()` и `new MockMailer()`. Тест будет выполняться за миллисекунды и не будет зависеть от внешних систем.
2.  **Гибкость:** Если мы меняем почтовый сервис, мы просто создаем новый класс `AmazonMailer implements MailerInterface` и меняем одну строчку в конфигурации DI-контейнера. Сам `UserRegistrationService` остается нетронутым.
3.  **Чистота:** Бизнес-логика теперь отделена от деталей реализации (БД, API, Файловая система). Это и есть суть чистой архитектуры.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

### Рассуждение

Это отличный вопрос, который отделяет «академического» разработчика от инженера. В учебниках SOLID преподносятся как незыблемые законы, но в реальном производстве (Production) мы всегда работаем в условиях ограниченных ресурсов: **времени, денег и когнитивной нагрузки**.

Если отвечать коротко: **Да, нарушать SOLID не только можно, но иногда и нужно.**

Инженерная задача — это всегда поиск баланса (trade-off). Слепое следование принципам может привести к **overengineering** (избыточному проектированию). Если вы строите систему абстракций для задачи, которая решится простым скриптом, вы тратите деньги компании впустую. Если вы создаете 10 интерфейсов для одного класса, который никогда не будет иметь других реализаций, вы увеличиваете сложность проекта, не принося никакой пользы.

Я выделяю три критерия, когда нарушение принципов оправдано:
1. **Time-to-market (Скорость выхода на рынок):** В стартапе на стадии MVP (Minimum Viable Product) важнее проверить гипотезу, чем построить идеально расширяемую архитектуру.
2. **Простота и читаемость (YAGNI — You Ain't Gonna Need It):** Если вероятность появления второй реализации интерфейса близка к нулю, создание этого интерфейса — это лишний шум в коде.
3. **Масштаб задачи:** Для небольшого внутреннего инструмента или разового скрипта обработки данных архитектура уровня Enterprise избыточна.

---

### Финальный ответ

Да, принципы SOLID — это не догма, а набор рекомендаций для управления сложностью. Нарушение принципов оправдано, когда цена следования принципу (в виде сложности или затраченного времени) превышает пользу, которую он приносит.

#### Пример оправданного нарушения: Принцип инверсии зависимостей (DIP) и Single Responsibility (SRP)

Представьте, что вы пишете небольшой CLI-скрипт для разовой миграции данных из одного JSON-файла в одну таблицу PostgreSQL. Это задача на один вечер.

**Вариант «По SOLID» (Overengineering):**
Вы создаете `JsonReaderInterface`, `JsonReaderImplementation`, `DataTransformerInterface`, `DataTransformerImplementation`, `DatabaseConnectionInterface`, `UserRepositoryInterface` и т.д. Вы регистрируете всё это в контейнере.
*   **Результат:** Вы потратили 5 часов на создание инфраструктуры, которую выбросите через день. Код стал размазан по десяти файлам.

**Вариант «Нарушение принципов» (Прагматичный подход):**
Вы пишете один плотный скрипт, где логика чтения, трансформации и записи идет последовательно.

```php
// Один класс, нарушающий SRP и DIP
class MigrationScript {
    public function run(string $filePath): void {
        // Нарушаем DIP: создаем зависимость напрямую
        $pdo = new PDO('pgsql:host=localhost;dbname=test', 'user', 'pass');
        
        // Нарушаем SRP: логика чтения, парсинга и записи в одном месте
        $data = json_decode(file_get_contents($filePath), true);
        
        foreach ($data as $row) {
            $stmt = $pdo->prepare("INSERT INTO users (name) VALUES (?)");
            $stmt->execute([$row['name']]);
        }
    }
}
```

**Почему это оправдано?**
1. **YAGNI:** Нам не нужно менять способ чтения данных (это всегда будет JSON) или способ записи (это разовая миграция).
2. **Срок жизни кода:** Этот код — «одноразовый». Инвестировать время в его идеальную архитектуру экономически нецелесообразно.
3. **Простота:** Любой разработчик может открыть этот файл и за 10 секунд понять, что он делает. В случае с SOLID-версией ему пришлось бы прыгать по интерфейсам и реализациям.

**Мой принцип как инженера:** 
Я начинаю с простого и понятного кода (часто с нарушениями), но как только я вижу признаки того, что код начинает «болеть» (сложно тестировать, трудно менять, много дублирования) — я провожу рефакторинг и внедряю SOLID. **SOLID должен быть инструментом борьбы со сложностью, а не источником новой сложности.**

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

### Рассуждение

Когда говорят об **Open/Closed Principle (OCP)**, первой ассоциацией часто является наследование: «создай базовый класс и расширяй его через подклассы». Но в современном объектно-ориентированном проектировании (и особенно в PHP) наследование считается «сильной» связью (tight coupling), которая несет в себе много рисков (проблема хрупкого базового класса, нарушение инкапсуляции).

На самом деле, OCP требует лишь того, чтобы поведение системы можно было изменить, не меняя её исходный код. Наследование — это лишь один из путей реализации полиморфизма, но не единственный.

Если мы посмотрим на проектирование систем шире, то увидим, что полиморфизм можно реализовать через:
1. **Композицию (Composition)** — классический путь через интерфейсы.
2. **Функциональный подход (First-class functions)** — передача поведения через замыкания.
3. **Метапрограммирование/Динамику** — использование магических методов или атрибутов (хотя это более специфичный путь).
4. **Паттерны проектирования** — такие как «Стратегия» или «Декоратор», которые по сути являются обертками над композицией.

Я бы разделил ответы на три ключевых архитектурных подхода: композиция, функциональный подход и паттерн «Декоратор».

---

### Финальный ответ

Помимо наследования, OCP реализуется через механизмы, которые обеспечивают **полиморфизм без жесткой иерархической связи**.

#### 1. Композиция и интерфейсы (Strategy Pattern)
Это самый распространенный и рекомендуемый способ в PHP. Вместо того чтобы наследоваться от класса, мы внедряем в него объект, реализующий определенный интерфейс. Мы расширяем поведение, подставляя новую реализацию интерфейса в конструктор.

**Пример:**
```php
interface PaymentMethodInterface {
    public function pay(int $amount): void;
}

class StripePayment implements PaymentMethodInterface {
    public function pay(int $amount): void { /* ... */ }
}

class PayPalPayment implements PaymentMethodInterface {
    public function pay(int $amount): void { /* ... */ }
}

class Checkout {
    // Класс Checkout закрыт для изменений, но открыт для новых способов оплаты
    public function __construct(
        private PaymentMethodInterface $paymentMethod
    ) {}

    public function process(int $amount): void {
        $this->paymentMethod->pay($amount);
    }
}
```
*Здесь мы не меняем `Checkout`, чтобы добавить новый способ оплаты — мы просто реализуем новый интерфейс.*

#### 2. Функциональный подход (Callbacks / Closures)
В PHP функции являются объектами первого класса. Мы можем реализовать OCP, передавая логику поведения в качестве замыкания (callable). Это позволяет изменять алгоритм внутри метода, не меняя сам метод.

**Пример:**
```php
class DataProcessor {
    // Метод открыт для новых алгоритмов трансформации через callback
    public function process(array $data, callable $transformer): array {
        return array_map($transformer, $data);
    }
}

$processor = new DataProcessor();
$data = [1, 2, 3];

// Расширяем поведение "на лету" без создания классов
$squared = $processor->process($data, fn($n) => $n * $n);
$stringified = $processor->process($data, fn($n) => "Num: $n");
```
*Это максимально гибкий способ, когда логика трансформации проста и не требует сложного состояния.*

#### 3. Паттерн Декоратор (Decorator Pattern)
Декоратор позволяет расширять функциональность объекта, «оборачивая» его в другой объект, который реализует тот же интерфейс. Это позволяет добавлять ответственность динамически, не меняя исходный класс и не используя наследование.

**Пример:**
```php
interface LoggerInterface {
    public function log(string $message): void;
}

class FileLogger implements LoggerInterface {
    public function log(string $message): void { /* запись в файл */ }
}

// Декоратор, который добавляет отправку в Telegram к обычному логгеру
class TelegramLoggerDecorator implements LoggerInterface {
    public function __construct(private LoggerInterface $innerLogger) {}

    public function log(string $message): void {
        $this->innerLogger->log($message); // Выполняем базовое действие
        $this->sendToTelegram($message);   // Добавляем новое поведение
    }

    private function sendToTelegram(string $msg): void { /* ... */ }
}
```
*Мы расширили возможности логгера, не меняя код `FileLogger` и не создавая сложную иерархию наследования.*

**Резюме:**
Если наследование — это связь **"is-a"** (является), то композиция и функциональный подход — это связь **"has-a"** (имеет) или **"acts-as"** (действует как). Для чистого кода и соблюдения OCP в современных PHP-приложениях я всегда отдаю предпочтение **композиции через интерфейсы** и **декораторам**.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

### Рассуждение

Это отличный вопрос на проверку того, понимает ли разработчик суть принципа или просто зазубрил его в контексте «классов». 

Если отвечать формально: в контек la ООП (Object-Oriented Programming), где SOLID и зародились, SRP (Single Responsibility Principle) часто преподносится как «принцип одной ответственности для класса». Но это упрощение, которое может ввести в заблуждение.

Если мы начнем анализировать вопрос глубже, то увидим, что «ответственность» — это не свойство кода, а характеристика **модуля** или **единицы логики**. Ответственность — это «причина для изменения» (reason to change), как гласит определение Роберта Мартина. 

Причины для изменения могут возникнуть на самых разных уровнях:
1. **На уровне функций/методов** (особенно в процедурном или функциональном подходе).
2. **На уровне модулей/пакетов** (в микросервисной архитектуре или при работе с Composer-пакетами).
3. **На уровне целых сервисов/микросервисов** (в распределенных системах).
4. **На уровне баз данных** (схемы данных и хранимые процедуры).

Если я буду применять SRP только к классам, я рискую создать «микро-классы», которые делают по одной мелочи, но при этом вся бизнес-логика будет размазана по сотням файлов, превращая проект в нечитаемый пазл. Это называется **"Fragmented Logic"**.

---

### Финальный ответ

**Нет, SRP не ограничивается только классами.** 

Принцип единственной ответственности применим к любой логической единице кода, которую можно выделить как самостоятельный модуль. Если мы будем применять его только к классам, мы упустим масштабы системы.

Я выделяю следующие уровни применения SRP:

#### 1. Уровень функций и методов
Даже если вы не используете классы (например, в простых скриптах или функциональных компонентах), функция должна делать что-то одно.
* **Нарушение:** Функция `processOrder()`, которая одновременно валидирует данные, считает налоги, сохраняет в БД и отправляет email.
* **Решение:** Разбить на `validateOrder()`, `calculateTaxes()`, `saveOrder()` и т.д.

#### 2. Уровень модулей и пакетов (Composer/Namespaces)
В PHP мы часто группируем код в пространства имен (`namespace`). Весь пакет или модуль должен иметь четкую зону ответственности.
* **Нарушение:** Пакет `UserManagement`, который внутри себя внезапно начинает содержать логику генерации PDF-отчетов для бухгалтерии.
* **Решение:** Вынести логику отчетов в отдельный пакет `ReportingModule`.

#### 3. Уровень микросервисов и сервисов (Bounded Contexts)
В распределенных системах SRP перерастает в концепцию **Bounded Context** из DDD. Каждый микросервис должен отвечать за свой контекст.
* **Нарушение:** Микросервис `OrderService`, который знает всё: и о составе корзины, и о том, какой цвет у товара, и о том, какой баланс у пользователя.
* **Решение:** Разделение на `OrderService`, `CatalogService` и `PaymentService`. Каждый сервис отвечает за свою область данных и бизнес-логики.

#### 4. Уровень базы данных
Даже на уровне SQL-схемы можно увидеть нарушение SRP.
* **Нарушение:** Одна гигантская таблица `users`, в которой лежат и данные для авторизации, и настройки профиля, и история логов входа, и платежные данные.
* **Решение:** Нормализация и разделение на `users`, `user_profiles`, `user_auth_logs` и `user_payments`.

**Мой инженерный вывод:**
При применении SRP важно не впасть в крайность **"Atomization"** (атомизации), когда мы дробим код на слишком мелкие части. Задача SRP — не уменьшить количество строк в классе, а **сгруппировать код так, чтобы изменения в одной части системы (например, смена провайдера почты) не требовали изменений в другой части (логика расчета цены товара).**

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

### Рассуждение

Вопрос касается «сердца» Symfony. Чтобы ответить на него глубоко, нужно понимать, что DI-контейнер в Symfony — это не просто «хранилище объектов» (как часто думают новички), а сложная система, состоящая из двух фаз: **Compile Time** (когда строится схема) и **Runtime** (когда создаются объекты).

Важно прояснить одну деталь: контейнер в Symfony — это **Compiled Container**. Это значит, что в рантайме он работает максимально быстро, потомуs что почти вся «магия» (поиск классов, разрешение зависимостей, автовайринг) происходит заранее, на этапе компиляции, и результат сохраняется в виде оптимизированного PHP-файла.

Я разберу процесс по этапам: от конфигурации до момента получения объекта.

---

### Финальный ответ

Работа Symfony DI-контейнера делится на три ключевых этапа: загрузка конфигурации, компиляция и выполнение (runtime).

#### 1. Этап компиляции (Compile Time)
Этот этап происходит один раз (при очистке кэша или в среде `dev`). Он превращает ваши YAML/XML/PHP конфиги в эффективный PHP-код.

1.  **Loading:** Контейнер загружает все конфигурационные файлы (из `config/`, бандлов и т.д.). На этом этапе создаются **Definition**-объекты (`Definition`). `Definition` — это не сам сервис, а «рецепт» его создания: какой класс использовать, какие аргументы нужны, какие методы вызвать.
2.  **Processing & Autowiring:** Здесь происходит магия. Symfony сканирует ваши конструкторы через Reflection API. Если он видит тип `UserRepositoryInterface`, он ищет в контейнере сервис, который реализует этот интерфейс.
3.  **Compiler Passes:** Это важнейший этап. Symfony и сторонние бандлы (например, Doctrine) запускают свои «проходы». Они могут изменять `Definition` на лету. Например, `DoctrineBundle` находит все сервисы с тегом `doctrine.repository` и автоматически регистрирует их.
4.  **Optimization:** Контейнер удаляет неиспользуемые сервисы (unused services) и оптимизирует дерево зависимостей.
5.  **Compilation (Caching):** Итогом становится огромный PHP-файл в папке `var/cache/.../AppKernelDevDebugContainer.php`. Это и есть ваш контейнер. В нем нет Reflection — там написан прямой PHP-код для создания объектов.

#### 2. Как работает Autowiring
Autowiring — это не магия, а результат работы процесса компиляции. 

Когда вы пишете `public function __construct(MailerInterface $mailer)`, Symfony во время компиляции:
1.  Смотриет на тип аргумента через Reflection.
2.  Ищет в текущем дереве определений (`Definition`) сервис, который помечен как реализация этого интерфейса.
3.  Если находит один подходящий сервис, он записывает в `Definition` вашего класса: *"При создании этого класса, передай в первый аргумент вот тот сервис"*.

Если подходящих сервисов несколько, Symfony выбросит исключение при компиляции, требуя уточнения через `#[Target]` или именованные аргументы.

#### 3. Момент запроса сервиса (Runtime)
Когда вы вызываете `$container->get(MyService::class)` (или это делает фреймворк через `autowire`), происходит следующее:

1.  **Проверка кэша (Singleton pattern):** Контейнер проверяет внутренний массив `$services`. Если сервис уже был создан ранее, он просто возвращает готовый экземпляр. В Symfony по умолчанию все сервисы — это **Shared services** (синглтоны в рамках одного запроса).
2.  **Создание (Instantiating):** Если сервиса еще нет:
    *   Контейнер берет «рецепт» (`Definition`), который был подготовлен на этапе компиляции.
    *   Он смотрит на список зависимостей для этого рецепта.
    *   **Рекурсивно** вызывает процесс создания всех зависимостей (если им тоже нужны другие сервисы).
    *   Вызывает `new MyService($dep1, $dep2, ...)`.
3.  **Возврат:** Объект сохраняется в массив `$services` и возвращается пользователю.

**Резюме:** 
В рантайме Symfony не «думает» и не «ищет». Она просто выполняет заранее написанный, оптимизированный PHP-код, который говорит: *"Создай объект А, передав в него объект Б, который уже лежит в памяти"*. Это делает DI в Symfony одним из самых быстрых в экосистеме PHP.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

### Рассуждение

Циклическая зависимость (Circular Dependency) — это ситуация, когда `ServiceA` требует `ServiceB`, а `ServiceB` требует `ServiceA`. В контек контейнерах, работающих по принципу построения графа зависимостей, это приводит к бесконечной рекурсии и ошибке `CircularReferenceException`.

Прежде чем предлагать технические «костыли», я всегда задаю себе вопрос: **«Почему это произошло?»**. 
В 90% случаев циклическая зависимость — это симптом архитектурной ошибки. Она сигнализирует о том, что:
1. Ваши сервисы перегружены ответственностью (нарушение SRP).
2. Ваши границы контекстов (Bounded Contexts) размыты.
3. Вы пытаетесь сделать слишком много логики в одном месте.

**Мой алгоритм действий всегда строится так:**
1. **Сначала — рефакторинг (правильный путь).** Попытаться разбить циклическую связку на более мелкие части.
2. **Затем — перенос ответственности.** Выделить третью сущность.
3. **В крайнем случае — технические обходные пути.** Использовать инструменты фреймворка, если рефакторинг невозможен или экономически нецелесообразен.

---

### Финальный ответ

Я разделяю решение этой проблемы на два уровня: стратегический (архитектурный) и тактический (инженерный).

#### 1. Стратегический уровень (Рефакторинг)

Это то, что я делаю в первую очередь. Я ищу способы разорвать цикл, изменив структуру кода.

**А) Выделение третьего сервиса (Extract Class)**
Если `ServiceA` и `ServiceB` зависят друг от друга, скорее всего, у них есть общая логика, которая и вызывает конфликт. Я выделяю эту логику в `ServiceC` и заставляю оба сервиса зависеть от него.

*   *Пример:* `OrderService` вызывает `InvoiceService`, а `InvoiceService` должен обновить статус заказа в `OrderService`. 
*   *Решение:* Создать `OrderStateManager`, который будет отвечать за изменение статусов, и внедрить его в оба сервиса.

**Б) Использование событий (Event Dispatcher) — самый чистый способ**
Вместо того чтобы один сервис вызывал другой напрямую, я использую событийную модель. Это превращает жесткую связь в слабую (loose coupling).

*   *Пример:* `ServiceA` делает что-то и вместо вызова `ServiceB->doSomething()`, просто выбрасывает событие `SomethingHappenedEvent`.
*   *Результат:* `ServiceA` больше ничего не знает о `ServiceB`. `ServiceB` подписывается на это событие. Цикл разорван.

**В) Пересмотр границ (DDD)**
Иногда цикл — это признак того, что два разных доменных контекста (например, `Billing` и `Shipping`) ошибочно смешаны в одном модуле. Я разделяю их, оставляя общение только через интерфейсы или сообщения (Messenger/RabbitMQ).

#### 2. Тактический уровень (Технические решения)

Если рефакторинг невозможен (например, вы работаете с legacy-кодом, где изменение структуры слишком рискованно), я использую инструменты Symfony.

**А) Ленивая инициализация (Lazy Services)**
В Symfony можно пометить зависимость как `lazy`. В этом случае вместо реального объекта в конструктор будет внедрен **Virtual Proxy**.

```php
// В сервисе A
public function __construct(
    #[Autorequire(lazy: true)]
    private ServiceB $serviceB
) {}
```
*Как это работает:* Контейнер создаст прокси-объект для `ServiceB`. Реальный объект `ServiceB` будет создан только в тот момент, когда вы впервые вызовете метод у `$this->serviceB`. Это разрывает цикл при инициализации.

**Б) Использование `ServiceSubscriberInterface` (в Symfony)**
Если сервис — это контроллер или сервис, работающий с другими сервисами, можно внедрять не сами сервисы, а `ContainerInterface` (точнее, его ограниченную версию через `ServiceSubscriberInterface`). Это позволяет запрашивать сервис из контейнера только в момент обращения к нему.

**В) Передача зависимости в метод (Method Injection)**
Если `ServiceB` нужен в `ServiceA` только в одном конкретном методе, я не внедряю его в конструктор, а передаю как аргумент в этот метод.

```php
// Вместо внедрения в конструктор
public function performAction(ServiceB $serviceB): void {
    $serviceB->doSomething();
}
```

**Итог:** Мой приоритет — **Event Dispatcher** или **выделение третьего сервиса**. Я использую **Lazy Services** только как «аварийный выход», когда архитектурная чистота приносится в жертву ради скорости или работы с чужим кодом.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

### Рассуждение

Это классическая задача на проектирование систем с **асинхронным выполнением задач** (Asynchronous Task Processing). 

Основная цель здесь — минимизировать время ответа (latency) для пользователя. Если мы будем отправлять письмо и обновлять индекс (который может быть тяжелой операцией с внешним API типа Elasticsearch) прямо в контроллере, то пользователь будет смотреть на «крутилку» браузера, пока не отработает сетевой запрос к почтовому серверу или поисковому движку. Если один из этих сервисов «приляжет» или будет тормозить, упадет весь процесс регистрации.

Я рассмотрю три варианта реализации: от самого простого (но ненадежного) до промышленного стандарта.

---

### Финальный ответ

Я предложу три архитектурных решения, от простого к сложному.

#### Вариант 1: Процедурный (Синхронный) — **ПЛОХОЙ ПУТЬ**
Выполнение всех задач последовательно в одном запросе.
*   **Реализация:** В контроллере вызывается `$userService->register()`, затем `$mailer->send()` и `$indexer->update()`.
*   **Trade-offs:**
    *   **Pros:** Максимальная простота реализации.
    *   **Cons:** Высокий latency. Если почтовый сервер отвечает 3 секунды, пользователь ждет 3 секунды. Если обновление индекса упадет с ошибкой, транзакция регистрации может откатиться (или наоборот — регистрация пройдет, а индекс не обновится, и мы получим рассинхрон). **Это не подходит для данной задачи.**

#### Вариант 2: Использование Symfony Messenger (Брокер сообщений) — **ОПТИМАЛЬНЫЙ ПУТЬ**
Это стандарт для современной Symfony-разработки. Мы используем паттерн «Сообщение -> Обработчик».

*   **Реализация:**
    1. В сервисе регистрации мы создаем два сообщения: `SendWelcomeEmailMessage` и `UpdateSearchIndexMessage`.
    2. Мы отправляем их в шину (Bus): `$bus->dispatch(new SendWelcomeEmailMessage($user));`.
    3. Symfony Messenger берет эти сообщения и кладет их в транспорт (Transport).
    4. Отдельный процесс (Worker) в фоновом режиме слушает транспорт и выполняет обработчики (`MessageHandler`).

*   **Выбор транспорта:**
    *   Для разработки: `doctrine` (сообщения хранятся в БД).
    *   Для продакшена: `RabbitMQ` или `Redis`.

*   **Trade-offs:**
    *   **Pros:** 
        *   **Мгновенный ответ:** Пользователь получает ответ сразу после сохранения пользователя в БД.
        *   **Отказоустойчивость (Retries):** Если почтовый сервис временно недоступен, Messenger автоматически попробует отправить письмо еще раз через 5, 10, 60 минут.
        *   **Масштабируемость:** Мы можем запустить 10 воркеров для тяжелого индексирования и 2 воркера для легких писем.
    *   **Cons:** Усложняется инфраструктура (нужен брокер сообщений и запущенные воркеры).

#### Вариант 3: Архитектура на основе событий (Domain Events) + Messenger
Это «продвинутый» уровень, который я предпочитаю в проектах с DDD.

*   **Реализация:**
    1. `UserService` не знает о письмах или индексе. Он делает только свою работу: сохраняет пользователя и генерирует доменное событие `UserRegistered`.
    2. В Symfony мы настраиваем `EventSubscriber` или используем Messenger для прослушивания этого события.
    3. На это событие навешано несколько независимых обработчиков (Handlers), каждый из которых отправляет свою асинхронную задачу в шину.

*   **Trade-offs:**
    *   **Pros:** 
        *   **Максимальная слабая связанность (Loose Coupling):** `UserService` вообще не знает, что после регистрации нужно что-то еще делать. Он просто сообщает миру: «Событие произошло!».
        *   **Легкость расширения:** Если завтра придет бизнес и скажет: «Теперь при регистрации нужно еще создать бонусную карту», я просто добавлю новый `Handler`, не трогая код регистрации.
    *   **Cons:** Чуть выше когнитивная нагрузка при отслеживании цепочки событий.

---

### Итоговая рекомендация

Для решения вашей задачи я выберу **Вариант 3**. 

**Технический стек:**
1. **Domain Layer:** Выбрасываем событие `UserRegistered`.
2. **Application Layer:** `UserRegisteredEventHandler` подхватывает событие.
3. **Infrastructure Layer:** Handler отправляет две асинхронные команды в **Symfony Messenger**.
4. **Transport:** Используем **RabbitMQ** (для надежности и гарантии доставки).
5. **Workers:** Запускаем фоновые процессы через `php bin/console messenger:consume`.

Это обеспечит мгновенную реакцию интерфейса, гарантию выполнения задач (через ретраи) и идеальную чистоту кода.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

### Рассуждение

Вопрос затрагивает фундаментальное различие между «кто ты?» (**Authentication**) и «что тебе можно?» (**Authorization**). В Symfony эти процессы разделены, и понимание этой границы — ключ к построению безопасной системы.

Часто разработчики совершают ошибку, пытаяясь запихнуть всю логику проверки прав в роли (например, создавая роли `ROLE_EDIT_USER_DEPARTMENT_5`). Это ведет к взрывному росту количества ролей и невозможности поддерживать систему.

Я рассматриваю контроль доступа как трехслойный пирог:
1. **Authentication (Кто ты?):** Процесс идентификации пользователя (Login, JWT, OAuth).
2. **Role-Based Access Control (RBAC):** Грубая проверка по принадлежности к группе (есть ли у тебя «корочка»?).
3. subject-based Access Control (через **Voters**): Тонкая проверка прав на конкретный объект (можешь ли ты редактировать *именно этот* документ?).

---

### Финальный ответ

В Symfony контроль доступа строится на взаимодействии трех компонентов: **Authenticators**, **Role Hierarchy** и **Voters**.

#### 1. Аутентификация (Authentication)
Это процесс превращения учетных данных (логин/пароль, токен) в объект `User`.
*   В современных версиях Symfony используется компонент `Security` с системой **Authenticators**. 
*   Каждый аутентификатор отвечает за свой способ входа: один для формы логина, другой для JWT-токена в заголовке `Authorization`.
*   Результат успешной аутентификации — объект `Token` (содержащий пользователя), который сохраняется в `TokenStorage`.

#### 2. Роли (Roles)
Роли — это самый простой и грубый инструмент авторизации. Они проверяются через `isGranted('ROLE_ADMIN')`.
*   **Role Hierarchy:** Symfony позволяет выстраивать иерархию (например, `ROLE_ADMIN` включает в себя `ROLE_USER`), что упрощает управление.
*   **Где применять:** Только для глобальных уровней доступа. Например: «Может ли этот человек зайти в админку?», «Может ли этот человек удалять любые статьи?».

#### 3. Voters (Голосующие)
Voters — это мощный инструмент для реализации **Attribute-Based Access Control (ABAC)**. Когда проверка прав зависит от состояния самого объекта (сущности), без Voter не обойтись.

**Как работает Voter:**
При вызове `$this->denyAccessUnlessGranted('EDIT', $article)`, Symfony опрашивает все зарегистрированные вотеры. Каждый вотер получает:
1. **Атрибут** (`EDIT`).
2. **Субъект** (`$article`).
3. **User** (текущий пользователь).

Вотер должен вернуть один из трех ответов: `ACCESS_GRANTED`, `ACCESS_DENIED` или `ACCESS_ABSTAIN` (если вотер не умеет работать с этим типом объекта).

---

### Когда выбирать Voter, а когда Роли?

Это главный архитектурный вопрос. Я использую следующее правило:

#### Выбирай РОЛИ, если проверка статична и глобальна
Если право доступа не зависит от конкретного экземпляра объекта.
*   *Пример:* «Доступ к панели управления», «Право на создание новых пользователей», «Доступ к системным логам».
*   *Проверка:* `if ($user->hasRole('ROLE_ADMIN'))`.

#### Выбирай VOTER, если проверка динамична и зависит от контекста (субъекта)
Если право доступа зависит от владельца объекта, его статуса или связей в базе данных.
*   *Пример:* 
    *   «Может ли пользователь редактировать *этот* пост?» (Проверка: `post.author === user`).
    *   «Может ли менеджер одобрить *этот* заказ?» (Проверка: `order.department === user.department`).
    *   «Может ли пользователь смотреть этот документ?» (Проверка: `document.isPublic === true || document.isSharedWith(user)`).
*   *Проверка:* `$this->isGranted('POST_EDIT', $post)`.

**Пример нарушения (антипаттерн):**
Создавать роль `ROLE_EDIT_POST_123`. Это невозможно масштабировать.

**Пример правильного подхода:**
Создать `PostVoter`, который проверяет:
```php
protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token): bool {
    $user = $token->getUser();
    if (!$user instanceof User) return false;

    return match($attribute) {
        self::EDIT => $subject->getAuthor() === $user || $user->isAdmin(),
        self::VIEW  => $subject->isPublished() || $subject->getAuthor() === $user,
        default => false,
    };
}
```

**Итог:** Роли — это для **групп людей**, Voters — это для **взаимодействия людей с объектами**.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

### Рассуждение

Это фундаментальный вопрос на стыке DDD (Domain-Driven Design) и реализации. В идеальном мире Value Object (VO) — это простая, неизменяемая (immutable) структура данных без идентификатора, которая гарантирует инварианты (валидность) в момент создания.

Проблема в том, что Doctrine ORM «заточена» под работу с сущностями (Entities), которые имеют жизненный цикл и идентификаторы. Она ожидает, что она будет управлять состоянием объектов через рефлексию или сеттеры. Value Objects же не должны иметь сеттеров и не должны зависеть от базы данных.

Когда мы пытаемся сохранить VO, у нас возникает конфликт: **как превратить сложный объект в плоские колонки таблицы и обратно, не нарушая инкапсуляцию?**

Я выделяю три основных способа маппинга, каждый из которых имеет свои компромиссы.

---

### Финальный ответ

В Doctrine существует три основных спосоях хранения Value Objects. Выбор зависит от сложности VO и того, насколько «плоским» вы хотите видеть его в БД.

#### 1. Embeddables (Встроенные объекты) — «Золотой стандарт»
Это нативный механизм Doctrine для реализации VO. Он позволяет разложить свойства объекта по колонкам той же таблицы, в которой лежит Entity.

**Реализация:**
```php
#[ORM\Embeddable]
readonly class Money {
    public function __construct(
        #[ORM\Column(type: 'decimal', precision: 10, scale: 2)]
        public string $amount,
        #[ORM\Column(type: 'string', length: 3)]
        public string $currency,
    ) {
        // Валидация внутри конструктора гарантирует неизменяемость и валидность
        if ($amount <= 0) throw new InvalidArgumentException();
    }
}

#[ORM\Entity]
class Product {
    #[ORM\Embedded(class: Money::class)]
    private Money $price;
}
```

*   **Плюсы:**
    *   **Нативность:** Полная поддержка Doctrine.
    *   **Производительность:** Нет лишних `JOIN`, данные лежат в той же таблице.
    *   **Чистота домена:** VO остается полноценным объектом с логикой и валидацией.
*   **Минусы:**
    *   **Ограниченность:** Нельзя использовать Embeddable, если он должен быть общим для множества разных сущностей с разной структурой (хотя это редкость).
*   **Подводные камни:** При использовании `readonly` свойств в PHP 8.2+ нужно быть внимательным с тем, как Doctrine пытается восстанавливать объект через рефлексию (она обходит конструктор, но в современных версиях это работает корректно).

#### 2. Custom Types (Пользовательские типы) — «Сериализация»
Вы можете создать свой тип (наследуясь от `Doctrine\DBAL\Types\Type`), который будет превращать объект в строку (например, JSON или строку с разделителем) и обратно.

**Реализация:**
Объект `Money` превращается в строку `"100|USD"` в одной колонке `price`.

*   **Плюсы:**
    *   **Компактность:** Одна колонка в БД вместо нескольких.
    *   **Гибкость:** Можно хранить любые сложные структуры, которые не хочется раздувать в таблице.
*   **Минусы:**
    *   **Невозможность поиска/фильтрации:** Вы не сможете сделать SQL-запрос `WHERE price_amount > 100`, так because для БД это просто строка.
    *   **Потеря атомарности:** Вы не можете обновить только валюту, не перезаписав всю строку.
*   **Подводные камни:** Это убивает возможности SQL-агрегации (SUM, AVG). Используйте только для данных, по которым **никогда** не будет поиска.

#### 3. Entity (Превращение VO в Entity) — «Антипаттерн»
Иногда разработчики делают VO сущностью с ID, чтобы «просто работало».

*   **Почему это плохо:** Это нарушает саму суть Value Object. VO не имеет идентичности. Если вы приравняете два объекта с одинаковыми полями, это должен быть один и тот же VO. Если это Entity, то это два разных объекта с разными ID. Это размывает границы домена.

---

### Итоговая таблица выбора

| Критерий | Embeddables | Custom Types (JSON/String) | Entity (Anti-pattern) |
| :--- | :--- | :--- | :--- |
| **Сложность маппинга** | Низкая | Средняя | Низкая |
| **Поиск в SQL** | **Да (полный)** | Нет (только LIKE) | Да |
| **Чистота DDD** | **Высокая** | Высокая | Низкая |
| **Производительность** | Высокая | Высокая (но плохая для Query) | Средняя (JOINs) |

**Мой вердикт:** 
Для большинства бизнес-объектов (Деньги, Адрес, Координаты, Период) я использую **Embeddables**. Это дает идеальный баланс между чистотой доменной модели и мощностью SQL-запросов. Если же объект — это просто метаданные, по которым не будет поиска (например, массив настроек), я использую **Custom Type** с JSON-сериализацией.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

### Рассуждение

Этот вопрос бьет в самую болезненную точку интеграции DDD и ORM. Главный конфликт здесь в том, что **Doctrine мыслит таблицами и связями (Identity)**, а **DDD мыслит агрегатами и границами (Consistency)**.

В DDD Агрегат — это единица целостности. Все изменения внутри агрегата должны быть атомарны. Если мы меняем дочерний элемент, мы фактически меняем состояние всего агрегата. 

**Основные проблемы, которые я вижу:**
1. **Проблема «дырявого» агрегата:** Если мы разрешим менять дочерние сущности напрямую через репозиторий (например, `childRepository->save($child)`), мы нарушим инварианты корня агрегата.
2. **Проблема производительности:** При сохранении большого агрегата Doctrine может начать делать десятки лишних `UPDATE` или `INSERT`.
3. **Проблема транзакционности:** Кто отвечает за то, чтобы изменения в агрегате не застряли «на полпути»?

Я разберу это на примере агрегата **`Order` (Заказ)**, который содержит коллекцию **`OrderItem` (Позиции заказа)**.

---

### Финальный ответ

#### 1. Маппипнг и структура (Инфраструктурный слой)

Чтобы сохранить границы агрегата, мы должны маппить дочерние элементы так, чтобы они были «привязаны» к корню. В Doctrine это делается через `orphanRemoval=true` и `cascade={"persist", "remove"}`.

**Пример реализации:**

```php
// Корень агрегата (Aggregate Root)
#[ORM\Entity]
class Order {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column]
    private string $status;

    /**
     * orphanRemoval=true — КРИТИЧНО. 
     * Если мы удалим элемент из коллекции, Doctrine удалит его из БД.
     * cascade={"persist"} — позволяет сохранять агрегат целиком.
     */
    #[ORM\OneToMany(
        mappedBy: 'order', 
        targetEntity: OrderItem::class, 
        cascade: ['persist', 'remove'], 
        orphanRemoval: true
    )]
    private Collection $items;

    public function __construct() {
        $this->items = new ArrayCollection();
        $this->status = 'new';
    }

    // Бизнес-логика внутри агрегата (Инварианты)
    public function addItem(Product $product, int $quantity): void {
        if ($this->status !== 'new') {
            throw new DomainException("Cannot add items to a processed order");
        }
        
        // Мы не даем снаружи создать OrderItem, мы создаем его сами
        $this->items->add(new OrderItem($this, $product, $quantity));
    }

    public function getItems(): Collection {
        // Возвращаем только для чтения (ReadOnly), чтобы нельзя было сделать $order->getItems()->add(...)
        return $this->items->wrap(); 
    }
}

// Дочерняя сущность (Entity внутри агрегата)
#[ORM\Entity]
class OrderItem {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'items')]
    #[ORM\JoinColumn(nullable: false)]
    private Order $order;

    public function __construct(Order $order, Product $product, int $qty) {
        $this->order = $order;
        // ...
    }
}
```

#### 2. Границы транзакции и вызов `flush()` (Прикладной слой)

Это самый важный архитектурный момент. **Никогда не вызывайте `flush()` внутри доменного сервиса или внутри самого агрегата.**

`flush()` — это инфраструктурная операция. Она должна вызываться на уровне **Application Service (Use Case)**. Именно здесь определяется граница транзакции.

**Правильный паттерн использования:**

```php
class PlaceOrderService { // Application Service
    public function __construct(
        private OrderRepositoryInterface $orderRepository,
        private EntityManagerInterface $entityManager, // Инфраструктурный объект
    ) {}

    public function execute(int $orderId, int $productId, int $qty): void {
        // 1. Открываем транзакцию (если нужно гарантировать атомарность на уровне БД)
        $this->entityManager->beginTransaction();

        try {
            // 2. Загружаем агрегат через репозиторий (только корень!)
            $order = $this->orderRepository->find($orderId);

            // 3. Выполняем бизнес-действие (внутри агрегата проверяются правила)
            $order->addItem($product, $qty);

            // 4. Сохраняем агрегат. 
            // Благодаря cascade="persist", Doctrine сама поймет, что нужно сохранить OrderItem
            $this->orderRepository->save($order);

            // 5. Фиксируем изменения
            $this->entityManager->flush();
            $this->entityManager->commit();

        } catch (\Exception $e) {
            $this->entityManager->rollback();
            throw $e;
        }
    }
}
```

#### 3. Резюме правил организации

1.  **Доступ к дочерним элементам:** Дочерние сущности не должны иметь публичных репозиториев. Вы не должны писать `$orderItemRepository->save($item)`. Все изменения — только через методы `Order->addItem()` или `Order->removeItem()`.
2.  **Управление жизненным циклом:** Используйте `orphanRemoval=true`. Это гарантирует, что если вы удалили элемент из коллекции внутри агрегата, он физически исчезнет из БД при вызове `flush()`.
3.  **Инварианты:** Корень агрегата (`Order`) обязан проверять состояние коллекции перед любым действием.
4.  **Кто вызывает `flush()`:** Только **Application Service** (или Unit of Work в более сложных системах). Репозиторий должен лишь «подготовить» объект к сохранению (`persist`), а `flush` должен закрыть всю транзакцию целиком.
5.  **Транзакции:** Граница транзакции совпадает с границей работы одного Application Service. Один вызов сервиса = одна транзакция = один `flush`.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

### Рассуждение

Проблема N+1 — это классическая ловушка ORM. Она возникает, когда мы загружаем список основных сущностей (1 запрос), а затем в цикле обращаемся к их связанным объектам (N запросов), потомуs Doctrine использует **Lazy Loading** (ленивую загрузку) по умолчанию.

Прежде чем бросаться исправлять код, я никогда не верю «подозрениям». В высоконагруженных системах можно ошибочно принять за N+1 тяжелый запрос к БД, который просто плохо оптимизирован, или за задержку сетевого соединения.

**Мой алгоритм диагностики:**
1.  **Профилирование (Инструменты):** Я не буду гадать. Я использую **Symfony Profiler** (вкладка Doctrine) — он наглядно показывает количество запросов и дубликаты. Если я вижу 50 одинаковых запросов к таблице `user`, это N+1. В продакшене я использую **Blackfire.io** или **Sentry**, чтобы увидеть дерево вызовов и реальные задержки.
2.  **Логирование:** Если профилировщика нет, я включаю `SQL Log` в конфиге Doctrine и смотрю в консоль/логи.
3.  **Анализ кода:** Я ищу циклы `foreach`, внутри которых вызываются геттеры связанных сущностей (например, `$order->getCustomer()->getName()`).

---

### Финальный ответ

Когда проблема подтверждена, я выбираю один из трех способов решения в зависимости от контекста.

#### 1. Eager Loading через JOIN (Fetch Join) — Основной способ
Вместо того чтобы грузить связи по одной, мы просим Doctrine сделать `JOIN` и сразу вытянуть данные в одном запросе.

**Реализация:**
В репозитории я пишу кастомный метод с `leftJoin` и `addSelect`.

```php
// Было (N+1): $repository->findAll();
// Стало (1 запрос):
public function findAllWithCustomers(): array {
    return $this->createQueryBuilder('o')
        ->leftJoin('o.customer', 'c')
        ->addSelect('c') // Ключевой момент: мы заставляем Doctrine заполнить объект c
        ->getQuery()
        ->getResult();
}
```

*   **Плюсы:** Решает проблему полностью за один проход. Высокая производительность.
*   **Минусы:** Если связей слишком много или они «многие-ко-многим», запрос может стать гигантским (Cartesian Product), что перегрузит память БД и PHP.
*   **Trade-off:** Идеально для связей «один-к-одному» или «многие-к-одному». Осторожно с коллекциями (OneToMany).

#### 2. Изменение Fetch Mode в маппинге (Eager Fetching)
Мы можем изменить настройки сущности, чтобы Doctrine *всегда* подгружала связь сразу.

**Реализация:**
```php
#[ORM\ManyToOne(targetEntity: Customer::class, fetch: 'EAGER')]
private Customer $customer;
```

*   **Плюсы:** Очень просто реализовать. Проблема N+1 исчезает автоматически во всем приложении.
*   **Минусы:** **Это опасно.** Теперь эта связь будет грузиться *всегда*, даже там, где она не нужна. Это может привести к скрытому замедлению всей системы (Overfetching).
*   **Trade-off:** Используйте только если эта связь критически нужна в 99% случаев использования данной сущности. Я рекомендую избегать этого в пользу Fetch Join в репозиториях.

#### 3. Использование Partial Objects или DTO (Data Transfer Objects)
Если нам не нужен весь объект (со всеми его тяжелыми полями), а нужны только пара полей (например, `id` и `name`), я не использую сущности вообще.

**Реализация:**
Я пишу запрос, который возвращает массив данных или DTO через конструктор.

```php
public function findOrderSummaries(): array {
    return $this->createQueryBuilder('o')
        ->select('new App\Dto\OrderSummaryDto(o.id, c.name)')
        ->join('o.customer', 'c')
        ->getQuery()
        ->getResult();
}
```

*   **Плюсы:** Самый быстрый способ. Минимальное потребление памяти (не создаются тяжелые объекты Doctrine с их Unit of Work и Identity Map).
*   **Минусы:** Вы получаете простые объекты, а не полноценные Entity. Вы не сможете вызвать на них `flush()` или изменить их состояние и сохранить обратно.
*   **Trade-off:** Идеально для списков, таблиц, отчетов и Read-only моделей (CQRS подход).

---

### Итоговая стратегия выбора

1.  Если это **страница списка** (Read-only) $\rightarrow$ **DTO** (самый быстрый путь).
2.  Если это **бизнес-логика**, где нужны полноценные сущности $\rightarrow$ **Fetch Join** в репозитории.
3.  Если связь **всегда** нужна везде $\rightarrow$ **Eager Fetching** (но с большой осторожностью).

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

### Рассуждение

Это отличный вопрос, который проверяет понимание концепции **"Defense in Depth" (эшелонированной обороны)**. 

Многие разработчики совершают архитектурную ошибку, полагая, что если в коде написаны проверки (например, в сервисе или через Symfony Validator), то база данных — это просто «склад» для хранения данных. Это опасное заблуждение.

Я исхожу из того, что **бизнес-валидация** и **ограничения целостности (Constraints)** решают разные задачи:
1. **Бизнес-валидация (Application level):** Отвечает на вопрос «Соответствует ли это действие правилам бизнеса?». Она может быть сложной, зависеть от внешних API, контекста сессии или временных условий. Она дает пользователю понятные сообщения об ошибках.
2. **Ограничения целостности (Database level):** Отвечают на вопрос «Являются ли эти данные корректными с точки зрения структуры и неизменности системы?». Это последний рубеж обороны.

**Почему нельзя полагаться только на код?**
*   **Race Conditions (Состояние гонки):** Два параллельных запроса могут пройти бизнес-валидацию одновременно. Например, оба проверяют «хватит ли денег на счету», оба получают `true`, и оба списывают деньги, уводя баланс в минус. БД (через `CHECK` или `UNIQUE`) остановит это.
*   **Прямой доступ к БД:** Кто-то может запустить миграцию, скрипт импорта или залезть через консоль. Без ограничений в БД мы рискуем получить «мусорные» данные.
*   **Ошибки в коде:** Человеческий фактор. Кто-то может забыть вызвать валидатор в новом сервисе или написать некорректный Unit-тест.

---

### Финальный ответ

Я использую ограничения в PostgreSQL как **последний рубеж защиты**, который гарантирует структурную целостность данных, даже если слой приложения даст сбой.

#### Какие средства я использую и когда:

**1. Primary Keys & Unique Constraints (Уникальность)**
*   **Когда:** Всегда. Это база.
*   **Зачем:** Чтобы избежать дубликатов (например, два пользователя с одним email). Даже если в коде стоит проверка `if ($repo->findByEmail($email))`, в высоконагруженной системе между проверкой и записью может проскочить второй запрос. `UNIQUE constraint` на уровне БД гарантирует, что запись не будет создана.

**2. Foreign Keys (Ссылочная целостность)**
*   **Когда:** Всегда при связях между таблицами.
*   **Зачем:** Чтобы не возникло «сиротских» записей. Если мы удаляем пользователя, БД должна либо запретить это (RESTRICT), либо каскадно удалить связанные данные (CASCADE), либо установить `NULL`. Это предотвращает ситуацию, когда `order.user_id` ссылается на несуществующего пользователя.

**3. NOT NULL Constraints (Обязательность)**
*   **Когда:** Для всех полей, которые не могут быть пустыми по логике системы.
*   **Зачем:** Это защита от ошибок маппинга и пропущенных данных в коде. Если поле `email` критично, оно должно быть `NOT NULL` в БД.

#### 4. Check Constraints (Бизнес-инварианты на низком уровне)**
Это более продвинутый инструмент, который я применяю для критически важных правил.
*   **Когда:** Когда инвариант должен быть соблюден абсолютно всегда, независимо от того, откуда приходят данные.
*   **Примеры:**
    *   `balance >= 0` (баланс не может быть отрицательным).
    *   `price > 0` (цена не может быть нулевой или отрицательной).
    *   `status IN ('new', 'paid', 'shipped')` (строгая проверка перечисления).
*   **Зачем:** Это защита от «гонки условий» (race conditions) и ошибок в расчетах.

**5. Triggers (Триггеры) — с большой осторожностью**
*   **Когда:** Для сложной автоматизации, которую невозможно эффективно реализовать на уровне приложения (например, сложные аудиторские логи или автоматическое обновление агрегированных данных в других таблицах).
*   **Зачем:** Обеспечение целостности при массовых операциях.
*   **Trade-off:** Я стараюсь их избегать, так как они скрывают логику от разработчика (магия в БД) и усложняют отладку.

#### Итоговая стратегия:

| Уровень | Инструмент | Задача |
| :--- | :--- | :--- |
| **Application** | Symfony Validator / Domain Logic | Показать пользователю красивую ошибку: *"Ваш баланс слишком мал"* |
| **Database** | `UNIQUE`, `FK`, `CHECK` | Гарантировать, что в БД никогда не попадет: `balance = -500` или `user_id = NULL` |

**Мой принцип:** Приложение — это «умная» часть, которая управляет процессом. База данных — это «строгий» контролер, который гарантирует, что правила системы не будут нарушены физически.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

### Рассуждение

Когда запрос работает медленно, моя первая задача — перестать гадать и перейти к доказательной базе. Проблема может быть на трех уровнях: **Схема данных (индексы/структура)**, **Сам запрос (логика/JOIN-ы)** или **Ресурсы сервера (CPU/IO/Memory)**.

Я не начинаю с переписывания кода. Я следую методологии: **Сбор метрик $\rightarrow$ Планирование выполнения $\rightarrow$ Анализ узких мест $\rightarrow$ Гипотеза $\rightarrow$ Тестирование $\rightarrow$ Валидация.**

---

### Финальный ответ

Мой процесс диагностики и оптимизации строится по четкому алгоритму.

#### 1. Инструментарий и сбор данных
Первым дестом я смотрю, *что именно* тормозит.
*   **`EXPLAIN (ANALYZE, BUFFERS)`:** Это мой главный инструмент. `EXPLAIN` показывает план выполнения, а `ANALYZE` — реальное время выполнения и количество прочитанных страниц (buffers). Без `BUFFERS` я не пойму, уперлись мы в диск (I/O) или в память.
*   **`pg_stat_statements`:** Если проблема плавающая, я использую это расширение. Оно позволяет увидеть статистику по всем запросам в системе: сколько времени они занимают в сумме, как часто вызываются и какой у них средний план.
*   **System Monitoring (Prometheus/Grafnet/CloudWatch):** Чтобы понять, не забита ли полоса пропускания диска (IOPS) или не закончилась ли оперативная память (что вызывает Swapping).
*   **PostgreSQL Slow Query Log:** Для вылова запросов, которые не попадают в текущий фокус, но тормозят систему в целом.

#### 2. Что я ищу в плане выполнения (Execution Plan)
При анализе `EXPLAIN ANALYZE` я ищу следующие «красные флаги»:
*   **Seq Scan (Sequential Scan):** Полное сканирование таблицы. Если таблица большая — это почти всегда признак отсутствия нужного индекса.
*   **Bitmap Heap Scan:** Часто это промежуточный этап, но если он слишком тяжелый, значит, индекс не очень эффективен.
*   **Nested Loop на больших объемах:** Если PostgreSQL выбирает `Nested Loop` для соединения двух огромных таблиц вместо `Hash Join` или `Merge Join`, это признак неверной статистики.
*   **Disk Spills (External Merge/Sort):** Если я вижу, что сортировка или Hash Join выходят за пределы `work_mem` и сбрасываются на диск, запрос будет работать в десятки раз медленнее.
*   **Costly Estimates:** Если `estimated rows` сильно отличается от `actual rows`, значит, статистика базы устарела.

#### 3. Типовые причины и способы решения

Я классифицирую решения по четырем направлениям:

**А) Проблемы с индексами (Самое частое)**
*   **Причина:** Отсутствие индекса на колонках в `WHERE`, `JOIN` или `ORDER BY`.
*   **Решение:** Создание B-tree индексов. Если поиск идет по части строки — `GIN` или `trigram` индексы. Если важна сортировка или фильтрация по диапазону — `BRIN` индексы (для очень больших таблиц).
*   **Нюанс:** Я всегда проверяю, не мешают ли существующие индексы (избыточность), так как они замедляют `INSERT/UPDATE`.

**Б) Проблемы со структурой запроса**
*   **Причина:** Использование функций над индексированными колонками (например, `WHERE DATE(created_at) = '2023-01-01'`). Это делает индекс бесполезным (SARGability issue).
*   **Решение:** Переписать запрос так, чтобы функция применялась к значению, а не к колонке: `WHERE created_at >= '2023-01-01' AND created_at < '2023-01-02'`.
*   **Причина:** Слишком много `JOIN` или `DISTINCT`, которые вызывают тяжелые сортировки.
*   **Решение:** Оптимизация подзапросов или использование оконных функций (`Window Functions`).

**В) Проблемы с настройкой БД (Configuration)**
*   **Причина:** Маленький `work_mem` (сортировки на диске) или `shared_buffers` (недостаточно кэша).
*   **Решение:** Тюнинг конфигурации PostgreSQL под конкретное железо.
*   **Причина:** Устаревшая статистика.
*   **Решение:** Запуск `ANALYZE` для обновления статистики планировщика.

**Г) Проблемы с планировщиком (Plan Instability)**
*   **Причина:** Неверный выбор плана из-за коррелированных данных.
*   **Решение:** Использование `CREATE STATISTICS` для создания многоколоночной статистики, чтобы планировщик лучше понимал зависимости между колонками.

#### Резюме процесса:
Если запрос тормозит, я сначала смотрю `EXPLAIN ANALYZE`. Если вижу `Seq Scan` — добавляю индекс. Если вижу `Disk Spill` — увеличиваю `work_mem`. Если вижу неверный план — обновляю статистику или переписываю запрос. И только в самом конце, если ничего не помогает, я иду в архитектуру (денормализация, партиционирование или шардирование).

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

### Рассуждение

Вопрос об агрегатах — это проверка понимания того, как управлять **сложностью и консистентностью** в больших системах. 

Частая ошибка — воспринимать агрегат как «группу связанных таблиц». Это не так. Агрегат — это не про базу данных, это про **бизнес-правила (инварианты)**. Если вы определяете агрегат исходя из структуры БД, вы получите «хрупкую» модель, которая развалится, как только бизнес-логика усложнится.

Я определяю агрегат через вопрос: **«Какие изменения должны быть атомарными (неделимыми) с точки зрения бизнеса?»**. Если изменение объекта А требует немедленного и обязательного изменения объекта Б, чтобы система не вошла в противоречивое состояние — они должны быть в одном агрегате.

---

### Финальный ответ

**Агрегат (Aggregate)** — это кластер связанных объектов (сущностей и Value Objects), которые рассматриваются как единое целое для изменения данных. У агрегата всегда есть **Корень (Aggregate Root)** — единственная точка входа, через которую внешние объекты могут взаимодействовать с содержимым агрегата.

#### Как я определяю границы агрегата?

Я использую три критерия:

1.  **Инварианты (Consistency):** Главный критерий. Если для соблюдения правила «Сумма всех позиций заказа не может превышать лимит кредита клиента» мне нужно гарантировать атомарность, то `Order` и `OrderItems` должны быть в одном агрегате.
2.  **Жизненный цикл:** Если дочерние объекты не имеют смысла вне родителя (например, `OrderItem` не существует без `Order`), они — часть агрегата.
3.ty **Транзакционность:** Граница агрегата — это граница одной транзакции. В идеале одна транзакция должна изменять только один агрегат.

---

#### Пример: Система управления онлайн-магазином

**Агрегат: `Order` (Заказ)**

*   **Aggregate Root:** `Order` (сущность).
*   **Внутренние элементы:** `OrderItem` (сущность), `ShippingAddress` (Value Object), `Money` (Value Object).
*   **Граница:** Когда мы добавляем товар в заказ, мы вызываем `$order->addItem($product, $quantity)`. Внутри этого метода `Order` проверяет: «Не превышен ли общий вес заказа?», «Не изменилась ли общая сумма?». 
*   **Почему это агрегат?** Потому что мы не можем изменить вес одного `OrderItem`, не изменив общее состояние `Order`. Изменение должно быть атомарным.

**Другой агрегат: `Product` (Товар)**
*   **Root:** `Product`.
*   **Внутренние элементы:** `Price`, `Description`.
*   **Связь:** `Order` и `Product` связаны только через `ProductId`. `Order` **не содержит** в себе объект `Product`, он хранит только его ID.

---

#### Типовая ошибка: «Раздутый агрегат» (The Fat Aggregate)

Самая частая ошибка — попытка включить в один агрегат всё, что кажется «связанным».

**Ошибка:** Попытка объединить `Order`, `OrderItem`, `Customer` и `Product` в один огромный агрегат.

**Почему это плохо:**
1.  **Проблемы конкурентности (Concurrency):** Если два менеджера одновременно пытаются изменить разные заказы, но оба заказа ссылаются на одного и того же `Customer`, который включен в агрегат, они могут столкнуться с конфликтом версий (Optimistic Locking), хотя фактически они не трогают одни и те же данные.
2.  **Производительность:** При загрузке одного `Order` вам придется выкачивать из БД всю цепочку: клиента, его историю, описание товаров и т.д. Это превращается в огромный, тяжелый объект.
3.  **Нарушение границ:** Агрегат становится слишком сложным для понимания и тестирования.

**Как правильно:**
`Order` должен ссылаться на `Customer` только через `CustomerId`. Если вам нужно узнать имя клиента для отображения в заказе, вы либо делаете это через отдельный запрос, либо (в высоконагруженных системах) дублируете минимально необходимые данные (денормализация) в рамках `Order`.

**Золотое правило:** 
> **Связывайте агрегаты только по ID, а не по ссылкам на объекты.** Это обеспечивает слабую связность и позволяет масштабировать систему.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

### Рассуждение

Это классическая проблема конкурентного доступа в распределенных системах. Если два процесса (например, два разных HTTP-запроса или два воркера) одновременно считывают состояние агрегата, изменяют его в памяти и пыта пытаются сохранить обратно, возникает состояние гонки (**Race Condition**).

Если мы не будем ничего с этим делать, произойдет **Lost Update (Потерянное обновление)**:
1. Процесс А считывает `Order(status: 'new', total: 100)`.
2. Процесс Б считывает `Order(status: 'new', total: 100)`.
3. Процесс А добавляет товар и сохраняет `Order(status: 'new', total: 150)`.
4. Процесс Б меняет адрес доставки и сохраняет `Order(status: 'new', total: 100)`.
**Итог:** Изменение суммы (150) было перезаписано старым значением (100). Данные повреждены.

Я рассматриваю две стратегии решения: **Pessimistic Locking** (Пессимистичная блокировка) и **Optimistic Locking** (Оптимистичная блокировка).

---

### Финальный ответ

Я выбираю стратегию в зависимости от вероятности конфликтов и требований к производительности.

#### 1. Optimistic Locking (Оптимистичная блокировка) — Мой основной выбор
Я предполагаю, что конфликты случаются редко. Мы не блокируем базу данных, а проверяем, не изменился ли объект, пока мы с ним работали.

**Как это работает в Doctrine:**
Мы добавляем специальное поле `version` (обычно `integer`) в сущность.

```php
#[ORM\Entity]
class Order {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Version] // Магия Doctrine
    #[ORM\Column(type: 'integer')]
    private int $version;
}
```

**Процесс:**
1. Процесс А считывает `Order` с `version = 1`.
2. Процесс Б считывает `Order` с `version = 1`.
3. Процесс А сохраняет изменения. SQL: `UPDATE orders SET total = 150, version = 2 WHERE id = 1 AND version = 1`. Успешно.
4. Процесс Б пытается сохранить. SQL: `UPDATE orders SET address = '...', version = 2 WHERE id = 1 AND version = 1`.
5. **Результат:** БД возвращает `0 affected rows`, так как `version` уже равна `2`. Doctrine выбрасывает `OptimisticLockException`.

**Trade-offs:**
* **Pros:** Высокая производительность (нет блокировок на уровне БД), масштабируемость.
* **Cons:** При высокой частоте конфликтов пользователям придется постоянно получать ошибки и повторять действия.

#### 2. Pessimistic Locking (Пессимистичная блокировка)
Если конфликты происходят постоянно (например, в высоконагруженном банковском приложении при списании средств), я использую блокировки на уровне БД.

**Как это работает:**
Мы используем SQL-команду `SELECT ... FOR UPDATE`.

```php
// В репозитории
public function findForUpdate(int $id): ?Order {
    return $this->createQueryBuilder('o')
        ->where('o.id = :id')
        ->setParameter('id', $id)
        ->getQuery()
        ->setLockMode(\Doctrine\DBAL\LockMode::PESSIMISTIC_WRITE)
        ->getOneOrNullResult();
}
```

**Процесс:**
1. Процесс А вызывает `findForUpdate`. БД блокирует строку.
2. Процесс Б вызывает `findForUpdate` для той же строки. **Процесс Б замирает (ждет)** на уровне БД, пока Процесс А не завершит транзакцию (`commit` или `rollback`).

**Trade-offs:**
* **Pros:** Гарантирует, что конфликт не возникнет (процессы выстраиваются в очередь).
* **Cons:** Резкое снижение пропускной способности (throughput). Риск **Deadlocks** (взаимных блокировок), если процессы блокируют ресурсы в разном порядке.

---

### Моя инженерная стратегия (Best Practices)

При проектировании я придерживаюсь следующих правил:

1.  **По умолчанию — Optimistic Locking.** Для 95% бизнес-задач (заказы, профили, контент) этого достаточно. Я обрабатываю `OptimisticLockException` на уровне Application Service: либо пробрасываю ошибку пользователю («Данные были изменены другим пользователем, обновите страницу»), либо (если это фоновый процесс) делаю автоматический **Retry** (повторную попытку).
2.  **Для критических финансовых операций — Pessimistic Locking.** Если мы работаем с балансом кошелька, где потеря даже одного цента недопустима, а конкуренция за одну запись высока, я использую `PESSIMISTIC_WRITE`.
3.  **Уменьшение области конфликта.** Я проектирую агрегаты так, чтобы они были как можно меньше. Чем меньше агрегат, тем меньше вероятность, что два процесса наткнутся на него одновременно.
4.  **Использование Idempotency Keys.** В API я всегда требую `Idempotency-Key` для мутирующих запросов. Это позволяет безопасно повторять запрос (Retry) при ошибках сети или конкуренции, не создавая дубликатов.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

### Рассуждение

Вопрос о доменных событиях (Domain Events) — это вопрос о переходе от **командно-ориентированной** архитектуры (где один сервис вызывает другой) к **событийно-ориентированной** (где сервисы реагируют на факты).

Многие путают доменные события с техническими событиями (например, `UserRegistered` в системе аутентификации). Важно понимать: **Доменное событие — это свершившийся факт в прошлом**, который имеет значение для бизнеса. Оно описывает *что произошло*, а не *что нужно сделать*.

Я разделяю применение событий на два уровня: **внутри процесса** (In-process) и **между процессами** (Out-of-process/Distributed).

---

### Финальный ответ

#### 1. Когда публиковать события?
Событие должно публиковаться **только после того, как агрегат перешел в новое валидное состояние** и готов к сохранению.

*   **Правильно:** Изменить состояние `Order` $\rightarrow$ Добавить событие `OrderPaid` в коллекцию событий агрегата $\rightarrow$ Сохранить агрегат $\rightarrow$ Опубликовать события.
*   **Неправильно:** Публиковать событие *до* сохранения в БД. Если транзакция откатится, событие уже «улетело» (например, в RabbitMQ), и мы получим несогласованность: письмо отправлено, а заказ в базе не оплачен.

#### 2. Как обрабатывать?

Я использую два подхода в зависимости от сложности:

**А) Внутри одного процесса (Synchronous/In-process):**
Используется для поддержания целостности внутри одного агрегата или связанных сущностей в рамках одной транзакции.
*   *Инструмент:* Symfony EventDispatcher.
*   *Пример:* Когда `Order` меняет статус, он вызывает внутренний обработчик, который обновляет `Inventory`.

**Б) Между процессами (Asynchronous/Distributed):**
Используется для связи между разными микросервисами или тяжелых задач.
*   *Инструмент:* Symfony Messenger + RabbitMQ/Redis.
*   *Пример:* После оплаты заказа сервис `Order` публикует сообщение в очередь. Сервис `Email` и сервис `Analytics` подхватывают его независимо.

#### 3. Какие проблемы решает и какие создает?

| Проблема | Решение через события |
| :---s | :--- |
| **Tight Coupling (Связность)** | Сервис `Order` больше не знает о существовании сервиса `Email`. Он просто говорит: «Я оплачен». |
| **Side Effects (Побочные эффекты)** | Логика уведомлений или аналитики вынесена из основного бизнес-процесса, что упрощает тестирование и чтение кода. |
| **Scalability (Масштабируемость)** | Мы можем масштабировать обработчики (воркеры) независимо от основного приложения. |

**Но подход создает новые сложности:**
*   **Eventual Consistency (Согласованность в конечном счете):** Система не будет обновлена мгновенно во всех местах. Это нужно учитывать в UI (например, показывать пользователю «Заказ обрабатывается»).
*   **Complexity (Сложность отладки):** Трассировать цепочку событий, разбросанных по разным сервисам и очередям, гораздо сложнее, чем обычный вызов метода.
*   **Idempotency (Идемпотентность):** События могут прийти дважды (из-за сетевых сбоев или ретраев). Обработчик **обязан** уметь обрабатывать одно и то же событие много раз без дублирования действий.

#### 4. Связь с транзакциями (Transactional Outbox Pattern)

Это самая критическая техническая часть. Как гарантировать, что и БД обновится, и событие в очередь уйдет?

**Проблема:** Если мы сначала делаем `commit` в БД, а потом отправляем сообщение в RabbitMQ, и в этот момент сеть падает — событие потеряно. Если наоборот — мы можем отправить событие для операции, которая не прошла в БД.

**Мое решение: Паттерн Transactional Outbox.**
Вместо того чтобы отправлять сообщение напрямую в RabbitMQ, я сохраняю его в ту же самую базу данных в специальную таблицу `outbox_messages` **в рамках той же транзакции**, что и основной агрегат.

1.  `BEGIN TRANSACTION`
2.  `UPDATE orders SET status = 'paid' ...`
3.  `INSERT INTO outbox_messages (event_type, payload) VALUES ('OrderPaid', '...')`
4.  `COMMIT`

Затем отдельный процесс (Relay) читает таблицу `outbox_messages`, отправляет сообщения в брокер и удаляет их оттуда после подтверждения доставки. Это гарантирует доставку **At-least-once** (как минимум один раз).

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

### Рассуждение

Эти вопросы касаются фундамента, на котором строится вся методология DDD. Если здесь допустить ошибку, вся дальнейшая архитектура (агрегаты, репозитории, сервисы) будет построена на песке.

Различие между Entity и Value Object — это не вопрос «сложности» объекта, а вопрос **идентичности**. 
*   Если два объекта можно считать разными, даже если их поля идентичны — это **Entity**. 
*   Если два объекта считаются одинаковыми, если их поля одинаковы — это **Value Object**.

Что касается **Ubiquitous Language (Единого языка)**, это не просто «словарь терминов». Это инструмент устранения когнитивного диссонанса между бизнесом и разработкой. Если бизнес говорит «Заказ отменен», а в коде у нас метод `setStatus(0)`, — мы провалили проектирование.

---

### Финальный ответ

#### 1. Entity vs Value Object

Я разделяю их по трем ключевым критериям: **Идентичность, Изменяемость и Сравнение**.

| Критерий | Entity (Сущность) | Value Object (Объект-значение) |
| :--- | :--- | :---вый |
| **Идентичность** | Имеет уникальный ID (Identity), который не меняется на протяжении жизни. | Не имеет ID. Идентичность определяется набором его свойств. |
| **Изменяемость** | **Mutable**. Состояние может меняться, но объект остается тем же самым. | **Immutable**. Любое изменение — это создание нового объекта. |
| **Сравнение** | Сравнивается по ID (`$a->getId() === $b->getId()`). | Сравнивается по значениям свойств (`$a->equals($b)`). |

**Пример:**
*   **User** — это `Entity`. Если пользователь сменил фамилию, он остается тем же самым пользователем (тот же ID).
*   **Address** — это `Value Object`. Если изменилась улица, это уже другой адрес. Мы не «редактируем» старый адрес, мы заменяем один объект адреса на другой.

#### 2. Как я принимаю решение (Decision Process)

Когда я проектирую новую концепцию, я задаю себе три вопроса:

1.  **Нужен ли этому объекту жизненный цикл?** Если объекту важно «прожить» в системе (создаться, измениться, удалиться), сохраняя связь с другими объектами — это `Entity`.
2.  **Важен ли нам этот объект как самостоятельная единица?** Если нам важно, *кто именно* это сделал (ID) — это `Entity`. Если нам важно только *что* было сделано (значение) — это `Value Object`.
3.  **Могут ли два таких объекта быть равны?** Если я создам два объекта `Money(100, 'USD')` в разных частях системы, и они должны вести себя идентично — это `Value Object`.

#### 3. Единый язык (Ubiquitous Language)

**Ubiquitous Language** — это общий, живой язык, на котором общаются разработчики, эксперты предметной области (Domain Experts) и стейкхолдеры. Он используется везде: в обсуждениях, в требованиях, в документации и, самое главное, **в коде**.

**Как он влияет на код:**

*   **Именование (Naming):** Если бизнес говорит «Заказ перешел в стадию доставки», в коде должен быть метод `$order->ship()`, а не `$order->setStatus(Status::SHIPPED)`. Мы переносим *смысл* действия в имя метода.
*   **Границы (Bounded Contexts):** Язык может меняться в зависимости от контекста. Слово «Пользователь» в контексте `Identity` (логин/пароль) и в контекте `Shipping` (адрес доставки/телефон) — это разные концепции. Это заставляет нас разделять модели.
*   **Снижение когнитивной нагрузки:** Когда я читаю код, я читаю бизнес-процесс, а не техническую реализацию. Код становится самодокументированным.

**Пример влияния:**
*   **Плохо (Технический язык):** `UserMapper::mapToDto($userEntity);` (Мы говорим о маппинге данных).
*   **Хорошо (Единый язык):** `UserPresenter::present(User $user);` (Мы говорим о представлении пользователя пользователю).

**Мой принцип:** Если я не могу объяснить логику метода, используя термины, которые использует бизнес-эксперт, значит, мой код не отражает реальность, и я должен пересмотреть модель.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

### Рассуждение

Когда мы говорим о Чистой архитектуре (Clean Architecture) или Гексагональной архитектуре, мы говорим о **разделении ответственности**. Главная цель — сделать так, чтобы бизнес-логика (ядро) ничего не знала о деталях реализации (базе данных, фреймворке, внешних API).

Основная ошибка при реализации — когда разработчик начинает внедрять сущности Doctrine (с их аннотациями и связями) в доменный слой. В этот момент «чистота» исчезает, и бизнес-логика становится заложником конкретной библиотеки.

Я использую классическое разделение на слои, где **зависимости всегда направлены внутрь, к центру**.

---

### Финальный ответ

В моей реализации типичное приложение делится на четыре основных слоя.

#### 1. Схема слоев

**Слой 1: Domain (Ядро / Entity Layer)**
Это центр системы. Здесь живут правила бизнеса.
*   **Что лежит:** `Entities` (Агрегаты), `Value Objects`, `Domain Exceptions`, `Domain Events`, и `Repository Interfaces` (только интерфейсы!).
*   **Зависимости:** **Ноль.** Этот слой не зависит ни от чего. Он не знает ни о Symfony, ни о Doctrine, ни о чем-либо еще. Это чистый PHP.

**Слой 2: Application (Use Case Layer)**
Здесь описывается, *что* приложение делает. Это оркестратор.
*   **Что лежит:** `Use Case` (или `Service`), `DTO` (Data Transfer Objects) для входа/выхода, `Command/Query` (если используем CQRS).
*   **Логика:** Здесь нет бизнес-правил (они в Domain), здесь только координация: «взять агрегат из репозитория $\rightarrow$ вызвать метод агрегата $\rightarrow$ сохранить агрегат».
*   **Зависимости:** Только от слоя **Domain**.

**Слой 3: Infrastructure (Слой реализации)**
Здесь живут детали.
*   **Что лежит:** Реализации репозиториев (Doctrine), клиенты для внешних API (Guzzle), интеграция с очередями, реализация почтовых сервисов.
*   **Зависимости:** От слоя **Application** (чтобы реализовать интерфейсы) и от слоя **Domain**.

**Слой 4: User Interface / Presentation (Входные точки)**
То, через что пользователь взаимодействует с системой.
*   **Что лежит:** `Symfony Controllers`, `CLI Commands`, `API Endput/Resources`.
*   **Зависимости:** От слоя **Application** (вызывают Use Case) и от слоя **Infrastructure** (иногда, для маппинга запросов).

---

#### 2. Размещение конкретных компонентов

*   **Symfony-контроллер:** Слой **Presentation**. Его задача — принять HTTP-запрос, превратить его в DTO и передать в `Application Service`. Он не должен содержать логику.
*   **Doctrine (EntityManager, Repositories):** Слой **Infrastructure**. Сами сущности, размеченные атрибутами `#[ORM\Entity]`, технически находятся в слое Infrastructure (или в отдельном слое `Persistence`), чтобы не загрязнять чистый Domain.
*   **Обработчик очереди (Message Handler):** Слой **Infrastructure**. Это техническая деталь доставки сообщения. Он вызывает `Application Service`, точно так же, как это делает контроллер.

#### 3. Правило зависимостей (Dependency Rule)

**Зависимости всегда направлены внутрь.**
`Presentation` $\rightarrow$ `Application` $\rightarrow$ `Domain`.
`Infrastructure` $\rightarrow$ `Application` $\rightarrow$ `Domain`.

**Важное уточнение:** Чтобы слой `Application` мог работать с базой данных, не зная о Doctrine, мы используем **Dependency Inversion**. Мы объявляем интерфейс `UserRepositoryInterface` в слое `Domain`, а реализуем его в слое `Infrastructure`. Контейнер Symfony связывает их во время выполнения.

#### 4. Как следить за нарушением границ?

Чтобы архитектура не превратилась в «спагетти» со временем, я использую три метода:

1.  **Статический анализ (PHPStan/Psalm):** Я настраиваю строгие правила. Но еще лучше — использование специализированных расширений, которые проверяют зависимости между пространствами имен.
2.  **Архитектурные тесты (Deptrac):** Это мой любимый инструмент. **Deptrac** позволяет мне прописать правила в YAML-файле: «Слой Domain не может импортировать ничего из слоя Infrastructure». Если кто-то добавит `use Doctrine\ORM...` в доменный класс, тест упадет на CI.
3.  **Code Review:** Это последний рубеж. Я всегда проверяю, не «протекли» ли детали реализации в бизнес-логику. Если я вижу в `Domain Service` тип `Request` или `EntityManagerInterface` — это непроходимый ревью.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

### Рассуждение

Вопрос тестирования — это вопрос о балансе между **уверенностью** (confidence) и **скоростью обратной связи** (feedback loop). 

Если мы будем писать только интеграционные тесты (которые дергают БД и сеть), наши тесты станут «хрупкими» (flaky) и очень медленными. Если напишем только Unit-тесты, мы рискуем получить идеальный код, который падает в рантайме из-за ошибки в конфигурации Symfony или SQL-запросе.

Я придерживаюсь классической **Пирамиды тестирования**, но с поправкой на специфику Symfony и реальный опыт: в современных приложениях слой интеграционных тестов часто расширяется, так как стоимость написания Unit-тестов для чистого домена иногда перевешивает пользу, если домен очень прост.

---

### Финальный ответ

#### 1. Стратегия: Пирамида тестирования

Я распределяю усилия следующим образом:

**А) Unit-тесты (Основание пирамиды — ~70%)**
*   **Что тестируем:** Чистую бизнес-логику в `Domain Layer` (Value Objects, Entities, Domain Services).
*   **Как:** Тестируем поведение объектов в изоляции.
*   **Мокание:** Здесь мы **ничего не мокаем**, кроме если это действительно внешняя зависимость (например, математический сервис). Мы создаем реальные объекты.

**Б) Integration Tests (Середина — ~20%)**
*   **Что тестируем:** Взаимодействие компонентов Symfony и работу с БД.
*   **Как:** Тестируем `Repository` (реальный SQL), `Command Handlers`, `Service` с внедренными зависимостями.
*   **Мокание:** Здесь мы **мокаем внешние API** (HTTP-клиенты), но **не мокаем базу данных**. Мы используем реальную PostgreSQL (в Docker), чтобы убедиться, что наши SQL-запросы и маппинг Doctrine верны.

**В) Functional/E2E Tests (Вершина — ~10%)**
*   **Что тестируем:** Полный жизненный цикл запроса (HTTP Request $\rightarrow$ Controller $\rightarrow$ DB $\rightarrow$ Response).
*   **Как:** Используем `WebTestCase` в Symfony. Проверяем, что после `POST /api/order` статус ответа 201 и в БД появилась запись.
*   **Мокание:** Мокаем только внешние системы (платежные шлюзы, почтовые сервисы), чтобы тесты не зависели от интернета.

---

#### 2. Что мокать, а что нет? (Золотое правило)

Моё правило: **«Мокай то, что ты не контролируешь, и не мокай то, что контролируешь»**.

*   **НЕ МОКАТЬ:**
    *   **Базу данных.** Мокать репозиторий в интеграционном тесте — это бесполезно, вы тестируете свой мок, а не реальную работу с данными.
    *   **Value Objects и Entities.** Они просты и предсказуемы.
    *   **Внутренние сервисы (Domain/Application).** Если вы тестируете Use Case, используйте реальные доменные объекты.

*   **МОКАТЬ (или использовать Stub/Spy):**
    *   **Внешние API (HTTP-клиенты).** Никогда не ходите в реальный Stripe или Twilio во время тестов.
    *   **Файловая система / Cloud Storage (S3).** Используйте `vfsStream` или мок-объект.
    *   **Системное время.** Если логика зависит от текущей даты, я внедряю `ClockInterface` (PSR-20), чтобы в тестах можно было «заморозить» время.

---

#### 3. Как поддерживать тесты быстрыми и стабильными?

Чтобы тесты не превратились в ад, я применяю следующие практики:

1.  **Использование SQLite в памяти (с осторожностью) или отдельной БД в Docker:** 
    *   Для интеграционных тестов я использую отдельную БД в Docker. SQLite — это быстро, но она не поддерживает специфичные фичи PostgreSQL (JSONB, сложные типы), что создает ложное чувство безопасности.
2.  **Database Transactions (Transaction Rollback):**
    *   В Symfony `KernelTestCase` я оборачиваю каждый тест в транзакцию и делаю `rollback` в конце (`$this->entityManager->rollback()`). Это позволяет не очищать БД через `TRUNCATE` (что очень медленно) и гарантирует, что тесты не влияют друг на друга.
3.  **Параллельный запуск:**
    *   Я использую инструменты вроде `ParaTest`, чтобы запускать тесты в несколько потоков. Это сокращает время выполнения в разы.
4.  **Избегание «Flaky Tests» (нестабильных тестов):**
    *   Никогда не используйте `sleep()`. Если нужно дождаться асинхронного процесса, используйте `retry` логику или проверяйте состояние БД в цикле с таймаутом.
    *   Всегда делайте тесты **детерминированными**: используйте фиксированные даты и исключайте зависимость от случайных чисел (используйте Seed для Random).

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

### Рассуждение

Это классическая задача на управление конкурентным доступом (Concurrency Control). Когда два процесса одновременно читают, изменяют и записывают одни и те те же данные, возникает риск нарушения целостности данных.

Основная проблема здесь — **Lost Update (Потерянное обновление)**. 
Представим сценарий:
1. Пользователь А считывает баланс (100$).
2. Пользователь Б считывает баланс (100$).
3. Пользователь А прибавляет 50$ и сохраняет (150$).
4. Пользователь Б прибавляет 30$ и сохраняет (130$).
**Итог:** Баланс стал 130$, хотя должен был быть 180$. Изменение пользователя А было «затерто».

Существует два фундаментальных подхода к решению этой проблемы: **Optimistic (Оптимистичный)** и **Pessimistic (Пессимистичный)**. Также существует третий, более системный — **MVCC** (который реализован в самом PostgreSQL, но это уровень движка, а не прикладного кода).

---

### Финальный ответ

Я разделяю подходы на два уровня: на уровне приложения (как мы управляем логикой) и на уровне базы данных.

#### 1. Optimistic Locking (Оптимистичная блокировка)
Мы предполагаем, что конфликты случаются редко. Мы не блокируем строку, а просто проверяем версию данных в момент записи.

*   **Механизм:** В таблицу добавляется колонка `version` (integer). При каждом `UPDATE` мы проверяем, совпадает ли версия в БД с той, которую мы прочитали.
*   **SQL:** `UPDATE accounts SET balance = 150, version = 2 WHERE id = 1 AND version = 1;`
*   **Результат:** Если кто-то уже изменил запись, `affected rows` будет 0. Приложение получает ошибку (в Doctrine это `OptimisticLockException`) и должно решить, что делать дальше (показать ошибку пользователю или попробовать еще раз).

**Trade-offs:**
*   **Pros:** Максимальная производительность, отсутствие блокировок (никаких deadlocks), отличная масштабируемость.
*   **Cons:** Если конфликты частые, пользователи будут постоянно получать ошибки «Данные изменились», что портит UX.

#### 2. Pessimistic Locking (Пессимистичная блокировка)
Мы предполагаем, что конфликт неизбежен. Мы «захватываем» запись сразу при чтении.

*   **Механизм:** При чтении мы используем SQL-команду `SELECT ... FOR UPDATE`.
*   **SQL:** `SELECT * FROM accounts WHERE id = 1 FOR UPDATE;`
*   **Результат:** База данных блокирует эту строку. Второй процесс, попытавшийся сделать такой же `SELECT ... FOR UPDATE`, будет **стоять и ждать**, пока первый процесс не сделает `COMMIT` или `ROLLBACK`.

**Trade-offs:**
*   **Pros:** Гарантированная консистентность без ошибок «повторите попытку». Идеально для критических операций (финансы).
*   **Cons:** Низкая производительность (процессы стоят в очереди). Высокий риск возникновения **Deadlocks** (когда процесс А ждет Б, а Б ждет А).

#### 3. MVCC (Multi-Version Concurrency Control) — уровень PostgreSQL
Важно понимать, что PostgreSQL сам по себе использует MVCC. Это значит, что `SELECT` (чтение) никогда не блокирует `UPDATE` (запись), и наоборот. Читающий видит «снимок» (snapshot) данных на момент начала транзакции. Это позволяет системе работать очень быстро, но это **не спасает от Lost Update**, который описан выше. MVCC защищает от грязного чтения, но не от логической перезаписи.

---

### Сравнение и мой выбор

| Критерий | Optimistic Locking | Pessimistic Locking |
| :--- | :--- | :--- |
| **Вероятность конфликтов** | Низкая | Высокая |
| **Производительность** | Очень высокая | Низкая (из-за очередей) |
| **Риск Deadlock** | Нет | Высокий |
| **UX (User Experience)** | Возможны ошибки «повторите действие» | Пользователь просто ждет (задержка) |

#### Когда и что я выбираю:

1.  **Выбираю Optimistic Locking (по умолчанию):**
    *   В большинстве CRUD-приложений (профили, статьи, настройки).
    *   Там, где конфликты редки.
    *   Это мой стандартный выбор для обеспечения масштабируемости.

2.  **Выбираю Pessimistic Locking:**
    *   В финансовых операциях (списание денег, транзакции).
    *   Там, где цена ошибки или потери данных критически высока.
    *   Там, где конкуренция за одну запись очень высокая (например, «горячие» остатки товаров на складе во время распродажи).

3.  **Дополнительный прием (Atomic Updates):**
    Если задача простая (например, инкремент счетчика), я вообще избегаю захвата объектов в Doctrine и использую чистый SQL: `UPDATE counters SET value = value + 1 WHERE id = 42;`. Это самый быстрый и безопасный способ, так как атомарность гарантирует сама БД.

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

### Рассуждение

Когда меня спрашивают про Git-процесс, я не рассматриваю его как «набор команд». Для меня Git — это инструмент управления **рисками** и **скоростью доставки (Velocity)**.

Плохой процесс — это либо «хаос» (все пушат в `main`, ломая сборку), либо «бюрократия» (огромные ветки, которые живут неделями и превращаются в кошмар при мердже). Моя задача как инженера — выстроить процесс так, чтобы разработчик мог быстро и безопасно доставлять код, а команда не тратила время на разбор конфликтов.

Я придерживаюсь модели, которая сочетает элементы **GitFlow** (для релизов) и **GitHub Flow** (для быстрой разработки), адаптированных под CI/CD.

---

### Финальный ответ

Мой процесс строится на принципе: **«Маленькие, атомарные изменения — частые интеграции — автоматизированная проверка»**.

#### 1. Ветвление (Branching Strategy)
Я использую модель, близкую к **Trunk-based development** с короткими жизненными циклами веток.

*   **`main` (или `master`)**: Единственный источник истины. Всегда стабилен, готов к деплою.
*   **`feature/task-id-description`**: Ветки для задач. Они живут недолго (от пары часов до пары дней). Если задача большая, она разбивается на несколько мелких фич.
*   **`hotfix/description`**: Короткие ветки для исправления критических багов на продакшене.
*   **`release/v1.x`** (опционально): Если проект требует строгого версионирования, создается ветка для подготовки релиза, но в современных CI/CD средах чаще используется прямой деплой из `main` через теги.

**Почему так?** Длинные ветки — это смерть для проекта. Чем дольше ветка живет в изоляции, тем сложнее её мержить. Короткие ветки минимизируют конфликты.

#### 2. Формат коммитов (Commit Messages)
Я сторонник **Conventional Comm commits**. Это не просто «красота», это способ автоматизировать чейнджлоги и понимать историю.

**Формат:** `<type>(<scope>): <description>`
*   `feat`: новая функциональность.
*   `fix`: исправление ошибки.
*   `refactor`: изменение кода без изменения логики.
*   `test`: добавление тестов.
*   `chore`: обновление зависимостей, конфигов.

**Почему так?** Это позволяет использовать инструменты типа `semantic-release`, которые автоматически определяют версию (SemVer) и генерируют список изменений на основе коммитов.

#### 3. Pull Request (PR) и Code Review
PR — это не просто «проверка кода», это инструмент передачи знаний в команде.

*   **Описание:** Хороший PR содержит: *Что сделано*, *Зачем это сделано* (ссылка на задачу в Jira/YouTrack) и *Как это протестировать*.
*   **Review:** Я смотрю на:
    1.  **Архитектуру и чистоту:** Не нарушены ли границы слоев? Нет ли дублирования?
    2.  **Тесты:** Покрыт ли новый код? Не сломали ли мы старый?
    3.  **Безопасность и производительность:** Нет(ли) SQL-инъекций? Нет ли N+1 запросов?
*   **Правило:** Ни один код не попадает в `main` без хотя бы одного одобрения (Approve) от коллеги.

**Почему так?** Ревью снижает вероятность ошибок и гарантирует, что знания о коде распределены по всей команде, а не заперты в голове одного разработчика.

#### 4. CI/CD и Релиз (Deployment)
Процесс деплоя максимально автоматизирован.

1.  **CI (Continuous Integration):** При создании PR или пуше в ветку запускается пайплайн:
    *   Линтеры (PHP-CS-Fixer, PHPStan).
    *   Unit-тесты.
    *   Integration тесты (в Docker).
    *   Если что-то упало — PR не может быть вмержен.
2.  **Merge:** После Approve и прохождения CI происходит `Squash and Merge`. Все мелкие коммиты из ветки схлопываются в один чистый, осмысленный коммит в `main`.
3.  **CD (Continuous Deployment):** После попадания в `main` срабатывает пайплайн деплоя:
    *   Сборка артефакта (Docker-образ).
    *   Запуск миграций БД.
    *   Деплой на стейджинг $\rightarrow$ Автотесты $\rightarrow$ Деплой на продакшен.

**Почему так?** Мы минимизируем человеческий фактор. Если человек нажимает кнопку «Deploy», он должен быть уверен, что все проверки уже пройдены роботами.

#### Резюме процесса:
`Задача в Jira` $\rightarrow$ `Feature-ветка` $\rightarrow$ `Атомарные коммиты` $\rightarrow$ `PR + CI + Code Review` $\rightarrow$ `Squash & Merge в main` $\rightarrow$ `Автоматический деплой`.

## Q20 · Git и процесс

### Рассуждение

Для меня код-ревью — это не «экзамен» и не «поиск ошибок». Это **процесс обеспечения качества и обмена знаниями**. Если ревью превращается в борьбу эго, он становится токсичным и замедляет разработку.

Я разделяю ревью на две составляющие: **техническую** (проверка кода) и **коммуникационную** (как мы общаемся). Хороший ревьюер — это ментор, а не судья.

---

### Финальный ответ

#### 1. На что я смотрю в первую очередь (Приоритеты)

Я не трачу время на обсуждение расстановки пробелов (это задача линтеров), я иду от общего к частному:

1.  **Архитектура и бизнес-логика (High Priority):**
    *   Решает ли этот код поставленную задачу?
    *   Не нарушает ли он границы слоев (например, не полез ли `Entity` в `Controller`)?
    *   Соблюден ли принцип единственной ответственности (SRP)?
    *   Нет ли здесь «дырявого» агрегата или нарушения инвариантов?
2.  **Безопасность и надежность:**
    *   Нет ли уязвимостей (SQL-инъекции, XSS, CSRF)?
    *   Как код обрабатывает исключения? Не «проглатываются» ли они?
    *   Неты ли Race Conditions (состояние гонки)?
3.  **Производительность:**
    *   Нет ли проблемы N+1 в запросах к БД?
    *   Не выполняются ли тяжелые операции в циклах?
    *   Не слишком ли тяжелый объект мы пытаемся загрузить?
4.  **Читаемость и поддержка (Maintainability):**
    *   Насколько понятны имена переменных и методов? (Соответствуют ли они Ubiquitous Language?)
    *   Не слишком ли сложен метод? Можно ли его упростить?

#### 2. Как я маркирую замечания (Стиль общения)

Чтобы избежать двусмысленности и агрессии, я использую систему уровней важности. Это помогает автору понять, что критично, а что — лишь моё мнение.

*   **[BLOCKER] / [MUST]**: Критическая ошибка, баг или нарушение архитектуры. Код **не может** быть вмержен в таком виде. (Например: «Здесь SQL-инъекция»).
*   **[SUGGESTION] / [NIT] (Nitpick)**: Мелкое замечание, касающееся стиля или микро-оптимизации. Это **не блокирует** мерж. (Например: «Здесь можно назвать переменную чуть короче»).
*   **[QUESTION]**: Я не уверен, что здесь происходит, и хочу понять логику автора. Это не критика, а уточнение. (Например: «Почему здесь выбран этот паттерн вместо другого?»).
*   **[COMMENT]**: Просто наблюдение или предложение для будущего рефакторинга.

**Важное правило:** Я стараюсь использовать вопросы вместо утверждений. Вместо «Это плохо, переделай» я пишу «Как ты думаешь, что произойдет здесь, если придет `null`?». Это стимулирует обсуждение, а не защиту.

Конфликты — это нормально. Если мы не можем прийти к согласию, я действую по следующим шагам:

1.  **Переход в офлайн (Sync communication):** Если обсуждение в комментариях затянулось (больше 3-4 итераций), я предлагаю созвониться или подойти к столу. Текстом очень легко неправильно считать тон и эмоцию. В живом разговоре 90% споров решаются за 2 минуты.
2.  **Аргументация через факты:** Я не говорю «мне так больше нравится». Я говорю: «Это решение может привести к проблеме производительности при росте таблицы до 1 млн строк» или «Это нарушает наш принцип инверсии зависимостей».

4.  **Принятие решения (Tie-break):** Если это не критический баг, а вопрос вкуса/стиля, и мы зашли в тупик — мы принимаем решение в пользу **скорости**. Мы мержим код, но фиксируем это как «технический долг», который нужно обсудить на следующем ретроспективе.

**Мой девиз:** *«Цель ревью — сделать продукт лучше, а не доказать свою правоту»*.

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

### Рассуждение

Прежде чем отвечать на вопрос, я должен внести критически важную поправку: **в PostgreSQL нет команды `FORCE INDEX`**. 

Если вы встретите такой запрос в коде или услышите его от другого разработчика, это либо ошибка (человек путает PostgreSQL с MySQL), либо он имеет в виду другой механизм. В MySQL `FORCE INDEX` — это подсказка (hint) планировщику использовать конкретный индекс, даже если он считает, что это невыгодно. В PostgreSQL философия иная: **планировщик должен быть умным, и разработчик не должен «дирижировать» им напрямую через SQL-запросы.**

Однако, если вопрос подразумевает «как заставить PostgreSQL использовать нужный индекс, если он его игнорирует?», то у нас есть два пути: один — для отладки, другой — для «костылей», и третий — правильный архитектурный.

---

### Финальный ответ

Поскольку прямой команды `FORCE INDEX` в PostgreSQL не существует, я разберу, как решается задача «принудительного» использования индекса и почему это обычно плохой знак.

#### 1. Как это делается в PostgreSQL (Механизмы)

Если планировщик по какой-то причине игнорирует индекс, который, по вашему мнению, должен работать, используются следующие методы:

**А) Использование `SET enable_seqscan = off;` (Для тестов и отладки)**
Это не «форсирование» конкретного индекса, а временное запрещение планировщику использовать `Sequential Scan`.
*   **Зачем:** Чтобы проверить, насколько эффективен ваш индекс, если бы БД его применила.
*   **Важно:** Это не решение для продакшена. Это инструмент для диагностики.

**Б) Создание функциональных индексов (Индексация выражений)**
Если индекс не используется, потому потому что в `WHERE` применяется функция, например `WHERE DATE(created_at) = '...'`.
*   **Решение:** Вместо «форсирования» мы создаем индекс именно по этому выражению:
    `CREATE INDEX idx_created_date ON orders (DATE(created_at));`
*   Это позволяет планировщику использовать индекс естественным путем.

**В) Использование расширения `pg_hint_plan` (Если очень нужно)**
Существует стороннее расширение, которое добавляет в PostgreSQL синтаксис, похожий на MySQL (`/*+ IndexScan(table index) */`).
*   **Зачем:** В крайне редких случаях, когда планировщик систематически ошибается на очень сложных запросах.

#### 2. Почему планировщик может игнорировать индекс? (Причины)

Прежде чем «форсить» индекс, я всегда проверяю эти причины через `EXPLAIN ANALYZE`:

1.  **Низкая селективность (Low Cardinality):** Если в колонке всего два значения (например, `is_active`), и 50% строк имеют `true`, планировщик решит, что быстрее прочитать всю таблицу целиком (`Seq Scan`), чем прыгать по индексу для каждой строки.
2.  **Устаревшая статистика:** Планировщик строит план на основе данных из `pg_statistic`. Если данные изменились (был массовый импорт), он может думать, что индекс бесполезен.
    *   *Решение:* `ANALYZE table_name;`.
3.  **Несоответствие типов данных:** Если колонка `string`, а вы ищете по `integer` (или наоборот), PostgreSQL может не использовать индекс из-за неявного приведения типов.
4.  **Малый объем данных:** Если в таблице всего 100 строк, `Seq Scan` всегда будет быстрее, чем чтение индекса + чтение куска таблицы.

#### 3. Итоговая стратегия

Мой подход к решению проблемы «медленного запроса из-за игнорирования индекса»:

1.  **Диагностика:** Запускаю `EXPLAIN (ANALYZE, BUFFERS)`. Смотрю, почему выбран `Seq Scan`.
2.  **Проверка статистики:** Запускаю `ANALYZE`.
3.  **Проверка селективности:** Считаю распределение значений в колонке. Если оно почти равномерное — индекс не поможет.
4.  **Рефакторинг запроса:** Переписываю запрос так, чтобы он был **SARGable** (Search Argumentable) — без функций над колонками.
5.  **Создание правильного индекса:** Вместо «форсирования» старого, создаю новый (например, составной индекс или функциональный).
6.  **Крайний случай:** Если планировщик объективно ошибается на сложном запросе, и все методы выше не помогли, я использую `pg_hint_plan`, но фиксирую это как технический долг.

**Резюме:** В PostgreSQL мы не «форсируем» индексы, мы **помогаем планировщику** видеть актуальную статистику и писать запросы, которые он сможет эффективно оптимизировать.

### Рассуждение

Если мы говориим о производительности, нам нужно разделить два аспекта:
1.  **Runtime overhead (накладные расходы при выполнении):** Время, затраченное на проверку соответствия типов.
2.  **JIT (Just-In-Time compilation):** Влияние типизации на оптимизацию кода компилятором.

---

### Финальный ответ

По моему опыту и пониманию работы движка Zend, `strict_types=1` **не замедляет код, а в некоторых сценариях даже может способствовать его ускорению.**

#### 1. Почему нет замедления (Runtime)
В PHP проверки типов выполняются на уровне виртуальной машины (Zend VM). Когда вы вызываете функцию с объявленным типом (например, `int $a`), PHP **в любом случае** должен проверить, является ли переданное значение целым числом.

*   **В режиме `strict_types=0` (Coercive):** PHP делает проверку + потенциальное преобразование (например, из `"10"` в `10`). Это преобразование само по себе требует процессорного времени.
*   **В режиме `strict_types=1` (Strict):** PHP делает только проверку. Если тип не совпадает, он сразу выбрасывает `TypeError`.

Поскольку проверка типа — это атомарная операция для движка, разница в наносекундах между «проверить и преобразовать» и «просто проверить» ничтожна и обычно нивелируется на уровне микро-оптимизаций движка. В реальных приложениях (Web/API) накладные расходы на сетевой стек, работу с БД или парсинг JSON в тысячи раз превышают разницу в проверке типов.

#### 2. Влияние на JIT (PHP 8+)
С появлением JIT-компилятора ситуация меняется в пользу строгой типизации. JIT работает эффективнее, когда он точно знает типы данных. 

Когда код написан в строгом режиме, компилятору проще генерировать оптимизированный машинный код, так потому, что он может быть уверен: в переменную `$a` никогда не придет `string`, если заявлен `int`. Это позволяет JIT избегать генерации лишних проверок на тип внутри скомпилированного машинного кода. Таким образом, **строгая типизация может косвенно ускорять код при включенном JIT.**

#### 3. Где на самом деле кроется «замедление»?
Единственный случай, когда можно заметить разницу — это микро-бенчмарки, где вы вызываете функцию миллионы раз в цикле. Но даже там разница будет в пределах погрешности измерений.

**Реальное замедление в PHP происходит не из-за `strict_types`, а из-за:**
*   Избыточного использования тяжелых объектов.
*   Неэффективных алгоритмов.
*   Избыточных вызовов функций и методов (Call Stack overhead).
*   Неоптимальных запросов к БД.

**Итог:**
Я никогда не отказываюсь от `strict_types=1` из соображений производительности. Напротив, я использую его везде, потому потому что **цена ошибки (runtime bug) несоизмеримо выше, чем мифическая цена производительности**. В современном PHP `strict_types` — это не инструмент для скорости, это инструмент для **предсказуемости и надежности**.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

### Рассуждение

Прежде чем отвечать, я должен сделать важную техническую ремарку: утверждение «Doctrine не поддерживает составные первичные ключи» является **не совсем верным**. 

Технически, Doctrine **поддерживает** составные ключи (Composite Primary Keys). Вы можете объявить несколько полей с атрибутом `#[ORM\Id]`, и Doctrine позволит вам работать с ними. Однако на практике разработчики и архитекторы часто избегают этого подхода, и я сейчас объясню, почему это превращается в «боль» и как мы с этим работаем.

Проблема не в том, что это «невозможно», а в том, что это нарушает принципы проектирования, на которых построена вся философия Doctrine и многих других ORM.

---

### Финальный ответ

#### Почему использование составных ключей в Doctrine — это «плохой путь»?

Хотя поддержка существует, использование составных ключей в качестве первичных (Primary Keys) создает цепочку проблем:

1.  **Сложность Identity Map (Управление объектами):**
    Doctrine использует паттерн *Identity Map*, чтобы гарантировать, что для одной строки в БД существует только один объект в памяти. Для этого ей нужен уникальный идентификатор. Если ключ состоит из трех полей, то для поиска объекта в Map Doctrine приходится работать с кортежем (tuple) из трех значений вместо одного простого `int`. Это усложняет внутреннюю логику и снижает производительность.

2.  **Проблемы с ассоциациями (Relationships):**
    Это самая большая головная боль. Если `Entity A` имеет составной ключ `(id_part1, id_part2)`, то любая другая сущность (`Entity B`), которая хочет ссылаться на `A` через `ManyToOne`, должна будет хранить **оба** этих поля как Foreign Key. 
    *   Ваши таблицы начинают «раздуваться».
    *   Ваши маппинги становятся монструозными.
    *   Любое изменение состава ключа в одной таблице вызывает каскадную перестройку всей схемы БД.

3.  **Несовместимость с некоторыми инструментами:**
    Многие библиотеки (например, для построения API, сериализации или интеграции с внешними системами) ожидают, что у сущности есть один простой `id`. Составные ключи ломают их логику «из коробки».

#### Как с этим живут в реальных проектах?

В профессиональной разработке мы используем три основные стратегии, чтобы избежать проблем с составными ключами.

**Стратегия №1: Surrogate Key (Заместительный ключ) — Мой выбор по умолчанию**
Вместо того чтобы использовать естественный составной ключ (например, `order_id` + `product_id`), мы добавляем в таблицу искусственное поле `id` (обычно `AUTO_INCREMENT` или `UUID`).

*   **Как это выглядит:** У вас есть табличка `order_items`. Вместо PK `(order_id, product_id)`, вы делаете `id (PK)`, `order_id (FK)`, `product_id (FK)`.
*   **Как обеспечить уникальность:** Чтобы не допустить дублей (что было целью составного ключа), мы вешаем на пару `(order_id, product_id)` ограничение **`UNIQUE constraint`** на уровне базы данных.
*   **Плюсы:** Чистые связи, легкая работа с Doctrine, предсказуемость.

**Стратегия №2: Использование Value Objects для естественных ключей**
Если составной ключ — это логически единая сущность (например, координаты `latitude` + `longitude` или `street` + `house_number`), мы не делаем их первичным ключом. Мы маппим их как **Embeddable (Value Object)**.

*   **Как это выглядит:** Мы используем `id (Surrogate Key)` для связи, а составные поля храним как объект внутри сущности.
*   **Плюсы:** Мы сохраняем чистоту доменной модели и при этом не ломаем работу ORM.

**Стратегия №3: Использование UUID**
В распределенных системах или микросервисах вместо составных ключей часто используют `UUID (v4 или v7)`.

*   **Почему это помогает:** UUID по своей природе уникален и самодостаточен. Он заменяет собой любую необходимость в составных ключах, позволяя сущностям быть независимыми и легко перемещаться между контекстами.

#### Резюме
Я никогда не использую составные первичные ключи в качестве `#[ORM\Id]`. Вместо этого я всегда внедряю **Surrogate Key** (простой `id`) и накладываю **`UniqueConstraint`** на те поля, которые должны быть уникальной комбинацией. Это дает мне все преимущества составного ключа (целостность данных) без всех его недостатков (сложность маппинга и связей).

### Анализ проблем

Я разделяю проблемы на три уровня: критические (безопасность), архитектурные (структура) и эксплуатационные (надежность).

#### 1. Критические проблемы (Security)
*   **SQL Injection:** Самая страшная ошибка. Переменная `$id` вставляется напрямую в строку запроса. Злоумышленник может передать `1; DROP TABLE orders;`, и база данных будет уничтожена.

#### 2. Архитектурные проблемы (Design)
*   **Нарушение SRP (Single Responsibility Principle):** Контроллер делает всё: обрабатывает HTTP, работает с БД, отправляет почту, логирует. Контроллер должен быть тонким (Thin Controller), его задача — только принять запрос и вызвать нужный сервис.
*   **Нарушение слоев (Leaky Abstractions):** Логика работы с БД (SQL-запросы) находится прямо в контроллере. Это делает код нетестируемым и привязывает нас к конкретной реализации БД.
*   **Жесткая связь (Tight Coupling):** Мы используем статические вызовы `DB::connect()`, `Mailer::send()` и `new Logger()`. Это делает невозможным подмену этих сервисов на Mock-объекты в тестах. Мы не можем протестировать этот метод в изоляции.

#### 3. Эксплуатационные проблемы (Reliability)
*   **Отсутствие транзакционности:** Если `UPDATE` прошел успешно, а `Mailer::send()` упал (например, из-за таймаута сети), заказ останется в статусе `paid`, но пользователь не получит письмо. Или наоборот: если мы сначала шлем письмо, а потом БД падает — клиент получил подтверждение оплаты, которой нет в системе.
*   **Проблема атомарности:** Состояние системы меняется в несколько этапов, и между этими этапами может произойти сбой.

### Как я бы это переделал

Я бы начал не с переписывания методов, а с **проектирования слоев**. Мой подход: **«Вынеси логику из контроллера в Use Case, а работу с данными — в Репозиторий»**.

#### Шаг 1: Создание доменных сущностей и репозиториев
Я создам `Order` (Entity) и `OrderRepositoryInterface` (Domain Layer), чтобы изолировать работу с данными.

#### Шаг 2: Создание Application Service (Use Case)
Я создам `PayOrderService`, который будет оркестровать процесс.

#### Шаг 3: Применение Transactional Outbox или транзакций
Я оберну все изменения в одну транзакцию.

### Финальный результат (Рефакторинг)

**1. Слой Domain (Entity):**
```php
readonly class Order {
    public function __construct(
        public int $id,
        public string $email,
        public string $status,
    ) {}

    public function markAsPaid(): self {
        if ($this->status === 'paid') {
            throw new OrderAlreadyPaidException();
        }
        return new self($this->id, $this->email, 'paid');
    }
}
```

**2. Слой Application (Use Case):**
```php
class PayOrderUseCase {
    public function __construct(
        private OrderRepositoryInterface $repository,
        private MailerInterface $mailer,
        private LoggerInterface $logger,
        private EntityManagerInterface $em // Для управления транзакцией
    ) {}

    public function execute(int $orderId): void {
        $this->em->wrapInTransaction(function() use ($orderId) {
            $order = $this->repository->findById($orderId);
            
            if (!$order) {
                throw new OrderNotFoundException($orderId);
            }

            $paidOrder = $order->markAsPaid();
            $this->repository->save($paidOrder);

            // Важно: отправка сообщения/письма должна быть частью транзакции 
            // или реализована через паттерн Outbox.
            $this->mailer->send($paidOrder->email, 'Ваш заказ оплачен');
            $this->logger->info("Order paid: {$orderId}");
        });
    }
}
```

**3. Слой Presentation (Controller):**
```php
class OrderController extends AbstractController 
{
    public function __construct(
        private PayOrderUseCase $payOrderUseCase
    ) {}

    public function pay(Request $request): Response
    {
        $id = $request->query->get('order_id');

        if (!is_numeric($id)) {
            return new Response('Invalid ID', 400);
        }

        try {
            $this->payOrderUseCase->execute((int)$id);
            return new Response('ok', 200);
        } catch (OrderNotFoundException $e) {
            return new Response('Not found', 404);
        } catch (OrderAlreadyPaidException $e) {
            return new Response('Already paid', 409);
        } catch (\Exception $e) {
            return new Response('Internal error', 500);
        }
    }
}
```

1.  **Безопасность:** SQL-инъекции невозможны, так как мы используем Prepared Statements через ORM/Repository.
2.  **Тестируемость:** Я могу написать Unit-тест на `PayOrderUseCase`, подставив Mock-объекты для репозитория и почты. Мне не нужна БД для теста логики.
3.  **Надежность:** Благодаря `wrapInTransaction`, мы гарантируем атомарность: либо всё (заказ + статус + лог), либо ничего.
4.  **Чистота:** Контроллер стал «тонким». Он только принимает запрос и возвращает ответ. Вся магия скрыта в слое приложения.

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void

```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Этот код — классический пример «антипаттерна», который часто встречается у разработчиков, переходящих от процедурного стиля к ООП. Здесь нарушены практически все базовые принципы проектирования доменных моделей.

### Что не так с этой сущностью?

Я выделю пять критических проблем:

**1. Нарушение принципа инкапсуляции и чистоты домена (Dependency Inversion Principle)**
Это самая серьезная ошибка. Сущность `User` (объект домена) зависит от `EntityManagerInterface` (объект инфраструктуры). 
*   **Почему это плохо:** Доменный слой должен быть «чистым» и не зависеть от библиотек или инструментов хранения данных. Теперь, чтобы создать объект `User` (даже для теста), вам нужно подложить ему мок или реальный `EntityManager`. Ваша бизнес-логика «отравлена» деталями реализации БД.

**2. Нарушение ответственности (Single Responsibility Principle)**
Сущность `User` теперь отвечает за две вещи: за хранение данных пользователя и за процесс сохранения этих данных в базу.
*   **Почему это плохо:** Сущность должна управлять своим внутренним состоянием (инвариантами), но она не должна знать, как это состояние синхронизировать с внешним миром.

**3. Нарушение транзакционности и прозрачности (Side Effects)**
Метод `changeEmail` вызывает `$this->em->flush()`. Это создает скрытые побочные эффекты.
*   **Почему это плохо:** Когда разработчик вызывает `changeEmail`, он ожидает изменения состояния объекта. Он может не ожидать, что в этот же момент в базу данных полетит `COMMIT`. Если позже в том же бизнес-процессе произойдет ошибка, мы не сможем откатить изменение email, так как оно уже зафиксировано в БД.

**4. Нарушение принципа непредсказуемости (Predictability)**
Метод `changeEmail` выглядит как простая мутация, но на самом деле это тяжелая операция ввода-вывода (I/O). Это делает Unit-тесты медленными и сложными.

**5. Проблема с конструктором**
Конструктор сущности теперь требует `EntityManager`. Это делает создание объекта в тестах или в сценариях, где БД не нужна, крайне неудобным.

---

### Как бы я это исправил?

Я бы разделил **состояние** (Domain) и **механизм сохранения** (Infrastructure).

#### Шаг 1: Очистка Доменного слоя
Сущность должна содержать только данные и правила их изменения.

```php
// Domain Layer
#[ORM\Entity]
class User
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(unique: true)]
    private string $email;

    public function __construct(string $email)
    {
        // Здесь может быть валидация формата email
        if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException("Invalid email format");
        }
        $this->email = $email;
    }

    public function changeEmail(string $newEmail): void
    {
        if (!filter_var($newEmail, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException("Invalid email format");
        }
        
        $this->email = $newEmail;
    }

    public function getEmail(): string
    {
        return $this->email;
    }

    public function getId(): ?int
    {
        return $this->id;
    }
}
```

#### Шаг 2: Создание Application Service (Use Case)
Логика «изменил и сохрани» переносится на уровень приложения. Именно здесь управляется транзакция.

```php
// Application Layer
class ChangeUserEmailService
{
    public function __construct(
        private UserRepositoryInterface $repository,
        private EntityManagerInterface $entityManager
    ) {}

    public function execute(int $userId, string $newEmail): void
    {
        // Транзакция гарантирует, что изменения будут зафиксированы атомарно
        $this->entityManager->wrapInTransaction(function() use ($userId, $newEmail) {
            $user = $this->repository->findById($userId);
            
            if (!$user) {
                throw new UserNotFoundException($userId);
            }

            $user->changeEmail($newEmail);
            
            // Мы сохраняем изменения через репозиторий или Unit of Work
            $this->repository->save($user);
        });
    }
}
```

### Итог рефакторинга:
1.  **Domain Layer** стал чистым: он не знает о базе данных, его легко тестировать Unit-тестами.
2.  **Соблюдена инверсия зависимостей:** Мы используем `UserRepositoryInterface`, а не конкретный `EntityManager` внутри домена.
3.  **Управляется транзакционность:** Мы контролируем, когда данные попадают в БД, что делает систему надежной.
4.  **Код стал предсказуемым:** Вызов `$user->changeEmail()` теперь — это просто изменение переменной в памяти, а не тяжелый запрос к диску.

## Q29 · Процесс и рассуждение

**Интервьюер:** Тебе нужно решить техническую проблему на незнакомых тебе технологии или стеке. Опиши последовательность своих действий от первого взгляда на задачу до уверенного ответа о сроках решения. Когда, по-твоему, нужно просить помощи у команды, а когда разбираться самому?

**Кандидат:**

Это вопрос не о знаниях, а о **процессе управления неопределенностью**. Как опытный инженер, я знаю: самая дорогая ошибка — это когда разработчик «закопался» в задаче, не понимая, что он идет не туда, и молчит об этом.

Мой подход базируется на принципе **«минимизации потерь времени»**.

---

### 1. Этапы работы с незнакомым стеком

Я разделяю процесс на четыре фазы: **Исследование $\rightarrow$ Прототипирование $\rightarrow$ Оценка $\rightarrow$ Реализация.**

#### Фаза 1: Исследование (Discovery) — *«Понять, что я не знаю»*
Прежде чем писать код, я должен построить ментальную модель.
1.  **Анализ документации и «Hello World»:** Я не читаю документацию как книгу. Я ищу ответы на конкретные вопросы: «Как здесь работает жизненный цикл объекта?», «Как организована передача данных?». Я запускаю минимальный рабочий пример.
2.  **Анализ существующего кода (Codebase):** Я смотрю, как коллеги уже используют этот стек в нашем проекте. Это дает мне понимание принятых паттернов и «местных» стандартов.
3.  **Формирование гипотез:** Я формулирую: «Я думаю, эта проблема решается через компонент X, потому Cap de механизм Y работает так-то».

#### Фаза 2: Прототипирование (Spike) — *«Проверить гипотезы»*
Я создаю так называемый **Spike** — изолированный, «грязный» проект или ветку, где я могу ломать вещи, не боясь испортить основную кодовую базу.
*   **Цель:** Не написать чистый код, а проверить, работает ли выбранный инструмент/подход в принципе.
*   **Результат:** Либо «Да, это работает, вот пример кода», либо «Нет, этот инструмент нам не подходит, потому что...».

#### Фазаю 3: Оценка (Estimation) — *«Озвучить сроки»*
Только после фазы прототипирования я могу дать оценку. Я никогда не называю одну цифру. Я использую **диапазоны и буферы**.
*   Я оцениваю задачу в категориях: `Оптимистичный сценарий` (всё пошло по плану) и `Пессимистичный сценарий` (всплыли сложности).
*   Я всегда добавляю **буфер на тестирование и рефакторинг**. Если я думаю, что задача займет 4 часа, я скажу «полдня» или «от 4 до 8 часов».

#### Фаза 4: Реализация (Implementation)
Когда прототип подтвержден, я переношу решение в основной проект, превращая «грязный» код Spike в чистый, протестированный код, соответствующий нашим стандартам.

---

### 2. Когда разбираться самому, а когда просить помощи?

Это вопрос **экономики времени**. Я использую правило **«30-60 минут»** и принцип **«прогрессирующей эскалации»**.

#### Когда разбираться самому:
*   **Первые 30-60 минут:** Я активно ищу ответы в документации, StackOverflow, GitHub Issues и локальных логах. Это время на «самостоятельный поиск».
*   Если проблема в синтаксисе или незнакомом API — я решаю это сам.

#### Когда просить помощи (Escalation):
Я прошу помощи, если выполнение одного из следующих условий:
1.  **Тупик (Deadlock):** Я потратил более часа, и у меня **ноль** новых гипотез. Я хожу по кругу. В этот момент мои попытки «покопать глубже» — это просто трата денег компании.
2.  **Неясность требований:** Если я не понимаю не *как* реализовать, а *что* именно нужно сделать с точки зрения бизнеса. Это вопрос к Product Owner.
3.  **Риск архитектурного конфликта:** Если я вижу, что моё решение может нарушить принципы системы, о которых я не знаю (например, специфические настройки инфраструктуры), я иду к Senior/Lead разработчику за советом.
4.  **Блокировка (Blocker):** Если проблема лежит вне моей зоны ответственности (например, права доступа в облаке или упавший сервер), я не пытаюсь это «починить сам», а немедленно передаю задачу ответственному.

**Как я прошу помощи:**
Я никогда не прихожу с вопросом «Как это сделать?». Я прихожу с формулировкой:
> *«Я решаю задачу X. Я изучил документацию и попробовал подход Y (вот мой прототип), но столкнулся с проблемой Z. Мои гипотезы такие: [Гипотеза 1, Гипотеза 2]. Подскажи, я двигаюсь в правильном направлении?»*

**Это показывает, что я не перекладываю работу на других, а пришел с результатами своего исследования.**

## Q30 · Процесс и рассуждение

**Интервьюер:** Ты пообещал сделать задачу к завтрашнему дню, но по ходу работы понял, что это два дня работы. Что делаешь?

**Кандидат:**

Это критический момент, который проверяет не твою способность программировать, а твою **надежность как профессионала** и умение управлять ожиданиями стейкхолдеров.

Мой главный принцип: **«Никогда не сообщай о проблеме в последний момент»**. Если я скажу об этом завтра в день дедлайна — я подвел команду. Если я скажу об этом сразу, как только понял — я управляю рисками.

Вот мой алгоритм действий:

### 1. Немедленная остановка и переоценка
Как только я понимаю, что оценка неверна, я не пытаюсь «бежать быстрее» (это ведет к накоплению технического долга и багов). Я останавливаюсь и провожу быстрый анализ:
*   **Почему оценка неверна?** (Не учел сложность интеграции? Всплыла неописанная бизнес-логика? Проблема с инфраструктурой?).
*   **Что уже сделано?** (Какой кусок задачи готов и может быть задеплоен отдельно?).
*   **Что именно занимает время?** (Я должен уметь четко назвать причину задержки).

### 2. Коммуникация (Проактивность)
Я немедленно сообщаю менеджеру или заказчику. Я не просто прихожу с проблемой, я прихожу с **вариантами решения**.

**Я использую структуру: Факт $\rightarrow$ Причина $\rightarrow$ Варианты $\rightarrow$ Рекомендация.**

**Пример того, что я скажу:**
> «По задаче X: я обнаружил, что интеграция с API платежной системы требует обработки специфических ошибок, о которых не было известно изначально. Это увеличивает объем работы с 1 дня до 2-х. 
> 
> **У нас есть три варианта:**
> 1. **Сдвинуть дедлайн:** Я закончу всё качественно завтра вечером.
> 2. **Частичный релиз (MVP):** Я завтра сделаю базовую интеграцию (Happy Path), но обработку ошибок вынесу во вторую задачу. Это позволит нам запуститься вовремя.
> 3. **Смена приоритетов:** Если эта задача критична к завтра, я могу отложить задачу Y, над которой сейчас работаю, чтобы сфокусироваться здесь».

### 3. Выбор стратегии (Trade-offs)
Я не принимаю решение за менеджера, но я даю ему **инструменты для принятия решения**.

*   Если проект **Time-to-market driven** (нужно выкатить любой ценой) — я предложу вариант №2 (MVP/Scope Cut).
*   Если проект **Mission Critical** (финансы, медицина, где нельзя ошибаться) — я буду настаивать на варианте №1 (качество важнее скорости).
*   Если у нас **жесткий спринт** — я предложу вариант №3 (перераспределение ресурсов).

### Почему я делаю именно так?

1.  **Доверие (Trust):** Люди прощают задержки, если они предупреждены заранее. Люди не прощают сюрпризов в день дедлайна.
2.  **Управление рисками:** Моя задача как инженера — подсветить риски, а задача менеджера — управлять приоритетами бизнеса. Я даю ему данные для этого решения.
3.  **Профессионализм:** Предлагая варианты (MVP или перенос задачи), я показываю, что я не просто «кодер», который застрял, а инженер, который думает о целях бизнеса и ищет компромиссы.

**Итог:** Я никогда не обещаю «сделать за ночь», если понимаю, что это невозможно. Лучше один раз честно пересмотреть сроки, чем три раза оправдываться за некачественный код или сорванный релиз.

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

Это один из самых сложных вопросов в инженерной практике, потому Detached Engineering (чистое проектирование) и Business Value (бизнес-ценность) часто находятся в конфликте. Если я буду бесконечно улучшать код, мы никогда не выпустим продукт. Если я буду писать только «быстро», мы утонем в техническом долге через три месяца.

Для меня «достаточно хороший код» — это код, который **решает задачу, легко тестируется и не создает неконтролируемого риска для системы.**

### 1. Мои критерии «достаточно хорошего кода»

Я считаю задачу выполненной и готовой к отдаче, если она проходит через следующие фильтры:

*   **Корректность (Correctness):** Код выполняет бизнес-требования. Нет багов в основной логике.
*   **Тестируемость (Testability):** Код покрыт тестами. Если я не могу написать Unit-тест на этот код, значит, он слишком сложный или тесно связан с инфраструктурой — его нужно упростить.
*   **Читаемость (Readability):** Другой разработчик (или я сам через месяц) поймет, что здесь происходит, не тратя час на расшифровку магии.
*   **Безопасность и надежность:** Нет SQL-инъекций, обработаны исключения, нет утечек памяти.
*   **Предсказуемость:** Код не имеет скрытых побочных эффектов (Side Effects) в других частях системы.

Если эти 5 пунктов выполнены — код **готов к деплою**. Все остальное (красивые абстракции, оптимизация производительности на микроуровне, переименование переменной на более «элегантное») — это работа на будущее.

---

### 2. Как я соблюдаю баланс (Стратегии)

Я использую три подхода для управления балансом между скоростью и качеством:

#### А. Принцип YAGNI (You Ain't Gonna Need It)
Я не проектирую системы «на вырост». Если бизнес говорит: «Нам нужна поддержка 10 типов оплаты», а сейчас у нас только один — я не буду строить сложную систему плагинов и стратегий. Я сделаю простую реализацию, но сделаю её **расширяемой** (через интерфейс). 
*   *Правило:* Пиши код для текущих задач, но оставляй место для будущих изменений.

#### Б. Управление техническим долгом (Technical Debt Management)
Я осознаю, что технический долг — это не всегда плохо. Иногда это **инструмент**.
*   Если нам нужно проверить гипотезу (MVP), я могу написать чуть менее идеальный код, чтобы быстрее получить фидбек от рынка.
*   Но я всегда фиксирую этот долг. Я создаю задачу в бэклоге: `[Tech Debt] Refactor OrderService to remove tight coupling`.
*   **Мой принцип:** Допустимый долг — это тот, который мы осознаем, задокументировали и запланировали погасить.

#### В. Определение «точек невозврата»
Я разделяю код на две зоны:
1.  **Core Domain (Ядро):** Здесь я перфекционист. Код в ядре должен быть идеальным, с соблюдением всех принципов DDD и Clean Architecture. Ошибки здесь стоят очень дорого.
2.  **Infrastructure/Glue Code (Внешний слой):** Здесь я более прагматичен. Если скрипт для миграции данных или контроллер для простого CRUD-запроса написан «нормально», но не идеально — это допустимо.

---

### 3. Резюме: Мой алгоритм принятия решения

Когда я стою перед выбором «дожать или отдать», я задаю себе три вопроса:

1.  **Если я отдам сейчас, сломается ли что-то в продакшене?** (Если да — доделываю).
2.  **Если я оставлю это как есть, будет ли нам сложно менять этот код через месяц?** (Если да — рефакторю сейчас).
3.  **Приносит ли дополнительное улучшение реальную ценность бизнесу прямо сейчас?** (Если нет — записываю в техдолг и иду дальше).

**Мой подход: «Доставляй ценность быстро, но не ценой создания хаоса».**
