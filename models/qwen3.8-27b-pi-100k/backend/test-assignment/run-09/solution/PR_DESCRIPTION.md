# PR: учёт расходов на LLM-токены

## Что сделано

Реализован консольный сервис учёта расходов на LLM-токены по заданию
`TASK.md`: импорт справочника цен и событий использования, тарификация
событий по цене, действовавшей в момент запроса, CSV-отчёт по
`user`/`model`, и бонус — ретро-коррекция цены.

Рабочая связка (из `Приёмка` в `TASK.md`) — воспроизводится на чистой базе:

```bash
make db-up   # PostgreSQL 17 в docker (порт 5544 по умолчанию)
make migrate # создать БД и накатить миграции
bin/console app:prices:import fixtures/prices.json
bin/console app:usage:import  fixtures/usage.jsonl
bin/console app:billing:rate
bin/console app:billing:report --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z
```

Вывод отчёта совпадает с примером из `TASK.md` байт-в-байт; повторный
импорт + rate + report результат не меняет (идемпотентность).

## Ключевые решения и допущения

### Архитектура (слои)
- `App\Domain\Billing` — чистое ядро без зависимостей от фреймворка и БД:
  - `DecimalMath` — bcmath-арифметика со «запасным» масштабом (20 знаков),
    чтобы промежуточные значения не округлялись;
  - `Money` — стоимость как строка; `roundTo6()` — единственный
    HALF_UP-оператор;
  - `Unit` — схемы тарификации и виды токенов;
  - `OffPeakWindow` — окно оф-пика UTC, корректно обрабатывает переход
    через полночь (`16:30`–`00:30`) и границы вкл./искл.;
  - `RateCalculator` — стоимость одного события по строке цен + оф-пик.
- `App\Entity` — Doctrine-сущности: `Provider`, `TokenModel`,
  `PriceRow`/`PriceRate`, `UsageEvent`.
- `App\Service` — слой приложения: валидация (`Validators`), импорты
  (`PricesImporter`, `UsageImporter`, `PriceRowWriter`), тарификация
  (`RateService`), отчёт (`ReportService`), ретро-коррекция (`RepriceService`),
  запросы к БД (`BillingRepository`).
- `App\Command` — 5 Symfony-команд.

### Деньги и время
- `float` для денег нигде не используется — только строки + bcmath.
- Округление ровно одно, на итоговой стоимости **события**: HALF_UP до 6
  знаков (2.5 → 3). Суммы отчёта — сумма уже округлённых стоимостей, без
  повторного округления слагаемых.
- Все временные значения — UTC, ISO-8601; выбор строки цен — наибольшее
  `valid_from ≤ ts` (включительно); период отчёта `--from ≤ ts < --to`.

### Выбор цены и оф-пик
- Событие берёт строку цен модели с наибольшим `valid_from ≤ ts`;
  если такой нет — событие `unrated` (не ошибка).
- Оф-пик задан на уровне провайдера, действует для всех его моделей;
  стоимость всего события умножается на `multiplier`, если время суток
  `ts` (UTC) в окне `[start, end)`.

### Итоговый выбор: «включить в стоимость» vs. «отдельно»
Стоимость события хранится одной строкой `cost` (уже с оф-пиком и итоговым
округлением) на сущности `UsageEvent`. Ретро-коррекция перезаписывает
`cost` (не дублирует и не «доначисляет»), поэтому `app:billing:report`
после reprice показывает пересчитанные суммы без задвоений.

## Как проверяли

1. `make db-up` — чистая БД поднялась.
2. `make migrate` — схема развернулась на чистой базе (1 миграция).
   Дополнительно: `bin/console doctrine:schema:validate` — «synchronization OK».
3. `bin/console app:prices:import fixtures/prices.json` → код 0.
4. `bin/console app:usage:import fixtures/usage.jsonl` → «импортировано 3».
5. `bin/console app:billing:rate` → `RATED=3 UNRATED=0`.
6. `bin/console app:billing:report --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z`
   → совпадает с примером из `TASK.md` (проверялось через `diff`).
7. Повторное выполнение шагов 3–6 → результат не меняется
   («импортировано 0, дубли пропущено 3», `RATED=0 UNRATED=0`, тот же отчёт).
8. Ретро-коррекция: изменение `output`-ставки `lumen-8` (строка
   2026-08-01) с `12` до `9` → `REPRICED_EVENTS=1`,
   `REPRICE_DELTA_USD=-2.400000`; отчёт корректно обновляется
   (14.262499 → 11.862499 для затронутой группы), остальные строки без
   изменений. Возврат ставки даёт `+2.400000`.
9. `unrated`: событие с `ts` до всех `valid_from` (model существует)
   → `RATED=0 UNRATED=1`, stderr:
   `UNRATED prism/REQ-9 2026-07-01T00:00:00Z no_price`.
10. Тесты: `make test` → `OK (17 tests, 48 assertions)`.

### Выбор способа управления схемой
Схема БД управляется через **Doctrine Migrations**: один миграционный
класс, накатывающий структуру. Это намеренный выбор — миграция идемпотентно
работает и на чистой базе, и повторяется без ошибок. `Makefile` предоставляет
`make migrate` (create + migrate), что соответствует «по умолчанию `make
migrate`» из `Приёмка`.

### Хранение идентификатора пользователя
Поле `user` события сохраняется в колонке `user_login`, а не в `user`:
`user` — зарезервированное слово PostgreSQL. Публичное API/сущность
используют имя `user` (смысловое), а маппинг колонки — `user_login`.

### Добавленные зависимости
Внешних зависимостей **не добавлялось**; `composer.json`/`composer.lock`
не менялись. Используется только штатное расширение PHP `bcmath` (уже
установлено) и существующие `symfony/*` + `doctrine/*` из каркаса.

### Что сделано по-своему
Наиболее спорное решение — ретро-коррекция реализована как **перезапись
стоимости затронутых событий** (без журнала корректировок и без
компенсирующих записей). В ТЗ прямо сказано, что механизм пересчёта — «на
ваше усмотрение»; критерий — итоговый отчёт без задвоений. Перезапись
`cost` на сущности + точная пересборка по строкам цен даёт ровно это,
минимально и прозрачно.
