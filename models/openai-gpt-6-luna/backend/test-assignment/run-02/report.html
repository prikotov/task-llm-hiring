Как запускался агент

PI_CODING_AGENT_DIR=<tmp>/pi-home PI_OFFLINE=1 \
pi -p --session-dir <прогон>/pi-session \
    --model openai/gpt-6-luna --thinking max \
    "Прочитай TASK.md в корне репозитория и выполни задание."
  • PI_CODING_AGENT_DIR — временный pi-home: models.json собран на лету под одну модель; адрес сервера — env OLLAMA_BASE_URL (в git не попадает).
  • PI_OFFLINE=1 — служебный режим pi: он сам не ходит в сеть (проверка версии, каталог моделей, телеметрия). Командам агента сеть при этом доступна.
  • агент работает в одноразовой копии skeleton/: каркас-эталон не загрязняется прогоном; .env раннер кладёт из .env.example, чтобы Symfony был рабочим с первой секунды. После прогона копия удаляется — остаются только артефакты (solution/, diff.patch, сессия).
  • версия задания — TASK.md, sha256 a9998d7fc38418eb — одинакова во всех прогонах.
  • лимиты: таймаут 90 мин на весь прогон; ответ модели в одном вызове — не больше 8 192 токенов, считая размышление (поднято со стандартных 8192: длинное размышление иначе съедает бюджет ещё до ответа).

Что дано кандидату

Скелет skeleton/ — рабочий Symfony-каркас (PHP >=8.4, Doctrine, bcmath) с TASK.md и AGENTS.md. Инструменты самопроверки в require-dev: phpunit/phpunit ^11.5, squizlabs/php_codesniffer ^3.13, vimeo/psalm ^6.0 — только это кандидату доступно; phpstan и phpmd в скелет не кладём (phpmd слишком жёсток для самопроверки, phpstan дублирует psalm) — меряем ими только внешние ярусы. Само задание — TASK.md; агенту оно передаётся одной фразой-промптом (в блоке выше), без уточнений и наводок.

Обоснование

ревьюер яруса 3
Решение рабочее: чекер 11/11 обязательных + 2/2 бонуса. Деньги полностью на bcmath (SCALE=50), единственное округление события через bcadd('0.0000005', 6) — корректный HALF_UP для неотрицательных сумм; стоимости хранятся округлёнными, отчёт суммирует их без повторного округления. Домен смоделирован: выбор цены по valid_from (включительно) отдельным запросом, оф-пик как полуинтервал с переходом через полночь, дедуп по (provider, provider_request_id) через ON CONFLICT DO NOTHING, unrated с повторными попытками и price_valid_from как основа для reprice — бонус реализован аккуратно (перезапись с подсчётом дельты, идемпотентно). Слабости: сервисы толстые (method_loc_over_50: 4, method_cc_over_10: 2, lcom4>1 у 8 классов), граница слоёв условная (команды тонкие, но BillingService тянет импорт цен); reprice молча перезаписывает стоимости — задание это допускает. Процесс: систематические самопроверки описаны в PR_DESCRIPTION (чистая база, повторный импорт, границы периода с микросекундами, doctrine:schema:validate, phpunit с тестами граничных значений окна), решения и допущения зафиксированы; мелкие шероховатости — в дифф попал служебный .phpunit.result.cache, COMMIT_MESSAGE однострочный без обоснования решений.

заметка судьи
Сильное решение: точная десятичная арифметика на bcmath (scale 50, одно округление HALF_UP на событии), корректные окна через полночь и выбор цены по valid_from ≤ ts, идемпотентные upsert'ы через ON CONFLICT с IS DISTINCT FROM, unrated-события и ретрай покрыты, плюс частичные индексы, тесты калькулятора и бонус reprice. Слабее — домен смоделирован анемично: тарификация живёт на голых ассоциативных массивах в DBAL-сервисах, а не в сущностях/VO; отчёт через ORM смешан с DBAL-путём тарификации, передача дат строкой с Types::STRING выглядит хрупко. Это не ломает корректность, но до «код читается как объяснение домена» (уровень 4) не дотягивает.

Цитаты-доказательства из диффа:

  • return bcadd($cost, '0.0000005', 6); // Все значения неотрицательны: добавление половины младшего разряда реализует HALF_UP
  • return $start < $end ? ($time >= $start && $time < $end) : ($time >= $start || $time < $end);
  • ON CONFLICT (provider_code, provider_request_id) DO NOTHING
  • SELECT * FROM prices WHERE provider_code = :provider AND model_code = :model AND valid_from <= :occurred_at ORDER BY valid_from DESC LIMIT 1
  • CREATE INDEX usage_events_unrated_idx ON usage_events (id) WHERE cost_usd IS NULL
