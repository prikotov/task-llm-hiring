# PR: учёт расходов на LLM-токены

Реализовано задание из `TASK.md`: загрузка истории цен и событий
использования, тарификация точной десятичной арифметикой (bcmath, без
float для денег), CSV-отчёт по (user, model) и бонусная команда ретро-коррекции цен.

## Что сделано

### Слой хранения (PostgreSQL 17, Doctrine ORM)

Миграция `migrations/Version20261020200000.php` (единственная, схема
создаётся с нуля на чистой базе):

- `providers` — справочник; `off_peak_start_minutes / off_peak_end_minutes /
  off_peak_multiplier` — оф-пик на уровне провайдера (минуты от полуночи
  UTC — целые, множитель — десятичная строка);
- `models` — `UNIQUE(provider_id, code)`;
- `price_rows` — `UNIQUE(provider_id, model_id, valid_from)`, `valid_from`
  `TIMESTAMPTZ`, `rates` — `JSONB` со строковыми десятичными значениями;
- `usage_events` — `UNIQUE(provider_code, provider_request_id)` (ключ
  дедупликации), `cost_usd NUMERIC(20, 6)`, `price_row_id` — ссылка на
  строку, которой считалось событие (нужна для бонусного reprice),
  `status` — `pending | rated`.

Сущности: `src/Entity/{Provider,Model,PriceRow,UsageEvent}.php`.

### Импорт

- `app:prices:import <file>` — парсинг JSON (`src/Import/PricesFile`,
  `ParsedProvider`), upsert: провайдеры по `code`, модели по
  `(provider, code)`, строки цен по `(provider, model, valid_from)`
  (existing-строка перезаписывается новыми полями — повторная загрузка
  тех же сумм не меняет данных). Всё в одной транзакции (`PricesImporter`);
  некорректный JSON — `ImportException`, код 1.
- `app:usage:import <file>` — `UsageLineParser` валидирует каждую строку
  (тип/форматы, токены — целые >= 0, ts — ISO-8601 UTC с `Z`/`+00:00`),
  `UsageImporter` дедуплицирует по `(provider, provider_request_id)` в
  сравнении с БД **и внутри файла**: неизвестные события пишутся целиком в
  одной транзакции; файл с одной некорректной строкой не записывается
  вовсе; повторное событие не обновляет и не доначисляет ничего.

### Тарификация

- `Rater` + `PriceBook`: перед запуском строится в-memory-индекс
  `(provider, model) -> [строки по valid_from]`; выбор цены — строка с
  наибольшим `valid_from <= ts` («правосторонняя непрерывность»: в момент
  смены `ts == valid_from` действует новая строка — проверено событием e2).
- `CostCalculator` — формулы из пп. 2–3: `per_1m_tokens` (сумма по видам)
  и `per_1m_tokens_unified` (все токены × `rate_any`), деление на 1 000 000,
  оф-пиковый множитель, единственное округление — HALF_UP до 6 знаков.
- `MoneyCalculator` — вся арифметика bcmath: промежуточный масштаб 20
  (без промежуточных округлений), округление HALF_UP реализовано явно
  (прибавить 0.5×10^-6 до отбрасывания хвоста) — в отличие от `round()`
  PHP, который для `14.26249875` с float-арифметикой дал бы 14.262498.
- Суммы отчёта — сумма уже округлённых стоимостей событий (bcmath-сложение
  6-значных строк), без повторного округления слагаемых (п. 4).
- Unrated — не ошибка: событие остаётся `pending`, каждый запуск `rate`
  повторяет попытку для всех pending; в отчёт unrated не попадают.

### Отчёт и бонус

- `app:billing:report [--from] [--to]` — CSV в stdout (UTF-8, `\n`):
  заголовок как в примере, строки по (user, model) с `model =
  "<provider>/<code>"`, лексикографическая сортировка по (user, model),
  `TOTAL` с пустым model; `--from` включительно, `--to` исключительно.
  Unrated события исключены. Код 0.
- `app:billing:reprice <file>` (бонус) — на входе те же `prices`, что в
  `prices:import`: строка `(provider, model, valid_from)` создаётся, если
  не существует, или перезаписывается; события, рассчитанные именно этой
  строкой, пересчитываются по новым rate'ам, стоимость события
  обновляется, выводится `REPRICED_EVENTS=<n>` и `REPRICE_DELTA_USD=<d>`.
  В статистику попадают только реально сменившиеся стоимости, поэтому
  повторный запуск той же правки → `REPRICED_EVENTS=0`, дельта 0.

## Ключевые решения и допущения

1. **Окно `start == end` трактуется как пустое** (скидки нет), а не как
   24 часа: непрерывная скидка для всего дня — нефункциональный случай;
   поведение зафиксировано тестом `OffPeakWindowTest`.
2. **Границы оф-пика точны до минуты** (как и заданные «время дня»):
   `16:29:59` — пик, `16:30:00` — оф-пик, `00:29:59` — оф-пик,
   `00:30:00` — пик. Окно `[start, end)`; окно через полночь =
   `[start, 24:00) ∪ [00:00, end)`.
3. **Тарификация и reprice работают через ORM-репозитории**, а не через
   DQL-объединения по справочникам: индекс всех строк цен строится один
   раз на запуск (`PriceBook`) и переиспользуется для всех событий —
   это упрощает код и гарантирует то же поведение, что и выбор по SQL.
4. **`prices:import` — upsert со перезаписью existing-строк**, т.к.
   «история цен» в задаче — источник истины (режим «ретро-правки через
   повторную загрузку файла»); отдельный `reprice` (бонус) делает то же
   локально и показывает дельту.
5. **Колонка пользователя названа `user_id`**, а не `user`: `user` —
   зарезервированное слово PostgreSQL, а генератор SQL ORM не кавычит
   колонки автоматически (проверено: INSERT в `user` падает — пришлось
   переименовать). Вывод CSV не затрагивается.
6. **Явные `flush()` в импортёрах**: установленная версия Doctrine ORM не
   делает auto-flush перед запросами, поэтому после upsert'а сущностей
   перед следующими запросами вызывается `flush()` явно (иначе новый
   провайдер «не находится» для моделей того же файла).
7. **Целые токены — PHP-int**, суммы в отчёте до ~9e15 (BIGINT) — для
   объёмов из задания с запасом; float не используется ни для денег,
   ни для сумм токенов.
8. **Статистика `rate` считает события, изменившиеся в этом запуске**:
   `RATED` — сколько pending стало rated, `UNRATED` — сколько осталось
   pending после запуска; для каждого unrated — строка в stderr
   `UNRATED <provider>/<rid> <ts> no_price`.

## Как проверяли

Пошагово, на чистой базе (docker PostgreSQL 17 из `docker-compose.yml`):

```
make db-up && make migrate          # схема с нуля

bin/console app:prices:import fixtures/prices.json   # exit 0
bin/console app:usage:import fixtures/usage.jsonl    # exit 0
bin/console app:billing:rate                        # RATED=3 UNRATED=0
bin/console app:billing:report \
    --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z
```

Отчёт совпадает с ожидаемым из `TASK.md` побайтно (проверено `cmp`):

```
user,model,tokens_input,tokens_output,tokens_cache_read,tokens_cache_write,cost_usd
u-alice,prism/lumen-8,1200000,800000,2500000,83333,14.262499
u-alice,sfera/gyro-pro,3000000,500000,0,0,8.400000
u-bob,prism/lumen-8,2000000,1000000,0,0,11.000000
TOTAL,,6200000,2300000,2500000,83333,33.662499
```

Дополнительно проверено вручную:

- **идемпотентность**: повторные `prices:import`/`usage:import`/`rate`/
  `report` — те же данные, `RATED=0`, отчёт идентичен;
- **границы**: e2 с `ts == valid_from` новой строки (12:00:00) тарифицируется
  по новой цене (11.000000);
- **оф-пик**: событие prism в 18:00 → стоимость половинная
  (1.5M×1.5×0.5/1M = 1.125 → 1.125000); вне окна — без скидки;
- **unrated/retry**: модель без строки цен → `UNRATED ... no_price` в stderr,
  код 0; после `prices:import` файла с новой строкой `rate` досчитывает её,
  повторный `rate` → `RATED=0 UNRATED=0`;
- **дубли**: повторный `provider_request_id` (в файле и в БД) игнорируется —
  токены и стоимость не суммируются два раза;
- **ошибки**: файл с не-JSON-строкой → `app:usage:import` возвращает 1 и не
  пишет ничего в БД (транзакция);
- **reprice**: смена input-rate 1.5 → 6.0 для строки 2026-08-01 даёт
  `REPRICED_EVENTS=1`, `REPRICE_DELTA_USD=3.600000`
  (1.2M×(6−1.5)/1M), повторный запуск — `0`/`0.000000`.
