# PR: Учёт расходов на LLM-токены — консольное приложение

## Что сделано

Реализовано консольное приложение на PHP 8 + Symfony (console) + Doctrine ORM + PostgreSQL 17:

- **`app:prices:import <file>`** — идемпотентный upsert справочника
  (провайдеры по `code`, модели по `(provider, code)`, строки цен по
  `(provider, model, valid_from)`). Некорректный JSON — код 1.
- **`app:usage:import <file>`** — импорт событий (JSONL) с дедупликацией по
  `(provider, provider_request_id)` (`INSERT ... ON CONFLICT DO NOTHING`),
  код 0 даже если все строки — дубли; некорректная строка — код 1.
- **`app:billing:rate`** — тарификация всех ещё не рассчитанных событий
  (повторные попытки для unrated), stdout строго `RATED=<n> UNRATED=<m>`,
  unrated-детали — в stderr.
- **`app:billing:report [--from] [--to]`** — CSV по (user, model) с TOTAL;
  на закреплённом примере вывод совпадает байт-в-байт.
- **`app:billing:reprice <file>`** (бонус) — ретро-коррекция цены: upsert
  строк цен справочника, пересчёт всех событий, тарифицированных заменёнными
  строками; stdout ровно `REPRICED_EVENTS=<n>` и `REPRICE_DELTA_USD=<x.xxxxxx>`.
- 32 юнит-теста (Money/округление HALF_UP, границы off-peak-окна, выбор цены
  по времени, расчёт стоимости по обеим схемам тарификации): `make test`.

## Ключевые решения

**Слои** (`src/`):
- `Domain/` — сущности (Provider, Model, PriceRow, UsageEvent) и
  значения: `Money` (десятичная строка поверх bcmath, масштаб 24),
  `OffPeak` (окно + множитель), `TokenUsage` (4 вида токенов),
  `RateUnit` (enum схем тарификации);
- `Importer/` — разбор/валидация входных файлов и upsert-логика
  (общий парсер `PriceFile` используется и для импорта, и для коррекции);
- `Billing/` — `CostCalculator` (формулы обеих схем + off-peak),
  `PriceCatalog` (выбор действовавшей строки цены), `RaterService`,
  `ReportService`, `RepriceService`;
- `Command/` — тонкие консольные команды (парсинг аргументов, вывод, коды
  выхода); `Support/` — разбор ISO-8601 UTC, валидация/нормализация
  десятичных строк.

**Деньги — только десятичные строки + bcmath.** Тип `float` не
используется. Все промежуточные вычисления с масштабом 24 — без округления
(в наших формулах точность ≥ 6 знаков достаточна для точного представления
всех промежуточных величин: rate — до 6 знаков, умножение на целые токены,
деление на 10⁶, множитель — до 6 знаков). Единственное округление — стоимость
события до 6 знаков, HALF_UP, реализовано как «+ 0.0000005 и отброс хвоста»
(стоимость всегда ≥ 0). Суммы отчёта/дельты — bcmath-суммы уже округлённых
стоимостей, без повторного округления.

**Выбор цены** — строка с наибольшим `valid_from ≤ ts` (`valid_from`
включительно) среди строк модели события; отсутствует — unrated (не ошибка).

**Оф-пик** — окно `[window_start, window_end)` по времени суток UTC,
поддержка окна через полночь; вырожденное окно `start == end` трактуется как
пустое; множитель применяется к стоимости всего события.

**Идемпотентность** — справочник: upsert по ключам (повтор той же суммы в
ДБ не приводит к изменениям); события: уникальное ограничение
`(provider, provider_request_id)` + `ON CONFLICT DO NOTHING`. Рассчитанное
событие (`rated = TRUE`) больше rate-командой не трогается.

**Схема БД** — одна ручная миграция `migrations/Version20261020000001.php`
(разворачивается на чистой базе через `make migrate`):
`providers`, `models`, `price_rows` (уник. `(provider, model, valid_from)`),
`usage_events` (уник. `(provider, provider_request_id)`, `cost
numeric(28,6)`, `applied_price_valid_from`). При каскадном сбросе/повторном
развёртывании схема чистая; миграция пишется в `up()`/`down()`.

**Отчёт** — выборка рассчитанных событий за период `[from, to)` (включительно/
исключительно) и агрегация в PHP: суммы токенов — целые, суммы стоимостей —
bcmath; сортировка строк по (user, model) лексикографически; `model` печатается
как `<provider>/<code>`; `cost_usd` — ровно 6 знаков; `TOTAL` — по отчёту.
Unrated-события в отчёт не попадают.

**Реализация бонуса (ретро-коррекция цены)** — при расчёте события
фиксируется ключ применённой строки цены (`applied_price_valid_from`).
`app:billing:reprice` (1) проверяет существование провайдера/модели
**в справочнике БД** (секции providers/models в файле коррекции не нужны),
(2) upsert-ом подставляет/добавляет строки цен, (3) ищет все `rated`
события, чей ключ применённой строки совпал с ключами из файла, (4)
пересчитывает их по актуальной строке цены (в т.ч. с учётом
off-peak), перезаписывает `cost` и суммирует дельту. Остальные
рассчитанные события не изменяются. Механизм — прямая перезапись
стоимости (журнал корректировок/компенсации в задаче не требовался;
итоговый `report` отражает новые суммы без задвоений). Повторный запуск
correction файла — не меняет стоимости, дельта 0.000000.

## Допущения (неоговорённые детали)

- Цена: секции `providers`/`models` в файле импорта могут отсутствовать
  (считаются пустыми); секция `prices` обязательна и непустая. В файле
  коррекции секция `prices` может быть пустой.
- Строки цен и `rates`/`multiplier` — десятичные строки ≥ 0, до 6 знаков
  после точки; при записи нормализуются до ровно 6. `currency` — строка
  ≤ 3 символов (проверка формата кода значения не выполняется).
- Строка цены (и модель) в файле импорта могут ссылаться на
  провайдеров/модели, загруженные ранее (в т.ч. из предыдущих
  файлов); отсутствие ссылки при полном отсутствии — ошибка импорта (код 1).
- Событие: все 9 полей обязательны. Пустые строки JSONL (в т.ч.
  завершающий перенос) игнорируются. `ts` — строго `YYYY-MM-DDTHH:MM:SSZ`
  (допустимы доли секунды до микросекунд); другие timezone-префиксы
  считаются некорректными.
- Событие с неизвестными/ещё не загруженными `provider`/`model` не
  ошибка импорта, а unrated-событие (ценовой/справочный поток может
  опережать журнал).
- `REPRICED_EVENTS` — число всех пересчитанных затронутых событий, в т.ч.
  тех, чья стоимость не изменилась (дельта по ним 0).
- Отчёт строится как сумма по группе; `TOTAL` — сумма по всем группам
  (эквивалентна сумме по всем событиям отчёта).
- Окно off-peak, задающее `start == end`, трактуется как отсутствие
  скидки (в спецификации такого случая нет).
- Время хранится и читается в UTC (колонки `TIMESTAMP`; значения всегда
  UTC); сравнение `valid_from` и `ts` по наивным timestamp — эквивалентно
  сравнению UTC-моментов.

## Как проверяли

Чистая база + миграция:

```bash
make db-up
make migrate
```

Приёмка (шаги 3–5 TASK.md, на чистой БД):

```bash
bin/console app:prices:import fixtures/prices.json
bin/console app:usage:import fixtures/usage.jsonl
bin/console app:billing:rate            # RATED=3 UNRATED=0
bin/console app:billing:report --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z
#   вывод сравнен байт-в-байт с примером (cmp) — совпадает
# повтор той же тройки команд — состояние и отчёт не меняются
```

Дополнительные проверенные сценарии (вручную, на тестовой копии данных):
- off-peak: начало окна включительно (16:30 — скидка), окончание
  исключительно (00:30 — пик), окно через полночь (00:15 — скидка);
- unrated: событие раньше первой цены — `RATED=… UNRATED=1` + строка в
  stderr; после импорта пропущенной цены повторный `rate` рассчитал его;
- смена цены ровно в `valid_from`: e2 тарифицированной новой строкой;
- дельта репрайсинга: ручные значения (в т.ч. отрицательная);
  повторный запуск correction файла — дельта 0.000000;
- коды ошибок (1) и понятные сообщения в stderr: плохой JSON,
  не-JSONL строка, отсутствующий файл, отрицательные токены,
  не-UTC `ts`, корректный reprice-файл на отсутствующую модель.

Тесты: `make test` (32/32).

## Отступления от каркаса / изменения

- **Изменённые/добавленные файлы каркаса: нет** (изменения — `src/`,
  `tests/`, `migrations/`, плюс данные в `var/`).
- **Зависимости**: не добавлялись — используется только то, что уже в
  `composer.json` (`doctrine/orm`, `doctrine-migrations-bundle`,
  `symfony/*`, `ext-bcmath`).
- В `migrations/` одна миграция `Version20261020000001.php` — полная
  начальная схема (4 таблицы, ограничения, индексы на все ключи и `ts`),
  применяется на чистой базе одним `make migrate`.
- Консольные команды зарегистрированы автоконфигурацией
  (`#[AsCommand]`, autowire из `config/services.yaml` — файл не переделывался).
- Управление схемой — штатное: `make migrate` (doctrine-migrations).
