# PR: консольное приложение учёта расходов на LLM-токены

## Что сделано

Полная реализация TASK.md на PHP 8.4+ / Symfony Console / Doctrine ORM 3 + DBAL 4 (PostgreSQL 17), включая бонусный функционал.

### Команды

| Команда | Назначение |
|---|---|
| `app:prices:import <file>` | Импорт справочника цен (JSON): провайдеры (с оф-пиком), модели, строки цен. Апсёрт: провайдеры/модели — по коду, строки цен — по `(provider, model, valid_from)` (повторный импорт идемпотентен). |
| `app:usage:import <file>` | Импорт событий использования (JSONL) с дедупликацией по `(provider, provider_request_id)`. Файл читается целиком до записи, импорт — в одной транзакции; ошибка любой строки отбрасывает весь файл (код возврата 1). |
| `app:billing:rate` | Тарификация всех pending-событий. Событие считается строкой, чей `valid_from <= ts`, с самым поздним `valid_from` (момент смены цены действует уже по новой строке). Неразрешённые события не прерывают запуск: их список выводится в stderr с причиной, код возврата 0. |
| `app:billing:report --from=… --to=…` | CSV в stdout: одна строка на `(user, model)` в периоде `[from, to)` (отсортировано по user, model) + строка `TOTAL` (user/model пустые). Суммы построчно и в TOTAL — **сумма уже округлённых** стоимостей событий, без повторного округления. Период с пустым набором событий — только заголовок и `TOTAL` нулей. |
| `app:billing:reprice <file>` | **Бонус.** Файл того же формата с исправленными строками цен. Строка с тем же `(provider, model, valid_from)` обновляется; события, рассчитанные именно по ней (у события хранится ссылка на строку), пересчитываются в той же транзакции. Вывод: `REPRICED_EVENTS=<n>` и `REPRICE_DELTA_USD=<delta>` (новая сумма − старая, 6 знаков). Повторный запуск с тем же файлом — `REPRICED_EVENTS=0`, `DELTA=0.000000` (идемпотентно). |

### Доменная модель

- `catalog.provider` — код/имя + оф-пик: минуты от полуночи `window_start` (включительно), `window_end` (независимо от порядка, т.е. `16:30–00:30` корректно переходит через полночь), десятичный множитель; `null` — скидки нет.
- `catalog.model` — код модели в рамках провайдера (уникально).
- `catalog.price_line` — `valid_from`, `unit` (`per_1m_tokens` | `per_1m_tokens_unified`), `rates_json` — ставки **десятичными строками** (в JSON и в БД — строки, не числа), уникальный ключ `(provider, model, valid_from)`.
- `usage.usage_event` — payload события, `status` ∈ {`pending`, `rated`}, `cost` (bcmath-строка, 6 знаков), `price_line_id` — строка, по которой считалось (основа для reprice), unique `(provider, provider_request_id)`.

### Ключевые решения

1. **Точность денег.** Все денежные вычисления — bcmath (масштаб 20, ≥ требуемых 16); float в домене не используется. Округление ровно одно — `Money::roundHalfUp(..., 6)` по HALF_UP; реализовано через «+half на рабочем масштабе → отсечение», что корректно и для отрицательных значений, и для длинных дробей. Стоимость события = `sum(tokens_i × rate_i) / 1e6` (per-1m) или `total_tokens × rate_any / 1e6` (unified), затем ×off-peak multiplier, затем округление.
2. **Выбор тарифа.** `PriceLineRepository::findApplicable(provider, model, ts)` — все строки с `valid_from <= ts`, берётся максимум по `valid_from`; `valid_from` включительно (проверено тестом на моменте смены цены 12:00:00).
3. **Дедупликация приёма.** Ключ `(provider, provider_request_id)` закреплён уникальным индексом БД; все строки файла обрабатываются в одной транзакции (с промежуточным flush, чтобы дубли **внутри** одного файла тоже находились); ошибка любой строки откатывает всю транзакцию — файл не принимается частично. Кроме того, нарушение уникальности (гонка) ловится отдельно и считается дубликатом, а не ошибкой.
4. **Reprice по содержательной ссылке.** Событие хранит `price_line_id`, поэтому «заменённой строкой» (тот же `valid_from`) однозначно определён пересчитываемый набор; `id` строки при коррекции не меняется, события других ценовых окон не трогаются.
5. **Импортер цен как апсёрт по содержимому.** Строки цен сверяются по сигнатуре (`unit + rates`): при совпадении запись не изменяется (не трогает `updated_at`-подобные эффекты и не пересчитывает ничего).
6. **CLI-контракт.** Все ошибки входа — человекочитаемые `ERROR`-сообщения в stderr и код 1; успех — 0. Неизвестные provider/model в событии — не ошибка импорта (событие принимается, а при тарификации помечается unrated).

## Отступления от каркаса и допущения

Каркас репозитория (компоненты, DI, Makefile, docker-compose, конфиги) изменён **минимально**; `composer.json`/`composer.lock` не менялись — новые зависимости **не добавлялись** (используются только то, что было в `vendor/`: doctrine, symfony/console, bcmath).

1. **Колонка `user_code` вместо `user` в `usage_event`.** `user` — зарезервированное слово PostgreSQL; Doctrine ORM при генерации INSERT не кавычит идентификатор, из-за чего SQL ломался (`ERROR: syntax error at or near "user"`). Свойство сущности осталось `user`, в БД колонка `user_code`, в CSV-отчёте заголовок `user` — без изменений. Альтернатива (кавычить колонку в схеме) дала бы расхождение `schema:validate` «наизнанку».
2. **`OffPeakWindow` как чистый calculator, а не «окно-сущность».** Окно хранится в `provider` как минуты от полуночи; класс `App\Domain\Pricing\OffPeakWindow` — только логика `isOffPeak(ts)` (включая переход через полночь). Это упрощает миграции и сравнения.
3. **`rates` в JSON — строки.** ТЗ требует 6 знаков после точки; числа JSON теряли бы точность (0.300000 → 0.3), поэтому ставки импортируются как десятичные строки и так хранятся (`rates_json`).
4. **Период отчёта `[from, to)`.** `--from` включительно, `--to` exclusively (как и время действия тарифа, кроме `valid_from`). Требовалось «в точности» примерное значение — так и есть.
5. **`app:billing:report` с пустым набором событий** печатает заголовок и строку `TOTAL` с нулями (а не просто заголовок), код 1 — если `--from >= --to`; без границ считается всё.
6. **`app:billing:rate` с unrated — код 0** (рассчитал, что смог; unrated — диагностика в stderr). Это осознанное допущение: повторный импорт цен → повторный `rate` добирает хвост, и это показано самопроверкой.
7. **Импорт цен игнорирует «пустые» секции**, но требует корректности всех присутствующих: если провайдер/модель строки цен не найден ни в файле, ни в БД — ошибка `неизвестная модель «…»`, файл не принимается.

## Как проверяли

Локально (PostgreSQL 17 через `docker-compose`, порт из `.env`):

```bash
make db-up                                  # 1. чистая база
make migrate                                # 2. схема на чистой базе (миграция Doctrine)
bin/console app:prices:import fixtures/prices.json
bin/console app:usage:import fixtures/usage.jsonl
bin/console app:billing:rate
bin/console app:billing:report \
  --from=2026-09-01T00:00:00Z --to=2026-10-01T00:00:00Z   # 4. байт-в-байт пример
# 5. повторный импорт + rate + report → результат идентичен
```

Полученный отчёт совпал с эталоном из ТЗ байт-в-байт:

```csv
user,model,tokens_input,tokens_output,tokens_cache_read,tokens_cache_write,cost_usd
u-alice,prism/lumen-8,1200000,800000,2500000,83333,14.262499
u-alice,sfera/gyro-pro,3000000,500000,0,0,8.400000
u-bob,prism/lumen-8,2000000,1000000,0,0,11.000000
TOTAL,,6200000,2300000,2500000,83333,33.662499
```

`make test` — 21 тест (76 ассёртаций), включая:
- точные значения e1/e2/e3 (14.262499 / 11.000000 / 8.400000) и пересечение `valid_from` (12:00:00 → новая строка);
- оф-пик: вход в окне (`16:30`), переход через полночь (`00:29`), граница конца окна (`00:30` → пик);
- HALF_UP-округление (0.9000005 → 0.900001);
- валидация ISO-8601 (отклоняются `2026-02-30`, `+02:00`, без `Z`), `HH:MM` и десятичные ставки.

Дополнительно вживую (вне юнит-тестов): повторный `reprice` того же файла идемпотентен; unrated (event `t4` — неизвестная модель) не блокирует rate, а после догрузки цен пересчитывается; импорт с битой строкой отбрасывает файл целиком (код 1).
