# Карта знаний PHP (да/нет): blueprint

Зонд **чистых** знаний модели о PHP, по мотивам теста Карпаты
«Land or Water?» (см. «Происхождение» ниже): каждая клетка карты — один
независимый сырой запрос «утверждение → да/нет», ответы рисуются картинкой.
Зелёная клетка — верный ответ, красная — неверный, серая — ответ не удалось
разобрать (в нём нет «да»/«нет»). Модель отвечает только из весов: без
system prompt,
файлов, инструментов и истории между клетками.

## Происхождение: тест Карпаты «Land or Water?»

История наводки (записано 2026-11-06, когда родилась идея карты знаний PHP):

- **Первопроходец — Henry (@arithmoquine), август 2025**, Substack-пост:
  сетка широт/долгот по всему глобусу, модели скармливается координата
  текстом, вопрос «Land or Water?». ~40 моделей; ответ читается по
  logprob двух целевых токенов; вероятности рисуются пикселями
  равнопромежуточной карты (с весом по cos широты).
- **Celeste (@celestepoasts)** собрала карту из двенадцати Claude-моделей
  (точность с весом по площади: Opus 5.5 thinking — 99.0%, слабые —
  ниже базовой линии).
- **Andrej Karpathy** процитировал эту карту с формулой: *«Simply ask an
  LLM "Land or Water?" and give it a latitude and longitude coordinate as
  text. Ask 16,200 times, plot as image. The models know.»* — сетка 2°
  по обеим осям, 90×180 = 16 200 точек. Именно его формулировка сделала
  тест знаменитым: география мира неявно закодирована в весах модели.
- **Открытая репродукция — Favio Vazquez** (`github.com/FavioVazquez/land-or-water`):
  open-weight модели на CPU, ключ ответов — маска суши Natural Earth.
  Лучшие открытые модели рисуют грубые континенты, но **не дотягивают до
  константного базлайна «всегда вода»** (66.8% точек по счёту, 71.1% с
  весом по площади — Земля в основном океан).

Уроки теста, которые мы переносим на PHP:

1. **Бинарный текстовый вопрос по плотной сетке → картинка** — дешёвый и
   наглядный зонд латентных знаний; карту можно оценивать глазами.
2. **Константный базлайн обязателен.** «Всегда вода» у Карпаты, «всегда
   да» у нас: при балансе 50/50 модель обязана уйти от 50%, иначе её
   ответы ничего не знают, а только следуют формату.
3. **Формат ответа — главный источник артефактов.** У открытых моделей
   Карпаты главная болезнь — потерянный минус у отрицательных координат
   (квадрант объяснял 71% разброса ответов вместо географии); одна модель
   ответила «Water» на 16 199 точках из 16 200. Парсинг и дегенеративные
   ответы надо видеть отдельно, не смешивать со знанием.
4. **После ~97% точность меряет «береговую линию»** — детали, а не знание.

## Формат карты

- **Одна клетка = один независимый запрос.** Клетка карты — одно
  утверждение о PHP. Запрос — единственное сообщение чата: `<утверждение>
  Верно или неверно? Ответь одним словом: «да» или «нет».` Без system,
  без истории между клетками, без инструментов — как координата у Карпаты.
  Хранить историю не нужно: у клеток нет контекста, изоляция полная.
- **Карта = сетка «темы × уровни».** Строки — 12 тем языка (синтаксис,
  типы, строки, массивы, функции, ООП, интерфейсы/трейты, исключения,
  пространства имён, ссылки и области видимости, генераторы/SPL,
  конфигурация и безопасность), столбцы — 8 уровней от базовых фактов к
  тонкостям. Порядок уровней — приближённый градиент, а не строгая шкала
  сложности; читайте карту, помня об этом.
- **Цвет клетки = верность ответа**: зелёный — верно, красный — неверно,
  серый — ответ не разобран. Отдельно от знания формат ответа — тоже
  измерение (урок 3 Карпаты).
- **Параметры — как в собесах**: дефолтные параметры генерации, seed не
  фиксируется; `think: off` (стандарт локальных собесов); `keep_alive:
  10m` внутри прогона (клетки независимы, префиксы не шарятся — кэш тут
  просто держит веса загруженными), выгрузка модели до и после прогона.
- **Парсинг строгий.** Первое слово нормализованного ответа: «да» (yes)
  → да, «нет» (no) → нет. Синонимы («верно», «истина»…) форматом не
  считаются: если первое слово не да/нет, ищем первое подходящее слово —
  ответ засчитывается с пометкой «поздний парсинг»; если и его нет —
  клетка серая. Серые клетки в строгой точности считаются неверными, но
  доля разобранных показывается отдельно.
- **Thinking не парсится**: поле `thinking` ollama (и `<think>`-блок в
  контенте, если модель игнорирует think off) отсекается до парсинга.
- **System-промпт и JSON** (решение владельца, 2026-11-06): протокол
  теста перенесён из хвоста запроса в **system-сообщение** — фиксированная
  рамка («Ты проходишь тест на знание PHP… Отвечай строго в JSON…»),
  одинаковая для всех моделей и прогонов (сравнимость). Каноничное место
  инструкций; эффект подтверждён прогоном: huihui 73.2% → 84.8%
  (+11.6 п.п.) на том же вопроснике v3. User-сообщение клетки — только
  вопрос с коротким суффиксом типа («Верно или неверно?» / «Ответь
  результатом…»). Ответ строго в JSON `{"answer": ..., "пояснение":
  "..."}`; парсинг: первый сбалансированный `{...}` (мягкий ремонт
  одиночных бэкслешей в путях); флаг `json_ok` в CSV; при невалидном
  JSON — текстовый фолбэк с пометкой late (комплаенс huihui 27B:
  110/112 = 98% на текстовом JSON-суффиксе).
- **Кэш префикса: эксперимент 2026-11-06**. Ожидалось, что общий system
  будет кэшироваться движком — не сработало: ollama 0.40 переиспользует
  KV-кэш **только для продолжений** (накопительный чат: cached 50/85
  подтверждены), а независимые запросы с общим system перепросчитывает
  полностью (prompt_eval 169/176/167, cached 0 на каждый). Цена для
  локальных моделей несущественна (~140 ток × ~0.1 c на клетку, модель
  и так загружена). Для дорогих облачных моделей (Opus и др.) кэш
  префикса работает **на стороне провайдера** независимо от нашего
  движка: OpenAI — автоматом (общий префикс ≥1024 ток, −50% на хит),
  Anthropic — явно через cache_control (чтение ~−90%), т.е. system-промпт
  там окупается и попадёт в кэш.
- **Пояснение модели фиксируется** (решение владельца, 2026-11-06):
  берётся из JSON-поля «пояснение» (текстовый фолбэк — из хвоста raw).
  Пояснение не влияет на вердикт, пишется в session, CSV и отчёт
  (тултип + «Все утверждения») и служит **сигналом двусмысленности
  клетки и кросс-языковой контаминации**: систематические возражения —
  повод переписать клетку; факты чужих языков в пояснениях — диагноз
  «путает с JS/Rust/Python», а не «не знает PHP» (run-08 huihui: print
  «возвращает None», '5'+5 «конкатенация как в JavaScript»,
  ZeroDivisionError из Python, оператор is из C#).
- **Протоколы ответов.** Chat-модели отвечают через ollama `/api/chat`
  (текст «да»/«нет», строгий парсинг). Decision-модели (clef, clef-flash)
  chat не умеют — они отвечают родным протоколом `/v1/systemone`
  (`runner_map.py --protocol decision`, формат state — по образцу
  `build_state` из `interview/score.py`): сервис возвращает вероятность
  верности утверждения (noul), клетка — «да» при p ≥ 0.5. Вероятность
  сохраняется в клетку (поле `p`) и видна в подсказке отчёта — это наш
  аналог logprob-семплирования Карпаты: знание читается из вероятности,
  а не из текста. Уровень рассуждений к decision-протоколу не применяется
  (в session такой прогон помечен «— (decision-протокол)»).

## Вопросник

- `questions.json` — объект `{"version": N, "questions": [...]}`; правила
  версионирования как в собесах: изменения набора — новая версия, старая
  хранится рядом (`questions.v1.json`), версия пишется в `session.json`.
- **Состав v5 (ось зон — по решению владельца)**: **14 строк × 8 уровней
  = 112 клеток в одной матрице** — один прогон содержит все вопросы
  (запрет владельца на раскидывание вопросов по разным прогонам).
  **Три зоны знаний**: зона 1 «База PHP» — 12 строк тем языка (96
  клеток: 72 да/нет + 24 recall «только результат», вневременное ядро
  8.x); зона 2 «PHP 8.4–8.5» — 8 клеток текущей эры; зона 3 «Будущее:
  8.6+, trunk» — 8 клеток (пары «принятый RFC vs правдоподобная ложь»
  зондируют галлюцинации будущего). Зона «PHP 7.0–8.1» удалена в v5 по
  решению владельца: знания о версиях накапливаются назад, данные о 7.x
  в весах в избытке — зона почти не дискриминирует модели (huihui: 75%
  на прошлом при 25% на эре); свежесть меряется эрой 8.4–8.5 и будущим.
  У каждой клетки тег `kind`: fact / myth (ловушка) / version /
  inference и поле `zone`.
- **Полярность сбалансирована по столбцам** (фикс конфаунда v1: нечётные
  уровни почти всегда «да», чётные — «нет», и столбец мерял аквиесценцию):
  оптимизатор раскладки довёл Σ|да−нет| verify до минимума при сохранении
  приблизительного градиента «база → тонкости».
- **Аудит применён**: клетка про приоритет конкатенации переписана — в v1
  наш ответ был фактической ошибкой (подтверждена php 8.5 тремя моделями
  независимо); тривиальные дубли из консенсус-списка аудита заменены;
  заметки уточнены (суперглобалы, parse error для use в функции, Warning
  vs TypeError, __clone для readonly). Версионные факты из основных тем
  переехали в версионные строки, их места заняли новые не-версионные
  вопросы.
- Утверждения формулируются под **актуальный PHP 8.x**; версионные
  проверяются на php.net перед сериями. Каждая клетка имеет поле `note`;
  обоснования прошли аудит трёх моделей и эмпирическую проверку на php 8.5.
- Утверждения-ловушки (правдоподобные «мифы») — обязательная часть
  набора: на них модель чаще всего и горит красным.
- **as_of** в шапке вопросника — дата снимка версионных строк
  (2026-11-06; источник wiki.php.net/rfc). Интерпретация версионных строк
  — **интервал cutoff**: между последними уверенно верными и первыми
  неверными клетками по возрастанию эры (пример huihui 2026-11-06:
  знает 8.0/8.4-property-hooks, не знает 8.4-array_find и всё после 8.4 →
  cutoff ≈ конец 2024). Пилотные файлы `questions-recall.json` и
  `questions-versions.json` (слепки до объединения) хранятся для
  пересборки отчётов run-04/run-06; живой набор — один: `questions.json`.

## Метрики и отчёт

- **Точность** — доля верных клеток (серые — неверные), отдельно: общая,
  по темам, по уровням.
- **Доля ответов «да»** против баланса 50/50 — детектор дегенеративных
  ответов (аналог «always water» у Карпаты: константный ответ обязан
  показать ~50% и пустую карту без континентов).
- **report.html** — карта (сетка клеток с всплывающими подсказками:
  утверждение, ответ модели, верный ответ, note), точность по темам и
  уровням, приложение со всеми 96 парами «утверждение → ответ» для
  вычитки. Отчёт самодостаточен: не содержит внутренних адресов (они в
  `session.json`).
- **Стоимость прогона** — время и токены фиксируются на каждый вопрос
  (`duration_s`, `eval_count`, `prompt_eval_count`,
  `prompt_eval_cached_count` в `session.json` и `answers.csv`) и
  суммарно на прогон (`totals` в `session.json`; чипы отчёта; в режиме
  `--model-dir` — колонки think/время/токены в таблице прогонов).
  Прогоны разных моделей или одного уровня рассуждений сравниваются
  «сколько стоит решение теста»: секунды и входные/выходные токены
  при данном think.
- **Файлы прогона** `models/<модель>/knowledge-map/run-XX/`:
  `session.json` (условия + все пары вопрос-ответ с таймингами,
  прогрессивная запись — крах не теряет серию), `answers.csv` (тот же
  разбор одной строкой на клетку — для анализа кодом), `report.html`,
  `summary.md`.

## Устойчивость: серия прогонов и тепловая карта (этап 2)

1. Прогон = полный опрос с нуля, модель выгружена перед стартом. Серия —
   **3 прогона на один уровень рассуждений** (число уточним, когда
   закончим отладку теста).
2. **Уровни рассуждений не смешиваются.** Тепловая карта и флипы
   считаются только внутри одного think: прогоны off и low — разные
   качества, «флип» между ними мерил бы смену режима, а не устойчивость
   знания. `build_map_report.py --model-dir` отказывается строить
   смешанную карту — при нескольких уровнях в папке требует
   `--think <уровень>` (правило появилось 2026-11-06 после того, как
   первый compare смешал off/low/medium и был удалён).
3. Клетка тепловой карты — **доля верных ответов по серии**: стабильная
   клетка (0% или 100%) окрашивается насыщенно, «флипующая» (меняется от
   прогона к прогону) — промежуточным цветом с маркером.
4. Считается число флипов на клетку (нестабильность знания) и разброс
   точности по прогонам — как устойчивость ответов в собесах.
5. Сравнение моделей — по средней точности и по картам глазами: где
   «континенты знаний» рваные у всех, а где у модели дыры.
6. Лестница уровней (off/low/medium/xhigh — где модель умеет) сверяется
   **уровень против уровня**, таблицей метрик: точность, время и токены
   из `totals` каждого прогона; карты уровней никогда не объединяются.
   Для thinking-булевых моделей (gemma) уровни неразличимы.

## Слои A/B: верификация и продукция

- **Слой A (verify)** — основной `questions.json`: утверждение → да/нет.
  Меряет распознавание и дискриминацию; угадывание гасится балансом 48/48
  и серией прогонов, но одиночная клетка даёт лишь бит, и «не знает» не
  отличить от «поддался риторике».
- **Слой B (recall)** — `questions-recall.json`: вопрос просит **сам
  результат** — да/нет, число или строку («Что выведет…», «Какая
  минимальная версия…», «Какая функция…»). Протокол клетки — **ответ без
  рассуждений**: «Ответь только сам результат одним значением (число,
  строка или да/нет), без пояснений» (решение владельца, 2026-11-06).
  Угадывание 1/N вместо 1/2: для «что выведет» — почти ноль.
- **Грейдер объективен**: эталон recall-клетки вычисляет php 8.5 машины
  теста (`grader.php` — сниппет в клетке; все сниппеты проверяются до
  прогона), для невычислимых — `accept`-список допустимых значений.
  Зачёт: нормализованный эталон (нижний регистр, без кавычек, сжатые
  пробелы) входит в нормализованный ответ; строгое равенство считается
  отдельным флагом (`strict`) в CSV.
- **Пары A+B** на одном факте — отдельная ось интерпретации: зелёная
  да/нет + красная recall = «знает правило, но не может применить».
- Recall-клетки не применимы в decision-протоколе (noul даёт вероятность
  утверждения, не значение) — decision-модели тестируются слоем A.
- Первый пилот слоя B: huihui-ai:pi-100k, 24 клетки (questions-recall v1).
  Уже на смооке поймал то же заблуждение, что и да/нет-версия, но через
  продукцию: «(int) '42abc'» → «ошибка» (верно: 42).

## Запуск

    # один прогон (карта зелёный/красный)
    python3 knowledge-map/runner_map.py --model huihui-ai:pi-100k --runs 1
    python3 knowledge-map/runner_map.py --model gemma4:26b --runs 1 --limit 8  # smoke
    python3 knowledge-map/build_map_report.py --run-dir models/huihui-ai-pi-100k/knowledge-map/run-01

    # decision-модели (clef-flash): вероятностный протокол /v1/systemone
    python3 knowledge-map/runner_map.py --model clef-flash:latest --runs 1 --protocol decision

    # слой B (recall): «что выведет/какая версия», эталон — php 8.5
    python3 knowledge-map/runner_map.py --model huihui-ai:pi-100k --runs 1 \
        --questions knowledge-map/questions-recall.json

    # этап 2: тепловая карта по всем прогонам модели
    python3 knowledge-map/build_map_report.py --model-dir models/huihui-ai-pi-100k/knowledge-map

Сервер моделей и пути — из env (`OLLAMA_BASE_URL`, `.env.local`
подхватывается при старте), как во всех раннерах workspace.
