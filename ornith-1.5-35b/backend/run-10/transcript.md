## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

# Важные возможности PHP 8+ для чистого кода

Отличный вопрос. Выберу те функции, которые реально влияют на качество кода — не просто «крутые фичи», а те, что помогают избегать ошибок и делать намерения явными.

## 1. Match — там, где switch уже неактуален

`match` не допускает «проваливания» (fallthrough) и сравнивает строго, поэтому меньше ошибок.

```php
// Было
$status = match($httpCode) {
    200, 201 => 'ok',
    404 => 'not_found',
    default => 'error',
};

// Нельзя случайно забыть break и уйти в следующий case
```

## 2. Named arguments — читаемость и стабильность вызовов

```php
// Плохо: порядок аргументов — скрытая ловушка
new Address('Москва', 'Ленина', 15, true);

// Хорошо: намерение в коде
new Address(
    city: 'Москва',
    street: 'Ленина',
    building: 15,
    hasElevator: true,
);
```

## 3. Constructor promotion — убирает boilerplate

```php
// Было
final class User {
    public function __construct(
        private string $name,
        private Carbon $createdAt,
    ) {}
}

// (в PHP 8.0+ поля уже приватные автоматически)
```

## 4. Enumerations — типизированные константы

Заменяют «магические строки» и static-константы на типобезопасную конструкцию.

```php
enum OrderStatus: string {
    case Pending = 'pending';
    case Paid = 'paid';
    case Cancelled = 'cancelled';

    public function isFinal(): bool {
        return $this === self::Cancelled;
    }
}

// Нельзя передать произвольную строку — только значения из enum
```

## 5. Nullsafe operator — явная работа с null

```php
// Было
$country = null;
if ($user->getAddress() !== null) {
    $country = $user->getAddress()->getCountry();
}

// Стало — короче и читается как намерение
$country = $user?->getAddress()?->getCountry();
```

## 6. First-class callable syntax — чище передаём функции

```php
// Было
array_map(function ($x) { return strlen($x); }, $names);

// Стало
array_map(strlen(...), $names);
```

## 7. Enums + Match — вместе дают чистую логику

```php
function discount(OrderStatus $status): float {
    return match($status) {
        OrderStatus::Paid => 0.1,
        OrderStatus::Cancelled => 0.0,
        OrderStatus::Pending => 0.05,
    };
}

// PHP гарантирует, что все варианты перебраны
```

## 8. Attributes — метаданные без магических строк

```php
#[Route('/users/{id}', methods: ['GET'])]
public function show(int $id): Response
```

## Что я бы выделил как самое важное

Если выбирать **три**, которые сильнее всего влияют на чистоту и надёжность:

1. **Match** — устраняет целые классы багов с `switch`
2. **Enums** — делают намерения типобезопасными
3. **Named arguments** — повышают читаемость вызовов

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

# Система типов в PHP

Хорошая тема, потому что PHP здесь — это мини-драма с компромиссами. Язык шел к строгой типизации долго и до сих пор делает это осторожно. Разберём по порядку.

## Как устроена типизация вообще

PHP — **слабо типизированный** язык с **динамической** типизацией (тип имеет значение, а не переменная). Но есть важное уточнение: есть *loose* и *strict* режимы сравнения и приведения, и это разные вещи.

Ключевой момент: PHP делает **нотенлы приведения (coercion)** — нетипизированные значения автоматически приводятся к ожидаемым типам в большинстве случаев. `strict_types` меняет это поведение для **встроенных** функций и параметров.

## strict_types — что на самом деле даёт

Объявляется в **самом начале** файла, сразу после `<?php`:

```php
<?php
strict_types=1;

function sum(int $a, int $b): int {
    return $a + $b;
}

sum(1, 2);        // OK
sum('1', '2');    // TypeError в strict-режиме
sum(1.5, 2);      // TypeError: float не int
```

Важные нюансы:

- Работает **только для скалярных** типов (int, float, string, bool, null) и array, object. Для массивов и объектов проверка строгая всегда.
- Влияет на **передачу аргументов** и **возвращаемые значения**, но не на операции внутри.
- Действует **лоально** — в каждом файле свой режим, даже если другой файл его подключил.

## Как ведут себя приведения (самая «интересная» часть)

Давай посмотрим на то, что удивляет больше всего. Вот классический пример:

```php
function check(int $value): void {}

check(42);        // OK
check(42.0);      // OK! float 42.0 становится int 42
check(3.14);      // TypeError
check('42');      // OK! строка '42' становится int 42
check('abc');     // TypeError
check(true);      // OK! true -> 1
check(null);      // TypeError
```

Обрати внимание на `42.0` и `'42'` — в strict-режиме PHP всё равно приводит их, потому что они «представимы» как int без потери данных. Это не баг, а осознанное поведение: **приведение без потери данных разрешено даже в strict-режиме**.

А вот что точно вызывает(TypeError):

```php
check('42px');    // нельзя вывести число из строки
check([]);        // пустой массив -> 0 в loose, но TypeError здесь
check(new \DateTime()); // объект -> TypeError
```

## Ловушки на практике

### 1. Сравнение loose vs strict — легендарная ловушка

```php
// loose (==) — классика багов
0 == 'abc';       // true! строка приводится к 0
'' == 0;          // true
'1' == '01';      // true
'10' == 10;       // true

// strict (===) — всё честно
0 === 'abc';      // false
'' === 0;         // false
'1' === '01';     // false
```

Рекомендация: **всегда использовать `===`** в условиях. Это одна из самых частых причин багов в старом PHP-коде.

### 2. Loose comparison с уязвимостями безопасности

```php
// УЯЗВИМО: comparison with hash
if (sha1($input) == $knownHash) { ... }

// '0e12345' — строка, начинающаяся на 0e, воспринимается как 0×10^12345
// == '0e...' может дать неожиданные true
```

Это реальный класс уязвимостей. Строгое сравнение `===` здесь спасает.

### 3. array_search и null-ловушка

```php
$found = array_search(0, $array);
if ($found === false) { /* ... */ }

// array_search возвращает false, если не найдено,
// но ключ 0 тоже валиден!
```

### 4. Float precision

```php
$a = 0.1 + 0.2;
$a === 0.3;       // false! из-за представления float
abs($a - 0.3) < 0.0001; // правильный способ сравнения
```

## Где типизация спасает

### Пример 1: Защита от неверных данных на входе

```php
function calculateInterest(float $amount, float $rate): float {
    return $amount * $rate;
}

// До strict-режима можно было случайно передать '50%'
// и получить странную логику приведения
```

### Пример 2: Nullability вместо магии

```php
// Плохо: неясно, может ли быть null
function findUser(?int $id): ?User { /* ... */ }

// Хорошо: ? явно показывает, что результат может отсутствовать
```

### Пример 3: Readonly properties (PHP 8.1)

```php
final class Money {
    public function __construct(
        public readonly float $amount,
        public readonly string $currency,
    ) {}
}

$money->amount = 100; // Error: cannot modify readonly property
```

## Где типизация «удивляет» (подвохи)

### 1. int vs float при больших числах

```php
$x = 9223372036854775807; // max int (PHP_INT_MAX)
$x + 1;                    // float! переполнение в float
```

### 2. Strict types в подключаемых файлах

```php
// В main.php: strict_types=1
// require 'library.php';
// Если в library.php нет strict_types=1,
// его функции работают в loose-режиме для аргументов
```

Это частая причина путаницы в больших проектах — режим зависит от каждого файла отдельно.

### 3. Coercion «за углами»

```php
function padRight(string $s, int $length): string {
    // ...
}

padRight('hello', 10);      // OK
padRight('hello', '10px');  // TypeError
padRight('hello', '10');    // OK! приводится к int
```

---

## Резюме: что взять на практику

1. **Всегда `strict_types=1`** в новых файлах.
2. **Всегда `===`** вместо `==`, кроме осознанных случаев.
3. **Не доверяй приведению строк** — `'42px'` и `'42'` ведут себя по-разному.
4. **Будь осторожен с float** — сравнивай с допуском.
5. **Понимай разницу** между loose-приведением (разрешено) и TypeErrOr (запрещено).

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

# Работа с исключениями в PHP-приложении

От вопросов про типы мы плавно подошли к одной из самых важных архитектурных тем. Исключения — это не просто «обработка ошибок», это **контракт** между слоями приложения. Разберём, как это проектировать.

## Приоритет: проверять условия до выполнения

Прежде чем говорить об исключениях, важный принцип: **лучшая обработка ошибок — их предотвращение**.

```php
// Плохо: ловим то, что можно было проверить до
try {
    $user = $repository->find($id);
    $user->delete();
} catch (UserNotFoundException $e) {
    // ...
}

// Хорошо: проверяем до
if (!$repository->exists($id)) {
    throw new UserNotFoundException($id);
}
$user->delete();
```

Осознанно применяй try/catch только там, где исключение — часть нормального потока (парсинг, сетевые запросы, работа с файлами).

## Своя иераррия исключений

Создай **свою базовую иераррию**, чтобы слои могли общаться на одном языке. Раздели на два больших типа:

```php
namespace App\Exception;

// Базовый интерфейс для всех «своих» исключений
interface DomainExceptionInterface {}

// Исключения домена/бизнес-логики
class DomainException extends \RuntimeException 
    implements DomainExceptionInterface {}
```

### Разделение по типам ошибок

```php
// Пользовательские (user errors) — ожидаемые, можно показать пользователю
class UserNotFoundException extends DomainException {}
class InvalidPaymentException extends DomainException {}
class ValidationError extends DomainException {}

// Внутренние (system errors) — баги, внешние зависимости
class DatabaseException extends DomainException {}
class ExternalApiException extends DomainException {}
class PaymentGatewayTimeout extends DomainException {}
```

## Что считается контрактом метода

Контракт метода — это **то, что вызываете вызывающий код**. Исключения частью этого контракта. Раздели их на две категории:

**Ожидаемые (part of contract)** — объявляй явно:

```php
/**
 * @throws UserNotFoundException
 * @throws InvalidArgumentException
 */
public function find(int $id): ?User
```

**Неожиданные (internal)** — не часть контракта, это баги:

```php
// DatabaseException — это ошибка инфраструктуры, 
// её нужно логировать и показывать «что-то пошло не так», 
// а не валидировать в бизнес-логике
```

Правило: **ошибки инфраструктуры не должны «утекать» в бизнес-логику как часть её контракта.**

## Оборачивание чужих исключений

Это критически важная техника. Когда ты ловишь исключение из внешнего источника (Doctrine, PDO, API) и бросаешь своё, **всегда передавай оригинал как предыдущее исключение**.

```php
try {
    $connection->executeQuery($sql);
} catch (\PDOException $e) {
    throw new DatabaseException(
        'Не удалось выполнить запрос к базе данных',
        previous: $e
    );
}
```

Почему это важно:

- **Сохраняется chain exceptions** — можно отследить первопричину
- **Порог вложенности снижается** — `getPrevious()` вместо ручного хранения
- **Логирование показывает полный путь** ошибки

## Практический пример архитектуры

```php
namespace App\Service;

use App\Exception\UserNotFoundException;
use App\Exception\PaymentFailedException;
use App\Repository\UserRepository;

class PaymentService
{
    public function __construct(
        private UserRepository $users,
        private GatewayInterface $gateway,
    ) {}

    public function charge(int $userId, float $amount): Receipt
    {
        $user = $this->users->findById($userId);
        if ($user === null) {
            throw new UserNotFoundException("Пользователь $userId не найден");
        }

        try {
            $receipt = $this->gateway->charge($user, $amount);
        } catch (GatewayException $e) {
            // Оборачиваем, но сохраняем оригинал
            throw new PaymentFailedException(
                "Ошибка оплаты для пользователя $userId",
                previous: $e
            );
        }

        return $receipt;
    }
}
```

## Что делать в обработчиках ошибок

**Автоматическая обработка (framework-level):**

```php
// Symfony-подход: EventSubscriber
class ExceptionListener
{
    public function onKernelException(\Throwable $e): void
    {
        // 1. Логируем всё через monolog
        $this->logger->error('Ошибка', ['exception' => $e]);

        // 2. Различаем типы
        if ($e instanceof UserExceptionInterface) {
            // 400 Bad Request — ошибка пользователя
        } else {
            // 500 Internal Server Error — внутренняя ошибка
        }
    }
}
```

## Антипаттерны

### 1. «Ловим всё и глушим»

```php
try {
    // ...
} catch (\Throwable $e) {
    // silently swallow — самая опасная практика
    // Никогда не теряй исключение без логирования
}
```

### 2. Логическая неразбериха

```php
// Плохо: смешиваем разные типы в одном catch
try { /* ... */ } 
catch (UserNotFoundException $e) { /* обработка */ }
catch (DatabaseException $e) { /* та же обработка?! */ }
```

### 3. Исключение как управление потоком

```php
try {
    $item = $collection->get($index);
} catch (OutOfBoundsException $e) {
    // Не надо так — проверяй существование до доступа
}
```

### 4. Потеря контекста

```php
// Плохо: теряем стек вызовов и оригинальную причину
throw new Exception('Ошибка');

// Хорошо: контекст + предыдущее исключение
throw new Exception('Ошибка обработки', previous: $original);
```

### 5. Исключение в нормальных условиях

```php
// Плохо: бросаем исключение там, где можно проверить
if ($value <= 0) {
    throw new InvalidAmountException(); // вместо проверки до
}

// Проверять до выполнения операции — предпочтительнее
```

## Практические рекомендации

1. **Иераррия должна отражать слои**: доменные ошибки ≠ системные ошибки
2. **Всегда сохраняй previous exception** при оборачивании
3. **Разделяй user-ошибки и system-ошибки** — разная обработка
4. **Проверяй до выполнения**, а не лови всё подряд
5. **Не глуши исключения** — логируй или перебрасывай
6. **Контракт = ожидаемые исключения** — документируй их явно
7. **Исключения не должны быть частью «обычной» логики**

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

# Нарушение принципов SOLID в реальном коде

Хотя у меня нет личного опыта в классном понимании (я не писал продактывный код годами), я хорошо знаю, какие паттерны нарушаются чаще всего на основе огромного количества реального кода, который анализировал. Давай разберём самый типовой.

## Самый частый нарушитель: Single Responsibility

Не случайно. Причин несколько:

- **Принцип единственной ответственности трудно соблюдать** в условиях дедлайнов
- **Код «привыкает» расти** — добавляешь новую функцию, и метод разрастается
- **Сложно увидеть нарушение** в «безобидных» методах, которые «просто делают свою работу»
- **FRP-мышление** (functional programming) часто противоречит SRP в ООП-стиле

## Типовой пример нарушения

Вот классическая ситуация — метод делает сразу несколько вещей:

```php
class OrderService
{
    public function processOrder(array $orderData): void
    {
        // 1. Валидация
        if (empty($orderData['email'])) {
            throw new InvalidArgumentException('Email обязателен');
        }
        if (!filter_var($orderData['email'], FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException('Некорректный email');
        }
        
        // 2. Расчёт суммы
        $total = 0;
        foreach ($orderData['items'] as $item) {
            $total += $item['price'] * $item['quantity'];
        }
        $orderData['total'] = $total;
        
        // 3. Сохранение в базу
        $pdo = new PDO('mysql://...', 'user', 'pass');
        $stmt = $pdo->prepare('INSERT INTO orders (...) VALUES (...)');
        $stmt->execute($orderData);
        
        // 4. Отправка email
        $mail = new Mailer();
        $mail->send($orderData['email'], 'Заказ оформлен');
    }
}
```

Что здесь нарушено — **четыре ответственности в одном методе**:
1. Валидация входных данных
2. Расчет финансовых операций
3. Прямая работа с базой данных (и плохая — голый PDO)
4. Отправка уведомлений

Почему это проблема:
- **Тестировать тяжело** — нужно мокать всё сразу
- **Изменить одну вещь сложно** — бояться сломать другое
- **Нельзя переиспользовать** части логики

## Рефакторинг

Разбиваем на маленькие классы с одной ответственностью:

```php
// 1. Валидация — отдельный класс
class OrderValidator
{
    public function validate(array $data): void
    {
        if (empty($data['email'])) {
            throw new InvalidArgumentException('Email обязателен');
        }
        if (!filter_var($data['email'], FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException('Некорректный email');
        }
    }
}

// 2. Расчет суммы — отдельно
class OrderCalculator
{
    public function calculateTotal(array $items): float
    {
        return array_sum(array_map(fn($item) => $item['price'] * $item['quantity'], $items));
    }
}

// 3. Репозиторий — инкапсулируем работу с БД
class OrderRepository
{
    public function __construct(private OrderTable $table) {}
    
    public function save(Order $order): void
    {
        $this->table->insert([
            'email' => $order->email,
            'total' => $order->total,
        ]);
    }
}

// 4. Уведомления — отдельно
class OrderNotifier
{
    public function __construct(private MailerInterface $mailer) {}
    
    public function notify(string $email): void
    {
        $this->mailer->send($email, 'Заказ оформлен');
    }
}

// Сервис объединяет, но не дублирует логику
class OrderService
{
    public function __construct(
        private OrderValidator $validator,
        private OrderCalculator $calculator,
        private OrderRepository $repository,
        private OrderNotifier $notifier,
    ) {}
    
    public function process(array $data): Order
    {
        $this->validator->validate($data);           // валидация
        $total = $this->calculator->calculateTotal($data['items']); // расчет
        
        $order = new Order($data['email'], $total);  // доменный объект
        $this->repository->save($order);             // сохранение
        $this->notifier->notify($order->email);      // уведомление
        
        return $order;
    }
}
```

## Почему это лучше

- **Тестирование** — можно тестировать каждый класс отдельно
- **Изменения** — можно менять валидацию, не трогая отправку email
- **Переиспользование** — `OrderValidator` можно использовать в других местах
- **Читаемость** — каждый класс объясает «зачем», а не «как»

## Другие частые нарушения

### Dependency Inversion (частая проблема)

```php
class UserService
{
    private $repository = new MySQLUserRepository(); // жёсткая зависимость
    
    // Плохо: привязка к конкретной реализации
}

// Хорошо: зависимость от абстракции
class UserService
{
    public function __construct(private UserRepository $repository) {}
}
```

### Interface Segregation (редко, но бывает)

```php
// Плохо: один огромный интерфейс
interface Repository {
    public function find();
    public function save();
    public function delete();
    public function export();
    public function import();
    // ...
}

// Хорошо: разделение по потребностям
interface ReadableRepository { public function find(); }
interface WritableRepository { public function save(); }
```

## Что делать на практике

1. **Разбивай на шаги** — каждый метод делает одну вещь
2. **Проверяй «если бы мне нужно было изменить...»** — если изменение одной вещи ломает другую, вероятно, ответственности смешаны
3. **Тестируй каждый слой отдельно**
4. **Используй зависимости, а не конкретные классы**
5. **Не бойся маленьких классов** — лучше 10 маленьких, чем 1 большой

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

# Можно ли нарушать SOLID?

Да, и это честный вопрос — потому что правильный ответ: **да, но с осознанностью**. Принципы SOLID — это не заповеди, а рекомендации, выведенные из практики. Нарушение само по себе не грех; грех — нарушение «ради удобства», без понимания последствий.

## Ключевое различие: осознанное vs неосознанное нарушение

- **Неосознанное нарушение** — ты нарушил и даже не заметил, что нарушил
- **Осознанное нарушение** — ты понимаешь, что нарушаешь принцип, зачем и какую цену за это заплатишь

Как сказал бы опытный разработчик: «Знать правила, чтобы нарушать их правильно» (как в поэмме Ли Куаны о программировании).

## Пример 1: Нарушение SRP ради производительности (иногда)

Иногда объединение нескольких «ответственностей» в одном объекте оправдано, если это **доменная концепция**:

```php
// Кэширование рядом с доменным объектом — технически нарушение SRP,
// но часто оправдано, если кэш тесно связан с жизнью объекта
class User
{
    private array $cache;
    
    public function __construct(private int $id) {}
    
    // Геттер с кэшированием — смешал «доступ к данным» и «кэш»
    public function getProfile(): array
    {
        if (!isset($this->cache['profile'])) {
            $this->cache['profile'] = $this->fetchProfile();
        }
        return $this->cache['profile'];
    }
}
```

Если кэш критичен к производительности, а разделение усложнит код — компромисс возможен.

## Пример 2: Нару DIP в «точках входа»

В точках сборки (composition root) иногда нарушают Dependency Inversion ради простоты:

```php
// В composition root можно напрямую использовать конкретную реализацию
// Это не нарушение в логике, а точка сборки приложения
$service = new PaymentService(new StripeGateway());
```

Здесь нарушение «разрешено», потому что это **внешний слой**, а не бизнес-логика.

## Пример 3: Нарушение LSP для «защиты инвариантов»

Иногда子class сознательно делает метод недоступным или throws, чтобы защитить инварианты домена:

```php
class ReadOnlyRepository implements Repository
{
    // Нарушаем интерфейс через исключение:
    public function save(): void
    {
        throw new UnsupportedException('Этот репозиторий только для чтения');
    }
}
```

Технически это нарушение LSP, но если домен требует такого поведения — оправдано.

## Пример 4: Нарушение ISP для «унификации»

```php
// Один общий интерфейс для всех репозиториев
interface Repository {
    public function find();
    public function save();
    public function delete();
    public function export();
}

// Если все репозитории используют все методы — нарушение ISP не критично
// (хотя лучше всё равно разделять)
```

## Когда нарушение ОПРАВДАНО

1. **Понимание последствий** — ты знаешь, что теряешь
2. **Производительность/практичность** — принцип усложняет работу без пользы
3. **Доменная модель** — концепция естественным образом объединяет ответственности
4. **Точки сборки** — composition root, где абстракции не нужны
5. **Прототипирование** — когда важна скорость, а не архитектура

## Когда нарушение НЕОПРАВДАНО

1. **Ради удобства** — «так проще написать сейчас»
2. **Без понимания** — ты не осознал, что нарушил
3. **В ядре логики** — нарушения в бизнес-логике бьют по поддерживаемости
4. **Постоянно** — каждый раз «нем Нарушаем» накапливается в техническом долге

## Золотое правило

> Нарушай принцип только тогда, когда понимаешь, что именно ты теряешь и почему это того стоит.

Неосознанное нарушение = технический долг. Осознанное нарушение = архитектурный выбор.

**Кандидат:**

# OCP без наследования: несколько подходов

Отличный вопрос — и он обнажает распространённое заблуждение. Наследование — **наихудший** способ实现 OCP, и вот почему: оно часто приводит к хрупкой иерархии, «висящим» методам subclass'ов и нарушению инкапсуляции. Давай разберём способы получше.

## Почему наследование — плохой выбор для OCP

Перед тем как показывать альтернативы, важно понять, что классический «OCP через наследование» имеет проблемы:

```php
// Классический, но проблемный подход
abstract class Shape {
    abstract public function area(): float;
}

class Circle extends Shape { /* ... */ }
class Rectangle extends Shape { /* ... */ }

// Проблема: добавление нового метода (например, perimeter)
// заставит править ВСЕ subclass'ы — нарушение OCP!
```

Наследование часто **нарушает** OCP в длинных цепочках, а не помогает. Вот лучшие способы.

## Способ 1: Composition (внутренняя вариация)

Разделяй «то, что меняется» и «то, что нет» через внедрение поведения.

```php
// Поведение инкапсулировано в отдельных объектах
interface DiscountStrategy {
    public function calculate(float $amount): float;
}

class PercentageDiscount implements DiscountStrategy {
    public function __construct(private float $percentage) {}
    
    public function calculate(float $amount): float {
        return $amount * ($this->percentage / 100);
    }
}

class FixedDiscount implements DiscountStrategy {
    public function __construct(private float $amount) {}
    
    public function calculate(float $amount): float {
        return min($this->amount, $amount);
    }
}

// Клиент не знает о конкретных стратегиях
class Cart {
    public function __construct(private DiscountStrategy $discount) {}
    
    public function total(float $amount): float {
        return $amount - $this->discount->calculate($amount);
    }
}

// OCP соблюден: добавление новой стратегии 
// НЕ требует изменения Cart
```

## Способ 2: Dependency Inversion + стратегии

Выноси стратегию за пределы класса, чтобы он зависел от абстракции.

```php
interface PaymentProcessor {
    public function pay(float $amount): void;
}

// Основной класс зависит от абстракции, не от конкретики
class Checkout {
    public function __construct(
        private PaymentProcessor $processor
    ) {}
    
    public function process(float $amount): void {
        $this->processor->pay($amount);
    }
}

// StripeProcessor, PayPalProcessor — новые реализации
// без изменения Checkout — OCP выполнен
```

## Способ 3: Policy Object / Behavior Injection

Выноси меняющееся поведение в policy-объекты.

```php
// Политика расчета доставки — отдельный объект
interface DeliveryPolicy {
    public function calculate(float $weight): float;
    public function estimateDays(): int;
}

class StandardDelivery implements DeliveryPolicy { /* ... */ }
class ExpressDelivery implements DeliveryPolicy { /* ... */ }
class InternationalDelivery implements DeliveryPolicy { /* ... */ }

// Заказ зависит от политики, а не от её реализации
class Order {
    public function __construct(
        private DeliveryPolicy $deliveryPolicy
    ) {}
}
```

## Способ 4: Data-driven подход (максимальное OCP)

Иногда лучший способ «не менять код» — вынести логику в данные.

```php
// Конфигурация вместо кода
$discounts = [
    'VIP' => ['type' => 'percentage', 'value' => 20],
    'NEW' => ['type' => 'fixed', 'value' => 100],
];

class DiscountCalculator {
    public function calculate(string $code, float $amount): float {
        $config = $discounts[$code] ?? null;
        if ($config === null) {
            return $amount; // без скидки
        }
        
        return match($config['type']) {
            'percentage' => $amount * (1 - $config['value'] / 100),
            'fixed' => max(0, $amount - $config['value']),
        };
    }
}

// Добавление нового типа скидки — это изменение данных, 
// а не кода (в пределах match)
```

## Способ 5: Extension через event/hook system

Позволь другим кодам «расширять» поведение через события.

```php
class OrderProcessor {
    private array $handlers = [];
    
    public function onBeforeProcess(callable $handler): void {
        $this->handlers[] = $handler;
    }
    
    public function process(array $order): void {
        // Вызываем все зарегистрированные хэндлеры
        foreach ($this->handlers as $handler) {
            $handler($order);
        }
        // ... основная логика
    }
}

// Внешний код «расширяет» поведение без изменения OrderProcessor
```

## Сравнение подходов

| Подход | Когда использовать |
|--------|-------------------|
| **Composition** | Когда поведение можно инкапсулировать в объект |
| **Dependency Inversion** | Когда нужно менять реализацию «под капотом» |
| **Policy Object** | Когда логика «расчета/выбора» меняется часто |
| **Data-driven** | Когда логика по сути параметризуема |
| **Event system** | Когда нужно дать сторонам «подключаться» |

## Что выбрать

- **Если поведение можно описать как стратегию** → Composition + Strategy
- **Если нужно менять реализацию** → Dependency Inversion
- **Если логика параметризуема** → Data-driven
- **Если нужно расширение без вмешательства** → Event/hook

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

# SRP не только к классам — это принцип организации ответственности

Хороший вопрос, который обнажает распространённое заблуждение. Single Responsibility Principle применяется **шире**, чем классы — это принцип разделения **ответственности** (responsibility), который работает на разных уровнях. Разберём.

## Что такое «ответственность» (responsibility)

Ответственность — это **причина существования** компонента, набор изменений, которые его касаются. Ключевой тест: **изменяется ли компонент из-за одной причины?** Если да — он отвечает за одну вещь.

Этот принцип применяется на разных уровнях:

## 1. Методы и функции

```php
// Плохо: метод делает несколько вещей
public function calculateAndSaveAndNotify(float $amount): void
{
    // расчет, сохранение, уведомление — три ответственности
}

// Хорошо: каждый метод — одну ответственность
public function calculateTotal(float $amount): float { /* ... */ }
public function persist(Order $order): void { /* ... */ }
public function notify(): void { /* ... */ }
```

Метод должен делать **одну вещь** и делать её хорошо.

## 2. Слой приложения

```php
// Контроллер не должен знать о БД напрямую
class OrderController {
    // Только оркестрация, никакой валидации/расчётов
}

// Доменный слой — чистая бизнес-логика
// Слой инфраструктуры — работа с базой
```

Каждый слой отвечает за свою зону ответственности.

## 3. Модуль / пакет

```php
// Плохо: один «универсальный» класс
class Utils { // делает всё: работа с БД, email, расчеты }

// Хорошо: разделение по ответственностям
namespace App\Db;      // работа с базой
namespace App\Mailer;  // отправка писем
namespace App\Calc;    // расчеты
```

## 4. Микросервис / сервис

```php
// Плохо: один сервис делает всё
class EverythingService { /* БД, email, расчеты, интеграции */ }

// Хорошо: каждый сервис — одна бизнес-возможность
class PaymentService;
class InventoryService;
class NotificationService;
```

## 5. Функциональная область (как в DDD)

- **Domain** — бизнес-правила
- **Application** — use cases
- **Infrastructure** — технические детали
- **Presentation** — API/UI

Каждый слой отвечает за свою зону.

## Ключевой нюанс: не путай с разбиением по «типам действий»

Частая ошибка — разделять классы по типам операций вместо ответственностей:

```php
// Плохо: разделяю по «типу действия»
class UserValidator;   // валидация
class UserSaver;       // сохранение
class UserMailer;      // рассылка
// Но все они про User!

// Хорошо: разделяю по ответственности/доменным концепциям
class UserRegistration;   // ответственна за регистрацию
class UserNotifications;  // ответственна за уведомления
```

## Практический тест на SRP

Задай себе вопросы:

1. **«Почему этот компонент существует?»** — ответ должен быть одним
2. **«Из-за чего его можно изменить?»** — причина одна
3. **«Можно ли переименовать компонент по одной ответственности?»** — например, «OrderCalculator» отвечает за calculation

Если ответы «разные» или «нельзя переименовать по одной вещи» — вероятно, ответственность раздута.

## Что НЕ является нарушением SRP

- **Класс с несколькими тесно связанными методами**, которые про одну доменную концепцию
- **Геттеры/сеттеры** — это реализационные детали, не ответственность
- **Класс, который оркестирует других** — если это его роль

## Резюме

SRP применяется к:
- ✅ **Методам** (один метод — одна вещь)
- ✅ **Классам** (один класс — одна ответственность)
- ✅ **Слоям** (каждый слой — своя зона)
- ✅ **Модулям/пакетам** (разделение по доменным концепциям)
- ✅ **Сервисам/микросервисам** (один сервис — одна бизнес-возможность)

Главное — **причина изменения**, а не размер кода. Компонент нарушает SRP, если его можно изменить из-за нескольких причин, независимо от того, класс это, метод или модуль.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

# Контейнер внедрения зависимостей в Symfony

Отличный вопрос — Container в Symfony это не абстракция, а реально компилируемый код. Разберём, что происходит на каждом этапе: от описания до первого запроса сервиса.

## Общая картина: два режима работы

Container имеет **два режима**:

1. **dev** — перекомпиляция при изменении кода (быстро, но есть оверхед)
2. **prod** — полная компиляция в оптимизированный код (максимальная скорость)

Именно поэтому компиляция — это не «лишняя» операция, а ключевой этап.

## Этап 1: Загрузка определений (Definition)

Сначала Symfony собирает **определения сервисов** (Definitions). Они могут быть из:

- Автоматической конфигурации (service.yaml)
- Ручного описания
- Attributes (PHP 8)

```yaml
# config/services.yaml
services:
  App\Service\OrderService:
    arguments:
      $database: '@App\Repository\PaymentRepository'
```

Или через attributes:

```php
namespace App\Service;

use Symfony\Component\DependencyInjection\Attribute\AsService;

#[AsService]
class OrderService
{
    public function __construct(
        private PaymentRepository $payments
    ) {}
}
```

## Этап 2: Компиляция контейнера

Вот здесь происходит «магия». Процесс компиляции состоит из нескольких фаз:

### Фаза A: PassConfig

Компиляция проходит через цепочку **compiler passes** — каждый проход что-то делает:

```
PassConfig::registerPass()
  ├── MergeExtensionPass — слияние всех расширений
  ├── RegisterPass — регистрация сервисов
  ├── ResolveParameterPlaceHolderPass — разрешение плейсхолдеров
  ├── ... (много промежуточных)
  ├── InlineServiceDefinitionsPass — «встраивает» маленькие сервисы
  ├── RemovePrivateServicesPass — удаляет приватные, которые не используются
  └── ...
```

### Фаза B: Инлайн и оптимизация

Ключевые оптимизации:

1. **InlineServiceDefinitions** — если сервис используется только один раз и не публичный, он «встраивается» прямо в код создания, а не хранится в контейнере

```php
// Было: получение из контейнера
$repository = $container->get(PaymentRepository::class);

// После инлайна: прямое создание
$repository = new PaymentRepository($connection);
```

2. **RemoveUnusedDefinitions** — сервисы, которые никто не использует, удаляются из финального контейнера

3. **ResolveClassPass** — определяет класс на основе type-hint

### Итог компиляции

Symfony генерирует **PHP-код класса-контейнера** (например, `App_KernelProdContainer`), который выглядит так:

```php
// Сгенерированный код
public function getOrderService()
{
    // Инлайним зависимости прямо здесь
    $payments = new PaymentRepository($this->get('doctrine')->getConnection());
    
    return new $this->services['App\\Service\\OrderService']($payments);
}
```

Это **написанный вручную PHP-код**, а не reflection! Именно поэтому prod-контейнер работает быстро.

## Этап 3: Autowiring

Autowiring — это **автоматическое определение зависимостей** на основе type-hint конструктора.

### Как это работает

```php
class OrderService
{
    public function __construct(
        private PaymentRepository $payments,  // Symfony сам находит сервис
        private OrderRepository $orders,      // ... по type-hint
    ) {}
}
```

Процесс:
1. Symfony смотрит на типы параметров конструктора
2. Ищет сервис по классу/интерфейсу этого типа
3. Рекурсивно разрешает и их зависимости

### Что нужно для работы

1. **Регистрация сервисов** — обычно через service.yaml с автоконфигурацией

```yaml
services:
  App\:
    resource: '../src/'
  # ...
```

2. **Типизированные параметры** — type-hint должен быть понятен

```php
// Работает
public function __construct(PaymentRepository $repo) {}

// Тоже работает через interface
public function __construct(PaymentGateway $gateway) {}
```

### Edge-кейсы autowiring

```php
// 1. Если нет публичного сервиса по class — ошибка
public function __construct(SpecificService $service) {}
// Нужно либо зарегистрировать, либо указать в yaml

// 2. Scalar-аргументы ($id) не ауэрятся — нужны explicit
public function __construct(private int $timeout) {}
// Нужно указать: arguments: { $timeout: 30 }

// 3. Интерфейсы — ищутся реализации
public function __construct(LoggerInterface $logger) {}
// Symfony знает о своих сервисах
```

## Этап 4: Первый запрос сервиса

Когда ты запрашиваешь сервис впервые:

```php
$service = $container->get(OrderService::class);
```

### Процессы в момент запроса

**1. Проверка существования**
```php
public function get(string $id) {
    if (!isset($this->files[$id])) {
        // Если это «realid» — ищем в compiled контейнере
        $this->load($id);
    }
    
    if (!$this->runningInstance->has($id)) {
        throw new ServiceNotFoundException($id);
    }
}
```

**2. Инстанцирование (впервые)**
```php
// Первый раз создаётся объект
$service = new OrderService($payments, $orders);
```

**3. Цепочка разрешения**
```
get(OrderService) 
  → need PaymentRepository 
    → need (doctrine connection) 
    → need (EntityManager) 
    → ... (рекурсивно)
```

**4. Синглтон**
```php
// После первого создания — кэшируется
$this->realServices[$id] = $service;

// Повторные запросы — тот же объект
```

### Синглтон-поведение

```php
$a = $container->get(OrderService::class);
$b = $container->get(OrderService::class);
$a === $b; // true — тот же инстанс
```

## Производительность: dev vs prod

| Режим | Поведение |
|-------|-----------|
| **dev** | Перекомпиляция при изменении, использование reflection, slower |
| **prod** | Сгенерированный код, reflection отключен, fast |
| **Тесты** | Отдельные контейнеры, reset между запросами |

## Типичные проблемы и их объяснение

### 1. «Сервис не найден»

```php
// Ошибка: нет публичного сервиса для класса
Class 'App\Service\MissingService' not found

// Причина: либо не зарегистрирован, либо приватный и не используется
```

### 2. «Ambiguous argument»

```php
// Ошибка: несколько реализаций интерфейса
Cannot autowire $logger: ambiguous

// Причина: нет одного уникального сервиса по type-hint
```

### 3. «Service is private»

```php
// Ошибка: попытка получить приватный сервис извне
// Причина: приватные сервисы — внутренние, доступны только через внедрение
```

## Итог: полный цикл

```
1. Определение сервисов (yaml/attributes)
       ↓
2. Компиляция:
   - PassConfig (много passes)
   - Inline (встраивание)
   - RemoveUnused (удаление)
   - Генерация PHP-кода
       ↓
3. Autowiring: type-hint → сервис
       ↓
4. First get():
   - Проверка
   - Инстанцирование (цепочка)
   - Кэширование (синглтон)
```

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

# Разруливанию циклических зависимостей

Циклические зависимости — это **красный флаг** архитектуры. Они указывают на смешанные ответственности или неправильную организацию слоёв. Разберём способы разруливания, от самого «правильного» к «менее красивому».

## Почему циклы — это плохо

- **Сложно инстанцировать** — нужно угадывать порядок создания
- **Трудно тестировать** — приходится мокать циклы
- **Скрытая связанность** — нельзя понять, кто за что отвечает
- **Требует специальных решений** — нативного way нет

## Способ 1: Extract — вынести общую логику (лучший)

Часто цикл означает, что есть **общая ответственность**, которую стоит вынести.

```php
// Плохо: цикл A ↔ B
class ServiceA {
    public function __construct(private ServiceB $b) {}
}

class ServiceB {
    public function __construct(private ServiceA $a) {}
}

// Хорошо: выносим общую логику в ServiceC
class ServiceC {
    public function __construct() {}
    public function doWork(): void { /* ... */ }
}

class ServiceA {
    public function __construct(private ServiceC $c) {}
}

class ServiceB {
    public function __construct(private ServiceC $c) {}
}
```

## Способ 2: Event Dispatcher / Event System

Разорвать цикл через события — классика Symfony.

```php
// Плохо: A вызывает B и наоборот
class PaymentService {
    public function __construct(private NotificationService $notifications) {}
}

class NotificationService {
    public function __construct(private PaymentService $payments) {}
}

// Хорошо: события
class PaymentService {
    public function __construct(private EventDispatcher $dispatcher) {}
    
    public function pay(float $amount): void {
        // ... процесс оплаты
        $this->dispatcher->dispatch(new PaymentSucceededEvent($amount));
    }
}

// Слушатель реагирует на событие — без циклической зависимости
class PaymentNotificationListener {
    public function onPaymentSucceeded(PaymentSucceededEvent $e): void {
        // Отправляем уведомление
        $this->mailer->send(...);
    }
}
```

## Способ 3: Lazy Loading / Proxy

Иногда циклы возникают из-за того, что один сервис «нужен только иногда».

```php
// Плохо: жёсткая зависимость
class OrderService {
    public function __construct(private CartService $cart) {}
}

class CartService {
    public function __construct(private OrderService $orders) {}
}

// Хорошо: lazy-доступ через замыкание
class OrderService {
    public function __construct(
        private CartFactory $cartFactory  // factory, не инстанс
    ) {}
    
    public function getCart(): CartService {
        return $this->cartFactory->create(); // ленивая инициализация
    }
}
```

## Способ 4: Interface Segregation

Разделить сервисы так, чтобы цикл не мог возникнуть.

```php
// Плохо: один сервис делает много и зависит обратно
class OrderProcessor {
    public function __construct(private CartManager $cart) {}
}

class CartManager {
    public function __construct(private OrderProcessor $orders) {}
}

// Хорошо: разделение по ролям
interface OrderProcessorInterface { /* ... */ }
interface CartManagerInterface { /* ... */ }

// Каждый зависит только от нужной ему части
```

## Способ 5: Setter Injection (менее предпочтительно)

Иногда помогает, но Symfony не любит этот паттерн.

```php
// Не рекомендуемо в Symfony, но рабочий способ
class ServiceA {
    private ServiceB $b;
    
    public function setB(ServiceB $b): void {
        $this->b = $b;
    }
}
```

## Способ 6: Static factory / Singleton

Для «глобальных» ресурсов (базы данных, конфигурации) иногда допустим singleton.

```php
// Плохо: цикл из-за общего «ресурса»
class DatabaseA {
    public function __construct(private DatabaseB $db) {}
}

class DatabaseB {
    public function __construct(private DatabaseA $db) {}
}

// Хорошо: общий ресурс — singleton
class Database {
    private static ?Database $instance = null;
    
    public static function getInstance(): Database {
        if (self::$instance === null) {
            self::$instance = new Database();
        }
        return self::$instance;
    }
}
```

## Как распознать тип цикла

| Тип цикла | Решение |
|-----------|---------|
| **Общая логика** | Extract (вынеси в отдельный класс) |
| **Асинхронное действие** | Event Dispatcher |
| **Ленивая инициализация** | Lazy / Factory |
| **Разные роли** | Interface Segregation |
| **Глобальный ресурс** | Singleton |

## Практический пример разруливания

```php
// Сценарий: OrderService нужно отправить уведомление,
// а NotificationService нужно знать об Orders

// Плохо (цикл):
class OrderService {
    public function __construct(private NotificationService $notifications) {}
}

class NotificationService {
    public function __construct(private OrderRepository $orders) {}
}

// Решение через событие:
class OrderService {
    public function __construct(
        private EventDispatcher $dispatcher
    ) {}
    
    public function create(array $data): Order {
        $order = /* ... */;
        $this->dispatcher->dispatch(new OrderCreatedEvent($order));
        return $order;
    }
}

// Отдельный слушатель — без зависимости от OrderService
class OrderCreatedListener {
    public function __construct(private OrderRepository $orders) {}
    
    public function __invoke(OrderCreatedEvent $e): void {
        $order = $e->order;
        $this->orders->save($order);
        // ... отправка уведомления
    }
}
```

## Что НЕ делать

1. **Не оставлять циклы** — «оно же работает»
2. **Не использовать static** для всего подряд
3. **Не применять setter injection** без крайней необходимости
4. **Не скрывать проблему** — цикл указывает на архитектурную проблему

## Золотое правило

> Циклическая зависимость = смешанная ответственность. Найди «лишнюю» связь и разорви её через вынесение логики, события или разделение ролей.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

# Организация асинхронных задач в Symfony

Отличный вопрос — это классическая проблема «что делать с побочными эффектами после основного действия». Разберём несколько подходов с их trade-offs.

## Вариант 1: Async Event Dispatcher (базовый)

Symfony по умолчанию работает **синхронно**, но можно настроить асинхронную отправку событий через `EventDispatcher`.

```php
// Регистрация события после создания пользователя
$this->eventDispatcher->dispatch(
    new UserRegisteredEvent($user),
    'user_registered'
);

// Слушатель — отдельный класс
class UserRegisteredListener {
    public function __construct(
        private MailerInterface $mailer,
        private SearchIndex $searchIndex
    ) {}
    
    public function __invoke(UserRegisteredEvent $e): void {
        // Отправка email
        $this->mailer->send(...);
        // Обновление индекса
        $this->searchIndex->index($e->user->id);
    }
}
```

**Trade-offs:**
- ✅ Простота — базовый механизм Symfony
- ❌ **Синхронный по умолчанию** — без настройки async-transport'а это тот же оверхед
- ❌ Если транспорт не настроен, события всё равно выполняются синхронно

## Вариант 2: Messenger — асинхронная обработка сообщений (рекомендуемо)

Symfony Messenger — это **готовый framework** для async-обработки. Идеально подходит для твоего случая.

```php
// 1. Создаём «message» — данные о событии
class UserRegisteredMessage {
    public function __construct(private int $userId) {}
}

// 2. Отправляем сообщение
$this->messageBus->dispatch(
    new UserRegisteredMessage($user->getId())
);

// 3. Handler обрабатывает (может быть async)
#[AsMessageHandler]
class UserRegisteredHandler {
    public function __construct(
        private MailerInterface $mailer,
        private SearchIndex $searchIndex
    ) {}
    
    public function __invoke(UserRegisteredMessage $message): void {
        $user = $this->userRepository->find($message->userId);
        $this->mailer->sendEmail($user);
        $this->searchIndex->index($user);
    }
}
```

**Конфигурация async (framework-bundle):**

```yaml
# config/framework.yaml
framework:
    messenger:
        transports:
            async:
                dsn: 'amqp://user:pass@localhost:5672/default_vhost'
                options:
                    exchange:
                        name: notifications
                        type: topic
        routing:
            'UserRegisteredMessage': async  # это сообщение → async
```

**Trade-offs:**
- ✅ **Асинхронно** через очередь (AMQP, Redis, database)
- ✅ **Надёжность** — сообщения не теряются при падении
- ✅ **Ретраи** и error handling встроен
- ❌ Сложнее настройка — нужна очередь
- ❌ Нужно понимать модель Messenger

## Вариант 3: Console Command + Queue

Сложные задачи можно выносить в отдельную команду и запускать через queue (например, через `queue` extension).

```php
// app/Command/UserSyncCommand.php
#[Command(name: 'app:user:sync')]
class UserSyncCommand extends Command {
    protected static $defaultName = 'app:user:sync';
    
    public function execute(): int {
        // Синхронизация поиска, отправка писем
        return Command::SUCCESS;
    }
}

// В основном коде — добавляем задачу в queue
$this->queue->push('app:user:sync', ['userId' => $user->getId()]);
```

**Trade-offs:**
- ✅ Контроль над выполнением
- ❌ Больше ручной работы
- ❌ Сложнее масштабирование

## Вариант 4: Separate Worker Process

Запускать отдельный worker, который читает из queue и обрабатывает.

```php
// worker: php bin/console messenger:consume async
// Это долгоживущий процесс, который обрабатывает сообщения

// В основном коде — только dispatch
$this->messageBus->dispatch(new UserRegisteredMessage($id));
```

**Trade-offs:**
- ✅ Полностью асинхронно, масштабируемо
- ❌ Нужен отдельный процесс (доп. инфраструктура)
- ❌ Сложнее деплой и мониторинг

## Вариант 5: Database Queue (без AMQP)

Если нет возможности настроить AMQP, можно использовать database-transport.

```yaml
# config/framework.yaml
framework:
    messenger:
        transports:
            async:
                dsn: 'doctrine://default?queue_name=async'
```

**Trade-offs:**
- ✅ Простота — используется existing БД
- ❌ Меньше производительность, чем AMQP
- ❌ Нужен consumer для обработки

## Сравнительная таблица

| Вариант | Async? | Сложность | Надёжность | Когда использовать |
|---------|--------|-----------|------------|-------------------|
| **Event Dispatcher** | Нет (или да с настройкой) | Низкая | Средняя | Простые синхронные задачи |
| **Messenger** | Да | Средняя | Высокая | **Рекомендуемо для async** |
| **Console Command + Queue** | Да | Средняя | Средняя | Сложные batch-задачи |
| **Worker Process** | Да | Высокая | Высокая | Высоконагруженные системы |
| **Database Queue** | Да | Средняя | Средняя | Нет возможности AMQP |

## Моя рекомендация

Для твоего случая (отправка email + обновление индекса) я бы использовал **Messenger с AMQP-транспортом**:

1. **Асинхронность** — пользователь не ждёт
2. **Надёжность** — сообщения в очереди, не теряются
3. **Ретраи** — если email не отправился, можно повторить
4. **Масштабирование** — можно добавить несколько consumer'ов

```yaml
# config/routes.yaml
# Не забудьте: messenger:consume — в отдельном worker-процессе
```

# Контроль доступа в Symfony: аутентификация, роли, voters

| Метод | Когда использовать |
|-------|-------------------|

| **oauth2** | Соцсети, сторонние провайдеры |
| **custom** | Специальная логика (2FA, SSO) |

## Роли (Roles)

Роли — это **строковые константы**, начинающиеся с `ROLE_`.

### Базовое использование

```php
// В controller
#[IsGranted('ROLE_USER')]
public function profile(): Response { /* ... */ }

// В template
{% if is_granted('ROLE_ADMIN') %}
    <!-- ... -->
{% endif %}
```

### Иерархия ролей

```yaml
# config/packages/security.yaml
security:
    roles: ROLE_ADMIN  # наследует все роли ROLE_USER
```

### Проблема ролей

Роли — **грубый инструмент**. Они хорошо отвечают на вопрос «разрешено ли вообще?», но плохо — «разрешено именно ЭТО?»

```php
// Плохо: проверяем через role, что не должно быть в role
if ($user->hasRole('ROLE_USER') && $document->owner === $user) {
    // ...
}
```

## Voters (Authorizator)

Voter — это **гибкий механизм** для детального контроля доступа.

### Что делает voter

```php
class DocumentAccessVoter implements VoterInterface
{
    public function supports(string $attribute, mixed $subject): bool
    {
        // Проверка: это то, что мы умем проверять?
        return str_starts_with($attribute, 'VIEW_DOCUMENT')
            && $subject instanceof Document;
    }
    
    public function isGranted(string $attribute, mixed $subject): bool
    {
        $user = $this->userResolver->getUser();
        $document = $subject;
        
        // Логика проверки
        return $document->getOwner()->getId() === $user->getId();
    }
}
```

### Регистрация voter'а

```yaml
# config/services.yaml
services:
    App\Security\DocumentAccessVoter:
        tags: ['security.voter']
```

### Использование в контроллере

```php
#[IsGranted('VIEW_DOCUMENT')]
public function show(Document $document): Response
{
    // $document автоматически валидируется через type-hint
    // и проверяется через DocumentAccessVoter
}
```

## Когда использовать роли, а когда voters

Вот тут самое интересное — границы размыты.

### Достаточно ролей, если:

1. **Доступ к разделам приложения**
```php
#[IsGranted('ROLE_ADMIN')]  // админка
#[IsGranted('ROLE_USER')]   // личный кабинет
```

2. **Простая иерархия прав**
```php
#[IsGranted('ROLE_EDITOR')]  // редакторы
#[IsGranted('ROLE_MANAGER')]  // менеджеры
```

3. **Глобальные привилегии**
```php
#[IsGranted('ROLE_SUPER_ADMIN')]  // доступ ко всему
```

### Нужен voter, если:

1. **Доступ привязан к данным (не к ролям)**
```php
#[IsGranted('EDIT_OWN_POST')]
public function edit(Post $post) {
    // Проверка: $post->author === $user
    // Роль это не проверит!
}
```

2. **Правила зависят от состояния**
```php
#[IsGranted('APPROVE_ORDER')]
public function approve(Order $order) {
    // Проверка: order.status === 'PENDING'
    // Динамическое состояние!
}
```

3. **Доступ зависит от нескольких факторов**
```php
#[IsGranted('VIEW_REPORT')]
public function report() {
    // Проверка: 
    // 1. пользователь активен
    // 2. у него есть подписка
    // 3. сейчас рабочее время
}
```

## Практический пример: смешанный подход

```php
// 1. Роли для базового доступа
#[IsGranted('ROLE_USER')]
public function dashboard(): Response { /* личный кабинет */ }

// 2. Voter для доступа к конкретному пользователю
#[IsGranted('VIEW_PROFILE')]
public function profile(User $targetUser): Response {
    // DocumentAccessVoter проверяет:
    // - это я сам?
    // - у меня ROLE_ADMIN?
    // - мы друзья?
}

// 3. Voter для динамического доступа
#[IsGranted('EDIT_DOCUMENT')]
public function edit(Document $document): Response {
    // DocumentAccessVoter проверяет право собственности
}
```

## Trade-offs ролей vs voters

| Критерий | Роли | Voters |
|----------|------|--------|
| **Простота** | ✅ Просто | ❌ Сложнее |
| **Гибкость** | ❌ Грубые | ✅ Детальные |
| **Тестируемость** | ✅ Легко | ✅ Легко |
| **Поддержка** | ❌ Растут проблемы | ✅ Чистая логика |
| **Производительность** | ✅ Быстро | ⚠️ Чуть медленнее |
| **Масштаб** | ❌ Плохо для сложной логики | ✅ Хорошо |

## Рекомендации

1. **Роли для «грубых» прав** — разделы приложения, иерархии
2. **Voters для доступа к данным** — привязка к объектам, состоянию
3. **Не дублируй логику** — если видишь повторяющиеся проверки в ролях, выноси в voter
4. **Тестируй оба** — и роли, и voter'ы
5. **Используй type-hint'ы** — Symfony валидирует объекты автоматически

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

# Хранение Value Object в Doctrine

Отличный вопрос — тут Doctrine сталкивается с тем, что VO должен быть неизменяемым и валидным, но Doctrine работает с мутабельными сущностями. Разберём способы.

## Проблема

Doctrine по умолчанию работает с **Entity** — мутабельными объектами, у которых:
- Есть identity (id)
- Можно менять свойства
- Нет гарантии валидности

Но Value Object:
- **Неизменяем** (immutable) — нельзя менять после создания
- **Валиден по определению** (valid-by-construction) — нельзя создать невалидный

Разберём способы маппинга.

## Способ 1: Embeddable Doctrine

Doctrine Embeddable — это «значение», которое маппингуется как поля в той же таблице, что и Entity.

```php
namespace App\ValueObject;

use Doctrine\ORM\Mapping as ORM;

#[ORM\Embeddable]
class Money
{
    #[ORM\Column(type: 'decimal', precision: 10, scale: 2)]
    private string $amount;
    
    #[ORM\Column(type: 'string', length: 3)]
    private string $currency;
    
    // Constructor — valid by construction
    private function __construct(string $amount, string $currency)
    {
        if (!filter_var($amount, FILTER_VALIDATE_FLOAT)) {
            throw new InvalidMoneyException("Неверная сумма: $amount");
        }
        if (!preg_match('/^[A-Z]{3}$/', $currency)) {
            throw new InvalidMoneyException("Неверная валюта: $currency");
        }
        $this->amount = $amount;
        $this->currency = $currency;
    }
    
    public static function create(string $amount, string $currency): self
    {
        return new self($amount, $currency);
    }
    
    // Immutable — return new instance, no mutation
    public function add(self $other): self
    {
        // ... математика
        return self::create($newAmount, $this->currency);
    }
}
```

### Использование

```php
#[ORM\Entity]
class Order
{
    #[ORM\Column]
    private Money $total; // embeddable
    
    public function __construct(Money $total)
    {
        $this->total = $total;
    }
}
```

**Плюсы:**
- ✅ Валидность в конструкторе
- ✅ Неизменяемость сохранена в домене
- ✅ Doctrine управляет маппингом

**Минусы:**
- ❌ Doctrine требует **публичных геттеров/сеттеров** или reflection
- ❌ Нельзя полностью скрыть mutable-доступ
- ❌ Сложнее работа с Doctrine

## Способ 2: Custom String/Value Type (DBAL Types)

Если VO — это «просто значение» (например, Email), можно создать custom DBAL type.

```php
namespace App\Doctrine;

use Doctrine\DBAL\Platforms\AbstractPlatform;
use Doctrine\DBAL\Types\Type;

class EmailType extends Type
{
    public function getSQLDeclaration(array $column, AbstractPlatform $platform): string
    {
        return $platform->getBooleanTypeDeclarationSQL($column);
    }
    
    public function convertToPHPValue($value, AbstractPlatform $platform): Email
    {
        // Создаём валидный VO
        return Email::fromString((string)$value);
    }
    
    public function convertToDatabaseValue($value, AbstractPlatform $platform): string
    {
        // Преобразуем в строку для БД
        return $value->toString();
    }
}
```

### Регистрация

```php
// doctrine config
doctrine:
    dbal:
        types:
            email: App\Doctrine\EmailType
```

**Плюсы:**
- ✅ Полная валидность
- ✅ Независимость от Doctrine internals
- ✅ Переиспользование

**Минусы:**
- ❌ Сложнее
- ❌ Ограничения (VO должен маппиться в один тип)

## Способ 3: Embeddable + Custom type

Комбинируем: Embeddable для структуры, Custom type для валидности.

```php
#[ORM\Embeddable]
class Money
{
    #[ORM\Column(type: 'money')] // custom type
    private MoneyValue $amount;
    
    // ...
}
```

## Способ 4: Repository + Converter (внешний маппинг)

Иногда удобнее маппить во外部 Converter, чемEmbeddable.

```php
class OrderRepository
{
    public function save(Order $order): void
    {
        $this->entityManager->persist($order);
        $this->entityManager->flush();
    }
}

// Converter для VO
class MoneyConverter
{
    public function toEntity(Money $vo): array {
        return ['amount' => $vo->amount, 'currency' => $vo->currency];
    }
}
```

**Плюсы:**
- ✅ Полный контроль
- ✅ Не зависишь от Doctrine

**Минусы:**
- ❌ Больше кода
- ❌ Нужно вручную управлять life cycle

## Подводные камни

### 1. Doctrine и иммутабельность

Doctrine **не понимает** иммутабельность. Он ожидает setter'ов.

```php
// Doctrine пытается сделать так:
$entity->setTotal($money); // но у VO нет setter'а!
```

**Решение:** Embeddable + reflection, но не скрывай getters.

### 2. Валидность в конструкторе vs Doctrine

Doctrine создаёт объекты через reflection, **минуя конструктор**.

```php
// Doctrine делает:
$money = (new \ReflectionClass(Money::class))->newInstanceWithoutConstructor();
// Это обходит твой valid-by-construction!
```

**Решение:** Используй factory-методы, не полагайся на reflection.

### 3. Embeddable и composite keys

Если VO используется как часть composite key — могут быть проблемы.

### 4. Null vs empty

VO должен решать, что делать с null.

```php
// Вариант 1: null допустим
#[ORM\Column(nullable: true)]
private ?Email $email;

// Вариант 2: никогда null
// Тогда null в БД → InvalidEmailException
```

## Рекомендации

| Сценарий | Способ |
|----------|--------|
| **VO — структура** (Money, Address) | Embeddable |
| **VO — скаляр** (Email, PhoneNumber) | Custom DBAL type |
| **VO — сложная логика** | Repository + Converter |
| **VO — только чтение** | Embeddable + readonly |

## Практический пример: Embeddable + factory

```php

class Address
{
    #[ORM\Column(type: 'string')]
    private string $street;
    
    #[ORM\Column(type: 'string')]
    private string $city;
    
    private function __construct(string $street, string $city)
    {
        if (trim($street) === '') {
            throw new InvalidAddressException("Улица не может быть пустой");
        }
        if (trim($city) === '') {
            throw new InvalidAddressException("Город не может быть пустой");
        }
        $this->street = $street;
        $this->city = $city;
    }
    
    public static function fromString(string $street, string $city): self
    {
        return new self($street, $city);
    }
}
```

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

# Организация хранения агрегата в Doctrine

Хороший вопрос — тут Doctrine напрямую конфликтует с концепцией агрегата. Разберём на примере **магазина с заказами**.

## Проблема

Doctrine по умолчанию работает с **плоскими сущностями** (flattened entities). Но aggregate root должен:
- Управлять целостностью всей структуры
- Инициализировать дочерние сущности
- Держать их в памяти (вместо разрозненных таблиц)

## Модель данных

```php
#[ORM\Entity]
class Order
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column]
    private int $id;
    
    #[ORM\Column(type: 'string')]
    private string $status;
    
    // Collection of OrderItem (embedded)
    #[ORM\OneToMany(mappedBy: 'order', cascade: ['persist', 'remove'])]
    private ArrayCollection $items;
    
    // Collection of OrderHistory (embedded)
    #[ORM\OneToMany(mappedBy: 'order', cascade: ['persist', 'remove'])]
    private ArrayCollection $history;
    
    private function __construct(int $id)
    {
        $this->id = $id;
        $this->items = new ArrayCollection();
        $this->history = new ArrayCollection();
        $this->status = 'PENDING';
    }
}
```

## Доменные сущности

```php
class OrderItem
{
    public function __construct(
        private Product $product,
        private int $quantity
    ) {}
}

class OrderHistory
{
    public function __construct(
        private string $event,
        private \DateTimeImmutable $timestamp
    ) {}
}
```

## Организация хранения

### Вариант 1: OneToMany в одной таблице

```php
// order_items таблица
class Order {
    #[ORM\OneToMany(mappedBy: 'order')]
    private $items;
}
```

Проблема: Doctrine **ленивая загрузка** (lazy loading) — коллекция загружается в отдельном запросе.

### Вариант 2: Embeddable для вложенных структур

```php
#[ORM\Embeddable]
class OrderItems {
    #[ORM\ManyToMany]
    private $products;
}
```

## Границы транзакции

```php
// В Service
class OrderService
{
    public function __construct(
        private EntityManagerInterface $em,
        private OrderRepository $orders
    ) {}
    
    public function addProduct(int $orderId, Product $product, int $qty): Order
    {
        $order = $this->orders->find($orderId);
        
        // Внутри одного метода — граница агрегата
        $order->addItem($product, $qty);  // меняем домен
        
        // flush — вызываем в конце
        $this->em->flush();
        
        return $order;
    }
}
```

## Кто вызывает flush

### Рекомендация: flush в конце use-case

```php
//плохо: flush после каждой операции
$order->addItem(...);
$em->flush();
$order->addHistory('item_added');
$em->flush();  // второй flush!

//хорошо: один flush в конце
$order->addItem(...);
$order->addHistory('item_added');
$em->flush();  // один flush — целостность агрегата
```

## Проблемы Doctrine и aggregate

### 1. Ленивая загрузка коллекций

```php
// order.items — это Proxy
// Доступ к нему → отдельный SQL-запрос
foreach ($order->getItems() as $item) {
    // каждый доступ → potential N+1 query problem
}
```

**Решение:** Используй `JOIN` в запросах

```php
$orders = $em->getRepository(Order::class)
    ->createQueryBuilder('o')
    ->leftJoin('o.items', 'i')
    ->addSelect('i')
    ->getQuery()
    ->getResult();
```

### 2. Detached объекты

```php
// Если EntityManager закрыт, объекты detached
// Doctrine не видит изменений
```

### 3. Dirty checking

Doctrine может detecting изменения через `flush()`, но это:
- Работает только для простых свойств
- Не видит изменений в deeply nested структурах

## Практический пример: Store

```php
namespace App\Domain\Order;

#[ORM\Entity]
class Order
{
    private ArrayCollection $items;
    private ArrayCollection $history;
    
    public function addItem(Product $product, int $quantity): void
    {
        // Валидация домена
        if ($quantity <= 0) {
            throw new InvalidQuantityException();
        }
        
        // Изменение состояния
        $this->items->add(new OrderItem($product, $quantity));
        $this->history->add(new OrderHistory('ITEM_ADDED', new \DateTimeImmutable()));
        
        // aggregate root управляет целостностью
        $this->recalculateTotal();
    }
    
    private function recalculateTotal(): void
    {
        $total = 0;
        foreach ($this->items as $item) {
            $total += $item->getProduct()->getPrice() * $item->getQuantity();
        }
        // ... обновление total
    }
}
```

## Repository паттерн

```php
class OrderRepository
{
    public function __construct(private EntityManagerInterface $em) {}
    
    public function find(int $id): ?Order
    {
        // С JOIN для items
        return $this->em->getRepository(Order::class)
            ->createQueryBuilder('o')
            ->leftJoin('o.items', 'i')
            ->addSelect('i')
            ->where('o.id = :id')
            ->setParameter('id', $id)
            ->getQuery()
            ->getOneResult();
    }
    
    public function persist(Order $order): void
    {
        $this->em->persist($order);
        // flush — в Service
    }
}
```

## Рекомендации

1. **Один flush в конце use-case** — целостность агрегата
2. **JOIN для коллекций** — избегай N+1
3. **Валидация в aggregate root** — не позволяй невалидному состоянию
4. **Не разделяй aggregate на разные Repository** — aggregate root единый
5. **Используй Type Hint для collections** — ArrayCollection

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

# Диагностика и решение проблемы N+1 в Doctrine

Хорошая практическая тема — N+1 это одна из самых частых причин тормозов Doctrine. Разберём диагностику по шагам и способы решения.

## Диагностика

### Шаг 1: Symfony Debug Toolbar

Symfony по умолчанию показывает, сколько запросов сделал Doctrine:

```
Doctrine: 45 requests in 12ms
```

Если число запросов кратно числу сущностей — это N+1.

### Шаг 2: Profiler + Doctrine

## Способы решения

### Способ 1: JOIN в QueryBuilder

```php
// Плохо
$orders = $repository->findAll();

// Хорошо — JOIN в одном запросе
$orders = $em->getRepository(Order::class)
    ->createQueryBuilder('o')
    ->leftJoin('o.items', 'i')
    ->addSelect('i')
    ->leftJoin('o.author', 'a')
    ->addSelect('a')
    ->getQuery()
    ->getResult();
```

**Trade-offs:**
- ✅ **Один запрос** вместо N
- ✅ **Максимальный контроль**
- ❌ **Ручная работа** — нужно помнить о JOIN
- ❌ **Можно забыть** в новом методе

### Способ 2: DQL с fetch join

```php
$dql = 'SELECT o, i FROM Order o JOIN o.items i WHERE o.status = :status';
$orders = $em->createQuery($dql)
    ->setParameter('status', 'PENDING')
    ->getResult();
```

**Trade-offs:**
- ✅ **Один запрос**
- ✅ **Чистый DQL**
- ❌ **Требует знания DQL**
- ❌ **Сложнее читать**

### Способ 3: Custom Repository с JOIN

```php
class OrderRepository extends ServiceEntityRepository
{

    {
        return $this->createQueryBuilder('o')
            ->leftJoin('o.items', 'i')
            ->addSelect('i')
            ->getQuery()
            ->getResult();
    }
}
```

**Trade-offs:**
- ✅ **Повторное использование**
- ✅ **Чистый код**
- ❌ **Нужно помнить** о наличии метода

### Способ 4: Lazy Loading через Proxy (с оговорками)

```php
// Доступ к proxy → тот же N+1
```

**Trade-offs:**
- ❌ **Не решает проблему**
- ⚠️ **Лень использования**

### Способ 5: Second Level Cache

```php

    orm:
        second_level_cache:
            region_cache_driver:
                type: array
```

**Trade-offs:**
- ✅ **Кэширование** — снижение нагрузки
- ❌ **Сложность** — инвалидация, cache invalidation
- ❌ **Не всегда уместно** — volatile данные

### Способ 6: DTO Projection

Иногда лучше вообще не грузить сущности:

```php
// Плохо: грузим сущности
$orders = $repository->findAll();

// Хорошо: грузим DTO
$orders = $em->createQueryBuilder()
    ->select('new App\Dto\OrderDto(o.id, o.total, COUNT(i.id))')
    ->from(Order::class, 'o')
    ->leftJoin('o.items', 'i')
    ->groupBy('o.id')
    ->getQuery()
    ->getResult();
```

**Trade-offs:**
- ✅ **Один запрос**
- ✅ **Экономия памяти**
- ❌ **Отдельный класс DTO**
- ❌ **Потеря entity functionality**

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

# Ограничения целостности в PostgreSQL: зачем, если валидация в коде

Отличный вопрос — потому что здесь есть тонкая грань. Давай разберёмся.

## Почему это не дублирование, а defense-in-depth

Ключевая мысль: **валидация в коде и ограничения в БД — это не конкурирующие, а дополнительные слои защиты**.

Причины, почему нужны оба:

1. **Защита от «дыр» в логике** — код всегда можно обойти
2. **Многопоточность/параллельный доступ** — валидация в коде не атомарна
3. **Разные клиенты** — API, админка, миграции, прямой доступ к БД
4. **Инварианты данных** — некоторые правила должны выполняться всегда, независимо от того, кто пишет

## Средства PostgreSQL и их применение

### 1. NOT NULL

```sql
-- Обязательные поля
ALTER TABLE orders 
    ALTER COLUMN customer_id SET NOT NULL,
    ALTER COLUMN created_at SET DEFAULT now();
```

**Когда использовать:** всегда для обязательных полей — cheapest way to prevent NULL.

### 2. CHECK constraints

```sql
-- Валидация вне PHP
ALTER TABLE orders
    ADD CONSTRAINT chk_status 
    CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
    ADD CONSTRAINT chk_amount_positive 
    CHECK (amount > 0),
    ADD CONSTRAINT chk_email_format 
    CHECK (email ~ '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$');
```

**Когда использовать:**
- ✅ Формат данных (email, phone, JSON)
- ✅ Диапазоны (0-100%, положительные суммы)
- ✅ Ограниченные перечни (ENUM-аналоги)

**Подводный камень:** MySQL/другие СУБД не поддерживают CHECK — это привязывает к PostgreSQL.

### 3. UNIQUE constraints

```sql
-- Уникальность
ALTER TABLE users ADD CONSTRAINT uniq_email UNIQUE (email);

-- Составная уникальность
ALTER TABLE order_items 
    ADD CONSTRAINT uniq_item 
    UNIQUE (order_id, product_id);
```

**Когда использовать:** когда бизнес-правило «не может быть двух одинаковых».

**Trade-off:** уникальный индекс + ограничение — это два индекса.

### 4. PRIMARY KEY / FOREIGN KEY

```sql
-- Целостность ссылок
ALTER TABLE order_items
    ADD CONSTRAINT fk_order 
    FOREIGN KEY (order_id) REFERENCES orders(id)
    ON DELETE CASCADE;
```

**When to use:** всегда для внешних ключей — защищает от orphan-записей.

**ON DELETE CASCADE** — автоматическое удаление зависимостей.

### 5. Триггеры (Trigger functions)

```sql
-- Когда CHECK недостаточно
CREATE OR REPLACE FUNCTION check_stock()
RETURNS trigger AS $$
BEGIN
    IF NEW.quantity > 0 THEN
        RETURN NEW;
    ELSE
        RAISE EXCEPTION 'quantity must be positive';
    END IF;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_check_stock
BEFORE INSERT ON order_items
FOR EACH ROW
EXECUTE FUNCTION check_stock();
```

**When to use:**
- ✅ Сложная логика, которую нельзя выразить в CHECK
- ✅ Зависимость от других таблиц/данных
- ✅ Логирование изменений

**Trade-off:** сложнее поддерживать, медленнее, но мощнее.

### 6. Partial indexes

```sql
-- Индекс только для активных заказов
CREATE INDEX idx_active_orders 
ON orders (created_at) 
WHERE status = 'active';
```

**When to use:** когда нужны индексы только для части данных.

### 7. Enumerations

```sql
-- Строго типизированные значения
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'cancelled');
```

**When to use:**
- ✅ Строгая типизация значений
- ✅ Меньше размер данных

**Trade-off:** сложно менять enum (нужна миграция).

## Практический пример: таблица заказов

```sql
CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers(id),
    status order_status NOT NULL DEFAULT 'pending',
    amount DECIMAL(10,2) NOT NULL CHECK (amount > 0),
    email TEXT NOT NULL CHECK (email ~* '^[^@]+@[^@]+$'),
    created_at TIMESTAMP NOT NULL DEFAULT now(),
    CONSTRAINT chk_active CHECK (status IN ('pending', 'paid'))
);

-- Составной индекс для часто используемых запросов
CREATE INDEX idx_orders_customer_status 
ON orders (customer_id, status);
```

## Когда что использовать

| Правило | Средство | Почему |
|---------|----------|--------|
| **Обязательное поле** | NOT NULL | Дешево, всегда |
| **Диапазон** | CHECK | Валидация в БД |
| **Уникальность** | UNIQUE | Защита от дублей |
| **Связь с другой таблицей** | FOREIGN KEY | Целостность ссылок |
| **Сложная логика** | Trigger | Гибкость |
| **Строгий перечень** | ENUM | Типизация |

## Trade-offs и подводные камни

### Производительность
- ✅ Индексы ускоряют запросы
- ❌ Уникальные индексы замедляют вставку
- ❌ Триггеры добавляют накладные расходы

### Портативность
- ❌ CHECK, триггеры, ENUM — PostgreSQL-specific
- ❌ Трудно мигрировать на другую СУБД
- ❌ Тестирование требует БД

### Поддержание
- ❌ Логика в двух местах (код + БД)
- ❌ Нужно синхронизировать изменения
- ❌ Тесты должны проверять и то, и другое

## Рекомендации

1. **NOT NULL + FOREIGN KEY** — всегда
2. **CHECK для простых правил** — формат, диапазоны
3. **UNIQUE для бизнес-уникальности** — email, коды
4. **Trigger для сложной логики** — когда CHECK не справляется
5. ** ENUM для строгих перечней** — статусы, типы

## Главный принцип

> Ограничения в БД — это **последний рубеж защиты**, а не замена валидации в коде.

БД не должна знать о бизнес-логике, но должна гарантировать **фундаментальные инварианты** данных.

# Диагностика и оптимизация медленных запросов в PostgreSQL

Хорошая праксная тема — разберём процесс от диагностики до оптимизации.

## Этап диагностики

### 1. EXPLAIN ANALYZE — главный инструмент

```sql
EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT * FROM orders 
WHERE customer_id = 123 
ORDER BY created_at DESC;
```

**Что смотреть:**
- **Execution Time** — общее время
- **Planning Time** — время планирования
- **Node Types** — какие операции занимают время
- **Actual Rows** — сколько строк на выходе
- **Rows Removed by Filter** — сколько отфильтровано

### 2. Типичные признаки проблем

```
Seq Scan on orders (cost=0.00..25.50 rows=1 width=100)
  Actual Time=10.50..15.20 rows=10000 loops=1
  Filter: (customer_id = 123)
  Rows Removed by Filter: 500000  -- ОЧЕНЬ много!
```

**Красные флаги:**
- **Seq Scan** на большой таблице — нет индекса
- **Rows Removed by Filter** >> Actual Rows
- **Hash Join** / **Merge Join** — плокое присоединение
- **Sort** nodes — внешняя сортировка

## Типовые причины и решения

### Причина 1: Отсутствие индекса

```sql
-- Плохо: Seq Scan
SELECT * FROM orders WHERE customer_id = 123;

-- Решение: создаём индекс
CREATE INDEX idx_orders_customer ON orders (customer_id);
```

**Trade-off:**
- ✅ Быстрее SELECT
- ❌ Медленнее INSERT/UPDATE
- ❌ Больше памяти

### Причина 2: Плохой индекс — wrong column order

```sql
-- Плохо: composite index, но ищем по второй колонке
CREATE INDEX idx_orders_customer_created 
ON orders (customer_id, created_at);

SELECT * FROM orders 
WHERE created_at > '2024-01-01';  -- индекс не используется!
```

**Решение:** правильный порядок колонок:
```sql
CREATE INDEX idx_orders_created_customer 
ON orders (created_at, customer_id);
```

### Причина 3: N+1 запросы

```sql
-- 1000 SELECT запросов вместо 1
SELECT * FROM items WHERE order_id = 1;
SELECT * FROM items WHERE order_id = 2;
-- ... (1000 раз)
```

**Решение:** JOIN или IN:
```sql
SELECT i.* FROM items i 
WHERE i.order_id IN (1, 2, 3, ..., 1000);

-- Или JOIN
SELECT i.* FROM items i 
JOIN orders o ON i.order_id = o.id 
WHERE o.customer_id = 123;
```

### Причина 4: Перегрузка JOIN'ами

```sql
-- Плохо: много JOIN, сложная логика
SELECT * FROM orders o
JOIN items i ON o.id = i.order_id
JOIN customers c ON o.customer_id = c.id
JOIN products p ON i.product_id = p.id
JOIN categories cat ON p.category_id = cat.id
-- ... ещё 5 JOIN
```

**Решение:**
1. Проверяй, нужны ли все JOIN
2. Используй LEFT JOIN вместо JOIN, если возможно
3. Разбивай запросы

### Причина 5: Неоптимальная сортировка

```sql
-- Плохо: внешняя сортировка
SELECT * FROM orders ORDER BY created_at;
-- Sort Method: external 2-way Mergesort  -- на диске!
```

**Решение:** индекс для сортировки:
```sql
CREATE INDEX idx_orders_created ON orders (created_at);
```

# Агрегат в DDD

Хорошая тема — границы агрегата это одно из самых сложных решений в DDD. Разберём что это и как определять.

## Что такое агрегат

**Агрегат** — это кластер из сущностей и value object'ов, которые рассматриваются как единое целое с точки зрения:
- **Целостности** (integrity)
- **Границы транзакции** (transaction boundary)
- **Распределения доступа** (access boundary)

```php
// Aggregate Root — точка входа
class Order {
    // Сущности
    private $items;  // array of OrderItem
    private $history; // array of OrderHistory
    
    // Value Objects
    private Money $total;
}
```

## Ключевые характеристики

### 1. Aggregate Root — единая точка доступа

```php
// Все операции через корень
$order->addItem($product, $qty);
$order->cancel();
$order->pay();
```

**Правило:** Внешний код не имеет прямого доступа к дочерним сущностям.

### 2. Invariants внутри агрегата

```php
class Order {
    public function addItem(Product $product, int $qty): void
    {
        // Валидация целостности
        if ($this->status !== 'PENDING') {
            throw new OrderCannotModifyException();
        }
        if ($qty <= 0) {
            throw new InvalidQuantityException();
        }
        // ... инварианты
    }
}
```

### 3. Consistency — единое состояние

```php
// Изменение одного элемента меняет весь aggregate
$order->addItem($product, 2);
// total пересчитывается автоматически
// history записывается
// всё в едином состоянии
```

## Определение границ агрегата

### Правило: границы определяются через invariants

```php
// Если изменение A зависит от изменения B — 
// они в одном агрегате
class Order {
    public function addItem(Product $product, int $qty): void
    {
        // total зависит от items
        $this->total = $this->calculateTotal();
    }
    
    private function calculateTotal(): Money
    {
        $total = 0;
        foreach ($this->items as $item) {
            $total += $item->getProduct()->getPrice() * $item->getQuantity();
        }
        return Money::fromFloat($total);
    }
}
```

### Правило: если нужны внешние ссылки — не в aggregate

```php
// Плохо: Order ссылается на Payment прямо
class Order {
    private Payment $payment;  // не должно быть здесь
}

// Хорошо: ссылка на Payment через ID
class Order {
    private ?string $paymentId;  // внешний ID
}
```

## Пример: интернет-магазин

### Агрегат «Order»

```php
namespace App\Domain\Order;

class Order
{
    private array $items;      // OrderItem[]
    private array $history;    // OrderHistory[]
    private Money $total;
    private OrderStatus $status;
    
    public function __construct(int $id, Customer $customer)
    {
        $this->id = $id;
        $this->customer = $customer;
        $this->items = [];
        $this->history = [];
        $this->total = Money::fromFloat(0);
        $this->status = OrderStatus::PENDING;
    }
    
    // Методы изменяющие aggregate root
    public function addItem(Product $product, int $qty): void
    {
        $this->guardPending();
        $this->items[] = new OrderItem($product, $qty);
        $this->total = $this->recalculate();
        $this->recordEvent(new ItemAddedEvent($product, $qty));
    }
    
    public function pay(): void
    {
        $this->guardPending();
        $this->status = OrderStatus::PAID;
        $this->recordEvent(new OrderPaidEvent());
    }
    
    // Внутренние инварианты
    private function guardPending(): void
    {
        if ($this->status !== OrderStatus::PENDING) {
            throw new OrderCannotModifyException();
        }
    }
}
```

### Почему именно эти границы?

| Элемент | Внутри aggregate? | Почему |
|---------|------------------|--------|
| **items** | ✅ Да | Зависит от total — инвариант |
| **status** | ✅ Да | Состояние aggregate |
| **total** | ✅ Да | Производная от items |
| **customer** | ⚠️ Ссылка | Внешняя сущность |
| **payment** | ⚠️ Ссылка | Внешняя сущность |

## Типовые ошибки при выборе границ

### Ошибка 1: Too big aggregate (аномалия)

```php
// Плохо: Order + items + payment + shipping + reviews + 
//        notifications + ... — всё в одном
class Order {
    private Reviews $reviews;      // не должно быть здесь
    private Shipping $shipping;    // не должно быть здесь
}

// Причина: все хотят менять Aggregate Root
// Результат: огромный класс, сложно тестировать
```

**Решение:** Разделить на отдельные aggregate.

### Ошибка 2: Too small aggregate (fragmentation)

```php
// Плохо: каждый item — отдельная сущность
class OrderItem {
    // каждый item свой aggregate — сложно управлять
}

// Причина: «правильно» с точки зрения DDD, но
// нарушается целостность
// Результат: сложно поддерживать invariants
```

**Решение:** Сгруппировать в aggregate root.

### Ошибка 3: External references вместо ID

```php
// Плохо: ссылки на другие aggregate
class Order {
    private Payment $payment;  // внешний aggregate
}

// Хорошо: ID
class Order {
    private ?string $paymentId;
}

// Причина: aggregate не должен знать о других
// Результат: нарушения целостности
```

### Ошибка 4: Mixing value objects and entities

```php
// Плохо: mixing

    private Money $total;         // value object
    private Payment $payment;     // entity (внешний)
}

// Решение: separating по границам
```

1. **Invariants** — что должно быть всегда верно?
2. **Consistency** — что должно меняться вместе?
3. **Transaction** — что в одной транзакции?
4. **Access** — кто имеет доступ к чему?
5. **External references** — какие ссылки?

## Практический совет

> Границы aggregate определяются не по «физической близости» данных, а по **инвариантам целостности**.

Проверь: «Могу ли я изменить A без изменения B?» Если нет — они в одном aggregate.

# Одновременное изменение одного агрегата двумя процессами

Отличный вопрос о concurrency — это критически важная проблема в распределённых системах. Разберём что происходит и как проектировать.

## Что произойдёт без защиты

### Классическая гонка (race condition)

```
Process A: Read Order (id=5, status=PENDING, total=100)
Process B: Read Order (id=5, status=PENDING, total=100)

Process A: Add item (total=150)
Process A: Write Order (status=PENDING, total=150)

Process B: Add item (total=200)  // работает со stale data!
Process B: Write Order (status=PENDING, total=200)

// ИТОГ: total=200, но должно быть 250!
// Данные A потеряны — lost update
```

### Потерянное обновление (Lost Update)

```
T1: A reads (total=100)
T2: B reads (total=100)
T3: A writes (total=150)  // A's change committed
T4: B writes (total=200)  // B's change OVERWRITES A's
   // A's +50 is LOST
```

## Решения

### 1. Optimistic Locking (рекомендуемо)

Используем версию (version) агрегата.

```php
class Order
{
    #[ORM\Column]
    private int $version; // для optimistic locking
    
    public function incrementVersion(): void
    {
        $this->version++;
    }
}
```

**В Doctrine:**

```php
class Order
{
    #[ORM\Version] // @Version annotation
    private int $version = 0;
}
```

**Логика:**

```php
// В Repository
public function save(Order $order): void
{
    $current = $this->em->getRepository(Order::class)
        ->find($order->getId());
    
    if ($current->getVersion() !== $order->getVersion()) {
        // CONFLICT — кто-то изменил
        throw new ConcurrentModificationException();
    }
    
    $order->incrementVersion();
    $this->em->flush();
}
```

**Trade-offs:**
- ✅ **Простота** — добавляем поле version
- ✅ **Высокая параллельность** — нет блокировок
- ❌ **Нужна обработка конфликтов**
- ❌ **Возможны retry'ы**

### 2. Pessimistic Locking

Блокируем запись на время транзакции.

```php
// Doctrine
$order = $this->em->getRepository(Order::class)
    ->find($id, LockMode::PESSIMISTIC_WRITE);

// SQL: SELECT ... FOR UPDATE
```

**Trade-offs:**
- ✅ **Гарантия** — нет race condition
- ❌ **Низкая параллельность** — другие ждут
- ❌ **Deadlock risk**
- ❌ **Сложность** — управление lock'ами

### 3. Database-level constraints

Используем валидацию на уровне БД.

```sql
-- CHECK constraint для валидации состояния
ALTER TABLE orders 
    ADD CONSTRAINT chk_status 
    CHECK (status IN ('pending', 'paid'));

-- Transaction isolation level
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

**Trade-offs:**
- ✅ **Надёжность** — защита на уровне БД
- ❌ **Сложность** — нужно знать SQL
- ❌ **Не портативно**

### 4. External Locking (Redis/Memcache)

Внешняя блокировка.

```php
class OrderLock {
    public function __construct(private Redis $redis) {}
    
    public function acquire(string $orderId): bool
    {
        return $this->redis->set("lock:order:$orderId", 1, ['nx' => true, 'ex' => 60]);
    }
    
    public function release(string $orderId): void
    {
        $this->redis->del("lock:order:$orderId");
    }
}
```

**Trade-offs:**
- ✅ **Гибкость** — внешняя система
- ❌ **Дополнительная инфраструктура**
- ❌ **Сложность** — нужно управлять lifetime

### 5. Queued Processing (рекомендуемо для high-load)

Обрабатываем изменения последовательно.

```php
// Все изменения одного агрегата — в очередь
class OrderChangeQueue
{
    public function __construct(private Queue $queue) {}
    
    public function enqueue(Order $order, Change $change): void
    {
        $this->queue->push("order:{$order->getId()}", $change);
    }
}

// Single consumer processes changes sequentially
class OrderProcessor
{
    public function process(Order $order, Change $change): void
    {
        // Применяем изменение
        $order->apply($change);
        $this->repository->save($order);
    }
}
```

**Trade-offs:**
- ✅ **Гарантия порядка** — последовательно
- ✅ **Высокая параллельность** — разные aggregate
- ❌ **Задержка** — async processing
- ❌ **Сложность** — need queue infrastructure

## Проектирование с учётом concurrency

### Рекомендация: Optimistic + Retry

```php
class OrderService
{
    public function __construct(
        private OrderRepository $orders,
        private RetryPolicy $retry
    ) {}
    
    public function addItem(int $orderId, Product $product, int $qty): Order
    {
        return $this->retry->execute(function() use ($orderId, $product, $qty) {
            $order = $this->orders->find($orderId);
            
            // Пытаемся применить изменение
            $order->addItem($product, $qty);
            
            // Если conflict — try() перезапустит
            return $order;
        });
    }
}
```

### Pattern: Compare-And-Swap

```php
// CAS — атомарная операция
class OrderRepository
{
    public function save(Order $order): void
    {
        // Compare current version, Swap if match
        $result = $this->db->execute(
            'UPDATE orders SET total = :total, version = version + 1 
             WHERE id = :id AND version = :current_version',
            [
                'total' => $order->getTotal()->toFloat(),
                'id' => $order->getId(),
                'current_version' => $order->getVersion(),
            ]
        );
        
        if ($result->rowCount() === 0) {
            throw new ConcurrentModificationException();
        }
    }
}
```

## Выбор стратегии

| Сценарий | Стратегия |
|----------|-----------|
| **Low concurrency** | Optimistic Locking |
| **High concurrency, low latency** | Queued Processing |
| **Critical data** | Pessimistic Locking |
| **Distributed system** | External Locking |

## Практический совет

> **Никогда не предполагай отсутствие concurrency.** Всегда защищайся от race conditions.

- **Optimistic Locking** — default для большинства случаев
- **Queued Processing** — для high-load систем
- **Pessimistic** — для критичных операций

# Доменные события в DDD

Отличная тема — доменные события это мощный инструмент, но с подводными камнями. Разберём всё по порядку.

## Что такое доменное событие

**Доменное событие** — это факт, произошедший в домене, о котором другие части системы хотят узнать.

```php
class OrderShippedEvent
{
    public function __construct(
        private string $orderId,
        private \DateTimeImmutable $shippedAt,
    ) {}
}

class PaymentSucceededEvent
{
    public function __construct(
        private string $paymentId,
        private float $amount,
    ) {}
}
```

## Когда публиковать

### Правило: публикуй, когда факт произошёл в aggregate

```php
class Order
{
    private array $events;
    
    public function markAsShipped(): void
    {
        // Меняем состояние
        $this->status = OrderStatus::SHIPPED;
        
        // Регистрируем событие
        $this->events[] = new OrderShippedEvent($this->id, new \DateTimeImmutable());
    }
    
    public function popEvents(): array
    {
        $events = $this->events;
        $this->events = [];
        return $events;
    }
}
```

### Когда НЕ публиковать

- **Валидация** — это не событие
- **Изменения состояния** — только значимые факты
- **Внутренние операции** — только то, что нужно другим

## Как обрабатывать

### Вариант 1: Event Dispatcher (Symfony)

```php
// Публикация
$this->eventDispatcher->dispatch(new OrderShippedEvent($id));

// Обработчик
#[AsEventListener(event: 'order.shipped')]
class OrderShippedHandler
{
    public function __invoke(object $event): void
    {
        // Обновление поискового индекса
        $this->searchIndex->update($event->orderId);
    }
}
```

### Вариант 2: Domain Event Bus (в домене)

```php
// В aggregate root
private array $domainEvents = [];

public function addDomainEvent(object $event): void
{
    $this->domainEvents[] = $event;
}

// При сохранении
public function getDomainEvents(): array
{
    $events = $this->domainEvents;
    $this->domainEvents = [];
    return $events;
}
```

## Проблемы, которые решают доменные события

### 1. Decoupling (развязка)

```php
// БЕЗ событий: tight coupling
class OrderService {
    public function ship(Order $order): void {
        $order->markAsShipped();
        $this->searchIndex->update($order->getId());  // прямая зависимость
        $this->email->send('shipping');  // прямая зависимость
        $this->analytics->track('shipped');  // прямая зависимость
    }
}

// С событиями: decoupling
class OrderService {
    public function ship(Order $order): void {
        $order->markAsShipped();  // только меняем состояние
    }
}

// Отдельные обработчики реагируют
```

### 2. Async processing

```php
// Отправка email — async
$this->eventDispatcher->dispatch(new OrderShippedEvent($id));
// email отправится позже
```

### 3. Consistency (eventual)

```php
// Обновление индекса — не синхронно
// Система в конечном итоге согласована
```

## Проблемы, которые создают доменные события

### 1. Eventual consistency

```php
// Данные не сразу, а «в конце концов»
// Тесты должны учитывать async
```

### 2. Order of events

```php
// Порядок обработки важен
// order.shipped должен быть перед order.cancelled
```

### 3. Debugging

```php
// Сложно отследить цепочку событий
// Нужны инструменты логирования
```

### 4. Duplicate processing

```php
// Событие может обработаться дважды
// Нужна idempotency
```

## Связь с транзациями базы данных

### Критически важный вопрос!

```php
// Плохо: события после flush
$this->em->persist($order);
$this->em->flush();  // committed
// Теперь события
$this->eventDispatcher->dispatch(new OrderShippedEvent($id));
// Если dispatcher падает — committed change, но no event!
```

### Решение: Events before commit (Transactional Outbox)

```php
// Решение 1: события до flush
$order->markAsShipped();  // event added to aggregate
$events = $order->getDomainEvents();

$this->em->flush();  // committed
// Now dispatch events — they're safe
foreach ($events as $event) {
    $this->eventDispatcher->dispatch($event);
}
```

### Решение 2: Transactional Outbox pattern

```php
// 1. Событие сохраняется в outbox (в той же транзакции)
$this->em->persist($order);
$this->em->persist(new OutboxMessage($event));
$this->em->flush();  // committed — both order AND event

// 2. Worker читает outbox и разсылает
class OutboxWorker {
    public function process(): void {
        $messages = $this->outboxRepository->getUnsent();
        foreach ($messages as $message) {
            $this->dispatcher->dispatch($message->toDomainEvent());
            $this->outboxRepository->markSent($message);
        }
    }
}
```

### Проблема: Events vs DB consistency

| Подход | Проблема | Решение |
|--------|----------|---------|
| **Events after flush** | Если dispatcher падает — no event | Transactional Outbox |
| **Events before flush** | Events не committed | Transactional Outbox |
| **Transactional Outbox** | Extra table | Worker processing |

## Практический пример

### Aggregate с событиями

```php
        $this->status = OrderStatus::PAID;
        $this->domainEvents[] = new OrderPaidEvent($this->id);

    public function popDomainEvents(): array
    {
```

### Service с транзакцией

```php
class PaymentService
{
    public function __construct(
        private EntityManagerInterface $em,
        private EventDispatcherInterface $dispatcher
    ) {}
    
    public function pay(int $orderId): void
    {
        $order = $this->em->getRepository(Order::class)->find($orderId);
        $order->pay();
        
        // События собраны до flush
        $events = $order->popDomainEvents();
        
        // Commit
        $this->em->flush();
        
        // Dispatch AFTER commit
        foreach ($events as $event) {
            $this->dispatcher->dispatch($event);
        }
    }
}
```

1. **Events before commit** — через Transactional Outbox
2. **Idempotent handlers** — защита от duplicate
3. **Event ordering** — порядок обработки
4. **Async для heavy operations** — email, search
5. **Sync для critical consistency** — в той же транзакции

## Trade-offs

| Плюс | Минус |
|------|-------|
| **Decoupling** | Eventual consistency |
| **Async processing** | Order of events |
| **Scalability** | Debugging complexity |
| **Maintainability** | Duplicate processing |

# Value Object vs Entity в DDD

Отличные вопросы — это фундаментальные концепции DDD. Разберём всё по порядку.

## Value Object vs Entity

### Ключевое отличие: Identity

```php
// Entity — имеет identity
class User
{
    private int $id;  // уникальная идентификация
}

// Value Object — определяется значениями
class Money
{
    // Нет identity — две суммы по 100 это «один и тот же»
}
```

### Entity

| Характеристика | Значение |
|----------------|----------|
| **Identity** | ✅ Есть (id) |
| **Mutable** | ✅ Обычно да |
| **Логика** | ✅ Да (методы) |
| **Сравнение** | ✅ По identity |
| **Жизненный цикл** | ✅ Длинный |

```php
class Order
{
    private int $id;
    
    public function markAsShipped(): void
    {
        // Меняем состояние, но это тот же order
        $this->status = OrderStatus::SHIPPED;
    }
}
```

### Value Object

| Характеристика | Значение |
|----------------|----------|
| **Identity** | ❌ Нет |
| **Immutable** | ✅ Всегда |
| **Логика** | ✅ Да |
| **Сравнение** | ✅ По значениям |
| **Жизненный цикл** | ⚠️ Временный |

```php
class Money implements \JsonSerializable
{
    private function __construct(
        private float $amount,
        private string $currency,
    ) {}
    
    public static function from(float $amount, string $currency): self
    {
        return new self($amount, $currency);
    }
    
    // Immutable — новый экземпляр
    public function add(self $other): self
    {
        Money::assertSameCurrency($this, $other);
        return self::from($this->amount + $other->amount, $this->currency);
    }
    
    // Comparaison по значениям
    public function equals(self $other): bool
    {
        return $this->amount === $other->amount 
            && $this->currency === $other->currency;
    }
}
```

## Как решать: к чему что относить

### Критерии для Entity

```php
// Это Entity, если:
// 1. Есть уникальный идентификатор
// 2. Важна идентичность во времени
// 3. Есть жизненный цикл
// 4. Можно менять состояние

    // Entity: order #12345 всегда #12345
}

    // Entity: мы знаем, что это тот же человек
}

class Product {
    // Entity: у каждого товара свой id
}
```

### Критерии для Value Object

```php
// Это Value Object, если:
// 1. Нет identity — только значения
// 2.Immutable
// 3. Определяется значениями
// 4. Можно заменить без последствий

class Money {
    // VO: сумма 100 рублей = сумма 100 рублей
}

class Address {
    // VO: адрес "Ленина 15" = "Ленина 15"
}

class Email {
    // VO: "user@example.com" = "user@example.com"
}

class DateRange {
    // VO: период с по = период с по
}
```

### Сложные случаи

```php
// Product — Entity (есть id)

    // Value Object: спецификация = спецификация

// OrderItem — Composite

```

## Правило зависимостей (Dependency Rule)

**Ключевой принцип:** зависимости направлены внутрь, от периферии к центру.

```
                    ┌─────────────────┐
                    │     Entities     │  <- ядро домена
                    │  (Business Rules)│
                    └────────┬────────┘
                             ↑
                    ┌────────▼────────┐
                    │ Use Cases        │  <- application logic
                    │ (Interactors)    │
                    └────────┬────────┘
                             ↑
                    ┌────────▼────────┐
                    │ Infrastructure   │  <- Doctrine, Symfony, etc.
                    │ (Adapters)       │
                    └────────┬────────┘
                             ↑
                    ┌─────────────────┐
                    │   Interface      │  <- controllers, web
                    │   Adapters       │
                    └─────────────────┘
```

## Слои (из внутрь наружу)

### 1. Domain Layer (Entities + Value Objects)

**Что здесь:**
- Доменные сущности (Entities)
- Value Objects
- Домальные сервисы

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

# Concurrent modification записи в базе

Хороший вопрос о concurrency — разные подходы решают разные проблемы. Разберём детально.

## Какие проблемы возникают

### 1. Lost Update (потерянное обновление)

```
T1: A reads record (value=100)
T2: B reads record (value=100)
T3: A writes (value=150)  // committed
T4: B writes (value=200)  // OVERWRITES A's update
   // A's +50 LOST!
```

### 2. Dirty Read

```
T1: A writes (value=150)  // NOT committed yet
T2: B reads (value=150)   // sees uncommitted data
T3: A rolls back           // A's changes undone
T4: B now has wrong data
```

### 3. Non-repeatable Read

```
T1: A reads (value=100)
T2: B writes (value=200)  // committed
T3: A reads again (value=200)  // different result
```

### 4. Phantom Read

```
T1: A reads all rows (3 rows)
T2: B inserts row            // committed
T3: A reads again (4 rows)   // "phantom" row
```

## Способы защиты

### 1. Transaction Isolation Levels

| Уровень | Dirty Read | Non-Repeatable | Phantom | Performance |
|---------|-----------|----------------|---------|-------------|
| **READ UNCOMMITTED** | ✗ | ✗ | ✗ | Fast |
| **READ COMMITTED** | ✓ | ✗ | ✗ | Normal |
| **REPEATABLE READ** | ✓ | ✓ | ✗ | Slower |
| **SERIALIZABLE** | ✓ | ✓ | ✓ | Slowest |

**PostgreSQL default:** READ COMMITTED

```sql
START TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- или
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

### 2. Optimistic Locking

**Через version column:**

```php
class Product
{
    #[ORM\Column]
    private int $version = 0;
    
    public function incrementVersion(): void
    {
        $this->version++;
    }
}
```

**SQL:**
```sql
UPDATE products 
SET price = 150, version = version + 1 
WHERE id = 1 AND version = 5;  -- compare version

-- rowCount = 0 → CONFLICT!
```

**Trade-offs:**
- ✅ **High concurrency** — no blocking
- ✅ **Simple** — добавляем поле version
- ❌ **Conflict detection** — нужно обработать
- ❌ **Retries** — возможно

### 3. Pessimistic Locking

**PostgreSQL:** `SELECT ... FOR UPDATE`

```php
// Doctrine
$product = $em->getRepository(Product::class)
    ->find(1, LockMode::PESSIMISTIC_WRITE);

// SQL: SELECT ... FOR UPDATE
```

**Trade-offs:**
- ✅ **No lost updates** — guarantee
- ❌ **Blocking** — others wait
- ❌ **Deadlock risk**
- ❌ **Low concurrency**

### 4. Database-level guards

**CHECK constraints:**
```sql
ALTER TABLE products
    ADD CONSTRAINT chk_price 
    CHECK (price > 0);
```

**Triggers:**
```sql
-- Locking check
CREATE FUNCTION price_check() RETURNS trigger AS $$
BEGIN
    IF NEW.price < OLD.price THEN
        RAISE EXCEPTION 'price must increase';
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

**Trade-offs:**
- ✅ **Guarantee** — DB-level
- ❌ **Rigid** — hard to change
- ❌ **Complex** — harder to test

### 5. Application-level locking

**External lock (Redis):**
```php
class ProductLock {
    public function lock(int $id): void {
        $this->redis->set("lock:product:$id", 1, 
            ['nx' => true, 'ex' => 30]);
    }
    public function unlock(int $id): void {
        $this->redis->del("lock:product:$id");
    }
}
```

**Trade-offs:**
- ✅ **Flexible** — external
- ❌ **Complexity** — extra system
- ❌ **Failure risk** — need timeout

### 6. Queued processing

**Sequential processing:**
```php
// All changes queued
$queue->push("product:1", $change);

// Single consumer processes sequentially
class ProductProcessor {
    public function process(Product $product, Change $change): void {
        $product->apply($change);
        $this->repository->save($product);
    }
}
```

**Trade-offs:**
- ✅ **Guarantee order** — sequential
- ✅ **High concurrency** — different records
- ❌ **Latency** — async
- ❌ **Complexity** — queue infra

## Сравнение подходов

| Подход | Lost Update | Performance | Complexity | When |
|--------|-------------|-------------|------------|------|
| **Isolation** | ✓ | Med | Low | Simple cases |
| **Optimistic** | ✓ | High | Low | High concurrency |
| **Pessimistic** | ✓ | Low | Med | Critical data |
| **DB guards** | ✓ | Med | High | Strict rules |
| **App lock** | ✓ | Med | High | Distributed |
| **Queued** | ✓ | Med | High | High-load |

## Когда какой выбирать

### Low concurrency → Isolation

```php
// Простая система, мало пользователей
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```

### High concurrency → Optimistic

```php
// Много пользователей, low criticality
// version column + conflict handling
```

### Critical data → Pessimistic

```php
// Финансы, критичные операции
// SELECT ... FOR UPDATE
```

## Практический пример

### Optimistic + Retry

```php
class ProductService {
    public function updatePrice(int $id, float $newPrice): void {
        $retry = 0;
        while ($retry < 3) {
            try {
                $product = $this->em->getRepository(Product::class)
                    ->find($id);
                
                // Update
                $product->setPrice($newPrice);
                $product->incrementVersion();
                
                $this->em->flush();  // committed
                return;
            } catch (OptimisticLockException $e) {
                // Conflict — retry
                $retry++;
                $this->em->clear();
            }
        }
        throw new TooManyRetriesException();
    }
}
```

## Рекомендации

1. **Low concurrency** → Isolation levels
2. **High concurrency** → Optimistic locking
3. **Critical data** → Pessimistic locking
4. **High-load** → Queued processing
5. **Always** → Consider DB-level guards

Отличная ситуация — обе требуют зрелости и коммуникации. Разберём каждый случай.

## а) Нашёл попутный баг, не связанный с задачей

### Мой подход

**1. Зафиксируй находку**

```markdown
## Найденный баг
- **Описание:** в методе X происходит Y вместо Z
- **Воспроизведение:** шаги для复现
- **Влияние:** насколько серьёзный
- **Где находится:** файл:строка
```

**2. Оцени серьёзность**

| Критичность | Действие |
|-------------|----------|
| **🔴 Блокирует** (CRITICAL) | Остановись, реши сразу |
| **🟡 Серьёзный** (MAJOR) | Зафиксируй, обсуди |
| **🟢 Мелкий** (MINOR) | Заведи задачу |

**3. Действия по критичности**

### Критичный баг (блокирует работу)

```php
// Например, баг в оплате — блокирует бизнес
// Это нужно решить, даже вне задачи
```

**Почему:** если баг блокирует основную функциональность, 
его нельзя игнорировать. Но:
- Связаться с руководителем / заказчиком
- Оценить, можно ли временно «забыть» о задаче

### Серьёзный баг (но не блокирующий)

```markdown
## Что сделаю
1. Зафиксирую баг (GitHub issue / Jira)
2. Продолжу текущую задачу
3. Обсужу с тимлидом: «Нашёл баг X, 
   рекомендую выделить в отдельную задачу»
```

**Почему:** не стоит отклоняться от задачи ради 
«соседского» бага — это раздувает PR.

### Мелкий баг

```markdown
- Завести отдельную задачу
- Не включать в текущий PR
- (Возможно) поправить, если < 5 минут
```

**Почему:** 
- Мелкие правки раздувают PR
- Отдельная задача проще ревью
- Чистая история комитов

### Практический совет

> **Separation of concerns:** каждый PR решает одну задачу. 
> Баг → отдельная задача, даже если «мелкий».

**Преимущества:**
- ✅ PR остаётся фокусированным
- ✅ Легче ревью
- ✅ Чистая история
- ✅ Баг не потеряется

## б) Критерием приёмки противоречит цель задачи

### Это серьёзнее! 

**Почему:** противоречие означает, что:
- Цели задачи сформулированы некорректно
- Критерии приёмки устарели
- Непонимание между заказчиком и исполнителем

### Мой подход

**1. Не делать вид, что всё ок**

```
❌ «Просто сделаю как в критериях»
   — создашь неверный продукт
❌ «Просто сделаю как понял цель»
   — проигнорируешь требования
```

**2. Проанализировать противоречие**

```markdown
## Противоречие
- **Критерий приемки:** X
- **Цель задачи:** Y
- **В чем конфликт:** ...
```

**Пример:**

```markdown

- **Критерий:** «Отображать все заказы без фильтрации»
- **Цель:** «Помочь найти заказы из прошлого»
- **Конфликт:** без фильтрации пользователь 
  тонет в списке старых заказов
```

**3. Определить приоритет**

| Сценарий | Приоритет |
|----------|-----------|
| **Критерий явно устарел** | Цель > Критерий |
| **Цель расплывчата** | Критерий > Цель |
| **Оба неоднозначны** | Обсудить |


**Почему:** нельзя угадывать намерения заказчика. 
Лучше уточнить, чем сделать неправильно.

### Вариант B: Можно предложить решение

```markdown
## Что сделаю
1. Сформулирую своё понимание цели
2. Предложить решение:
   «Похоже, X и Y конфликтуют. 
   Предлагаю: Z (объяснить почему)
   Согласуете?»
3. Получить подтверждение
4. Реализовать согласованное решение
```

**Почему:** проактивность ценится. 
Предложи решение, а не только проблему.

### Практический пример

```markdown
## Ситуация
- **Цель:** «Помочь найти заказы из прошлого»
- **Критерий:** «Отображать все заказы» (без фильтра)

3. После подтверждения реализую
```

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

# FORCE INDEX в PostgreSQL

Хорошая тема — FORCE INDEX (в PostgreSQL это `FORCE_INDEX` через hint'ы в расширениях, или `SET plan_cache_mode`, но чаще используется через `setenable`). Разберём, что это и когда применять.

## Важное уточнение

**В PostgreSQL нет нативного `FORCE INDEX`** как в MySQL. В PostgreSQL используются другие механизмы. Разберём, что есть.

## Механизмы управления индексами в PostgreSQL

### 1. `SET enable_indexscan`, `SET enable_seqscan`

```sql
-- Запретить sequential scan — заставить использовать индекс
SET enable_seqscan = off;

-- Или запретить use индекса
SET enable_indexscan = off;
```

**Применение:**
```sql
-- Force index usage
SET enable_indexscan = on;
SET enable_seqscan = off;

SELECT * FROM orders WHERE customer_id = 123;
```

### 2. Отключение оптимизатора (force в planner)

```sql
-- Разные настройки
SET random_page_cost = 1.1;  -- SSD
SET effective_cache_size = '8GB';
```

## Чем отличается от MySQL

| MySQL | PostgreSQL |
|-------|-----------|
| `FORCE INDEX` (hint) | `SET enable_...` |
| `FORCE INDEX FOR JOIN` | `SET enable_indexjoin` |
| `IGNORE INDEX` | `SET enable_...` |

## Когда применять

### 1. Planner выбрал плохой план

```sql
-- Planner выбрал Seq Scan вместо индекса
EXPLAIN SELECT * FROM orders WHERE customer_id = 123;

-- Seq Scan on orders (cost=0.00..25.50 rows=1 width=100)
```

**Решение:**
```sql
-- Проверить почему
SET enable_seqscan = off;
EXPLAIN SELECT * FROM orders WHERE customer_id = 123;
```

### 2. После изменения статистики

```sql
-- После VACUUM ANALYZE planner может 
-- изменить план
VACUUM ANALYZE orders;
```

### 3. Тестирование альтернативных индексов

```sql
-- Сравнить планы с разными индексами
SET enable_indexscan = on;
SET enable_bitmapscan = off;
EXPLAIN ...;
```

## Практический пример

### Ситуация

```sql
-- Большой запрос, planner использует плохой план
EXPLAIN ANALYZE
SELECT * FROM orders 
WHERE customer_id = 123 
ORDER BY created_at DESC;

-- Seq Scan (плохо!)
```

### Решение

```sql
-- Вариант 1: Force index scan
SET enable_seqscan = off;

-- Вариант 2: Force index specific
-- (PostgreSQL не поддерживает force конкретного индекса)
-- Использовать hint'ы через extensions

-- Вариант 3: Изменить статистику
ANALYZE orders;
```

## Force Index через extensions

### pg_hint_plan

```sql
-- Установка
CREATE EXTENSION IF NOT EXISTS pg_hint_plan;

-- Force index
/*+ IndexScan(orders idx_orders_customer) */
SELECT * FROM orders WHERE customer_id = 123;
```

**Применение:**
```sql
/*+ IndexOnlyScan(orders idx_orders_customer_created) */
SELECT id, created_at FROM orders 
WHERE customer_id = 123;
```

## Типичные случаи применения

| Случай | Механизм |
|--------|----------|
| **Плохой план** | `SET enable_seqscan = off` |
| **После VACUUM** | `ANALYZE` |
| **Тестирование** | `SET enable_...` |
| **Force конкретный** | `pg_hint_plan` |

## Осторожно!

### Почему НЕ стоит часто использовать

```sql
-- ❌ Плохо: форсит индекс всегда
SET enable_seqscan = off;  -- глобально!

-- Это влияет на ВСЕ запросы
```

**Проблемы:**
- ❌ planner неоптимальный
- ❌ влияет на другие запросы
- ❌ сложность поддержки

## Рекомендации

| Сценарий | Решение |
|----------|---------|
| **Один плохой запрос** | `SET` в сессии |
| **Постоянная проблема** | Переписать запрос |
| **Тестирование** | `pg_hint_plan` |
| **Плохая статистика** | `VACUUM ANALYZE` |

## Практический чеклист

1. **EXPLAIN ANALYZE** — понять текущий план
2. **Проверить индекс** — есть ли подходящий
3. **Проанализировать статистику** — `ANALYZE`
4. **Попробовать `SET enable_...`** — temporarily
5. **Переписать запрос** — чаще лучше
6. **pg_hint_plan** — для конкретных hint'ов

## Q25 · Провокации

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

# strict_types=1 и производительность

Хорошая тема! Ответ может удивить — **zero performance impact** (в обычных условиях). Разберём почему.

## Ключевой ответ

```
strict_types=1 → ~0% slowdown в production
```

## Почему так

### strict_types влияет на:

| Что проверяется | Где |
|----------------|-----|
| **Type coercion** | При передаче аргументов |
| **Return types** | При возврате значения |
| **Scalar types** | int, float, string, bool |

**Не проверяется:**
- ✅ Object types
- ✅ Array types
- ✅ Type hints в интерфейсах

## Что происходит при включении

### 1. При вызове функции

```php
<?php
strict_types=1;

function sum(int $a, int $b): int {
    return $a + $b;
}

sum(1, 2);    // OK
sum('1', '2'); // TypeError
```

**Проверка кода:**
```php
// При строгом типе:
// - '1' не будет приведено к int (TypeError)
// - проверка происходит на уровне zend
```

## Измерения производительности

### Benchmarks (приблизительно)

| Сценарий | Разница |
|----------|---------|
| **Функция с scalar type** | ~0.001ms (шутка) |
| **Миллион вызовов** | ~1-2ms |
| **Real-world** | 0% |

**Почему «0%»:**
- Проверка типа — это **C-операция** в zend engine
- Не дороже обычного вызова функции

## Где может быть небольшое влияние

### 1. Проверка return type

```php
function calculate(): int {
    return $this->getValue(); // проверка типа возврата
}
```

**Влияние:** минимальное, только scalar.

### 2. Scalar аргументы в hot path

```php
// В цикле с миллионами вызовов
for ($i = 0; $i < 1000000; $i++) {
    process($i);  // проверка int
}
```

**Влияние:** ~1-2ms на миллион — незначительно.

# Составные первичные ключи в Doctrine ORM

Хорошая тема — Doctrine действительно имеет ограничения с composite keys. Разберём почему и как живут в реальности.

## Почему Doctrine плохо работает с composite PK

### Ограничения ORM

| Причина | Почему проблема |
|---------|-----------------|
| **Identity map** | ORM ждёт single identifier |
| **Cascade operations** | Сложно управлять |
| **Lazy loading** | Proxy для composite tricky |
| **Serialization** | Composite keys hard to cache |

### Техникая причина

```php
// Doctrine Entity
#[ORM\Entity]
class OrderItem
{
    // Doctrine хочет single identifier
    // Composite = (order_id, product_id) — проблема
}
```

## Как живут в реальных проектах

### Решение 1: Сгенерированный ID (рекомендуемо)

```php
#[ORM\Entity]
class OrderItem
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column]
    private ?int $id = null;
    
    // Составной «бизнес-ключ» — обычный column
    #[ORM\Column]
    private int $orderId;
    
    #[ORM\Column]
    private int $productId;
    
    // Уникальность на уровне БД
    // (не через Doctrine)
}
```

**В БД:**
```sql
CREATE TABLE order_items (
    id SERIAL PRIMARY KEY,
    order_id INT NOT NULL,
    product_id INT NOT NULL,
    UNIQUE (order_id, product_id)  -- уникальный constraint
);
```

**Почему:**
- ✅ Doctrine счастлива (single ID)
- ✅ Бизнес-ключ через DB constraint
- ✅ Простота работы

### Решение 2: Embeddable для composite key

```php
#[ORM\Embeddable]
class OrderItemIdentifier
{
    #[ORM\Column]
    private int $orderId;
    
    #[ORM\Column]
    private int $productId;
}

#[ORM\Entity]
class OrderItem
{
    #[ORM\Id]
    #[ORM\Embedded(class: OrderItemIdentifier::class)]
    private OrderItemIdentifier $id;
}
```

**Ограничения:**
- ⚠️ Ограниченная поддержка
- ⚠️ Сложнее в использовании

### Решение 3: Composite key через @Id × N

```php
#[ORM\Entity]
class OrderItem
{
    #[ORM\Id]
    #[ORM\Column]
    private int $orderId;
    
    #[ORM\Id]
    #[ORM\Column]
    private int $productId;
}
```

**Проблемы:**
- ⚠️ Doctrine 2.x имеет баги
- ⚠️ Не все операции работают
- ⚠️ Ограниченная поддержка

## Практический пример

### Bad: Doctrine composite key

```php
#[ORM\Entity]
class UserPreference
{
    #[ORM\Id]
    #[ORM\Column]
    private string $userId;
    
    #[ORM\Id]
    #[ORM\Column]
    private string $preferenceKey;
    
    // Множество проблем:
    // - cascade
    // - identity
    // - lazy loading
}
```

### Good: Single ID + DB constraint

```php
#[ORM\Entity]
class UserPreference
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    #[ORM\Column]
    private ?int $id = null;
    
    #[ORM\Column]
    private string $userId;
    
    #[ORM\Column]
    private string $preferenceKey;
}
```

```sql
-- В БД
ALTER TABLE user_preferences 
    ADD CONSTRAINT uniq_user_preference 
    UNIQUE (user_id, preference_key);
```

## Trade-offs подходов

| Решение | Плюсы | Минусы |
|---------|-------|--------|
| **Single ID** | Doctrine happy | Лишний ID |
| **Embeddable** | Компактно | Ограничено |
| **Composite @Id** | «Правильно» | Баги, сложно |

## Рекомендации

| Сценарий | Решение |
|----------|---------|
| **Большинство случаев** | Single ID + DB constraint |
| **Строгая модель** | Embeddable |
| **Критично** | Composite @Id (с тестами) |

## Практический совет

> **Используй single surrogate ID + DB unique constraint 
> для бизнес-ключа. Doctrine счастлив, БД защищает целостность.**

```php
namespace App\Domain\User;

use App\Domain\User\Email;

class User
{
    private int $id;
    private Email $email;
    private array $events = [];  // domain events
    
    private function __construct(int $id, Email $email)
    {
        $this->id = $id;
        $this->email = $email;
    }
    
    public static function create(Email $email): self
    {
        $user = new self(0, $email);  // 0 = new (not persisted)
        $user->events[] = new UserCreated($email);
        return $user;
    }
    
    public function withId(int $id): self
    {
        $clone = clone $this;
        $clone->id = $id;
        return $clone;
    }
    
    // Validated change
    public function changeEmail(Email $newEmail): void
    {
        // Invariant check
        if ($newEmail->equals($this->email)) {
            return;  // no change
        }
        
        $this->email = $newEmail;
        $this->events[] = new EmailChanged($this->email);
    }
    
    public function email(): Email
    {
        return $this->email;
    }
    
    public function getDomainEvents(): array
    {
        $events = $this->events;
        $this->events = [];
        return $events;
    }
}
```

Отличная ситуация — важна проактивность и честность. Разберём.

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

# Когда код «достаточно хорош» vs продолжать улучшать

Отличная тема — баланс quality vs speed это искусство, не точная наука. Разберём.

## Ключевая идея

**«Enough» ≠ «mediocre»** — достаточно хороший код:
- ✅ Решает задачу
- ✅ Тестируем
- ✅ Поддерживаем
- ❌ Не over-engineered для текущего этапа

## Фреймворк принятия решения

### Матрица приоритетов

| Фактор | Качество | Скорость |
|--------|----------|----------|
| **Core/Domain** | 🔴 Высокое | ⚠️ |
| **Infra/Tooling** | 🟡 Среднее | 🟡 |
| **Prototype/Spikes** | 🟢 Низкое | 🔴 |
| **One-off script** | 🟢 Низкое | 🔴 |

## Когда достаточно «good enough»

| Сценарий | Почему |
|----------|--------|
| **Prototype/MVP** | Проверка гипотезы важнее |
| **One-off script** | Не поддерживается |
| **Spike/Experiments** | Учить, не production |
| **Умирающий проект** | Не стоит вкладывать |

## Когда нужно качество

| Сценарий | Почему |
|----------|--------|
| **Core business logic** | Ошибка дорого стоит |
| **Security-critical** | Взлом = катастрофа |
| **Reusable library** | Many depend on it |
| **Long-lived code** | Поддержка годами |

## Практический чеклист

```markdown
## quality gate для production code
- [ ] Решает задачу?
- [ ] Тестируем (unit/integration)?
- [ ] Нет security issues?
- [ ] Readable другим?
- [ ] Не ломает архитектуру?
- [ ] Есть plan для tech debt?
```

## Баланс в реальном проекте

### Принцип: «Right tool for the job»

```markdown
## По слоям
- **Domain** → Высокое качество (всегда)
- **Application** → Высокое качество
- **Infrastructure** → Среднее качество
- **Tests** → Высокое качество
```

### Принцип: «Technical Debt как кредит»

```
✅ Разумный долг → скорость
❌ Накопленный долг → ипотека
   (дорого, проценты)
```

## Как я решаю

### 1. Оценка стоимости ошибки

```markdown
## Если ошибка дорога:
- Финансы/безопасность
- Много людей зависят
→ Качество прежде всего
```

### 2. Оценка жизненного цикла

```markdown
## Если код «на вечность»:
- Библиотека, фреймворк
- Core система
→ Вкладываться в качество
```

### 3. Наличие ресурсов

```markdown
## Если есть время на refactoring:
- Можно сделать хорошо
❌ Если дедлайн горит:
- Сначала working, потом improve
```

## Красные флаги (нужно улучшить)

| Флаг | Почему |
|------|--------|
| **Security issue** | Нельзя сдавать |
| **Logic too complex** | Непонятно |
| **No tests** | Хрупко |
| **Duplication** | Tech debt |

## Практический пример

```markdown
## Ситуация: deadline скоро

Сделано:
✅ Working code
✅ Basic tests
⚠️ Some code smell

Решение:
- Сдать working version (MVP)
- Записать tech debt tasks
- Refactor в next iteration
```

## Anti-patterns

```
❌ Over-engineering для MVP
❌ «Perfect» → never shipped
❌ Никогда не улучшать
❌ Quality only when no deadline
```

## Совет

> **«Good enough» = working, tested, maintainable. 
> «Over-engineered» = too much for now. 
> «Insufficient» = risky, untested.**
