## 1. Типизированные свойства и улучшенная типизация

**Зачем важно.** До 8.0 свойства классов либо были не типизированными (всё через reflection и `__set`-хаки), либо требовали сеттеров для каждого поля. Nowcasting типизированных свойств позволяет записать инвариант сущности прямо в её определение.

```php
final class Money
{
    /**
     * @param positive-int|0 $amount
     */
    public function __construct(
        public readonly float $amount,
        public readonly string $currency,
    ) {}
}
```

Сужение типов через аннотации (`positive-int|0`) переносит проверку «значение должно быть положительным» из тела метода в сигнатуру — ошибка становится невозможной на уровне вызова, а не в рантайме.

## 2. Readonly-свойства

**Зачем важно.** Значимые объекты (value objects) по определению иммутабельны. Раньше это эмулировалось через приватные сеттеры и кучу копипейста. Теперь иммутабельность — это язык, а не конвенция.

```php
final class Email
{
    public function __construct(public readonly string $value)
    {
        $this->assertValid($this->value);
    }

    public static function fromString(string $value): self
    {
        return new self($value);
    }
}

$e = new Email('a@b.com');
// $e->value = 'x'; // ОШИБКА: readonly свойство
```

Обратите внимание: конструктор-фабрика `fromString` здесь нужен не столько для синтаксиса, сколько для того, чтобы **место создания не совпало с местом валидации** — это позволяет позже расширить логику (например, нормализацию регистра) без изменения контракта.

## 3. Enum-ы

**Зачем важно.** Состояния, которые раньше моделировались через магические строки или константы (и где «неправильная строка» была источником почти всех багов), теперь становятся типобезопасным типом данных.

```php
enum OrderStatus: string
{
    case Pending;
    case Paid;
    case Shipped;
    case Cancelled;

    public function canTransitionTo(OrderStatus $next): bool
    {
        // Машинa состояний: невозможные переходы физически нельзя выразить
        // как допустимые, потому что это просто другой case enum'а.
        return match([$this, $next]) {
            [self::Pending, self::Paid],
            [self::Paid, self::Shipped] => true,
            default => false,
        };
    }
}
```

Здесь ключевой момент для надёжности: **переходы кодируются как отношения между типами**, а не как строковые константы, которые можно напечатать с опечаткой. Компилятор/статический анализатор видит все варианты.

## 4. `match` вместо `switch`

**Зачем важно.** `switch` тихо «проскакивает» при забывчивости с `break` и не возвращает значение по умолчанию — это классический источник молчаливых ошибок. `match` не имеет fall-through и требует исчерпывающего перебора.

```php
// До: легко забыть break → баг
switch ($status) {
    case 'paid': ... // пропустить break
}

// После: exhaustivenesscheck на уровне анализатора
$label = match ($status) {
    OrderStatus::Pending => 'Ожидает',
    OrderStatus::Paid => 'Оплачен',
    // Если добавить новый case — компилятор/PHPStan скажет, что случай не обработан
};
```

## 5. First-class callable syntax

**Зачем важно.** Убирает обёртки `fn ($x) => $this->method($x)` там, где они были нужны исключительно ради передачи вызываемого значения. Меньше шума — меньше возможностей для ошибки.

```php
$process = str_starts_with(...); // или
array_map($this->orderRepository->findByStatus(...), $statuses);
```

## 6. Nullsafe-оператор

**Зачем важно.** Снижает объём вложенной защиты от null, но — и это важно — **делает намерение автора очевидным**: где-то значение может отсутствовать.

```php
// До
$name = $user ? ($user->getProfile() ? $user->getProfile()->getName() : null) : null;

// После
$name = $user?->getProfile()?->getName();
```

## 7. Attributes (атрибуты)

**Зачем важно.** декларативнаяmetadata-информация заменяет конфиг-строки и reflection-хики, что особенно критично в Symfony (маркеры валидации, событий, кэша).

```php
final class User
{
    #[Assert\NotNull]
    #[Assert\Email]
    public string $email;
}
```

## 8. `never`-тип и `never`-возврат

**Зачем важно.** Позволяет сказать компилятору: «после этого кода дальше не идём» — это улучшает анализ достижимости кода.

```php
function fail(string $message): never
{
    throw new InvalidArgumentException($message);
}

function login(string $email): void
{
    $email === '' && fail('Введите email');
    // PHPStan видит, что здесь $email гарантированно не пустой
}
```

Стоит прямо сказать: **большую ценность для надёжности даёт не сама фича, а связка с статическим анализом (PHPStan/Psalm)**. Это не «излишняя скромность», а констатация: PHP сам по себе даёт слабую статическую проверку, и надеяться только на runtime — значит оставлять дыры.

Кроме того, хочу оговорить спорное утверждение: **readonly-свойства и enums не делают код «чистым» автоматически** — можно написать крайне нечитабельный код и с их помощью. Фича снимает ограничения, но дизайн всё равно принимает человек.

## Анализ вопроса

Сразу сделаю важную оговорку, потому что вопрос звучит так, будто в PHP есть некая целостная «система типов», которую можно описать линейно. Это не совсем так: в PHP **три параллельные системы типизации**, и непонимание этой тройственности — источник почти всех заблуждений:

1. **Статическая** — через аннотации (`@param`, `@return`) для PHPStan/Psalm; её **не существует** в рантайме.
2. **Рантймная (декларативная)** — через сигнатуры функций и свойства, проверяется встроенным движком.
3. **Динамическая** — переменные хранят тип в процессе выполнения, и тип переменной может меняться.

Важнейший инсайт: эти три системы **не синхронизированы**. Code-анализатор видит статические типы, движок PHP — только рантаймные, а логика работает с динамическими. Отсюда большинство «дивных» ситуаций.

## 1. Что реально даёт `strict_types`

**Предпосылка вопроса на проверку.** Многие думают, что `strict_types` — это «та самая волшебная штука для типобезопасности». Это не так. `strict_types` влияет **только на подстановку аргументов при вызове функций**, и только на **ковариантность по подклассам/родительским типам**. Давайте по пунктам.

```php
<?php
strict_types = 1;

function sum(float $a, float $b): float
{
    return $a + $b;
}

sum(1, 2);       // ОШИСКА: int не приводится к float автоматически
sum(1.0, 2.0);   // OK
sum(1, 2.5);     // ОШИБКА (первый аргумент — int)
```

**Ключевое:** `strict_types` работает **направленно вниз по иерархии подстановки аргументов**, но **не меняет поведение возвращаемых значений** и **не влияет на присваивания внутри функций**.

```php
<?php
strict_types = 1;

function makeArray(): array
{
    return 'не массив'; // PHPStan осуждает, но ТЫКАЕТ в рантайме? Нет.
}

// Внутри тела функции strict_types НЕ действует.
// Возврат несоответствующего значения — это отдельная история.
```

**Второй критический нюанс — scope.** directive `strict_types` должен быть **первой строкой** файла и действует **только внутри этого файла**. Если вы вызываете функцию из файла A (без strict) из файла B (со strict), то проверка идёт по правилам **вызывающего** контекста. Это редкий источник багов в больших проектах:

```php
// File: Library.php (NO strict_types)
function parse(string $value): int
{
    return intval($value);
}

// File: App.php (strict_types = 1)
require 'Library.php';
$result = parse('42'); // Что будет?
```

Здесь зависит от того, какой контекст применяется к *аргументам*, и это запутанно. На практике решение: **включайте strict_types в каждом файле осознанно**, а не «где-то в проекте».

## 2. Как ведут себя приведения типов (juggling)

Это — **главная ловушка PHP**, и она не исчезла даже в 8.x. PHP проводит различие между **«числовыми строками»** и обычными строками, и это различие определяет всё.

### Правило «numeric string»

Строка считается числовой, если PHPStan мог бы её распарсить как число. Это определяет поведение в арифметике, сравнениях и приведении.

```php
$str = '42';
$str + 1;       // 43  (string '42' → int 42)

$str = '42abc';
$str + 1;       // 1   (не numeric string → 0 + 1)
```

**Ловушка №1 — сравнения:**

```php
'42abc' == 42;   // false — строка не numeric, сравнивается как string "42abc" == "42"
'42' == 42;      // true  — numeric string сравнивается как число
0 == 'abc';      // true  — 'abc' → 0 как non-numeric
'0' == 0;        // true
```

**Ловушка №2 — `strcmp` и ему подобные:**

```php
strcmp('abc', 'abc') === 0; // true, но...
strcmp('abc', 'abc') == 0;  // true
// А теперь баг:
strcmp('abc', 'abc') === 0 // да
// Но если вы ожидаете strict-сравнения, а получаете int,
// то 'abc' == 0 будет true в loose сравнении!
```

### Приведение типов в арифметике — самое коварное

```php
$a = '0.1s';
$b = $a + 1;
// $b = 1.0 (не 1.1!) — '0.1s' не numeric string, интерпретируется как 0
```

**Ловушка №3 — float-точность после приведения:**

```php
$n = '1.0';
var_dump($n + 0); // float(1) — но это float, не int!
// Если далее используется как int в каком-то контексте — возможны сюрпризы
```

## 3. «Дивные» ситуации, которые ловят на практике

### А. `==` vs `===` — вечная классика, но с нюансом 8.x

В PHP 8.x **is_numeric** стал строже:

```php
is_numeric('0x1A');    // true (hex в 8.0+)
is_numeric('  42');    // true (whitespace обрезается)
is_numeric('1_000');   // false
is_numeric('1e3');     // true
```

### Б. Сравнение массивов и объектов

```php
[] == 0;       // true — пустой массив «равен» нулю в loose!
[] === 0;      // false
$a = [];
$a == null;    // true — пустой массив равен null
```

**Ловушка:** `if ($collection)` где `$collection` — пустой массив, будет **false**, но `if ($collection == null)` — тоже может ввести в заблуждение.

### В. Ordinal vs Numeric arrays — путаница в key-type

```php
$arr = ['a', 'b'];
isset($arr[0]);   // true
$arr[0] = null;
isset($arr[0]);   // false — null не isset
// Но:
$arr = ['0' => null];
isset($arr[0]);   // false
```

### Г. `null`-коллапс и nullsafe

```php
strict_types = 1;

$obj->get()?->value;
// Если get() вернул null, то nullsafe остановит цепочку.
// Но если get() вернул non-null с null-внутри — это не остановка.
```

## 4. Где типизация спасает

### Пример 1: Валидация через type-декларации вместо if-ов

```php
class BankAccount
{
    public function __construct(
        private readonly int $balance, // negative-int? check via annotation
    ) {}

    public function deposit(int $amount): void
    {
        // strict_types: нельзя передать float '10.5' как int
        $this->balance += $amount;
    }
}

$acc->deposit('100');  // strict_types → TypeError
// Good:
$acc->deposit(100);
```

```php
enum PaymentStatus: string
{

}
```

```php
function requireLogin(?User $user): never

```

## 5. Где типизация «дивит»

### Дивность 1: `array_sum` на assoc-массиве

```php
$arr = ['a' => 1, 'b' => 2];
array_sum($arr); // 3 — ключи игнорируются!
// Но:
array_sum(['a', 'b']); // Warning: expects parameter 1 to be number, string given
// Массив со string-key — ok, со string-values — ошибка
```

### Дивность 2: `in_array` strict-флаг

```php
in_array('5', ['1', '2', '5']); // true
in_array(5, ['1', '2', '5']);   // false! (5 !== '5')
in_array(5, ['1', '2', '5'], true); // false (strict, 5 !== '5')
in_array(5, ['1', '2', '5'], false); // true (loose, 5 == '5')
// Многие забывают, что без strict-флага PHP проводит numeric-string comparison
```

### Дивность 3: `match` vs `switch` и exhaustiveness

```php
$status = /* ... */;
$result = match ($status) {
    PaymentStatus::PAID => 'paid',
    // Если PaymentStatus добавит новый case, match НЕ скомпилируется
    // в режиме strict, но в runtime просто вернёт null
};
```

### Дивность 4: `strict_types` не защищает от `array`/`object`

```php
function process(array $data): void {}
process('not array'); // TypeError!
process([...]); // OK

// Но:
function process($data): void {} // без type-declaration
process('anything'); // OK — никакой защиты
```

## 6. Практические рекомендации (как я это решаю)

1. **Включайте `strict_types = 1` в каждом файле осознанно**, понимая, что он влияет на подстановку аргументов.
2. **Всегда используйте `===` для сравнения**, особенно с внешними данными (GET, POST, БД).
3. **Для числовых данных требуйте явного приведения** через `intval()`, `floatval()`, или type-declaration.
4. **Для state-машин используйте enum**, чтобы «невозможные состояния» были невозможны в типе.
5. **Покрывайте критичный код PHPStan с высоким уровнем строгости** — именно он ловит то, что runtime не видит.
6. **Для numeric-string извне (из БД, API) валидируйте явно**, не полагайтесь на «магию» PHP.

Система типов PHP — это **три раздельные подсистемы** (статическая для анализатора, рантаймная для движка, динамическая для логики), которые не синхронизированы, и непонимание этого — главная причина багов. `strict_types` влияет **только** на подставку аргументов в вызовах функций, а не на return-значения или присваивания. Типизация спасает там, где делает невозможными корректными «плохие» состояния (enum-ы, type-declarations), но «дивит» в loose-сравнениях и приведении типов.

## Анализ вопроса

Хороший вопрос, но в нём есть скрытая предпосылка, которую я хочу сразу обозначить: многие думают, что «иераргия исключений» — это про красоту кода. На деле это **протокол обмена информацией между слоями**, и проектирование исключений — это проектирование контрактов ошибок, а не классовой иerarхии ради иерархии. Поэтому я отвечу через призму: *что вызывающий код может гарантировать, получив исключение?*

Также оговорюсь: единого «правильного» подхода нет — зависит от того, есть ли у вас слои (application/domain/infrastructure) и где вы хотите перехватывать ошибки. Я покажу свой подход с оговорками.

---

## 1. Фундаментальный принцип: исключение = сообщение о нарушении контракта

**Контракт метода** — это всё, что вызывающий код вправе ожидать:

- Входные требования (preconditions): «принимаю non-null Money, положительную сумму».
- Результаты (guarantees): «вернёт валидный Order или…».
- **Побочные эффекты при нарушении**: «бросит `InvalidMoneyException` с конкретным типом, который я могу отловить».

Исключение — это **часть контракта**, а не «неожиданное событие». Если метод может отклонить ввод, он *обязан* сообщить об этом через исключение определённого типа, чтобы вызывающий мог на него отреагировать.

```php
final class Money
{
    public function __construct(
        private readonly int $amount,
        private readonly string $currency,
    ) {
        if ($amount <= 0) {
            // Это НЕ баг, это ожидаемое нарушение контракта.
            // Вызывающий код знает: может получить NegativeAmountException
            throw new NegativeAmountException($amount);
        }
    }
}
```

## 2. Своя иеархия: разделяю по «месту возникновения» и «управляемости»

Главное разделение, которое я провожу — между **ожидаемыми нарушениями контракта** (business rules) и **непредвиденными ошибками** (infrastructure failures). Это критично, потому что реагируют на них по-разному: первое — логируется как часть нормального flow, второе — как сбой.

```php
namespace App\Exception\Domain;

/**
 * Базовый класс для доменных исключений — нарушений бизнес-правил.
 * Эти исключения предсказуемы и могут быть обработаны в application-слое.
 */
class DomainException extends \RuntimeException {}

namespace App\Exception\Application;

/**
 * Нарушение бизнес-логики приложения (например, «недостаточно средств»).
 * Это ожидаемо — flow прерывается по бизнес-причине.
 */
class BusinessException extends \RuntimeException {}
```

**Практический паттерн:** создаю иеархию по слоям, а не по «типу ошибки»:

```
App\Exception
├── Domain          // Нарушения инвариантов доменных сущностей
│   ├── Money.php (NegativeAmountException)
│   ├── Order.php   (OrderCannotBeCancelledException)
│   └── ...
├── Application     // Нарушения бизнес-правил на уровне сервисов
│   └── BusinessException
└── Infrastructure  // Ошибки внешних систем (БД, HTTP, очередь)
    ├── DatabaseException
    └── ExternalServiceException
```

## 3. Оборачивание (wrapping) чужих исключений — и где тут ловушки

**Зачем Оборачивать.** Когда вы переходите из слоя, который бросает «низкоуровневые» исключения (Doctrine, PDO, HTTP-клиенты), в слой выше, вы **теряете контекст**. Оборачивание сохраняет и исходную причину (cause), и ваш доменный контекст.

```php
class OrderRepository implements OrderRepositoryInterface
{
    public function save(Order $order): void
    {
        try {
            $this->entityManager->persist($order);
            $this->entityManager->flush();
        } catch (\Doctrine\ORM\ORMException $e) {
            // Оборачиваем: теряем детали Doctrine, но добавляем контекст
            throw new OrderPersistenceException(
                'Не удалось сохранить заказ в базе данных',
                previous: $e  // <-- chain preserved
            );
        }
    }
}
```

**Ключевое правило оборачивания:**

1. **Всегда сохраняйте `previous`** (chain) — без этого теряется причина.
2. **Переводите язык ошибки на язык целевого слоя**: Doctrine говорит о `SQL`, домен говорит о «заказе».
3. **Не оборачивайте «всенепременно»** — если чужое исключение уже имеет понятный для вызывающего тип, оборачивание добавляет только шум.

**Ловушка №1 — потеря типа через «общее» оборачивание:**

```php
// ПЛОХО: ловим всё в один мешок
catch (\Throwable $e) {
    throw new \RuntimeException('Ошибка', previous: $e);
    // Callsite не понимает, что произошло — доменная логика или БД?
}
```

**Ловушка №2 — «exception to exception» без добавления ценности:**

```php
// ПХО: просто перебрасываем то же самое исключение
catch (SpecificException $e) {
    throw new SpecificException($e->getMessage(), previous: $e);
    // Зачем? Вызывающий и так получил SpecificException.
}
```

**Ловушка №3 — перехватываете слишком поздно:** оборачивание в `flush()` потеряло контекст *конкретного* заказа, хотя он был бы полезен.

## 4. Что считается контрактом метода — разбор

**Входит в контракт (вызыва预期ет):**

- Типы параметров и возвращаемых значений.
- **Конкретные типы исключений**, которые метод бросает при нарушении precondition.
- Состояние системы после вызова: «если exception — состояние не изменилось» (transactional integrity).

**Не входит в контракт:**

- Детали реализации (какой SQL сгенерирован).
- Сообщение об ошибке (оно — implementation detail, не должно парситься).
- Внутренняя иеархия исключений нижних слоёв.

```php
class PaymentService
{
    /**
     * @throws InsufficientFundsException  — ожидаемо, business rule
     * @throws PaymentGatewayException     — external failure
     *
     * @throws \InvalidArgumentException   — precondition violation
     */
    public function charge(Money $amount, Order $order): PaymentResult
    {
        // ...
    }
}
```

Здесь контракт чёткий: вызывающий может отловить `InsufficientFundsException` и ответить пользователю «недостаточно средств», но `PaymentGatewayException` — это внешний сбой, который логируется.

## 5. Антипаттерны (то, что я вижу на практике и сам тут ошибался)

### Антипаттерн 1: «catch-all» в одном месте

```php
try {
    // ...
} catch (\Throwable $e) {
    logger()->error($e);
}
// Проблема: весь business-flow «проваливается» в generic handler,
// теряется возможность разной реакции.
```

**Решение:** перехватывайте там, где можно принять решение. Доменные исключения — в application-слое, инфраструктурные — в boundary.

### Антипаттерн 2: использование исключений для управления обычным flow

```php
// ПЛОХО: проверка через try/catch вместо return-type
try {
    $user = $this->userRepository->findByEmail($email);
} catch (UserNotFoundException $e) {
    // Используем исключение как механизм return-value
}
```

**Решение:** если «не найдено» — это нормальное состояние, используйте `null`, `Optional`-аналог или Result-тип. Исключение — только для *аномалий*.

### Антипаттерн 3: исключение как способ «выбора ветки»

```php
// ПЛОХО
if (!$isValid) {
    throw new Exception(); // вместо того, чтобы сделать что-то другое
}
```

### Антипаттерн 4: слишком плоская или слишком глубокая иеархия

- **Слишком плоская** (все `RuntimeException`) — нельзя отловить конкретно.
- **Слишком глубокая** (по классу на каждую ошибку) — спам классами, сложность поддержки.

**Компромисс:** одна иеархия по слоям + конкретные subclass'ы только там, где они реально нужны для обработки.

### Антипаттерн 5: логирование в доменном слое

```php
// ПЛОХО: доменная сущность лотирует свою ошибку
class BankAccount {
    public function withdraw(Money $amount): void {
        if ($amount > $this->balance) {
            logger()->warning('Недостаточно средств'); // НЕЗДЕСЬ!
            throw new InsufficientFundsException(...);
        }
    }
}
```

**Решение:** доменный слой должен быть «чистым» — только бросать исключения, логированием занимается application/infrastructure.

### Антипаттерн 6: потеря previous в wrap

```php
// ПХО
catch (\Exception $e) {
    throw new DomainException('Ошибка'); // no previous!
}
```

```php

 * Базовый интерфейс для «обрабатываемых» исключений —
 * тех, на которые application-слой может отреагировать.

interface UserFacingExceptionInterface {}

// Доменные исключения
namespace App\Exception\Domain;

class InsufficientFundsException extends \RuntimeException
    implements UserFacingExceptionInterface
{
    public static function fromAmount(int $amount, int $balance): self

}
```

**Application-слой** перехватывает `UserFacingExceptionInterface` и преобразует в HTTP-ответ/сообщение. **Infrastructure** перехватывает всё остальное и лотирует.

Проектирование исключений — это **проектирование контрактов ошибок**, а не классов. Главные антипаттерны — catch-all, использование исключений для обычного flow, логирование в домене и потеря `previous`.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

## Анализ вопроса

Сразу оговорюсь о терминологической точности, потому что вопрос содержит скрытую неточность. **SOLID — это не единый своп правил, а пять отдельных принципов**, и у каждого своя «зона риска». Если бы мне пришлось назвать один, который нарушается чаще всего в реальном PHP-коде (особенно в Symfony-проектах), я бы сказал — **Principle of Single Responsibility (SRP)**, но с важной оговоркой: речь не столько о «класс делает слишком много», сколько о том, что **ответственность за ошибки и побочные эффекты «размывается» между слоями**.

Но прежде чем дать однозначный ответ, хочу проверить предпосылку: действительно ли SRP нарушается чаще всего? Давайте рассудим так:

- **O (Open/Closed)** — нарушается, но реже, потому что разработчики интуитивно понимают ценность расширяемости.
- **L (Liskov)** — нарушается в複杂ных иеархиях наследования, но в современном PHP с его emphasis на composition over inheritance — реже.
- **I (Interface Segregation)** — нарушается, особенно в Doctrine-репозиториях, но это более нишевая проблема.
- **D (Dependency Inversion)** — нарушается постоянно, но часто через призму SRP.

На практике **SRP и D идут рука об руку**: когда класс нарушает SRP, он обычно и инкапсулирует зависимости, которые следовало бы инвертировать. Поэтому я выберу SRP, но покажу, как он связан с D.

---

## Типовой пример нарушения SRP

Вот классическая ситуация — **контроллер, который делает всё сразу**. В Symfony это частый гость.

```php
namespace App\Controller;

use App\Repository\OrderRepository;
use App\Service\EmailService;
use App\Service\PaymentService;
use App\Service\ShippingService;
use Symfony\Bundle\FrameworkBundle\Controller\AbstractController;
use Symfony\Component\HttpFoundation\JsonResponse;
use Symfony\Component\HttpFoundation\Request;

class OrderController extends AbstractController
{
    public function __construct(
        private OrderRepository $orderRepository,
        private EmailService $emailService,
        private PaymentService $paymentService,
        private ShippingService $shippingService,
    ) {}

    #[Route('/order/{id}/confirm', methods=['POST'])]
    public function confirmOrder(int $id, Request $request): JsonResponse
    {
        $order = $this->orderRepository->find($id);
        if (!$order) {
            return $this->json(['error' => 'Order not found'], 404);
        }

        // 1. Валидация тела запроса
        $data = json_decode($request->getContent(), true);
        if (!isset($data['paymentMethod'])) {
            return $this->json(['error' => 'Invalid payment method'], 400);
        }

        // 2. Расчет стоимости доставки
        $shippingCost = $this->shippingService->calculate($order);

        // 3. Взятие оплаты
        $paymentResult = $this->paymentService->charge(
            $order->getAmount(),
            $data['paymentMethod']
        );
        if (!$paymentResult->isSuccess()) {
            return $this->json(['error' => 'Payment failed'], 402);
        }

        // 4. Обновление статуса заказа
        $order->markAsPaid($paymentResult->transactionId());
        $this->orderRepository->save($order);

        // 5. Отправление email
        $this->emailService->sendConfirmation($order);

        // 6. Запуск доставки
        $this->shippingService->schedule($order);

        return $this->json(['status' => 'confirmed', 'order' => $order]);
    }
}
```

### Что здесь нарушено (и почему это проблема)

**Нарушение SRP:** этот класс отвечает за:
- Валидацию входных данных.
- Расчет логистики.
- Интеграцию с платежной системой.
- Управление состоянием заказа.
- Коммуникацию с почтовым сервисом.
- Формирование HTTP-ответа.

**Почему это плохо на практике:**

1. **Тестируемость:** чтобы протестировать «логтику оплаты», нужно мокать всё вокруг.
2. **Переиспользование:** логику подтверждения заказа нельзя вызвать из CLI-команды или другого контроллера.
3. **Изменяемость:** любое изменение в логике оплаты требует правки контроллера, который «не должен» об этом знать.
4. **Читаемость:** 40 строк кода, где каждая отвечает за разное.

## Рефакторинг: разделение ответственности

Ключевая идея — **вынести бизнес-логику из контроллера в доменный/application-слой**, оставив контроллеру только оркестрацию вход/выход.

### Шаг 1: Application-сервис как единственная точка ответственности

```php
namespace App\Application\Service;

use App\Domain\Order\Order;
use App\Domain\Order\OrderCannotBeConfirmedException;
use App\Domain\Order\OrderRepository;
use App\Domain\Payment\PaymentService;
use App\Domain\Shipping\ShippingService;
use App\Infrastructure\Notification\EmailNotifier;

/**
 * Единая ответственность: «подтвердить заказ».
 * Этот класс знает про flow, но не про HTTP.
 */
final class OrderConfirmationService
{
    public function __construct(
        private OrderRepository $orderRepository,
        private PaymentService $paymentService,
        private ShippingService $shippingService,
        private EmailNotifier $emailNotifier,
    ) {}

    public function confirm(int $orderId, string $paymentMethod): OrderConfirmedResult
    {
        $order = $this->orderRepository->find($orderId);
        // Домeнный exception вместо return — контракт:
        // «OrderNotFoundException», если заказа нет
        $this->ensureOrderExists($order);

        // Валидация paymentMethod — часть invariant'ов Order
        $this->validatePaymentMethod($order, $paymentMethod);

        // Интеграция с внешними системами через port interface
        $paymentResult = $this->paymentService->charge(
            $order->getAmount(),
            $paymentMethod
        );
        if (!$paymentResult->isSuccess()) {
            return OrderConfirmedResult::failed(
                PaymentFailedException::forMethod($paymentMethod)
            );
        }

        // Все side effects через доменные события/порталы
        $order->markAsPaid($paymentResult->transactionId());
        $this->orderRepository->save($order);

        // События (не прямые вызовы) — decoupling
        $this->emailNotifier->notify(
            new OrderConfirmationEvent($order)
        );
        $this->shippingService->schedule($order);

        return OrderConfirmedResult::success($order);
    }

    private function ensureOrderExists(?Order $order): void
    {
        if ($order === null) {
            throw new OrderNotFoundException();
        }
    }
}
```

### Шаг 2: Контроллер — только оркестрация

```php
namespace App\Controller;

use App\Application\Service\OrderConfirmationService;
use App\Application\Service\OrderConfirmedResult;
use App\Exception\OrderNotFoundException;
use App\Exception\Payment\PaymentFailedException;
use Symfony\Component\HttpFoundation\JsonResponse;

class OrderController
{
    public function __construct(
        private OrderConfirmationService $confirmationService
    ) {}

    public function confirm(int $id, string $paymentMethod): JsonResponse
    {
        try {
            $result = $this->confirmationService->confirm($id, $paymentMethod);
            return $this->json([
                'status' => 'confirmed',
                'order' => $result->order(),
            ], 200);
        } catch (OrderNotFoundException $e) {
            return $this->json(['error' => 'Order not found'], 404);
        } catch (PaymentFailedException $e) {
            return $this->json(['error' => 'Payment failed'], 402);
        }
    }
}
```

### Что изменилось

| До | После |
|----|-------|
| Контроллер делает 6 разных вещей | Контроллер только мапит exception → HTTP-код |
| Логика «приклеена» к HTTP | Логика в `OrderConfirmationService`, тестируема и переис可упоузаем |
| `return JsonResponse` при каждой ошибке | Exception-driven flow |
| Зависимости инкапсулированы | Зависимости инвертированы через constructor |

---

## Почему SRP нарушается чаще всего (анализ причин)

1. **«Быстро написать» vs «поддерживать».** Контроллер-«бог» пишется за 5 минут, но убивает тестируемость.

2. **Symfony-фреймворк «позволяет».** AbstractController соблазняет держать логику рядом с route.

3. **Непонимание, что SRP — про «причину изменений».** Класс нарушает SRP не потому, что «много кода», а потому что **у него больше одной причины для изменения**. Ваш контроллер изменится, если: поменяется валидация, оплата, логистика или формат ответа. Это 5 разных причин.

4. **Смешение уровней абстракции.** Контроллер смешивает HTTP-детаали (Request) с бизнес-логикой (Payment).

---

## Связь с D (Dependency Inversion)

SRP почти всегда влечет нарушение D: если класс делает много, он инкапсулирует много зависимостей, которые нельзя инвертировать. В рефакторинге выше:

- **High-level modules** (`OrderConfirmationService`) больше не зависят от **low-level modules** (`PaymentService`, `ShippingService`) напрямую — через port interfaces.
- Абстракции не зависят от деталей — детали зависят от абстракций.

---

## Антипаттерны, связанные с SRP (на что обращать внимание)

1. **ORM-сущности, которые логируют/выполняют бизнес-логику** — нарушают SRP (сущность должна только репрезентировать состояние).
2. **Repositories, которые делают валидацию** — репозиторь должен только доступ к данным.
3. **Factories, которые валидируют и сохраняют** — фабрике нужен только `create()`.
4. **Services, которые миксуют чтение и запись** — лучше разделять read/write модели.

---

## Итог

**Чаще всего нарушается SRP**, и причина в том, что его часто понимают неправильно («слишком много методов» вместо «слишком много причин для изменения»). Типовой пример — контроллер-«бог», который миксует валидацию, интеграцию с внешними системами, управление состоянием и HTTP. Рефакторинг — вынос логики в application-сервис с exception-driven flow, а контроллер оставляет только маппинг исключений на HTTP-коды. SRP тесно связан с D: разделение ответственности неизбежно ведет к инверсии зависимостей.

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

## Анализ вопроса

Хороший вопрос, но я хочу сразу обратить внимание на формулировку: он предполагает, что есть «нарушение принципа», которое можно «оправдать». Это не совсем корректно. Более точная формулировка: **принципы SOLID — это рекомендации для управления сложностью, а не законы физики**. Их можно *игнорировать*, но не «нарушать» в смысле «получить правильный результат через нарушение». 

Если я «нарушил» принцип, но код стал хуже — я просто совершил ошибку. Если я сознательно выбрал другой путь — это не нарушение, а **осознанный выбор дизайна**. Поэтому я отвечу так: **принципы можно игнорировать, когда их применение усложняет код больше, чем сама решаемая проблема**, но это должно быть осознанное решение, а не лень.

---

## Пример 1: Интуитивная читаемость важнее строгого следования SRP

**Ситуация:** есть простой DTO, где все поля логически связаны.

```php
// Следование SRP в чистом виде — разбить на классы
class Point {
    public function __construct(
        public float $x,
        public float $y
    ) {}
}

class Rectangle {
    public function __construct(
        public Point $topLeft,
        public Point $bottomRight
    ) {}
}
```

**Здесь SRP «нарушается» в том смысле, что класс содержит несколько свойств**, но это **не нарушение**, а осознанный выбор. Разбивать `Rectangle` на подклассы для каждого свойства — абсурд. SRP говорит «единая причина для изменения» — а у `Rectangle` и так единственная причина (изменится, если изменится геометрия). **Следование принципам здесь усложнило бы код без пользы.**

---

## Пример 2: Composition over Inheritance и «маленькие» классы

**Ситуация:** Doctrine-сущности часто нарушают SRP в том смысле, что **содержат и данные, и поведение**.

```php
class Order {
    public function __construct(
        private Money $total,
        private OrderStatus $status,
    ) {}

    public function isPaid(): bool {
        return $this->status === OrderStatus::PAID;
    }
}
```

**Традиционный SRP** сказал бы: вынеси `isPaid()` в отдельный класс-обработчик. Но это **нарушило бы принцип «анемичной модели данных»** и сделало бы код хуже. Здесь **поведение привязано к данным по смыслу**, и разделение было бы искусственным. **Следование SRP здесь усложнило бы доменную модель.**

---

## Пример 3: LSP и «устойчивость к изменениям»

**Ситуация:** иногда намеренное нарушение LSP (что подкласс может нарушать контракт родителя) *оправдано* для оптимизации.

```php
// Теоретически LSP требует, чтобы Substitution работал всегда
interface Repository {
    public function find(int $id): ?object;
}

class FastRepository implements Repository {
    public function find(int $id): ?object {
        // Кэш в памяти — faster, но stateful
        return $this->cache->get($id) ?? $this->db->find($id);
    }
}
```

**Здесь `FastRepository` нарушает «контракт» в том смысле, что** добавляет statefulness. Но это **оправдано**, если:
- Кэш — часть публичного контракта (документировано).
- Performance критичен, а чистота LSP — нет.

**Это не нарушение, а осознанный trade-off** между принципом и производительностью.

---

## Пример 4: «YAGNI» vs «готовность к расширению» (OCP)

**Ситуация:** часто **не стоит** сразу делать код расширяемым (OCP), если расширение реально не нужно.

```php
// OCP требует абстракции под каждое поведение
interface PaymentStrategy {
    public function charge(Money $amount): PaymentResult;
}

// Но если есть только один способ оплаты сейчас:
class SimplePayment {
    public function charge(Money $amount): PaymentResult {
        // Прямая реализация — проще, чем абстракция
        return $this->gateway->charge($amount);
    }
}
```

**Следование OCP здесь преждевременно** (YAGNI — «you aren't gonna need it»). **Внедрение абстракции усложнило бы код без пользы.**

---

## Когда игнорирование принципов оправдано — резюме

1. **Когда следование усложняет код больше, чем сама проблема** (маленькие классы, DTO).
2. **Когда принцип конфликтует с читаемостью или естественностью модели** (доменные сущности).
3. **Когда есть осознанный trade-off** (производительность, YAGNI).
4. **Когда принцип применяется догматично** вместо решения реальной проблемы.

---

## Важная оговорка: что НЕ следует считать «оправданным нарушением»

- **Лень** («не хочу делать интерфейс, сделаю abstract class»).
- **Непонимание принципа** («ну это же работает»).
- **Отсутствие тестов как оправдание** (нарушение принципа не делает код неправильным, но и не оправдывает отсутствие тестов).

---

## Итог

**Принципы SOLID нельзя «нарушать», их можно игнорировать осознанно**, когда их применение усложняет код больше, чем сама решаемая проблема. Реальные примеры: доменные сущности со встроенным поведением (нарушение «чистого» SRP), YAGNI вместо преждевременного OCP, оптимизации, нарушающие LSP. Но это должно быть **осознанное решение с пониманием следствий**, а не лень или непонимание. Истинный профессионализм — не в слепом следовании, и не в слепом нарушении, а в понимании, **когда принцип служит, а когда мешает**.

Хороший, точный вопрос. Но я хочу сразу уточнить контекст, потому что в нём есть скрытая предпосылка: **OCP (Open/Closed Principle) сам по себе не требует конкретной реализации** — он требует лишь того, чтобы сущности были «открыты для расширения, но закрыты для изменения». ## Способ 1: Композиция и внедрение зависимостей

**Суть.** Вместо наследования вы встраиваете поведение через интерфейсы/трейты, которые можно менять runtime.

```php
// До: наследование
class EmailNotifier extends Notifier {}

// После: composition
interface Notifier {
    public function notify(string $message): void;
}

class EmailNotifier implements Notifier {}
class SlackNotifier implements Notifier {}

class NotificationService {
    public function __construct(private Notifier $notifier) {}
    
    // Расширение без изменения: подставьте другой Notifier
}
```

**Почему это лучше наследования для OCP:** вы не меняете класс, а **заменяете зависимость**. Новые типы поведения — через новые классы, не трогая существующие.

## Способ 2: Стратегии (Strategy Pattern)

**Суть.** Разное поведение — через стратегии, выбираемые runtime.

```php
interface DiscountStrategy {
    public function calculate(Money $amount): Money;
}

class SeasonalDiscount implements DiscountStrategy {}
class BulkDiscount implements DiscountStrategy {}

class PricingService {
    public function __construct(private DiscountStrategy $strategy) {}
    
    // Расширение: новый тип скидки = новый класс стратегии
}
```

## Способ 3: Хуки и callback'и

**Суть.** Класс определяет точки расширения через внедрённые callback'и.

```php
class OrderProcessor {
    /**
     * @param callable(Order $order): void[] $hooks
     */
    public function __construct(
        private array $hooks = []
    ) {}
    
    public function process(Order $order): void {
        foreach ($this->hooks as $hook) {
            $hook($order);
        }
    }
}

// Расширение: подставьте свой hook
$processor = new OrderProcessor([
    fn(Order $o) => $log->info('processed'),
    fn(Order $o) => $metrics->track('order'),
]);
```

## Способ 4: Decorator (декорирование)

**Суть.** Расширение через оборачивание в декораторы.

```php
interface Logger {

class FileLogger implements Logger {}

    }
```

```php
        $rate = $this->taxRules[$category] ?? 0.19;

    // Расширение: новый category = изменение данных, не кода
}
```

| Способ | Когда использовать | Плюсы перед наследованием |
|--------|-------------------|---------------------------|
| Composition | Зависимости меняются runtime | Тестируемость, replacement без изменения |

## Важная оговорка про наследование

**Наследование не «плохо»**, но у него есть ограничения для OCP:
- Оно «жёстко» связывает child с parent.
- Изменение parent влияет на children (нарушение Closed).
- Сложнее тестировать.

**Композиция предпочтительнее**, когда нужно расширение **поведения**, а не типа.

Наследование — лишь один (и часто не лучший) способ, потому что оно «жёстко» связывает классы. В современном PHP-коде чаще доминирует композиция, потому что она даёт гибкость замещения без изменения существующего кода, что и есть суть OCP.

## Анализ вопроса

Хороший вопрос, но в нём есть **скрытая и важная неточность**, которую я хочу сразу обозначить. Многие путают SRP с чем-то, что «применяется к классам». Это неверно. **Single Responsibility Principle относится к единице ответственности, а не к классу**. Класс — это часто удобная единица, но ответственность может быть у:

- **Функции/метода**
- **Модуля/пакета**
- **Сервиса/компонента**
- **Файла конфигурации**
- **Даже строки кода внутри функции**

Формулировка Гербера/Соммервиля: «класс должен иметь причину для изменения». Но **причина для изменения** — это про ответственность, и она применима к любой границе, где можно «изменить что-то одно».

---

## SRP применяется к разным уровням абстракции

### 1. Функция/метод

**Пример нарушения:** метод делает сразу несколько разных вещей.

```php
// Нарушение: метод валидирует, сохраняет и логирует
public function saveUser(string $email): void {
    if (!$this->validateEmail($email)) { // валидация
        throw new Exception();
    }
    $this->userRepository->save($email); // сохранение
    $this->logger->info('User saved');  // логирование
    $this->emailService->sendWelcome(); // уведомление
}
```

**Рефакторинг** — разделение на методы по ответственности:

```php
public function registerUser(string $email): void {
    $user = $this->createUser($email); // ответственность: создание
    $this->userRepository->save($user); // ответственность: сохранение
    $this->notifyWelcome($user);        // ответственность: уведомление
}
```

### 2. Класс

Это то, о чём обычно думают. Класс должен иметь единственную причину для изменения.

```php
// Нарушение: контроллер + бизнес-логика + HTTP
class OrderController { /* ... делает всё ... */ }
```

### 3. Сервис/компонент

Причина для изменения — «поменялась логика оплаты» vs «поменялся способ логирования».

```php
// Нарушение: PaymentService инкапсулирует и платёжку, и логирование, и кэш
```

### 4. Модуль/пакет

В больших проектах ответственность — у модуля. Например, модуль «billing» не должен отвечать за «notifications».

### 5. Даже строка/фрагмент

Иногда одна строка смешивает ответственности (например, `$x = $a && $b || $c` — это и валидация, и логика, и присваивание).

---

## Почему это важно понимать

**Ключевая ошибка:** пытаться применить SRP только к классам и игнорировать ответственность внутри методов. Тогда:

- Методы-«боги» остаются незамеченными.
- Ответственность «размывается» на уровне логики, а не только структуры.

**Более глубокий смысл:** SRP — это про **границы изменения**, и эти границы могут быть где угодно. Если вы меняете что-то и вам нужно править «несколько разных вещей» в одном месте — это нарушение SRP на этом уровне.

---

## Практический тест «где у меня SRP»

**Вопрос для проверки:** «Если мне нужно изменить одну вещь, придется ли мне править несколько разных аспектов в этом элементе?»

- Метод: «Если меняю валидацию, мне нужно править логирование?» → значит, нарушение.
- Класс: «Если меняю бизнес-логику, мне нужно править HTTP-маппинг?» → значит, нарушение.

---

## Оговорка: SRP не про «один метод» или «одну переменную»

SRP **не означает**, что класс должен делать *одну операцию*. Это частая ошибка. Класс может иметь много методов, но **единственная причина для изменения** — например, `Point` может иметь `x`, `y`, `distance()`, `normalize()`, но все они про геометрию точки. Это **не нарушение SRP**.

**Тест:** все методы класса должны меняться вместе (одна ответственность).

---

## Итог

**SRP применяется не только к классам, но и к функциям, методам, сервисам, модулям и даже отдельным фрагментам кода.** Ключ — это **единственная причина для изменения**, а не конкретная единица. Класс — частый, но не единственный носитель ответственности. Нарушение SRP внутри метода (метод-«бог») — не менее распространённая и опасная проблема, чем нарушение в классе.

**Важное уточнение:** в Symfony есть **три разных «контейнера»**, и их легко перепутать:

2. **`ContainerBuilder`** — объект, который *компилирует* определение сервисов в `Container`.

## 1. Жизненный цикл контейнера

Контейнер проходит через несколько фаз:

```
1. Загрузка определений (configs)
   ↓
2. Компиляция (CompilerPass)
   ↓
3. Генерация PHP-кога (ContainerBuilder::compile())
   ↓
4. Инстанцирование (впервые запрашиваемый сервис)
```

---

## 2. Что происходит при компиляции (Compilation)

Это **самая важная часть**, которую часто недооценивают. В Symfony (особенно в Symfony 6+) **всё, что связано с определением сервисов, компилируется один раз** при генерации кэша.

### Фаза A: Загрузка определений

Сервисы определяются в:
- `config/services.yaml`
- attributes (`#[AsService]`, `#[Autoconfigure]`)
- compiler passes

```yaml
# config/services.yaml
services:
    App\Service\OrderService:
        arguments:
            $orderRepository: '@App\Repository\OrderRepository'
```

### Фаза B: Compiler Passes

**Compiler Pass** — это код, который выполняется во время компиляции и **изменяет определения сервисов**. Symfony запускает их в определённом порядке:

```
1. AddConcreteDefinitionsPass
2. AutowiringPass (autowiring)
3. ServiceSubContainerPass
4. RegisterPass
5. ... (много других)
```

**Пример кастомного compiler pass:**

```php
namespace App\Compiler;

use Symfony\Component\DependencyInjection\Compiler\CompilerPassInterface;
use Symfony\Component\DependencyInjection\Definition;
use Symfony\Component\DependencyInjection\ContainerBuilder;

final class RegisterOrderHandlersPass implements CompilerPassInterface
{
    public function process(ContainerBuilder $container): void
    {
        // Находим все определения с тегом 'order_handler'
        $taggedServices = $container->findTaggedServiceIds('order_handler');
        
        // Манипулируем определениями: инжектим их в order processor
        foreach ($taggedServices as $id => $tags) {
            $definition = $container->getDefinition($id);
            // ... добавляем в коллекцию handlers
        }
    }
}
```

**RegisterKernelComponentsPass**, `AnnotatePass`, `RegisterServiceLocatorsPass` — все они модифицируют контейнер до генерации кода.

### Фаза C: Генерация PHP-кога

Самое важное: **Symfony генерирует PHP-код**, репрезентирующий ваш контейнер.

```php
// var/cache/prod/AppProdEnvProjectContainerLegacy.php (упрощённо)
class AppProdEnvProjectContainer extends Container
{
    private $loaded = [];
    
    private function getAuthService(): \App\Service\OrderService
    {
        if (function_exists('apcu_fetch') && apcu_fetch('app.service.order')) {
            return include __DIR__.'/../services/'.$this->services['app.service.order'].'.php';
        }
        
        $instance = new \App\Service\OrderService(
            $this->containers['app']['App\\Repository\\OrderRepository'] ?? $this->load(getenv('APP_DEBUG') ? 'service_OrderRepository' : 'service_OrderRepository.php'),
            // ... другие зависимости
        );
        
        return $instance;
    }
}
```

**Это ключевой момент:** после компиляции ваш `services.yaml` **больше не читается из файла**. Вместо него генерируется **голый PHP-код**, который инстанцирует сервисы прямо в методах контейнера. Это **миллионы операций в секунду**, потому что нет reflection, нет парсинга YAML в runtime.

## 3. Как работает Autowiring

**Autowiring** — это механика, при которой Symfony **автоматически определяет зависимости** по типам параметров конструктора.

### Механика

```php
class OrderService
{
    public function __construct(
        private OrderRepository $orderRepository,
        private PaymentGateway $paymentGateway,
    ) {}
}
```

Symfony смотрит на конструктор:
1. Виждет `$orderRepository` типизирован как `OrderRepository`.
2. Ищет определение с id `App\Repository\OrderRepository`.
3. Инжектит его автоматически.

**Автоматическая регистрация (`autoconfigure`):**

```php
namespace App\Service;

use Symfony\Component\DependencyInjection\Attribute\Autowire;
use Symfony\Component\DependencyInjection\Attribute\TaggedIterator;

class OrderService
{
    public function __construct(
        #[TaggedIterator('order_validator')] // автоматически собирает все сервисы с тегом
        private iterable $validators,
    ) {}
}
```

### Autowiring vs AutowireByType

В Symfony 6+ появилось разделение:
- **`#[Autowire]`** — конкретное определение.
- **`#[AutowireByType]`** — для collection-типов.

## 4. Что происходит при первом запросе сервиса

**Вот самый важный момент, который часто упускают:**

```
1. Request -> Kernel::handle()
   ↓
2. -> Container::get('App\Service\OrderService')
   ↓
3. -> Container::make()
   ↓
4. -> Container::loadClass(...) // Проверка, что сервис уже создан
   ↓
5. -> Container::instantiate()
   ↓
6. -> new \App\Service\OrderService($dep1, $dep2, ...)
   ↓
7. -> getInstance() // Singleton-ish кэш в $this->services
```

### Детально

**Первый запрос:**

```php
public function get(string $id): mixed
{
    $id = $this->normalizeId($id);
    
    // Проверка singleton
    if (str_starts_with($id, 'services.')) {
        // ...
    }
    
    $method = 'get' . str_replace('.', '_', $id) . 'Service';
    
    // Динамический вызов сгенерированного метода
    return $this->methods[$id] ?? ($this->methods[$id] = [$this, $method])()[0] ?? null;
}
```

**Ключевой инсайт:** `get('App\Service\OrderService')` вызывает метод `getAuthService()`, который **уже содержит скомпилированные зависимости**. Нет reflection, нет автоподбора — всё уже вычислено в compile-time.

**Повторный запрос:**

```php

```

**Кандидат:**

## Анализ вопроса

Хороший вопрос, но я хочу сразу сделать важную оговорку о терминах, потому что «циклические зависимости» часто путают с разными явлениями:

1. **Циклическая зависимость в DI-контейне** (Symfony ругается, не может инстанцировать).
2. **Логический цикл в доменной модели** (аггрегаты ссылаются друг на друга).
3. **Циклическая зависимость через события** (EventListener → EventDispatcher → Listener).

Также важно понимать: **циклическая зависимость — это не просто «плохой код», а сигнал о неправильной границе ответственности**. Если у вас есть цикл, то классы A и B *на самом деле* принадлежат одному слою/модулю, но разделены.

---

## Причина циклических зависимностей

**Корневая причина:** два сервиса зависят друг от друга прямо или через цепочку:

```
A → B → A
```

Или через цепочку:

```
A → B → C → A
```

Это часто происходит, когда:
- Логика «размазана» между двумя сервисами.
- Сервисы должны общаться, но общаются напрямую вместо через абстракцию.

---

## Способы разруливания

### 1. Интроспекция (Introspection) — признать, что сервисы один слой

**Суть.** Если A и B зависят друг от друга, значит они **одного уровня абстракции**. Нужно **объединить их в один сервис** или **вынести общую логику в третий сервис**.

```php
// До: циклическая зависимость
class OrderService {
    public function __construct(private PaymentService $payment) {}
    public function confirm() {
        $this->payment->charge();
    }
}

class PaymentService {
    public function __construct(private OrderService $orders) {}
    public function charge() {
        $this->orders->markPaid();
    }
}

// После: выносим общую логику в OrderConfirmationService
class OrderConfirmationService {
    public function __construct(
        private PaymentService $payment,
        private OrderRepository $orders
    ) {}
}
```

### 2. Интерфейс вместо конкретной зависимости

**Суть.** Один из сервисов зависит от **интерфейса**, а не от конкретного класса, что разрывает цикл.

```php
// До: конкретная зависимость
class OrderService {
    public function __construct(private PaymentGateway $gateway) {}
}

// После: абстракция
class OrderService {
    public function __construct(private PaymentGatewayInterface $gateway) {}
}

interface PaymentGatewayInterface {
    public function charge(Money $amount): PaymentResult;
}
```

**Почему это работает:** `OrderService` зависит от абстракции, а `PaymentGateway` implements её. Теперь `OrderService` не требует конкретную реализацию, и цикл разрушен.

### 3. События/издания-подписчики (Event/Subscriber)

**Суть.** Вместо прямого вызова — публикуйте событие, и другой сервис подписывается.

```php
// До: прямой вызов (циклический)
class OrderService {
    public function confirm() {
        $this->paymentService->charge();
        $this->emailService->send();
    }
}

class EmailService {
    public function send() {
        $this->orderService->markSent();
    }
}

// После: события
class OrderService {
    public function confirm() {
        $this->paymentService->charge();
        $this->eventDispatcher->dispatch(new OrderConfirmedEvent($order));
    }
}

class OrderConfirmedSubscriber implements EventSubscriberInterface {
    public function onOrderConfirmed(OrderConfirmedEvent $event): void {
        $this->emailService->sendConfirmation($event->order);
    }
    
    public static function getSubscribedEvents(): array {
        return [OrderConfirmedEvent::class => 'onOrderConfirmed'];
    }
}
```

**Почему это работает:** `OrderService` не зависит от `EmailService`, `EmailService` не зависит от `OrderService`. Оба зависят от EventDispatcher.

### 4. Lazy-загрузка (Lazy Service)

**Суть.** Symfony позволяет сделать сервис **ленивым**, чтобы цикл не ломал инстанцирование.

```yaml
services:
    App\Service\OrderService:
        lazy: true  // не инстанцируется до первого вызова
```

**Важно:** это **не разрушает цикл, а маскирует его**. Цикл всё ещё есть, но инстанцирование откладывается. **Не рекомендую как основное решение**, потому что это костыль.

### 5. Setter Injection вместо Constructor

**Суть.** Один из сервисов получает зависимость через сеттер, а не через конструктор.

```php
class OrderService {
    private PaymentService $paymentService;
    
    public function setPaymentService(PaymentService $payment): void {
        $this->paymentService = $payment;
    }
}
```

**Важно:** Symfony **не поддерживает setter injection для циклов напрямую**, но можно через `#[Autowire]` и lazy-прокси. **Это тоже костыль.**

### 6. Factory Pattern

**Суть.** Выносим создание одного из сервисов в factory, которое инстанцируется позже.

```php
class OrderFactory {
    public function createOrder(): Order {
        // Инстанцируем с зависимостями, но лениво
        return new Order($this->repository, $this->payment);
    }
}
```

### 7. Domain Event Sourcing / CQRS

**Суть.** Если цикл в доменной модели — используйте доменные события.

```php
// Аггрегат A вызывает, но через доменные события
class Order {
    public function confirm(): void {
        $this->recordEvent(new OrderConfirmedEvent($this));
    }
}
```

---

## Как распознать, что у вас именно цикл

**Тест «один слой»:** если вы можете нарисовать `A → B → A`, то A и B **должны быть одного модуля/сервиса**. Разделение — артефакт плохого дизайна.

---

## Что НЕ следует делать (антипаттерны)

1. **Просто делать lazy** — вы маскируете проблему, не решаете её.
2. **Использовать static-синглтоны** — это усугубляет тестируемость.
3. **Игнорировать цикл** — он не «решится сам».

---

## Практический workflow

```
1. Найдите цикл: A → B → A
2. Спросите: «Один ли это слой?»
   ↓
3. Если да → объедините в один сервис или вынесите общую логику
4. Если разные слои → введите интерфейс
5. Если логический цикл → доменные события
6. Как последнее средство → lazy (с пониманием, что это костыль)
```

---

## Итог

**Циклические зависимости — это сигнал о неправильной границе ответственности.** Основные способы разруливания: **объединение сервисов одного слоя, введение интерфейсов, доменные/диспетчеризованные события**. **Lazy-загрузка — последнее средство, маскирующее проблему.** Главная идея: если два сервиса ссылаются друг на друга, они одного уровня и должны быть объединены или связаны через абстракцию.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

## Анализ вопроса

Хороший, практичный вопрос, но я хочу сразу сделать важную оговорку о терминологии, потому что «роли» и «voters» — это не взаимоисключающие механизмы, а **разные уровни абстракции одного и того же** — процесса авторизации.

**Ключевое понимание:** Symfony Security работает так: после аутентификации у вас есть `Token` с `UserInterface` и списком `roles`. **Voters** — это *механизм*, которым Symfony (или вы) проверяет право. **Роли** — это *специальный случай* проверки: `ROLE_ADMIN` проверяется через встроенный `RoleVoter`.

Таким образом, **роли — это просто предопределённые флаги в токене**, а **voters — универсальный механизм проверки прав**.

---

## Архитектура Symfony Security

### Уровень 1: Аутентификация (Authentication)

```
Request → Firewall → Authenticator → Token → Security Context
```

**Процесс:**
1. incoming request достигает firewall.
2. Если token уже в security context — пропускаем.
3. Иначе — запуск authenticators (проверка credentials).
4. Успешная аутентификация → создание token → сохранение в token storage.

**Пример custom authenticator (Symfony 6+):**

```php
namespace App\Security;

use Symfony\Component\Security\Http\Authenticator\AbstractFormLoginAuthenticator;

class LoginAuthenticator extends AbstractFormLoginAuthenticator
{
    public function authenticate(Request $request): AuthInterface // ...
    {
        // Создаём UserToken
    }
}
```

### Уровень 2: Token Storage

```php
// security.token_storage — держит текущий token
$token = $this->tokenStorage->getToken();
$user = $token->getUser();
$roles = $token->getRoles();
```

### Уровень 3: Authorize (Access Decision)

```php
// access_control в yaml
access_control:
    - { path: /admin, roles: ROLE_ADMIN }
    - { path: /profile, roles: ROLE_USER }
```

## Роли (Roles)

**Суть.** Роли — это строковые флаги в токене: `ROLE_USER`, `ROLE_ADMIN`, `ROLE_EDITOR`.

### Как работает

```php
// В контроллере
#[Route('/admin')]
#[IsGranted('ROLE_ADMIN')] // Проверка через RoleVoter
public function admin(): JsonResponse
{
    return new JsonResponse(['ok' => true]);
}
```

### Преимущества ролей

1. **Простота.** `roles: ROLE_ADMIN` — минимальная конфигурация.
2. **Читаемость.** `access_control` явно показывает, что нужно.
3. **Быстрая настройка** для простых «да/нет» прав.

### Недостатки ролей

1. **Rollout-проблема (role explosion):** если нужно 50 типов пользователей, то 2^50 комбинаций ролей.
2. **Грубость.** `ROLE_ADMIN` — это «да/нет», нет тонких прав.
3. **Смешение уровней.** `ROLE_USER` смешивает «зарегистрирован» и «админ».

---

## Voters (Voters)

**Суть.** Voters — это **универсальный механизм проверки**, который получает:
- `TokenInterface` (содержит user + roles).
- Объект, доступ к которому проверяется (например, `Order`, `Article`).
- Атрибут проверки (`'view'`, `'edit'`, `'delete'`).

### Базовый пример

```php
namespace App\Voter;

use App\Entity\Order;
use App\Entity\User;
use Symfony\Component\Security\Core\AuthenticationInterface;
use Symfony\Component\Security\Core\Authorization\AuthorizationCheckerInterface;
use Symfony\Component\Security\Core\User\UserInterface;

class OrderVoter extends Voter
{
    public function supports(string $attribute, mixed $subject): bool
    {
        return substr($attribute, 0, 6) === 'ORDER_' && $subject instanceof Order;
    }

    protected function grant($attribute, $subject, TokenInterface $token): bool
    {
        $user = $token->getUser();
        if (!$user instanceof User) {
            return false;
        }
        
        switch ($attribute) {
            case 'ORDER_VIEW':
                return $user === $subject->getOwner() || $user->hasRole('ROLE_ADMIN');
            case 'ORDER_EDIT':
                return $user === $subject->getOwner() && $subject->isEditable();
            default:
                return false;
        }
    }
}
```

**Регистрация:**

```yaml
services:
    App\Voter\OrderVoter:
        tags: ['security.voter']
```

**Использование:**

```php
#[Route('/order/{id}')]
#[IsGranted('ORDER_VIEW', 'order')]
public function show(Order $order): JsonResponse
{
    return JsonResponse::create(['order' => $order]);
}
```

## Когда использовать роли, когда voters?

Это **ключевой вопрос** в моём ответе. Вот моя методика:

### Выбирай роли, когда:

1. **Простое «да/нет».** «Только админ может сюда».
2. **Группы пользователей не меняются часто.** `ROLE_ADMIN`, `ROLE_EDITOR`, `ROLE_USER`.
3. **Нужна быстрая настройка `access_control`.**
4. **Прав очень немного** (< 10 total).

**Пример:**

```yaml
access_control:
    - { path: /admin, roles: ROLE_ADMIN }
    - { path: /editor, roles: ROLE_EDITOR }
```

### Выбирай voters, когда:

1. **Права зависят от данных объекта** («пользователь может редактировать только свой заказ»).
2. **Нужна сложная логика** (проверка времени, статуса, владения).
3. **Много комбинаций прав** (избегаем role explosion).
4. **Права зависят от контекста** («редактировать статью можно только в рабочее время»).

**Пример:**

```php
#[IsGranted('ARTICLE_EDIT', $article)]
// OrderVoter проверит: $user === $article->getAuthor()
```

## Гибридный подход (наибее практичный)

**Правильная стратегия:** используйте **роли для coarse-grained** (группы пользователей), а **voters для fine-grained** (доступ к конкретным данным).

```php
// Грубо: только для пользователей
#[Route('/profile')]
#[IsGranted('ROLE_USER')]
public function profile() { /* ... */ }

// Тонко: только владелец может смотреть
#[Route('/order/{id}')]
#[IsGranted('ORDER_VIEW', $order)]
public function show(Order $order) { /* OrderVoter проверяет владельца */ }
```

## Advanced: Custom Voter для сложных сценариев

**Пример: доступ по времени**

```php
class TimeBasedVoter extends Voter
{
    protected function grant($attribute, $subject, TokenInterface $token): bool
    {
        $now = new \DateTime();
        $hour = $now->format('G');
        return $hour >= 8 && $hour <= 18; // только в рабочее время
    }
}
```

**Пример: доступ по роли + данным**

```php
class ArticleVoter extends Voter
{
    protected function grant($attribute, $subject, TokenInterface $token): bool
    {
        $user = $token->getUser();
        if ($user->hasRole('ROLE_ADMIN')) {
            return true; // админ может всё
        }
        
        return $user === $subject->getAuthor(); // иначе только свой
    }
}
```

## Ошибки и антипаттерны

1. **Использование ролей для всего.** → role explosion.
2. **Использование voters для простого «да/».** → over-engineering.
3. **Hardcode прав в контроллерах.** → выносите в voters.
4. **Забыть зарегистрировать voter.** → `security.voter` tag.
5. **Проверка `ROLE_ADMIN` через `in_array`.** → используйте `IsGranted`.

- **v6/v7:** custom authenticators, `AuthenticatorInterface`, улучшения.

**Следуйте принципу:** роли для групп, voters для данных. **Используйте роли** для `access_control` и простых «да/» прав. **Используйте voters** для доступа к конкретным данным (владение, статус, время). **Комбинируйте** для гибкости.

## Итог

**Роли и voters — это не конкуренты, а разные уровни одной системы.** Роли — это флаги в токене (простые «да/» права), voters — универсальный механизм проверки доступа к данным. **Выбирайте роли** для coarse-grained прав (группы пользователей), **voters** для fine-grained (доступ к конкретным объектам по владению/статусу/контексту). Лучший подход — гибридный: роли для групп, voters для данных.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

## Анализ вопроса

Хороший, практический вопрос, но я хочу сразу уточнить терминологию, потому что Doctrine и immutable-состояние — это **встроенный конфликт интересов**.

**Ключевое понимание:** Doctrine ORM полагает, что:
1. Сущности **mutable** (можно менять поля через сеттеры).
2. Сущности можно **инстанцировать пустыми** (`new Order()`).
3. Поля могут быть **null** до валидации.

Value Objects (VO) по определению:
1. **Immutable** (нельзя менять после создания).
2. **Всегда валидны** (invalid state невозможен).
3. **Равенство по значению** (не по identity).

**Вывод:** Doctrine не «не любит» immutable-VO, но и **не поддерживает их нативно**. Есть несколько способов обойти эти ограничения, и у каждого — свои trade-offs.

---

## Способ 1: Embedded (Doctrine Embeddables)

**Суть.** VO хранится как часть родительской сущности через `#[Embeddable]` и `#[Embedded]`.

### Реализация

```php
use Doctrine\ORM\Mapping as ORM;

#[ORM\Embeddable]
final class Money
{
    public function __construct(
        #[ORM\Column(type: 'decimal', precision: 10, scale: 2)]
        private string $amount,
        
        #[ORM\Column(type: 'string', length: 3)]
        private string $currency,
    ) {
        // Validation here — never invalid
        $this->assertValid();
    }
    
    private function assertValid(): void { ... }
}

class Order
{
    #[ORM\Embedded(class: Money::class, name: "amount_")]
    private Money $total;
}
```

### Плюсы

1. **VO — часть сущности**, нет separate table.
2. **Immutable** (VO never changes once set).
3. **Валидация в конструкторе** VO.

### Минусы

1. **Cannot be null** (embedded field).
2. **Cannot reference another entity** (VO can't have FK to table).
3. **Harder to reuse** across entities (must define columns).

### Подводные камни

1. **Embedded VOs cannot be used as FK targets.**
2. **Cannot be null** — no lazy loading.
3. **Cannot have lifecycle callbacks.**

---

## Способ 2: Custom DBAL Types (Array / JSON)

**Суть.** Маппим VO в **JSON-столбец** (PostgreSQL `jsonb`) или **array**.

### Реализация

```php
use Doctrine\DBAL\Types\Type;
use Doctrine\DBAL\Platforms\Platform;

class MoneyType extends Type
{
    public function getSQLDeclaration(array $column, Platform $platform): string
    {
        return $platform->getJSONColumnTypeSQL();
    }
    
    public function convertToPHPValue($value, Platform $platform): mixed
    {
        $data = json_decode($value, true);
        return new Money($data['amount'], $data['currency']);
    }
    
    public function convertToDatabaseValue($value, Platform $platform): mixed
    {
        return json_encode([
            'amount' => $value->amount->getValue(),
            'currency' => $value->currency->getValue(),
        ]);
    }
}

// Регистрация
Connection::registerType('money', MoneyType::class);
```

### Плюсы

1. **Full encapsulation** (VO immutable + valid).
2. **Reusable** across entities.
3. **No schema pollution.**

### Минусы

1. **Cannot query in SQL** (jsonb fields are hard to index for queries).
2. **No foreign key** (can't reference).
3. **Serialization overhead.**

### Подводные камни

1. **Queries need jsonb operators** (PostgreSQL specific).
2. **No type safety in queries.**
3. **Cannot use in JOINs.**

---

## Способ 3: Custom DBAL Type for Structured Column

**Суть.** Маппим VO в **одну колонку** с сериализацией.

### Реализация

```php
class EmailType extends Type
{
    public function getSQLDeclaration(array $column, Platform $platform): string
    {
        return 'string(255)';
    }
    
    public function convertToPHPValue($value, Platform $platform): mixed
    {
        return $value !== null ? new Email($value) : null;
    }
    
    public function convertToDatabaseValue($value, Platform $platform): mixed
    {
        return $value?->getValue();
    }
}
```

### Плюсы

1. **Immutable VO.**
2. **Simple single column.**
3. **Queryable** (string index).

### Минусы

1. **No separation** of fields.
2. **No FK.**
3. **Validation in convertToPHPValue?** (must re-validate on read).

### Подводные камни

1. **Must handle null** (can't make null VO).
2. **Re-validation on read** (performance).

---

## Способ 4: DTO + Entity mapping

**Суть.** В entity храните **primitive fields**, и маппите в VO через **repository/DTO**.

### Реализация

```php
class Order
{
    #[ORM\Column(type: 'decimal', precision: 10, scale: 2)]
    private string $totalAmount;
    
    #[ORM\Column(type: 'string', length: 3)]
    private string $totalCurrency;
    
    public function getTotal(): Money
    {
        return new Money($this->totalAmount, $this->totalCurrency);
    }
    
    public function setTotal(Money $money): void
    {
        $this->totalAmount = $money->amount->getValue();
        $this->totalCurrency = $money->currency->getValue();
    }
}
```

### Плюсы

1. **Immutable VO** exposed via getter.
2. **Queryable** fields.
3. **Separation** of concerns.

### Минусы

1. **Entity has mutable fields** (can be changed directly).
2. **Duplicated data** (fields + VO).
3. **Must manage mapping** manually.

### Подводные камни

1. **Entity fields mutable** (bypass VO).
2. **No encapsulation** in DB.
3. **Manual mapping** errors.

---

## Способ 5: Separate entity (VO as entity)

**Суть.** Сделайте VO **отдельной entity** (например, `MoneyEntity`).

### Реализация

```php
#[ORM\Entity]
class Money
{
    #[ORM\Id]
    #[ORM\Column(type: 'uuid')]
    private string $id;
    
    #[ORM\Column(type: 'decimal', precision: 10, scale: 2)]
    private string $amount;
    
    #[ORM\Column(type: 'string', length: 3)]
    private string $currency;
}

class Order
{
    #[ORM\OneToOne(cascade: ['persist', 'remove'])]
    private Money $total;
}
```

### Плюсы

1. **Full encapsulation.**
2. **Queryable** (separate table).
3. **Referable** (can FK).

### Минусы

1. **Separate table** (schema pollution).
2. **FK overhead.**
3. **Complex cascade.**

### Подводные камни

1. **Separate table** (not a real VO).
2. **Cannot be immutable** (entity mutable).
3. **Overkill** for simple VO.

|--------|-----------|-------|-----------|----------|------------|
| Embeddable | ✅ | ✅ | ⚠️ (limited) | ⚠️ | Средняя |
| JSON Type | ✅ | ✅ | ❌ | ✅ | Средняя |
| Single Column | ✅ | ✅ | ✅ | ✅ | Низкая |
| DTO + Entity | ⚠️ (fields mutable) | ✅ | ✅ | ✅ | Средняя |
| Separate Entity | ⚠️ (mutable) | ✅ | ✅ | ✅ | Высокая |

---

## Рекомендации

### Для Value Objects:

1. **Simple VO (Email, Money):** **Single Column Type** — просто, queryable.
2. **Complex VO:** **JSON Type** (PostgreSQL jsonb) — encapsulation.
3. **VO used in queries:** **Single Column** или **DTO + Entity**.
4. **VO as FK target:** **Separate Entity** (но это уже entity, не VO).

### Для недопущения mutable state:

1. **Always validate in constructor** (VO immutable).
2. **Never expose setters** for VO fields.
3. **Use getters returning VO** (not raw fields).

### Для валидности:

1. **Never store invalid state** (validate in VO constructor).
2. **Re-validate on read** (for column types).

---

## Подводные камни (общие)

1. **Doctrine expects mutable entities** — VO immutable conflicts.
2. **Cannot use VO in JOINs** (except separate entity).
3. **No lazy loading** for embedded VO.
4. **Re-validation on read** (performance cost).

---

## Итог

**Doctrine не поддерживает immutable VO нативно, но есть способы обойти это:** embeddables (VO в сущности), custom DBAL types (JSON/single column), DTO + entity mapping, или separate entity. **Рекомендую:** **single column type** для простых VO, **JSON** для сложных, **DTO + entity** для queryable-VO. **Главный trade-off:** инкапсуляция (immutable) vs queryability.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

## Анализ вопроса

Хороший, технически глубокий вопрос, но я хочу сразу сделать важные оговорки, потому что в нём есть **две частые путаницы**:

1. **Аггрегат ≠ сущность + коллекции.** Аггрегат — это **граница целостности**, а не просто «корневая сущность с полями».
2. **Doctrine и DDD по-разному понимают «сущность».** В Doctrine `@Entity` — это **любая persistent-сущность**, включая children. В DDD `Child Entity` — это сущность **без собственного identity**, но Doctrine об этом не заботится.

**Ключевое понимание:** Doctrine ORM работает с graph objects, а DDD-аггаты — с graph of aggregates. Их граничные модели различаются, и это создаёт **дизайн-проблемы** при маппинге.

---

## Пример: Магазин — Заказы — Позиции

```php
namespace App\Domain\Order;

#[Entity] // Aggregate root
class Order
{
    private array $items; // Collection of Item (child entities)
}

#[Entity] // Child entity (no separate identity)
class OrderItem
{
    public function __construct(
        private Product $product,
        private int $quantity,
    ) {}
}
```

---

## Маппинг коллекций в Doctrine

### Вариант A: OneToMany + cascade

```php
class Order
{
    #[ORM\OneToMany(mappedBy: 'order', targetEntity: OrderItem::class, cascade: ['persist', 'remove'], orphanRemoval: true)]
    private array $items;
}

class OrderItem
{
    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'items')]
    #[ORM\JoinColumn(nullable: false)]
    private Order $order;
}
```

**Trade-offs:**
- **+** Doctrine автоматически управляет collection.
- **+** `cascade: persist` — children save'ятся с parent.
- **+** `orphanRemoval` — удалённые children delete'ятся.

### Подводные камни:

1. **Collection type:** Doctrine `Collection` vs `array` vs `iterable`. **Используйте `Collection`**, не `array`.
2. **`cascade` vs `orphanRemoval`:** `cascade: remove` + `orphanRemoval` — для children.

---

## Граница агрегата в Doctrine

**Ключевая проблема:** Doctrine видит **graph of entities**, а DDD — **graph of aggregates**. Когда вы:

```php
$order->addItem($item); // DDD: изменение агрегата
$repository->save($order); // Doctrine: flush + children
```

**Вопрос:** должен ли `Item` иметь собственный `id`, быть отдельным aggregate?

**Ответ DDD:** `OrderItem` — это **child entity**, не отдельный aggregate. У него **нет identity вне агрегата**, но Doctrine всё равно даёт ему `id` (для FK-цели).

---

## Кто и когда вызывает flush?

Это **самая важная часть** и самая частая путаница. Есть **три подхода**:

### Подход 1: Unit of Work (Doctrine по умолчанию)

**Суть.** Doctrine автоматически flush'ит graph при `flush()` aggregate root.

```php
class OrderRepository
{
    public function save(Order $order): void
    {
        $this->entityManager->persist($order);
        $this->entityManager->flush();
    }
}
```

**Trade-offs:**
- **+** Doctrine управляет children автоматически.
- **+** Unit of Work — graph consistency.
- **-** `flush()` flush'ит **всё dirty**, не только агрегат.

### Подход 2: Explicit persistence (DDD)

**Суть.** Aggregate root управляет своим graph'ом, repository flush'ит.

```php
class OrderRepository
{
    public function save(Order $order): void
    {
        $this->entityManager->persist($order);
        $this->entityManager->flush();
    }
}
```

**Trade-offs:**
- **+** Explicit.
- **-** Same as Unit of Work.

### Подход 3: Command handlers (recommended)

**Суть.** Flush вызывает **command handler** (application layer), не repository.

```php
class ConfirmOrderCommandHandler
{
    public function handle(ConfirmOrderCommand $command): void
    {
        $order = $this->orderRepository->find($command->orderId);
        $order->confirm(); // business logic
        $this->orderRepository->save($order); // flush here
    }
}
```

**Trade-offs:**
- **+** Clear separation (command → persist).
- **+** Aggregate graph bounded at command boundary.

---

## Граница транзакции

**Важное понимание:** Doctrine `flush()` = **single DB transaction** (если не в уже active transaction).

### Уровень 1: Repository flush

```php
$order = $this->orderRepository->find($id); // read
$order->confirm();                            // business logic
$this->orderRepository->save($order);         // write (flush)
```

**Транзакция:** `find` + `confirm` + `save` — **всё в одной транзакции** (Doctrine default).

### Уровень 2: Explicit transaction (recommended)

**Суть.** Command handler оборачивает operation в transaction.

```php
class ConfirmOrderCommandHandler
{
    public function handle(ConfirmOrderCommand $command): void
    {
        $this->em->beginTransaction();
        try {
            $order = $this->em->find(Order::class, $command->orderId);
            $order->confirm();
            $this->em->flush($order); // flush only aggregate
            $this->em->commit();
        } catch (\Throwable $e) {
            $this->em->rollback();
            throw $e;
        }
    }
}
```

**Trade-offs:**
- **+** Explicit transaction boundary.
- **+** Only aggregate flushed (via `flush($aggregateRoot)`).

### Подход `flush($entity)`:

```php
$this->em->flush($order); // flush only $order graph
```

**Важно:** `flush($order)` flush'ит **graph, reachable от `$order`**, не всё dirty.

---

## Граница агрегата и consistency

**Проблема:** Doctrine Unit of Work flush'ит **graph, reachable от flush()'**, и **всё dirty**.

**Решение:** aggregate root управляет своим graph'ом, и `flush($aggregateRoot)` ограничивает write graph.

```php
// Order aggregate
public function confirm(): void
{
    // business logic — modify items internally
    foreach ($this->items as $item) {
        $item->markConfirmed();
    }
    $this->status = OrderStatus::CONFIRMED;
}
```

**Важно:** `flush($order)` flush'ит `$order` + `$order->items` (reachable graph).

---

## Подводные камни

1. **`flush()` vs `flush($entity)`:** `flush()` flush'ит всё dirty, `flush($aggregate)` — только graph aggregate.
2. **Collection vs array:** используйте `Collection`, не `array`.
3. **`cascade` vs `orphanRemoval`:** `cascade` для persist, `orphanRemoval` для remove.
4. **Child entity vs separate aggregate:** `OrderItem` — child, не separate aggregate.
5. **Unit of Work flush'ит graph:** graph consistency важнее per-aggregate.

---

## Рекомендации

1. **Use `Collection`**, не `array` для children.
2. **`cascade: [persist, remove]` + `orphanRemoval`** для child entities.
3. **`flush($aggregateRoot)`** в command handler (ограничение graph).
4. **Explicit transaction** в command handler (не reliance Doctrine default).
5. **Aggregate root** управляет своим graph'ом, не child entities.

---

## Итог

**Маппинг:** OneToMany + cascade + orphanRemoval для child entities. **Транзакция:** explicit transaction в command handler. **Flush:** `flush($aggregateRoot)` в command handler (ограничение graph). **Подводя graph:** aggregate root управляет graph children, Doctrine Unit of Work flush'ит graph. **Главный trade-off:** Doctrine Unit of Work flush'ит всё dirty, но `flush($aggregate)` ограничивает graph.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

## Анализ вопроса

Хороший практический вопрос, но я хочу сразу сделать важные оговорки, потому что N+1 — это не просто «много запросов», а симптом **плохой настройки маппинга или доступа к данным**.

**Ключевое понимание:** N+1 проблема — это когда Doctrine выполняет 1 запрос за основной entity и **N запросов за each related entity** (за each element коллекции). Это **не** про «много записей», а про **повторяющиеся запросы за related data**.

---

## Диагностика N+1

### Способ 1: Doctrine Profiler (dev)

**Суть.** Symfony Profiler показывает количество запросов за запрос.

```php
// В Symfony Profiler:
// SQL Queries: N queries
// N+1 detection: "Detected N+1 problem in ..."
```

**Как использовать:**
1. `app_dev.php` → Profiler.
2. Смотрите **SQL Queries** tab.
3. **N+1 detection** показывает problematic queries.

### Способ 2: Doctrine Debug Batch

**Суть.** Включите **SQL logging** и посчитайте запросы.

```php
use Doctrine\ORM\EntityManagerInterface;

/** @var EntityManagerInterface $em */
$em->getConfiguration()->setSQLLogger($logger);
```

### Способ 3: Custom Query Count

**Суть.** В тесте/дебаге посчитайте запросы.

```php
public function testOrderList()
{
    $em = $this->getEntityManager();
    $em->getConnection()->getConfiguration()->setSQLLogger($counter = new \Doctrine\DBAL\Logging\EasyLogger());
    
    $orders = $this->orderRepository->findAll();
    foreach ($orders as $order) {
        $order->getItems(); // triggers N+1
    }
    
    $this->assertGreaterThan(1, $counter->queries);
}
```

### Способ 4: PHPStan / static analysis

**Суть.** Some static analyzers detect N+1.

---

## Способы решения

### Способ 1: `fetch="EAGER"` (маппинг)

**Суть.** Doctrine load related data в основном запросе.

```php
class Order
{
    #[ORM\OneToMany(fetch: 'EAGER', ...)]
    private $items;
}
```

**Trade-offs:**
- **+** Simple.
- **+** No query count.
- **-** **SELECT N+1 problem!** (Doctrine still does N+1 for collections).
- **-** **Load unnecessary data** (eager load everything).
- **-** **Performance** for large collections.

**Важно:** `EAGER` **не решает** N+1 для collections — Doctrine **всё равно** делает N+1. **Не рекомендую.**

### Способ 2: `JOIN` в DQL (`LEFT JOIN FETCH`)

**Суть.** Load related data через JOIN.

```php
$dql = 'SELECT o, i FROM Order o LEFT JOIN o.items i';
$orders = $this->em->createQuery($dql)->getResult();
```

**Trade-offs:**
- **+** Single query.
- **+** N+1 solved.
- **-** **No pagination** (JOIN + COUNT problem).
- **-** **Data duplication** (order repeated for each item).
- **- ** **Complex DQL.**

### Способ 3: `JOIN FETCH` в QueryBuilder

**Суть.** Same as DQL but with QueryBuilder.

```php
$repository->createQueryBuilder('o')
    ->leftJoin('o.items', 'i')
    ->addSelect('i')
    ->getQuery()
    ->getResult();
```

**Trade-offs:**
- **+** Same as DQL.
- **+** Fluent API.

### Способ 4: Subselect / Subquery

**Суть.** Load related data в subselect.

```php
$dql = 'SELECT o FROM Order o WHERE o.id IN (SELECT i.order.id FROM Item i)';
```

**Trade-offs:**
- **+** No N+1.
- **-** Complex.

### Способ 5: Lazy loading + explicit fetch

**Суть.** Load related data explicitly when needed.

```php
$orders = $this->orderRepository->findAll();
foreach ($orders as $order) {
    if ($needItems) {
        $items = $this->itemRepository->findBy(['order' => $order]);
    }
}
```

**Trade-offs:**
- **+** Explicit.
- **+** No unnecessary load.
- **-** Manual N+1.

### Способ 6: DTO projection (recommended)

**Суть.** Projection into DTO, load needed data.

```php
$dql = 'SELECT NEW App\Dto\OrderDto(o.id, o.total, i) FROM Order o JOIN o.items i';
$dtos = $this->em->createQuery($dql)->getResult();
```

**Trade-offs:**
- **+** **No N+1.**
- **+** **Only needed data.**
- **+** **Clean separation** (entity vs DTO).
- **-** **Projection complexity.**

### Способ 7: Repository custom query

**Суть.** Custom repository method with JOIN.

```php
class OrderRepository extends ServiceEntityRepository
{
    public function findWithItems(): array
    {
        return $this->createQueryBuilder('o')
            ->leftJoin('o.items', 'i')
            ->addSelect('i')
            ->getQuery()
            ->getResult();
    }
}
```

**Trade-offs:**
- **+** Reusable.
- **+** Explicit N+1 solve.

---

## Сравнительная таблица

| Способ | N+1 Solved | Pagination | Complexity | Reusable |
|--------|------------|------------|------------|----------|
| EAGER fetch | ❌ (nope) | ✅ | Низкая | ✅ |
| JOIN FETCH | ✅ | ❌ (problem) | Средняя | ✅ |
| QueryBuilder | ✅ | ❌ | Средняя | ✅ |
| Subselect | ✅ | ✅ | Высокая | ⚠️ |
| Explicit fetch | ✅ | ✅ | Средняя | ⚠️ |
| DTO Projection | ✅ | ✅ | Средняя | ✅ |
| Custom Repository | ✅ | ✅ | Средняя | ✅ |

---

## Trade-offs по сценарию

### Для pagination:

1. **JOIN FETCH не работает** (COUNT problem).
2. **Use DTO projection** или **subselect**.

### Для single entity:

1. **JOIN FETCH** — для single related entity.
2. **DQL** — для complex.

### For collections:

1. **DTO projection** — best.
2. **Explicit fetch** — when needed.

---

## Подводные камни

1. **EAGER не решает N+1** ( Doctrine still N+1 for collections).
2. **JOIN FETCH breaks pagination** (COUNT).
3. **Data duplication** in JOIN.
4. **Projection mapping** complexity.

---

## Рекомендации

1. **Detect first** (Profiler).
2. **For pagination:** DTO projection.
3. **For single related:** JOIN FETCH.
4. **For collections:** DTO projection.
5. **Never rely on EAGER** for collections.

---

## Итог

**N+1 — это симптом**, а не причина. **Диагностика:** Symfony Profiler, SQL logging. **Решения:** JOIN FETCH (single), DTO projection (collections/pagination), explicit fetch, custom repository. **Главный trade-off:** JOIN FETCH solves N+1 but breaks pagination; DTO projection solves both but adds complexity. **EAGER fetch не решает N+1** для collections.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

## Анализ вопроса

Хороший, глубокий вопрос, но я хочу сразу сделать **важную оговорку о предпосылке**, потому что в нём есть **распространённая ложная дотомка**: будто бизнес-валидация в коде и ограничения в БД — это **конкурирующие** подходы.

**Реальность:** это **разные уровни защиты**, и они **дополняют**, а не исключают друг друга. Это как **двойная проверка** в авиации — у пилотов есть проверка перед взлётом (приложение), но есть и датчики в двигателе (БД).

---

## Почему оба уровня нужны (defense in depth)

### Уровень 1: Приложение (бизнес-валидация)

**Зачем:**
- **Богатая бизнес-логика** (validations, cross-field rules).
- **Портативность** (одна логика для SQLite, MySQL, PostgreSQL).
- **Читаемость** (валидация в коде).

**Ограничения:**
- **Не все правила** можно выразить в коде (конкурентность, integrity).

### Уровень 2: База данных (integrity)

**Зачем:**
- **Data integrity** (final guardian).
- **Concurrency safety** (DB enforces atomicity).
- **Performance** (DB-optimized checks).
- **Multiple entry points** (API, CLI, direct DB access).

**Ключевое понимание:** **Приложение — это front-line defense**, **БД — это last line of defense**. Если приложение упадёт или будет обойдено (API, raw SQL, другой сервис), **БД всё равно защитит данные**.

---

## Средства PostgreSQL для integrity

### 1. NOT NULL

**Суть.** Column cannot be NULL.

```sql
CREATE TABLE users (
    id uuid PRIMARY KEY,
    email text NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now()
);
```

**Когда:** для **обязательных** fields.

### 2. UNIQUE

**Суть.** No duplicate values.

```sql
CREATE TABLE users (
    id uuid PRIMARY KEY,
    email text NOT NULL UNIQUE
);
```

**Когда:** для **business rules** (unique email).

**Trade-off:** UNIQUE vs application-level uniqueness. **UNIQUE в БД** — для **concurrency safety** (multiple app instances).

### 3. PRIMARY KEY

**Суть.** Entity identity.

```sql
CREATE TABLE orders (
    id uuid PRIMARY KEY
);
```

**Когда:** для **entities** (aggregate roots).

### 4. FOREIGN KEY

**Суть.** Referential integrity.

```sql
CREATE TABLE order_items (
    id uuid PRIMARY KEY,
    order_id uuid NOT NULL REFERENCES orders(id) ON DELETE CASCADE
);
```

**Когда:** для **relationships**.

**Trade-off:** FK vs application-level. **FK** — для **integrity**, application — для **business logic**.

### 5. CHECK constraints

**Суть.** Custom business rules.

```sql
CREATE TABLE orders (
    id uuid PRIMARY KEY,
    total numeric(10,2) NOT NULL CHECK (total >= 0),
    status text NOT NULL CHECK (status IN ('pending', 'paid', 'shipped'))
);
```

**Когда:** для **simple domain rules** (positive amount, valid status).

**Trade-off:** **CHECK** — для **simple rules**, application — для **complex cross-field rules**.

### 6. Indexes (partial, expression)

**Суть.** Enforce partial uniqueness.

```sql
CREATE UNIQUE INDEX idx_active_users ON users (email) WHERE deleted_at IS NULL;
```

**Когда:** для **conditional uniqueness**.

### 7. CHECK constraints для complex logic

**Суть.** Multiple conditions.

```sql
CREATE TABLE orders (
    id uuid PRIMARY KEY,
    start_date date,
    end_date date,
    CHECK (end_date >= start_date)
);
```

**Когда:** для **cross-field validation** (end >= start).

---

## Когда использовать БД-ограничения (и почему)

### Случай 1: Data integrity (final guardian)

**Пример:** `total >= 0`, `email NOT NULL`.

**Почему:** **Application может быть обойщено** (API, CLI, DB access). **БД — последняя защита**.

### Случай 2: Concurrency safety

**Пример:** unique email, FK integrity.

**Почему:** **Multiple app instances** (microservices, multiple servers). **Application-level unique check** имеет **race condition** (two inserts, both check unique, both pass). **БД-уникальность** — **atomic**.

### Случай 3: Multiple entry points

**Пример:** API + CLI + direct DB.

**Почему:** **Application validation** только для **API**, **БД** — для **all**.

### Случай 4: Performance

**Пример:** CHECK constraints vs application validation.

**Почему:** **БД-validation** — **faster** (native), **application** — **PHP overhead**.

---

## Что НЕ следует перекладывать на БД

### Антипаттерн 1: Вся бизнес-логика в CHECK

```sql
-- ПЛОХО: сложная бизнес-логика в БД
CHECK (
    (status = 'paid' AND total > 0) OR
    (status = 'cancelled' AND total = 0)
    -- ... сложная логика
)
```

**Почему:** **Дублирование** business logic, **сложность**, **portability problem**.

### Антипаттерн 2: Отказ от integrity constraints

```sql
-- ПХО: no constraints
CREATE TABLE orders (id uuid, total numeric);
```

**Почему:** **Data integrity** lost.

### Антипаттерн 3: Дублирование application validation в CHECK

```sql
-- ПЛОХО: дублирование
CHECK (email ~ '^[^@]+@[^@]+$')  -- duplicate of application regex
```

**Почему:** **Дублирование**, **сложность**.

---

## Правильная стратегия (defense in depth)

### Уровень 1: Application (business rules)

```php
class Order {
    public function __construct(public Money $total) {
        if ($total->getAmount() < 0) {
            throw new NegativeAmountException();
        }
    }
}
```

### Уровень 2: БД (integrity)

```sql
CREATE TABLE orders (
    id uuid PRIMARY KEY,
    total numeric(10,2) NOT NULL CHECK (total >= 0),
    email text NOT NULL UNIQUE
);
```

**Почему both:**
- **Application:** business logic, portability.
- **БД:** integrity, concurrency, multiple entry points.

---

## Trade-offs по каждому средству

| Средство | Когда использовать | Trade-off |
|----------|-------------------|-----------|
| NOT NULL | обязательные fields | simple, no complexity |
| UNIQUE | business rules | concurrency safety |
| FK | relationships | integrity, cascade |
| CHECK | simple domain rules | portable, native performance |
| Indexes | conditional uniqueness | performance, complexity |
| CHECK (complex) | cross-field rules | portability, duplication |

---

## Практический пример: заказы

### Application validation:

```php
class Order {
    public function __construct(
        public Money $total,
        public User $customer
    ) {
        if ($total->getAmount() <= 0) {
            throw new InvalidOrderException('Order total must be positive');
        }
        if ($customer->isBlacklisted()) {
            throw new BlacklistedCustomerException();
        }
    }
}
```

### БД constraints:

```sql
CREATE TABLE orders (
    id uuid PRIMARY KEY,
    total numeric(10,2) NOT NULL CHECK (total > 0),
    customer_id uuid NOT NULL REFERENCES customers(id),
    created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE customers (
    id uuid PRIMARY KEY,
    email text NOT NULL UNIQUE
);
```

**Почему both:**
- **Application:** `isBlacklisted()` (business logic, не в БД).
- **БД:** `total > 0`, `email UNIQUE`, FK integrity.

1. **Не дублируйте** application validation в CHECK.
2. **Не перекладывайте** complex business logic в БД.
3. **UNIQUE vs application** — для concurrency safety use БД.
4. **Portability** — CHECK syntax differs between DBs.
5. **Migration complexity** — constraints hard to change.

---

## Итог

**Приложение и БД — это defense in depth, не конкуренты.** **Application** — business logic, portability, readability. **БД** — integrity (final guardian), concurrency safety, multiple entry points, performance. **Средства:** NOT NULL, UNIQUE, PRIMARY KEY, FK, CHECK, indexes. **Стратегия:** application для business rules, БД для integrity и concurrency. **Не дублируйте** и **не перекладывайте** complex logic в БД.

Также оговорюсь: **медленный запрос ≠ медленный код**. Часто проблема в **данных** (большая таблица), **индексах**, **statistics**, **lock'ах**, **concurrency**, а не в SQL-синтаксисе.

## Процесс диагностики

### Шаг 1: Измерить (EXPLAIN ANALYZE)

**Самый важный инструмент.**

```sql

```

**Что смотреть:**
- **Execution time** vs **Planning time**.
- **Node types** (Seq Scan vs Index Scan).
- **Rows estimate vs actual** — **главная подсказка!**
- **Buffers** (shared hit vs read).
- **Duration per node**.

### Шаг 2: Понять plan

**Пример плохого plan:**

```
Limit  (cost=... rows=100)

        Sort Key: total DESC

              ->  Hash
                    ->  Seq Scan on customers
```

**Проблемы:**
- **Seq Scan** на 1M rows.
- **Rows estimate vs actual mismatch**.

## Типовые причины медленных запросов

### Причина 1: Отсутствие индекса

**Симптом:** **Sequential Scan** на large table.

**Решение:**

```sql
CREATE INDEX idx_orders_created_at ON orders (created_at);
CREATE INDEX idx_orders_customer ON orders (customer_id);
```

**Trade-off:** index **ускоряет read**, **замедляет write**.

### Причина 2: Плохая оценка строк (stale statistics)

**Симптом:** **Rows estimate ≠ actual** (например, estimated 100, actual 1M).

**Решение:**

```sql
ANALYZE orders;  -- update statistics
ANALYZE orders (created_at);
```

**Почему:** planner использует statistics для выбора plan. **Stale stats → wrong plan**.

### Причина 3: Плохой план из-за типов

**Симптом:** **implicit type cast** в WHERE.

```sql
-- ПЛОХО: text column vs integer param
WHERE customer_id = '123'  -- text cast
```

**Решение:** match types, add index matching the type.

### Причина 4: N+1 в DQL

**Симптом:** **many queries** (not one slow query).

**Решение:** JOIN FETCH, DTO projection.

### Причина 5: Missing index для ORDER BY

**Симптом:** **Sort node** expensive.

```sql
-- Bad: sort 1M rows
ORDER BY total DESC

-- Good: index
CREATE INDEX idx_orders_total ON orders (total DESC);
```

### Причина 6: Locking / contention

**Симптом:** **Fast query but blocks**.

**Диагностика:**

```sql
SELECT * FROM pg_locks;
SELECT * FROM pg_stat_activity WHERE state = 'active';
```

**Почему:** another transaction holds lock.

### Причина 7: Missing statistics для functions

**Симптом:** **complex function** in WHERE.

```sql
WHERE lower(email) = 'test@example.com'
```

**Решение:** expression index.

```sql
CREATE INDEX idx_users_lower_email ON users (lower(email));
```

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

## Анализ вопроса

Хороший, концептуальный вопрос, но в нём есть **распространённая путаница**, которую я хочу сразу снять: многие думают, что **аггрегат** — это «сущность + её children» или «таблица в БД». **Это не так.**

**Определение (Эван, Domain-Driven Design):**

> Аггат — это **набор объектов, объединённых概念ом целостности (consistency boundary)**, внутри которой **одно состояние** регулируется как единое целое. Аггат — **корневой объект (aggregate root)**, управляющий graph'ом.

**Ключевые критерии:**

1. **Boundary of consistency** (граница согласованности): внутри агрегата **всегда** consistent.
2. **Aggregate root**: единственный entry point для graph.
3. **Identify**: root имеет identity, children — нет (вне aggregate).
4. **Rules**: business rules enforce consistency **внутри** boundary.

---

## Как определять границы агрегата

**Главные вопросы:**

1. **Какое состояние должно быть always consistent?** (single consistency boundary).
2. **Что требует atomicity?** (commit/rollback together).
3. **Что имеет единый identity?**
4. **Через что обращаются?** (single entry point).

**Практический heuristic:**

- Если **изменение одного объекта** требует **изнения другого** для consistency → **один aggregate**.
- Если **objects могут меняться независимо** → **separate aggregates**.
- Если **данные** referenced **внешними** entities → **reference by identity**, не embed.

---

## Пример: Магазин — Заказ и Платеж

### Плохая граница (всё в одном aggregate)

```php
class Order {  // aggregate root
    public function __construct(
        private Money $total,
        private Payment $payment,  // embed
        private Shipping $shipping // embed
    ) {}
    
    public function pay(PaymentDetails $details): void {
        // modify payment + shipping consistency
    }
}
```

**Почему плохо:**
- **Одно massive aggregate** (order + payment + shipping).
- **Lock contention** (all modifications).
- **Large graph**.

### Хорошая граница (aggregate + references)

```php
class Order {  // aggregate root
    public function __construct(
        private Money $total,
        private PaymentReference $payment,  // reference (not embed)
    ) {}
    
    public function confirm(): void {
        // business logic
    }
}

class Payment {  // separate aggregate
    public function __construct(
        private PaymentId $id,
        private OrderReference $order,
        private Money $amount,
    ) {}
    
    public function confirm(): void {
        // business logic
    }
}
```

**Почему хорошо:**
- **Separate consistency boundaries** (Order, Payment).
- **Reference by identity** (Payment has Order reference).
- **Independent modifications**.
- **Smaller graph**.

---

## Типовая ошибка: too wide / too narrow

### Ошибка 1: Too wide (всё в одном aggregate)

**Пример:** Order + Payment + Shipping + Customer + Inventory в one aggregate.

**Почему плохо:**
- **Lock contention**.
- **Large graph**.
- **Complex consistency**.

**Решение:** split into separate aggregates.

### Ошибка 2: Too narrow (один object per aggregate)

**Пример:** OrderItem — separate aggregate из-за «чистоты».

**Почему плохо:**
- **Every change requires loading + saving each item** (N+1).
- **Consistency across aggregates hard**.

**Решение:** Aggregate **Order** includes **items** (they're consistency boundary).

---

## Как выбрать границы (heuristic)

### Правило «consistency + atomicity»:

1. **Single consistency:** если objects **должны** быть always consistent → **one aggregate**.
2. **Atomicity:** если change **one** → change **all** (atomically) → **one aggregate**.
3. **Reference:** если object referenced externally → **separate aggregate**.

### Пример: Заказ + Позиции

```php
class Order {  // aggregate root
    private array $items; // children (part of consistency)
    
    public function addItem(OrderItem $item): void {
        $this->items[] = $item;
        // total consistency
        $this->total = $this->total->add($item->getAmount());
    }
}
```

**Почему items — children:**
- **Consistency** (total ↔ items).
- **Atomicity** (add item → update total together).
- **Reference** (no external reference to items).

---

## Boundary enforcement

### Aggregate root:

```php
class Order {
    public function pay(Money $amount): void {
        // Only aggregate root modifies consistency
    }
}
```

**Почему:** children (items) **not directly modified** from outside. **Only via root**.

---

## Подводные камни

1. **Не embed external objects** — reference by identity.
2. **Не делать too wide** (lock contention).
3. **Не делать too narrow** (N+1, consistency hard).
4. **Single consistency** (not multiple).
5. **Aggregate root** — single entry point.

---

## Итог

**Аггат — это boundary of consistency**, а не «сущность + children». **Границы определяются по:** single consistency, atomicity, reference, entry point. **Пример:** Order (root) + items (children) в one aggregate; Payment — separate aggregate. **Типовая ошибка:** too wide (всё в одном) или too narrow (один object per aggregate). **Правильно:** aggregate + references.

**Кандидат:**

## Анализ вопроса

Хороший, глубокий вопрос, но я хочу сразу сделать **важную оговорку о предпосылке**: «два процесса изменяют один aggregate» — это **не просто concurrent modification**, а **problem of concurrency in distributed system**. **Важное понимание:** агрегат DDD — это **consistency boundary**, и **одновременная модификация** одного aggregate — это **optimistic vs pessimistic concurrency**.

**Ключевое понимание:** DDD-аграт — это **not** просто «объект в памяти», а **logical boundary**. Физически aggregates хранятся в БД (обычно one table per aggregate). Concurrent modification = **two transactions modify same DB row**.

---

## Что произойдёт без защиты

### Scenario: Race condition

```
Process A: read Order (version=5)
Process B: read Order (version=5)
Process A: update total, write (version=6) ✓
Process B: update shipping, write (version=?) ✗ ← LOST UPDATE
```

**Результат:** **lost update** — изменение B перезаписывает изменение A. **Data corruption.**

---

## Способы решения

### Способ 1: Optimistic Concurrency Control (OCC)

**Суть.** Version column, compare on write.

```php
class Order {
    #[ORM\Column(type: 'integer')]
    private int $version;  // versioning
}
```

```sql
UPDATE orders SET total = 100, version = version + 1
WHERE id = 123 AND version = 5;  -- only if version unchanged

-- rows affected = 0 → conflict!
```

**Trade-offs:**
- **+** No locks (better concurrency).
- **+** DDD-friendly (aggregate boundary).
- **-** **Conflict resolution** needed (retry, merge, error).
- **- ** **Lost update** detection.

**Реализация в Doctrine:**

```php
class Order {
    #[ORM-Version]
    private $version;
}
```

**Doctrine handles version column automatically.**

### Способ 2: Pessimistic Locking

**Суть.** Database lock on read.

```sql
SELECT * FROM orders WHERE id = 123 FOR UPDATE;  -- lock row
```

**Trade-offs:**
- **+** No conflict (serialized).
- **+** Simple (no resolution).
- **- ** **Lock contention** (serialized).
- **- ** **Performance** (locks block).
- **- ** **Deadlock risk**.

**Doctrine:**

```php
$em->clear();
$order = $this->em->find(Order::class, 123);
$this->em->lock($order, EntityManager::LOCK_PESSIMISTIC);
```

### Способ 3: Optimistic Locking + Retry

**Суть.** OCC + retry on conflict.

```php
public function update(Order $order): void {
    try {
        $order->update();
        $this->em->flush();
    } catch (OptimisticLockFailureException $e) {
        // reload + retry
        $this->retryUpdate($order);
    }
}
```

**Trade-offs:**
- **+** No lost update.
- **+ ** Better concurrency than pessimistic.
- **- ** Retry logic.

### Способ 4: Pessimistic + Lock timeout

**Суть.** Lock + timeout, avoid deadlock.

```sql
SET LOCK_TIMEOUT = '2s';
```

### Способ 5: Command-based serialization

**Суть.** Single command handler serializes.

```php
class OrderCommandHandler {
    public function handle(OrderCommand $command): void {
        // Single process handles commands for aggregate
        $order = $this->repository->find($command->orderId);
        $order->apply($command);
        $this->repository->save($order);
    }
}
```

**Trade-offs:**
- **+ ** Correct (serialized).
- **- ** Throughput (one process).

## Как проектировать с учётом

### Уровень 1: Aggregate design

**Суть.** **Small aggregate** — less contention.

```php
class Order {  // small aggregate
    // only necessary fields + children
}
```

**Почему:** small aggregate = less lock contention.

### Уровень 2: Versioning

**Суть.** Optimistic version.

```php
class Order {
    #[ORM\Version]
    private $version;
}
```

**Почему:** detect conflict.

### Уровень 3: Conflict resolution

**Суть.** Define strategy:
- **Retry** (auto-recovery).
- **Error** (notify user).
- **Merge** (business logic).

```php
class OrderUpdateService {
    public function update(OrderCommand $command): OrderUpdateResult {
        try {
            // ...
            return OrderUpdateResult::success();
        } catch (OptimisticLockFailureException $e) {
            return OrderUpdateResult::conflict();
        }
    }
}
```

### Уровень 4: Pessimistic vs Optimistic

**Суть.** Choose based on:
- **Conflict frequency** (rare → optimistic).
- **Contention** (high → pessimistic).
- **Throughput** (high → optimistic).

**Heuristic:**
- **Low contention:** **Optimistic**.
- **High contention:** **Pessimistic**.

---

## Trade-offs сравнение

| Способ | Correct | Concurrency | Complexity |
|--------|---------|-------------|------------|
| Optimistic | ✅ | ✅ | Средняя |
| Pessimistic | ✅ | ❌ | Низкая |
| OCC + Retry | ✅ | ✅ | Средняя |
| Serialized | ✅ | ❌ | Низкая |

## Подводные камни

1. **Lost update** — без защиты.
2. **Optimistic → conflict** — need resolution.
3. **Pessimistic → contention** — serialized.
4. **Deadlock** — pessimistic.
5. **Over-optimization** — premature.

---

## Рекомендации

1. **Small aggregate** — less contention.
2. **Optimistic versioning** — default (low contention).
3. **Conflict resolution** — retry/error.
4. **Pessimistic** — high contention.
5. **Never** — unprotected concurrent.

---

## Итог

**Concurrent modification одного aggregate = lost update без защиты.** **Решения:** optimistic versioning (OCC), pessimistic locking, OCC + retry. **Проектирование:** small aggregate, versioning, conflict resolution strategy. **Выбор:** optimistic (low contention), pessimistic (high contention). **Главное:** never unprotected.

**Кандидат:**

## Анализ вопроса

Хороший, глубокий вопрос, но я хочу сразу сделать важные оговорки, потому что «доменные события» часто путают с разными концепциями:

1. **Доменные события** (domain events) — часть DDD, **факты о том, что произошло** в домене.
2. **События приложения** (application events) — технические.
3. **События базы данных** (database events) — triggers.

**Ключевое понимание:** доменное событие — это **immutable fact о прошлом** (past tense: «заказ оплачен»). Оно **публикуется**, а не **вызывается**.

---

## Что такое доменное событие

**Определение:**

```php
namespace App\Domain\Event;

final class OrderPaidEvent {
    public function __construct(
        private OrderId $orderId,
        private Money $amount,
        private \DateTimeImmutable $occurredAt,
    ) {}
}
```

**Характеристики:**
- **Immutable** (past fact).
- **Past tense** (название: «Paid», не «Pay»).
- **Recorded** (aggregat records it).

---

## Когда публиковать (record)

**Суть.** Aggregate **records** events, **doesn't dispatch** them.

```php
class Order {
    private array $recordedEvents = [];
    
    public function pay(Money $amount): void {
        $this->assertPaid();
        $this->status = OrderStatus::PAID;
        // record event (not dispatch)
        $this->recordedEvents[] = new OrderPaidEvent(
            OrderId::from($this->id),
            $amount
        );
    }
    
    public function popRecordedEvents(): array {
        $events = $this->recordedEvents;
        $this->recordedEvents = [];
        return $events;
    }
}
```

**Почему record + pop:**
- Aggregate **manages** events internally.
- Events **published** after flush.

---

## Как обрабатывать (dispatch + handlers)

### Уровень 1: Application layer (recommended)

**Суть.** Repository flush'ит aggregate, application dispatch'ит events.

```php
class OrderRepository {
    public function save(Order $order): void {
        $events = $order->popRecordedEvents();  // record
        $this->em->persist($order);
        $this->em->flush();
        // dispatch after flush
        $this->eventBus->dispatch($events);
    }
}
```

### Уровень 2: Symfony Messenger

**Суть.** Messenger dispatch'ит events.

```php
$this->messageBus->dispatch(new OrderPaidEvent(...));
```

### Handlers

```php
class SendConfirmationEmailHandler {
    public function __invoke(OrderPaidEvent $event): void {
        $this->emailService->send($event->orderId);
    }
}
```

---

## Проблемы, которые решают доменные события

### 1. Decoupling

**Проблема:** aggregate знает про all dependents.

**Решение:** aggregate records event, **не знает** кто обрабатывает.

```php
// Order doesn't know about EmailService, InventoryService, etc.
```

### 2. Audit trail

**Проблема:** что произошло?

**Решение:** events = audit log.

### 3. Eventual consistency

**Проблема:** consistency across aggregates.

**Решение:** events **notify** other aggregates.

### 4. Rebuilding state

**Проблема:** recompute derived state.

**Решение:** replay events.

---

## Проблемы, которые создают доменные события

### 1. **Finality / ordering**

**Проблема:** events processed **asynchronously**, **ordering** uncertain.

**Решение:** event ordering (sequence id), or synchronous.

### 2. **At-least-once delivery**

**Проблема:** event processed twice.

**Решение:** idempotency (event id dedup).

### 3. **Testing complexity**

**Проблема:** async flow hard to test.

**Решение:** test dispatch + handlers separately.

### 4. **Eventual consistency bugs**

**Проблема:** reading stale state.

**Решение:** read model, or synchronous.

### 5. **Event schema evolution**

**Проблема:** events change over time.

**Решение:** versioning events.

## Связь с транзациями БД

**Это самый важный и самый сложный аспект.**

### Проблема: two-write problem

**Суть.** Aggregate saved to DB, events sent to queue — **two separate writes**. **Не atomic.**

```
1. SAVE aggregate to DB (transaction commits)
2. DISPATCH event to queue  ← if this fails, DB and queue inconsistent
```

**Результат:** aggregate saved, event lost → inconsistent.

### Решение 1: Transactional outbox

**Суть.** Events saved to DB (same transaction), then published.

```sql
CREATE TABLE outbox (
    id uuid PRIMARY KEY,
    event text NOT NULL,
    payload jsonb NOT NULL,
    processed_at timestamptz
);

-- same transaction: save aggregate + outbox row
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 123;
INSERT INTO outbox (event, payload) VALUES ('order_paid', '{...}');
COMMIT;

-- background job publishes outbox → queue
```

**Trade-offs:**
- **+ ** **Transactional** (DB + outbox atomic).
- **+ ** **Reliable** delivery.
- **- ** Background job.

### Решение 2: In-memory event bus + flush

**Суть.** Dispatch after flush, same process.

```php
$em->flush();  // commit
$this->eventBus->dispatch($events);  // in-memory
```

**Trade-offs:**
- **+ ** Simple.
- **- ** **Not distributed** (single process).
- **- ** If dispatch fails after commit → lost.

### Решение 3: Synchronous handlers

**Суть.** Handle events in same transaction.

```php
$em->beginTransaction();
try {
    $em->persist($order);
    $em->flush();
    foreach ($events as $event) {
        $this->handlers[$event::class]($event); // sync
    }
    $em->commit();
} catch (\Throwable $e) {
    $em->rollback();
}
```

**Trade-offs:**
- **+ ** **Transactional** (all in one).
- **+ ** **Consistent**.
- **- ** **Synchronous** (blocking).
- **- ** **Tight coupling** (handlers in transaction).

---

## Symfony Messenger + транзакции

**Суть.** Messenger **doesn't** integrate with DB transaction by default.

**Решение:** **Transactional outbox** или **synchronous handlers**.

### Symfony Messenger в транзации:

```php
// messenger.yaml
framework:
    messenger:
        default_bus:
            handlers:
                App\Event\OrderPaidEvent:
                    # synchronous, in-process
                    type: sync
```

**Trade-offs:**
- **Sync:** consistent, but blocking.
- **Async:** decoupled, but two-write problem.

---

## Trade-offs: async vs sync

| Аспект | Async (queue) | Sync (transaction) |
|--------|---------------|-------------------|
| Coupling | Low | High |
| Consistency | At-least-once | Atomic |
| Performance | Parallel | Blocking |
| Complexity | Higher | Lower |
| Ordering | Need manage | Preserved |

---

## Рекомендации

1. **Record, don't dispatch** — aggregate manages events.
2. **Application layer** dispatches (not domain).
3. **Transactional outbox** — for distributed (reliable).
4. **Synchronous** — for consistency (small systems).
5. **Idempotent handlers** — for at-least-once.

## Итог

**Доменные события — это immutable facts о прошлом,** published aggregates **record** (not dispatch). **Решают:** decoupling, audit, eventual consistency. **Создают:** ordering, at-least-once, testing, evolution. **С транзациями:** **two-write problem** — aggregate в БД, events в queue. **Решения:** **transactional outbox** (reliable), **synchronous handlers** (consistent), or **in-memory** (simple).

**Ключевое понимание:** это **не технические различия**, а **фундаментальные**. И **принятие решения** «к чему относить концепцию» — это **не технический выбор**, а **моделирование домена**.

## Value Object vs Entity

### Entity (сущность)

**Определение:** объект, определённый своим **identity** (не значением).

**Характеристики:**
- **Identity** (уникальный ID).
- **Mutable** (может меняться).
- **Lifelong** (жизненный цикл).
- **Reference** (other objects reference by identity).

**Пример:** `Order`, `User`, `Account`.

```php
class User {
    public function __construct(
        private UserId $id,  // identity
        private string $name,
    ) {}
    
    public function changeName(string $newName): void {  // mutable
        $this->name = $newName;
    }
}
```

**Проверка на равенство:** по **identity** (`===`), не по полям.

### Value Object (значимый объект)

**Определение:** объект, определённый своим **значение** (не identity).

**Характеристики:**
- **No identity** (no ID).
- **Immutable** (нельзя менять).
- **Equality by value** (равенство по полям).
- **Replaceable** (any VO with same value).

**Пример:** `Money`, `Email`, `DateRange`, `Address`.

```php
final class Money {
    public function __construct(
        private Amount $amount,
        private Currency $currency,
    ) {
        // immutable + valid
    }
    
    public function __equals(Money $other): bool {
        return $this->amount === $other->amount 
            && $this->currency === $other->currency;
    }
}
```

**Проверка на равенство:** по **полям** (value equality).

## Как принимать решение (heuristic)

### Вопросы:

1. **Определяется ли концепция identity или значением?**
   - **Identity → Entity.**
   - **Value → VO.**

2. **Нужен ли ей уникальный ID?**
   - **Да → Entity.**
   - **Нет → VO.**

3. **Меняется ли она со временем?**
   - **Да → Entity.**
   - **Нет (immutable) → VO.**

4. **Можно ли заменить другойной концепцией same value?**
   - **Нет (identity) → Entity.**
   - **Да (value) → VO.**

5. **Reference другими objects?**
   - **By identity → Entity.**
   - **By value → VO.**

## Ubiquitous Language (Единый язык)

**Определение:**

> Единый язык — **общий словарь** между **разработчиками** и **экспертами домена** (domain experts), используемый в **коде** и **общении**.

**Суть:**
- **Один термины** для концепций.
- **Код отражает домен** (названия классов, методов).
- **Общение без недопонимания**.

### Как влияет на код

**Пример: «Заказ» вместо «OrderEntity»**

```php
// Bad: technical naming
class OrderEntity {
    public function setStatus($s) {}
}

// Good: ubiquitous language
class Order {
    public function markAsPaid(): void {
        // domain method name
    }
}
```

**Пример: «Оплатить» вместо «processPayment»**

```php
// Bad: technical
public function processPayment(Money $money): void {}

// Good: domain
public function pay(Money $money): void {}
```

---

## Влияние единого языка

### 1. **Читаемость**

**Проблема:** technical naming ≠ домен.

**Решение:** domain naming → readable.

### 2. **Снижение недопонимания**

**Проблема:** разработчик vs эксперт говорят на разных языках.

**Решение:** **единый словарь** → no translation.

### 3. **Код как источник истины**

**Проблема:** документация устаревает.

**Решение:** **код отражает домен** → always current.

### 4. **Моделирование**

**Проблема:** wrong conceptualization.

**Решение:** **единый язык** → correct model.

**Главное правило:** **зависимости направлены внутрь** (toward the core).

## Детализация слоёв

### 1. Domain (Core / Entity Layer)

**Содержание:**
- **Entities** (аггрегаты).
- **Value Objects**.
- **Domain Services**.
- **Domain Rules / Business Logic**.

**Зависимости:** **none** (pure PHP, no framework).

```php
namespace App\Domain\Order;

class Order {
    public function pay(Money $money): void {
        // pure domain logic
    }
}
```

**Требования:**
- **No framework imports.**
- **No Doctrine, no Symfony.**
- **No database access.**

### 2. Application (Use Case / Service Layer)

**Содержание:**
- **Use Cases** (command handlers, services).
- **DTO**.
- **Ports** (interfaces for infrastructure).

**Зависимости:** **Domain** (defines ports, used by infrastructure).

```php
namespace App\Application\Service;

use App\Domain\Order\OrderRepository; // port (interface)

class OrderService {
    public function __construct(
        private OrderRepository $repository // port
    ) {}
    
    public function confirm(int $id): void {
        $order = $this->repository->find($id);
        $order->confirm();
        $this->repository->save($order);
    }
}
```

**Зависимости:** **Domain** (via port interfaces).

### 3. Infrastructure (Adapters Layer)

**Содержание:**
- **Doctrine** (persistence adapters).
- **Symfony** (controllers, HTTP).
- **Queue adapters** (Messenger).
- **External services**.

**Зависимости:** **Application** (implements ports).

```php
namespace App\Infrastructure\Persistence\Doctrine;

use App\Application\Service\OrderService;
use App\Domain\Order\OrderRepository; // implements port

class DoctrineOrderRepository implements OrderRepository {
    public function __construct(
        private EntityManagerInterface $em
    ) {}
    
    public function save(Order $order): void {
        $this->em->persist($order);
        $this->em->flush();
    }
}
```

**Зависимости:** **Application** (implements interfaces).

```
            /‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
           /  End-to-End (少量)     \
          /──────────────────────────\
         /   Integration (средне)     \
        /──────────────────────────────\
       /     Unit (много)               \
      /──────────────────────────────────\
```

### 1. Unit-тесты (большая часть)

**Суть.** Тестируем **один класс/функцию**, **мокаем** зависимости.

**Что мокаем:**
- **Внешние сервисы** (HTTP, queue).
- **Ports** (infrastructure interfaces).

**Что не мокаем:**
- **Domain logic** (тестируем реально).

```php
class OrderServiceTest extends TestCase
{
    public function testConfirmOrder(): void
    {
        $repository = $this->mock(OrderRepository::class);
        $repository->expects($this->once())
            ->method('save')
            ->with($this->isInstanceOf(Order::class));
        
        $service = new OrderService($repository);
        $service->confirm($order);
    }
}
```

**Trade-offs:**
- **+ Fast** (no DB).
- **+ Isolated**.
- **- Mocks hide integration bugs**.

### 2. Integration-тесты (средне)

**Суть.** Тестируем **interaction со внешними системами** (БД, cache).

**Что не мокаем:**
- **PostgreSQL** (real DB).
- **Doctrine** (real query).

```php
class OrderRepositoryIntegrationTest extends TestCase
{
    private EntityManagerInterface $em;
    
    protected function setUp(): void
    {
        $this->em = static::getContainer()->get(EntityManagerInterface::class);
    }
    
    public function testSaveOrder(): void
    {
        $this->em->persist($order);
        $this->em->flush();
        
        $found = $this->em->find(Order::class, $order->getId());
        $this->assertEquals($order, $found);
    }
}
```

**Trade-offs:**
- **+ Tests real integration**.
- **- Slower** (DB).

### 3. End-to-End (много)

**Суть.** Тестируем **full flow** (HTTP → DB).

**Что не мокаем:**
- **Всё реально**.

```php
class ApiIntegrationTest extends WebTestCase
{
    public function testOrderEndpoint(): void
    {
        $client = static::createClient();
        $client->request('POST', '/api/orders', [
            'json' => ['total' => 100],
        ]);
        
        $this->assertResponseIsSuccessful();
    }
}
```

**Trade-offs:**
- **+ Real flow**.
- **慢慢**.

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

## Анализ вопроса

Хороший, практически важный вопрос. Сразу сделаю **важную оговорку**: «два пользователя изменяют одну запись» — это **concurrent modification problem**, и есть **несколько типов проблем**:

1. **Lost Update** (одна перезапись другую).
2. **Dirty Read** (чтение грязного данных).
3. **Non-Repeatable Read** (разные значения в транзакции).
4. **Phantom Read** (появление/исчезновение строк).

---

## Проблемы concurrent modification

### Проблема 1: Lost Update

**Суть.** Оба читают (version=5), оба пишут. **Последний выиграл**, изменение первого потеряно.

```
User A: read (v5) → update → write (v6) ✓
User B: read (v5) → update → write (v6) ✗ ← A's update lost!
```

### Проблема 2: Dirty Read

**Суть.** Чтение **незафиксированных** данных.

```
User A: update (uncommitted)
User B: read → gets dirty data
User A: rollback  ← B read wrong data
```

### Проблема 3: Write-Write Conflict

**Суть.** Обе транзакции **write**, conflict на commit.

---

## Способы защиты

### Способ 1: Optimistic Locking (OCC)

**Суть.** Version column, compare on write.

```php
class Entity {
    #[ORM\Column(type: 'integer')]
    private int $version;
}
```

```sql
UPDATE items SET value = 1, version = version + 1
WHERE id = 1 AND version = 5;

-- rows = 0 → conflict!
```

**Trade-offs:**
- **+ ** No locks (high concurrency).
- **+ ** DDD-friendly.
- **- ** Conflict resolution needed (retry, error).
- **- ** Requires app support.

### Способ 2: Pessimistic Locking

**Суть.** DB lock on read (`FOR UPDATE`).

```sql
SELECT * FROM items WHERE id = 1 FOR UPDATE;  -- lock row
```

**Trade-offs:**
- **+ ** No conflict (serialized).
- **+ ** Simple.
- **- ** Lock contention (serialized).
- **- ** Performance.
- **- ** Deadlock risk.

**Doctrine:**

```php
$this->em->lock($entity, EntityManager::LOCK_PESSIMISTIC);
```

### Способ 3: Transaction Isolation Levels

**Суть.** Control read/write behavior.

**Levels:**
- **READ UNCOMMITTED** (dirty read possible).
- **READ COMMITTED** (default, no dirty).
- **REPEATABLE READ** (no non-repeatable).
- **SERIALIZABLE** (no phantom, full serialization).

**PostgreSQL:**

```sql
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

**Trade-offs:**
- **+ ** Granular control.
- **- ** SERIALIZABLE slow (serialization).

### Способ 4: Application-level locking

**Суть.** Application lock (Redis, lock service).

```php
$lock = $this->lockFactory->createLock("item:1");
if ($lock->acquire()) {
    try {
        // modify
    } finally {
        $lock->release();
    }
}
```

**Trade-offs:**
- **+ ** Cross-process.
- **+ ** Distributed.
- **- ** Complexity.
- **- ** Lock service down.

### Способ 5: Merge on conflict

**Суть.** Merge changes (business logic).

```php
try {
    $em->flush();
} catch (OptimisticLockFailureException $e) {
    // merge changes
    $merged = mergeChanges($current, $incoming);
}
```

**Trade-offs:**
- **+ ** No lost update.
- **- ** Merge logic complex.

### Способ 6: Last-Write-Wins (LWW)

**Суть.** Accept last write (with timestamp).

```sql
UPDATE items SET value = 1, updated_at = now()
WHERE id = 1 AND updated_at < now() - interval '10 seconds';
```

**Trade-offs:**
- **+ ** Simple.
- **- ** Lost update.
- **+ ** For eventual consistency.

---

## Сравнительная таблица

| Способ | Correct | Concurrency | Complexity | Distributed |
|--------|---------|-------------|------------|-------------|
| Optimistic | ✅ | ✅ | Средняя | ✅ |
| Pessimistic | ✅ | ❌ | Низкая | ✅ |
| Isolation Level | ✅ | ⚠️ | Средняя | ✅ |
| App Locking | ✅ | ❌ | Высокая | ✅ |
| Merge | ✅ | ✅ | Высокая | ✅ |
| LWW | ⚠️ | ✅ | Низкая | ✅ |

---

## Когда какой выбирать

### Optimistic (default)

**Когда:**
- **Low contention** (rare conflict).
- **High concurrency** (many readers).
- **DDD** (aggregate boundary).

**Пример:** user editing profile (rare conflict).

### Pessimistic

**Когда:**
- **High contention** (frequent conflict).
- **Critical data** (no lost update).
- **Low concurrency**.

**Пример:** bank account balance (never lost).

### Isolation Level SERIALIZABLE

**Когда:**
- **Critical transactions**.
- **Full consistency**.
- **Can tolerate slowness**.

**Пример:** financial transactions.

### App Locking (Redis)

**Когда:**
- **Cross-process**.
- **Distributed system**.
- **External service**.

**Пример:** microservices, distributed cache.

### Merge

**Когда:**
- **Conflicts expected**.
- **Business logic for merge**.

**Пример:** collaborative editing.

### LWW

**Когда:**
- **Eventual consistency**.
- **Non-critical data**.

**Пример:** analytics, cache.

---

## Выбор по сценарию

### Сценарий 1: Profile editing

**Состояние:** **Low contention**, **user**.

**Выбор:** **Optimistic** (retry on conflict).

### Сценарий 2: Bank balance

**Состояние:** **High stakes**, **never lost**.

**Выбор:** **Pessimistic** or **SERIALIZABLE**.

### Сценарий 3: Inventory

**Состояние:** **Stock limits**, **critical**.

**Выбор:** **Pessimistic** (no oversell).

### Сценарий 4: Content with revisions

**Состояние:** **Merge changes**.

**Выбор:** **Merge** or **event sourcing**.

## Doctrine + PostgreSQL

### Optimistic with Doctrine:

```php
/**
 * @ORM\Version
 * @ORM\Column(type="integer")
 */

```

**Doctrine handles automatically.**

### Pessimistic with Doctrine:

```php
$this->em->beginTransaction();
$item = $this->em->find(Item::class, 1);
$this->em->lock($item, EntityManager::LOCK_PESSIMISTIC_SHARED);
// ... modify
$this->em->commit();
```

### Isolation:

```php
$this->em->getConnection()->getConfiguration()
    ->setDefaultTransactionIsolation(Connection::ISOLATION_SERIALIZABLE);
```

## Подводные камни

1. **Optimistic → conflict** (need resolution).
2. **Pessimistic → deadlock** (lock ordering).
3. **SERIALIZABLE → slowness** (serialization).
4. **App Locking → service down** (availability).
5. **LWW → lost update** (accept).

---

## Рекомендации

1. **Optimistic** — default (low contention).
2. **Pessimistic** — high contention (critical).
3. **SERIALIZABLE** — critical transactions.
4. **App Locking** — distributed.
5. **Merge** — expected conflicts.

---

## Итог

**Проблемы:** lost update, dirty read, write-write conflict. **Способы:** optimistic (low contention), pessimistic (high contention), isolation levels (SERIALIZABLE), app locking (distributed), merge (expected). **Выбор:** optimistic default, pessimistic critical. **Главное:** match strategy to contention level.

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

## Анализ вопроса

Хороший, практический вопрос, но я хочу сразу сделать **важную оговорку о предпосылке**: нет единого «правильного» git-процесса — всё зависит от **размера команды**, **частоты релизов**, **criticality системы**. Я опишу **свой approach**, но с оговорками, что в small startup и enterprise процессы отличаются.

**Ключевое понимание:** git-процесс — это **не техника**, а **коммуникация + автоматизация + доверие**. Главное — не process, а **why**.

---

## Мой git-процесс (от задачи до продакшена)

### Фаза 1: Постановка задачи

**Суть.** Задача → issue (Jira, GitHub Issues) с **jasper criteria** (acceptance criteria).

```
ISSUE: [ORDER-123] Добавить оплату заказа
Acceptance:
- Can confirm paid order
- Invalid payment → error
```

**Почему:** **clear definition of done**, no ambiguity.

---

### Фаза 2: Ветвление (Branching)

**Мой approach:** **GitHub Flow** (не git-flow для большинства).

```
main ──────────────────────────────▶
├── feature/ORDER-123-add-payment
├── fix/ORDER-124-payment-retry
└── refactor/ORDER-125-clean-repo
```

**Почему GitHub Flow:**
- **Simple** (main + feature).
- **Fast** (fast feedback).
- **Small teams**.

**Почему НЕ git-flow:**
- **Complex** (develop, release, hotfix branches).
- **Slow** (release cycles).
- **For large teams / frequent releases**.

---

### Фаза 3: Формат коммитов

**Мой format:** **Conventional Commits**.

```
feat(order): add payment confirmation
fix(order): handle invalid payment method
docs(readme): update setup
test(order): add payment unit tests
refactor(repo): simplify composer deps
```

**Почему Conventional Commits:**
- **Semantic versioning** (auto from commits).
- **Readable** changelog.
- **Standard** (team alignment).

**Почему НЕ free-form:**
- **Inconsistent** (every commit different).
- **Hard** to automate.

**Правила format:**

```
<type>(<scope>): <description>

[optional body]

[optional footer: BREAKING CHANGE]
```

**Types:**
- **feat** (new feature).
- **fix** (bugfix).
- **docs** (documentation).
- **style** (format, no logic).
- **refactor** (no behavior change).
- **test** (add/fix tests).
- **chore** (build, deps).

---

### Фаза 4: Pull Request (PR)

**Мой PR process:**

1. **Small PR** (≤ 400 lines, 1 concern).
2. **Clear description** (what, why, how).
3. **Linked issue** (#123).
4. **Checklist** (tests, docs, no debug).

**Почему small PR:**
- **Faster review**.
- **Easier to review**.
- **Less context switch**.

**Почему NOT giant PR:**
- **Review impossible**.
- **Merge risk**.

---

### Фаза 5: Code Review

**Мой approach:** **required approval** (1+ reviewers) before merge.

**Что смотрю в review:**

1. **Correctness** (logic right?).
2. **Testability** (testable?).
3. **Readability** (readable?).
4. **Consistency** (team conventions?).
5. **Security** (input validation?).

**Почему required review:**
- **Quality** (catch bugs).
- **Knowledge share**.
- **Standards**.

**Почему НЕ auto-merge:**
- **No human check**.
- **Risk**.

**Rules review:**

```
- Review within 24h
- Request changes if critical
- Approve if good
- Comment, don't block trivial
```

---

### Фаза 6: Автоматизация в CI

**Что в CI:**

1. **Lint** (PHPStan, CodeSniffer).
2. **Test** (PHPUnit).
3. **Format** (PHP-CS-Fixer).
4. **Security** (composer audit).

**Почему CI:**
- **Automated quality gate**.
- **Consistent** (not manual).
- **Fast feedback**.

---

### Фаза 7: Releas

**Мой approach:** **semantic versioning** + **release branch**.

```
main: v1.0.0 → v1.1.0
├── feature/* (development)
├── release/1.1.0 (freeze)
└── hotfix/* (emergency)
```

**Почему semantic versioning:**
- **Predictable** (semver).
- **CHANGELOG auto**.
- **Breaking changes** visible.

**Почему release branch:**
- **Freeze** (no new features).
- **QA**.
- **Deploy**.

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

## Анализ вопроса

Хороший, культурный вопрос, но я хочу сразу сделать **важную оговорку о предпосылке**: «хорошее ревью» — это **не checklist**, а **коммуникация + качество**. Главная проблема — **ревью как полиция** (поиск ошибок), а не **помощь автору** (улучшение кода).

## Что я считаю хорошим ревью

### 1. **Помощь, а не полиция**

**Почему:**
- **Author** хочет **улучшить код**, не чувствовать себя дураком.
- **Reviewer** — **mentor**, не **judge**.

**Как marking:**
- **Constructive** comments.
- **Why** > **what**.

```
// Плохо: "Wrong!"
// Хорошо: "I think this should use == instead of === because 
// user IDs come as strings from the API. What do you think?"
```

### 2. **Конструктивность**

**Почему:**
- **Каждое замечание** → **recommendation**.
- **Вопрос** → **discussion**.

```
// Плохо: "This is bad"
// Хорошо: "Consider extracting this logic into a service method
// to keep the controller thin. What's your take?"
```

### 3. **Prioritization**

**Почему:**
- **Critical** issues first.
- **Nitpicks** last.

## На что смотрю в первую очередь

### Уровень 1: Correctness (критично)

**Вопросы:**
- **Logic correct?**
- **Edge cases handled?**
- **Security issues?** (injection, validation)
- **Race conditions?**

```php
// CRITICAL: SQL injection
```

**Inline** (конкретный код):

**Thematic** (обсуждение):
```

> This could have a race condition. Should we use optimistic locking?
```

## Как поступаешь при разногласии

### 1. **Assume good faith**

**Почему:**
- **Author** — **expert** в своём коде.
- **Reviewer** — может **не понимать контекст**.

### 2. **Ask, don't tell**

**Почему:**
- **Вопрос** → **discussion**.
- **Директива** → **resistance**.

```
// Bad: "Change this"
// Good: "I'm not sure this handles [X]. Have you considered [Y]?"
```

### 3. **Escalate, don't argue**

**Почему:**
- **Спорит 10+ комментариев** → **bad**.
- **Escalate** to **tech lead** / **discussion**.

```
> 💬 Let's discuss this in the sync to avoid rabbit-holing. 
> I'll defer to your judgment on this one.
```

### 4. **Defer to author**

**Почему:**
- **Author** owns code.
- **Review** = suggestion, not command.

```
> 💬 Your call on this — I'd lean toward X, but I trust your judgment.
```

### 5. **Resolve offline**

**Почему:**
- **Comments thread** — **not for debate**.
- **Chat/voice** — **faster resolution**.

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

## Анализ вопроса

Хороший технический вопрос, но я хочу сразу сделать **важную оговорку**: `FORCE INDEX` — это **last resort tool**, а **не routine optimization**. Главная ошибка — **форсировать индекс**, когда planner его не выбрал, **без понимания почему**.

**Ключевое понимание:** planner (query optimizer) **умеет выбирать индексы лучше**, чем человек, **в 90% случаев**. `FORCE INDEX` — это **исключение**, когда planner **ошибся** (stale statistics, wrong estimate).

---

## Для чего FORCE INDEX

**Суть.** **Принудительно** заставить planner использовать конкретный индекс, **игнорируя** его оценку cost.

```sql
-- Force specific index
SELECT * FROM orders FORCE INDEX (idx_orders_created_at)
WHERE created_at > '2024-01-01';
```

**PostgreSQL:** `FORCE INDEX` — это **MySQL syntax**. **В PostgreSQL** аналог:
- **`SET enable_seqscan = off;`** (for testing).
- **Indexes** via planner (not force).
- **`pg_hint_plan`** extension (hints).

---

## Когда применять (реальные кейсы)

### Кейс 1: Wrong plan из-за stale statistics

**Суть.** Planner **неправильно оценил** rows → **wrong index**.

```sql
-- Planner picks seq scan (wrong estimate)
SELECT * FROM orders WHERE status = 'paid';

-- UPDATE statistics
ANALYZE orders;

-- If still wrong (rare), hint/test
SET enable_seqscan = off;
```

**Почему:** **fix statistics** > **force index**.

### Кейс 2: Multiple indexes, wrong choice

**Суть.** Planner выбрал **suboptimal** index.

```sql
-- 2 indexes: idx1, idx2
-- Planner picks idx1 (suboptimal for this query)
SELECT * FROM orders FORCE INDEX (idx2) WHERE ...;
```

**Почему:** **rare**, usually planner right.

### Кейс 3: Testing alternative plans

**Суть.** **Compare** plan B vs planner's choice.

```sql
-- Test: force scan off
SET enable_seqscan = off;
EXPLAIN ANALYZE SELECT ...;

-- vs normal
SET enable_seqscan = on;
EXPLAIN ANALYZE SELECT ...;
```

**Почему:** **explore** options, **not commit**.

---

## Типичные случаи применения

| Случай | FORCE INDEX? | Better approach |
|--------|--------------|-----------------|
| Stale statistics | ❌ | `ANALYZE table` |
| Wrong index choice | ⚠️ | Fix statistics first |
| Testing plan | ✅ | `enable_seqscan=off` |
| Missing index | ❌ | Add index |
| Rare query | ⚠️ | Per-session setting |

---

## Почему НЕ стоит форсировать (обычно)

### 1. **Planner > human (usually)**

**Почему:** planner учитывает **cost, selectivity, stats**. **Human** — **local optimum**.

### 2. **Stale stats = real problem**

**Почему:** **force index** маскирует **stale statistics**. **Fix root cause**.

### 3. **Fragile**

**Почему:** forced index **breaks** when data distribution changes.

### 4. **No maintenance**

**Почему:** **hint** = **hardcoded**, future queries break.

---

## Как делать правильно (вместо FORCE INDEX)

### 1. **EXPLAIN ANALYZE first**

**Суть.** **Understand** why planner's plan is slow.

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
-- See: Seq Scan vs Index Scan, rows estimate vs actual
```

### 2. **Update statistics**

**Суть.** `ANALYZE` fix wrong estimates.

```sql
ANALYZE orders;
ANALYZE orders (created_at);
```

### 3. **Add missing index**

**Суть.** If no index → add.

```sql
CREATE INDEX idx_orders_created ON orders (created_at);
```

### 4. **Query rewrite**

**Суть.** Sometimes rewrite helps more than index.

```sql
-- Bad: function in WHERE (no index)
WHERE lower(email) = 'x@y.com'

-- Good: expression index
CREATE INDEX idx_lower_email ON users (lower(email));
```

### 5. **Per-session hint (if truly needed)**

**Суть.** **Not hardcoded** in query.

```sql
-- Session-level (temporary)
SET enable_seqscan = off;
SELECT ...;
```

---

## PostgreSQL-specific approach

**PostgreSQL** doesn't have `FORCE INDEX`. **Tools:**

### 1. **`enable_*` settings**

```sql
SET enable_seqscan = off;        -- force index scan
SET enable_bitmapscan = off;     -- disable bitmap scan
SET random_page_cost = 1.1;      -- SSD tuning
```

**Почему:** **per-session**, **temporary**, **testable**.

### 2. **`pg_hint_plan` extension**

```sql
-- Hint in comment
/*+ IndexScan(orders idx_orders_created) */
SELECT * FROM orders WHERE created_at > '2024-01-01';
```

**Почему:** **explicit hint**, **controllable**.

### 3. **Partial indexes**

```sql
CREATE INDEX idx_paid_orders ON orders (created_at)
WHERE status = 'paid';
```

**Почему:** **targeted** index for specific query pattern.

---

## Trade-offs FORCE INDEX

| Плюс | Минус |
|------|-------|
| Quick fix for wrong plan | Masks root cause |
| Testing tool | Fragile (data changes) |
| Control specific query | Hardcoded, no maintenance |

---

## Подводные камни

1. **Не форсировать без EXPLAIN** (understand first).
2. **Не маскировать stale stats** (fix root).
3. **Не hardcode** (per-session).
4. **Planner usually right** (don't override blindly).
5. **Test before commit** (hint ≠ production).

---

## Итог

**`FORCE INDEX`** — **last resort** для **wrong planner plan**. **PostgreSQL** doesn't have it (use `enable_seqscan`, `pg_hint_plan`). **Better fix:** `ANALYZE` (stale stats), add index, rewrite query. **Применять:** только для **testing** or **rare wrong estimate**, **после EXPLAIN ANALYZE**.

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

## Анализ вопроса

Хороший вопрос, но я хочу сразу сделать **важную оговорку**: **`strict_types=1` НЕ замедляет выполнение runtime-кода вообще** — это **статический directive**, работающий **на этапе компиляции/пarsing'а**, а **не в runtime**.

**Ключевое понимание:** `strict_types` — это **compile-time** (parse-time) directive, который влияет **только на** **подстановку аргументов** в вызовах функций. **Runtime overhead** от него **стресово минимален** (фактически — ноль для большинства app).

---

## Что делает `strict_types` (и не делает)

**`strict_types=1`:**
- Влияет **на type coercion при вызове функций**.
- **Strict** typing: `int` ≠ `string`, даже если значение «сравнимо».
- **Влияет** на **declaration checks** (function args).

**`strict_types=0` (default):**
- **Weak** typing: `'42'` → `42` при необходимости.
- **Implicit** coercion.

**НЕ делает:**
- **Не влияет** на **переменные** в теле.
- **Не влияет** на **арифметику**.
- **Не влияет** на **operator precedence**.

---

## Реальный overhead

### Runtime overhead: **~0%**

**Почему:**
- **Type check** при вызове функции — **fast** (engine already tracks types).
- **No per-variable check**.
- **No reflection**.

**Пример:**

```php
strict_types = 1;

function sum(float $a, float $b): float {
    return $a + $b;
}

sum(1.0, 2.0);  // Fast check, no overhead
```

### Parse overhead: **negligible**

**Почему:**
- Directive **parsed once** per file.
- **Negligible** vs code execution.

---

## Откуда миф о «замедлении»

**Миф:** «strict_types замедляет код**.

**Реальность:**
- **Confusion** с **type checking libraries** (PHPStan, Psalm).
- **PHPStan/Psalm** (static analysis) **замедляют** **dev-time** (не runtime).
- **Runtime** — **fast**.

**Важно:** **Static analysis** (Stan) — **dev-time**, **не** runtime.

---

## Сравнение: runtime vs dev-time

| Aspect | `strict_types=1` | PHPStan/Psalm |
|--------|------------------|---------------|
| **Phase** | Runtime | Dev-time (analysis) |
| **Overhead** | ~0% | High (analysis) |
| **Purpose** | Type safety | Bug detection |

---

## Почему `strict_types` (причины использовать)

**1. Type safety** (no implicit coercion bugs).

**2. Catch bugs early** (`'42'` vs `42`).

**3. Consistency** (predictable behavior).

**Не:** performance.

---

## Реальные причины «замедления» (не strict_types)

**1. Reflection-heavy code** (not strict_types).

**2. Dynamic typing** (runtime type juggling).

**3. No JIT** (for CPU-heavy code).

---

## Итог

**`strict_types=1` НЕ замедляет runtime-код** — overhead ~0% (type check при вызове функций fast). **Миф** от **confusion** с static analysis (PHPStan dev-time). **Причины «замедления»:** reflection, dynamic typing, **не** strict_types.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

## Анализ вопроса

Хороший технический вопрос, но я хочу сразу сделать **важную оговорку о предпосылке**: **Doctrine ORM **поддерживает** составные первичные ключи** (composite primary keys) через `#[Id]` attribute на несколько полей. **Вопрос неверен** в части «не поддерживает» — Doctrine **умеет**, хотя и **с ограничениями**.

**Ключевое понимание:** Doctrine **поддерживает** composite PK, но **не рекомендуется** (best practice — surrogate key), и есть **ограничения** (ManyToMany, some relations).

---

## Doctrine и составные ключи

### Как это работает:

```php
#[ORM\Entity]
class OrderItem
{
    #[ORM\Id]
    #[ORM\Column(type: 'integer')]
    private int $orderId;
    
    #[ORM\Id]
    #[ORM\Column(type: 'integer')]
    private int $productId;
    
    // composite key: (orderId, productId)
}
```

**Или через composite ID class:**

```php
#[ORM\Entity]
class OrderItem
{
    #[ORM\Id]
    #[ORM\Embeddded(idClass: OrderItemId::class)]
    private OrderItemId $id;
}
```

---

## Почему composite PK проблематичен в Doctrine

**Doctrine поддерживает, но есть ограничения:**

### 1. **ManyToMany relations**

**Проблема:** Doctrine **не любит** composite keys в join tables.

```php
// problematic
#[ORM\ManyToMany]
private array $tags; // if tag has composite key
```

### 2. **Identifier as array**

**Проблема:** entity identifier becomes **array** (not scalar), complicates:
- **`find()`** (need array).
- **`remove()`** (need array).
- **Caching** (array key).

```php
// find with composite key
$em->find(OrderItem::class, [
    'orderId' => 1,
    'productId' => 2,
]);
```

### 3. **DQL limitations**

**Проблема:** some DQL operations **restrict** with composite keys.

### 4. **Caching (second-level)**

**Проблема:** **L2 cache** problematic with composite keys.

---

## Почему best practice — surrogate key

**Рекомендация DDD/Doctrine:** **single surrogate key** (`id`), even for association entities.

**Почему:**

### 1. **Simplicity**

```php
#[ORM\Entity]
class OrderItem
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    private int $id; // surrogate
    
    // business fields as unique constraint
    #[ORM\UniqueConstraint(name: "uniq_order_product")]
    #[ORM\Column(type: 'integer')]
    private int $orderId;
    
    #[ORM\Column(type: 'integer')]
    private int $productId;
}
```

**Почему:** single scalar ID, easy find/remove/caching.

### 2. **Stability**

**Суть:** composite key = **business logic** (changes = data migration). **Surrogate** = **immutable**.

### 3. **Relation simplicity**

**Суть:** no array identifiers in relations.

---

## Как живут в реальных проектах

### Pattern 1: Surrogate key + Unique constraint

**推荐 (best practice):**

```php
#[ORM\Entity]
class OrderItem
{
    #[ORM\Id]
    #[ORM\GeneratedValue]
    private ?int $id = null;
    
    #[ORM\ManyToOne]
    #[ORM\JoinColumn(nullable: false)]
    private Order $order;
    
    #[ORM\ManyToOne]
    #[ORM\JoinColumn(nullable: false)]
    private Product $product;
    
    #[ORM\Column]
    private int $quantity;
}
```

**Почему:** **use relations** (ManyToOne), **surrogate** PK, Doctrine handles join.

### Pattern 2: Composite key when truly needed

**Суть:** **association entities** (join tables) or **natural composite**.

```php
#[ORM\Entity]
class UserPermission
{
    #[ORM\Id]
    #[ORM\Column(type: 'string', length: 36)]
    private string $userId; // FK part 1
    
    #[ORM\Id]
    #[ORM\Column(type: 'string', length: 36)]
    private string $permissionId; // FK part 2
}
```

**Почему:** **pure association** (no other data), composite = natural key.

---

## Trade-offs composite vs surrogate

| Аспект | Composite Key | Surrogate Key |
|--------|---------------|---------------|
| **Simplicity** | ❌ complex | ✅ simple |
| **Relations** | ⚠️ limited | ✅ full |
| **Stability** | ❌ business change | ✅ immutable |
| **Caching** | ❌ problematic | ✅ works |
| **Semantics** | ✅ natural | ❌ arbitrary |

---

## Когда реально использовать composite

**Случаи:**

1. **Association entity** (manyToMany join) — **only association**.

2. **Natural composite key** (business rule, immutable).

3. **Legacy DB** (composite PK already exists).

**Не случаи:**

1. **Regular entity** (use surrogate).

2. **Entities с relations** (array ID issues).

3. **Frequently changing** keys.

---

## Практический совет

**Рекомендация:**
- **Default:** **surrogate key** (`id`).
- **Association entities:** composite **or** surrogate + relations.
- **Never:** composite for entities с complex relations.

**Почему:** Doctrine **optimizes** for single ID, **avoid** array identifiers.

---

## Итог

**Doctrine **поддерживает** composite PK** (через несколько `#[Id]`), но **не рекомендуется** из-за: array identifiers, limited relations, caching issues, DQL restrictions. **Best practice:** **surrogate key** + unique constraint/relations. **Composite:** только для association entities или immutable natural keys.

## Проблемы (в порядке приоритета)

### 🔴 Критические (security, data loss)

**1. SQL-инъекция — главная проблема**


**Почему критично:** `$id` подставляется прямо в SQL. **Полная уязвимость** (UNION-based, boolean-based).


**Fix:** prepared statements.

**2. Atomicity — нет транзакции**


**Почему критично:** partial state — «half-baked» transaction.

**3. No transaction isolation / idempotency**

**Почему:** повторный POST → двойной `UPDATE`, race condition.

**4. Нарушены все слои архитектуры**

**Это controller god object** — нарушает Single Responsibility и Clean Architecture.

**5. Raw PDO вместо Doctrine** (еслиDoctrine в проекте)

**6. Hardcoded business rules**

**Формула:**

```

Low cost → accept debt, pay later
```

```
- Impact: $1000 (chargeback)
```

**Почему:** **sustainable**, **no debt crisis**.

## Типовые сценарии выбора

### Сценарий 1: Fast-moving MVP (стартап)

**Стек:** **PHP (Laravel/Symfony) + PostgreSQL**

**Почему:**
- **Быстрая разработка** (готовые решения).
- **Маленькая команда**.
- **Time-to-market** важнее оптимизации.

### Сценарий 2: High-load / real-time

**Стек:** **Go или Java/Spring + PostgreSQL + Redis**

**Почему:**
- **Производительность** (concurrency).
- **Type safety** (Spring).
- **Кэш** (Redis).

### Сценарий 3: Data-heavy / ML

**Стек:** **Python (FastAPI/Django) + PostgreSQL**

**Почему:**
- **Data science экосистема**.
- **Быстрая интеграция** ML.

### Сценарий 4: Enterprise / large team

**Стек:** **Java/Spring Boot + PostgreSQL + Kubernetes**

**Почему:**
- **Стандарты** (big teams).
- **Tooling** (Spring ecosystem).
- **Supportability**.

## Что бы я выбрал для «среднего» проекта (пример защиты)

**Стек:** **Symfony + PostgreSQL + Doctrine ORM**

**Аргументы для команды:**

**1. Зрелость и поддержка.**
- **Готовые решения** (не изобретаем велосипед).
- **Community**, **документация**.

**2. Продуктивность.**
- **DI, Messenger, events** из коробки.
- **Profiler** для оптимизации.

**3. Масштабируемость.**
- **PostgreSQL** (extensions, partitioning).
- **Doctrine** (repository pattern).

**4. Поддерживаемость.**
- **Паттерны** (Clean Architecture).
- **Стандарты** (легко найти разработчиков).

**5. Trade-offs (честно).**
- **Плюсы:** скорость разработки, зрелость.
- **Минусы:** overhead для ultra-high-load (но это не our case).
