## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

Современные версии PHP, начиная с PHP 8.0, предлагают множество новых возможностей и улучшений, которые помогают писать более чистый, надёжный и эффективный код. Вот некоторые из наиболее значимых нововведений:

1. **Тип возврата `never`**. Этот тип указывает, что функция не возвращает никакого значения и никогда не завершается нормально, например, из-за выброса исключения. Это помогает улучшить статический анализ кода.
```php
function handleError(): never {
    throw new Exception('An error occurred');
}
```

2. **Union и Intersection типы**. Позволяют указывать несколько возможных типов для переменной или возвращаемого значения функции, что делает код более выразительным и гибким.
```php
function getData(): array|null {
    // ...
}

function processData(array|string $data) {
    // ...
}
```

3. **Атрибуты (Attributes)**. Позволяют добавлять метаданные к классам, методам и свойствам, что полезно для различных целей, включая валидацию, сериализацию и т. д.
```php
#[Attribute]
class MyAttribute {
    public function __construct(public string $value) {}
}

class MyClass {
    #[MyAttribute('example')]
    public function myMethod() {}
}
```

4. **Строгие типы параметров функций (`strict types`)**. Упрощают работу с типами параметров, делая код более предсказуемым и надёжным.
```php
declare(strict_types=1);

function add(int $a, int $b): int {
    return $a + $b;
}
```

5. **Nullsafe-операторы (`?->` и `?.`)**. Позволяют безопасно работать с потенциально нулевыми значениями, избегая ошибок `NullPointerException`.
```php
$result = $user?->getAddress()?->getCity();
```

6. **Match выражения**. Предоставляют более краткий и выразительный способ написания сложных условных конструкций.
```php
$action = match ($input) {
    'start' => 'Begin the process',
    'stop' => 'End the process',
    default => 'Invalid input',
};
```

Эти возможности помогают сделать код более читаемым, безопасным и поддерживаемым, что является ключевым для разработки качественных веб-приложений.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

### Система типов в PHP

Система типов в PHP является динамической и слабой, что означает, что типы переменных определяются автоматически во время выполнения программы, и преобразования типов могут происходить неявно. Однако PHP также предоставляет возможности для более строгой типизации, чтобы повысить надёжность кода.

#### `declare(strict_types=1)`

Директива `strict_types` позволяет включить строгий режим типизации для параметров функций и возвращаемых значений. В строгом режиме PHP будет выдавать ошибку, если типы не соответствуют ожидаемым.

**Пример:**
```php
declare(strict_types=1);

function add(int $a, int $b): int {
    return $a + $b;
}

echo add(1, '2'); // TypeError: Argument 2 passed to add() must be of the type int, string given
```

Без `strict_types` PHP автоматически преобразует строку `'2'` в целое число `2`, и функция выполнится без ошибок, но с `strict_types` произойдёт ошибка типа.

#### Приведения типов

PHP поддерживает неявное и явное приведение типов. Неявное приведение происходит автоматически, когда контекст требует определённого типа данных. Явное приведение выполняется с помощью приведения типов.

**Неявное приведение:**
```php
$num = 42;
$str = 'Hello, ' . $num; // $str становится 'Hello, 42'
```

**Явное приведение:**
```php
$num = (int) '42'; // $num становится 42
```

#### Типичные ловушки

1. **Сравнение строк и чисел:**
   ```php
   if ('0' == 0) { // true
       echo 'Это верно';
   }
   ```
   Это может привести к неожиданным результатам, если не учитывать неявное приведение типов.

2. **Логические операции:**
   ```php
   var_dump((bool) 'false'); // true
   ```
   Строка `'false'` при приведении к булевому типу будет `true`, так как она не пустая.

3. **Сложение строк и чисел:**
   ```php
   $result = '10' + '5'; // $result становится 15
   ```
   Это может быть неочевидно, если не следить за типами данных.

#### Где типизация спасает

Строгая типизация помогает предотвратить ошибки, связанные с неправильным использованием типов данных. Например, если функция ожидает целое число, а получает строку, строгий режим выдаст ошибку, что поможет обнаружить проблему на ранней стадии.

**Пример:**
```php
declare(strict_types=1);

function divide(int $a, int $b): float {
    return $a / $b;
}

echo divide(10, '2'); // TypeError: Argument 2 passed to divide() must be of the type int, string given
```

#### Где типизация удивляет

Слабая типизация может привести к неожиданным результатам, особенно при работе со строками и числами. Например, сравнение строки и числа может дать неожиданный результат из-за неявного приведения типов.

**Пример:**
```php
if ('10' > 2) { // true
    echo 'Строка больше числа';
}
```

**Кандидат:**

### Проектирование работы с исключениями в PHP-приложении

#### Иерархии исключений

При проектировании работы с исключениями важно создать собственную иерархию исключений, чтобы чётко разграничивать различные типы ошибок. Это позволяет более гибко обрабатывать исключения в зависимости от их типа.

**Пример иерархии:**
```php
namespace App\Exceptions;

class AppException extends \Exception {}

class ValidationException extends AppException {}

class DatabaseException extends AppException {}

class NotFoundException extends AppException {}
```

#### Оборачивание чужих исключений

При использовании сторонних библиотек или фреймворков часто возникает необходимость оборачивать исключения, чтобы они соответствовали вашей иерархии исключений. Это помогает сохранить консистентность обработки ошибок в приложении.

**Пример оборачивания исключений:**
```php
try {
    // Код, который может вызвать исключение от сторонней библиотеки
} catch (\SomeLibrary\Exception $e) {
    throw new AppException('Ошибка при работе с библиотекой', 0, $e);
}
```

#### Контракт метода

Контракт метода определяет, какие исключения может выбросить метод. Это важная часть документации метода, которая помогает разработчикам понимать, как правильно обрабатывать ошибки.

**Пример контракта метода:**
```php
/**
 * @throws ValidationException Если данные не прошли валидацию
 * @throws DatabaseException Если произошла ошибка при работе с базой данных
 */
public function processData(array $data): void {
    // Логика метода
}
```

#### Антипаттерны

1. **Обработка всех исключений одним блоком `catch`:**
   ```php
   try {
       // Код
   } catch (\Exception $e) {
       echo 'Произошла ошибка';
   }
   ```
   Это может привести к тому, что важные ошибки будут обрабатываться некорректно.

2. **Отсутствие обработки исключений:**
   ```php
   function dangerousFunction() {
       // Код, который может вызвать исключение
   }
   ```
   Отсутствие обработки может привести к аварийному завершению работы приложения.

3. **Использование исключений для управления потоком выполнения:**
   ```php
   try {
       while (true) {
           throw new \Exception('Повторить');
       }
   } catch (\Exception $e) {
       // Логика повторной попытки
   }
   ```
   Это нарушает принцип использования исключений только для обработки исключительных ситуаций.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

Чаще всего в реальном коде нарушается **принцип единственной ответственности (Single Responsibility Principle, SRP)**. Это происходит из-за того, что со временем код может усложняться и обрастать новыми функциями, в результате чего классы начинают выполнять несколько задач одновременно.

**Пример нарушения SRP:**

Предположим, у нас есть класс `User`, который отвечает как за аутентификацию пользователя, так и за работу с его профилем в базе данных.

```php
class User {
    public function authenticate(string $username, string $password): bool {
        // Логика аутентификации
    }

    public function save(): void {
        // Логика сохранения пользователя в базе данных
    }
}
```

В этом примере класс `User` имеет две ответственности:
1. Аутентификация пользователя.
2. Работа с базой данных.

Это нарушает принцип SRP, так как класс должен иметь только одну ответственность.

**Рефакторинг:**

Чтобы исправить это нарушение, мы можем разделить класс `User` на два отдельных класса: `UserAuthenticator` и `UserRepository`.

```php
interface UserAuthenticator {
    public function authenticate(string $username, string $password): bool;
}

class UserAuthenticatorImpl implements UserAuthenticator {
    public function authenticate(string $username, string $password): bool {
        // Логика аутентификации
    }
}

interface UserRepository {
    public function save(User $user): void;
}

class UserRepositoryImpl implements UserRepository {
    public function save(User $user): void {
        // Логика сохранения пользователя в базе данных
    }
}
```

Теперь у нас есть два отдельных класса, каждый из которых имеет свою единственную ответственность:
- `UserAuthenticator` отвечает за аутентификацию пользователя.
- `UserRepository` отвечает за работу с базой данных.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Принципы SOLID — это рекомендации, а не строгие правила. В некоторых ситуациях может быть оправдано их нарушение, если это приведёт к более простому, понятному и поддерживаемому коду. Однако такие случаи должны быть тщательно взвешены и обоснованы.

**Пример оправданного нарушения принципа инверсии зависимостей (Dependency Inversion Principle, DIP):**

Предположим, у вас есть небольшое приложение, где добавление новых зависимостей через интерфейсы или абстрактные классы приведёт к излишней сложности и увеличит количество кода. В таком случае можно напрямую зависеть от конкретных реализаций, чтобы упростить структуру приложения.

**Пример:**
```php
class EmailService {
    public function sendEmail(string $to, string $subject, string $body): void {
        // Логика отправки email
    }
}

class UserRegistration {
    private EmailService $emailService;

    public function __construct(EmailService $emailService) {
        $this->emailService = $emailService;
    }

    public function registerUser(string $email): void {
        // Логика регистрации пользователя
        $this->emailService->sendEmail($email, 'Welcome', 'Welcome to our service!');
    }
}
```

В этом примере `UserRegistration` напрямую зависит от `EmailService`. Хотя это нарушает принцип инверсии зависимостей, в контексте небольшого приложения это может быть оправдано, чтобы избежать излишней сложности.

Однако в более крупных и сложных системах лучше придерживаться принципов SOLID для обеспечения гибкости, тестируемости и поддерживаемости кода.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Принцип открытости/закрытости (OCP) можно реализовать не только через наследование, но и с помощью других подходов. Вот несколько примеров:

1. **Использование интерфейсов и абстрактных классов:** вместо прямого наследования можно определить интерфейсы или абстрактные классы, которые задают контракт для поведения. Реализации этих интерфейсов могут быть изменены или расширены без модификации исходного кода.

   **Пример:**
   ```php
   interface Shape {
       public function getArea(): float;
   }

   class Circle implements Shape {
       private float $radius;

       public function __construct(float $radius) {
           $this->radius = $radius;
       }

       public function getArea(): float {
           return pi() * $this->radius * $this->radius;
       }
   }
   ```

2. **Шаблоны проектирования:** некоторые шаблоны проектирования, такие как стратегия, декоратор и посетитель, позволяют добавлять новое поведение без изменения существующего кода.

   **Пример с использованием шаблона стратегия:**
   ```php
   interface SortStrategy {
       public function sort(array &$data): void;
   }

   class QuickSort implements SortStrategy {
       public function sort(array &$data): void {
           // Реализация быстрой сортировки
       }
   }

   class Sorter {
       private SortStrategy $strategy;

       public function __construct(SortStrategy $strategy) {
           $this->strategy = $strategy;
       }

       public function sort(array &$data): void {
           $this->strategy->sort($data);
       }
   }
   ```

3. **Композиция и агрегация:** вместо наследования можно использовать композицию или агрегацию, чтобы объединить несколько объектов и создать новое поведение.

   **Пример:**
   ```php
   class Report {
       private array $data;
       private ReportFormatter $formatter;

       public function __construct(array $data, ReportFormatter $formatter) {
           $this->data = $data;
           $this->formatter = $formatter;
       }

       public function generate(): string {
           return $this->formatter->format($this->data);
       }
   }
   ```

4. **Использование конфигураций и плагинов:** можно разработать систему так, чтобы новое поведение добавлялось через конфигурации или плагины, без изменения исходного кода.

   **Пример:**
   ```php
   class PluginManager {
       private array $plugins = [];

       public function registerPlugin(Plugin $plugin): void {
           $this->plugins[] = $plugin;
       }

       public function executePlugins(): void {
           foreach ($this->plugins as $plugin) {
               $plugin->execute();
           }
       }
   }
   ```

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Нет, принцип единственной ответственности (SRP) не применяется только к классам. Хотя чаще всего его обсуждают в контексте объектно-ориентированного программирования и классов, этот принцип может быть применён и к другим сущностям в программировании, таким как модули, функции, микросервисы и даже целые системы.

Суть SRP заключается в том, что каждый модуль или компонент должен иметь только одну причину для изменения, то есть отвечать за одну конкретную задачу или ответственность. Это помогает сделать код более понятным, тестируемым и поддерживаемым.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

**Контейнер внедрения зависимостей (DI-контейнер) в Symfony** — это компонент, который управляет созданием объектов и их зависимостями. Он позволяет разработчикам избегать жёсткой связи между компонентами приложения, делая код более гибким и тестируемым.

### Компиляция контейнера

При компиляции контейнера Symfony анализирует конфигурацию и определения сервисов, чтобы создать оптимизированный PHP-код, который будет использоваться для создания объектов. Этот процесс включает в себя:

1. **Анализ конфигурации:** контейнер считывает определения сервисов из конфигурационных файлов (например, `services.yaml`).

### Autowiring

Autowiring — это механизм, который позволяет контейнеру автоматически связывать зависимости сервисов на основе их типов. Это избавляет от необходимости вручную указывать все зависимости в конфигурационных файлах.

Когда Symfony встречает новый сервис, он анализирует его конструктор и методы установки, чтобы определить, какие зависимости требуются. Затем контейнер ищет соответствующие сервисы в своей конфигурации и автоматически связывает их.

1. **Поиск определения сервиса:** контейнер ищет определение запрашиваемого сервиса в своей конфигурации.

В Symfony контроль доступа организован через систему безопасности, которая включает в себя аутентификацию, авторизацию и управление доступом на основе ролей и voters.

### Аутентификация

Аутентификация в Symfony осуществляется с помощью системы пользователей и их паролей, которые обычно хранятся в базе данных. Symfony использует компонент Security для управления процессом аутентификации. Этот компонент проверяет учётные данные пользователя и, если они верны, создаёт токен безопасности, который содержит информацию о пользователе и его ролях.

### Роли

Роли в Symfony — это способ определения прав доступа для пользователей. Они представляют собой строки, которые указывают на определённые права или разрешения. Например, роль `ROLE_ADMIN` может предоставлять права на управление пользователями, а роль `ROLE_USER` — на просмотр определённых страниц.

Роли используются для контроля доступа к контроллерам, маршрутам и другим ресурсам. Например, можно настроить доступ к определённому маршруту так, чтобы его могли просматривать только пользователи с ролью `ROLE_ADMIN`.

### Voters

Voters в Symfony — это более гибкий механизм контроля доступа, который позволяет определять права доступа на основе более сложных условий. Voter — это класс, который реализует интерфейс `VoterInterface` и определяет, имеет ли пользователь право на выполнение определённого действия.

Voters могут использоваться в случаях, когда необходимо реализовать более сложные правила доступа, которые не могут быть описаны с помощью ролей. Например, voter может проверять, является ли пользователь владельцем определённого объекта, или имеет ли он право на редактирование определённого ресурса.

### Выбор между voter и ролями

Выбор между voter и ролями зависит от сложности правил доступа и гибкости, которую необходимо обеспечить.

- **Роли** подходят для простых случаев, когда права доступа можно описать с помощью нескольких строк. Например, если необходимо предоставить доступ к определённому разделу сайта только администраторам, то достаточно использовать роль `ROLE_ADMIN`.
- **Voters** следует использовать в более сложных случаях, когда необходимо учитывать дополнительные условия, такие как владение объектом или права на редактирование. Voters позволяют реализовать более гибкие и настраиваемые правила доступа.

В некоторых случаях можно комбинировать использование ролей и voters для достижения оптимального баланса между простотой и гибкостью.

4. **Обеспечение атомарности транзакций.** Ограничения целостности помогают гарантировать, что все операции в рамках транзакции будут выполнены успешно или отменены в случае ошибки, обеспечивая согласованность данных.

- **В многопользовательских системах.** Ограничения помогают предотвратить конфликты и обеспечить согласованность данных при одновременном доступе нескольких пользователей.

**Кандидат:**

**Value Object и Entity в DDD**

В Domain-Driven Design (DDD) Value Object и Entity являются двумя ключевыми концепциями, которые отличаются по своему назначению и свойствам.

- **Entity** — это объект, который имеет идентификатор и уникальный ключ, позволяющий отличать его от других объектов. Entity отслеживает изменения своего состояния и может быть связан с другими объектами. Примеры Entity могут включать пользователя, заказ, продукт и т. д.

- **Value Object** — это неизменяемый объект, который описывает характеристики или атрибуты сущности или другого Value Object. Value Object не имеет идентификатора и определяется своими свойствами. Примеры Value Object могут включать адрес, цвет, сумму и т. д.

**Как решить, к чему отнести концепцию домена**

Чтобы определить, является ли концепция домена Entity или Value Object, нужно задать себе следующие вопросы:

- Имеет ли концепция уникальный идентификатор, который отличает её от других объектов? Если да, то это скорее всего Entity.
- Изменяется ли состояние концепции со временем? Если да, то это также указывает на Entity.
- Определяется ли концепция своими свойствами, и не имеет ли она уникального идентификатора? Если да, то это Value Object.

**Единый язык (Ubiquitous Language)**

Ubiquitous Language — это общий язык, который используется всеми участниками проекта для описания домена. Он включает термины, определения и концепции, которые понятны как разработчикам, так и бизнес-аналитикам.

**Влияние единого языка на код**

Ubiquitous Language влияет на код следующим образом:

- Обеспечивает единое понимание домена всеми участниками проекта.
- Способствует созданию более чистого и понятного кода, который легче поддерживать и расширять.
- Помогает избежать недоразумений и ошибок при реализации бизнес-логики.

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

Когда два пользователя одновременно пытаются изменить одну и ту же запись в базе данных, могут возникнуть следующие проблемы:

1. **Потеря данных (data loss)**: изменения одного пользователя могут быть перезаписаны изменениями другого пользователя, что приведёт к потере части данных.
2. **Несогласованность данных (data inconsistency)**: данные могут оказаться в некорректном состоянии, если оба пользователя вносят взаимоисключающие изменения.
3. **Конфликты параллельного доступа (concurrency conflicts)**: системы управления базами данных (СУБД) могут блокировать записи для предотвращения одновременного доступа, что может привести к задержкам и снижению производительности.

Для защиты от этих проблем используются различные стратегии управления параллелизмом:

1. **Оптимистическая блокировка (optimistic locking)**:
   - **Описание**: предполагается, что конфликты возникают редко, и каждый раз при изменении данных проверяется, не были ли они изменены другим процессом. Если изменения обнаружены, транзакция откатывается, и предпринимается попытка повторного выполнения.
   - **Преимущества**: минимизация блокировок и повышение производительности в условиях низкой конкуренции.
   - **Недостатки**: риск потери данных и необходимость повторных попыток выполнения транзакций при конфликтах.
   - **Когда использовать**: в системах с низкой вероятностью одновременного доступа к данным.

2. **Пессимистическая блокировка (pessimistic locking)**:
   - **Описание**: предполагается, что конфликты вероятны, и перед изменением данных процесс блокирует их, предотвращая доступ других процессов. После завершения операции блокировка снимается.
   - **Преимущества**: гарантированная защита от конфликтов и несогласованности данных.
   - **Недостатки**: возможное снижение производительности из-за блокировок и риск взаимоблокировок (deadlocks).
   - **Когда использовать**: в системах с высокой вероятностью одновременного доступа к данным и необходимостью строгой согласованности.

3. **Версионная блокировка (versioning)**:
   - **Описание**: каждый агрегат имеет версию, которая увеличивается при каждом изменении. При попытке обновления проверяется текущая версия, и если она не совпадает с ожидаемой, транзакция откатывается.
   - **Преимущества**: эффективное управление параллелизмом и предотвращение потери данных.
   - **Недостатки**: необходимость реализации механизма версионного контроля и возможные сложности при работе с сложными структурами данных.
   - **Когда использовать**: в системах, где важна согласованность данных и требуется эффективное управление параллельными изменениями.

Выбор стратегии зависит от требований к производительности, согласованности данных и вероятности одновременного доступа в конкретной системе.

- Обсудить изменения и получить обратную связь.

### 4. Ревью

Ревью кода — важный этап для обеспечения качества и соответствия стандартам проекта. Во время ревью проверяются:

#[ORM\Entity]
class User

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

1. **Зависимость от инфраструктуры.** Сущности в DDD должны быть независимы от инфраструктуры и слоёв сохраняемости данных. В данном случае сущность `User` зависит от `EntityManagerInterface`, что нарушает принцип разделения ответственности и затрудняет тестирование.
2. **Нарушение принципа единственной ответственности (SRP).** Метод `changeEmail` не только изменяет email, но и выполняет сохранение изменений в базе данных через `flush`. Это нарушает принцип SRP, так как метод выполняет две задачи.
