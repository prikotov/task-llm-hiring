# Модели: исследование чистых способностей к кодингу

## Цель workspace

Здесь мы выясняем **чистые** способности LLM к программированию — то, что модель
знает «из базы» (из обучения), без помощи окружения:

- **без харнеса** — никаких агентных циклов, инструментов, файловых операций;
- **без подсказок** — никаких system prompt, few-shot примеров, наводок;
- один сырой user-запрос → один ответ модели.

## Git-процесс (важно)

Любые правки попадают в `main` **только через pull request**:
ветка → коммиты → push → PR → ревью → мерж. Прямые коммиты и пуш
в `main` запрещены всегда и всем — включая правки, сделанные
ассистентом (ZCode): ассистент открывает PR, а не коммитит в `main`.
Ветку для PR отделяем от актуального `origin/main`, один PR — одна тема.

**Мерж — только после явного апрува владельца** (Дмитрий): ассистент
открывает PR, при необходимости прогоняет проверки и останавливается —
ждёт одобрения. Нажимать merge (сам или через gh) без прямого подтверждения
владельца в чате или на GitHub ассистенту запрещено; «молчание» или
автономный режим апрувом не считаются. Правило с 2026-10-14; технически
на `main` уже стоит ruleset «только через pull request» (без force-push
и удаления ветки) — требование апрува держим этой конвенцией, потому что
solo-репо не может требовать аппрув второго человека у PR владельца.

## Сервер моделей

Все модели берём с ollama на внутреннем сервере (адрес — env
`OLLAMA_BASE_URL`, локальное значение — в `.env.local`, см. следующую
секцию):

- список: `curl "$OLLAMA_BASE_URL/api/tags"`
- детали: `curl "$OLLAMA_BASE_URL/api/show" -d '{"name":"<тег>"}'`
- генерация: `curl "$OLLAMA_BASE_URL/api/generate"` (или `/api/chat`)

Локальный ollama этой машины для тестов **не используется**
(позже `gemma4:e2b` была скачана на сервер и включена в набор).

## Окружение запусков (env, вне git)

Скрипты не содержат внутренних адресов, путей и ID — всё берётся из env
(в git только нейтральные дефолты; полный список переменных — README,
«Быстрый старт»). Локальные значения — `.env.local` в корне workspace:
в git не попадает (шаблон — `.env.local.example`), скрипты `interview/`
подхватывают его при старте автоматически, переменные из профиля шелла
главнее. Какие бывают переменные:

- `OLLAMA_BASE_URL` — сервер моделей (`runner.py`, `score.py`,
  `embed_compare.py`);
- `MODELS_RU_ENV` — путь к внешнему env-файлу с ключами облаков
  (`runner_ru_cloud.py`): `GIGACHAT_AUTHORIZATION_KEY`,
  `YANDEXFM_API_KEY`, `DEEPSEEK_API_KEY`;
- `YANDEXFM_FOLDER_ID` — ID каталога Яндекса;
- `OPENROUTER_KEY_FILE`, `OPENROUTER_PROXY_FILE` (или `OPENROUTER_PROXY` —
  прямой адрес прокси).

Сами ключи в `.env.local` не лежат — только пути к файлам с ними (файлы
вне workspace, не шарить). При незаданной переменной скрипт падает
с подсказкой, какую переменную задать.

## Структура

- Папки моделей лежат в `models/`: одна папка = одна уникальная
  модель (по дайджесту весов).
- Имя папки = ollama-тег, где `:` и `/` заменены на `-`
  (пример: `huihui_ai/Qwen3.8-abliterated:latest` →
  `huihui_ai-Qwen3.8-abliterated-latest`).
- Если одни и те же веса лежат под разными тегами — одна папка,
  оба тега перечислены в её `model.md` (пример: `qwen3.8/` для
  `qwen3.8:27b` и `qwen3.8:latest`).
- Внутри папки модели — `model.md` (характеристики и статус) и
  **все результаты** по каждой роли; внутри роли — по этапам:
  - `<роль>/interview/run-XX/` — собесы (этап 1): `session.json`
    (messages, thinking, тайминги, условия серии) + `transcript.md`;
  - `<роль>/interview/scorecard.md` — судейский свод по модели;
  - `<роль>/interview/judgments/<судья>/<run>.json` — вердикты внешних судей
    (clef, clef-flash, glm-5.3-flash-iso…), рядом `judgments/tasks/` —
    входные пары вопрос-ответ для воспроизводимости;
  - `<роль>/interview/judgments/judges-<run>.csv` — сырые данные всех судей
    по ответам (для анализа кодом);
  - `<роль>/interview/judgments/COMPARE.md` — резюме судейства этой модели
    со ссылкой на CSV;
  - `<роль>/test-assignment/run-XX/` — тестовое задание (этап 2):
    `solution/` (полный код решения), `pi-session/` (JSONL-след
    агентной сессии), `pi-run.log`, `diff.patch`, `run.json` (условия),
    `check.json` (чекер), `metrics.json` (качество кода; сырые выводы
    инструментов — в `metrics-raw/`),
    `session-profile.md`, `summary.md`, `report.html` (визуальный отчёт
    прогона — дашборд показателей), `scorecard.md`, `judge-glm.md`
    (ярус 2).
- `interview/` — только методология собеседований (этап 1): blueprint,
  вопросники ролей, рубрики, скрипты (`runner.py`, `score.py`, `judge_glm.py`).
  Никаких результатов.
- `test-assignment/` — методология тестового задания (этап 2): параллельный
  независимый этап отбора, не часть интервью. `backend/billing/` — задание
  (TASK.md, скелет, чекер, судьи, README), `original.md` — исходное задание
  до адаптации под TasK. Никаких результатов.
- `reports/` — кросс-модельные сводные отчёты и агрегаты
  (`judges-all.csv` — все вердикты всех судей, `COMPARE-judges.md`,
  `AUDIT-glm-flash.md`, будущий `REPORT.md` по моделям).
- Embedding-модели не тестируются и папок не получают
  (`bge-m3`, `mxbai-embed-large`, `nomic-embed-text-v2-moe`,
  `jeffh/intfloat-multilingual-e5-large-instruct`) — но используются
  как инструмент: `interview/embed_compare.py` (близость к SOTA-эталону,
  выводы — `reports/EMBEDDINGS-experiment.md`; рабочий эмбеддер — bge-m3).

## Правила тестирования (важно)

1. Запрос к модели — единый сырой промпт через API сервера моделей, без system-сообщения
   и без инструментов. Прямой вызов API предпочтительнее `ollama run`,
   чтобы ничего лишнего не подмешивалось.
2. Никаких уточняющих диалогов, ретраев «до правильного ответа» и правок промпта
   под конкретную модель — сравниваем базовые способности, а не умение вести диалог.
3. Параметры генерации — дефолтные модели, если для теста не оговорено иное.
4. Результаты и наблюдения по каждой модели фиксируем в её папке.
5. **Судья яруса 2 (GLM-5.3-Flash) запускается ТОЛЬКО скриптом
   `interview/judge_glm.py`** — он вызывает `pi -p --no-session --model
   glm-5.3-flash` по подписке Z.AI (изолированный запуск на каждый ответ,
   проверки фактов кодом через bash: php 8.5, docker psql). ЗАПРЕЩЕНО:
   судить сабагентами Agent tool (наследуют модель сессии GLM-5.3 и
   сжигают квоту подписки) и через OpenRouter (платные токены).

## Методика: тех-собесы по ролям

Основной формат — **собеседование на роль** (подробно: `interview/blueprint.md`):

- один собес = один чат, контекст только `messages` (без system prompt,
  файлов, инструментов);
- собесы по ролям проекта TasK: `backend` (бэкендер), `architect`,
  `frontend`, `devops`, `qa` (тестировщик), `analyst`, `product`,
  `techwriter`, `designer` — вопросник каждой роли в
  `interview/roles/<роль>/questions.json`; далее можно добавить
  teamlead по тому же шаблону;
- **версионирование вопросников**: `questions.json` — объект
  `{"version": N, "questions": [...]}`; при изменении набора вопросов
  поднимаем version и сохраняем старую версию рядом как
  `questions.vN.json` (пример: `questions.v1.json` — 32 вопроса без
  финальной секции). Раннеры пишут версию в `session.json` поле
  `"questionnaire"`; исторические сессии проштампованы ретроактивно
  (v1: qwen3.8 run-01–10, ornith-35b run-01–16, huihui/orcarouter
  run-01–05, Opus run-01; v2: остальные). В отчёте версии видны
  в таблице результатов (плашка «вопросник v1») и колонке §9;
- **вопросы на знания и остальные**: у каждого вопроса поле
  `knowledge` (PHP/ООП/Symfony/Doctrine/PostgreSQL/DDD/архитектура/
  тесты/конкурентность/git/провокации/код-ревью = true; разминка,
  работа с задачами, процесс, финал = false; уточнения наследуют
  вопрос). Итоговые баллы (clef и судья) и проценты галлюцинаций в
  отчёте считаются ТОЛЬКО по вопросам на знания (30 ответов из 41); судья
  яруса 2 (`judge_glm.py`) по умолчанию тоже гоняет только их;
- вопросы открытые, скриптованные, одинаковые для всех моделей и прогонов;
  покрывают стек TasK: PHP 8, Symfony, Doctrine, PostgreSQL, DDD, чистая
  архитектура, фронтенд (Bootstrap/Stimulus), тестирование, конкурентность,
  git, работа с задачами (постановка, следование, отчёт);
- у всех ролей есть follow-up'ы (фиксированные углубления), провокации
  (вопросы с ложной предпосылкой — проверка признания незнания) и
  кейсы/мини-код-ревью (контекст внутри вопроса);
- кастомные конвенции TasK (naming, `save()` без `flush()` и т.п.) как
  знание не спрашиваем — их нет в весах моделей; но **врождённые
  предпочтения моделей наблюдаем** через датчики (`interview/conventions-probe.md`):
  тестовое задание + код в ответах собеса → вывод, что писать в конвенции
  проекта, а что «и так общее»;
- судья — ZCode, оценивает по карточкам эталонов
  (`interview/rubrics/<роль>/<ID>.md`), шкала 0–4, две оси: «что ответил»
  и «как ответил»; карточки ревьюит владелец;
- устойчивость: 5 прогонов на модель, каждый с нуля, seed не фиксируется;
  сравнивается постоянство ответов и разброс баллов;
- KV-кэш ollama — двумя уровнями: кэш сессии включён (`keep_alive: 10m`
  внутри собеса, транспортная оптимизация), кэш прогонов выключен
  (выгрузка модели до и после каждого прогона — собесы изолированы);
- запуск: `python3 interview/runner.py --questions
  interview/roles/<роль>/questions.json --model <тег> --runs 5`
  (роль и пути определяются автоматически);
  транскрипты — `models/<model>/<роль>/interview/run-XX/` (transcript.md + session.json),
  свод — `<model>/<роль>/interview/scorecard.md`, сравнение моделей — `REPORT.md`.

## Облачные модели через OpenRouter

Кроме локальных (ollama), облачные модели ходят на собесы через OpenRouter
(сильные модели — сравнение потолка):

- запуск: `interview/runner_openrouter.py` — протокол тот же (один чат,
  только messages, без system prompt); reasoning effort задаётся явно,
  стандарт серии — `low` (сравнимо с think-off локальных);
- доступ из домашней сети только через прокси (WAF OpenRouter режет прямой
  доступ): ключ и адрес прокси — через env `OPENROUTER_KEY_FILE` /
  `OPENROUTER_PROXY_FILE` (сами файлы вне workspace, не шарить; локальные
  пути — в `.env.local`);
- папка модели — слаг OpenRouter с `/` → `-` (пример: `openai-gpt-6-luna/`),
  внутри те же `<роль>/interview/run-XX/` и `model.md`;
- каждая платная операция пишется в журнал `reports/openrouter-spend.csv`
  (модель, цель, запросы, токены, стоимость) — сверяться перед прогонами;
- у ключа дневной лимит: остаток смотреть `GET /api/v1/auth/key`
  (поле `limit_remaining`);
- decision-судьи OpenRouter (Jev, облачный clef) — `interview/judge_openrouter.py`, скрипт deprecated (пробный путь, не развивается; если нужны облачные decision-модели — поддержку провайдеров делаем в `score.py`);
  выводы по ним: `reports/COMPARE-jev.md` (локальный clef не хуже, траты
  не обоснованы).

## Облачные модели через родные API (Сбер, Яндекс, DeepSeek)

- запуск: `interview/runner_ru_cloud.py` (`--provider gigachat --model GigaChat-2-Max`
  или `--provider gigachat --model GigaChat-3-Ultra`, или `--provider yandexfm`,
  или `--provider deepseek --model deepseek-flash`);
  протокол собеса тот же;
- ключи не копируем в workspace: раннер читает их из внешнего env-файла
  (путь — env `MODELS_RU_ENV`; `GIGACHAT_AUTHORIZATION_KEY` — OAuth Basic,
  `YANDEXFM_API_KEY`; каталог Яндекса — env `YANDEXFM_FOLDER_ID`);
- GigaChat: OAuth-токен живёт ~30 мин, входные токены в usage — без
  кэшированной части (precached_prompt_tokens отдельно); endpoint по умолчанию
  `api.giga.chat` (переопределяется env `GIGA_CHAT_URL`); для физлиц действует
  Freemium: 365 млн токенов/12 мес по категориям (Max 25 млн, Ultra 50 млн) —
  списаний нет, GigaChat-3-Ultra доступна только физлицам и только во Freemium;
- бизнес-тарифы GigaChat (юрлицо): ₽650/1M Max (₽325 асинхронно, вх/вых
  не разделяются, мин. ₽600/мес, тарификация кэша не раскрыта); Ultra юрлицам
  у Сбера не продаётся — коммерческий доступ через cloud.ru Foundation
  Models (₽96/1M вх + ₽289/1M вых); расчёты по нашим сессиям — в model.md
  обеих гигачат-папок и BUSINESS_RUB_1M в build_report.py;
- у Яндекса замечен контент-фильтр на технических вопросах
  (`finish_reason: content_filter`) — фиксировать в model.md;
- Яндекс: URI `gpt://<folder>/yandexgpt/latest` (folder —
  `YANDEXFM_FOLDER_ID`) резолвится в **YandexGPT Pro 5** (имя видно
  только в детализации биллинга, API эхом возвращает URI); тариф плоский
  ₽1.2/1k токенов любого типа — кэш не даёт скидки (TARIFFS в раннере);
- DeepSeek (родной API): `DEEPSEEK_API_KEY` из того же .env TasK,
  `https://api.deepseek.com`, модель `deepseek-flash` (DeepSeek-V4.1-Flash);
  `reasoning_effort` задаётся раннером (стандарт серий low), thinking
  пишется в транскрипт; тариф пик $0.30/1M вх, $0.006/1M кэш-хит (×50
  дешевле), $1.20/1M вых, оф-пик ×0.5 (TARIFFS_USD в раннере); в раннере
  `max_tokens: 16000` — API-дефолт 4096 режет ответы в полуслове;
- папки моделей: `gigachat/` (GigaChat-2-Max), `gigachat-3-ultra/`,
  `yandexgpt/`, `deepseek-flash/`.

Язык заметок и промптов — русский (если для конкретного теста не нужно иначе).
