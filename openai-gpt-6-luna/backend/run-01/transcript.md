## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

Для чистого и надёжного кода особенно полезны возможности, которые делают контракты явными, сокращают неоднозначные конструкции и помогают ловить ошибки раньше. Вот те, которые я бы выделил.

### 1. Типы и типы объединения — PHP 8.0

Типы параметров, свойств и результатов фиксируют контракт метода. Union-типы позволяют явно описать несколько допустимых вариантов.

```php
function findUser(int|string $id): ?User
{
    // ...
}
```

Здесь `null` — допустимый результат, а для аргумента явно разрешены только `int` и `string`. Для более строгого поведения обычно также включают строгую проверку типов:

```php
<?php
declare(strict_types=1);
```

### 2. Именованные аргументы и promotion свойств конструктора — PHP 8.0

Именованные аргументы делают вызовы понятнее, а promotion избавляет от повторения объявления свойств и присваиваний.

```php
final class UserService
{
    public function __construct(
        private UserRepository $users,
        private LoggerInterface $logger,
    ) {}
}

$service = new UserService(
    users: $repository,
    logger: $logger,
);
```

Особенно удобно это для объектов с несколькими зависимостями или параметрами одного типа. Но в публичных API стоит помнить: переименование имени аргумента может нарушить совместимость с именованными вызовами.

### 3. `match` и nullsafe-оператор — PHP 8.0

`match` — выражение с точным сравнением, которое должно покрыть все варианты или явно обработать остальные.

```php
$label = match ($status) {
    'new'       => 'Новый',
    'paid'      => 'Оплачен',
    'cancelled' => 'Отменён',
    default     => 'Неизвестный',
};
```

Nullsafe-оператор упрощает цепочки обращений, где промежуточное значение может быть `null`:

```php
$email = $order?->customer?->email;
```

Он возвращает `null`, если объект в цепочке отсутствует, вместо необходимости писать несколько проверок.

### 4. Перечисления — PHP 8.1

Enums помогают заменить неформальные строковые константы ограниченным набором допустимых значений.

```php
enum OrderStatus: string
{
    case New = 'new';
    case Paid = 'paid';
    case Cancelled = 'cancelled';
}

function pay(OrderStatus $status): void
{
    // ...
}
```

Вместо произвольной строки вроде `'paidd'` код получает типизированное значение, а IDE и анализаторы могут лучше проверять варианты.

### 5. `readonly` — PHP 8.1 и 8.2

`readonly` полезен для данных, которые должны быть неизменяемыми после создания объекта. В PHP 8.1 его можно использовать для свойств, а с PHP 8.2 — для целых классов.

```php
final readonly class Money
{
    public function __construct(
        public int $cents,
        public string $currency,
    ) {}
}
```

Это хорошо подходит для объектов-значений и DTO: состояние нельзя незаметно изменить после создания. Для изменяемых сущностей такую модель нужно выбирать осознанно.

### 6. Intersection-типы и DNF-типы — PHP 8.1 и 8.2

Intersection-типы требуют, чтобы значение соответствовало нескольким типам одновременно:

```php
function process(Countable&IteratorAggregate $items): void
{
    // ...
}
```

PHP 8.2 добавил DNF-типы — сочетание объединений и пересечений:

```php
function process((Countable&Iterator)|array $items): void
{
    // ...
}
```

Они позволяют точнее описывать контракты, хотя чрезмерно сложные типы могут ухудшить читаемость.

### 7. Типизированные константы классов — PHP 8.3

Тип константы делает её контракт явным и не позволяет случайно присвоить значение неподходящего типа.

```php
final class RetryPolicy
{
    public const int MAX_ATTEMPTS = 3;
}
```

### 8. Асимметричная видимость свойств — PHP 8.4

В PHP 8.4 можно разрешить чтение свойства снаружи, но ограничить его изменение:

```php
final class User
{
    public private(set) string $name;

    public function __construct(string $name)
    {
        $this->name = $name;
    }
}
```

Это помогает защищать состояние объекта, не добавляя отдельный геттер для простого свойства. Возможность доступна начиная с PHP 8.4.

В целом я бы использовал эти функции не ради самого современного синтаксиса, а чтобы сделать допустимые состояния и контракты очевидными. Для надёжности они особенно эффективны вместе со строгой типизацией, статическим анализом и тестами.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

PHP имеет динамическую систему типов: переменная сама по себе не объявляется «типа `int`», но в конкретный момент содержит значение определённого типа. Типы можно задавать параметрам, результатам функций и свойствам — тогда PHP проверяет эти контракты во время выполнения.

## Что меняет `strict_types`

Директива ставится в начале файла:

```php
<?php
declare(strict_types=1);
```

Она отключает многие автоматические преобразования скалярных типов при вызовах функций и методов **из этого файла**. Важная деталь: для аргументов режим определяется файлом, **откуда вызывают** функцию, а не файлом, где она объявлена.

```php
// api.php
function charge(int $cents): void
{
    // ...
}
```

```php
// weak.php — строгий режим не включён
require 'api.php';

charge('1200'); // в слабом режиме строка может быть преобразована в int
```

```php
// strict.php
declare(strict_types=1);

require 'api.php';

charge('1200'); // TypeError
```

В строгом режиме `int` всё ещё можно передать туда, где ожидается `float`:

```php
function calculate(float $amount): float
{
    return $amount * 1.2;
}

calculate(10); // допустимо: int → float
```

Но `float` нельзя автоматически усечь до `int`:

```php
function quantity(int $count): void {}

quantity(2.7); // TypeError в strict-файле
```

Для возвращаемых значений скалярные типы тоже проверяются; учитывайте, что режим строгой типизации связан с файлом, где функция объявлена. При работе с библиотеками полезно проверять контракты и тестами, а не рассчитывать только на `strict_types`.

`strict_types` не превращает PHP в статически типизированный язык: проверка происходит во время выполнения, и директива в одном файле не делает автоматически строгим весь проект. Она также не заменяет типизацию свойств, анализатор вроде PHPStan/Psalm или проверку внешних данных.

## Где типизация спасает

**Недопустимый аргумент ловится у границы метода:**

```php
declare(strict_types=1);

function retry(int $attempts): void {}

retry('three'); // TypeError вместо неожиданного поведения дальше по коду
```

**Enum защищает от опечаток в статусах:**

```php
enum Status: string
{
    case Draft = 'draft';
    case Published = 'published';
}

function publish(Status $status): void {}

publish(Status::Published); // допустимо
publish('publshed');        // TypeError
```

**Nullable-типы заставляют явно учитывать отсутствие значения:**

```php
function findUser(int $id): ?User
{
    // Может вернуть User или null
}
```

Вместо неявного предположения, что пользователь всегда найден, вызывающий код должен обработать оба варианта.

## Где типизация удивляет

**Слабый режим может принимать неожиданные значения.** В нестрогом файле скалярные типы могут приводиться:

```php
function add(int $a, int $b): int
{
    return $a + $b;
}

add('10', 5); // строка может быть преобразована в int
```

При этом правила зависят от значения и контекста; полагаться на неявные преобразования в бизнес-коде рискованно.

**`bool` особенно легко получить случайно:**

```php
$enabled = (bool) 'false';

var_dump($enabled); // true: непустая строка — truthy
```

Строка `'false'` не является `false`. Для значений из формы или конфигурации нужно разбирать формат явно, например через `filter_var()` или собственный парсер.

**`==` сравнивает с приведением типов, `===` — без него:**

```php
var_dump(0 == '0');  // true
var_dump(0 === '0'); // false
```

Для проверки конкретного значения обычно безопаснее использовать `===`. Особую осторожность стоит соблюдать при сравнении данных из HTTP-запросов и при работе с числовыми строками.

**Типизированное свойство может быть ещё не инициализировано:**

```php
final class User
{
    public string $name;
}

$user = new User();
echo $user->name; // Error: свойство типизировано, но не инициализировано
```

Тип свойства не означает, что у него автоматически появилось значение. Его нужно инициализировать в конструкторе либо задать значение по умолчанию.

## Практический вывод

Я обычно ставлю `declare(strict_types=1)` в новых PHP-файлах, использую типы аргументов, результатов и свойств, а для ограниченных наборов значений — enum. Но данные извне всё равно нужно валидировать: `strict_types` не проверяет содержимое JSON, формы или базы данных сам по себе.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

Я рассматриваю исключение как часть контракта метода: оно сообщает, что операция не смогла завершиться обычным для вызывающего кода способом. В PHP этот контракт не проверяется компилятором, поэтому его нужно выражать именами исключений, документацией и тестами.

## Иерархия исключений

Обычно я создаю небольшую иерархию по смысловым границам, а не отдельный класс на каждую строку кода:

```php
abstract class DomainException extends RuntimeException {}

final class InsufficientFunds extends DomainException {}
final class AccountNotFound extends DomainException {}
```

Метод может явно описывать ожидаемые ошибки:

```php
/**
 * @throws AccountNotFound
 * @throws InsufficientFunds
 */
public function transfer(AccountId $from, AccountId $to, Money $amount): Transfer
{
    // ...
}
```

Стоит различать ошибки предметной области и технические сбои. Например, недостаток средств — ожидаемый отказ бизнес-операции; недоступность PostgreSQL — инфраструктурная проблема. Их не следует смешивать в одной общей ошибке.

При этом не каждую ситуацию нужно представлять исключением. Если отсутствие результата — штатный вариант, контракт может быть `?User`, `User|null` или объект результата. Исключение уместнее, когда операция не может продолжаться согласно своему контракту.

## Оборачивание чужих исключений

На границе инфраструктурного адаптера я преобразую низкоуровневую ошибку в понятную приложению, сохраняя исходное исключение как `previous`:

```php
final class UserStorageFailure extends RuntimeException {}

final class PdoUserRepository
{
    public function find(UserId $id): ?User
    {
        try {
            // Запрос к БД
        } catch (PDOException $e) {
            throw new UserStorageFailure(
                'Не удалось получить пользователя из хранилища.',
                previous: $e,
            );
        }
    }
}
```

Так верхние слои не зависят от `PDOException`, а исходная причина остаётся доступна для логирования и диагностики. Оборачивать стоит тогда, когда действительно меняется смысл ошибки или скрывается деталь конкретной технологии. Если преобразование ничего не добавляет, часто лучше не перехватывать исключение.

## Где перехватывать

Перехватываю исключение там, где можно принять осмысленное решение:

- на инфраструктурной границе — преобразовать техническую ошибку;
- на границе HTTP-запроса или очереди — превратить её в подходящий ответ, повтор задачи или сообщение об ошибке;
- внутри операции — только если можно восстановиться или выполнить компенсацию.

Например, HTTP-слой может централизованно отображать ошибки приложения:

```php
try {
    $transfer = $service->transfer($command);
} catch (InsufficientFunds $e) {
    return new JsonResponse(['error' => 'insufficient_funds'], 409);
}
```

Обычно я предпочитаю централизованный обработчик исключений контроллеру, который ловит десятки разных ошибок. Важно не выдавать клиенту SQL-сообщения, трассировки и внутренние детали; их следует оставить в логах с идентификатором запроса.

## Что считается контрактом метода

Контракт включает не только типы аргументов и результата, но и важные режимы отказа: какие исключения ожидаемы, какие условия их вызывают и что вызывающий код должен с ними делать. Для публичных методов это стоит документировать через PHPDoc, например `@throws`, и проверять тестами.

Не нужно обещать исчерпывающий список всех возможных исключений, если метод может пробрасывать неожиданные системные ошибки. Но ожидаемые доменные отказы должны быть понятны вызывающему коду.

## Частые антипаттерны

**Потеря исходной причины:**

```php
catch (PDOException $e) {
    throw new RuntimeException('Ошибка БД'); // потеряна причина
}
```

Нужно передать `$e` как `previous`.

**Пустой `catch`:**

```php
try {
    $service->run();
} catch (Throwable) {
    // Ошибка исчезла
}
```

Это скрывает сбой и может оставить систему в неконсистентном состоянии. Если исключение перехвачено, его нужно обработать, преобразовать или хотя бы корректно зарегистрировать и завершить операцию.

**Перехват слишком общего типа без причины:**

```php
catch (Throwable $e) {
    return null;
}
```

Так в один «обычный» результат превращаются и ожидаемая ошибка, и программный дефект вроде `TypeError`. Ловить `Throwable` уместно в верхнем аварийном обработчике или при обязательной очистке ресурсов, но не как универсальный способ продолжить работу.

**Исключения как управление обычным потоком.** Если «пользователь не найден» — штатный результат поиска, часто яснее вернуть `null`, чем заставлять каждый вызов ловить исключение. Если отсутствие означает нарушение бизнес-условия, исключение может быть уместно.

**Слишком общие или чрезмерно многочисленные классы.** `AppException` почти ничего не говорит вызывающему коду, а отдельный класс на каждую техническую мелочь усложняет систему. Класс исключения должен помогать принять решение.

Итого: я стараюсь держать исключения точными и осмысленными, преобразовывать их на границах слоёв, сохранять `previous` и перехватывать только там, где есть конкретная реакция.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

Если говорить о типичных проблемах PHP-бэкенда, я чаще всего вижу нарушение **SRP — принципа единственной ответственности**. Особенно в контроллерах и сервисах, которые одновременно принимают запрос, проверяют права, применяют бизнес-правила, работают с БД и отправляют уведомления.

У меня нет личного опыта работы с коммерческими кодовыми базами, поэтому это не вывод из собственной практики. Но такой пример часто встречается при обсуждении рефакторинга: класс постепенно обрастает несвязанными обязанностями и становится трудно тестируемым.

### До рефакторинга

```php
final class RegistrationController
{
    public function register(Request $request): Response
    {
        $email = trim((string) $request->request->get('email'));

        if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
            return new Response('Invalid email', 400);
        }

        $pdo = new PDO('pgsql:host=db;dbname=app', 'user', 'secret');
        $stmt = $pdo->prepare('INSERT INTO users (email) VALUES (?)');
        $stmt->execute([$email]);

        mail($email, 'Welcome', 'Thanks for registering!');

        return new Response('Created', 201);
    }
}
```

Контроллер связан с HTTP, валидацией, подключением к базе, SQL и отправкой почты. Изменение схемы БД или почтового провайдера затрагивает его напрямую, а тестирование регистрации требует контролировать сразу несколько внешних систем.

### После рефакторинга

Контроллер отвечает за HTTP, а сценарий регистрации делегируется приложению:

```php
final class RegistrationController
{
    public function __construct(
        private RegisterUser $registerUser,
    ) {}

    public function register(Request $request): Response
    {
        $result = $this->registerUser->execute(
            new RegisterUserCommand(
                email: (string) $request->request->get('email'),
            ),
        );

        return new Response('', 201);
    }
}
```

Сценарий зависит от абстракций, а не от конкретных способов хранения и отправки почты:

```php
final class RegisterUser
{
    public function __construct(
        private UserRepository $users,
        private WelcomeMailer $mailer,
    ) {}

    public function execute(RegisterUserCommand $command): void
    {
        $email = EmailAddress::fromString($command->email);

        if ($this->users->exists($email)) {
            throw new EmailAlreadyRegistered();
        }

        $user = User::register($email);

        $this->users->save($user);
        $this->mailer->sendWelcome($email);
    }
}
```

`UserRepository` и `WelcomeMailer` реализуются инфраструктурными адаптерами — например, через Doctrine и Symfony Mailer. Это упрощает замену технологий и позволяет тестировать сценарий с подменами этих зависимостей.

Важно не дробить код механически: SRP не означает «один метод или класс на каждую операцию». Критерий практичнее — у класса должна быть одна связная причина для изменения. Например, если правила регистрации меняются независимо от HTTP-формата или способа отправки писем, эти ответственности стоит разделить.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Да. SOLID — это набор эвристик, а не обязательные правила. Их смысл — снижать стоимость изменений и сопровождения. Если буквальное следование принципу усложняет код, а вероятные изменения от него не зависят, отступление может быть разумным.

Например, для маленькой CLI-команды может быть оправдано объединить разбор аргументов и выполнение простого сценария в одном классе:

```php
final class CleanupCommand extends Command
{
    protected function execute(
        InputInterface $input,
        OutputInterface $output,
    ): int {
        $days = (int) $input->getOption('days');
        $cutoff = new DateTimeImmutable("-{$days} days");

        $deleted = $this->connection->executeStatement(
            'DELETE FROM sessions WHERE created_at < ?',
            [$cutoff],
        );

        $output->writeln("Удалено записей: {$deleted}");

        return Command::SUCCESS;
    }
}
```

Можно выделить отдельные классы для парсинга параметров, построения даты, выполнения SQL и форматирования результата. Но если команда короткая, используется только здесь и имеет одну связную причину для изменения — например, меняется только логика очистки, — такое разбиение добавит навигацию и абстракции без заметной пользы.

Я бы пересмотрел решение, если команда разрастётся, ту же логику понадобится переиспользовать или её станет трудно тестировать. То есть важен не факт «нарушения» SRP, а осознанный компромисс: простота сегодня против ожидаемой цены изменений завтра.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Да. OCP — принцип «открыт для расширения, закрыт для изменения» — не требует наследования. Смысл в том, чтобы добавление нового варианта поведения по возможности не вынуждало переписывать уже проверенный код.

### 1. Композиция и стратегии

Клиент зависит от интерфейса, а конкретное поведение передаётся как зависимость:

```php
interface DiscountPolicy
{
    public function calculate(Order $order): Money;
}

final class RegularDiscount implements DiscountPolicy
{
    public function calculate(Order $order): Money
    {
        return Money::zero();
    }
}

final class VipDiscount implements DiscountPolicy
{
    public function calculate(Order $order): Money
    {
        return $order->total()->multiply(0.1);
    }
}

final class Checkout
{
    public function __construct(
        private DiscountPolicy $discounts,
    ) {}

    public function total(Order $order): Money
    {
        return $order->total()->subtract(
            $this->discounts->calculate($order),
        );
    }
}
```

Новая политика скидки добавляется отдельной реализацией. `Checkout` не нужно менять. Это композиция, хотя конкретные реализации здесь могут быть и классами, и функциями.

### 2. Функции или callable

Если поведение небольшое и отдельный класс был бы избыточным, можно передать callable:

```php
function export(
    array $rows,
    callable $formatRow,
): string {
    return implode("\n", array_map($formatRow, $rows));
}

$csv = export($rows, fn (array $row) => implode(',', $row));
```

Так можно расширять алгоритм форматирования, не добавляя ветвления в `export`.

### 3. Регистрация обработчиков или плагинов

Например, вместо `switch` по типу события можно зарегистрировать обработчики по ключу:

```php
interface EventHandler
{
    public function handle(object $event): void;
}

final class HandlerRegistry
{
    /** @var array<class-string, EventHandler> */
    private array $handlers = [];

    public function register(string $eventClass, EventHandler $handler): void
    {
        $this->handlers[$eventClass] = $handler;
    }

    public function handlerFor(object $event): EventHandler
    {
        return $this->handlers[$event::class]
            ?? throw new LogicException('Обработчик не зарегистрирован');
    }
}
```

Новый тип события поддерживается регистрацией обработчика, а не расширением центрального `switch`. В реальном приложении регистрацию обычно настраивает DI-контейнер.

### 4. Конфигурация и таблицы данных

Когда различаются только параметры, а не алгоритм, часто лучше конфигурация:

```php
$limits = [
    'free' => 100,
    'pro' => 10_000,
];

$limit = $limits[$plan] ?? throw new InvalidArgumentException('Unknown plan');
```

Это проще, чем создавать подкласс для каждого тарифного плана. Но если варианты имеют существенно разное поведение, одной таблицы значений может быть недостаточно.

Важно не трактовать OCP как запрет на изменение кода. Например, добавление нового значения в `enum` может потребовать обновить `match` и тесты — это нормальная работа с явным исчерпывающим набором вариантов. Абстракция полезна, когда действительно ожидаются независимые расширения; иначе она может оказаться преждевременным усложнением.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Нет. **SRP — принцип единственной ответственности — применим не только к классам**, но и к любым единицам кода: функциям, модулям, сервисам, пакетам и даже командам команды разработки.

Его часто формулируют так: у компонента должна быть одна связная причина для изменения. Это не означает, что функция должна делать ровно одну низкоуровневую операцию: она может выполнять несколько шагов, если они вместе реализуют одну цель.

Например, функция, которая проверяет данные, сохраняет их в БД и отправляет письмо, может иметь несколько независимых причин для изменения:

```php
function registerUser(array $input): void
{
    // Проверка HTTP-формата
    // Сохранение пользователя
    // Отправка письма
}
```

Разделение может выглядеть так:

```php
function parseRegistrationInput(array $input): RegisterUserCommand
{
    // Преобразование и проверка формата входных данных
}

function registerUser(RegisterUserCommand $command): User
{
    // Бизнес-сценарий регистрации
}

function sendWelcomeEmail(User $user): void
{
    // Уведомление
}
```

Но дробить код автоматически тоже не стоит: если выделенная функция не имеет самостоятельного смысла или причины меняться, она лишь усложнит чтение. SRP полезен на том уровне, где появляются разные, независимые поводы менять код.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

Важное уточнение: в обычном Symfony-контейнере приложение обычно **не строит граф зависимостей заново при каждом запросе сервиса**. Большая часть работы выполняется при компиляции контейнера; после этого Symfony использует сгенерированный PHP-код и кэширует созданные сервисы.

## 1. Описание сервисов и компиляция контейнера

Определения сервисов поступают из конфигурации (`services.yaml`, XML, PHP), бандлов и атрибутов. Во время сборки контейнера Symfony обрабатывает эти определения:

1. Загружает и объединяет конфигурацию.
2. Регистрирует определения сервисов и алиасы.
3. Применяет compiler passes: например, обрабатывает autowiring, autoconfigure, декораторы и tagged-сервисы.
4. Проверяет часть графа зависимостей: например, что нужные сервисы существуют и что их можно связать.
5. Оптимизирует и генерирует PHP-классы контейнера в каталоге кэша.

Упрощённо:

```yaml
services:
    App\Service\Mailer:
        autowire: true
        autoconfigure: true
```

Компилятор контейнера разрешает зависимости `Mailer` и генерирует код, который создаёт этот сервис. В production при прогретом кэше эта сборка обычно не выполняется на каждом HTTP-запросе. В режиме разработки контейнер может перестраиваться при изменении конфигурации или отслеживаемых файлов.

Компиляция проверяет конфигурацию и известные связи, но это не означает, что каждый сервис немедленно создаётся: создание объектов обычно отложено.

## 2. Как работает autowiring

Autowiring использует типы конструктора, чтобы подобрать сервисы из контейнера:

```php
final class OrderService
{
    public function __construct(
        private OrderRepository $orders,
        private LoggerInterface $logger,
    ) {}
}
```

Если в контейнере есть подходящие определения `OrderRepository` и `LoggerInterface`, Symfony связывает их автоматически. Для интерфейсов обычно нужен alias на конкретную реализацию:

```yaml
services:
    App\Repository\OrderRepository: ~

    App\Repository\OrderRepositoryInterface:
        alias: App\Repository\OrderRepository
```

Если подходящих кандидатов несколько, Symfony не может выбрать один только по типу. Тогда нужно задать alias, binding или явное значение:

```yaml
services:
    App\Service\ReportGenerator:
        arguments:
            $formatter: '@App\Formatter\CsvFormatter'
```

Autowiring — это разрешение зависимостей по типам при построении контейнера, а не поиск реализации во время каждого вызова метода.

## 3. Что происходит при первом запросе сервиса

Предположим, контроллер зависит от `OrderService`. При обработке запроса Symfony вызывает код скомпилированного контейнера, который получает контроллер и передаёт ему зависимости. Если сервис ещё не создан, контейнер выполняет примерно такие действия:

1. Создаёт зависимости, которые нужны для конструктора.
2. Создаёт сам сервис.
3. Сохраняет экземпляр, если сервис shared — это поведение по умолчанию.
4. Возвращает его вызывающему коду.

Следующий запрос того же сервиса **в рамках того же экземпляра контейнера** обычно получает сохранённый объект. Но это не означает, что PHP-объект автоматически переживает отдельные HTTP-запросы: в типичной модели PHP-FPM процесс может обслуживать несколько запросов, а состояние контейнера и сервисов зависит от окружения и способа выполнения. В приложениях на долгоживущих воркерах важно особенно внимательно относиться к состоянию shared-сервисов, чтобы данные одного задания не попали в другое.

## 4. Ленивые сервисы и различия с `ServiceSubscriber`

Некоторые сервисы могут быть ленивыми: при внедрении контейнер передаёт прокси, а реальный объект создаётся при первом обращении к прокси. Это полезно, например, для дорогих или редко используемых зависимостей. Ленивая загрузка не включается автоматически для любого сервиса и зависит от конфигурации и поддержки проксирования.

Также важно отличать обычное внедрение сервисов от `ServiceSubscriberInterface` и `ServiceLocator`: они позволяют получать ограниченный набор сервисов по запросу. Это не то же самое, что внедрять весь контейнер, и обычно помогает сохранить более явные зависимости.

Итого: Symfony заранее строит и оптимизирует граф сервисов, autowiring сопоставляет типы с определениями или алиасами, а при первом обращении к обычному lazy-сервису скомпилированный контейнер создаёт объект и обычно сохраняет его как shared.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

Сначала стараюсь не «разруливать» цикл технически, а выяснить, почему он возник: обычно два сервиса взяли на себя взаимные обязанности, либо слой приложения смешан с инфраструктурой. Внедрение через `set*()` или `ServiceLocator` может скрыть цикл, но не устранить его.

Например, если `OrderService` вызывает `EmailService`, а тот обращается обратно к `OrderService`, полезно отделить общий сценарий или правило:

```text
OrderService → EmailService → OrderService
```

Варианты рефакторинга:

1. **Вынести общий сценарий в отдельный сервис.**  
   Если оба сервиса используют одну операцию, её можно поместить в третий компонент с более узкой ответственностью.

2. **Инвертировать зависимость через порт.**  
   Сервис зависит от интерфейса, а реализация подключается на границе приложения. Это помогает разорвать зависимость между слоями, хотя само по себе не исправляет неудачное разделение обязанностей.

3. **Использовать событие или сообщение, если связь действительно асинхронная.**  
   Например, заказ публикует событие, а отдельный обработчик отправляет письмо. Это ослабляет связанность, но добавляет вопросы доставки, повторов и согласованности — не стоит вводить очередь лишь ради устранения цикла в контейнере.

```php
final readonly class OrderPlaced
{
    public function __construct(public int $orderId) {}
}

final class PlaceOrder
{
    public function __construct(
        private OrderRepository $orders,
        private EventBus $events,
    ) {}

    public function execute(PlaceOrderCommand $command): void
    {
        $order = Order::place($command);
        $this->orders->save($order);
        $this->events->publish(new OrderPlaced($order->id()));
    }
}
```

Обработчик события может отправить уведомление, не делая сервис заказа зависимым от почтового сервиса.

Если цикл обнаружен в Symfony, сначала проверяю сообщения компилятора контейнера и путь зависимостей, затем рисую граф и ищу общую обязанность, которую можно выделить. `ServiceLocator`, setter injection или ленивые прокси иногда уместны для намеренно отложенных или условных зависимостей, но я не использую их как первое средство: они могут замаскировать архитектурную проблему.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

Я бы вынес отправку письма и обновление индекса из HTTP-запроса в асинхронную обработку. В Symfony типичный вариант — **Symfony Messenger**: после регистрации приложение публикует сообщение, а отдельный worker обрабатывает его.

## Базовый вариант: Messenger и очередь

Сценарий регистрации сохраняет пользователя и отправляет сообщение:

```php
final readonly class UserRegistered
{
    public function __construct(public string $userId) {}
}

final class RegisterUser
{
    public function __construct(
        private UserRepository $users,
        private MessageBusInterface $bus,
    ) {}

    public function __invoke(RegisterUserCommand $command): User
    {
        $user = User::register($command->email);
        $this->users->save($user);

        $this->bus->dispatch(new UserRegistered($user->id()));

        return $user;
    }
}
```

Обработчик выполняется worker’ом:

```php
#[AsMessageHandler]
final class HandleUserRegistered
{
    public function __construct(
        private WelcomeMailer $mailer,
        private SearchIndexer $indexer,
    ) {}

    public function __invoke(UserRegistered $message): void
    {
        $user = $this->users->get($message->userId);

        $this->mailer->sendWelcome($user);
        $this->indexer->index($user);
    }
}
```

В `messenger.yaml` задаётся транспорт для сообщений, например Doctrine, Redis, RabbitMQ или облачная очередь. Для фоновой обработки должен работать отдельный worker:

```bash
php bin/console messenger:consume async
```

HTTP-ответ можно вернуть после фиксации регистрации и постановки сообщения в очередь, не дожидаясь внешних сервисов.

## Одно сообщение или два

Можно отправить одно сообщение `UserRegistered`, которое обработчик направит почтовому и поисковому сервисам. Это просто, но сбой одной операции способен задержать повторное выполнение другой: например, письмо уже ушло, а индексация упала, и при повторе письмо может отправиться снова.

Если операции должны независимо повторяться, лучше поставить два сообщения:

```php
$bus->dispatch(new SendWelcomeEmail($user->id()));
$bus->dispatch(new IndexUser($user->id()));
```

Тогда у них могут быть отдельные очереди, приоритеты, обработчики и политики повторов. Цена — больше конфигурации и необходимость учитывать независимое выполнение.

## Надёжность постановки сообщений

Обычная последовательность `save user` и затем `dispatch()` имеет окно сбоя: процесс может завершиться после коммита БД, но до отправки сообщения. Возможен и обратный порядок, когда сообщение ушло, а транзакция регистрации откатилась.

Для критичных событий используют **transactional outbox**: в одной транзакции с пользователем записывают событие в таблицу outbox, а отдельный процесс доставляет его в Messenger или брокер. Это надёжнее, но требует очистки outbox, обработки повторной доставки и дополнительной инфраструктуры. Middleware `DispatchAfterCurrentBus` помогает управлять моментом обработки в рамках Messenger, но сам по себе не даёт атомарности между БД и внешним брокером.

## Повторы и идемпотентность

Очереди обычно дают доставку «как минимум один раз», поэтому обработчик может выполниться повторно. Операции нужно делать идемпотентными или защищать от дубликатов:

- индексацию выполнять как upsert по стабильному ID;
- для писем хранить ключ идемпотентности или статус отправки;
- настроить retries и failure transport;
- предусмотреть мониторинг очереди и повторную обработку ошибок.

Также стоит передавать в сообщение ID пользователя, а не сериализовать целиком Doctrine-сущность: сообщение остаётся компактным и не привязано к состоянию ORM. Нужно решить и то, какие данные читает обработчик: актуальное состояние пользователя или снимок данных на момент регистрации.

## Альтернативы и компромиссы

- **Синхронный вызов после регистрации** — проще всего, но задерживает ответ и связывает доступность регистрации с почтой и поиском.
- **FastCGI/background task после ответа** — может уменьшить воспринимаемую задержку, но обычно хуже контролируется, чем durable queue: задача может потеряться при завершении процесса.
- **Messenger с базой данных** — простая эксплуатация и транзакционное окружение уже есть, но при большом потоке может стать узким местом.
- **Отдельный брокер** — лучше масштабируется и позволяет разделять очереди, но добавляет инфраструктуру и операционные обязанности.
- **Outbox** — повышает надёжность согласования БД и очереди, но оправдан прежде всего для событий, потеря которых недопустима.

Для обычного приложения я начал бы с Messenger, двух независимых сообщений и настроенных retries/failure transport. Если потеря уведомления или индексационного события недопустима, добавил бы transactional outbox.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

В Symfony **аутентификация** отвечает на вопрос «кто пользователь?», а **авторизация** — «может ли он выполнить это действие?». Основные элементы — firewall, провайдер пользователя, authenticator, роли и voters.

## Аутентификация

Firewall определяет, как обрабатывать запросы в соответствующей части приложения: например, через форму входа, API-токен или HTTP Basic. Аутентификатор проверяет учётные данные и формирует аутентифицированный объект пользователя, обычно реализующий `UserInterface`. Пользователь загружается через настроенный user provider.

Упрощённо конфигурация может выглядеть так:

```yaml
# security.yaml
security:
    providers:
        app_users:
            entity:
                class: App\Entity\User
                property: email

    firewalls:
        main:
            lazy: true
            provider: app_users
            form_login:
                login_path: app_login
                check_path: app_login
            logout:
                path: app_logout
```

Для API часто используют другой firewall и подходящий authenticator. Важно не путать проверку логина с проверкой разрешений: успешная аутентификация сама по себе не даёт доступ ко всем ресурсам.

## Роли

Роли подходят для **грубых, общих разрешений**, которые не зависят от конкретного объекта:

```yaml
security:
    access_control:
        - { path: ^/admin, roles: ROLE_ADMIN }
```

Или в коде:

```php
$this->denyAccessUnlessGranted('ROLE_ADMIN');
```

Роли удобны, когда нужно разрешить категорию пользователей: администратору — вход в административный раздел, редактору — доступ к управлению контентом. Их можно организовать через иерархию ролей, например `ROLE_ADMIN` наследует `ROLE_EDITOR`.

Однако проверка только роли часто недостаточна для объектного правила: например, пользователь может редактировать собственный заказ, но не чужой.

## Voters

Voter реализует решение для конкретного атрибута и объекта. Например, право редактировать заказ зависит от текущего пользователя и владельца заказа:

```php
final class OrderVoter extends Voter
{
    public const EDIT = 'ORDER_EDIT';

    protected function supports(string $attribute, mixed $subject): bool
    {
        return $attribute === self::EDIT && $subject instanceof Order;
    }

    protected function voteOnAttribute(
        string $attribute,
        mixed $subject,
        TokenInterface $token,
    ): bool {
        $user = $token->getUser();

        if (!$user instanceof User) {
            return false;
        }

        /** @var Order $order */
        $order = $subject;

        return $order->ownerId()->equals($user->id())
            || in_array('ROLE_ADMIN', $user->getRoles(), true);
    }
}
```

Проверка в контроллере:

```php
$this->denyAccessUnlessGranted(OrderVoter::EDIT, $order);
```

Аналогично можно проверять права в сервисном слое, чтобы важное правило не зависело только от наличия конкретного HTTP-контроллера.

## Когда выбирать что

- **Роли** — для общих разрешений, не зависящих от конкретного ресурса: доступ к админ-разделу, функции редактора или модератора.
- **Voter** — для правил, зависящих от объекта, действия, владельца ресурса или состояния бизнес-процесса: редактирование своего заказа, публикация статьи, возврат платежа.
- **Комбинация** — обычный вариант: роль задаёт общий уровень доступа, voter проверяет доступ к конкретному объекту.

Я стараюсь не кодировать каждое бизнес-правило в ролях вроде `ROLE_CAN_EDIT_ORDER_123`: роли описывают категорию полномочий пользователя, а voter решает контекстный вопрос для конкретного ресурса. При проектировании также важно определить поведение для анонимного пользователя и централизованно обрабатывать отказ в доступе.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

В Doctrine важно различать две гарантии:

1. **Объект валиден при создании в доменном коде.**
2. **Объект остаётся валидным после загрузки из БД.**

Вторая гарантия не появляется автоматически: ORM обычно восстанавливает состояние сущности и её полей, не вызывая обычный конструктор доменного объекта. Поэтому маппинг нужно сочетать с ограничениями БД и продуманной гидратацией.

## 1. Embeddable — обычно лучший вариант для составного Value Object

Подходит, когда объект состоит из нескольких полей, имеет смысл только внутри сущности и не обладает собственной идентичностью.

```php
#[ORM\Embeddable]
final class EmailAddress
{
    #[ORM\Column(name: 'value', length: 254)]
    private string $value;

    private function __construct(string $value)
    {
        $this->value = $value;
    }

    public static function fromString(string $value): self
    {
        $value = mb_strtolower(trim($value));

        if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException('Некорректный email');
        }

        return new self($value);
    }

    public function value(): string
    {
        return $this->value;
    }
}
```

```php
#[ORM\Entity]
final class User
{
    #[ORM\Embedded(class: EmailAddress::class, columnPrefix: 'email_')]
    private EmailAddress $email;
}
```

**Плюсы:** поля VO хранятся в таблице владельца; модель остаётся выразительной; к VO можно привязать отдельные правила и сравнение по значению.

**Минусы и подводные камни:**

- Embeddable не становится отдельной сущностью: у него нет собственной идентичности и жизненного цикла.
- Конструктор VO не следует считать гарантированно вызываемым при гидратации. Данные из старой или некорректной БД могут обойти фабрику `fromString()`.
- Встроенные поля — это отдельные колонки, поэтому ограничения вроде `NOT NULL`, `CHECK` и длины нужно корректно настроить и в схеме БД.
- Необязательный VO требует продуманного отображения: набор `NULL`-колонок сам по себе не всегда выражает доменное понятие «объекта нет».
- Поддержка `readonly` и особенности гидратации зависят от версии PHP и Doctrine. Не стоит предполагать, что обычный доменный конструктор будет использован ORM.

Для неизменяемого VO в сущности обычно заменяют объект целиком:

```php
$user->changeEmail(EmailAddress::fromString($newEmail));
```

Так доменная операция остаётся явной. Изменять поля VO после создания не нужно.

## 2. Пользовательский DBAL Type — для VO, хранящегося в одной колонке

Если VO естественно представляется одним скалярным значением — например, `EmailAddress`, `Uuid` или `CurrencyCode`, — можно написать собственный DBAL-тип. Он преобразует объект в значение БД и обратно:

```php
final class EmailAddressType extends Type
{
    public const NAME = 'email_address';

    public function convertToPHPValue(mixed $value, AbstractPlatform $platform): ?EmailAddress
    {
        if ($value === null || $value instanceof EmailAddress) {
            return $value;
        }

        return EmailAddress::fromString((string) $value);
    }

    public function convertToDatabaseValue(mixed $value, AbstractPlatform $platform): ?string
    {
        if ($value === null) {
            return null;
        }

        if (!$value instanceof EmailAddress) {
            throw new InvalidArgumentException('Ожидался EmailAddress');
        }

        return $value->value();
    }

    // Также нужно реализовать требуемые текущей версией Doctrine
    // методы объявления SQL-типа и зарегистрировать тип.
}
```

После регистрации типа его можно использовать как обычный тип колонки.

**Плюсы:** VO остаётся целостным объектом в модели; преобразование в доменный тип сосредоточено в одном месте; удобно для поиска по значению и передачи параметров запросам.

**Минусы и подводные камни:**

- Один DBAL-тип обычно соответствует **одной колонке**. Для VO из нескольких независимых значений embeddable обычно естественнее.
- В `convertToPHPValue()` следует валидировать данные: это важная граница между БД и доменом. Но неожиданная ошибка при чтении может сорвать загрузку целой сущности — грязные данные нужно обнаруживать и исправлять.
- Следует корректно обрабатывать `null` и уже преобразованные значения.
- Тип нужно зарегистрировать; детали API, включая SQL-декларацию и методы для комментариев схемы, зависят от версии DBAL/Doctrine.
- Для запросов нужно передавать объект или явно задать тип, чтобы Doctrine знала, как преобразовать параметр.

## 3. JSON-колонка — если объект действительно хранится как документ

Можно сериализовать несколько свойств VO в JSON, используя штатную JSON-поддержку платформы или собственный тип.

**Плюсы:** удобно для структурированных, редко запрашиваемых данных с меняющейся формой.

**Минусы:** хуже переносимость и индексация; сложнее накладывать ограничения на отдельные поля; схема JSON может разойтись с моделью. Десериализацию нужно считать границей валидации и не допускать создания некорректного VO без проверки.

## Что выбрать

- **Несколько полей, принадлежащих сущности** — обычно embeddable.
- **Одно скалярное значение** — пользовательский DBAL Type.
- **Гибкая документная структура** — JSON, если ограничения и запросы к отдельным полям несущественны.

Для любого варианта я бы проверял входящие значения при преобразовании в доменную модель, добавлял ограничения БД для инвариантов, которые можно выразить на уровне схемы, и тестировал round-trip: создание VO → сохранение → загрузка → проверка равенства и валидности. Не стоит полагаться только на фабрику или только на ORM-маппинг: исторические данные и прямые SQL-записи тоже могут нарушить инварианты.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

Возьму агрегат `Order` с дочерними сущностями `OrderLine`. Предположим, строки заказа нельзя менять независимо от заказа: все операции выполняются через корень агрегата. Тогда репозиторий нужен для `Order`, а не для `OrderLine`.

## Маппинг

У `Order` есть коллекция строк, а владеющая сторона связи — `OrderLine`, потому что внешний ключ `order_id` находится в таблице строк заказа.

```php
#[ORM\Entity]
final class Order
{
    /** @var Collection<int, OrderLine> */
    #[ORM\OneToMany(
        mappedBy: 'order',
        targetEntity: OrderLine::class,
        cascade: ['persist'],
        orphanRemoval: true,
    )]
    private Collection $lines;

    #[ORM\Version]
    #[ORM\Column]
    private int $version = 1;

    public function __construct(
        #[ORM\Id]
        #[ORM\Column(type: 'uuid')]
        private Uuid $id,
    ) {
        $this->lines = new ArrayCollection();
    }

    public function addLine(ProductId $productId, int $quantity, Money $price): void
    {
        if ($quantity <= 0) {
            throw new DomainException('Количество должно быть положительным.');
        }

        $this->lines->add(new OrderLine($this, $productId, $quantity, $price));
    }

    public function removeLine(OrderLineId $lineId): void
    {
        foreach ($this->lines as $line) {
            if ($line->id()->equals($lineId)) {
                $this->lines->removeElement($line);
                return;
            }
        }

        throw new DomainException('Строка заказа не найдена.');
    }
}
```

```php
#[ORM\Entity]
final class OrderLine
{
    #[ORM\Id]
    #[ORM\Column(type: 'uuid')]
    private Uuid $id;

    public function __construct(
        #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'lines')]
        #[ORM\JoinColumn(nullable: false)]
        private Order $order,

        #[ORM\Column(type: 'uuid')]
        private ProductId $productId,

        #[ORM\Column]
        private int $quantity,

        #[ORM\Embedded(class: Money::class)]
        private Money $price,
    ) {
        $this->id = Uuid::v7();
    }

    public function id(): OrderLineId
    {
        return OrderLineId::fromUuid($this->id);
    }
}
```

Пример схематичный: типы для `Uuid`, `ProductId` и `Money` должны быть сопоставлены с Doctrine подходящим способом.

Здесь важно следующее:

- `OrderLine::$order` — **владеющая сторона** связи. Doctrine сохраняет внешний ключ именно по ней.
- Добавление строки происходит через `Order::addLine()`, поэтому в памяти агрегата сразу обновляется коллекция и устанавливается ссылка на корень.
- `cascade: ['persist']` позволяет сохранить новые строки вместе с новым агрегатом.
- `orphanRemoval: true` означает, что удалённая из коллекции строка будет удалена из БД при `flush()`. Использовать это стоит, только если строка действительно не имеет смысла вне заказа и удаление из коллекции означает её физическое удаление.
- `cascade: ['remove']` я бы добавлял только при явно желаемой семантике удаления заказа вместе со всеми строками; каскады не следует включать «на всякий случай».

Для существующего заказа Doctrine загружает коллекцию как `PersistentCollection`, часто лениво. Не нужно заменять её обычным массивом или `ArrayCollection` в бизнес-коде: лучше работать через методы агрегата.

## Репозиторий и `flush()`

Операцию предметной области выполняют через корень. Репозиторий тоже ориентирован на корень:

```php
interface OrderRepository
{
    public function get(OrderId $id): Order;
    public function add(Order $order): void;
}
```

```php
final class DoctrineOrderRepository implements OrderRepository
{
    public function __construct(private EntityManagerInterface $em) {}

    public function get(OrderId $id): Order
    {
        return $this->em->find(Order::class, $id)
            ?? throw new OrderNotFound();
    }

    public function add(Order $order): void
    {
        $this->em->persist($order);
    }
}
```

Я обычно **не вызываю `flush()` внутри каждого метода репозитория или агрегата**. `persist()` регистрирует новый объект в Unit of Work; изменение уже управляемой сущности Doctrine отслеживает самостоятельно. При `flush()` Unit of Work вычисляет изменения и записывает их в БД.

`flush()` удобно вызывать на границе прикладного сценария — после завершения одной операции:

```php
final class AddOrderLine
{
    public function __construct(
        private OrderRepository $orders,
        private EntityManagerInterface $em,
    ) {}

    public function __invoke(AddOrderLineCommand $command): void
    {
        $order = $this->orders->get($command->orderId);

        $order->addLine(
            $command->productId,
            $command->quantity,
            $command->price,
        );

        $this->em->flush();
    }
}
```

Для нового агрегата сценарий вызывает `persist()` через репозиторий, затем один раз делает `flush()`. Для уже загруженного агрегата отдельный `persist()` обычно не нужен.

Так граница сохранения соответствует прикладному use case, а не случайному количеству вызовов репозитория. Если проект использует Unit of Work или middleware, ответственным за `flush()` может быть этот инфраструктурный компонент — важно, чтобы в приложении была одна понятная политика.

## Транзакция

Если изменение агрегата затрагивает несколько записей, они должны фиксироваться атомарно. Часто один `flush()` Doctrine сам оборачивает SQL-операции в транзакцию, но явная транзакционная граница полезна, когда сценарий включает дополнительные операции или требуется чётко зафиксировать атомарность:

```php
$this->em->wrapInTransaction(function () use ($command): void {
    $order = $this->orders->get($command->orderId);
    $order->addLine(
        $command->productId,
        $command->quantity,
        $command->price,
    );

    $this->em->flush();
});
```

Точная сигнатура и поведение обёрток транзакций зависят от версии Doctrine. Смысл один: транзакция охватывает изменение агрегата и его запись, а после ошибки выполняется rollback.

Не стоит держать транзакцию открытой во время сетевого вызова — например, при обращении к платёжному сервису. Для внешних эффектов обычно применяют события после коммита, очередь и при необходимости transactional outbox.

## Инварианты и параллельные изменения

Все изменения, связанные с правилами заказа, следует проводить через `Order`, чтобы нельзя было обойти инварианты прямым редактированием `OrderLine`. Но агрегатная граница сама по себе не защищает от конкурентного обновления двумя запросами.

Для обнаружения потерянных обновлений можно использовать optimistic locking — например, `#[ORM\Version]`, как в примере. При конфликте приложение получает исключение и решает, повторить операцию или вернуть конфликт пользователю. Для особенно строгих сценариев возможны блокировки, но их нужно выбирать с учётом нагрузки и длительности транзакций.

Итого: мапплю дочерние сущности как коллекцию корня, поддерживаю обе стороны связи через методы агрегата, сохраняю и загружаю агрегат целиком, а `flush()` и транзакцию привязываю к границе прикладной операции.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

Сначала подтверждаю, что проблема действительно в N+1: медленная страница может упираться не только в БД, но и в сериализацию, шаблоны, внешние API или блокировки. Затем нахожу повторяющийся шаблон запросов и выбираю исправление под конкретный сценарий чтения.

## Диагностика

1. **Воспроизвожу запрос с реалистичными данными** и измеряю время, число SQL-запросов и их суммарную длительность.
2. **Смотрю Symfony Profiler в dev-окружении**, вкладку Doctrine: список запросов, длительности и повторяющиеся SQL. Если страница формируется из нескольких запросов, проверяю именно нужный контроллер и шаблон.
3. **Проверяю логи и трассировки в окружении, близком к production.** Profiler сам добавляет накладные расходы, поэтому для нагрузочной проверки полезны метрики или трассировка.
4. **Сопоставляю число запросов с размером результата.** Если для списка из 50 заказов выполняется один запрос списка и затем 50 одинаковых запросов за клиентами — это типичный N+1.
5. **Проверяю, кто обращается к ленивым связям.** Дополнительные запросы часто запускаются не в репозитории, а позднее — в шаблоне, serializer normalizer, логгере или коде маппинга DTO.
6. **Смотрю `EXPLAIN ANALYZE` и индексы.** Иногда проблема не в количестве запросов, а в одном дорогом запросе.

В тесте можно проверять разумную границу количества запросов, но жёсткий точный счётчик часто хрупок: он зависит от конфигурации, кэшей и версии ORM.

## Способы решения

### 1. Fetch join в DQL

Если страница показывает заказы вместе с клиентами, можно загрузить их одним запросом:

```php
$orders = $em->createQueryBuilder()
    ->select('o', 'c')
    ->from(Order::class, 'o')
    ->join('o.customer', 'c')
    ->where('o.status = :status')
    ->setParameter('status', OrderStatus::Open)
    ->getQuery()
    ->getResult();
```

Это устраняет запрос на каждого клиента.

**Плюсы:** просто и эффективно для связи `ManyToOne` или `OneToOne`.

**Минусы:** объединение двух `OneToMany`/`ManyToMany` коллекций может раздувать набор строк из-за декартова произведения; в результирующем SQL будут повторяться данные родителя. Также нужно внимательно сочетать fetch join коллекций с пагинацией: лимит строк SQL не всегда соответствует лимиту корневых сущностей.

Не следует превращать все связи в `EAGER`: это часто лишь переносит проблему и загружает данные, которые конкретная страница не использует.

### 2. Batch fetch / `EXTRA_LAZY`

Если коллекция нужна не у всех сущностей или нужен ограниченный объём данных, можно использовать пакетную загрузку, например через настройки batch size в поддерживаемой конфигурации Doctrine. ORM будет загружать связи пачками, а не по одной.

`EXTRA_LAZY` полезен для отдельных операций над большой коллекцией, например `count()`, без полной загрузки всех элементов. Но он не гарантирует устранение N+1 для произвольного обхода коллекции.

**Плюсы:** меньше риск получить огромный join; полезно для больших коллекций.

**Минусы:** запросов всё ещё может быть несколько; поведение сложнее предсказать, чем у одного явно написанного запроса; конкретные настройки зависят от версии Doctrine.

### 3. Два явных запроса и группировка по идентификатору

Сначала загружают страницу заказов, затем связанную информацию одним запросом `WHERE ... IN (...)`, после чего собирают результат.

```php
$orders = $orderRepository->findPage($criteria);
$ids = array_map(fn (Order $o) => $o->id(), $orders);

$linesByOrder = $lineRepository->findForOrders($ids);
```

**Плюсы:** контролируемый SQL, нет огромного join; удобно для коллекций и DTO.

**Минусы:** нужна логика сборки результата; легко ошибиться с пустым списком ID или лимитами `IN`; это уже не обязательно полноценная загрузка агрегатов Doctrine, а отдельная read-модель.

### 4. Проекция или DTO-запрос

Для страницы, которой нужны только имя клиента, номер заказа и итог, часто не требуется гидратировать целые сущности:

```php
$rows = $em->createQuery(
    'SELECT new App\ReadModel\OrderRow(o.id, c.name, o.total)
     FROM App\Entity\Order o
     JOIN o.customer c
     WHERE o.status = :status'
)
    ->setParameter('status', OrderStatus::Open)
    ->getResult();
```

**Плюсы:** меньше данных, проще контролировать форму ответа, часто быстрее для read-heavy страниц.

**Минусы:** DTO-запрос не подходит для изменения агрегатов; нужно поддерживать отдельные запросы и read-модели. Это оправдано для экранов чтения, но не должно подменять доменную модель в командах.

### 5. Кэширование

Если связанные данные редко меняются, кэш можно применить на уровне результата или отдельной read-модели.

**Плюсы:** снижает нагрузку при повторных чтениях.

**Минусы:** не исправляет неэффективный первый запрос; появляются вопросы инвалидации, актуальности и ключей кэша. Кэш — не первое средство диагностики N+1.

## Как выбираю

Для `ManyToOne`, которую страница гарантированно показывает, обычно начинаю с fetch join. Для больших коллекций и пагинации чаще выбираю пакетную или двухзапросную загрузку. Для отчётной страницы, которой не нужна доменная логика сущностей, предпочитаю DTO/projection. После изменения повторяю измерения на реалистичном объёме данных и проверяю не только число запросов, но и объём результата, план запроса и общее время.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

Бизнес-валидация в приложении нужна для понятных пользователю ошибок и реализации предметных правил. Ограничения PostgreSQL нужны как **последняя линия защиты данных**. Между проверкой в коде и записью в БД возможна гонка, запись может прийти не через основной сценарий приложения, а баг или ручной SQL способны обойти доменную проверку.

Важно: ограничения БД не заменяют бизнес-валидацию. Например, приложение может заранее проверить уникальность email, чтобы вернуть удобный ответ, но окончательное решение об уникальности принимает БД.

## Основные средства PostgreSQL

### `NOT NULL`

Для обязательных значений:

```sql
CREATE TABLE users (
    id uuid PRIMARY KEY,
    email text NOT NULL
);
```

Если отсутствие значения недопустимо по модели данных, это должно быть явно отражено в схеме. Одной PHP-типизации недостаточно: поле может не пройти через предполагаемый код записи.

### `UNIQUE` и составные ограничения уникальности

Для инвариантов уникальности:

```sql
ALTER TABLE users
    ADD CONSTRAINT users_email_unique UNIQUE (email);
```

Или для составной уникальности:

```sql
ALTER TABLE memberships
    ADD CONSTRAINT one_membership_per_user_team
    UNIQUE (user_id, team_id);
```

В приложении можно предварительно проверить наличие записи, но два параллельных запроса могут одновременно пройти эту проверку. Поэтому при создании пользователя нужно обработать нарушение unique constraint и преобразовать его в понятную доменную или HTTP-ошибку.

Для мягкого удаления можно использовать частичный уникальный индекс:

```sql
CREATE UNIQUE INDEX users_active_email_unique
    ON users (email)
    WHERE deleted_at IS NULL;
```

### `CHECK`

Для ограничений на конкретную строку:

```sql
ALTER TABLE order_lines
    ADD CONSTRAINT positive_quantity CHECK (quantity > 0);
```

Или для ограниченного диапазона:

```sql
ALTER TABLE products
    ADD CONSTRAINT nonnegative_price CHECK (price >= 0);
```

`CHECK` хорош для простых инвариантов, которые можно проверить по значениям строки. Он не предназначен для проверки произвольных связей с другими строками или таблицами; для этого нужны другие механизмы.

### `FOREIGN KEY`

Для ссылочной целостности:

```sql
ALTER TABLE order_lines
    ADD CONSTRAINT order_lines_order_fk
    FOREIGN KEY (order_id)
    REFERENCES orders (id)
    ON DELETE CASCADE;
```

Внешний ключ не даст сохранить строку с несуществующим заказом. Действие `ON DELETE` нужно выбирать осознанно: `CASCADE` удобно, когда дочерняя запись не имеет самостоятельного смысла, но может привести к неожиданному массовому удалению, если границы жизненного цикла выбраны неверно.

### Транзакции и блокировки

Не все правила выражаются обычным `CHECK` или `UNIQUE`. Для многострочных операций используют транзакции и подходящий уровень изоляции, а при необходимости — явные блокировки.

Например, «списать деньги, только если остаток не станет отрицательным» нельзя надёжно реализовать схемой как проверку отдельной строки без корректной синхронизации конкурирующих обновлений. Часто это выражают атомарным SQL-обновлением:

```sql
UPDATE accounts
SET balance = balance - :amount
WHERE id = :id
  AND balance >= :amount;
```

Если обновлена одна строка — списание прошло; если ни одной — условие не выполнилось. Для более сложных сценариев нужны транзакция и, возможно, `SELECT ... FOR UPDATE` или оптимистическая версия.

## Какие ограничения выбирать

- **`NOT NULL`** — обязательные значения.
- **`UNIQUE`** — уникальность, включая составную и частичную.
- **`CHECK`** — простые инварианты строки: положительное количество, допустимый диапазон.
- **`FOREIGN KEY`** — корректные ссылки и политика удаления.
- **Уникальные индексы, транзакции и блокировки** — конкурентные операции, где одной предварительной проверки приложения недостаточно.

Ограничения желательно задавать через миграции и давать им осмысленные имена. При разборе `PDOException` или исключения Doctrine стоит ориентироваться на тип нарушения и имя constraint, а не разбирать текст сообщения БД: текст и детали драйвера могут отличаться.

## Практическое разделение

В приложении я сначала проверяю входные данные и доменные правила, чтобы вернуть понятную ошибку. БД затем обеспечивает инварианты, которые должны сохраняться независимо от пути записи. Например, проверка `email` в форме улучшает обратную связь, а `UNIQUE(email)` гарантирует, что два параллельных запроса не создадут дубликаты.

Не все бизнес-правила нужно переносить в SQL: ограничения на сложный процесс могут быть неудобны для поддержки в виде триггеров или нестандартных конструкций. Но простые правила целостности, которые должны выполняться всегда, разумно дублировать на уровне БД.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

Я бы оптимизировал не запрос «на глаз», а подтверждённый узкий участок. Важно сначала понять, что именно означает «медленно»: большой latency в приложении может быть вызван не только планом PostgreSQL, но и ожиданием соединения, передачей большого результата, блокировкой или внешним вызовом.

## 1. Зафиксировать исходную проблему

Собираю:

- сам SQL и параметры;
- частоту выполнения и долю общей нагрузки;
- p50/p95/p99 latency, число возвращаемых строк и объём данных;
- версию PostgreSQL, схему, индексы и примерный размер таблиц;
- условия, при которых проблема воспроизводится.

Проверяю запрос с типичными параметрами и объёмом данных, близким к production: один и тот же SQL может иметь разные планы для разных значений.

## 2. Найти самые дорогие запросы

Использую `pg_stat_statements`, если он включён:

```sql
SELECT query, calls, mean_exec_time, total_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

Смотрю не только на среднее время: важны общее потраченное время, частота вызовов и хвостовые задержки. `pg_stat_statements` агрегирует запросы, поэтому для конкретных параметров нужны логи, трассировка или воспроизводимый тест.

В логах полезны долгие запросы и сведения об ожиданиях. Также проверяю `pg_stat_activity`: не ждёт ли запрос блокировку и не простаивает ли он из-за другого сеанса.

## 3. Разобрать план выполнения

Запускаю `EXPLAIN`, а для измерения на тестовой или безопасной выборке — `EXPLAIN (ANALYZE, BUFFERS)`:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
```

Смотрю:

- **estimated rows против actual rows** — ошибка оценки может привести к неудачному плану;
- **последовательные и индексные сканирования** — `Seq Scan` сам по себе не плох: для чтения большой доли таблицы он может быть оптимальным;
- **узлы с наибольшим временем и числом строк**;
- **число циклов (`loops`)** — дешёвый узел, вызванный тысячи раз, часто и есть N+1 внутри плана;
- **буферы и чтение с диска** — запрос может быть ограничен I/O;
- сортировки, хеши и временные файлы — не хватает ли памяти или подходящего индекса;
- способ и порядок соединений таблиц;
- фильтры, применённые после чтения большого числа строк;
- фактическую кардинальность результата.

`EXPLAIN ANALYZE` действительно выполняет запрос. Для `UPDATE`/`DELETE` его следует запускать в контролируемой среде или внутри транзакции с последующим rollback, учитывая побочные эффекты. Также он добавляет измерительные накладные расходы, поэтому цифры нужно трактовать осторожно.

## 4. Проверить статистику и ожидания

Если оценки строк сильно расходятся с фактическими, проверяю актуальность статистики (`ANALYZE`/autovacuum), распределение данных и селективность условий. Для перекошенных данных могут потребоваться повышенные statistics targets или extended statistics для коррелирующих столбцов.

Если запрос долго работает, но не расходует CPU и не читает активно данные, проверяю блокировки. Для I/O-bound случая смотрю `BUFFERS`, системные метрики диска и состояние кэша. Для тяжёлых сортировок и хеширования — временные файлы и использование памяти, но не повышаю `work_mem` глобально без оценки конкурентной нагрузки: эта память может использоваться несколькими операциями одного запроса и многими сеансами.

## 5. Исправлять по причине

### Индекс

Если запрос выбирает малую долю строк по фильтру или соединению, может помочь индекс:

```sql
CREATE INDEX CONCURRENTLY orders_status_created_at_idx
    ON orders (status, created_at);
```

Порядок колонок в составном индексе важен; он должен соответствовать реальным фильтрам и сортировкам. Для частого узкого сценария иногда уместен частичный индекс:

```sql
CREATE INDEX CONCURRENTLY active_orders_created_at_idx
    ON orders (created_at)
    WHERE status = 'active';
```

`CREATE INDEX CONCURRENTLY` уменьшает блокировку записи при создании, но имеет ограничения и тоже создаёт нагрузку. Индексы ускоряют часть чтений, но занимают место и замедляют `INSERT`, `UPDATE`, `DELETE`, поэтому нельзя добавлять их без подтверждённого сценария.

### SQL и объём чтения

- выбираю только нужные колонки вместо `SELECT *`;
- фильтрую как можно раньше;
- проверяю, не оборачивает ли условие индексируемое поле функцией или не приводит ли неявное преобразование типов к неэффективному плану;
- устраняю лишние соединения и дублирование строк;
- для постраничной выдачи на больших смещениях рассматриваю keyset pagination вместо большого `OFFSET`;
- проверяю, можно ли заменить повторные запросы пакетной выборкой.

Не переписываю подзапрос в join или CTE автоматически: современные версии PostgreSQL могут оптимизировать эти формы одинаково или иначе в зависимости от запроса. Решение принимаю по плану и измерениям.

### Данные и схема

Проверяю, не сканируется ли слишком большая таблица, не раздулась ли она, достаточно ли часто работает autovacuum и соответствуют ли типы данным. Для очень больших таблиц с естественным разбиением по времени или диапазонам может помочь partitioning, но он добавляет требования к ключам, планам и обслуживанию и не является универсальной заменой индексу.

## 6. Проверить результат

После каждого существенного изменения сравниваю тот же запрос на одинаковых данных:

- latency и пропускную способность;
- actual plan, число прочитанных буферов и возвращённых строк;
- потребление CPU/I/O;
- влияние на запись и конкурирующие запросы.

Типичные причины медленных запросов — неподходящий или отсутствующий индекс, неверная оценка селективности, чтение слишком большого объёма данных, сортировка большого набора, перекошенные данные, N+1 на уровне приложения, устаревшая статистика, блокировки и перегруженный диск. Индекс — лишь один из вариантов; сначала план должен показать, что именно является причиной.

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

**Агрегат** в DDD — это группа доменных объектов, которую мы рассматриваем как единое целое при выполнении бизнес-операций и сохранении согласованности данных. У агрегата есть **корень (Aggregate Root)**: внешний код обращается к агрегату через него, а корень защищает инварианты и управляет изменениями дочерних сущностей.

## Пример: заказ

Предположим, у заказа есть строки, и по правилам магазина:

- нельзя добавить строку в отменённый заказ;
- количество в строке должно быть положительным;
- итоговая сумма должна соответствовать строкам.

Тогда `Order` может быть корнем агрегата, а `OrderLine` — дочерней сущностью:

```php
final class Order
{
    /** @var list<OrderLine> */
    private array $lines = [];

    private OrderStatus $status = OrderStatus::Draft;

    public function addLine(ProductId $productId, int $quantity, Money $price): void
    {
        if ($this->status !== OrderStatus::Draft) {
            throw new DomainException('Нельзя менять оформленный заказ.');
        }

        if ($quantity <= 0) {
            throw new DomainException('Количество должно быть положительным.');
        }

        $this->lines[] = new OrderLine($productId, $quantity, $price);
    }

    public function total(): Money
    {
        return array_reduce(
            $this->lines,
            fn (Money $sum, OrderLine $line) => $sum->add($line->subtotal()),
            Money::zero(),
        );
    }
}
```

Приложение загружает заказ, вызывает метод корня и сохраняет его. Оно не должно независимо менять `OrderLine`, обходя правила заказа.

## Как определяю границы

Я начинаю не с таблиц БД, а с бизнес-инвариантов и сценариев:

1. **Какие правила должны соблюдаться сразу после одной операции?** Объекты, нужные для соблюдения одного инварианта, часто должны входить в один агрегат.
2. **Какие изменения должны быть атомарными?** Если правило требует согласованно обновить несколько объектов, проверяю, действительно ли им нужно находиться в одной транзакционной границе.
3. **Кто владеет жизненным циклом объектов?** Если дочерний объект не имеет самостоятельного смысла без корня, это аргумент включить его в агрегат.
4. **Насколько велики и конкурентны записи?** Агрегат часто становится единицей загрузки, сохранения и блокировки. Чрезмерно большой агрегат ухудшает производительность и увеличивает конфликты при параллельных изменениях.

Обычно связь между агрегатами моделируют через идентификаторы, а не через прямое изменение чужих объектов. Если, например, заказу нужна информация о товаре, он может хранить `ProductId` и цену на момент покупки, а не включать весь `Product` в свой агрегат. Так изменение каталога не требует загружать или сохранять каждый связанный заказ.

## Типичная ошибка

Частая ошибка — делать агрегат слишком большим: например, включить в `Order` каталог, покупателя, платежи и все доставочные события, потому что между ними есть связи в схеме БД. Тогда чтение и изменение заказа загружают много лишних данных, а любая операция получает чрезмерно широкую транзакционную и конкурентную границу.

Обратная ошибка — считать корнем каждую таблицу и менять дочерние записи независимо, из-за чего инварианты агрегата обходятся. Границы лучше выбирать по правилам согласованности и реальным командам приложения, а не по диаграмме таблиц. Не каждый связанный объект обязан входить в один агрегат; иногда согласованность между агрегатами обеспечивают отдельным процессом и событиями.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

Без дополнительной защиты оба процесса могут прочитать одну и ту же версию агрегата, внести изменения и сохранить их. Один из вариантов:

1. Процесс A и процесс B загружают заказ с остатком `10`.
2. A списывает `3`, B списывает `4`.
3. A сохраняет остаток `7`, затем B сохраняет `6`, опираясь на старое значение `10`.

В итоге изменение A потерялось: при последовательном исполнении остаток должен был бы стать `3`. Это называется **lost update**. Конкретное поведение зависит от SQL, транзакций, режима блокировок и того, как ORM формирует `UPDATE`; рассчитывать на то, что Doctrine автоматически защитит бизнес-инвариант, нельзя.

## Оптимистическая блокировка

Если конфликты редки и допустимо отклонить одну из конкурирующих команд, обычно выбираю optimistic locking. В Doctrine для этого можно добавить версионное поле:

```php
#[ORM\Version]
#[ORM\Column]
private int $version = 1;
```

При сохранении Doctrine проверяет и увеличивает версию. Если другая транзакция уже изменила агрегат, обновление не затронет ожидаемую строку, и Doctrine сообщит о конфликте, обычно через `OptimisticLockException`.

Приложение должно явно решить, что делать дальше:

- вернуть клиенту конфликт и предложить повторить операцию;
- перечитать агрегат и повторно выполнить команду, если это безопасно;
- отправить задачу на повторную обработку.

Автоматический retry опасен, если операция уже произвела внешний эффект или её повторная семантика не определена.

## Пессимистическая блокировка

Если конфликты часты или требуется сериализовать критическую операцию, можно блокировать строку внутри транзакции:

```php
$em->wrapInTransaction(function () use ($orderId): void {
    $order = $this->orders->getForUpdate($orderId);

    $order->reserve(/* ... */);

    $em->flush();
});
```

Репозиторий может использовать `LockMode::PESSIMISTIC_WRITE` или SQL `SELECT ... FOR UPDATE` — конкретный API зависит от версии Doctrine. Блокировка удерживается до завершения транзакции.

Это уменьшает вероятность конфликта при записи, но заставляет остальные процессы ждать, повышает риск таймаутов и взаимных блокировок. Транзакции нужно держать короткими и не выполнять внутри них сетевые вызовы.

## Инварианты на уровне SQL

Для простых конкурентных операций иногда надёжнее сделать условное обновление одной атомарной командой:

```sql
UPDATE inventory
SET quantity = quantity - :amount
WHERE product_id = :id
  AND quantity >= :amount;
```

Если обновлена одна строка, резервирование удалось; если ноль — товара недостаточно или запись отсутствует. Такая проверка и изменение происходят атомарно на стороне PostgreSQL.

Это хорошо подходит для простого счётчика или остатка, но может обходить доменную логику агрегата. Поэтому её нужно использовать как осознанную атомарную операцию с тестами, а не как произвольный способ обновлять сущность в обход модели.

## Как проектирую

Сначала определяю, какой конкурентный исход допустим. Затем выбираю защиту:

- **optimistic lock** — обычно для редких конфликтов и команд, которые можно безопасно отклонить или повторить;
- **pessimistic lock** — для часто конкурирующих критических операций;
- **атомарный `UPDATE` с условием** — для локального простого инварианта, который можно выразить в одном SQL-операторе.

Кроме того, проверяю:

- что все изменения агрегата идут через его корень;
- что транзакционная граница соответствует одной команде приложения;
- что обработка конфликтов понятна клиенту;
- что повторы идемпотентны, особенно в очередях;
- что код не держит блокировку во время обращения к внешним сервисам.

Само понятие агрегата задаёт логическую границу согласованности, но не решает конкурентные конфликты автоматически: для этого нужны подходящие транзакции, блокировки или контроль версии.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

Доменное событие фиксирует уже произошедший значимый факт в предметной области: например, `OrderPlaced`, `PaymentReceived` или `UserRegistered`. Это не просто техническое уведомление вроде `SendEmail`; событие формулируется языком домена и обычно не содержит команду что-либо сделать.

## Когда публиковать

Событие возникает в момент успешного выполнения доменной операции. Например:

```php
final class Order
{
    /** @var list<object> */
    private array $events = [];

    public function place(): void
    {
        if ($this->status !== OrderStatus::Draft) {
            throw new DomainException('Заказ уже оформлен.');
        }

        $this->status = OrderStatus::Placed;
        $this->events[] = new OrderPlaced($this->id);
    }

    /** @return list<object> */
    public function releaseEvents(): array
    {
        $events = $this->events;
        $this->events = [];

        return $events;
    }
}
```

Событие создаётся, когда доменное изменение произошло, но его побочные действия должны выполняться отдельно. Например, `OrderPlaced` может привести к отправке письма, обновлению поискового индекса или резервированию товара.

События обычно содержат идентификаторы и важные неизменяемые факты, а не Doctrine-сущности: так их проще сериализовать, хранить и передавать между процессами.

## Обработка

Есть несколько уровней доставки:

- **Внутрипроцессная синхронная обработка** через dispatcher или Messenger. Просто, удобно для реакций внутри одного процесса, но обработчик может увеличить время ответа и выполнение события зависит от жизни текущего процесса.
- **Асинхронная обработка через Messenger и транспорт**. Запрос быстрее завершается, обработчики масштабируются отдельно, можно настроить повторы и failure transport. Цена — eventual consistency, задержки, дублирование и необходимость эксплуатации worker’ов.
- **Outbox и отдельный publisher**. Событие сначала надёжно записывается в ту же БД-транзакцию, что и изменение агрегата, а затем доставляется наружу.

Обработчики должны быть устойчивы к повторному выполнению. Очередь обычно обеспечивает доставку «как минимум один раз», поэтому для внешних эффектов нужны идемпотентность, ключи дедупликации или операции вида upsert. Повторы и окончательно неудачные сообщения нужно логировать, мониторить и направлять в failure transport.

## Связь с транзакцией БД

Наивная схема опасна:

```text
1. Изменить и сохранить заказ.
2. Отправить событие в брокер.
```

Если процесс упадёт между шагами, заказ сохранится, но событие потеряется. Если сначала отправить событие, а транзакция БД затем откатится, обработчик увидит факт, которого в БД не существует.

**`DispatchAfterCurrentBus` сам по себе не делает запись в БД и публикацию в брокер атомарными.** Он может помочь с порядком обработки сообщений, но не устраняет окно сбоя между двумя системами.

Надёжный вариант для важных событий — **transactional outbox**:

1. В одной транзакции сохранить агрегат и запись outbox с событием.
2. После коммита отдельный процесс читает outbox и публикует событие в транспорт.
3. Отметить событие доставленным или удалить запись после успешной публикации.
4. Обработчики дедуплицируют повторные доставки.

Упрощённая структура:

```text
BEGIN;
UPDATE orders ...;
INSERT INTO outbox (event_id, type, payload) VALUES (...);
COMMIT;
```

Так состояние агрегата и намерение опубликовать событие фиксируются атомарно. Но outbox не даёт магической доставки «ровно один раз»: процесс может упасть после публикации, но до отметки о доставке, поэтому событие может уйти повторно. Именно поэтому получатели должны быть идемпотентными.

Для необязательного внутреннего уведомления можно выбрать более простой механизм, принимая небольшой риск потери. Если же событие запускает критичный бизнес-процесс или должно обновить другие системы, outbox обычно оправдан.

## Что события дают и усложняют

**Решают:** ослабляют прямую связанность между компонентами, позволяют добавлять реакции на факт без перегрузки основного сценария, дают основу для асинхронной обработки и интеграции с другими контекстами.

**Создают:** eventual consistency, сложность порядка событий, повторов и компенсаций, трудности диагностики по распределённым логам, необходимость версионировать сообщения и поддерживать совместимость старых потребителей.

Поэтому я использую доменные события для значимых фактов и независимых реакций на них, но не заменяю ими прямой вызов там, где операция должна немедленно вернуть результат или обеспечить строгую согласованность.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

В DDD **Entity** и **Value Object** различаются прежде всего тем, что определяет их идентичность.

## Entity и Value Object

**Entity** сохраняет свою идентичность, даже если её атрибуты меняются. Обычно у неё есть устойчивый идентификатор:

```php
final class User
{
    public function __construct(
        private UserId $id,
        private EmailAddress $email,
    ) {}

    public function changeEmail(EmailAddress $email): void
    {
        $this->email = $email;
    }

    public function id(): UserId
    {
        return $this->id;
    }
}
```

Пользователь остаётся тем же пользователем после смены email. Чтобы понять, та же ли это сущность, сравнивают `UserId`, а не все её поля.

**Value Object** не имеет отдельной идентичности: он описывает значение, сравнивается по содержимому и часто делается неизменяемым:

```php
final readonly class EmailAddress
{
    private function __construct(public string $value) {}

    public static function fromString(string $value): self
    {
        $value = mb_strtolower(trim($value));

        if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException('Некорректный email');
        }

        return new self($value);
    }
}
```

Два объекта `EmailAddress` с одинаковым нормализованным значением эквивалентны. Если email пользователя изменился, это не значит, что прежний `EmailAddress` «превратился» в новый: обычно создаётся новое значение.

## Как решаю, что моделировать

Я задаю предметные вопросы, а не ориентируюсь на то, есть ли соответствующая таблица:

- Сохраняется ли идентичность концепции при изменении её атрибутов?
- Нужно ли ссылаться на неё из разных частей модели независимо от её текущих значений?
- Имеет ли она собственный жизненный цикл и операции?
- Или это просто описываемое значение, которое можно заменить другим эквивалентным значением?

Например, `Money` обычно удобно моделировать как Value Object: сумма и валюта вместе определяют его смысл. `Order` — Entity, потому что он сохраняет идентичность на протяжении жизненного цикла. А `OrderLine` может быть Entity внутри агрегата заказа, если на неё нужно ссылаться и менять её независимо от других строк; в более простой модели она может быть Value Object. Решение зависит от правил и сценариев домена, а не от универсального списка типов.

Также наличие первичного ключа в БД само по себе не делает концепцию доменной Entity. База может использовать технический ID для хранения, тогда как в домене объект остаётся значением.

## Единый язык

**Единый язык (Ubiquitous Language)** — это общая для экспертов предметной области и разработчиков терминология, используемая при обсуждении требований и в модели кода. Он должен отражать реальные понятия и различия домена, а не быть просто набором технических названий.

Например, если бизнес различает «создать черновик», «оформить заказ» и «отправить заказ», код лучше отражает эти операции явно:

```php
$order->place();
$order->dispatch();
```

вместо универсального:

```php
$order->setStatus(2);
```

Язык влияет на названия классов, методов, событий и команд: `PlaceOrder`, `OrderPlaced`, `Money`, `AccountBalance`. Это делает код ближе к бизнес-правилам и помогает заметить, когда два похожих слова обозначают разные понятия. При этом единый язык может различаться между ограниченными контекстами: одно и то же слово в продажах и бухгалтерии не обязательно должно обозначать одну модель или один класс.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

В разных проектах доменный порт репозитория размещают в `Domain`, если это часть модели, или в `Application`, если это исключительно потребность use case. Существенно не расположение файла, а то, что интерфейс находится внутри границы, а реализация — снаружи.

### Domain

Сущности, Value Objects, агрегаты, доменные сервисы, события и доменные правила. Домен не должен импортировать `Symfony\Component\...`, `Doctrine\ORM\...` или классы инфраструктурного транспорта.

### Application

Сценарии приложения: обработчики команд, координация репозиториев и других портов, транзакционная граница, DTO входа и результата. Здесь задаётся, **что выполнить**, но детали БД, HTTP и очереди остаются за адаптерами.

Например, `PlaceOrder` зависит от интерфейса `OrderRepository`, а не от `DoctrineOrderRepository`.

### Infrastructure

Адаптеры к технологиям: реализации репозиториев, Doctrine-маппинг, клиенты внешних API, отправка почты, транспорт Messenger, конфигурация DI. Этот слой может импортировать Doctrine и Symfony.

### Presentation

Входные точки и преобразование протокола: Symfony-контроллеры, консольные команды, consumer’ы сообщений. Они преобразуют HTTP-запрос или сообщение в команду application-слоя и преобразуют результат в HTTP-ответ или ack/retry.

## Где находятся конкретные компоненты

- **Doctrine:** реализация репозитория и ORM-маппинг — в Infrastructure. Если доменные классы размечены Doctrine-атрибутами, это уменьшает количество отдельных маппингов, но создаёт техническую зависимость домена от ORM. Для строгих границ маппинг держат вне доменной модели; для более прагматичной архитектуры иногда принимают зависимость на атрибуты, осознавая компромисс.
- **Symfony-контроллер:** Presentation. Он не должен содержать бизнес-правила и напрямую строить SQL.
- **Обработчик очереди:** сам Messenger handler — адаптер на границе Presentation/Infrastructure: получает транспортное сообщение, преобразует его и вызывает application use case. Бизнес-операция остаётся в Application/Domain, а не в consumer’е.
- **Репозиторий:** интерфейс принадлежит внутреннему слою, реализация Doctrine — внешнему. Dependency Injection связывает интерфейс с реализацией.

Схема вызовов может выглядеть так:

```text
HTTP controller ─┐
Queue handler ───┼──> Application use case ──> Domain
                 │              │
                 └──────────────┴──> port interface
                                      ↑
                           Doctrine implementation
```

## Как проверять границы

1. **Правила импортов.** Архитектурные тесты, например Deptrac или PHPArkitect, могут запрещать `Domain` импортировать Symfony и Doctrine и задавать допустимые направления между namespaces.
2. **Статический анализ.** PHPStan или Psalm ловят ошибки типов и помогают сделать зависимости явными, но сами по себе не доказывают чистоту архитектуры.
3. **Code review и соглашения.** Контроллеры и queue handlers должны оставаться тонкими; доступ к инфраструктуре идёт через адаптеры и порты.
4. **Тесты на границах.** Use case можно тестировать с подменами портов, а Doctrine-адаптер — отдельными интеграционными тестами.
5. **Проверка транзитивных зависимостей.** Недостаточно убедиться, что домен не импортирует Symfony напрямую: нежелательная зависимость может прийти через общий класс или пакет.

При этом не стоит создавать слой и интерфейс для каждого класса. Граница полезна, когда она защищает доменную логику от меняющихся внешних деталей, а не просто увеличивает число абстракций.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

Я бы строил набор вокруг критичных бизнес-сценариев и реальных рисков, а не стремился к максимальному проценту покрытия. Для Symfony-приложения с PostgreSQL это обычно **пирамида с большим числом быстрых тестов и меньшим числом полноценных интеграционных и системных**.

## Пирамида тестов

### 1. Unit-тесты домена

Проверяют агрегаты, Value Objects и бизнес-правила без Symfony, Doctrine и БД:

```php
public function testCannotAddLineToPlacedOrder(): void
{
    $order = OrderMother::placed();

    $this->expectException(OrderAlreadyPlaced::class);

    $order->addLine(ProductIdMother::valid(), 1, MoneyMother::valid());
}
```

Они должны быть быстрыми и проверять поведение, а не внутреннюю структуру объекта. Для чистого доменного кода обычно не нужен контейнер Symfony.

### 2. Тесты use case

Проверяют координацию сценария приложения: вызов репозитория, изменение агрегата, публикацию события, реакцию на ожидаемые ошибки.

Здесь можно использовать подмены внешних портов — например, spy для `EventBus` или fake-репозиторий, если сценарий не проверяет SQL. Но не стоит мокать каждую внутреннюю сущность: это часто связывает тест с реализацией вместо поведения.

### 3. Интеграционные тесты с PostgreSQL

Они проверяют, что Doctrine mapping, репозитории, миграции, ограничения, транзакции и запросы действительно работают с PostgreSQL. Для этого я использовал бы именно PostgreSQL, а не SQLite: различия в типах, ограничениях, JSON, индексах и SQL могут скрывать проблемы.

Такие тесты особенно важны для:

- custom DBAL types и embeddable;
- сложных DQL/SQL-запросов;
- уникальных ограничений и внешних ключей;
- optimistic locking и транзакционных сценариев;
- миграций и специфичного для PostgreSQL поведения.

### 4. Функциональные тесты Symfony

Проверяют HTTP-границу через `KernelBrowser`: маршрутизацию, security, сериализацию, валидацию, преобразование ошибок и работу контроллера с контейнером. БД можно поднимать тестовую и очищать транзакциями или fixture-механизмом.

В таком тесте полезно пройти путь через Symfony, но не обязательно подключать все реальные внешние сервисы.

### 5. Небольшое число end-to-end и контрактных тестов

E2E-тесты проверяют несколько компонентов в связке, но они медленнее и хрупче. Их стоит оставить для ключевых пользовательских потоков. Для интеграций с внешними API могут быть полезны контрактные тесты или проверка сериализуемости сообщений.

## Что мокать, а что нет

**Обычно не мокать:**

- объекты доменной модели;
- простые Value Objects;
- коллекции и DTO;
- код, чьё поведение удобно проверить напрямую.

**Мокать или подменять в unit-тестах:**

- внешние системы — HTTP-клиенты, почту, брокер;
- время, случайность, генерацию ID, если результат должен быть детерминирован;
- порты приложения, когда проверяется сценарий, а не инфраструктурный адаптер.

Для репозитория вместо глубокого mock обычно выбираю один из двух подходов:

- fake-реализацию для unit-тестов use case, если важен сценарий;
- настоящий Doctrine-репозиторий с PostgreSQL в интеграционном тесте, если важен запрос или маппинг.

Не стоит проверять взаимодействия моками там, где важнее наблюдаемое поведение. Например, для регистрации может быть полезно проверить, что пользователь действительно сохранился, а не только что был вызван конкретный метод с конкретным объектом.

## Быстрые и стабильные тесты

- Запускаю быстрые unit-тесты отдельно и раньше в CI, интеграционные — своим набором; при необходимости использую параллельное выполнение.
- Избегаю сна, реального времени и случайных данных без фиксированного seed. Время и генераторы делаю контролируемыми зависимостями.
- Создаю компактные fixture/factory-объекты с осмысленными значениями, а не огромный общий набор данных.
- Для БД использую отдельную тестовую схему или контейнер PostgreSQL, запускаю миграции в CI и очищаю состояние после тестов. Важно не запускать тесты против случайно выбранной базы.
- Не полагаюсь на порядок тестов: каждый должен подготавливать свои данные и убирать последствия.
- Избегаю чрезмерного `refresh database` перед каждым тестом, если это становится узким местом; можно использовать транзакционные стратегии очистки, учитывая, что тестируемый код может сам коммитить или запускать асинхронную обработку.
- Для очередей и внешних интеграций использую тестовый транспорт, fake или тестовый сервер, чтобы тест не зависел от сети.
- Наблюдаю за нестабильными тестами и исправляю причину, а не просто перезапускаю их до «зелёного» результата.

Итог: доменную логику проверяю дешёвыми unit-тестами, взаимодействие слоёв и SQL — интеграционными тестами на PostgreSQL, HTTP и конфигурацию Symfony — функциональными, а сквозные сценарии оставляю для небольшого набора E2E. Моки применяю в основном на границах системы, а не вместо проверки собственного кода и реальной БД.

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

При конкурентном изменении одной записи возможны **потерянное обновление**, нарушение бизнес-инварианта, чтение устаревших данных и конфликты на уникальных ограничениях. Конкретный риск зависит от того, как приложение читает и записывает данные, а также от уровня изоляции транзакций.

### Потерянное обновление

Допустим, у счёта баланс `100`. Два запроса читают его одновременно:

```text
A читает 100, собирается вычесть 30
B читает 100, собирается вычесть 20
A записывает 70
B записывает 80
```

Итог — `80`, хотя при последовательном исполнении должен был бы получиться `50`: обновление A потерялось.

## Основные способы защиты

### 1. Optimistic locking — версия строки

Подходит, когда конфликты редки и операция может быть отклонена или безопасно повторена. Добавляется версия:

```sql
ALTER TABLE accounts ADD COLUMN version integer NOT NULL DEFAULT 1;
```

Обновление выполняется с проверкой версии:

```sql
UPDATE accounts
SET balance = :new_balance,
    version = version + 1
WHERE id = :id
  AND version = :expected_version;
```

Если обновлено ноль строк, запись успел изменить кто-то другой. Приложение перечитывает состояние и решает, показать конфликт или повторить операцию.

В Doctrine для этого есть version field:

```php
#[ORM\Version]
#[ORM\Column]
private int $version = 1;
```

**Плюсы:** нет длительных блокировок; хорошо масштабируется при редких конфликтах.  
**Минусы:** вызывающая сторона должна обрабатывать конфликт; не всякую команду безопасно повторять — особенно если до повтора уже был внешний эффект.

### 2. Pessimistic locking — блокировка записи

Если конфликты часты или критическую операцию нужно сериализовать, запись блокируют внутри короткой транзакции, например через `SELECT ... FOR UPDATE`:

```sql
BEGIN;

SELECT balance
FROM accounts
WHERE id = :id
FOR UPDATE;

UPDATE accounts
SET balance = balance - :amount
WHERE id = :id;

COMMIT;
```

В Doctrine можно использовать пессимистическую блокировку через EntityManager/LockMode; конкретный API зависит от версии.

**Плюсы:** второй процесс ждёт и затем работает с актуальным состоянием.  
**Минусы:** ожидания, таймауты и риск deadlock; длительные транзакции снижают пропускную способность. Внутри такой транзакции нельзя обращаться к медленным внешним сервисам.

Нужно также правильно выбирать уровень изоляции: например, в PostgreSQL `READ COMMITTED` не делает произвольную последовательность «прочитать — вычислить — записать» атомарной. Более строгая изоляция может приводить к serialization failure, которую приложение должно обработать и при необходимости повторить.

### 3. Атомарное условное обновление

Для простого инварианта полезно выполнить проверку и изменение одним SQL-оператором. Например, не списывать больше доступного остатка:

```sql
UPDATE accounts
SET balance = balance - :amount
WHERE id = :id
  AND balance >= :amount;
```

Если обновлена одна строка — списание удалось; если ноль — условие не выполнено либо записи нет. Проверка и изменение атомарны для этой строки.

**Плюсы:** мало round trips, нет отдельного окна между чтением и записью, хорошо подходит для счётчиков и остатков.  
**Минусы:** логика становится SQL-специфичной; такой путь может обходить обычную загрузку и проверки агрегата. Результат нужно корректно преобразовать в доменный исход операции.

### 4. Ограничения и уникальные индексы

Для инвариантов вроде «email уникален» окончательную защиту должна обеспечивать база:

```sql
ALTER TABLE users
ADD CONSTRAINT users_email_unique UNIQUE (email);
```

Предварительная проверка в приложении улучшает пользовательский ответ, но не защищает от гонки: две транзакции могут одновременно решить, что значение свободно. Нарушение ограничения нужно обработать и преобразовать в понятную ошибку.

### Как выбираю

- **Редкие конфликты при редактировании объекта** — optimistic locking и понятный ответ о конфликте.
- **Часто конкурирующая критическая операция**, где нужно последовательно обработать изменения, — короткая транзакция с пессимистической блокировкой.
- **Простой атомарный инвариант** — условный `UPDATE`.
- **Уникальность и ссылочная целостность** — ограничения БД независимо от проверок в приложении.

Во всех вариантах я проверяю поведение при повторе команды. Если операция запускается через очередь, она должна быть идемпотентной или иметь механизм дедупликации. Для внешнего эффекта — например, списания у платёжного провайдера — одной транзакции PostgreSQL недостаточно; нужны отдельные средства согласования, такие как idempotency key и, в критичных сценариях, transactional outbox.

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

У меня нет собственной рабочей истории с коммерческими релизами, поэтому опишу процесс, который выбрал бы для команды. Он рассчитан на регулярные поставки и небольшую или среднюю команду; конкретные правила стоит адаптировать под частоту релизов и требования продукта.

## От задачи до ветки

После уточнения требований и критериев приёмки создаю короткоживущую ветку от актуального `main`:

```text
feature/APP-123-add-order-export
fix/APP-456-handle-expired-token
```

Ветка связана с задачей, а не с релизом или человеком. Работа небольшими порциями упрощает ревью и снижает вероятность конфликтов. Долгоживущие feature-ветки стараюсь не использовать: они долго расходятся с `main` и делают интеграцию рискованнее.

Для команды с непрерывной поставкой я предпочёл бы trunk-based подход: небольшие PR быстро попадают в `main`, а незавершённые возможности скрываются feature flags. Если релизы планируются реже и есть отдельная стабилизационная фаза, можно добавить release-ветку на этот период, но не держать параллельные ветки постоянно без необходимости.

## Коммиты

Коммиты делаю небольшими и логически цельными: изменение и его тесты — вместе. Сообщение отвечает на вопрос «что изменилось и зачем», например:

```text
feat(orders): add CSV export
fix(auth): reject expired refresh tokens
```

Формат Conventional Commits полезен, если на его основе автоматизируют changelog или версионирование, но сам по себе не гарантирует хорошую историю. Важнее, чтобы сообщение было конкретным, а случайные форматирования и несвязанные изменения не попадали в один коммит.

Перед PR запускаю локально релевантные проверки: тесты, статический анализ, форматирование и линтер. Не стоит полагаться только на локальную среду — окончательное решение принимает CI на чистом окружении.

## Pull request и ревью

PR должен быть небольшим и содержать:

- контекст и ссылку на задачу;
- краткое описание решения;
- важные компромиссы;
- тесты и миграции;
- при необходимости скриншоты или инструкцию для проверки.

Ревьюер смотрит на корректность, инварианты, безопасность, обратную совместимость, обработку ошибок и тестируемость, а не только на стиль. Автоматические проверки снимают рутинные замечания. Для значимой архитектурной или опасной миграции я бы просил дополнительного владельца соответствующей области.

Я предпочитаю не затягивать PR и не требовать много формальных approve для простых изменений. Для рискованных изменений полезны feature flag, план выката и план отката.

## CI, слияние и релиз

CI на PR запускает тесты и анализ кода; при необходимости — интеграционные тесты с PostgreSQL. После успешного ревью ветка обновляется относительно `main`, затем сливается. `Squash merge` даёт компактную историю по задаче; сохранение отдельных коммитов полезнее, если они осмысленны и важны для bisect. Выбор зависит от соглашений команды.

Релиз создаю из проверенного состояния `main`: обычно это тег с версией и автоматически собранный артефакт. Миграции БД должны быть совместимы с порядком выката приложения: часто используют expand-and-contract — сначала добавляют совместимую схему, потом выкатывают код, а удаление старой схемы делают отдельным шагом.

После деплоя проверяю метрики, ошибки и ключевые пользовательские сценарии. Для постепенного или рискованного изменения использую canary/feature flag, если инфраструктура это поддерживает. Откат приложения не всегда откатывает данные или миграцию, поэтому план восстановления нужно продумывать отдельно.

Такой процесс ограничивает размер изменений, делает проверки повторяемыми и позволяет быстро доставлять код, не превращая каждую поставку в большой интеграционный риск.

## Как формулировать замечания

Я стараюсь писать конкретно: указать проблему, возможное последствие и предложить вариант или вопрос.

- **Blocker / must fix:** вероятный баг, нарушение безопасности, потеря данных, поломка совместимости или критичный пробел в проверках.
- **Важно, но не блокирует само по себе:** риск производительности, сложность сопровождения, существенное упущение в обработке ошибок.
- **Предложение / nit:** стиль или альтернативный вариант, который не влияет на корректность.
- **Вопрос:** если контекст неясен и я не уверен, что это ошибка.

Например: «Если два запроса одновременно пройдут эту проверку, оба могут создать запись. Можно ли опереться на `UNIQUE`-ограничение и обработать конфликт?»

Я избегаю расплывчатого «это плохо» и категоричных формулировок без объяснения. Замечания о стиле лучше автоматизировать линтером и formatter’ом.

## На что смотрю в первую очередь

1. **Корректность и инварианты:** что происходит с граничными случаями, конкурентными запросами, `null`, повторной доставкой задачи?
2. **Безопасность и данные:** авторизация, валидация входа, SQL-инъекции, утечки секретов и персональных данных.
3. **Поведение и ошибки:** корректные транзакции, rollback, исключения, идемпотентность и совместимость API.
4. **Производительность:** N+1, лишние запросы, большие выборки, потенциально дорогие циклы.
5. **Тесты и читаемость:** покрывают ли тесты поведение и можно ли понять намерение кода.
6. **Архитектура:** не нарушает ли изменение важные границы и не добавляет ли неоправданную связанность.

Начинаю с наиболее рискованных частей diff, а не с мелких замечаний. Стараюсь учитывать и контекст вне изменённых строк, если он необходим для понимания поведения.

## При разногласии

Сначала уточняю цель и ограничения: возможно, автор знает о компромиссе, которого не видно из diff. Затем обсуждаю последствия и требования — например, надёжность против сложности, а не «мой стиль против твоего». Если спор можно снять тестом, метрикой или коротким экспериментом, предлагаю это сделать.

Для необязательного предложения можно оставить решение автору. Если речь о блокирующем риске, обращаюсь к согласованным командным правилам или прошу мнение владельца компонента. После решения фиксирую вывод в PR или документации, если он важен для будущих изменений.

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

В PostgreSQL нет команды или конструкции `FORCE INDEX` — это распространённая путаница с MySQL. В PostgreSQL планировщик сам выбирает план доступа: последовательное сканирование, индексное сканирование, bitmap scan и другие варианты. Обычно ему не следует без необходимости навязывать использование индекса: для небольшой таблицы или запроса, читающего значительную часть строк, `Seq Scan` может быть быстрее.

Для диагностики можно временно отключить некоторые типы планов в текущей сессии:

```sql
SET LOCAL enable_seqscan = off;
```

Это **не эквивалент `FORCE INDEX`**: настройка лишь делает последовательное сканирование нежелательным для планировщика, не указывает конкретный индекс и не гарантирует его использование. Применять её в production как постоянное решение обычно не стоит.

Если планировщик выбирает неудачный план, я сначала проверяю его через `EXPLAIN (ANALYZE, BUFFERS)` и выясняю причину: актуальность статистики, оценки числа строк, селективность условий, индексы и форму запроса. Подсказку можно использовать как временный диагностический эксперимент; для управления планами существуют сторонние расширения, например `pg_hint_plan`, но это дополнительная зависимость, а не штатный синтаксис PostgreSQL.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

Утверждение требует оговорки: **Doctrine ORM поддерживает составные первичные ключи**, но у них есть ограничения, поэтому их обычно избегают там, где они не несут важного смысла.

Например, можно описать таблицу-связку с ключом из двух внешних ключей:

```php
#[ORM\Entity]
#[ORM\Id]
#[ORM\ManyToOne(targetEntity: User::class)]
private User $user;

#[ORM\Id]
#[ORM\ManyToOne(targetEntity: Role::class)]
private Role $role;
```

Точный синтаксис зависит от версии Doctrine. В таком случае идентификатор сущности — пара `User` и `Role`.

Составной ID **не поддерживается так же удобно и универсально, как одиночный**. В частности, он усложняет:

- поиск сущности по ID и передачу идентификатора через слои приложения;
- генерацию идентификатора: автоматическая генерация составного ключа ограничена, обычно все его части задаёт приложение;
- ссылки на сущность в других связях;
- репозитории, DTO, сериализацию и кэширование;
- гидратацию и тестирование;
- использование ассоциации как ключа карты в Unit of Work.

Поэтому в новых проектах часто вводят суррогатный первичный ключ, а бизнес-уникальность обеспечивают отдельным ограничением:

```sql
CREATE TABLE user_roles (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id bigint NOT NULL REFERENCES users(id),
    role_id bigint NOT NULL REFERENCES roles(id),
    CONSTRAINT user_roles_user_role_unique UNIQUE (user_id, role_id)
);
```

Суррогатный ключ упрощает работу ORM и связи с этой записью, а `UNIQUE (user_id, role_id)` не даёт создать дубликат пары. В PHP для такой сущности появляется простой `id`, вместо передачи пары значений повсюду.

Составной ID всё же уместен, когда он естественно отражает идентичность записи и не создаёт неудобных ссылок — например, в небольшой таблице-связке без дополнительного жизненного цикла. Если же у связи появляются собственные данные, поведение или ссылки из других таблиц, часто удобнее моделировать её отдельной сущностью с суррогатным ID и уникальным ограничением на бизнес-ключ.

Итого: Doctrine составные ключи поддерживает; чаще от них отказываются не из-за полного отсутствия поддержки, а потому что одиночный технический ID проще в эксплуатации, а уникальность бизнес-комбинации можно сохранить ограничением БД.

## Q27 · Мини-код-ревью

**Интервьюер:** Посмотри на этот код:

```php
class OrderController
{
    public function pay(Request $req): Response
    {
        $id = $req->get('order_id');
        $pdo = DB::connect();
        $order = $pdo->query("SELECT * FROM orders WHERE id = $id")->fetch();
        if (!$order) {
            return new Response('not found', 404);
        }
        $order['status'] = 'paid';
        $pdo->exec("UPDATE orders SET status = 'paid' WHERE id = $id");
        Mailer::send($order['email'], 'Ваш заказ оплачен');
        (new Logger())->log('paid ' . $id);
        return new Response('ok');
    }
}
```

Какие проблемы ты видишь и как бы ты этот код переделал? С чего начал бы и почему?

**Кандидат:**

Начал бы не с разбиения класса на слои, а с **безопасности и корректности оплаты**. Сейчас код не просто трудно тестировать — он может выполнить произвольный SQL и пометить заказ оплаченным без подтверждения платежа.

### Основные проблемы

1. **SQL-инъекция:** `$id` напрямую вставляется в SQL. Значение приходит из запроса и не является доверенным.
2. **Нет авторизации и проверки владельца:** любой, кто знает или угадает `order_id`, потенциально может изменить заказ. Для браузерного запроса также нужно учитывать CSRF.
3. **Оплата считается успешной по факту вызова метода:** нет проверки платёжного провайдера, суммы, валюты или статуса платежа. Клиентский запрос не должен сам по себе подтверждать оплату.
4. **Не проверяется переход состояния:** заказ можно повторно оплатить или перевести в `paid` из недопустимого статуса.
5. **Гонки и повторные запросы:** два параллельных вызова могут оба выполнить побочные действия. Нужны идемпотентность и защита от конкурентного изменения.
6. **Письмо отправляется до гарантированной фиксации результата:** если отправка письма завершится ошибкой, HTTP-запрос упадёт, хотя статус уже изменён. Если отправить письмо после `UPDATE`, но процесс завершится до этого, статус изменится, а письмо не уйдёт.
7. **Контроллер смешивает обязанности:** HTTP, SQL, бизнес-правила, почта и логирование связаны в одном методе. `DB`, `Mailer` и `Logger` используются как скрытые зависимости.
8. **Нет обработки ошибок и явного контракта:** сбой БД или почты может превратиться в 500 без подходящего логирования и реакции. Возвращаемый ответ также не уточняет, что именно считается успешной оплатой.

## С чего начал бы

Сначала выяснил бы, кто вызывает endpoint и откуда берётся подтверждение оплаты: от платёжного провайдера, пользователя или внутреннего процесса. Это меняет модель безопасности. Если это webhook провайдера, нужно проверить подпись и идемпотентность события. Если это пользовательский запрос, он должен инициировать оплату, но не объявлять её завершённой без подтверждения провайдера.

Затем закрыл бы SQL-инъекцию, проверку доступа и допустимость перехода статуса. После этого вынес бы сценарий из контроллера и отделил внешние эффекты.

## Возможное направление рефакторинга

Контроллер отвечает за HTTP и передаёт команду сценарию приложения:

```php
final class OrderController
{
    public function __construct(
        private ConfirmPayment $confirmPayment,
    ) {}

    public function pay(Request $request): Response
    {
        $orderId = OrderId::fromString(
            (string) $request->request->get('order_id'),
        );

        $this->confirmPayment->execute($orderId);

        return new Response('', Response::HTTP_NO_CONTENT);
    }
}
```

Это только форма примера: фактическую проверку личности и прав следует выполнять через Symfony Security, а webhook — проверять по правилам платёжного провайдера.

Сценарий приложения координирует доменную операцию и сохранение:

```php
final class ConfirmPayment
{
    public function __construct(
        private OrderRepository $orders,
        private PaymentVerifier $payments,
        private EntityManagerInterface $em,
    ) {}

    public function execute(OrderId $id): void
    {
        $this->em->wrapInTransaction(function () use ($id): void {
            $order = $this->orders->getForUpdate($id);

            if ($order->isPaid()) {
                return; // Повторное подтверждение — идемпотентный no-op
            }

            $payment = $this->payments->confirmedPaymentFor($order->id());

            $order->confirmPayment(
                $payment->id(),
                $payment->amount(),
                $payment->currency(),
            );

            $this->orders->save($order);
            $this->em->flush();
        });
    }
}
```

Здесь `getForUpdate()` иллюстрирует один из способов сериализовать изменения; при редких конфликтах вместо пессимистической блокировки можно выбрать optimistic locking с версией. Внешний платёжный API не следует вызывать внутри долгой транзакции. Обычно его проверяют до короткой транзакции либо обрабатывают подписанное событие провайдера, учитывая, что данные могут устареть или прийти повторно.

Письмо лучше отправлять не прямо из сценария, а реагировать на подтверждённое доменное событие, например `OrderPaid`. Для надёжной доставки можно записывать событие в **outbox в той же транзакции**, а затем публиковать его в очередь. Обработчик отправляет письмо идемпотентно. Логирование при этом можно оставить отдельной инфраструктурной ответственностью; для аудита оплаты лучше хранить сам факт оплаты в доменной модели или журнале, а не полагаться только на текстовый лог.

Если временно сохранять текущую структуру, минимальный шаг — параметризованный запрос:

```php
$stmt = $pdo->prepare('SELECT * FROM orders WHERE id = :id');
$stmt->execute(['id' => $id]);
$order = $stmt->fetch(PDO::FETCH_ASSOC);
```

Но это устраняет только SQL-инъекцию, а не проблемы авторизации, подтверждения платежа, конкурентного доступа и надёжной отправки письма.

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Главная проблема — доменная сущность управляет инфраструктурой и сама сохраняет себя. Из-за этого `User` зависит от Doctrine, а изменение email неожиданно вызывает запись в БД.

### Что здесь не так

- **Нарушена граница слоёв:** доменная модель зависит от `EntityManagerInterface`, то есть от Doctrine.
- **Смешаны доменная логика и сохранение:** сущность должна защищать свои инварианты, а не решать, когда вызывать `flush()`.
- **Неявная транзакционная граница:** `flush()` может записать не только этого пользователя, но и другие изменения, отслеживаемые тем же EntityManager.
- **Состояние меняется до сохранения:** если `flush()` завершится ошибкой, объект в памяти уже содержит новый email, хотя БД могла его не сохранить.
- **Email — не просто произвольная строка:** обычно полезно нормализовать и валидировать его при создании отдельного Value Object.
- **Уникальность нельзя гарантировать только проверкой в PHP:** параллельные запросы могут пройти проверку одновременно. Нужен уникальный индекс или constraint в БД.
- **Отдельный нюанс Doctrine:** внедрять EntityManager в сущность не нужно; ORM сам управляет жизненным циклом сущностей и их гидратацией.

## Доменная сущность

Сущность выражает изменение состояния и проверяет доменные правила, но ничего не знает о `flush()`:

```php
#[ORM\Entity]
final class User
{
    #[ORM\Id]
    #[ORM\Column(type: 'uuid')]
    private UserId $id;

    #[ORM\Embedded(class: EmailAddress::class)]
    private EmailAddress $email;

    public function __construct(UserId $id, EmailAddress $email)
    {
        $this->id = $id;
        $this->email = $email;
    }

    public function changeEmail(EmailAddress $email): void
    {
        if ($this->email->equals($email)) {
            return;
        }

        // Здесь — доменные проверки и изменение состояния.
        $this->email = $email;
    }

    public function email(): EmailAddress
    {
        return $this->email;
    }
}
```

`EmailAddress::fromString()` может нормализовать и валидировать значение. Конкретный способ маппинга — `Embeddable`, DBAL type или отдельный маппер — зависит от используемой версии Doctrine и предпочтений проекта.

## Сохранение на уровне сценария приложения

Use case получает сущность через репозиторий, изменяет её и завершает операцию сохранением:

```php
final class ChangeUserEmail
{
    public function __construct(
        private UserRepository $users,
        private EntityManagerInterface $em,
    ) {}

    public function execute(UserId $id, string $rawEmail): void
    {
        $user = $this->users->get($id);
        $user->changeEmail(EmailAddress::fromString($rawEmail));

        $this->em->flush();
    }
}
```

В более строгом разделении `EntityManagerInterface` можно скрыть за Unit of Work или прикладным портом; важен принцип: границу сохранения задаёт сценарий приложения, а не доменная сущность. Для операции из нескольких записей здесь же, на уровне use case, задают транзакционную границу.

Проверку «такой email уже используется» можно сделать в приложении ради понятной ошибки, но надёжность обеспечивает ограничение уникальности в БД. Нарушение ограничения нужно преобразовать в ожидаемый ответ, учитывая, что между проверкой и записью возможна гонка.
