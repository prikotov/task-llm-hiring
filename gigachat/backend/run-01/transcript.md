## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

С версии PHP 8 появились важные нововведения, существенно упрощающие написание чистого, поддерживаемого и безопасного кода. Вот несколько ключевых возможностей и примеров их практического использования:

## 1. Атрибуты (`Attributes`)
Атрибуты позволяют аннотировать классы, методы и свойства удобным способом без зависимости от DocBlocks и сторонних библиотек. Например, вы можете создать собственный атрибут `@Route` для роутинга:

```php
#[Route('/users/{id}', methods: ['GET'])]
public function showUser(int $id): User {
    return $this->userRepository->findById($id);
}
```

## 2. Объединённые типы (`Union Types`)
Теперь вы можете указать сразу несколько допустимых типов аргументов функции или возвращаемого значения:

```php
function normalizeValue(mixed $value): int|float|string|null {
    if ($value === null || is_numeric($value)) {
        return $value;
    }
    
    throw new InvalidArgumentException('Invalid value type');
}
```

## 3. Тип `mixed`
Тип `mixed` позволяет указывать, что функция принимает любой тип данных:

```php
function convertToString(mixed $input): string {
    return strval($input);
}
```

Это удобно для универсальных функций обработки данных.

## 4. Конструктор свойств (`Constructor Property Promotion`)
Позволяет автоматически инициализировать свойства класса прямо в конструкторе, уменьшая количество шаблонного кода:

```php
class User 
{
    public function __construct(
        private readonly string $name,
        private readonly int $age
    ) {}
}

$user = new User(name: 'Иван', age: 35); // name и age сразу станут приватными свойствами
```

## 5. Строгий режим типа по умолчанию
Начиная с PHP 8, объявлен строгий режим типов по умолчанию. Теперь аргументы методов и переменные проверяются строго на соответствие объявленным типам, предотвращая потенциальные ошибки. Пример старого поведения и нового:

```php
// Раньше допускалось такое поведение (без strict_types):
function addNumbers(float $a, float $b): float {
    return $a + $b;
}

echo addNumbers(1, 2); // выведет число 3.0

// Но теперь при вызове такого метода будет ошибка:
addNumbers("1", "2"); // Fatal error: Uncaught TypeError
```

Таким образом, даже случайно переданные неверные данные будут немедленно выявлены, что улучшает качество и безопасность вашего кода.

## 6. Nullsafe оператор (`Nullsafe Operator`)
Операция `?->` предотвращает выброс исключений при попытке вызова метода на NULL-значении объекта:

```php
$address = $user?->getProfile()?->getAddress();

if (!is_null($address)) {
    echo "Адрес пользователя: {$address}";
}
```

Этот подход делает ваш код чище и сокращает необходимость в многочисленных проверок на NULL.

Эти улучшения вместе делают разработку проще, а сам код более выразительным, читаемым и устойчивым к ошибкам.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

Система типов в PHP прошла долгий путь развития, начиная от динамической типизации ранних версий и заканчивая современными возможностями строгих и гибких ограничений. Попробуем разобраться подробнее в работе системы типов, поведении оператора `strict_types`, особенностях приведения типов и типичных проблемах, возникающих на практике.

### Система типов в PHP

#### Основные моменты:

- **Dynamically typed language**: изначально PHP был языком с динамическими типами, то есть типы переменных определяются автоматически при присвоении значений. С развитием языка добавились статические проверки и строгие типы.
- **Статическая проверка типов**: начиная с PHP 7, появилась возможность явно указывать типы параметров и возвращаемых значений, а также проверять их на этапе выполнения.
- **Strict typing mode**: используется директива `declare(strict_types=1)` для включения режима строгой проверки типов.

### Что даёт `strict_types=1`?

Режим строгой типизации активируется добавлением специальной директивы вверху файла скрипта:

```php
<?php declare(strict_types=1);
```

Эта директива означает следующее:

- Все параметры и возвращаемые значения функций обязаны соответствовать указанным типам.
- Автоматическое приведение типов запрещено. Если аргумент или результат имеют другой тип, генерируется исключение `TypeError`.

Пример правильной работы строгой типизации:

```php
<?php declare(strict_types=1);

function sum(int $x, int $y): int {
    return $x + $y;
}

sum(1, 2);       // OK
sum(1, "2");     // TypeError: Argument #2 must be of type int, string given
```

Без строгой типизации такой вызов прошёл бы успешно, поскольку строка `"2"` была бы автоматически преобразована в целое число.

### Особенности автоматического приведения типов

По умолчанию, если режим строгой типизации отключён, PHP пытается привести типы автоматически, когда это возможно. Примеры автоматического приведения:

```php
$a = "1";         // строковый тип
$b = true;        // булевый тип
$c = $a + $b;     // результатом будет число 2, потому что "1" -> 1 и true -> 1
```

Однако важно помнить, что автоматическое приведение часто ведёт к непредсказуемости и скрытым багам. Именно поэтому использование строгой типизации крайне рекомендуется.

### Ловушки и проблемы с типизацией

Рассмотрим несколько распространённых ситуаций, где неправильное использование типов вызывает трудности:

#### 1. Ошибка с нулём (`null`) и целыми числами (`int`)
При сравнении чисел и пустых значений возникают нюансы:

```php
if ("0" == false) {   // Вернёт true!
    echo "Ноль равен false";
}
```

Здесь строка `"0"` приводится к числу `0`, которое интерпретируется как ложное значение. Чтобы избежать подобной путаницы, лучше использовать строгое сравнение:

```php
if ("0" === false) {   // Вернёт false
    echo "Ошибка!";
}
```

#### 2. Проблемы с числовыми строками и числами
Автоматическое приведение типов в арифметике может вызывать странности:

```php
$a = "123abc";      // строка содержит цифры и буквы
$result = $a * 2;    // Результат будет числом 246, т.к. строки превращаются в числа путём отсечения букв
```

Такой сценарий легко провоцирует баги. Решением является явная проверка типов перед операциями:

```php
if (is_int($a)) {
    $result = $a * 2;
} else {
    throw new Exception("Ожидался целый тип");
}
```

#### 3. Нулевые значения (`NULL`) и численные операции
Пустые значения приводят к неожиданностям при выполнении операций:

```php
$x = null;
$y = $x + 1;            // Результатом будет integer(1)
```

Здесь пустой объект превращается в ноль, а затем выполняется операция сложения. Опять же, правильнее контролировать типы заранее:

```php
if ($x !== null && is_int($x)) {
    $y = $x + 1;
} else {
    throw new TypeError("Некорректный параметр x");
}
```

### Где типизация помогает

Типизация действительно полезна там, где она защищает от ошибок:

```php
<?php declare(strict_types=1);

function divide(float $dividend, float $divisor): float {
    if ($divisor == 0) {
        throw new DivisionByZeroError("Делить на ноль нельзя!");
    }
    return $dividend / $divisor;
}

divide(10, 0);             // Возникнет TypeError
divide(10, "0");           // Возникнет TypeError
```

Типизация гарантирует корректность входных данных и предотвращает ненужные преобразования.

### Итоговые рекомендации:

- Всегда используйте строгую типизацию (`declare(strict_types=1)`).
- Проверяйте типы вручную, используя встроенные функции вроде `is_string()`, `is_array()` и т.п., чтобы минимизировать риск непредвиденного поведения.
- Избегайте автоматического приведения типов и полагайтесь на строгие сравнения (`===` вместо `==`).

Правильное применение системы типов значительно повышает надежность приложений и облегчает поддержку кода.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

Проектирование механизма обработки исключений — важный аспект разработки любого качественного программного продукта. Правильно спроектированная система исключений позволяет сделать приложение стабильным, предсказуемым и легче поддерживать. Рассмотрим основные аспекты дизайна исключения в PHP-приложениях.

### Иерархия собственных исключений

Создание собственной иерархии исключений помогает стандартизировать обработку ошибок внутри проекта и улучшить читаемость кода. Вот некоторые рекомендации по созданию своей иерархии:

1. **Корневой класс исключений:** Обычно создается один базовый класс исключений для всего приложения, который наследуется от стандартного `Throwable`. Этот класс определяет общие поля и методы, специфичные для вашего проекта.
   
   ```php
   class AppException extends Throwable
   {
       protected $contextData;
       
       public function getContext(): array
       {
           return $this->contextData ?? [];
       }
   }
   ```

2. **Специфичные подклассы:** Для каждого вида ошибок создаются специализированные классы исключений, отражающие контекст возникновения ошибки.

   ```php
   class DatabaseConnectionException extends AppException {} // проблема подключения к БД
   class EntityNotFoundException extends AppException {}     // сущность не найдена
   class ValidationFailedException extends AppException {}   // ошибка валидатора
   ```

3. **Имена классов исключений:** Следите за четкостью именования, желательно добавлять суффикс `Exception`: `EntityNotFoundException`, `ServiceUnavailableException`, `ValidationException`.

### Оборачивание чужих исключений

Обработка внешних библиотек или фреймворков требует аккуратной работы с их внутренними исключениями. Важно обернуть внешние исключения в собственные, чтобы скрыть детали реализации библиотеки и обеспечить единообразную обработку ошибок:

```php
try {
    $result = $externalApiClient->callMethod();
} catch (\ExternalLibrary\Exception $e) {
    throw new ExternalApiCallException($e->getMessage(), previous: $e);
}
```

Такое оборачивание обеспечивает две ключевые выгоды:
- Скрывает внутренние подробности реализации API.
- Единообразит систему обработок ошибок, позволяя разработчикам фокусироваться на семантическом значении возникшей ошибки, а не на технических деталях конкретных библиотек.

### Контракт метода и обязанности по обработке исключений

Контрактом метода называется набор правил, определяющий обязательства метода по отношению к своему поведению. Эти правила включают:

- Гарантированные результаты (возвращаемое значение, состояние объектов после вызова).
- Возможные ошибки (какие исключения могут возникать и почему).
- Предположения относительно входа (предусловия).

Важно соблюдать следующие правила:

1. **Четкое документирование возможных исключений.** Каждый публичный метод должен содержать документацию с описанием всех возможных исключительных ситуаций и соответствующих классов исключений.

   ```php
   /**
    * Получает пользователя по идентификатору.
    *
    * @param int $id Идентификатор пользователя
    * @return User Объект пользователя
    * @throws EntityNotFoundException Когда пользователь не найден
    */
   public function findUser(int $id): User
   {
       ...
   }
   ```

2. **Не выбрасывайте необработанное исключение высокоуровневыми методами.** Чем ближе к внешнему интерфейсу находится ваш метод, тем важнее обрабатывать или корректно передавать исключения дальше по цепочке. Выбрасывать исключения непосредственно клиенту недопустимо, так как нарушают стабильность API и усложняют клиентский код.

3. **Логика должна сообщать бизнес-смысл ошибки.** Не стоит скрывать причину сбоя за техническими деталями. Например, сообщение «не удалось подключиться к серверу» полезно лишь в рамках диагностики инфраструктуры, тогда как клиентам важна информация уровня «невозможно завершить операцию». Используйте исключения таким образом, чтобы передавалась нужная информация для бизнеса и пользователей.

### Антипаттерны и распространенные ошибки

1. **Переизбыточная обработка ошибок**
   
   Частое явление, когда разработчики стараются обработать абсолютно каждое возможное исключение в каждом месте программы. Такой подход ведет к избыточности, ухудшению читаемости и увеличению объема кода. Вместо этого имеет смысл обрабатывать исключения там, где вы реально знаете, как исправить ситуацию либо смягчить последствия.

   **Антипаттерн:**
   
   ```php
   try {
       $user = $this->repository->findUser($id);
   } catch (EntityNotFoundException $e) {
       // Ничего не делаем...
   }
   ```

   **Решение:** Исключения обрабатываются только там, где это имеет смысл. Иногда исключение должно подняться выше по стеку.

2. **Лишние уровни обертки исключений**
   
   Чрезмерное оборачивание исключений снижает прозрачность происходящего и затрудняет диагностику проблем. Лучше избегать промежуточных уровней переобёрток, сохраняя одну-две ступени разделения ответственности.

   **Антипаттерн:**
   
   ```php
   try {
       doSomething();
   } catch (AppException $e) {
       throw new WrapperException($e->getMessage());
   }
   ```

   **Решение:** Оставляйте минимально необходимое количество слоев оберток и убедитесь, что каждый слой добавляет ценность.

3. **Потеря контекста в сообщении исключения**
   
   Часто исключение возникает глубоко внутри какой-то сложной логики, и теряется важная информация, необходимая для анализа причины сбоя. Каждое исключение должно включать достаточный объем данных, позволяющих точно определить место и природу проблемы.

   **Антипаттерн:**
   
   ```php
   throw new RuntimeException("Что-то пошло не так");
   ```

   **Решение:** Добавьте детальное описание и контекст в ваше исключение:
   
   ```php
   throw new RuntimeException("Невозможно получить доступ к ресурсу X: {$errorDetails}");
   ```

4. **Игнорирование причин повторных исключений**
   
   Повторное возникновение одного и того же исключения сигнализирует о фундаментальной проблеме в вашем приложении. Игнорирование этого факта приведет к накапливанию ошибок и падениям системы.

   **Антипаттерн:**
   
   ```php
   while (!$success) {
       try {
           processPayment();
           $success = true;
       } catch (PaymentFailureException $e) {
           sleep(1); // Просто ждем и пробуем снова
       }
   }
   ```

   **Решение:** Логируйте и мониторьте повторы сбоев, предусмотрите стратегию действий (аварийное завершение, уведомление разработчиков).

### Заключение

Исключения являются мощным инструментом управления состоянием ошибок в приложениях, однако требуют внимательного подхода к дизайну и внедрению. Четко продуманная структура исключений, разумная документация контрактов методов и осознанная работа с внешними зависимостями помогут вам построить качественное и надежное решение.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

Из пяти принципов SOLID наиболее часто нарушаемым принципом, судя по моему опыту, является **Принцип единственной ответственности (Single Responsibility Principle, SRP)**. Нарушение данного принципа проявляется, когда класс берет на себя слишком много обязанностей, становится многозадачным и сложно поддерживаемым.

### Почему нарушение происходит?

Основные причины нарушений принципа SRP:

1. **Жадность программистов**: желание решить все задачи одной функцией или методом, забывая о простоте и ясности структуры.
2. **Копипаст-код**: многократное копирование блоков кода без должного выделения общих абстракций и ответственности.
3. **Недостаточная декомпозиция**: стремление быстро реализовать новую функцию вместо тщательной проработки архитектуры и понимания обязанностей каждой части системы.

Нарушенный принцип SRP мешает дальнейшей поддержке и развитию кода, увеличивает вероятность появления багов и усложняет внесение изменений.

### Пример нарушения принципа SRP

Представим простую реализацию контроллера для регистрации пользователя в веб-приложении:

```php
class RegistrationController
{
    public function registerUser(string $email, string $password)
    {
        // Проверяем email на существование
        if ($this->checkEmailExists($email)) {
            throw new EmailAlreadyExistsException();
        }
        
        // Создаем хэш пароля
        $hashedPassword = password_hash($password, PASSWORD_DEFAULT);
        
        // Сохраняем пользователя в базу данных
        $this->saveUserInDatabase($email, $hashedPassword);
        
        // Отправляем приветственное письмо
        $this->sendWelcomeEmail($email);
    }

    private function checkEmailExists(string $email): bool
    {
        // логика проверки существования email
    }

    private function saveUserInDatabase(string $email, string $hashedPassword)
    {
        // логика сохранения пользователя в БД
    }

    private function sendWelcomeEmail(string $email)
    {
        // логика отправки письма
    }
}
```

Почему этот пример нарушает SRP?

- Один класс решает сразу четыре разные задачи: проверку наличия email, создание хэша пароля, сохранение пользователя в базу данных и отправку писем.
- Такое разделение ответственностей создает сложности при модификации каждой отдельной функциональности.
- Изменяя одно действие (например, механизм хранения паролей), мы затрагиваем весь класс целиком, увеличивая риски появления новых дефектов.

### Рефакторинг по принципу SRP

Разделим ответственность между несколькими независимыми классами:

```php
interface IRegistrationService
{
    public function registerUser(string $email, string $password): void;
}

class RegistrationService implements IRegistrationService
{
    private IUserRepository $userRepository;
    private IEmailSender $emailSender;
    private IPasswordHasher $passwordHasher;

    public function __construct(IUserRepository $userRepository, IEmailSender $emailSender, IPasswordHasher $passwordHasher)
    {
        $this->userRepository = $userRepository;
        $this->emailSender = $emailSender;
        $this->passwordHasher = $passwordHasher;
    }

    public function registerUser(string $email, string $password): void
    {
        if ($this->userRepository->exists($email)) {
            throw new EmailAlreadyExistsException();
        }

        $hashedPassword = $this->passwordHasher->hash($password);
        $this->userRepository->save(new User($email, $hashedPassword));
        $this->emailSender->sendWelcomeEmail($email);
    }
}

class UserRepository implements IUserRepository
{
    public function exists(string $email): bool
    {
        // реализация проверки email
    }

    public function save(User $user): void
    {
        // сохраняем пользователя в базу данных
    }
}

class PasswordHasher implements IPasswordHasher
{
    public function hash(string $password): string
    {
        return password_hash($password, PASSWORD_DEFAULT);
    }
}

class EmailSender implements IEmailSender
{
    public function sendWelcomeEmail(string $email): void
    {
        // отправляем письмо
    }
}
```

### Преимущества новой структуры:

- Каждый класс выполняет единственную обязанность: регистрация пользователя делегирована сервису, хранение данных — репозиториям, создание хэша — классу-хешеру, отправка почты — почте.
- Легче тестировать отдельные модули отдельно друг от друга.
- Упрощается поддержка и развитие функционала.
- Каждая отдельная область изменения изолирована и не влияет на другие части системы.

Следовательно, правильное соблюдение принципа SRP помогает делать код проще, удобнее для поддержки и тестирования, уменьшает риски внесения багов и позволяет быстрее развивать продукт.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Да, можно и иногда даже нужно нарушать принципы SOLID, если это целесообразно в конкретной ситуации. Принципы SOLID представляют собой хорошие практики, направленные на улучшение качества и удобочитаемости кода, облегчение сопровождения и расширения проектов. Тем не менее, слепо следовать им буквально во всех ситуациях нецелесообразно. Давайте рассмотрим случай, когда оправданы отступления от принципов SOLID.

### Отклонение от принципа Open-Closed (OCP)

**Принцип OCP гласит:** сущности (классы, модули, функции) должны быть открыты для расширения, но закрыты для модификаций.

Однако бывают случаи, когда изменения в существующий класс целесообразны и эффективны, несмотря на формальные требования OCP.

Например, предположим, что у вас есть небольшой проект, состоящий из нескольких компонентов, и вы разрабатываете компонент калькулятора процентов скидки. Первоначально было решено реализовывать простой алгоритм расчета скидок:

```php
class DiscountCalculator
{
    public function calculateDiscount(float $price, float $discountRate): float
    {
        return $price * (1 - $discountRate);
    }
}
```

Затем приходит задача добавить новое правило: скидка зависит еще и от категории товара («электроника», «одежда»). Конечно, формально следовало бы расширить интерфейс и создавать новый класс-наследник для учета категорий товаров, однако в небольшом проекте такая перегрузка не нужна. Более рационально обновить существующую реализацию:

```php
class DiscountCalculator
{
    public function calculateDiscount(float $price, float $discountRate, ?string $category = null): float
    {
        if ($category === 'electronics') {
            $discountRate += 0.05; // дополнительная скидка на электронику
        }
        return $price * (1 - $discountRate);
    }
}
```

Таким образом, изменение сделано простым путем добавления параметра и небольшого условия. Несмотря на формальное нарушение OCP, данное отклонение вполне обосновано и уместно в данном случае, так как затраты на расширение излишни и вызывают неоправданное усложнение кода.

### Когда еще допускается отход от SOLID?

- **Минималистичный проект или прототип**: иногда важнее быстро проверить идею, чем придерживаться всех лучших практик. В маленьких проектах временные решения часто эффективнее, чем строгое соблюдение SOLID.
- **Оптимизация производительности**: порой лучшие паттерны требуют дополнительного слоя абстракции, который замедляет выполнение критически важных участков кода. В таких случаях отказ от отдельных принципов SOLID ради скорости бывает оправдан.
- **Исторический долг**: в старых системах переделывать архитектуру исключительно ради соответствия SOLID зачастую нерентабельно. Здесь важны приоритеты бизнеса и польза от внедрения изменений.

Тем не менее, стоит помнить, что любое отклонение от принципов SOLID должно быть осмысленным решением, принятым сознательно и обоснованно. Важно понимать, какие преимущества приносит следование принципам и какие издержки влечет отклонение от них.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Да, принцип Open/Closed (OCP) можно эффективно применять не только с помощью наследования. Существует ряд альтернативных способов реализации этого принципа, среди которых наиболее распространены:

### 1. Композиция и делегирование
Композиция подразумевает объединение различных независимых компонентов для достижения нужного результата. Можно разделить сложную логику на небольшие компоненты, предоставляя основной объект способ изменять свое поведение посредством комбинирования этих компонентов.

**Пример: Стратегия (Strategy Pattern)**
Допустим, нам нужен калькулятор цен, который поддерживает различные стратегии расчета стоимости заказа (обычная цена, цена с учетом скидки, цена с налогом и т.д.).

Используя композицию, мы можем выделить отдельную группу классов-стратегий для расчетов цены и делегировать вычисление этим стратегиям.

```php
interface PriceCalculationStrategy
{
    public function calculatePrice(float $basePrice): float;
}

class RegularPriceStrategy implements PriceCalculationStrategy
{
    public function calculatePrice(float $basePrice): float
    {
        return $basePrice;
    }
}

class DiscountedPriceStrategy implements PriceCalculationStrategy
{
    private float $discountRate;

    public function __construct(float $discountRate)
    {
        $this->discountRate = $discountRate;
    }

    public function calculatePrice(float $basePrice): float
    {
        return $basePrice * (1 - $this->discountRate);
    }
}

class OrderCalculator
{
    private PriceCalculationStrategy $strategy;

    public function setStrategy(PriceCalculationStrategy $strategy): void
    {
        $this->strategy = $strategy;
    }

    public function calculateTotal(float $basePrice): float
    {
        return $this->strategy->calculatePrice($basePrice);
    }
}
```

Добавлять новые стратегии теперь можно без изменения основного класса `OrderCalculator`.

### 2. Инъекция зависимостей (Dependency Injection)
Инъекция зависимостей (DI) позволяет менять внутреннее поведение компонента, заменяя его зависимости. Это идеально соответствует принципу OCP, так как замена зависимостей позволяет вводить новые алгоритмы без изменения исходного кода самого компонента.

**Пример: внедрение сервиса доставки**
Предположим, у нас есть сервис заказа, который использует разные службы доставки (почтовая служба, курьерская доставка и др.). Мы можем использовать DI для замены конкретного поставщика услуг доставки без изменения самой службы заказов.

```php
interface DeliveryService
{
    public function deliver(Order $order): void;
}

class PostalDeliveryService implements DeliveryService
{
    public function deliver(Order $order): void
    {
        // Почтовая доставка
    }
}

class CourierDeliveryService implements DeliveryService
{
    public function deliver(Order $order): void
    {
        // Курьерская доставка
    }
}

class OrderService
{
    private DeliveryService $deliveryService;

    public function __construct(DeliveryService $deliveryService)
    {
        $this->deliveryService = $deliveryService;
    }

    public function placeOrder(Order $order): void
    {
        // логика размещения заказа
        $this->deliveryService->deliver($order);
    }
}
```

Мы можем заменить службу доставки без изменения кода самого `OrderService`.

### 3. Шаблоны проектирования (Design Patterns)
Некоторые шаблоны проектирования специально созданы для соблюдения принципа OCP:

- **Шаблон Decorator**: позволяет динамически расширять объекты новыми функциями без изменения оригинального класса.
- **Шаблон Observer**: разрешает объектам подписываться на события и реагировать на них без необходимости модификации базовых классов.
- **Шаблон Adapter**: адаптирует существующие интерфейсы без модификации самих классов.

Каждый из этих шаблонов помогает отделить основную логику от деталей реализации и открыть пространство для дальнейшего расширения без необходимости редактировать первоначальный код.

### 4. Использование композитов и плагинов
Иногда имеет смысл реализовать открытость для расширения с помощью специализированных плагинов или модулей, которые загружаются динамически и меняют поведение базовой системы. Такая схема применяется, например, в CMS WordPress или Joomla.

### Заключение
Наследование — это лишь один из способов реализации принципа OCP. Существуют и другие эффективные техники, такие как композиция, инъекция зависимостей, шаблоны проектирования и плагинизация, которые позволяют достигать той же цели — обеспечивать закрытость кода для изменений и открытость для расширения. Выбор способа зависит от конкретной задачи и требований вашей системы.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Нет, принцип единственной ответственности (Single Responsibility Principle, SRP) применяется не только к классам, но и ко многим другим элементам архитектуры программного обеспечения. Его суть заключается в том, что каждая единица (будь то модуль, класс, метод, функция или пакет) должна иметь ровно одну зону ответственности, четко определенную цель, которую она решает.

Вот основные элементы, к которым может применяться SRP:

### 1. Классы
Класс должен отвечать только за одну задачу или область функционирования. Например, класс не должен одновременно заниматься чтением файлов, хранением данных и отображением результатов. Лучший подход — разделить эти обязанности на несколько самостоятельных классов.

### 2. Методы и Функции
Методы и функции также должны выполнять одну главную задачу. Метод не должен смешивать логику валидации, формирования запроса и вывода сообщений. Желательно ограничиваться одной ответственностью, иначе возрастает сложность тестирования и поддержания кода.

### 3. Модули и Пакеты
Модуль или пакет должен быть посвящен определенной группе взаимосвязанных элементов. Например, отдельный модуль может отвечать за аутентификацию пользователей, другой — за взаимодействие с базой данных, третий — за формирование отчетов. Смешивание этих зон ответственности приведет к снижению гибкости и повышению рисков возникновения побочных эффектов при изменениях.

### 4. Интерфейсы
Интерфейс должен определять единую область взаимодействия, охватывающую одну конкретную задачу. Создание единого интерфейса, объединяющего несвязанные концепции, противоречит SRP и затрудняет дальнейшее развитие и сопровождение.

### 5. Сервисы и Микросервисы
Сервисы и микросервисы должны сосредоточиться на предоставлении одной четко определенной услуги или набора тесно связанных сервисов. Комбинация множества разнородных функций в одном сервисе приводит к проблемам масштабируемости и управляемости.

### Почему важен SRP вне классов?

Соблюдение SRP помогает:

- Делать код легким для чтения и понимания.
- Повышать устойчивость системы к изменениям.
- Минимизировать побочные эффекты при внесении изменений.
- Улучшить удобство тестирования и повторного использования компонентов.

Таким образом, принцип SRP распространяется далеко за пределы классов и касается практически любых структурных единиц программного обеспечения.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

Контейнер внедрения зависимостей (dependency injection container) в Symfony представляет собой мощный инструмент для автоматизации управления зависимостями и конфигурирования сервисов. Давай разберемся подробно, как он устроен и как происходят процессы компиляции контейнера, автоподстановки зависимостей (autowiring) и первого обращения к сервису.

### Как устроен контейнер?

Контейнер внедрения зависимостей (Container) отвечает за управление жизненным циклом и конфигурацией ваших сервисов. В отличие от простых случаев передачи зависимостей вручную, контейнер берет на себя контроль над созданием экземпляров сервисов, инжекцией их зависимостей и поддержкой правил, заданных вами в конфигурации.

### Этапы работы контейнера:

#### 1. Конфигурация (Configuration Phase)
На первом этапе контейнер считывает вашу конфигурацию сервисов, включая XML-файлы, YAML-конфигурации, аннотации и метаданные классов. Конфигурация включает определения сервисов, их зависимости, опции и параметры.

#### 2. Сборка графа зависимостей (Building Dependency Graph)
После прочтения всей конфигурации, контейнер строит граф зависимостей, где узлы соответствуют вашим сервисам, а ребра — отношениям "зависимость". Таким образом, он видит полную картину отношений между объектами и способен определить порядок создания сервисов.

#### 3. Генерация прокси-классов (Proxy Classes Generation)
Для повышения производительности Symfony создаёт proxy-классы (прокси-сервисы) для тех сервисов, которые помечены как ленивые (lazy services). Прокси-класс выглядит примерно так:

```php
namespace Proxies\__CG__;
use ProxyManager\Proxy\LazyLoadingInterface;
final class SomeService_Proxy extends SomeService implements LazyLoadingInterface
{
    private $initializer;

    public function initialize()
    {
        $this->__initializer__->__invoke($this);
    }

    // остальные методы остаются такими же, как в оригинальном классе
}
```

Прокси-классы используются, чтобы отложить фактическое создание объекта до момента, пока он не понадобится.

#### 4. Компилирование контейнера (Compilation)
На этом этапе запускается процесс компиляции, который объединяет всю собранную информацию и готовит финальный контейнер для исполнения. Это важнейший этап, так как на нём выполняются следующие шаги:

- Замещаются абстрактные зависимости конкретными реализациями (если были указаны абстрактные интерфейсы).
- Генерируются необходимые вспомогательные файлы и классы (например, кэш-файл контейнера).
- Применяются различные оптимизаторы и инструменты для увеличения производительности (например, оптимизатор служб и автотайминг).

Финальный контейнер сохраняется в виде сериализированного массива или генерируемого класса, что ускоряет загрузку и уменьшает накладные расходы при последующих запусках.

#### 5. Запуск и получение сервиса (Runtime Phase)
Когда ваше приложение запрашивает конкретный сервис, происходит следующая последовательность событий:

- Сначала контейнер ищет нужный сервис в своем реестре.
- Если сервис отсутствует, проверяется наличие ленивого прокси-класса (proxy service).
- Если существует прокси-класс, вызывается метод инициализации прокси, который создаст реальный экземпляр требуемого сервиса.
- Если сервис зарегистрирован обычным образом (не lazy), то контейнер создаёт его инстанс и внедряет все необходимые зависимости.

### Autowiring (Автоподстановка зависимостей)
Autowiring — это мощная возможность Symfony, позволяющая автоматически находить и вставлять нужные зависимости в ваши классы без ручного задания инъекций в конфигурации.

Как это работает:

- Во время компиляции контейнера проходит фаза анализа всех зарегистрированных сервисов и классов.
- Контейнер сопоставляет типы аргументов конструктора (методов) с зарегистрированными сервисами.
- Если найдено совпадение имени типа (класс или интерфейс) с сервисом, зависимость автоматически подставляется в конструктор или метод.

Пример использования autowiring:

```php
class MyService
{
    private LoggerInterface $logger;

    public function __construct(LoggerInterface $logger)
    {
        $this->logger = $logger;
    }
}
```

Контейнер автоматически находит подходящий сервис, реализующий интерфейс `LoggerInterface`, и передает его в конструктор.

Чтобы включить автоподстановку глобально, добавьте в файл конфигурации:

```yaml
services:
    _defaults:
        autowire: true
```

Или укажите `autowire: true` для конкретного сервиса.

### Пример полного процесса:

1. Приложение регистрирует сервисы в контейнере через конфигурацию (YAML/XML/аннотации).
2. После запуска команды компиляции (`bin/console cache:clear`), контейнер собирает граф зависимостей и компилирует оптимальный вариант.
3. Финальный контейнер сохраняет список сервисов и готовых определений в кэш-файл.
4. Когда первый раз запрашивается сервис, контейнер смотрит, есть ли готовый экземпляр. Если нет, то он создаёт его и реализует все зависимости.
5. Если включена опция lazy loading, то сначала возвращается прокси-сервис, который позднее инициирует реальную реализацию.

### Оптимизация производительности:

Для ускорения загрузки контейнер формирует предварительно подготовленный PHP-класс с готовыми сервисами и правилами инжекции. Так как контейнер строится один раз, последующие запросы становятся намного быстрее благодаря предварительной подготовке и кэшированию.

---

Итак, Symfony Dependency Injection Container — это сложный, но эффективный инструмент, позволяющий упростить управление зависимостями и повысить производительность вашего приложения. Правильная настройка контейнера, грамотное использование autowiring и знание внутренних процессов позволят вашему проекту оставаться гибким и масштабируемым.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

Циклические зависимости (circular dependencies) — это ситуация, когда два или более сервисов зависят друг от друга, образуя замкнутый круг взаимозависимости. Такие зависимости создают серьезные проблемы в управлении зависимостями и затрудняют поддержание и тестирование кода. В Symfony и вообще в современном подходе к проектированию ПО принято стремиться избегать циклических зависимостей, но иногда они всё-таки возникают. Рассмотрим возможные способы решения данной проблемы.

### Способы разрешения циклических зависимостей:

#### 1. Переработка структуры сервисов
Самый надежный способ избавиться от циклических зависимостей — пересмотреть структуру и разбить цикл, уменьшив количество взаимодействующих классов. Например, если есть два класса, сильно зависящих друг от друга, попробуйте выделить общую функциональность в отдельный класс, который обе стороны смогут использовать независимо друг от друга.

Пример двух классов с циклическими зависимостями:

```php
class ServiceA
{
    private ServiceB $serviceB;

    public function __construct(ServiceB $serviceB)
    {
        $this->serviceB = $serviceB;
    }

    public function methodA()
    {
        $this->serviceB->methodB(); // Вызываем метод другого сервиса
    }
}

class ServiceB
{
    private ServiceA $serviceA;

    public function __construct(ServiceA $serviceA)
    {
        $this->serviceA = $serviceA;
    }

    public function methodB()
    {
        $this->serviceA->methodA(); // Вызываем метод другого сервиса
    }
}
```

В таком примере оба класса зависят друг от друга, создавая замкнутый цикл. Простое решение — убрать прямую связь и ввести посредника или внешний координатор:

```php
class CommonService
{
    public function performAction()
    {
        // общая логика, используемая обоими сервисами
    }
}

class ServiceA
{
    private CommonService $commonService;

    public function __construct(CommonService $commonService)
    {
        $this->commonService = $commonService;
    }

    public function methodA()
    {
        $this->commonService->performAction();
    }
}

class ServiceB
{
    private CommonService $commonService;

    public function __construct(CommonService $commonService)
    {
        $this->commonService = $commonService;
    }

    public function methodB()
    {
        $this->commonService->performAction();
    }
}
```

#### 2. Ленивая загрузка (Lazy Loading)
Ленивая загрузка (lazy initialization) — это техника, при которой сервис загружается только тогда, когда он действительно необходим. В Symfony эта возможность доступна через контейнер внедрения зависимостей. Благодаря этому механизму, мы можем разрешить циклические зависимости временно, отсрочив момент реальной загрузки сервиса до последнего возможного момента.

Например, в нашем предыдущем примере мы могли бы воспользоваться механизмом lazy loading:

```php
class ServiceA
{
    private ServiceB $serviceB;

    public function __construct(?ServiceB $serviceB = null)
    {
        $this->serviceB = $serviceB ?: new ServiceB($this); // Ленивая инициализация
    }

    public function methodA()
    {
        $this->serviceB->methodB();
    }
}

class ServiceB
{
    private ServiceA $serviceA;

    public function __construct(ServiceA $serviceA)
    {
        $this->serviceA = $serviceA;
    }

    public function methodB()
    {
        $this->serviceA->methodA();
    }
}
```

Но обратите внимание, что это временное решение, предназначенное скорее для облегчения текущего состояния, нежели устранения корня проблемы. Главная рекомендация — устранить циклы через реструктуризацию кода.

#### 3. Применение паттерна Mediator
Паттерн mediator полезен, когда сервисы активно обмениваются информацией друг с другом. Паттерн mediator предполагает введение специального класса-посредника, который управляет коммуникацией между различными частями системы. Используя этот подход, можно разорвать прямой цикл зависимости, оставив посредника единственным источником координации.

Пример паттерна mediator:

```php
class Mediator
{
    private ServiceA $serviceA;
    private ServiceB $serviceB;

    public function __construct(ServiceA $serviceA, ServiceB $serviceB)
    {
        $this->serviceA = $serviceA;
        $this->serviceB = $serviceB;
    }

    public function coordinate()
    {
        $this->serviceA->doWork();
        $this->serviceB->doOtherWork();
    }
}

class ServiceA
{
    public function doWork()
    {
        // выполняем свою работу
    }
}

class ServiceB
{
    public function doOtherWork()
    {
        // выполняем другую работу
    }
}
```

#### 4. Передача зависимости через Setter-инжекцию
Еще один способ временного обхода циклических зависимостей — передача зависимости через setter-методы, а не через конструктор. Это позволяет позже установить нужную зависимость, избежав жесткой конструкции в самом конструкторе.

Пример:

```php
class ServiceA
{
    private ServiceB $serviceB;

    public function setServiceB(ServiceB $serviceB)
    {
        $this->serviceB = $serviceB;
    }

    public function methodA()
    {
        $this->serviceB->methodB();
    }
}

class ServiceB
{
    private ServiceA $serviceA;

    public function setServiceA(ServiceA $serviceA)
    {
        $this->serviceA = $serviceA;
    }

    public function methodB()
    {
        $this->serviceA->methodA();
    }
}
```

Хотя этот подход технически разрешит проблему, его стоит использовать осторожно, так как он может приводить к более запутанной структуре.

### Важные выводы:

- Циклические зависимости лучше устранять путем переработки структуры и уменьшения количества связей между классами.
- Временные решения (ленивая загрузка, медиатор, setter-инжекция) помогают облегчить симптомы, но главная цель — устранение первопричины проблемы.
- Всегда старайтесь сохранять независимость классов и четко обозначать зоны ответственности.

Циклические зависимости указывают на проблемы с дизайном и архитектурой, поэтому правильным подходом будет переработка кода, а не попытка спрятать проблему за временными фиксаторами.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

Такая задача характерна для асинхронных сценариев, когда необходимо выполнять ресурсоемкую или длительную операцию параллельно основному потоку выполнения, не блокируя отклик пользователю. В частности, после успешной регистрации пользователя нам нужно выполнить две потенциально медленных операции: отправку электронного письма и обновление поискового индекса. Оба действия могут занять значительное время и замедлить ответ пользователю, поэтому их следует исполнять асинхронно.

Ниже представлены основные варианты организации асинхронных операций в Symfony и их плюсы/минусы.

---

### Варианты решений:

#### 1. Очереди задач (Task Queues) c использованием RabbitMQ или Redis
Один из самых популярных вариантов — использование брокера очередей задач (task queues), таких как RabbitMQ или Redis. Суть состоит в следующем:

- Основной процесс помещает задачу в очередь.
- Отдельный воркер (worker) слушает очередь и исполняет поставленную задачу.

##### Пример использования RabbitMQ с Symfony Messenger:

1. Установите Symfony Messenger:

```bash
composer require symfony/messenger
```

2. Настройте RabbitMQ-подключение и маршрутизацию:

```yaml
# config/packages/messenger.yaml
framework:
    messenger:
        transports:
            async: '%env(MESSENGER_TRANSPORT_DSN)%'
        routing:
            'App\Message\SendEmail': async
            'App\Message\UpdateSearchIndex': async
```

3. Определите сообщения и обработчики:

```php
// src/Message/SendEmail.php
namespace App\Message;

class SendEmail
{
    private string $email;

    public function __construct(string $email)
    {
        $this->email = $email;
    }

    public function getEmail(): string
    {
        return $this->email;
    }
}

// src/MessageHandler/SendEmailHandler.php
namespace App\MessageHandler;

use App\Message\SendEmail;
use Psr\Log\LoggerInterface;

class SendEmailHandler
{
    private LoggerInterface $logger;

    public function __construct(LoggerInterface $logger)
    {
        $this->logger = $logger;
    }

    public function __invoke(SendEmail $message)
    {
        $this->logger->info('Sending email to '.$message->getEmail());
        // здесь идет логика отправки письма
    }
}
```

4. Отправьте сообщение после регистрации пользователя:

```php
// src/Controller/UserController.php
use App\Message\SendEmail;
use App\Message\UpdateSearchIndex;
use Symfony\Component\HttpFoundation\Response;
use Symfony\Component\Mercure\PublisherInterface;
use Symfony\Component\Routing\Annotation\Route;
use Symfony\Component\Messenger\MessageBusInterface;

class UserController extends AbstractController
{
    #[Route('/register')]
    public function register(MessageBusInterface $bus): Response
    {
        // логика регистрации пользователя

        // асинхронно отправляем сообщение на отправку письма
        $bus->dispatch(new SendEmail($user->getEmail()));

        // асинхронно обновляем поисковый индекс
        $bus->dispatch(new UpdateSearchIndex($user->getId()));

        return new Response('Регистрация успешна!', 201);
    }
}
```

5. Запустите воркер:

```bash
symfony console messenger:consume async --time-limit=3600
```

##### Trade-offs:
- **Плюсы**:
  - Масштабируемость и высокая пропускная способность очереди.
  - Возможность распределенной обработки задач на множестве воркеров.
  - Отказоустойчивость: задачи сохраняются в очереди и повторно обрабатываются в случае падения воркера.
- **Минусы**:
  - Требует дополнительную инфраструктуру (RabbitMQ, Redis).
  - Дополнительная нагрузка на обслуживание и мониторинг системы.

---

#### 2. Синхронная отложенная обработка с помощью Messaging Component (Process Worker)
Другой популярный подход — использование Symfony Process-компонента для запуска отдельного дочернего процесса. Процесс стартует синхронно, но фактически реализуется асинхронно.

Пример использования Process:

```php
use Symfony\Component\Process\Process;

class UserController extends AbstractController
{
    #[Route('/register')]
    public function register(Request $request): Response
    {
        // логика регистрации пользователя

        // запускаем фоновый процесс для отправки письма
        $process = new Process(['php', 'bin/console', 'app:send-email', $user->getEmail()]);
        $process->start();

        // аналогично запускаем процесс обновления поиска
        $searchProcess = new Process(['php', 'bin/console', 'app:update-search-index', $user->getId()]);
        $searchProcess->start();

        return new Response('Регистрация успешна!', 201);
    }
}
```

##### Trade-offs:
- **Плюсы**:
  - Быстрая интеграция и отсутствие необходимости в дополнительной инфраструктуре.
  - Простота развертывания и мониторинга.
- **Минусы**:
  - Сложность в отслеживании статуса заданий и управлении ими.
  - Потенциальные проблемы с выполнением долгоиграющих задач.
  - Ограниченность ресурсов сервера (процессы потребляют память и ресурсы CPU).

---

#### 3. Использование Cron-триггеров
Третий подход — настроить периодическое задание cron, которое периодически проверяет базу данных на наличие незавершённых задач и выполняет их последовательно.

Примером реализации может служить скрипт, который регулярно обращается к базе данных и выбирает записи для отправки писем и обновления поисковых индексов.

##### Пример crontab-задачи:

```bash
*/5 * * * * php bin/console app:process-tasks >> /var/log/app.log
```

Где команда `app:process-tasks` — консольная команда, которая занимается поиском и исполнением задач.

##### Trade-offs:
- **Плюсы**:
  - Нет необходимости настраивать дополнительную инфраструктуру.
  - Подходит для небольших объемов задач.
- **Минусы**:
  - Периодичность выполнения (задержка в исполнении задач).
  - Отсутствие гибкости и реального параллелизма.

---

### Какой подход выбрать?
Выбор подходящего варианта зависит от размера проекта, нагрузки и доступности инфраструктуры:

- Если ожидается значительный рост трафика и большая нагрузка, предпочтительнее использовать очереди задач (RabbitMQ, Redis), обеспечив высокую степень масштабируемости и отказоустойчивости.
- Если инфраструктура проста и проект небольшой, подойдет синхронная отложенная обработка с помощью Process-компонента.
- Если количество задач невелико и задержки в обработке приемлемы, можно рассмотреть вариант с cron-trigger.

Наиболее популярным вариантом сегодня является использование очередей задач (RabbitMQ, Redis), так как он предлагает максимальную гибкость и масштабируемость.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

Контроль доступа в Symfony организован с применением трёх основных механизмов: **аутентификации**, **ролевой модели безопасности** и **voters (голосующих субъектов)**. Рассмотрим детально, как устроен каждый из этих механизмов и как правильно выбирать тот или иной подход в зависимости от решаемой задачи.

### Аутентификация (Authentication)
Аутентификация — это процесс подтверждения личности пользователя. Она основана на проверке предъявляемых учетных данных (логина, токенов и пр.) и выдаче пользователю соответствующего удостоверения (`User object`).

Процесс аутентификации в Symfony состоит из следующих этапов:

1. **Сбор учетных данных**: Пользователь вводит имя пользователя и пароль, которые отправляются на сервер.
2. **Проверка учетных данных**: Сервер проверяет введенную информацию с данными в хранилище (БД, LDAP и т.д.), используя провайдеры пользователей (`User Providers`).
3. **Авторизация**: Если данные совпадают, сервер выдает удостоверение (`User object`), включающее информацию о пользователе и его ролях.

Примеры распространенных схем аутентификации:
- Формы входа (form_login)
- JWT-аутентификация
- OAuth/OAuth2
- HTTP Basic Auth

### Роли (Roles)
Ролевая модель безопасности основывается на назначении пользователям определенных ролей. Эти роли определяют права доступа пользователя к различным частям приложения. Чаще всего роли назначаются при создании аккаунта или изменении прав пользователя администратором.

#### Механизм ролевого контроля:

- Роли хранятся в объекте пользователя (`User entity`).
- Контроллер или Twig-шаблон проверяют наличие необходимых ролей с помощью функций проверки (например, `$this->denyAccessUnlessGranted()` или `is_granted()`).
- Например, роль ROLE_ADMIN позволит доступ к административным страницам, а ROLE_USER даст доступ к профилю обычного пользователя.

Пример использования ролевой модели:

```php
$this->denyAccessUnlessGranted('ROLE_ADMIN'); // запрет доступа, если нет роли ROLE_ADMIN
```

### Voters (Голосующие субъекты)
Voters предоставляют дополнительный уровень контроля доступа поверх ролевых моделей. Они применяются, когда простого назначения ролей недостаточно для точной настройки авторизационных правил. Голосующие субъекты оценивают конкретную ситуацию и принимают решение, основываясь на контексте и дополнительных условиях.

Примеры ситуаций, где нужны voters:
- Нужно ограничить доступ к данным в зависимости от владельца ресурса.
- Необходимо учитывать дополнительные факторы, такие как дата публикации, статус элемента, принадлежность к определенной группе и т.д.

Механизм голосования:

- Создается класс-вотер, который реализует интерфейс `VoterInterface`.
- Вотер получает запрос на проверку доступа и возвращает одно из трех состояний: GRANTED (разрешено), ABSTAIN (нейтрально), ACCESS_DENIED (запрещено).
- В вотере можно написать любую логику, учитывающую контекст текущей сессии, данные объекта и прочие факторы.

Пример simple-voter:

```php
class PostVoter extends Voter
{
    const VIEW = 'view';
    const EDIT = 'edit';

    protected function supports(string $attribute, mixed $subject): bool
    {
        return in_array($attribute, [self::VIEW, self::EDIT]) &&
               $subject instanceof Post;
    }

    protected function voteOnAttribute(string $attribute, mixed $subject, TokenInterface $token): bool
    {
        /** @var User $user */
        $user = $token->getUser();

        switch ($attribute) {
            case self::VIEW:
                return true; // просмотр доступен любому авторизованному пользователю
            case self::EDIT:
                return $subject->getAuthor()->getId() === $user->getId(); // Редактировать пост может только автор
        }

        return false;
    }
}
```

Использование вотера:

```php
$this->denyAccessUnlessGranted(PostVoter::EDIT, $post); // разрешение на редактирование поста
```

### Когда выбирать roles vs voters?

- **Пользуйтесь ролями**, если ваша политика безопасности определяется простыми условиями, основанными на назначенных правах (например, доступ администратора к административной панели).
- **Выбирайте voters**, если необходимо учесть дополнительные условия и контекст (например, ограничение доступа к контенту на основе принадлежности автора, даты публикации и т.д.).

### Итоги:

- **Аутентификация** — подтверждение личности пользователя.
- **Роли** — назначение привилегий пользователям на основе предопределенных ролей.
- **Voters** — точный контроль доступа с возможностью учитывать контекст и дополнительные условия.

Чаще всего оптимальным решением является комбинация всех перечисленных инструментов: аутентификация подтверждает личность пользователя, роли задают общий доступ, а voters обеспечивают тонкую настройку политики безопасности.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

Хранение Value Object (объектов-значений) в Doctrine может вызвать сложности, особенно если домен требует, чтобы Value Object оставались неизменяемыми (immutable) и всегда находились в валидном состоянии. Причина в том, что Doctrine, будучи системой, ориентированной на сущности (Entities), по умолчанию работает с изменяемыми объектами и не всегда отлично подходит для работы с immutable-объектами.

Давайте рассмотрим несколько способов маппинга Value Object в Doctrine и обсудим их достоинства и недостатки.

---

### 1. Хранение Value Object как скалярных полей сущности

Простейшим подходом является представление Value Object в виде примитивных типов (скаляров), таких как строки или массивы, записываемых непосредственно в таблицу.

#### Пример:

Допустим, у нас есть Value Object `MoneyAmount`, содержащий сумму денег и валюту. Мы можем сохранить его как строку формата "$amount-$currency":

```php
class Product
{
    /**
     * @ORM\Column(type="string")
     */
    private string $moneyAmount;

    public function getMoneyAmount(): MoneyAmount
    {
        [$amount, $currency] = explode('-', $this->moneyAmount);
        return new MoneyAmount((float)$amount, $currency);
    }

    public function setMoneyAmount(MoneyAmount $moneyAmount): void
    {
        $this->moneyAmount = sprintf('%f-%s', $moneyAmount->getAmount(), $moneyAmount->getCurrency());
    }
}
```

#### Pros:
- **Простота**: минимальное вмешательство в модель данных.
- **Производительность**: минимальные накладные расходы при чтении и сохранении.

#### Cons:
- **Отсутствие защиты от неправильных данных**: поле можно изменить напрямую, минуя validation.
- **Зависимость от сериализации**: неудобство при необходимости изменений в формате представления данных.
- **Проблемы с консистентностью**: если домен требует валидных объектов, простое хранение примитивов не гарантирует валидность данных.

---

### 2. Custom Mapping with Embeddable

Более продвинутый подход — использование встраиваемых объектов (`Embeddable`). Доктрина позволяет создавать специальные классы для встраивания, которые сохраняют группы полей, относящихся к одному объекту.

#### Пример:

```php
/** @ORM\Embeddable */
class MoneyAmount
{
    /**
     * @ORM\Column(type="decimal", precision=10, scale=2)
     */
    private float $amount;

    /**
     * @ORM\Column(type="string", length=3)
     */
    private string $currency;

    public function __construct(float $amount, string $currency)
    {
        $this->amount = $amount;
        $this->currency = $currency;
    }

    // геттеры и сеттеры
}

/** @ORM\Entity */
class Product
{
    /**
     * @ORM\Embedded(class="MoneyAmount")
     */
    private MoneyAmount $moneyAmount;

    public function getMoneyAmount(): MoneyAmount
    {
        return $this->moneyAmount;
    }

    public function setMoneyAmount(MoneyAmount $moneyAmount): void
    {
        $this->moneyAmount = $moneyAmount;
    }
}
```

#### Pros:
- **Поддержка целостности**: легко реализовать проверку валидности при установке значений.
- **Удобство работы с объектом**: прямое обращение к полям Value Object без конверсий.

#### Cons:
- **Изменчивость**: embeddables изменяемы по умолчанию, и если домен требует неизменяемых объектов, придется дополнительно позаботиться о защите мутабельности.
- **Техническая сложность**: возможна путаница с полем видимости и изменением данных через embeddable.

---

### 3. Mapped Superclasses or Traits

Ещё один способ — использование суперклассов или трейтов для предоставления общей логики и хранения данных.

#### Пример:

```php
abstract class BaseProduct
{
    abstract public function getMoneyAmount(): MoneyAmount;

    abstract public function setMoneyAmount(MoneyAmount $moneyAmount): void;
}

class Product extends BaseProduct
{
    use MoneyAmountTrait;

    public function getMoneyAmount(): MoneyAmount
    {
        return $this->moneyAmount;
    }

    public function setMoneyAmount(MoneyAmount $moneyAmount): void
    {
        $this->moneyAmount = $moneyAmount;
    }
}

trait MoneyAmountTrait
{
    /**
     * @ORM\Column(type="decimal", precision=10, scale=2)
     */
    private float $amount;

    /**
     * @ORM\Column(type="string", length=3)
     */
    private string $currency;

    public function __construct(float $amount, string $currency)
    {
        $this->amount = $amount;
        $this->currency = $currency;
    }

    // далее идут геттеры и сеттеры
}
```

#### Pros:
- **Общая логика**: единый подход к реализации поведения Value Object.
- **Гибкость**: легко адаптировать и масштабировать с ростом приложения.

#### Cons:
- **Проблемы с иммутабельностью**: неизменяемость обеспечивается только частично, необходима защита от прямого изменения полей.
- **Повышенная сложность**: более сложная структура, связанная с использованием трейтовых классов и абстрактных родительских классов.

---

### 4. Использование специальных мапперов (Custom Hydrators and Converters)

Самым надежным способом добиться правильного хранения и работы с неизменяемыми Value Object является разработка кастомных конвертеров (custom hydrators) для доктрины.

#### Пример:

```php
class MoneyAmountConverter implements Type
{
    public function convertToDatabaseValue($value, AbstractPlatform $platform)
    {
        return [
            'amount' => $value->getAmount(),
            'currency' => $value->getCurrency(),
        ];
    }

    public function convertToPHPValue($value, AbstractPlatform $platform)
    {
        return new MoneyAmount($value['amount'], $value['currency']);
    }

    // остальное логику Type-реализации опускаю для краткости
}
```

#### Pros:
- **Полноценная поддержка Value Object**: полное соответствие требованиям домена (неизменяемость, валидность).
- **Надёжность**: полная гарантия правильности данных.

#### Cons:
- **Дополнительная сложность**: потребуется разработать специальный тип (custom type), обеспечивающий сериализацию и десериализацию.
- **Увеличение накладных расходов**: немного снижается производительность из-за сериализации/десериализации.

---

### Подводные камни:

- **Мутабельность**: большинство стандартных подходов предполагают мутабельные объекты, что конфликтует с требованием неизменяемости.
- **Проверка валидности**: если вы используете примитивные типы или встраиваемые объекты, помните, что данные могут стать недействительными при непосредственном доступе к полям.
- **Производительность**: выбор неправильного подхода может повлиять на производительность (например, чрезмерное использование сериализации или большой объём данных в виде вложенных объектов).

---

### Выводы:

Наиболее правильный подход для удовлетворения требования неизменяемости и валидности Value Object — использование кастомных типов (`custom types`) и конверторов (`converters`). Хотя это потребует чуть больше усилий на старте, оно обеспечит точное соответствие домену и гарантирует правильную работу приложения.

Остальные подходы могут использоваться как компромиссные решения в случае временных ограничений или низкой важности постоянного поддержания неизменности и валидности данных.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

Организация хранения агрегатов в Doctrine — одна из важнейших задач при построении эффективных и надежных систем. Особенно важно правильно управлять границами транзакций и отношениями между корнем агрегата и дочерними сущностями.

Агрегаты состоят из главного объекта (корня) и набора подчиненных объектов (детей). Ключевое требование — целостность данных: любые изменения, внесенные в корень или дочерние сущности, должны гарантированно происходить атомарно и целостно.

Давайте посмотрим на полный пример с точки зрения маппинга коллекций, транзакционной изоляции и вызова операции `flush`.

### Пример доменного агрегата: заказ и позиции заказа

Пусть наш агрегат — это заказ (`Order`), который содержит коллекцию позиций заказа (`OrderItem`). Каждая позиция заказа привязана к заказу и содержит информацию о товаре и количестве.

#### 1. Маппинг коллекций

Доктрина позволяет удобно маппировать коллекции дочерних сущностей, обеспечивая ссылочную целостность и каскадное удаление/обновление.

```php
// src/Entity/Order.php
/**
 * @ORM\Entity(repositoryClass=OrderRepository::class)
 * @ORM\Table(name="orders")
 */
class Order
{
    /**
     * @ORM\Id
     * @ORM\GeneratedValue(strategy="AUTO")
     * @ORM\Column(type="integer")
     */
    private $id;

    /**
     * @ORM\Column(type="datetime")
     */
    private $createdAt;

    /**
     * @ORM\OneToMany(targetEntity="OrderItem", mappedBy="order", cascade={"persist", "remove"})
     */
    private Collection $items;

    public function __construct()
    {
        $this->items = new ArrayCollection();
        $this->createdAt = new DateTimeImmutable();
    }

    public function addItem(OrderItem $item): void
    {
        if (!$this->items->contains($item)) {
            $this->items[] = $item;
            $item->setOrder($this);
        }
    }

    public function removeItem(OrderItem $item): void
    {
        $this->items->removeElement($item);
    }

    public function getItems(): Collection
    {
        return $this->items;
    }
}

// src/Entity/OrderItem.php
/**
 * @ORM\Entity(repositoryClass=OrderItemRepository::class)
 * @ORM\Table(name="order_items")
 */
class OrderItem
{
    /**
     * @ORM\Id
     * @ORM\GeneratedValue(strategy="AUTO")
     * @ORM\Column(type="integer")
     */
    private $id;

    /**
     * @ORM\Column(type="string", length=255)
     */
    private $productName;

    /**
     * @ORM\Column(type="integer")
     */
    private $quantity;

    /**
     * @ORM\ManyToOne(targetEntity="Order", inversedBy="items")
     * @ORM\JoinColumn(nullable=false)
     */
    private $order;

    public function getOrder(): Order
    {
        return $this->order;
    }

    public function setOrder(Order $order): void
    {
        $this->order = $order;
    }

    // геттеры и сеттеры для productName и quantity
}
```

#### 2. Границы транзакции

Все манипуляции с агрегатом должны быть заключены в единую транзакцию, чтобы гарантировать целостность данных. Для этого используют транзакционную изоляцию в Doctrine.

Пример правильного начала и завершения транзакции:

```php
// src/Service/OrderService.php
class OrderService
{
    private EntityManagerInterface $em;

    public function __construct(EntityManagerInterface $em)
    {
        $this->em = $em;
    }

    public function createOrder(array $data): Order
    {
        $order = new Order();
        foreach ($data['items'] as $itemData) {
            $item = new OrderItem();
            $item->setProductName($itemData['product_name']);
            $item->setQuantity($itemData['quantity']);
            $order->addItem($item);
        }

        $this->em->beginTransaction();
        try {
            $this->em->persist($order);
            $this->em->flush();
            $this->em->commit();
        } catch (\Exception $e) {
            $this->em->rollback();
            throw $e;
        }

        return $order;
    }
}
```

#### 3. Кто и когда вызывает `flush`?

Обычно вызовом `flush` занимаются сервисные слои, отвечающие за CRUD-операции с агрегацией (контроллеры, сервисы). Это гарантирует, что вся операция выполняется в единой транзакции и либо полностью завершится успешно, либо отменится целиком в случае ошибки.

Ключевые моменты:
- Выполнение `flush` должно произойти после полной сборки агрегата (добавлены все дочерние сущности).
- Управление транзакцией централизованно осуществляется в сервисе (или специальном слое).
- Обновления корней и детей должны идти единым пакетом, иначе возможны расхождения данных.

### Итоги:

- Агрегаты следует представлять в виде главной сущности и коллекции дочерних объектов.
- Важно использовать каскадные операции (`cascade={...}`), чтобы обеспечить согласованность при удалении и обновлении.
- Граница транзакции должна покрывать все операции с агрегатом, гарантируя целостность данных.
- Вызов `flush` должен производиться после полного формирования агрегата и желательно централизованно управляться в сервисе или соответствующем слое.

Организовав работу с агрегатами подобным образом, можно гарантировать сохранность данных и минимизировать вероятность некорректных состояний базы данных.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

Проблема N+1 запросов возникает, когда приложение делает большое количество мелких запросов к базе данных вместо одного крупного, что приводит к резкому росту нагрузки на СУБД и заметному замедлению страницы. Диагностика и исправление проблемы N+1 — обычная задача для разработчиков, работающих с Doctrine и Symfony.

### Диагностика проблемы N+1

Первый шаг — убедиться, что проблема действительно вызвана проблемой N+1. Для этого есть несколько проверенных методов:

1. **Профилирование запросов с помощью Blackfire или Xdebug**: инструменты профилирования позволяют увидеть, сколько запросов выполняется и насколько они влияют на скорость отклика страницы.

2. **Расширение Doctrine Debug Toolbar**: специальная панель Symfony Profiler показывает подробный отчет о выполненных запросах, позволяя выявить N+1 запросы.

3. **Просмотр логов запросов**: включите журналирование запросов Doctrine и посмотрите на количество и вид запросов. Обращайте особое внимание на одинаковые SELECT-запросы, выполняемые многократно.

Пример лога N+1:

```
SELECT * FROM orders WHERE id = :id1;
SELECT * FROM users WHERE id = :id2;
SELECT * FROM users WHERE id = :id3;
...
```

Здесь видно, что каждый запрос SELECT в отдельности вызывает задержку, когда можно было обойтись одним большим запросом JOIN.

### Решение проблемы N+1

Существует несколько техник для борьбы с проблемой N+1. Рассмотрим самые популярные из них и их плюсы и минусы.

#### 1. Eager Loading (Жадная загрузка)
Eager Loading — самый распространенный способ борьбы с N+1. Суть метода заключается в том, чтобы загружать связанные данные сразу при первой выборке, а не отдельными запросами впоследствии.

Пример:

```php
$queryBuilder
    ->select('o')
    ->from(Order::class, 'o')
    ->leftJoin('o.user', 'u')
    ->addSelect('u');
```

#### Pros:
- **Быстрое и эффективное решение**: сводит количество запросов к минимуму.
- **Легкость реализации**: легко применить через стандартные средства Doctrine.

#### Cons:
- **Перегруженность данных**: если отношение содержит большие объемы данных, жадная загрузка может негативно сказаться на памяти и производительности.
- **Избыточные данные**: при наличии большого количества ненужных данных могут возникать неэффективные запросы.

#### 2. Batch Loading (Пакетная загрузка)
Batch Loading — это стратегия, при которой запросы собираются и исполняются партиями. Используется, когда количество записей велико, и жесткие соединения невозможны.

Пример:

```php
foreach ($orders as $order) {
    $ids[] = $order->getUserId();
}

// Загрузить пользователей оптом
$users = $entityManager->createQueryBuilder()
    ->select('u')
    ->from(User::class, 'u')
    ->where('u.id IN (:ids)')
    ->setParameter('ids', $ids)
    ->getResult();
```

#### Pros:
- **Эффективность**: сокращение количества запросов при больших наборах данных.
- **Контроль данных**: можно фильтровать ненужные данные.

#### Cons:
- **Требует ручной работы**: необходимо самостоятельно собирать и группировать запросы.
- **Менее прозрачно**: сложнее читать и поддерживать код.

#### 3. Использование Hydration Mode (Гидрация)
Гидрация (hydration) позволяет задать форму извлечения данных из Doctrine. Режимы гидрации могут влиять на эффективность получения данных.

Пример использования ARRAY_HYDRATION:

```php
$query = $queryBuilder->getQuery();
$results = $query->getArrayResult(Query::HYDRATE_ARRAY);
```

#### Pros:
- **Быстродействие**: может ускорить выборку данных за счет отсутствия затрат на создание объектов.
- **Возможность тонкой настройки**: контроль извлеченных данных.

#### Cons:
- **Усложняется дальнейшая работа**: потери преимуществ ORM, сложность дальнейшей обработки данных.
- **Проблемы с ассоциациями**: может потребоваться дополнительное решение для восстановления связей.

#### 4. Using Query Cache (Кэширование запросов)
Кэширование запросов может уменьшить нагрузку на базу данных, сократив количество обращений к ней.

Пример:

```php
$query = $queryBuilder->getQuery();
$query->useQueryCache(true);
$query->useResultCache(true);
```

#### Pros:
- **Значительное ускорение**: заметно сокращает количество запросов при повторных обращениях.
- **Проще интегрировать**: легко добавляется в существующее приложение.

#### Cons:
- **Не решает саму проблему N+1**: не устраняет источник проблемы, а маскирует его.
- **Необходимость очистки кэша**: может требовать дополнительных мер по очистке устаревших данных.

### Trade-offs каждого способа:

- **Eager Loading**: лучший баланс эффективности и удобства, но возможен оверхед на крупные наборы данных.
- **Batch Loading**: хорошая альтернатива при больших объемах данных, но требует большей работы и внимания к деталям.
- **Hydration Mode**: быстрое повышение производительности, но лишает многие преимущества ORM.
- **Query Cache**: быстрое снижение нагрузки, но не устраняет проблему полностью и требует дополнительной настройки.

### Заключение

N+1 запросы — довольно распространённая проблема, которая решается разными способами в зависимости от характера приложения и особенностей используемых данных. Наиболее эффективными средствами борьбы являются Eager Loading и Batch Loading, но выбор конкретного подхода зависит от конкретных условий и требований к производительности.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

Бизнес-валидация на уровне приложения и ограничения целостности на уровне базы данных выполняют схожие, но не дублирующие функции. Их сочетание усиливает защиту данных и обеспечивает надежную и безопасную работу приложения.

### Почему необходимы ограничения целостности на уровне базы данных?

Даже если бизнес-правила прописаны в коде приложения, база данных выступает последним рубежом защиты целостности и достоверности данных. Причины, по которым ограничения на уровне базы данных важны:

1. **Безопасность**: в случае ошибки приложения или уязвимости база данных сможет защитить данные от повреждения или несогласованных изменений.
2. **Совместимость**: ограничения базы данных работают независимо от платформы и среды выполнения приложения.
3. **Непрерывность работы**: даже если в приложении произойдёт сбой, ограничения на уровне базы данных предотвратят потерю данных или повреждение.
4. **Резервный план**: валидация на уровне базы данных служит резервным уровнем защиты, защищающим от ошибок программирования.

### Средства для обеспечения ограничений целостности в PostgreSQL

PostgreSQL предлагает мощные механизмы для обеспечения целостности данных, позволяющие предотвратить нарушения ограничений и ошибки.

#### 1. Уникальность данных (UNIQUE constraints)
Обеспечивает уникальность значений столбцов таблицы, чтобы исключить дублирование записей.

Пример:

```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(255) UNIQUE NOT NULL
);
```

Pros:
- Предотвращение дубликатов на уровне базы данных.
- Высокая производительность.

Cons:
- Может вызвать проблемы с производительностью при большом объеме данных.

#### 2. Внешние ключи (Foreign Key Constraints)
Внешний ключ устанавливает ссылку между двумя таблицами, гарантируя, что запись ссылается на существующую запись в другой таблице.

Пример:

```sql
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INT REFERENCES users(id),
    amount DECIMAL NOT NULL
);
```

Pros:
- Поддерживает целостность ссылок между таблицами.
- Устойчивость к потере данных.

Cons:
- Несколько более низкая производительность при массовом вставлении данных.

#### 3. Индексы (Indexes)
Индексы улучшают производительность запросов и позволяют оперативно искать уникальные записи.

Пример:

```sql
CREATE INDEX idx_username ON users(username);
```

Pros:
- Значительно повышают производительность запросов.
- Надежность уникальных данных.

Cons:
- Увеличение потребления диска и некоторое увеличение накладных расходов при записи данных.

#### 4. Триггеры (Triggers)
Триггеры — это процедуры, запускающиеся автоматически при возникновении определенного события (вставка, обновление, удаление данных).

Пример:

```sql
CREATE FUNCTION validate_order_amount() RETURNS TRIGGER AS $$
BEGIN
    IF NEW.amount < 0 THEN
        RAISE EXCEPTION 'Сумма заказа не может быть отрицательной!';
    END IF;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER order_amount_validation BEFORE INSERT OR UPDATE ON orders FOR EACH ROW EXECUTE PROCEDURE validate_order_amount();
```

Pros:
- Гибкая логика для комплексных проверок.
- Непревзойденная защита от ошибок.

Cons:
- Сложность в сопровождении и диагностике.
- Производительность может снизиться при массовых операциях.

#### 5. Check Constraints
Check constraints — это декларативные выражения, проверяющие условие для столбца или комбинации столбцов.

Пример:

```sql
ALTER TABLE orders ADD CONSTRAINT positive_amount CHECK (amount >= 0);
```

Pros:
- Быстрое и легкое объявление ограничений.
- Надежность на уровне базы данных.

Cons:
- Невозможность комплексной логики, ограничивается простыми выражениями.

#### 6. Транзакционная целостность
Обеспечение целостности транзакций позволяет объединить серию операций в единую единицу работы, которая либо полностью выполняется, либо отменяется в случае ошибки.

Пример:

```sql
BEGIN TRANSACTION;
INSERT INTO users (username) VALUES ('user1');
INSERT INTO orders (user_id, amount) VALUES ((SELECT id FROM users WHERE username='user1'), 100.00);
COMMIT;
```

Pros:
- Обеспечивает атомарность и согласованность данных.
- Эффективность и простота реализации.

Cons:
- Рост нагрузки на базу данных при интенсивных операциях.

### Когда использовать?

- **UNIQ/EQUALITY CONSTRAINTS**: полезны везде, где важна уникальность данных (имена пользователей, номера счетов и т.д.).
- **FOREIGN KEYS**: обязательны при ссылочной целостности между таблицами.
- **CHECK CONSTRAINTS**: подходят для простых ограничений, таких как диапазон дат или неотрицательность суммы.
- **TRIGGERS**: используются для более сложных проверок, таких как бизнес-логика (например, подсчет остатков).
- **TRANSACTIONS**: обязательно при совершении сложных операций, влияющих на согласованность данных.

### Заключение

Несмотря на полноценную бизнес-валидацию на уровне приложения, ограничения целостности на уровне базы данных играют важную роль в обеспечении надежности и устойчивости системы. PostgreSQL предоставляет богатый инструментарий для этого, позволяя защищать данные даже в условиях неполадок или уязвимостей в приложении.

Медленно работающий запрос в PostgreSQL — это распространённая проблема, с которой сталкиваются разработчики и админы баз данных. Корень проблемы может крыться в неправильном индексе, плохом плане выполнения запроса, неподходящих настройках сервера или неправильно сформированном запросе. Я расскажу про пошаговую процедуру диагностики и оптимизации запросов, а также перечислю наиболее частые причины плохого быстродействия.

### Шаги диагностики и оптимизации:

#### 1. Профилировка и EXPLAIN ANALYZE
Первое, что нужно сделать — проанализировать, как именно PostgreSQL выполняет запрос. Самый полезный инструмент для этого — команда `EXPLAIN ANALYZE`, которая выводит подробную информацию о планах выполнения запроса.

```sql
EXPLAIN ANALYZE SELECT * FROM your_table WHERE some_column = 'some_value';
```

Команда покажет:
- План выполнения запроса (индексированный доступ, последовательное сканирование, сортировка и т.д.)
- Сколько времени занимает каждая стадия выполнения
- Количество затронутых строк и размер данных
- Фактическое время выполнения

#### 2. Анализ плана выполнения
Посмотрев вывод `EXPLAIN ANALYZE`, можно заметить узкие места. Обратите внимание на:
- Наличие последовательного сканирования (Seq Scan) — плохо, если таблица большая.
- Высокое время на сортировку (Sort) — значит, возможно, отсутствуют подходящие индексы.
- Недостаточно селективные фильтры (Filter) — вероятно, индекс выбран неудачно или отсутсвует вовсе.

Если видите значительные задержки, переходите к следующему шагу.

#### 3. Индексация
Самая частая причина медленного выполнения запроса — недостаточное покрытие нужных индексов. Посмотрим, как добавить индекс, если его нет:

```sql
-- Индекс по колонке some_column
CREATE INDEX index_your_table_some_column ON your_table(some_column);

-- Составной индекс, если фильтр сложный
CREATE INDEX composite_index ON your_table(col_a, col_b);
```

После добавления индексов проверьте заново с командой `EXPLAIN ANALYZE`, чтобы убедиться, что PostgreSQL начал их использовать.

#### 4. Мониторинг активности сервера
Может оказаться, что сама база данных испытывает высокие нагрузки, и дело не в конкретном запросе. Постарайтесь узнать общее состояние сервера с помощью утилиты pg_stat_statements или специализированных панелей мониторинга (например, PgHero или pgbadger):

```sql
SELECT query, total_time, calls, rows, mean_time 
FROM pg_stat_statements ORDER BY total_time DESC LIMIT 10;
```

#### 5. Проверка настроек сервера
Проверьте, правильно ли настроены параметры конфигурации PostgreSQL. Некоторые важные параметры:
- `work_mem`: Размер оперативной памяти, выделяемой на сортировки и группировки.
- `shared_buffers`: Объем буферов, используемых для кэширования данных.
- `effective_cache_size`: Указывает PostgreSQL предполагаемый объем доступной памяти для ОС и базы данных.

#### 6. Нормализация и денормализация
Если база данных нормализованная, подумайте, нет ли необходимости в денормализации. Присоединение большого количества таблиц может снизить производительность. Денормализация может сократить количество соединений и ускорить чтение данных.

#### 7. Пересборка статистики
Иногда статистика, хранимая PostgreSQL, устаревает, что приводит к плохим планам выполнения. Обновите статистику командой:

```sql
ANALYZE your_table;
```

#### 8. Дефрагментация и Vacuum
Со временем в таблицах накапливаются "мертвые" строки (особенно после удаления или изменения данных). Рекомендуется регулярное выполнение команд `VACUUM` и `REINDEX`:

```sql
VACUUM FULL your_table;
REINDEX TABLE your_table;
```

#### 9. Использование Partial Indexes
Частичные индексы (partial indexes) помогают оптимизировать запросы, содержащие фильтрацию по условиям. Если известно, что условие встречается редко, создайте индекс с условием:

```sql
CREATE INDEX partial_index_your_table_active_users ON your_table(user_status) WHERE active = TRUE;
```

#### 10. Материализованные представления
Если запрос часто выполняется и его результат меняется редко, рассмотрите возможность использования материализованного представления (materialized view). Оно поможет значительно ускорить последующий доступ к данным:

```sql
CREATE MATERIALIZED VIEW materialized_view AS
SELECT column1, SUM(column2) AS total_sum
FROM your_table GROUP BY column1;
```

### Типовые причины медленной работы запросов:

1. **Последовательное сканирование таблиц (Sequential Scans)** — отсутствуют полезные индексы.
2. **Недостаточно оперативной памяти (RAM)** — увеличьте `work_mem` или пересмотрите планы запросов.
3. **Большой объем сортируемых данных** — проверьте наличие индексов, помогающих сортировке.
4. **Загруженность сервера** — одновременные тяжелые запросы могут перегружать базу данных.
5. **Недостаточные настройки конфигурации** — перепроверьте базовые настройки PostgreSQL.
6. **Отсутствующие аналитические индексы** — убедитесь, что индексы обновляются и актуальны.
7. **Частые блокировки (Locking)** — выясните, не порождают ли долгие транзакции проблемы с конкурентностью.

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

В Domain-driven design (DDD) понятие агрегата играет ключевую роль. **Агрегат** — это группа связанных объектов (сущностей и объектов-значений), рассматриваемая как единое целое для целей обеспечения внутренней согласованности (consistency boundary). Внутри агрегата существует главный объект, называемый **агрегат-корнем** (Aggregate root), который контролирует доступ к остальным членам агрегата и гарантирует внутреннюю целостность и согласованность данных.

### Определение границ агрегата

Определение границ агрегата — это вопрос баланса и глубокого понимания предметной области. Границы агрегата устанавливаются исходя из логической близости и необходимости совместной работы объектов для поддержания их внутреннего состояния. Основные критерии выбора границ:

1. **Единичность изменений**: Если несколько объектов меняются одновременно в результате одного бизнес-процесса, они могут относиться к одному агрегату.
2. **Целостность**: Внутри агрегата данные должны находиться в согласованном состоянии. Поэтому агрегат объединяет объекты, чья внутренняя согласованность критична для успеха операции.
3. **Простота и удобство**: Следует избегать слишком крупных агрегатов, так как это сделает их трудноуправляемыми и громоздкими.

### Пример: Магазин электронной коммерции

Представим интернет-магазин с корзиной покупок и заказами.

#### Корзина (Shopping Cart)

- **Агрегат-корень**: Корзина (`Cart`).
- **Составляющие**:
  - Товары в корзине (`CartItem`).
  - Общая сумма (`total_price`).

Каждая операция (добавление товара, изменение количества, оформление покупки) должна поддерживать целостность данных корзины. Поэтому корзину и товары логично рассматривать как единый агрегат.

```php
class Cart
{
    private UUID $id;
    private array $cartItems = []; // Массив CartItem
    private float $totalPrice;

    public function addItem(CartItem $item): void
    {
        $this->cartItems[] = $item;
        $this->recalculateTotalPrice();
    }

    public function recalculateTotalPrice(): void
    {
        $this->totalPrice = array_reduce($this->cartItems, fn($carry, $item) => $carry + $item->getPrice(), 0);
    }

    // Другие методы
}

class CartItem
{
    private Product $product;
    private int $quantity;

    public function getPrice(): float
    {
        return $this->product->getUnitPrice() * $this->quantity;
    }

    // Другие методы
}
```

### Типовая ошибка при определении границ агрегата

Распространённой ошибкой является создание слишком широких или слишком узких агрегатов.

#### Проблема "слишком широкого агрегата"
Создавая крупный агрегат, разработчики пытаются объединить слишком много взаимосвязанных объектов, что усложняет их совместное использование и управление. Например, если объединить корзину и профиль пользователя в один агрегат, то простая операция, как смена адреса доставки, станет частью сложного процесса обновления корзины, что вызовет трудности при эксплуатации и снижении производительности.

#### Проблема "слишком узкого агрегата"
Другая крайность — создание слишком мелких агрегатов, которые слабо связаны между собой. Например, если сделать отдельным агрегатом каждый товар в корзине, это приведет к необходимости постоянно обращаться к нескольким разным агрегатам для совершения элементарных операций (например, расчёта итоговой суммы).

### Правильный подход к определению границ

- Изучите реальные сценарии использования.
- Соблюдайте границу согласования (consistent boundary): все объекты внутри агрегата должны меняться совместно.
- Рассматривайте потребности будущих изменений и потенциал роста системы.

### Заключение

Правильно установленные границы агрегата помогают минимизировать сложности и поддерживать высокий уровень производительности и согласованности данных. Поняв предметную область и придерживаясь критериев единства изменений и целостности, можно грамотно проектировать агрегаты, избегая типичных ошибок.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

Когда два процесса одновременно пытаются изменить один и тот же агрегат, возникает классическая проблема параллельного доступа (concurrent access problem), известная как проблема гонки данных (race condition). Последствия такого конфликта могут быть серьезными: потеря данных, рассогласованное состояние агрегата, неопределённое поведение системы.

Чтобы справиться с этой ситуацией, необходимо обеспечить согласованную работу с агрегатом в многопользовательской среде. Рассмотрим два основных подхода, применимые в большинстве современных систем:

### 1. Оптимистичная блокировка (Optimistic Locking)

Оптимистичная блокировка предполагает, что конкуренция за ресурс маловероятна, и при попытке обновления проверяется версия данных (version number или timestamp). Если другая транзакция успела внести изменения, вторая транзакция прерывается и уведомляет пользователя о конфликте.

**Как это работает:**

- В таблицу добавляется специальное поле (timestamp или version number).
- Перед началом транзакции берется текущее значение версии или временной отметки.
- При завершении транзакции сравнивается начальная версия с актуальной.
- Если версии отличаются, транзакция откатывается и выдается ошибка.

**Пример реализации:**

Допустим, у нас есть агрегат «Заказ» (`Order`), и мы хотим защититься от конфликтов при параллельном изменении:

```php
// Таблица Orders
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    status TEXT,
    updated_at TIMESTAMP DEFAULT NOW(),
    version INTEGER DEFAULT 0
);

// Класс Order
class Order
{
    private $id;
    private $status;
    private $updatedAt;
    private $version;

    public function updateStatus($newStatus, $currentVersion)
    {
        $this->status = $newStatus;
        $this->version++;
        // обновляем версию
    }
}

// Репозиторий
class OrderRepository
{
    public function update(Order $order)
    {
        $stmt = $this->db->prepare("UPDATE orders SET status=:status, updated_at=NOW(), version=version+1 WHERE id=:id AND version=:current_version");
        $stmt->execute([
            ':status' => $order->getStatus(),
            ':id' => $order->getId(),
            ':current_version' => $order->getVersion()
        ]);

        if ($stmt->rowCount() === 0) {
            throw new OptimisticLockException("Версия изменилась, повторите попытку.");
        }
    }
}
```

**Преимущества:**
- Низкий расход ресурсов на синхронизацию.
- Позволяет большинству транзакций проходить успешно, если конкуренция низка.

**Недостатки:**
- Не подходит для высококонкурентных сред, где столкновения вероятны.
- Пользователям приходится повторять попытки при конфликтах.

### 2. Пессимистичная блокировка (Pessimistic Locking)

Пессимистичная блокировка предполагает, что конфликты неизбежны, и для предотвращения конфликтов вводится жесткая блокировка на агрегат. Пока один процесс удерживает блокировку, другие вынуждены ждать освобождения ресурса.

**Как это работает:**

- При попытке изменения блока система накладывает эксклюзивную блокировку на агрегат.
- Другие процессы ожидают снятия блокировки.
- Когда первая транзакция освобождает ресурс, следующий процесс продолжает работу.

**Пример реализации:**

```php
// Пример с PDO
$stmt = $pdo->prepare("SELECT * FROM orders WHERE id=? FOR UPDATE");
$stmt->execute([$orderId]);
$order = $stmt->fetch(PDO::FETCH_ASSOC);

// Далее работаем с заблокированным агрегатом
// После окончания работы снимаем блокировку
$pdo->commit();
```

**Преимущества:**
- Полностью исключает конфликты и потерянные обновления.
- Хорошо подходит для высоконагруженных систем с высокой степенью конкуренции.

**Недостатки:**
- Потребляет больше ресурсов на блокировку.
- Может снижать производительность из-за ожидания блокировки.

### Практические советы:

- **Оценивайте частоту столкновений**: если конфликты редки, оптимистичная блокировка предпочтительна.
- **Используйте гибридный подход**: если частота конфликтов высока, рассмотрите комбинацию обоих методов.
- **Мониторьте конфликты**: ведение логов и анализ частоты конфликтов поможет принимать взвешенные решения.

### Заключение

Параллельное изменение одного и того же агрегата неизбежно, если система обслуживает множество пользователей. Проектируя систему, важно выбрать подходящую стратегию блокировок, учитывая характеристики предметной области и ожидаемые рабочие нагрузки. Оптимистичная блокировка хороша в обычных условиях, а пессимистичная — в высоконагруженных средах с высоким риском конфликтов.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

Доменные события (domain events) широко применяются в DDD (Domain-Driven Design) для обмена информацией между элементами системы, реагирования на изменения в бизнесе и децентрализации логики. Доменные события помогают выстроить более гибкую и слабосвязанную архитектуру, делая систему масштабируемой и удобной для поддержки.

### Когда публиковать доменные события?

- **После значимых изменений в предметной области**: публикация событий после успешных операций, таких как регистрация пользователя, оплата заказа, размещение товара на складе и т.д.
- **Перед принятием важного решения**: событие может информировать другие компоненты о наступлении какого-либо обстоятельства, которое может потребовать реакции (например, исчерпывание запасов товара).
- **Реакция на внешние воздействия**: уведомления о событиях от внешней системы или пользователя.

### Пример использования доменных событий

Допустим, у нас есть магазин одежды, и при размещении заказа необходимо опубликовать событие, чтобы запустить соответствующую реакцию (рассылку уведомлений, уменьшение складского остатка, выставление счета покупателю).

#### Публикация события:

```php
// Заказ успешно оформлен
class OrderPlacedEvent
{
    private Order $order;

    public function __construct(Order $order)
    {
        $this->order = $order;
    }

    public function getOrder(): Order
    {
        return $this->order;
    }
}

// Внутренняя логика заказа
class OrderService
{
    public function placeOrder(Order $order): void
    {
        // логика оформления заказа
        $eventDispatcher->publish(new OrderPlacedEvent($order)); // публикуем событие
    }
}
```

#### Обработка события:

```php
// обработчик события
class NotifyCustomerWhenOrderPlacedListener
{
    public function handle(OrderPlacedEvent $event): void
    {
        $order = $event->getOrder();
        $customerEmail = $order->getCustomer()->getEmail();
        mail($customerEmail, 'Ваш заказ №'.$order->getNumber().' успешно оформлен.', 'Спасибо за покупку!');
    }
}

// диспетчер событий
class EventDispatcher
{
    private array $listeners = [];

    public function publish(DomainEvent $event): void
    {
        foreach ($this->listeners as $listener) {
            $listener->handle($event);
        }
    }

    public function subscribe(EventListener $listener): void
    {
        $this->listeners[] = $listener;
    }
}
```

### Проблемы, которые решают доменные события:

1. **Разделение ответственности**: логика обработки событий перемещается в отдельные обработчики, оставляя корни агрегатов чистыми и свободными от второстепенной логики.
2. **Масштабируемость**: появляется возможность горизонтального масштабирования за счёт вынесения обработчиков событий в отдельные сервисы.
3. **Устойчивость к изменениям**: легко добавить новые обработчики событий, не меняя существующего кода.
4. **Упрощение архитектуры**: уменьшается сложность и связность компонентов, улучшается читаемость и сопровождаемость кода.

### Проблемы, создаваемые доменными событиями:

1. **Трудности с трассировкой**: увеличивается сложность отладки, так как логику обработки событий приходится отслеживать отдельно.
2. **Потенциальные аномалии**: если событие обработано дважды или упущено, возможны несоответствия данных.
3. **Производительность**: обработка событий может увеличить потребление ресурсов и снизить производительность системы.

### Связь с транзакциями базы данных

Важнейший аспект применения доменных событий — обеспечение их атома́рности с транзакциями базы данных. Два основных подхода:

1. **After-commit hook**: событие публикуется после успешного завершения транзакции. Это позволяет быть уверенным, что событие будет опубликовано только в случае успешного завершения операции.

   Пример:

   ```php
   // публикация события после фиксации транзакции
   class TransactionalEventDispatcher
   {
       private array $events = [];

       public function queueEvent(DomainEvent $event): void
       {
           $this->events[] = $event;
       }

       public function dispatchEvents(): void
       {
           foreach ($this->events as $event) {
               $this->publish($event);
           }
           $this->events = [];
       }
   }

   // в репозитории или службе
   $dispatcher->queueEvent(new OrderPlacedEvent($order));
   $entityManager->transactional(function () use ($dispatcher) {
       // логика обработки
       $dispatcher->dispatchEvents();
   });
   ```

2. **Сообщения очереди**: помещение события в очередь сообщений (например, RabbitMQ) с гарантией транзакционного поведения (используя двойную фиксацию).

   Пример:

   ```php
   // постановка события в очередь
   class QueueBasedEventDispatcher
   {
       public function publish(DomainEvent $event): void
       {
           $producer->produce(json_encode($event));
       }
   }
   ```

   В таком случае само событие ставится в очередь после фиксации транзакции, и его обработка выполняется отдельным рабочим процессом.

### Заключение

Применение доменных событий способствует улучшению архитектуры и гибкости системы, позволяя разделять ответственность и улучшать масштабируемость. Вместе с тем, необходимо внимательно подходить к вопросам транзакционности и согласованности данных, чтобы избежать потенциальных проблем.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

В терминологии Domain-Driven Design (DDD) понятия Value Object и Entity принципиально различаются, хотя внешне могут выглядеть похожими. Правильное различие между ними оказывает огромное влияние на дизайн и архитектуру системы, поэтому давайте разберём их различия и поясним, как принять решение о классификации концепций домена.

### Отличия Value Object от Entity

1. **Identity (идентичность)**:
   - **Entity**: Имеет уникальную идентификацию (identity), которая отличает её от других объектов. Даже если содержимое (данные) одинаковое, экземпляры рассматриваются как разные объекты.
   - **Value Object**: Идентифицируется своим содержимым (значение, state). Экземпляры считаются равнозначными, если их содержимое совпадает.

2. **Mutability (изменяемость)**:
   - **Entity**: Обычно изменяется (мутируется) в течение своего жизненного цикла. То есть его свойства могут изменяться, оставаясь тем же самым объектом.
   - **Value Object**: Должен быть неизменяемым (immutable). Любой его изменение приводит к созданию нового объекта.

3. **Цель использования**:
   - **Entity**: Представляет уникальный объект с историей изменений (например, пользователь, заказ, статья).
   - **Value Object**: Служит для описания характеристик или качеств (например, деньги, адрес, цвет).

### Примеры:

- **Entity**: Пользователь (User), заказ (Order), автомобиль (Car).
- **Value Object**: Деньги (Money), почтовый адрес (Postal Address), телефонный номер (Phone Number).

### Как принимаешь решение о классификации?

Есть несколько признаков, которые помогут классифицировать концепцию домена:

1. **Наличие уникальной идентификации**: если концепция требует уникальности и постоянства идентификатора, это Entity. Например, ID пользователя или ID заказа.
2. **Способность мутировать**: если объект подлежит изменению (изменение данных, статуса и т.д.), это Entity. Если объект описывает характеристику и не нуждается в изменениях (адрес или денежная сумма), это Value Object.
3. **Иммутабельность**: если свойство концепта может меняться без влияния на сам объект (например, баланс банковского счёта), это признак Entity. Если изменение свойства подразумевает замену объекта новым (например, новая валюта для денежной суммы), это Value Object.

### Пример принятия решения:

- **Концепция "Денежная сумма"**: она однозначно относится к Value Object, так как представлена уникальным набором валюты и номинала, и при изменении валюты или номинала получается новый объект.
- **Концепция "Продукт"**: это Entity, так как каждый продукт уникален, имеет постоянный идентификатор и подвержен изменениям (например, изменению названия или цены).

### Ubiquitous Language (Единый язык)

Ubiquitous Language (UL) — это один из центральных терминов DDD, означающий общепринятый и понятный язык общения между разработчиками и бизнесом. UL призван преодолеть разрыв между техническим жаргоном и терминами бизнеса, устанавливая чёткие и однозначные обозначения для всех концепций предметной области.

**Особенности Ubiquitous Language:**

- **Язык команды**: общими усилиями участников проекта формируется словарь терминов, который понимают все участники процесса.
- **Однозначность**: каждое слово и фраза в языке имеют единственное значение и употребляются одинаково всеми участниками.
- **Практичность**: язык должен быть простым и естественным, близок к языку реальных сотрудников компании.

### Влияние Ubiquitous Language на код

Использование единого языка отражается на дизайне и архитектуре системы следующим образом:

1. **Имя объектов и методов**: имена классов, методов и переменных отражают термины, используемые в предметной области. Например, класс `Product` вместо технического термина `Good`, название метода `calculateTax` вместо `computeVAT`.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

Чистая архитектура (Clean Architecture) — это подход к проектированию программного обеспечения, предложенный Робертом Мартином (Uncle Bob), который стремится к максимальной независимости бизнес-логики от технологий, платформ и внешних зависимостей. Согласно чистой архитектуре, система делится на слои, где каждый слой обладает собственными обязанностями и зависимостями, направленными строго внутрь. Давайте рассмотрим, как структура типичного PHP-приложения (например, на Symfony) может быть организована согласно принципам чистой архитектуры.

### Слои чистой архитектуры

Чистая архитектура традиционно делит приложение на четыре слоя:

1. **Domain layer (ядро домена)**:
   - Бизнес-логика, бизнес-правила и модели предметной области.
   - Независимо от внешних факторов (фреймворков, баз данных, UI).
   - Включает в себя доменные сущности, Value objects, Aggregates и Domain Events.
   - Не зависит ни от чего снаружи.

2. **Application layer (прикладной слой)**:
   - Координация работы бизнес-логики и трансляция её в команды и запросы.
   - Содержит Use Cases, которые воплощают конкретные сценарии взаимодействия с пользователями.
   - Работает с бизнес-логикой (доменом), но не зависит от представлений или инфраструктуры.

3. **Infrastructure layer (инфраструктурный слой)**:
   - Взаимодействие с внешним миром: базы данных, сети, почта, RESTful API, очереди и т.д.
   - Сюда входят драйвера, адаптеры и реализации репозиториев.
   - Зависящий от внешнего мира, например, от Doctrine или Symfony.

4. **Presentation layer (слой презентации)**:
   - Ответственен за взаимодействие с конечными пользователями (UI, фронтенд, API).
   - Этот слой зависит от прикладного слоя и никак не вмешивается в бизнес-логику.
   - Например, сюда относятся контроллеры, формы, представления и шаблоны.

### Правила зависимостей

Самое важное правило чистой архитектуры — направление зависимостей идёт только вовнутрь. Верхние слои зависят от нижних, но обратное невозможно. Другими словами:

- Инфраструктура и Презентация зависят от Прикладного слоя.
- Прикладной слой зависит от ядра домена.
- Ядро домена не зависит ни от кого.

Графически это изображается в виде концентрических окружностей, где ядро находится в центре, а остальные слои располагаются вокруг него.

### Распределение компонентов по слоям

- **Doctrine** попадает в **инфраструктурный слой**, так как это драйвер доступа к данным (DAO), обеспечивающий подключение к базе данных.
- **Symfony-контроллер** располагается в **слое презентации**, так как он отвечает за приём запросов от пользователя и передачу их на верхний слой.
- **Обработчик очереди** тоже находится в **инфраструктурном слое**, поскольку это компонент, ответственный за работу с внешней системой (очередью сообщений).

### Пример распределения по слоям:

1. **Domain layer (ядро домена)**:
   - Продукты (Product), заказы (Order), пользователи (User).
   - Business rules: расчет налогов, скидок, проверка корректности заказа.

2. **Application layer (прикладной слой)**:
   - PlaceOrderUseCase, CalculateDiscountUseCase.
   - Facades и Interactors для взаимодействия с Presentation и Infrastructure.

3. **Infrastructure layer (инфраструктурный слой)**:
   - Doctrine ORM (для доступа к базе данных).
   - Mailer (SMTP, почтовая рассылка).
   - AMQP (RabbitMQ, обработка очередей).

4. **Presentation layer (слой презентации)**:
   - Symfony-контроллеры, рендеринг HTML, REST API.
   - Входящие HTTP-запросы, формы ввода, шаблоны (Twig).

### Следим за соблюдением границ слоёв

Чтобы следить за соблюдением чистоты архитектуры и не допустить проникновения зависимостей наружу, применяют несколько методик:

1. **Архитектурные тесты**: Напишите автоматизированные тесты, проверяющие правильность следования правилам зависимостей (правило "зависимости направлены вовнутрь").

2. **Анализ зависимостей**: Современные IDE (например, PhpStorm) и статические анализаторы (Psalm, Phan) способны выявлять нежелательные зависимости между модулями.

3. **Абстрактные контракты**: Создавайте интерфейсы (Contracts) в верхних слоях и внедряйте их в нижние слои через внедрение зависимостей (Dependency Injection). Например, пусть презентативный слой знает только интерфейс `IPlaceOrderInteractor`, а реализация принадлежит прикладному слою.

4. **Код ревью**: Руководители и опытные коллеги могут анализировать и обсуждать код, убеждаясь, что соблюдаются правила чистых зависимостей.

### Заключение

Организация приложения по принципам чистой архитектуры помогает минимизировать риски технической задолженности, делает приложение гибким и легкопереносимым на другие технологические стеки. Самое главное преимущество — ясно очерченные границы и направления зависимостей, что позволяет бизнесу развиваться независимо от технических деталей.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

Тестирование в Symfony-приложении с PostgreSQL следует проводить в соответствии с классической пирамидой тестов, где большее количество низкоуровневых тестов сочетается с меньшими количествами высокоуровневых интеграционных и end-to-end тестов. Тестирование должно охватывать все важные компоненты и гарантировать высокое качество кода и стабильность системы.

### Пирамида тестов:

1. **Юнит-тесты (Unit tests)**:
   - Цель: проверка работоспособности отдельных классов и функций.
   - Основное внимание уделяется внутренним компонентам, сервисам и модулям, работающим с бизнес-логикой и основными вычислительными алгоритмами.

   - Проверяются связи между слоями (репозитории, сервисы, контроллеры), взаимодействие с внешними системами (например, база данных, очереди сообщений).

3. **Функциональные (End-to-end) тесты (Functional/E2E tests)**:
   - Цель: тестирование сквозных сценариев пользователя (User Journey).
   - Проводятся на уровне браузера или HTTP-запросов, имитируют поведение пользователя.
   - Пример: тестирование прохождения полного сценария регистрации, оформления заказа и оплаты.

### Юнит-тесты (Unit Tests)

Цель юнит-тестов — проверить работоспособность отдельных компонентов, игнорируя зависимости и внешние системы. Тестируются сервисы, репозитории, фабрики и доменные объекты.

#### Что мокается:
- Внешние зависимости (базы данных, сетевые вызовы, внешние сервисы).
- Сторонние библиотеки и компоненты.

#### Пример теста с мокингом:

```php
use PHPUnit\Framework\TestCase;
```

### Интеграционные тесты (Integration Tests)

Интеграционные тесты проверяют взаимодействие между несколькими компонентами. Важно протестировать весь стэк приложения, включая взаимодействие с базой данных, очереди сообщений и сторонние сервисы.

#### Что мокается:
- Только сторонние внешние системы (API, внешние базы данных), если их трудно эмулировать локально.


Эти тесты проверяют работу приложения в целом, от фронта до бэка. Для этого подойдут инструменты вроде Behat, Selenium WebDriver или же PHPUnit с симуляцией HTTP-запросов.

1. **Избегайте внешних зависимостей**: Мокайте внешние сервисы, чтобы не зависеть от сторонних ресурсов (это сделает тесты быстрее и стабильнее).

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Когда два пользователя одновременно изменяют одну и ту же запись в базе данных, возникает так называемая проблема "гонки данных" (**Race Condition**) или "конкуренции" (**Concurrency Problem**). Это может привести к ряду серьёзных проблем:

### Возможные проблемы:

1. **Потеря данных (Lost Updates)**:
   - Второй пользователь перезаписывает изменения, сделанные первым пользователем, что приводит к потере данных.

2. **Несоответствие данных (Dirty Reads)**:
   - Первый пользователь считывает данные, второй пользователь меняет их, и затем первый пользователь вновь записывает старые данные, аннулируя изменения второго пользователя.

3. **«Фантомные» записи (Phantom Read)**:
   - Пользователи видят разные копии данных в процессе работы, что может приводить к непоследовательности данных.

4. **Deadlock (блокировка)**:
   - Происходит взаимоисключение, когда оба пользователя ждут друг друга, что приводит к остановке работы обеих транзакций.

### Способы защиты от гонок данных:

Существуют два основных подхода к обеспечению конкурентоспособности и согласованности данных: **пессимистическая блокировка** и **оптимистическая блокировка**.

#### 1. Пессимистическая блокировка (Pessimistic locking)

Идея пессимистической блокировки заключается в том, что перед изменением записи производится её монопольная блокировка. Пока один пользователь занят изменениями, другие пользователи ждут освобождения блокировки.

##### Как это работает:
- Пользователь открывает транзакцию и блокирует запись.
- Другой пользователь вынужден ожидать освобождения блокировки.
- После завершения транзакции блокировка снимается.

Пример в PostgreSQL:

```sql
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT * FROM products WHERE id = 1 FOR UPDATE;
-- тут производим изменения
UPDATE products SET price = 100 WHERE id = 1;
COMMIT;
```

##### Pros:
- Абсолютная уверенность в отсутствии коллизий и потерь данных.
- Удобство реализации в случае высоких нагрузок и сильной конкуренции.

##### Cons:
- Блокировки снижают производительность и увеличивают время отклика.
- Возможны deadlocks, если блокировки пересекаются.

#### 2. Оптимистическая блокировка (Optimistic locking)

Вместо физической блокировки оптимистическая блокировка полагается на проверку того, изменилось ли состояние записи с момента её первоначального чтения. Если запись осталась прежней, изменения применяются; в противном случае происходит сброс изменений и выдаётся ошибка.

Оптимистическая блокировка часто реализуется с помощью добавления поля **версии** (version field) или **таймстемп** (timestamp), проверяя их при обновлении.

Пример в PostgreSQL:

```sql
UPDATE products
SET price = 100, version = version + 1
WHERE id = 1 AND version = 5;
```

Если запрос возвращает 0 обновлённых строк, значит, произошла коллизия, и нужно повторить попытку.

Также можно реализовать это в Doctrine ORM:

```php
class Product
{
    /**
     * @ORM\Column(type="integer")
     * @ORM\Version
     */
    private $version;

    // getter/setter
}
```

Теперь Doctrine автоматически проверяет версию при обновлении и поднимает исключение, если возникла коллизия.

##### Pros:
- Малое влияние на производительность и доступность.
- Простота реализации и минимум влияния на нормальную работу приложения.

##### Cons:
- Необходимость дополнительной логики для обработки коллизий.
- Некоторое количество попыток повторных операций при конфликте.

### Сравнение подходов:

- **Пессимистическая блокировка**:
  - Плюс: абсолютная гарантия защиты от конфликтов.
  - Минус: сильная нагрузка на систему, возможность блокировки (deadlock).

- **Оптимистическая блокировка**:
  - Плюс: минимальная нагрузка на систему, хорошая производительность.
  - Минус: необходимо аккуратно обрабатывать коллизии и повторные попытки.

### Когда выбирать:

- **Пессимистическая блокировка**: используется в случаях высокой интенсивности изменений и риска потерять данные. Например, в финансовых системах, где точность данных критична.

- **Оптимистическая блокировка**: подходит для большинства случаев, где конфликты редки и потери данных не столь критичны. Например, онлайн-магазины, блоги и социальные сети.

### Заключение

Выбор подхода зависит от природы приложения и степени чувствительности к потерям данных. В большинстве случаев оптимистическая блокировка предпочтительнее, так как она обеспечивает лучшую производительность и меньше влияет на повседневную работу системы. Однако в особо чувствительных областях (банковская сфера, медицинская информация) предпочтение отдаётся пессимистическим подходам.

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

Мой рабочий процесс с использованием Git охватывает этапы от постановки задачи до выпуска готового продукта в production. Основная цель процесса — обеспечить качественную и контролируемую доставку кода, свести к минимуму человеческие ошибки и позволить команде эффективно сотрудничать. Вот мой подход:

### 1. Постановка задачи и ветвление

Каждую задачу (bug fix, feature, improvement) начинаю с создания новой ветви от основной линии разработки (`main` или `develop`):

- **Feature branches**: Названия ветвей выглядят так: `feature/<описание>`, например, `feature/add-user-profile-page`.
- **Bugfix branches**: Название начинается с префикса `bugfix/`, например, `bugfix/login-error`.
- **Hotfix branches**: При срочных исправлениях создается ветвь `hotfix/*`, например, `hotfix/db-connection-failure`.

Почему так:
- Ясные и короткие названия ветвей позволяют мгновенно понять, какая задача решается.
- Разработчику предоставляется свобода экспериментировать в обособленном пространстве без риска сломать мастер.

### 2. Формат коммитов

Коммиты формируют историю проекта, поэтому их содержание и стиль крайне важны. Мой подход к формированию сообщений коммитов:

- **Стандарт commitlint**: Сообщения коммитов формируются по схеме `<type>(optional scope): subject\n\nbody`.
- **Типы коммитов**: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `chore`, `build`, `ci`, `revert`.
- **Краткость и ясность**: лаконичные, точные заголовки и тела коммитов, объясняющие, зачем и что именно сделано.

Пример хорошего коммита:

```
feat(authentication): Добавлена возможность входа через Google OAuth
Добавлено новое окно для авторизации через Google, исправлены пути перенаправления.
Fixes #123
```

Почему так:
- Структурированное сообщение коммита упрощает навигацию по истории проекта.
- Чёткие и регулярные стандарты облегчают ревью и последующее понимание логики изменений.

### 3. Pull Request (PR) и Code Review

Когда задача выполнена, я создаю PR обратно в основную линию разработки. Обязательным этапом является peer review:

- **Правила ревью**: Минимум один одобряющий отзыв от коллег с опытом работы над проектом.
- **Требования к PR**: Должны быть включены чеклисты по качеству кода, покрытию тестами, документации и возможному воздействию на продакшн.
- **Branch protection rules**: Основные ветки защищены, принудительные пуши запрещены.

Почему так:
- Ревью улучшает качество кода, помогает найти ошибки и улучшает взаимопонимание в команде.
- Предварительная проверка перед слиянием снижает риски попадания некачественного кода в mainline.

### 4. Кодогенерация и Continuous Integration (CI)

До слияния ветки проходят через автоматизированные тесты и проверки:

- **Linter & Formatter**: Автопроверка стиля кода (PSR-12, prettier, eslint и т.д.).
- **Static Analysis**: Анализ кода инструментами (Psalm, PHPStan).
- **Unit & Integration Testing**: Автоматическое выполнение тестов на Jenkins/GitHub Actions.
- **Security Checks**: Безопасность кода проверяется через scanners (Snyk, SonarQube).

Почему так:
- Раннее выявление ошибок экономит время и усилия разработчиков.
- Стандартизированные проверки повышают качество и чистоту кода.

### 5. Release Cycle и Deployment

Выпуски (релизы) готовятся и выпускаются через отдельную ветвь (`release/*`) или тег:

- **Semantic Versioning**: Новые выпуски маркируются по стандартной схеме MAJOR.MINOR.PATCH.
- **Changelog**: Ведётся история изменений, описывающая внесённые доработки и улучшения.
- **Automated deployment pipeline**: Прохождение релизов через CI/CD конвейер (Docker/Kubernetes, Ansible/SaltStack).

Почему так:
- Семантическое версионирование позволяет пользователям и команде понять масштабы изменений.
- Automated deployments обеспечивают бесшовный и безопасный деплоймент.

### Итог

Весь процесс построен на:

- Четкой организационной структуре (ветви, коммиты, ревью).
- Качественных проверках (анализ, тестирование, security checks).
- Подготовленности к деплою и выпуску качественных релизов.

Такой подход позволяет своевременно выявлять ошибки, повышать качество кода и эффективно выпускать готовые продукты.

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

Хороший code-review — это сбалансированный процесс, направленный на повышение качества кода, обучение и сотрудничество между членами команды. Ниже я изложу мои взгляды на организацию эффективного ревью и как я действую в ходе него.

### Признаки хорошего code-review:

1. **Чёткость формулировки комментариев**: замечания сформулированы конкретно и понятно, без двусмысленности. Автор должен ясно видеть, что именно надо исправить и почему.

2. **Фокус на качестве**: акцент сделан на повышении качества кода, будь то улучшение структуры, производительность, безопасность или читаемость.

3. **Этика и уважение**: комментарии вежливые, доброжелательные и уважительны к труду автора. Критика направлена на код, а не на человека.

4. **Активное обсуждение**: ревью предполагает диалог, а не диктаторские указы. Важно выслушать точку зрения автора и обсудить возможные компромиссы.

5. **Баланс между глубиной и широтой**: ревью не сводится к мелочным придиркам или поверхностному взгляду. Важно найти золотую середину, обратить внимание на существенные аспекты, но не отвлекаться на незначительные детали.

### Маркировка замечаний:

- **Blocker (блокирующая ошибка)**: критичное замечание, которое препятствует принятию PR. Требует обязательного исправления.
- **Major (важное)**: значительное замечание, касающееся архитектуры, производительности или очевидных недостатков. Исправление настоятельно рекомендовано.
- **Minor (незначительное)**: мелкие замечания по стилю или мелочам, которые можно поправить позже.
- **Suggestion (совет)**: предложения по улучшению, которые не обязательны к исполнению, но рекомендуются.

### Что смотрю в первую очередь:

1. **Читаемость и поддерживаемость**: соответствует ли код стандартам качества, PSR, лучшим практикам и стилю команды.
2. **Соответствие требованиям задачи**: решены ли все пункты задачи, ничего не пропущено?
3. **Производительность**: нет ли узких мест, медленных запросов или излишних итераций.
4. **Тестовое покрытие**: покрыты ли изменения соответствующими тестами (unit/integration/e2e)?
5. **Безопасность**: отсутствуют ли известные угрозы безопасности (XSS, SQL-injections, CSRF и т.д.)?
6. **Логирование и обработка ошибок**: адекватно ли логируются ошибки и исключения?

### Действия при разногласиях с автором:

1. **Обсудить лично**: предпочитаю личное общение (видео-конференция, чат) для быстрого разрешения вопросов и недопониманий.
2. **Проговорить преимущества и недостатки**: объяснить свою позицию и выслушать контраргументы автора.
3. **Спросить мнение третьих лиц**: привлечь старших разработчиков или тимлидов для помощи в принятии решения.
4. **Принять компромисс**: если компромисс найден, зафиксировать его в комментариях к ревью.
5. **Продолжить дискуссию**: если соглашение не достигнуто, продолжать конструктивное обсуждение вплоть до принятия коллективного решения.

### Итог

Хороший code-review — это искусство сочетать глубину и такт, умение критиковать профессионально и поддерживать атмосферу сотрудничества. Эффективный ревью помогает команде расти, укрепляет доверие и улучшает качество продукта.

## Q22 · Работа с задачами

**Интервьюер:** Ты выполняешь задачу с чёткими критериями приёмки. По ходу работы выясняется: а) нашёл попутный баг, не связанный с задачей; б) понял, что один из критериев приёмки противоречит цели задачи. Что делаешь в каждом случае и почему?

**Кандидат:**

Решая задачу с чёткими критериями приёмки, очень важно действовать ответственно и этично, учитывая интересы проекта и заказчиков. Рассмотрим, как поступить в обоих случаях:

### Случай a) Нашёл попутный баг, не связанный с задачей

**Действия:**

1. **Зафиксировать баг**: записать точную информацию о баге (ошибочном поведении, окружении воспроизведения, предполагаемых причинах и рекомендациях по устранению).
2. **Создать тикет**: завести отдельный issue/ticket в трекере задач (JIRA, YouTrack, Trello и т.д.), описать проблему и прикрепить необходимую информацию.
3. **Сообщить руководителю или менеджеру проекта**: проинформировать команду о находке, отметив важность и приоритет багфикса.
4. **Получить инструкции**: дождаться обратной связи руководства о дальнейших действиях (исправить баг в рамках текущей задачи или передать другому специалисту).

**Почему так:**

- Баг, не связанный с текущей задачей, не входит в рамки работы, и включение его в текущую задачу увеличит срок выполнения и стоимость.  
- Создавая отдельное задание, мы обеспечиваем прозрачность процесса и можем вовремя спланировать исправление дефекта.
- Команда сможет оценить значимость бага и расставить приоритеты соответственно.

### Случай b) Один из критериев приёмки противоречит цели задачи

**Действия:**

1. **Сделать заметку**: отметить противоречивый критерий в документах задачи или внутреннем документе.
2. **Связаться с заказчиком или менеджером**: обратиться к инициатору задачи и разъяснить проблему, обосновав несоответствие.
3. **Предложить коррекцию**: подготовить предложение по исправлению или отмене критерия, подкрепленное аргументами и преимуществами.
4. **Добиться согласия**: дожидаясь одобрения или официального разъяснения.

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

В PostgreSQL нет директивы `FORCE INDEX`, как это присутствует в некоторых других СУБД (например, MySQL). Вместо этого PostgreSQL использует подсказки и настройку конфигурации для управления выбором оптимального плана выполнения запросов.

### Что используется вместо `FORCE INDEX` в PostgreSQL?

В PostgreSQL для «принуждения» использования определённого индекса применяют такие подходы:

1. **Настройка cost parameters (стоимость операций)**:
   PostgreSQL оценивает стоимость выполнения различных путей выполнения запроса (например, индексный доступ или последовательное сканирование). Можно искусственно изменить эти оценки, заставив PostgreSQL предпочитать определенный индекс.

   Пример:
   ```sql
   SET enable_seqscan TO off; -- отключить последовательное сканирование
   ```

   Или наоборот:
   ```sql
   SET cpu_tuple_cost = 1000; -- завышенная стоимость последовательного сканирования
   ```

2. **Указание индексов через конструкцию `USING INDEX`**:
   Хотя это не прямая директива `FORCE INDEX`, в PostgreSQL можно явно указать индекс в запросе через конструкцию `JOIN USING INDEX` или указав в EXPLAIN плане индекс, который хочется использовать.

   Пример:
   ```sql
   EXPLAIN ANALYZE SELECT * FROM users WHERE id = 123 USING INDEX users_pkey;
   ```

3. **Ограничение доступа к данным**:
   Иногда запросы намеренно сужают область данных для того, чтобы подтолкнуть оптимизатор к использованию конкретного индекса. Например, фильтрация по диапазону данных может заставить оптимизатор использовать подходящий индекс.

   Пример:
   ```sql
   SELECT * FROM users WHERE created_at > CURRENT_DATE - INTERVAL '30 days'; -- предполагается наличие индекса по полю created_at
   ```

### Когда и зачем нужно использовать такую технику?

- **Оптимизация запросов**: если стандартный план выполнения запроса неэффективен, и вы хотите, чтобы PostgreSQL использовал другой индекс, можно попробовать подтолкнуть его к такому плану.
- **Проблемы с оптимизатором**: иногда оптимизатор запросов PostgreSQL может ошибочно выбрать менее эффективный план. Явное указание индекса помогает обойти эту проблему.
- **Экспериментальные замеры производительности**: при анализе производительности запроса можно попросить оптимизатор принудительно использовать определённый индекс, чтобы сравнить результаты.

### Недостатки и риски принуждения использования индексов:

- **Невыгода для других запросов**: произвольное навязывание индексов может ухудшить производительность других запросов, использующих тот же индекс.
- **Повышенные риски ошибок**: изменения параметров могут привести к негативным последствиям, если оптимизатор выбрал наилучшую стратегию по умолчанию.
- **Заблуждения оптимизатора**: даже если вы вынуждаете использовать конкретный индекс, оптимизатор может переоценить выгоду от этого шага, что приведет к ухудшению производительности.

### Итог

В PostgreSQL нет команды `FORCE INDEX`, но можно косвенно направить оптимизатор на использование определённого индекса, изменяя параметры стоимости или используя хитрости в формулировании запросов. Однако такие вмешательства следует производить осмотрительно и только после тщательных измерений и экспериментов, чтобы избежать негативных последствий.

Напротив, в ряде случаев она может незначительно повысить производительность, так как помогает избежать дорогостоящего автоматического приведения типов (type juggling), которое происходит в режиме `strict_types=0`.

### Почему строгий режим типов не замедляет выполнение?

1. **Удаление автоматической конвертации типов**: в режиме строгих типов PHP перестает тратить ресурсы на лишние преобразования, такие как приведение строк к числам или наоборот. Например, выражение `1 + "1"` в обычном режиме приведет к приведению строки к числу, а в строгом режиме сразу возникнет ошибка.

2. **Повышение точности и предсказуемости**: строгий режим заставляет разработчика внимательнее относиться к типам данных, что снижает риск ошибок и аварийных ситуаций. Это в конечном итоге положительно сказывается на производительности и безопасности кода.

3. **Современные оптимизаторы PHP**: Zend Engine и современные виртуальные машины PHP научились эффективно обрабатывать строгие типы, не вызывая значительных задержек. Сегодняшние версии PHP обладают оптимизированными механизмами обработки строгих типов, что компенсирует любые теоретические издержки.

### Практические измерения

Опыт показывает, что разница в производительности между строгим и нестрогим режимами настолько мала, что она едва заметна в реальных приложениях. Единственное существенное изменение — это улучшение стабильности и качества кода, вызванное отсутствием скрытого приведения типов.

### Экспериментальные результаты

Несколько исследований и бенчмаркинги показывают, что средний прирост производительности в строгом режиме составляет около **0–2%**, причём это связано с исключением дорогостоящих операций по приведению типов.

### Когда стоит задуматься о производительности?

Единственный случай, когда строгий режим может слегка отразиться на производительности — это очень нагруженные участки кода, работающие с большими объемами данных и интенсивно осуществляющих операции с типами. Но даже в таких редких случаях эффект будет пренебрежимо малым по сравнению с общим выигрышем от повышенной стабильности и уверенности в типах.

### Заключение

Директива `strict_types=1` не замедляет выполнение PHP-кода, а наоборот, может способствовать небольшому улучшению производительности за счет избавления от лишнего приведения типов. Рекомендуется использовать строгий режим повсеместно, так как выгода от него перевешивает гипотетические затраты на производительность.

### Почему Doctrine ORM не поддерживает составные первичные ключи?

Первоначально разработчики Doctrine приняли сознательное решение отказаться от полноценной поддержки составных первичных ключей (Composite Primary Keys) по следующим причинам:

1. **Трудности поддержки и развития**:
   - Поддержка составных ключей добавила бы значительную сложность в архитектуру ORM, увеличив объем необходимого кода и тестов.
   - Появилась бы необходимость переписывания многих компонентов (генераторы запросов, маппинги, кэширование и т.д.), что привело бы к риску возникновения ошибок и снижению производительности.

2. **Лучшее проектирование базы данных**:
   - Многие эксперты рекомендуют избегать составных первичных ключей в пользу суррогатных ключей (Surrogate keys), таких как автоинкрементные идентификаторы или GUID. Суррогатные ключи упрощают работу с базами данных и поддерживают лучшее масштабирование.
   - Surrogate key упрощает миграцию данных, изменения схемы и интеграцию с внешними системами.

3. **Best practices в мире ORM**:
   - Большинство ведущих ORM-фреймворков (таких как Laravel’s Eloquent, Django ORM, Ruby on Rails ActiveRecord) предпочитают суррогатные ключи, что свидетельствует о преобладании такой практики в индустрии.

4. **Performance considerations**:
   - Составные ключи могут ухудшать производительность в крупных проектах, особенно если речь идет о распределенных системах или больших объемах данных.

5. **Сложность поддержки и интеграции**:
   - В сложных сценариях (связи Many-To-Many, Foreign Key Relations) использование составных ключей могло бы создать массу проблем с зависимостями и целостностью данных.

### Как с этим живут в реальных проектах?

Многие проекты успешно обходятся без использования составных первичных ключей, применяя следующие подходы:

1. **Использование суррогатных ключей**:
   - Почти все современные проекты выбирают суррогатные ключи (автоинкрементные или UUID), что значительно упрощает работу с ORM и снимает необходимость заботиться о составных ключах.

2. **Unique Constraints**:
   - Если есть потребность в уникальном сочетании нескольких полей, можно использовать уникальные ограничения (unique constraint), сохраняя при этом суррогатный первичный ключ.

3. **Business Logic**:
   - Часто логика работы с составными ключами переносится на бизнес-уровень, а база данных просто поддерживает это на уровне уникальности данных.

4. **Custom solutions**:
   - В особых случаях, когда составные ключи жизненно необходимы, разработчики находят обходные пути, такие как использование композитных идентификаторов в собственном коде и дополнительная обработка в моделях.

### Пример решения проблемы в реальном проекте:

Допустим, у вас есть таблица продуктов, где продукт может существовать в разных категориях, и нужно обеспечить уникальность пары (продукт-категория). Вместо составного ключа можно использовать суррогатный идентификатор и уникальное ограничение:

```sql
CREATE TABLE product_categories (
    id SERIAL PRIMARY KEY,
    product_id INT NOT NULL,
    category_id INT NOT NULL,
    UNIQUE(product_id, category_id)
);
```

Отсутствие полноценной поддержки составных первичных ключей в Doctrine ORM обусловлено соображениями проектирования, производительности и удобства использования. Практически все современные проекты обходятся без них, применяя суррогатные ключи и уникальные ограничения, что доказало свою эффективность и популярность в сообществе разработчиков.

Данный фрагмент кода демонстрирует множество проблем, которые могут отрицательно сказаться на безопасности, читаемости, производительности и удобстве сопровождения приложения. Давайте разберем эти проблемы и предложим поэтапный рефакторинг.

### Проблемы в текущем коде:

1. **Безопасность (SQL-инъекции)**:
   Прямая интерполяция переменной в SQL-запрос делает код уязвимым к SQL-инъекциям. Это серьезная угроза безопасности.

2. **Неправильное использование PDO**:
   PDO-метод `query()` предназначен для выполнения простых запросов, а здесь он используется для получения одной записи. Правильнее было бы использовать подготовленные запросы (prepared statements).

3. **Жёсткая зависимость от глобальной переменной**:
   Использование глобальной переменной `DB::connect()` делает код хрупким и сложным для тестирования.

4. **Напрямую вызываемые служебные классы**:
   Mailer и Logger вызываются напрямую, что нарушает принцип инверсии зависимостей (Dependency Inversion Principle). Лучше использовать внедрение зависимостей (Dependency Injection).

5. **Скрытие логики в контроллере**:
   Логика обработки заказа размещена непосредственно в контроллере, что нарушает принцип единственной ответственности (Single Responsibility Principle).

6. **Прямой доступ к БД из контроллера**:
   Контроллер напрямую обращается к базе данных, что нарушает разделение ответственности и затрудняет тестирование.

7. **Отсутствие валидации данных**:
   Нет никакой проверки корректности полученных данных, что оставляет приложение уязвимым к атакам и непредвидённым случаям.

8. **Logging**:
   Создание нового экземпляра Logger внутри метода контроллера — плохой подход. Логгер лучше передавать через DI.

### Этап 1: Обеспечение безопасности (Refactoring for Security)

Первым делом уберём уязвимость SQL-инъекций, перейдя на подготовленные запросы (Prepared Statements).

```php

$stmt->bindParam(':id', $id, PDO::PARAM_INT);
$stmt->execute();
$order = $stmt->fetch();
```

Далее перенесём логику обработки заказа в специализированный сервис, чтобы контроллер оставался тонким и сосредоточился только на маршруте и ответах.

```php
class OrderService
{
    private PDO $pdo;
    private Mailer $mailer;
    private Logger $logger;

    public function __construct(PDO $pdo, Mailer $mailer, Logger $logger)
    {
        $this->pdo = $pdo;
        $this->mailer = $mailer;
        $this->logger = $logger;
    }

    public function markAsPaid(int $orderId): void
    {
        $stmt = $this->pdo->prepare("SELECT * FROM orders WHERE id = :id");
        $stmt->bindParam(':id', $orderId, PDO::PARAM_INT);
        $stmt->execute();
        $order = $stmt->fetch();

        if (!$order) {
            throw new NotFoundHttpException('Order not found');
        }

        $stmt = $this->pdo->prepare("UPDATE orders SET status = 'paid' WHERE id = :id");
        $stmt->bindParam(':id', $orderId, PDO::PARAM_INT);
        $stmt->execute();

        $this->mailer->send($order['email'], 'Ваш заказ оплачен');
        $this->logger->log('paid ' . $orderId);
    }
}
```

### Этап 3: Использование Dependency Injection (DI)

Внедрим зависимости (PDO, Mailer, Logger) через DI-контейнер, чтобы обеспечить лёгкость тестирования и расширения функционала.

```php
class OrderController
```

1. Удалили уязвимость SQL-инъекций.
2. Перенесли логику в сервис, убрали её из контроллера.
3. Использовали внедрение зависимостей (DI).

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

В представленном фрагменте имеется несколько серьезных проблем с точки зрения принципов Domain-Driven Design (DDD) и чистой архитектуры. Давайте разберем их подробнее:

### Проблемы с текущей реализацией:

1. **Смешение уровней ответственности**:
   - Доменная сущность (`User`) напрямую зависит от инфраструктуры (`EntityManagerInterface`). Это нарушает принципы чистой архитектуры и DDD, так как доменные сущности должны быть независимы от внешних зависимостей и технологий.

2. **Нарушение принципа единственной ответственности (SRP)**:
   - Метод `changeEmail()` выполняет сразу две задачи: изменение поля и сохранение в базе данных. Доменная сущность должна заниматься только своими внутренними делами, а изменения в БД должны происходить на уровне инфраструктуры.

3. **Неизменяемость (Immutability)**:
   - Идеологически доменные сущности в DDD должны быть либо изменяемыми (с контролем изменения через методы), либо неизменяемыми (где изменение состояния приводит к созданию нового объекта). Здесь допущен грубый подход, который разрушает концепцию.

4. **Отсутствие целостности данных**:
   - Нет гарантии, что новое значение поля `email` корректно (например, прошел ли валидатор). Сразу происходит запись в базу данных без предварительной проверки.

5. **Плохая тестируемость**:
   - Из-за непосредственной зависимости от Entity Manager тестирование сущности осложняется необходимостью моков и сложного окружения.

### Как исправить данную сущность?

#### 1. Выделим чистую доменную сущность:

```php
#[ORM\Entity]
class User
{
    private string $email;

    public function __construct(string $email)
    {
        $this->email = $email;
    }

    public function changeEmail(string $email): void
    {
        $this->email = $email;
    }

    public function getEmail(): string
    {
        return $this->email;
    }
}
```

#### 2. Переместим взаимодействие с базой данных на уровень инфраструктуры:

```php
class UserRepository
{
    private EntityManagerInterface $em;

    public function __construct(EntityManagerInterface $em)
    {
        $this->em = $em;
    }

    public function save(User $user): void
    {
        $this->em->persist($user);
        $this->em->flush();
    }

    public function findById(int $id): ?User
    {
        return $this->em->find(User::class, $id);
    }
}
```

#### 3. Валидируем данные до сохранения:

Если нужно подтвердить корректность email, добавляем проверку на уровне применения (application level):

```php
class ChangeEmailUseCase
{
    private UserRepository $userRepo;

    public function __construct(UserRepository $userRepo)
    {
        $this->userRepo = $userRepo;
    }

    public function execute(int $userId, string $newEmail): void
    {
        $user = $this->userRepo->findById($userId);
        if (!$user) {
            throw new UserNotFoundException();
        }

        if (!filter_var($newEmail, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidEmailFormatException();
        }

        $user->changeEmail($newEmail);
        $this->userRepo->save($user);
    }
}
```

### Итог:

После исправлений мы получаем чистые и независимые доменные сущности, которые отвечают за собственное состояние и бизнес-логику, а взаимодействие с инфраструктурой (базой данных) передано специальному уровню — репозиторию. Чистота архитектуры позволяет легко тестировать компоненты и вносить изменения без риска поломки остальных частей системы.

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

### Когда код «достаточно хорош»?

1. **Выполнение всех требований**:  
   Прежде всего, код должен соответствовать спецификации задачи. Если все оговоренные требования удовлетворены, это уже серьезный повод считать код готовым.

2. **Покрытие тестами**:  
   Обязательно убедись, что написанный код покрыт тестами. Это могут быть юнит-тесты, интеграционные тесты или даже smoke-тесты. Если покрытие достаточное и тесты проходят стабильно, это знак, что код стабилен.

3. **Качество кода**:  
   Следуй принципам Clean Code, SOLID, KISS и YAGNI. Удостоверься, что код легко читается, поддерживается и расширяется.

4. **Производительность**:
