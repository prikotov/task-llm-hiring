## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

Я считаю, что главная ценность новых версий PHP — это переход от «динамического языка, который можно написать как угодно» к «строго типизированному языку, который диктует архитектуру». Это снижает количество runtime-ошибок и делает код самодокументированным.

Вот наиболее важные нововведения, на мой взгляд:

### 1. Constructor Property Promotion (PHP 8.0)
Это критически важно для чистого кода и уменьшения «бойлерплейта» (шаблонного кода). В связке с Dependency Injection это делает объявление сервисов максимально лаконичным.

**До PHP 8.0:**
```php
class UserService {
    private UserRepository $repository;
    private LoggerInterface $logger;

    public function __construct(UserRepository $repository, LoggerInterface $logger) {
        $this->repository = $repository;
        $this->logger = $logger;
    }
}
```

**В PHP 8.0+:**
```php
class UserService {
    // Свойства объявляются, инициализируются и типизируются прямо в конструкторе
    public function __construct(
        private UserRepository $repository,
        private LoggerInterface $logger,
    ) {}
}
```

### 2. Readonly Properties (PHP 8.1)
Это фундамент для создания **Value Objects** и обеспечения **неизменяемости (immutability)**. В DDD это критически важно: если объект (например, `Money` или `Email`) создан, его состояние не должно меняться в ходе выполнения программы. Это гарантирует предсказуемость.

```php
readonly class Money {
    public function __construct(
        public int $amount,
        public string $currency,
    ) {}
}

$price = new Money(100, 'USD');
// $price->amount = 200; // Вызовет Fatal Error — это гарантирует надежность.
```

### 3. Enums (PHP 8.1)
До появления Enum мы использовали константы, что было небезопасно (в метод можно было передать любое число или строку). Перечисления позволяют использовать строгую типизацию для состояний бизнес-логики.

```php
enum OrderStatus: string {
    case Pending = 'pending';
    case Shipped = 'shipped';
    case Delivered = 'delivered';
}

// Теперь тип строго ограничен только вариантами Enum
public function updateStatus(OrderStatus $status): void {
    $this->status = $status;
}

// Использование:
$this->updateStatus(OrderStatus::Shipped); // OK
// $this->updateStatus('shipped'); // Ошибка типизации!
```

### 4. Union Types & Intersection Types (PHP 8.0 / 8.1)
Это позволяет описывать сложные контракты без использования сомнительных проверок `is_a()` или `instanceof` внутри методов.

```php
// Union Types: параметр может быть либо строкой, либо int
public function processId(string|int $id): void { /* ... */ }

// Intersection Types: объект ДОЛЖЕН реализовывать оба интерфейса одновременно
// Идеально для сложных паттернов или композиции
public function execute(Iteratorable&Countable $collection): void { /* ... */ }
```

### 5. Match Expression (PHP 8.0)
Это более безопасная и строгая альтернатива `switch`. В отличие от `switch`, `match` возвращает значение и использует строгое сравнение (`===`), что исключает классические ошибки с приведением типов.

```php
$status = OrderStatus::Shipped;

$message = match($status) {
    OrderStatus::Pending => 'Ваш заказ готовится',
    OrderStatus::Shipped => 'Заказ в пути',
    OrderStatus::Delivered => 'Заказ доставлен',
    // Если не покрыть все случаи, выбросит UnhandledMatchError, что лучше, чем молчаливый баг
};
```

**Итог:** Эти фичи позволяют нам писать код, который **невозможно сломать по неосторожности** (благодаря `readonly` и `enums`), и который **легко читать** (благодаря `promotion` и `match`), что в совокупности делает систему более надежной.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

Это отличный вопрос, который затрагивает саму суть того, как PHP управляет данными. По умолчанию PHP — язык с **слабой (weak) типизацией**, что дает гибкость, но порождает неопределенность.

### 1. Как ведут себя приведения типов (Coercive Mode)
По умолчанию PHP работает в «коэрцитивном» режиме. Это значит, что если тип не совпадает, PHP попытается магически преобразовать одно значение в другое, чтобы функция не упала.

```php
function add(int $a, int $b): int {
    return $a + $b;
}

echo add(5, "10"); // Выведет 15. PHP превратил строку "10" в int.
echo add(5, "abc"); // Выведет 5 (в PHP 8 это может вызвать ошибку или предупреждение, но концепция та же).
```

Это удобно для быстрого прототипирования, но в больших системах это ведет к «тихому» распространению некорректных данных.

### 2. Что дает `declare(strict_types=1);`
Когда мы добавляем эту директиву в начало файла, мы переключаем PHP в режим **строгой типизации** для этого конкретного файла. Теперь PHP не будет пытаться преобразовать типы — если тип не совпадает на 100%, будет выброшен `TypeError`.

**Важный нюанс:** `strict_types` работает только для вызовов функций, которые находятся **в этом же файле**. Если вы вызываете функцию из другого файла, где `strict_types` не объявлен, PHP будет использовать режим приведения типов.

```php
// file_a.php
declare(strict_types=1);

function setAge(int $age) { /* ... */ }

setAge("25"); // Fatal error: Uncaught TypeError
```

### 3. Типичные ловушки на практике

#### А) Ловушка "Nullability"
Самая частая причина ошибок `Uncaught TypeError: Argument 1 must be of type X, null given`. Если параметр может быть `null`, его нужно явно пометить знаком вопроса.

```php
// ОПАСНО
function printName(string $name) { /* ... */ }

// ПРАВИЛЬНО
function printName(?string $name) { /* ... */ }
```

#### Б) Ловушка "Магия объектов" (stdClass vs Entity)
При работе с JSON или API часто прилетают объекты типа `stdClass`. Если вы ожидаете конкретный класс, типизация спасет вас, но если вы привыкли к "гибким массивам", вы можете столкнуться с тем, что свойства объекта отсутствуют.

#### В) Ловушка "Float и точность"
Использование `float` для денег — это классическая ошибка. Из-за особенностей представления чисел в памяти, `0.1 + 0.2 !== 0.3`.

```php
function setPrice(float $price) { /* ... */ }
// Лучше передавать int (копейки/центы) или использовать BCMath/Money Object.
```

---

### 4. Примеры: Где типизация спасает, а где удивляет

#### Где спасает (Защита бизнес-логики)
Представим метод обработки платежа. Без типизации туда может прилететь строка `"0"` или пустой массив, что приведет к непредсказуемому поведению.

```php
declare(strict_types=1);

class PaymentService {
    public function process(int $amountInCents, string $currency): void {
        // Логика...
    }
}

$service = new PaymentService();

// ТИПИЗАЦИЯ СПАСАЕТ: 
// Если API прислало "100" (строку), выполнение прервется немедленно, 
// не успев списать неверную сумму или записать мусор в БД.
$service->process("100", "USD"); // Fatal error!
```

#### Где удивляет (Странное поведение)
Типизация может удивить при работе с массивами и типами объектов, если не учитывать, что массив — это не объект, а `iterable` — это интерфейс.

```php
declare(strict_types=1);

function countItems(iterable $items): void {
    echo count($items);
}

// УДИВЛЕНИЕ:
// Мы передаем массив — работает.
// Мы передаем объект Generator — работает.
// Мы передаем объект, который реализует Countable, но НЕ является iterable — ОШИБКА.
// Мы передаем массив, но внутри него объекты, которые мы не ожидали — типизация не проверяет содержимое массива!
```

**Главный вывод:** Типизация в PHP — это ваш первый и самый дешевый уровень тестирования. Она не заменяет Unit-тесты, но она гарантирует, что "мусор" не пройдет через границы ваших методов, позволяя вам фокусироваться на логике, а не на проверке `is_numeric()` или `is_string()`.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

Проектирование обработки исключений — это вопрос не только обработки ошибок, но и управления **потоком управления (control flow)**. Мой подход строится на том, что исключение должно нести информацию о том, *что* пошло не так, и *почему*, не раскрывая при этом лишних деталей реализации.

### 1. Иерархия исключений
Я никогда не использую стандартные `\Exception` или `\RuntimeException` напрямую в бизнес-логике. Вместо этого я создаю собственную иерархию, разделяя их по зонам ответственности.

Обычно я разделяю исключения на две большие ветви:
1.  **Domain Exceptions (DomainException):** Отражают нарушение бизнес-правил. Это "ожидаемые" ошибки. Например: `InsufficientFundsException`, `OrderAlreadyShippedException`. Они не являются признаком поломки системы, это результат выполнения бизнес-логики.
2.  **Infrastructure Exceptions (InfrastructureException):** Отражают технические сбои. Например: `DatabaseConnectionException`, `ExternalApiTimeoutException`. Это "неожиданные" ошибки.

**Пример структуры:**
```text
App\Exception\
├── Domain\
│   ├── DomainException (Base)
│   │   └── Order\
│   │       └── OrderNotFoundException
├── Infrastructure\
│   ├── InfrastructureException (Base)
│   │   └── Persistence\
│   │       └── RecordNotFoundException (хотя это может быть и Domain)
```

### 2. Контракт метода и исключения
**Контракт метода** — это обещание того, что метод вернет определенный тип данных, **ЛИБО** выбросит исключение, которое вызывающий код *обязан* знать.

*   Если метод выбрасывает `UserNotFoundException`, вызывающий код должен понимать, как на это реагировать (например, вернуть 404).
*   Если метод выбрасывает `PDOException`, это плохой контракт, так как вызывающий код (например, Controller) не должен знать о существовании базы данных.

**Правило:** Исключения, которые вы выбрасываете, должны быть частью сигнатуры вашего интерфейса (в документации или в понимании архитектуры).

### 3. Оборачивание (Exception Wrapping / Chaining)
Это важнейший прием при работе с внешними библиотеками или слоями инфраструктуры. Мы не должны пробрасывать "сырые" ошибки наружу.

**Плохо:** Пробрасывать `PDOException` из репозитория в сервис.
**Хорошо:** Перехватить `PDOException` и выбросить свое `RepositoryException`, передав оригинальное исключение в конструктор (Exception Chaining).

```php
try {
    $this->db->query("...");
} catch (\PDOException $e) {
    // Мы оборачиваем ошибку, сохраняя цепочку (cause), 
    // чтобы при логировании мы видели и наш контекст, и реальную причину.
    throw new PersistenceException("Failed to save user", 0, $e);
}
```
Это позволяет слою Application работать с абстракциями, а не с деталями реализации БД.

### 4. Антипаттерны

#### А) Исключения для управления логикой (Exceptions for Flow Control)
Это использование `try-catch` вместо обычных `if-else` для проверки условий.
*   *Пример:* Выбрасывать `UserNotFoundException` каждый раз, когда вы просто хотите проверить, существует ли пользователь. Это очень дорого по ресурсам.
*   *Решение:* Если ситуация нормальна (например, поиск пользователя по email при регистрации), метод должен возвращать `?User` (nullable).

#### Б) "Глотание" исключений (Silent Catch)
Пустой блок `catch`. Это самый опасный антипаттерн, который превращает отладку в ад.
```php
try {
    $this->doSomething();
} catch (\Exception $e) {
    // Ничего не делаем. Ошибка исчезла, система в невалидном состоянии.
}
```

#### В) Слишком широкие catch-блоки
Перехват `\Throwable` или `\Exception` там, где это не нужно. Это может скрыть критические ошибки (например, `TypeError` или `ParseError`), которые должны приводить к падению приложения для исправления бага.

#### Г) Нарушение абстракции (Leaking Abstractions)
Когда исключение из нижнего слоя (например, `GuzzleHttp\Exception\ConnectException`) "протекает" в самый верхний слой (Controller). Это делает систему жестко связанной (tightly coupled) с конкретной библиотекой.

### Итог моей стратегии:
1.  **Domain Layer:** Бросает только Domain Exceptions.
2.  **Infrastructure Layer:** Ловит сторонние ошибки и оборачивает их в свои (Infrastructure Exceptions).
3.  **Application Layer:** Обрабатывает бизнес-исключения (превращает их в понятные ответы) и позволяет техническим ошибкам уходить в глобальный Error Handler (для логирования и 500 ошибки).

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

По моему опыту, чаще всего в реальном коде нарушается принцип **Single Responsibility Principle (SRP)** — Принцип единственной ответственности.

### Почему это происходит?
Это происходит из-за стремления к "удобству" и скорости разработки. Разработчику кажется, что раз он всё равно пишет код в одном классе, то почему бы не добавить туда и отправку email, и логирование, и сохранение в базу? В итоге возникают так называемые **"Божественные объекты" (God Objects)** — классы, которые знают слишком много и умеют делать слишком много.

**Последствия:**
*   Класс становится невозможно тестировать (нужно мокать 10 зависимостей вместо одной).
*   Любое изменение в логике отправки почты может случайно сломать логику сохранения заказа.
*   Код превращается в "спагетти", где связи между компонентами запутаны.

---

### Типовой пример нарушения (Bad Practice)

Представим класс `OrderService`, который делает всё: считает цену, сохраняет в БД и отправляет уведомление.

```php
class OrderService {
    public function placeOrder(array $data): void {
        // 1. Логика расчета цены (Бизнес-логика)
        $total = $data['price'] * $data['quantity'];
        if ($total <= 0) {
            throw new \Exception("Invalid price");
        }

        // 2. Логика сохранения в БД (Инфраструктура)
        // Представим, что здесь прямой SQL или вызов DB-драйвера
        echo "Saving order to database with total: $total\n";

        // 3. Логика уведомления (Внешний сервис)
        // Здесь может быть прямой вызов SMTP или API
        echo "Sending email to {$data['email']}...\n";
    }
}
```
**Проблема:** `OrderService` теперь зависит от способа хранения данных и способа отправки почты. Если мы захотим сменить Email на SMS или использовать другую БД, нам придется переписывать этот класс.

---

### Рефакторинг (Good Practice)

Мы применяем SRP и внедряем зависимости (Dependency Injection). Теперь `OrderService` отвечает только за **координацию процесса** (оркестрацию).

```php
// 1. Выносим работу с данными в репозиторий
interface OrderRepositoryInterface {
    public function save(Order $order): void;
}

// 2. Выносим уведомления в отдельный сервис
interface NotificationServiceInterface {
    public function notify(string $recipient, string $message): void;
}

// 3. Создаем Value Object или Entity для заказа
class Order {
    public function __construct(
        public readonly float $total,
        public readonly string $customerEmail
    ) {}
}

// 4. Чистый сервис, который только управляет процессом
class OrderService {
    public function __construct(
        private OrderRepositoryInterface $repository,
        private NotificationServiceInterface $notifier
    ) {}

    public function placeOrder(float $price, int $quantity, string $email): void {
        // Расчет (в идеале логика расчета должна быть внутри сущности Order)
        $total = $price * $quantity;
        
        if ($total <= 0) {
            throw new \InvalidArgumentException("Invalid total amount");
        }

        $order = new Order($total, $email);

        // Координация действий через абстракции
        $this->repository->save($order);
        $this->notifier->notify($email, "Your order of $total is placed!");
    }
}
```

### Что изменилось?
1.  **Тестируемость:** Теперь я могу легко написать Unit-тест для `OrderService`, передав ему "заглушки" (Mocks) для репозитория и сервиса уведомлений. Мне не нужна реальная база или почтовый сервер.
2.  **Гибкость:** Если завтра мы перейдем на MongoDB или будем отправлять сообщения в Telegram, мы просто создадим новую реализацию `OrderRepositoryInterface` или `NotificationServiceInterface`. Сам `OrderService` **не изменится ни на одну строчку**.
3.  **Читаемость:** Код стал декларативным. Читая метод `placeOrder`, мы видим высокоуровневые шаги, а не детали реализации протоколов передачи данных.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Короткий ответ: **Да, можно.**

В профессиональной разработке существует концепция **"Engineering Trade-offs" (Инженерных компромиссов)**. SOLID — это не священное писание, а набор инструментов для борьбы со сложностью. Если цена следования принципу превышает пользу, которую он приносит, принципом стоит пренебречь.

Главный враг чистого кода — **Overengineering (избыточное проектирование)**.

Вот несколько ситуаций, когда нарушение SOLID оправдано:

### 1. MVP, прототипирование или Proof of Concept (PoC)
Если ваша задача — проверить гипотезу или создать работающий прототип за 2 дня, чтобы показать инвесторам, построение идеальной иерархии интерфейсов и внедрение Dependency Injection может стать "смертным приговором" проекту из-за нехватки времени.
*   **Риск:** Накопление технического долга.
*   **Оправдание:** Скорость выхода на рынок (Time-to-Market) важнее чистоты кода на этапе проверки идеи.

### 2. Масштаб и сложность задачи (YAGNI — You Ain't Gonna Need It)
Принцип **Interface Segregation (ISP)** или **Dependency Inversion (DIP)** часто заставляет нас создавать интерфейсы "на будущее". 
*   **Пример:** Вы создаете интерфейс `StorageInterface` с методами `save()`, `delete()`, `find()`, `update()`, хотя на 100% знаете, что в ближайшие два года у вас будет только один тип хранилища — локальная файловая система.
*   **Оправдание:** Если вероятность появления второго хранилища близка к нулю, создание лишней абстракции только усложняет навигацию по коду и увеличивает количество файлов без реальной пользы.

### 3. Сверхмалые утилиты или скрипты
Если вы пишете одноразовый скрипт для миграции данных или парсинга логов, который будет запущен один раз и удален, применение SOLID превращается в абсурд.
*   **Пример:** Написать полноценный сервис с репозиториями и интерфейсами для скрипта, который просто берет CSV и заливает его в базу.
*   **Оправдание:** Тратить время на архитектуру кода, который не будет поддерживаться, — это неэффективное использование ресурсов компании.

### 4. Производительность (Performance Critical)
В редких случаях (особенно в высоконагруженных вычислительных модулях) лишние уровни абстракции, вызовы методов через интерфейсы и динамическое связывание могут создавать накладные расходы на CPU.
*   **Пример:** Внутри горячего цикла (hot loop), который обрабатывает миллионы математических операций в секунду, может быть оправдано использование прямого обращения к свойствам или использование конкретных классов вместо интерфейсов.
*   **Оправдание:** В экстремальных условиях производительность системы важнее чистоты архитектуры.

### Золотое правило инженера:

**Нарушайте принципы осознанно.**

Разница между "плохим разработчиком" и "опытным инженером" заключается в следующем:
*   **Плохой разработчик** нарушает SOLID, потому что он не знает, как правильно, или ему лень. Он создает хаос.
*   **Опытный разработчик** нарушает SOLID, потому что он понимает, что в данных конкретных обстоятельствах (время, бюджет, сложность, производительность) следование принципу принесет больше вреда, чем пользы.

**Мой подход:** Я всегда стремлюсь к SOLID как к стандарту, но если я вижу, что архитектура становится "слишком умной" и запутанной для простой задачи, я останавливаюсь и выбираю более простое решение, документируя это решение как осознанный выбор.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Это отличный вопрос, который бьет прямо в цель: многие ошибочно полагают, что **Open/Closed Principle (OCP)** — это синоним наследования. На самом деле, наследование (Inheritance) — это самый жесткий и часто самый опасный способ реализации OCP из-за проблемы «хрупкого базового класса» (Fragile Base Class).

В современном PHP (и вообще в объектно-ориентированном дизайне) предпочтение отдается **композиции** над наследованием. Вот основные способы реализации OCP без использования наследования:

### 1. Композиция и паттерн «Стратегия» (Strategy)
Это самый распространенный способ. Вместо того чтобы менять поведение класса через расширение (наследование), мы передаем ему объект, который инкапсулирует это поведение.

**Как это работает:** Класс остается закрытым для изменений, но он "открыт" для новых алгоритмов через внедрение зависимостей.

```php
// Вместо создания subclass OrderWithDiscount, OrderWithTax...
interface DiscountStrategy {
    public function apply(float $amount): float;
}

class BlackFridayDiscount implements DiscountStrategy {
    public function apply(float $amount): float { return $amount * 0.5; }
}

class RegularDiscount implements DiscountStrategy {
    public function apply(float $amount): float { return $amount; }
}

class Order {
    public function __construct(
        private float $amount,
        private DiscountStrategy $discountStrategy // Композиция
    ) {}

    public function getTotal(): float {
        return $this->discountStrategy->apply($this->amount);
    }
}

// Мы добавляем новые типы скидок, НЕ меняя класс Order.
$order = new Order(100, new BlackFridayDiscount());
```

### 2. Паттерн «Декоратор» (Decorator)
Декоратор позволяет динамически добавлять объекту новую функциональность, не меняя его исходный код и не используя наследование для создания бесконечного количества комбинаций.

**Как это работает:** Вы оборачиваете исходный объект в "обертку", которая реализует тот же интерфейс, добавляет логику и вызывает оригинальный метод.

```php
interface Logger {
    public function log(string $message): void;
}

class FileLogger implements Logger {
    public function log(string $message): void { /* пишет в файл */ }
}

// Декоратор добавляет функциональность (например, отправку в Slack)
class SlackLoggerDecorator implements Logger {
    public function __construct(private Logger $wrappedLogger) {}

    public function log(string $message): void {
        $this->wrappedLogger->log($message); // Вызываем старое поведение
        // Добавляем новое поведение
        echo "Sending to Slack: $message\n"; 
    }
}

$logger = new SlackLoggerDecorator(new FileLogger());
$logger->log("System error");
```

### 3. Паттерн «Наблюдатель» (Observer / Event Dispatcher)
Этот способ реализует OCP на уровне взаимодействия между компонентами. Вместо того чтобы модифицировать основной класс для вызова новых действий, мы заставляем его "излучать" события.

**Как это работает:** Основной класс (Subject) просто сообщает: "Что-то произошло". Другие классы (Observers/Listeners) подписываются на это событие.

```php
// В Symfony это работает через EventDispatcher
class OrderService {
    public function __construct(private EventDispatcher $dispatcher) {}

    public function completeOrder(Order $order): void {
        // ... логика завершения заказа ...

        // Мы не вызываем здесь EmailService или InventoryService напрямую.
        // Мы просто кидаем событие.
        $this->dispatcher->dispatch(new OrderCompletedEvent($order));
    }
}

// Теперь, чтобы добавить отправку SMS после заказа, нам НЕ НУЖНО менять OrderService.
// Мы просто создаем новый Listener и подписываем его на событие.
```

### 4. Использование функций высшего порядка (Closures / Callables)
В PHP это очень мощный и лаконичный способ. Вместо создания целых классов-стратегий, вы можете передавать поведение прямо в виде анонимных функций.

```php
class DataProcessor {
    public function process(array $data, callable $transformation): array {
        return array_map($transformation, $data);
    }
}

$processor = new DataProcessor();
$data = [1, 2, 3];

// Мы реализуем новое поведение (умножение на 2) прямо "на лету", 
// не меняя класс DataProcessor.
$result = $processor->process($data, fn($n) => $n * 2);
```

### Резюме: что выбрать?

| Способ | Когда использовать |
| :--- | :--- |
| **Стратегия** | Когда нужно менять один из алгоритмов внутри объекта. |
| **Декоратор** | Когда нужно "наслаивать" новые обязанности на объект (например, логирование, кэширование). |
| **Observer** | Когда нужно оповестить другие, независимые части системы о событии. |
| **Closures** | Для простых, разовых трансформаций или когда создание целого класса избыточно. |

**Мой вердикт:** Наследование — это OCP "в лоб". Композиция (Стратегия, Декоратор, Observer) — это OCP "в ширину", который делает систему гибкой, слабосвязанной и по-настоящему расширяемой.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Короткий ответ: **Нет, не только.**

Хотя в классическом учебнике SOLID принцип SRP (Single Responsibility Principle) рассматривается применительно к классам, в современной архитектуре его следует применять к **любому элементу системы, который имеет значение для понимания или поддержки кода**.

Если мы будем применять SRP только к классам, мы рискуем создать "чистые" классы, которые являются частью "грязных" и перегруженных модулей или функций.

Вот где еще необходимо применять SRP:

### 1. Функции и методы (Functions/Methods)
Это самый очевидный уровень. Функция должна выполнять одну задачу.
*   **Нарушение:** Функция `registerUser()`, которая проверяет валидацию, хеширует пароль, сохраняет в БД и отправляет приветственное письмо.
*   **Следствие:** Такую функцию невозможно тестировать изолированно (нужно мокать всё сразу) и сложно переиспользовать.
*   **Решение:** Разбить на `validateUser()`, `saveUser()` и `sendWelcomeEmail()`.

### 2. Модули и пакеты (Modules/Packages)
На уровне архитектуры целого приложения или микросервиса.
*   **Нарушение:** "Монолитный" модуль `Billing`, который внутри себя содержит логику обработки платежей, управления подписками, генерации PDF-инвойсов и интеграции с налоговой службой.
*   **Следствие:** Изменение логики налогов может привести к ошибке в расчете платежей. Модуль становится слишком тяжелым для развертывания и масштабирования.
*   **Решение:** Разделение на подмодули или отдельные микросервисы: `PaymentService`, `SubscriptionService`, `InvoicingService`.

### 3. Микросервисы (Microservices)
В распределенных системах SRP переходит на уровень инфраструктуры.
*   **Нарушение:** Микросервис, который делает "всё понемногу" для одного бизнес-процесса (например, сервис заказов, который одновременно управляет складом, доставкой и возвратами).
*   **Следствие:** Сложность масштабирования (вам нужно масштабировать весь сервис, даже если нагрузка только на склад) и риск каскадных сбоев.
*   **Решение:** Разделение на специализированные сервисы согласно **Bounded Contexts** (из DDD).

### 4. Файлы и пространство имен (Files/Namespaces)
Даже организация файлов в проекте подчиняется SRP.
*   **Нарушение:** Один огромный файл `Utils.php`, в котором лежат и функции для работы со строками, и функции для работы с датами, и работа с файловой системой.
*   **Следствие:** Трудности в навигации, конфликты при слиянии веток (git merge conflicts) и плохая структура автозагрузки.
*   **Решение:** Создание специализированных пространств имен и файлов: `StringHelper`, `DateHelper`, `FileStorage`.

### Как понять, что вы нарушили SRP?

Самый простой способ — это использовать два критерия:

1.  **Критерий "Причины для изменения" (из определения Роберта Мартина):**
    Если у вас есть "повод" изменить этот элемент по двум разным причинам (например, изменился формат базы данных И изменился формат писем), значит, у элемента больше одной ответственности.

2.  **Критерий "Слова-связки" (The "And" Test):**
    Попробуйте описать, что делает ваш класс/функция/модуль. Если в описании вы используете союз **"и"** (например: *"Этот класс сохраняет заказы **и** отправляет уведомления"*), — поздравляю, вы нарушили SRP.

**Резюме:** SRP — это ментальная модель, которая учит нас **изолировать причины изменений**. Мы применяем её на всех уровнях абстракции: от одной строки кода до целой инфраструктуры облачных сервисов.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

Работа Dependency Injection Container (DIC) в Symfony — это сложный, но элегантно спроектированный процесс. Чтобы понять его, нужно разделить жизненный цикл приложения на три фазы: **Compile Time** (сборка), **Freeze** (заморозка) и **Runtime** (выполнение).

### 1. Compile Time: Сборка и компиляция контейнера

В Symfony контейнер не создается "на лету" из XML/YAML файлов при каждом запросе. Вместо этого происходит процесс **компиляции**.

**Что происходит:**
1.  **Загрузка конфигурации:** Компоненты (Bundle) загружают свои настройки из YAML, XML, PHP или атрибутов.
2.  **Построение Graph (Графа):** Symfony строит дерево всех сервисов и их зависимостей.
3.  **Compiler Passes (Компиляционные проходы):** Это "магия" Symfony. Контейнер проходит по своему графу несколько раз, выполняя специальные классы (`CompilerPassInterface`).
    *   *Пример:* Проход находит все сервисы, помеченные тегом `kernel.event_listener`, и регистрирует их в специальном реестре для `EventDispatcher`.
    *   *Оптимизация:* Здесь удаляются неиспользуемые сервисы, объединяются конфигурации и подменяются реализации (например, замена абстрактного интерфейса на конкретный класс).
4.  **Генерация PHP-класса:** После всех проходов Symfony берет итоговую структуру и **генерирует чистый PHP-код** (файл в `var/cache/.../ProjectServiceContainer.php`). 
    *   Этот файл содержит инструкции по созданию каждого сервиса. Теперь контейнер — это не набор конфигураций, а огромный, оптимизированный PHP-класс.

### 2. Как работает Autowiring

Autowiring — это механизм, который позволяет Symfony автоматически определять, какие зависимости нужны конструктору, не требуя явного указания каждого сервиса в конфиге.

**Механика:**
1.  **Reflection API:** Во время компиляции (на этапе построения графа) Symfony использует PHP Reflection, чтобы "заглянуть" в конструкторы ваших классов.
2.  **Type-hinting:** Контейнер видит типы аргументов. Если он видит `UserRepository $repository`, он ищет в своем графе сервис, который соответствует этому типу (или является его реализацией).
3.  **Резолвинг:** Если тип уникален (один сервис на один интерфейс), Symfony автоматически связывает их. Если типов несколько (например, два разных сервиса, реализующих `StorageInterface`), autowiring "сломается", и вам придется явно указать, какой именно нужен, через атрибуты или конфиг.

*Важно: Autowiring работает на этапе компиляции, а не в рантайме. Это значит, что если автовайринг не может разрешить зависимость, вы получите ошибку еще на этапе сборки контейнера.*

### 3. Runtime: Момент запроса сервиса (First Hit)

Когда ваше приложение уже запущено и вы вызываете `$container->get(MyService::class)` (или через DI в контроллер), происходит следующее:

1.  **Проверка в Map:** Контейнер проверяет, создан ли уже экземпляр этого сервиса.
2.  **Lazy Initialization (Ленивая инициализация):** По умолчанию сервисы в Symfony являются **shared** (синглтонами внутри одного запроса). Если сервис еще не создан, запускается процесс его создания.
3.  **Инстанцирование (Construction):**
    *   Контейнер смотрит в сгенерированный PHP-код (тот самый `ProjectServiceContainer.php`), который говорит: *"Чтобы создать MyService, сначала создай UserRepository, затем Logger, а потом передай их в конструктор MyService"*.
    *   Происходит рекурсивное создание всех зависимостей (если они еще не созданы).
4.  **Кэширование экземпляра:** Как только объект создан, он сохраняется во внутренний массив (реестр) контейнера.
5.  **Возврат объекта:** При повторном запросе того же сервиса в рамках того же запроса, Symfony просто вернет уже готовый объект из массива, не тратя ресурсы на создание.

### Итоговая схема:

*   **Конфиг (YAML/Attributes)** $\rightarrow$ **Compiler Passes** (оптимизация/теги) $\rightarrow$ **Generated PHP Class** (скомпилированный контейнер).
*   **Runtime:** `get(Service)` $\rightarrow$ **Check Cache** $\rightarrow$ **New Instance (via Generated Code)** $\rightarrow$ **Store in Cache** $\rightarrow$ **Return**.

**Почему это быстро?** ПотомуEP что вся тяжелая работа (анализ типов, поиск зависимостей, обход дерева) сделана **один раз** при компиляции. В рантайме выполнение сводится к простым вызовам `new Class(...)` в сгенерированном PHP-файле.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

Циклические зависимости (Circular Dependencies) — это ситуация, когда `ServiceA` требует `ServiceB`, а `ServiceB` требует `ServiceA`. В контейнере Symfony это приводит к бесконечной рекурсии при попытке создания объектов и выбрасывает ошибку.

Я рассматриваю решение этой проблемы на двух уровнях: **архитектурном** (как устранить причину) и **техническом** (как обойти проблему, если она временная).

---

### 1. Архитектурный подход (Правильный путь)

Если появилась циклическая зависимость, это почти всегда сигнал о том, что **нарушен принцип SRP** или **границы контекстов (Bounded Contexts)**.

#### А) Выделение третьего компонента (Refactoring to Third Service)
Чаще всего цикл возникает потому, что оба сервиса пытаются делать одно и то же действие, которое "разрывает" их.
*   **Проблема:** `OrderService` вызывает `PaymentService` (чтобы списать деньги), а `PaymentService` вызывает `OrderService` (чтобы обновить статус заказа).
*   **Решение:** Создать третий сервис `OrderCompletionService` (или использовать Event Dispatcher), который будет координировать их работу. Теперь оба сервиса зависят от нового компонента, но не друг от друга.

#### Б) Перенос ответственности (Refactoring to Domain Model)
Иногда зависимость возникает из-за того, что бизнес-логика, которая должна принадлежать **Сущности (Entity)**, вынесена в **Сервис**.
*   **Проблема:** Сервис считает цену, а потом вызывает сервис уведомлений, который снова лезет в этот же сервис за данными.
*   **Решение:** Перенести расчеты внутень в саму Entity. Сущности не должны зависеть от сервисов, что автоматически разрывает цикл.

#### В) Использование событий (Event-Driven Approach) — мой фаворит
Вместо прямой связи "вызов метода" я использую события. Это превращает жесткую связь в слабую.
*   **Вместо:** `PaymentService -> OrderService->updateStatus()`
*   **Делаем:** `PaymentService` кидает событие `PaymentCompletedEvent`. А `OrderService` слушает это событие. 
*   **Результат:** `PaymentService` больше ничего не знает об `OrderService`. Цикл разорван.

---

### 2. Технический подход (Когда нужно "заткнуть дыру")

Если рефакторинг архитектуры сейчас невозможен (например, это legacy-код или очень сложная интеграция), в Symfony есть инструменты для обхода проблемы.

#### А) Lazy Services (Ленивые сервисы)
Это самый элегантный технический способ. Symfony позволяет пометить сервис как `lazy`. В этом случае контейнер не создает реальный объект сразу, а подсовывает **Proxy-объект**.
*   **Как это работает:** Proxy-объект выглядит как ваш сервис, но он "пустой". Реальный объект будет создан только в тот момент, когда вы впервые вызовете у этого прокси какой-либо метод.
*   **Конфигурация:**
    ```yaml
    services:
        App\Service\ServiceA:
            lazy: true
    ```
*   **Результат:** Цикл разрывается, так как на этапе конструирования `ServiceB` мы получаем лишь "пустышку" `ServiceA`.

#### Б) Setter Injection (Внедрение через сеттеры)
Вместо того чтобы требовать зависимость в `__construct` (Constructor Injection), можно внедрить её через метод.
*   **Как это работает:** Мы создаем `ServiceA`, затем создаем `ServiceB`, и только потом вызываем `$serviceA->setServiceB($serviceB)`.
*   **Минус:** Это делает объект "недособранным" в момент создания и нарушает принцип неизменяемости (immutability). Я использую это только в крайних случаях.

### Мой алгоритм действий:
1.  **Вижу ошибку цикла.**
2.  **Рисую схему зависимостей на бумаге/в голове.**
3.  **Пытаюсь выделить общую логику в третий сервис или перенести её в Entity.** (Приоритет №1)
4.  **Если это возможно, внедряю события (Event Dispatcher).** (Приоритет №2)
5.  **Если это legacy и рефакторинг слишком рискован, использую `lazy: true`.** (Последний шанс)

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

Для решения этой задачи нужно разделить **синхронный процесс** (регистрация пользователя) и **асинхронные побочные эффекты** (отправка письма и обновление индекса). Главная цель — минимизировать время ответа (latency) и гарантировать, что побочные задачи будут выполнены, даже если произойдет сбой.

Вот три основных подхода, от простого к профессиональному.

---

### 1. Вариант "Событийная модель" (Event Dispatcher)
Это первый шаг к правильной архитектуре. Мы убираем логику писем и индексации из `RegistrationService`.

*   **Реализация:** В момент успешной регистрации сервис вызывает `EventDispatcher::dispatch(new UserRegisteredEvent($user))`. На это событие подписаны два слушателя: `SendWelcomeEmailListener` и `UpdateSearchIndexListener`.
*   **Плюсы:**
    *   Слабая связность (Low Coupling): `RegistrationService` ничего не знает о почте или поиске.
    *   Легко добавлять новые действия (например, выдать бонус).
*   **Минусы (Trade-offs):**
    *   **Это всё еще синхронно!** В стандартном Symfony-приложении слушатели выполняются в том же потоке. Пользователь будет ждать, пока отправится письмо и обновится индекс. Если почтовый сервер "зависнет", регистрация тоже "повиснет".

### 2. Вариант "Фоновые задачи" (Symfony Messenger + Message Queue) — **Рекомендуемый**
Это промышленный стандарт. Мы объединяем событийную модель с очередями (RabbitMQ, Redis, или даже база данных).

*   **Реализация:**
    1.  `RegistrationService` отправляет `UserRegisteredEvent`.
    2.  Слушатели (Handlers) вместо выполнения работы просто создают и отправляют в шину сообщений (Message Bus) два разных сообщения: `SendEmailMessage` и `UpdateIndexMessage`.
    3.  **Worker** (отдельный процесс в фоне) слушает очередь и выполняет эти задачи независимо.
*   **Плюсы:**
    *   **Мгновенный ответ:** Пользователь получает ответ "Успех" сразу после записи в БД.
    *   **Отказоустойчивость (Retry Policy):** Если индекс не обновился из-за сетевого сбоя, Messenger автоматически попробует выполнить задачу еще раз через 5 минут.
    *   **Масштабируемость:** Мы можем запустить 10 воркеров для писем и 2 для индексации.
*   **Минусы (Trade-offs):**
    *   **Инфраструктурная сложность:** Нужно разворачивать и поддерживать брокер сообщений (например, RabbitMQ).
    *   **Eventual Consistency:** Данные в поиске обновятся не мгновенно, а через доли секунды/секунду.

### 3. Вариант "Простой фоновый процесс" (FastCGI Finish Request)
Если нам нельзя ставить RabbitMQ, но нужно быстро "отвязаться" от клиента.

*   **Реализация:** Использование функции `fastcgi_finish_request()`. После завершения основного цикла обработки запроса, PHP отправляет ответ клиенту, но продолжает выполнять код в фоне.
*   **Плюсы:**
    *   Не нужна внешняя инфраструктура (очереди).
    *   Клиент получает ответ мгновенно.
*   **Минусы (Trade-offs):**
    *   **Ненадежность:** Если процесс упадет или сервер перезагрузится, задача (письмо) будет потеряна навсегда. Нет механизма повторов (retries).
    *   **Потребление ресурсов:** PHP-FPM процесс остается занятым и не может обрабатывать новый запрос, пока не закончит работу в фоне.

---

### Итоговое сравнение

| Критерий | Event Dispatcher (Sync) | **Messenger (Async)** | FastCGI Finish |
| :--- | :--- | :--- | :--- |
| **Скорость ответа** | Низкая (ждет всё) | **Высокая (мгновенно)** | Высокая |
| **Надежность** | Средняя | **Высокая (есть Retry)** | Низкая (риск потери) |
| **Сложность** | Низкая | **Высокая** | Средняя |
| **Когда выбирать** | Простые CRUD-задачи | **Критические бизнес-процессы** | Маленькие проекты без очереди |

**Мой выбор для продакшена:** 
Я бы использовал **Symfony Messenger** с транспортом **RabbitMQ** (или Redis для меньшей нагрузки). Это обеспечивает идеальный баланс между скоростью ответа пользователя и гарантией того, что письмо будет отправлено, а индекс — обновлен, даже если во время этого "мигнул" интернет.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

В Symfony контроль доступа разделяется на два фундаментальных этапа: **«Кто ты?»** (Authentication) и **«Что тебе можно?»** (Authorization).

### 1. Аутентификация (Authentication) — "Кто ты?"
Это процесс идентификации пользователя. В Symfony за это отвечает компонент `Security`.
*   **Authenticators:** Это классы, которые перехватывают запрос (например, проверяют логин/пароль в форме, JWT-токен в заголовке или сессию в Cookie).
*   **User Interface:** Объект, реализующий `UserInterface`, который представляет пользователя в системе.
*   **Результат:** Если аутентификация прошла успешно, объект пользователя помещается в `TokenStorage`.

### 2. Авторизация (Authorization) — "Что тебе можно?"
Когда мы знаем, кто пользователь, нам нужно понять, имеет ли он право выполнить действие. В Symfony это реализуется через три уровня:

#### А) Роли (Roles) — "Статусный" доступ
Это самый простой уровень. Роли — это просто строки (например, `ROLE_USER`, `ROLE_ADMIN`).
*   **Как работает:** Вы можете ограничить доступ в конфигурации (`access_control`) или через атрибут `#[IsGranted('ROLE_ADMIN')]`.
*   **Ограничение:** Роли статичны. Они описывают *кто* пользователь по его социальному статусу в системе, но не говорят о его отношениях с конкретным объектом.

#### Б) Voter (Голосующий) — "Контекстный" доступ
Это мощнейший механизм, позволяющий реализовать сложную бизнес-логику доступа. Voter — это класс, который проверяет конкретное правило.
*   **Как работает:** Когда вы вызываете `isGranted('EDIT', $article)`, Symfony опрашивает все зарегистрированные Voter-ы. Каждый Voter говорит: «Я могу решить этот вопрос» (`SUPPORTS`) и затем выдает вердикт: `ACCESS_GRANTED`, `ACCESS_DENIED` или `ACCESS_ABSTAIN` (пропустить).

---

### Когда выбирать Roles, а когда Voters?

Это ключевой архитектурный вопрос.

#### Выбирай РОЛИ, когда:
Доступ зависит только от **статуса пользователя** и не зависит от того, **над каким именно объектом** совершается действие.
*   *Пример:* Доступ к странице `/admin` разрешен только пользователям с `ROLE_ADMIN`.
*   *Пример:* Доступ к разделу «Управление пользователями» разрешен только `ROLE_MANAGER`.
*   **Критерий:** "Если я нажму на эту кнопку, мне важно только, что я — админ".

#### Выбирай VOTER, когда:
Доступ зависит от **содержимого объекта** или **отношений между пользователем и объектом**. Это называется "Ownership" или "Business Logic Access".
*   *Пример:* Пользователь может редактировать статью (`EDIT`), только если он является её **автором**. (Роли тут не помогут, так как авторы — это разные пользователи с одной ролью `ROLE_USER`).
*   *Пример:* Доступ к документу разрешен, если документ имеет статус `PUBLISHED` ИЛИ если пользователь является владельцем черновика.
*   *Пример:* Доступ к заказу разрешен, если сумма заказа меньше 1000$ (для `ROLE_USER`) или если пользователь — `ROLE_MANAGER`.
*   **Критерий:** "Мне нужно проверить не только кто я, но и *какой* это объект и в каком он состоянии".

---

### Пример архитектурного решения

Представим систему управления задачами (Task Management).

1.  **Роли:**
    *   `ROLE_USER` — может видеть список задач.
    *   `ROLE_ADMIN` — может удалять любые задачи.
    *   *Реализуем через `access_control` в `security.yaml`.*

2.  **Voter (`TaskVoter`):**
    *   **Правило 1:** Пользователь может редактировать задачу, если он её **создатель** (`$task->getOwner() === $user`).
    *   **Правило 2:** Пользователь может просматривать задачу, если она имеет статус `COMPLETED` (для всех) или если он её создатель.
    *   *Реализуем через класс `TaskVoter`.*

**Резюме:** Роли — это **широкая сетка** (уровень доступа к разделам), а Voter — это **хирургический скальпель** (уровень доступа к конкретным данным). В хорошем приложении они всегда работают вместе.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

Хранение Value Objects (VO) в Doctrine — это классическая задача при переходе от анемичной модели данных к богатой доменной модели (Rich Domain Model). Главная проблема в том, что реляционные БД не знают о понятии "Value Object", они знают только о примитивах (string, int, decimal).

Чтобы VO оставался неизменяемым и всегда валидным, мы должны скрыть детали хранения от доменного слоя. Вот три основных способа:

### 1. Embeddables (Встраиваемые объекты) — "Стандартный путь"
Это встроенный в Doctrine механизм, который позволяет "разложить" свойства VO по столбцам той же таблицы, где находится Entity.

*   **Как это работает:** Вы помечаете класс VO атрибутом `#[Embeddable]`, а в Entity используете `#[Embedded]`.
*   **Пример:**
    ```php
    #[Embeddable]
    class Money {
        public function __construct(
            #[Column(type: 'int')] private int $amount,
            #[Column(type: 'string', length: 3)] private string $currency
        ) {
            if ($amount < 0) throw new \InvalidArgumentException(); // Валидация в конструкторе
        }
    }

    #[Entity]
    class Order {
        #[Embedded(class: Money::class)]
        private Money $total;
    }
    ```
*   **Плюсы:**
    *   **Прозрачность БД:** В таблице `orders` будут колонки `total_amount` и `total_currency`. Никаких лишних JOIN-ов.
    *   **Нативность:** Это "родной" способ Doctrine.
*   **Минусы:**
    *   **Ограниченность:** Embeddable не может быть самостоятельной сущностью с собственным ID.
    *   **Сложность с коллекциями:** Вы не можете легко сделать `Embeddable` списком (коллекцией) внутри сущности без дополнительных костылей.
*   **Подводный камень:** Если вы измените структуру VO (добавите поле), вам придется делать миграцию таблицы основной сущности.

### 2. Custom Doctrine Types — "Абстрактный путь"
Вы создаете свой собственный тип данных для Doctrine, который умеет конвертировать VO в строку/число и обратно.

*   **Как это работает:** Вы реализуете `Doctrine\DBAL\Types\Type` и методы `convertToDatabaseValue` (VO $\rightarrow$ примитив) и `convertToPHPValue` (примитив $\rightarrow$ VO). Часто используется для хранения VO в формате JSON.
*   **Пример:** Хранение адреса как JSON-строки в одной колонке.
*   **Плюсы:**
    *   **Чистота схемы:** Одна колонка — один объект.
    *   **Универсальность:** Можно использовать один тип для разных VO.
*   **Минусы:**
    *   **Проблемы с поиском/фильтрацией:** Если вы храните VO в JSON, искать по конкретному полю внутри него в SQL становится сложно и медленно (нужны специфичные JSON-функции БД).
    *   **Отсутствие типизации в БД:** БД видит просто `TEXT` или `JSON`, она не знает о правилах валидации вашего VO.
*   **Подводный камень:** Вы теряете возможность использовать индексы по полям внутри VO (если это не специализированный JSON-индекс в PostgreSQL).

### 3. Entity Association (Связь One-to-One) — "Путь сущности"
Вы превращаете VO в полноценную Entity с собственным ID.

*   **Как это работает:** Вместо VO вы создаете класс с `#[Id]`.
*   **Плюсы:**
    *   Максимальная гибкость и возможность расширения.
*   **Минусы:**
    *   **Это больше не Value Object!** Как только у объекта появляется Identity (ID), он становится Entity. Это нарушает саму суть DDD.
    *   **Производительность:** Лишние JOIN-ы при каждом запросе.
*   **Подводный камень:** Это архитектурная ошибка, если вы пытаетесь имитировать VO через Entity.

---

### Итоговая рекомендация и "Золотые правила"

**Что выбирать?**
1.  Если VO — это набор простых полей (как `Money` или `Address`), используйте **Embeddables**. Это дает лучший баланс между производительностью и чистотой схемы.
2.  Если VO — это сложная структура, которую не нужно искать по отдельным полям, используйте **Custom Type (JSON)**.

**Как гарантировать неизменяемость и валидность?**

Чтобы ваш VO не превратился в "дырявое ведро", соблюдайте три правила:

1.  **Валидация в конструкторе:** Объект не должен иметь возможности существовать в невалидном состоянии. Все проверки (не отрицательная ли цена, валидный ли Email) должны быть в `__construct`.
2.  **Immutability (Неизменяемость):** Используйте `readonly` свойства (PHP 8.1+) или делайте свойства `private` без сеттеров. Любое изменение должно возвращать **новый экземпляр** объекта.
    ```php
    public function addAmount(int $extra): self {
        return new self($this->amount + $extra, $this->currency);
    }
    ```
3.  **Защита от "протекания" (Leakage):** Никогда не позволяйте Doctrine или сторонним библиотекам менять состояние вашего VO через рефлексию или обход конструктора. Если вы используете `Embeddables`, Doctrine сама создает объекты через рефлексию — это допустимый компромисс, так как это происходит внутри инфраструктурного слоя.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

Это фундаментальный вопрос проектирования систем на DDD. Главная цель здесь — **защитить инварианты агрегата**. Агрегат — это граница целостности. Никакое изменение внутри агрегата не должно происходить в обход его **Корня (Aggregate Root)**.

Разберем на примере агрегата **`Order` (Заказ)**, который содержит коллекцию **`OrderItem` (Позиции заказа)**.

### 1. Маппинг коллекций (Encapsulation)

Самая частая ошибка — сделать коллекцию внутри агрегата публичной или возвращать её напрямую. Это позволяет любому сервису сделать `$order->getItems()->add($item)`, минуя логику самого `Order`.

**Правильный подход:** Коллекция должна быть скрыта, а доступ к ней — строго контролируемым.

```php
#[Entity]
class Order {
    #[Id, Column, GeneratedValue]
    private int $id;

    // Используем Collection для связи
    #[OneToMany(mappedBy: 'order', targetEntity: OrderItem::class, cascade: ['all'], orphanRemoval: true)]
    private Collection $items;

    public function __construct() {
        $this->items = new ArrayCollection();
    }

    // МЫ НЕ возвращаем коллекцию для изменения. 
    // Мы возвращаем только Read-only представление (итератор или массив).
    /** @return Collection<int, OrderItem> */
    public function getItems(): Collection {
        return $this->items;
    }

    // Изменение состояния происходит ТОЛЬКО через метод Корня
    public function addProduct(Product $product, int $quantity): void {
        if ($quantity <= 0) throw new \InvalidArgumentException("Quantity must be > 0");
        
        // Здесь проверяем инварианты (например, лимит товаров в заказе)
        if ($this->items->count() >= 10) throw new \DomainException("Max 10 items allowed");

        $item = new OrderItem($this, $product, $quantity);
        $this->items->add($item);
    }
}
```

**Важные детали маппинга:**
*   `cascade: ['all']`: Позволяет сохранять/удалять позиции заказа автоматически при работе с `Order`.
*   `orphanRemoval: true`: Если мы удалим позицию из коллекции `$items`, Doctrine автоматически удалит соответствующую строку из таблицы `order_items`. Это критично для поддержания целостности.

---

### 2. Границы транзакции (Transaction Boundaries)

В DDD действует правило: **Один запрос (Usecase) = Один Агрегат = Одна Транзакция.**

Вы не должны менять два разных агрегата в одной транзакции, если это возможно. Если изменение одного агрегата требует изменения другого, используйте **Domain Events** (события), чтобы запустить процесс во втором агрегате асинхронно.

**Пример транзакции:**
Когда клиент нажимает "Оплатить", мы открываем транзакцию, которая затрагивает *только* агрегат `Order`. Мы меняем его статус и добавляем запись о транзакции оплаты внутри него.

---

### 3. Кто и когда вызывает `flush()`?

Это вопрос разделения ответственности между **Domain Layer** (бизнес-логика) и **Application Layer** (оркестрация).

*   **Domain Layer (Entity/Aggregate):** **Никогда** не вызывает `flush()`. Он не знает о существовании базы данных. Он только меняет свое состояние и проверяет правила.
*   **Application Layer (Service/Command Handler):** Именно здесь живет `EntityManager`. Сервис получает команду, загружает агрегат из репозитория, вызывает метод агрегата и в конце вызывает `flush()`.

**Правильная схема работы (Usecase):**

```php
class PlaceOrderHandler {
    public function __construct(
        private OrderRepository $repository,
        private EntityManagerInterface $entityManager
    ) {}

    public function __invoke(PlaceOrderCommand $command): void {
        // 1. Начинаем транзакцию (в Symfony это часто делает middleware или явно)
        $this->entityManager->wrapInTransaction(function() use ($command) {
            
            // 2. Загружаем корень агрегата
            $order = $this->repository->find($command->orderId);

            // 3. Выполняем бизнес-действие (внутри агрегата проверяются инварианты)
            $order->addProduct($command->product, $command->quantity);

            // 4. Сохраняем изменения. 
            // Мы вызываем flush() только ОДИН РАЗ в конце всей операции.
            // Doctrine сама поймет, что нужно сохранить и Order, и новый OrderItem.
            $this->entityManager->flush();
        });
    }
}
```

### Итоговое резюме:

1.  **Маппинг:** Используйте `cascade: ['all']` и `orphanRemoval: true`. Скрывайте коллекцию за методами, которые гарантируют валидность (не давайте прямой доступ к `Collection`).
2.  **Транзакции:** Одна транзакция на один агрегат. Если нужно затронуть другой — используйте события (Event Dispatcher).
3.  **Flush:** Вызывается строго в **Application Layer** (Service/Handler) после того, как все изменения в доменной модели завершены. Никогда не вызывайте `flush` внутри сущности или репозитория.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

Проблема N+1 — это классическая ловушка ORM, когда для получения списка из $N$ объектов вы делаете 1 запрос для получения самих объектов, а затем еще $N$ запросов для получения связанных с ними данных (Lazy Loading).

### 1. Диагностика

Прежде чем оптимизировать, нужно подтвердить проблему.

*   **Symfony Profiler (Toolbar):** Самый быстрый способ. Я открываю вкладку **Doctrine**, смотрю на количество запросов. Если я вижу десятки почти одинаковых запросов к одной и той же таблице (например, `SELECT ... FROM user WHERE id = ?`), — это 100% N+1.
*   **SQL Log / Debug Bar:** Просмотр сырых SQL-запросов, которые уходят в БД.
*   **Профилировщики БД:** Использование `EXPLAIN` в PostgreSQL, чтобы понять, как выполняются запросы, или использование инструментов вроде `pgBadger`.

---

### 2. Способы решения и их Trade-offs

#### А) Eager Loading через `JOIN FETCH` (в Query Builder)
Это самый эффективный способ. Вместо того чтобы позволять Doctrine подгружать связи позже, мы явно говорим ей: "Загрузи это сразу одним запросом через JOIN".

```php
// В репозитории
return $this->createQueryBuilder('o')
    ->leftJoin('o.items', 'i') // Присоединяем коллекцию
    ->addSelect('i')           // Говорим Doctrine заполнить объекты из этого JOIN
    ->getQuery()
    ->getResult();
```

*   **Плюсы:** Решает проблему максимально эффективно. Вместо $N+1$ запроса мы получаем ровно **1 запрос**.
*   **Минусы:** 
    *   **Cartesian Product (Декартово произведение):** Если у вас много связей `OneToMany`, количество строк в результате запроса растет экспоненциально ($Rows = Orders \times Items \times Comments$). Это может перегрузить память PHP.
    *   **Дублирование данных:** В результате SQL-запроса данные родительского объекта будут дублироваться в каждой строке.
*   **Когда использовать:** Когда нужно загрузить связанные данные для списка объектов.

#### Б) Использование `Partial Objects` или `DTO` (Data Transfer Objects)
Вместо того чтобы тянуть тяжелые сущности со всеми их связями, мы выбираем только те поля, которые реально нужны для отображения страницы.

```php
// Выбираем только нужные поля прямо в конструктор DTO
return $this->createQueryBuilder('o')
    ->select(sprintf('new %s(o.id, o.createdAt, i.productName)', OrderDto::class))
    ->leftJoin('o.items', 'i')
    ->getQuery()
    ->getResult();
```

*   **Плюсы:** 
    *   **Минимальный расход памяти:** Мы не создаем тяжелые объекты `Entity` и не забиваем Identity Map.
    *   **Максимальная скорость:** БД отдает только нужные колонки.
*   **Минусы:** 
    *   **Потеря функциональности:** DTO — это простые объекты данных. Вы не можете вызвать на них метод `order->calculateTotal()`, который использует логику сущности.
    *   **Привязка к представлению:** Если на странице понадобится еще одно поле, придется менять и запрос, и DTO.
*   **Когда использовать:** Для тяжелых списков (Read-only страницы), где важна чистая скорость чтения.

#### В) Использование `Extra Lazy` коллекций
Если вам не нужно выводить все элементы коллекции, а нужно только их количество или проверка `contains`, можно настроить коллекцию как `EXTRA_LAZY`.

```php
#[OneToMany(..., fetch: 'EXTRA_LAZY')]
private Collection $items;
```

*   **Плюсы:** Методы `$items->count()` или `$items->contains($item)` не будут загружать всю коллекцию в память. Doctrine выполнит легкий `SELECT COUNT(*)...`.
*   **Минусы:** Это не решает проблему N+1, если вы всё же решите итерироваться по коллекции.
*   **Когда использовать:** Когда коллекция очень большая (тысячи элементов) и вам нужно только знать её размер.

#### Г) Кэширование (Second Level Cache)
Использование кэша (Redis/Memcached) на уровне Doctrine.

*   **Плюсы:** Позволяет избежать запросов к БД вообще для часто запрашиваемых объектов.
*   **Минусы:** Сложность инвалидации кэша. Если данные изменились, а кэш остался — пользователь видит мусор.
*   **Когда использовать:** Для редко меняющихся справочных данных.

---

### Итоговая стратегия:

1.  **Нашел N+1 через Profiler.**
2.  **Если это список объектов и нужны их связи** $\rightarrow$ использую `leftJoin` + `addSelect` (Eager Loading). Если строк становится слишком много из-за декартова произведения $\rightarrow$ разбиваю на два запроса (сначала ID, потом `WHERE IN (...)`).
3.  **Если это тяжелый Read-only список** $\rightarrow$ перехожу на **DTO**. Это самый "чистый" и быстрый способ для отображения данных.
4.  **Если нужно просто количество элементов** $\rightarrow$ включаю `EXTRA_LAZY`.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

Это отличный вопрос, который затрагивает разницу между **бизнес-логикой** (которая динамична и сложна) и **целостностью данных** (которая должна быть абсолютной).

Короткий ответ: **Бизнес-валидация в коде — это "защита от дурака" и интерфейс для пользователя. Ограничения в БД — это "последний рубеж" и гарантия того, что данные не превратятся в мусор, даже если в коде случится баг, ошибка в миграции или кто-то залезет в базу напрямую через консоль.**

### Почему кода недостаточно?

1.  **Race Conditions (Состояние гонки):** 
    Представьте, что два параллельных запроса одновременно проверяют, достаточно ли денег на счету (`if ($balance >= $amount)`). Оба проходят проверку, оба списывают деньги, и баланс уходит в минус. Только `CHECK constraint` или транзакция с правильным уровнем изоляции в БД спасут ситуацию.
2.  **Множественные точки входа:** 
    Ваше приложение — не единственный способ взаимодействия с данными. Есть миграции, консольные команды, инструменты администрирования (DBeaver, pgAdmin), аналитические скрипты. Если логика валидации только в PHP, любой другой инструмент может нарушить правила.
3.  **Целостность связей:** 
    Если вы удаляете пользователя в коде, но забыли удалить его заказы, в БД останутся "сироты". `FOREIGN KEY` в БД гарантирует, что это физически невозможно.

---

### Какие средства я использую и когда?

Я разделяю ограничения на несколько уровней:

#### 1. Constraints (Ограничения целостности) — **Обязательно всегда**
Это фундамент. Я использую их для всего, что касается структуры и базовых правил.

*   **`NOT NULL`**: Для всех полей, которые обязательны.
*   **`UNIQUE`**: Для email, логинов, артикулов. Это защищает от дублей при конкурентных запросах (race conditions), чего не может сделать обычный `if` в PHP.
*   **`FOREIGN KEY (ON DELETE CASCADE/SET NULL)`**: Для поддержания связей между сущностями.
*   **`CHECK constraints`**: Для простых диапазонов значений.
    *   *Пример:* `CHECK (price > 0)` или `CHECK (status IN ('pending', 'paid', 'shipped'))`. Это защищает от логических ошибок (например, если в коде случайно передали отрицательную цену).

#### 2. Типы данных (Data Types)
Использование правильных типов в PostgreSQL — это тоже валидация.
*   Использование `UUID` вместо `INT` для безопасности (нельзя перебором найти ID).
*   Использование `JSONB` для структурированных, но гибких данных (с валидацией схем через `CHECK`).
*   Использование `NUMERIC` вместо `FLOAT` для денег (чтобы избежать проблем с точностью).

#### 3. Транзакции и уровни изоляции
Для сложных бизнес-процессов, затрагивающих несколько строк или таблиц.
*   Использую `transactional` блоки, чтобы гарантировать атомарность: либо всё сохранилось, либо ничего.

---

### Когда я НЕ использую ограничения в БД

Нельзя превращать базу данных в "умный сервер с логикой". 

*   **Сложная бизнес-логика:** Если правило звучит как *"Пользователь может получить скидку, если он купил более 5 товаров за последние 3 месяца"*, это **не должно** быть в БД. Это слишком тяжело для SQL, это сложно тестировать и изменять. Это место для **Domain Layer**.
*   **Интерфейсные проверки:** Проверка "пароль должен содержать спецсимвол" или "email должен иметь формат @" — это задача для валидатора в коде (Symfony Validator), чтобы быстро вернуть ошибку пользователю, не нагружая БД.

### Итоговая стратегия (The Golden Rule)

Я придерживаюсь правила: **"Валидируй в коде для пользователя, но защищай в БД для данных"**.

1.  **PHP (Validator/Domain):** Дает красивые, понятные ошибки пользователю и реализует сложную логику.
2.  **PostgreSQL (Constraints):** Гарантирует, что даже при полном крахе логики приложения, данные останутся консистентными, связанными и физически корректными.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

Когда запрос тормозит, моя задача — пройти путь от "что именно тормозит" до "как это исправить на уровне физики данных". Я не гадаю, а опираюсь на план выполнения (Execution Plan).

### 1. Диагностика (Поиск причины)

Первым дементом я использую команду **`EXPLAIN (ANALYZE, BUFFERS)`**. 
*   `EXPLAIN` показывает, какой план выполнения составил планировщик.
*   `ANALYZE` реально выполняет запрос и показывает реальное время и количество строк.
*   `BUFFERS` показывает, сколько данных было прочитано из памяти (Shared Buffers), а сколько — с диска. Это критически важно для понимания, упираемся ли мы в I/O.

**На что я смотрю в плане:**
1.  **Seq Scan (Sequential Scan):** Если я вижу полный перебор таблицы там, где ожидаю поиск по ID или индексу — это первая точка боли.
2.  **Cost & Actual Time:** Сравнение ожидаемой стоимости (`cost`) и реального времени (`actual time`). Если разрыв огромный, значит, статистика БД устарела.
3.  **Rows vs Loops:** Если планировщик ожидал 1 строку, а пришло 1 000 000, значит, статистика неверна.
4.  **Hash Join / Nested Loop:** Если при соединении таблиц я вижу `Nested Loop` на огромных объемах данных — это признак отсутствия подходящего индекса.
5.  **Disk Read vs Memory Hit:** Если в `BUFFERS` я вижу много `Read`, значит, индекс или данные не помещаются в RAM, и мы уперлись в медленный диск.

---

### 2. Типовые причины и способы решения

#### А) Отсутствие или неэффективный индекс
Самая частая причина.
*   **Решение:** Добавление B-Tree индекса на колонки, участвующие в `WHERE`, `JOIN` и `ORDER BY`.
*   **Сложный случай:** Если условие в `WHERE` содержит функцию, например `WHERE LOWER(email) = '...'`, обычный индекс не сработает.
*   **Решение:** Создание **функционального индекса** `CREATE INDEX ... ON users (LOWER(email))`.

#### Б) Проблема с селективностью (Index Scan vs Seq Scan)
Иногда PostgreSQL решает, что проще просканировать всю таблицу, чем использовать индекс. Это происходит, если индекс "не помогает" (например, если вы ищете значение, которое встречается в 50% строк таблицы).
*   **Решение:** Использование **Partial Indexes** (частичных индексов). Если мы часто ищем только "активные" заказы, создаем индекс `WHERE status = 'active'`. Это сделает индекс маленьким и быстрым.

#### В) Устаревшая статистика
Планировщик строит план на основе статистики. Если данные сильно изменились, он может выбрать неверный путь.
*   **Решение:** Запуск `ANALYZE table_name`.

#### Г) Проблема с "раздуванием" таблиц (Bloat)
В PostgreSQL при `UPDATE` и `DELETE` старые версии строк не удаляются физически сразу (механизм MVCC), а помечаются как мертвые. Если `VACUUM` не справляется, таблица "раздувается", и `Seq Scan` становится катастрофически медленным.
*   **Решение:** Настройка `Autovacuum` или ручной `VACUUM FULL` (но осторожно, так как он блокирует таблицу).

#### Д) Неэффективные Join-ы и подзапросы
Использование `IN (SELECT ...)` часто работает хуже, чем `EXISTS` или прямой `JOIN`.
*   **Решение:** Рефакторинг запроса. Переход от подзапросов к `JOIN` или использование `Common Table Expressions (CTE)` для читаемости и иногда производительности.

---

### 3. Мой алгоритм действий (Step-by-step)

1.  **Идентифицировать запрос** (через `pg_stat_statements` или логи медленных запросов).
2.  **Запустить `EXPLAIN (ANALYZE, BUFFERS)`**.
3.  **Проверить индексы:** Есть ли индекс на колонках фильтрации и джойна? Если есть — подходит ли он (тип индекса, селективность)?
4.  **Проверить статистику:** Не пора ли сделать `ANALYZE`?
5.  **Проверить нагрузку на железо:** Не уперлись ли мы в Disk I/O или CPU? (Если да, то индекс — это только часть решения, возможно, нужно больше RAM или оптимизация самой архитектуры).
6.  **Проверить Bloat:** Не слишком ли раздута таблица?
7.  **Рефакторинг запроса:** Если индексы есть, но план плохой — переписываю SQL (убираю функции из WHERE, меняю подзапросы на JOIN и т.д.).
8.  **Валидация:** Снова запускаю `EXPLAIN ANALYZE` и сравниваю метрики "До" и "После".

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

**Агрегат (Aggregate)** в Domain-Driven Design — это кластер связанных объектов (сущностей и Value Objects), которые рассматриваются как **единое целое** с точки зрения изменения данных.

Главная цель агрегата — обеспечить соблюдение **инвариантов** (бизнес-правил, которые всегда должны быть истинными). Внутри агрегата правила проверяются мгновенно, а за его границей — нет.

### Как определять границы агрегата?

Границы агрегата определяются не техническими требованиями, а **бизнес-правилами**. Чтобы найти границы, я задаю себе три вопроса:

1.  **Какие данные должны изменяться атомарно?** Если изменение А требует немедленного и обязательного изменения Б, они должны быть в одном агрегате.
2.  **Какие инварианты нужно защитить?** Если правило требует проверки состояния нескольких объектов одновременно, эти объекты должны быть внутри одной границы.
3.  **Кто является "точкой входа"?** В каждом агрегате есть только один **Корень (Aggregate Root)**. Все внешние объекты могут взаимодействовать с агрегатом *только* через этот корень.

---

### Пример: Система бронирования отелей

Представим процесс бронирования. У нас есть сущности: `Booking` (Бронирование), `Room` (Номер), `Guest` (Гость) и `Payment` (Платеж).

**Агрегат: `Booking`**
*   **Корень (Root):** `Booking`.
*   **Внутренние элементы:** `BookingItem` (позиции в бронировании), `PaymentDetails` (Value Object).
*   **Инвариант:** "Общая сумма бронирования должна быть равна сумме всех позиций в нем". Если мы добавим товар, сумма должна обновиться. Чтобы это гарантировать, мы не даем менять `BookingItem` напрямую — мы вызываем метод `Booking::addItem()`.

**Почему `Room` — это другой агрегат?**
Потомутому что статус номера (свободен/занят) — это инвариант другого процесса. Если мы засунем `Room` внутрь `Booking`, то при каждом изменении бронирования нам придется "трогать" и залочивать номер, что создаст огромные проблемы при параллельных запросах.

---

### Типовая ошибка: "Слишком большой агрегат" (The Fat Aggregate)

Самая частая ошибка — попытка запихнуть в один агрегат всё, что связано между собой по смыслу.

**Пример ошибки:**
Разработчик решает, что `Hotel` должен быть агрегатом, который содержит в себе все `Rooms`, все `Bookings` и всех `Guests`.

**Почему это плохо:**
1.  **Проблемы с конкурентностью (Locking):** Если один пользователь бронирует номер в отеле, а другой в это же время пытается изменить имя гостя, оба запроса будут пытаться обновить одну и ту же строку `hotels` (или залочат весь агрегат). Это создаст очереди и тормоза.
2.  **Производительность:** При загрузке отеля из БД вам придется подтянуть (или хотятельно инициализировать) тысячи связанных объектов.
3.  **Нарушение смысла:** Агрегат должен иметь четкий жизненный цикл. Жизненный цикл бронирования (`Booking`) и жизненный цикл отеля (`Hotel`) — это разные вещи.

**Как исправить:**
Разбить на маленькие агрегаты. `Hotel` управляет списком номеров, а `Booking` ссылается на `Hotel` только через его `ID`.

---

### Золотые правила работы с агрегатами:

1.  **Ссылайтесь на другие агрегаты только по ID.** Никогда не держите прямую ссылку на объект другого агрегата внутри сущности. Это предотвращает неконтролируемую цепочку загрузок (Lazy Loading hell) и помогает избежать проблем с транзакциями.
    *   *Плохо:* `private Room $room;`
    *   *Хорошо:* `private RoomId $roomId;`
2.  **Один агрегат = одна транзакция.** Если вам нужно изменить два агрегата, используйте **Domain Events**. Первый агрегат меняется, выбрасывает событие, и отдельный обработчик (Handler) меняет второй агрегат в новой транзакции.
3.  **Минимизируйте размер.** Чем меньше агрегат, тем выше масштабируемость системы. Ищите баланс между "слишком мелкими объектами" (проблема лишних запросов) и "слишком большими" (проблема блокировок).

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

Это классическая проблема **конкурентного доступа (Concurrency Control)**. Если два процесса одновременно прочитают состояние агрегата, изменят его в памяти и попытаются сохранить, возникнет ситуация **Lost Update (Потерянное обновление)**: второй процесс просто перезапишет изменения первого, и данные станут неконсистентными.

В проектировании я использую два основных подхода: **Optimistic (Оптимистичный)** и **Pessimistic (Пессимистичный)** контроль.

---

### 1. Optimistic Concurrency Control (OCC) — Мой основной выбор

Оптимистичный подход исходит из предположения, что конфликты случаются редко. Мы не блокируем данные при чтении, но при записи проверяем, не изменил ли кто-то агрегат, пока мы с ним работали.

**Как я это реализую:**
Я использую **версионирование (Versioning)**. В каждую таблицу агрегата добавляется колонка `version` (обычно `INT`).

**Механика:**
1.  Процесс А читает `Order` (версия 1).
2.  Процесс Б читает `Order` (версия 1).
3.  Процесс А сохраняет изменения: `UPDATE orders SET status = 'paid', version = 2 WHERE id = 1 AND version = 1`. Успешно.
4.  Процесс Б пытается сохранить: `UPDATE orders SET status = 'cancelled', version = 2 WHERE id = 1 AND version = 1`.
5.  **Результат:** БД возвращает `0 affected rows`, так как версия уже стала `2`.

**В коде (Symfony/Doctrine):**
Doctrine делает это автоматически, если добавить атрибут `#[Version]` к полю. При конфликте она выбросит `OptimisticLockException`.

*   **Плюсы:** Высокая производительность (нет блокировок БД), отлично масштабируется.
*   **Минусы:** Нужно обрабатывать исключение на уровне приложения (например, просить пользователя обновить страницу или реализовать автоматический retry).
*   **Когда использовать:** В 95% случаев в веб-приложениях.

---

### 2. Pessimistic Concurrency Control (PCC) — Когда риск велик

Пессимистичный подход предполагает, что конфликт почти неизбежен. Мы блокируем запись в БД в тот момент, когда начинаем её читать.

**Как я это реализую:**
Использую SQL-команду `SELECT ... FOR UPDATE`.

**Механика:**
1.  Процесс А делает `SELECT ... FOR UPDATE`. БД ставит эксклюзивную блокировку на эту строку.
2.  Процесс Б пытается сделать такой же `SELECT ... FOR UPDATE`. Он **зависает** и ждет, пока Процесс А завершит транзакцию (`COMMIT` или `ROLLBACK`).
3.  Процесс А завершает транзакцию, блокировка снимается, Процесс Б "просыпается" и читает уже обновленные данные.

**В коде (Doctrine):**
```php
$em->beginTransaction();
try {
    $order = $repository->findWithLock($id); // Использует SELECT ... FOR UPDATE
    // ... логика ...
    $em->flush();
    $em->commit();
} catch (\Exception $e) {
    $em->rollback();
}
```

*   **Плюсы:** Гарантированная консистентность, никакой необходимости в повторных попытках (retry) на стороне клиента.
*   **Минусы:** 
    *   **Низкая производительность:** Другие процессы ждут, ресурсы БД расходуются на удержание блокировок.
    *   **Риск Deadlock (Взаимная блокировка):** Если Процесс А заблокировал Объект 1 и ждет Объект 2, а Процесс Б сделал наоборот — система встанет.
*   **Когда использовать:** В критических финансовых операциях (например, списание денег с баланса), где цена ошибки — потеря денег, а цена ожидания — допустимая задержка.

---

### Моя стратегия проектирования

При проектировании я следую иерархии решений:

1.  **Предотвращение через архитектуру:** Я стараюсь проектировать агрегаты так, чтобы они были маленькими. Чем меньше агрегат, тем меньше вероятность, что два процесса одновременно заденут один и тот же объект.
2.  **Разделение ответственности (CQRS):** Я разделяю операции чтения и записи. Если нам нужно просто показать список заказов, мы используем обычные `SELECT` (без блокировок). Блокировки нужны только при изменении.
3. way **Default — Optimistic:** По умолчанию я всегда использую `versioning`. Это делает систему отзывчивой и масштабируемой.
4.  **Strict — Pessimistic:** Я перехожу к пессимистичным блокировкам только в узких местах, где конкуренция за конкретную строку гарантирована и критична (например, инвентаризация остатков товара на складе при массовых распродажах).
5.  **Retry Mechanism:** Для оптимистичных блокировок я внедряю механизм автоматических повторов (например, через Symfony Messenger), чтобы пользователь даже не заметил кратковременного конфликта.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

Доменные события (Domain Events) — это способ сказать: «В системе произошло что-то важное, и другие части системы могут захотеть на это отреагировать». Это ключевой инструмент для соблюдения принципа **Loose Coupling** (слабой связности).

### 1. Когда публиковать события?

Событие должно публиковаться **только тогда, когда агрегат перешел в новое, валидное состояние**. 

**Важное правило:** Никогда не публикуйте событие *до* того, как транзакция будет завершена. Если вы отправите событие `OrderPaid`, а база данных выбросит ошибку и сделает `rollback`, ваше событие станет «лживым» — платеж не прошел, а система уже начала отгружать товар.

**Механика в коде:**
Я не вызываю `EventDispatcher` прямо внутри метода агрегата (это нарушит чистоту доменного слоя, так как агрегат станет зависим от инфраструктуры). Вмеме этого я использую **внутренний список событий**:
1. Агрегат собирает события внутри себя: `$this->record(new OrderPaid($this))`.
2. В конце операции, в слое приложения (Application Service), после успешного `flush()`, я собираю все события из агрегата и публикую их в шину.

---

### 2. Как обрабатывать события?

Я разделяю обработку на два типа в зависимости от критичности:

1.  **Синхронные обработчики (In-process):** Выполняются в той же транзакции и том же потоке. Используются для вещей, которые являются частью того же бизнес-процесса (например, изменение статуса связанного агрегата в рамках одного контекста).
2.  **Асинхронные обработчики (Out-of-process):** Через очередь (RabbitMQ/Messenger). Это основной путь для побочных эффектов: отправка Email, уведомления в Slack, обновление поискового индекса, синхронизация с другими микросервисами.

---

### 3. Какие проблемы решает этот подход?

*   **Слабая связность (Decoupling):** `OrderService` не должен знать о существовании `EmailService`. Он просто говорит: «Заказ оплачен». Это позволяет добавлять новые функции (например, "начислить бонусы") без изменения кода заказа.
*   **Соблюдение Single Responsibility:** Сервис заказа занимается только заказами. Логика уведомлений уходит в свои обработчики.
*   **Масштабируемость:** Тяжелые задачи (генерация PDF, отправка почты) выносятся в фоновые воркеры, не замедляя пользователя.

---

### 4. Какие проблемы создаёт?

*   **Eventual Consistency (Согласованность в конечном счете):** Это главная сложность. После того как заказ оплачен, поисковый индекс обновится не мгновенно, а через 500мс. Система должна быть спроектирована так, чтобы это ожидание было допустимым.
*   **Сложность отладки:** Поток управления становится нелинейным. Трудно проследить цепочку: "Ага, заказ создался $\rightarrow$ вызвалось событие $\rightarrow$ отработал воркер $\rightarrow$ обновился индекс". Нужно хорошее логирование и Trace ID.
*   **Дублирование событий (Idempotency):** В распределенных системах событие может прийти дважды. Обработчик должен быть **идемпотентным** (повторный вызов с тем же событием не должен привести к повторному списанию денег).

---

### 5. Связь с транзакциями БД (Transaction & Event Pattern)

Это самая тонкая часть. Если событие публикуется **до** коммита — мы рискуем "фантомными" событиями. Если **после** — мы рискуем потерять событие, если приложение упадет сразу после коммита, но до отправки в очередь.

Я использую один из двух паттернов:

#### А) Transactional Outbox Pattern (Самый надежный)
Вместо того чтобы отправлять событие в RabbitMQ напрямую, мы записываем его в ту же базу данных в специальную таблицу `outbox` в рамках **той же самой транзакции**, что и изменение агрегата.
1. `BEGIN TRANSACTION`
2. `UPDATE orders ...`
3. `INSERT INTO outbox (event_type, payload) ...`
4. `COMMIT`

Затем отдельный процесс (Relay) читает таблицу `outbox` и перекладывает события в реальную очередь. Это гарантирует, что событие будет отправлено **только если транзакция прошла успешно**.

#### Б) Post-Commit Dispatch (Проще, но менее надежно)
В Symfony это реализуется через слушателей на событие `kernel.terminate` или через обертку над `EntityManager`, которая делает `dispatch` только после успешного `flush()`. 
*   *Риск:* Если сервер "умрет" между `flush()` и `dispatch()`, данные в базе будут верны, но событие потеряется. Для критических задач (деньги) это неприемлемо.

### Итог
Доменные события превращают монолитную "лапшу" из вызовов в гибкую систему, управляемую фактами. Но это требует перехода от мышления "сделай это сейчас" к мышлению "сообщи, что это произошло".

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

Это фундаментальные вопросы, которые определяют, будет ли ваш код "просто набором классов" или настоящей реализацией предметной области.

### 1. Entity vs Value Object

Главное различие заключается в том, **как мы определяем идентичность объекта**.

| Характеристика | Entity (Сущность) | Value Object (Объект-значение) |
| :--- | :--- | :--- |
| **Идентичность** | Определяется уникальным ID, который не меняется со временем. | Определяется только набором своих свойств (значений). |
| **Жизненный цикл** | Имеет историю изменений (состояние меняется, но это тот же объект). | Неизменяем (Immutable). При изменении создается новый экземпляр. |
| **Сравнение** | Два объекта равны, если у них одинаковый ID. | Два объекта равны, если все их свойства идентичны. |
4. **Пример** | `User` (у него есть ID, даже если он сменил имя и почту). | `Money` (100 USD и еще раз 100 USD — это одно и то же значение). |

**Простой тест:**
Если я возьму два объекта, изменю в одном из них одно поле и спрошу: *"Это тот же самый объект?"*
*   Если ответ **"Да"** (потому что ID тот же) $\rightarrow$ это **Entity**.
*   Если ответ **"Нет"** (потому потому что значение изменилось) $\rightarrow$ это **Value Object**.

---

### 2. Как я принимаю решение о классификации?

Когда я проектирую новую концепцию, я иду по алгоритму:

1.  **Нужен ли этому объекту жизненный цикл?** Если объект "рождается", "живет", "меняется" и "умирает" (например, `Order`), это **Entity**. Если это просто описание чего-то (например, `Address`) — это **Value Object**.
2.  **Важен ли нам уникальный идентификатор?** Если нам важно отличать два одинаковых по набору полей объекта (например, два одинаковых товара в корзине, но это разные позиции), то это **Entity**. Если нам неважно, какой именно это "Адрес", важно только, что это "ул. Ленина, 5" — это **Value Object**.
3.  **Нарушается ли инвариант при изменении?** Если изменение одного поля требует проверки всей истории объекта — это **Entity**. Если мы просто создаем "новое значение" — это **Value Object**.

**Мой принцип:** Я всегда стараюсь сделать как можно больше объектов **Value Objects**. Это уменьшает количество состояний, которые нужно отслеживать, и делает код предсказуемым.

---

### 3. Единый язык (Ubiquitous Language)

**Ububiquitous Language** — это общий язык, на котором говорят разработчики, эксперты предметной области (бизнес), аналитики и менеджеры. Это не просто "термины", это способ мышления.

В DDD этот язык должен проникать во все слои приложения:
*   В разговоры (на дейли, на планировании).
*   В названия классов и методов в коде.
*   В названия таблиц в БД.
*   В названия событий в шине сообщений.

#### Как это влияет на код?

**А) Устранение когнитивного диссонанса.**
Если бизнес говорит: *"Мы **отменяем** заказ"*, то в коде должен быть метод `$order->cancel()`, а не `$order->setStatus(OrderStatus::CANCELLED)`. Слово `cancel` несет в себе смысл действия, а `setStatus` — это просто техническая операция.

**Б) Самодокументированный код.**
Когда разработчик читает код, он не должен "переводить" с технического на человеческий. 
*   *Плохо:* `$service->process($data, 1);` (Что такое 1? Что делает process?)
*   *Хорошо:* `$subscriptionService->renew($subscriptionId);` (Сразу понятно, что происходит).

**В) Предотвращение ошибок проектирования.**
Если во время обсуждения задачи бизнес-эксперт говорит: *"Когда клиент **оформляет** заказ..."*, а разработчик пишет в коде `createOrder()`, может выясниться, что "оформление" в бизнесе — это сложный процесс, включающий проверку склада и бронь, а `create` — это просто запись в БД. Единый язык заставляет нас синхронизировать модели.

**Резюме:** 
Если в коде и в разговоре с бизнесом используются разные слова для одних и тех же вещей — вы строите систему, которая рано или поздно развалится из-за непонимания требований. **Код должен быть живым отражением бизнес-процесса.**

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

В Чистой Архитектуре (Clean Architecture) главная цель — **независимость бизнес-логики от внешних факторов** (фреймворков, БД, UI). Это достигается через строгое разделение на слои и соблюдение правила: **зависимости направлены только внутрь, к центру (к бизнес-логике).**

Вот как я структурирую типичное PHP-приложение:

### 1. Слои архитектуры

#### **I. Domain Layer (Ядро / Центр)**
Это самый чистый слой. Он не знает ни о Symfony, ни о Doctrine, ни о базе данных.
*   **Что внутри:** 
    *   **Entities (Агрегаты):** Объекты с идентичностью (например, `Order`).
    *   **Value Objects:** Объекты без ID (например, `Money`, `Email`).
    *   **Domain Exceptions:** Исключения, специфичные для бизнеса (например, `InsufficientFundsException`).
    *   **Domain Services:** Логика, которая не вписывается в одну сущность (например, `TaxCalculator`).
    *   **Repository Interfaces:** Контракты (интерфейсы) для сохранения данных.

#### **II. Application Layer (Слой использования / Use Cases)**
Координирует выполнение конкретных задач пользователя. Он "дирижирует" доменными объектами.
*   **Что внутри:**
    *   **Command/Query Objects (DTO):** Объекты, описывающие, что нужно сделать.
    *   **Command/Query Handlers:** Классы, которые принимают команду, загружают агрегат через интерфейс репозитория, вызывают методы агрегата и сохраняют результат.
    *   **Application Services:** Если задача слишком простая для Command Handler.

#### **III. Infrastructure Layer (Внешний мир / Реализация)**
Здесь живут все детали реализации. Этот слой "загрязняет" приложение, но он необходим.
*   **Что внутри:**
    *   **Persistence (Doctrine):** Реализация интерфейсов репозиториев, маппинг сущностей.
    *   **External APIs:** Клиенты для сторонних сервисов (Stripe, Twilio).
    *   **Messaging:** Реализация очередей (RabbitMQ, Messenger).

#### **IV. User Interface / Presentation Layer (Входные точки)**
Слой, который принимает запросы извне и превращает их в команды для Application Layer.
*   **Что внутри:**
    *   **Controllers (Symfony):** Принимают Request, превращают его в Command, передают в Handler.
    *   **CLI Commands:** Symfony Console команды.
    *   **API Resources:** Преобразование сущностей в JSON/XML.

---

### 2. Куда попадут компоненты?

| Компонент | Слой | Почему? |
| :--- | :--- | :--- |
| **Doctrine ORM** | **Infrastructure** | Это инструмент хранения. Домен не должен знать, как данные пишутся в SQL. |
| **Symfony Controller** | **Presentation** | Это точка входа. Его задача — принять HTTP-запрос и передать управление дальше. |
| **Queue Handler** | **Infrastructure** | Это механизм доставки сообщения. Сам обработчик (логика) будет в Application слое, но "движок" очереди — это инфраструктура. |

---

### 3. Правило зависимостей (Dependency Rule)

**Направление стрелок: `Presentation -> Application -> Domain <- Infrastructure`**

*   **Presentation** знает об **Application** (вызывает Handler).
*   **Application** знает только о **Domain** (использует Entity и интерфейсы репозиториев).
*   **Infrastructure** знает и о **Domain** (реализует интерфейсы), и о **Application** (запускает обработчики).
*   **Domain** — это остров. Он **ничего** не знает о других слоях.

---

### 4. Как следить, чтобы границы не нарушались?

Соблюдать чистоту архитектуры вручную сложно, поэтому я использую три метода:

1.  **Dependency Injection (DI):** Я никогда не создаю объекты инфраструктуры внутри домена. Я передаю их через интерфейсы. Если я вижу в конструкторе `Order` что-то вроде `EntityManagerInterface`, я сразу понимаю, что архитектура сломана.
2.  **Статический анализ (PHPStan / Psalm):** Я настраиваю правила, которые запрещают импорт определенных пространств имен в определенных папках. 
    *   *Например:* Запретить использование `Symfony\*` или `Doctrine\*` внутри папки `src/Domain`.
3.  **Архитектурные тесты (Deptrac):** Это инструмент, специально созданный для проверки слоев. Я пишу конфиг, где описываю: "Слой Domain не может зависеть от слоя Infrastructure". При запуске тестов Deptrac выдаст ошибку, если кто-то нарушил правило.
4.  **Code Review:** Самый важный этап. Я смотю не только на "работает ли код", но и на "где этот код живет". Если логика расчета налога оказалась в контроллере — это повод для рефакторинга.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

Для Symfony-приложения с PostgreSQL я придерживаюсь классической **Пирамиды Тестирования**, но с поправкой на специфику современной разработки (где интеграционные тесты часто важнее чистых Unit-тестов из-за сложности связей).

### 1. Пирамида тестов

#### **L1: Unit Tests (Основание — много)**
*   **Что тестируем:** Чистую бизнес-логику в `Domain Layer`. Value Objects, методы сущностей (Entity), Domain Services.
*   **Что мокаем:** **Всё**. В Unit-тестах не должно быть ни базы данных, ни репозиториев, ни даже других сущностей (если можно заменить их на Value Objects).
*   **Цель:** Проверить сотни граничных условий (edge cases) за миллисекунды.

#### **L2: Integration Tests (Середина — умеренно)**
*   **Что тестируем:** Взаимодействие компонентов. В Symfony это проверка работы `Repository -> Database`, `Command Handler -> Repository`, или `Event Listener -> Service`.
*   **Что мокаем:** Внешние API (четкие HTTP-запросы к сторонним сервисам), но **не мокаем базу данных**.
*   **Цель:** Убедиться, что маппинг Doctrine верный, SQL-запросы корректны и компоненты "склеиваются" правильно.

#### **L3: Functional/End-to-End Tests (Вершина — мало)**
*   **Что тестируем:** Полный цикл запроса через `WebTestCase`. От HTTP-запроса в контроллер до ответа в JSON.
*   **Что мокаем:** Внешние системы (Email, Stripe, SMS), но не внутренние компоненты приложения.
*   **Цель:** Проверить, что "путь пользователя" работает от начала до конца.

---

### 2. Что мокать, а что нет?

Это самый тонкий момент. Мокирование всего подряд ведет к "тестам, которые проходят, но код не работает".

*   **НЕ МОКАЮ:**
    *   **Базу данных (в интеграционных тестах).** Вместо мока репозитория я использую реальную БД (PostgreSQL) в тестовом окружении. Мок репозитория не поймает ошибку в SQL-запросе или неверный тип данных в маппинге.
    *   **Value Objects и простые Entity.** Это просто данные.
*   **МОКАЮ:**
    *   **Внешние API (HTTP-клиенты).** Использую `MockHttpClient` в Symfony, чтобы не зависеть от доступности стороннего сервиса.
    *   **Тяжелые инфраструктурные сервисы:** Отправка почты, генерация тяжелых PDF, работа с файловой системой. Вместо них использую `Spy` или `Mock`, чтобы проверить, был ли вызван метод.
    *   **Time/Clock:** Всегда мокаю текущее время, чтобы тесты не зависели от того, в какой момент они запущены.

---

### 3. Как поддерживать тесты быстрыми и стабильными?

Медленные тесты — это тесты, которые перестают запускать. Стабильные (не "флапающие") тесты — это тесты, которым доверяют.

#### **Для скорости:**
1.  **Database Transactions (Самый важный пункт):** В интеграционных тестах я оборачиваю каждый тест в транзакцию и делаю `rollback` в конце (`$em->beginTransaction()` ... `test` ... `$em->rollback()`). Это в разы быстрее, чем `recreate database` или `TRUNCATE` перед каждым тестом.
2.  **SQLite in Memory (с осторожностью):** Иногда используют SQLite для скорости, но я **предпочитаю реальный PostgreSQL** (в Docker), так because SQLite не поддерживает специфичные фичи Postgres (JSONB, специфичные типы), и тесты могут проходить на SQLite, но падать в продакшене.
3.  **Parallel Testing:** Использование инструментов типа `Paratest` для запуска тестов в несколько потоков.

#### **Для стабильности (Deterministic Tests):**
1.  **Чистая база на каждый запуск:** Использование Docker-контейнера с чистой БД для CI/CD. Никаких "общих" тестовых баз, которые замусориваются.
2.  **Избегание Non-determinism:** Никаких `rand()`, `time()` или случайных строк без использования `seed` в генераторах (например, Faker с фиксированным сидом).
3.  **Изоляция данных:** Каждый тест должен создавать свои данные. Никогда не полагайтесь на то, что в базе "уже лежит пользователь с ID 1".
4.  **Управление временем:** Использование `ClockInterface` (введен в PHP 8.3 и поддерживается в Symfony), чтобы жестко фиксировать время в тестах.

**Мой девиз:** "Unit-тесты — для логики, интеграционные тесты — для контрактов с БД, E2E — для проверки маршрутов".

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Это классическая проблема конкурентного доступа к данным. Когда два процесса читают состояние $A$, изменяют его локально и пытают записать обратно, возникает состояние **Race Condition** (состояние гонки).

Основная проблема — **Lost Update (Потерянное обновление)**. Процесс №2 перезаписывает изменения Процесса №1, и изменения первого просто исчезают, как будто их и не было.

Я выделяю два основных стратегии защиты: **Optimistic** и **Pessimistic**.

---

### 1. Optimistic Concurrency Control (Оптимистичный подход)

Мы предполагаем, что конфликты случаются редко. Мы не блокируем запись, но при попытке сохранения проверяем, не изменилась ли версия данных с момента нашего чтения.

**Как это работает:**
В таблицу добавляется колонка `version` (целое число).
1. Процесс А читает запись: `id=1, version=5`.
2. Процесс Б читает запись: `id=1, version=5`.
3. Процесс А делает `UPDATE ... SET version=6 WHERE id=1 AND version=5`. Успех.
4. Процесс Б делает `UPDATE ... SET version=6 WHERE id=1 AND version=5`. 
5. **Результат:** БД возвращает `0 affected rows`, потому что версия уже `6`.

**Реализация в Symfony/Doctrine:**
Просто добавляю атрибут `#[Version]` к полю в сущности. Doctrine сама берет на себя проверку и выбросит `OptimisticLockException`.

*   **Плюсы:**
    *   Максимальная производительность (нет блокировок в БД).
    *   Высокая масштабируемость (нет риска Deadlock'ов).
*   **Минусы:**
    *   Нужно обрабатывать исключение в коде (например, просить пользователя "Обновите страницу и попробуйте снова").
*   **Когда выбирать:** В 90% случаев в веб-приложениях (редактирование профиля, изменение описания товара, обновление настроек).

---

### 2. Pessimistic Concurrency Control (Пессимистичный подход)

Мы предполагаем, что конфликт неизбежен. Мы блокируем запись на уровне базы данных сразу, как только начинаем её читать.

**Как это работает:**
Используется механизм `SELECT ... FOR UPDATE`.
1. Процесс А делает `SELECT ... FOR UPDATE`. БД ставит эксклюзивную блокировку на строку.
2. Процесс Б делает такой же запрос. Он **зависает** и ждет на уровне ядра БД.
3. Процесс А делает `COMMIT`. Блокировка снимается.
4. Процесс Б "просыпается", читает уже обновленные данные и продолжает работу.

**Реализация в Doctrine:**
```php
$em->beginTransaction();
$order = $repository->findWithLock($id); // Внутри SELECT ... FOR UPDATE
// ... логика ...
$em->flush();
$em->commit();
```

*   **Плюсы:**
    *   Гарантированная консистентность без необходимости повторных попыток со стороны пользователя.
    *   Идеально для критических операций.
*   **Минусы:**
    *   Низкая производительность (другие процессы ждут).
    *   Риск **Deadlock** (если два процесса заблокировали разные объекты и пытаются захватить те, что у другого).
*   **Когда выбирать:** В финансовых операциях, где цена ошибки — потеря денег (списание средств, инвентаризация остатков на складе, бронирование последнего места).

---

### Сравнительная таблица

| Критерий | Optimistic (Версионирование) | Pessimistic (Блокировка) |
| :--- | :--- | :--- |
| **Основной механизм** | Проверка версии при записи | Блокировка строки при чтении |
| **Производительность** | Высокая | Низкая |
| **Риск Deadlock** | Нет | Высокий |
| **Поведение при конфликте** | Ошибка (нужен Retry/User action) | Ожидание (процесс висит) |
| **Сложность реализации** | Низкая (через `#[Version]`) | Средняя (нужны транзакции) |

### Мой выбор (Decision Matrix)

1.  **Если это CRUD-операция** (редактирование текста, смена статуса, где конфликт маловероятен) $\rightarrow$ **Optimistic**.
2.  **Если это критическая транзакция** (деньги, ресурсы, которые нельзя "продать дважды") $\rightarrow$ **Pessimistic**.
3.  **Если это высоконагруженная очередь задач** (обработка сообщений) $\rightarrow$ **Optimistic** + механизм автоматического повтора (Retry) на уровне Application layer.

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

Мой Git-процесс строится вокруг принципа **стабильности основной ветки** и **минимизации стоимости интеграции**. Я сторонник модели, близкой к *GitHub Flow*, но адаптированной под корпоративную разработку с использованием защищенных веток.

Вот пошаговый путь:

### 1. Ветвление (Branching Strategy)

Я использую модель **Feature Branching** с разделением на три типа веток:
*   `main` (или `master`): Единственная стабильная ветка. То, что находится здесь, всегда готово к деплою на продакшен.
*   `develop` (опционально): Если в компании принят GitFlow, я использую её как интеграционную ветку. Если проект небольшой — пишу сразу в `main`.
*   `feature/JIRA-123-description`: Ветки под конкретные задачи. Название всегда содержит ID задачи и краткое описание.

**Почему так:** Это позволяет изолировать разработку. Ни одна незаконченная фича не попадет в `main` и не сломает сборку.

---

### 2. Коммиты (Commit Messages)

Я придерживаюсь стандарта **Conventional Commats**. Это не просто "красота", а инструмент для автоматизации.

**Формат:** `<type>(<scope>): <description>`
*   `feat`: Новая функциональность.
*   `fix`: Исправление ошибки.
*   `refactor`: Изменение кода без изменения логики.
*   `test`: Добавление или изменение тестов.
*   `chore`: Обновление зависимостей, конфигов (не меняет логику).
*   `docs`: Изменения в документации.

**Пример:** `feat(order): add discount calculation logic`

**Почему так:**
1.  **Читаемость:** История понятна даже через полгода.
2.  **Автоматизация:** На основе этих префиксов можно автоматически генерировать `CHANGELOG.md` и определять версию для семантического релиза (SemVer).

---

### 3. Pull Request (PR) и Code Review

PR — это не просто "просьба влить код", это инструмент передачи знаний и контроля качества.

**Мой процесс создания PR:**
*   **Self-Review:** Прежде чем звать коллег, я сам прохожу по своим диффам. Это убирает 50% глупых ошибок (забытый `dd()`, лишний лог).
*   **Описание:** В PR я пишу: *Что сделано*, *Зачем это сделано*, *Как протестировать* и *На что обратить внимание*.

**Процесс ревью:**
*   **Цель:** Не "поймать на ошибке", а убедиться, что решение соответствует архитектуре и легко поддерживается.
*   **Принципы:** Если замечание касается стиля (PSR) — это должен решать линтер. Если замечание касается архитектуры — это обсуждение.
*   **Слияние:** Я использую **Squash and Merge**. Все мелкие коммиты типа "fix typo", "typo again" схлопываются в один чистый, осмысленный коммит в `main`.

**Почему так:** Это держит историю `main` чистой и линейной. Один PR = один логический коммит.

---

### 4. Релизы (Releases)

Я использую принцип **Continuous Delivery**.

*   **Версионирование:** Придерживаюсь **Semantic Versioning (SemVer)**: `MAJOR.MINOR.PATCH`.
*   **Автоматизация:** При слиянии в `main` запускается CI-пайплайн:
    1.  Запуск тестов (Unit, Integration).
    2.  Статический анализ (PHPStan, Psalm).
    3.  Проверка стиля (PHP-CS-Fixer).
    4.  Сборка артефакта (Docker-образ).
*   **Деплой:** Если тесты прошли, артефакт улетает на `Staging`. После ручного или автоматического подтверждения — на `Production`.

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

Для меня хороший Code Review — это не "экзамен" и не поиск ошибок, а **процесс обмена знаниями и совместного обеспечения качества**. Это диалог, целью которого является улучшение продукта и рост команды, а не поиск виноватых.

### 1. На что я смотрю в первую очередь (Приоритеты)

Я разделяю проверку на три уровня, чтобы не зарыться в мелочах, пропустив критические проблемы.

**Уровень 1: Архитектура и Логика (Самое важное)**
*   **Соблюдение SRP и SOLID:** Не превратился ли этот класс в "Божественный объект"? Не нарушена ли инкапсуляция?
*   **Корректность бизнес-логики:** Решает ли этот код задачу, поставленную в задаче? Нет ли пограничных случаев (edge cases), которые не учтены?
*   **Безопасность и производительность:** Нет есть ли здесь потенциальные SQL-инъекции, уязвимости или N+1 запросы? Не заблокирует ли этот код базу данных?
*   **Сложность:** Не слишком ли переусложнен код? Можно ли сделать это проще?

**Уровеньй 2: Тестируемость и Надежность**
*   **Покрытие тестами:** Есть ли тесты на новый функционал? Покрывают ли они негативные сценарии (ошибки, пустые данные)?
*   **Обработка исключений:** Не "проглатываются" ли ошибки? Достаточно ли информативны сообщения об ошибках?

**Уровень 3: Стиль и Читаемость (Style & Clean Code)**
*   **Читаемость:** Понятны ли названия переменных и методов? Не слишком ли длинные методы?
*   **Стандарты:** Соответствует ли код PSR и принятым в команде правилам именования.
*   *Примечание: Если у нас настроен PHP-CS-Fixer и PHPStan, я не трачу время на проверку этих вещей врумальную — это должен делать робот.*

---

### 2. Как я маркирую замечания

Чтобы не выглядеть токсично и помочь автору понять серьезность замечания, я использую систему тегов (или эмодзи). Это помогает автору расставить приоритеты.

*   **[BLOCKER] / 🔴:** Критическая ошибка. Ошибка в логике, дыра в безопасности или нарушение архитектуры. PR не может быть принят, пока это не исправят.
*   **[CHORE] / 🟡:** Не критично, но стоит поправить. Например, переименовать переменную для ясности или упростить сложный `if`.
*   **[QUESTION] / ❓:** Я не уверен, что это ошибка, но хочу понять логику автора. Это приглашение к дискуссии, а не указание.
*   **[NIT] (Nitpick) / 💡:** Мелкие придирки по стилю или очень мелкие улучшения, которые не влияют на работу. Автор может проигнорировать это, если очень спешит.
*   **[PRAISE] / ✅:** Я обязательно пишу, если вижу крутое решение или очень чистый код. Ревью должно состоять не только из критики.

---

### 3. Как поступать при разногласии с автором

Разногласия — это нормально. Это признак того, что код заставляет думать.

**Мой алгоритм разрешения конфликтов:**

1.  **Сначала — аргументация через "Почему":** Я не говорю "Это плохо". Я говорю: *"Если мы сделаем так, то при масштабировании мы столкнемся с проблемой X, потому что..."*. Я привожу ссылки на принципы (SOLID, паттерны) или документацию.
2.  **Предложение альтернативы:** Я не просто критикую, я предлагаю вариант: *"Как ты смотришь на то, чтобы вынести это в отдельный сервис? Это позволит нам..."*.
3.  **Признание правоты:** Если автор аргументированно доказывает, что его решение лучше или уместнее в данном контексте — я принимаю его позицию без споров. **Цель — лучшее решение, а не моя правота.**
4.  **Эскалация (как крайний случай):** Если мы зашли в тупик и не можем договориться (и это критически важный вопрос), я предлагаю вынести обсуждение на обсуждение всей команды или привлечь лида/архитектора. Но это должно быть разовым случаем.

**Главное правило:** Мы критикуем **код**, а не **человека**. Я всегда использую формулировки типа *"Этот метод кажется сложным"* вместо *"Ты написал слишком сложный метод"*.

### Моя формулировка задачи (User Story + Acceptance Criteria)

**Title:** Реализация фильтрации и поиска по истории заказов в личном кабинете пользователя.

Как зарегистрированный пользователь, я хочу иметь возможность фильтровать свои заказы по дате и искать их по номеру заказа, чтобы быстро находить информацию о прошлых покупках без обращения в поддержку.

1.  **Фильтрация по дате:** В интерфейсе личного кабинета добавить выбор диапазона дат (от/до). Запрос должен корректно обрабатывать выбор одного дня или периода.
2.  **Поиск по номеру:** Добавить текстовое поле поиска. Поиск должен работать по частичному совпадению номера заказа (`LIKE %number%`).
3.  **Пагинация:** Результаты поиска должны быть разбиты на страницы (по 20 заказов на страницу).
4.  **Производительность:** Время выполнения запроса при поиске в истории (более 100 заказов) не должно превышать 200 мс.
5.  **API:** Создать новый эндпоинт `GET /api/v1/orders?date_from=...&date_to=...&query=...` с поддержкой пагинации.
6.  **Тесты:** Покрыть логику фильтрации в репозитории Unit-тестами, а эндпоинт — интеграционными тестами.

4.  **Критерии приемки (Acceptance Criteria):** Это чек-лист. Когда разработчик закончит, он сможет сам проверить: "Так, поиск по дате работает? Да. Пагинация есть? Да. API соответствует спецификации? Да".

**Итог:** Такая задача превращает "жалобу" в **конкретный план действий**, где понятны входные данные, ожидаемый результат и границы ответственности.

**Интервьюер:** Ты выполняешь задачу с чёткими критериями приёмки. По ходу работы выясняется: а) нашёл попутный баг, не связанный с задачей; б) понял, что один из критериев приёмки противоречит цели задачи. Что делаешь в каждом случае и почему?

**Кандидат:**

Это классическая ситуация, проверяющая профессионализм: умение отделять «сигнал» от «шума» и способность управлять ожиданиями бизнеса.

### Сценарий А: Нашёл попутный баг (Side Effect / Opportunistic Bug)

Здесь важно не превратить разработку фичи в бесконечный процесс исправления всего подряд (это называется *Scope Creep*).

**Мои действия:**
1.  **Оценить масштаб и критичность.** Я задаю себе вопросы: «Насколько это опасно?», «Насколько это сложно исправить?», «Зависит ли текущая задача от этого бага?».
2.  **Задокументировать.** Я создаю отдельный тикет в бэклоге (Jira/Trello) с четким описанием бага, шагами воспроизведения и приоритетом.
3.  **Принять решение на основе стоимости (Cost-Benefit):**
    *   **Если баг критический (P0/P1):** (например, дыра в безопасности или баг, блокирующий текущую задачу). Я сообщаю лиду/менеджеру: *"Я нашел критическую проблему. Чтобы задача была выполнена корректно, мне нужно сначала исправить это. Это добавит +X часов к сроку"*.
    *   **Если баг косметический или низкоприоритетный:** Я **не трогаю** его в рамках текущей задачи. Я продолжаю делать задачу по плану, а баг остается в бэклоге.

**Почему так:**
Если я начну чинить всё, что вижу, я никогда не закончу текущую задачу. Это демотивирует команду и срывает сроки. Но если я проигнорирую критический баг, я проявлю халатность.

---

### Сценарий Б: Критерий приёмки противоречит цели задачи

Это ситуация, когда требования «сломаны». Например: *«Цель: ускорить поиск заказов. Критерий: при поиске обязательно подтягивать все связанные данные из 10 связанных таблиц через JOIN»*. Это противоречит друг другу.

**Мои действия:**
1.  **Ни в коем случае не игнорировать.** Нельзя просто «сделать как написано» и выпустить медленный код, оправдываясь тем, что «так в ТЗ было».
2.  **Собрать доказательства.** Я подготовлю цифры. Например: *"Если мы реализуем критерий №2 (тяжелые JOIN), время ответа увеличится с 200мс до 2с, что прямо противоречит цели задачи (ускорение поиска)"*.
3.  **Инициировать обсуждение (Refinement).** Я иду к владельцу продукта (PO) или аналитику с вопросом: *"Я заметил противоречие. Мы хотим ускорить поиск, но критерий X его замедляет. Что для нас в приоритете: полнота данных или скорость?"*.
4.  **Предложить альтернативу.** Я не прихожу с проблемой, я прихожу с решением. *"Чтобы и скорость сохранить, и данные получить, я предлагаю вместо тяжелого JOIN использовать два быстрых запроса или кэширование"*.

**Почему так:**
Разработчик — это не «кодер», который слепо перекладывает требования из Jira в код. Разработчик — это инженер, который несет ответственность за **результат**. Если я вижу, что выполнение требований приведет к провалу цели, моя обязанность — поднять флаг (Stop the line).

| :--- | :--- | :--- |

| **Противоречие в ТЗ** | Остановить и прояснить. | **Целесообразность результата.** |

## Q23 · Работа с задачами

**Интервьюер:** Задача выполнена: код написан, тесты проходят. Из чего состоит твой отчёт о выполнении? Что меняется, если часть задачи сделать не удалось?

**Кандидат:**

Когда задача считается выполненной, мой отчет — это не просто фраза «всё готово». Это набор артефактов, который позволяет команде и бизнесу оценить результат, провести качественное ревью и обеспечить стабильный деплой.

### 1. Структура отчета о выполнении (Completion Report)

Я структурирую отчет так, чтобы он отвечал на вопросы: **Что сделано? Как это работает? Как это проверить?**

**Состав отчета:**

1.  **Summary (Резюме):** Краткое описание выполненной работы в контек Pend (в контексте задачи).
    *   *Пример: "Реализован поиск заказов по номеру и дате, оптимизированы запросы через индексы".*
2.  **Implementation Details (Технические детали):** Краткий технический лог для коллег-разработчиков.
    *   Какие изменения внесены в БД (миграции).
    *   Какие новые сущности или сервисы добавлены.
    *   Какие изменения затронули архитектуру (например, "добавлен новый Listener для событий").
3.  **Verification (Результаты тестирования):** Доказательство того, что код работает.

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

Важное уточнение: в **PostgreSQL нет команды `FORCE INDEX`**. Эта команда существует в MySQL. 

В PostgreSQL управление использованием индексов работает иначе. Планировщик (Query Planner) сам решает, использовать индекс или нет, основываясь на статистике. Если вы хотите "заставить" PostgreSQL использовать определенный путь, вы используете другие механизмы.

Вот как это работает в Postgres и какие альтернативы существуют.

### 1. Почему планировщик может игнорировать индекс?
Прежде чем "принуждать" базу, нужно понять, почему она этого не делает:
*   **Низкая селективность:** Если планировщик видит, что по вашему условию `WHERE` будет выбрано, например, 80% всей таблицы, он решит, что `Sequential Scan` (полный перебор) будет быстрее, чем прыжки по индексу и последующее чтение страниц данных.
*   **Устаревшая статистика:** Планировщик "думает", что данных мало или они распределены иначе.
*   **Неподходящий тип данных:** Например, сравнение `integer` с `text` вызывает неявное приведение типов, что делает индекс бесполезным.
*   **Функции в условии:** `WHERE LOWER(email) = '...'` делает обычный индекс по `email` бесполезным.

---

### 2. Как "заставить" PostgreSQL использовать индекс (Альтернативы FORCE INDEX)

Если вы уверены, что индекс эффективен, но Postgres его игнорирует, есть три пути:

#### А) Использование расширения `pg_hint_plan` (Самый близкий аналог)
Это стороннее расширение, которое добавляет поддержку "хинтов" (hints) в PostgreSQL, подобно Oracle или MySQL.
*   **Как это работает:** Вы вставляете специальные комментарии прямо в SQL-запрос.
*   **Пример:** `/*+ IndexScan(users user_email_idx) */ SELECT * FROM users WHERE email = 'test@test.com';`
*   **Когда использовать:** Когда вы точно знаете, что планировщик ошибается, и вам нужно принудительное управление в критических запросах. *Но будьте осторожны: это может стать "костылем", который сломается при обновлении данных.*

#### Б) Исправление статистики (`ANALYZE`)
Часто проблема не в планировщике, а в том, что он "глупый" из-за старых данных.
*   **Решение:** Запуск команды `ANALYZE table_name;`. Это обновит статистику распределения значений.
*   **Когда использовать:** Если запросы внезапно стали тормозить после массовой вставки или удаления данных.

#### В) Создание специализированных индексов (Самый правильный путь)
Вместо того чтобы "пинать" планировщик, нужно дать ему инструмент, который ему понравится.
*   **Partial Indexes (Частичные индексы):** Если вы часто ищете только активных пользователей: `CREATE INDEX idx_active_users ON users (id) WHERE status = 'active';`.
*   **Expression Indexes (Функциональные индексы):** Если вы ищете по `LOWER(email)`, создайте индекс именно по этому выражению: `CREATE INDEX idx_lower_email ON users (LOWER(email));`.
*   **Covering Indexes (Индексы с включением данных):** Использование `INCLUDE` в индексе, чтобы база могла взять все данные прямо из индекса, не обращаясь к основной таблице (Index Only Scan).

---

### Резюме: мой подход к оптимизации

Я никогда не начинаю с "принуждения" (hints). Мой процесс выглядит так:

1.  **`EXPLAIN ANALYZE`**: Понять, что именно делает база (Seq Scan или Index Scan) и почему.
2.  **Проверка типов и функций**: Убедиться, что нет неявных приведений типов или функций, убивающих индекс.
3.  **Обновление статистики**: Запустить `ANALYZE`.
4.  **Оптимизация структуры индекса**: Если индекс есть, но он не подходит — создать **Partial** или **Expression** индекс. Это "чистый" способ, который не ломает логику планировщика.
5.  **`pg_hint_plan`**: Только как крайняя мера, если все остальные способы провалились, а запрос критически важен для производительности.

## Q25 · Провокации

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

Это очень глубокий вопрос, который затрагивает разницу между восприятием «строгости» и реальной работой движка Zend Engine.

Короткий ответ: **Влияние `strict_types=1` на производительность практически равно нулю (менее 0.1% в типичных задачах).**

Более того, в некоторых специфических сценариях использование строгой типизации может даже **немного ускорить** выполнение кода.

### Почему это не замедляет код?

Многие ошибочно полагают, что при `strict_types=1` PHP вынужден делать дополнительные проверки «на лету» при каждом вызове функции. На самом это не так.

1.  **Проверки происходят в момент вызова, а не внутри функции:** Когда вы вызываете `foo(123)`, PHP проверяет тип аргумента *в момент передачи* в функцию. Если тип не совпадает, выполнение прерывается немедленно. Внутри самой функции переменная уже имеет гарантированный тип, и PHP не тратит ресурсы на повторную проверку того, что он уже знает.
2.  **Оптимизации JIT и Zend Engine:** Современные версии PHP (особенно 8.x с JIT-компилятором) полагаются на предсказуемость типов. Когда типы жестко заданы (чеи через `strict_types`, так и через type-hinting), движку проще оптимизировать машинный код, так как он заранее знает, с какими типами данных будет работать регистр процессора.
3.  **Отсутствие преобразований (Coercion):** В режиме по умолчанию (coercive mode) PHP тратит микросекунды на то, чтобы превратить строку `"10"` в число `10`. В режиме `strict_types` он просто выбрасывает ошибку. В этом смысле `strict_types` даже **экономит** циклы процессора, так как исключает логику приведения типов.

### Когда может возникнуть «замедление»?

Единственный случай, когда можно заметить разницу — это если ваше приложение **массово генерирует ошибки типов** (что само по себе является архитектурной катастрофой). Генерация исключения `TypeError` — это дорогая операция с точкистью создания Stack Trace. Но это не замедление из-за `strict_types`, это замедление из-за обработки ошибок.

### В чем реальная польза (помимо скорости)?

Если мы отбросим производительность, то ценность `strict_types` заключается в **снижении стоимости разработки и поддержки**:

*   **Fail Fast:** Ошибка обнаруживается в момент вызова, а не в недрах глубокой бизнес-логики, когда "кривое" значение (например, `null` вместо `string`) привело к непредсказуемому результату спустя 10 шагов.
*   **Документированность:** Код становится самодокументированным. Вы точно знаете, что функция принимает, и вам не нужно гадать, может ли там оказаться `0` или `false`.
*   **Безопасность:** Это защищает от тонких багов, связанных с приведением типов (например, когда строка `"0"` приводится к `false`, что может изменить логику условия).

**Мой вердикт:** Я использую `strict_types=1` во всех своих проектах по умолчанию. Это стандарт профессиональной разработки, и миф о том, что он замедляет код, не имеет под собой технического обоснования.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

Это утверждение требует небольшого уточнения: **Doctrine на самом деле поддерживает составные первичные ключи (Composite Primary Keys)**, но делает это с существенными ограничениями, которые заставляют разработчиков избегать этого паттерна.

Когда говорят, что Doctrine «не поддерживает» их, имеют в виду, что она не поддерживает их **удобно и полноценно** в контекine Identity Map и управления жизненным циклом сущностей.

### Почему это проблема в Doctrine?

Основная причина кроется в архитектуре **Identity Map** (карты идентичности).

1.  **Уникальность в памяти:** Чтобы гарантировать, что для одной и тойтой же строки в БД у вас существует только один объект в памяти PHP, Doctrine использует внутренний реестр, где ключом является комбинация `[EntityClassName, PrimaryKey]`. 
2.  **Сложность управления:** Когда первичный ключ состоит из нескольких полей, логика сравнения объектов, их кэширования и отслеживания изменений (Unit of Work) становится значительно сложнее и подвержена ошибкам.
3.  **Проблемы с ассоциациями:** Если сущность `A` имеет составной ключ, то любая другая сущность `B`, которая ссылается на `A` через `ManyToOne`, должна будет хранить **все** поля этого ключа в качестве внешнего ключа (Foreign Key). Это раздувает таблицы и усложняет маппинг.

---

### Как с этим живут в реальных проектах?

В профессиональной разработке на Symfony/Doctrine принято использовать **Surrogate Keys (Суррогатные ключи)** вместо **Natural Keys (Естественных ключей)**.

#### Способ 1: Введение суррогатного ID (Рекомендуемый)
Вместо того чтобы использовать составной ключ (например, `order_id` + `product_id`), мы добавляем к таблице техническое поле `id` (автоинкремент или UUID) и делаем его единственным первичным ключом.

*   **Как это выглядит:**
    *   Таблица `order_items` имеет `id` (PK).
    *   Уникальность пары `order_id` + `product_id` обеспечивается через **Unique Constraint** на уровне базы данных.
*   **Плюсы:**
    *   Все связи в системе (Foreign Keys) простые и состоят из одного поля.
    *   Doctrine работает идеально быстро и предсказуемо.
    *   Соблюдается чистота архитектуры.

#### Способ 2: Использование Value Objects для естественных ключей
Если составной ключ несет в себе важный смысл (например, координаты или составной код), мы маппим его не как набор колонок в сущности, а как один **Embeddable (Value Object)**.

*   **Пример:** Вметь использовать `composite_id_part1` и `composite_id_part2`, мы создаем `class CompositeId` и используем его как `@Embedded`. Но даже в этом случае для связи с другими таблицами нам все равно придется вводить суррогатный `id`.

#### Способ 3: Использование UUID
В распределенных системах часто отказываются от автоинкремента в пользу UUID. Это позволяет генерировать уникальный ключ на стороне приложения, не дожидаясь ответа от БД, и при этом сохранять ключ простым (одно поле), избегая проблем составных ключей.

---

### Итоговое правило (Rule of Thumb)

Если вы столкнулись с необходимостью использовать составной ключ:

1.  **Спросите себя:** «Могу ли я добавить в эту таблицу простое поле `id` (UUID или BigInt)?»
2.  **Если да:** Добавляйте `id` как Primary Key, а старый составной ключ делайте `UNIQUE constraint`. Это сделает вашу модель в Doctrine чистой, а связи — простыми.
3.  **Если нет (крайне редкие случаи):** Используйте стандартный механизм `#[Id]` на нескольких полях в Doctrine, но будьте готовы к тому, что работа с ассоциациями (отношениями) станет болезненной.

**Мой выбор:** Всегда использовать суррогатные ключи (`id`). Это стандарт индустрии, который экономит часы отладки и упрощает масштабирование системы.

## Q27 · Мини-код-ревью

**Интервьюер:** Посмотри на этот код:

```php
class OrderController
{
    public function pay(Request $req): Response
    {
        $id = $req->get('order_id');
        $pdo = DB::connect();
        $order = $pdo->query("SELECT * FROM orders WHERE id = $id")->fetch();
        if (!$order) {
            return new Response('not found', 404);
        }
        $order['status'] = 'paid';
        $pdo->exec("UPDATE orders SET status = 'paid' WHERE id = $id");
        Mailer::send($order['email'], 'Ваш заказ оплачен');
        (new Logger())->log('paid ' . $id);
        return new Response('ok');
    }
}
```

Какие проблемы ты видишь и как бы ты этот код переделал? С чего начал бы и почему?

**Кандидат:**

Этот код — классический пример «антипаттерна», который часто встречается в старых проектах или при быстрой разработке. В нем нарушены почти все принципы чистого кода, безопасности и надежности.

### 1. Анализ проблем

Я бы разделил проблемы на несколько критических категорий:

**А) Безопасность (Критично!):**
*   **SQL Injection:** Переменная `$id` вставляется напрямую в строку запроса. Злоумышленник может передать `1 OR 1=1`, что позволит манипулировать всей базой.
*   **Отсутствие авторизации:** Код не проверяет, принадлежит ли заказ именно тому пользователю, который делает запрос. Любой может оплатить (или "оплатить" без оплаты) чей угодно заказ.

**Б) Архитектура (Нарушение слоев):**
*   **Нарушение SRP (Single Responsibility Principle):** Контроллер делает всё: работает с HTTP, работает с БД, управляет бизнес-логикой (статус заказа), отправляет почту и пишет логи.
*   **Нарушение слоев (Layer Violation):** Бизнес-логика (изменение статуса) и инфраструктура (SQL, Mailer, Logger) перемешаны в одном месте. Контроллер "знает" слишком много о реализации.
*   **Жесткая зависимость (Tight Coupling):** Использование статических вызовов `DB::connect()`, `Mailer::send()` и `new Logger()` делает код нетестируемым. Мы не можем написать Unit-тест, не поднимая реальную БД и не отправляя реальные письма.

**В) Надежность и консистентность:**
*   **Отсутствие транзакций:** Если `UPDATE` прошел успешно, а `Mailer::send()` упал с ошибкой, заказ останется в статусе `paid`, но пользователь не получит подтверждения. Или наоборот: если бы логика была сложнее, данные могли бы остаться в неконсистентном состоянии.

---

### 2. Как бы я это переделал?

Я бы начал с **разделения ответственности**. Я бы вынес логику из контроллера в **Application Layer** (Command Handler) и **Domain Layer** (Entity).

#### Шаг 1: Создание Доменной модели (Domain Layer)
Сначала создаем сущность, которая инкапсулирует правила изменения заказа.

```php
class Order {
    private int $id;
    private string $status;
    private string $email;

    // ... конструктор и геттеры ...

    public function markAsPaid(): void {
        if ($this->status === 'paid') {
            throw new DomainException("Order is already paid");
        }
        $this->status = 'paid';
    }
}
```

#### Шаг 2: Создание репозитория (Infrastructure Layer)
Определяем интерфейс в Domain, а реализацию — в Infrastructure.

```php
interface OrderRepositoryInterface {
    public function find(int $id): ?Order;
    public function save(Order $order): void;
}
```

```php
        $this->em->wrapInTransaction(function() use ($orderId) {
            $order = $this->repository->find($orderId);
            
            if (!$order) {
                throw new OrderNotFoundException($orderId);
            }

            $order->markAsPaid();
            $this->repository->save($order);

            // Побочные эффекты (в идеале через события, но для простоты здесь)
            $this->mailer->send($order->getEmail(), 'Ваш заказ оплачен');
            $this->logger->info('Order paid: ' . $orderId);
        });
    }
}
```

#### Шаг 4: Чистый Контроллер (Presentation Layer)
Теперь контроллер максимально тонкий.

```php
class OrderController extends AbstractController
{
    public function pay(int $orderId, PayOrderHandler $handler): Response
    {
        try {
            // Здесь должна быть проверка прав доступа (IsGranted)
            $handler->handle($orderId);
            return new Response('ok');
        } catch (OrderNotFoundException $e) {
            return new Response('not found', 404);
        } catch (\Exception $e) {
            return new Response('error', 500);
        }
    }
}
```

### 3. Почему я начал именно с этого?

Я начал с **проектирования границ (Boundaries)**. 

Если вы начнете исправлять код, просто добавляя `prepared statements` в текущий контроллер, вы исправите безопасность, но не решите проблему тестируемости или масштабируемости. 

**Мой алгоритм декомпозиции:**
1.  **Выделение сущности:** Сначала я определяю, что такое "Заказ" и как он меняется (Domain).
2.  **Определение контрактов:** Я решаю, как мы будем сохранять заказы, не привязываясь к SQL (Repository Interface).
3.  **Оркестрация:** Я создаю сценарий использования (Use Case), который управляет транзакцией.
4.  **Инфраструктура:** В последнюю очередь я "навешиваю" реализацию (SQL, Mailer, Logger).

Это позволяет сделать код **тестируемым** (мы можем замокать репозиторий и мейлер), **безопасным** (защита от SQLi и нарушение границ) и **надежным** (атомарность через транзакции).

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Эта сущность — классический пример того, как архитектурные границы размываются, превращая доменную модель в инструмент управления базой данных. Здесь нарушено сразу несколько фундаментальных принципов.

### Что не так?

**1. Нарушение принципа единственной ответственности (SRP) и чистоты домена**
Сущность `User` теперь не только хранит данные и бизнес-правила, но и знает о том, как их сохранять. Она стала зависима от `EntityManagerInterface` (инфраструктурный слой). Доменная сущность не должна знать о существовании ORM или базы данных.

**2. Нарушение инверсии зависимостей (DIP)**
Вместо того чтобы доменной модели диктовать правила, она сама управляет инфраструктурой. Это делает сущность "тяжелой" и невозможной для чистого Unit-тестирования без подмены всей инфраструктуры.

**3. Нарушение инкапсуляции и управления транзакциями**
Метод `changeEmail` вызывает `flush()`. Это критическая ошибка.
*   **Потеря контроля:** Вызывающий код (например, сервис) не знает, что внутри сущности произойдет запись в базу. Он может вызвать три метода сущности, ожидая, что всё сохранится одним транзакционным блоком, а на самом деле произойдет три независимых коммита.
*   **Невозможность отката:** Если после `changeEmail` произойдет ошибка в другом месте той же бизнес-операции, вы не сможете откатить изменение email, так как `flush()` уже зафиксировал его в БД.

**4. Проблема тестирования**
Чтобы протестировать простейший метод `changeEmail`, вам придется создавать мок для `EntityManagerInterface`. Это превращает простой тест в сложный интеграционный сценарий.

---

### Как бы я это исправил?

Я разделю сущность (данные и правила) и процесс сохранения (инфраструктуру).

#### 1. Чистая Доменная Сущность (Domain Layer)
Она становится максимально простой, "глупой" относительно базы данных и "умной" относительно своих правил.

```php
#[ORM\Entity]
class User
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private int $id;

    #[ORM\Column(unique: true)]
    private string $email;

    public function __construct(string $email)
    {
        $this->validateEmail($email);
        $this->email = $email;
    }

    public function changeEmail(string $newEmail): void
    {
        $this->validateEmail($newEmail);
        $this->email = $newEmail;
    }

    public function email(): string
    {
        return $this->email;
    }

    private function validateEmail(string $email): void
    {
        if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException("Invalid email format");
        }
    }
}
```

#### 2. Применение в Application Layer (Use Case)
Теперь управление жизненным циклом и сохранением берет на себя сервис (или Command Handler).

```php
class ChangeEmailService
{
    public function __construct(
        private UserRepositoryInterface $repository, // Интерфейс, а не конкретная реализация
        private EntityManagerInterface $em
    ) {}

    public function execute(int $userId, string $newEmail): void
    {
        // 1. Загружаем объект
        $user = $this->repository->find($userId);
        if (!$user) {
            throw new UserNotFoundException($userId);
        }

        // 2. Выполняем бизнес-логику (сущность сама проверяет валидность)
        $user->changeEmail($newEmail);

        // 3. Сохраняем изменения (Unit of Work управляет транзакцией)
        $this->em->flush(); 
    }
}
```

### Итог изменений:
1.  **Сущность стала чистой:** Она больше не зависит от `EntityManager`. Ее легко тестировать: `new User('test@test.com')->changeEmail('new@test.com');` — и всё.
2.  **Управление транзакциями:** Теперь `flush()` вызывается один раз в конце бизнес-операции. Мы гарантируем атомарность.
3.  **Соблюдение границ:** Домен отвечает за **что** (правила), Приложение — за **когда** (оркестрация), Инфраструктура — за **как** (сохранение в БД).

## Q29 · Процесс и рассуждение

**Интервьюер:** Тебе нужно решить техническую проблему на незнакомых тебе технологии или стеке. Опиши последовательность своих действий от первого взгляда на задачу до уверенного ответа о сроках решения. Когда, по-твоему, нужно просить помощи у команды, а когда разбираться самому?

**Кандидат:**

Работа с неизвестным стеком — это проверка не столько знаний, сколько **методологии мышления**. Мой подход строится на минимизации неопределенности и управлении рисками.

### 1. Алгоритм работы над неизвестной задачей

Я делю процесс на четыре четких этапа:

#### Этап 1: Исследование и "Разведка" (Exploration)
Вместо того чтобы сразу писать код, я пытаюсь понять «ландшафт».
*   **Понимание контекста:** Я изучаю документацию, архитектурные схемы и существующий код в этом модуле. Моя цель — понять, как эта технология встроена в наш проект.
*   **Создание "Песочницы" (Proof of Concept):** Я создаю максимально маленький, изолированный пример (tiny app или скрипт), который воспроизводит проблему или реализует минимальный функционал. Это позволяет мне прощупать API технологии, не боясь сломать основной проект.
*   **Поиск аналогов:** Я ищу, как подобные задачи решались в других частях нашего проекта или в открытом сообществе (StackOverflow, GitHub Issues, официальные дискуссии).

#### Этап 2: Формирование гипотезы и Проверка (Spike)
Если задача сложная, я выделяю время на так называемый **Spike** — исследовательскую задачу.
*   Я формулирую гипотезу: *"Если я применю паттерн X с использованием библиотеки Y, то получу результат Z"*.
*   Я пробую реализовать этот прототип. Если он работает — я перехожу к основной задаче. Если нет — я понимаю, что этот путь тупиковый, и у меня есть данные для изменения плана.

#### Этап 3: Оценка и Проектирование (Estimation)
Только после того, как я "потрогал" технологию руками, я готов давать сроки.
*   Я не называю одну цифру. Я называю **диапазон** (например, от 3 до 5 дней) и аргументирую его.
*   Я декомпозирую задачу на мелкие подзадачи. Если подзадача звучит как *"Разобраться, как работает эта библиотека"*, я выделяю её как отдельный риск.

#### Этап 4: Реализация и Тестирование
Переход к написанию основного кода с учетом полученного опыта.

---

**Что я включаю в ответ о сроках:**
Я никогда не говорю "сделаю к среде". Я говорю: *"Я оцениваю задачу в 3 дня. Один день уйдет на исследование интеграции с X, один день на реализацию и один день на покрытие тестами и стабилизацию. Если на этапе исследования я столкнусь с проблемой Y, срок может вырасти еще на 1 день"*. Это честная оценка рисков.

---

### 2. Когда разбираться самому, а когда просить помощи?

Это вопрос **экономической целесообразности** (Cost of Delay).

#### Когда разбираться самому (Deep Dive):
*   Если проблема касается **фундаментальных основ** (как работает этот язык/фреймворк). Это инвестиция в мой рост и в проект.
*   Если задача **не срочная** и имеет низкий приоритет.
*   Если я чувствую, что "нахожусь в тупике", но у меня есть четкий план, как выйти из него (нужно просто еще немного времени на поиск в документации).

#### Когда просить помощи (Escalation):
*   **Правило "Золотого часа":** Если я бьюсь над одной и той же проблемой больше 1-2 часов без малейшего прогресса (даже в понимании причины) — я иду к команде. Нельзя тратить день на то, что коллега объяснит за 5 минут.
*   **Блокирующие факторы:** Если решение задачи требует прав доступа, которые у меня есть, или знаний о внутреннем бизнес-процессе, которые есть только у эксперта.
*   **Риск для проекта:** Если я понимаю, что мое решение может быть архитектурно неверным или нарушать стандарты проекта, я иду за ревью **до** того, как потрачу много времени на реализацию.

**Моя философия:** 
*   *Разбираться самому* — чтобы расти как инженер.
*   *Просить помощи* — чтобы быть эффективным сотрудником. 
**Плохой разработчик сидит и молчит, пока дедлайн не сгорает. Хороший разработчик сигнализирует о проблеме вовремя.**

## Q30 · Процесс и рассуждение

**Интервьюер:** Ты пообещал сделать задачу к завтрашнему дню, но по ходу работы понял, что это два дня работы. Что делаешь?

**Кандидат:**

Это критический момент, который проверяет не только технические навыки, но и **профессиональную зрелость (Ownership)**. Самая большая ошибка здесь — надеяться на чудо, работать всю ночь и прийти завтра с полуфабрикатом или, что еще хуже, с неработающим кодом.

Мой алгоритм действий в такой ситуации:

### 1. Немедленная коммуникация (Stop the Lie)
Как только я осознал масштаб проблемы — я сообщаю об этом. **Чем раньше я сообщу, тем меньше ущерб для проекта.** Я не жду завтрашнего утра или конца рабочего дня.

### 2. Анализ и подготовка аргументации
Я не прихожу с фразой «я не успеваю». Я прихожу с **анализом причин и планом решения**. Я должен четко понимать:
*   **Почему возникла задержка?** (Например: «Я столкнулся с непредвиденной сложностью в интеграции с API, которую не смог оценить на этапе планирования» или «В процессе реализации выяснилось, что архитектура требует рефакторинга старого модуля, чтобы избежать багов»).
*   **Что уже сделано?** (Показать прогресс, чтобы команда видела, что работа идет).
*   **Какой новый срок?** (Конкретная дата и время).

### 3. Предложение вариантов (Negotiation)
Я не просто ставлю перед менеджером перед фактом, я предлагаю варианты решения проблемы, чтобы он мог принять бизнес-решение.

**Варианты, которые я предложу:**

*   **Вариант А: "Сдвинуть дедлайн".** «Если нам важно сделать задачу идеально и покрыть её тестами, мне нужно еще один день. Новая дата — послезавтра».
*   **Вариант Б: "Декомпозиция (MVP)".** «Если нам критично выкатить что-то завтра, я могу сделать базовую функциональность (без сложной фильтрации), но это будет работать в ограниченном режиме. Полную версию я доделаю вторым этапом».
*   **Вариант В: "Помощь команды".** «Если задача должна быть готова завтра любой ценой, мне нужна помощь коллеги на пару часов, чтобы вместе разобраться с этим сложным модулем».

---

### Пример того, как это выглядит на практике (в Slack/личном разговоре):

> «Привет, [Имя Менеджера]! По задаче с поиском заказов возник нюанс.

2.  **Я помогаю бизнесу принимать решения.** Менеджер может решить, что "медленный поиск — это не страшно, катите завтра", и это будет его осознанный выбор, а не моя неудача.
3.  **Я демонстрирую ответственность.** Я не просто "не успел", я понимаю причины, вижу последствия и предлагаю пути выхода.

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

Это один из самых сложных вопросов в инженерии, потомуный разрыв между «идеальным миром» и «реальным бизнесом». Мой подход базируется на понимании того, что **код — это не самоцель, а инструмент для извлечения прибыли**.

Я использую концепцию **«Достаточной чистоты» (Good Enough Software)**, балансируя между тремя факторами: **Бизнес-ценность**, **Технический долг** и **Стоимость поддержки**.

---

### 1. Когда код «достаточно хорош» (Definition of Done)

Я считаю задачу выполненной и готовой к релизу, если она соответствует критериям **Definition of Done (DoD)**:

*   **Функциональность:** Все Acceptance Criteria (критерии приемки) выполнены. Пользователь получает именно то, что просил бизнес.
*   **Надежность:** Написаны Unit и интеграционные тесты, покрывающие основные сценарии (включая негативные). Код не падает при неверных входных данных.
*   **Безопасность:** Нет очевидных дыр (SQLi, XSS, отсутствие проверки прав доступа).
*   **Читаемость:** Код понятен любому члену команды. Если я вернусь к нему через 3 месяца, я пойму, что он делает.
*   **Предсказуемость:** Код не вносит неявных побочных эффектов в другие части системы.

**Если эти пункты соблюдены — код готов к продакшену. Дальнейшее "полирование" архитектуры без изменения функционала — это раздувание сроков (Gold Plating).**

---

###  boy 2. Когда стоит продолжать улучшать (Refactoring)

Я продолжаю улучшать код только в двух случаях:

1.  **Предотвращение деградации (Boy Scout Rule):** Если я в процессе выполнения задачи вижу небольшой, локальный беспорядок (плохое имя переменной, лишний `if`), который исправляется за 5 минут — я исправляю его сразу. Это правило «оставь место стоянки чуть чище, чем оно было до тебя».
2.  **Борьба с архитектурным долгом:** Если я вижу, что текущая реализация создает серьезные препятствия для будущих задач (например, жесткая связность, которая заблокирует внедрение новой фичи), я выношу это в отдельную задачу (Technical Debt Ticket) и планирую её в бэклог.

---

### 3. Как я соблюдаю баланс (Стратегия)

Чтобы не превратиться в "вечного рефакторинга" и не стать "грязным кодером", я использую следующие принципы:

#### А) Оценка стоимости (Cost of Change)
Перед тем как начать глубокий рефакторинг, я спрашиваю себя: *"Сколько времени я потрачу на это сейчас и сколько времени я сэкономлю в будущем?"*.
*   Если рефакторинг займет 3 дня, а сэкономит 10 минут работы раз в месяц — **я его не делаю**.
*   Если рефакторинг займет 2 дня, но позволит нам внедрять новые фичи в два раза быстрее в следующем квартале — **я его инициирую**.

#### Б) Технический долг как осознанный выбор
Я отношусь к техдолгу не как к греху, а как к **кредиту**.
*   **Целенаправленный долг:** Мы сознательно пишем "быстрый и грязный" код, чтобы проверить гипотезу (MVP) или успеть к релизу. Это нормально, если мы зафиксировали это и запланировали "возврат кредита" (рефакторинг) сразу после запуска.
*   **Неосознанный долг:** Это когда мы пишем плохо, потому потому что не знаем, как правильно. Это я пытаюсь минимизировать через Code Review и обучение.
