## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

Для написания чистого и надёжного кода я выделяю три ключевых направления: **строгая типизация** (снижение количества runtime-ошибок), **лаконичность синтаксиса** (уменьшение визуального шума) и **улучшенная работа с объектами** (безопасность данных).

Вот самые важные возможности с примерами:

### 1. Constructor Property Promotion (PHP 8.0)
Это, пожалуй, самое заметное изменение для чистоты кода. Оно избавляет от огромного количества шаблонного кода (boilerplate) при объявлении свойств и их инициализации в конструкторе.

**До PHP 8.0:**
```php
class UserService {
    private UserRepository $repository;
    private LoggerInterface $logger;

    public function __construct(UserRepository $repository, LoggerInterface $logger) {
        $this->repository = $repository;
        $this->logger = $logger;
    }
}
```

**В PHP 8.0+:**
```php
class UserService {
    // Свойства объявляются, типизируются и инициализируются одной строкой
    public function __construct(
        private UserRepository $repository,
        private LoggerInterface $logger,
    ) {}
}
```

### 2. Readonly Properties (PHP 8.1)
Это критически важная фича для реализации **Value Objects** и обеспечения иммутабельности (неизменяемости) объектов. Если объект не должен меняться после создания, `readonly` гарантирует это на уровне языка.

```php
readonly class Money {
    public function __construct(
        public int $amount,
        public string $currency,
    ) {}
}

$price = new Money(100, 'USD');
// $price->amount = 200; // Fatal Error: Cannot modify readonly property
```
Это делает код предсказуемым: вы точно знаете, что состояние объекта не будет изменено где-то в недрах сервиса.

### 3. Union Types & Intersection Types (PHP 8.0 / 8.1)
Эти возможности позволяют делать сигнатуры методов максимально точными, что заменяет громоздкие проверки `is_a()` или `instanceof` внутри функций.

*   **Union Types (8.0):** Объект может быть одного из нескольких типов.
*   **Intersection Types (8.1):** Объект **обязан** реализовывать сразу несколько интерфейсов.

```php
// Union Types: параметр может быть либо строкой, либо int
public function processId(string|int $id): void { ... }

// Intersection Types: объект должен быть и Logger, и конкретным классом (очень полезно для DI)
public function configure(LoggerInterface&Configurable $service): void { ... }
```

### 4. Match Expression (PHP 8.0)
В отличие от `switch`, `match` является выражением (expression), то есть возвращает значение, и использует строгое сравнение (`===`). Это снижает риск логических ошибок, связанных с приведением типов.

**До PHP 8.0 (switch):**
```php
switch ($status) {
    case 200:
        $message = 'OK';
        break;
    case 404:
        $message = 'Not Found';
        break;
    default:
        $message = 'Unknown';
}
```

**В PHP 8.0+ (match):**
```php
$message = match ($status) {
    200 => 'OK',
    404 => 'Not Found',
    default => 'Unknown',
};
```
Код стал короче, его легче читать, и он исключает проблему «забытого break».

### Резюме
Если суммировать, то **Constructor Promotion** и **Match** делают код чище (меньше визуального мусора), а **Readonly** и **Strict Typing (Union/Intersection)** делают его надёжнее, позволяя ловить ошибки на этапе написания кода или выполнения, а не в продакшене.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

Система типов в PHP — это гибридная модель. По умолчанию она работает в режиме **weak typing** (слабая типизация) с неявным приведением типов, но современные возможности позволяют перевести её в режим **strict typing** (строгая типизация).

### 1. Что даёт `declare(strict_types=1);`

По умолчанию PHP пытается быть «полезным» и приводит типы так, чтобы код не упал. Если вы передадите строку `"10"` туда, где ожидается `int`, PHP тихо преобразует её в `10`.

Инструкция `declare(strict_types=1);` меняет поведение **в пределах того файла, где она объявлена**. Она заставляет PHP выбрасывать `TypeError`, если тип переданного аргумента не совпадает с объявленным (без попыток автоматического приведения).

**Важный нюанс:** `strict_types` влияет на то, как вызывается функция, а не на то, как она работает внутри. Если файл `A.php` вызывает функцию из `B.php`, то правила строгости будут определяться в файле `A.php`.

---

### 2. Приведения типов и ловушки

#### Ловушка №1: Неявное приведение (Weak Typing)
Без `strict_types` PHP делает «магию», которая часто ведет к трудноуловимым багам.

```php
declare(strict_types=0); // По умолчанию

function add(int $a, int $b): int {
    return $a + $b;
}

echo add(5, "10"); // Выведет 15. PHP тихо превратил строку в число.
echo add(5, "10 apples"); // Выведет 15 (в старых версиях) или ошибку, но поведение непредсказуемо.
```

#### Ловушка №2: Проблема с `null`
До PHP 8.0, если тип был указан как `int`, передача `null` вызывала ошибку. Теперь появились **Nullable types** (`?int`), но часто разработчики забывают об этом, и типизация «взрывается» в рантайме.

#### Ловушка №3: Сравнение через `==` vs `===`
Это классика. Слабая типизация при сравнении может привести к абсурдным результатам.

```php
echo 0 == "false"; // true (потому что строка "false" при приведении к числу в контексте сравнения может вести себя странно, или 0 == "" это true)
echo 0 == "0";     // true
echo 0 === "0";    // false (правильное поведение)
```

---

### 3. Примеры: где типизация спасает и где удивляет

#### Где типизация спасает (Fail Fast)
Представьте, что из API приходят данные. Без строгой типизации ошибка «просочится» глубоко в бизнес-логику.

```php
declare(strict_types=1);

class Order {
    public function __construct(
        public int $amount,
        public string $currency
    ) {}
}

function processOrder(Order $order): void {
    // Если бы мы передали объект с ошибкой в данных, 
    // strict_types поймал бы несоответствие типов на входе.
}

// Ошибка подсветится сразу при вызове, а не когда мы попытаемся 
// сделать математическую операцию с неправильным типом внутри метода.
```

#### Где типизация удивляет (Edge Cases)
Самый частый случай «удивления» — это работа с `bool` и `int` при слабой типизации, а также нюансы с `float`.

```php
declare(strict_types=0);

function check(int $value): void {
    echo "Value is: $value\n";
}

check(true);  // Выведет "Value is: 1" (Булево true стало int 1)
check(false); // Выведет "Value is: 0" (Булево false стало int 0)

// Еще один пример: сравнение строк и чисел
$id = "123";
$expected = 123;

if ($id == $expected) {
    echo "Match!"; // Сработает, хотя типы разные. Это может скрыть ошибку, 
                   // если мы ожидали, что ID — это всегда строковый UUID.
}
```

### Мой подход как разработчика:
1.  **Всегда** использовать `declare(strict_types=1);` во всех файлах проекта.
2.  **Использовать Scalar Type Hints** (int, string, bool, float) везде, где это возможно.
3.  **Использовать Return Types**: это гарантирует, что метод не вернет «что-то не то», что сломает цепочку вызовов.
4.  **Использовать Value Objects**: вместо того чтобы передавать `string $email`, я создам класс `Email`, что даст еще один уровень типизации на уровне доменной модели.
5.  **Доверять только `===`**: полное исключение нестрогого сравнения в коде.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

Проектирование обработки исключений — это вопрос не только «как поймать ошибку», но и того, как передать информацию о ней, не нарушая инкапсуляцию и не превращая логику в «спагетти» из `try-catch`.

Мой подход строится на трех принципах: **предсказуемость**, **информативность** и **сохранение контекста**.

### 1. Иерархия исключений
Я никогда не использую базовый `\Exception` для бизнес-логики. Вместо этого я строю иерархию, разделяя технические ошибки и ошибки предметной области.

*   **Domain Exceptions (Бизнес-логика):** Наследуются от моего базового `DomainException`. Они описывают ситуации, которые являются частью бизнес-процесса (например, `InsufficientFundsException`, `UserAlreadyExistsException`). Эти ошибки **ожидаемы** в рамках бизнес-логики, и их можно (и нужно) обрабатывать.
*   **Infrastructure Exceptions (Технические):** Наследуются от `InfrastructureException`. Это проблемы внешнего мира: `DatabaseConnectionException`, `ExternalApiTimeoutException`. Они обычно не обрабатываются на уровне домена, а всплывают выше к уровню приложения или контроллеров.

**Пример структуры:**
```php
// Базовый класс для всех моих исключений
abstract class AppException extends \Exception {}

// Бизнес-слой
class DomainException extends AppException {}
class InsufficientFundsException extends DomainException {}

// Инфраструктурный слой
class InfrastructureException extends AppException {}
class RepositoryException extends InfrastructureException {}
```

### 2. Оборачивание (Exception Wrapping)
Это критически важный момент для соблюдения слоев архитектуры. Если мой репозиторий (Infrastructure) выбрасывает `PDOException`, я **не должен** пробрасывать его в сервис (Domain). Это нарушит инкапсуляцию: сервис внезапно узнает о том, что мы используем PostgreSQL.

**Правило:** Оборачиваем низкоуровневое исключение в высокоуровневое, сохраняя оригинал.

```php
public function findUser(int $id): User 
{
    try {
        return $this->db->query("..."); 
    } catch (\PDOException $e) {
        // Мы оборачиваем техническую ошибку в нашу инфраструктурную,
        // передавая $e третьим аргументом (previous), чтобы не потерять stack trace.
        throw new RepositoryException("Failed to fetch user by ID: $id", 0, $e);
    }
}
```
Это позволяет вызывающему коду реагировать на `RepositoryException`, не заботясь о том, какая именно БД используется.

### 3. Контракт метода
Контракт метода — это не только типы аргументов и возвращаемого значения, но и **список исключений, которые метод может выбросить**.

*   Если метод выбрасывает `DomainException`, это часть контракта. Вызывающий код *должен* знать, что это может случиться, и решить, как на это реагировать (например, показать пользователю сообщение об ошибке).
*   Если метод выбрасывает `RuntimeException` или системные ошибки (типа `DivisionByZeroError`), это нарушение контракта или критический сбой, который мы не планируем обрабатывать локально.

В хорошей документации (или PHPDoc) я всегда указываю `@throws`.

---

### 4. Антипаттерны

1.  **"Catch-and-Forget" (Поймал и забыл):**
    ```php
    try {
        $this->doSomething();
    } catch (\Exception $e) {
        // Пусто или просто log::error
    }
    ```
    Это самый опасный антипаттерн. Приложение продолжает работать в неопределенном состоянии, что ведет к повреждению данных. Если вы поймали ошибку — вы должны либо исправить её, либо пробросить выше, либо корректно завершить процесс.

2.  **Использование исключений для управления потоком (Flow Control):**
    Использование `try-catch` для проверки условий (например, `if ($user === null) throw new UserNotFound()`, а затем поимка этого в каждом методе). Исключения — это **дорогая** операция. Для логики, которая происходит постоянно (например, проверка прав доступа), лучше использовать обычные `if/else` или возвращать специальные объекты (например, `Result` объект).

3.  **Слишком широкие `catch` блоки:**
    ```php
    try {
        // код
    } catch (\Throwable $e) { // Ловим вообще всё, включая ошибки синтаксиса или памяти
        // ...
    }
    ```
    Это маскирует реальные баги. Нужно ловить только те исключения, которые вы действительно можете обработать.

4.  **Потеря контекста (Lost Stack Trace):**
    Когда разработчик делает `throw new MyException($e->getMessage())` вместо `throw new MyException("message", 0, $e)`. В итоге при отладке вы видите только новое исключение, а первопричина (root cause) теряется.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

По моему опыту, чаще всего в реальных проектах нарушается принцип **SRP (Single Responsibility Principle — Принцип единственной ответственности)**.

### Почему это происходит?
Разработчики часто стремятся к «удобству» на текущем этапе. Проще написать один метод или один класс, который делает всё сразу: проверяет валидность данных, сохраняет их в базу, отправляет email-уведомление и логирует результат. Это кажется быстрым, но со временем такой класс превращается в «Божественный объект» (God Object), который невозможно тестировать, сложно изменять и страшно трогать.

---

### Типовой пример нарушения (SRP)

Представьте класс `OrderService`. Он кажется логичным, но по факту он делает слишком много вещей.

```php
class OrderService 
{
    public function placeOrder(array $data): void 
    {
        // 1. Валидация (Бизнес-логика/Правила)
        if (empty($data['items']) || $data['total'] <= 0) {
            throw new \InvalidArgumentException("Invalid order data");
        }

        // 2. Работа с БД (Инфраструктура)
        // Представим, что здесь прямой вызов PDO или EntityManager
        $this->db->query("INSERT INTO orders ..."); 

        // 3. Отправка уведомления (Внешний сервис)
        // Прямая зависимость от Mailer
        $this->mailer->send("Order placed: " . $data['id']);

        // 4. Логирование (Инфраструктура)
        $this->logger->info("Order created");
    }
}
```

**Проблемы этого кода:**
1.  **Сложность тестирования:** Чтобы протестировать создание заказа, вам нужно замокать БД, Mailer и Logger.
2.  **Хрупкость:** Если изменится способ отправки уведомлений (например, перейдем на SMS), нам придется менять класс `OrderService`.
3.  **Дублирование:** Если другому сервису понадобится валидация заказа, она заперта внутри `OrderService`.

---

### Рефакторинг (Соблюдение SRP и внедрение DI)

Мы разделяем ответственности между специализированными объектами. `OrderService` теперь только **оркестрирует** процесс.

```php
// 1. Отдельный сервис для валидации (или используем Value Objects)
class OrderValidator {
    public function validate(array $data): void {
        if (empty($data['items']) || $data['total'] <= 0) {
            throw new \InvalidArgumentException("Invalid order data");
        }
    }
}

// 2. Репозиторий для работы с БД
class OrderRepository {
    public function save(Order $order): void {
        // Логика сохранения
    }
}

// 3. Сервис уведомлений (интерфейс для гибкости)
interface NotificationServiceInterface {
    public function notifyOrderPlaced(Order $order): void;
}

// 4. Итоговый OrderService
class OrderService 
{
    public function __construct(
        private OrderValidator $validator,
        private OrderRepository $repository,
        private NotificationServiceInterface $notifier,
        private LoggerInterface $logger // Стандартный интерфейс PSR-3
    ) {}

    public function placeOrder(array $data): void 
    {
        // Оркестрация: вызываем специализированные компоненты
        $this->validator->validate($data);
        
        $order = Order::fromArray($data); // Создаем сущность (Domain Model)
        
        $this->repository->save($order);
        
        $this->notifier->notifyOrderPlaced($order);
        
        $this->logger->info("Order processed successfully");
    }
}
```

### Что изменилось?

1.  **Single Responsibility:** `OrderService` теперь отвечает только за *процесс* размещения заказа. Он не знает, как данные сохраняются в базу или как улетает email.
2.  **Тестируемость:** Теперь я могу написать Unit-тест для `OrderService`, подставив моки для интерфейсов. Я могу протестировать `OrderValidator` отдельно, не создавая заказов в базе.
3.  **Гибкость (Open/Closed Principle):** Если мы захотим отправлять уведомления через Telegram, мы просто создадим `TelegramNotificationService`, реализующий `NotificationServiceInterface`, и передадим его в конструктор. **Сам `OrderService` менять не придется.**
4.  **Читаемость:** Код стал декларативным. Глядя на метод `placeOrder`, я сразу вижу высокоуровневые шаги бизнес-процесса, не отвлекаясь на детали реализации.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Короткий ответ: **Да, можно.** 

В инженерной практике существует понятие **YAGNI** (*You Ain't Gonna Need It* — вам это не понадобится) и баланс между «чистотой кода» и «стоимостью разработки». SOLID — это не религиозный догмат, а инструмент управления сложностью. Если вы будете применять его фанатично к каждой строчке кода, вы превратите разработку в бесконечное проектирование абстракций, которые никогда не будут использованы.

### Когда нарушение оправдано?

Нарушение оправдано в трех основных случаях:

1.  **Прототипирование и MVP (Proof of Concept):** Когда главная цель — проверить жизнеспособность идеи. Здесь скорость важнее архитектуры. Если гипотеза не подтвердится, код будет выброшен, и инвестиции в идеальную архитектуру будут потрачены впустую.
2.  **Малые скрипты и утилиты:** Если вам нужно написать скрипт на 50 строк для миграции данных из одной таблицы в другую, который запустится один раз и умрет, внедрение интерфейсов, репозиториев и DTO — это «архитектурный оверкилл».
3.  **Жесткие ограничения по времени/бюджету:** Когда бизнес требует фичу «вчера», и цена идеального кода выше, чем цена технического долга, который можно будет выплатить позже.

---

### Пример оправданного нарушения: "The Quick Script"

Представьте задачу: написать консольную команду для разового импорта данных из CSV-файла в базу данных для исправления ошибки в данных.

**Вариант "По SOLID" (Overengineering):**
Вы создаете `CsvReaderInterface`, `CsvReaderImplementation`, `DataMapperInterface`, `UserMapper`, `UserEntity`, `UserRepositoryInterface`, `UserRepositoryImplementation`, `ImportOrchestrator`...
*   **Результат:** Вы потратили 2 дня на написание 10 классов для задачи, которая решается простым циклом.

**Вариант "Оправданное нарушение" (Pragmatic approach):**
Вы пишете один класс `ImportCommand`, который напрямую использует `PDO` и `fgetcsv`.

```php
class ImportCommand extends Command 
{
    protected function execute(InputInterface $input, OutputInterface $output): int 
    {
        $handle = fopen('data.csv', 'r');
        $pdo = $this->getDbConnection(); // Прямое использование БД

        while (($data = fgetcsv($handle)) !== false) {
            // Прямой SQL-запрос без репозитория и сущностей
            $pdo->prepare("UPDATE users SET email = ? WHERE id = ?")
                ->execute([$data[1], $data[0]]);
        }

        fclose($handle);
        return Command::SUCCESS;
    }
}
```

**Почему это оправдано?**
*   **Цель достигнута:** Задача решена за 15 минут.
*   **Риски минимальны:** Этот код не станет частью ядра системы, он не будет расширяться.
*   **Стоимость владения:** Технический долг здесь практически равен нулю, так как код не будет поддерживаться долго.

### Золотое правило
Нарушайте принципы SOLID только тогда, когда **стоимость написания чистого кода превышает выгоду от его поддержки**. 

Если вы понимаете, что нарушаете принцип (например, создаете «толстый» класс), вы должны зафиксировать это как **технический долг** и иметь план, как вы его вернете, когда код начнет расти. Как говорят опытные архитекторы: *"Сначала сделай это так, чтобы работало, а потом сделай это так, чтобы это было красиво"*.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Вы абсолютно правы. Наследование часто является «ловушкой» реализации OCP, так как оно создает жесткую связь между родителем и потомком (нарушая при этом принцип композиции над наследованием).

В современном объектно-ориентированном программировании (особенно в PHP) существует три основных альтернативных способа реализации **Open/Closed Principle**:

### 1. Композиция и паттерн «Стратегия» (Strategy)
Это самый распространенный способ. Вместо того чтобы расширять класс через наследование, мы передаем ему объект, который реализует нужный интерфейс. Класс остается «закрытым» для изменений, но «открыт» для новых алгоритмов через внедрение новых стратегий.

**Пример:**
Вместо создания `FastOrderService` и `SlowOrderService` через наследование, мы создаем один `OrderService`, который принимает объект `ShippingStrategy`.

```php
interface ShippingStrategy {
    public function calculate(float $weight): float;
}

class FastShipping implements ShippingStrategy {
    public function calculate(float $weight): float { return $weight * 1.5; }
}

class StandardShipping implements ShippingStrategy {
    public function calculate(float $weight): float { return $weight * 1.0; }
}

class OrderService {
    public function __construct(private ShippingStrategy $shippingStrategy) {}

    public function process(float $weight): void {
        $cost = $this->shippingStrategy->calculate($weight);
        // ... логика обработки
    }
}
```
*Чтобы добавить новый тип доставки, нам не нужно менять `OrderService`, мы просто создаем новый класс стратегии.*

### 2. Паттерн «Декоратор» (Decorator)
Декоратор позволяет динамически добавлять объекту новую функциональность, не изменяя его код и не используя наследование. Мы «оборачиваем» базовый объект в новый, который расширяет его поведение.

**Пример:**
Допустим, у нас есть сервис отправки сообщений. Мы хотим добавить логирование, не меняя сам сервис.

```php
interface Messenger {
    public function send(string $msg): void;
}

class SimpleMessenger implements Messenger {
    public function send(string $msg): void {
        echo "Sending: $msg\n";
    }
}

// Декоратор
class LoggingMessengerDecorator implements Messenger {
    public function __construct(private Messenger $wrapped) {}

    public function send(string $msg): void {
        echo "Log: Before sending\n";
        $this->wrapped->send($msg); // Вызов оригинального метода
        echo "Log: After sending\n";
    }
}

// Использование:
$messenger = new LoggingMessengerDecorator(new SimpleMessenger());
$messenger->send("Hello!");
```
*Мы расширили поведение (добавили логирование), не меняя `SimpleMessenger`. Класс закрыт для изменений, но открыт для расширения через декорацию.*

### 3. Использование паттерна «Визитор» (Visitor)
Этот паттерн позволяет добавлять новые операции к существующей структуре объектов, не изменяя сами классы этих объектов. Это особенно полезно, когда у вас есть сложное дерево объектов (например, элементы документа), и вы хотите добавлять к ним разные операции (экспорт в PDF, экспорт в HTML, подсчет суммы).

**Пример (схематично):**
Вместо того чтобы добавлять метод `exportToPdf()` в каждый класс элемента, вы создаете класс `PdfExportVisitor`, который «обходит» все элементы и знает, как каждый из них должен отрисоваться в PDF.

### 4. Dependency Injection & Service Container (Инфраструктурный уровень)
В контексте Symfony/Laravel, OCP часто реализуется через систему **Compiler Passes** или **Tagging**.

Вы можете написать сервис, который собирает все объекты с определенным тегом.
*   **Пример:** Система плагинов. Вы создаете интерфейс `PluginInterface`. Любой новый плагин, добавленный в контейнер с тегом `app.plugin`, автоматически подхватывается вашей системой. Вам **не нужно менять код ядра**, чтобы система начала работать с новым плагином. Вы просто регистрируете новый класс в конфиге или через атрибуты.

### Итог:
| Способ | Суть | Когда использовать |
| :--- | :--- | :--- |
| **Стратегия** | Замена алгоритма внутри объекта | Когда нужно менять *способ* выполнения действия. |
| **Декоратор** | Обертка вокруг объекта | Когда нужно *добавить* поведение (логи, кэш, валидация). |
| **Визитор** | Вынос операции за пределы классов | Когда структура классов стабильна, а операции меняются часто. |
| **DI / Tags** | Регистрация через контейнер | Когда нужно реализовать расширяемую плагинную систему. |

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Нет, это распространенное заблуждение. Хотя в учебниках по ООП SRP чаще всего объясняют на примере классов, **принцип единственной ответственности применим к любому уровню абстракции в разработке**.

Если говорить обобщенно: **любая единица кода должна отвечать за одну концепцию (один аспект сложности).**

Вот где еще необходимо применять SRP:

### 1. Функции и методы (самый важный уровень)
Это то, с чем разработчики сталкиваются чаще всего. Метод должен выполнять одну задачу. Если в методе появляется ключевое слово `and` в его описании (например, *"метод валидирует данные **и** сохраняет их в базу"*), значит, принцип нарушен.

*   **Нарушение:** Метод `registerUser()` делает проверку почты, хеширование пароля, запись в БД и отправку письма.
*   **Соблюдение:** Метод `registerUser()` вызывает `Validator`, `UserRepository` и `EmailService`.

### 2. Модули и пакеты (Packages/Modules)
На уровне архитектуры системы модули (или микросервисы) должны иметь одну зону ответственности.
*   **Нарушение:** Модуль `Billing`, который одновременно управляет пользователями, каталогом товаров и рассылкой новостей.
*   **Соблюдение:** Разделение на `UserModule`, `CatalogModule` и `BillingModule`.

### 3. Микросервисы (Services)
В распределенных системах SRP масштабируется до уровня сервисов. 
*   **Нарушение:** «Монолитный микросервис», который отвечает и за обработку заказов, и за генерацию тяжелых PDF-отчетов, и за поиск по товарам. Если поиск начнет нагружать процессор, упадет и сервис заказов.
*   **Соблюдение:** Выделение `SearchService` и `ReportService` в отдельные сущности.

### 4. Базы данных (Tables/Schemas)
Даже в проектировании БД есть свой SRP. 
*   **Нарушение:** Одна таблица `users`, в которой хранятся и данные профиля, и логи входов, и настройки уведомлений, и история транзакций.
*   **Соблюдение:** Разделение на `users`, `user_profiles`, `user_logs` и `user_settings`.

### 5. Файлы и структура проекта
Даже структура файлов подчиняется SRP.
*   **Нарушение:** Один файл `Utils.php`, в котором лежат и функции для работы со строками, и функции для работы с файловой системой, и функции для работы с датами.
*   **Соблюдение:** `StringHelper.php`, `FileHelper.php`, `DateHelper.php`.

---

### Почему важно понимать это шире, чем просто "классы"?

Потомуed, что **причина изменения (Reason to Change)** — это суть SRP.
*   Если у вас один метод делает три вещи, у него **три разные причины для изменения**.
*   Если у вас один модуль делает три задачи, у него **три разных бизнес-стейкхолдера**, которые могут потребовать правок.

**Резюме:** Когда вы применяете SRP, всегда спрашивайте себя: *"Если эта бизнес-задача изменится, сколько мест в моем коде мне придется переделывать?"*. Если мест много и они относятся к разным сущностям — вы нарушили SRP на каком-то уровне.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

Работа DI-контейнера в Symfony — это многоэтапный процесс, который делится на этап **сборки (build time)** и этап **работы (runtime)**. Это позволяет минимизировать накладные расходы во время выполнения запроса.

### 1. Этап компиляции контейнера (Compile Time)

Symfony не читает ваши YAML/XML файлы при каждом запросе. Вместо этого она «компилирует» их в один огромный, оптимизированный PHP-класс. Этот процесс происходит, когда вы очищаете кэш или устанавливаете приложение.

**Что происходит во время компиляции:**

1.  **Loading:** Контейнер считывает все конфигурационные файлы (`services.yaml`, `packages/*.yaml`, атрибуты классов). Создается «сырое» дерево определений сервисов (`Definition` объектов).
2.  **Dependency Resolution:** Контейнер анализирует связи. Он строит граф зависимостей: какой сервис какой требует.
3.  **Compiler Passes (Самый важный этап):** Это «плагины» для самого процесса компиляции. Symfony запускает множество проходов, чтобы оптимизировать контейнер:
    *   **Autowiring Pass:** Анализирует типы аргументов в конструкторах и связывает их с существующими сервисами.
    *   **Definition Optimization:** Если сервис не имеет зависимостей или является приватным, контейнер оптимизирует его создание.
    *   **Removal of unused services:** Если сервис помечен как `public: false` и не используется никем другим, он удаляется из финального контейнера.
    *   **Service Decoration:** Если вы используете декораторы, именно здесь происходит «обертывание» одного сервиса в другой.
4.  **Dump:** Результат — сгенерированный PHP-файл (обычно в `var/cache/.../App_KernelDevDebugContainer.php`). Это плоский массив инструкций по созданию объектов.

---

### 2. Как работает Autowiring

Autowwiring — это не «магия», а результат работы **Compiler Pass** во время компиляции.

Когда вы пишете в конструкторе `private UserRepository $repository`, Symfony делает следующее:
1.  Смотрит на **Reflection API** вашего класса, чтобы узнать тип аргумента (`UserRepository`).
2.  Ищет в своем внутреннем реестре (Service ID) сервис, который соответствует этому типу.
3.  Если найден один подходящий сервис, Symfony записывает в `Definition` этого класса: *"При создании этого сервиса, передай в первый аргумент вот тот самый объект UserRepository"*.

**Важно:** В рантайме никакой Reflection не происходит. Весь процесс «угадывания» типов уже завершен и записан в сгенерированный PHP-файл в виде жестких инструкций.

---

### 3. Момент запроса сервиса (Runtime)

Когда вы вызываете `$container->get(MyService::class)` (или когда сервис запрашивается через DI в контроллере), происходит следующее:

1.  **Проверка в кэше (Singleton pattern):** Контейнер первым делом проверяет внутренний массив `$services`. Если объект уже был создан ранее в этом же запросе, он просто возвращает его. В Symfony почти все сервисы по умолчанию являются **Shared** (синглтонами в рамках одного процесса/запроса).
2.  **Создание (Instantiating):** Если объекта еще нет:
    *   Контейнер берет «рецепт» из сгенерированного класса.
    *   Он видит список зависимостей для этого сервиса.
    *   Он **рекурсивно** вызывает процесс создания для каждой зависимости.
    *   Используя `new`, он создает объект, передавая в конструктор уже созданные (или создаваемые в этот момент) зависимости.
3.  **Возврат:** Объект сохраняется в массив `$services` для повторного использования и возвращается вызывающему коду.

### Итоговая схема:

*   **Конфигурация (YAML/Attributes)** $\to$ **Compilation (Compiler Passes + Autowiring)** $\to$ **Compiled PHP Class (The Recipe)**.
*   **Runtime:** **Request Service** $\to$ **Check Cache** $\to$ *(если нет)* $\to$ **Recursive Instantiation (using the Recipe)** $\to$ **Return & Cache**.

**Почему это быстро?** Потому что в рантайме Symfony не «думает». Она просто выполняет набор команд `new ServiceA(new ServiceB(new ServiceC()))`, которые были заранее рассчитаны и записаны в PHP-файл.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

Циклические зависимости (Circular Dependencies) — это ситуация, когда `ServiceA` требует `ServiceB`, а `ServiceB` требует `ServiceA`. В Symfony это приводит к ошибке `CircularReferenceException` еще на этапе компиляции контейнера, так как контейнер не может понять, с чего начать создание объектов.

Я подхожу к решению этой проблемы в два этапа: сначала пытаюсь **исправить архитектуру** (так как цикл — это почти всегда признак нарушения SRP), и если это невозможно, использую **инструменты контейнера**.

### 1. Архитектурные решения (Preferred)

Это правильный путь, так как циклы обычно означают, что ваши сервисы слишком много знают друг о друге.

*   **Выделение третьего сервиса (Extracting a third service):**
    Если `A` и `B` зависят друг от друга из-за общей логики, эту логику нужно вынести в новый `ServiceC`. Теперь `A` и `B` зависят от `C`, но не друг от друга.
    *   *Пример:* `OrderService` и `InvoiceService` зависят друг от друга. Выносим общую логику расчетов в `PriceCalculator`.

*   **Разделение интерфейсов (Interface Segregation):**
    Иногда цикл возникает, потому что сервис требует *весь* функционал другого сервиса, хотя ему нужна лишь одна маленькая часть. Если разбить большой сервис на несколько интерфейсов, можно разорвать цикл.

*   **Перенос ответственности (Relocation):**
    Часто один из сервисов в цикле "перегружен". Если перенести метод, вызывающий цикл, из `ServiceA` в `ServiceB` (или наоборот), цикл может исчезнуть сам собой.

---

### 2. Технические решения (Workarounds)

Если архитектурно рефакторинг невозможен (например, при работе с legacy-кодом или очень сложными внешними библиотеками), я использую возможности Symfony.

*   **Ленивая инициализация (Lazy Services):**
    Это самый элегантный технический способ. Вместо того чтобы внедрять реальный объект, Symfony внедряет **Proxy-объект**. Прокси выглядит как ваш сервис, но он не создает реальный объект до тех пор, пока вы не вызовете у него какой-либо метод.

    В Symfony это делается через атрибут `#[Autoconfigure(lazy: true)]` или в конфигурации:
    ```yaml
    services:
        App\Service\ServiceA:
            lazy: true
    ```
    *Как это работает:* Контейнер создает "пустышку". Когда `ServiceB` просит `ServiceA`, контейнер отдает ему прокси. Цикл разрывается, так как реальный `ServiceA` создается только тогда, когда он реально понадобится в работе.

*   **Использование Service Locator (но осторожно!):**
    Вместо внедрения сервиса в конструктор, можно внедрить `ContainerInterface` или `ServiceSubscriberInterface` и запрашивать сервис только в момент вызова метода.
    *   *Внимание:* Это считается антипаттерном (Service Locator), так как скрывает зависимости и делает класс труднотестируемым. Я использую это только в крайнем случае.

*   **Использование Setter Injection вместо Constructor Injection:**
    Если использовать конструктор, цикл блокирует создание обоих объектов. Если использовать сеттеры, мы можем сначала создать `ServiceA`, потом `ServiceB`, а затем вызвать `$serviceA->setServiceB($serviceB)`.
    *   *Минус:* Это делает объект "неполноценным" в момент создания (он может быть в нестабильном состоянии), и это нарушает принцип неизменяемости (immutability).

### Мой алгоритм действий:
1. Попробовать выделить общую логику в **третий сервис**.
2. Если не помогает — применить **Lazy Services** (через прокси).
3. Если это legacy и ничего не помогает — использовать **Setter Injection** или **Service Locator** как временную меру с обязательным комментарием в коде `// TODO: Refactor circular dependency`.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

Для решения этой задачи ключевым является переход от **синхронной** модели выполнения (когда пользователь ждет завершения всех действий) к **асинхронной** (когда пользователь получает ответ сразу, а задачи выполняются в фоне).

В Symfony я бы рассматривал три основных подхода, в зависимости от масштаба проекта и требований к надежности.

---

### 1. Symfony Messenger (Рекомендуемый вариант)

Это стандарт индустрии для Symfony. Мы используем паттерн «Команда» (Command/Message) и «Обработчик» (Handler).

**Как это работает:**
1. В контроллере или сервисе регистрации мы создаем сообщение: `UserRegisteredEvent`.
2. Вмегасто того чтобы вызывать `Mailer` или `SearchIndexer` напрямую, мы отправляем это сообщение в шину (Bus): `$bus->dispatch(new UserRegisteredEvent($userId));`.
3. Конфигурация `messenger.yaml` указывает, что эти сообщения должны уходить в транспорт (например, RabbitMQ, Redis или Amazon SQS), а не обрабатываться сразу.
4. Отдельный процесс (worker) в фоне слушает очередь и выполняет задачи.

**Trade-offs:**
*   **Плюсы:** 
    *   **Высокая скорость ответа:** Пользователь получает `201 Created` мгновенно.
    *   **Отказоустойчивость:** Если почтовый сервис упал, Messenger может автоматически перезапустить задачу (retry strategy) через 5-10 минут.
    *   **Масштабируемость:** Можно запустить 10 воркеров для тяжелых задач (индексация) и 2 для легких (письма).
*   **Минусы:** 
    *   **Сложность инфраструктуры:** Нужно поднимать и поддерживать брокер сообщений (RabbitMQ/Redis).
    *   **Eventual Consistency:** Данные в поиске обновятся не мгновенно, а через долю секунды/минуту.

---

### 2. Использование событий (Event Dispatcher) + Messenger

Чтобы не «засорять» сервис регистрации логикой отправки писем, я бы использовал **Domain Events**.

**Как это работает:**
1. `UserService` выполняет регистрацию и генерирует событие `UserRegistered`.
2. В Symfony создается `EventListener` или `EventSubscriber`, который слушает это событие.
3. Слушатель **не выполняет** работу сам, а лишь перенаправляет задачу в Messenger:
   ```php
   public function onUserRegistered(UserRegistered $event): void {
       $this->messageBus->dispatch(new SendWelcomeEmailMessage($event->getUserId()));
       $this->messageBus->dispatch(new UpdateSearchIndexMessage($event->getUserId()));
   }
   ```

**Trade-offs:**
*   **Плюсы:** Максимальная чистота кода (Separation of Concerns). Сервис регистрации вообще не знает о существовании писем или поиска.
*   **Минусы:** Чуть больше кода (нужно создать и событие, и слушателя, и сообщения, и хендлеры).

---

### 3. "Легкий" вариант: Свой планировщик (Scheduler/Cron)

Если проект маленький и мы не хотим внедрять RabbitMQ.

**Как это работает:**
1. При регистрации мы просто записываем в БД задачу: `outbox_messages` (например, `type: 'send_email', user_id: 1, status: 'pending'`).
2. Раз в минуту запускается консольная команда по Cron, которая выбирает все `pending` задачи и выполняет их.

**Trade-offs:**
*   **Плюсы:** Не нужно стороннего софта (только БД), очень просто реализовать.
*   **Минусы:** 
    *   **Задержка:** Пользователь может ждать письма до минуты (зависит от частоты Cron).
    *   **Плохая масштабируемость:** Если задач станет тысячи, один Cron-скрипт не справится.
    *   **Риск дублей:** Нужно аккуратно обрабатывать статус "в процессе", чтобы два запуска Cron не отправили два письма.

---

### Итоговое сравнение и мой выбор

| Критерий | Messenger + RabbitMQ | Event Dispatcher + Messenger | Cron + DB Outbox |
| :--- | :--- | :--- | :--- |
| **Скорость ответа** | Мгновенно | Мгновенно | Мгновенно |
| **Надежность** | Очень высокая (Retries) | Очень высокая | Средняя |
| **Сложность** | Высокая | Средняя | Низкая |
| **Чистота кода** | Высокая | **Максимальная** | Средняя |

**Мой выбор для продакшн-системы:** 
Комбинация **Domain Events + Symfony Messenger**. 
Это дает идеальный баланс: сервис регистрации остается "чистым" (он просто говорит: "пользователь зарегистрирован"), а система становится гибкой, отказоустойчивой и готовой к любым нагрузкам.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

В Symfony контроль доступа разделяется на два четких этапа: **"Кто ты?" (Authentication)** и **"Что тебе можно?" (Authorization)**.

### 1. Аутентификация (Authentication) — "Кто ты?"
Это процесс идентификации пользователя. В Symfony за это отвечает компонент `Security`.

*   **Authenticators:** Это классы, которые извлекают учетные данные (логин/пароль, токен JWT, сессия) из запроса.
*   **User Provider:** Механизм, который загружает объект `User` из хранилища (база данных, LDAP, API) на основе предоставленных данных.
*   **Firewalls:** Настройки в `security.yaml`, которые определяют, какие части приложения защищены, какие методы аутентификации использовать и как хранить состояние (stateful/stateless).

### 2. Авторизация (Authorization) — "Что тебе можно?"
После того как мы узнали, кто перед нами, мы проверяем его права. В Symfony это работает через два уровня:

#### А) Роли (Roles) — Грубый контроль
Роли — это простые строки (например, `ROLE_USER`, `ROLE_ADMIN`). Они подходят для проверки прав на уровне URL или контроллера через атрибут `#[IsGranted('ROLE_ADMIN')]`.

*   **Как это работает:** Проверка идет по принципу иерархии (Role Hierarchy), которую можно настроить в конфиге. Если у пользователя есть `ROLE_ADMIN`, и в конфиге прописано, что админ включает в себя `ROLE_USER`, то проверка `ROLE_USER` пройдет успешно.

#### Б) Voters (Вотеры) — Тонкий контроль
Voters — это специализированные классы, которые реализуют сложную бизнес-логику проверки доступа. Они реализуют интерфейс `VoterInterface` и имеют метод `vote()`.

**Логика работы Voter:**
Когда вы вызываете `$this->denyAccessUnlessGranted('EDIT', $article)`, Symfony опрашивает все зарегистрированные вотеры:
1.  **supports():** Вотер проверяет: "Умею ли я работать с атрибутом `EDIT` и объектом `Article`?". Если нет — возвращает `false`.
2.  **vote():** Если да, вотер выполняет проверку (например, `return $user === $article->getAuthor();`).
3.  **Результат:** Вотеры возвращают `ACCESS_GRANTED`, `ACCESS_DENIED` или `ACCESS_ABSTAIN`. Итоговое решение принимает Decision Manager (обычно по стратегии "Affirmative" — достаточно одного "Да").

---

### Когда выбирать Roles, а когда Voters?

Это ключевой архитектурный вопрос.

#### Выбирай РОЛИ, если:
*   **Доступ зависит только от статуса пользователя.** (Например: "Только администраторы могут заходить в панель управления").
*   **Правила статичны и глобальны.** (Например: "Все авторизованные пользователи могут смотреть профиль").
*   **Проверка происходит на уровне маршрутов (URL).** Это самый быстрый и дешевый способ отсечь лишних пользователей.

#### Выбирай VOTERS, если:
*   **Доступ зависит от владельца объекта (Ownership).** (Например: "Редактировать статью может только её автор или администратор"). Роли здесь не помогут, так как нам нужно сравнить `ID` пользователя с `author_id` в базе.
*   **Доступ зависит от состояния объекта (State).** (Например: "Заказ можно отменить, только если его статус 'New'").
*   **Доступ зависит от сложной бизнес-логики.** (Например: "Пользователь может скачивать файл, если у него есть подписка, и он не заблокирован, и сегодня рабочий день").
*   **Нужна проверка на уровне доменной модели.** Если логика проверки "прилипает" к сущности (Entity), её место в Voter.

### Резюме (шпаргалка)

| Ситуация | Инструмент | Почему? |
| :--- | :--- | :--- |
| Доступ к `/admin` | **Role** | Простая проверка принадлежности к группе. |
| Редактирование своего профиля | **Voter** | Нужно сравнить `User->getId()` с `Profile->getUserId()`. |
| Удаление комментария | **Voter** | Проверка прав автора + проверка, не забанен ли он. |
| Просмотр ленты новостей | **Role** | Проверка, что пользователь вообще залогинен (`ROLE_USER`). |

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

Это отличный вопрос, который затрагивает разрыв между **Domain Model** (где важна чистота и инкапсуляция) и **Relational Model** (где данные — это плоские колонки в таблице).

В Doctrine по умолчанию нет нативной поддержки Value Objects (VO) как отдельных сущностей, но есть несколько способов "подружить" их.

### 1. Embeddables (Рекомендуемый способ)
Это встроенный механизм Doctrine для маппинга объектов, которые являются частью другой сущности.

**Как это работает:**
Вы помечаете класс VO атрибутом `#[Embeddable]`. В основной сущности вы используете этот VO как свойство. В базе данных поля VO будут "развернуты" в ту же таблицу, где лежит основная сущность.

```php
#[Embeddable]
readonly class Money {
    public function __construct(
        #[Column(type: 'int')]
        public int $amount,
        #[Column(type: 'string', length: 3)]
        public string $currency,
    ) {
        if ($amount < 0) throw new \InvalidArgumentException("Amount cannot be negative");
    }
}

#[Entity]
class Product {
    #[Id, Column, GeneratedValue]
    private int $id;

    #[Embedded(class: Money::class)]
    private Money $price;
}
```

**Плюсы:**
*   **Целостность:** Валидация происходит в конструкторе VO. Невозможно создать "невалидный" объект.
*   **Простота:** Данные хранятся в одной таблице (нет лишних `JOIN`).
*   **Инкапсуляция:** Вы работаете с объектом, а не с набором примитивов.

**Минусы и подводные камни:**
*   **Отсутствие самостоятельности:** Вы не можете запросить `Money` напрямую через Repository. Только через `Product`.
*   **Нюанс с изменениями:** Поскольку VO неизменяемы (`readonly`), при изменении цены вы должны заменить весь объект: `$product->setPrice(new Money(200, 'USD'))`.

---

### 2. Custom Types (Собственные типы данных)
Если ваш VO представляет собой что-то одно (например, `Email` или `Color`), можно создать свой тип данных для Doctrine.

**Как это работает:**
Вы реализуете `Doctrine\DBAL\Types\Type` и переопределяете методы `convertToDatabaseValue` (из объекта в строку/число) и `convertToPHPValue` (из строки/числа в объект).

**Плюсы:**
*   **Прозрачность:** Вы можете использовать `#[Column(type: 'email')]` в любой сущности.
*   **Переиспользование:** Один и тот же тип можно использовать повсеместно.

**Минусы и подводные камни:**
*   **Сложность для составных VO:** Этот метод плохо подходит для объектов с несколькими полями (как `Money`), так как в одной колонке БД может лежать только одно значение (строка или число). Для `Money` пришлось бы сериализовать его в JSON или строку `100_USD`, что убьет возможность делать поиск по сумме через SQL.
*   **Потеря типизации в запросах:** DQL/SQL будет видеть строку, а не объект.

---

### 3. Serializing (JSON/String в колонке)
Хранение VO как сериализованного объекта (JSON) в одной текстовой колонке.

**Плюсы:**
*   **Гибкость:** Можно хранить любые сложные структуры.

**Минусы и подводные камни:**
*   **Ужасный поиск:** Вы не можете написать эффективный SQL-запрос типа `WHERE price_amount > 100`, так как данные лежат внутри JSON-строки.
*   **Нарушение контракта БД:** База данных перестает быть источником истины о структуре данных.

---

### Итоговая стратегия выбора

1.  **Если VO состоит из нескольких полей (Money, Address, Period):**
    Используйте **Embeddables**. Это единственный способ сохранить возможность фильтрации и сортировки по отдельным полям (amount, currency) через SQL, сохраняя при этом объектную модель в PHP.

2.  **Если VO — это "обертка" над одним примитивом (Email, ISBN, PasswordHash):**
    Используйте **Custom Types**. Это сделает код чистым, а маппинг — автоматическим.

3.  **Если VO — это сложный, динамический набор данных (Settings, Metadata):**
    Используйте **JSON column** (через Custom Type или встроенный тип Doctrine), но будьте готовы к ограничениям в поиске.

### Главный совет по неизменяемости (Immutability)
Чтобы гарантировать, что VO всегда валиден, **никогда не делайте сеттеров**. Только конструктор. В PHP 8+ используйте `readonly class`. Это гарантирует, что после того, как объект прошел через "фильтр" конструктора, его состояние не будет испорчено извне.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

Это фундаментальный вопрос проектирования. Основная сложность здесь в том, что **Doctrine — это Unit of Work**, который работает с таблицами, а **DDD — это управление границами агрегатов**, где мы работаем с цельными объектами.

Чтобы агрегат работал правильно, мы должны следовать правилу: **изменения внутри агрегата могут происходить только через корень (Aggregate Root).**

### Пример: Агрегат "Заказ" (Order)
*   **Root:** `Order` (содержит ID, статус, дату, клиента).
*   **Entities (внутри агрегата):** `OrderItem` (товар, количество, цена).
*   **Граница:** Мы не можем изменить количество товара в заказе, не обратившись к самому заказу.

---

### 1. Маппинг коллекций

Для связи Root $\to$ Entities используется `OneToMany` с обязательным использованием `orphanRemoval: true`.

**Почему `orphanRemoval: true` критически важен?**
В DDD, если вы удаляете элемент из коллекции внутри агрегата, этот элемент должен быть удален из базы данных. Без этого параметра Doctrine просто "отвяжет" `OrderItem` от `Order` (установит `order_id = NULL`), но запись останется в таблице как "сирота".

```php
#[Entity]
class Order 
{
    #[Id, Column, GeneratedValue]
    private int $id;

    /** @var Collection<int, OrderItem> */
    #[OneToMany(mappedBy: 'order', targetEntity: OrderItem::class, cascade: ['persist', 'remove'], orphanRemoval: true)]
    private Collection $items;

    public function __construct() {
        $this->items = new ArrayCollection();
    }

    // Важный метод для управления коллекцией
    public function addItem(Product $product, int $quantity): void 
    {
        $item = new OrderItem($this, $product, $quantity);
        $this->items->add($item);
    }

    public function removeItem(OrderItem $item): void 
    {
        $this->items->removeElement($item);
    }
}

#[Entity]
class OrderItem 
{
    #[Id, Column, GeneratedValue]
    private int $id;

    #[ManyToOne(targetEntity: Order::class, inversedBy: 'items')]
    #[JoinColumn(nullable: false)]
    private Order $order;

    // ... другие поля
}
```

### 2. Кто и когда вызывает `flush()`?

Это самый частый вопрос. В чистой архитектуре **Service (Application Layer) управляет транзакцией и жизненным циклом Unit of Work.**

**Правило:** `flush()` вызывается **один раз** в конце завершения сценария использования (Use Case/Application Service).

**Почему так?**
1.  **Атомарность:** Если вы вызовете `flush()` внутри `Order->addItem()`, а потом что-то пойдет не так в другом методе, вы получите частично сохраненные данные.
2.  **Производительность:** Doctrine оптимизирует запросы. Один `flush()` позволяет ей собрать все изменения и отправить их максимально эффективно.

**Пример Application Service:**

```php
class PlaceOrderService 
{
    public function __construct(
        private OrderRepository $repository,
        private EntityManagerInterface $entityManager
    ) {}

    public function execute(int $customerId, array $itemsData): void 
    {
        // 1. Начинаем транзакцию (Implicitly or Explicitly)
        // В Symfony транзакции обычно управляются на уровне EntityManager
        
        $order = new Order($customerId);

        foreach ($itemsData as $data) {
            // Мы взаимодействуем ТОЛЬКО с корнем агрегата
            $order->addItem($data['product'], $data['quantity']);
        }

        // 2. Сохраняем агрегат через репозиторий
        $this->repository->save($order);

        // 3. ЕДИНСТВЕННЫЙ flush в конце сценария
        // Это гарантирует, что либо весь заказ и все позиции сохранятся, либо ничего
        $this->entityManager->flush();
    }
}
```

---

### 3. Границы транзакции

Транзакция должна охватывать **весь сценарий изменения одного агрегата**.

*   **Где начинать?** В Application Service.
*   **Что внутри?** Все действия, которые приводят к изменению состояния системы в рамках одного бизнес-кейса.
*   **Важный нюанс:** Если ваш сценарий затрагивает **два разных агрегата** (например, `Order` и `Inventory`), у вас есть два пути:
    1.  **Strong Consistency (Транзакция на оба агрегата):** Делаем один `flush()` для обоих. Это рискованно, так как увеличивает время блокировки БД.
    2.  **Eventual Consistency (Рекомендуемый путь):** Сначала сохраняем `Order` и фиксируем транзакцию. Затем через `Messenger` отправляем событие `OrderPlaced`, которое в отдельном процессе/транзакции обновит `Inventory`.

### Итоговое резюме:

1.  **Маппинг:** Используем `OneToMany` + `orphanRemoval: true` + `cascade: ['persist']`. Это делает коллекцию "частью" корня.
2.  **Инкапсуляция:** Дочерние сущности (`OrderItem`) не должны иметь публичных методов для изменения их состояния извне агрегата. Все изменения — через `Order::addItem()` или `Order::removeItem()`.
3.  **Flush:** Вызывается **только в Application Service** в самом конце метода. Никогда не вызывайте `flush()` внутри доменных объектов или репозиториев.
4.  **Транзакции:** Один сценарий (Use Case) = одна транзакция (один `flush`). Если нужно затронуть другой агрегат — используйте события и асинхронность.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

Проблема N+1 — это классическая ловушка ORM. Она возникает, когда вы загружаете список объектов (1 запрос), а затем в цикле обращаетесь к их связанным сущностям, что заставляет Doctrine делать по одному дополнительному запросу для каждой записи (N запросов).

Вот мой план действий.

### 1. Диагностика

Прежде чем что-то чинить, нужно подтвердить проблему цифрами.

*   **Symfony Profiler (Первый шаг):** Это самый быстрый способ. Я открываю вкладку **Doctrine** в профилировщике. Там наглядно видно количество запросов, их дублирование и время выполнения. Если я вижу 50 одинаковых запросов `SELECT ... FROM table WHERE id = ?`, это оно.
*   **SQL Log / Debug Bar:** Если я работаю в headless-режиме или API, я смотрю логи SQL (через `doctrine/sql-logger` или логи самого контейнера), чтобы увидеть паттерн повторяющихся запросов.
*   **Инструменты APM (New Relic, Tideways, Blackfire):** В продакшене я использую их. Они показывают "горячие" участки кода и позволяют увидеть, что большая часть времени тратится на ожидание ответов от БД из-за огромного количества мелких запросов.

---

### 2. Способы решения и их Trade-offs

Я выделяю три основных стратегии: **Eager Loading**, **Partial Objects** и **DTO/SQL**.

#### А) Eager Loading (через `JOIN FETCH` в DQL/QueryBuilder)
Это основной способ. Мы говорим Doctrine: "Когда будешь загружать сущность А, сразу подтяни связанные сущности Б одним запросом через `JOIN`".

```php
// Вместо $repo->findAll();
return $this->createQueryBuilder('a')
    ->leftJoin('a.relation', 'r')
    ->addSelect('r') // Ключевой момент: мы выбираем данные из связанной таблицы
    ->getQuery()
    ->getResult();
```

*   **Плюсы:** Решает проблему N+1 за один запрос. Мы получаем полностью инициализированные объекты.
*   **Минусы:** 
    *   **Cartesian Product (Проблема декартова произведения):** Если у вас один `Order` имеет 10 `Items`, и вы делаете `JOIN` для обоих, база вернет 10 строк для одного заказа. Если сущностей много, объем передаваемых данных растет экспоненциально.
    *   **Память:** Doctrine все равно будет строить дерево объектов в памяти.
*   **Когда использовать:** Когда вы знаете, что вам точно понадобятся связанные данные для каждого элемента списка.

#### Б) Использование `Batch Size` (Fetch Mode)
В конфигурации маппинга можно указать `fetch="EXTRA_LAZY"` или настроить размер порции загрузки. Это не совсем решает N+1, но превращает его в "N/batch + 1".

*   **Плюсы:** Помогает, если вы не можете изменить запрос (например, в стороннем коде).
*   **Минусы:** Это "костыль". Количество запросов всё равно остается высоким, и вы не контролируете процесс полностью.
*   **Когда использовать:** Крайний случай, когда архитектура не позволяет переписать QueryBuilder.

#### В) Проекция в DTO (Data Transfer Objects) через QueryBuilder
Вместо того чтобы загружать тяжелые Entity, мы выбираем только те поля, которые нужны для отображения (например, только `id` и `name`).

```php
return $this->createQueryBuilder('a')
    ->select('NEW App\Dto\UserSummaryDto(u.id, u.username, r.name)')
    ->leftJoin('a.role', 'r')
    ->getQuery()
    ->getResult();
```

*   **Плюсы:** 
    *   **Максимальная производительность:** Мы не создаем тяжелые объекты Entity, не тратим память на Identity Map и Unit of Work.
    *   **Минимальный трафик:** Из БД тянутся только нужные колонки.
*   **Минусы:** 
    *   **ReadOnly:** Полученные DTO нельзя изменить и сохранить через `flush()`. Это только для чтения.
    *   **Дублирование кода:** Нужно описывать DTO под каждый конкретный запрос.
*   **Когда использовать:** Идеально для списков, таблиц и API-ответов, где данные только читаются.

#### Г) Чистый SQL (Native Query)
Если запрос слишком сложный для DQL и требует специфических функций БД (Window functions, сложные агрегаты).

*   **Плюсы:** Полный контроль над выполнением.
*   **Минусы:** Потеря абстракции, риск SQL-инъекций (если не использовать параметры), привязка к конкретной СУБД.
*   **Когда использовать:** Для очень тяжелых аналитических отчетов.

---

### Итоговая стратегия моего выбора:

1.  Если нужно **редактировать** объекты $\to$ **Eager Loading** через `leftJoin` + `addSelect`.
2.  Если нужно только **показать список** (Read-only) $\to$ **DTO** через `SELECT NEW ...`. Это самый масштабируемый и быстрый способ для высоконагруженных страниц.
3.  Если запрос **невероятно сложный** $\to$ **Native SQL**.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

Это отличный вопрос, который затрагивает разницу между **бизнес-логикой** (которая может меняться, быть сложной и контекстной) и **гарантиями целостности данных** (которые должны быть незыблемыми).

Короткий ответ: **Код приложения — это "первая линия обороны", а база данных — это "последний рубеж" (last line of defense).**

### Почему нельзя полагаться только на код?

1.  **Множественные точки входа:** Приложение — это не единственный способ записи в БД. Кто-то может запустить миграцию, администратор может поправить данные через консоль (psql), или другой микросервис может написать в ту же таблицу. Код вашего PHP-приложения не защитит базу от этих действий.
2.  **Race Conditions (Состояние гонки):** Это самая опасная причина. В высоконагруженных системах два параллельных запроса могут одновременно пройти проверку в коде.
    *   *Пример:* Проверка баланса: `if ($balance >= 100)`. Два запроса одновременно видят баланс 100, оба проходят проверку и оба списывают деньги, уводя баланс в минус. Только `CHECK constraint` или транзакция с уровнем изоляции в БД спасут ситуацию.
3.  **Человеческий фактор:** Ошибки в коде, баги в новых релизах или неверная реализация логики в одном из сервисов. БД выступает как страховочный трос.

---

### Какие средства я использую в PostgreSQL

Я разделяю ограничения на три уровня:

#### 1. Структурные ограничения (Schema Constraints)
Это база, которая должна быть в каждой таблице.
*   **`NOT NULL`**: Гарантирует, что поле не будет пустым.
*   **`UNIQUE`**: Гарантирует уникальность (email, артикул товара, UUID). Это критично для предотвращения дублей при одновременных запросах.
*   **`FOREIGN KEY`**: Гарантирует ссылочную целостность. Вы не сможете удалить пользователя, если у него есть активные заказы (или удалите их каскадно).
*   **`CHECK`**: Позволяет задать простые правила (например, `price > 0`, `status IN ('new', 'paid', 'shipped')`).

#### 2. Профилактика Race Conditions
Когда бизнес-логика требует проверки состояния, зависящего от других строк.
*   **Уровни изоляции транзакций (Isolation Levels):** Использование `REPEATABLE READ` или `SERIALIZABLE` для критических операций.
*   **Пессимистические блокировки (`SELECT ... FOR UPDATE`):** Я использую их в Doctrine, когда нужно заблокировать строку до завершения транзакции (например, при списании денег со счета).

#### 3. Сложная логика (Triggers & Functions)
Если проверка требует обращения к другим таблицам или сложной математики.
*   **Триггеры:** Например, автоматическое обновление поля `updated_at` или ведение аудиторского лога (кто и когда изменил строку).

---

### Когда и что применять (Стратегия)

| Тип проверки | Где реализуем | Пример |
| :--- | :--- | :--- |
| **Сложная бизнес-логика** (зависит от внешних API, условий, контекста) | **PHP (Domain/Service)** | "Пользователь может купить товар, только если он из категории 'Premium' и у него есть купон". |
| **Формат данных** | **PHP + БД** | PHP проверяет формат email для удобства пользователя, а БД имеет `CHECK (email ~* '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$')` для безопасности. |
| **Уникальность** | **БД (обязательно)** | `UNIQUE constraint` на email. PHP может проверить это через `exists`, но только БД гарантирует защиту от race condition. |
| **Связи между данными** | **БД (обязательно)** | `FOREIGN KEY`. Это стандарт целостности. |
| **Математические границы** | **БД (обязательно)** | `CHECK (amount >= 0)`. Это страховка от багов в расчетах. |

### Резюме
Я придерживаюсь правила: **"Валидируй в коде для пользователя, ограничивай в БД для данных"**. 
Код приложения должен давать понятные и красивые ошибки пользователю, а база данных должна гарантировать, что в ней никогда не окажется "мусора", даже если код приложения сойдет с ума.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

Когда запрос начинает тормозить, я не пытаюсь «угадать» проблему, а действую по строгому алгоритму: от анализа плана выполнения до оптимизации физического хранения данных.

### 1. Диагностика: "Где именно мы теряем время?"

Мой первый инструмент — **`EXPLAIN ANALYZE`**. Обычного `EXPLAIN` недостаточно, так как он показывает только предсказанный план, а `ANALYZE` реально выполняет запрос и показывает реальное время и количество строк.

**На что я смотрю в выводе:**
*   **Seq Scan vs Index Scan:** Если я вижу `Seq Scan` (последовательное сканирование всей таблицы) на большой таблице вместо `Index Scan` — это первая и самая частая причина.
*   **Cost & Actual Time:** Я ищу узлы (nodes) с самым высоким значением времени.
*   **Rows vs Loops:** Если планировщик ожидает 1 строку, а получает 1 000 000 (`rows` vs `actual rows`), значит, статистика базы устарела.
*   **Hash Join vs Nested Loop:** Если при большом количестве данных я вижу `Nested Loop`, это может означать, что планировщик выбрал неэффективный способ соединения таблиц.
*   **Filter:** Если я вижу много строк, которые отфильтровываются после сканирования, это сигнал, что текущий индекс не покрывает условия `WHERE`.

**Дополнительные инструменты:**
*   **`pg_stat_statements`:** Если запрос тормозит "иногда", я использую это расширение, чтобы увидеть общую статистику по всем запросам в системе (среднее время, частота, нагрузка).
*   **Postgres Slow Query Log:** Для отслеживания запросов, превышающих порог выполнения.
*   **CloudWatch / Datadog:** Если мы в облаке, я смотрю на общую нагрузку на CPU, Disk I/O и Memory (возможно, проблема не в запросе, а в нехватке ресурсов сервера).

---

### 2. Типовые причины и способы решения

Я группирую причины на три уровня:

#### Уровень А: Индексы (Самое частое)
*   **Отсутствие индекса:** Добавляю индекс на колонки в `WHERE`, `JOIN` и `ORDER BY`.
*   **Неподходящий индекс:** Индекс по `name` не поможет, если я ищу `WHERE name LIKE '%ivan%'`. Тут поможет только `trgm` (триграммный индекс).
*   **Неиспользование индекса (SARGability):** Если я пишу `WHERE DATE(created_at) = '2023-01-01'`, индекс по `created_at` не сработает. Решение: `WHERE created_at >= '2023-01-01 00:00:00' AND ...`.
*   **Избыточность индексов:** Слишком много индексов замедляют `INSERT/UPDATE`.

#### Уровень Б: Структура запроса и данных
*   **N+1 запросы:** (Уже обсуждали) — решается через `JOIN FETCH`.
*   **Неэффективные JOIN:** Соединение таблиц по неиндексированным колонкам или по типам данных, которые требуют приведения (например, `int` к `text`).
*   **SELECT *:** Выборка всех колонок увеличивает нагрузку на I/O и память. Решение — выбирать только нужные поля.
*   **Запрос слишком тяжелых агрегатов:** `COUNT(*)` по огромной таблице. Решение — материализованные представления (Materialized Views) или счетчики в отдельной таблице.

#### Уровень В: Параметры БД и "здоровье" сервера
*   **Устаревшая статистика:** Планировщик строит плохой план, потому что думает, что в таблице 10 строк, а там 10 миллионов. Решение: `ANALYZE table_name`.
*   **Bloat (Раздувание таблиц):** После массовых `UPDATE/DELETE` в Postgres остаются "мертвые" строки. Если `VACUUM` не справляется, чтение замедляется. Решение: `VACUUM ANALYZE`.
*   **Нехватка памяти (Work Mem):** Если сортировка (`ORDER BY`) не влезает в оперативную память, Postgres сбрасывает её на диск (Temporary Files), что в разы медленнее. Решение: настройка `work_mem`.

---

### 3. Мой алгоритм (Summary)

1.  **Локализовать:** Найти медленный запрос через `pg_stat_statements` или Profiler.
2.  **Проанализировать:** Запустить `EXPLAIN ANALYZE`.
3.  **Проверить индексы:** Есть ли они? Работают ли они? Покрывают ли они условия `WHERE` и `JOIN`?
4.  **Переписать запрос:** Убрать `SELECT *`, убрать функции от колонок в `WHERE`, заменить подзапросы на `JOIN`.
5.  **Оптимизировать хранение:** Если индексы не помогают — рассмотреть создание материализованного представления, партиционирование таблицы (Partitioning) или изменение структуры (денормализацию).
6.  **Проверить окружение:** Убедиться, что статистика актуальна (`ANALYZE`) и памяти достаточно.

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

В DDD **Агрегат (Aggregate)** — это кластер связанных объектов (сущностей и Value Objects), который рассматривается как единая единица для изменения данных. 

Главная цель агрегата — **поддержание инвариантов** (бизнес-правил, которые всегда должны быть истинными).

### Ключевые правила агрегата:
1.  **Корень агрегата (Aggregate Root):** Это единственная сущность, с которой взаимодействует внешний мир. Никто не может изменить внутренние объекты агрегата, не обратившившись к корню.
2.  **Граница целостности:** Все изменения внутри агрегата должны происходить транзакционно. Если вы меняете что-то внутри, всё состояние агрегата должно оставаться валидным.
3.  **Ссылки только на корни:** Объекты внутри агрегата могут ссылаться друг на друга, но внешние агрегаты могут ссылаться на агрегат **только через его корень** (обычно по ID).

---

### Пример: Система управления заказами

Представим процесс покупки.

**Агрегат `Order` (Заказ):**
*   **Root:** `Order` (содержит статус, общую сумму, дату).
*   **Внутренние сущности:** `OrderItem` (состав заказа: товар, кол-во, цена на момент покупки).
*   **Value Objects:** `Address` (адрес доставки), `Money` (сумма).

**Как это работает в коде:**
Вы не можете просто прийти в базу и изменить цену в `OrderItem`. Вы должны вызвать метод у `Order`:
`$order->changeItemQuantity(productId, newQuantity);`

Внутри этого метода `Order` делает свою работу:
1. Проверяет, не превышен ли лимит веса заказа.
2. Пересчитывает общую сумму заказа.
3. Проверяет, не заблокирован ли заказ.

**Если бы мы не использовали агрегат**, кто-то мог бы изменить количество товара, и сумма заказа осталась бы старой. Это нарушение инварианта.

---

### Как я определяю границы агрегата?

Я использую три критерия:

1.  **Критерий инварианта (самый важный):** Какие данные должны меняться **всегда вместе**? Если изменение объекта А требует немедленного и обязательного изменения объекта Б, чтобы система не вошла в противоречивое состояние — А и Б должны быть в одном агрегате.
2.  **Критерий транзакции:** Какую группу изменений мы хотим гарантировать как атомарную (All or Nothing)?
3.  **Критерий жизненного цикла:** Если объект Б не имеет смысла без объекта А (например, `OrderItem` не существует без `Order`), они должны быть в одном агрегате.

---

### Типовая ошибка: "Слишком большой агрегат" (The Fat Aggregate)

Это самая распространенная ошибка. Разработчик пытается запихнуть в один агрегат всё, что связано логически.

**Ошибка:** Создать агрегат `Customer`, который содержит в себе коллекцию всех его `Order`, а каждый `Order` содержит все свои `OrderItem`.

**Почему это плохо?**
1.  **Проблемы с производительностью:** При попытке изменить один `OrderItem` в заказе трехлетней давности, Doctrine будет вынуждена загрузить в память **всю** историю заказов этого клиента.
2.  **Конфликты блокировок (Concurrency):** Если клиент делает новый заказ, агрегат `Customer` блокируется. В это же время другой процесс (например, служба доставки) пытается обновить статус старого заказа. Из-за того, что это один агрегат, они будут ждать друг друга, создавая очереди и ошибки.
3.  **Нарушение границ:** Агрегат становится слишком тяжелым и сложно управляемым.

**Как правильно:**
Разбить на два агрегата: `Customer` и `Order`. 
*   `Order` ссылается на `Customer` только через `customerId`.
*   Изменение заказа не затрагивает данные клиента.
*   Связь между ними поддерживается через **Domain Events** (например, `OrderPlaced` $\to$ `CustomerLoyaltyService` увеличивает баллы клиента).

### Итог
*   **Маленькие агрегаты** = высокая производительность и масштабируемость.
*   **Большие агрегаты** = риск блокировок и тормозов.
*   **Золотое правило:** Делай агрегат настолько маленьким, насколько это возможно, но настолько большим, насколько это необходимо для соблюдения бизнес-правил.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

Если два процесса одновременно пытаются изменить один и тотший агрегат, возникает классическая проблема **состояния гонки (Race Condition)**. Результат зависит от того, как настроена база данных и как мы управляем транзакциями.

### 1. Что произойдёт (на уровне БД)

Без специальной защиты возможны два сценария:

*   **Lost Update (Потерянное обновление):** 
    Процесс А и Процесс Б одновременно читают агрегат (например, баланс 100). Процесс А вычитает 10 и записывает 90. Процесс Б вычитает 20 и записывает 80. В итоге в базе окажется 80, хотя должно быть 70. Обновление процесса А "потеряно".
*   **Исключение нарушения целостности:** 
    Если у нас есть `UNIQUE constraint` или `CHECK constraint`, то один из процессов завершится успешно, а второй упадет с ошибкой БД. Это "хороший" сценарий, так как данные остались целостными.

---

### 2. Как я проектирую систему (Стратегии решения)

Я выбираю стратегию в зависимости от критичности данных и ожидаемой нагрузки.

#### А. Оптимистичная блокировка (Optimistic Locking) — мой выбор по умолчанию
Мы предполагаем, что конфликты редки. Мы добавляем в агрегат поле `version` (целое число).

**Как это работает:**
1. Процесс А читает `Order` с `version = 1`.
2. Процесс Б читает тот же `Order` с `version = 1`.
3. Процесс А сохраняет изменения: `UPDATE orders SET status = 'paid', version = 2 WHERE id = 5 AND version = 1`. Успешно.
4. Процесс Б пытается сохранить: `UPDATE orders SET status = 'cancelled', version = 2 WHERE id = 5 AND version = 1`. 
5. **Результат:** БД возвращает "0 строк изменено", потому что `version` уже равна 2. Doctrine выбрасывает `OptimisticLockException`.

**Плюсы:** Не блокирует базу, высокая производительность.
**Минусы:** Процесс Б должен уметь обрабатывать ошибку (например, повторить операцию или сообщить пользователю: "Данные были изменены другим пользователем").

#### Б. Пессимистичная блокировка (Pessimistic Locking)
Мы предполагаем, что конфликты неизбежны. Мы блокируем строку на уровне БД в момент чтения.

**Как это работает:**
Используется SQL-команда `SELECT ... FOR UPDATE`.

1. Процесс А читает строку: `SELECT * FROM orders WHERE id = 5 FOR UPDATE`. База ставит на эту строку "замок".
2. Процесс Б пытается прочитать ту же строку с `FOR UPDATE`. Он **замирает** и ждет, пока Процесс А не завершит транзакцию (`COMMIT` или `ROLLBACK`).
3. Процесс А завершает работу. Процесс Б "просыпается", читает уже обновленные данные и продолжает работу.

**Плюсы:** Гарантированная последовательность, никакой потери данных.
**Минусы:** 
*   **Риск Deadlocks:** Если Процесс А заблокировал Объект 1 и ждет Объект 2, а Процесс Б сделал наоборот — система встанет.
*   **Снижение производительности:** Процессы ждут друг друга, увеличивая время ответа.

#### В. Смена парадигмы (Eventual Consistency)
Если агрегат слишком "горячий" (например, счетчик лайков под постом), я вообще ухожу от прямой конкуренции за одну строку.

**Как это работает:**
Вместо `UPDATE counter SET value = value + 1`, я пишу события в очередь: `LikeEvent(postId)`. Специальный воркер накапливает их и раз в минуту обновляет итоговое значение в базе.

---

### Мой алгоритм выбора:

1.  **Нужна максимальная скорость и конфликты редки?** $\to$ **Optimistic Locking** (через поле `version`). Это стандарт для большинства веб-приложений.
2.  **Критически важные финансовые операции?** (Списание денег, где цена ошибки — потеря денег) $\to$ **Pessimistic Locking** (`FOR UPDATE`). Здесь лучше подождать лишние 50 мс, чем потерять транзакцию.
3.  **Очень высокая нагрузка на одну точку (High contention)?** $\to$ **Асинхронная обработка событий** или использование специализированных инструментов (Redis/Atomic counters).

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

Доменные события (Domain Events) — это мощный инструмент для реализации **слабой связности (loose coupling)** между частями системы. Они позволяют агрегатам сообщать миру: «Что-то важное произошло», не заботясь о том, кто и как на это отреагирует.

---

### 1. Когда публиковать события?

Событие должно публиковаться **внутри агрегата** в тот момент, когда его состояние изменилось, но **до того**, как транзакция будет завершена.

**Важное правило:** Событие — это не команда. 
*   **Команда (Command):** «Сделай это» (`PlaceOrder`). Она выражает намерение.
*   **Событие (Event):** «Это случилось» (`OrderPlaced`). Оно выражает факт в прошлом.

**Пример в коде:**
```php
class Order {
    private array $events = [];

    public function ship(): void {
        if ($this->status !== Status::PAID) {
            throw new \DomainException("Cannot ship unpaid order");
        }
        $this->status = Status::SHIPPED;
        
        // Мы не вызываем Mailer здесь! Мы просто записываем факт.
        $this->record(new OrderShipped($this->id, $this->customerEmail));
    }

    private function record(DomainEvent $event): void {
        $this->events[] = $event;
    }

    public function pullEvents(): array {
        $events = $this->events;
        $this->events = []; // Очищаем, чтобы не дублировать
        return $events;
    }
}
```

---

### 2. Как обрабатывать события?

Я разделяю обработку на два уровня:

1.  **Синхронная (внутри той же транзакции):**
    Используется, если действие **обязательно** должно завершиться для обеспечения целостности (например, расчет налогов при изменении суммы заказа).
2.  **Асинхронная (через очередь/Message Bus):**
    Используется для всего остального: отправка Email, уведомления в Telegram, обновление поискового индекса, синхронизация с аналитикой. Это то, что делает систему масштабируемой.

---

### 3. Связь с транзакциями БД (Критический момент)

Это самая сложная часть. Если вы опубликуете событие и отправите его в очередь (например, в RabbitMQ) **до того**, как `EntityManager->flush()` завершит транзакцию, может возникнуть ситуация:
*   Событие улетело в очередь.
*   Воркер подхватил его и пытается найти `Order` в базе.
*   **Но транзакция в основном процессе еще не закоммичена!** Воркер получает ошибку "Order not found".

**Как я это решаю:**

*   **Transactional Outbox Pattern (Самый надежный способ):** 
    Вместо прямой отправки в RabbitMQ, я сохраняю события в ту же БД в специальную таблицу `outbox_messages` в рамках той же транзакции, что и изменения агрегата. Отдельный процесс (Relay) читает эту таблицу и перекладывает сообщения в очередь. Так мы гарантируем, что событие попадет в очередь **только если** данные успешно сохранились в БД.
*   **Post-Flush Dispatching:** 
    В Symfony я использую `Doctrine Lifecycle Events` (например, `onFlush` или `postFlush`). Я собираю события из всех измененных агрегатов и отправляю их в шину только **после** успешного коммита транзакции.

---

### 4. Проблемы и решения

#### Какие проблемы решает подход?
*   **Снижение связности (Decoupling):** `OrderService` не знает о `MailerService`.
*   **Single Responsibility:** Каждый сервис делает только свою работу.
*   **Масштабируемость:** Тяжелые задачи уходят в фоновые воркеры.
*   **Расширяемость:** Можно добавить новое действие (например, отправку SMS) на событие `OrderPlaced`, не меняя ни одной строчки кода в `OrderService`.

#### Какие проблемы создаёт?
*   **Eventual Consistency (Согласованность в конечном итоге):** Система становится распределенной. Пользователь может увидеть "Заказ оформлен", но в поиске его еще нет. Нужно проектировать UI так, чтобы это не пугало пользователя (например, через оптимистичный UI).
*   **Сложность отладки:** Трудно проследить цепочку "Событие $\to$ Обработчик $\to$ Еще событие". Требуется хорошая сквозная трассировка (Distributed Tracing).
*   **Проблема дублей (Idempotency):** Из-за особенностей сетей сообщение может прийти дважды. **Обработчики событий обязаны быть идемпотентными** (повторный вызов с тем же ID события не должен приводить к повторному списанию денег).

### Резюме
Доменные события — это клей, который соединяет части системы, не склеивая их намертво. Я использую их для декомпозиции логики, всегда связываю их с транзакцией через паттерн Outbox или Post-Flush, и всегда проектирую обработчики как идемпотентные функции.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

Это фундаментальные вопросы, которые отделяют просто «написание кода» от «проектирования программного обеспечения».

### 1. Entity vs Value Object

Главное различие заключается в том, **как мы определяем идентичность объекта**.

| Характеристика | Entity (Сущность) | Value Object (Объект-значение) |
| :--- | :--- | :--- эксперт
| **Идентичность** | Имеет уникальный ID, который не меняется.
| **Сравнение** | Сравнивается по ID. Два объекта с одинаковыми полями, но разными ID — это разные объекты.
| **Жизненный цикл** | Имеет историю. Состояние меняется со временем.
| **Изменяемость** | Mutable (изменяем). Мы меняем поля, но объект остается тем же.
| **Пример** | `User` (id: 5), `Order` (id: 102).

**Value Object** же определяется своими свойствами. Если два объекта имеют одинаковые значения всех полей, они **равны**.

| Характеристика | Value Object (Объект-значение) |
| :--- | :--- |
| **Идентичность** | Нет ID. Сравнивается по значениям свойств. |
| **Сравнение** | Два объекта с одинаковыми полями — это один и тот тот же объект. |
| **Жизненный цикл** | Не имеет истории. Если нужно изменить значение — создаем новый объект. |
| **Изменяемость** | **Immutable (неизменяем).** Это критически важно для предсказуемости. |
| **Пример** | `Money(100, 'USD')`, `Email('test@test.com')`, `Address`. |

---

### 2. Как я принимаю решение: к чему отнести концепцию?

Когда я вижу новую бизнес-сущность, я задаю себе три вопроса:

1.  **«Нужен ли этому объекту уникальный идентификатор, чтобы отличить его от другого такого же?»**
    *   Если я создам два заказа на одну и ту ту же сумму в одну секунду — это разные заказы? Да. $\to$ **Entity**.
    *   Если я создам два адреса "Москва, ул. Ленина, 1" — это разные адреса? Нет, это один и тот же адрес. $\to$ **Value Object**.

2.  **«Будет ли этот объект меняться?»**
    *   Если я меняю цвет автомобиля, это тот же автомобиль или новый? Автомобиль тот же, но его атрибут изменился. Автомобиль — **Entity**, цвет — **Value Object**.
    *   Если я меняю дату рождения человека, он становится другим человеком? Нет, дата просто изменилась. Но дата — это **Value Object**.

3.  **«Должен ли я контролировать валидность этого объекта?»**
    *   Если объект не может существовать в невалидном состоянии (например, отрицательная цена или некорректный email), я упаковываю эту логику в **Value Object**. Это гарантирует, что если объект создан, он корректен.

---

### 3. Единый язык (Ubiquitous Language)

**Ubiquitous Language** — это общий язык, который используют разработчики и бизнес-эксперты (Domain Experts) для описания предметной области. Это не просто "термины", это способ мышления.

**Как это работает:**
Если бизнес говорит: *"Мы **аннулируем** заказ, если он уже **отгружен**"*, то в коде не должно быть методов `setStatus(3)` или `cancelOrder()`. Там должны быть методы `cancel()` и проверка состояния `isShipped()`.

**Как он влияет на код:**

1.  **Имена классов и методов:** Они в точности повторяют терминологию бизнеса. Никаких `processData()` или `handleRequest()`. Только `calculateTax()`, `applyDiscount()`, `shipOrder()`.
2.  **Структура проекта:** Папки и модули называются так, как их называет бизнес (например, `Billing`, `Inventory`, `Shipping`), а не как технические слои (`Controllers`, `Models`).
3.  **Снижение когнитивной нагрузки:** Когда разработчик читает код, он читает описание бизнес-процесса, а не алгоритм перекладывания данных из таблицы в таблицу. Это минимизирует риск "трудного перевода" с языка бизнеса на язык кода.
4.  **Упрощение коммуникации:** Если возникает баг, разработчик говорит: *"Проблема в логике расчета налога при отмене заказа"*, и бизнес-эксперт сразу понимает, о чем речь, так как эти термины идентичны в обоих мирах.

**Мой принцип:** Если я использую в коде термин, который не понимает бизнес-эксперт (например, `Entity Manager`, `Repository`, `DTO`), это нормально — это технический язык. Но если я использую термин, который бизнес называет иначе — я совершаю ошибку проектирования.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

Применение **Clean Architecture** (Чистой архитектуры) в PHP-приложении направлено на то, чтобы бизнес-логика была изолирована от внешних деталей (фреймворка, базы данных, сторонних API).

Основное **правило зависимостей**: зависимости направлены только **внутрь**, к центру (к бизнес-логике). Слои "внешнего мира" знают о слоях "ядра", но ядро ничего не знает о внешнем мире.

---

### Структура слоев

#### 1. Domain Layer (Ядро / Domain) — Самый центр
Здесь живет чистая бизнес-логика. Этот слой не зависит ни от чего.
*   **Что лежит:** 
    *   **Entities (Агрегаты):** Объекты с идентификаторами (`Order`, `User`).
    *   **Value Objects:** Объекты без ID (`Money`, `Email`).
    *   **Domain Exceptions:** Исключения, специфичные для бизнеса (`InsufficientFundsException`).
    *   **Repository Interfaces:** Интерфейсы, которые описывают, *что* нужно сделать с данными, но не *как*.
    *   **Domain Services:** Логика, которая не вписывается в одну сущность (например, перевод валют).

#### 2. Application Layer (Слой приложений / Use Cases)
Оркестратор процесса. Он управляет потоком данных, но не содержит правил бизнеса.
*   **Что лежит:**
    *   **Use Cases (Command Handlers):** Классы, реализующие конкретный сценарий (например, `PlaceOrderHandler`).
    *   **DTO (Data Transfer Objects):** Объекты для передачи данных из контроллера в Use Case.
    *   **Interfaces:** Интерфейсы для внешних сервисов (например, `EmailServiceInterface`).

#### 3. Infrastructure Layer (Инфраструктура)
Реализация технических деталей. Это "грязный" слой.
*   **Что лежит:**
    *   **Repositories Implementations:** Реализация интерфейсов из Domain с помощью Doctrine.
    *   **External API Clients:** Реализация интерфейсов для работы с внешними сервисами (Stripe, Twilio).
    *   **Persistence:** Конфигурации БД, миграции.

#### 4. Presentation / Interface Layer (Интерфейс)
Точка входа в приложение.
*   **Что лежит:**
    *   **Controllers:** Принимают HTTP-запрос, превращают его в DTO и отдают в Use Case.
    *   **CLI Commands:** Консольные команды.
    *   **API Resources:** Форматирование ответа (JSON/XML).

---

### Куда попадут ваши компоненты?

*   **Symfony-контроллер $\to$ Presentation Layer.** Его задача — принять запрос и передать управление в Application Layer. Он не должен содержать бизнес-логики.
*   **Doctrine $\to$ Infrastructure Layer.** Сама библиотека и её реализация репозиториев лежат здесь. Доменный слой видит только интерфейс `OrderRepositoryInterface`, но не знает, что за ним стоит Doctrine.
*   **Обработчик очереди (Messenger Handler) $\to$ Application Layer.** Обработчик является "точкой входа" (как и контроллер). Он получает сообщение, превращает его в команду и вызывает соответствующий Use Case.

---

### Визуализация зависимостей

`Presentation` $\to$ `Application` $\to$ `Domain` $\leftarrow$ `Infrastructure`

*Инфраструктура реализует интерфейсы из Домена, поэтому она зависит от Домена. Контроллер вызывает Use Case, поэтому он зависит от Application. Но Domain не зависит ни от кого.*

---

### Как следить, чтобы границы не нарушались?

Соблюдать эти правила вручную сложно, поэтому я использую три метода:

1.  **Dependency Injection (DI):** Я никогда не создаю объекты инфраструктуры (например, `EntityManager`) внутри доменных классов. Я только внедряю интерфейсы через конструктор. Если я пытаюсь внедрить `EntityManager` в `Order`, я сразу вижу нарушение.

2.  **Static Analysis (PHPStan / Psalm):** 
    Я настраиваю строгую типизацию. Если я случайно использую класс из слоя `Infrastructure` в слое `Domain`, статический анализатор подсветит это (особенно если использовать плагины для проверки архитектуры).

3.  **Архитектурные тесты (Deptrac):**
    Это мой любимый инструмент. **Deptrac** позволяет описать слои и правила их взаимодействия в YAML-конфиге. 
    *Например, я пишу правило: "Слой Domain не может зависеть от слоя Infrastructure".* 
    При запуске CI/CD Deptrac сканирует код и, если находит `use Doctrine\ORM\...` в доменном классе, падает с ошибкой. Это делает архитектуру "непробиваемой".

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

Для Symfony-приложения я придерживаюсь классической **Пирамиды тестирования**, но с поправкой на специфику работы с БД и внешними сервисами. Моя цель — иметь максимально широкий охват при минимальном времени выполнения и высокой надежности (отсутствии flaky-тестов).

### 1. Структура пирамиды

#### **Unit Tests (Основание — ~70%)**
*   **Что тестируем:** Чистую бизнес-логику в `Domain Layer` (Entity, Value Objects, Domain Services).
*   **Что мокаем:** Вообще всё. В идеальном Unit-тесте не должно быть ни одной зависимости от фреймворка или БД. Мы используем `Mockery` или встроенные средства PHPUnit для имитации интерфейсов.
*   **Цель:** Проверить все граничные условия, исключения и сложные алгоритмы. Они должны выполняться за миллисекунды.

#### **Integration Tests (Середина — ~20%)**
*   **Что тестируем:** Взаимодействие компонентов. В Symfony это проверка того, что `Repository` правильно работает с БД, или что `Service` правильно собирает зависимости через DI.
*   **Что мокаем:** Внешние API (HTTP-клиенты), файловую систему, почтовые сервисы.
*   **Что НЕ мокаем:** Базу данных (PostgreSQL) и сам Symfony Kernel.
*   **Цель:** Убедиться, что наши SQL-запросы верны, маппинг Doctrine работает, а конфигурация сервисов корректна.

#### **Functional / E2E Tests (Вершина — ~10%)**
*   **Что тестируем:** Полный жизненный цикл запроса: `HTTP Request $\to$ Controller $\to$ Service $\to$ DB $\to$ Response`. Используем `WebTestCase` в Symfony.
*   **Что мокаем:** Только самые медленные и нестабильные внешние системы (платежные шлюзы, SMS-сервисы).
*   **Цель:** Проверить "счастливый путь" (happy path) и критические сценарии (регистрация, оформление заказа).

---

### 2. Что мокать, а что нет?

Мой подход базируется на **границе ответственности**:

*   **Мокаем (Mock):** Все, что находится за пределами нашего контроля (Third-party API, почтовые сервера, платежные системы). Для этого я использую интерфейсы и внедряю их моки через DI.
*   **Не мокаем (Real):**
    *   **Базу данных:** Мокать репозиторий — значит тестировать мок, а не код. Я использую реальную PostgreSQL в Docker.
    *   **Value Objects и Entities:** Они — часть нашего кода, их нужно тестировать как есть.
    *   **Внутренние сервисы:** Если я тестирую интеграцию, я хочу видеть, как `ServiceA` взаимодействует с `ServiceB`.

---

### 3. Как сделать тесты быстрыми и стабильными?

Самая большая проблема тестов в PHP — это медленная работа с БД и "мусор" в состоянии между тестами.

#### **Для скорости:**
1.  **SQLite in Memory (Осторожно):** Иногда используют SQLite для скорости, но я **против** этого. SQLite не поддерживает специфичный синтаксис PostgreSQL (JSONB, Window functions), что создает ложное чувство безопасности.
2.  **Database Transactions (БД в памяти):** Вместо того чтобы пересоздавать схему перед каждым тестом, я использую транзакции. Каждый тест оборачивается в транзакцию, которая в конце делает `rollback`. База остается чистой, а скорость возрастает в разы.
3.  **Parallel Testing:** Использование `ParaTest` для запуска тестов в несколько потоков.

#### **Для стабильности (Anti-Flaky):**
1.  **Isolated Database:** Для каждого разработчика и для CI запускается отдельный контейнер с PostgreSQL. Никаких общих баз.
2.  **Database State Reset:** Использование `DAMADoctrineTestBundle`. Этот бандл автоматически оборачивает каждый тест в транзакцию и делает откат, гарантируя, что тесты не влияют друг на друга.
3.  **Idempotency в тестах:** Я никогда не полагаюсь на порядок выполнения тестов. Каждый тест должен быть самодостаточным: сам создает нужного пользователя, сам создает заказ.
4.  **Deterministic Data:** Избегайте использования `now()` или `rand()` без фиксации "зерна" (seed). В тестах время должно быть зафиксировано (используйте `ClockInterface` из PSR-20).

### Итоговая стратегия:
Я пишу **много Unit-тестов** для логики, **среднее количество интеграционных тестов** с реальной БД через транзакции, и **минимум E2E-тестов** для проверки ключевых бизнес-путей. Это дает идеальный баланс между скоростью разработки и уверенностью в качестве.

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Когда два процесса одновременно пытаются обновить одну и ту же строку, возникает классическая проблема **конкурентного изменения данных**. Если не принять мер, мы столкнемся с потерей данных или нарушением бизнес-логики.

### 1. Основные проблемы

*   **Lost Update (Потерянное обновление):** Это самый частый сценарий. 
    *   *Пример:* Пользователь А и Б одновременно читают баланс (100 руб). А вычитает 20, Б вычитает 30. Оба записывают результат. Если Б запишет последним, баланс станет 70, а 20 рублей от пользователя А просто «испарятся».
*   **Dirty Read (Грязное чтение):** Процесс А читает данные, которые еще не закоммичены процессом Б. Если Б сделает `rollback`, процесс А будет работать с «призрачными» данными.
*   **Non-repeatable Read (Неповторяющееся чтение):** В рамках одной транзакции процесс А читает строку, затем процесс Б меняет её и делает `commit`. Если процесс А прочитает ту же строку снова, данные изменятся.
*   **Phantom Read (Фантомное чтение):** Процесс А читает набор строк по условию (например, все заказы клиента). Процесс Б добавляет новый заказ. При повторном чтении процесс А видит «фантомную» новую строку.

---

### 2. Способы защиты

Я разделяю подходы на **Оптимистичные** и **Пессимистичные**.

#### А) Optimistic Locking (Оптимистичная блокировка)
Мы предполагаем, что конфликты случаются редко. Мы не блокируем строку, а проверяем, не изменилась ли она, пока мы с ней работали.

*   **Механизм:** В таблицу добавляется колонка `version` (integer). При обновлении мы проверяем: `UPDATE ... SET val = x, version = version + 1 WHERE id = 1 AND version = current_version`.
*   **Результат:** Если кто-то успел обновить запись, `version` изменится, наш `WHERE` не найдет строку, и БД вернет "0 строк изменено". Doctrine выбросит `OptimisticLockException`.

#### Б) Pessimistic Locking (Пессимистичная блокировка)
Мы предполагаем, что конфликт неизбежен, и блокируем ресурс на время работы.

*   **Механизм:** Используется SQL-команда `SELECT ... FOR UPDATE`. База данных ставит на строку "замок". Любой другой процесс, пытающийся прочитать эту строку с `FOR UPDATE` или изменить её, будет ждать, пока первая транзакция не завершится (`COMMIT` или `ROLLBACK`).
*   **Результат:** Процессы выстраиваются в очередь.

#### В) Уровни изоляции транзакций (Transaction Isolation Levels)
Настройка того, как база данных видит изменения других транзакций.
*   `READ COMMITTED` (дефолт в Postgres): защищает от грязного чтения.
*   `REPEATABLE READ`: защищает от неповторяющихся чтений.
*   `SERIALIZABLE`: самый строгий уровень, имитирующий последовательное выполнение транзакций.

---

### 3. Сравнение и выбор стратегии

| Критерий | Optimistic Locking | Pessimistic Locking |
| :--- | :--- | :--- |
| **Производительность** | **Высокая** (нет ожиданий) | **Низкая** (процессы ждут) |
| **Масштабируемость** | Отличная | Низкая (риск очередей и дедлоков) |
| **Поведение при конфликте** | Ошибка в приложении (нужно обрабатывать) | Задержка в выполнении (ожидание) |
| **Сложность реализации** | Легко (просто добавить колонку) | Средне (нужно управлять временем блокировки) |

#### Когда я выбираю Оптимистичную блокировку:
Это мой **выбор по умолчанию** для 90% веб-приложений. 
*   Когда нагрузка высокая, а конфликты — редкое событие.
*   Когда мы работаем в stateless-среде (HTTP), где пользователь может открыть страницу, уйти пить кофе, а через 5 минут нажать "Сохранить". Мы не можем держать транзакцию открытой всё это время (это убьет базу).

#### Когда я выбираю Пессимистичную блокировку:
*   В критически важных финансовых операциях, где цена ошибки — потеря денег, и где мы можем позволить себе небольшую задержку ради гарантии.
*   Когда конфликт почти гарантирован (например, высоконагруженный счетчик остатков на складе во время распродажи).
*   В коротких, бысттых транзакциях внутри одного процесса.

#### Когда я выбираю Уровни изоляции:
*   Когда нужно решить проблему на уровне всей системы, а не конкретной сущности (например, при генерации сложных финансовых отчетов, где данные не должны меняться во время чтения).

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

Мой Git-процесс базируется на принципах **предсказуемости, атомарности и автоматизации**. Я придерживаюсь модифицированной модели **GitFlow**, адаптированной под CI/CD, чтобы обеспечить быструю доставку кода без потери качества.

### 1. Стратегия ветвления (Branching Model)

Я использую три типа веток:

*   **`main` (или `master`):** Содержит только стабильный, протестированный код, который находится в продакшене. Каждая точка в истории `main` — это релиз.
*   **`develop`:** Интеграционная ветка. Здесь собираются все фичи перед релизом. Это "черновик" будущего продакшена.
*   **`feature/feature-name` (или `bugfix/issue-id`):** Временные ветки для разработки. Создаются от `develop`, вливаются обратно в `develop` через Pull Request.

**Почему так?** Это разделяет "стабильное" и "разрабатываемое". Мы не можем пушить в `main` напрямую, так как это нарушит процесс тестирования. Использование feature-веток позволяет работать параллельно над разными задачами, не мешая друг другу.

---

### 2. Формат коммитов (Commit Messages)

Я использую стандарт **Conventional Commits**. Это делает историю читаемой и позволяет автоматизировать генерацию `CHANGELOG`.

**Формат:** `<type>(<scope>): <description>`

*   `feat`: Новая функциональность.
*   `fix`: Исправление ошибки.
*   `docs`: Изменения в документации.
*   `style`: Правки стиля (пробелы, форматирование — не влияет на логику).
*   `refactor`: Изменение кода, которое не исправляет баг и не добавляет фичу.
*   `test`: Добавление или изменение тестов.
*   `chore`: Обновление зависимостей, конфигов сборки.

**Пример:** `feat(order): add validation for shipping address`

**Почему так?** Это превращает историю коммитов из "набора заметок" в структурированный лог. С помощью инструментов вроде `semantic-release` можно автоматически определять версию следующего релиза (SemVer) на основе типов коммитов.

---

### 3. Pull Request (PR) и Code Review

PR — это не просто просьба "влей мой код", это этап контроля качества.

**Процесс PR:**
1.  **Описание:** Я пишу подробный PR: *Что сделано? Зачем? Как протестировать? Ссылка на задачу в Jira/Trello.*
2.  **Автоматизация (CI):** Как только PR создан, запускается CI-пайплайн:
    *   Linter (PHP_CodeSniffer/PHP-CS-Fixer).
    *   Static Analysis (PHPStan/Psalm).
    *   Unit & Integration Tests.
    *   *Если CI упал, PR не рассматривается.*
3.  **Review:** Минимум один (лучше два) коллеги должны одобрить код.
    *   Я смотрю на: архитектурную чистоту, соблюдение SOLID, покрытие тестами и отсутствие "магических чисел".
    *   **Правило:** Обсуждение должно быть конструктивным. Комментарий должен предлагать решение, а не просто критиковать.

**Почему так?** Это распределяет ответственность за качество и позволяет знаниям внутри команды распространяться (Knowledge Sharing).

---

### 4. Релизный цикл (Releases)

Когда в `develop` накопилось достаточно протестированных фич, начинается процесс релиза.

1.  **Release Branch:** Создается ветка `release/v1.2.0` от `develop`.
2.  **Stabilization:** В этой ветке разрешены только исправления критических багов (bugfixes). Никаких новых фич.
3.  **Final QA:** Проводится финальное тестирование на стейджинге.
4.  **Merge & Tag:**
    *   `release` вливается в `main`.
    *   В `main` ставится Git Tag (например, `v1.2.0`).
    *   `release` вливается обратно в `develop`, чтобы все фиксы попали в будущие задачи.
5.  **Deployment:** Автоматический деплой из `main` в продакшен.

**Почему так?** Это создает "буферную зону" (release branch) для стабилизации, гарантируя, что в `main` попадет только проверенный код, и позволяя команде продолжать разработку новых фич в `develop`, не прерывая процесс релиза.

---

### Итоговая схема процесса:
`Task` $\to$ `Feature Branch` $\to$ `Commits (Conventional)` $\to$ `PR` $\to$ `CI (Tests/Lint)` $\to$ `Code Review` $\to$ `Merge to Develop` $\to$ `Release Branch` $\to$ `Merge to Main & Tag` $\to$ `Production`.

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

Для меня хороший код-ревью — это не «инспекция ошибок», а **процесс обмена знаниями** и совместного обеспечения качества. Это диалог, а не вердикт.

### 1. На что я смотрю в первую очередь (Приоритеты)

Я делю проверку на три уровня, чтобы не утонуть в мелочах:

**Уровень 1: Архитектура и логика (High Priority)**

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

Важное уточнение: в PostgreSQL **не существует прямой команды `FORCE INDEX`**, как это сделано в MySQL. В MySQL вы можете явно указать оптимизатору: `SELECT * FROM table FORCE INDEX (idx_name)`. В PostgreSQL у разработчика нет прямого синтаксического спососа "приказать" планировщику использовать конкретный индекс в обычном запросе.

Однако, если вы столкнулись с ситуацией, когда PostgreSQL **не использует нужный индекс** (выбирая `Seq Scan` вместо `Index Scan`), у вас есть три спосо�нобы «заставить» его это сделать.

---

### 1. Метод "Стимуляции" через изменения в запросе

Часто планировщик игнорирует индекс, потомуs он считает, что сканирование таблицы будет дешевле (например, из-за устаревшей статистики или специфики типа данных).

*   **Приведение типов (Type Casting):** Если индекс создан по `integer`, а вы передаете `text`, индекс не сработает. Нужно явно привести тип: `WHERE id = 123::int`.
*   **Избегание функций над колонками:** Вместо `WHERE DATE(created_at) = '2023-01-01'` (что убивает индекс), нужно писать `WHERE created_at >= '2023-01-01 00:00:00' AND created_at < '2023-01-02 00:00:00'`.
*   **Использование CTE (Common Table Expressions):** Иногда можно "подтолкнуть" планировщик, заставив его сначала выполнить выборку по индексу во временной таблице (CTE), а затем соединить её с основной.

---

### 2. Метод "Принуждения" через настройки сессии (Самый близкий аналог FORCE INDEX)

Если вы понимаете, что планировщик ошибается, вы можете временно изменить его параметры поведения для конкретного сеанса или запроса.

*   **`SET enable_seqscan = off;`**
    Это "грубый" метод. Вы отключаете возможность последовательного сканирования для текущей сессии. Планировщик будет вынужден искать альтернативы (индексы).
    *   *Риск:* Это не гарантирует, что индекс *лучший*. Он просто запрещает планировщику выбирать самый простой (но в данном случае плохой) путь.

---

### 3. Метод "Исправления причины" (Правильный путь)

Вместо того чтобы борожаться с планировщиком, нужно сделать так, чтобы его расчеты стали верными.

*   **Обновление статистики (`ANALYZE`):**
    Если вы загрузили миллион строк, а статистика говорит, что их 10, планировщик выберет `Seq Scan`. Команда `ANALYZE table_name;` обновит статистику, и индекс "включится" сам.
*   **Создание покрывающего индекса (Covering Index):**
    Если запрос выбирает `id` и `name`, создайте индекс `(id, name)`. Тогда PostgreSQL возьмет данные прямо из индекса (`Index Only Scan`), не заглядывая в саму таблицу.
*   **Частичные индексы (Partial Indexes):**
    Если вы часто ищете только "активные" заказы, создайте индекс `CREATE INDEX idx_active_orders ON orders (id) WHERE status = 'active';`. Он будет крошечным и сверхбыстрым.

---

### Итоговая таблица выбора

| Ситуация | Что делать? | Почему? |
| :--- | :--- | :--- |
| Индекс есть, но не используется | `ANALYZE` | Скорее всего, устарела статистика. |
| Типы данных не совпадают | Явное приведение типов (`::type`) | Индекс не работает, если типы не идентичны. |
| Нужно "заставить" любой ценой (тест/эксперимент) | `SET enable_seqscan = off` | Это аналог `FORCE INDEX`, но опасен в продакшене. |
| Запрос всегда медленный на больших данных | Переписать запрос или создать покрывающий индекс | Это устраняет первопричину, а не симптом. |

**Мой вердикт:** В PostgreSQL я никогда не использую `enable_seqscan = off` в постоянном коде приложения. Это "костыль". Если планировщик игнорирует индекс, я сначала лечу статистику (`ANALYZE`), затем проверяю типы данных, и только если ничего не помогает — пересматриваю структуру индекса или сам запрос.

## Q25 · Провокации

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

Ответ на этот вопрос может удивить: **влияние `strict_types=1` на производительность практически равно нулю, а в некоторых специфических сценариях оно может даже слегка ускорить выполнение кода.**

Если говорить о цифрах, то разница в типичных веб-приложениях составляет **менее 0.1%**, что на практике невозможно измерить без сверхточных инструментов и миллионов итераций.

Вот детальный разбор, почему это так.

### 1. Почему это НЕ замедляет код (Миф о проверках)

Часто думают, что `strict_types` заставляет PHP при каждом вызове функции выполнять тяжелую проверку типов. На самом на деле это не так.

*   **Компиляция в OpCode:** Когда PHP компилирует ваш скрипт в OpCode, он видит объявление `strict_types=1`. Это становится **инструкцией для виртуальной машины Zend**.
*   **Отсутствие "угадывания":** В режиме `strict_types=0` (по умолчанию) PHP вынужден выполнять дополнительные операции при каждом вызове функции: он должен проверить, можно ли безопасно привести тип (например, строку `"10"` в `int 10`). Эти проверки — **дополнительные инструкции процессора**.
*   **Прямая работа:** В режиме `strict_types=1` PHP не тратит время на попытки преобразования. Если тип не совпадает, он сразу выбрасывает `TypeError`. Это более прямой и быстрый путь выполнения.

### 2. Когда это может даже УСКОРИТЬ код?

В современных версиях PHP (8.0+) работает **JIT-компилятор (Just-In-Time)**. 

*   Для JIT-компилятора типизация — это критически важная информация. Если типы строго определены и не меняются (благодаря `strict_types` и `readonly` свойствам), JIT может генерировать гораздо более эффективный машинный код, таквно как он может быть уверен в типах данных, с которыми работает процессор, и не вставлять проверки на приведение типов на уровне машинных инструкций.

### 3. Где может возникнуть задержка? (Реальные причины)

Если вы заметили замедление после включения `strict_types`, причина **не в самом режиме**, а в том, что он **проявил скрытые проблемы архитектуры**:

1.  **Избыточные преобразования в коде:** Если ваш код написан так, что он постоянно "прыгает" между типами (например, вы получаете строку из БД, а потом вручную приводите её к числу, чтобы передать в функцию, которая тоже делает приведение), то вы тратите время на лишние операции, которые раньше скрывались за "магией" PHP.
2.ло **Рефакторинг и ошибки:** Если из-за строгости типов вы начали использовать больше проверок `is_int()`, `is_string()` или `instanceof` внутри функций, чтобы избежать ошибок, то именно эти проверки и замедляют код, а не сам режим `strict_types`.

### Итоговый вывод

**Для меня `strict_types=1` — это не вопрос производительности, а вопрос надежности и чистоты.**

*   **Производительность:** Влияние ничтожно.
*   **Надежность:** Огромный прирост. Вы ловите ошибки на этапе разработки, а не когда пользователь получает "White Screen of Death" из-то того, что в функцию вместо ID пришла пустая строка.
*   **Чистота:** Код становится самодокументированным. Вы точно знаете, что функция принимает, и не гадаете, придет туда `int` или `string`.

**Мой вердикт: Всегда включать `strict_types=1` во всех проектах.**

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

Это утверждение требует важного уточнения: **Doctrine ORM на самом деле поддерживает составные первичные ключи (Composite Primary Keys)**. Вы можете объявить их в сущности, используя несколько атрибутов `#[Id]`.

Однако, существует фундаментальное архитектурное напряжение между идеей **Составного ключа** и философией **Data Mapper**, на которой построена Doctrine. Именно из-за этого «поддержка» кажется неудобной, и многие разработчики (и даже авторы паттернов) советуют их избегать.

### Почему составные ключи — это "боль" в Doctrine?

Проблема не в том, что Doctrine не может их прочитать, а в том, как они ломают привычные механизмы работы ORM:

1.  **Сложность идентификации (Identity Map):** Doctrine использует внутренний кэш (Identity Map), чтобы гарантировать, что для одной записи в БД существует только один объект в памяти. Для этого ей нужен уникальный идентификатор. Если ключ составной, логика сопоставления объектов становится сложнее.
2.  **Сложность связей (Associations):** Если сущность `A` имеет составной ключ, то любая сущность `B`, которая ссылается на `A` через `ManyToOne`, должна будет хранить **все** поля ключа `A` в качестве Foreign Key. Это раздувает таблицы и делает запросы `JOIN` громоздкими.
3.  **Проблемы с Generic-методами:** Многие методы в Symfony и Doctrine (например, `find()`, `remove()`, `merge()`) ожидают один скалярный ID. При работе с составными ключами вам приходится либо передавать массив, либо использовать более сложные методы, что нарушает единообразие кода.
4. pivot-таблицы (Many-to-Many): В связях Many-to-Many Doctrine сама управтляет промежуточной таблицей, и попытка навязать там сложную логику составных ключей часто приводит к конфликтам с механизмом автоматического управления связями.

---

### Как с этим "живут" в реальных проектах? (Три стратегии)

Если вы столкнулись с необходимостью использовать составные ключи (например, при проектировании связи Many-to-Many с дополнительными полями или при работе с legacy-базой), у вас есть три пути:

#### 1. Surrogate Key (Суррогатный ключ) — Рекомендуемый путь
Это золотой стандарт современного проектирования. Вместо того чтобы использовать составной ключ (например, `order_id` + `product_id`), вы добавляете в таблицу одну техническую колонку `id` (автоинкремент или UUID).

*   **Как это выглядит:** Составные поля остаются, но они больше не являются первичным ключом. Они становятся просто уникальным индексом (`UNIQUE constraint`).
*   **Плюсы:** Идеальная совместимость с Doctrine, простые связи, легкость в управлении объектами.
*   **Минусы:** Лишняя колонка в БД (но для современных БД это ничтожная цена).

#### 2. Использование Composite Identifier (Если нельзя изменить БД)
Если вы работаете с существующей базой, где ключи уже составные, вы используете возможности Doctrine, но принимаете все неудобства.

```php
#[Entity]
class OrderItem {
    #[Id, Column]
    private int $orderId;

    #[Id, Column]
    private int $productId;

    // Работа с таким объектом в репозитории будет выглядеть так:
    // $repo->find(['orderId' => 1, 'productId' => 5]);
}
```
*   **Когда использовать:** Только в интеграционных задачах с Legacy-системами.

#### 3. Вынос связи в отдельную сущность (Entity-per-Relation)
Если ваша составная связь — это не просто "связь", а полноценный объект с поведением (например, `Subscription` между `User` и `Plan`), вы превращаете эту связь в самостоятельную сущность с собственным суррогатным ID.

*   **Вместо:** Таблица `user_plans` с ключами `user_id` и `plan_id`.
*   **Делаем:** Сущность `Subscription` с `id`, `user_id` и `plan_id`.

---

### Итоговое резюме

| Подход | Когда применять | Вердикт |
| :--- | :--- | :--- |
| **Surrogate Key (UUID/ID)** | Все новые проекты | **Best Practice.** Проще, быстрее, надежнее. |
| **Composite Key** | Legacy-базы, где нельзя менять структуру | **Necessary Evil.** Работает, но усложняет код. |
| **Entity-per-Relation** | Когда связь — это важный бизнес-объект | **Архитектурно правильно.** Помогает соблюдать DDD. |

**Мой совет:** Всегда начинайте с суррогатного ключа (`id`). Составные ключи — это признак того, что вы пытаетесь моделировать связи на уровне базы данных, а не на уровне бизнес-сущностей.

## Q27 · Мини-код-ревью

**Интервьюер:** Посмотри на этот код:

```php
class OrderController
{
    public function pay(Request $req): Response
    {
        $id = $req->get('order_id');
        $pdo = DB::connect();

        if (!$order) {
            return new Response('not found', 404);
        }

```

Какие проблемы ты видишь и как бы ты этот код переделал? С чего начал бы и почему?

**Кандидат:**

Этот код — классический пример «спагетти-кода», который нарушает почти все принципы чистого программирования. Он небезопасен, его невозможно тестировать, и он крайне хрупок.

### 1. Список проблем

Я разделю их на три категории:

**А) Безопасность (Критично):**
*   **SQL Injection:** Переменная `$id` вставляется напрямую в строку запроса. Злоумышленник может передать `1 OR 1=1` и манипулировать базой. Это дыра в безопасности.

**Б) Нарушение архитектурных принципов (Design Smells):**
*   **Нарушение SRP (Single Responsibility Principle):** Контроллер делает **всё**: обрабатывает HTTP, работает с БД (SQL), управляет бизнес-логикой (статус заказа), отправляет письма и логирует.
*   **Нарушение инкапсуляции:** Логика изменения заказа (статус) размазана по контроллеру. Мы не можем гарантировать, что статус изменится правильно в другом месте приложения.
*   **Жесткая зависимость (Tight Coupling):** Контроллер жестко привязан к глобальным классам `DB`, `Mailer` и `Logger`. Мы не можем протестировать этот контроллер без поднятия реальной базы, почтового сервера и системы логирования.

**В) Надежность и чистота:**
*   **Отсутствие транзакционности:** Если `Mailer::send()` упадет с ошибкой, статус в базе останется `paid`, но пользователь не получит письмо. Или наоборот: если база упадет после отправки письма, мы получим десинхронизацию.
*   **Смешивание уровней:** Контроллер знает о структуре таблицы (`status`, `email`), что делает его зависимым от схемы БД.

### 2. Как бы я это переделал?

Я бы применил многослойную архитектуру (Layered Architecture) с использованием паттернов **Repository**, **Service (Use Case)** и **Domain Entity**.

#### Шаг 1: Создание Доменной сущности (Entity)
Сначала выносим логику изменения заказа в сам объект.

```php
class Order {
    private int $id;
    private string $status;
    private string $email;

    public function pay(): void {
        // Здесь может быть бизнес-валидация (например, нельзя оплатить отмененный заказ)
        if ($this->status === 'cancelled') {
            throw new OrderAlreadyCancelledException();
        }
        $this->status = 'paid';
    }
    
    // Геттеры...
}
```

#### Шаг 2: Создание Репозитория (Repository Interface)
Определяем, как мы работаем с данными, не привязываясь к SQL.

```php
interface OrderRepositoryInterface {
    public function findById(int $id): ?Order;
    public function save(Order $order): void;
}
```

#### Шаг 3: Создание Сервиса (Use Case)
Создаем класс, который оркестрирует процесс оплаты.

```php
class PayOrderService {
    public function __construct(
        private OrderRepositoryInterface $repository,
        private MailerInterface $mailer,
        private LoggerInterface $logger
    ) {}

    public function execute(int $orderId): void {
        // Вся логика в одной транзакции (чеветка через EntityManager или транзакцию БД)
        $this->repository->transactional(function() use ($orderId) {
            $order = $this->repository->findById($orderId);
            if (!$order) {
                throw new OrderNotFoundException($orderId);
            }

            $order->pay();
            $this->repository->save($order);
            
            // Отправляем письмо (лучше через очередь/событие, но здесь для простоты)
            $this->mailer->send($order->getEmail(), 'Ваш заказ оплачен');
            $this->logger->info("Order paid: " . $order->getId());
        });
    }
}
```

#### Шаг 4: Чистый Контроллер
Теперь контроллер только принимает запрос и отдает ответ.

```php
class OrderController extends AbstractController 
{
    public function __construct(
        private PayOrderService $payOrderService
    ) {}

    public function pay(Request $req): Response 
    {
        $id = (int) $req->get('order_id');

        try {
            $this->payOrderService->execute($id);
            return new Response('ok', 200);
        } catch (OrderNotFoundException $e) {
            return new Response('not found', 404);
        } catch (\Exception $e) {
            return new Response('error', 500);
        }
    }
}
```

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Эта сущность — классический пример нарушения почти всех фундаментальных принципов проектирования доменных моделей. В ней смешаны разные слои приложения, что делает её «грязной» и труднотестируемой.

### Что не так (Анализ нарушений)

**1. Нарушение принципа инкапсуляции и ответственности (SRP):**
Сущность `User` теперь не просто описывает данные пользователя, она отвечает за **сохранение самой себя в базу данных**. Это смешивание **Domain Layer** (бизменная логика) и **Infrastructure Layer** (работа с БД через `EntityManager`).

**2. Нарушение правила чистоты Домена (Dependency Rule):**
Доменная сущность не должна знать о существовании инфраструктурных объектов, таких как `EntityManagerInterface`. Это делает ваш домен «загрязненным» зависимостями от фреймворка (Symfony/Doctrine).

**3. Невозможность Unit-тестирования:**
Чтобы протестировать простой метод `changeEmail`, вам теперь нужно создать или замокать тяжелый `EntityManagerInterface`. Сущность больше не является "чистым" PHP-объектом; она не может сущежить в отрыве от инфраструктуры.

**4. Нарушение транзакционной целостности:**
Вызов `$this->em->flush()` внутри метода сущности — это очень опасно. Если этот метод вызывается внутри другого процесса, который тоже управляет транзакцией, вы можете совершить преждевременный `commit`, что приведет к частичному сохранению данных и нарушению атомарности.

**5. Нарушение концепции Identity:**
Сущность не имеет идентификатора (`id`). В DDD сущность — это объект, который обладает идентичностью. Без `id` вы не сможете надежно отличить двух пользователей с одинаковым email.

---

### Как бы я это исправил

Я бы разделил ответственность: сущность будет хранить состояние и правила, а сохранение будет делегировано репозиторию.

#### 1. Чистая Доменная Сущность (Domain Layer)
Она становится "глупой" относительно БД, но "умной" относительно своих правил.

```php
#[ORM\Entity]
class User
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 180, unique: true)]
    private string $email;

    public function __construct(string $email)
    {
        // Валидация прямо в конструкторе гарантирует валидное состояние
        $this->validateEmail($email);
        $this->email = $email;
    }

    public function changeEmail(string $newEmail): void
    {
        $this->validateEmail($newEmail);
        $this->email = $newEmail;
    }

    private function validateEmail(string $email): void
    {
        if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
            throw new \InvalidArgumentException("Invalid email format");
        }
    }

    public function getId(): ?int { return $this->id; }
    public function getEmail(): string { return $this->email; }
}
```

#### 2. Репозиторий (Interface в Domain, Implementation в Infrastructure)
Интерфейс описывает, *что* мы хотим сделать, а Doctrine реализует это *как*.

```php
// В слое Domain
interface UserRepositoryInterface 
{
    public function save(User $user): void;
    public function findById(int $id): ?User;
}

// В слое Infrastructure (реализация)
class DoctrineUserRepository implements UserRepositoryInterface 
{
    public function __construct(private EntityManagerInterface $em) {}

    public function save(User $user): void {
        $this->em->persist($user);
        $this->em->flush(); // Flush вызывается здесь или в Application Service
    }

    public function findById(int $id): ?User {
        return $this->em->find(User::class, $id);
    }
}
```

#### 3. Прикладной сервис (Application Layer)
Он оркестрирует процесс: находит объект, меняет его и просит репозиторий сохранить.

```php
class ChangeUserEmailService 
{
    public function __construct(
        private UserRepositoryInterface $userRepository
    ) {}

    public function execute(int $userId, string $newEmail): void 
    {
        $user = $this->userRepository->findById($userId);
        
        if (!$user) {
            throw new UserNotFoundException($userId);
        }

        $user->changeEmail($newEmail);
        
        // Сохранение происходит через репозиторий, а не через саму сущность
        $this->userRepository->save($user);
    }
}
```

### Итог изменений:
1.  **Тестируемость:** Теперь я могу написать Unit-тест на `User`, просто создав `new User('test@test.com')`. Мне не нужна база.
2.  **Чистота:** `User` ничего не знает о Doctrine. Если мы решим перейти с SQL на MongoDB, класс `User` не изменится.
3.  **Надежность:** Валидация email теперь гарантирована на уровне конструктора и метода изменения.
4.  **Архитектура:** Мы четко разделили: **Domain** (правила), **Application** (сценарии), **Infrastructure** (сохранение).

## Q29 · Процесс и рассуждение

**Интервьюер:** Тебе нужно решить техническую проблему на незнакомых тебе технологии или стеке. Опиши последовательность своих действий от первого взгляда на задачу до уверенного ответа о сроках решения. Когда, по-твоему, нужно просить помощи у команды, а когда разбираться самому?

Столкнуться с неизвестным стеком — это нормальная часть работы Senior-разработчика. Мой подход базируется на минимизации «времени блуждания» (wandering time) и переходе от хаотичного изучения к системному анализу.

Вот мой алгоритм действий:

### 1. Фаза исследования (Исследование «Черного ящика»)

Прежде чем лезть в код, я пытаюсь понять контекст.

*   **Анализ документации и экосистемы:** Я ищу официальную документацию, примеры использования и типичные паттерны в этом стеке. Моя цель — понять ментальную модель: как здесь устроены циклы жизни объектов, как работает DI, как происходит работа с данными.
*   **Локальное окружение (Hello World):** Я разворачиваю минимальный рабочий пример (PoC) на этом стеке. Если я не могу запустить простейший скрипт, я не могу решать задачу.
*   **Чтение существующего кода:** Я ищу в проекте примеры реализации похожих задач. Это лучший способ понять, какие внутренние соглашения (conventions) приняты в данной конкретной кодовой базе.

### 2. Фаза гипотез (Метод проб и ошибок)

Когда я понимаю основы, я перехожу к активному кодингу.

*   **Изоляция проблемы:** Я создаю минимально воспроизводимый пример (Minimal Reproducible Example). Если проблема в интеграции, я пытаюсь воспроизвести её в отдельном изолированном скрипте.
*   **Проверка гипотез:** Я формулирую гипотезу («Я думаю, это происходит из-за race condition в этом сервисе») и проверяю её с помощью логов, отладки (Xdebug) или инструментов профилирования.
*   **Метод исключения:** Я отключаю части системы, чтобы понять, где именно локализована проблема.

### 3. Фаза оценки (Оценка сроков)

Я никогда не называю срок, пока не пройду этап **Proof of Concept (PoC)**.

*   **Не говорите «Я сделаю это за 2 часа»**, если вы еще не написали ни одной строчки кода, которая работает.
*   **Метод «Спирали»:** Я сначала оцениваю время на исследование (Spike), затем на реализацию, а затем добавляю буфер на тесты и возможные сложности.
*   **Формула оценки:** `(Время на исследование + Время на реализацию + Время на тесты) * Коэффициент неопределенности`. Если стек совсем новый, коэффициент может быть 1.5 или 2.

### Когда разбираться самому, а когда просить помощи?

Это вопрос управления рисками и стоимостью рабочего времени компании.

#### Разбираться самому, если:
1.  **Это вопрос синтаксиса или API:** Я просто загляну в документацию или StackOverflow.
2.  **Проблема в рамках моей компетенции:** Я понимаю концепцию, но не знаю конкретного метода. Это вопрос времени, а не знаний.
3.  **Я нахожусь в фазе исследования:** Если я еще не понял, *почему* это не работает, я должен сначала попытаться локализовать проблему.

#### Просить помощи (Escalation), если:
1.  **«Стена» (Time-boxing):** Я установил себе лимит (например, 2 часа) на изучение конкретного вопроса, и за это время не продвинулся ни на шаг. **Нельзя сидеть над задачей весь день в молчании.**
2.  **Риск архитектурного решения:** Я нашел решение, но оно кажется мне сомнительным или нарушает принципы проекта. Мне нужно подтверждение от команды, чтобы не делать лишнюю работу.
3.  **Непонятный контекст бизнеса:** Я понимаю техническую часть, но не понимаю, *зачем* мы это делаем и какие побочные эффекты это может вызвать для других модулей.
4. way **Проблема инфраструктуры:** Если я вижу, что проблема не в моем коде, а в настройках CI/CD, Docker или конфигурации БД, я не трачу время на попытки «починить код», а иду к DevOps/SRE.

**Мое золотое правило:** *«Лучше задать "глупый" вопрос через час, чем потратить два дня на решение задачи неверным способом»*. В профессиональной среде ценится не тот, кто знает всё, а тот, кто умеет эффективно находить решения и вовремя сигнализирует о рисках.

### 2. Структура сообщения (Как я это преподнесу)
Я не прихожу с проблемой «я не успеваю». Я прихожу с **анализом и вариантами решения**. Мой отчет менеджеру или заказчику будет состоять из четырех частей:

*   **Что произошло (The Reality):** «В процессе реализации задачи X выяснилось, что архитектура текущего модуля требует рефакторинга (или возникла непредвиденная сложность с API), что увеличивает объем работ».

    *   *Вариант В (Декомпозиция):* «Мы можем выкатить часть задачи завтра, а вторую часть отложить».
*   **Моя рекомендация (The Recommendation):** Я всегда предлагаю тот вариант, который, по моему мнению, наиболее выгоден для проекта. Например: «Я рекомендую вариант А, так так качество кода и стабильность системы сейчас приоритетнее».

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

Это вопрос о поиске баланса между **Engineering Excellence** (инженерным совершенством) и **Business Value** (бизнес-ценностью). В реальном проекте «идеальный код» — это враг «работающего продукта».

Мой подход базируется на понимании того, что **код — это затраты, а не актив**. Каждый лишний час рефакторинга — это час, не потраченный на фичи.

### 1. Когда код «достаточно хорош» (Definition of Done)

Я считаю задачу завершенной, когда она достигает следующих критериев:

*   **Функциональность:** Она полностью соответствует критериям приемки (Acceptance Criteria).
*   **Надежность:** Код покрыт тестами (Unit/Integration), которые проверяют не только «счастливый путь», но и граничные условия (edge cases).
*   **Безопасность:** В коде нет очевидных уязвимостей (SQL-инъекций, XSS и т.д.).
*   **Поддерживаемость:** Код соответствует принятым в команде стандартам (Style Guide, архитектурные паттерны). Он достаточно чист, чтобы другой разработчик мог его понять без моей помощи.
*   **Производительность:** Код не нарушает установленные SLA (например, время ответа API).

Если эти пункты выполнены — код готов к релизу. Дальнейшее «вылизывание» — это **Overengineering**.

---

### 2. Как я соблюдаю баланс (Стратегии)

Чтобы не превратить разработку в бесконечный процесс рефакторинга, я использую три стратегии:

#### А. Правило бойскаута (Boy Scout Rule)
*«Оставь место стоянки чуть чище, чем оно было до тебя».*
Если я делаю задачу и вижу мелкое нарушение (плохое имя переменной, лишний `if`), я исправляю это **сразу**. Это не требует отдельного планирования, но предотвращает постепенную деградацию кодовой базы (Technical Debt).

#### Б. Разделение «Должно» и «Хотелось бы» (Must vs Could)
При планировании задачи я всегда разделяю её на:
1.  **Core (Must):** То, что нужно для работы фичи и стабильности.
2.  **Refactoring/Cleanup (Could):** То, что сделало бы код идеальным, но не критично.
Если время поджимает, я оставляю пункт "Could" на следующий спринт или на время, когда будет "окно" между задачами.

#### В. Управление техническим долгом (Technical Debt Management)
Я осознаю, что иногда **намеренно** создаю технический долг.
*   *Пример:* Нам нужно срочно выкатить фичу, чтобы не потерять клиента. Мы пишем решение "в лоб", без идеальной архитектуры.
*   **Мое правило:** Такой долг должен быть задокументирован. Я создаю тикет в бэклоге (Technical Debt Ticket) с описанием: «Здесь костыль, нужно отрефакторить, когда будет время». Это превращает «случайный мусор» в «управляемый кредит».

---

### 3. Когда стоит продолжать улучшать (Red Flags)

Я понимаю, что «достаточно хорошо» превратилось в «плохо» и пора останавливаться и рефакторить, если:

1.  **Сложность растет экспоненциально:** Каждая новая фича в этом модуле занимает в 2 раза больше времени, чем предыдущая. Это признак того, что код стал слишком запутанным.
2.  **Рост количества багов:** Мы постоянно фиксим одно и то же место. Это значит, что архитектура не выдерживает изменений.
3.  **Трудности с тестированием:** Написание теста на новую фичу превращается в пытку из-за огромного количества моков.
