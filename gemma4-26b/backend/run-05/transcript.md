## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

Для написания чистого и надежного кода я выделяю возможности, которые направлены на три цели: **уменьшение объема шаблонного кода (boilerplate)**, **усиление типизации** и **упрощение логики**. Чем меньше кода мы пишем вручную, тем меньше мест, где может спрятаться ошибка.

Вот мои фавориты:

### 1. Constructor Property Promotion (PHP 8.0)
Это, пожалуй, самое заметное улучшение для чистоты кода. Оно избавляет от необходимости дублировать свойства в объявлении класса, аргументах конструктора и внутри самого конструктора. Это делает DTO и сервисы гораздо лаконичнее.

```php
// До PHP 8.0
class UserRegistrationService {
    private UserRepository $repository;
    private MailerInterface $mailer;

    public function __construct(UserRepository $repository, MailerInterface $mailer) {
        $this->repository = $repository;
        $this->mailer = $mailer;
    }
}

// PHP 8.0+
class UserRegistrationService {
    public function __construct(
        private UserRepository $repository,
        private MailerInterface $mailer,
    ) {}
}
```

### 2. Union Types и Intersection Types (PHP 8.0, 8.1)
Типизация — фундамент надежности. **Union Types** позволяют явно указать, что переменная может быть одного из нескольких типов, что избавляет от использования `mixed` или запутанных проверок `is_int()`. **Intersection Types** (PHP 8.1) позволяют требовать, чтобы объект реализовывал сразу несколько интерфейсов, что критично для строгого соблюдения контрактов.

```php
// Union Types: Явное указание возможных типов
public function processId(int|string $id): void { ... }

// Intersection Types: Объект должен быть и Logger, и Authenticator одновременно
public function registerService(LoggerInterface&AuthenticatorInterface $service): void { ... }
```

### 3. Match Expression (PHP 8.0)
В отличие от `switch`, `match` является выражением (возвращает значение) и использует строгое сравнение (`===`). Это делает код более функциональным, уменьшает вероятность ошибок из-за неявного приведения типов и избавляет от необходимости писать `break`.

```php
// Вместо громоздкого switch
$statusLabel = match ($status) {
    Status::ACTIVE => 'Активен',
    Status::PENDING => 'В ожидании',
    Status::ARCHIVED => 'Архивирован',
    default => throw new \InvalidArgumentException('Неизвестный статус'),
};
```

### 4. Readonly Properties (PHP 8.1/8.2)
Это важнейшая фича для реализации **Immutability** (неизменяемости). В DDD и чистой архитектуре это позволяет создавать Value Objects, которые гарантированно не изменят свое состояние после создания. Это радикально снижает количество побочных эффектов в системе.

```php
readonly class Money {
    public function __construct(
        public int $amount,
        public string $currency,
    ) {}
}

$price = new Money(100, 'USD');
// $price->amount = 200; // Fatal Error: Cannot modify readonly property
```

### 5. Nullsafe Operator (PHP 8.0)
Позволяет избежать "пирамид" из проверок на `null`. Это делает цепочки вызовов читаемыми, не нарушая при этом надежность кода.

```php
// Вместо:
$country = null;
if ($user !== null && $user->getAddress() !== null) {
    $country = $user->getAddress()->getCountry();
}

// PHP 8.0+:
$country = $user?->getAddress()?->getCountry();
```

**Итог:** Эти возможности позволяют сместить фокус с написания инфраструктурного кода (обработка null, типизация, присваивание свойств) на описание **бизнес-логики**, делая её более явной и защищенной от ошибок на уровне синтаксиса.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

Система типов в PHP — это гибридная модель: она динамическая по своей природе, но за последние годы стала всё более строгой. Понимание того, как PHP обрабатывает типы «под капотом», критически важно для предотвращения трудноуловимых багов.

### 1. Как работают приведения типов (Coercive mode)
По умолчанию PHP работает в **коэрцитивном (приводящем) режиме**. Это значит, что если вы передаете аргумент, который не совпадает с объявленным типом, PHP попытается «мягко» преобразовать его, если это кажется ему логичным.

```php
function setAge(int $age): void {
    echo "Age is: " . $age;
}

setAge("25"); // Работает! PHP преобразует строку "25" в int 25.
setAge("abc"); // Fatal Error: TypeError (здесь преобразование невозможно).
```

### 2. Что дает `declare(strict_types=1);`
Эта директива переводит PHP в режим **строгой типизации** для текущего файла. Теперь PHP не будет пытаться приводить типы автоматически. Если тип не совпадает на 100% (с учетом возможности расширения, например, если передать дочерний класс вместо родителя), будет выброшен `TypeError`.

**Важный нюанс:** `strict_types` работает для **вызывающей** стороны. Если файл `A.php` вызывает функцию из файла `B.php`, и в `A.php` включен strict mode, то приведение типов не произойдет, даже если в `B.php` его нет.

```php
declare(strict_types=1);

function setAge(int $age): void {
    echo $age;
}

setAge("25"); // Fatal Error: TypeError (строка не является int)
```

### 3. Типичные ловушки на практике

#### Ловушка №1: Сравнение с `0` и `null` (Weak typing)
В PHP до 8.0 сравнение `0 == 'apple'` возвращало `true` из-за странных правил приведения строк к числам. В PHP 8.0+ это поведение исправили, но использование нестрогого сравнения `==` всё еще остается источником багов.

#### Ловушка №2: Смешивание типов в массивах
PHP не умеет типизировать содержимое массивов на уровне ядра (например, нельзя написать `array<int>`). Если вы ожидаете массив чисел, а пришла строка, вы узнаете об этом только в момент выполнения кода, когда начнете делать математические операции. Это решается через **DTO** или **Collection objects**.

#### Ловушка №3: Возврат `null` (The Billion Dollar Mistake)
Если метод объявлен как `public function getName(): string`, а он возвращает `null` (например, из-за ошибки в БД), это вызовет `TypeError`. Разработчики часто забывают использовать nullable-тип `?string`, что приводит к падениям в неожиданных местах.

---

### Примеры: где типизация спасает и где удивляет

#### Где типизация спасает: Защита инвариантов
Представьте, что мы работаем с финансовой системой. Без строгой типизации ошибка в логике может привести к передаче строки вместо числа, что в итоге «проглотится» и превратится в `0`, исказив баланс.

```php
declare(strict_types=1);

class Wallet {
    public function __construct(private int $balance) {}

    public function deposit(int $amount): void {
        $this->balance += $amount;
    }
}

$wallet = new Wallet(100);
$wallet->deposit("50"); // Ошибка сразу! Мы не дадим применить "грязные" данные к деньгам.
```

#### Где типизация удивляет: Полиморфизм и наследование
Новички часто удивляются, почему код, который кажется правильным, падает при наследовании или использовании расширений.

```php
class Animal {}
class Dog extends Animal {}

function processAnimal(Animal $animal): void {
    echo "Processing...";
}

function processDog(Dog $dog): void {
    echo "Processing dog...";
}

$myDog = new Dog();

processAnimal($myDog); // Работает (Liskov Substitution Principle)

// А вот тут ловушка:
function takeAnimalOrDog(Animal|Dog $animal): void {} // Ok
// Но если мы используем Intersection types (PHP 8.1):
// interface CanBark {}
// class Dog extends Animal implements CanBark {}
// function bark(Animal&CanBark $animal) {} 
// Если передать объект, который не реализует оба интерфейса — будет TypeError.
```

**Резюме для собеседования:**
Я всегда использую `declare(strict_types=1);` во всех проектах. Я считаю, что лучше получить `TypeError` на этапе интеграционного теста, чем получить непредсказуемое поведение бизнес-логики из-за того, что PHP «решил» за нас, как преобразовать строку в число.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

Проектирование обработки исключений — это вопрос не «как поймать ошибку», а «как сообщить о проблеме, не нарушая архитектуру». Я придерживаюсь принципа: **исключение — это не способ управления потоком выполнения (flow control), а способ сообщения о невозможности выполнения задачи.**

Вот мой подход к проектированию этой системы:

### 1. Иерархия собственных исключений
Я никогда не использую стандартные `\Exception` или `\RuntimeException` напрямую в бизнес-логике. Вместо этого я создаю дерево исключений, привязанное к слоям приложения.

*   **Domain Exceptions:** Это исключения, которые описывают нарушение бизнес-правил. Они являются частью контракта. Например: `InsufficientFundsException`, `UserAlreadyExistsException`.
*   **Application Exceptions:** Ошибки на уровне сценариев использования (Use Cases). Например: `OrderProcessingFailedException`.
*   **Infrastructure Exceptions:** Ошибки внешнего мира (БД, API, Filesystem). Они не должны просачиваться в Domain-слой.

**Пример структуры:**
```text
App\Exception\
├── Domain\
│   ├── DomainException (Base)
│   │   └── InsufficientFundsException
├── Application\
│   ├── ApplicationException (Base)
│   │   └── PaymentGatewayTimeoutException
└── Infrastructure\
    └── InfrastructureException (Base)
```

### 2. Оборачивание (Exception Wrapping) и Abstraction
Это критически важный момент для соблюдения чистоты архитектуры. Если мой репозиторий (Infrastructure слой) использует Doctrine, он не должен выбрасывать `Doctrine\ORM\Exception`. Если это произойдет, мой Domain-слой внезапно станет зависимым от Doctrine.

**Правило:** Я оборачиваю низкоуровневые исключения в высокоуровневые, соответствующие слою.

```php
// В Infrastructure слое (Repository)
try {
    $this->entityManager->flush();
} catch (\Doctrine\ORM\ORMException $e) {
    // Оборачиваем: сохраняем оригинальное исключение для отладки через $previous
    throw new RepositoryWriteException("Failed to save user", 0, $e);
}
```
Это позволяет вызывающему коду (Application/Domain) обрабатывать ошибку, не зная о деталях реализации БД.

### 3. Исключение как контракт метода
В чисто архитектурных подходах (DDD/Clean Architecture) важно понимать: **что метод обязан выбросить?**

*   Если метод `withdraw(int $amount)` может не иметь денег на счету, то `InsufficientFundsException` — это **часть его контракта**. Я должен явно задокументировать это (в PHPDoc или через понимание логики), и вызывающий код **обязан** его обработать.
*   Если метод `save()` может упасть из-за диска — это инфраструктурная деталь, которая обычно обрабатывается глобальным обработчиком (Exception Listener/Middleware).

### 4. Антипаттерны, которых я избегаю

1.  **Использование исключений для логики (Flow Control):** 
    *   *Плохо:* `try { $user = $repo->find($id); } catch (NotFoundException $e) { ... }`
    *   *Хорошо:* `$user = $repo->findByIdOrNull($id);` (Возврат `null` — это нормальное состояние, а не ошибка).
2.  **«Глотание» исключений (Silent Catch):**
    *   *Плохо:* `catch (\Exception $e) { }` — это делает отладку невозможной. Если и ловить, то только для логирования или трансформации.
3.  **Слишком общие исключения:**
    *   *Плохо:* Выбрасывать везде `\Exception`. Это заставляет обработчик ловить всё подряд, включая критические ошибки самого PHP (например, нехватку памяти), которые не нужно «обрабатывать» логикой.
4.  **Отсутствие контекста:**
    *   *Плохо:* `throw new Exception("Error occurred");`
    *   *Хорошо:* `throw new UserNotFoundException("User with ID {$id} not found", $id);` (Передача ID или других данных в конструктор исключения).
5.  **Нарушение цепочки (Lost Stack Trace):**
    *   *Плохо:* При перехвате исключения создавать новое, забывая передать `$previous`. Мы теряем историю того, где на самом деле произошел сбой.

### Итог
Моя стратегия: **Domain слой диктует свои исключения, Infrastructure слой маскирует свои, а Application слой управляет их трансформацией в понятные пользователю ответы (например, через Symfony Kernel Exception Listeners, превращающих исключение в JSON-ответ с нужным HTTP-статусом).**

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

По моему опыту, чаще всего в реальных проектах нарушается **Single Responsibility Principle (SRP)** — принцип единственной ответственности.

### Почему это происходит?
Разработчики часто поддаются искушению «удобства». Проще всего добавить метод отправки письма или логирования прямо в сервис, который отвечает за бизнес-логику, потому что «так быстрее» и «все переменные под рукой». Это приводит к созданию так называемых **God Objects** (Божественных объектов) — классов, которые знают слишком много и делают слишком много.

В итоге код становится хрупким: вы хотите изменить способ отправки уведомлений, но внезапно рискуете сломать логику расчета налогов, потому что они «сшиты» в одном классе.

---

### Типовой пример нарушения (SRP)

Представим сервис регистрации пользователя. Он делает три вещи: сохраняет в БД, отправляет Email и логирует действие.

```php
class UserRegistrationService {
    public function register(array $userData): void {
        // 1. Валидация (бизнес-логика)
        if (empty($userData['email'])) {
            throw new \InvalidArgumentException("Email is required");
        }

        // 2. Работа с БД (инфраструктура)
        // Представим, что здесь прямой вызов PDO или Doctrine
        $sql = "INSERT INTO users (email) VALUES (:email)";
        // ... выполнение запроса ...

        // 3. Отправка Email (внешний сервис)
        $mailer = new PHPMailer(); 
        $mailer->isSMTP();
        $mailer->addAddress($userData['email']);
        $mailer->Body = "Welcome!";
        $mailer->send();

        // 4. Логирование (инфраструктура)
        file_put_contents('app.log', "User registered: " . $userData['email'], FILE_APPEND);
    }
}
```

**Проблемы этого кода:**
1.  **Низкая тестируемость:** Чтобы протестировать регистрацию, вам нужно иметь доступ к БД, почтовому серверу и файловой системе.
2.  **Жесткая зависимость:** Мы привязаны к конкретной реализации `PHPMailer` и записи в файл.
3.  **Сложность изменения:** Если завтра мы заменим почту на SMS, нам придется менять класс, отвечающий за регистрацию.

---

### Рефакторинг (Соблюдение SRP и DI)

Мы разделяем ответственность, делегируя выполнение задач специализированным сервисам через интерфейсы.

```php
// Интерфейсы (контракты)
interface UserRepositoryInterface {
    public function save(User $user): void;
}

interface NotificationServiceInterface {
    public function sendWelcomeNotification(User $user): void;
}

interface LoggerInterface {
    public function log(string $message): void;
}

// Чистый сервис регистрации
class UserRegistrationService {
    public function __construct(
        private UserRepositoryInterface $userRepository,
        private NotificationServiceInterface $notificationService,
        private LoggerInterface $logger
    ) {}

    public function register(User $user): void {
        // Сервис теперь только управляет процессом (оркестрация)
        
        // 1. Сохраняем (делегируем репозиторию)
        $this->userRepository->save($user);

        // 2. Уведомляем (делегируем сервису уведомлений)
        $this->notificationService->sendWelcomeNotification($user);

        // 3. Логируем (делегируем логгеру)
        $this->logger->log("User registered: " . $user->getEmail());
    }
}
```

### Что изменилось?
1.  **Единственная ответственность:** `UserRegistrationService` теперь отвечает только за *процесс* регистрации. Он не знает, *как* сохраняется пользователь и *как* отправляется письмо.
2.  **Легкое тестирование:** В Unit-тестах мы можем легко подложить "заглушки" (Mocks/Stubs) для всех интерфейсов. Нам не нужен реальный SMTP-сервер.
3.  **Гибкость (Open/Closed Principle):** Если мы захотим отправлять уведомления через Telegram, мы просто создадим `TelegramNotificationService`, реализующий `NotificationServiceInterface`, и пробросим его в конструктор. Сам класс `UserRegistrationService` менять **не придется**.
4.  **Читаемость:** Код стал декларативным. Глядя на метод `register`, мы сразу видим высокоуровневые шаги процесса, не отвлекаясь на детали реализации.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Короткий ответ: **Да, можно.** 

В инженерной среде существует понятие **Engineering Trade-offs** (инженерный компромисс). Любое решение в разработке — это выбор между скоростью, стоимостью, сложностью и качеством. Принципы SOLID — это не законы физики, а руководства по минимизации стоимости поддержки кода в долгосрочной перспективе.

Если вы будете следовать SOLID фанатично в каждой строчке кода, вы рискуете создать **Overengineered** (переусложненный) проект, который будет невозможно запустить вовремя или в котором будет слишком много «магии» и абстракций для простых задач.

Вот три сценария, когда нарушение принципов может быть оправданным:

### 1. Прототипирование и MVP (Proof of Concept)
Когда ваша цель — проверить гипотезу бизнеса за 2 недели, вам не нужна идеальная иерархия интерфейсов и внедрение зависимостей через DI-контейнер. 

*   **Нарушение:** Вы пишете монолитный класс, где всё перемешано (нарушение SRP), и используете жесткие зависимости (нарушение DIP).
*   **Оправдание:** Скорость выхода на рынок (Time-to-Market) важнее чистоты кода. Если гипотеза провалится, этот код будет удален, и его «грязность» не принесет убытков. Если гипотеза взлетит — у вас будут ресурсы и бюджет на рефакторинг.

### 2. Масштаб и сложность задачи (YAGNI — You Ain't Gonna Need It)
Принцип SOLID часто толкает к созданию абстракций «на будущее».

*   **Нарушение:** У вас есть один класс `FileLogger`, который пишет в локальный файл. Вы чувствуете, что скоро может появиться `SentryLogger` или `CloudWatchLogger`, и начинаете строить сложную иерархию интерфейсов и фабрик (нарушение Open/Closed Principle и Interface Segregation).
*   **Оправдание:** Если вероятность появления второго логгера составляет 1%, то создание абстракции сейчас — это трата времени и усложнение системы без реальной необходимости. Это нарушение принципа **YAGNI**.

### 3. Сверхмалые или вспомогательные скрипты
Если вы пишете одноразовый скрипт для миграции данных из одной таблицы в другую или скрипт для очистки кэша.

*   **Нарушение:** Весь скрипт — это один файл на 50 строк с процедурным кодом и прямыми запросами к БД.
*   **Оправдание:** Стоимость написания чистого, протестированного кода с использованием SOLID здесь будет в 10 раз выше, чем ценность самого скрипта. Сложность поддержки такого кода стремится к нулю, так как он не будет жить в репозитории долго.

---

### Золотое правило (Rule of Thumb)

Я использую подход **"Evolutionary Architecture"** (эволюционная архитектура):

1.  **Пишите просто**, пока сложность системы позволяет это.
2.  **Следите за "запахом кода" (Code Smells).** Как только вы чувствуете, что изменение в одном месте заставляет вас менять код в пяти других — это сигнал, что пора применять SOLID.
3.  **Рефакторинг — это не роскошь, а процесс.** Нарушение принципов на ранних этапах допустимо, если у вас есть план по их исправлению при росте сложности.

**Резюме для собеседования:** 
*«Нарушение SOLID оправдано тогда, когда цена следования принципу (затраты времени и усложнение) превышает потенциальную выгоду от чистоты кода. Главное — не превращать временное нарушение в технический долг, который вы не планируете возвращать».*

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Это отличный вопрос, который проверяет понимание того, что **OCP (Open/Closed Principle)** — это не про ООП-наследование, а про **композицию** и **абстракцию**. Наследование часто является слишком жестким и хрупким инструментом (проблема «хрупкого базового класса»).

Вот основные способы реализации OCP без использования наследования:

### 1. Композиция через Интерфейсы (Strategy Pattern)
Это самый распространенный и правильный способ в современном PHP. Вместо того чтобы расширять класс, мы внедряем в него объект, реализующий определенный интерфейс.

**Пример:** Вам нужно расширить логику расчета стоимости корзины.

```php
// Вместо наследования DiscountedCart от StandardCart...

interface DiscountStrategy {
    public function apply(float $amount): float;
}

class BlackFridayDiscount implements DiscountStrategy {
    public function apply(float $amount): float {
        return $amount * 0.5;
    }
}

class Cart {
    // Мы не меняем класс Cart, мы меняем стратегию (Open for extension)
    public function __construct(
        private DiscountStrategy $discountStrategy 
    ) {}

    public function calculateTotal(float $amount): float {
        return $this->discountStrategy->apply($amount);
    }
}
```
**Почему это OCP:** Чтобы добавить новый тип скидки, мы создаем новый класс стратегии. Класс `Cart` остается закрытым для изменений.

### 2. Композиция через Делегацию (Decorator Pattern)
Декоратор позволяет добавлять поведение объекту, «оборачивая» его. Это позволяет расширять функциональность без изменения исходного класса и без использования наследования.

**Пример:** Добавление логирования к отправке сообщений.

```php
interface Messenger {
    public function send(string $message): void;
}

class EmailMessenger implements Messenger {
    public function send(string $message): void {
        echo "Sending email: $message\n";
    }
}

// Декоратор расширяет поведение, не меняя EmailMessenger
class LoggingMessengerDecorator implements Messenger {
    public function __construct(private Messenger $wrapped) {}

    public function send(string $message): void {
        echo "Log: Attempting to send message...\n";
        $this->wrapped->send($message);
        echo "Log: Message sent successfully.\n";
    }
}

// Использование
$messenger = new LoggingMessengerDecorator(new EmailMessenger());
$messenger->send("Hello!");
```

### 3. Использование Коллекций (Registry / Observer Pattern)
Вы можете реализовать OCP, позволив внешним объектам «подписываться» на события или регистрироваться в системе.

**Пример:** Система плагинов или хуков. Вместо того чтобы прописывать все действия в методе `process()`, вы позволяете регистрировать обработчики.

```php
class OrderProcessor {
    /** @var callable[] */
    private array $hooks = [];

    public function addHook(callable $hook): void {
        $this->hooks[] = $hook;
    }

    public function process(Order $order): void {
        // Основная логика...
        
        // Вызов всех зарегистрированных расширений
        foreach ($this->hooks as $hook) {
            $hook($order);
        }
    }
}

// Теперь мы можем расширять поведение OrderProcessor, 
// просто добавляя новые хуки извне, не меняя сам класс.
```

### 4. Использование атрибутов (Attributes) и Reflection (PHP 8+)
В современных фреймворках (Symfony, Laravel) OCP часто реализуется через метаданные.

Вы можете написать код, который сканирует классы на наличие определенных атрибутов и выполняет действия. Если вам нужно добавить новое поведение (например, новую валидацию), вы просто создаете новый класс и вешаете на него атрибут. Основной движок (движок валидации) менять не нужно — он просто найдет ваш новый атрибут через Reflection.

### Итог: разница подходов

| Способ | Суть | Когда использовать |
| :--- | :--- | :--- |
| **Наследование** | "Я являюсь разновидностью X" | Когда есть жесткая иерархия (редко в чистом коде). |
| **Стратегия** | "Я использую X для выполнения действия" | Когда нужно менять алгоритм на лету. |
| **Декоратор** | "Я оборачиваю X, добавляя ему обертку" | Когда нужно динамически добавлять обязанности. |
| **Хуки/События** | "Я уведомляю всех, кто меня слушает" | Когда нужно расширять систему плагинами. |

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Короткий ответ: **Нет.**

Хотя в контексте ООП чаще всего говорят о классах, принцип единственной ответственности (SRP) в широком смысле относится к **любому модулю системы**, который имеет свою границу. Если у модуля есть «задача» или «причина для изменения», он должен быть сфокусирован на чем-то одном.

Вот где еще необходимо применять SRP:

### 1. Функции и методы
Это самый первый уровень, на который стоит смотреть. Если метод выполняет несколько логических шагов (например: получает данные $\to$ валидирует $\to$ сохраняет $\to$ отправляет email), он нарушает SRP.
*   **Симптом:** Метод становится слишком длинным («God Method»).
*   **Решение:** Разбить метод на несколько маленьких, специализированных функций.

### 2. Модули и пакеты (Packages/Libraries)
На уровне архитектуры приложения целые модули (например, `BillingModule`, `AuthModule`, `InventoryModule`) должны иметь одну зону ответственности.
*   **Нарушение:** Если в модуле `Billing` вы начинаете менять логику генерации PDF-отчетов или настройки подключения к базе данных, модуль становится «всеядным».
*   **Решение:** Выделение функционала в отдельные микросервисы или независимые пакеты (Composer packages).

### 3. Микросервисы
В распределенных системах SRP переходит на уровень сервисов. Один микросервис должен отвечать за один **Bounded Context** (ограниченный контекст в терминах DDD).
*   **Нарушение:** «Распределенный монолит», когда один сервис отвечает и за пользователей, и за заказы, и за складские остатки. Если изменение в логике склада требует деплоя сервиса пользователей — это нарушение SRP на уровне архитектуры.

### 4. Базы данных (Схемы и таблицы)
Даже на уровне данных есть SRP.
*   **Нарушение:** Одна огромная таблица `users`, которая содержит и данные для авторизации, и настройки профиля, и историю заказов, и лог активности.
*   **Решение:** Нормализация данных. Разделение на таблицы `users` (сущность), `user_profiles` (метаданные) и `user_logs` (события).

### 5. Файлы (в контексте организации кода)
Даже структура файлов в проекте подчиняется SRP.
*   **Нарушение:** Один файл `functions.php`, в котором лежат и функции для работы с датами, и функции для работы с файловой системой, и функции для форматирования HTML.
*   **Решение:** Разделение по смысловым папкам и файлам: `DateHelper.php`, `FileUploader.php`, `HtmlFormatter.php`.

---

### Как понять, что SRP нарушен (универсальный критерий)?

Самый простой способ проверить любой сущности (классу, методу, сервису или модулю) на соблюдение SRP — это задать вопрос:

> **«Сколько разных типов пользователей (стейкхолдеров) могут потребовать изменений в этом модуле?»**

*   Если вы меняете **бизнес-логику** (правила компании) $\to$ меняется класс.
*   Если вы меняете **инфраструктуру** (переход с MySQL на PostgreSQL) $\to$ меняется тот же класс.
*   Если вы меняете **формат вывода** (JSON на XML) $\to$ меняется тот же класс.

**Если у одного модуля три разных повода для изменений от разных людей — SRP нарушен.**

> ⏱ 3.1s · prompt 4309 tok · output 1042 tok

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

Контейнер внедрения зависимостей (Dependency Injection Container, DIC) в Symfony — это не просто «хранилище объектов». Это мощный механизм, который превращает декларативное описание сервисов в высокооптимизированный PHP-код.

Его работу можно разделить на три ключевых этапа: **Компиляция**, **Загрузка** и **Инициализация (Lazy Loading)**.

---

### 1. Этап компиляции (Compilation Phase)
Это самый важный этап, который происходит **один раз** (при очистке кэша). Symfony не парсит YAML/XML файлы при каждом запросе пользователя. Вместо этого она компилирует всё дерево зависимостей в один огромный PHP-класс.

Что происходит во время компиляции:
1.  **Сбор конфигурации:** Symfony проходит по всем `services.yaml`, бандлам и атрибутам, собирая информацию о том, какие сервисы существуют.
2.  **Dependency Graph (Граф зависимостей):** Контейнер строит дерево: какой сервис от кого зависит.
3.  **Compiler Passes (Компиляционные проходы):** Это «магия» Symfony. На этом этапе работают специальные классы, которые могут изменять конфигурацию контейнера «на лету».
    *   *Пример:* Если вы используете `autoconfigure: true`, Compiler Pass находит все классы, реализующие `EventSubscriberInterface`, и автоматически регистрирует их в `EventDispatcher`.
    *   *Пример:* Удаление неиспользуемых сервисов (Optimization pass), чтобы уменьшить размер контейнера.
4.  **Генерация PHP-кода:** Результат компиляции — это сгенерированный PHP-файл (находится в `var/cache/.../container.php`). В нем описаны методы для создания каждого сервиса. Это делает контейнер невероятно быстрым, так как никакой логики поиска или парсинга в рантайме нет — только прямой вызов методов.

### 2. Как работает Autowiring
Autowiring — это возможность Symfony автоматически понимать, какие аргументы нужно передать в конструктор, основываясь на **Type-hinting** (типизации).

**Механизм:**
1.  Во время компиляции (см. выше) Symfony использует **Reflection API**, чтобы изучить конструкторы ваших классов.
2.  Если она видит `public function __construct(UserRepository $repository)`, она ищет в своем реестре сервис, который является экземпляром `UserRepository`.
3.  Если найден — она записывает в сгенерированный PHP-файл контейнера: «При создании этого сервиса сначала создай `UserRepository` и передай его в конструктор».

*Важно:* Autowiring работает только для **сервисов**. Если вы укажете тип `string $apiKey`, Symfony не поймет, какую строку подставить, и потребует явного указания параметра в конфигурации.

### 3. Момент запроса сервиса (Runtime / Lazy Loading)
Когда вы вызываете `$container->get(MyService::class)` (или, что чаще, когда сервис запрашивается через конструктор другого сервиса), происходит следующее:

1.  **Проверка в Registry:** Контейнер проверяет, создан ли уже экземпляр этого сервиса. В Symfony все сервисы по умолчанию являются **Singleton** (Shared) в рамках одного жизненного цикла запроса.
2.  **Если сервис еще не создан (First request):**
    *   Контейнер вызывает сгенерированный метод из скомпилированного класса (например, `getMyService()`).
    *   Этот метод начинает цепочку создания: он проверяет зависимости `MyService`, и если им тоже нужны другие сервисы, он рекурсивно вызывает их методы создания.
    *   **Instantiating:** Происходит реальное создание объекта через `new MyService(...)`.
3.  **Кэширование экземпляра:** Созданный объект сохраняется в приватном свойстве контейнера.
4.  **Повторный запрос:** При втором вызове того же сервиса контейнер просто возвращает уже готовый объект из памяти, не выполняя никаких вычислений.

### Что такое Lazy Services (дополнение)?
Если сервис очень «тяжелый» (например, подключается к удаленному API), его создание при первом запросе может замедлить систему. Symfony позволяет помечать сервисы как `lazy`. В этом случае контейнер вместо реального объекта подставляет **Proxy-объект**. Реальный сервис будет создан только в тот момент, когда вы вызовете у этого прокси хотя бы один метод.

---

**Резюме для интервью:**
*   **Компиляция** — это превращение конфигов в оптимизированный PHP-код через Compiler Passes.
*   **Autowiring** — это использование Reflection во время компиляции для автоматического сопоставления типов.
*   **Runtime** — это ленивая инициализация (Lazy Loading) и возврат синглтона из внутреннего кэша контейнера.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

Циклические зависимости (Circular Dependencies) — это ситуация, когда `ServiceA` требует `ServiceB`, а `ServiceB` требует `ServiceA`. Это классическая проблема проектирования, которая в Symfony приведет к ошибке `CircularReferenceException` при попытке создания сервисов.

Я подхожу к решению этой проблемы в три этапа: от «лечения болезни» (архитектурного) до «симптоматического» (технического).

### 1. Архитектурный подход (Правильный путь)
В 90% случаев циклическая зависимость — это сигнал о том, что **нарушен SRP** или **нарушена иерархия слоев**.

*   **Выделение третьего сервиса (Extraction):** Если `A` и `B` зависят друг от друга, скорее всего, у них есть общая логика, которая должна жить в третьем сервисе `C`.
    *   *Было:* `UserService` $\leftrightarrow$ `OrderService`.
    *   *Стало:* `UserService` $\to$ `OrderProcessingService` $\leftarrow$ `OrderService`.
*   **Разделение на интерфейсы (Dependency Inversion):** Иногда цикл возникает из-за того, что сервисы слишком «знают» друг о друге. Разделение на интерфейсы может помочь, но в чистом PHP это редко решает именно циклическую проблему в контейнере, так как контейнеру всё равно нужно создать оба экземпляра.
*   **Пересмотр границ (Bounded Contexts):** Если два сервиса так сильно переплетены, что не могут существовать друг без друга, возможно, они **не являются разными сервисами**. Я рассмотрю возможность объединения их в один более крупный компонент.

### 2. Технический подход (Симптоматический)
Если архитектурно вытянуть код сложно (например, при работе с legacy), я использую инструменты Symfony для разрыва цикла.

*   **Lazy Services (Proxy):** Это самый эффективный способ. Если мы пометим один из сервисов как `lazy`, Symfony подставит вместо него **Proxy-объект**. 
    *   *Как это работает:* Контейнер создаст `ServiceA`, передаст в него `Proxy(ServiceB)`. `ServiceB` создастся позже, только когда вы реально вызовете метод у прокси. Цикл в момент инициализации разрывается.
    *   *В Symfony:* `services: App\Service\ServiceB: lazy: true`
*   **Использование Setter Injection вместо Constructor Injection:** Конструктор требует объект немедленно. Setter-метод позволяет создать объект, а затем «долить» в него зависимость позже.
    *   *Внимание:* Я стараюсь избегать этого, так как это делает объект «недособранным» (невалидным) в промежуточный момент времени, что нарушает инкапсуляцию.

### 3. Использование событий (Event Dispatcher)
Это самый «чистый» способ разрыва жесткой связи. Вмеме того чтобы `ServiceA` вызывал `ServiceB` напрямую, `ServiceA` просто генерирует событие: *"Я завершил регистрацию пользователя"*.

*   **Как это работает:** `ServiceB` подписывается на это событие. `ServiceA` ничего не знает о существовании `ServiceB`. Цикл полностью исчезает, так как зависимость становится **односторонней и неявной**.

---

**Мой алгоритм действий:**
1.  **Анализ:** Понять, почему они зависят друг от друга. Это логическая ошибка или техническая необходимость?
2.  **Рефакторинг:** Попробовать выделить общую логику в новый сервис (предпочтительно).
3.  **События:** Если один сервис просто должен «уведомить» другой о чем-то — использовать `EventDispatcher`.
4.  **Lazy/Proxy:** Если архитектурно рефакторинг невозможен или слишком дорог — использовать `lazy: true`.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

Это классическая задача на проектирование асинхронных процессов. Главная цель — минимизировать время ответа (Latency) для пользователя, вынеся тяжелые задачи (I/O, сетевые запросы) из основного потока выполнения.

Я предложу три варианта, от самого простого до наиболее профессионального.

### 1. Вариант "Fast & Dirty": Использование терминального процесса (exec/shell)
Мы можем запустить фоновый процесс прямо из PHP-кода (например, через `exec("php bin/console app:update-index > /dev/null 2>&1 &")`).

*   **Как это работает:** PHP-скрипт запускает команду в ОС и тут же завершается, не дожидаясь ответа.
*   **Trade-offs:**
    *   **Плюсы:** Не требует настройки инфраструктуры (Redis, RabbitMQ).
    *   **Минусы:** Очень сложно масштабировать, трудно обрабатывать ошибки (если процесс упал, мы об этом не узнаем), нет контроля нагрузки на систему (можно "положить" сервер, если придет 1000 регистраций в секунду), плохая наблюдаемость (Observability).
*   **Вердикт:** Только для мелких скриптов или MVP, где нагрузка предсказуема и мала.

### 2. Вариант "Standard": Symfony Messenger + Транспорт (Redis/Database)
Это **золотой стандарт** для современных Symfony-приложений. Мы используем компонент **Messenger** для реализации паттерна "Message Bus".

**Архитектура:**
1.  **Message:** Создаем простой DTO `UserRegisteredEvent` (содержит только `userId`).
2.  **Command/Message Bus:** В сервисе регистрации мы только отправляем этот объект в шину: `$bus->dispatch(new UserRegisteredEvent($user->getId()))`. Это занимает миллисекунды.
3.  **Handlers:** Создаем два независимых хендлера: `SendWelcomeEmailHandler` и `UpdateSearchIndexHandler`.
4.  **Transport:** Настраиваем транспорт (например, **Redis** или **RabbitMQ**). Сообщения улетают в очередь.
5.  **Worker:** В фоне работают воркеры (`php bin/console messenger:consume`), которые забирают задачи из очереди и выполняют их.

*   **Trade-offs:**
    *   **Плюсы:** 
        *   **Асинхронность:** Пользователь получает ответ мгновенно.
        *   **Отказоустойчивость:** Если почтовый сервис упал, Messenger может автоматически переотправить сообщение (retry strategy) через 5, 10, 60 минут.
        *   **Масштабируемость:** Можно запустить 10 воркеров на разных серверах, если очередь растет.
        *   **Разделение ответственности:** Регистрация ничего не знает о письмах или поиске.
    *   **Минусы:** Требует инфраструктуру (Redis/RabbitMQ) и мониторинг воркеров.
*   **Вердикт:** Лучший выбор для большинства продакшн-систем.

### 3. Вариант "Enterprise": Распределенная архитектура (Event-Driven Microservices)
Если приложение превращается в систему микросервисов, где "Поиск" — это отдельный сервис, а "Email" — еще один.

**Архитектура:**
Мы используем полноценный брокер сообщений (например, **Apache Kafka** или **RabbitMQ** с продвинутой маршрутизацией). Сервис регистрации публикует событие в топик `user.events`. Подписчики (Email Service, Search Service) сами слушают этот топик.

*   **Trade-offs:**
    *   **Плюсы:** Максимальная автономность сервисов. Мы можем добавлять новые подписчики (например, сервис аналитики), вообще не трогая сервис регистрации и брокер.
    *   **Минусы:** Огромная сложность инфраструктуры, необходимость решать вопросы консистентности данных (Eventual Consistency) и сложности в локальной разработке.
*   **Вердикт:** Только для очень крупных систем (Highload/Microservices).

---

### Мой выбор и реализация (Summary)

Для типичного качественного бэкенд-проекта я выберу **Вариант №2 (Symfony Messenger + Redis)**.

**Как бы я это реализовал (Step-by-step):**

1.  **Domain Layer:** Создаю `UserRegistered` сообщение.
2.  **Application Layer:** В `RegisterUserHandler` (сценарий использования) после сохранения пользователя вызываю `$messageBus->dispatch(new UserRegistered($userId))`.
3.  **Infrastructure Layer:** 
    *   Настраиваю `messenger.yaml`, указывая транспорт `redis://`.
    *   Пишу `SendEmailHandler` и `UpdateIndexHandler`.
    *   Настраиваю `retry_strategy` в конфиге, чтобы при сетевых сбоях задачи не терялись.
4.  **Infrastructure (DevOps):** Настраиваю `Supervisor` (или Kubernetes Sidecar), чтобы он следил за тем, чтобы процесс `messenger:consume` всегда был запущен и перезапускался при падении.

**Результат:** Пользователь видит "Регистрация успешна" через 50мс, а письмо и индекс обновляются в фоне в течение нескольких секунд, даже если внешние сервисы тормозят.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

Контроль доступа в Symfony строится на четком разделении двух понятий: **Authentication** (Кто ты?) и **Authorization** (Что тебе можно?).

### 1. Аутентификация (Authentication)
Это процесс проверки личности пользователя. В Symfony за это отвечает компонент **Security**.
*   **Firewalls:** В `security.yaml` мы определяем "зоны" приложения. Для каждой зоны прописываются `authenticators`.
*   **Authenticators:** Это механизмы проверки учетных данных. Например, `FormLoginAuthenticator` (пароль из формы), `JwtAuthenticator` (токен в заголовке) или `AccessToken` (для API).
*   **User Provider:** После того как учетные данные проверены, Symfony должна загрузить объект `User` из хранилища (БД, LDAP, API).

### 2. Авторизация (Authorization)
Когда мы поняли, кто перед нами, нужно решить, есть ли у него права на действие. Здесь есть два уровня:

#### А) Роли (Roles) — Простой уровень
Роли — это плоские или иерархические строки (например, `ROLE_USER`, `ROLE_ADMIN`).
*   **Как работают:** Мы проверяем наличие строки в массиве ролей пользователя.
*   **Иерархия:** В Symfony можно настроить `role_hierarchy`, чтобы `ROLE_ADMIN` автоматически включал в себя `ROLE_USER`.
*   **Когда использовать:** Для глобальных прав доступа. Например: "Только администратор может зайти в панель управления" или "Только авторизованный пользователь может видеть страницу профиля".

#### Б) Voters (Голосующие) — Сложный уровень
Voters — это специализированные классы, которые реализуют логику проверки прав на основе **конкретного объекта (сущности) и действия**.

*   **Как работают:** Когда вы вызываете `$this->denyAccessUnlessGranted('EDIT', $article)`, Symfony опрашивает все зарегистрированные Voter-ы. Каждый Voter получает:
    1.  **Атрибут** (действие: `EDIT`, `VIEW`, `DELETE`).
    2.  **Субъект** (объект: экземпляр `$article`).
    3.  **Токен** (текущий пользователь).
*   Voter возвращает один из трех ответов: `ACCESS_GRANTED`, `ACCESS_DENIED` или `ACCESS_ABSTAIN` (если он не знает, что делать с этим объектом).

---

### Когда выбирать Voter, а когда Роли?

Это ключевой архитектурный вопрос. Я использую следующее правило:

#### Выбирай Роли, если:
Доступ зависит **только от типа пользователя** и не зависит от данных самого объекта.
*   *Пример:* "Может ли пользователь зайти в админку?" $\to$ Проверяем `ROLE_ADMIN`.
*   *Пример:* "Может ли пользователь менять настройки сайта?" $\to$ Проверяем `ROLE_SUPER_ADMIN`.
*   **Плюс:** Это быстро и просто настраивается в конфигурации (через `access_control` в `security.yaml`).

#### Выбирай Voter, если:
Доступ зависит от **бизнес-логики** или **отношений между пользователем и объектом**.
*   *Пример:* "Может ли пользователь редактировать *этот конкретный* комментарий?"
    *   Проверка роли `ROLE_USER` здесь бесполезна, так как любой пользователь может отредактировать *чужой* комментарий.
    *   Voter проверит: `return $user === $comment->getAuthor();`
*   *Пример:* "Может ли пользователь видеть этот заказ?"
    *   Проверка: `return $user->getCompany() === $order->getCompany();`
*   **Плюс:** Позволяет реализовать очень гибкую и гранулярную политику безопасности, которая не загромождает контроллеры.

### Итоговая таблица для принятия решения

| Ситуация | Что использовать | Почему |
| :--- | :--- | :--- |
| Доступ по "статусу" (Админ/Модератор) | **Roles** | Это глобальный признак личности. |
| Доступ к функционалу (Кнопка "Удалить") | **Roles** | Проверка прав на само действие. |
| Доступ к конкретной записи (Свой/Чужой) | **Voter** | Требуется сравнение свойств объекта и пользователя. |
| Сложные правила (Владелец + Статус заказа "Новый") | **Voter** | Требуется проверка нескольких условий и состояний. |

**Мой профессиональный совет:** Если логика проверки доступа занимает более одной строки `if` — это верный признак того, что пора выносить её в отдельный **Voter**. Это сделает код контроллеров чистым, а логику безопасности — тестируемой.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

Хранение **Value Objects (VO)** — это классическая задача на стыке чистоты доменной модели (DDD) и ограничений ORM. Проблема в том, что Doctrine «заточена» под работу с Entity (объектами с идентификатором и жизненным циклом), а VO — это объекты, определяемые своими свойствами, которые должны быть неизменяемыми (`readonly`).

В Doctrine нет встроенного типа "Value Object", поэтому мы используем три основных способа маппинга.

---

### 1. Embeddables (Встроенные объекты)
Это официальный и рекомендуемый способ в Doctrine для реализации VO. `Embeddable` позволяет разбить один объект на несколько колонок в той же таблице, где находится Entity.

**Пример:**
```php
#[ORM\Embeddable]
readonly class Money {
    public function __construct(
        #[ORM\Column(type: 'int')]
        public int $amount,
        #[ORM\Column(type: 'string', length: 3)]
        public string $currency,
    ) {
        if ($amount < 0) throw new \InvalidArgumentException("Amount cannot be negative");
    }
}

#[ORM\Entity]
class Product {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Embedded(class: Money::class)]
    private Money $price;
}
```

*   **Плюсы:**
    *   **Нативность:** Doctrine понимает этот механизм.
    *   **Производительность:** Данные лежат в той же таблице (нет лишних `JOIN`).
    *   **Валидность:** Конструктор VO гарантирует, что объект не может быть создан в невалидном состоянии.
*   **Минусы:**
    *   **Связанность:** Embeddable нельзя использовать как отдельную сущность (у него нет своего ID).
    *   **Переиспользование:** Если вы захотите использовать этот VO в разных сущностях с разными именами колонок, придется настраивать маппинг для каждой.
*   **Подводные камни:**
    *   **Mutable state:** Если забыть про `readonly` (в PHP 8.1+) или не сделать свойства приватными, Doctrine может попытать изменить свойства объекта через рефлексию, что нарушит принцип неизменяемости.

---

### 2. Custom Doctrine Types (Пользовательские типы)
Этот способ подходит, если ваш VO можно представить как примитив (строку, число) или сериализованный формат (JSON).

**Пример:** Хранение VO `Color` как строки `#FFFFFF`.

```php
// Внутри Custom Type
public function convertToDatabaseValue($value, AbstractPlatform $platform): mixed {
    return $value->toHex(); // Превращаем объект в строку для БД
}

public function convertToPHPValue($value, AbstractPlatform $platform): mixed {
    return new Color($value); // Превращаем строку обратно в объект
}
```

*   **Плюсы:**
    *   **Чистота БД:** В базе данных лежат простые типы (`VARCHAR`, `INT`), что удобно для SQL-запросов.
    *   **Прозрачность:** Для Entity это выглядит как обычный тип поля.
*   **Минусы:**
    *   **Сложность поиска:** Если вы храните сложный объект как JSON, вы теряете возможность эффективно делать выборки по отдельным полям через обычный SQL (хотя в PostgreSQL есть JSONB, это усложняет маппинг).
    *   **Потеря структуры:** Вы превращаете богатый доменный объект в «плоский» при записи.
*   **Подводные камни:**
    *   **Сериализация:** При использовании JSON легко потерять типизацию или структуру при чтении/записи.

---

### 3. Entity-как-VO (С использованием @Id)
Иногда VO настолько сложен, что его мапят как полноценную Entity, но в доменном слое обращаются с ней как с VO.

*   **Плюсы:** Можно использовать связи (ManyToOne/OneToMany).
*   **Минусы:** Это **нарушение сути VO**. У объекта появляется ID, он становится "живым" в базе, его можно изменить, что убивает смысл неизменяемости.
*   **Вердикт:** Не рекомендую, если вы действительно следуете DDD.

---

### Сводная таблица и рекомендации

| Критерий | Embeddables | Custom Types (JSON/String) |
| :--- | :--- | :--- |
| **Сложность объекта** | Несколько полей (структура) | Одно значение (скаляр) |
| **Поиск в БД** | Легко (по колонкам) | Сложно (если JSON) |
| **Связи (Relations)** | Нет | Нет |
| **Идеально для...** | `Money`, `Address`, `Coordinate` | `Color`, `Email`, `DateRange` (как строка) |

### Мой алгоритм выбора:

1.  **Если у объекта несколько значимых полей** (например, `Address` с улицей, городом и индексом) $\to$ **только Embeddables**. Это сохранит типизацию и позволит делать SQL-запросы типа `WHERE address_city = 'Moscow'`.
2.  **Если объект — это "обертка" над одним значением** (например, `Email` или `Uuid`) $\to$ **Custom Doctrine Type**. Это сохранит чистоту базы (в таблице будет просто `email VARCHAR`).
3.  **Как обеспечить неизменяемость?**
    *   Всегда использовать `readonly` свойства в PHP 8.2+.
    *   В конструкторе делать жесткую валидацию (Fail-fast).
    *   Никогда не использовать сеттеры. Если нужно изменить значение — создаем новый экземпляр объекта (`$money = $money->add(10);`).

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

Это фундаментальный вопрос проектирования. Основная сложность здесь в том, что **Doctrine работает на уровне таблиц и сущностей**, а **DDD работает на уровне Агрегатов**. 

Главная заповедь: **Изменения в агрегате должны происходить только через его корень (Aggregate Root).** Мы никогда не вызываем репозиторий для дочерних сущностей, только для корня.

Рассмотрим пример: **Заказ (`Order`)** — это корень, а **Позиции заказа (`OrderItem`)** — дочерние сущности.

### 1. Маппинг коллекции (Mapping)

Чтобы дочерние сущности были частью агрегата, их жизненный цикл должен быть жестко привязан к корню. В Doctrine это реализуется через `orphanRemoval=true` и `cascade={"persist", "remove"}`.

```php
#[ORM\Entity]
class Order {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    /**
     * orphanRemoval=true: если мы удалим элемент из коллекции, 
     * Doctrine сама удалит строку из БД.
     * cascade: если мы добавим новый OrderItem в коллекцию и сохраним Order,
     * новый элемент автоматически сохранится.
     */
    #[ORM\OneToMany(
        mappedBy: 'order', 
        targetEntity: OrderItem::class, 
        cascade: ['persist', 'remove'], 
        orphanRemoval: true
    )]
    private Collection $items;

    public function __construct() {
        $this->items = new ArrayCollection();
    }

    // Метод для изменения состояния агрегата (единственный путь)
    public function addItem(Product $product, int $quantity): void {
        $item = new OrderItem($this, $product, $quantity);
        $this->items->add($item);
    }

    public function removeItem(OrderItem $item): void {
        $this->items->removeElement($item);
    }
}

#[ORM\Entity]
class OrderItem {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'items')]
    #[ORM\JoinColumn(nullable: false)]
    private Order $order;

    public function __construct(Order $order, Product $product, int $quantity) {
        $this->order = $order;
        // ... инициализация ...
    }
}
```

### 2. Границы транзакции (Transaction Boundaries)

В DDD транзакция должна охватывать **весь процесс изменения агрегата**. 

*   **Где открывать транзакцию?** На уровне **Application Service** (или Use Case). Слой домена не должен знать о транзакциях.
*   **Что входит в транзакцию?** Все действия, которые меняют состояние агрегата и его дочерних элементов.

**Плохо:** Открывать транзакцию внутри `OrderItemRepository::save()`. Это нарушает целостность, так как мы не можем гарантировать атомарность изменений в нескольких объектах.

### 3. Кто и когда вызывает `flush()`?

Это самый частый вопрос. В чистой архитектуре **`flush()` вызывается один раз в конце работы Application Service.**

**Правило:** Репозиторий не должен вызывать `flush()`. Репозиторий — это просто коллекция в памяти. `flush()` — это команда Unit of Work (Doctrine) синхронизировать состояние памяти с базой.

#### Полный цикл работы (Пример Use Case):

```php
class CreateOrderService {
    public function __construct(
        private OrderRepository $orderRepository,
        private EntityManagerInterface $entityManager // Используем для flush
    ) {}

    public function execute(int $productId, int $qty): void {
        // 1. Начинаем транзакцию (опционально, если работаем с несколькими агрегатами)
        $this->entityManager->beginTransaction();

        try {
            // 2. Создаем агрегат
            $order = new Order();
            $product = $this->productRepository->find($productId);
            
            // 3. Работаем ТОЛЬКО через корень
            $order->addItem($product, $qty);

            // 4. Сохраняем корень (Doctrine увидит новые элементы в коллекции благодаря cascade)
            $this->orderRepository->save($order);

            // 5. Фиксируем изменения (Unit of Work делает один batch-запрос)
            $this->entityManager->flush();
            $this->entityManager->commit();

        } catch (\Exception $e) {
            $this->entityManager->rollback();
            throw $e;
        }
    }
}
```

### Резюме архитектуры:

1.  **Маппинг:** Используем `orphanRemoval=true` и `cascade={"persist"}`. Это превращает `Order` в полноценный владелец жизненного цикла своих `OrderItem`.
2.  **Доступ:** Дочерние сущности не имеют публичных методов для изменения их состояния извне агрегата. Все изменения — через методы `Order`.
3.  **Транзакция:** Оборачивает весь сценарий использования в `Application Service`.
4.  **Flush:** Вызывается один раз в самом конце `Application Service`. Это гарантирует, что либо весь агрегат сохранится целиком, либо ничего не сохранится (атомарность).

**Почему это важно?** Если вы начнете вызывать `flush()` внутри методов репозитория или внутри цикла, вы получите:
*   Лишние запросы к БД (проблема N+1).
*   Частично обновленные данные при ошибке (нарушение целостности).
*   Непредсказуемое поведение из-за того, что Doctrine может попытаться сохранить объект, который еще не полностью инициализирован в рамках текущей транзакции.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

Проблема N+1 — это классическая ситуация, когда для получения списка из $N$ объектов вы делаете 1 запрос для получения самих объектов, а затем еще $N$ запросов для подгрузки их связанных сущностей (Lazy Loading).

### 1. Диагностика

Прежде чем оптимизировать, нужно доказать наличие проблемы.

*   **Symfony Profiler (самый быстрый способ):** В разделе "Doctrine" профилировщика я сразу вижу количество запросов. Если я вижу десятки идентичных запросов к одной и той же таблице (например, `SELECT ... FROM user WHERE id = ?`), — это 100% N+1.
*   **SQL Log (в разработке):** Включение логирования запросов в консоль или файл. Визуально повторяющиеся паттерны запросов сразу бросаются в глаза.
*   **Инструменты APM (Production):** В реальной среде я использую **New Relic**, **Blackfire** или **Sentry**. Они строят трейсы запросов и показывают "hot paths", где база данных является узким местом.
*   **Blackfire.io:** Идеально для глубокого профилирования. Он показывает не только количество запросов, но и время, затраченное на их выполнение и на "Hydration" (превращение строк из БД в объекты PHP).

---

### 2. Способы решения и их Trade-offs

#### А) Eager Loading через Join (Fetch Join)
Это основной метод. Мы меняем запрос так, чтобы он сразу забирал связанные данные одним `JOIN`.

```php
// В Repository
public function findAllWithUsers(): array {
    return $this->createQueryBuilder('p')
        ->leftJoin('p.user', 'u')
        ->addSelect('u') // Ключевой момент: добавляем сущность в выборку
        ->getQuery()
        ->getResult();
}
```

*   **Плюсы:** Решает проблему одним запросом. Максимальная производительность для конкретного случая.
*   **Минусы:** 
    *   **Проблема декартова произведения (Cartesian Product):** Если вы делаете `leftJoin` для нескольких "один-ко-многим" коллекций одновременно, количество строк в результате запроса растет экспоненциально, что может убить память.
    *   **Избыточность данных:** Вы тянете больше колонок, чем нужно, если вам нужны только ID.
*   **Когда использовать:** Когда вы точно знаете, что связанные данные понадобятся для каждого элемента списка.

#### Б) Использование `FETCH JOIN` для коллекций (че समझते Batch Loading)
Если `JOIN` вызывает слишком много дублирующихся данных из-за коллекций, можно использовать стратегию загрузки коллекций отдельным запросом.

*   **Как работает:** Сначала загружаем основные сущности, а затем одним запросом `WHERE IN (...)` подгружаем все связанные элементы для этой пачки.
*   **Плюсы:** Избегает раздувания результирующей таблицы (Cartesian Product).
*   **Минусы:** Вместо 1 запроса будет 2.
*   **Когда использовать:** При работе с крупными коллекциями (One-to-Many), где `JOIN` делает выборку слишком тяжелой.

#### В) Настройка `fetch="EAGER"` в маппинге
В метаданных сущности можно указать, что связь всегда должна грузиться сразу.

```php
#[ORM\ManyToOne(targetEntity: User::class, fetch: "EAGER")]
private User $user;
```

*   **Плюсы:** Проще всего — не нужно менять каждый запрос в репозитории.
*   **Минусы:** **Очень опасно.** Это глобальное решение. Теперь, когда вам понадобится просто список сущностей *без* пользователей, Doctrine всё равно будет делать `JOIN` или второй запрос. Это создает скрытую нагрузку на всю систему.
*   **Когда использовать:** Почти никогда. Только если эта связь нужна в 99% случаев во всем приложении.

#### Г) DTO Projection (Partial Objects / DTO)
Вместо того чтобы загружать тяжелые объекты Entity, мы выбираем только нужные поля и мапим их сразу в легкие DTO.

```php
return $this->createQueryBuilder('p')
    ->select('new App\Dto\ProductDto(p.id, p.name, u.email)')
    ->leftJoin('p.user', 'u')
    ->getQuery()
    ->getResult();
```

*   **Плюсы:** 
    *   **Экстремальная скорость:** Нет процесса Hydration (превращения строк в тяжелые объекты с Unit of Work).
    *   **Минимальный трафик:** Из БД тянутся только нужные колонки.
*   **Минусы:** Вы получаете только данные для чтения. Вы не сможете вызвать метод `$product->changePrice()` и сохранить изменения, так как DTO — это не Entity.
*   **Когда использовать:** Для Read-only списков, API-ответов и сложных отчетов.

---

### Итоговая стратегия выбора

1.  **Проблема в списке (Read-only):** Использую **DTO Projection**. Это самый быстрый путь для производительности.
2.  **Проблема в списке (нужно редактировать):** Использую **Fetch Join** (через `addSelect`) для связей Many-to-One.
3.  **Проблема с большими коллекциями (One-to-Many):** Использую **Batch Loading** (загрузка через `WHERE IN`) или разбиваю задачу.
4.  **Никогда** не использую глобальный `fetch="EAGER"`, если не готов к деградации производительности всего приложения.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

Это отличный вопрос, который часто вызывает споры между сторонниками «чистого кода» и «безопасной базы». Моя позиция такова: **Бизнес-валидация в коде и ограничения в БД решают разные задачи.**

Бизнес-валидация (в сервисах или Entity) отвечает за **правила игры** (например: «скидка не может быть больше 50%»), а ограничения в БД отвечают за **целостность данных** (например: «цена не может быть отрицательной» или «заказ не может существовать без пользователя»).

### Зачем нужны ограничения в БД, если есть код?

1.  **Защита от "дыр" в приложении:** Приложение — это не единственная точка входа в БД. К базе могут подключаться:
    *   Миграции.
    *   Админские скрипты или консольные команды.
    *   Другие микросервисы (написанные на Python, Go и т.д.).
    *   Прямые SQL-запросы аналитиков.
    Без ограничений в БД один кривой скрипт может разрушить структуру данных, которую код приложения старательно защищал.

2.  **Конкурентный доступ (Race Conditions):** Код приложения работает в изолированных процессах. Если два пользователя одновременно нажмут кнопку «купить последний товар», код может проверить остаток на складе ($1 > 0$) для обоих и разрешить покупку. БД (благодаря транзакциям и уровням изоляции) — это единственный уровень, способный гарантировать атомарность и предотвратить этот конфликт.

3.  **Data Integrity (Целостность):** Ограничения вроде `FOREIGN KEY` гарантируют, что у вас не появятся «сироты» (заказы без клиентов), которые сломают логику JOIN-ов и отчетности.

---

### Какие средства я использую в PostgreSQL и когда?

Я придерживаюсь принципа: **«В базе храним только то, что физически не должно быть иначе»**.

#### 1. Primary Keys и Foreign Keys (`REFERENCES`)
*   **Когда:** Всегда. Это фундамент.
*   **Зачем:** Гарантия того, что связи между сущностями не разорвутся. Я всегда использую `ON DELETE RESTRICT` или `ON DELETE CASCADE` в зависимости от бизнес-логики (например, нельзя удалить пользователя, у которого есть активные подписки).

#### 2. NOT NULL Constraints
*   **Когда:** Всегда для обязательных полей.
*   **Зачем:** Чтобы избежать бесконечных проверок на `null` в коде и гарантировать, что критически важные данные (email, price) всегда присутствуют.

#### 3. Unique Constraints (`UNIQUE`)
*   **Когда:** Для полей, которые должны быть уникальны (email, slug, артикул товара).
*   **Зачем:** Это единственная надежная защита от дублей при одновременных запросах (Race Condition). Код может проверить уникальность, но только БД может её **гарантировать**.

#### 4. Check Constraints (`CHECK`)
*   **Когда:** Для простых математических или логических инвариантов.
*   **Примеры:** `price >= 0`, `status IN ('new', 'paid', 'shipped')`, `discount_percent <= 100`.
*   **Зачем:** Это "последний рубеж". Если баг в коде попытается записать отрицательную цену, база просто отвергнет транзакцию.

#### 5. JSONB Schema Validation (если используем JSONB)
*   **Когда:** Если в PostgreSQL хранится неструктурированный JSON.
*   **Зачем:** Чтобы гарантировать, что внутри JSON есть обязательные ключи нужного типа.

---

### Резюме: Разделение ответственности

| Тип проверки | Где реализуется | Цель | Пример |
| :--- | :--- | :--- | :--- |
| **Бизнес-валидация** | Код (Service/Entity) | Обработка ошибок, UI-сообщения, сложные правила | "Пользователь не может купить товар, если он заблокирован" |
| **Целостность данных** | БД (Constraints) | Защита от повреждения данных и Race Conditions | "Цена не может быть меньше нуля" |

**Мой подход:** Я пишу богатую валидацию в коде (чтобы пользователь сразу получил понятную ошибку "Ваш пароль слишком короткий"), но дублирую критические ограничения (unique, not null, check) на уровне БД, чтобы спать спокойно.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

Когда запрос в PostgreSQL тормозит, я не начинаю "тыкать" пальцем в индексы. Я следую системному подходу: **от общего к частному** — от диагностики всей системы до анализа конкретного плана выполнения запроса.

### 1. Этап диагностики (Где именно проблема?)

Прежде всего, нужно понять: это медленный **запрос**, медленная **база** или медленный **приложение**?

*   **Инструменты:**
    *   **`pg_stat_statements`:** Мой первый шаг. Это модуль, который собирает статистику по всем выполненным запросам. Я смотрю на `total_exec_time` (общие затраты) и `mean_exec_time` (среднее время). Это позволяет найти "убийц" производительности, которые выполняются часто.
    *   **`pg_stat_activity`:** Позволяет увидеть, что происходит прямо сейчас. Неты ли там зависших транзакций или процессов, которые блокируют (Locking) другие запросы.
    *   **Инструменты APM (New Relic/Blackfire):** Если проблема на стороне приложения (например, слишком много мелких запросов — N+1).

### 2. Анализ конкретного запроса (Deep Dive)

Как только я выделил проблемный SQL, я использую команду **`EXPLAIN (ANALYZE, BUFFERS)`**. Это «рентген» запроса.

**На что я смотрю в плане выполнения (Query Plan):**
*   **Seq Scan (Sequential Scan):** Самый плохой знак. Это значит, что база читает всю таблицу целиком. Значит, нет подходящего индекса.
*   **Index Scan vs Index Only Scan:** `Index Only Scan` — идеал, так как данные берутся прямо из индекса без обращения к самой таблице (Heap).
*   **Cost & Actual Time:** Я сравниваю *ожидаемую* стоимость (cost) с *фактическим* временем (actual time). Если разрыв огромный, значит, статистика базы устарела.
*   **Rows vs Loops:** Если `rows` в плане сильно отличается от реального количества строк, значит, планировщик ошибся.
*   **Buffers (Shared Hit/Read):** Показывает, читаются ли данные из кэша (Hit) или с диска (Read). Если много `Read`, значит, мы уперлись в I/O (диск).

---

### 3. Типовые причины и способы решения

Я делю причины на три категории:

#### А. Проблемы с индексами
*   **Отсутствие индекса:** Самая частая причина.
    *   *Решение:* Создать B-tree индекс.
*   **Неэффективный индекс:** Индекс есть, но он не используется из-за условий в `WHERE`.
    *   *Пример:* Использование функций над колонкой (`WHERE DATE(created_at) = ...`) делает индекс бесполезным.
    *   *Решение:* Использовать функциональные индексы или переписать запрос.
*   **Низкая селективность:** Индекс есть, но колонка имеет мало уникальных значений (например, `gender`). Базе проще просканировать всю таблицу.
*   **Composite Indexes (Составные индексы):** Индекс по `(a, b)` не сработает, если в `WHERE` указана только `b`.
    *   *Решение:* Соблюдать правило "левого префикса".

#### Б. Проблемы со статистикой и планировщиком
*   **Устаревшая статистика:** Планировщик строит плохой план, потомуs что думает, что в таблице 100 строк, а там 1 000 000.
    *   *Решение:* Выполнить `ANALYZE`.
*   **Bloat (Раздувание таблиц/индексов):** Из-за частых `UPDATE` и `DELETE` в таблице много "мертвых" строк, которые замедляют сканирование.
    *   *Решение:* Настройка `autovacuum` или ручной `VACUUM FULL` (но осторожно, это блокирует таблицу).

#### В. Проблемы проектирования и нагрузки
*   **N+1 запросы:** Проблема на уровне приложения (ORM).
    *   *Решение:* Использовать `JOIN FETCH` или `Eager Loading`.
*   **Lock Contention (Блокировки):** Один тяжелый запрос (например, `ALTER TABLE` или долгий `UPDATE`) блокирует все остальные.
    *   *Решение:* Оптимизация транзакций, использование более низких уровней изоляции или разделение чтения и записи (Read Replicas).
*   **Неправильный тип данных:** Например, сравнение `integer` с `bigint` или `text` с `varchar` может привести к неявным приведениям типов, отключающим индексы.

### Мой алгоритм действий (Summary):
1.  Найти тяжелый запрос через `pg_stat_statements`.
2.  Запустить `EXPLAIN (ANALYZE, BUFFERS)`.
3.  Искать `Seq Scan` или высокую нагрузку на чтение с диска (`Read`).
4.  Если `Seq Scan` — добавить индекс. Если индекс не работает — проверить условия `WHERE` и типы данных.
5.  Если индексы есть, но план плохой — проверить статистику (`ANALYZE`) и наличие Bloat (`VACUUM`).
6.  Если всё в порядке с БД — смотреть на приложение (N+1, отсутствие кэширования).

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

В Domain-Driven Design (DDD) **Агрегат (Aggregate)** — это кластер связанных объектов (Entity и Value Objects), который рассматривается как единое целое с точки зрения изменения данных.

Главная цель агрегата — **поддержание инвариантов** (бизнес-правил, которые всегда должны быть истинными).

### Основные правила агрегата:
1.  **Корень агрегата (Aggregate Root):** Это единственная точка входа в агрегат. Внешние объекты могут ссылаться только на корень. Все изменения внутри агрегата должны происходить через методы корня.
2.  **Граница транзакции:** Изменение одного агрегата должно быть атомарным. В идеале, одна транзакция = один агрегат.
3.  **Инварианты:** Агрегат гарантирует, что внутри него правила бизнеса не нарушены. Если вы пытаетесь перевести деньги со счета на счет, агрегат "Счет" должен гарантировать, что баланс не станет отрицательным.

---

### Пример: Система заказа (E-commerce)

Представим процесс оформления заказа.

*   **Aggregate Root:** `Order` (Заказ).
*   **Дочерние сущности:** `OrderItem` (Позиция заказа).
*   **Value Objects:** `Money` (Цена), `Address` (Адрес доставки).

**Как это работает:**
Вы не можете напрямую создать `OrderItem` в базе данных. Вы должны вызвать метод у `Order`: `$order->addItem($product, $quantity)`. 
Внутри этого метода `Order` проверяет свои правила: например, "нельзя добавить более 10 единиц одного товара" или "общая сумма заказа не может превышать лимит кредита клиента". **Это и есть защита инварианта.**

---

### Как я определяю границы агрегата?

Я не пытаюсь "угадать" границы. Я использую два подхода:

1.  **По инвариантам (Bottom-up):** Я спрашиваю: «Какие данные должны меняться одновременно, чтобы система осталась в консистентном состоянии?». Если изменение `A` требует немедленного изменения `B`, чтобы правила не нарушились — `A` и `B` должны быть в одном агрегате.
2.  **По жизненному циклу (Top-down):** Если объект `B` не имеет смысла без объекта `A` и удаляется вместе с ним — это кандидат в дочерние элементы агрегата `A`.

---

### Типовая ошибка: "Слишком большой агрегат" (The Fat Aggregate)

Самая частая ошибка — попытка запихнуть всё в один огромный агрегат.

**Пример ошибки:**
Представим, что мы решили, что `Customer` (Клиент) — это корень, который содержит в себе коллекцию всех его `Order` (Заказов).

```php
// ОШИБКА: Клиент — это корень, содержащий все заказы
class Customer {
    private array $orders = []; // Огромная коллекция!

    public function addOrder(Order $order) { ... }
}
```

**Почему это плохо?**
1.  **Проблемы производительности:** Чтобы просто изменить имя клиента, вам придется загружать из базы данных *все* его заказы за последние 5 лет (т.к. они часть агрегата).
2.  **Конфликты конкурентности (Concurrency):** Если клиент одновременно делает заказ и меняет свой адрес, два процесса будут пытаться обновить одну и ту же строку `customers` в БД. Один из них упадет с ошибкой оптимистичной блокировки.
3.  **Нарушение масштабируемости:** Агрегат становится "узким местом". Чем больше в нем данных, тем сложнее его удерживать в памяти и тем выше вероятность блокировок.

**Как правильно:**
`Order` и `Customer` — это **разные агрегаты**. 
*   `Order` ссылается на `Customer` через его `CustomerId` (просто ID, а не объект).
*   Если нужно обновить адрес клиента, мы работаем с агрегатом `Customer`. 
*   Если нужно создать заказ, мы создаем агрегат `Order`, передав туда `CustomerId`. 
*   Связь между ними становится **событийной** (Eventual Consistency): когда клиент меняет адрес, `Customer` может выбросить событие `CustomerAddressChanged`, на которое подпишется сервис заказов, если это критично.

**Золотое правило:** Делайте агрегаты как можно меньше. Лучше иметь два маленьких агрегата, связанных по ID, чем один огромный, который тормозит всю систему.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

Это классическая проблема **конкурентного доступа** (Race Condition). Если два процесса одновременно прочитают состояние агрегата, внесут изменения в памяти и попытаются сохранить их в базу, возникнет конфликт.

В зависимости от стратегии обработки, произойдет одно из двух:
1.  **Lost Update (Потерянное обновление):** Первый процесс сохранит данные, а второй процесс перезапишет их своими, фактически «стерв» изменения первого. Это критическая ошибка целостности.
2.  **Ошибка БД:** Если настроены ограничения (constraints), база выбросит исключение (например, `UniqueConstraintViolationException`).

Чтобы этого избежать, я использую два основных подхода: **Optimistic Locking** и **Pessimistic Locking**.

---

### 1. Optimistic Locking (Оптимистическая блокировка)
Это мой основной выбор для большинства веб-приложений. Мы исходим из предположения, что конфликты случаются редко.

**Как это работает:**
Мы добавляем в агрегат специальное поле — **версию** (обычно `int` или `datetime`).

1.  Процесс А читает `Order` (version = 1).
2.  Процесс Б читает `Order` (version = 1).
3.  Процесс А сохраняет изменения. SQL: `UPDATE orders SET status = 'paid', version = 2 WHERE id = 1 AND version = 1`. Успешно.
4.  Процесс Б пытается сохранить изменения. SQL: `UPDATE orders SET status = 'cancelled', version = 2 WHERE id = 1 AND version = 1`.
5.  **Результат:** БД возвращает "0 строк изменено", так как `version` уже равна 2. Doctrine выбрасывает `OptimisticLockException`.

**Реализация в Doctrine:**
Просто добавляю атрибут `#[ORM\Version]` к полю версии.

**Trade-offs:**
*   **Плюсы:** Не блокирует базу данных, не снижает пропускную способность, отлично масштабируется.
*   **Минусы:** Требует обработки исключения на уровне приложения. Если конфликт случился, пользователю нужно либо показать ошибку, либо автоматически повторить операцию (retry).

---

### 2. Pessimistic Locking (Пессимистическая блокировка)
Мы исходим из того, что конфликты неизбежны, и «запираем» данные на время работы.

**Как это работает:**
При чтении агрегата мы говориp базе данных: «Заблокируй эту строку для всех остальных до конца моей транзакции».

1.  Процесс А читает `Order` с флагом `PESSIMISTIC_WRITE`. БД ставит блокировку на строку.
2.  Процесс Б пытается прочитать этот же `Order` с тем же флагом. **Процесс Б встает в очередь и ждет.**
3.  Процесс А завершает транзакцию (commit). Блокировка снимается.
4.  Процесс Б наконец получает данные и продолжает работу.

**Реализация в Doctrine:**
`$entityManager->find(Order::class, $id, LockMode::PESSIMISTIC_WRITE);`

**Trade-offs:**
*   **Плюсы:** Гарантирует, что конфликт не возникнет. Идеально для критических финансовых операций (например, списание денег со счета).
*   **Минусы:** 
    *   **Снижение производительности:** Процессы стоят в очереди, время ответа растет.
    *   **Риск Deadlocks:** Если два процесса заблокируют разные ресурсы в разном порядке, они могут заблокировать друг друга навечно.

---

### Моя стратегия проектирования

При проектировании я выбираю метод исходя из **бизнес-ценности данных** и **частоты конфликтов**:

1.  **По умолчанию — Optimistic Locking.** Это стандарт для 90% CRUD-операций. Он легкий и не мешает другим пользователям. Я проектирую систему так, чтобы `OptimisticLockException` обрабатывался на уровне Middleware или контроллера (например, через автоматический ретрай или вежливое сообщение пользователю: *"Данные были изменены другим пользователем, пожалуйста, обновите страницу"*).

2.  **Для высококонкурентных финансовых операций — Pessimistic Locking.** Если речь идет о списании средств с баланса, где ошибка в 1 цент недопустима, я использую пессимистическую блокировку на уровне БД, чтобы гарантировать строгую последовательность.

3.  **Для борьбы с Race Condition в высоконагруженных местах — Atomic SQL.** Иногда вместо загрузки агрегата я использую атомарные запросы: `UPDATE accounts SET balance = balance - 100 WHERE id = 1 AND balance >= 100`. Это самый быстрый и надежный способ на уровне самой БД.

**Итог:** Я проектирую систему так, чтобы агрегаты были максимально маленькими (минимизация конфликтов), использую `Version` для защиты от случайных перезаписей и применяю `Pessimistic Lock` только там, где цена ошибки выше, чем цена ожидания.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

Доменные события (Domain Events) — это мощный инструмент для реализации **слабой связанности (loose coupling)**. Они позволяют агрегату сообщить миру: «Со мной что-то произошло», не объясняя, кто именно должен на это отреагировать.

### 1. Когда публиковать события?

События должны публиковаться **внутри доменной логики**, в момент, когда инвариант агрегата успешно изменен.

**Важное правило:** Событие не должно публиковаться *до* того, как изменение зафиксировано. Мы не можем сказать «Заказ оплачен», если транзакция в БД упала.

**Как это выглядит в коде:**
Я не вызываю `EventDispatcher` прямо в методе агрегата (это нарушает чистоту домена, так как агрегат становится зависимым от инфраструктуры). Вместо этого агрегат **накапливает** события внутри себя.

```php
class Order {
    private array $recordedEvents = [];

    public function markAsPaid(): void {
        $this->status = Status::PAID;
        // Просто записываем событие в память объекта
        $this->recordedEvents[] = new OrderPaidEvent($this->id);
    }

    public function releaseEvents(): array {
        $events = $this->recordedEvents;
        $this->recordedEvents = [];
        return $events;
    }
}
```

### 2. Как обрабатывать события?

Процесс обработки обычно разделяется на два уровня:

1.  **Синхронная обработка (внутри той же транзакции):**
    Используется, когда действие является критически важной частью того же бизнес-процесса. Например, при создании заказа нужно проверить лимит кредита.
2.  **Асинхронная обработка (через шину сообщений/Messenger):**
    Используется для побочных эффектов (Side Effects). Например: отправить Email, обновить поисковый индекс, отправить данные в аналитику. Это не должно тормозить основной процесс.

### 3. Связь с транзакциями (Самый важный момент)

Здесь кроется главная ловушка. Если вы опубликуете событие **до** `flush()`, может случиться так:
1.  Вы отправили событие `OrderPaid`.
2.  Слушатель (Handler) поймал его и начал отправлять Email.
3.  В этот момент в основной транзакции произошла ошибка (например, `Deadlock` или `Constraint Violation`), и `flush()` откатился.
4.  **Итог:** Пользователю ушло письмо об оплате, хотя в базе заказ остался в статусе «Новый». Это катастрофа.

**Мое решение: Transactional Outbox Pattern (или интеграция с Unit of Work).**

Я использую подход, где события «выстреливаются» только **после успешного завершения транзакции**.
В Symfony это удобно делать через `Doctrine Lifecycle Listeners` или интеграцию `Messenger` с `DoctrineTransactionMiddleware`. События собираются в агрегате, а Dispatcher вызывает их только тогда, когда `EntityManager` подтверждает успешный `commit`.

---

### 4. Проблемы и их решение

#### Какие проблемы решает подход:
*   **Слабая связанность (Decoupling):** `OrderService` ничего не знает о `EmailService`. Он просто говорит: «Заказ оплачен».
*   **Соблюдение SRP:** Логика отправки почты или обновления индекса не загромождает бизнес-логику заказа.
*   **Масштабируемость:** Мы можем легко вынести обработчики в отдельные микросервисы.

#### Какие проблемы создает:
1.  **Eventual Consistency (Согласованность в конечном счете):** Система становится распределенной. После оплаты заказ может отображаться как «оплаченный» в одном месте и «в обработке» в другом (пока дойдет асинхронное событие). Это нужно учитывать в UI (например, показывать статус "Processing").
2.  **Сложность отладки:** Трудно проследить сквозной поток (Trace) выполнения, когда один процесс порождает цепочку асинхронных событий. Решается использованием `Correlation ID` в логах.
3.  **Дублирование событий (At-least-once delivery):** В распределенных системах событие может прийти дважды (например, из-за сбоя сети при подтверждении получения).
    *   **Решение:** Обработчики должны быть **идемпотентными**. Если `SendEmailHandler` получил дважды одно и то же событие, он должен проверить, не отправляли ли мы это письмо уже.

### Резюме
Я использую доменные события для отделения **основного процесса** от **побочных эффектов**. Я накапливаю их внутри агрегата, публикую только после успешного коммита транзакции и всегда проектирую обработчики как идемпотентные, осознавая, что мы переходим в мир Eventual Consistency.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

Это фундаментальные вопросы, которые отделяют «просто программиста» от «проектировщика программных систем».

### 1. Entity vs Value Object

Разница заключается не в том, *что* это за данные, а в том, *как мы их идентифицируем* и *как они ведут себя при изменении*.

| Характеристика | Entity (Сущность) | Value Object (Объект-значение) |
| :--- | :--- | :--- |
| **Идентичность** | Имеет уникальный ID, который не меняется. | Не имеет ID. Идентичность определяется значениями свойств. |
| **Жизненный цикл** | Имеет историю. Мы отслеживаем изменения конкретного объекта. | Не имеет истории. Если значение меняется, мы создаем новый объект. |
| **Сравнение** | Сравнивается по ID (`$a->getId() === $b->getId()`). | Сравнивается по значениям всех свойств (`$a->equals($b)`). |
| **Изменяемость** | **Mutable** (может менять состояние). | **Immutable** (неизменяем). |

**Пример:**
*   **User** — это `Entity`. Даже если пользователь сменит имя, почту и адрес, он останется тем же самым пользователем (у него тот же ID).
*   **Address** — это `Value Object`. Если человек переехал, у него не появился «новый адрес с тем же смыслом», у него появился **другой** адрес. Если два человека живут по одному адресу, их адреса идентичны.

---

### 2. Как я принимаю решение (Алгоритм)

Когда я проектирую новую модель, я задаю себе три вопроса:

1.  **«Нужен ли этому объекту уникальный идентификатор?»**
    Если я могу отличить два объекта с одинаковыми данными (например, два одинаковых товара в корзине, но это разные позиции), значит, это `Entity`. Если нет — это `Value Object`.
2.  **«Важна ли история изменений этого объекта?»**
    Если мне важно знать, что этот объект *был* таким, а стал другим (сохранение истории состояний), это `Entity`. Если мне важно только текущее состояние (например, цвет кнопки) — это `Value Object`.
3.  **«Будет ли этот объект менять свое состояние?»**
    Если я хочу гарантировать, что объект всегда валиден и не изменится случайно в другом конце системы — я делаю его `Value Object` (immutable).

---

### 3. Единый язык (Ubiquitous Language)

**Ubiquitous Language** — это общий язык, на котором говорят **все** участники процесса: разработчики, бизнес-аналитики, менеджеры и заказчики. Это не просто «термины», это единый способ описания реальности.

**Как он влияет на код:**

В плохом коде терминология разработчиков (база данных, таблицы, CRUD, контроллеры) смешивается с терминологией бизнеса. В хорошем коде **термины из разговора с бизнесом превращаются в названия классов, методов и свойств.**

**Пример трансформации:**

*   **Разговор с бизнесом:** «Когда клиент совершает *оформление заказа*, мы должны *заблокировать* его *кредитный лимит*».
*   **Плохой код (Технический язык):**
    ```php
    // Разработчик думает о базе данных и CRUD
    $db->update('users', ['status' => 2], ['id' => $userId]);
    $db->insert('transactions', [...]);
    ```
*   **Хороший код (Ubiquitous Language):**
    ```php
    // Код читается как бизнес-правило
    $customer->reserveCreditLimit($amount);
    $order->place();
    ```

**Почему это критически важно:**
1.  **Снижение когнитивной нагрузки:** Разработчику не нужно постоянно «переводить» с бизнес-языка на программный.
2.  **Минимизация ошибок (Translation Gap):** Большинство багов возникает там, где разработчик неправильно понял бизнес-требование. Если язык один и тот же, риск ошибки минимален.
3.  **Самодокументированный код:** Код становится настолько понятным, что его можно использовать как живую документацию проекта.

**Мой подход к внедрению:** Я активно участвую в обсуждениях с экспертами предметной области (Domain Experts). Если они называют процесс «отгрузкой», я не называю его `sendOrder`, я называю его `dispatchOrder`. Если они говорят «заблокировать», я не использую `setStatus(0)`, я использую метод `block()`.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

Чистая архитектура (Clean Architecture) строиطся вокруг идеи **инверсии зависимостей**. Главная цель — сделать ядро приложения (бизнес-логику) независимым от внешних факторов: фреймворков, баз данных, API и инструментов.

### 1. Слои архитектуры

Я разделяю приложение на четыре логических слоя.

#### А. Domain Layer (Ядро)
Это самый внутренний слой. Он не зависит ни от чего. Здесь живет «чистая» бизнес-логика.
*   **Что внутри:** Entities, Value Objects, Domain Exceptions, Domain Services (логика, не принадлежащая одной сущности), Repository Interfaces (интерфейсы, а не реализации).
*   **Зависимости:** **Никаких.** Здесь нет упоминаний Doctrine, Symfony или даже PHP-библиотек для работы с сетью.

#### Б. Application Layer (Сценарии использования)
Слой, который оркеструет выполнение задач. Он описывает, *что* приложение делает, но не *как* это реализовано технически.
*   **Что внутри:** Use Cases (Сценарии), DTO (Data Transfer Objects), Command/Query (в случае CQRS), Application Services.
*   **Зависимости:** Только от **Domain Layer**.

#### В. Infrastructure Layer (Инфраструктура)
Слой, реализующий технические детали. Это «грязный» слой, который связывает приложение с реальным миром.
*   **Что внутри:** Реализации репозиториев (Doctrine), работа с почтой (Mailer), работа с очередями (Messenger), работа с внешними API, реализация интерфейсов из Domain слоя.
*   **Зависимости:** От **Application Layer** и **Domain Layer**, а также от внешних библиотек.

#### Г. Presentation / UI Layer (Интерфейс)
Входная точка в приложение.
*   **Что внутри:** Symfony Controllers, CLI Commands, API Resources (разбор JSON/XML), Webhooks.
*   **Зависимости:** От **Application Layer**. Контроллер не должен знать о базе данных, он только принимает запрос и вызывает Use Case.

---

### 2. Куда попадут компоненты?

| Компонент | Слой | Обоснование |
| :--- | :--- | :--- |
| **Symfony Controller** | **Presentation** | Это точка входа. Его задача — принять HTTP-запрос, превратить его в DTO и передать в Application слой. |
| **Doctrine (Repository Implementation)** | **Infrastructure** | Это деталь реализации хранения данных. В Domain лежит только интерфейс `UserRepositoryInterface`. |
| **Message Handler (Queue)** | **Application / Infrastructure** | Сам *обработчик* (логика) живет в Application, но *механизм* получения сообщений (Symfony Messenger) — в Infrastructure. |

---

### 3. Правило зависимостей (Dependency Rule)

Это фундаментальное правило: **Зависимости всегда направлены внутрь.**

*   `Presentation` $\to$ `Application` $\to$ `Domain`
*   `Infrastructure` $\to$ `Application` $\to$ `Domain`

**Никогда** не должно быть зависимости: `Domain` $\to$ `Infrastructure`. 
*Если вашему Domain-сервису нужно отправить Email, он не вызывает `Mailer`. Он вызывает интерфейс `NotificationServiceInterface`, который определен в Domain, а реализация этого интерфейса лежит в Infrastructure.*

---

### 4. Как следить, чтобы границы не нарушались?

Соблюдение границ — это самая сложная часть в долгосрочной перспективе. Я использую три уровня контроля:

#### А. Когнитивный уровень (Code Review)
Это первая линия обороны. На ревью я проверяю:
*   Импортирует ли класс из `Domain` что-то из `Infrastructure`? (Если да — это архитектурный баг).
*   Используются ли в `Domain` классы вроде `EntityManagerInterface` или `Request`? (Если да — это нарушение).

#### Б. Статический анализ (PHPStan / Psalm)
Я настраиваю правила статического анализа так, чтобы они проверяли зависимости.
*   Можно использовать пакеты вроде `phpstan-deprecation-rules` или писать кастомные правила, которые запрещают импорт определенных пространств имен (например, `App\Infrastructure\*`) в слое `App\Domain\*`.

#### В. Инструменты проверки архитектуры (ArchUnit для PHP)
Существует библиотека **PHPArch** или интеграции для PHPStan, которые позволяют писать тесты на архитектуру.
*   *Пример теста:* «Все классы в пространстве имен `App\Domain` не должны зависеть от пространства имен `App\Infrastructure`». 
*   Если разработчик случайно добавит `use Doctrine\ORM\...` в доменную сущность, тест упадет при запуске CI/CD.

**Итог:** Чистая архитектура — это не про то, как разложить файлы по папкам, а про то, **как направлены стрелки зависимостей**. Если стрелки смотрят наружу — архитектура рассыпается.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

Для Symfony-приложения я выбираю классическую **Пирамиду Тестирования**, но с учетом специфики работы с базой данных и инфраструктурой. Моя цель — достичь баланса между уверенностью в коде и скоростью обратной связи (feedback loop).

### 1. Структура пирамиды

#### А. Unit Tests (Основание — 70-80%)
Тестируют изолированную бизнес-логику.
*   **Что тестируем:** Value Objects, Domain Entities (логика внутри них), Domain Services, чистые алгоритмы.
*   **Что мокаем:** **Всё.** Здесь не должно быть никакой связи с БД, файловой системой или сетью. Если тесту нужен репозиторий, мы подкладываем `Mock` или `Stub` интерфейса.
*   **Цель:** Мгновенная проверка логики. Тысячи тестов должны пролетать за секунды.

#### Б. Integration Tests (Середина — 15-20%)
Проверяют взаимодействие компонентов системы.
*   **Что тестируем:** Репозитории (взаимодействие с PostgreSQL), интеграция сервисов (Application Service + Repository), работа с очередями (Messenger).
*   **Что мокаем:** Внешние API (через `MockHttpClient`), но **не мокаем базу данных**.
*   **Особенности:** Здесь мы используем реальную БД (обычно в Docker), чтобы убедиться, что наши SQL-запросы, маппинг Doctrine и ограничения (Constraints) работают правильно.

#### В. Functional/E2E Tests (Вершина — 5-10%)
Проверяют путь пользователя от запроса до ответа.
*   **Что тестируем:** Контроллеры, жизненный цикл запроса, авторизацию, преобразование JSON в DTO и обратно. В Symfony это делается через `WebTestCase`.
*   **Что мокаем:** Внешние тяжелые системы (платежные шлюзы, SMS-сервисы, сторонние API), но оставляем внутреннюю инфраструктуру (БД, кэш).

---

### 2. Стратегия работы с базой данных (PostgreSQL)

Тесты с базой — самые медленные и нестабильные. Чтобы они не превратились в кошмар, я использую следующие подходы:

1.  **Database Transactions (Самый важный прием):**
    Вместо того чтобы пересоздавать базу перед каждым тестом, я оборачиваю каждый тест в транзакцию. 
    *   Тест начинается $\to$ `BEGIN`.
    *   Тест выполняет действия $\to$ данные пишутся в БД.
    *   Тест заканчивается $\to$ `ROLLBACK`.
    Это позволяет держать базу в «чистом» состоянии и работает на порядки быстрее, чем `DROP/CREATE`. В Symfony это настраивается через `DAMA\DoctrineTestBundle`.

2.  **Тестовая БД в Docker:** Использование изолированного контейнера, который идентичен продакшну, гарантирует, что тесты не упадут из-за разницы версий PostgreSQL.

3.  **Миграции:** Тесты должны запускаться на актуальной схеме БД, созданной через `doctrine:migrations:migrate`.

---

### 3. Что мокать, а что нет?

| Объект | Тип теста | Решение | Почему? |
| :--- | :--- | :--- | :--- |
| **Value Object** | Unit | **Не мокать** | Они дешевые, простые и должны проверяться как реальные объекты. |
| **Repository Interface** | Unit | **Мокать** | Чтобы не зависеть от БД и не замедлять тест. |
| **Repository Implementation** | Integration | **Не мокать** | Нужно проверить, что SQL-запрос и маппинг корректны. |
| **External API (Stripe, Twilio)** | Integration/E2E | **Мокать** | Чтобы тесты не зависели от интернета и не тратили деньги/ресурсы. |
| **Messenger/Queue** | Integration | **Мокать/In-memory** | Чтобы не запускать реальных воркеров, но проверить, что сообщение было отправлено. |

---

### 4. Как поддерживать тесты быстрыми и стабильными?

1.  **Избегайте "Flaky Tests" (Мигающих тестов):**
    *   Никогда не используйте `sleep()`. Используйте `wait` (ожидание конкретного состояния) или проверяйте асинхронные события через проверки в базе/логах.
    *   Не полагайтесь на порядок выполнения тестов. Каждый тест должен быть независимым.

2.  **Параллелизация:**
    Используйте `Paratest`, чтобы запускать тесты в несколько потоков. Это критично, когда база данных уже раздута, а тестов сотни.

3.  **Разделение по профилям:**
    Разделяйте запуск: `vendor/bin/phpunit --group fast` (Unit) для локальной разработки и `vendor/bin/phpunit --group integration` для CI. Разработчик должен получать фидбек за секунды, а не за 10 минут.

4.  **Использование Test Data Builders:**
    Вместо того чтобы вручную создавать сложные объекты в каждом тесте, я использую паттерн **Builder** или библиотеки (типа `Foundry`). Это делает тесты читаемыми и устойчивыми к изменениям конструкторов сущностей.

**Итог:** Моя стратегия — **максимум Unit-тестов** для логики, **транзакционные интеграционные тесты** для БД и **строгая изоляция внешних систем** через моки. Это дает быструю, надежную и предсказуемую систему тестирования.

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Это классическая проблема конкурентного доступа. Если два процесса одновременно прочитают состояние записи, изменят его в памяти и попытаются сохранить обратно, возникнет ситуация **Lost Update (Потерянное обновление)**: изменения первого пользователя будут безвозвратно стерты изменениями второго.

Я выделяю три основных стратегии защиты: **Optimistic Locking**, **Pessimistic Locking** и **Atomic Updates**.

---

### 1. Optimistic Locking (Оптимистическая блокировка)

Мы предполагаем, что конфликты происходят редко. Мы не блокируем запись, но проверяем, не изменил ли её кто-то другой, пока мы работали.

*   **Механизм:** В таблицу добавляется поле `version` (число или таймштамп). При обновлении выполняется запрос: 
    `UPDATE table SET value = 'new', version = version + 1 WHERE id = 1 AND version = 5`.
*   **Результат:** Если другой процесс уже увеличил версию до 6, запрос вернет «0 строк изменено». Приложение поймет, что данные устарели, и выбросит исключение (`OptimisticLockException` в Doctrine).

**Плюсы:**
*   Не занимает ресурсы БД (нет удержания блокировок).
*   Высокая масштабируемость (подходит для высоконагруженных систем).

**Минусы:**
*   Требует обработки исключения на стороне приложения (нужно либо просить пользователя обновить страницу, либо реализовывать стратегию повтора/retry).

---

### 2. Pessimistic Locking (Пессимистическая блокировка)

Мы предполагаем, что конфликт почти неизбежен. Мы «запираем» запись в момент чтения.

*   **Механизм:** Используются SQL-команды `SELECT ... FOR UPDATE`.
*   **Результат:** Когда первый процесс читает запись с такой блокировкой, второй процесс, пытающийся прочитать её с тем же флагом, **замирает и ждет**, пока первый процесс не завершит транзакцию (`COMMIT` или `ROLLBACK`).

**Плюсы:**
*   Гарантирует абсолютную целостность.
*   Проще для программиста: не нужно обрабатывать ошибки «устаревшей версии», поток выполнения просто приостанавливается.

**Минусы:**
*   **Риск Deadlocks:** Если два процесса заблокируют разные записи и попытаются заблокировать записи друг друга — система встанет.
*   **Снижение производительности:** Пользователи вынуждены ждать друг друга, что увеличивает Latency.

---

### 3. Atomic Updates (Атомарные обновления)

Это перенос логики изменения из памяти приложения прямо в SQL-запрос.

*   **Механизм:** Вмеме `SET balance = 100` (где 100 — это вычисленное в PHP значение), мы используем `SET balance = balance - 10`.
*   **Результат:** База данных сама гарантирует атомарность изменения поля, используя свои внутренние механизмы блокировок на уровне строки.

**Плюсы:**
*   Максимальная скорость и отсутствие конфликтов на уровне приложения.
*   Не требует версионирования или длительных блокировок.

**Минусы:**
*   Не подходит для сложной бизнес-логики, которую невозможно описать одним SQL-запросом.
*   Вы теряете контроль над состоянием объекта в PHP (объект в памяти может не соответствовать тому, что в БД).

---

### Сравнительная таблица и мой выбор

| Критерий | Optimistic | Pessimistic | Atomic Update |
| :--- | :--- | :--- | :--- |
| **Производительность** | Высокая | Низкая | Очень высокая |
| **Сложность обработки** | Нужно обрабатывать ошибки | Нужно следить за дедлоками | Самая простая |
| **Тип конфликта** | "Ты опоздал" (Error) | "Подожди" (Wait) | "Сделай инкремент" (Atomic) |

#### Когда я выбираю каждый из подходов:

1.  **Выбираю Optimistic Locking**, если:
    *   Это обычное CRUD-приложение (редактирование профиля, описание товара).
    *   Конфликты случаются редко.
    *   Мне важна высокая пропускная способность системы.

2.  **Выбираю Pessimistic Locking**, если:
    *   Я работаю с критически важными данными, где цена ошибки — огромные деньги (например, бронирование места в самолете или сложная банковская операция).
    *   Конкуренция за одну и ту же запись очень высокая.

3.  **Выбираю Atomic Updates**, если:
    *   Задача простая: инкремент счетчика, списание суммы, изменение статуса.
    *   Мне нужно избежать всей сложности с версиями и блокировками.

**Мой профессиональный совет:** Всегда начинай с **Optimistic Locking**. Это самый сбалансированный подход для современной веб-архитектуры. Переходи к пессимистическим блокировкам только тогда, когда бизнес-требования или профилирование показывают, что это единственный способ избежать потерь.

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

Мой Git-процесс строится на принципах **предсказуемости, атомарности и высокой скорости обратной связи**. Я сторонник модели, близкой к **GitHub Flow**, но адаптированной под строгий контроль качества в командах.

Вот мой пайплайн:

### 1. Ветвление (Branching Model)
Я использую модель **Feature Branches**. В основной ветке (`main` или `master`) всегда находится стабильный, готовый к деплою код.

*   **`main`**: Единственная долгоживущая ветка. Запрещен прямой push. Только через Pull Request.
*   **`feature/JIRA-123-description`**: Ветки для новых фич.
*   **`hotfix/description`**: Ветки для критических исправлений на продакшене.
*   **`bugfix/description`**: Ветки для исправления багов в текущей разработке.

**Почему так?** Это исключает «загрязнение» основной ветки недоделанным кодом и позволяет изолированно тестировать каждую задачу.

### 2. Коммиты (Commit Messages)
Я придерживаюсь стандарта **Conventional Commats**. Это делает историю понятной, а автоматизацию (например, генерацию Changelog) — возможной.

**Формат:** `<type>(<scope>): <description>`

*   `feat`: Новая функциональность.
*   `fix`: Исправление бага.
*   `refactor`: Изменение кода без изменения логики.
*   `test`: Добавление или изменение тестов.
*   `chore`: Обновление зависимостей, конфигов, сборки.
*   `docs`: Изменение документации.

**Пример:** `feat(order): add validation for discount percentage`

**Почему так?** Это превращает лог коммитов из «помойки» в структурированный журнал событий. Это помогает быстро понять, когда и зачем была внесена та или иная правка.

### 3. Pull Request (PR) и Code Review
PR — это не просто «просьба влить код», это этап **обмена знаниями**.

*   **Описание PR:** Я всегда пишу подробный Template: *Что сделано? Зачем? Как протестировать? Скриншоты (если есть UI).*
*   **Review:** Я ищу не только ошибки, но и архитектурные несоответствия (соблюдение SOLID, чистота слоев).
*   **Атомарность PR:** Один PR = одна задача. Если задача большая, я разбиваю её на несколько маленьких PR. Это критически важно для качественного ревью.

**Почему так?** Маленькие PR читаются быстро и внимательно. Большие PR (на 1000+ строк) обычно ревьюят «по верхам», что приводит к пропуску багов.

### 4. CI/CD и автоматизация
Перед тем как PR попадет к человеку, он должен пройти через **CI (Continuous Integration)**.

**Pipeline в CI:**
1.  **Linting:** Проверка стиля (PHP-CS-Fixer) и статического анализа (PHPStan/Psalm).
2.  **Tests:** Запуск Unit и Integration тестов.
3.  **Build:** Сборка Docker-образа (если применимо).

**Если CI упал — PR не рассматривается.** Это экономит время ревьюера.

### 5. Релиз и деплой (Release Process)
Я предпочитаю **Continuous Deployment (CD)** для малых и средних изменений и **Scheduled Releases** для крупных обновлений.

*   **Merge:** После одобрения PR, ветка вливается в `main` (обыeчно через `squash and merge`, чтобы история в `main` была чистой и состояла из завершенных фич, а не кучи мелких коммитов разработчика).
*   **Tagging:** При каждом успешном деплое создается Git Tag (например, `v1.2.0`) согласно **Semantic Versioning (SemVer)**.
*   **Deployment:** Автоматический деплой из `main` в staging, а затем (после успешных тестов на staging) — в production.

**Почему так?**
*   **Squash and merge** делает историю `main` линейной и понятной.
*   **SemVer** позволяет другим командам и системам понимать, насколько изменение может быть разрушительным.
*   **Автоматизация** убирает человеческий фактор из процесса деплоя.

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

Для меня хороший код-ревью — это не «экзамен» и не поиск ошибок, а **процесс совместного улучшения продукта и обмена знаниями**. Хороший ревьюер не просто говорит «тут плохо», а объясняет «почему это плохо и как сделать лучше».

### 1. На что я смотрю в первую очередь (Приоритеты)

Я разделяю проверку на три уровня, чтобы не утонуть в деталях:

1.  **Корректность и надежность (Critical):**
    *   Работает ли код так, как описана задача?
    *   Нет(ли) здесь багов, утечек памяти или проблем с производительностью (N+1, отсутствие индексов)?
    *   Обработаны ли краевые случаи (edge cases) и ошибки (Exceptions)?
    *   **Это "Blocker" уровень. Если здесь есть проблема, ревью не завершается.**

2.2. **Архитектура и дизайн (Structural):**
    *   Соблюдены ли принципы SOLID и Clean Architecture?
    *   Не нарушены ли границы слоев (например, не поползла ли логика из Domain в Controller)?
    *   Правильно ли выбраны паттерны (Entity vs Value Object)?
    *   Насколько легко будет тестировать этот код?

3.  **Чистота и стиль (Stylistic):**
    *   Читаемость: Понятно ли по именованию переменных и методов, что происходит?
    *   Соблюдение стандартов (PSR).
    *   Избыточность: Нет ли здесь "мертвого" кода или лишних абстракций?

---

### 2. Как я маркирую замечания

Чтобы ревью было конструктивным, я использую систему уровней критичности. Это помогает автору понять, что из этого — «обязательно исправить», а что — «просто совет».

*   **[BLOCKER] / [MUST]**: Критическая ошибка, баг или серьезное нарушение архитектуры. PR не может быть влит, пока это не будет исправлено.
*   **[SUGGESTION] / [HINT]**: «Я бы сделал иначе, потомуs на это...». Это не ошибка, а предложение по улучшению. Автор имеет право не согласиться, если у него есть веские аргументы.
*   **[QUESTION]**: Я не уверен, как это работает. Вместо утверждения «здесь ошибка», я спрашиваю: «Почему здесь используется этот подход?». Это стимулирует диалог, а не защиту.
*   **[NITPICK]**: Мелкие стилистические придирки (лишний пробел, опечатка). Я помечаю их так, чтобы автор понимал: это не критично, но было бы круто исправить.

---

### 3. Как я поступаю при разногласии с автором

Конфликты в ревью — это нормально. Главное — не переходить на личности и не превращать обсуждение в борьбу эго.

**Мой алгоритм разрешения споров:**

1.  **Аргументация через "Почему":** Я никогда не говорю «сделай так». Я говорю: «Если мы сделаем так, то в будущем мы столкнемся с проблемой X, потому что...». Я всегда апеллирую к принципам (SOLID, производительность, поддерживаемость).
2.  **Поиск третьего пути:** Если мы зашли в тупик (я хочу А, автор хочет Б), я предлагаю: «Давай обсудим это голосом/в звонке на 5 минут». Текстовое обсуждение часто порождает ложную агрессию.
3.  **Принятие решения (Tie-breaking):**
    *   Если это вопрос **стиля** или спорного (но не критичного) решения — я уступаю. Моя задача — не доказать свою правоту, а пропустить задачу.
    *   Если это вопрос **архитектуры или надежности** — я привлекаю третьего человека (Lead/Architect). Решение принимается на основе консенсуса или авторитета, но не через "победу в споре".
4.  **Правило "Disagree and Commit":** Если решение принято (пусть даже не в мою пользу), я принимаю его и работаю дальше. Моя цель — успех команды, а не победа в споре.

**Резюме:** Хороший ревьюер — это **фасилитатор**. Моя цель — сделать код лучше, при этом сохранив мотивацию и уважение в команде.

Чтобы задача была «закрытой» и не требовала уточнений, я использую 5 компонентов:

Я не просто говорю «сделай поиск», а объясняю **зачем** (снижение нагрузки на поддержку). Это помогает разработчику понять масштаб: если он увидит, что поиск по датам будет тормозить при 1 млн записей, он сам предложит индекс или оптимизацию, понимая бизнес-ценность.

#### 4. Технические ограничения/требования (Non-functional requirements)
Я добавляю требования к производительности (200 мс) и покрытию тестами. Это гарантирует, что решение не станет «техническим долгом» сразу после деплоя.

#### 5. Определение "Готово" (Definition of Done)
Я подразумеваю, что задача считается выполненной не когда «код написан», а когда он прошел через:
*   Написание тестов.
*   Проверку производительности.
*   Соответствие API-контракту.

**Итог:** Такая формулировка переводит задачу из разряда «какая-то проблема с заказами» в разряд **«конкретный объем работ с измеримым результатом»**. Разработчик понимает, что ему делать, как проверять результат и как его будет оценивать QA.

## Q22 · Работа с задачами

**Интервьюер:** Ты выполняешь задачу с чёткими критериями приёмки. По ходу работы выясняется: а) нашёл попутный баг, не связанный с задачей; б) понял, что один из критериев приёмки противоречит цели задачи. Что делаешь в каждом случае и почему?

**Кандидат:**

Это ситуации, которые проверяют не только технический навык, но и профессиональную зрелость (Seniority). В обоих случаях я действую исходя из принципа **максимизации ценности для бизнеса при минимизации рисков**.

---

### Случай А: Нашёл «попутный» баг (Side-bug)

Главное правило здесь: **Не смешивать исправление багов с реализацией фичи.** Это классическая ловушка, которая ведет к раздуванию задач и риску сломать то, что работало.

**Мои действия:**
1.  **Оцениваю критичность:**
    *   Если это **Blocker** (например, баг в коде, который я сейчас меняю и который может привести к потере данных или падению системы), я исправляю его немедленно в рамках текущей задачи. Это оправдано, так как я всё равно нахожусь в этом контекте.
    *   Если это **некритичный баг** (например, опечатка в интерфейсе или неверное отображение цвета), я **не трогаю его**.
2.  **Регистрирую баг:** Я создаю отдельную задачу (Ticket/Issue) в Jira/Backlog с описанием: как воспроизвести, ожидаемый результат и фактический.
3.  **Информирую:** Я пишу в комментариях к текущей задаче или в Slack: *"При реализации фильтрации обнаружил баг [ссылка на тикет], связанный с X. В текущую задачу не включал, чтобы не затягивать сроки, но зафиксировал для исправления"*.

**Почему так?**
*   **Чистота истории:** В Git-логе и в истории задачи должно быть четко видно: что относится к фиче, а что — к багу.
*   **Предсказуемость:** Если я начну чинить всё подряд, я не уложусь в сроки (Estimation) и не смогу гарантировать, что новая фича работает корректно (я могу случайно внести регрессию в старый код).

---

### Случай Б: Критерий противоречит цели задачи

Это ситуация, когда **Acceptance Criteria (AC) конфликтуют с бизнес-целью**. Например: цель — «быстрый поиск», а критерий — «выводить в результатах детальную информацию о каждом заказе, включая все позиции и историю статусов» (что приведет к тяжелым JOIN-ам и медленной работе).

**Мои действия:**
1.  **Ни в коем случае не игнорирую критерий и не меняю его втихую.** Это приведет к тому, что задача будет «сдана», но клиент будет недоволен.
2.  **Анализирую конфликт:** Я готовлю аргументацию. Я не говорю «это плохо», я говорю: «Если мы реализуем критерий №3 именно так, то мы не достигнем цели "быстрый поиск", так как время ответа вырастет с 200мс до 2с».
3.  **Инициирую обсуждение (Communication):** Я иду к владельцу продукта (PO) или менеджеру.
    *   *«Я заметил противоречие: критерий X требует [такого-то действия], но это нарушает нашу цель по производительности. Как нам поступить?»*
4.  **Предлагаю альтернативу:** Я не прихожу с проблемой, я прихожу с вариантами решения.
    *   *Вариант 1:* Упростить критерий (выводить только краткую информацию в списке, а детали — по клику).
    *   *Вариант 2:* Усложнить архитектуру (добавить кэширование или использовать ElasticSearch), но это увеличит сроки разработки.

**Почему так?**
*   **Прозрачность:** Я снимаю с себя ответственность за «неправильное» решение, перекладывая её на того, кто определяет требования.
*   **Экономия ресурсов:** Лучше потратить 15 минут на обсуждение противоречия сейчас, чем 2 дня на написание кода, который потом придется переписывать.

### Итоговая философия

Я структурирую отчет в Pull Request или в комментарии к задаче (Jira/Trello) по следующим пунктам:

**А. Краткое резюме (Summary)**

*   **Manual Testing:** Список сценариев, которые я проверил вручную (например: «Проверил поиск с пустыми датами, поиск с невалидным форматом даты, поиск по существующему и несуществующему статусу»).

*   Если это UI: путь в интерфейсе (например, «Личный кабинет -> Мои заказы -> Фильтры»).

### 2. Что делать, если часть задачи сделать не удалось?

В реальном мире задачи часто сталкиваются с непредвиденными препятствиями. Скрывать это — верный способ потерять доверие команды.

**Мой алгоритм действий:**

1.  **Принцип радикальной прозрачности:** Я сообщаю об этом **сразу**, как только понял, что не укладываюсь в рамки или не могу выполнить часть критериев. Не в момент сдачи задачи, а в процессе.
2.  **Классификация проблемы:** Я разделяю, *почему* задача не сделана:
    *   **Техническая невозможность:** «Мы не можем реализовать фильтр по названию товара в рамках текущей архитектуры без внедрения ElasticSearch».
    *   **Нехватка времени/ресурсов:** «Я успел реализовать фильтры по датам и статусам, но не успел покрыть их интеграционными тестами из-за сложности миграции».
    *   **Обнаруженное ограничение (Dependency):** «Фильтр по датам не работает, так как поле `created_at` в базе данных имеет неверный часовой пояс».

3.  **Формат отчета при частичном выполнении:**
    Я использую подход **"Done vs Not Done"**:
    *   ✅ **Done:** Список реализованного функционала.
    *   ❌ **Not Done / Blocked:** Список того, что не сделано, и **причина**.
    *   🚀 **Proposed Solution / Next Steps:** Мои предложения, как закрыть «хвосты» (например, «Вынести фильтр по названию в следующую задачу/спринт»).

**Почему это важно?**
Это превращает «провал» в «управляемый риск». Вместо того чтобы сказать «Я не сделал задачу», я говорю: «Я сделал часть задачи, выявил проблему X и предлагаю решение Y». Это переводит дискуссию из плоскости «почему ты не справился» в плоскость «как нам двигаться дальше».

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

Важно начать с важного уточнения: в **PostgreSQL нет команды `FORCE INDEX`**. Эта конструкция существует в MySQL. В PostgreSQL управление использованием индексов работает иначе — через **планировщик (Planner/Optimizer)**.

Если вы встретили требование «заставить базу использовать индекс» в контексте PostgreSQL, это означает борьбу с тем, что планировщик решил сделать `Seq Scan` (последовательное сканирование) вместо `Index Scan`.

Вот как это работает в PostgreSQL и что делать, если индекс игнорируется.

---

### 1. Почему PostgreSQL может игнорировать индекс?

Планировщик PostgreSQL — это «умная» система, основанная на статистике. Он выбирает путь, который, по его мнению, будет самым дешевым (с наименьшим `cost`). Он может игнорировать индекс, если:

*   **Низкая селективность:** Если в таблице 1 000 000 строк, а вы ищете по полю, где 500 000 значений — планировщик решит, что проще прочитать всю таблицу целиком, чем прыгать по дереву индекса и постоянно обращаться к основной таблице (Heap).
*   **Устаревшая статистика:** Планировщик «думает», что в таблице мало строк, и выбирает `Seq Scan`.
*   **Функции над колонками:** Если вы пишете `WHERE UPPER(email) = 'USER@EXAMPLE.COM'`, обычный индекс по `email` не сработает.
*   **Типы данных:** Сравнение `integer` с `text` может привести к неявному приведению типов, что «убивает» индекс.

---

### 2. Как «заставить» PostgreSQL использовать индекс?

Поскольку прямой команды `FORCE` нет, мы используем следующие методы:

#### А. Создание функциональных (Expression) индексов
Если в запросе используется функция, индекс должен быть создан по результату этой функции.
*   **Проблема:** `WHERE DATE(created_at) = '2023-01-01'` (индекс по `created_at` не работает).
*   **Решение:** `CREATE INDEX idx_created_date ON orders (DATE(created_at));`

#### Б. Частичные индексы (Partial Indexes)
Если нам часто нужны только «активные» пользователи, не нужно индексировать всю таблицу.
*   **Решение:** `CREATE INDEX idx_active_users ON users (last_login) WHERE is_active = true;`
Это делает индекс крошечным, очень быстрым и эффективным.

#### В. Покрывающие индексы (Covering Indexes / `INCLUDE`)
Если запрос выбирает только те поля, которые уже есть в индексе, PostgreSQL сделает **Index Only Scan** (не заглядывая в основную таблицу).
*   **Решение:** `CREATE INDEX idx_user_email ON users (email) INCLUDE (username);` (В PostgreSQL 11+).

#### Г. Настройка параметров сессии (Для отладки)
Если нужно проверить, поможет ли индекс, можно временно «обмануть» планировщик, запретив ему использовать последовательное сканирование:
```sql
SET enable_seqscan = off;
EXPLAIN ANALYZE SELECT ...;
SET enable_seqscan = on; -- Вернуть обратно!
```
*Примечание: Это не решение проблемы, а инструмент диагностики.*

---

### 3. Когда стоит (и не стоит) вмешиваться?

**Не стоит вмешиваться, если:**
*   `EXPLAIN ANALYZE` показывает, что план запроса корректен, а время выполнения устраивает.
*   Статистика устарела (в этом случае достаточно выполнить `ANALYZE table_name`).

**Стоит вмешаться, если:**
1.  Вы видите в плане `Seq Scan` на огромной таблице при наличии подходящего индекса.
2.  Вы понимаете, что запросы часто используют специфические условия (например, поиск только по `is_deleted = false`), и частичный индекс даст колоссальный прирост.
3.  Вы наблюдаете высокую нагрузку на I/O (диск) из-за постоянного чтения всей таблицы.

### Итог для собеседования:
«В PostgreSQL нет `FORCE INDEX`. Вместо этого мы работаем с планировщиком. Если он игнорирует индекс, я анализирую план через `EXPLAIN ANALYZE`, проверяю селективность данных, актуальность статистики и наличие функций в `WHERE`. Для оптимизации я использую **функциональные**, **частичные** или **покрывающие (INCLUDE)** индексы, чтобы сделать доступ к данным максимально дешевым для планировщика».

## Q25 · Провокации

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

Короткий ответ: **На практике замедление практически равно нулю (менее 0.1% в большинстве сценариев).**

Если вы измеряете микробенчмарки (миллионы итераций в пустом цикле), вы можете увидеть разницу, но в реальном приложении, где 99% времени тратится на I/O (запросы к БД, сеть, чтение файлов, работа с фреймворком), влияние `strict_types` на производительность ничтожно.

### Почему это не замедляет код (техническая сторона)

Многие думают, что `strict_types=1` заставляет PHP выполнять «дополнительные проверки» на каждом шаге, и это должно стоить ресурсов. Но это не совсем так.

1.  **Оптимизация на уровне Zend Engine:** Современный PHP (особенно с использованием **JIT** в PHP 8) очень эффективно работает с типизированными данными. Когда вы явно указываете типы (и в аргументах, и в возвращаемых значениях), движку PHP гораздо проще оптимизировать машинный код. Ему не нужно постоянно проверять: «А что мне пришло? Строка? Число? Объект?». Он уже знает тип и может работать с ним напрямую.
2.  **Снижение нагрузки на Runtime:** В режиме `coercive` (по умолчанию) PHP тратит время на **приведение типов** (type juggling). Например, если вы передаете `"123"` вместо `123`, PHP тратит циклы процессора на преобразование строки в число. В режиме `strict` он просто сравнивает типы. Если они не совпадают — он выбрасывает ошибку. С точки�            *в чем парадокс:* **Strict mode может даже немного ускорить код**, так как исключается процесс неявного приведения типов.

### Когда замедление может стать заметным (теоретически)

Единственный сценарий, где можно увидеть разницу — это экстремальные вычислительные задачи, где миллионы раз вызывается функция с аргументами, которые постоянно меняют свой тип (например, то `int`, то `float`). В этом случае PHP будет тратить время на проверку типа при каждом вызове. Но в реальном веб-приложении такие сценарии — исключение.

### Почему я всё равно это использую?

Для меня `strict_types=1` — это не про производительность, а про **безопасность и предсказуемость**.

1.  **Предотвращение "тихих" ошибок:** Без `strict_types` передача `null` туда, где ожидается `string`, или передача `"0"` там, где ожидается `bool`, может не вызвать ошибки сразу, а привести к неверным расчетам в глубокой бизнес-логике. Это дико сложно отлаживать.
2.  **Документация в коде:** Типы становятся частью контракта. Глядя на сигнатуру метода, я точно знаю, что он принимает и что возвращает.
3.  **Помощь статическим анализаторам:** PHPStan и Psalm работают в разы эффективнее и точнее, когда код написан в строгом режиме.

**Итог:** Выбирать между `strict_types` и производительностью — это ложная дилемма. Выигрыш в надежности и читаемости кода многократно перевешивает микроскопические (и часто несуществующие) затраты на проверку типов.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

На самом деле, утверждение, что Doctrine **не поддерживает** составные первичные ключи, не совсем верно. Технически Doctrine **поддерживает** составные ключи (Composite Primary Keys), но делает это с большим неудобством, чем другие ORM (например, Hibernate в Java).

### Как это работает в Doctrine
Вы можете объявить составной ключ, указав `id` у нескольких полей:

```php
#[ORM\Entity]
class OrderItem {
    #[ORM\Id]
    #[ORM\ManyToOne(targetEntity: Order::class)]
    private Order $order;

    #[ORM\Id]
    #[ORM\Column(type: 'int')]
    private int $productId;
}
```

Однако, это порождает массу проблем, из-за которых опытные разработчики стараются их избегать.

---

### Почему это неудобно (Проблемы)

1.  **Сложность работы с `find()` и `getReference()`:**
    Вместо одного ID вам нужно передавать массив: `$repo->find(['orderId' => 1, 'productId' => 10])`. Это делает код более громоздким и менее читаемым.
2.  **Проблемы с отношениями (Associations):**
    Если другая сущность должна ссылаться на `OrderItem`, ей придется хранить **два** внешних ключа (`order_id` и `product_id`). Это усложняет маппинг, увеличивает количество JOIN-ов и раздувает размер таблиц.
3.  **Трудности с Unit of Work:**
    Doctrine внутри себя использует Identity Map (кэш объектов). Управление объектами с составными ключами внутри этого механизма сложнее, что иногда приводит к нюансам при работе с `flush()` и связями.
4. weak **Сложность в интеграции с инструментами:** Многие библиотеки (например, для построения API или генерации форм) ожидают, что у сущности есть один простой `id`.

---

### Как с этим «живут» в реальных проектах (Best Practices)

В современной разработке на PHP/Symfony принято придерживаться стратегии **Surrogate Keys (Суррогатных ключей)**.

#### 1. Использование суррогатного ID (Основной способ)
Вместо того чтобы использовать бизнес-ключ (составной ключ) в качестве первичного, мы добавляем техническое поле `id` (обычно `AUTO_INCREMENT` или `UUID`).

*   **Как это выглядит:** У `OrderItem` есть свой собственный `id` (Primary Key). Составной ключ (пара `order_id` + `product_id`) становится **Unique Constraint**.
*   **Почему это лучше:**
    *   Все связи в системе (Foreign Keys) теперь используют один простой `id`.
    *   В коде всегда можно вызвать `$repo->find($id)`.
    *   Бизнес-логика (составной ключ) отделена от технической реализации (суррогатный ключ).

```php
#[ORM\Entity]
#[ORM\UniqueConstraint(columns: ['order_id', 'product_id'])] // Гарантируем уникальность на уровне БД
class OrderItem {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null; // Суррогатный ключ

    #[ORM\ManyToOne(targetEntity: Order::class)]
    private Order $order;

    #[ORM\Column]
    private int $productId;
}
```

#### 2. Использование UUID
В распределенных системах или микросервисах вместо инкрементальных ID используют UUID. Это позволяет генерировать идентификаторы на стороне приложения (Domain Layer), не дожидаясь ответа от БД, что идеально сочетается с принципами DDD.

#### 3. Использование Value Objects для ключей
Если бизнес-логика требует, чтобы идентификатор был сложным (например, код филиала + номер счета), я не делаю это составным ключом в БД. Я создаю `Value Object` и маплю его в одну колонку (например, строку), чтобы сохранить простоту связей.

### Резюме
Я никогда не использую составные первичные ключи в Doctrine. Я всегда внедряю **суррогатный первичный ключ (`id`)** и накладываю на нужные поля **`UniqueConstraint`**. Это дает мне чистоту кода, предсказуемость ORM и при этом сохраняет целостность данных на уровне базы.

## Q27 · Мини-код-ревью

**Интервьюер:** Посмотри на этот код:

```php
class OrderController
{
    public function pay(Request $req): Response
    {
        $id = $req->get('order_id');
        $pdo = DB::connect();
        $order = $pdo->query("SELECT * FROM orders WHERE id = $id")->fetch();
        if (!$order) {
            return new Response('not found', 404);
        }
        $order['status'] = 'paid';
        $pdo->exec("UPDATE orders SET status = 'paid' WHERE id = $id");
        Mailer::send($order['email'], 'Ваш заказ оплачен');
        (new Logger())->log('paid ' . $id);
        return new Response('ok');
    }
}
```

Какие проблемы ты видишь и как бы ты этот код переделал? С чего начал бы и почему?

**Кандидат:**

Этот код — классический пример «антипаттерна», который в промышленной разработке недопустим. Он нарушает почти все правила безопасности, архитектуры и надежности.

### 1. Список проблем

**А. Критические (Security & Integrity):**
1.  **SQL Injection:** Переменная `$id` вставляется напрямую в запрос. Злоумышленник может передать `1; DROP TABLE users;`, и база будет уничтожена.
2.  **Race Condition (Состояние гонки):** Нет никакой защиты от одновного выполнения. Если два запроса придут одновременно, статус может обновиться некорректно или возникнуть логическая ошибка.
3.  **Отсутствие транзакционности:** Если `Mailer::send` упадет с ошибкой, статус в базе останется `paid`, но пользователь не получит письмо. Система окажется в противоречивом состоянии.

**Б. Архитектурные (Design & Maintainability):**
1.  **Нарушение SRP (Single Responsibility Principle):** Контроллер делает *всё*: работает с HTTP, работает с БД, отправляет почту, логирует. Он стал «Божественным объектом».
2.  **Жесткие зависимости (Tight Coupling):** Контроллер намертво привязан к статическим методам `DB::connect()`, `Mailer::send()` и `new Logger()`. Это делает невозможным юнит-тестирование.
3.  **Смешивание уровней:** Логика изменения статуса (бизнес-правило) лежит в контроллере, а не в доменной модели.

---

### 2. Как бы я это переделал (План действий)

Я бы начал не с написания кода, а с **проектирования слоев**. Мой план:
1.  Вынести бизнес-логику в **Domain Layer** (Entity + Domain Service).
2.  Вынести работу с данными в **Infrastructure Layer** (Repository).
3.  Вынести побочные эффекты в **Application Layer** (Use Case + Messenger).
4.  Очистить контроллер, сделав его только «входной дверью».

---

### 3. Итоговый рефакторинг

#### Шаг 1: Domain Layer (Сущность)
```php
readonly class Order {
    public function __construct(
        private int $id,
        private string $email,
        private string $status,
    ) {}

    public function pay(): void {
        if ($this->status === 'paid') {
            throw new OrderAlreadyPaidException();
        }
        // В реальности здесь может быть изменение состояния через приватное свойство
        // или создание нового экземпляра (если используем immutability)
    }

    public function getId(): int { return $this->id; }
    public function getEmail(): string { return $this->email; }
}
```

#### Шаg 2: Application Layer (Use Case)
```php
class PayOrderUseCase {
    public function __construct(
        private OrderRepositoryInterface $repository,
        private MessageBusInterface $eventBus, // Для асинхронных событий
    ) {}

    public function execute(int $orderId): void {
        // Транзакция гарантирует атомарность
        $this->repository->transactional(function() use ($orderId) {
            $order = $this->repository->find($orderId);
            if (!$order) {
                throw new OrderNotFoundException($orderId);
            }

            $order->pay();
            $this->repository->save($order);

            // Отправляем событие, а не вызываем Mailer напрямую
            $this->eventBus->dispatch(new OrderPaidEvent($order->getId(), $order->getEmail()));
        });
    }
}
```

#### Шаг 3: Infrastructure Layer (Реализация)
```php
class SqlOrderRepository implements OrderRepositoryInterface {
    public function find(int $id): Order {
        // Используем prepared statements (защита от SQL Injection)
        $data = $this->connection->fetchAssociative(
            'SELECT * FROM orders WHERE id = ?', [$id]
        );
        if (!$data) throw new OrderNotFoundException($id);
        return new Order((int)$data['id'], $data['email'], $data['status']);
    }

    public function save(Order $order): void {
        $this->connection->executeStatement(
            'UPDATE orders SET status = "paid" WHERE id = ?', 
            [$order->getId()]
        );
    }
}
```

#### Шаг 4: Presentation Layer (Контроллер)
```php
class OrderController extends AbstractController 
{
    public function __construct(
        private PayOrderUseCase $payOrderUseCase
    ) {}

    public function pay(Request $req): Response
    {
        $id = (int) $req->get('order_id');

        try {
            $this->payOrderUseCase->execute($id);
            return new JsonResponse(['status' => 'ok']);
        } catch (OrderNotFoundException $e) {
            return new JsonResponse(['error' => 'Not found'], 404);
        } catch (OrderAlreadyPaidException $e) {
            return new JsonResponse(['error' => 'Already paid'], 400);
        } catch (\Exception $e) {
            return new JsonResponse(['error' => 'Internal error'], 500);
        }
    }
}
```

### Что мы получили в итоге?
1.  **Безопасность:** SQL Injection исключен через prepared statements.
2.  **Надежность:** Транзакция гарантирует, что статус изменится только если всё прошло успешно.
3.  **Тестируемость:** Я могу написать Unit-тест на `PayOrderUseCase`, подставив Mock репозитория и Mock шины событий.
4.  **Масштабируемость:** Отправка письма теперь идет через событие (`OrderPaidEvent`). Если завтра мы захотим добавить SMS или логирование в ElasticSearch, мы просто добавим новый `EventHandler`, не меняя основной код.
5.  **Чистота:** Контроллер стал тонким, он только принимает запрос и возвращает ответ.

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Эта сущность нарушает сразу несколько фундаментальных принципов проектирования: **Чистую архитектуру**, **DDD** и даже базовые принципы **SOLID**.

### Что не так?

1.  **Нарушение Single Responsibility Principle (SRP):** Сущность `User` теперь отвечает не только за свои данные (бизнес-логику), но и за сохранение самой себя в базу данных. Это превращает её в «умную» сущность, которая знает слишком много об инфраструктуре.
2.  **Нарушение чистоты Domain Layer (Dependency Leakage):** Это самая грубая ошибка. В доменный слой (Entity) «просочился» объект из инфраструктурного слоя — `EntityManagerInterface`. Теперь ваш домен напрямую зависит от Doctrine. Если вы захотите сменить ORM или написать тесты без БД, вы не сможете этого сделать без огромных сложностей.
3.  **Нарушение инвариантов и предсказуемости (Side Effects):** Метод `changeEmail` имеет побочный эффект — он вызывает `flush()`. Вызывающий код может не ожидать, что вызов обычного сеттера внезапно инициирует тяжелую транзакцию в базе данных. Это делает поведение объекта непредсказуемым.
4.  **Сложность тестирования:** Чтобы написать простой Unit-тест на смену email, вам придется создавать тяжелый мок для `EntityManagerInterface`, что превращает простой тест в сложный интеграционный.

---

### Как бы я это исправил?

Принцип исправления: **«Домен — это чистые данные и правила. Инфраструктура — это способ их сохранить».**

#### Шаг 1: Очищаем Domain Layer
Убираем `EntityManager` и делаем сущность «глупой» относительно базы данных. Она только меняет свое состояние.

```php
#[ORM\Entity]
class User
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 180, unique: true)]
    private string $email;

    public function __construct(string $email)
    {
        // Здесь может быть валидация формата email
        $this->email = $email;
    }

    public function changeEmail(string $newEmail): void
    {
        // Здесь может быть бизнес-логика (например, проверка на уникальность через доменный сервис)
        $this->email = $newEmail;
    }

    public function getEmail(): string
    {
        return $this->email;
    }

    public function getId(): ?int
    {
        return $this->id;
    }
}
```

#### Шаг 2: Создаем Application Layer (Use Case)
Теперь за координацию действий отвечает сервис (Use Case), который знает и о домене, и об инфраструктуре.

```php
class ChangeEmailUseCase
{
    public function __construct(
        private UserRepositoryInterface $userRepository,
        private EntityManagerInterface $entityManager,
    ) {}

    public function execute(int $userId, string $newEmail): void
    {
        // 1. Загружаем сущность через репозиторий
        $user = $this->userRepository->find($userId);
        
        if (!$user) {
            throw new UserNotFoundException($userId);
        }

        // 2. Выполняем бизнес-действие
        $user->changeEmail($newEmail);

        // 3. Сохраняем изменения (Unit of Work управляет транзакцией)
        $this->entityManager->flush();
    }
}
```

### Итог изменений:
1.  **Чистота:** `User` больше не знает о существовании Doctrine. Он состоит только из данных и правил.
2.ten **Тестируемость:** Теперь я могу написать Unit-тест на `User` за миллисекунды, просто создав объект `new User('test@test.com')`.
3.  **Предсказуемость:** Изменение состояния объекта в памяти отделено от момента записи в базу.
4.  **Соблюдение SRP:** `User` отвечает за данные, `UserRepository` за поиск, `UseCase` за процесс, а `EntityManager` за синхронизацию.

## Q29 · Процесс и рассуждение

**Интервьюер:** Тебе нужно решить техническую проблему на незнакомых тебе технологии или стеке. Опиши последовательность своих действий от первого взгляда на задачу до уверенного ответа о сроках решения. Когда, по-твоему, нужно просить помощи у команды, а когда разбираться самому?

**Кандидат:**

Это ситуация, которая проверяет не только технический кругозор, но и **инженерную зрелость**. Мой подход строится на принципе: «Максимизировать скорость решения, минимизируя риски и затраты времени команды».

Вот мой пошаговый алгоритм:

### 1. Фаза исследования (Discovery) — «Не гадай, а изучай»

Первые 30–60 минут я трачу на деконструкцию задачи.

*   **Понимание контекста:** Прежде чем лезть в код, я должен понять: *что* именно должно произойти? Каков ожидаемый результат? Каковы ограничения (производительность, безопасность)?
*   **Анализ существующего решения:** Если задача касается существующего кода, я изучаю, как это реализовано сейчас. Я ищу паттерны, которые уже используются в проекте, чтобы не изобретать велосипед.
*   **Изучение документации и экосистемы:** Я иду в официальную документацию технологии. Если задача связана с библиотекой, я смотрю её `README`, примеры использования и типичные ошибки (Issues на GitHub).
*   **Локальное воспроизведение:** Я пытаюсь создать минимальный, изолированный пример (PoC — Proof of Concept), который воспроизводит проблему или демонстрирует решение. Это позволяет мне тестировать гипотезы, не ломая основной проект.

### 2. Фаза проверки гипотез (Spike)

Если задача сложная, я выделяю небольшое время (например, 2–4 часа) на «Spike» — исследование без обязательства написать идеальный код.

*   Я пробую разные подходы.
*   Я фиксирую, что работает, а что — нет.
*   Я оцениваю сложность: «Это простая настройка конфига или нам нужно переписывать целый модуль?».

### 3. Формирование оценки (Estimation)

Только после того, как я понял механику решения, я готов дать ответ по срокам. Мой ответ клиенту/менеджеру состоит из трех компонентов:
1.  **Оценка реализации:** Сколько времени займет написание кода.
2.  **Оценка рисков:** «Есть риск, что библиотека X не поддерживает Y, тогда нам придется делать Z».
3.  **Запас (Buffer):** Я всегда закладываю 20-30% времени на непредвиденные сложности (тестирование, отладка, рефакторинг).

---

### Когда разбираться самому, а когда просить помощи?

Это вопрос **экономики времени команды**.

#### Разбираться самому, если:
*   Проблема в области, где я обладаю базовыми знаниями (например, я знаю PHP, но не знаю конкретную библиотеку — я разберусь сам).
*   Проблема решается поиском в документации, StackOverflow или через отладку (Debugger).
*   Я нахожусь в фазе «исследования» (Spike) — это мое личное время на обучение.

**Правило:** Если я застрял, я даю себе ограниченное время (например, 1 час) на самостоятельный поиск. Если прогресса нет — пора менять стратегию.

#### Просить помощи, если:
1.  **Проблема в архитектуре проекта:** Если решение требует изменений, которые затронут несколько модулей или нарушат общие принципы проекта. Здесь нужен совет более опытного коллеги (Senior/Architect).
2.  **Блокирующая неопределенность:** Если я не понимаю *бизнес-требования* (что именно хочет клиент). Это не техническая проблема, а проблема коммуникации.
3.  **Риск для продакшена:** Если решение требует изменений в критическом пути (например, миграция БД на огромной таблице), я обязан проконсультироваться с командой, чтобы оценить риски.
4.  **«Стена»:** Если я потратил разумное количество времени (например, 2-3 часа) и не продвинулся ни на шаг. Постоянное «битье головой об стену» — это не продуктивность, это трата денег компании.

**Как правильно просить помощи:**
Я никогда не прихожу с вопросом: *«Я не понимаю, как это работает»*.
Я прихожу с формулировкой: *«Я пытаюсь решить задачу X. Я изучил документацию, попробовал подходы А и Б. Подход А не работает, потому что [причина]. У меня есть гипотеза В, но я сомневаюсь в её влиянии на производительность. Можешь подсказать?»*

**Это показывает, что я проделал работу, а не просто переложил ответственность на другого.**

## Q30 · Процесс и рассуждение

**Интервьюер:** Ты пообещал сделать задачу к завтрашнему дню, но по ходу работы понял, что это два дня работы. Что делаешь?

**Кандидат:**

Это критический момент, который проверяет мою **честность, проактивность и умение управлять ожиданиями (Stakeholder Management)**. Самая большая ошибка здесь — промолчать, надеясь «дожать» задачу за ночь, или попытаться сдать некачественный, сырой код, лишь бы успеть в дедлайн.

Мой алгоритм действий:

### 1. Немедленная коммуникация (Early Warning)
Я сообщу о проблеме **как можно раньше**. Если я понял это в 14:00, я не буду ждать 18:00 или завтрашнего утра. Чем раньше команда узнает о задержке, тем больше у неё пространства для маневра.

### 2. Анализ и классификация (Why & What)
Прежде чем идти к менеджеру/заказчику, я должен четко понимать, *почему* это произошло. Я разделяю причины на две категории:
*   **Недооценка сложности (Estimation Error):** «Я не учел, что в этой библиотеке нет метода X, и мне придется писать свой».
*   **Новые вводные (Discovery):** «В процессе работы выяснилось, что данные в БД приходят в другом формате, и это ломает текущую логику».

### 3. Предложение вариантов (Options, not just Problems)
Я никогда не прихожу с проблемой «я не успеваю». Я прихожу с **вариантами решения**. Я предлагаю три сценария на выбор:

*   **Вариант А: Сохранение качества (Full Scope).**
    *   *Суть:* Мы делаем задачу полностью, как планировалось, но срок сдвигается на +1 день.
    *   *Когда выбирать:* Если задача критически важна и её нельзя дробить.
*   **Вариант Б: Декомпозиция (MVP / Phase 1).**
    *   *Суть:* Мы делаем основную часть задачи к завтрашнему дню, но откладываем второстепенные части (например, обработку пограничных случаев или второстепенные поля) на следующий день.
    *   Когда выбираю: Если бизнес очень ждет фичу «здесь и сейчас».
*   **Вариант В: Смена приоритетов.**
    **Суть:** Я спрашиваю: «Если я задержу эту задачу на день, как это повлияет на другие задачи в этом спринте? Стоит ли мне бросить текущую задачу и переключиться на более приоритетную задачу Y?».

---

### Пример того, как я это озвучу (Сценарий)

**Плохо:** *"Я не успею доделать задачу к завтра. Нужно еще один день".* (Это создает панику и не дает вариантов).

**Хорошо:**
> «Я работаю над задачей по интеграции платежного шлюза. В процессе реализации выяснилось, что API шлюза требует сложной трансформации данных, которую я не учел при оценке. 
> 
> Сейчас ситуация такая:
> 1. Основной процесс оплаты готов, но обработка возвратов (refunds) требует еще около 8 часов работы.
> 2. У меня есть два варианта: 
>    — Либо мы деплоим завтра только оплату, а возвраты добавим в среду.
    — Либо я продолжаю работать и сдаю всё вместе в среду утром.
>
> Как нам будет лучше поступить, исходя из планов релиза?»

### Почему это правильно?
1.  **Прозрачность:** Я не скрываю проблему.
2.  **Профессионализм:** Я показываю, что понимаю технические причины задержки.
3.  **Бизнес-ориентированность:** Я даю менеджеру **инструменты для принятия решения**, а не просто констатирую факт провала. Я помогаю ему управлять рисками.

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

Это вопрос о поиске баланса между **инженерным совершенством** и **бизнес-ценностью**. В идеальном мире код должен быть идеальным, но в реальном мире «идеальный код, который никогда не дошел до продакшена, не имеет никакой ценности».

Я использую концепцию **«Достаточно хорошего качества» (Good Enough Quality)**, опираясь на следующие критерии.

### 1. Когда код «достаточно хорош» (Definition of Done)

Я считаю код готовым к отдаче, если он соответствует четырем критериям:

1.  **Корректность (Correctness):** Он решает поставленную бизнес-задачу и проходит все согласованные Acceptance Criteria.
2.  **Надежность (Reliability):** Он покрыт тестами (Unit и Integration), которые проверяют не только «счастливый путь» (happy path), но и критические ошибки. Он не ломает существующий функционал (пройдены регрессионные тесты).
3.  **Безопасность и производительность:** Он не создает дыр в безопасности (SQL Injection, XSS) и не содержит явных проблем с производительностью (N+1, отсутствие индексов), которые могут «положить» систему под нагрузкой.
4.  **Поддерживаемость (Maintainability):** Код достаточно чист, чтобы другой разработчик мог его прочитать и понять логику без моего участия. Он следует принятым в команде стандартам (PSR, Style Guide).

**Если эти 4 пункта выполнены — код готов к релизу. Любое дальнейшее улучшение — это уже рефакторинг.**

---

### 2. Когда стоит продолжать улучшать (Refactoring)

Я продолжаю улучшать код, если замечаю признаки **технического долга**, который начнет мешать скорости разработки в будущем:

*   **Накопление сложности:** Если я вижу, что класс становится слишком большим и сложно меняется (нарушение SRP).
*   **Дублирование:** Если я пишу один и тот тот же код во второй или третий раз (нарушение DRY).
*   **Запах «хрупкости»:** Если при изменении одного модуля внезапно «отваливается» другой, совершенно не связанный с ним. Это сигнал, что связи слишком жесткие (Tight Coupling).

---

### 3. Как я соблюдаю баланс (Стратегия)

В реальном проекте я использую три подхода для управления этим балансом:

#### А. Правило «Бойскаута» (Boy Scout Rule)
*«Оставляй место стоянки чище, чем оно было до тебя».*
Я не выделяю отдельные спринты на «просто рефакторинг» (бизнес это не любит). Вместо этого я делаю микро-улучшения прямо во время реализации фичи. Если я лезу в старый класс, чтобы добавить туда поле, я заодно исправлю там опечатку или разобью слишком длинный метод.
