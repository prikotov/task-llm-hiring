## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

### Рассуждение

Когда говорят о «чистом и надежном коде» в контексте PHP, я сразу выделяю две стороны медали: **предсказуемость** (чтобы код вел себя так, как от него ожидают) и **лаконичность** (чтобы код было легко читать и поддерживать).

Если раньше PHP часто критиковали за «слабую типизацию» и «неявное поведение», то начиная с версии 8.0, язык движется в сторону строгой типизации и уменьшения шаблонного кода (boilerplate). 

Я бы выделил четыре ключевых направления:
1. **Строгость типов и уменьшение неопределенности.** Это база надежности. Если мы можем на уровне языка запретить передачу `null` туда, где он не ожидается, мы предотвращаем целый класс ошибок (те самые `Uncaught TypeError`).
2. **Снижение визуального шума.** Чистый код — это не только архитектура, но и отсутствие лишних строк, которые мешают видеть суть. Чем меньше «мусора», тем легче проводить Code Review.
3. **Улучшение работы с Nullable-объектами.** Это напрямую влияет на читаемость логики ветвления.
4. **Property Promotion.** Это киллер-фича для DTO и сервисов, которая делает конструкторы, наконец-то, человечными.

Я не буду упоминать JIT, так как это вопрос производительности, а не чистоты или надежности кода, хотя это и важно.

---

### Ответ

Для меня наиболее важными являются следующие возможности:

#### 1. Constructor Property Promotion (PHP 8.0+)
Это радикально упрощает объявление DTO (Data Transfer Objects) и сервисов. Раньше мы писали по 3-4 строки на каждое свойство, что раздувало файлы. Теперь описание структуры и инициализация происходят в одном месте.

```php
// Было (до PHP 8.0)
class UserDto {
    public string $email;
    public int $age;

    public function __construct(string $email, int $age) {
        $this->email = $email;
        $this->age = $age;
    }
}

// Стало (PHP 8.0+)
class UserDto {
    public function __construct(
        public readonly string $email,
        public readonly int $age,
    ) {}
}
```
*Это делает код чище и уменьшает вероятность ошибки при присваивании в конструкторе.*

#### 2. Readonly Properties (PHP 8.1+)
В DDD и чистой архитектуре мы постоянно используем Value Objects и DTO. Эти объекты должны быть неизменяемыми (immutable) по своей сути. `readonly` гарантирует, что состояние объекта не будет изменено случайно после создания, что критически важно для надежности.

```php
readonly class Money {
    public function __construct(
        public int $amount,
        public string $currency,
    ) {}
}

$money = new Money(100, 'USD');
// $money->amount = 200; // Fatal Error: Cannot modify readonly property
```

#### 3. Union Types и Intersection Types (PHP 8.0 / 8.1+)
Раньше для описания нескольких возможных типов мы использовали PHPDoc (`@param string|int $id`), что не гарантировало защиту во время выполнения. Теперь это часть системы типов. Intersection Types позволяют более точно описывать требования к объектам, реализующим несколько интерфейсов.

```php
// Union Types: объект может быть либо User, либо Guest
public function authenticate(User|Guest $actor): void { ... }

// Intersection Types: объект ОБЯЗАН реализовывать оба интерфейса
public function process(LoggerInterface&CacheableInterface $service): void { ... }
```
*Это позволяет на уровне сигнатуры метода четко заявлять о контракте, не прибегая к проверкам `instanceof` внутри тела функции.*

#### 4. Match Expression (PHP 8.0+)
`match` — это более строгая и лаконичная замена `switch`. В отличие от `switch`, `match` возвращает значение и использует строгое сравнение (`===`), что исключает трудноуловимые баги с приведением типов.

```php
// Надежнее и чище, чем switch
$statusLabel = match ($status) {
    Status::Active => 'Пользователь активен',
    Status::Pending => 'Ожидает подтверждения',
    Status::Banned  => 'Заблокирован',
    default         => throw new \InvalidArgumentException("Unknown status"),
};
```

**Итог:** Сочетание **Property Promotion**, **Readonly** и **строгой типизации (Union/Intersection)** превращает PHP в язык, на котором можно писать максимально предсказуемый, иммутабельный и защищенный от ошибок код, при этом тратя гораздо меньше времени на написание шаблонного кода.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

### Рассуждение

Вопрос о системе типов в PHP — это классическая проверка на понимание того, как язык работает «под капотом». Здесь важно не просто сказать «типы бывают такие-то», а разобрать фундаментальное различие между **коэрцитивным** (приведение типов) и **строгим** режимом.

Многие разработчики ошибочно полагают, что PHP — это «слаботипизированный» язык. На самом деле, начиная с PHP 7 и 8, он стал довольно строгим, но по умолчанию сохраняет обратную совместимость, работая в режиме автоматического приведения типов.

Я разделю ответ на три части:
1. **Механика приведения типов (Coercive mode)** — почему PHP «прощает» ошибки по умолчанию.
2. **Роль `declare(strict_types=1)`** — как мы переключаем движок в режим строгого контроля.
3. **Практические ловушки и кейсы** — где новички спотыкаются, а опытные инженеры используют типы для защиты бизнес-логики.

Важный нюанс, который часто упускают: `strict_types` действует только на **вызовы функций внутри того файла, где она объявлена**. Это не глобальный флаг для всей программы. Если файл `A.php` объявил `strict_types=1` и вызывает функцию из файла `B.php`, где этот флаг не стоит — приведение типов будет происходить по правилам файла `B.php`. Это часто сбивает с толку на больших проектах.

---

### Ответ

#### 1. Поведение по умолчанию (Coercive Mode)
Если вы не объявили `strict_types=1`, PHP работает в режиме «попытки угодить». Если тип не совпадает, он пытается привести его к нужному типу (coercion).

```php
function add(int $a, int $b): int {
    return $a + $b;
}

// PHP молча приведет строку "5" к числу 5
echo add(5, "5"); // Результат: 10 (без ошибок)

// Но если строка не числовая — будет TypeError
// echo add(5, "five"); // Fatal error: Uncaught TypeError
```

#### 2. Что дает `declare(strict_types=1)`
Эта директива отключает автоматическое приведение типов при вызове функций. Если функция ожидает `int`, а вы передали `string`, даже если это строка `"5"`, PHP выбросит `TypeError`. Это превращает PHP из языка, который «угадывает», в язык, который «требует».

```php
declare(strict_types=1);

function setAge(int $age): void {
    echo "Age set to $age";
}

setAge(25);   // OK
// setAge("25"); // Fatal error: Uncaught TypeError (даже если строка числовая!)
```

#### 3. Типичные ловушки на практике

**Ловушка №1: Неявное приведение в условиях (Loose Comparison)**
Это не совсем про систему типов функций, но это фундаментальная проблема PHP. Использование `==` вместо `===` — источник бесконечного количества багов.

```php
$status = 0;
if ($status == "active") { // true! В PHP 7/8 "0" == "active" может вести себя странно, 
                           // но классический пример: 0 == "anything" часто давал true в старых версиях.
}
// Правило: Всегда используем ===
```

**Ловушка №2: Типизация в массивах**
Это самая большая «дыра» в безопасности типов PHP. Вы можете типизировать аргумент как `array`, но вы **не можете** типизировать содержимое массива средствами языка.

```php
/** @param User[] $users */ // Это лишь подсказка для IDE и статического анализатора
function processUsers(array $users): void {
    foreach ($users as $user) {
        // В рантайме здесь может оказаться строка или null, 
        // и PHP это пропустит, пока вы не вызовете метод у объекта.
        $user->getId(); 
    }
}
```
*Решение: Использовать коллекции (объекты-обертки) или DTO вместо сырых массивов.*

**Ловушка №3: Nullable типы и "Silent Failure"**
Если не использовать явные nullable-типы (`?int`), а полагаться на то, что «ну там как-нибудь придет», можно получить трудноотловимые ошибки.

#### 4. Где типизация спасает, а где удивляет

**Пример «Спасения» (Бизнес-логика):**
Использование `Value Objects` с типизацией гарантирует, что в систему не попадет мусор.

```php
readonly class Email {
    public function __construct(public string $value) {
        if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
            throw new \InvalidArgumentException("Invalid email");
        }
    }
}

function registerUser(Email $email): void { ... }

// registerUser("not-an-email"); // Ошибка еще на этапе создания объекта, а не внутри функции
```

**Пример «Удивления» (Приведение типов в сравнениях):**
PHP иногда ведет себя контринтуитивно при сравнении разных типов, если не использовать строгий режим.

```php
// В некоторых версиях и контекстах:
var_dump(0 == "0");      // true
var_dump(0 == "foo");    // false (но это может зависеть от версии PHP)
var_dump(false == "");   // true
```

**Мой вывод:** Для профессиональной разработки на Symfony/Doctrine использование `declare(strict_types=1)` во всех файлах является **обязательным стандартом**. Это позволяет переложить часть ответственности за корректность данных с «тестов и надежды» на движок языка, делая систему предсказуемой. А для защиты содержимого коллекций я всегда предпочитаю типизированные объекты вместо массивов.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

### Рассуждение

Вопрос об исключениях — это вопрос о том, как приложение сообщает о своем состоянии, когда что-то идет не по плану. В плохих проектах исключения используются как способ управления логикой (flow control), что превращает код в спагетти. В хороших — исключение является сигналом о том, что **предусловие было нарушено** или **невозможно продолжить выполнение текущей операции**.

При проектировании я опираюсь на три принципа:
1. **Исключение — это не поток управления.** Мы не используем `try-catch` для реализации `if-else`.
2. **Исключение должно быть информативным.** Оно должно нести контекст (что именно пошло не так) и быть типизированным.
3. **Разделение на ожидаемые и непредвиденные ошибки.** Это ключевой момент для стратегии обработки (catch vs global handler).

Я разделяю исключения на две большие категории:
*   **Domain/Application Exceptions (Ожидаемые):** Например, `InsufficientFundsException`. Это часть бизнес-логики. Мы *ожидаем*, что это может случиться, и мы должны это обработать (показать пользователю сообщение).
*   **Infrastructure/Runtime Exceptions (Непредвиденные):** Например, `PDOException` или `ConnectionTimeoutException`. Это технические сбои. Мы не можем «исправить» их логикой, поэтому они должны всплывать наверх к глобальному обработчику (Sentry/Logger), чтобы разработчик узнал о них.

---

### Ответ

#### 1. Иерархия исключений
Я никогда не использую базовый `\Exception`. Я всегда создаю свою иерархию, привязанную к слоям архитектуры.

*   **Domain Layer:** `DomainException` (базовый для домена) $\to$ `OrderNotFoundException`, `InsufficientStockException`.
*   **Application Layer:** `ApplicationException` $\to$ `UserRegistrationFailedException`.
*   **Infrastructure Layer:** Здесь я обычно не создаю свои классы, а пробрасываю или оборачиваю системные.

Это позволяет мне в контроллере или Middleware делать точечную обработку:
```php
try {
    $this->orderService->placeOrder($order);
} catch (InsufficientStockException $e) {
    // Возвращаем 400 Bad Request с понятным текстом
} catch (OrderNotFoundException $e) {
    // Возвращаем 404 Not Found
} catch (\Throwable $e) {
    // Логируем ошибку (500 Internal Server Error)
}
```

#### 2. Оборачивание (Exception Wrapping)
Это важнейшая техника при работе с внешними библиотеками (Doctrine, AWS SDK, Stripe API). Если библиотека выбрасывает `Stripe\Exception\CardException`, я не должен пробрасывать её напрямую в контроллер. Это нарушает инкапсуляцию (контроллер начинает зависеть от Stripe).

Я использую паттерн **"Catch and Wrap"**:
```php
try {
    $this->paymentGateway->charge($amount);
} catch (Stripe\Exception\CardException $e) {
    // Оборачиваем в наше доменное исключение
    throw new PaymentFailedException("Payment declined: " . $e->getMessage(), 0, $e);
}
```
*Примечание: Я всегда передаю `$e` третьим аргументом в конструктор (as `$previous`), чтобы сохранить **stack trace** оригинальной ошибки. Без этого дебаг превращается в ад.*

#### 3. Контракт метода
Контракт метода — это не только сигнатура `function doSomething(int $id): void`. Это также и **декларация того, какие исключения метод может выбросить**.

В чисто архитектурных проектах я придерживаюсь правила: если метод выбрасывает исключение, которое является частью бизнес-логики, это должно быть задокументировано (в PHPDoc или просто понятно из названия типа исключения). Если метод выбрасывает `RuntimeException`, это значит, что он нарушил свои обязательства (предусловия), и вызывающая сторона должна была это предотвратить.

#### 4. Антипаттерны

1.  **Exceptions for Flow Control:** Использование `try-catch` вместо проверки условий.
    *   *Плохо:* `try { $user->login(); } catch (LoginFailedException $e) { ... }`
    *   *Хорошо:* `if (!$user->canLogin()) { ... }`
2.  **Generic Catch-All:** `catch (\Exception $e) { // do nothing }`. Это "заглатывание" ошибок. Если ошибка произошла, она должна быть либо обработана, либо логирована, либо проброшена. "Тихое" проглатывание — самый быстрый способ получить несогласованные данные в базе.
3.  **Swallowing the Stack Trace:** Создание нового исключения без передачи `$previous`. Мы теряем информацию о том, где именно в глубоких слоях инфраструктуры произошел сбой.
4.  **Leaking Implementation Details:** Проброс `PDOException` или `Doctrine\ORM\EntityNotFoundException` напрямую в API-ответ. Это не только плохая практика (утечка структуры БД), но и дыра в безопасности.

**Итог:** Моя стратегия — **"Fail Fast"** (падай быстро и явно) на уровне инфраструктуры и **"Graceful Degradation"** (плавная обработка) на уровне доменной логики.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

### Рассуждение

Когда я анализирую legacy-проекты или код, написанный в спешке, я вижу, что SOLID нарушается повсеместно. Но если нужно выбрать «чемпиона» по нарушениям, то это однозначно **Single Responsibility Principle (SRP)**.

Почему именно он? Потому что SRP — это не про то, что «класс должен делать одну вещь». Это про то, что **«у класса должна быть только одна причина для изменения»**. 

Причины нарушений SRP в реальности:
1. **Спешка (Time-to-market):** Разработчику проще добавить еще один метод в существующий сервис, чем создавать новый класс и настраивать DI (Dependency Injection).
2. **Понимание абстракций:** Многие путают «функциональную ответственность» (сервис делает заказы) с «технической ответственностью» (сервис делает заказы, отправляет email, пишет в лог и обновляет кеш).
3. **Отсутствие культуры DDD:** Без четкого разделения на слои (Domain, Application, Infrastructure) логика неизбежно перемешивается.

Второй по частоте — **Dependency Inversion Principle (DIP)**, так как новички часто создают жесткие зависимости (`new Service()`) вместо использования интерфейсов, что убивает тестируемость. Но SRP — это корень большинства проблем с поддержкой кода.

---

### Ответ

Самый часто нарушаемый принцип — **Single Responsibility Principle (SRP)**.

#### Типовой пример нарушения (The "God Service")

Представьте сервис заказов. В реальности он часто превращается в "комбайн", который делает всё: считает цену, сохраняет в базу, отправляет email и уведомляет стороннюю службу доставки.

```php
class OrderService 
{
    public function placeOrder(array $data): void 
    {
        // 1. Логика расчета стоимости (Бизнес-логика)
        $total = $data['price'] * $data['quantity'];
        if ($total <= 0) {
            throw new \InvalidArgumentException("Invalid total");
        }

        // 2. Работа с БД (Инфраструктура)
        // Прямое использование PDO или EntityManager внутри бизнес-логики
        $db = new PDO('pgsql:host=localhost;dbname=shop', 'user', 'pass');
        $stmt = $db->prepare("INSERT INTO orders (total) VALUES (?)");
        $stmt->execute([$total]);

        // 3. Отправка уведомлений (Внешний сервис)
        $mail = new PHPMailer();
        $mail->send("Order created with total: $total");

        // 4. Логирование (Инфраструктура/Побочный эффект)
        file_put_contents('app.log', "Order placed: $total" . PHP_EOL, FILE_APPEND);
    }
}
```

**Почему это плохо?**
* **Причина изменения №1:** Изменится логика налогов — правим `OrderService`.
* **Причина изменения №2:** Перейдем с MySQL на PostgreSQL — правим `OrderService`.
* **Причина изменения №3:** Решим отправлять SMS вместо Email — правим `OrderService`.
* **Тестирование:** Невозможно протестировать расчет цены, не создав реальное подключение к БД и не отправив реальное письмо.

---

#### Рефакторинг (Применение SRP и DIP)

Мы разделяем ответственности. `OrderService` теперь отвечает только за **оркестрацию** процесса (Application Service).

```php
// 1. Domain Layer: Чистая логика
readonly class Order {
    public function __construct(
        public int $amount,
        public int $quantity
    ) {}

    public function calculateTotal(): int {
        return $this->amount * $this->quantity;
    }
}

// 2. Domain/Application Layer: Интерфейсы (DIP)
interface OrderRepositoryInterface {
    public function save(Order $order): void;
}

interface NotificationServiceInterface {
    public function notify(string $message): void;
}

// 3. Application Layer: Оркестратор
class PlaceOrderUseCase 
{
    public function __construct(
        private OrderRepositoryInterface $repository,
        private NotificationServiceInterface $notifier,
        private LoggerInterface $logger // Стандартный PSR-3 логгер
    ) {}

    public function execute(int $price, int $quantity): void 
    {
        $order = new Order($price, $quantity);
        $total = $order->calculateTotal();

        if ($total <= 0) {
            throw new \InvalidArgumentException("Invalid total");
        }

        // Мы не знаем КАК сохраняется и КАК отправляется, мы просто вызываем контракт
        $this->repository->save($order);
        $this->notifier->notify("Order placed: $total");
        $this->logger->info("Order processed successfully");
    }
}
```

**Что изменилось:**
1. **Разделение ответственности:** `Order` знает только про расчет, `OrderRepository` — только про БД, `PlaceOrderUseCase` — только про последовательность шагов.
2. **Тестируемость:** Теперь я могу легко написать Unit-тест для `PlaceOrderUseCase`, подложив **Mocks** для репозитория и нотификатора. Мне не нужна реальная база или SMTP-сервер.
3. **Гибкость:** Если завтра мы заменим `PHPMailer` на `Amazon SES`, мы просто создадим новый класс `AmazonSesNotifier` (реализующий `NotificationServiceInterface`) и поменяем его в DI-контейнере. Сам `PlaceOrderUseCase` не изменится ни на одну строку.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

### Рассуждение

Это отличный вопрос, который отделяет «академического» разработчика от «инженера». В учебниках SOLID — это закон. В реальном производстве — это **инструмент управления сложностью**. 

Любая архитектурная практика имеет свою цену: **время разработки, когнитивная нагрузка на команду и сложность системы**. Если цена применения принципа выше, чем профит от его соблюдения, то применение принципа становится антипаттерном (overengineering).

Я выделяю три ключевых фактора, когда нарушение SOLID может быть оправданным:
1. **Срок (Time-to-market):** Если нужно проверить гипотезу (MVP) завтра, а не через месяц, строить идеальную абстракцию — значит проиграть бизнесу.
2. **Масштаб (Scale):** Если код будет жить один раз (скрипт миграции, разовый импорт данных, прототип), тратить силы на DIP или SRP — это пустая трата денег компании.
3. **Сложность задачи (Complexity):** Иногда избыточное дробление на интерфейсы и классы делает код не «чище», а «нечитаемее» (так называемый *Indirection Hell*), когда для понимания одной строчки нужно пропрыгать по десяти файлам.

Я не считаю, что нарушения «оправданы» в долгосрочной перспективе, но я считаю их **допустимыми в краткосрочной**, при условии, что мы осознаем технический долг и готовы его вернуть.

---

### Ответ

Да, нарушать SOLID можно. Инженер должен уметь оценивать **Trade-offs** (компромиссы).

#### Пример оправданного нарушения: Принцип единственной ответственности (SRP) в скриптах или простых CRUD-контроллерах.

Представьте, что нам нужно написать небольшой скрипт для миграции данных из одной таблицы в другую или скрипт, который раз в сутки выгружает отчет в CSV и отправляет его администратору.

**Вариант «По SOLID» (Overengineering):**
Создать `MigrationCommand`, `DataExtractorService`, `DataTransformerService`, `CsvWriterService`, `FileStorageInterface`, `EmailNotificationService`... В итоге, чтобы написать 20 строк кода, нам нужно создать 10 классов и настроить их в DI-контейнере. Это превращает простую задачу в неповоротливую машину.

**Вариант «Оправданное нарушение» (Pragmatic approach):**
Мы пишем один класс или даже один метод, где логика извлечения, трансформации и отправки идет последовательно.

```php
class DailyReportCommand 
{
    public function execute(): void 
    {
        // 1. Извлечение (SQL)
        $data = $this->db->fetchAll("SELECT * FROM sales WHERE date = ...");

        // 2. Трансформация (Логика прямо здесь)
        $csv = "id,amount\n";
        foreach ($data as $row) {
            $csv .= "{$row['id']},{$row['amount']}\n";
        }

        // 3. Отправка (Внешний вызов)
        $this->mailer->send($csv);
    }
}
```

**Почему это оправдано?**
1. **Низкая вероятность изменений:** Этот скрипт написан один раз. Мы вряд ли будем менять способ формирования CSV или способ отправки письма в этом конкретном скрипте.
2. **Простота поддержки:** Любой разработчик, открыв этот файл, за 10 секунд поймет весь процесс. Ему не нужно дебажить цепочку из пяти сервисов.
3. **Экономия ресурсов:** Мы не тратим время на проектирование интерфейсов, которые никогда не будут реализованы во второй раз.

**Но есть критическое условие:** 
Как только мы понимаем, что этот функционал начинает дублироваться или его требования усложняются, мы **обязаны** провести рефакторинг и вынести логику в соответствующие сервисы, соблюдая SOLID. 

**Мой вывод:** Нарушение принципов — это осознанное взятие «технического кредита». Если вы берете кредит, вы должны понимать под какой процент и когда вы его вернете. Если вы нарушаете SOLID «просто потому что лень» — это плохой инженер. Если вы делаете это ради скорости доставки ценности без ущерба для понимания кода — это прагматичный инженер.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

### Рассуждение

Часто, когда говорят об **Open/Closed Principle (OCP)**, новички сразу вспоминают наследование: «Я создам базовый класс, а потом буду расширять его через `extends`». Но в современном PHP (и в объектно-ориентированном проектировании в целом) наследование — это самый «тяжелый» и опасный способ реализации OCP. Оно создает жесткую связь (tight coupling) между родителем и потомком (проблема *Fragile Base Class*).

Если мы хотим, чтобы система была открыта для расширения, но закрыта для модификации, нам нужно научиться **менять поведение без изменения самого класса**. 

Я выделяю три основных альтернативных способа, которые гораздо эффективнее наследования:
1. **Композиция (Composition) и паттерн «Стратегия»:** Вместо того чтобы *быть* чем-то, объект должен *иметь* что-то.
2. **Интерфейсы и Dependency Injection (DI):** Мы расширяем систему, подставляя новые реализации вместо новых подклассов.
3. **Декоратор (Decorator):** Позволяет динамически добавлять новую функциональность объекту, не меняя его исходный код и не используя наследование для расширения поведения.

Также стоит упомянуть более продвинутые вещи, такие как **Visitor** или использование **Атрибутов (Attributes)** в PHP 8, которые позволяют менять поведение через метаданные.

---

### Ответ

Помимо наследования, OCP реализуется через механизмы, которые отдают предпочтение **композиции над наследованием**.

#### 1. Композиция и паттерн «Стратегия» (Strategy)
Это самый мощный способ. Вместо создания иерархии классов, мы выносим изменяемую часть логики в отдельный объект (стратегию) и передаем его в основной класс.

**Пример:** Система расчета скидок.
*Вместо того чтобы создавать `BlackFridayOrderService`, `SummerSaleOrderService` через наследование, мы делаем так:*

```php
interface DiscountStrategy {
    public function apply(int $amount): int;
}

class DefaultDiscount implements DiscountStrategy {
    public function apply(int $amount): int { return $amount; }
}

class BlackFridayDiscount implements DiscountStrategy {
    public function apply(int $amount): int { return $amount * 0.5; }
}

class OrderProcessor {
    public function __construct(
        private DiscountStrategy $discountStrategy // Композиция
    ) {}

    public function process(int $amount): void {
        $finalPrice = $this->discountStrategy->apply($amount);
        // ... логика обработки заказа
    }
}

// Расширяем поведение, не меняя OrderProcessor:
$processor = new OrderProcessor(new BlackFridayDiscount());
```

#### 2. Паттерн «Декоратор» (Decorator)
Декоратор позволяет «оборачивать» объект, добавляя ему новую ответственность, сохраняя при этом тот же интерфейс. Это идеально подходит для реализации OCP, когда нужно добавить побочные эффекты (логирование, кеширование, валидацию).

**Пример:** Добавление логирования к сервису.

```php
interface ServiceInterface {
    public function execute(): void;
}

class CoreService implements ServiceInterface {
    public function execute(): void {
        echo "Core logic working...\n";
    }
}

class LoggingDecorator implements ServiceInterface {
    public function __construct(
        private ServiceInterface $wrappedService // Оборачивание
    ) {}

    public function execute(): void {
        echo "Log: Before execution\n";
        $this->wrappedService->execute();
        echo "Log: After execution\n";
    }
}

// Использование:
$service = new LoggingDecorator(new CoreService());
$service->execute();
```
*Здесь мы расширили функциональность `CoreService` (добавили логи), не меняя его код и не создавая сложную иерархию наследования.*

#### 3. Использование интерфейсов и Dependency Injection (DI)
Это фундаментальный способ. Если ваш класс зависит от интерфейса, а не от конкретной реализации, то любая новая реализация этого интерфейса будет расширять возможности системы, не требуя правок в вызывающем коде. Это OCP на уровне архитектуры приложения.

#### 4. Атрибуты (Attributes) — современный подход (PHP 8+)
С помощью атрибутов можно реалистично реализовать OCP на уровне метаданных. Например, мы можем создать систему, которая сканирует атрибуты на методах и выполняет определенные действия (валидация, права доступа). При добавлении нового правила мы просто создаем новый атрибут и соответствующий обработчик, не меняя логику существующих контроллеров.

**Резюме:** 
Если наследование — это вопрос **«что объект есть»**, то композиция и интерфейсы — это вопрос **«что объект делает»** и **«как он взаимодействует»**. Для соблюдения OCP в современной разработке всегда лучше выбирать композицию и внедрение зависимостей, так как это делает код гибким, тестируемым и слабосвязанным.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

### Рассуждение

Это отличный вопрос «на засыпку», который проверяет, понимает ли разработчик суть принципа или просто зазубрил его в контексте классов. 

Если отвечать кратко: **нет, SRP не ограничивается классами.** 

Многие ошибочно полагают, что SRP — это правило для классов, потому что в учебниках (и в классическом ООП) примеры всегда строятся на классах. Но на самом деле **SRP — это принцип управления сложностью и разделения ответственности на уровне любого модуля системы.**

Чтобы правильно ответить на этот вопрос, мне нужно разбить понятие «модуль» на разные уровни абстракции. Если мы будем нарушать SRP на более высоких уровнях (например, на уровне целого микросервиса), последствия будут гораздо тяжелее, чем если мы нарушим его в одном классе.

Я рассмотрю SRP на четырех уровнях:
1. **Уровень функций/методов (Function/Method level).**
2. **Уровень классов/объектов (Class level).**
3. **Уровень модулей/пакетов (Module/Package level).**
4. **Уровень сервисов/микросервисов (Service/Microservice level).**

---

### Ответ

Нет, SRP применим к любому элементу системы, который обладает определенной степенью автономности и ответственности. Если мы будем мыслить только категориями классов, мы пропустим архитектурные ошибки на более высоких уровнях.

Вот как это выглядит на практике:

#### 1. Уровень функций и методов
Метод должен делать одну вещь. Если метод `calculateAndSave()` одновременно вычисляет налоги, сохраняет данные в базу и отправляет email — он нарушает SRP.
* **Проблема:** Такой метод сложно тестировать (нужно мокать БД и почту) и сложно переиспользовать (вы не можете посчитать налоги без сохранения в базу).
* **Решение:** Разбить на `calculateTaxes()`, `saveOrder()` и `sendNotification()`.

#### 2. Уровень классов (классический SRP)
Класс должен иметь одну причину для изменения. Как мы обсуждали ранее, если класс `OrderService` отвечает и за бизнес-логику, и за форматирование SQL-запросов — это нарушение.

#### 3. Уровень модулей и пакетов (Namespace/Package level)
Это уровень, который часто упускают. Модуль (или набор пространств имен/пакет в Composer) должен отвечать за одну предметную область (Bounded Context в терминах DDD).
* **Нарушение:** Если у вас есть пакет `Company\Utils`, в котором лежат и инструменты для работы с датами, и логика расчета зарплаты, и парсер XML для импорта поставщиков — это нарушение SRP на уровне модуля.
* **Проблема:** Любое изменение в парсере XML заставляет пересобирать и тестировать весь пакет, который может использоваться в других частях системы, где XML не нужен. Это создает лишние зависимости.

#### 4. Уровень сервисов и микросервисов (System level)
Это самый масштабный уровень. Микросервис должен решать одну бизнес-задачу.
* **Нарушение:** «Божественный микросервис» (God Microservice), который отвечает и за управление пользователями, и за обработку платежей, и за складской учет.
* **Проблема:** Если сервис «взлетит» из-за нагрузки на платежи, упадет и складской учет. Масштабировать его невозможно эффективно (вам придется копировать весь сервис, хотя нужна только часть мощности). Развертывание становится рискованным: ошибка в коде склада может уронить авторизацию пользователей.

### Итог
SRP — это **философия разделения ответственности**. 
* В функциях мы боремся с **когнитивной сложностью**.
* В классах — с **жесткой связностью (coupling)**.
* В модулях — с **зависимостями на этапе сборки**.
* В микросервисах — с **операционными рисками и сложностью масштабирования**.

Понимание того, что SRP работает на всех уровнях, позволяет проектировать системы, которые не только легко писать, но и легко поддерживать, деплоить и масштабировать.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

### Рассуждение

Вопрос бьет в самую суть того, как работает Symfony. Многие разработчики воспринимают DI-контейнер как «магическую коробку», которая просто отдает нужные объекты. Но для опытного инженера контейнер — это сложный двухфазный процесс: **построение графа зависимостей** (Compile Time) и **создание объектов** (Runtime).

Чтобы ответить полно, я должен разделить жизненный цикл контейнера на две четкие фазы. 

Ошибка многих — путать *настройку* контейнера и его *использование*. Если мы будем пытаться делать сложные вычисления или искать файлы прямо в момент запроса сервиса, производительность упадет. Поэтому Symfony спроектирован так, чтобы перенести максимум работы на этап компиляции.

Я разберу:
1. **Compile Time:** Как из кучи YAML/XML/PHP конфигов рождается оптимизированный PHP-класс.
2. **Autowiring:** Как Symfony «угадывает» зависимости (подсказка: это не магия, а статический анализ типов).
3. **Runtime:** Что происходит в момент `get()` (ленивая инициализация и жизненный цикл).

---

### Ответ

В Symfony DI-контейнер — это не просто коллекция объектов, это **сгенерированный код**. Процесс можно разделить на три ключевых этапа.

#### 1. Этап компиляции (Compile Time)
Этот этап происходит не при каждом запросе пользователя, а только при очистке кеша (`cache:clear`) или прогреве кеша.

1.  **Загрузка конфигурации:** Symfony собирает все определения (Definitions) из ваших YAML, XML или PHP файлов, а также из Bundle-ов. На этом этапе создаются объекты `Definition` — это «рецепты» будущих сервисов (какие у них есть аргументы, методы, теги и т.д.).
2.  **Процесс компиляции (Compilation Pass):** Это самая важная часть. Контейнер запускает цепочку «проходов» (Compiler Passes). В этот момент происходят:
    *   **Слияние конфигураций:** Разные конфиги объединяются.
    *   **Обработка тегов:** Например, если вы пометили сервис тегом `kernel.event_listener`, компилятор найдет его и добавит в специальный реестр слушателей.
    *   **Оптимизация:** Удаляются неиспользуемые сервисы (если включена оптимизация), и, что самое важное, **строятся зависимости**.
3.  **Генерация PHP-класса:** После того как граф зависимостей построен и оптимизирован, Symfony генерирует огромный PHP-файл (обычно в `var/cache/.../App_KernelDevDebugContainer.php`). В этом файле прописаны методы для создания каждого сервиса. **Теперь контейнер — это не интерпретируемый конфиг, а высокооптимизированный, скомпилированный PHP-код.**

#### 2. Как работает Autowiring
Autowwiring — это не магия, а использование **Reflection API** и **Type Hinting**.

Когда вы пишете `public function __construct(UserRepository $repository)`, Symfony во время компиляции (а не в рантайме!) делает следующее:
1.  С помощью Reflection API смотрит на типы аргументов конструктора вашего класса.
2.  Ищет в уже построенном графе Definition-ов сервис, который является экземпляром `UserRepository` (или реализует этот интерфейс).
3.  Если находит — записывает это в «рецепт» вашего сервиса. Если не находит или находит несколько подходящих (и не знает, какой выбрать) — выбрасывает исключение на этапе компиляции.

*Важно: В режиме `dev` Autowiring работает чуть медленнее, но в `prod` всё уже «запечено» в сгенерированный класс, поэтому накладных расходов почти нет.*

#### 3. Момент запроса сервиса (Runtime)
Когда вы вызываете `$container->get(MyService::class)` (или когда сервис внедряется автоматически в контроллер), происходит следующее:

1.  **Проверка существования:** Контейнер проверяет, есть ли такой сервис в его сгенерированном списке.
2.  **Ленивая инициализация (Lazy Loading):** По умолчанию сервисы в Symfony являются **shared** (синглтонами внутри контейнера) и создаются **только при первом обращении**. 
3.  **Создание объекта (Instantiating):**
    *   Контейнер смотрит в свой сгенерированный метод для этого сервиса.
    *   Если сервису нужны другие сервисы (зависимости), он рекурсивно вызывает методы создания этих зависимостей.
    *   Вызывается конструктор вашего сервиса, передаются все необходимые объекты.
4.  **Кеширование экземпляра:** После создания сервис сохраняется внутри контейнера (в приватном массиве `$instances`). Все последующие вызовы `get(MyService::class)` будут возвращать тот же самый объект мгновенно.

**Резюме:**
*   **Компиляция** превращает описание сервисов в оптимизированный PHP-код.
*   **Autowiring** — это статический анализ типов во время компиляции.
*   **Runtime** — это просто выполнение быстрого PHP-кода, который создает объекты по мере необходимости и кеширует их.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

### Рассуждение

Когда я слышу фразу «циклическая зависимость», я сразу понимаю, что это не просто техническая проблема, которую нужно «заткнуть», а **сигнал о дефекте в архитектуре**. 

Если `ServiceA` требует `ServiceB`, а `ServiceB` требует `ServiceA`, это означает, что эти два сервиса на самом деле либо являются одним целым, либо их ответственности размыты. В идеальном мире (DDD, чистая архитектура) такого быть не должно.

Однако, в реальной жизни, особенно при работе с legacy-кодом или при интеграции сложных библиотек, такие ситуации встречаются. Я разделяю способы решения на три уровня:
1. **Архитектурный (правильный):** Рефакторинг для устранения причины.
2. **Инженерный (компромиссный):** Использование механизмов контейнера для обхода проблемы без изменения логики.
3. **«Костыльный» (крайний случай):** Когда время поджимает, а рефакторинг слишком дорог.

Я не буду предлагать просто «включить опцию в конфиге», потому что это не решает проблему, а лишь маскирует её, закладывая мину замедленного действия под фундамент проекта.

---

### Ответ

Я подхожу к решению этой проблемы в три этапа, двигаясь от лучшего к худшему.

#### 1. Архитектурный рефакторинг (Первоочередной шаг)

Прежде чем лезть в настройки Symfony, я пытаюсь понять, почему возник цикл. Обычно есть два сценария:

**Сценарий А: Разделение ответственности (Extraction)**
Если `ServiceA` и `ServiceB` зависят друг от друга, скорее всего, у них есть **общая логика**, которая не принадлежит ни одному из них.
* **Решение:** Я выношу общую логику в третий сервис — `ServiceC`. Теперь и `A`, и `B` зависят от `C`, но не друг от друга. Цикл разорван.

**Сценарий Б: Нарушение иерархии (Layering)**
Часто цикл возникает, когда сервис из верхнего слоя (Application) вызывает сервис из нижнего слоя (Domain), а тот пытается вызвать верхний слой для уведомления или обновления состояния.
* **Решение:** Использование **Domain Events**. Вместо того чтобы `DomainService` вызывал `ApplicationService`, он должен просто выбросить событие (Event). `ApplicationService` подпишется на это событие. Теперь связь стала односторонней: `Application -> Domain` и `Domain -> Event`.

#### 2. Инженерный обход (Lazy Services)

Если рефакторинг сейчас невозможен (например, это часть стороннего бандла или слишком большой кусок legacy), я использую механизм **Lazy Services** в Symfony.

Symfony позволяет пометить зависимость как `lazy`. В этом случае контейнер не будет создавать реальный объект сразу. Вместо него он подставит **Proxy-объект** (виртуальный двойник). Реальный объект будет создан только в тот момент, когда вы впервые вызовете на этом прокси какой-либо метод.

**В Symfony это делается через атрибут или конфиг:**

```php
// В конфигурации (services.yaml)
App\Service\ServiceB:
    lazy: true
```

Или через атрибут (если используется прокси-генератор):

```php
public function __construct(
    #[Autoref\Lazy]
    private ServiceB $serviceB 
) {}
```

Это «честный» способ, так как он не меняет архитектуру, а лишь меняет момент инициализации объекта, позволяя разорвать цикл при построении графа.

#### 3. Использование Setter Injection (Компромисс)

Если конструктор зациклен, можно перевести одну из зависимостей с **Constructor Injection** на **Setter Injection**.

```php
// Было (Цикл в конструкторах)
class ServiceA { public function __construct(ServiceB $b) {} }
class ServiceB { public function __construct(ServiceA $a) {} }

// Стало (Разрыв цикла)
class ServiceA {
    private ServiceB $b;
    public function setServiceB(ServiceB $b) { $this->b = $b; }
}
```

*Примечание: Я не люблю этот метод, так как он делает объект «неполноценным» в момент создания (он может быть в невалидном состоянии, если забыть вызвать сеттер), но это лучше, чем бесконечная рекурсия.*

### Итог моей стратегии:
1. **Попробовать вынести общую логику** в новый сервис (лучший вариант).
2. **Внедрить события (Events)**, чтобы превратить прямую зависимость в наблюдаемую (самый чистый вариант для архитектуры).
3. Если ничего не помогает — использовать **Lazy Services** (самый безопасный вариант для контейнера).
4. И только в самом крайнем случае — **Setter Injection**.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

### Рассуждение

Это классическая задача на проектирование **асинхронных процессов**. Основная цель здесь — минимизировать время отклика (latency) для конечного пользователя. Пользователь не должен ждать, пока отработает SMTP-сервер или API поискового движка (Elasticsearch/Algolia), так как это внешние системы с непредсказуемым временем ответа.

Я рассматриваю три основных архитектурных паттерна для решения этой задачи, ранжируя их от простого к надежному.

Мой критерий выбора будет базироваться на трех факторах:
1. **Reliability (Надежность):** Что будет, если письмо не отправится? Нужно ли нам повторить попытку (retry)?
2. **Complexity (Сложность):** Насколько сильно это усложнит инфраструктуру и код?
3. **Consistency (Согласованность):** Насколько критично, чтобы индекс обновился *мгновенно* (Strong consistency) или допустимо, если это произойдет через 2 секунды (Eventual consistency).

---

### Ответ

Я предложу три варианта реализации, от самого простого до промышленного стандарта.

#### Вариант 1: "Fire and Forget" через FastCGI (FPM)
Если проект небольшой и нам не нужна высокая надежность, можно использовать `fastcgi_finish_request()`. Это позволяет отправить HTTP-ответ пользователю, но оставить PHP-процесс работать в фоне.

*   **Как это работает:** Контроллер завершает запрос, пользователь видит "Успех", а PHP-процесс продолжает выполнение кода (отправка письма, обновление индекса).
*   **Trade-offs:**
    *   **(+) Плюсы:** Не нужна дополнительная инфраструктура (очереди, воркеры). Очень легко реализовать.
    *   **(-) Минусы:** Если процесс упадет (ошибка в письме), задача потеряется навсегда. Если задач станет много, PHP-FPM процессы будут заняты "фоновой" работой, что может привести к исчерпанию пула и отказу в обслуживании новых пользователей.

#### Вариант 2: Symfony Messenger + Transport (Промежуточный)
Это стандартный путь для средних проектов. Мы используем компонент **Symfony Messenger** для отправки сообщений в очередь.

*   **Как это работает:**
    1. В контроллере (или сервисe) мы создаем два сообщения: `SendWelcomeEmail` и `UpdateSearchIndex`.
    2. Отправляем их в шину: `$bus->dispatch(new SendWelcomeEmail($userId));`.
    3. Messenger мгновенно записывает эти сообщения в транспорт (например, в таблицу в PostgreSQL или в Redis) и возвращает управление пользователю.
    4. Отдельный процесс (Worker), запущенный в терминале, берет сообщения из очереди и выполняет их.
*   **Trade-offs:**
    *   **(+) Плюсы:** Отличная скорость ответа. Есть встроенная поддержка **Retry Strategy** (если почта упала, Messenger попробует еще раз через 5 минут). Можно масштабировать количество воркеров независимо.
    *   **(-) Минусы:** Требуется запущенный воркер (процесс в фоне/systemd). Нужно следить за состоянием очереди.

#### Вариант 3: Transactional Outbox Pattern (Enterprise-уровень)
Если нам критически важно, чтобы индекс обновился *обязательно* и мы не можем потерять сообщение из-за сбоя в момент записи в очередь (например, база данных закоммитила юзера, а Redis с очередью в этот момент моргнул), мы используем паттерн **Outbox**.

*   **Как это работает:**
    1. В рамках **одной транзакции БД** мы сохраняем нового пользователя И записываем задачу (событие) в специальную таблицу `outbox_messages` в той же базе данных.
    2. Поскольку это одна транзакция, либо запишется и юзер, и задача, либо ничего. Это гарантирует атомарность.
    3. Отдельный процесс (Relay) читает таблицу `outbox_messages`, отправляет задачи в реальную очередь (RabbitMQ/Kafka) и помечает их как выполненные.
*   **Trade-offs:**
    *   **(+) Плюсы:** Гарантированная доставка (Guaranteed Delivery). Полная согласованность между состоянием БД и очередью.
    *   **(-) Минусы:** Самая высокая сложность реализации и дополнительная нагрузка на БД.

---

### Мой итоговый выбор

Для типичного современного Symfony-приложения я выберу **Вариант 2 (Symfony Messenger)** с использованием **PostgreSQL** в качестве транспорта (через библиотеку `symfony/messenger` с поддержкой DBAL).

**Почему:**
1. **Надежность:** Использование БД как транспорта дает нам почти такие же гарантии, как Outbox (задача попадет в очередь только если транзакция с пользователем прошла успешно), но без лишней сложности.
2. **Retry:** Мы получаем автоматические повторные попытки при сбоях внешних API.
3. **Разделение:** Мы четко разделяем бизнес-логику (регистрация) и побочные эффекты (письма/индекс).

**Схема реализации:**
1. `RegistrationService` вызывает `UserRegisteredEvent`.
2. `Messenger` ловит событие и отправляет его в транспорт.
3. Контроллер отдает `201 Created`.
4. Два независимых `MessageHandler`: один шлет письмо, другой обновляет индекс. Если индекс обновится на 5 секунд позже — это допустимая **Eventual Consistency**.

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

### Рассуждение

Вопрос касается фундаментального различия между «кто ты есть» (Authentication) и «что тебе можно делать» (Authorization). В Symfony это разделено на четкие слои, и понимание их взаимодействия критично для безопасности.

Многие разработчики совершают ошибку, пытаясь запихнуть всю логику прав в роли (например, создавая роли вроде `ROLE_EDIT_USER_ONLY_IF_OWNER`). Это путь в тупик, который ведет к взрывному росту количества ролей и невозможности поддержки системы.

Я разделяю процесс на три этапа:
1. **Authentication (Аутентификация):** Идентификация субъекта (кто ты?).
2. **Role-Based Access Control (RBAC):** Простая проверка по ярлыкам (какой у тебя статус?).
3. **Attribute-Based Access Control (ABAC / Voters):** Сложная проверка по контексту (можешь ли ты сделать это прямо сейчас с этим конкретным объектом?).

---

### Ответ

#### 1. Аутентификация (Authentication)
Это процесс подтверждения личности пользователя. В Symfony за это отвечают `Authenticators`.
* Когда пользователь присылает логин/пароль, токен или JWT, аутентификатор проверяет их через `UserProvider`.
* Если данные верны, создается `Token` (объект `TokenInterface`), который сохраняется в `Security Context`. С этого момента система «знает», кто делает запрос.

#### 2. Роли (Roles)
Роли — это самый простой уровень авторизации. Это просто строки, привязанные к пользователю (например, `ROLE_USER`, `ROLE_ADMIN`).
* Проверка происходит через `isGranted('ROLE_ADMIN')`.
* Роли в Symfony имеют иерархию (можно настроить, что `ROLE_ADMIN` включает в себя `ROLE_USER`).

#### 3. Voters (Голосующие)
Voter — это механизм реализации сложной бизнес-логики доступа. Когда вы вызываете `isGranted('EDIT', $post)`, Symfony опрашивает все зарегистрированные вотеры. Каждый вотер говорит: «Я могу решить этот вопрос» или «Это не мой профиль», и в итоге выдается вердикт: `ACCESS_GRANTED`, `ACCESS_DENIED` или `ACCESS_ABSTAIN`.

---

### Когда выбирать Role, а когда Voter?

Это ключевой архитектурный вопрос. Я использую следующие критерии:

#### Выбираю Роли (RBAC), если:
Проверка **статична** и не зависит от данных объекта. Если право доступа зависит только от статуса пользователя.
* *Примеры:* 
    * «Только администраторы могут зайти в панель управления».
    * «Только менеджеры могут просматривать отчеты».
* **Почему:** Это быстро, декларативно (можно прописать прямо в `access_control` в `security.yaml`) и не требует написания кода.

#### Выбираю Voter (ABAC), если:
Проверка **динамична** и зависит от **контекста** (объекта, владельца, состояния системы).
* *Примеры:*
    * «Пользователь может редактировать пост, **только если он его автор**».
    * «Менеджер может одобрить заявку, **только если она находится в статусе 'NEW'**».
    * «Клиент может видеть заказ, **только если этот заказ принадлежит ему**».
* **Почему:** 
    1. **Объектная зависимость:** Роли не знают о существовании конкретного объекта `$post`. Они знают только о пользователе.
    2. **Сложность условий:** В вотере можно реализовать любую логику (проверить время суток, проверить связь пользователя с организацией через БД и т.д.).
    3. **Чистота кода:** Вместо того чтобы загромождать контроллер проверками `if ($post->getAuthor() === $user)`, я пишу один раз `isGranted('POST_EDIT', $post)`.

#### Сводная таблица для принятия решения:

| Критерий | Роли (RBAC) | Вотеры (ABAC) |
| :--- | :--- | :--- |
| **Зависимость от данных** | Нет (только от пользователя) | **Да (от объекта/сущности)** |
| **Сложность логики** | Низкая (простая проверка строки) | **Высокая (любые условия)** |
| **Где описывается** | `security.yaml` или аннотации | Отдельный PHP класс |
| **Пример** | `ROLE_ADMIN` | `can_edit_this_specific_article` |

**Мой совет:** Если вы чувствуете, что начинаете создавать роли вроде `ROLE_EDITOR_OF_DEPARTMENT_5`, немедленно останавливайтесь и пишите Voter. Это верный признак того, что вы пытаетесь решить задачу атрибутов с помощью ролей.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

### Рассуждение

Это фундаментальный вопрос на стыке DDD и реализации. Главный конфликт здесь заключается в том, что **Domain Model** хочет работать с чистыми, неизменяемыми (immutable) объектами, которые гарантируют инварианты (валидность) с момента создания, а **ORM** (Doctrine) по своей природе работает через рефлексию или сеттеры, что часто требует наличия пустого конструктора или публичных сеттеров, тем самым нарушая принцип неизменяемости.

Если мы просто сделаем `public readonly` свойства, Doctrine не сможет их заполнить при загрузке из базы (так как она не может вызвать конструктор с аргументами так, как это делает наш код).

Я выделяю три основных способа решения этой задачи, каждый из которых имеет свой баланс между «чистотой домена» и «удобством инфраструктуры».

---

### Ответ

#### 1. Использование Embeddables (Стандартный путь Doctrine)
Это встроенный механизм Doctrine для маппинга Value Objects. Мы помечаем класс атрибутом `#[ORM\Embeddable]`.

*   **Как это работает:** Поля Value Object «разворачиваются» в таблицу сущности (Entity), к которой он привязан. В базе нет отдельной таблицы для `Address`, есть только столбцы `address_street`, `address_city` в таблице `User`.
*   **Реализация неизменяемости:** Мы используем `readonly` свойства или только геттеры.
*   **Плюсы:**
    *   **Производительность:** Нет лишних `JOIN`, данные лежат в той же строке.
    *   **Простота:** Это нативно поддерживается Doctrine.
*   **Минусы:**
    *   **Жизненный цикл:** Embeddable не может существовать без владельца (Entity).
    *   **Сложность переиспользования:** Если вам нужно хранить этот же объект в другой сущности с другой структурой, придется настраивать маппинг заново.
*   **Подводный камень:** Doctrine при загрузке использует рефлексию, чтобы записать значения в свойства. Если вы используете `readonly` (PHP 8.1+), Doctrine сможет их заполнить, но вы должны быть уверены, что конструктор не вызывается повторно.

#### 2. Custom Type (Превращение в строку/JSON)
Мы создаем свой тип данных (например, `MoneyType` или `EmailType`), который реализует `Doctrine\DBAL\Types\Type`.

*   **Как это работает:** Мы говорим Doctrine: «Когда видишь этот класс, преврати его в строку (или JSON) при сохранении и создай новый объект через конструктор при чтении».
*   **Плюсы:**
    *   **Идеальная чистота домена:** Объект всегда создается через свой конструктор с валидацией.
    *   **Универсальность:** Один и тот же тип можно использовать везде.
*   **Минусы:**
    *   **Проблемы с запросами:** Если вы храните `Money` как JSON в одной колонке, вы не сможете эффективно сделать запрос `WHERE money.amount > 100` на уровне SQL (если не использовать специфичные функции БД вроде JSONB в PostgreSQL).
    *   **Производительность:** Десериализация каждого объекта при загрузке коллекции может быть накладной.
*   **Подводный камень:** Потеря возможности эффективно фильтровать и сортировать по полям Value Object средствами SQL.

#### 3. Использование Doctrine Lifecycle Callbacks (или Listeners)
Это "гибридный" способ, где мы позволяем Doctrine работать с данными, а затем в методах `postLoad` или через специальные методы конвертации восстанавливаем объект.

*   **Как это работает:** Мы храним данные в Entity в виде простых типов (string, int), а в методе `getMoney()` создаем новый объект `Money`.
*   **Плюсы:** Максимальная совместимость с любым SQL.
*   **Минусы:** Нарушает инкапсуляцию. Сущность (Entity) начинает "знать" о деталях реализации Value Object, храня его части в сыром виде.

---

### Итоговая рекомендация

Мой выбор зависит от природы данных:

1.  **Если это "структурный" Value Object** (например, `Address`, `Coordinate`, `Period`), состоящий из нескольких полей:
    👉 **Используйте `Embeddables`**. Это золотой стандарт. Это дает отличную производительность (нет JOIN) и сохраняет целостность. Чтобы обеспечить неизменяемость, используйте `readonly` свойства (PHP 8.1+).

2.  **Если это "атомарный" Value Object** (например, `Email`, `Money` в виде одной строки, `Color` в HEX):
    👉 **Используйте `Custom DBAL Type`**. Это позволит вам сохранить чистоту домена и гарантировать, что объект `Email` всегда проходит через валидацию в конструкторе при загрузке из БД.

3.  **Если вам нужно искать по полям внутри VO** (например, поиск по городам внутри адреса):
    👉 **Только `Embeddables`**. Только так вы сохраните возможность использовать индексы базы данных и эффективные SQL-запросы.

**Главный совет:** Никогда не допускайте состояния, когда Value Object может быть создан в невалидном виде. Если вы используете `Custom Type`, логика валидации должна быть **внутри конструктора** самого Value Object, а не в маппере.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

### Рассуждение

Это вопрос о том, как подружить принципы **DDD (Domain-Driven Design)** с механизмом **Data Mapper** (которым является Doctrine). 

Основная проблема здесь — **нарушение границ агрегата**. В DDD агрегат — это граница согласованности (consistency boundary). Все изменения внутри агрегата должны проходить через **Aggregate Root (Корень)**. Если мы позволим внешнему коду напрямую менять элементы коллекции внутри агрегата, мы нарушим инварианты (бизнес-правила).

При проектировании я всегда исхожу из следующих правил:
1. **Инкапсуляция коллекции:** Дочерние сущности не должны быть доступны для прямого манипулирования извне. Мы не даем `getEntities()` возвращать живую коллекцию Doctrine, которую можно модифицировать.
2. **Управление через корень:** Любое изменение (добавление, удаление, смена статуса) должно быть методом в классе Root.
3. **Границы транзакции:** Транзакция должна охватывать весь агрегат целиком. Один вызов `flush()` — один агрегат.
4. **Кто вызывает flush:** `flush()` — это задача инфраструктурного слоя (Application Service / Command Handler), а не доменного.

---

### Ответ

Разберем на примере агрегата **`Order` (Заказ)**, который содержит коллекцию **`OrderItem` (Позиции заказа)**.

#### 1. Маппинг и инкапсуляция коллекции

Самая большая ошибка — возвращать `ArrayCollection` напрямую. Если я сделаю `public function getItems()`, любой разработчик напишет `$order->getItems()->add(...)`, и это обойдет логику проверки цен или наличия товара в корне агрегата.

**Правильный подход:**

```php
#[ORM\Entity]
class Order // Aggregate Root
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    /**
     * @var Collection<int, OrderItem>
     */
    #[ORM\OneToMany(
        mappedBy: 'order', 
        targetEntity: OrderItem::class, 
        cascade: ['all'], // Важно: изменения в Item пропадут в БД, если не пробросить в Root
        orphanRemoval: true // Важно: если убираем Item из коллекции, он удаляется из БД
    )]
    private Collection $items;

    public function __construct() {
        $this->items = new ArrayCollection();
    }

    /**
     * Возвращаем только для чтения (итерации), но не для модификации!
     * @return Collection<int, OrderItem>
     */
    public function getItems(): Collection 
    {
        // Возвращаем обертку, которая защищает коллекцию от прямого add/remove
        return $this->items->wrap(); 
        // В реальности в PHP часто используют просто возвращение Iterator или 
        // создают ReadOnly коллекцию.
    }

    // Единственный путь изменения коллекции — через метод корня
    public function addItem(Product $product, int $quantity): void 
    {
        if ($quantity <= 0) {
            throw new \InvalidArgumentException("Quantity must be positive");
        }
        
        // Здесь может быть бизнес-логика: например, проверка лимита суммы заказа
        if ($this->calculateTotal() + ($product->getPrice() * $quantity) > 10000) {
            throw new \DomainException("Order limit exceeded");
        }

        $item = new OrderItem($this, $product, $quantity);
        $this->items->add($item);
    }

    public function removeItem(OrderItem $item): void
    {
        $this->items->removeElement($item);
    }
}

#[ORM\Entity]
class OrderItem // Child Entity
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'items')]
    #[ORM\JoinColumn(nullable: false)]
    private Order $order;

    // ... остальные поля
    public function __construct(Order $order, Product $product, int $qty) {
        $this->order = $order;
        // ...
    }
}
```

#### 2. Границы транзакции и вызов `flush`

В архитектуре со слоями (Layered Architecture) ответственность распределяется так:
* **Domain Layer (`Order`):** Гарантирует инварианты.
* **Infrastructure Layer (`OrderRepository`):** Знает, как сохранить агрегат.
* **Application Layer (`PlaceOrderUseCase`):** Управляет транзакцией и жизненным циклом запроса.

**Пример Application Service (Command Handler):**

```php
class PlaceOrderUseCase 
{
    public function __construct(
        private OrderRepositoryInterface $repository,
        private EntityManagerInterface $entityManager // Для управления транзакцией
    ) {}

    public function execute(OrderData $data): void 
    {
        // 1. Начинаем транзакцию на уровне БД
        $this->entityManager->beginTransaction();

        try {
            // 2. Создаем агрегат
            $order = new Order();

            // 3. Изменяем агрегат через методы корня (инкапсуляция соблюдена)
            foreach ($data->items as $itemData) {
                $product = $this->productRepository->find($itemData->productId);
                $order->addItem($product, $itemData->quantity);
            }

            // 4. Сохраняем агрегат
            $this->repository->save($order);

            // 5. Фиксируем изменения (один flush на один агрегат/транзакцию)
            $this->entityManager->flush();
            $this->entityManager->commit();

        } catch (\Exception $e) {
            // Если что-то пошло не так — откатываем всё
            $this->entityManager->rollback();
            throw $e;
        }
    }
}
```

#### Резюме по ключевым моментам:

1.  **Маппинг:** Обязательно используйте `cascade: ['all']` и `orphanRemoval: true` в корневом классе. Это гарантирует, что управление жизненным циклом дочерних сущностей полностью делегировано корню.
2.  **Инкапсуляция:** Никогда не позволяйте внешнему коду делать `$order->getItems()->add()`. Все изменения — только через методы `Order`.
3.  **Транзакции:** `flush()` вызывается **один раз** в конце успешного выполнения бизнес-операции в Application Layer.
4.  **Границы:** Агрегат — это единица сохранения. Мы не сохраняем `OrderItem` отдельно. Мы сохраняем `Order`, а Doctrine, благодаря каскадам, сама позаботится о дочерних элементах.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

### Рассуждение

Проблема **N+1** — это классическая ловушка при использовании ORM. Она возникает, когда мы загружаем список объектов (1 запрос), а затем в цикле обращаемся к их связанным сущностям, которые не были загружены сразу. В итоге для каждого элемента коллекции ORM делает дополнительный запрос (N запросов).

При диагностике я не гадаю по коду, а смотрю на реальный поток данных. Моя стратегия:
1. **Обнаружение:** Понять, что проблема есть (чеवीं через метрики или профилировщик).
2. **Локализация:** Найти конкретный цикл или место в коде, генерирующее лишние запросы.
3. **Устранение:** Выбрать наиболее подходящий по архитектуре и производительности способ.

Я разделяю способы решения на три уровня: **загрузка данных** (Fetch), **изменение стратегии маппинга** (Mapping) и **оптимизация на уровне приложения** (Application).

---

### Ответ

#### 1. Диагностика

Я никогда не пытаюсь угадать N+1, глядя на код. Я использую инструменты:

*   **Symfony Profiler (Doctrine Tab):** Это первое, что я открываю. Если я вижу в списке запросов десятки почти одинаковых запросов к одной и той же таблице (например, `SELECT ... FROM user WHERE id = ?`), это 100% N+1.
*   **SQL Log / DebugBar:** Позволяет увидеть порядок выполнения запросов и время их выполнения.
*   **Blackfire.io или Tideways:** Если проблема на продакшене и она трудноуловима, я использую профилировщики, которые показывают "стоимость" вызовов и количество обращений к БД в дереве вызовов.
*   **Логирование:** В режиме разработки я всегда проверяю количество запросов на один жизненный цикл запроса (Request).

#### 2. Способы решения и их Trade-offs

##### Способ А: Eager Loading через JOIN (DQL/Query Builder)
Это самый правильный способ для конкретных случаев. Вместо того чтобы полагаться на ленивую загрузку, мы явно просим Doctrine подтянуть связи через `JOIN FETCH`.

```php
// Плохо (вызовет N+1)
$users = $repository->findAll(); 

// Хорошо (решает проблему одним запросом)
$users = $this->createQueryBuilder('u')
    ->leftJoin('u.profile', 'p')
    ->addSelect('p') // Важно! Без addSelect Doctrine не заполнит объект профиля
    ->getQuery()
    ->getResult();
```

*   **(+) Плюсы:** Один эффективный SQL-запрос; максимально высокая производительность; контроль над тем, что именно загружается.
*   **(-) Минусы:** Возможный "взрыв" количества строк в результате (Cartesian Product), если делать много `JOIN` к коллекциям (OneToMany). Это может забить память PHP.

##### Способ Б: Fetch Join в маппинге (Eager Loading в Entity)
Мы меняем настройку в самой сущности: `fetch="EAGER"`.

```php
#[ORM\OneToMany(targetEntity: Item::class, mappedBy: 'order', fetch: 'EAGER')]
private Collection $items;
```

*   **(+) Плюсы:** Решает проблему "автоматически" для всех мест в приложении, где используется эта сущность.
*   **(-) Минусы:** **Опасно.** Это "глобальное" решение. Если в одном месте вам нужны заказы с товарами, а в другом (например, в админке для списка) — только заказы, вы все равно будете тянуть товары. Это приводит к избыточной нагрузке на БД и памяти.

##### Способ В: Использование Partial Objects (с осторожностью)
Загрузка только определенных полей.

*   **(+) Плюсы:** Снижает объем передаваемых данных.
*   **(-) Минусы:** Опасно. Если вы попытаетесь обратиться к полю, которое не было загружено, вы получите либо `null`, либо (в некоторых конфигурациях) ошибку. Это нарушает предсказуемость работы сущности.

##### Способ Г: Использование DTO (Data Transfer Objects)
Вместо загрузки полноценных сущностей через ORM, мы пишем чистый SQL или DQL, который сразу мапит результат в плоский DTO.

```php
// SELECT new App\Dto\UserSummaryDto(u.id, u.name, p.avatar) FROM User u JOIN u.profile p
```

*   **(+) Плюсы:** Самый быстрый способ. Никакого оверхеда на управление состоянием сущностей, Unit of Work и жизненным циклом объектов. Идеально для Read-моделей (CQRS).
*   **(-) Минусы:** Вы теряете возможность изменять эти данные и сохранять их через `EntityManager` (так как это не сущности, а просто объекты с данными).

---

### Итоговая стратегия выбора

1.  Если это **список (List view)**: Я использую **Способ А (JOIN FETCH)** или **Способ Г (DTO)**. Для списков важна скорость и отсутствие лишнего веса объектов.
2.  Если это **детальная страница (Detail view)**: Я оставляю **Lazy Loading**, так как там обычно загружается один объект и его связанные данные, и N+1 там не возникает.
3.  Если это **сложная бизнес-логика**: Я использую **Eager Loading через репозиторий**, чтобы гарантировать, что агрегат загружен целиком и готов к работе.

**Золотое правило:** Никогда не используй `fetch="EAGER"` в маппинге сущностей, если только ты не на 100% уверен, что эта связь нужна *всегда и везде*. Это самая частая причина деградации производительности в долгосрочной перспективе.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

### Рассуждение

Этот вопрос проверяет понимание концепции **"Defense in Depth" (эшелонированная оборона)**. 

Многие разработчики совершают ошибку, полагая, что если у них есть качественные Unit-тесты и валидация в доменном слое (Value Objects, Entity), то база данных — это просто «тупое хранилище». Это опасное заблуждение. 

Я разделяю валидацию на две категории:
1.  **Бизнес-валидация (Application/Domain Level):** Проверка правил бизнеса. Например: «Скидка не может превышать 50%» или «Пользователь может купить только один такой товар». Это сложно выразить на языке SQL, и это должно жить в коде.
2.  **Техническая целостность данных (Database Level):** Гарантия того, что данные в физическом хранилище не превратились в мусор из-за ошибки в коде, бага в сторонней библиотеке, ручного вмешательства DBA или сбоя в процессе миграции.

Если мы полагаемся *только* на код, мы оставляем «дыры» в безопасности данных. База данных — это **последний рубеж обороны**.

---

### Ответ

Я использую ограничения целостности в PostgreSQL как страховку от нарушения фундаментальных правил данных. Даже если код приложения «сломается», база данных не позволит ему испортить состояние системы.

Вот основные средства, которые я применяю, и критерии их использования:

#### 1. Primary Keys и Foreign Keys (Обязательно)
Это база. Я всегда использую `FOREIGN KEY` для связей между таблицами.
* **Зачем:** Чтобы избежать «сиротских» записей (orphans). Если мы удаляем категорию, БД либо запретит это (`RESTRICT`), либо сама удалит связанные товары (`CASCADE`).
* **Когда:** Всегда, где есть связь между сущностями.

#### 2. Not Null Constraints
* **Зачем:** Чтобы гарантировать, что критически важные поля (email, id, price) никогда не окажутся пустыми.
* **Когда:** Для любого поля, которое является обязательным по смыслу бизнеса.

#### 3. Unique Constraints
* **Зачем:** Чтобы предотвратить дублирование уникальных сущностей (например, два пользователя с одним email).
* **Когда:** Всегда для полей, которые должны быть уникальными. Это гораздо надежнее, чем делать проверку `if ($repo->exists($email))` в коде, так because в высоконагруженных системах между проверкой и записью может возникнуть **Race Condition** (два процесса одновременно проверят и оба запишут).

#### 4. Check Constraints (Моя любимая часть)
Это мощный инструмент PostgreSQL для проверки простых инвариантов прямо в ядре БД.
* **Пример:** `CHECK (price > 0)` или `CHECK (status IN ('new', 'paid', 'shipped'))`.
* **Когда:** Когда правило очень простое, фундаментальное и не должно нарушаться ни при каких обстоятельствах.
* **Плюс:** Это защищает от ошибок в коде, где кто-то случайно передал отрицательную цену.

#### 5. Domain-specific Constraints (Complex Logic)
Для очень сложных правил (например, «сумма всех позиций в заказе должна совпадать с итоговой суммой заказа») я использую:
* **Triggers (Триггеры):** Если логика требует сложного вычисления перед вставкой.
* **Exclusion Constraints:** Для решения задач пересечения интервалов (например, «бронирование комнаты не может пересекаться с другим бронированием в это же время»).

---

### Сводная стратегия: когда и что использовать

| Тип проверки | Где реализуем | Пример | Почему не только в коде? |
| :--- | :--- | :--- | :--- |
| **Сложная бизнес-логика** | **Domain Layer (PHP)** | "Пользователь может применить промокод только раз в месяц" | Слишком сложно и дорого описывать это на SQL. |
| **Уникальность** | **DB (Unique Index)** | `email` должен быть уникальным | Код не защищен от Race Conditions. |
| **Связи (Integrity)** | **DB (Foreign Key)** | Пост принадлежит автору | Чтобы не плодить «битые» ссылки при удалениях. |
| **Базовые инварианты** | **DB (Check/Not Null)** | `amount >= 0` | Чтобы гарантировать физическую корректность данных. |

**Мой вывод:** Я рассматриваю код как **первую линию обороны** (она обеспечивает удобство и богатство бизнес-логики), а базу данных — как **последнюю линию обороны** (она обеспечивает математическую достоверность данных). Если код ошибается, база должна «выбросить ошибку» и не дать приложению сохранить невалидное состояние.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

### Рассуждение

Когда запрос выполняется медленно, я не начинаю переписывать код или добавлять индексы «наугад». Это путь к деградации производительности. Мой подход базируется на принципе: **«Сначала измерь, потом анализируй, и только потом исправляй»**.

Проблема может лежать на трех разных уровнях:
1. **Уровень написания запроса (SQL/DQL):** Неоптимальный план выполнения, лишние JOIN, неэффективные подзапросы.
2. **Уровень структуры данных (Schema/Indexes):** Отсутствие нужных индексов, неверный тип данных, избыточность индексов.
3. **Уровень ресурсов и конфигурации (Infrastructure/Config):** Недостаток памяти (shared buffers), проблемы с дисковой подсистемой (I/O Wait), блокировки (Locks).

Я разделяю процесс на три фазы: **Локализация $\to$ Анализ плана $\to$ Применение решения**.

---

### Ответ

#### 1. Фаза диагностики (Инструментарий)

Первым делом я должен увидеть, что именно делает база данных.

*   **`EXPLAIN (ANALYZE, BUFFERS)`:** Это мой главный инструмент. `EXPLAIN` показывает план выполнения, а `ANALYZE` — реально выполненные действия и время. Флаг `BUFFERS` критически важен: он показывает, сколько данных было прочитано из памяти (shared hit), а сколько — с диска (read). Это позволяет понять, упираемся ли мы в CPU или в I/O.
*   **`pg_stat_statements`:** Если проблема плавающая и проявляется на проде, я смотрю этот модуль. Он собирает статистику по всем запросам: сколько раз выполнялся, среднее время, общая нагрузка. Это помогает найти «самых тяжелых» убийц производительности.
*   **`pg_stat_activity`:** Использую для поиска активных блокировок (`Locks`). Если запрос «висит», я смотрю, не ждет ли он завершения другой транзакции.
*   **Инструменты профилирования (APM):** New Relic или Datadog, чтобы увидеть контекст: какой именно метод PHP вызвал этот тяжелый запрос.

#### 2. Анализ плана (Что я ищу в `EXPLAIN`)

Когда я получил план, я ищу следующие «красные флаги»:

*   **Seq Scan (Sequential Scan):** База читает всю таблицу целиком. Если таблица большая — это почти всегда проблема отсутствия индекса.
*   **Bitmap Heap Scan vs Index Scan:** Я смотрю, насколько эффективно используется индекс.
*   **Costly Joins:** Я ищу `Hash Join` или `Nested Loop` на больших объемах данных. Если `Nested Loop` выполняется миллион раз — это сигнал к оптимизации.
*   **External Merge / Disk Sort:** Если я вижу, что сортировка происходит на диске, а не в памяти (`Sort Method: external merge Disk`), значит, параметр `work_mem` слишком мал для этого запроса.
*   **Filter vs Index Cond:** Если в плане я вижу `Filter`, значит, индекс помог найти строки, но внутри них базе пришлось перебирать данные вручную. Это значит, индекс не совсем покрывает условие.

#### 3. Типовые причины и методы решения

| Проблема | Решение |
| :--- | :--- |
| **Отсутствие индекса (Seq Scan)** | Создание B-tree индекса по полям из `WHERE` или `JOIN`. |
| **Неэффективный индекс (Index не покрывает запрос)** | Создание **Covering Index** (использование `INCLUDE` в PostgreSQL), чтобы база брала все данные прямо из индекса, не обращаясь к Heap (таблице). |
| **Проблема с типами (Type Mismatch)** | Если в запросе `WHERE string_col = 123` (число), база может проигнорировать индекс из-за неявного приведения типов. Нужно привести типы к идентичным. |
| **Раздувание таблицы (Bloat)** | Если после массовых `UPDATE/DELETE` запросы тормозят, я проверяю `autovacuum`. Возможно, нужно запустить `VACUUM ANALYZE` вручную. |
| **Низкий Cardinality (Низкая селективность)** | Если индекс по полю `is_active` (где 99% значений `true`), база выберет Seq Scan, так как индекс не помогает. Решение: частичные индексы (`WHERE is_active = false`). |
| **Неправильная статистика** | Если план выглядит нелогичным, я запускаю `ANALYZE table_name`, чтобы обновить статистику планировщика. |

#### Мой алгоритм действий (Summary):
1. Взять «медленный» запрос и прогнать его через **`EXPLAIN (ANALYZE, BUFFERS)`**.
2. Проверить, не делает ли база **Seq Scan** там, где должен быть индекс.
3. Проверить, не происходит ли **Disk Sort** (нужно поднять `work_mem` или переписать запрос).
4. Проверить, не вызвано ли торможение **блокировками** (`pg_stat_activity`).
5. Если индексы есть, но они не работают — проверить **типы данных** и **селективность**.
6. Если запрос написан плохо (например, `LIKE '%text%'` — что убивает индексы) — переписать его (например, на `pg_trgm` для полнотекстового поиска).

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

### Рассуждение

Вопрос об агрегатах — это проверка понимания того, как управлять сложностью в долгосрочной перспективе. Многие путают «агрегат» с «таблицей в базе» или «набором связанных сущностей». Это фундаментальная ошибка.

В DDD **Агрегат (Aggregate)** — это кластер связанных объектов, которые рассматриваются как единое целое для изменения данных. Его главная задача — **поддержание инвариантов** (бизнес-правил, которые всегда должны быть истинными). 

Когда мы говорим о границах агрегата, мы решаем две задачи:
1. **Целостность:** Что должно изменяться атомарно (в одной транзакции)?
2. **Производительность:** Насколько большой будет этот «кусок» данных при загрузке из БД?

Если агрегат слишком маленький, мы не можем гарантировать бизнес-правила (нам придется делать сложные проверки в нескольких сервисах). Если слишком большой — мы получаем проблемы с производительностью и конфликтами при параллельном доступе (Lock contention).

---

### Ответ

#### Определение агрегата
Агрегат состоит из:
1. **Aggregate Root (Корень):** Единственная точка входа в агрегат. Только через Корень можно изменять состояние любого объекта внутри агрегата. Все внешние объекты должны ссылаться только на Корень.
2. **Entities (Сущности):** Объекты внутри агрегата, имеющие идентичность.
3. **Value Objects (Объекты-значения):** Объекты внутри агрегата, определяемые своими свойствами (неизменяемые).

#### Как я определяю границы (Критерии)

При проектировании я задаю себе три вопроса:
1. **«Должны ли эти объекты меняться одновременно, чтобы правила бизнеса не нарушились?»** (Если да — они в одном агрегате).
2. **«Могу ли я допустить временную несогласованность между этими объектами?»** (Если да — это разные агрегаты, связь между ними — через ID).
3. **«Насколько часто эти объекты будут конкурировать за доступ?»** (Если разные пользователи часто меняют разные части данных, агрегат нужно дробить).

---

#### Пример: Система управления заказами

**Правило (Инвариант):** «Сумма заказа не может превышать лимит кредита клиента, а статус заказа 'Доставлен' нельзя изменить на 'Отменен'».

**Правильная структура:**
* **Aggregate Root:** `Order`.
* **Entities внутри:** `OrderItem`.
* **Value Objects внутри:** `Money`, `Address`.

**Связь с другими агрегатами:**
`Order` не содержит в себе объект `Customer`. Он содержит только `CustomerId`. Это позволяет нам загружать заказ, не подтягивая всю историю покупок клиента из базы.

**Процесс изменения:**
Если нужно добавить товар, мы вызываем `$order->addItem($product, $qty)`. Внутри этого метода `Order` проверяет общую сумму и правила. Мы не вызываем `$orderItem->setPrice()`, потому что это нарушит контроль корня над ценой заказа.

---

#### Типовая ошибка: "Огромный агрегат" (The Fat Aggregate)

**Ошибка:** Попытка включить в агрегат `Order` все сущности, которые имеют к нему отношение, включая `Customer`, `Product` и `ShippingLog`.

**Как это выглядит в коде:**
`Order` содержит в себе объект `Customer`. Чтобы добавить товар в заказ, вам приходится загружать из базы данных не только заказ, но и весь профиль клиента со всеми его адресами, настройками и историей.

**Почему это плохо:**
1. **Производительность:** Вы тянете из БД гигантский граф объектов, даже если вам нужно просто изменить количество товара.
2. **Конфликты (Concurrency):** Если клиент одновременно меняет свой адрес в профиле и делает заказ, два процесса могут попытаться обновить одну и ту же строку/объект в базе, вызывая `Deadlock` или `Optimistic Lock Exception`.
3. **Нарушение границ:** Агрегат становится слишком "умным" и начинает знать слишком много о внешнем мире.

**Как исправить:** 
Заменить прямую связь объектом `Customer` на связь по идентификатору `CustomerId`. Теперь `Order` и `Customer` — это два разных агрегата. Они согласуются между собой через **Domain Events** (например, `OrderPlaced` $\to$ `UpdateCustomerStats`).

#### Резюме
* **Маленькие агрегаты** $\to$ высокая производительность, легкое масштабирование, но риск нарушить инварианты (нужна событийная согласованность).
* **Большие агрегаты** $\to$ гарантированная целостность, но низкая скорость и проблемы с конкурентным доступом.
* **Мой выбор:** Стремиться к максимально малым агрегатам, сохраняя целостность через **Aggregate Root** и обеспечивая связь между ними через **ID** и **Events**.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

### Рассуждение

Это классическая проблема конкурентного доступа (Concurrency Control). Когда два процесса одновременно читают состояние агрегата, изменяют его и пытаются сохранить обратно, возникает риск **"потери обновления" (Lost Update)**.

Если мы не примем мер, процесс Б может перезаписать изменения, внесенные процессом А, просто потому что процесс Б не знал об изменениях, сделанных процессом А между моментом чтения и моментом записи.

В проектировании систем я рассматриваю два основных подхода к решению этой проблемы: **Pessimistic Locking (Пессимистичная блокировка)** и **Optimistic Locking (Оптимистичная блокировка)**. Выбор между ними зависит от частоты конфликтов и требований к доступности системы.

---

### Ответ

#### 1. Что произойдёт (Проблема)
Представим агрегат `BankAccount` с балансом 100$.
1. **Процесс А** читает баланс (100$).
2. **Процесс Б** читает баланс (100$).
3. **Процесс А** вычитает 20$ (новый баланс 80$) и делает `flush()`. В БД теперь 80$.
4. **Процесс Б** вычитает 30$ (исходя из старого значения 100$, новый баланс 70$) и делает `flush()`.
5. **Итог:** В базе 70$. Мы "потеряли" списание 20$, которое сделал процесс А. Это критическая ошибка консистентности.

#### 2. Как я проектирую (Методы решения)

Я выбираю стратегию в зависимости от профиля нагрузки.

##### А. Optimistic Locking (Оптимистичная блокировка) — Мой основной выбор
Это стандарт для большинства веб-приложений. Мы предполагаем, что конфликты случаются редко.

* **Механизм:** Мы добавляем в агрегат поле `version` (целое число или таймштамп). При каждом обновлении Doctrine проверяет: `WHERE id = ? AND version = <старое_значение>`. Если кто-то уже изменил версию, запрос затронет 0 строк, и Doctrine выбросит `OptimisticLockException`.
* **Реализация в Symfony/Doctrine:** Достаточно добавить атрибут `#[ORM\Version]` над полем `$version`.
* **Trade-offs:**
    * **(+) Плюсы:** Не блокирует базу данных. Высокая производительность при низком уровне конфликтов.
    * **(-) Минусы:** Если конфликты частые, пользователю придется постоянно получать ошибки и повторять действие (Retry). Это плохо для UX.

##### Б. Pessimistic Locking (Пессимистичная блокировка)
Мы используем механизмы самой БД (`SELECT ... FOR UPDATE`), чтобы "застолбить" строку.

* **Механизм:** Когда процесс А читает агрегат, он вешает на него блокировку. Процесс Б, пытаяясь прочитать этот же агрегат с той же блокировкой, будет **ждать** на уровне БД, пока процесс А не завершит транзакцию (commit/rollback).
* **Реализация в Doctrine:** `$em->find(Order::class, $id, LockMode::PESSIMISTIC_WRITE);`.
* **Trade-offs:**
    * **(+) Плюсы:** Гарантированная целостность. Процессы не сталкиваются с ошибками, они просто выстраиваются в очередь.
    * **(-) Минусы:** Риск **Deadlocks** (взаимных блокировок). Снижение пропускной способности системы (Concurrency упадет, так как процессы ждут друг друга).

#### 3. Моя стратегия проектирования

Я использую комбинированный подход, исходя из бизнес-ценности данных:

1.  **Для большинства сущностей (Профиль, Настройки, Посты):** Я использую **Optimistic Locking**. Это дешево, безопасно и не тормозит систему. Если произошел конфликт, на уровне Application Layer мы можем реализовать автоматический `retry` (повтор операции) до 3 раз.
2.  **Для критических финансовых или инвентарных данных (Баланс, Остаток на складе):** Я использую **Pessimistic Locking**. Здесь цена ошибки (потеря денег или продажа несуществующего товара) выше, чем цена ожидания в очереди.
3.  **На уровне архитектуры (DDD):** Я стараюсь проектировать агрегаты так, чтобы они были **маленькими**. Чем меньше агрегат, тем меньше вероятность, что два процесса захотят его изменить одновременно. Если агрегат слишком велик, я дроблю его, чтобы уменьшить область конфликтов.

**Итог:** Я не выбираю один способ "навсегда". Я выбираю **Optimistic Locking** как стандарт для масштабируемости и **Pessimistic Locking** как инструмент для критических участков, где консистентность важнее скорости.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

### Рассуждение

Вопрос о доменных событиях (Domain Events) — это вопрос о переходе от монолитного, жестко связанного кода к архитектуре, основанной на **реакции на изменения**. 

Главная ошибка — путать *доменные события* с *событиями инфраструктуры* (например, "файл загружен" или "запрос завершен"). Доменное событие — это факт, который произошел в предметной области и имеет значение для бизнеса. Например: `OrderPlaced`, `UserRegistered`, `PaymentFailed`.

Я разделяю применение событий на два уровня:
1. **Внутри одного агрегата (Internal):** Для поддержания инвариантов.
2. **Между агрегатами/контекстами (External):** Для обеспечения согласованности (Eventual Consistency).

Проблема связи событий с транзакциями — самая сложная часть. Если мы опубликуем событие *до* того, как транзакция закоммитится, а потом транзакция откатится, мы получим "фантомное" событие (мы сказали миру, что заказ создан, но в базе его нет). Это катастрофа.

---

### Ответ

#### 1. Когда публиковать события?
Я публикую события **только после успешного завершения транзакции**. 

Событие — это свершившийся факт. Если транзакция в БД не завершена, факта еще не существует. Поэтому публикация должна происходить в момент, когда данные стали «перманентными».

#### 2. Как обрабатывать события?

Я использую два подхода в зависимости от типа обработки:

*   **Синхронная обработка (в рамках того же процесса):** Если действие является частью той же бизнес-логики (например, расчет скидки при добавлении товара). Это происходит внутри того же транзакционного контекста.
*   **Асинхронная обработка (через Message Bus):** Если действие является побочным эффектом (отправка Email, обновление индекса, уведомление службы доставки). Это реализуется через **Symfony Messenger**.

#### 3. Связь событий с транзакциями (The Outbox Pattern)

Чтобы избежать проблемы "фантомных событий" или их потери, я использую один из двух подходов:

**А. Transactional Outbox (Самый надежный)**
Вместо того чтобы отправлять сообщение в RabbitMQ/Redis напрямую, я записываю его в специальную таблицу `outbox` в **той же самой транзакции**, где сохраняется основной агрегат.
1. `BEGIN TRANSACTION`
2. `INSERT INTO orders ...`
3. `INSERT INTO outbox_messages (event_type, payload) ...`
4. `COMMIT`
Затем отдельный процесс (Relay) читает таблицу `outbox` и перекладывает сообщения в реальную очередь. Это гарантирует, что событие будет опубликовано **только если** данные в БД сохранились.

**Б. Post-Commit Dispatch (Проще, но менее надежно)**
В Symfony я использую слушатель жизненного цикла или обертку над `EntityManager`, которая собирает события внутри агрегата и только после `flush()` и успешного `commit()` отправляет их в шину сообщений.

#### 4. Какие проблемы решает этот подход?

*   **Loose Coupling (Слабая связанность):** `OrderService` не знает о существовании `EmailService`. Он просто говорит: "Заказ создан". Это позволяет добавлять новые реакции на события, не меняя старый код (соблюдение OCP).
*   **Scalability (Масштабируемость):** Мы можем вынести тяжелые задачи (генерация PDF, интеграция с API) в отдельные воркеры, не замедляя основной поток пользователя.
*   **Single Responsibility:** Код бизнес-логики остается чистым, он не замусорен вызовами сторонних сервисов.

#### 5. Какие проблемы создаёт?

*   **Eventual Consistency (Согласованность в конечном счете):** Это главная цена. После того как пользователь увидел "Успех", данные в поисковом индексе могут обновиться только через 500мс. Это нужно учитывать в UX (например, показывать сообщение "Обновляем данные...").
*   **Complexity (Сложность):** Появляется необходимость отслеживать состояние системы, управлять очередями, обрабатывать ошибки обработки событий (Retries).
*   **Idempotency (Идемпотентность):** События могут прийти дважды (из-за особенностей работы очередей "at-least-once delivery"). **Обработчики событий обязаны быть идемпотентными** — повторный вызов с тем же ID события не должен приводить к дублированию действий (например, двойному списанию денег).

**Итог:** Я использую доменные события для разрыва жестких связей и обеспечения масштабируемости, всегда связывая их жизненный цикл с транзакцией БД через паттерн **Outbox** или **Post-Commit Dispatch**, и всегда проектирую обработчики как **идемпотентные**.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

### Рассуждение

Эти вопросы касаются самой сути проектирования программного обеспечения. Здесь нет «магических формул», есть только способы управления сложностью.

Часто разработчики путают **Entity** и **Value Object**, потомую что в базах данных они оба выглядят как строки в таблицах. Но в DDD разница не в том, *как они хранятся*, а в том, *как они определяют свою идентичность и ведут себя в логике*.

Я разделяю понимание этих понятий на три уровня:
1.  **Идентичность (Identity):** Кто это?
2. way of life (Behavior): Как это меняется?
3. **Связь с языком (Ubiquitous Language):** Как об этом говорят эксперты?

Если я не буду использовать Единый Язык, мой код превратится в "перевод с технического на человеческий", где `Order` в базе — это `Order`, а в разговоре с бизнесом — это «заявка на отгрузку». Это ведет к огромному количеству ошибок при интерпретации требований.

---

### Ответ

#### 1. Различие между Entity и Value Object

Главное различие — в **Identity (Идентичности)**.

| Характеристика | Entity (Сущность) | Value Object (Объект-значение) |
| :--- | :--- | :--- |
| **Идентичность** | Имеет уникальный ID, который сохраняется на протяжении всей жизни. | Не имеет ID. Описывается только своими свойствами. |
| **Сравнение** | Сравнивается по ID (`$a->getId() === $b->getId()`). | Сравнивается по значениям всех полей (`$a->equals($b)`). |
| **Изменяемость** | **Mutable**. Состояние может меняться, но объект остается тем же самым. | **Immutable**. При любом изменении создается новый объект. |
| **Жизненный цикл** | Имеет историю (события, статусы, изменения). | "Рождается" и "умирает" мгновенно как набор данных. |

**Пример:** 
*   **Entity:** `User`. Если пользователь сменил имя, фамилию и email, он остается тем же самым пользователем (с тем же ID).
*   **Value Object:** `Money`. Если у вас есть 100$, и вы превращаете их в 200$ — это не "тот же самый объект, который стал другим", это совершенно другое значение. Если у двух разных людей по 100$ — это два разных объекта, но они **равны** по значению.

#### 2. Как я принимаю решение (Decision Process)

Когда я проектирую новую концепцию, я задаю себе два вопроса:

1.  **"Если я изменю все свойства этого объекта, останется ли он тем же самым предметом?"**
    *   Если **ДА** $\to$ это **Entity**.
    *   Если **НЕТ** $\to$ это **Value Object**.

2.  **"Нужна ли мне история изменений этого объекта?"**
    *   Если я должен отслеживать, как статус заказа менялся от `New` к `Shipped` $\to$ это **Entity**.
    *   Если мне просто нужно знать текущую цену или адрес $\to$ это **Value Object**.

#### 3. Единый язык (Ubiquitous Language)

**Ubiquitous Language** — это общий язык, который используют разработчики, бизнес-эксперты (Domain Experts) и аналитики. Это не "перевод" терминов, это **один и тот тот же словарь** для всех.

**Как он влияет на код:**
В хорошем DDD-проекте код читается как текст на этом языке.

*   **Плохо (Технический язык):**
    `$userService->updateStatus($userId, 2);` — Что такое `2`? Что делает `updateStatus`? Это технический манипулятор данными.
*   **Хорошо (Ubiquitous Language):**
    `$order->ship($shippingDetails);` — Здесь используется глагол из бизнес-процесса (`ship`) и объект, который понятен бизнесу. Код говорит: "Заказ отгружен".

**Как я внедряю его в процесс:**
1.  **Слушаю экспертов:** Я не придумываю названия классов сам. Я слушаю, как менеджер говорит: "Мы *аннулируем* заказ", а не "мы ставим флаг `is_cancelled = true`". В коде будет метод `cancel()`, а не `setIsCancelled()`.
2.  **Навязываю терминологию в коде:** Если в бизнесе есть термин "Скидка за лояльность", в коде не должно быть `DiscountType::TYPE_LOYALTY`. Должно быть `LoyaltyDiscount`.
3.  **Документирую через код:** Сами названия классов, методов и переменных становятся документацией. Если бизнес-эксперт посмотт на метод `applySeasonalPromotion()`, он должен сразу понять, что он делает, не зная PHP.

**Итог:** Entity и Value Object — это инструменты для реализации правил, а Ubiquitous Language — это клей, который гарантирует, что эти правила в коде соответствуют реальности в бизнесе.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

### Рассуждение

Когда я проектирую приложение по принципам чистой архитектуры (Clean Architecture) или гексагональной архитектуры (Ports and Adapters), моя главная цель — **инверсия зависимости**. 

Самая большая ошибка — построить приложение вокруг фреймворка (Symfony) или базы данных (Doctrine). В таком случае ваше приложение — это просто "надстройка" над библиотеками. Если Symfony обновится или вы решите сменить БД, вы переписываете всё. 

В чистой архитектуре **Бизнес-логика находится в центре и она ничего не знает о внешнем мире**. Все внешние инструменты (БД, API, очереди, фреймворки) — это лишь детали реализации, которые подключаются к центру через интерфейсы.

Я разделяю приложение на четыре четких слоя.

---

### Ответ

#### 1. Структура слоев

**Слой 1: Domain (Ядро)**
Это сердце системы. Здесь живут правила, которые существуют даже если у вас не будет компьютера.
* **Что лежит:** Entities, Value Objects, Domain Exceptions, Domain Services, Repository Interfaces (только интерфейсы!).
* **Зависимости:** **Ни от чего не зависит.** Этот слой — чистый PHP.

**Слой 2: Application (Use Cases)**
Этот слой оркеструет выполнение задач. Он говорит: «Возьми юзера, примени к нему скидку, сохрани результат».
* **Что лежит:** Use Cases (или Command Handlers), DTO (Data Transfer Objects), Application Services, интерфейсы для внешних систем (например, `EmailServiceInterface`).
* **Зависимости:** Зависит только от **Domain**.

**Слой 3: Infrastructure (Детали реализации)**
Здесь живут инструменты. Это то, что делает систему "реальной".
* **Что лежит:** Реализация репозиториев (Doctrine), реализации почтовых сервисов (Mailgun/Symfony Mailer), реализация работы с кешем (Redis), реализация работы с очередями.
* **Зависимости:** Зависит от **Application** (чтобы реализовать его интерфейсы) и от **Domain**.

**Слой 4: User Interface / Presentation (Входные точки)**
То, как мир общается с приложением.
* **Что лежит:** Symfony Controllers, CLI Commands, API Resources, консольные команды.
* **Зависимости:** Зависит от **Application** (вызывает Use Case) и от **Infrastructure** (для сборки контейнера/DI).

---

#### 2. Куда попадут компоненты?

* **Symfony Controller:** Попадает в слой **Presentation**. Его задача — принять HTTP-запрос, превратить его в DTO и передать в `Application Use Case`. Он не должен содержать логики.
* **Doctrine (EntityManager, Repository Implementations):** Попадает в слой **Infrastructure**. Контроллер не должен знать о Doctrine. Он знает только об интерфейсе `OrderRepositoryInterface` из слоя Domain.
* **Обработчик очереди (Messenger Handler):** Попадает в слой **Application** (как реализация логики) или в **Infrastructure** (как механизм запуска). Но суть обработки — это Use Case, который вызывается обработчиком.

**Визуализация потока:**
`HTTP Request` $\to$ `Controller (Presentation)` $\to$ `UseCase (Application)` $\to$ `Domain Model` $\to$ `Repository (Infrastructure/DB)`

---

#### 3. Правило зависимостей (Dependency Rule)

**Зависимости всегда направлены внутрь, к центру.**
* Слой `Presentation` $\to$ `Application` $\to$ `Domain`.
* Слой `Infrastructure` $\to$ `Application` $\to$ `Domain`.

**Никогда** не должно быть зависимости: `Domain` $\to$ `Infrastructure`. Если вашему доменному объекту нужно сохранить себя в базу, он не должен вызывать `$entityManager->persist()`. Он должен вызвать метод интерфейса `$repository->save()`, а реализация этого метода будет лежать в слое инфраструктуры.

---

#### 4. Как следить, чтобы границы не нарушались?

Соблюдать это вручную в большом проекте невозможно. Я использую три инструмента:

1.  **Static Analysis (PHPStan / Psalm):** Это мой основной инструмент. Я настраиваю правила, которые запрещают импорт классов из слоя `Infrastructure` в слой `Domain`. Если кто-то случайно напишет `use Doctrine\ORM\EntityManager;` внутри сущности — статический анализатор выдаст ошибку при CI.
2.  **Dependency Checkers (Deptrac):** Это специализированный инструмент для проверки слоев. Я создаю конфиг, где описываю: "Слой Domain не может зависеть от Application, а Application не может зависеть от Infrastructure". Если правило нарушено — сборка падает.
3.  **Code Review:** Никакая автоматика не заменит глаз опытного инженера, который увидит, что бизнес-логика "протекла" в контроллер или что репозиторий делает слишком много лишнего.

**Итог:** Чистая архитектура делает систему **тестируемой** (мы можем протестировать Domain без БД) и **гибкой** (мы можем заменить Symfony на другой фреймворк, не меняя бизнес-логику).

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

### Рассуждение

Тестирование — это не про "покрытие строк", а про **уверенность в том, что код работает как ожидается и не сломается при изменениях**. 

Если я буду писать только Unit-тесты, я не узнаю, что у меня сломался SQL-запрос или интеграция с базой. Если я буду писать только Functional тесты (прогонять каждый раз весь контейнер Symfony), мои тесты будут идти 40 минут, и разработчики перестанут их запускать.

Я придерживаюсь классической **Пирамиды тестирования**, но с поправкой на современные реалии (где интеграционные тесты часто важнее чистых Unit-тестов из-за сложности инфраструктуры).

---

### Ответ

#### 1. Стратегия: Пирамида тестов

Я распределяю усилия следующим образом:

**А. Unit-тесты (Основание пирамиды — ~70%)**
* **Что тестируем:** Чистую бизнес-логику. Value Objects, методы сущностей (Entities), сервисы без внешних зависимостей, Domain Services.
* **Что мокаем:** Всё. В Unit-тесте не должно быть ни одного обращения к БД, файловой системе или сети.
* **Цель:** Мгновенная обратная связь. Они должны выполняться тысячи за секунды.

**Б. Integration-тесты (Середина — ~20%)**
* **Что тестируем:** Взаимодействие кода с внешними компонентами. Работа репозиториев с реальной PostgreSQL, работа с Redis, интеграция с шиной сообщений (Messenger).
* **Что НЕ мокаем:** Базу данных, очередь, кеш. Мы проверяем, что наш SQL корректен и Doctrine правильно мапит данные.
* **Цель:** Убедиться, что наши "контракты" с инфраструктурой работают.

**В. Functional / End-to-End тесты (Вершина — ~10%)**
* **Что тестируем:** Сценарии использования (Use Cases) через HTTP-запросы. Мы имитируем запрос пользователя к контроллеру и проверяем финальный результат (статус ответа, изменения в БД, отправленное письмо).
* **Что НЕ мокаем:** Почти ничего. Используется полноценный Kernel Symfony.
* **Цель:** Проверка критических путей (Happy Path): "Регистрация -> Заказ -> Оплата".

---

#### 2. Что мокать, а что нет?

Это самый важный вопрос для баланса между скоростью и надежностью.

* **Мокаем (Mock/Stub):**
    * **Внешние API:** (Stripe, AWS, SendGrid). Мы не хотим делать реальные сетевые запросы. Используем `MockHttpClient` или специальные библиотеки (например, `Mailtrap`).
    * **Тяжелые сторонние сервисы:** Если нам нужно имитировать поведение генератора PDF.
    * **В Unit-тестах:** Все зависимости, чтобы изолировать тестируемый объект.

* **НЕ мокаем (Используем реальные объекты):**
    * **Value Objects и Entities:** Они должны быть реальными.
    * **Базу данных (в интеграционных тестах):** Мокать репозиторий — значит тестировать мок, а не работу с данными. Это бесполезно.
    * **Внутренние сервисы (в функциональных тестах):** Если мы тестируем контроллер, мы хотим, чтобы он прошел через всю цепочку до БД.

---

#### 3. Как поддерживать тесты быстрыми и стабильными?

Чтобы тесты не превратились в "медленное болото", я использую следующие практики:

**Для скорости:**
1. **Database Isolation:** Для интеграционных тестов я использую отдельную БД (или схему). Я использую транзакционный подход: каждый тест оборачивается в транзакцию, которая откатывается (`rollback`) в конце теста. Это в разы быстрее, чем пересоздавать базу или делать `TRUNCATE`.
2. **Avoid Kernel Boot in Unit Tests:** Никогда не поднимай Symfony Kernel в Unit-тестах. Если тебе нужен контейнер — это уже не Unit-тест.
3. **Parallel Execution:** Запуск тестов в несколько потоков (например, через `ParaTest`).

**Для стабильности (избавление от Flaky Tests):**
1. **Deterministic Data:** Я не использую `rand()` или `now()` внутри тестов. Для дат я использую `ClockInterface` (из PSR-20), который я могу «заморозить» в тесте.
2. **Clean State:** Каждый тест должен начинаться с чистого листа. Никаких зависших файлов в `/tmp` или записей в кеше.
3. **Idempotency in Integration:** Если тест зависит от состояния БД, он должен сам создавать необходимые данные (чеf через `Factories` или `DataFixtures`), а не полагаться на то, что "в базе уже что-то есть".
4. **Avoid Real Network/Time:** Все внешние задержки (sleep) и сетевые вызовы должны быть заменены на контролируемые заглушки.

**Итог:** Моя стратегия — **максимум Unit-тестов для логики, надежные Integration-тесты для БД и минимум, но критически важные Functional-тесты для проверки сценариев.**

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Это классическая проблема **конкурентного доступа** (Concurrency Control). Когда два процесса (или два пользователя) одновременно считывают состояние объекта, вносят изменения и пытаются сохранить их, возникает риск нарушения целостности данных.

### 1. Какие проблемы могут возникнуть?

Существует три основных типа проблем:

1.  **Lost Update (Потерянное обновление):**
    Это самый частый сценарий. 
    *   *Процесс А* читает баланс 100$. 
    *   *Процесс Б* читает баланс 100$. 
    *   *Процесс А* вычитает 20$ и записывает 80$. 
    *   *Процесс Б* прибавляет 50$ (исходя из старого значения 100) и записывает 150$. 
    *   **Итог:** Изменение процесса А (минус 20$) просто исчезло. В базе 150$ вместо ожидаемых 130$.

2.  **Dirty Read (Грязное чтение):**
    Процесс А изменяет данные, но еще не закоммитил транзакцию. Процесс Б читает эти изменения. Если процесс А сделает `rollback`, процесс Б будет работать с данными, которых никогда не существовало.

3.  **Phantom Read (Фантомное чтение):**
    Процесс А читает набор строк (например, все заказы клиента). В это время процесс Б вставляет новый заказ для этого клиента. Процесс А повторно читает набор строк и видит "фантомную" новую запись, которой не было в его первом чтении.

---

### 2. Способы защиты

Я разделяю подходы на две большие категории: **Optimistic** и **Pessimistic**.

#### А. Optimistic Locking (Оптимистичная блокировка)
Мы предполагаем, что конфликты случаются редко. Мы не блокируем запись при чтении, но проверяем, не изменилась ли она, в момент записи.

*   **Механизм:** В таблицу добавляется поле `version` (целое число).
    *   `UPDATE account SET balance = 80, version = 2 WHERE id = 1 AND version = 1;`
*   Если другой процесс уже успел изменить версию, запрос вернет `0 affected rows`. Приложение получает ошибку и должно либо повторить операцию, либо сообщить пользователю.
*   **Реализация в Symfony/Doctrine:** Просто добавляем атрибут `#[ORM\Version]`.

#### Б. Pessimistic Locking (Пессимистичная блокировка)
Мы предполагаем, что конфликт почти неизбежен. Мы блокируем запись в момент чтения.

*   **Механизм:** Используется SQL-команда `SELECT ... FOR UPDATE`.
    *   Процесс А читает запись и блокирует её на уровне БД.
    *   Процесс Б пытается прочитать ту же запись с `FOR UPDATE` и **ждет**, пока процесс А не сделает `COMMIT` или `ROLLBACK`.
*   **Реализация в Doctrine:** `$em->find(Account::class, $id, LockMode::PESSIMISTIC_WRITE);`.

---

### 3. Сравнение и выбор стратегии

| Критерий | Optimistic Locking | Pessistic Locking |
| :--- | :--- | :--- |
| **Производительность** | Высокая (нет блокировок) | Ниже (процессы ждут друг друга) |
| **Масштабируемость** | Отличная | Ограничена (риск дедлоков и очередей) |
| **Риск конфликтов** | Если конфликты частые — много ошибок | Если конфликты частые — система "тормозит" |
| **Сложность кода** | Нужно обрабатывать исключение и делать retry | Нужно следить за временем ожидания и дедлоками |

#### Когда я выбираю Optimistic Locking:
Это мой **стандартный выбор** для 90% веб-приложений.
*   Когда пользователи работают с данными по отдельности (например, редактируют профиль или статью).
*   Когда вероятность того, что два человека нажмут "Сохранить" в одну и ту же миллисекунду, крайне мала.
*   **Пример:** Редактирование контента в CMS, обновление настроек пользователя.

#### Когда я выбираю Pessimistic Locking:
Я использую его только для **критически важных финансовых или инвентарных операций**, где цена ошибки выше, чем цена ожидания.
*   Когда высокая конкуренция за одну и ту же запись гарантирована.
*   Когда операция должна быть атомарной и "неделимой" в плане времени.
*   **Пример:** Списание денег со счета в банковском приложении, бронирование последнего билета на самолет, списание остатка товара на складе.

**Итоговая рекомендация:** Всегда начинай с **Optimistic Locking**. Если профилирование показывает, что пользователи слишком часто сталкиваются с конфликтами версий (и это портит UX), переходи на **Pessimistic Locking** для конкретных узких участков кода.

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

В работе я придерживаюсь принципов **предсказуемости, атомарности и автоматизации**. Мой процесс построен так, чтобы минимизировать риск «сломать мастер» и обеспечить прозрачность истории изменений. 

Я не сторонник экстремального GitFlow (с его бесконечными ветками `develop`, `release`, `hotfix`), так потому что он избыточен для современных CI/CD циклов. Я использую упрощенный **GitHub Flow** с элементами **Trunk-Based Development**.

---

### 1. Ветвление (Branching Strategy)

Моя структура:
*   **`main` (или `master`):** Единственная стабильная ветка. То, что находится в `main`, всегда готово к деплою на продакшен.
*   **`feature/feature-name` или `task/JIRA-123`:** Короткоживущие ветки для конкретных задач.

**Почему так:** 
Длинные ветки (Long-lived branches) — это зло. Чем дольше ветка живет отдельно от `main`, тем больнее будет делать `merge`. Я стремлюсь к тому, чтобы ветки жили от нескольких часов до пары дней. Если задача большая — я разбиваю её на маленькие части и вливаю их в `main` через Feature Toggles (переключатели фич).

---

### 2. Формат коммитов (Commit Message)

Я использую стандарт **Conventional Commits**. Это не просто "красивые сообщения", это инструмент для автоматизации.

**Формат:** `<type>(<scope>): <description>`
*   `feat`: новая функциональность.
*   `fix`: исправление ошибки.
*   `refactor`: изменение кода без изменения логики/фич.
*   `test`: добавление тестов.
*   `docs`, `style`, `chore`, `perf`.

**Почему так:**
1.  **Читаемость:** Сразу понятно, что произошло в истории.
2.  **Автоматизация:** На основе этих тегов можно автоматически генерировать `CHANGELOG.md` и определять версию следующего релиза (Semantic Versioning).
3.  **Атомарность:** Один коммит = одна логическая задача. Если я сделал рефакторинг и фичу в одном коммите — это плохой коммит. Его невозможно нормально ревьюить или откатывать.

---

### 3. Pull Request (PR) и Code Review

PR — это не просто уведомление о готовности кода, это инструмент передачи знаний и контроля качества.

**Мой процесс:**
1.  **Описание:** В PR я всегда пишу: *Что сделано? Зачем это сделано? Как это протестировать?* (желательно со скриншотами, если затронут UI).
2.  **Self-Review:** Перед тем как позвать коллег, я сам прохожу по своим изменениям в интерфейсе PR. Это отлавливает 50% глупых ошибок (забытые `dd()`, лишние комментарии).
3.  **Review:** 
    *   Я ищу не только ошибки, но и соответствие архитектуре (не нарушен ли SRP/DIP?).
    *   Я не использую ревью как инструмент "придирок". Если вопрос не критичен для стабильности, я пишу: *"Nit: можно было бы сделать так, но не обязательно"*.
4.  **CI Check:** PR не может быть влит, пока не пройдут автоматические тесты (Unit, Integration) и линтеры (PHPStan, Psalm, PHP-CS-Fixer).

**Почему так:** Это гарантирует, что в `main` попадает только проверенный и качественный код, а знания о системе распределяются между членами команды.

---

### 4. Релизы (Releases & Deployment)

Я придерживаюсь концепции **Continuous Delivery**.

1.  **Merge в `main`:** После одобрения PR ветка сливается в `main` (обыюно через `squash and merge`, чтобы история `main` была чистой и линейной).
2.  **Автоматический деплой (Staging):** Слияние в `main` автоматически запускает пайплайн на стейджинг-окружении.
3.  **Тестирование на стейджинге:** Проверка "в поле" (Smoke tests).
4.  **Релиз на Prod:** Либо по нажатию кнопки в CI/CD, либо автоматически (если стейджинг прошел все проверки).

**Почему так:** 
Использование `squash and merge` делает историю `main` понятной: один коммит — один фичер/багфикс. Это упрощает `git revert`, если что-то пошло не так.

---

### Итоговая схема процесса:

`Задача в Jira` $\to$ `Создание ветки task/JIRA-123` $\to$ `Локальная разработка (атомарные коммиты)` $\to$ `Push` $\to$ `Создание PR` $\to$ `CI (Tests/Lint)` $\to$ `Code Review` $\to$ `Squash & Merge в main` $\to `Авто-деплой на Staging` $\to$ `Деплой на Prod`.

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

Для меня код-ревью — это не процесс «поиска ошибок», а **процесс обеспечения качества и обмена знаниями**. Хороший ревьюер не работает как компилятор (проверять синтаксис должен статический анализатор), он работает как архитектор и наставник.

### 1. На что я смотрю в первую очередь

Я делю процесс проверки на три уровня приоритетности:

**Уровень 1: Архитектура и дизайн (Самое важное)**
* **Соблюдение границ (Bounded Contexts):** Не «протекли» ли детали реализации одного слоя в другой? (например, использование Doctrine в Domain-слое).
* **Принципы SOLID:** Не превратился ли новый класс в «Божественный объект»? Соблюдена ли инверсия зависимостей?
* **Сложность (Complexity):** Не переусложнен ли код? Можно ли это решение сделать проще? Не нарушает ли оно принцип KISS?
* **Инварианты:** Гарантирует ли код, что объект всегда будет находиться в валидном состоянии?

**Уровень 2: Логика и надежность**
* **Edge Cases (Граничные случаи):** Что будет, если придет `null`? Если массив пустой? Если база данных ответит таймаутом?
* **Транзакционность:** Если в методе два изменения (запись в БД и отправка события), что произойдет при сбое на втором шаге?
* **Производительность:** Нет(ли) здесь потенциального N+1 или тяжелого цикла внутри цикла?

**Уровень ло 3: Чистота и стиль (Самое низкое)**
* **Именование:** Насколько переменные и методы соответствуют *Ubiquitous Language*?
* **Читаемость:** Понятен ли код без комментариев?
* *Примечание:* Я не трачу время на обсуждение отступов или скобок — это задача `PHP-CS-Fixer` и `PHPStan`. Если это не автоматизировано, это плохой процесс.

---

### 2. Как я маркирую замечания

Чтобы ревью не выглядело как "нападение", я использую систему префиксов. Это помогает автору понять степень критичности замечания и не тратить силы на спор с мелочами.

* **[BLOCKER] / [CRITICAL]:** Ошибка в логике, дыра в безопасности или нарушение архитектуры. Этот PR не может быть влит, пока не будет исправлено.
* **[QUESTION]:** Я не уверен, как это работает, или не понимаю, почему выбрано именно такое решение. Прошу пояснений.
* **[SUGGESTION] / [NIT]:** Необязательное предложение. "Было бы круче сделать так, но если тебе так удобнее — ок". Это не требует обязательного исправления.
* [**REFACTOR**]: Предложение по улучшению читаемости или структуры, не меняющее логику.

---

### 3. Как я поступаю при разногласиях

Разногласия — это нормальная часть инженерного процесса. Моя цель — не "победить в споре", а найти **лучшее решение для проекта**.

**Мой алгоритм при конфликте:**

1.  **Сначала задаю вопрос, а не даю утверждение.** Вместо *"Это плохо, переделай"*, я спрашиваю: *"Почему ты выбрал этот подход? Я беспокоюсь, что это может привести к [проблема]"*. Это переводит спор из плоскости "кто прав" в плоскость "что лучше для системы".
2.  **Аргументирую через принципы и последствия.** Я не говорю "мне не нравится". Я говорю: *"Этот подход нарушает принцип Single Responsibility, и в будущем нам будет сложно тестировать этот класс в изоляции"*.
3.  **Если спор затягивается (более 3-х итераций в комментариях):** Я предлагаю **созвониться на 5-10 минут**. Писать длинные простыни текста в комментариях — неэффективно и часто ведет к недопониманию тона. Живой разговор решает 90% конфликтов.
4.  **Если решение не найдено (Escalation):** Если мы зашли в тупик, я предлагаю привлечь третьего человека (Lead/Architect) для принятия решения. Но я никогда не использую это как способ "продавить" свою позицию.
5.  **Принятие решения:** Если после обсуждения решение принято (не обязательно мое), я принимаю его и иду дальше. В программировании редко бывает один "единственно верный" способ, часто это выбор между двумя типами компромиссов.

**Главное правило:** Я критикую **код**, а не **человека**. Моя задача — сделать код лучше, а не сделать автора "глупее".

## Q21 · Работа с задачами

**Интервьюер:** Вот сырая проблема от бизнеса: «Пользователи жалуются, что не могут найти свои заказы из прошлого, поддержка завалена обращениями». Сформулируй из неё задачу для исполнителя — так, чтобы её можно было выполнить без уточнений. Что обязательно включишь в формулировку и почему?

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

### Рассуждение

Сначала я должен сделать важную техническую ремарку: в **PostgreSQL нет команды `FORCE INDEX`**. Это синтаксис MySQL. В PostgreSQL планировщик (Query Planner) работает иначе, и у него нет прямого механического спососа сказать: «Используй именно этот индекс, не раздумывай».

Однако, если вопрос подразумевает «Как в PostgreSQL заставить планировщик использовать нужный индекс, если он его игнорирует?», то это глубокая тема, связанная с тем, как работает оптимизатор.

Обычно планировщик игнорирует индекс по одной причине: **он считает, что сканирование всей таблицы (Sequential Scan) будет дешевле, чем использование индекса.** Это происходит, если:
1.  **Низкая селективность:** Индекс вернет слишком много строк (например, вы ищете по полю, где 90% значений — `true`). Планировщику проще прочитать всю таблицу подряд, чем прыгать между индексом и кучей данных (Random I/O).
2.  **Устаревшая статистика:** Планировщик думает, что в таблице 100 строк, а там их 10 миллионов.
3.  **Несоответствие типов:** Вы сравниваете `integer` с `text`, и из-за неявного приведения типов индекс становится бесполезным.

---

### Ответ

Поскольку прямой команды `FORCE INDEX` в PostgreSQL не существует, для достижения того же эффекта (принудительного использования индекса) используются другие механизмы.

Если вы понимаете, что планировщик ошибается, вы можете временно отключить использование последовательного сканирования для текущей сессии:
```sql
SET enable_seqscan = off;
-- Ваш запрос здесь
SELECT * FROM users WHERE email = 'test@example.com';
SET enable_seqscan = on;
```
*Это не «заставляет» использовать индекс, а делает использование Seq Scan максимально «дорогим» для оптимизатора, вынуждая его выбрать индекс.*

**Б. Создание функциональных индексов**
Если запрос использует функцию, например `WHERE lower(email) = '...'`, обычный индекс по `email` не сработает. Нужно создать индекс именно по результату функции:
```sql
CREATE INDEX idx_users_lower_email ON users (lower(email));
```

**В. Использование Partial Indexes (Частичные индексы)**
Если нам нужен индекс по специфическому подмножеству данных (например, только по активным пользователям), мы создаем его с условием `WHERE`. Это делает индекс очень компактным и эффективным.
```sql
CREATE INDEX idx_active_users ON users (id) WHERE is_active = true;
```

#### 2. Когда это необходимо применять (Сценарии)

Я применяю эти методы в следующих случаях:

1.  **Когда статистика устарела:** Если я вижу, что план выполнения выглядит нелогично, первым делом я выполняю `ANALYZE table_name;`. Часто это решает проблему без всяких «форсирований».
2.  **Когда селективность низкая, но индекс всё равно нужен:** Например, при использовании `Index Only Scan`, когда нам нужны только значения из самого индекса, и мы не хотим трогать основную таблицу (Heap).
3.  **При работе с JSONB:** Когда нужно эффективно искать внутри JSON-документов через GIN-индексы.

#### 3. Подводные камни и Trade-offs

*   **Опасность `enable_seqscan = off`:** Это «костыль». Если вы примените это глобально или забудете вернуть, вы можете катастрофически уронить производительность других запросов, которые на самом деле *должны* сканировать таблицу целиком.
*   **Риск "застывшего" плана:** Если вы принудительно заставили индекс работать сегодня, а завтра объем данных или распределение значений изменится, этот индекс может стать обузой.
*   **Поддержка:** Любой «хитрый» индекс или изменение параметров сессии — это дополнительная сложность, которую нужно документировать и поддерживать.

**Мой итог:** Вместо того чтобы «форсить» индекс, я всегда сначала пытаюсь **понять причину**, по которой планировщик его не выбрал (проверяю статистику, типы данных и селективность), и лечу саму причину, а не симптом.

## Q25 · Провокации

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

Это отличный вопрос, который проверяет, понимаешь ли ты разницу между «накладными расходами на проверку» и «реальной производительностью».

Если отвечать прямо: **влияние `strict_types=1` на скорость выполнения кода стремится к нулю (менее 1%)**, а в некоторых специфических сценариях он может даже **незначительно ускорить** выполнение.

Давай разберем это с точки зрения того, что происходит под капотом PHP.

### 1. Почему кажется, что это должно замедлять?
Логика проста: если раньше PHP просто молча приводил `string "5"` к `int 5` (coercive mode), то теперь он должен выполнить дополнительную проверку: *«Является ли этот тип именно тем, который указан в сигнатуре?»*. Любая дополнительная проверка — это дополнительные инструкции процессора.

### 2. Почему на самом деле это не замедляет код?

**А. Оптимизации Zend Engine (JIT и OpCache)**
Современный PHP (особенно 8.x) — это не интерпретатор в старом понимании. Благодаря **JIT (Just-In-Time compilation)** и глубокой оптимизации **OpCache**, движок компилирует байт-код в машинный код. 
Когда ты объявляешь строгую типизацию, ты даешь компилятору **гарантию**. В режиме `strict_types=1` движку не нужно генерировать код для «проверки и преобразования типа» при каждом вызове функции. Он знает: «Сюда придет только `int`, и я могу сразу использовать оптимизированную математическую операцию для целых чисел». 

В режиме *coercive mode* движку приходится на каждый вызов под капотом делать проверку: *«А не строка ли пришла? Если строка, то можно ли её превратить в число?»*. То есть **строгая типизация убирает неявную работу по приведению типов**, которая в нестрогом режиме происходит постоянно.

**Б. Проблема не в проверке, а в логике**
В реальных приложениях (Symfony, Laravel) узкое место — это не микросекунды на проверку типа в функции, а:
*   I/O операции (запросы к БД, Redis, API).
*   Аллокация памяти под большие объекты.
*   Сложные алгоритмы в бизнес-логике.
На фоне этих операций затраты на `strict_types` физически невозможно измерить — они находятся за пределами погрешности.

### 3. Когда это может быть заметно? (Микро-бенчмарки)
Если ты напишешь цикл на 10 миллионов итераций, где внутри вызывается функция с приведением типов, в `strict_mode` он может быть чуть-чуть быстрее за счет того, что PHP не тратит время на попытки преобразования типов в каждой итерации. Но это лабораторные условия, которые не имеют отношения к веб-запросам.

### Резюме

*   **Влияние на скорость:** Ничтожно мало (близко к 0%).
*   **Влияние на надежность:** Колоссальное. Оно превращает трудноуловимые логические ошибки (когда `true` внезапно превращается в `1` и ломает расчеты) в явные `TypeError`, которые ты ловишь на этапе разработки или тестирования.

**Мой вердикт:** Использовать `strict_types=1` во всех файлах проекта — это **must-have**. Это не вопрос производительности, это вопрос **предсказуемости и стоимости поддержки кода**. Мы платим микроскопическим (невидимым) ресурсом процессора за огромную экономию времени разработчиков и стабильность системы.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

Это очень глубокий и провокационный вопрос. На самом деле, утверждение «Doctrine не поддерживает составные первичные ключи» — это **техническое упрощение**. Doctrine **поддерживает** их на уровне маппинга, но она **не поддерживает их полноценно** в контек�age с концепцией **Identity Map** и механизмом управления жизненным циклом сущностей.

Давай разберем, почему так происходит и как мы решаем эту проблему в реальной разработке.

### 1. Почему это проблема? (Архитектурная причина)

Основная причина кроется в самой философии **Data Mapper** и реализации паттерна **Identity Map** внутри Doctrine.

**Identity Map** — это внутренний кэш Doctrine. Когда ты запрашиваешь сущность, Doctrine проверяет: «А не загружал ли я её уже в этом Unit of Work?». Чтобы это работало быстро, Doctrine должна уметь однозначно идентифицировать объект в памяти.

Когда у тебя составной ключ (например, `order_id` + `product_id`), возникает несколько сложностей:
1.  **Сложность идентификации:** Идентификатором объекта становится не одно значение, а массив. Это усложняет внутренние хеш-таблицы и механизмы сравнения объектов.
2.  **Нарушение инкапсуляции:** В DDD первичный ключ (ID) должен быть скрыт внутри сущности. Составной ключ заставляет тебя «выставлять наружу» несколько полей, что размывает границы агрегата.
3.  **Связи (Associations):** Если сущность `A` имеет составной ключ, то любая сущность `B`, которая ссылается на `A`, должна хранить **все** поля этого ключа как Foreign Key. Это приводит к «раздуванию» таблиц и огромному количеству лишних JOIN-ов.

### 2. Как это работает в Doctrine (Reality Check)

Ты **можешь** описать составной ключ через атрибуты:
```php
#[ORM\Entity]
class OrderItem {
    #[ORM\Id, ORM\ManyToOne(targetEntity: Order::class)]
    private Order $order;

    #[ORM\Id, ORM\Column]
    private int $productId;
}
```
Doctrine это проглотит. Но ты сразу столкнешься с проблемами:
*   Сложность при вызове `$em->find()`.
*   Проблемы с генерацией ID (автоинкремент не работает для составных ключей в стандартном виде).
*   Трудности при работе с `ManyToMany` или глубокими вложенностями.

---

### 3. Как с этим «живут» в реальных проектах?

В профессиональной разработке мы используем три стратегии, чтобы не превратить код в ад.

#### Стратегия А: Surrogate Key (Заместитель) — Мой основной выбор
Вместо того чтобы использовать естественный составной ключ (Natural Composite Key), мы вводим **суррогатный ключ** — искусственный `id` (обычно `UUID` или `bigint auto_increment`).

*   **Как это выглядит:** У тебя есть таблица `order_items`, где первичный ключ — это просто `id`. А старый составной ключ (`order_id` + `product_id`) становится просто **Unique Constraint** (уникальным индексом).
*   **Плюсы:**
    *   Идеальная совместимость с Doctrine.
    *   Легкие связи между сущностями (всегда только один FK).
    *   Простая работа с Identity Map.
*   **Минусы:** Лишняя колонка в базе данных. Но в 2024 году это ничтожная цена за чистоту архитектуры.

#### Стратегия Б: Использование Value Objects (DDD Way)
Если составной ключ — это не просто техническая связь, а бизнес-понятие (например, координаты `Latitude` + `Longitude`), мы упаковываем его в **Value Object**.

*   **Как это выглядит:** Мы не мапим составной ключ в Doctrine напрямую. Мы храним поля отдельно, но в сущности работаем с объектом.
*   **Плюсы:** Соблюдение чистоты домена.
*   **Минусы:** Нужно вручную следить за синхронизацией полей объекта и колонок в БД.

#### Стратегия В: Использование DTO для чтения
Если составной ключ нужен только для того, чтобы выводить данные в отчеты (Read Model), мы вообще не используем Entity. Мы пишем чистый SQL или DQL, который мапит результат сразу в плоский DTO.

---

### Итоговый вердикт

Если ты видишь в проектировании базы данных составной первичный ключ — это повод задуматься. 

В 99% случаев в современном PHP-приложении я выбираю **Surrogate Key (UUID или BigInt ID)**. Это избавляет нас от боли при работе с ORM, упрощает связи и делает код предсказуемым. Мы сохраняем бизнес-ограничение (уникальность пары полей) через `UNIQUE INDEX` на уровне БД, но для приложения объект остается простым и понятным.

#### Слой Application (Use Case)
```php
class PayOrderUseCase {
    public function __construct(
        private OrderRepositoryInterface $repository,
        private MessageBusInterface $bus, // Symfony Messenger
        private LoggerInterface $logger
    ) {}

    public function execute(int $orderId, int $currentUserId): void {
        // 1. Используем транзакцию
        $this->repository->transactional(function() use ($orderId, $currentUserId) {
            $order = $this->repository->findById($orderId);

            if (!$order) throw new NotFoundException();
            if ($order->getUserId() !== $currentUserId) throw new AccessDeniedException();

            // 2. Меняем состояние через доменную модель
            $order->markAsPaid();
            $this->repository->save($order);

            // 3. Вместо прямой отправки — событие в очередь (асинхронно)
            $this->bus->dispatch(new OrderPaidEvent($order->getId(), $order->getEmail()));
            
            $this->logger->info("Order paid: $orderId");
        });
    }
}
```

```php

}
```

2.  **Надежно:** Транзакция гарантирует, что статус и событие оплаты синхронизированы.
3.  **Быстро:** Письмо отправляется в фоне (чеer-worker), пользователь не ждет.
4.  **Тестируемо:** Я могу написать Unit-тест на `PayOrderUseCase`, подставив моки репозитория и шины сообщений, не запуская базу и почту.

**Интервьюер:** Посмотри на эту доменную сущность:

#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    }

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Этот код — классический пример того, как начинающие разработчики пытаются «помочь» архитектуре, но на самом деле её разрушают. Здесь нарушены фундаментальные принципы разделения ответственности и чистоты доменного слоя.

### Что не так? (Анализ нарушений)

**1. Нарушение принципа единственной ответственности (SRP) и инверсии зависимостей (DIP)**
Это самая критическая ошибка. Сущность (`User`) теперь не просто описывает данные и бизнес-правила, она еще и **управляет сохранением данных**. 
*   Сущность зависит от `EntityManagerInterface` (инфраструктурный объект).
*   Доменный слой теперь жестко связан с библиотекой Doctrine. Если вы захотите сменить ORM или использовать этот объект в скрипте без контейнера, вы не сможете это сделать.

**2. Нарушение границ слоев (Layer Leaking)**
Инфраструктурный объект `EntityManager` «протек» в самый центр системы — в доменную модель. Домен должен быть «чистым» (Plain Old PHP Object), не знающим о существовании баз данных, API или фреймворков.

**3. Нарушение инкапсуляции и жизненного цикла (Side Effects)**
Метод `changeEmail` делает скрытое действие — `flush()`. 
*   Это делает поведение сущности непредсказуемым. Разработчик, вызывая метод, может не ожидать, что в этот же момент произойдет тяжелый сетевой запрос к БД.
*   Это делает невозможным работу с агрегатом в памяти без немедленного сброса в базу. Например, если мне нужно изменить email и статус пользователя одновременно, мой код сделает два запроса к БД вместо одного, что неэффективно.

**4. Проблема тестирования**
Чтобы написать простой Unit-тест на смену email, мне теперь нужно создавать сложный мок для `EntityManager`. Это превращает легкие тесты в тяжеловесную процедуру.

---

### Как бы я это исправил?

В DDD сущность должна только менять свое внутреннее состояние. Ответственность за сохранение этого состояния должна лежать на **Repository** или **Application Service**.

#### Правильный вариант (Clean Architecture / DDD)

**1. Чистая доменная сущность:**
Она ничего не знает о базе данных.

```php
#[ORM\Entity]
class User
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(unique: true)]
    private string $email;

    public function __construct(string $email) 
    {
        // Здесь может быть валидация email
        $this->email = $email;
    }

    public function changeEmail(string $newEmail): void
    {
        // Валидация бизнес-правил (например, формат или запрет на повтор)
        if (!filter_var($newEmail, FILTER_VALIDATE_EMAIL)) {
            throw new \InvalidArgumentException("Invalid email format");
        }
        
        $this->email = $newEmail;
    }

    public function email(): string
    {
        return $this->email;
    }
    
    public function getId(): ?int
    {
        return $this->id;
    }
}
```

**2. Слой приложения (Use Case / Application Service):**
Здесь происходит оркестрация: получение объекта, изменение и сохранение.

```php
class ChangeEmailUseCase 
{
    public function __construct(
        private UserRepositoryInterface $repository, // Интерфейс из Domain слоя
        private EntityManagerInterface $entityManager // Инфраструктура
    ) {}

    public function execute(int $userId, string $newEmail): void 
    {
        $user = $this->repository->findById($userId);
        
        if (!$user) {
            throw new UserNotFoundException();
        }

        // 1. Меняем состояние (в памяти)
        $user->changeEmail($newEmail);

        // 2. Сохраняем изменения (в БД) одним вызовом
        // Мы не вызываем flush() внутри сущности, мы делаем это здесь.
        $this->entityManager->flush();
    }
}
```

### Резюме изменений:
1.  **Убрал `EntityManager` из конструктора `User`.** Теперь сущность — это чистый PHP-объект.
2.  **Убрал `flush()` из метода `changeEmail`.** Теперь метод только меняет состояние. Сохранение — это ответственность вызывающего кода (Application Layer).
3.  **Разделил ответственность.** `User` отвечает за *правила* (валидность email), `Repository` — за *поиск*, `UseCase` — за *процесс* (координацию).

Теперь этот код легко тестировать, легко расширять и он не зависит от того, используете вы Doctrine, MySQL или просто массив в памяти.

#### Этап 1: Декомпозиция и локализация (30-60 мин)
Прежде чем лезть в документацию, я должен понять масштаб «бедствия».
* **Анализ симптомов:** Что именно не работает? Это ошибка в логах, падение производительности или неверный результат?
* **Изоляция:** Я стараюсь воспроизвести проблему в минимальном окружении (маленький скрипт или изолированный Unit-тест). Если я не могу воспроизвести баг — я не могу его починить.
Bloat (лишний код) или отсутствие нужных данных?

Если локализация пройдена, но решение не очевидно, я перехожу к фазе **Spike** (исследовательское прототипирование).
* **Формирование гипотез:** «Возможно, это проблема с кэшем?», «Возможно, это конфликт версий библиотек?».
* **Эксперименты:** Я пишу микро-код, который проверяет каждую гипотезу по очереди. Я не пишу основной код приложения, я пишу «грязные» скрипты для проверки предположений.
* **Документирование процесса:** Я записываю, что я уже попробовал и почему это не сработало. Это спасет меня от хождения по кругу и будет полезно для коллег.

Только после того, как я нащупал путь решения, я готов назвать сроки.
* **Оценка сложности:** Я оцениваю не только время на написание кода, но и время на написание тестов, ревью и деплой.
* **Коэффициент неопределенности:** Если технология совсем новая, я добавляю к оценке буфер (например, +30-50%).

---

### 2. Когда разбираться самому, а когда просить помощи?

Это вопрос **экономической целесообразности**. Я использую правило **«Часа»** и **«Прогресса»**.

#### Разбираться самому, если:
1. **Проблема в рамках моей компетенции:** Это просто новая библиотека, но принципы работы (например, HTTP-протокол или SQL) мне знакомы.
2. **Я нахожусь в фазе активного поиска:** Если я только начал и первые 30-60 минут я просто читаю документацию — это нормальный процесс обучения.
3. **У меня есть четкий план:** Я знаю, что именно я ищу, и мне просто нужно время, чтобы это реализовать.

#### Просить помощи (Escalation), если:
1. **Я застрял в «тупике» (Deadlock):** Я потратил более 1-2 часов на одну и ту же гипотезу, перепробовал все стандартные способы, но результат не меняется. Дальше я просто сжигаю время компании.
2. **Проблема инфраструктурная или системная:** Если баг связан с настройками сервера, доступами к БД или внутренними процессами компании, которые я не могу контролировать.
3. **Риск для продакшена:** Если я вижу, что проблема может привести к потере данных или падению системы, я немедленно сообщаю об этом, не пытаясь «починить втихую».
4. **Необходимость контекста:** Если проблема не в технологии, а в том, *почему бизнес-логика работает именно так*. Это вопрос к владельцу продукта или архитектору.

**Мой принцип:** Я не боюсь признать, что чего-то не знаю. Для меня **«быть полезным команде» важнее, чем «казаться умным инженером»**. Если я застрял — я иду к коллегам с четким отчетом: *"Я попробовал А, Б и В, вот что я увидел, я застрез в этой точке. Есть идеи?"*. Это превращает мой ступор в коллективное решение.

## Q30 · Процесс и рассуждение

**Интервьюер:** Ты пообещал сделать задачу к завтрашнему дню, но по ходу работы понял, что это два дня работы. Что делаешь?

**Кандидат:**

Это критический момент, который проверяет не только твою честность, но и твой профессионализм в управлении ожиданиями (Stakeholder Management). 

Худшее, что может сделать разработчик — это промолчать, надеяться на чудо, работать всю ночь и в итоге завтра утром сказать: «Я не успел». Это подрывает доверие к тебе как к специалисту и ломает планы всей команды (планирование релизов, тестов, деплоя).

Мой алгоритм действий: **«Раннее оповещение + аргументация + предложение альтернативы»**.

---

### 1. Сообщаю как можно раньше (Early Warning)
Как только я понял, что оценка неверна, я немедленно сообщаю об этом. Не жду дедлайна. Чем раньше я скажу, тем больше у менеджера будет времени перестроить планы.

### 2. Объясняю причину (The "Why")
Я не говорю «я не успеваю». Я объясняю, **почему** оценка изменилась. Важно разделять «я медленно кодил» и «объем задачи оказался больше».

*   **Плохо:** «Я не успеваю, задача сложнее, чем казалось». (Это звучит как оправдание).
*   **Хорошо:** «При реализации я обнаружил, что текущая структура базы данных не поддерживает новый тип связи, о котором мы говорили. Мне нужно либо провести миграцию, либо переписать логику репозитория. Это добавит еще один рабочий день».

### 3. Предлагаю варианты решения (Options)
Я никогда не прихожу с проблемой без предложений. Я даю менеджеру выбор, чтобы он мог принять решение на основе бизнес-приоритетов.

**Вариант А: "Сделать всё, но позже" (Quality First)**
«Если мы сделаем задачу полностью, включая рефакторинг базы, мне понадобится еще один день. Это будет надежное решение, которое не создаст проблем в будущем».

**Вариант Б: "Сделать часть, но сейчас" (Scope Cutting)**
«Если нам критично выкатить задачу завтра, я могу реализовать основную логику, но без [второстепенной фичи/автоматических тестов/красивого UI]. Это позволит закрыть задачу в срок, но создаст небольшой технический долг, который мы закроем в следующем спринте».

**Вариант В: "Делегирование/Помощь"**
«Если задача приоритетна на завтра, возможно, кто-то из команды сможет помочь мне с написанием тестов или документацией, чтобы я успел завершить ядро?».

---

### Мой идеальный сценарий (Пример сообщения в Slack/Jira)

> «Привет, [Имя Менеджера]!

2.  **Я проявляю экспертность:** Я не просто «не успел», я нашел скрытую техническую проблему и предложил пути её решения.
3.  **Я передаю ответственность за бизнес-решение менеджеру:** Я даю ему данные (цена vs качество), а он принимает решение, исходя из стратегии компании. Это и есть профессиональное взаимодействие.

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

Это один из самых сложных вопросов в инженерии, потомуPer, потому что здесь нет математической формулы. Это вопрос **экономики разработки**. 

Если ты будешь бесконечно улучшать код, ты никогда не выпустишь продукт (Overengineering). Если ты будешь выпускать «грязный» код, ты быстро утонешь в техническом долге и багах (Technical Debt).

Мой подход базируется на концепции **«Достаточной чистоты» (Sufficient Cleanliness)** и управлении рисками.

---

### 1. Критерии «Достаточно хорошего кода» (Definition of Done)

Я считаю код готовым к отдаче, когда он соответствует трем уровням:

1.  **Функциональная корректность:** Он решает бизнес-задачу и проходит все Acceptance Criteria.
2.  **Безопасность и надежность:** В нем нет критических уязвимостей (SQLi, XSS) и он покрыт базовыми тестами (Unit/Integration), чтобы при следующем изменении мы не «сломали» это место.
3.  **Читаемость и поддерживаемость:** Код не должен быть «гениальным» или «заковыристым». Он должен быть настолько простым, чтобы другой разработчик мог понять его за 5 минут. Если я вижу, что код слишком переусложнен — я возвращаюсь и упрощаю.

**Если код соответствует этим пунктам, он «достаточно хорош» для продакшена.**

---

###  la 2. Когда стоит продолжать улучшать?

Я продолжаю рефакторинг только в двух случаях:

1.  **Правило бойскаута (Boy Scout Rule):** Если я нахожу в процессе работы над задачей мелкий, некритичный, но явный «грязевой» участок (плохое имя переменной, дублирование кода), я исправляю его сразу. Это микро-инвестиции в качество.
2.  **Критический технический долг:** Если я вижу, что текущая реализация создает «бутылочное горлышко» (например, отсутствие индекса, который приведет к падению базы через месяц), я поднимаю этот вопрос перед командой.

---

### 3. Как я соблюдаю баланс (Стратегия)

Чтобы не превратиться в «вечного рефактора», я использую следующие инструменты:

#### А. Оценка стоимости (Cost of Change vs. Cost of Delay)
Перед тем как начать глубокий рефакторинг, я спрашиваю себя:
*   *Сколько времени я потрачу на улучшение?*
*   *Насколько это ускорит разработку в будущем?*
*   *Что будет, если я сделаю это позже?*

Если я трачу 2 дня на рефакторинг части, которая меняется раз в год — это **плохая инвестиция**. Если я трачу 2 дня на рефакторинг ядра системы, которое меняется каждый день — это **хорошая инвестиция**.

#### Б. Управление техническим долгом (Debt Management)
Я отношусь к техническому долгу как к кредиту. Кредит — это нормально, если ты понимаешь, как его отдавать.
*   Если мы сознательно идем на «грязное» решение, чтобы успеть к релизу (Time-to-market), я **обязательно** создаю тикет в бэклоге (Technical Debt Ticket).
*   Я не позволяю техдолгу накапливаться бесконтрольно. В каждом спринте я стараюсь выделять 10-20% времени на работу с этим бэклогом.

#### В. Использование метрик
Я опираюсь на факты, а не на ощущения:
*   Если количество багов в модуле растет — значит, код там стал слишком сложным, пора рефакторить.
*   Если время прохождения тестов или время выполнения запросов растет — пора оптимизировать.

### Резюме

Мой баланс — это **прагматизм**. 

*   **Код должен быть чистым настолько, чтобы быть безопасным и понятным.**
*   **Код не должен быть идеальным настолько, чтобы мешать бизнесу зарабатывать деньги.**

Я не стремлюсь к "идеальному коду", я стремщусь к **"предсказуемому и поддерживаемому коду"**.
