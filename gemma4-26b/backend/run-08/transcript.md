**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

### Рассуждение

Когда интервьюер задает такой вопрос, он хочет проверить не то, помню ли я названия новых фич (это можно подсмотреть в changelog), а понимаю ли я, **какую инженерную проблему каждая из них решает**. 

Для меня «чистый и надёжный код» — это код, который:
1. Имеет предсказуемое поведение (строгая типизация).
2. Минимизирует количество boilerplate-кода (лаконичность).
3. Избавляет от лишних проверок на `null` (безопасность).
4. Ясно выражает намерения разработчика (читаемость).

Я выберу следующие возможности:
* **Constructor Property Promotion** — для уменьшения шума в DTO и сервисах.
* **Union Types & Intersection Types** — для точного описания контрактов.
* **Nullsafe Operator** — для борьбы с «пирамидой ада» из `if (is_null(...))`.
* **Match Expression** — как более безопасная и строгая альтернатива `switch`.
* **Readonly Properties/Classes** — для обеспечения иммутабельности (важно для DDD).
* **Attributes** — для декларативного описания метаданных вместо аннотаций в комментариях.

Я проигнорирую такие вещи, как JIT или Fiber, так как они относятся к производительности и асинхронности, а не напрямую к «чистоте и надёжности» архитектуры кода.

---

### Ответ

Я выделяю несколько ключевых нововведений, которые радикально изменили то, как мы описываем структуру данных и бизнес-логику, делая код более декларативным и менее склонным к ошибкам типа "undefined property" или "null pointer exception".

#### 1. Constructor Property Promotion и Readonly Properties
В связке с PHP 8.1 это позволяет создавать неизменяемые (immutable) объекты с минимальным количеством кода. В DDD это критично для Value Objects и DTO. Раньше нам приходилось дублировать свойства в объявлении, в конструкторе и при присваивании.

```php
// Было (PHP 7.4)
class UserDto {
    public string $name;
    public int $age;
    public function __construct(string $name, int $age) {
        $this->name = $name;
        $this->age = $age;
    }
}

// Стало (PHP 8.1+)
readonly class UserDto {
    public function __construct(
        public string $name,
        public int $age,
    ) {}
}
```
*Результат: Код стал чище, а риск случайно изменить состояние объекта (side-effect) сведен к нулю.*

#### 2. Union Types и Nullsafe Operator
Типизация стала намного точнее. Мы можем явно сказать, что метод возвращает либо объект, либо ничего, а оператор `?->` позволяет безопасно проходить по цепочке вызовов.

```php
// Вместо громоздких проверок:
// if ($user !== null && $user->getAddress() !== null) { ... }

// Используем Nullsafe:
$city = $user?->getAddress()?->getCity()?->getName();

// А Union Types гарантируют, что мы обрабатываем все возможные варианты:
/** @param string|int $identifier */
public function findByIdentifier(string|int $identifier): void {
    // ...
}
```
*Результат: Снижается когнитивная нагрузка и количество потенциальных runtime-ошибок.*

#### 3. Match Expression
В отличие от `switch`, `match` является выражением (возвращает значение) и выполняет строгое сравнение (`===`). Это избавляет от классических ошибок, когда забыли написать `break`.

```php
// switch часто приводил к логическим ошибкам из-за отсутствия break
// match заставляет нас быть явными

$status = $order->getStatus();

$message = match ($status) {
    Status::New => 'Order is created',
    Status::Paid => 'Payment received',
    Status::Shipped => 'On the way',
    default => throw new \Exception("Unknown status"),
};
```
*Результат: Код становится более предсказуемым и безопасным (exhaustive checking).*

#### 4. Attributes
Переход от DocBlock-аннотаций к атрибутам сделал метаданные частью языка, а не просто комментариями, которые парсятся через Reflection API. Это позволило сделать интеграцию с Doctrine и Symfony более нативной и менее подверженной опечаткам в комментариях.

```php
// Раньше (Annotation)
/** @ORM\Column(type="string") */
private $name;

// Сейчас (Attribute)
#[ORM\Column(type: 'string')]
private string $name;
```
*Результат: Инструменты статического анализа (PHPStan/Psalm) гораздо лучше работают с атрибутами, что повышает надёжность.*

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

### Рассуждение

Этот вопрос — классическая проверка на «глубину погружения». Интервьюер хочет увидеть, понимает ли разработчик разницу между тем, как PHP работает «под капотом» (weak typing), и тем, как мы заставляем его работать в профессиональных проектах (strict typing).

Мне нужно разобрать три аспекта:
1. **Механизм приведения типов (Coercive mode):** Как PHP по умолчанию пытается «помочь» разработчику, превращая строки в числа и т.д.
2. **Strict Types:** Что именно меняет директива `declare(strict_types=1);` (спойлер: она влияет только на вызовы функций в текущем файле).
3. **Ловушки:** Здесь я должен упомянуть нюансы с `null`, работу со значениями `0` vs `false` vs `""`, и то, как типизация ведет себя при наследовании.

Я также должен предостеречь интервьюера: многие думают, что `strict_types=1` делает всё приложение строго типизированным. Это не так. Это работает локально для файла, где объявлена директива. Если я вызываю функцию из файла *без* этой директивы, приведение типов всё равно произойдет.

---

### Ответ

Система типов в PHP — это гибридная модель. По умолчанию она работает в режиме **coercive mode** (приведение типов), но мы можем переключить её в **strict mode**.

#### 1. Coercive Mode (Поведение по умолчанию)
Если директива `strict_types` не указана, PHP пытается привести аргумент к требуемому типу, если это «безопасно» (не теряя данных в некоторых контекстах, но на деле он очень гибкий).

```php
function add(int $a, int $b): int {
    return $a + $b;
}

echo add(5, "10"); // Выведет 15. PHP молча превратил строку "10" в int.
echo add(5, 10.5); // Выведет 15. PHP отбросил дробную часть (float -> int).
```
Это удобно для быстрых скриптов, но опасно для бизнес-логики, так как ошибки в данных (например, пришедшая из API строка вместо числа) замалчиваются.

#### 2. Strict Mode (`declare(strict_types=1);`)
Когда мы добавляем эту директиву в начало файла, PHP перестает «угадывать». Если тип не совпадает идеально — выбрасывается `TypeError`.

**Важный нюанс:** Директива действует на **вызов** функции из текущего файла.
* Если в `file_a.php` стоит `strict_types=1` и он вызывает `func(1, "2")`, будет ошибка.
* Если в `file_a.php` **нет** `strict_types=1` и он вызывает `func(1, "2")`, PHP всё равно приведёт типы, даже если внутри `func` стоит строгая типизация.

#### 3. Типичные ловушки

**Ловушка №1: Nullability**
Самая частая причина `TypeError`. Если тип указан как `string`, а не `?string`, передача `null` уронит приложение.
```php
function setName(string $name): void {}

setName(null); // Fatal error: Argument 1 must be of type string, null given
```

**Ловушка №2: Слабое сравнение в логике**
Хотя это не совсем про систему типов функций, это про то, как типы ведут себя в условиях.
```php
$value = "0";
if ($value) { /* Это условие НЕ выполнится, так как "0" приводится к false */ }
```

**Ловушка №3: Наследование (Covariance & Contravariance)**
PHP позволяет сужать тип возвращаемого значения (covariance), но запрещает расширять тип аргумента (contravariance) в старых версиях (хотя с PHP 7.4+ правила стали гибче). Ошибка в проектировании интерфейсов здесь — классика.

#### 4. Примеры: где спасает, а где удивляет

**Где спасает:**
Типизация спасает нас от "silent failures" (тихих ошибок). В финтех-проектах, если в метод `transfer(int $amount)` придет строка `"100.50"`, в обычном PHP она превратится в `100` (потеря 50 центов без ошибки). В `strict_types` это сразу вызовет исключение, и мы поймаем баг на этапе интеграции, а не когда деньги пропадут со счета.

**Где удивляет:**
Удивляет работа с `float` и `int`. Из-за особенностей представления чисел с плавающей точкой, попытка передать `int` туда, где ожидается `float` (или наоборот в строгом режиме), может вести себя контринтуитивно при сложных вычислениях.

Также удивляет "магия" приведения типов в `match` (который использует строгое сравнение `===`) против `switch` (который использует слабое `==`).

```php
$val = "5";

// switch сравнивает слабо
switch ($val) {
    case 5: echo "Match!"; break; // Сработает!
}

// match сравнивает строго
match ($val) {
    5 => "Match!", // Error: Argument 1 must be string, int given (или наоборот)
    default => "No match",
};
```

**Итог:** Для чистого кода я всегда использую `declare(strict_types=1);` во всех файлах проекта. Это делает контракт между компонентами явным и заставляет разработчика обрабатывать типы данных на входе (например, через DTO или валидацию), а не полагаться на магию PHP.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

### Рассуждение

Вопрос об исключениях — это вопрос о **стратегии обработки ошибок** и **дизайне API**. Плохая обработка исключений приводит либо к «проглатыванию» ошибок (silent failures), либо к «взрыву» приложения там, где пользователь должен был получить понятное сообщение.

При проектировании я опираюсь на следующие принципы:
1.  **Разделение типов ошибок:** Я разделяю ошибки, которые являются следствием программных багов (Logical Exceptions), и ошибки, которые являются частью бизнес-процесса (Domain/Runtime Exceptions).
2.  **Иерархия:** Исключения не должны быть плоскими. У каждого слоя должна быть своя ветка иерархии.
3.  **Контракт:** Метод обязан «предупреждать» о том, что он может выбросить. Если метод может выбросить `UserNotFoundException`, это часть его публичного интерфейса.
4.  **Оборачивание (Wrapping):** Это критический момент для сохранения контекста. Если база данных упала, мы не должны прокидывать `PDOException` на уровень контроллера. Мы должны обернуть её в `InfrastructureException` или `RepositoryException`, сохранив оригинальный `previous exception`.

Я должен упомянуть, что использование исключений для управления потоком выполнения (Flow Control) — это плохая практика. Исключение — это *исключительная* ситуация, а не ожидаемый результат ветвления `if/else`.

---

### Ответ

Проектирование обработки ошибок для меня — это создание системы, которая делает состояние приложения предсказуемым даже в случае сбоя.

#### 1. Иерархия исключений
Я строю иерархию, исходя из слоев архитектуры. Это позволяет на разных уровнях приложения по-разному реагировать на ошибки.

*   **Domain Layer:** Здесь живут `DomainException` (наследники `\LogicException`). Это ошибки, которые можно исправить только изменением кода или логики (например, `InvalidOrderStateException`). Они сигнализируют о нарушении инвариантов сущности.
*   **Application Layer:** Здесь живут исключения, связанные с бизнес-сценариями, например, `UserNotFoundException` или `InsufficientFundsException`. Это часто `RuntimeException`, так как они зависят от внешних данных.
*   **Infrastructure Layer:** Исключения для внешних систем (API, DB, Filesystem).

#### 2. Контракт метода
Контракт метода — это не только типы аргументов и возвращаемое значение, но и **набор исключений, которые он может выбросить**. 

В PHP нет механизма `throws` в синтаксисе, который бы заставлял компилятор проверять исключения (как в Java), поэтому я использую **PHPDoc** (`@throws`). Для меня это не просто комментарий, а обязательство. Если я пишу интерфейс репозитория, я обязан указать, что он может выбросить `RepositoryException`. Это дает понять вызывающему коду, что он *должен* подготовить `try-catch` блок.

#### 3. Оборачивание (Exception Wrapping)
Это золотое правило при работе с внешними зависимостями. Мы никогда не пробрасываем низкоуровневые исключения сквозь слои.

**Плохо:**
```php
public function getUser(int $id): User {
    // Если здесь упадет PDOException, контроллер узнает слишком много о реализации БД
    return $this->db->fetchOne("SELECT...", [$id]); 
}
```

**Хорошо:**
```php
public function getUser(int $id): User {
    try {
        return $this->db->fetchOne("SELECT...", [$id]);
    } catch (PDOException $e) {
        // Мы оборачиваем ошибку, сохраняя оригинальный контекст через $e
        throw new RepositoryException("Failed to fetch user with id $id", 0, $e);
    }
}
```
*Результат: Слой приложения работает с абстракциями, а не с деталями реализации.*

#### 4. Антипаттерны

*   **Empty Catch Block (Поглощение ошибки):**
    ```php
    try {
        $this->doSomething();
    } catch (\Exception $e) {
        // Ничего не делаем — это катастрофа. Ошибка исчезла бесследно.
    }
    ```
*   **Использование исключений для управления логикой (Flow Control):**
    Использовать `UserNotFoundException` для того, чтобы просто проверить, существует ли пользователь в цикле — это очень дорого по ресурсам (создание Stack Trace) и делает код запутанным. Для этого есть `null` или специальные Result-объекты.
*   **Catching `\Throwable` или `\Exception` слишком высоко:**
    Попытка поймать вообще всё на уровне сервиса делает невозможным точечное реагирование на конкретные ошибки. Мы ловим только то, что можем обработать.
*   **Слишком общие сообщения:**
    Бросать `new \Exception("Error occurred")`. Это бесполезно для отладки. Исключение должно содержать контекст: *что* произошло, *почему* и *с какими данными*.

**Мой подход:** Исключение должно быть максимально информативным, находиться на своем уровне иерархии и всегда сохранять цепочку первопричины (`previous`).

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

### Рассуждение

Когда говорят о SOLID, новички часто начинают с **Single Responsibility Principle (SRP)**, и технически они правы — это самый популярный нарушаемый принцип. Однако, как инженер с 15-летним стажем, я вижу, что самая «болезненная» и глубокая проблема в архитектуре — это нарушение **Dependency Inversion Principle (DIP)**.

Почему я считаю DIP более критичным? 
1. Нарушение SRP делает класс «толстым», но это можно исправить рефакторингом внутри одного модуля. 
2. Нарушение DIP (когда высокоуровневые модули зависят от низкоуровневых деталях реализации) делает систему **жесткой (rigid)** и **хрупкой (fragile)**. Это превращает проект в монолит, где невозможно заменить одну библиотеку или базу данных, не переписывая половину приложения.

Часто разработчики путают «использование класса» с «зависимостью от реализации». Они не используют интерфейсы там, где это необходимо для абстракции, и в итоге получают код, который невозможно тестировать юнит-тестами (потому что нельзя подменить реальный сервис моком без сложного хака).

Я продемонстрирую нарушение DIP через типичный кейс: сервис, который жестко завязан на конкретную реализацию отправки уведомлений через сторонний API.

---

### Ответ

По моему опыту, чаще всего в реальных проектах страдает **Dependency Inversion Principle (DIP)**. 

Разработчики часто пишут код, который «просто работает», создавая прямые зависимости от конкретных классов (реализаций), вместо того чтобы зависеть от абстракций (интерфейсов). Это приводит к тому, что бизнес-логика становится заложником инфраструктурных решений.

#### Типовое нарушение (DIP)

Представим сервис регистрации пользователя, который жестко привязан к сервису отправки Email через конкретный провайдер (например, Mailchimp).

```php
// Низкоуровневая реализация (деталь)
class MailchimpMailer {
    public function sendEmail(string $to, string $body): void {
        // Логика работы с API Mailchimp
        echo "Sending via Mailchimp to $to";
    }
}

// Высокоуровневый модуль (бизнес-логика)
class UserRegistrationService {
    private MailchimpMailer $mailer; // ОШИБКА: Зависимость от конкретного класса!

    public function __construct(MailchimpMailer $mailer) {
        $this->mailer = $mailer;
    }

    public function register(string $email): void {
        // Логика регистрации...
        $this->mailer->sendEmail($email, "Welcome!");
    }
}
```

**Почему это плохо?**
1. **Невозможность тестирования:** Я не могу протестировать `UserRegistrationService` без реального (или имитированного через сложные костыли) `MailchimpMailer`.
2. **Жесткая связность:** Если завтра бизнес скажет: «Переходим на SendGrid», мне придется менять код в `UserRegistrationService`.
3. **Нарушение тестов:** Мои юнит-тесты на бизнес-логику будут зависеть от стороннего сервиса.

#### Рефакторинг (Применение DIP)

Мы должны внедрить абстракцию (интерфейс), чтобы высокоуровневый модуль не знал о деталях реализации.

```php
// 1. Создаем абстракцию (Интерфейс)
interface MailerInterface {
    public function sendEmail(string $to, string $body): void;
}

// 2. Реализуем конкретный сервис (деталь реализации)
class MailchimpMailer implements MailerInterface {
    public function sendEmail(string $to, string $body): void {
        echo "Sending via Mailchimp to $to";
    }
}

// 3. Другая реализация (легко добавляется)
class SendGridMailer implements MailerInterface {
    public function sendEmail(string $to, string $body): void {
        echo "Sending via SendGrid to $to";
    }
}

// 4. Высокоуровневый модуль теперь зависит от интерфейса
class UserRegistrationService {
    private MailerInterface $mailer; // ТЕПЕРЬ ЗАВИСИМ ОТ АБСТРАКЦИИ

    public function __construct(MailerInterface $mailer) {
        $this->mailer = $mailer;
    }

    public function register(string $email): void {
        // Логика регистрации...
        $this->mailer = $this->mailer;
        $this->mailer->sendEmail($email, "Welcome!");
    }
}

// Использование через DI-контейнер (Symfony/Laravel делают это автоматически)
$service = new UserRegistrationService(new MailchimpMailer());
$service->register('test@example.com');

// Легко меняем поведение без изменения бизнес-логики:
$serviceWithSendGrid = new UserRegistrationService(new SendGridMailer());
```

**Что изменилось?**
* **Тестируемость:** Теперь я могу легко создать `MockMailer implements MailerInterface` и проверить регистрацию пользователя, не отправляя реальных писем.
* **Гибкость:** Бизнес-логика (регистрация) теперь полностью изолирована от инфраструктуры (отправка почты).
* **Масштабируемость:** Добавление новых способов уведомления (SMS, Telegram) больше не требует изменения существующего кода `UserRegistrationService`.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

### Рассуждение

Этот вопрос проверяет мою зрелость как инженера. На собеседованиях часто пытаются получить «правильный» ответ: «Нет, принципы SOLID — это закон». Но опытный разработчик знает, что в реальном мире существует понятие **Trade-off** (компромисс). 

Любое архитектурное решение — это выбор между скоростью разработки, стоимостью поддержки, производительностью и сложностью. SOLID — это набор инструментов для борьбы с энтропией (усложнением) кода. Если внедрение этих инструментов создает больше проблем, чем оно решает, то применение этих принципов становится **overengineering** (избыточным проектированием).

Я должен выделить три контекста, где нарушение SOLID оправдано:
1. **Time-to-Market (MVP):** Когда нужно проверить гипотезу «вчера».
2. **Прототипирование:** Когда архитектура еще не ясна и будет полностью переписана.
3. **Сверхмалые или высокопроизводительные системы:** Где абстракции (интерфейсы, DI-контейнеры, лишние слои) создают неприемлемые накладные расходы (overhead).

Я не буду говорить, что «нарушать — это нормально». Я скажу, что «нарушать — это осознанный инженерный выбор с пониманием последствий».

---

### Ответ

Короткий ответ: **Да, можно. И профессионал должен это уметь делать осознанно.**

SOLID — это не священное писание, а набор эмпирических правил, которые помогают бороться со сложностью. Но если цена борьбы со сложностью выше, чем сама сложность, мы нарушаем принципы. 

Я выделяю три основные ситуации, когда нарушение SOLID оправдано:

#### 1. Создание MVP (Minimum Viable Product)
Если стартапу нужно проверить гипотезу за две недели, чтобы не обанкротиться, я не буду строить идеальную многослойную архитектуру с соблюдением всех принципов DIP и ISP.

*   **Пример:** Я могу написать один «толстый» контроллер, который напрямую работает с базой данных и отправляет письма через жестко прописанный класс. 
*   **Риск:** Технический долг. 
*   **Оправдание:** Скорость выхода на рынок. Мы осознанно принимаем решение: «Мы напишем плохой код сейчас, чтобы выжить, но мы заложим время на рефакторинг, когда получим первую прибыль».

#### 2. Прототипирование и исследовательская работа (Spike)
Когда команда делает «Spike» — исследование новой технологии или метода, цель — получить знание, а не продукт.

*   **Пример:** Мы тестируем, подходит ли новая библиотека для обработки изображений. Я напишу быстрый скрипт, нарушая SRP и чистую архитектуру, чтобы просто увидеть, как библиотека ведет себя под нагрузкой.
*   **Оправдание:** Скорость получения обратной связи. Строить здесь слои абстракций — значит тратить время на создание структуры, которую мы, скорее всего, выбросим через два дня.

#### 3. Высокопроизводительные (Low-latency) системы
В некоторых случаях абстракции имеют цену в виде тактов процессора или потребления памяти.

*   **Пример:** Если мы пишем критический узел обработки данных, где важна каждая микросекунда, я могу отказаться от использования интерфейсов и DI-контейнеров в пользу жестких связей и конкретных реализаций, чтобы избежать лишних вызовов методов через таблицу виртуальных функций (vtable) и снизить нагрузку на CPU/Memory.
*   **Оправдание:** Производительность. Здесь нарушение принципов — это оптимизация.

### Резюме

Главное отличие между **плохим разработчиком** и **опытным инженером** при нарушении принципов заключается в следующем:

1.  **Плохой разработчик** нарушает принципы по незнанию, по лени или из-за неумения. Он создает «спагетти-код» и считает, что всё в порядке.
2.  **Опытный инженер** нарушает принципы **осознанно**. Он понимает, что делает, он осознает, какой технический долг он накапливает, и он может объяснить бизнесу, почему сейчас мы выбрали путь «быстро и грязно», а не «медленно и идеально».

**Мой девиз:** «Не усложняй там, где это не нужно, но и не упрощай там, где это убьет систему».

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

### Рассуждение

Этот вопрос — классическая ловушка на проверку того, понимает ли разработчик суть принципа **Open/Closed Principle (OCP)**. 

Часто новички думают, что OCP — это синоним полиморфизма через наследование (extends). Однако наследование в современном ООП (особенно в PHP) часто является «плохим» инструментом из-за жесткой связи (tight coupling) и проблемы «хрупкого базового класса» (fragile base class). 

Если мы говорим об OCP, мы говорим о возможности **расширять поведение системы без изменения её существующего кода**. 

Я выделю следующие способы реализации OCP, помимо классического наследования:
1. **Композиция (Composition over Inheritance):** Это база. Мы не наследуем поведение, а внедряем его.
2. **Интерфейсы и Полиморфизм (Contract-based):** Это то, что позволяет композиции работать.
3. **Паттерны проектирования:** 
    * **Strategy (Стратегия):** Позволяет менять алгоритм на лету.
    * **Decorator (Декоратор):** Позволяет динамически добавлять обязанности объекту.
    * **Observer (Наблюдатель):** Позволяет добавлять новые действия при наступлении события без изменения самого события.
    * **Visitor (Посетитель):** Позволяет добавлять новые операции к структурам объектов, не меняя сами структуры.
4. **Плагинная архитектура / Событийная модель (Event-driven):** Использование хуков или системы событий (как в Symfony Messenger или WordPress).

Я разберу самые практичные для PHP-разработчика способы: композицию через стратегии и декораторы.

---

### Ответ

Наследование — это лишь один из (и далеко не самый лучший) способов реализации OCP. В современной разработке на PHP мы стремимся к **композиции**, так как она обеспечивает более слабую связность.

Вот основные способы реализации OCP без использования `extends`:

#### 1. Паттерн «Стратегия» (Composition + Interface)
Это самый распространенный способ. Вместо того чтобы расширять класс, мы выносим изменяющееся поведение в отдельный объект, реализующий интерфейс, и внедряем его через конструктор.

```php
// Вместо наследования: class DiscountedOrder extends Order...

interface DiscountStrategy {
    public function apply(float $price): float;
}

class BlackFridayDiscount implements DiscountStrategy {
    public function apply(float $price): float { return $price * 0.5; }
}

class NoDiscount implements DiscountStrategy {
    public function apply(float $price): float { return $price; }
}

class Order {
    public function __construct(
        private float $price,
        private DiscountStrategy $discountStrategy // Зависим от абстракции
    ) {}

    public function getTotal(): float {
        return $this->discountStrategy->apply($this->price);
    }
}

// Мы можем добавлять любые новые скидки, НЕ меняя класс Order.
```

#### 2. Паттерн «Декоратор» (Wrapper)
Декоратор позволяет «оборачивать» существующий объект, добавляя ему новую функциональность, не меняя его исходный код и не создавая сложную иерархию наследования.

```php
interface Logger {
    public function log(string $message): void;
}

class FileLogger implements Logger {
    public function log(string $message): void {
        echo "Logging to file: $message\n";
    }
}

// Декоратор добавляет функциональность (например, отправку в Slack)
class SlackLoggerDecorator implements Logger {
    public function __construct(private Logger $wrappedLogger) {}

    public function log(string $message): void {
        $this->wrappedLogger->log($message); // Вызываем основной логгер
        echo "Sending to Slack: $message\n"; // Добавляем новое поведение
    }
}

// Использование:
$logger = new SlackLoggerDecorator(new FileLogger());
$logger->log("System error!");
```

#### 3. Событийная модель (Observer / Event Dispatcher)
Это способ реализации OCP на уровне архитектуры приложения. Вместо того чтобы вписывать вызов стороннего сервиса в бизнес-логику, мы просто генерируем событие.

```php
// В методе регистрации пользователя:
public function register(User $user): void {
    $this->repository->save($user);
    
    // Мы просто говорим "пользователь зарегистрирован".
    // Мы не знаем, кто на это отреагирует (Email, SMS, Analytics).
    // Мы не меняем этот метод, когда добавляем новый слушатель.
    $this->eventDispatcher->dispatch(new UserRegisteredEvent($user));
}
```
Здесь система открыта для новых подписчиков (расширение), но закрыта для изменений в методе `register` (изменение существующего кода).

#### 4. Паттерн «Визитор» (Visitor)
Используется, когда у вас есть сложная структура объектов, и вы хотите добавлять новые операции над ними, не меняя классы самих объектов. Это позволяет реализовать OCP для операций, а не для типов данных.

**Итог:** 
Если наследование — это связь **"является" (is-a)**, то основные способы реализации OCP через композицию — это связь **"имеет" (has-a)**. Именно композиция через интерфейсы, стратегии, декораторы и события делает систему по-настоящему гибкой и расширяемой.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

### Рассуждение

Этот вопрос — классическая проверка на понимание того, что такое «единая ответственность». Если человек отвечает «да, только к классам», это сигнал, что он воспринимает SRP как правило именования или оформления кода, а не как архитектурный принцип.

Мне нужно прояснить: **SRP — это принцип дизайна, а не правило синтаксиса.** Его суть в том, что «у модуля (компонента) должна быть только одна причина для изменения». 

Я разберу, на каких уровнях можно встретить нарушение SRP:
1. **Уровень функций/методов:** Слишком длинные функции, делающие всё подряд.
2. **Уровень классов:** (то, о чем спрашивает интервьюер) — «Божественные объекты».
3. **Уровень модулей/пакетов/микросервисов:** Когда один микросервис отвечает и за биллинг, и за каталог товаров, и за уведомления.
4. **Уровень файлов/модулей системы сборки:** Когда один файл конфигурации или один скрипт сборки превращается в нечитаемый монстр.

Я должен подчеркнуть, что «ответственность» в контексте SRP — это не про «что делает этот объект», а про «кто является его заказчиком (stakeholder) и чьи интересы он представляет».

---

### Ответ

Нет, **SRP не ограничивается только классами**. 

Принцип единственной ответственности применим к любому уровню абстракции в проектировании системы. Если мы сузим его только до классов, мы упустим огромный пласт проблем в архитектуре.

Вот уровни, на которых SRP проявляется в полной мере:

#### 1. Уровень функций и методов
Функция должна выполнять одну задачу. Если метод `processOrder()` внутри себя и валидирует данные, и считает скидку, и сохраняет в базу, и отправляет письмо — он нарушает SRP. 
* **Последствие:** Такой метод сложно тестировать, сложно переиспользовать и сложно изменять, не сломав соседние логические шаги.

#### 2. Уровень классов (классический подход)
Класс должен отвечать за одну область бизнес-логики или одну техническую задачу. 
* **Пример нарушения:** Класс `User`, который содержит и данные пользователя, и логику его авторизации, и методы для сохранения в базу данных (Active Record в его худшем проявлении).

#### 3. Уровень модулей и компонентов (Packages/Modules)
В современной разработке мы собираем систему из модулей. Если ваш модуль `Billing` одновременно отвечает за генерацию PDF-отчетов, обработку транзакций и управление подписками — он нарушает SRP на уровне архитектуры.
* **Последствие:** Изменение логики генерации PDF может случайно сломать процесс транзакции, так как они находятся в одном контексте (модуле).

#### 4. Уровень сервисов (Микросервисы)
Это самый высокий уровень. Если микросервис превращается в "Distributed Monolith" (распределенный монолит), где один сервис делает слишком много разнородных вещей, он нарушает SRP.
* **Пример:** Микросервис `OrderService`, который при поступлении заказа сам лезет в базу пользователей, сам дергает склад и сам управляет логистикой. Правильнее разбить его на `OrderService`, `InventoryService` и `ShippingService`.

#### 5. Уровень конфигурации и инфраструктуры
Даже на уровне DevOps это работает. Один огромный `docker-compose.yml` или один гигантский скрипт CI/CD, который делает и тесты, и сборку, и деплой, и проверку безопасности — это нарушение SRP.

### Важное уточнение про "Причину для изменения"
Чтобы правильно применять SRP на любом уровне, нужно использовать определение от Роберта Мартина: **«Ответственность — это причина для изменения»**.

Если у вас есть компонент (будь то метод, класс или микросервис), и изменения, продиктованные отделом маркетинга (изменился формат письма), заставляют вас менять тот же самый код, который меняет отдел бухгалтерии (изменился расчет налога) — вы нарушили SRP, независимо от того, является этот компонент классом или целым облачным сервисом.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

### Рассуждение

Это вопрос уровня Senior, который проверяет понимание не просто «как пользоваться Symfony», а как она работает «под капотом». Здесь важно не свалиться в описание использования `services.yaml`, а объяснить жизненный цикл контейнера.

Я разделю ответ на три четких этапа, как и просил интервьюер:
1. **Compile Time (Компиляция):** Это критически важный этап. Нужно объяснить, что контейнер в Symfony — это не просто «хранилище объектов», а сгенерированный PHP-код. Я должен упомянуть `ContainerBuilder`, `CompilerPasses` и то, что происходит превращение конфигурации в оптимизированный PHP-класс.
2. **Autowiring:** Нужно объяснить, что это не «магия», а процесс сопоставления типов (type-hinting) с ID сервисов, который происходит именно на этапе компиляции.
3. **Runtime (Request time / Lazy Loading):** Нужно объяснить разницу между созданием контейнера и созданием конкретного объекта. Ключевое слово здесь — **Lazy Loading** и то, что объекты создаются только в момент обращения к ним.

Я также должен уточнить, что контейнер в Symfony — это **Compiled Container**. Это не динамический реестр (как в некоторых других фреймворках), а жестко оптимизированная структура.

---

### Ответ

В Symfony DI-контейнер (Dependency Injection Container) — это не просто массив объектов. Это сложная система, которая проходит через два принципиально разных жизненных цикла: **этап сборки (компиляции)** и **этап выполнения (runtime)**.

#### 1. Этап компиляции (Compile Time)
Когда вы очищаете кэш или запускаете приложение в режиме `dev`, Symfony начинает собирать контейнер. Это происходит один раз и результат кэшируется.

*   **Загрузка конфигурации:** `ContainerBuilder` собирает все определения сервисов из `services.yaml`, атрибутов, аннотаций и конфигураций бандлов. На этом этапе у нас есть «чертежи» сервисов (Service Definitions), но не сами объекты.
*   **Compiler Passes (Проходы компилятора):** Это «мозг» контейнера. Symfony запускает цепочку специальных классов (CompilerPasses), которые модифицируют эти чертежи. Например:
    *   Они находят все сервисы, помеченные определенным тегом (например, `kernel.event_listener`).
    *   Они могут удалять неиспользуемые сервисы (optimization).
    *   Они могут подменять одну реализацию другой (например, если вы переопределили сервис в `test` окружении).
*   **Генерация кода (Dump):** После всех проходов Symfony берет итоговую карту зависимостей и **генерирует чистый PHP-класс** (например, `App_KernelDevDebugContainer`). Этот класс содержит методы `getServiceName()`, которые жестко прописывают цепочки `new Service(...)`. Это делает работу контейнера невероятно быстрой, так как нет никакого парсинга конфигурации во время запроса.

#### 2. Как работает Autowiring
Autowwiring — это не магия во время выполнения, это **магия во время компиляции**.

Когда вы пишете `public function __construct(UserRepository $repository)`, Symfony во время компиляции делает следующее:
1. Использует Reflection API, чтобы прочитать `UserRepository` из вашего конструктора.
2. Ищет в уже собранном списке сервисов тот, чей ID или класс совпадает с `UserRepository`.
3. Если находит — он записывает в «чертеж» сервиса, который вы вызываете, инструкцию: «При создании этого сервиса, первым аргументом передай результат вызова метода `getUserRepository()`».

Если Symfony не может найти подходящий сервис или находит два подходящих (ambiguous), она выбросит исключение **на этапе компиляции**, а не во время работы приложения.

#### 3. Момент запроса сервиса (Runtime / Lazy Loading)
Когда в коде вызывается `$container->get(MyService::class)` (или, что чаще, когда сервис внедряется в контроллер), происходит следующее:

1. **Проверка кэша:** Контейнер проверяет, был ли этот объект уже создан (синглтон по умолчанию).
2. **Создание (Instantiation):** Если объект еще не создан, вызывается сгенерированный метод из скомпилированного класса.
3. **Разрешение зависимостей:** Этот метод начинает строить дерево зависимостей «снизу вверх». Если `MyService` требует `Logger`, контейнер сначала вызовет метод создания `Logger`.
4. **Lazy Loading:** Благодаря тому, что мы используем интерфейсы и автовайринг, объекты создаются **только тогда, когда они реально понадобились**. Если в вашем сервисе есть 10 зависимостей, но в конкретном запросе вы используете только 2, остальные 8 даже не будут инициализированы. 

*Примечание: Если сервис помечен как `lazy: true`, Symfony создаст вместо него «прокси-объект». Реальный объект будет создан только в тот момент, когда вы впервые вызовете у этого прокси любой метод.*

**Итог:** Symfony превращает декларативное описание (YAML/Attributes) в высокооптимизированный императивный PHP-код, перенося всю тяжелую работу по анализу типов и связей с момента запроса (Runtime) на этап сборки (Compile Time).

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

### Рассуждение

Вопрос о циклических зависимостях — это проверка на умение отличать «симптомы» от «болезни». 

С точки зрения архитектуры, циклическая зависимость (когда `ServiceA` требует `ServiceB`, а `ServiceB` требует `ServiceA`) — это **архитектурный провал**. Это сигнал о том, что ваши абстракции размыты, а границы ответственности (SRP) нарушены. Вместо двух независимых компонентов вы получили один неявный, запутанный монолит, который просто разбит на два файла.

Когда я сталкиваюсь с такой проблемой, я действую в три этапа:
1. **Диагностика:** Понять, почему они зависят друг от друга.
2. **Рефакторинг (правильный путь):** Исправить архитектуру.
3. **Обход (emergency/technical path):** Использовать инструменты контейнера, если рефакторинг невозможен прямо сейчас (но я всегда помечаю это как технический долг).

Я должен упомянуть три основных способа решения через рефакторинг:
* **Выделение третьего компонента (Extraction):** Вынос общей логики в `ServiceC`.
* **Инверсия зависимости (Interface Segregation):** Использование интерфейсов, чтобы разорвать прямую связь.
* **Пересмотр иерархии (Re-layering):** Перенос логики на более высокий уровень (Application Layer).

И я обязательно упомяну «костыли» в Symfony: `Lazy services` (через прокси) и `Setter injection`.

---

### Ответ

Я рассматриваю циклическую зависимость не как техническую ошибку контейнера, а как **архитектурный дефект**. Если `A` зависит от `B`, а `B` от `A`, значит, эти сервисы не являются независимыми модулями.

Вот мой алгоритм решения:

#### 1. Правильный путь: Рефакторинг архитектуры
Это то, что я делаю в первую очередь. Есть три проверенных метода:

*   **Метод «Третьего компонента» (Extraction):** 
    Если `ServiceA` и `ServiceB` оба нуждаются в методе `doSomething()`, который заставляет их зависеть друг от друга, я выделяю этот метод в новый `ServiceC`. Теперь и `A`, и `B` зависят от `C`, но не друг от друга. Это самый чистый способ.
    
*   **Разделение ответственности (Interface Segregation):**
    Часто цикл возникает потому, что `ServiceA` нужен только один маленький метод из `ServiceB`. В этом случае я выделяю нужный метод в отдельный интерфейс `SmallInterfaceB` и заставляю `ServiceB` его реализовать. Если это не помогает, значит, проблема глубже.

*   **Перенос логики на уровень выше (Orchestration):**
    Если `ServiceA` и `ServiceB` должны взаимодействовать, возможно, ими должен управлять «дирижер» — сервис более высокого уровня (например, в слое Application). Вместо того чтобы `A` вызывал `B`, я создаю `OrchestratorService`, который вызывает сначала `A`, а затем `B`.

#### 2. Путь «быстрого исправления» (Technical Debt)
Если проект огромный, рефакторинг всей логики сейчас невозможен (например, перед релизом), я использую возможности Symfony, чтобы «заглушить» проблему, но обязательно создаю задачу в бэклог на рефакторинг.

*   **Lazy Services (Proxy):** 
    В Symfony я могу пометить один из сервисов как `lazy`.
    ```yaml
    # services.yaml
    App\Service\ServiceA:
        lazy: true
    ```
    В этом случае контейнер не будет создавать реальный `ServiceA` при создании `ServiceB`. Вмем него будет создан «прокси-объект». Реальный объект будет инициализирован только в тот момент, когда вы впервые вызовете метод у этого прокси. Это разрывает цикл инициализации в рантайме.

*   **Setter Injection (вместо Constructor Injection):**
    Если я не могу использовать конструктор из-за цикла, я могу внедрить зависимость через сеттер.
    ```php
    class ServiceA {
        private ServiceB $serviceB;

        public function setServiceB(ServiceB $serviceB): void {
            $this->serviceB = $serviceB;
        }
    }
    ```
    Контейнер сначала создаст `ServiceA`, а потом вызовет сеттер, чтобы передать `ServiceB`. Это позволяет избежать бесконечной рекурсии при создании объектов.

**Мой вывод:** Я всегда стараюсь идти по пути **извлечения третьей зависимости** или **оркестрации**, так как это делает код чистым и понятным. Использование `lazy: true` или `setter injection` для меня — это «красный флаг», который сигнализирует о том, что архитектура требует внимания.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

### Рассуждение

Это классическая задача на проектирование **асинхронных процессов** и **событийно-ориентированной архитектуры (Event-Driven Architecture)**. 

Главная цель здесь — минимизировать время отклика (latency) для пользователя. Если мы будем отправлять письмо и обновлять индекс (который может быть тяжелым сетевым запросом к Elasticsearch) прямо в основном потоке запроса, пользователь будет смотреть на крутящийся спиннер несколько секунд. Это плохой UX и риск таймаутов.

Я рассмотрю три варианта решения, от самого простого до наиболее масштабируемого, оценивая их по критериям: **сложность реализации**, **надежность (reliability)** и **масштабируемость**.

---

### Ответ

Для решения этой задачи я буду использовать подход, при котором основной процесс (регистрация) завершается как можно быстрее, а побочные эффекты (письмо, индекс) выносятся в фоновые задачи.

Вот три варианта реализации:

#### Вариант 1: Symfony Messenger + Transport (Рекомендуемый стандарт)
Это наиболее правильный и «нативный» путь для Symfony. Мы используем компонент `Messenger`, который позволяет превратить синхронную отправку сообщения в асинхронную.

*   **Как это работает:**
    1. В контроллере или сервисе регистрации мы просто вызываем `$messageBus->dispatch(new UserRegisteredEvent($user))`.
    2. Symfony не выполняет логику сразу, а «бросает» это сообщение в транспорт (например, **RabbitMQ**, **Redis** или даже базу данных через **Doctrine**).
    3. В фоне работает отдельный процесс (worker), который слушает транспорт, забирает сообщение и выполняет обработчики (Handlers): один для отправки письма, другой для обновления индекса.

*   **Trade-offs:**
    *   **Плюсы:** Высокая надежность (есть механизмы повторных попыток — retries), слабая связность (сервис регистрации ничего не знает о письмах и индексах), отличная масштабируемость (можно запустить 10 воркеров на разных серверах).
    *   **Минусы:** Требует наличия брокера сообщений (RabbitMQ/Redis) и настройки инфраструктуры (supervisor для воркеров).

#### Вариант 2: Использование Symfony EventDispatcher (Синхронный, но чистый)
Если мы не можем внедрить брокер сообщений прямо сейчас, мы можем использовать `EventDispatcher` для разделения логики, но это **не решит проблему скорости** сама по себе.

*   **Как это работает:**
    1. Регистрация генерирует событие `UserRegisteredEvent`.
    2. Существуют слушатели `SendWelcomeEmailListener` и `UpdateSearchIndexListener`.
    3. Они срабатывают в том же запросе.

*   **Trade-offs:**
    *   **Плюсы:** Очень легко реализовать, не требует новой инфраструктуры, отличная чистота кода (SRP соблюден).
    *   **Минусы:** **Не решает задачу скорости**. Пользователь все равно будет ждать, пока отработают все слушатели. Если индекс обновляется 2 секунды, пользователь ждет 2 секунды.

#### Вариант 3: FastCGI Process Manager (FPM) `fastcgi_finish_request()` (Хакерский/Low-level)
Если мы работаем на Nginx + PHP-FPM и нам нужно решение «здесь и сейчас» без настройки RabbitMQ.

*   **Как это работает:**
    1. Мы выполняем регистрацию и запись в БД.
    2. Вызываем `fastcgi_finish_request()`. Это заставляет Nginx закрыть соединение с клиентом и отдать ему HTTP 200.
    3. PHP-процесс продолжает работать в фоне. Мы выполняем отправку письма и обновление индекса.

*   **Trade-offs:**
    *   **Плюсы:** Не нужна дополнительная инфраструктура, пользователь получает ответ мгновенно.
    *   **Минусы:** Очень опасно. Если процесс упадет, мы не узнаем об этом. Если задач станет много, мы быстро забьем все PHP-FPM воркеры «фоновыми» задачами, и новые пользователи не смогут даже зайти на сайт. Это решение — «костыль» для очень маленьких проектов.

### Итоговое решение

Для серьезного приложения я выберу **Вариант №1 (Symfony Messenger + RabbitMQ/Redis)**.

**Мой план реализации:**
1. Создать `UserRegisteredEvent` (DTO с ID пользователя).
2. Создать два `MessageHandler`: `SendWelcomeEmailHandler` и `UpdateSearchIndexHandler`.
3. Настроить `messenger.yaml`, чтобы эти сообщения уходили в транспорт `async`.
4. Запустить воркеры через `bin/console messenger:consume async`.

Это обеспечит:
* **Мгновенный ответ пользователю.**
* **Гарантию доставки:** если сервис писем упадет, Messenger попробует отправить письмо еще раз через 5 минут.
* **Изоляцию ошибок:** если упадет обновление индекса, письмо все равно уйдет.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

### Рассуждение

Вопрос затрагивает фундаментальную разницу между «кто ты?» (Authentication) и «что тебе можно?» (Authorization). Многие разработчики путают эти понятия, пытаясь ограничить доступ только ролями, что ведет к созданию «дырявой» безопасности.

Я разделю ответ на три логических слоя, как это устроено в Symfony Security Component:
1.  **Authentication (Аутентификация):** Процесс идентификации пользователя (логин, токен, сессия).
2.  **Authorization (Авторизация) через Roles:** Простой механизм на основе атрибутов пользователя.
3.  **Authorization через Voters:** Гибкий механизм на основе бизнес-логики.

Главный инженерный вызов здесь — понять, когда логика «можно/нельзя» становится слишком сложной для простой проверки строки (роли). Если проверка зависит от состояния объекта (например, «можно редактировать пост, только если ты его автор»), роли здесь бессильны.

---

### Ответ

В Symfony безопасность строится на четком разделении ответственности между идентификацией личности и проверкой прав доступа.

#### 1. Аутентификация (Authentication)
Это процесс подтверждения того, что пользователь — это именно тот, за кого он себя выдает. В Symfony за это отвечают **Authenticators**.
*   **Как это работает:** При каждом запросе (или при входе) Authenticator проверяет учетные данные (пароль, JWT-токен, сессионную куку). Если данные верны, он создает объект `Token` и помещает его в `TokenStorage`. С этого момента система «знает» текущего пользователя (`$this->getUser()`).

#### 2. Авторизация через Роли (Role-based Access Control — RBAC)
Это самый простой уровень проверки прав. Роли — это просто строки (например, `ROLE_USER`, `ROLE_ADMIN`), которые привязаны к пользователю.
*   **Как это работает:** Вы используете `is_granted('ROLE_ADMIN')` в контроллере или `#[IsGranted('ROLE_ADMIN')]` над методом.
*   **Когда использовать:** Когда доступ определяется только статусом пользователя. Например: «только администратор может зайти в панель управления» или «только авторизованный пользователь может видеть страницу профиля».

#### 3. Авторизация через Voters (Attribute-based Access Control — ABAC)
Voters — это мощный инструмент, когда проверка прав требует глубокого анализа контекста или бизнес-правил.
*   **Как это работает:** Вы создаете класс, реализующий `VoterInterface`. Метод `voteOnAttribute()` получает объект (сущность) и действие (атрибут). Вы пишете произвольную PHP-логику для возврата `ACCESS_GRANTED` или `ACCESS_DENIED`.
*   **Пример:** `is_granted('POST_EDIT', $post)`.

---

### Когда выбирать Voter, а когда — Роли?

Это ключевой архитектурный вопрос. Я руководствуюсь следующим правилом:

#### Используй Роли, если:
*   Права **статичны** и привязаны только к пользователю.
*   Проверка не зависит от конкретного объекта (сущности).
*   *Пример:* «Доступ к разделу отчетов разрешен только пользователям с ролью `ROLE_MANAGER`».

#### Используй Voter, если:
*   Права **динамичны** и зависят от данных объекта (**Ownership**).
    *   *Пример:* «Пользователь может редактировать статью, только если `article.getAuthor() === user`». Роли здесь не помогут, так как у всех авторов одна и та же роль `ROLE_USER`.
*   Права зависят от **состояния объекта**.
    *   *Пример:* «Статью нельзя редактировать, если у неё статус `PUBLISHED`».
*   Права зависят от **сложных бизнес-правил** или связей.
    *   *Пример:* «Пользователь может просматривать документ, если он входит в ту же организацию, что и владелец документа».
*   Нужно **централизовать логику**. Если проверка «можно ли редактировать» встречается в 5 контроллерах и 3 шаблонах Twig, её нужно вынести в Voter, чтобы не дублировать `if ($post->getAuthor() === $user)`.

**Резюме:** Роли — это про «КТО ты», а Voters — это про «ЧТО ты хочешь сделать с ЭТИМ конкретным объектом в ТАКОЙ-ТО ситуации». В сложных проектах 90% сложной логики прав доступа живет именно в Voter.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

### Рассуждение

Этот вопрос бьет в самую суть конфликта между **DDD (Domain-Driven Design)** и **Relational Mapping**. 

Проблема в том, что реляционные базы данных (PostgreSQL) не знают о существовании «Value Objects». Они знают только о примитивах: `string`, `int`, `boolean`. С другой стороны, в доменном слое Value Object (VO) должен быть:
1. **Immutable (неизменяемым):** Мы не меняем свойства, мы создаем новый объект.
2. **Self-validating:** Объект не может сущеть в невалидном состоянии (конструктор должен кидать исключение).

Если мы просто сделаем `property` в сущности (Entity) типом нашего VO, Doctrine не поймет, как превратить строку из БД в этот объект и наоборот.

Я рассмотрю три спосовых решения:
1. **Embeddables (стандартный путь Doctrine).**
2. **Custom Mapping (через DBAL Type) — создание собственного типа данных.**
3. **Manual Mapping (в сущности) — ручное управление в Getters/Setters.**

Я также должен предупредить о «подводном камне» — потере инкапсуляции, когда ORM может обойти конструктор VO через рефлексию, создавая невалидные объекты.

---

### Ответ

Для хранения Value Objects в Doctrine существует три основных подхода. Выбор зависит от того, насколько сложен ваш VO и насколько «чистым» вы хотите оставить доменный слой.

#### 1. Doctrine Embeddables (Рекомендуемый путь для простых VO)
Это встроенный механизм Doctrine, который позволяет «встроить» свойства одного объекта в таблицу другого.

*   **Как это работает:** Вы помечаете класс VO аннотацией/атрибутом `#[Embeddable]`. В основной сущности вы используете `#[Embedded]`.
*   **Пример:** `Address` (street, city, zip) встраивается в `User`. В БД создадутся колонки `user_street`, `user_city` и т.д.

| Плюсы | Минусы |
| :--- | :--- |
| Нативно поддерживается Doctrine. | VO не имеет своего ID (это логично для VO). |
| Легко использовать в запросах (DQL). | Только для простых структур (нельзя вложить Embeddable в Embeddable глубоко). |
| Сохраняет типизацию в коде. | Если VO станет очень сложным, таблица разрастется. |

**Подводный камень:** Если вы забудете инициализировать Embeddable, в базе могут появиться `NULL` значения, что может нарушить инварианты вашего домена.

#### 2. Custom DBAL Types (Для сложных или атомарных VO)
Если ваш VO — это что-то вроде `Email`, `Money` (сумма + валюта) или `Color` (HEX-код), который в БД должен храниться как одна строка, лучше создать свой тип данных.

*   **Как это работает:** Вы создаете класс, наследуясь от `Doctrine\DBAL\Types\Type`, и переопределяете методы `convertToDatabaseValue` (из VO в примитив) и `convertToPHPValue` (из примитива в VO).
*   **Пример:** Тип `EmailType` превращает строку из БД в объект `Email`.

| Плюсы | Минусы |
| :--- | :--- |
| VO выглядит как примитив в БД (чистота схемы). | Сложно реализовать для составных объектов (лучше для одного значения). |
| Полный контроль над процессом трансформации. | Нужно регистрировать тип в конфигурации. |

**Подводный камень:** При использовании этого метода вы теряете возможность делать сложные выборки по отдельным полям внутри VO через DQL, так[] как для БД это просто одна «непонятная» строка/blob.

#### 3. Manual Mapping (Ручное управление)
Вы храните данные в сущности как примитивы, а VO создаете только в геттерах и сеттерах.

*   **Как это работает:**
    ```php
    class User {
        private string $emailString; // Храним примитив

        public function getEmail(): Email {
            return new Email($this->emailString);
        }

        public function setEmail(Email $email): void {
            $this->emailString = $email->toString();
        }
    }
    ```

| Плюсы | Минусы |
| :--- | :--- |
| Максимальный контроль и простота. | Нарушение инкапсуляции: сущность «знает» о примитивах, которые составляют VO. |
| Никакой магии Doctrine. | Много бойлерплейта (геттеры/сеттеры для каждого поля). |

**Подводный камень:** Это самый «грязный» способ с точки зрения DDD, так как ваша сущность вынуждена работать с «сырыми» данными, что размывает границы доменной модели.

### Итоговая рекомендация

1.  Если ваш VO — это **группа полей** (например, `Address`, `Coordinates`), используйте **Embeddables**. Это стандарт индустрии.
2.  Если ваш VO — это **одиночное значение** со своей логикой валидации (например, `Money`, `Email`, `PhoneNumber`), создайте **Custom DBAL Type**. Это даст самую чистую схему БД и лучшую типизацию.
3.  **Никогда** не используйте ручной маппинг в качестве основного решения, если только вы не пишете сверхлегкий скрипт. Это превращает ваши сущности в свалку примитивов.

**Важное замечание про валидность:** Чтобы гарантировать, что Doctrine не создаст невалидный VO через рефлексию (обходя конструктор), я всегда рекомендую добавлять проверку в методы `convertToPHPValue` (в кастомных типах) или использовать библиотетк типа `symfony/validator` на уровне сущностей, чтобы убедиться, что данные из БД корректны.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

### Рассуждение

Это вопрос на понимание того, как примитивные инструменты ORM (Doctrine) ложажатся на строгие правила DDD. Главная проблема здесь — **разрыв между Unit of Work (UoW) в Doctrine и границами агрегата в DDD**.

В DDD **Агрегат** — это граница согласованности (consistency boundary). Все изменения внутри агрегата должны быть атомарными. В Doctrine же `EntityManager` управляет *всеми* сущностями, которые он «видит», что может привести к случайному изменению данных за пределами агрегата.

Я разберу это на примере агрегата `Order` (Корень) и коллекции `OrderItem` (Дочерние сущности).

**Мои принципы проектирования здесь:**
1. **Инкапсуляция коллекции:** Мы никогда не даем доступ к коллекции `OrderItem` напрямую (через геттер, возвращающий саму коллекцию), чтобы нельзя было вызвать `$order->getItems()->add(...)` в обход бизнес-логики агрегата.
2. **Управление жизненным циклом:** Дочерние сущности не должны существовать без корня.
3. **Границы транзакции:** `flush()` должен вызываться только на уровне Application Service (или Command Handler), а не внутри доменного слоя.

---

### Ответ

Рассмотрим агрегат **Order** (Заказ), который содержит коллекцию **OrderItem** (Позиции заказа).

#### 1. Маппинг коллекции (Encapsulation)

Чтобы соблюсти инварианты агрегата, мы должны запретить внешнему коду манипулировать коллекцией напрямую.

```php
#[ORM\Entity]
#[ORM\Table(name: 'orders')]
class Order {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    /** @var Collection<int, OrderItem> */
    #[ORM\OneToMany(
        mappedBy: 'order', 
        targetEntity: OrderItem::class, 
        cascade: ['all'], // Важно: изменения в элементах пробросятся на корень
        orphanRemoval: true // Важно: удаление элемента из коллекции удалит его из БД
    )]
    private Collection $items;

    public function __construct() {
        $this->items = new ArrayCollection();
    }

    // ВАЖНО: Мы возвращаем только итератор или копию, чтобы нельзя было сделать $order->getItems()->add()
    /** @return Collection<int, OrderItem> */
    public function getItems(): Collection {
        return $this->items;
    }

    // Единственный способ изменить коллекцию — через метод агрегата
    public function addItem(Product $product, int $quantity): void {
        if ($quantity <= 0) {
            throw new DomainException("Quantity must be positive");
        }
        
        $item = new OrderItem($this, $product, $quantity);
        $this->items->add($item);
        
        // Здесь можно пересчитать общую сумму заказа (инвариант агрегата)
        $this->recalculateTotal();
    }

    public function removeItem(OrderItem $item): void {
        $this->items->removeElement($item);
        $this->recalculateTotal();
    }
}

#[ORM\Entity]
class OrderItem {
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'items')]
    #[ORM\JoinColumn(nullable: false)]
    private Order $order;

    public function __construct(Order $order, Product $product, int $quantity) {
        $this->order = $order;
        // ... инициализация
    }
}
```

**Ключевые настройки маппинга:**
*   `cascade: ['all']`: Позволяет нам просто вызвать `persist($order)`, и Doctrine автоматически сохранит все новые `OrderItem`.
*   `orphanRemoval: true`: Если мы удалим `OrderItem` из коллекции `$items`, Doctrine сама выполнит `DELETE` в базе. Это критично для целостности агрегата.

#### 2. Границы транзакции и вызов `flush()`

Это самая частая ошибка. **Никогда не вызывайте `$entityManager->flush()` внутри сущности или внутри доменного сервиса.**

**Правильная архитектура (Application Layer):**
Ответственность за сохранение лежит на **Application Service** (или Command Handler). Он управляет транзакцией и «сохранением состояния».

```php
class PlaceOrderService {
    public function __construct(
        private OrderRepository $orderRepository,
        private EntityManagerInterface $entityManager,
        private OrderTotalCalculator $calculator // Дополнительный сервис
    ) {}

    public function execute(OrderDTO $dto): void {
        // 1. Начинаем транзакцию (на уровне БД)
        $this->entityManager->beginTransaction();

        try {
            // 2. Создаем агрегат
            $order = new Order();
            
            // 3. Меняем состояние агрегата через его методы
            foreach ($dto->items as $itemDto) {
                $product = $this->productRepo->find($itemDto->productId);
                $order->addItem($product, $itemDto->quantity);
            }

            // 4. Сохраняем агрегат (Doctrine увидит изменения в коллекции благодаря cascade)
            $this->orderRepository->save($order);

            // 5. Синхронизируем всё с БД
            $this->entityManager->flush();
            
            // 6. Фиксируем транзакцию
            $this->entityManager->commit();
            
        } catch (\Exception $e) {
            // Если что-то пошло не так — откатываем всё к исходному состоянию
            $this->entityManager->rollback();
            throw $e;
        }
    }
}
```

#### Резюме по правилам:

1.  **Кто вызывает `flush()`?** Только Application Layer. Доменный слой (Entity/Aggregate) не должен знать о существовании `EntityManager`.
2.  **Когда вызывать `flush()`?** Один раз в конце успешного завершения бизнес-сценария.
3.  **Как управлять коллекцией?** Только через методы корня агрегата (`addItem`, `removeItem`). В маппинге обязательно использовать `cascade: ['all']` и `orphanRemoval: true`.
4.  **Границы транзакции:** Весь процесс изменения агрегата должен быть обернут в одну транзакцию на уровне Application Service, чтобы гарантировать, что либо весь агрегат обновился, либо ничего.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

### Рассуждение

Вопрос про N+1 — это проверка на умение не просто «тыкать пальцем в небо», а использовать инженерные инструменты диагностики и понимать цену оптимизации. 

Проблема N+1 возникает, когда мы загружаем список основных сущностей (например, `User`), а затем в цикле обращаемся к их связанным сущностям (например, `Profile`), что заставляет ORM делать по одному дополнительному запросу на каждую строку.

Мой план действий:
1. **Диагностика:** Нельзя лечить то, что не измерил. Я буду использовать профилировщик (Symfony Profiler) или инструменты анализа SQL-трафика.
2. **Решение:** Я предложу три уровня: от исправления запроса (Eager Loading) до изменения архитектуры (DTO/Read Model).
3. **Анализ Trade-offs:** Я обязан объяснить, что «оптимизация» не бесплатна. За каждый быстрый запрос мы платим либо памятью, либо сложностью кода, либо потерей гибкости.

---

### Ответ

Если у меня есть подозрение на N+1, я не буду менять код наугад. Я начну с доказательной базы.

#### 1. Диагностика

Первым делом я использую **Symfony Profiler** (вкладка Doctrine). Он наглядно показывает:
* Количество выполненных запросов.
* Дублирующиеся запросы (повторяющиеся паттерны).
* Время выполнения каждого запроса.

Если это не дает полной картины (например, проблема на уровне API), я использую:
* **SQL Loggers:** Настройка логирования всех запросов в лог-файл.
* **Blackfire.io или Xdebug:** Для построения call-graph и понимания, какая именно строка кода инициирует вызов БД.

Как только я вижу в логах паттерн: `SELECT * FROM profile WHERE user_id = ?` (повторяющийся 50 раз), диагноз подтвержден.

#### 2. Способы решения и их Trade-offs

Я выделяю три основных способа решения, в зависимости от контекста.

##### Способ А: Fetch Join (Eager Loading через DQL/QueryBuilder)
Самый частый способ. Мы явно говорим Doctrine: «При загрузке пользователей сразу подтяни их профили одним `JOIN`».

```php
// Было (N+1)
$users = $repository->findAll();

// Стало (Eager Loading)
$users = $this->createQueryBuilder('u')
    ->leftJoin('u.profile', 'p')
    ->addSelect('p') // Ключевой момент: заставляем Doctrine заполнить сущности
    ->getQuery()
    ->getResult();
```

* **Плюсы:** Решает проблему максимально быстро; данные приходят одним запросом.
* **Минусы:** 
    * **Memory Overhead:** Мы загружаем в память гораздо больше данных, чем нужно (все поля профиля, даже если нам нужно только имя).
    * **Cartesian Product (Декартово произведение):** Если мы делаем `JOIN` по нескольным One-to-Many коллекциям одновременно, количество строк в результате запроса растет экспоненциально, что может «повесить» БД и PHP.

##### Способ Б: Batch Loading (чеchten/Entity Hydration через ID)
Если нам нужно загрузить связанные данные, но `JOIN` слишком тяжелый (например, из-за объема данных), я использую загрузку по списку ID.

* **Как это работает:** Сначала загружаем `Users`, затем собираем все их `profile_id` и делаем один запрос `SELECT * FROM profiles WHERE id IN (1, 2, 3...)`. Затем мы можем вручную или через Doctrine (чеating with proxy) «прикрепить» их.

* **Плюсы:** Избавляет от проблемы декартова произведения; запросы остаются плоскими и быстрыми.
* **Минусы:** Требует дополнительного кода (ручной сбор ID и сопоставления); два запроса вместо одного (хотя это всё равно лучше, чем N+1).

##### Способ В: Использование DTO (Data Transfer Objects) и чистых SQL-запросов
Если это страница со списком (Read Model), где нам не нужно менять данные, а нужно только отобразить их, я вообще отказываюсь от использования сущностей (Entities) и Doctrine Hydrator.

* **Как это работает:** Я пишу чистый SQL или DQL, который возвращает не объекты `User`, а плоские массивы или специализированные `UserListDTO`.

```php
// SQL возвращает готовый набор данных для фронтенда
$data = $this->connection->fetchAllAssociative('
    SELECT u.name, p.avatar, p.bio 
    FROM users u 
    LEFT JOIN profiles p ON p.user_id = u.id
');
```

* **Плюсы:** 
    * **Максимальная производительность:** Нет накладных расходов на Hydration (превращение строк в объекты).
    * **Минимальное потребление памяти:** Мы берем только те поля, которые реально нужны для этой страницы.
* **Минусы:** 
    * **Потеря возможностей ORM:** Мы не можем вызвать методы сущности (`$user->getFullName()`).
    * **Нарушение архитектуры:** Мы смешиваем слой представления и слой данных (если не используем DTO).

#### Итоговая стратегия выбора:

1. Если это **стандартная админка** и сущностей немного — использую **Fetch Join**.
2. Если это **сложный отчет** с множеством связей — использую **Batch Loading** или несколько точечных запросов.
3. Если это **высоконагруженный публичный список** (например, лента постов) — я полностью ухожу от сущностей в сторону **DTO и сырого SQL**.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

### Рассуждение

Этот вопрос — классическая проверка на понимание концепции **«защиты в глубину» (Defense in Depth)**. 

Многие разработчики совершают ошибку, полагая, что если у них есть валидация в PHP (чеbage, Symfony Validator, Assertions), то база данных — это просто «склад» для хранения данных. Это опасное заблуждение.

Я должен разделить валидацию на два типа:
1.  **Бизнес-валидация (Domain Validation):** Проверка правил бизнеса (например, «сумма заказа не может быть отрицательной», «пользователь не может забронировать дату в прошлом»). Это место для сложной логики, которая требует контекста и внешних сервисов.
2.  **Обеспечение целостности данных (Data Integrity):** Гарантия того, что данные физически корректны и согласованы (например, «этот ID существует», «это поле не может быть NULL», «это значение должно быть уникальным»).

Мой тезис: **Бизнес-валидация в коде — для пользователя и UX; ограничения в БД — для защиты системы от ошибок кода, гонок (race conditions) и внешних манипуляций.**

---

### Ответ

Я придерживаюсь принципа, что ограничения в PostgreSQL — это **последняя линия обороны**. Даже если ваш PHP-код идеален, ошибки могут прийти из других источников: параллельные запросы (race conditions), баги в миграциях, прямые правки в БД администратором или ошибки в других микросервисах, работающих с той же БД.

#### Зачем нужны ограничения в БД, если есть валидация в коде?

1.  **Защита от Race Conditions (состояние гонки):**
    Представьте, что два параллельных запроса проверяют уникальность Email пользователя. Оба запроса в PHP проходят валидацию `if (!userExists($email))`, потому что в этот микросекундный момент записи еще нет в БД. В итоге оба выполняют `INSERT`, и у вас два пользователя с одинаковым Email. Только `UNIQUE constraint` в PostgreSQL остановит второй запрос.
2.  **Гарантия целостности связей (Referential Integrity):**
    Валидация в коде может проверить, существует ли `category_id`, но только `FOREIGN KEY` на уровне БД гарантирует, что никто не удалит категорию, пока к ней привязаны товары.
3.  **Единый источник истины (Single Source of Truth):**
    Если к вашей базе подключается BI-система, другой микросервис на Python или скрипт на Go, они не будут запускать ваш PHP-код и вашу бизнес-валидацию. Ограничения в БД гарантируют, что данные останутся корректными независимо от того, какой инструмент к ним обращается.

#### Какие средства я использую и когда?

Я использую ограничения в БД для всего, что касается **структурной целостности**, и оставляю код для **бизнес-логики**.

| Средство в PostgreSQL | Когда я его использую | Пример |
| :--- | :--- | :--- |
| **NOT NULL** | Всегда, где поле обязательно. Это база. | `email VARCHAR NOT NULL` |
| **UNIQUE Constraint** | Для полей, которые не должны дублироваться. | `email UNIQUE` или `slug UNIQUE` |
| **Primary Key** | Всегда для идентификации строк. | `id SERIAL PRIMARY KEY` |
| **Foreign Key (FK)** | Для всех связей между сущностями. Это база целостности. | `user_id INT REFERENCES users(id)` |
| **Check Constraint** | Для простых, атомарных правил, которые не требуют внешних данных. | `price NUMERIC CHECK (price > 0)` |
| **Enum Types** | Когда набор значений строго фиксирован на уровне схемы. | `status VARCHAR CHECK (status IN ('new', 'paid', 'shipped'))` |

#### Где проходит граница?

*   **В коде (PHP/Domain):** Я реализую проверку: «Может ли пользователь купить этот товар, учитывая его баланс и наличие товара на складе?». Это требует запросов к БД, проверки условий, возможно, обращения к API. Это **бизнес-логика**.
*   **В БД (PostgreSQL):** Я реализую проверку: «Является ли баланс числом, и не стал ли он отрицательным в результате ошибки в расчетах?». Это **целостность данных**.

**Итог:** Валидация в коде делает приложение **удобным** (дает понятные ошибки пользователю), а ограничения в БД делают приложение **надежным** (защищает данные от разрушения). В хорошей архитектуре они работают в тандеме.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

### Рассуждение

Когда я слышу «запрос тормозит», я понимаю, что это не проблема, которую можно решить «магической настройкой». Это инженерная задача, требующая перехода от интуиции к доказательствам. 

Мой подход строится на принципе: **«Сначала измерь, потом анализируй, потом меняй»**. Я не буду добавлять индексы наобум, потому что это замедляет запись и может не помочь.

Процесс я разделю на три фазы:
1. **Обнаружение и локализация:** Понять, *какой именно* запрос тормозит и *насколько* сильно.
2. **Глубокий анализ:** Понять, *почему* он тормозит (план выполнения).
3. **Применение стратегий оптимизации:** Исправление причин.

Я также должен упомянуть, что проблема может быть не в самом SQL-запросе, а в «окружении»: блокировках, нехватке памяти или проблемах на стороне приложения (например, N+1).

---

### Ответ

Диагностика медленного запроса — это детективная работа. Я иду от общего к частному.

#### 1. Этап диагностики (Где и что тормозит?)

Первым делом я должен понять масштаб проблемы.
*   **Инструменты:** 
    *   **`pg_stat_statements`**: Это мой главный инструмент в PostgreSQL. Это расширение позволяет видеть статистику по всем выполненным запросам: сколько раз запускался, сколько времени занял суммарно, сколько ресурсов потребил. Я ищу запросы с высоким `total_time` или `mean_time`.
    *   **Slow Query Log**: Если расширение не включено, я смотрю логи сервера, где настроен порог `log_min_duration_statement`.
    *   **Application Profiling (Symfony Profiler / Blackfire)**: Чтобы понять, не является ли проблема следствием того, что приложение делает 100 мелких запросов вместо одного большого (проблема N+1).

#### 2. Этап анализа (Почему он тормозит?)

Как только я выловил «виновника», я беру его текст и иду в «подвал» — к планировщику запросов.
*   **Инструмент:** `EXPLAIN (ANALYZE, BUFFERS)`.
    *   `ANALYZE` заставляет базу выполнить запрос и показать реальное время.
    *   `BUFFERS` показывает, сколько данных было прочитано из кэша (shared buffers), а сколько — с диска (I/O). Это критично для понимания, упираемся ли мы в диск.

**На что я смотрю в плане выполнения:**
*   **Seq Scan (Sequential Scan):** Это «красный флаг». База читает всю таблицу целиком. Это плохо для больших таблиц.
*   **Index Scan vs Index Only Scan:** Если я вижу `Seq Scan` там, где должен быть индекс, значит, индекс либо не создан, либо не подходит (например, из-за несовпадения типов или использования функций в `WHERE`).
*   **Bitmap Heap Scan:** Это промежуточный вариант, часто хороший, но если он переходит в тяжелый `Heap Scan`, значит, данных слишком много.
*   **Nested Loop vs Hash Join vs Merge Join:** Я смотрю, как соединяются таблицы. Если при огромных объемах данных я вижу `Nested Loop`, это может быть признаком отсутствия индексов на ключах соединения.
*   **Cost vs Actual Time:** Если планировщик ожидает 10 строк, а получает 1 000 000 — значит, статистика базы устарела.

#### 3. Типовые причины и способы оптимизации

Я выделяю четыре группы проблем:

**А. Отсутствие или неэффективность индексов**
*   *Причина:* Запрос фильтрует по полю, на котором нет индекса, или использует функцию (например, `WHERE LOWER(email) = ...`), которая делает обычный индекс бесполезным.
*   *Решение:* Создать индекс. Если используется функция — создать **функциональный индекс** (`CREATE INDEX ... ON users (LOWER(email))`).

**Б. Проблемы со статистикой**
*   *Причина:* Планировщик строит плохой план, потому потому что думает, что в таблице 10 строк, а там 10 миллионов.
*   *Решение:* Выполнить `ANALYZE` для обновления статистики.

**В. Неэффективная структура запроса / Схемы**
*   *Причина:* Слишком много `JOIN`, использование `SELECT *` (приводит к лишнему чтению данных), или использование `OR` в тяжелых условиях.
*   *Решение:* Переписать запрос, заменить `OR` на `UNION`, заменить `SELECT *` на список нужных полей. Если данных много — рассмотреть **материализованные представления (Materialized Views)**.

**Г. Проблемы инфраструктуры и блокировок**
*   *Причина:* Запрос ждет, пока другой процесс удержит блокировку (Lock). Или база уперлась в Disk I/O, потому что памяти (RAM) не хватает для кэширования индексов.
*   *Решение:* Проверить `pg_stat_activity` на наличие заблокированных процессов. Оптимизировать `shared_buffers` или добавить RAM.

#### Итоговый алгоритм:
1. Найти запрос через `pg_stat_statements`.
2. Прогнать `EXPLAIN (ANALYZE, BUFFERS)`.
3. Если вижу `Seq Scan` — ищу индекс.
4. Если индекс есть, но не работает — проверяю типы данных и функции в `WHERE`.
5. Если план верный, но медленный — проверяю нагрузку на диск и блокировки.

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

### Рассуждение

Этот вопрос проверяет не только знание терминологии, но и умение применять абстрактные концепции к проектированию реальных систем. Многие разработчики совершают ошибку, воспринимая «Агрегат» как просто «набор связанных сущностей», что приводит к созданию гигантских объектов, которыми невозможно управлять.

Для меня **Агрегат (Aggregate)** — это не про то, как данные лежат в базе, а про то, как мы гарантируем **инварианты** (бизнес-правила, которые всегда должны быть истинны).

Чтобы ответить структурно, я разделю объяснение на три части:
1. **Определение через инварианты** (суть агрегата).
2. **Правила определения границ** (как я решаю, что включить в агрегат, а что — нет).
3. **Практический пример и разбор типичной ошибки** (чтобы показать глубину понимания).

---

### Ответ

В DDD **Агрегат** — это кластер связанных объектов (сущностей и Value Objects), которые рассматриваются как единое целое для изменения данных. Главная цель агрегата — обеспечить **целостность (consistency)**.

#### 1. Суть агрегата: Инварианты
Граница агрегата определяется не структурой связей, а **инвариантами**. Инвариант — это бизнес-правило, которое никогда не должно нарушаться. Все изменения, которые могут нарушить это правило, должны проходить через **Корень Агрегата (Aggregate Root)**.

Если вы можете изменить объект внутри агрегата, не нарушив правила всего агрегата — значит, этот объект, возможно, должен быть отдельным агрегатом.

#### 2. Как я определяю границы (Принципы)

Когда я проектирую границы, я руководствуюсь тремя правилами:

1.  **Правило коренной сущности:** Внешний мир взаимодействует с агрегатом *только* через его Корень (Aggregate Root). Никто не может изменить «внутренности» агрегата, минуя корень.
2.  **Правило транзакционности:** Один агрегат = одна транзакция. Мы стремимся к тому, чтобы за один запрос в БД менялся только один агрегат. Это обеспечивает высокую масштабируемость и предотвращает конфликты блокировок.
3.  **Правило малого размера:** Агрегаты должны быть как можно меньше. Чем больше агрегат, тем выше вероятность конфликтов при одновременной записи и тем сложнее поддерживать его инварианты.

#### 3. Пример: Заказ в интернет-магазине

**Правильный агрегат:**
* **Корень (Aggregate Root):** `Order` (Заказ).
* **Внутренние элементы:** `OrderItem` (Позиция заказа), `ShippingAddress` (Адрес доставки — Value Object).

**Инвариант:** «Общая сумма заказа должна соответствовать сумме цен всех позиций».
Чтобы этот инвариант не нарушился, мы не даем методу `OrderItem::setPrice()` быть публичным. Мы создаем метод `Order::updateItemQuantity()`. Только через `Order` можно изменить позицию, и только `Order` пересчитает итоговую сумму. Таким�    **ти границы определены правилом целостности суммы.**

#### 4. Типовая ошибка: «Агрегат-монстр» (Big Aggregate)

**Ошибка:** Попытка включить в агрегат `Order` сущность `Product` (Товар).

Разработчик думает: «Заказ содержит товары, значит, товар должен быть внутри агрегата заказа». Он делает `Product` частью агрегата `Order`.

**Почему это катастрофа:**
1.  **Нарушение транзакционности:** Если я хочу изменить цену товара в каталоге (обновить `Product`), мне придется заблокировать все активные заказы, в которых этот товар участвует. Это убьет производительность системы.
2.  **Нарушение инвариантов:** Изменение товара вне контекста заказа (например, его удаление) может внезапно сломать старые заказы, которые уже завершены.
3.  **Сложность:** Агрегат становится огромным, его трудно тестировать и невозможно масштабировать.

**Как правильно:** `Product` — это **отдельный агрегат**. `Order` должен хранить в себе только `ProductId` (идентификатор) и, возможно, «снимок» цены на момент покупки (Snapshot), чтобы изменения цены в каталоге не влияли на старые заказы.

**Итог:** Я определяю границы агрегата, задавая вопрос: *«Какие объекты должны измениться одновременно, чтобы бизнес-правило осталось верным?»*. Если ответ требует изменения нескольких независимых сущностей — я разделяю их на разные агрегаты и связываю только через ID.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

### Рассуждение

Это вопрос о **конкурентном доступе (Concurrency Control)**. В высоконагруженных системах это неизбежность. Если два процесса одновременно прочитают состояние агрегата, изменят его и попытаются сохранить, мы столкнемся с проблемой **«потерянного обновления» (Lost Update)**.

Первый процесс запишет свои изменения, а второй — перезапишет их своими, фактически «стерев» то, что сделал первый. При этом бизнес-инварианты (например, остаток денег на счету) могут быть нарушены.

Я рассматриваю два основных стратемента решения:
1. **Pessimistic Locking (Пессимистичная блокировка):** «Я забираю этот объект и никто другой к нему не прикоснется, пока я не закончу».
2. **Optimistic Locking (Оптимистичная блокировка):** «Я предполагаю, что никто не изменит объект, пока я работаю, но перед сохранением я проверю, не изменился ли он за это время».

Я также должен упомянуть, что выбор между ними — это всегда **trade-off** между производительностью и надежностью.

---

### Ответ

Когда два процесса одновременно изменяют один агрегат, результат зависит от выбранной стратегии управления конкурентностью.

#### 1. Проблема: Lost Update
Без механизмов контроля произойдет следующее:
1. Процесс А читает `Order(status=NEW)`.
2. Процесс Б читает `Order(status=NEW)`.
3. Процесс А меняет статус на `PAID` и делает `flush()`.
4. Процесс Б (не зная об изменениях А) меняет статус на `CANCELLED` и делает `flush()`.
**Итог:** Статус `PAID` потерян, заказ отменен, хотя по логике оплаты он должен быть оплачен.

#### 2. Стратегия А: Optimistic Locking (Мой основной выбор)
Это наиболее масштабируемый подход для веб-приложений. Мы не блокируем базу данных, а проверяем версию данных в момент сохранения.

*   **Как это реализовано в Doctrine:** Мы добавляем в сущность поле `version` (обычно `int`).
*   **Процесс:**
    1. Процесс А и Б читают `Order` с `version = 1`.
    2. Процесс А сохраняет изменения. Doctrine выполняет: `UPDATE orders SET status='PAID', version=2 WHERE id=1 AND version=1`. Успех.
    3. Процесс Б пытается сохранить: `UPDATE orders SET status='CANCELLED', version=2 WHERE id=1 AND version=1`.
    4. **Результат:** База возвращает «0 строк изменено», потому что `version` уже равна `2`. Doctrine выбрасывает `OptimisticLockException`.

**Trade-offs:**
* **Плюсы:** Не блокирует базу, не снижает пропускную способность, идеально для систем с низкой вероятностью конфликтов.
* **Минусы:** Если конфликты случаются часто, пользователю придется постоянно получать ошибки и повторять действия (нужна логика ретраев — повторных попыток).

#### 3. Стратегия Б: Pessimistic Locking (Пессимистичный подход)
Мы используем механизмы самой БД (например, `SELECT ... FOR UPDATE`), чтобы заблокировать строку на время транзакции.

*   **Процесс:**
    1. Процесс А читает `Order` с блокировкой.
    2. Процесс Б пытается прочитать этот же `Order` с блокировкой, но база заставляет его **ждать**, пока транзакция А не завершится (COMMIT или ROLLBACK).

**Trade-offs:**
* **Плюсы:** Гарантирует успех операции (процесс Б просто дождется своей очереди), исключает исключения в приложении.
* **Минусы:** 
    * **Снижение производительности:** Процессы стоят в очереди.
    * **Риск Deadlocks (взаимных блокировок):** Если процесс А заблокировал объект 1 и ждет объект 2, а процесс Б заблокировал объект 2 и ждет объект 1 — система зависнет.

#### Как я проектирую систему с учетом этого?

Мой подход строится на трех уровнях:

1.  **По умолчанию — Optimistic Locking.** Я всегда добавляю поле `version` во все агрегаты. Это защищает от большинства случайных конфликтов без ущерба для масштабируемости.
2.  **Обработка исключений (Retries).** В Application Layer (в Command Handler) я реализую механизм автоматических повторных попыток. Если поймали `OptimisticLockException`, мы просто перезапускаем транзакцию (Reload -> Re-apply logic -> Save). Это незаметно для пользователя.
3.  **Pessimistic Locking — только для критических узлов.** Я использую пессимистичную блокировку только там, где цена конфликта критична и вероятность его очень высока (например, в высоконагруженном финансовом модуле при списании средств со счета, где важна строгая последовательность).

**Резюме:** Я проектирую систему так, чтобы она была **оптимистичной по умолчанию**, но имела инструменты для **пессимистичного контроля** в самых чувствительных точках.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

### Рассуждение

Вопрос о доменных событиях (Domain Events) — это проверка понимания того, как обеспечить слабую связанность (loose coupling) в сложной системе. 

Важно сразу разграничить: **Доменное событие** — это не просто «сообщение в шину». Это факт того, что в доменной модели *уже произошло* некое значимое изменение. Это событие из прошлого (название в прошедшем времени: `OrderPlaced`, а не `PlaceOrder`).

Я разделю ответ на:
1. **Проблемы, которые они решают** (зачем нам это вообще нужно).
2. **Механизм реализации** (когда и как публикуем).
3. **Связь с транзакциями** (самый сложный технический момент).
4. **Проблемы и риски** (side-effects).

---

### Ответ

#### 1. Какие проблемы решают доменные события?

Главная цель — **разрыв жесткой связности (Decoupling)**.
* **Устранение «раздутых» сервисов:** Вместо того чтобы в `OrderService` прописывать логику отправки email, обновления склада и уведомления аналитиков, сервис просто говорит: «Заказ создан». Он не знает, кто и как на это отреагирует.
* **Соблюдение SRP:** Сервис заказа отвечает только за заказ. Логика уведомлений уходит в свои отдельные слушатели (Listeners/Subscribers).
* **Подготовка к масштабированию:** События позволяют легко перейти от монолита к микросервисам. Сегодня слушатель работает в том же процессе, а завтра мы выносим его в отдельный сервис через RabbitMQ.

#### 2. Как я их применяю (Механика)

Я не рекомендую публиковать события прямо из методов сущности (это нарушает чистоту домена и создает зависимости от инфраструктуры).

**Мой паттерн:**
1. **Сбор событий внутри Агрегата:** Сущность накапливает события внутри себя (в приватном массиве `$recordedEvents`).
2. **Публикация в Application Service:** После того как агрегат изменил свое состояние, Application Service (или Command Handler) берет эти события и отправляет их в `EventDispatcher`.

```php
// Внутри Aggregate Root
public function placeOrder(): void {
    $this->status = Status::PLACED;
    $this->recordEvent(new OrderPlaced($this->id)); // Просто добавили в массив
}

// В Application Service
public function handle(PlaceOrderCommand $command): void {
    $order = $this->repository->find($command->id);
    $order->placeOrder();
    
    $this->repository->save($order); // Сохраняем агрегат
    
    // Публикуем события, которые накопились внутри агрегата
    foreach ($order->releaseEvents() as $event) {
        $this->eventBus->dispatch($event);
    }
}
```

#### 3. Связь с транзакциями (Критический момент)

Это самая опасная часть. Если я опубликую событие **до** того, как транзакция в БД будет зафиксирована (`commit`), возникнет проблема: слушатель (например, сервис отправки Email) получит событие, попытается найти заказ в базе, но... **заказа там еще нет** (или он в старом состоянии), потому что транзакция еще не завершена.

**Как я это решаю:**
Я использую паттерн **Transactional Outbox** или встроенные механизмы Symfony Messenger.

* **Вариант А (Messenger + Doctrine Transport):** Я настраиваю Messenger так, чтобы сообщения сохранялись в ту же БД, в которой лежит агрегат, в специальную таблицу `messenger_messages`. В рамках одной транзакции мы сохраняем и `Order`, и `Event`. Если транзакция откатится — событие не попадет в очередь. Если пройдет успешно — воркер подхватит его.
* **Вариант Б (Post-Commit Dispatch):** Я использую хуки жизненного цикла транзакции, чтобы вызывать `dispatch()` только *после* успешного `commit()`.

#### 4. Какие проблемы создаёт этот подход?

Несмотря на пользу, доменные события несут риски:

1. **Сложность отладки (Observability):** Поток выполнения становится нелинейным. Ты смотришь в код метода `placeOrder` и не видишь, почему после него внезапно обновился склад. Нужно уметь отслеживать цепочки событий.
2. **Проблема консистентности в конечном счете (Eventual Consistency):** Поскольку обработка событий часто происходит асинхронно, данные в системе могут быть не синхронизированы в течение долей секунды. Это нужно учитывать в UX (например, показывать пользователю статус «В обработке»).
3. **Риск дублирования (Idempotency):** В распределенных системах событие может прийти дважды. Поэтому **обработчики событий обязаны быть идемпотентными** (повторный вызов с тем же ID события не должен приводить к двойному списанию денег или повторной отправке письма).

**Итог:** Доменные события — это инструмент для построения гибких, слабосвязанных систем, но они требуют строгого контроля над транзакционностью и понимания того, что система переходит из модели «мгновенной согласованности» в модель «согласованности в конечном счете».

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

### Рассуждение

Этот вопрос проверяет фундаментальное понимание философии DDD. Здесь важно не просто дать определения из учебника, а показать, как эти концепции влияют на проектирование архитектуры и коммуникацию в команде.

Я разделю ответ на три части:
1. **Техническая разница между Entity и Value Object** (идентичность vs значение).
2. **Методология принятия решений** (как я определяю границы).
3. **Философия Ubiquitous Language** (как язык бизнеса становится языком кода).

---

### Ответ

#### 1. Entity vs Value Object: Идентичность против Значения

Главное различие заключается в том, **как мы определяем равенство объектов**.

*   **Entity (Сущность):** Имеет уникальную **идентичность (Identity)**, которая сохраняется на протяжении всей жизни объекта, даже если все его свойства изменились. Мы сравниваем сущности по их `ID`.
    *   *Пример:* `User`. Если пользователь сменил имя, фамилию и email, он остается тем же самым пользователем, потому что его `user_id` неизменен.
*   **Value Object (Объект-значение):** Не имеет идентичности. Он определяется исключительно своими **атрибутами (значениями)**. Если меняется хотя любая деталь — это уже другой объект. Важно: Value Object должен быть **Immutable (неизменяемым)**.
    *   *Пример:* `Money(amount: 100, currency: 'USD')`. Если я изменю 100 на 200, это не «измененные деньги», это совершенно другая сумма. Два объекта `Money(100, 'USD')` считаются равными, даже если они разные экземпляры в памяти.

#### 2. Как я решаю, к чему отнести концепцию?

Когда я проектирую модель, я задаю себе три вопроса:

1.  **«Важен ли для этого объекта его путь (история)?»** Если нам нужно отслеживать изменения этого объекта во времени (например, историю перемещений курьера), это **Entity**. Если нам важен только текущий срез данных — это **Value Object**.
2.  **«Можем перепутать два таких объекта, если у них одинаковые поля?»** Если два объекта с одинаковыми полями — это одно и то же (как два синих карандаша одного производителя), то это **Value Object**. Если это два разных человека с одинаковыми именами — это **Entity**.
3.  **«Нужно ли мне менять свойства этого объекта?»** Если бизнес-логика требует изменения части свойств, но объект остается тем же — это **Entity**. Если изменение означает создание чего-то нового — это **Value Object**.

#### 3. Единый язык (Ubiquitous Language)

**Ubiquitous Language** — это не просто «словарь терминов». Это живой язык, на котором общаются **все** участники процесса: разработчики, аналитики, менеджеры и заказчики.

**Как он влияет на код?**
В DDD мы переносим этот язык прямо в программный код. Если бизнес называет процесс не «запись в базу», а «бронированием слота» (`BookSlot`), то в моем коде не должно быть метода `saveSlot()`. Там должен быть метод `bookSlot()`.

**Преимущества:**
*   **Минимизация потерь при переводе:** Когда аналитик говорит «активируйте подписку», разработчик не должен в уме переводить это в «смените статус в базе на 1». В коде должен быть метод `subscription->activate()`.
*   **Самодокументированный код:** Код становится настолько понятным, что его можно читать как бизнес-спецификацию.
*   **Ускорение коммуникации:** Мы уходим от споров «что ты имел в виду под этим методом?» к обсуждению реальных бизнес-процессов.

**Мой подход к внедрению:**
Я не просто читаю требования. Я участвую в обсуждениях и, если вижу, что терминология размыта (например, разработчики говорят «объект», а бизнес — «контракт»), я предлагаю зафиксировать единый термин. Если термин зафиксирован — он обязан появиться в именах классов, методов и переменных. **Если в коде и в разговоре с бизнесом используются разные слова — значит, DDD не работает.**

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

### Рассуждение

Вопрос проверяет понимание того, как архитектурные принципы (Clean Architecture / Hexagonal Architecture) превращаются в физическую структуру папок и файлов. Основная ловушка здесь — смешивание понятий «слой» и «папка». Слой — это концепция, а папка — лишь способ её реализации.

Я буду строить ответ вокруг **Правила Зависимостей (Dependency Rule)**: зависимости должны быть направлены только внутрь, к бизнес-логике. Самая важная часть — это понимание того, что ядро (Domain) должно быть «чистым» и не знать о существовании Symfony, Doctrine или RabbitMQ.

Я разделю ответ на:
1. **Описание слоев и их ответственности.**
2. **Размещение конкретных компонентов (Doctrine, Symfony, Messenger).**
3. **Механизмы контроля границ.**

---

### Ответ

В чистой архитектуре приложение делится на слои, организованных в виде концентрических кругов. Главное правило: **зависимости направлены строго к центру**. Внутренние слои не знают ничего о внешних.

#### 1. Структура слоев

**I. Domain Layer (Ядро — Центр)**
Это самая чистая часть. Здесь живет бизнес-логика.
* **Что внутри:** Entities (Агрегаты), Value Objects, Domain Events, Domain Exceptions, Repository Interfaces (только интерфейсы!), Domain Services (если логика не влезает в сущность).
* **Зависимости:** **Ноль.** Этот слой не зависит ни от чего. Ни от фреймворков, ни от библиотек, ни от БД.

**II. Application Layer (Слой сценариев / Use Cases)**
Здесь описывается, *что* приложение делает. Это оркестратор.
* **Что внутри:** Command/Query handlers, DTO (Data Transfer Objects), Application Services, интерфейсы для внешних систем (например, `EmailServiceInterface`).
* **Зависимости:** Только на **Domain Layer**.

**III. Infrastructure Layer (Внешний мир)**
Здесь реализуются технические детали.
* **Что внутри:** Реализации репозиториев (Doctrine), реализация отправки Email (Symfony Mailer), работа с очередями, интеграции с внешними API.
* **Зависимости:** На **Application Layer** и **Domain Layer**.

**IV. Presentation Layer (Интерфейс пользователя)**
Точка входа в приложение.
* **Что что внутри:** Symfony Controllers, CLI Commands, API Resources.
* **Зависимости:** На **Application Layer** (четя через Command Bus или вызов сервисов).

---

#### 2. Размещение компонентов (Где они окажутся?)

* **Symfony-контроллер:** Это **Presentation Layer**. Его задача — принять HTTP-запрос, преобразовать его в DTO и передать в Application Layer. Он не должен содержать бизнес-логики.
* **Doctrine (Entity Manager, Repositories):** Это **Infrastructure Layer**. Реализация репозитория (`SqlUserRepository`) лежит здесь. Сами сущности (Entities) в чистой архитектуре должны быть **Domain Entities**, но в PHP-мире мы часто используем Doctrine-сущности как доменные (с компромиссом), поэтому маппинг (Attributes) технически является деталью инфраструктуры.
* **Обработчик очереди (Messenger Handler):** Это **Application Layer** (если он реализует сценарий использования) или **Infrastructure Layer** (если он является лишь «прослойкой» для получения сообщения). Я обычно отношу логику обработки к Application, а сам механизм получения сообщения — к Infrastructure.

#### 3. Как следить, чтобы границы не нарушались?

Соблюдать границы только «на честном слове» разработчика — плохая стратегия. Я использую три уровня контроля:

1.  **Static Analysis (PHPStan / Psalm):** Я настраиваю правила, которые запрещают импорт классов из `Infrastructure` в `Domain`. Это самый эффективный способ «на лету».
2.  **Архитектурные тесты (Deptrac):** Это специализированный инструмент для проверки слоев. Я пишу конфигурацию (например, `Domain cannot depend on Application`), и при запуске тестов Deptrac выдаст ошибку, если кто-то импортировал `App\Infrastructure` в `App\Domain`. Это «золотой стандарт» для контроля архитектуры.
3.  **Code Review:** Никакой инструмент не заменит человеческий глаз. На ревью я смотрю не только на логику, но и на `use`-стейтменты вверху файла. Если я вижу `use Doctrine\ORM\...` в классе `Domain\Model\...` — это автоматический `Request Changes`.

**Итог:** Чистая архитектура — это не про разделение файлов, а про **управление зависимостями**. Моя задача — сделать так, чтобы я мог заменить Symfony на другой фреймворк или PostgreSQL на MongoDB, не меняя ни одной строчки кода в слое `Domain`.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

### Рассуждение

Вопрос о тестировании — это вопрос о балансе между **уверенностью** (confidence) и **скоростью обратной связи** (feedback loop). 

Если мы будем писать только интеграционные тесты с реальной базой, CI/CD будет идти вечность, а тесты станут «флапающими» (flaky) из-за состояния данных. Я буду придерживаться классической **Пирамиды Тестирования**, но с поправкой на специфику Symfony и Doctrine.

---

### Ответ

Моя стратегия строится на четком разделении уровней тестирования и понимании того, что является «настоящим» объектом, а что — «подделкой».

#### 1. Пирамида тестирования

**I. Unit Tests (Основание — 70% тестов)**
* **Что тестируем:** Чистую бизнес-логику. Value Objects, Domain Services, правила внутри Entity, логику расчета скидок.
* **Что мокаем:** **Ничего.** Unit-тест должен быть максимально изолированным. Если сущности нужны друг другу — мы создаем их настоящими. Если нужна внешняя зависимость (API, почта) — мы используем Mock.
* **Цель:** Мгновенная проверка математики и логики.

**II. Integration Tests (Середина — 20% тестов)**
* **Что тестируем:** Взаимодействие компонентов. Взаимодействие `Repository -> Database`, `Service -> Repository`, или `Messenger -> Queue`.
* **Что мокаем:** Внешние API (через HTTP Mocking, например, `MockHttpClient`), но **не базу данных**.
* **Цель:** Проверить, что наши SQL-запросы корректны и Doctrine правильно маппит данные.

**III. Functional/E2E Tests (Вершина — 10% тестов)**
* **Что тестируем:** Полный жизненный цикл запроса. От HTTP-запроса до ответа.
* **Инструменты:** `Symfony WebTestCase` (KernelTestCase).
* **Что мокаем:** Только самые тяжелые и нестабильные внешние системы (платежные шлюзы, SMS-провайдеры).
* **Цель:** Проверить, что «всё работает вместе» (конфигурация, роутинг, безопасность, сериализация).

---

#### 2. Что мокать, а что нет? (Золотое правило)

Мой подход к мокам зависит от того, является ли зависимость **внутренней** или **внешней**.

*   **НЕ МОКАЮ:**
    *   **Value Objects и Entities:** Это простые объекты данных, мокать их — это писать больше кода, чем тестировать.
    *   **Repository (в интеграционных тестах):** Если мы тестируем сервис, нам нужна реальная БД. Использование мока репозитория в интеграционном тесте — это «тестирование мока», а не кода.
    *   **Domain Services:** Если они не имеют внешних связей.

*   **МОКАЮ:**
    *   **Внешние API и HTTP-клиенты:** Мы не хотим зависеть от доступности Stripe или Twilio.
    *   **Файловая система / Почтовые сервера:** Чтобы не спамить реальными письмами и не мусорить в `/tmp`.
    *   **Тяжелые сторонние библиотеки:** Если библиотека делает сложный расчет или запрос в сеть.

---

#### 3. Как поддерживать тесты быстрыми и стабильными?

Чтобы тесты не превратились в кошмар, я использую следующие практики:

**Для скорости:**
1.  **Тестовая БД в памяти или в Docker:** Для интеграционных тестов я использую отдельную БД (PostgreSQL в Docker), которая очищается перед каждым тестовым классом.
2. bypass тяжелой инициализации: В Unit-тестах я никогда не поднимаю Kernel Symfony.
3. **Параллелизация:** Запуск тестов в несколько потоков (через `paratest`).

**Для стабильности (избавление от Flakiness):**
1.  **Database Transactions (Transactional Tests):** Вместо того чтобы делать `TRUNCATE` после каждого теста (что медленно), я оборачиваю каждый тест в транзакцию и делаю `ROLLBACK` в методе `tearDown()`. Это гарантирует, что каждый тест начинает с чистого листа.
2.  **Изоляция данных:** Каждый тест должен создавать свои данные. Я избегаю использования «загруженных фикстур» (fixtures), которые общие для всех. Лучше использовать `FactoryBot`-подобный подход (например, `zenstruck/foundry`), чтобы создавать нужные объекты прямо в тесте: `$user = UserFactory::createOne();`.
3.  **Никаких `sleep()`:** Если нужно проверить асинхронность, я использую ожидание конкретного состояния в БД или логах, а не фиксированное время ожидания.

**Итог:** Моя стратегия — **максимум Unit-тестов для логики, интеграционные тесты для базы без моков, и минимум функциональных тестов для проверки «склейки» всех слоев.**

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

### Рассуждение

Этот вопрос — проверка понимания проблемы **конкурентного доступа (Concurrency Control)**. В многопользовательских системах ситуация, когда два процесса читают данные, изменяют их и пытаются записать обратно, является классической.

Основная проблема здесь — **Lost Update (Потерянное обновление)**. Если два пользователя одновременно редактируют одну и ту же сущность (например, описание товара), тот, кто нажал «Сохранить» вторым, просто перезапишет изменения первого, и изменения первого будут безвозвратно утеряны.

Я разделяю решения на две фундаментальные стратегии: **Pessimistic (Пессимистичная)** и **Optimistic (Оптимистичная)**. Выбор между ними — это всегда компромисс между **производительностью** и **целостностью**.

---

### Ответ

При одновременном изменении записи возникают две основные проблемы:
1.  **Lost Update:** Один процесс затирает изменения другого.
2.  **Inconsistent State (Нарушение инвариантов):** Если один процесс проверяет условие (например, «хватает ли денег на счету»), а второй в этот же момент списывает деньги, первый процесс может совершить операцию, которая приведет к отрицательному балансу.

#### 1. Pessimistic Locking (Пессимистичная блокировка)

Этот подход основан на принципе: «Я захватываю ресурс, и никто другой не может его даже читать для изменения, пока я не закончу».

*   **Как это работает:** На уровне БД выполняется запрос `SELECT ... FOR UPDATE`. База данных вешает блокировку на строку. Второй процесс, попытавшись прочитать эту же строку с `FOR UPDATE`, будет **ждать** (встанет в очередь), пока первый процесс не сделает `COMMIT` или `ROLLBACK`.
*   **Когда выбирать:** 
    *   В критических финансовых операциях (списание средств, инвентаризация склада).
    *   Там, где вероятность конфликтов (collisions) очень высока.
*   **Trade-offs:**
    *   **Плюсы:** Максимальная надежность; исключает любые конфликты на уровне БД.
    *   **Минусы:** Низкая производительность (процессы ждут); высокий риск **Deadlocks** (взаимных блокировок); риск исчерпания пула соединений с БД, если транзакции длятся долго.

#### 2. Optimistic Locking (Оптимистичная блокировка)

Этот подход предполагает, что конфликты случаются редко. Мы не блокируем запись, но проверяем, не изменилась ли она с момента нашего чтения.

*   **Как это работает:** В таблицу добавляется поле `version` (целое число).
    1. Процесс А читает запись: `id=1, version=5`.
    2. Процесс Б читает запись: `id=1, version=5`.
    3. Процесс А сохраняет: `UPDATE ... SET version=6 WHERE id=1 AND version=5`. Успех.
    4. Процесс Б пытается сохранить: `UPDATE ... SET version=6 WHERE id=1 AND version=5`.
    5. **Результат:** База возвращает «0 строк изменено», так как `version` уже равна `6`. Doctrine выбрасывает `OptimisticLockException`.
*   **Когда выбирать:**
    *   В большинстве стандартных CRUD-приложений (редактирование профиля, описание товара).
    *   Там, где конфликты редки, а высокая скорость отклика (low latency) важнее всего.
*   **Trade-offs:**
    *   **Плюсы:** Высокая производительность; отсутствие блокировок в БД; масштабируемость.
    *   **Минусы:** При конфликте пользователю придется повторять действие (нужно обрабатывать исключение на уровне приложения).

#### Сравнительная таблица

| Характеристика | Pessimistic Locking | Optimistic Locking |
| :--- | :--- | :--- |
| **Основной механизм** | Блокировка строки в БД (`FOR UPDATE`) | Проверка версии (`version` column) |
| **Поведение при конфликте** | Второй процесс **ждет** | Второй процесс **получает ошибку** |
| **Влияние на производительность** | Высокое (снижает пропускную способность) | Низкое (почти нет накладных расходов) |
| **Риск Deadlock** | Высокий | Отсутствует |
| **Сложность реализации** | Низкая (на уровне SQL) | Средняя (нужна обработка исключений) |

#### Моя стратегия выбора:

1.  **По умолчанию — Optimistic Locking.** Я всегда добавляю поле `version` во все сущности, которые могут редактироваться пользователями. Это защищает от большинства проблем без ущерба для системы.
2.  **Для критических операций — Pessimistic Locking.** Если я пишу модуль обработки платежей или управления остатками на складе, где два одновременных списания могут привести к финансовому ущербу, я использую `Pessimistic Write`.
3.  **Для высоконагруженного чтения — Ничего.** Если мы просто читаем данные для отображения, нам не нужны никакие блокировки. Мы жертвуем актуальностью в миллисекунды ради скорости.

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

### Рассуждение

Вопрос о Git-процессе — это вопрос не о командах `git commit` или `git merge`, а о **культуре разработки** и **управлении рисками**. 

Плохой процесс — это когда в `main` можно пушить напрямую, коммиты называются `fix`, а ревью проходит за 5 минут «глазами». Это путь к хаосу и падениям продакшена.

Я буду строить ответ, исходя из принципов **CI/CD (Continuous Integration / Continuous Deployment)** и минимизации «стоимости ошибки». Мой процесс базируется на модели **GitHub Flow** (или упрощенном GitFlow), так как она идеально подходит для современных команд, работающих с автоматизированными пайплайнами.

---

### Ответ

Мой процесс построен так, чтобы каждая строка кода проходила через несколько фильтров качества, прежде чем попасть к пользователю.

#### 1. Ветвление (Branching Strategy)
Я использую модель **Feature Branches**.
*   **`main` (или `master`)**: Всегда содержит стабильный, протестированный код, который готов к деплою. Прямые пуши в `main` запрещены на уровне прав в Git.
*   **`feature/task-id-description`**: Для каждой задачи создается отдельная ветка. Это позволяет изолировать работу и не мешать коллегам.
*   **`hotfix/description`**: Для экстренных исправлений на продакшене.

**Почему так?** Это позволяет параллельно работать над разными фичами, не создавая конфликтов в основной ветке и обеспечивая возможность тестировать каждую фичу в изоляции.

#### 2. Формат коммитов (Commit Message Convention)
Я придерживаюсь стандарта **Conventional Commates**. Это не просто вопрос красоты, это вопрос автоматизации (например, автоматического формирования Changelog).

Формат: `<type>(<scope>): <description>`
*   `feat`: Новая функциональность.
*   `fix`: Исправление ошибки.
*   `refactor`: Изменение кода без изменения логики.
*   `test`: Добавление тестов.
*   `chore`: Обновление зависимостей, конфигов (не меняет логику).

**Почему так?** Это делает историю Git читаемой. При просмотре `git log` я сразу вижу, где была логика, а где — просто рефакторинг. Это также позволяет использовать инструменты типа `semantic-release` для автоматического определения версии.

#### 3. Pull Request (PR) и Code Review
PR — это не просто «просьба влить код», это этап **Knowledge Sharing** (обмена знаниями).

*   **Описание PR:** Я всегда пишу подробное описание: *Что сделано? Зачем? Как тестировать? Какие есть риски?* (желательно со ссылкой на задачу в Jira/YouTrack).
*   **Процесс ревью:** 
    *   Минимум один (лучше два) аппрува от коллег.
    *   Ревьюер смотрит не только на синтаксис, но и на архитектуру, соблюдение принципов SOLID и покрытие тестами.
    *   Если найдены замечания — создается новый коммит в ту же ветку, и ревью повторяется.

**Почему так?** Ревью находит ошибки, которые пропустили тесты, и гарантирует, что код соответствует единому стилю команды. Это предотвращает появление «черных ящиков», которые понимает только один разработчик.

#### 4. CI/CD и Релизный цикл
Перед тем как PR будет влит в `main`, он должен пройти через **CI Pipeline**:
1.  **Linting/Static Analysis:** Проверка стиля (PHP-CS-Fixer) и статического анализа (PHPStan/Psalm).
2.  **Unit/Integration Tests:** Запуск всей пирамиды тестов.
3.  **Build:** Сборка Docker-образа или артефакта.

**Процесс релиза:**
*   После влития в `main` происходит автоматический деплой на **Staging/Pre-production** окружение.
*   Там проводится финальное ручное тестирование (QA) или автоматизированные E2E-тесты.
*   Если всё ок — деплой на **Production**.

**Почему так?** Мы минимизируем человеческий фактор. Если тесты упали — код не попадет в `main`. Если тесты прошли, но на стейджинге всё сломалось — мы поймали проблему до того, как её увидел клиент.

#### Резюме: Почему именно так?
Этот процесс превращает разработку из «написания кода» в **«производство надежного программного продукта»**. Он может казаться медленным на этапе написания одной фичи, но он экономит недели времени на исправлении багов, откатах и разборе инцидентов на продакшене.

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

### Рассуждение

Этот вопрос — проверка не только моей технической экспертизы, но и **Soft Skills**. На позиции Senior/Lead разработчика код-ревью — это не «экзамен» для младшего коллеги, а инструмент обучения, поддержания качества и формирования инженерной культуры.

Если я буду подходить к ревью как «надзиратель», я убью мотивацию команды и создам токсичную атмосферу. Если как «добрый друг», который пропускает всё подряд — я допущу технический долг. Моя цель — **конструктивный фидбек**.

Я разделю ответ на три части: приоритеты (что смотреть), методология (как писать) и конфликтология (что делать при спорах).

---

### Ответ

Для меня хороший код-ревью — это процесс, который делает код лучше, а команду — сильнее. Это не поиск ошибок, а совместный поиск лучшего решения.

#### 1. На что я смотрю в первую очередь (Приоритеты)

Я не трачу время на обсуждение того, где стоит пробел (это должна делать автоматика), я фокусируюсь на архитектуре и рисках. Мои приоритеты:

1.  **Корректность и бизнес-логика:** Решает ли этот код поставленную задачу? Нет ли логических дыр (edge cases), которые приведут к неверным данным?
2.  **Архитектура и SOLID:** Не нарушает ли этот код границы слоев? Не превращается ли новый класс в «Божественный объект»? Соблюден ли принцип единственной ответственности?
3.PR** (Reliability/Safety):** Есть ли обработка исключений? Что произойдет, если упадет база или стороннее API? Нет ли здесь Race Condition или утечки памяти?
4.  **Тестируемость:** Можно ли протестировать этот код? Если нет — значит, он слишком сильно связан с окружением (слишком много зависимостей).
5.  **Читаемость и поддерживаемость:** Поймет ли другой разработчик этот код через полгода? Насколько понятны имена переменных и структура методов?

#### 2. Как я маркирую замечания (Методология)

Чтобы ревью не выглядело как поток критики, я использую систему маркировки (часто называемую **Conventional Comments**). Это помогает автору понять, является ли мое замечание критичным или это просто совет.

*   **`[BLOCKER]` / `[MUST]`**: Критическая ошибка, баг или серьезное нарушение архитектуры. Код не может быть влит, пока это не будет исправлено.
*   **`[SUGGESTION]` / `[QUESTION]`**: «Мне кажется, здесь можно сделать лучше, но решение за тобой». Это не блокирует PR, а предлагает альтернативу.
*   **`[NIT]` (Nitpick)**: Мелкие замечания по стилю или синтаксису. «Тут лучше использовать `match` вместо `switch`». Это не критично, автор может проигнорировать.
*   **`[PRAISE]`**: Обязательно! Если я вижу изящное решение или хорошо написанный тест — я пишу об этом. Это создает позитивную обратную связь.

**Пример:**
> `[SUGGESTION] @ivan, здесь можно использовать nullsafe operator, чтобы сократить цепочку проверок.`
> `[BLOCKER] @ivan, здесь нет обработки исключения при вызове API, это может уронить весь процесс.`

#### 3. Как я поступаю при разногласии с автором

Конфликты на ревью — это нормально. Моя задача — перевести спор из плоскости «я прав, а ты нет» в плоскость «как будет лучше для проекта».

1.  **Аргументация через «Почему»:** Я никогда не говорю «сделай так». Я говорю: «Если мы сделаем так, то возникнет проблема X, потому что...». Я апеллирую к принципам (SOLID, DRY) или к производительности.
2.  **Выход из дискуссии в офлайн:** Если мы спорим в комментариях больше 3-4 итераций — **стоп**. Мы переходим в Slack или созваниваемся. Текст часто лишен интонации, и дискуссия может превратиться в токсичный спор. Живой разговор решает 90% проблем.
3.  **Принятие решения (Escalation):** Если мы не можем прийти к консенсусу, я не пытаюсь «продавить» свою волю. Я предлагаю вынести вопрос на обсуждение техлида или архитектора. 
4.  **Принцип «Disagree and Commit»:** Если решение принято (не моим, а лидом или командой), я принимаю его и работаю дальше. Моя задача — не быть правым, а чтобы продукт был качественным.

### Рассуждение

Прежде чем отвечать, я должен внести важную техническую правку. В PostgreSQL **не существует команды `FORCE INDEX`**. Эта конструкция характерна для MySQL. 

В PostgreSQL управление использованием индексов работает иначе. Планировщик (Query Planner) в Postgres считается одним из самых умных и самодостаточных в мире реляционных БД. Он основывается на статистике, собранной через команду `ANALYZE`, чтобы решить, использовать индекс или выполнить `Sequential Scan`.

Если разработчик пытается «заставить» Postgres использовать индекс (аналог `FORCE INDEX` в MySQL), он делает это не через синтаксис запроса, а через изменение параметров планировщика или манипуляцию стоимостью (cost) операций.

Я разберу, как на самом самом деле «управлять» индексами в PostgreSQL и почему попытки насильно заставить БД использовать индекс — это чаще всего признак архитектурной проблемы.

---

### Ответ

В PostgreSQL нет прямой директивы `FORCE INDEX`. Если вы встретите такое в коде, работающем с Postgres, это либо ошибка, либо использование специфического расширения/прослойки. 

Тем не менее, если планировщик выбирает неэффективный план (например, делает `Seq Scan` там, где индекс был бы быстрее), у инженера есть три пути «принуждения».

#### 1. Использование расширения `pg_hint_plan`
Это единственный способ в PostgreSQL добиться поведения, максимально похожего на `FORCE INDEX`. Это внешнее расширение, которое позволяет вставлять специальные комментарии в SQL-запрос.

*   **Как это работает:**
    ```sql
    /*+ IndexScan(users user_email_idx) */
    SELECT * FROM users WHERE email = 'test@example.com';
    ```
*   **Когда применять:** Крайне редко. Только если вы точно знаете, что статистика БД ошибочна, а запрос критически важен для производительности.

#### 2. Изменение параметров стоимости (Cost Constants)
Планировщик выбирает план на основе весов. Например, он «думает», что чтение с диска стоит дорого, а чтение индекса — дешево. Если он ошибается, можно подкрутить параметры сессии.

*   **Пример:** Если Postgres упорно избегает индекса, можно временно снизить `random_page_cost` (стоимость случайного чтения), чтобы сделать использование индексов более «привлекательным» для планировщика.
    ```sql
    SET random_page_cost = 1.1; -- Сделать индекс более выгодным
    ```

#### 3. Исправление причин (Правильный путь)
В 99% случаев, когда разработчик хочет «зафорсить» индекс, проблема не в планировщике, а в данных или запросе. Вместо `FORCE INDEX` я буду делать следующее:

*   **Обновление статистики:** Если данные сильно изменились, планировщик может не знать о них. Решение: `ANALYZE table_name;`.
*   **Исправление типа данных:** Если в `WHERE` используется функция над колонкой (например, `WHERE LOWER(email) = ...`), обычный индекс не сработает. Решение: **Функциональный индекс** (`CREATE INDEX ON users (LOWER(email))`).
*   **Пересмотр структуры запроса:** Иногда `Seq Scan` — это на самом деле самый быстрый путь, если запрос возвращает 80% таблицы. В этом случае «форсинг» индекса только замедлит работу.

#### Сводная таблица подходов

| Метод | Когда использовать | Риски |
| :--- | :--- | :--- |
| **`pg_hint_plan`** | Когда статистика БД явно ошибается, а запрос критичен. | Привязка к расширению, хрупкость кода при изменении схемы. |
| **Настройка `cost`** | Когда нужно глобально изменить поведение планировщика. | Может замедлить все остальные запросы в системе. |
| **Функциональные индексы** | Когда в `WHERE` используются функции или преобразования типов. | Увеличение времени записи (INSERT/UPDATE). |
| **`ANALYZE`** | Когда данные в таблице резко изменились (массовый импорт). | Почти нет, это стандартная процедура обслуживания. |

**Мой вердикт:** В PostgreSQL я никогда не буду пытаться «форсить» индекс как первой мерой. Мой первый шаг — `EXPLAIN ANALYZE`, чтобы понять, почему планировщик считает этот путь невыгодным, и последующее исправление статистики или создание правильного (функционального) индекса.

## Q25 · Провокации

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

### Рассуждение

Этот вопрос — классическая проверка на понимание того, как работает движок Zend (PHP). Многие ошибочно полагают, что `strict_types=1` — это какая-то тяжелая надстройка, которая добавляет «проверку типов» во время выполнения (runtime) через сложные алгоритмы.

На самом деле, важно понимать разницу между **Coercive Mode** (режим приведения типов по умолчанию) и **Strict Mode**.

В режиме по умолчанию (Coercive) PHP всё равно делает проверки. Когда вы передаете строку `"10"` в функцию `function(int $a)`, PHP не просто «верит» вам. Он выполняет внутреннюю операцию проверки и приведения: *«Является ли эта строка числом? Да. Могу ли я безопасно превратить её в int? Да. Делаю преобразование»*. Это занимает процессорное время.

В режиме `strict_types=1` PHP вместо преобразования просто выполняет проверку: *«Совпадает ли тип переданного значения с типом в объявлении? Нет. Выбрасываю TypeError»*.

Поэтому, с технической точки зрения, **`strict_types=1` может даже немного УСКОРИТЬ выполнение кода**, так क्योंकि PHP не тратит ресурсы на попытки преобразовать типы (coercion).

---

### Ответ

Если отвечать прямо: **`strict_types=1` не замедляет выполнение кода. В некоторых сценариях он может его даже ускорить.**

Цифры в процентах (например, «замедление на 5%») будут неверными, потому так как влияние этой директивы на CPU практически ничтожно. Весь вопрос здесь не в производительности, а в **предсказуемости и надежности**.

#### Почему это не замедляет код?

1.  **Механизм проверки:** В обоих режимах PHP обязан проверить тип аргумента. В режиме `coercive` он делает проверку + преобразование. В режиме `strict` он делает только проверку. С точки зрения жизненного цикла инструкции в Zend Engine, это две разные ветки одного и тогого процесса проверки типов.
2.  **OpCache:** При использовании OpCache (который включен на любом production-сервере) структура байт-кода оптимизируется. Типизация — это часть сигнатуры функции, и она обрабатывается на очень низком уровне.

#### Почему тогда возникают мифы о замедлении?

Замедление может ощущаться только в одном, очень специфичном случае: **если ваш код изначально был написан с расчетом на «магию» приведения типов.**

Если ваш бизнес-процесс строится на том, что вы постоянно передаете строки вместо чисел и надеетесь, что PHP их «проглотит», то переход на `strict_types` не замедлит код, а просто **сломает его**. Разработчики могут интерпретировать «код перестал работать» как «код стал работать медленнее/хуже».

#### Мой вердикт как инженера:

Для меня использование `strict_types=1` — это **обязательный стандарт** в профессиональной разработке. 

*   **С точки зрения производительности:** Разница между режимами стремится к нулю.
*   **С точки зрения надежности:** Выигрыш колоссальный. Вы ловите ошибки типизации на этапе написания кода или в Unit-тестах, а не когда в продакшене в базу прилетает `"10.5"` вместо `10`.

**Резюме:** Если вы боитесь использовать `strict_types` из-за производительности — вы боитесь призрака. Настоящая производительность — это когда ваш код работает предсказуемо и не тратит ресурсы на неявные преобразования типов, которые трудно отследить.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

### Рассуждение

Этот вопрос — отличная проверка на то, понимает ли разработчик, как работают абстракции. 

Сначала я должен сделать важное уточнение: утверждение, что «Doctrine **не поддерживает** составные первичные ключи» — **технически неверно**. Doctrine **поддерживает** составные ключи (Composite Primary Keys). Вы можете пометить два поля атрибутом `#[Id]`, и Doctrine будет работать с ними как с единым ключом.

Однако, когда спрашивают «почему не поддерживает», обычно имеют в виду, что в Doctrine (и в паттерне Data Mapper в целом) **составные ключи являются «граблями»**. Они создают массу неудобств при проектировании, работе с ассоциациями и интеграции с другими библиотеками.

Я разделю ответ на три части: почему это неудобно, как это на самом деле работает и как опытные разработчики обходят эту проблему.

---

### Ответ

Технически Doctrine позволяет использовать составные ключи, но на практике это считается **антипаттерном** в архитектуре приложения, использующего Data Mapper.

#### 1. Почему это считается «проблемой» (Проблемы составных ключей)

Проблема не в самой базе данных, а в том, как ORM управляет объектами в памяти (Identity Map).

*   **Сложность работы с ассоциациями:** Если сущность `OrderItem` имеет составной ключ `(order_id, item_id)`, то любая другая сущность, которая хочет ссылаться на `OrderItem` (например, `Shipment`), должна будет иметь **два** поля для связи вместо одного. Это раздувает количество колонок в таблицах и усложняет SQL-запросы.
*   Embarrassing Complexity в коде: Чтобы найти объект, вам нужно передавать массив или специальный объект-ключ, а не просто `int $id`. Это усложняет методы типа `find()`, `remove()` и работу с репозиториями.
*   Проблемы с типизацией и DTO: При маппинге данных из API или форм вам приходится постоянно работать с вложенными структурами, что увеличивает вероятность ошибок.
*   Нарушение принципа единственной ответственности (SRP) для идентификатора: Идентификатор становится «тяжелым» и несет в себе данные, что противоречит идее, что ID должен быть просто непрозрачным указателем.

#### 2. Как это работает в Doctrine (Техническая часть)

Если вам всё же необходимо использовать составной ключ, Doctrine позволяет это сделать так:

```php
#[ORM\Entity]
class OrderItem {
    #[ORM\Id]
    #[ORM\ManyToOne(targetEntity: Order::class)]
    private Order $order;

    #[ORM\Id]
    #[ORM\Column]
    private int $itemNumber;
}
```

В этом случае Doctrine будет использовать оба поля для идентификации объекта в `UnitOfWork`. Но вы столкнетесь с тем, что методы `EntityManager::find()` будут требовать массив: `$em->find(OrderItem::class, ['order' => $order, 'itemNumber' => 1])`. Это неудобно.

#### 3. Как с этим «живут» в реальных проектах (Best Practices)

В качественных проектах (особенно в DDD) мы практически никогда не используем составные ключи. Вместо этого мы применяем следующие стратегии:

**Стратегия А: Использование Surrogate Key (Суррогатный ключ) — Основной метод**
Это золотой стандарт. Мы добавляем к каждой таблице искусственный, технический первичный ключ (обычно `UUID` или `BIGINT AUTO_INCREMENT`), который никак не связан с бизнес-данными.

*   **Как это выглядит:** У вас есть `order_id` (PK, surrogate) и, если нужно, уникальный составной индекс `UNIQUE(order_id, item_number)` для обеспечения бизнес-правила.
*   **Плюсы:** Все связи (Foreign Keys) работают через один простой `id`. Код чистый, ассоциации работают идеально.
*   **Минусы:** В базе данных появляется «лишняя» колонка, которая не несет бизнес-смысла. Но для производительности и удобства разработки это ничтожная цена.

**Стратегия Б: Использование UUID**
В распределенных системах или микросервисах вместо инкрементальных ID я использую `UUID`. 

*   **Почему:** Это решает проблему генерации ID на стороне приложения (до записи в БД) и позволяет легко объединять данные из разных источников без конфликтов ключей.

**Резюме:**
В Doctrine составные ключи поддерживаются, но они **враждебны к удобству разработки и чистоте архитектуры**. В реальных проектах я всегда выбираю **Surrogate Key (UUID или ID)** для первичного ключа и использую **Unique Constraints** для реализации бизнес-логики уникальности комбинаций полей. Это делает систему предсказуемой, простой в тестировании и легкой в масштабировании.

## Q27 · Мини-код-ревью

**Интервьюер:** Посмотри на этот код:

```php
class OrderController
{
    public function pay(Request $req): Response
    {
        $id = $req->get('order_id');
        $pdo = DB::connect();
        $order = $pdo->query("SELECT * FROM orders WHERE id = $id")->fetch();
        if (!$order) {
            return new Response('not found', 404);
        }
        $order['status'] = 'paid';
        $pdo->exec("UPDATE orders SET status = 'paid' WHERE id = $id");
        Mailer::send($order['email'], 'Ваш заказ оплачен');
        (new Logger())->log('paid ' . $id);
        return new Response('ok');
    }
}
```

Какие проблемы ты видишь и как бы ты этот код переделал? С чего начал бы и почему?

**Кандидат:**

### Рассуждение

Этот код — классический пример «антипаттерна God Method» в контроллере. Он нарушает практически все принципы проектирования: SOLID, DRY, KISS и принципы безопасности.

Если я просто начну переписывать его по строчкам, я сделаю это неправильно. **Я должен начать с определения того, что здесь не так на уровне архитектуры.**

**Основные проблемы (по порядку критичности):**
1.  **Безопасность (SQL Injection):** Переменная `$id` вставляется напрямую в строку запроса. Это критическая уязвимость.
2.  **Нарушение слоев (Architecture Violation):** Контроллер делает всё: работает с HTTP, работает с БД (через PDO), занимается бизнес-логикой (смена статуса) и инфраструктурой (Mailer, Logger). Это «толстый контроллер».
3.  **Отсутствие атомарности (Transaction Risk):** Статус меняется в БД, а письмо отправляется отдельно. Если `Mailer::send` упадет, заказ в базе будет помечен как `paid`, но пользователь не получит подтверждение. Или наоборот: если мы сначала отправим письмо, а база упадет — пользователь получит письмо о заказе, которого нет.
4.  **Тестируемость (Testability):** Этот код невозможно протестировать Unit-тестами. Он жестко завязан на глобальные состояния (`DB::connect()`, `Mailer::send()`, `new Logger()`).
5.  **Нарушение инкапсуляции:** Данные хранятся в массиве `$order`, а не в объекте. Мы не контролируем инварианты (например, можно ли перевести заказ из `CANCELLED` в `PAID`).

---

### Решение

Я бы начал не с исправления SQL, а с **разделения ответственности**. Я вынесу логику из контроллера в **Application Service** (или Command Handler) и **Domain Model**.

#### Шаг 1: Создание Доменного слоя (Domain Layer)
Создадим сущность `Order`, которая будет управлять своим состоянием.

```php
// Domain/Entity/Order.php
class Order {
    private int $id;
    private string $status;
    private string $email;

    public function __construct(int $id, string $status, string $email) {
        $this->id = $id;
        $this->status = $status;
        $this->email = $email;
    }

    public function pay(): void {
        if ($this->status === 'paid') {
            throw new DomainException("Order is already paid");
        }
        // Здесь можно добавить проверку: можно ли вообще оплатить этот заказ
        $this->status = 'paid';
    }

    public function getId(): int { return $this->id; }
    public function getEmail(): string { return $this->email; }
    public function getStatus(): string { return $this->status; }
}
```

#### Шаг 2: Создание инфраструктурных интерфейсов
Мы не будем использовать статические методы `Mailer::send`. Мы создадим интерфейсы.

```php
// Domain/Service/MailerInterface.php
interface MailerInterface {
    public function send(string $to, string $message): void;
}

// Domain/Repository/OrderRepositoryInterface.php
interface OrderRepositoryInterface {
    public function find(int $id): ?Order;
    public function save(Order $order): void;
}
```

#### Шаг 3: Создание Application Service (Use Case)
Этот слой будет оркестрировать процесс и управлять транзакцией.

```php
// Application/Service/PayOrderService.php
class PayOrderService {
    public function __construct(
        private OrderRepositoryInterface $repository,
        private MailerInterface $mailer,
        private LoggerInterface $logger,
        private TransactionManager $transactionManager // Абстракция над транзакциями
    ) {}

    public function execute(int $orderId): void {
        $this->transactionManager->transactional(function() use ($orderId) {
            $order = $this->repository->find($orderId);
            if (!$order) {
                throw new OrderNotFoundException($orderId);
            }

            $order->pay(); // Бизнес-логика внутри сущности
            $this->repository->save($order); // Сохранение
            
            // Мы не отправляем письмо ТУТ, если хотим 100% надежности.
            // Лучше использовать Domain Events и Messenger, 
            // но для простоты примера отправим после транзакции.
        });

        // Отправляем письмо ТОЛЬКО после успешного commit транзакции
        $this->mailer->send($order->getEmail(), 'Ваш заказ оплачен');
        $this->logger->info("paid " . $orderId);
    }
}
```

#### Шаг 4: Чистый Контроллер
Теперь контроллер стал тонким. Его задача — принять запрос и вызвать сервис.

```php
// Presentation/Controller/OrderController.php
class OrderController extends AbstractController 
{
    public function __construct(
        private PayOrderService $payOrderService
    ) {}

    public function pay(Request $req): Response
    {
        $id = (int) $req->get('order_id'); // Приведение к типу

        try {
            $this->payOrderService->execute($id);
            return new Response('ok');
        } catch (OrderNotFoundException $e) {
            return new Response('not found', 404);
        } catch (DomainException $e) {
            return new Response($e->getMessage(), 400);
        } catch (\Exception $e) {
            return new Response('internal error', 500);
        }
    }
}
```

### Что изменилось и почему это лучше?

1.  **Безопасность:** Мы используем `OrderRepository`, который внутри использует **Prepared Statements**. SQL-инъекция невозможна.
2.  **Атомарность:** Благодаря `TransactionManager`, если `save()` не сработает, статус не изменится. Письмо не уйдет, если транзакция не зафиксирована.
3.  **Тестируемость:** Теперь я могу написать Unit-тест для `PayOrderService`, подставив ему `MockOrderRepository` и `MockMailer`. Мне не нужна база данных, чтобы проверить логику оплаты.
4.  **Соблюдение SOLID:**
    *   **SRP:** Контроллер отвечает за HTTP, Сервис — за сценарий, Сущность — за бизнес-правила.
    *   **DIP:** Сервис зависит от интерфейсов (`MailerInterface`), а не от конкретных реализаций.
5.  **Предсказуемость:** Бизнес-правила инкапсулированы в объекте `Order`. Никто не сможет перевести заказ в статус `paid` в обход метода `pay()`.

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

### Рассуждение

Этот код — классический пример того, как смешивание уровней ответственности (Layer Violation) разрушает архитектуру. Главная ошибка здесь в том, что **доменная сущность пытается управлять своей сохраненностью**.

В DDD сущность — это «умный» объект, который содержит бизнес-логику и инварианты, но она **не должна знать о существовании инфраструктуры** (базы данных, ORM, EntityManager).

**Основные нарушения:**
1.  **Нарушение Dependency Inversion Principle (DIP):** Сущность зависит от `EntityManagerInterface`. Это инфраструктурный объект. Теперь ваш доменный слой жестко привязан к Doctrine. Вы не сможете протестировать эту сущность без поднятия всего контейнера Symfony или сложных моков.
2.  **Нарушение Single Responsibility Principle (SRP):** Сущность отвечает и за бизнес-правила (смена email), и за процесс синхронизации своего состояния с базой данных (`$this->em->flush()`).
3.  **Нарушение инкапсуляции и чистоты домена:** Сущность становится «грязной». Она превращается из чистого представления бизнес-логики в объект, который сам управляет своим жизненным циклом в БД.
4.  **Проблема Unit-тестирования:** Чтобы протестировать простой метод `changeEmail`, вам придется создавать мок для `EntityManager`, что делает тесты тяжелыми и избыточными.

---

### Ответ

#### Как я бы исправил эту сущность

В чистой архитектуре сущность должна быть максимально «глупой» в плане инфраструктуры и «умной» в плане бизнеса. Она должна только менять свое внутреннее состояние. Сохранением должен заниматься внешний слой (Application Service или Repository).

**Правильный вариант:**

```php
// Domain/Entity/User.php
#[ORM\Entity]
class User
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 255, unique: true)]
    private string $email;

    public function __construct(string $email)
    {
        // Здесь можно добавить валидацию email через Value Object
        $this->email = $email;
    }

    public function changeEmail(string $newEmail): void
    {
        // 1. Бизнес-валидация (инвариант)
        if (!filter_var($newEmail, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidEmailException("Invalid email format");
        }

        // 2. Изменение состояния
        $this->email = $newEmail;
        
        // ВАЖНО: Мы НЕ вызываем здесь flush(). 
        // Мы просто меняем состояние объекта в памяти.
    }

    public function email(): string
    {
        return $this->email;
    }
    
    public function getId(): ?int
    {
        return $this->id;
    }
}
```

**Как это работает в связке с Application Layer:**

Теперь за сохранение отвечает сервис, который управляет транзакцией.

```php
// Application/Service/ChangeEmailService.php
class ChangeEmailService
{
    public function __construct(
        private UserRepository $userRepository,
        private EntityManagerInterface $entityManager
    ) {}

    public function execute(int $userId, string $newEmail): void
    {
        // 1. Загружаем сущность через репозиторий
        $user = $this->userRepository->find($userId);
        
        if (!$user) {
            throw new UserNotFoundException();
        }

        // 2. Выполняем бизнес-действие
        $user->changeEmail($newEmail);

        // 3. Сохраняем изменения (Unit of Work)
        // EntityManager сам поймет, что объект изменился, и сделает UPDATE
        $this->entityManager->flush();
    }
}
```

#### Что изменилось и почему это лучше:

1.  **Чистота домена:** `User` теперь не зависит от Doctrine. Его можно протестировать обычным `new User(...)` за микросекунды без всяких моков.
2.  **Разделение ответственности:** Сущность отвечает за **правила** (можно ли менять email), а сервис — за **процесс** (найти, изменить, сохранить).
3.  **Управление транзакциями:** Теперь мы можем обернуть вызов сервиса в транзакцию. Если после смены email нам нужно будет отправить уведомление или обновить профиль в другом сервисе, мы сможем сделать это атомарно. В старом варианте `flush()` внутри метода делал невозможным откат транзакции.
4.  **Предсказуемость:** Мы точно знаем, когда данные попадут в базу — только тогда, когда Application Service вызовет `flush()`. В старом варианте вызов любого метода сущности мог внезапно вызвать запрос к БД.

Это один из самых важных вопросов для Senior-разработчика. Он проверяет не только техническую экспертизу, но и **умение управлять рисками и временем**. 

Если я буду сидеть над задачей три дня в молчании — я подвожу бизнес. Если я буду бежать к коллегам при первой же ошибке — я буду бесполезен для команды. Мой подход — это структурированный процесс исследования.

### 1. Алгоритм решения новой задачи

Я разделяю процесс на четыре этапа: **Изучение $\rightarrow$ Гипотеза $\rightarrow$ Проверка $\rightarrow$ Оценка.**

#### Этап 1: Исследование (Research & Context)
Прежде чем писать код, я должен понять контекму.
*   **Изучение документации:** Я читаю официальную документацию (official docs), а не только StackOverflow. Мне нужно понять концепции, а не только синтаксис.
*   **Анализ существующего кода:** Как эта технология уже используется в нашем проекте? Какие паттерны мы применяем? (Это помогает не изобретать велосипед и соблюдать архитектуру).

Я не пытаюсь внедрить решение сразу в основной проект.
*   **Создание POC (Proof of Concept):** Я создаю минимальный, изолированный проект (sandbox), где пробую применить технологию.
*   **Проверка гипотезы:** Если я думаю, что библиотека `X` решит нашу проблему, я пишу микро-скрипт, который проверяет именно этот сценарий.

#### Этап 3: Анализ рисков и ограничений
Когда я понял, как это работает, я ищу «подводные камни»:
*   **Производительность:** Как это повлияет на CPU/RAM/DB?
*   **Безопасность:** Есть ли известные уязвимости?
*   **Поддержка:** Насколько это сложно будет поддерживать нашей команде?

#### Этап 4: Формирование ответа и сроков
Только после этих этапов я даю ответ. Мой ответ не будет: *"Я сделаю это за 2 дня"*. Он будет структурированным:
> «Я изучил задачу. Нам нужно внедрить `X`. Я провел POC, решение рабочее. Основная сложность в интеграции с нашей БД, на что уйдет около 4 часов. Итого, я оцениваю задачу в 2 дня, включая написание тестов и рефакторинг. Если мы выберем вариант `Y`, это займет 4 дня, но будет надежнее».

---

### 2. Когда разбираться самому, а когда просить помощи?

Я использую правило **«Золотого часа»** и принцип **«Ценности времени»**.

#### Когда разбираться самому:
*   **Первые 30-60 минут:** Я всегда даю себе время на самостоятельный поиск. Это время на «прогрев» мозга и работу с документацией.
*   **Когда проблема в синтаксисе или стандартной библиотеке:** Это базовые навыки, которые я должен уметь решать самостоятельно.
*   **Когда проблема в «незнакомом, но понятном»:** Если я понимаю концепцию, но просто не знаю названия функции — я ищу это сам.

#### Когда просить помощи (Escalation):
Я обращаюсь к команде или лиду в трех случаях:

1.  **Тупик (The Wall):** Если я потратил 1-2 часа, изучил документацию, попробовал три разных подхода, но всё равно не понимаю, *почему* это не работает. Дальше я просто трачу деньги компании впустую.
2.  **Архитектурная неопределенность:** Если решение технически возможно, но я не уверен, вписывается ли оно в наши архитектурные принципы. Лучше обсудить концепцию *до* написания кода, чем переделывать готовый.
3.  **Высокий риск (High Risk):** Если задача затрагивает критически важные части системы (платежи, ядро БД), я прошу «второе мнение» (peer review) еще на этапе планирования, чтобы минимизировать риск катастрофы.

**Мое правило коммуникации:** Я никогда не прихожу к коллеге с вопросом: *"Я не понимаю, как это работает"*. Я прихожу с вопросом: *"Я попробовал подходы А и Б, столкнулся с проблемой В, документация говорит X, но на практике получается Y. Что ты об этом думаешь?"*. 

**Это превращает вопрос из «просьбы о помощи» в «профессиональную дискуссию».**

*   **Новый прогноз:** Я называю реалистичную дату, основанную на новом понимании задачи.

#### 2. Анализ и предложение вариантов (Options, not Problems)
Я никогда не прихожу с проблемой, не имея предложений по её решению. Я предложу три варианта на выбор:

*   Почему я недооценил задачу?
*   Чего я не учел при первой оценке (недостаток знаний, отсутствие исследования, скрытые зависимости)?
*   Как мне изменить процесс оценки в следующий раз (например, закладывать буфер на исследование или делать Spike перед оценкой)?

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

### Рассуждение

Это, пожалуй, самый сложный вопрос в профессиональной разработке. Он бьет в корень конфликта между **инженерией** (желанием сделать идеально) и **бизнесом** (желанием получить прибыль как можно быстрее).

Если я буду стремиться к «идеальному коду» (Gold Plating), я стану «бутылочным горлышком» команды. Продукт не выйдет на рынок, конкуренты нас обгонят, а бюджет закончится на написании абстракций, которые никому не нужны.
Если я буду писать «быстро и грязно», я создам технический долг, который через полгода парализует разработку: любая новая фича будет занимать недели из-за хрупкости системы.

Мой подход базируется на понятии **«Достаточно хорошее качество» (Good Enough Quality)**, которое определяется не моим субъективным ощущением, а контекстом задачи.

---

### Ответ

Для меня баланс между качеством и скоростью — это не случайный выбор, а осознанное управление **техническим долгом**. Я использую три критерия для принятия решения.

#### 1. Контекст задачи (The Context)

Я задаю себе вопрос: «Для чего мы это делаем?»

*   **Прототип / MVP (Proof of Concept):** Здесь приоритет — **Скорость**. Если мы проверяем гипотезу, которая может не взлететь, я не буду строить сложную микросервисную архитектуру с идеальным DDD. Я напишу простой монолит, возможно, с небольшим нарушением принципов, чтобы быстро получить фидбек от рынка.
*   **Core Business Logic (Ядро системы):** Здесь приоритет — **Качество**. Если это модуль обработки платежей или расчет налогов, я буду биться за идеальный код, 100% покрытие тестами и строгую архитектуру. Ошибка здесь стоит слишком дорого.
*   **Второстепенные фичи (Admin Panel, Internal Tools):** Здесь приоритет — **Разумный компромисс**. Если это панель для админов, которая используется раз в месяц, мне не нужно строить для неё идеальную масштабируемую систему. Достаточно чистого, поддерживаемого кода, но без избыточного проектирования.

#### 2. Определение «Достаточно хорошего» (Definition of Done)

Я считаю код готовым к отдаче, когда он удовлетворяет следующим критериям:
1.  **Функциональность:** Он решает задачу, поставленную бизнесом.
2.  **Надежность:** Он покрыт тестами (Unit/Integration), которые проверяют основные сценарии и граничные случаи.
3.  **Безопасность и Производительность:** Он не создает уязвимостей и не вызывает деградацию системы (нет N+1, нет утечек памяти).
4.  **Читаемость:** Коллега сможет понять этот код без моего присутствия.

Если код соответствует этим четырем пунктам — он **готов**. Дальнейшее улучшение (например, вынос логики в еще более глубокие абстракции) — это уже не «исправление», а «полировка», которая должна планироваться отдельно.

#### 3. Управление техническим долгом (Managing Debt)

Я воспринимаю технический долг как финансовый инструмент. Его можно брать (писать быстрый код), но его нужно **возвращать**.

*   **Если я осознанно иду на компромисс** (например, пишу простой код, чтобы успеть к дедлайну), я обязательно:
    1.  Оставляю `// TODO: Refactor` с пояснением, почему сделано именно так.
    2.  Создаю задачу в бэклоге на рефакторинг этой части.
