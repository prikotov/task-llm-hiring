## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

### Рассуждение

Когда звучит вопрос о «самых важных возможностях», важно не свалиться в перечисление синтаксического сахара. Для опытного разработчика «чистый и надёжный код» — это код, который:
1. **Минимизирует неопределенность** (type safety).
2. **Снижает когнитивную нагрузку** (меньше лишнего текста — легче читать суть).
3. **Предотвращает ошибки на этапе написания**, а не во время исполнения (fail fast).

Если я буду говорить про `match` или `readonly`, это будет правильно, но я должен обосновать их через призму надежности. 

Я выделю четыре ключевых направления:
1. **Строгая типизация и уменьшение возможности `null`**: Это база для надежности. Раньше мы боролись с `null` повсюду, теперь язык дает инструменты, чтобы сделать это явным или невозможным.
2. **Снижение бойлерплейта (шаблонного кода)**: Чем меньше кода пишет разработчик, тем меньше мест, где он может ошибиться.
3. **Улучшение структур управления данными**: Замена громоздких `switch/case` на более строгие конструкции.
4. **Property Promotion и Readonly**: Это радикально меняет то, как мы описываем DTO (Data Transfer Objects) и Value Objects.

---

### Ответ

Для меня «чистота» — это когда структура кода максимально прозрачна и защищена от неверных состояний. Вот мой топ возможностей, которые в корне изменили подход к написанию бэкенда.

#### 1. Constructor Property Promotion и Readonly-классы
До PHP 8.0 описание DTO превращалось в бесконечные полотна из приватных свойств и конструкторов. Теперь мы можем описывать данные максимально лаконично. А `readonly` гарантирует неизменяемость (immutability), что критично для Value Objects в DDD.

```php
// До PHP 8.0: 20+ строк кода
// В PHP 8.2+: 
readonly class UserDto
{
    public function __construct(
        public int $id,
        public string $email,
        public DateTimeImmutable $createdAt,
    ) {}
}

// Использование: невозможно изменить email после создания, что гарантирует надежность данных.
```

#### 2. Union Types и Intersection Types
Это мощнейший инструмент для борьбы с неопределенностью. Union Types (`int|string`) позволяют явно описать варианты, а Intersection Types (`Iterator&Countable`) — требовать от объекта соблюдения сразу нескольких контрактов, что делает интерфейсы более строгими.

```php
// Union Types: четко говорим, что может прийти
public function processIdentifier(int|string $id): void { /* ... */ }

// Intersection Types: объект ОБЯЗАН реализовывать оба интерфейса
public function execute(Iterator&Countable $collection): void { /* ... */ }
```

#### 3. Match Expression
В отличие от `switch`, `match` — это выражение (expression), а не инструкция. Оно возвращает значение и, что самое важное, оно **строго проверяет типы** и требует обработки всех вариантов (exhaustive check). Это избавляет от классических ошибок, когда забыли добавить `break` или не обработали ветку `default`.

```php
// match возвращает результат и работает через строгое сравнение (===)
$statusLabel = match ($status) {
    Status::Active => 'Пользователь активен',
    Status::Pending => 'Ожидание подтверждения',
    Status::Banned  => 'Заблокирован',
    default         => throw new \InvalidArgumentException("Неизвестный статус: $status"),
};
```

#### 4. Nullsafe Operator
Это не просто «синтаксический сахар», это защита от `Fatal error: Uncaught Error: Call to a member function ... on null`. Он позволяет писать цепочки вызовов, которые безопасно «проваливаются» в `null`, если промежуточное звено отсутствует. Это делает код чище, избавляя от бесконечных проверок `if ($user !== null && $user->getAddress() !== null...)`.

```php
// Вместо нагромождения IF-ов:
$street = $user?->getAddress()?->getStreet();

// Если user или address — null, $street просто станет null, без ошибки.
```

**Итог:** Эти фичи позволяют мне сместить фокус с «защиты от ошибок типизации» на «реализацию бизнес-логики». Мы создаем систему, где ошибка типа или попытка изменить неизменяемый объект отсекаются еще на этапе статического анализа или компиляции.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

### Рассуждение

Вопрос про систему типов в PHP — это классическая проверка на то, понимает ли разработчик разницу между «языком, который работает» и «языком, который работает предсказуемо». 

Прежде всего, я должен прояснить важную предпосылку: PHP — это язык с **динамической типизацией**, но с возможностью **строгой типизации** на уровне объявлений. Это принципиально важно. В отличие от Java или C#, где тип переменной жестко привязан к ней с момента создания, в PHP тип привязан к *ожиданию* (сигнатуре функции или свойства).

При разборе я разделю ответ на три уровня:
1. **Механика приведения (Coercive mode):** как PHP пытается «быть добрым» и подстроить типы под сигнатуру.
2. **Строгий режим (`strict_types`):** как мы отключаем эту «доброту» для предсказуемости.
3. **Ловушки:** где даже со `strict_types` можно обжечься (например, с `null` и дженериками, которых в PHP нативно нет).

Я также разберу кейс с `mixed` и `null`, так как это самая частая причина багов в современных проектах.

---

### Ответ

Система типов в PHP работает в двух режимах: **коэрцитивном** (мягком) и **строгом**.

#### 1. Коэрцитивный режим (по умолчанию)
Если не указать `declare(strict_types=1);`, PHP будет пытаться привести входящие данные к нужному типу. Это удобно для работы с данными из `$_GET` или `$_POST`, но опасно для бизнес-логики.

```php
function setAge(int $age): void {
    echo "Age is: " . $age;
}

setAge("25"); // Работает! PHP приведет строку "25" к int 25.
setAge("abc"); // Fatal Error: TypeError (тут даже мягкий режим не спасет).
```

#### 2. Режим `strict_types=1`
Когда мы добавляем эту директиву (она должна быть в каждом файле), PHP перестает «угадывать». Если тип не совпадает идеально — выбрасывается `TypeError`. 

**Важный нюанс:** `strict_types` работает для **вызовов** функций в том файле, где написан вызов, а не в том, где объявлена функция. Это часто путает разработчиков.

```php
// File: functions.php
declare(strict_types=1);
function add(int $a, int $b): int { return $a + $b; }

// File: main.php
require 'functions.php';

add(1, 2);      // OK
add(1, "2");    // TypeError! (потому что вызов в main.php, где strict_types может не быть, но функция требует строгости)
```

#### 3. Типичные ловушки

**Ловушка №1: `null` и отсутствие Nullable-типов**
До PHP 8.0 мы использовали знак вопроса `?int`. В PHP 8.0+ появились Union Types. Ошибка новичков — передать `null` в параметр, который не помечен как `?` или не включает `null` в Union Type.

```php
function process(int $id): void {}

process(null); // Fatal Error. Нужно: function process(?int $id)
```

**Ловушка №2: Ложное чувство безопасности с массивами**
В PHP нет встроенных дженериков. Я могу написать `array $users`, но я не могу заставить PHP проверять, что внутри массива лежат именно объекты `User`. Это решается только на уровне статического анализа (PHPStan/Psalm).

**Ловушка №3: Приведение типов в `if` и сравнение `==` vs `===`**
Это классика. Использование `==` в логике — это всегда риск.

```php
$status = 0;
if ($status == "pending") { // Вернет true в некоторых старых версиях или при странных условиях
    // ...
}

// Всегда используем ===
```

#### Где типизация спасает (Пример из DDD)

Типизация спасает при проектировании **Value Objects**. Она гарантирует, что в систему не попадет «мусор».

```php
readonly class Email {
    public string $value;

    public function __construct(string $value) {
        if (!filter_var($value, FILTER_VALIDATE_EMAIL)) {
            throw new InvalidArgumentException("Invalid email");
        }
        $this->value = $value;
    }
}

// Если метод требует Email, я на 100% уверен, что внутри валидный email.
// Мне не нужно проверять строку на наличие '@' в каждом методе.
function registerUser(Email $email): void { ... }
```

#### Где типизация удивляет (Пример с `mixed` и `int`)

Иногда PHP ведет себя контринтуитивно при работе с результатами функций.

```php
function getSomething(): mixed {
    return "10";
}

$val = getSomething();
// Если я напишу:
// function check(int $n) { ... }
// check($val); 
// В режиме strict_types это упадет, хотя "10" — это число.
```

**Резюме:**
Для надежного кода я всегда использую `declare(strict_types=1);` во всех файлах, использую максимально строгие типы (избегаю `mixed`, где это возможно) и полагаюсь на **PHPStan** для проверки типов внутри массивов и коллекций. Типизация в PHP — это не только про запуск кода, это про создание контракта между компонентами системы.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

### Рассуждение

Вопрос проектирования обработки исключений — это вопрос о том, как приложение сообщает о своих сбоях и насколько легко это сообщение превратить в осмысленный ответ для пользователя или лог для разработчика.

Главная проблема в PHP-проектах — это смешивание **технических исключений** (база упала, диск переполнен) и **бизнес-исключений** (недостаточно средств на счету, пользователь уже зарегистрирован). Если их смешать, мы получим «спагетти» в блоках `catch`, где непонятно, нужно ли откатывать транзакцию или просто показать пользователю уведомление.

Я придерживаюсь стратегии разделения уровней. 
1. **Domain Exceptions:** это часть бизнес-логики. Они предсказуемы.
2. **Infrastructure/Technical Exceptions:** это внешние факторы. Они непредсказуемы.
3. **Application/Interface Exceptions:** это способ перевода ошибки в HTTP-ответ или CLI-вывод.

Я также должен затронуть вопрос «контракта метода». Хороший инженер понимает: если метод выбрасывает исключение, которое не описано в его документации/типизации, — это нарушение контракта.

---

### Ответ

Мой подход к исключениям строится на принципе **«Исключение — это не управление потоком, а сообщение о нарушении инварианта»**.

#### 1. Иерархия исключений

Я всегда разделяю исключения на две большие ветки:

*   **Domain Exceptions (Бизнес-исключения):**
    Они наследуются от специального интерфейса `DomainExceptionInterface` (или базового `DomainException`). Это ошибки, которые *могут* произойти в рамках бизнес-процесса.
    *Пример:* `InsufficientFundsException`, `UserAlreadyExistsException`.
    *Свойство:* Их можно (и нужно) перехватывать на уровне Application Layer, чтобы вернуть пользователю понятную ошибку (400 Bad Request или 422 Unprocessable Entity).

*   **Infrastructure Exceptions (Технические исключения):**
    Они наследуются от `InfrastructureExceptionInterface`. Это ошибки внешнего мира.
    *Пример:* `DatabaseConnectionException`, `ExternalApiTimeoutException`.
    *Свойство:* Их не стоит обрабатывать в бизнес-логике. Если упала база — это системная ошибка (500 Internal Server Error), которую должен поймать глобальный `ExceptionListener` в Symfony.

#### 2. Контракт метода

Контракт метода состоит из:
1. **Входных данных** (типы аргументов).
2. **Выходных данных** (возвращаемый тип).
3. **Ожидаемых исключений.**

В PHP мы не можем указать `throws` в сигнатуре метода (как в Java), поэтому я использую **PHPDoc** для документирования исключений. Если метод `transferMoney()` выбрасывает `InsufficientFundsException`, это обязана знать вызывающая сторона. Если я внезапно начну выбрасывать `PDOException` из сервиса — я нарушил контракт, так как я «протек» детали реализации инфраструктуры в домен.

#### 3. Оборачивание (Exception Wrapping)

Это критически важный паттерн. Когда я вызываю стороннюю библиотеку или API, я никогда не позволяю их исключениям "пролетать" сквозь мой слой. Я их оборачиваю.

**Зачем?** Чтобы сохранить контекст и не привязываться к сторонним классам.

```php
// Плохо: прокидываем исключение сторонней библиотеки напрямую
public function fetchData(): array {
    return $this->thirdPartyClient->get(); // Может бросить ThirdPartyException
}

// Хорошо: оборачиваем в свое исключение
public function fetchData(): array {
    try {
        return $this->thirdPartyClient->get();
    } catch (ThirdPartyException $e) {
        // Мы сохраняем исходное исключение ($e) как "previous", 
        // чтобы не потерять stack trace.
        throw new InfrastructureException("Failed to fetch data from provider", 0, $e);
    }
}
```

#### 4. Антипаттерны

Как опытный разработчик, я активно борюсь со следующими практиками:

1.  **Exceptions for Control Flow (Исключения для управления потоком):**
    Использование `try-catch` для проверки условий (например, `if (try { ... } catch (NotFoundException $e) { ... })`). Это очень дорого по производительности и делает код нечитаемым. Для логики "есть ли элемент" используйте методы типа `exists()`.

2.  **Catch-all (Перехват всего подряд):**
    `catch (\Exception $e)` без последующего анализа. Это "глушит" ошибки, которые вы не планировали обрабатывать, превращая отладку в ад. Если вы ловите `\Exception`, вы должны либо логировать её и пробрасывать дальше, либо превращать в высокоуровневое исключение.

3.  **Swallowing Exceptions (Проглатывание исключений):**
    Пустой блок `catch { }`. Это самый опасный антипаттерн. Если ошибка произошла, а система делает вид, что всё в порядке — вы получите непредсказуемое состояние данных.

4.  **Generic Exceptions (Слишком общие исключения):**
    Бросать везде `\RuntimeException`. Это не дает вызывающему коду возможности понять, *что именно* пошло не так, и как на это реагировать.

**Итог:** Моя цель — сделать так, чтобы на уровне контроллера я мог написать простой `catch (DomainException $e)` и превратить его в красивый JSON-ответ, в то время как все остальные ошибки автоматически уйдут в Sentry/ELK с полным стеком вызовов.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

### Рассуждение

Когда речь заходит о SOLID, новички часто спорят о Liskov Substitution (LSP) или Interface Segregation (ISP). Но если мы говорим о реальной «полевой» разработке, о проектах, которые живут годами и обрастают фичами, то безоговорочный лидер по нарушениям — это **Single Responsibility Principle (SRP)**.

**Почему это происходит?**
1. **Скорость разработки (Time-to-Market):** Проще дописать метод в существующий класс, чем создавать новый.
2. **«Естественное» разрастание:** Разработчик начинает с малого (например, `UserService` делает регистрацию), а через полгода этот сервис и отправляет письма, и пишет логи, и дергает стороннее API, и формирует отчеты для админки.
3. **Непонимание сути:** Часто путают «ответственность класса» с «ответственностью функции». Класс — это не просто набор функций, это единица ответственности за определенный аспект системы.

Нарушение SRP — это корень появления «Божественных объектов» (God Objects), которые сложно тестировать, страшно менять и невозможно переиспользовать.

---

### Ответ

Чаще всего в реальных проектах нарушается **Single Responsibility Principle (SRP)**. Классы превращаются в «комбайны», которые знают слишком много о разных частях системы.

#### Типовой пример нарушения (God Class)

Представь сервис, который должен регистрировать пользователя. В реальности он часто раздувается до такого состояния:

```php
class UserService
{
    public function register(array $data): void
    {
        // 1. Валидация (Логика проверки данных)
        if (empty($data['email'])) {
            throw new \InvalidArgumentException("Email is required");
        }

        // 2. Работа с БД (Инфраструктурная логика)
        // Представим, что здесь прямой вызов репозитория или даже SQL
        $user = new User($data['email'], $data['password']);
        $this->saveToDatabase($user);

        // 3. Отправка уведомлений (Внешняя коммуникация)
        mail($data['email'], "Welcome!", "Thanks for joining.");

        // 4. Логирование (Кросс-контрастная задача)
        file_put_contents('app.log', "User registered: " . $data['email'], FILE_APPEND);
    }

    private function saveToDatabase(User $user): void { /* ... */ }
}
```

**Почему это плохо?**
* **Сложность тестирования:** Чтобы протестировать только регистрацию, тебе нужно подменять почтовый сервер, файловую систему и базу данных.
* **Хрупкость:** Если изменится формат логов или способ отправки почты, тебе придется менять `UserService`. Это нарушение и принципа открытости/закрытости (OCP) тоже.
* **Низкая связность (Coupling):** Класс слишком сильно связан с почтой, БД и файловой системой.

---

#### Рефакторинг (Применение SRP и Dependency Injection)

Мы разбиваем «комбайн» на специализированные компоненты, которые взаимодействуют через интерфейсы.

```php
// 1. Выносим работу с данными в репозиторий
interface UserRepositoryInterface {
    public function save(User $user): void;
}

// 2. Выносим коммуникацию в сервис уведомлений
interface NotificationServiceInterface {
    public function sendWelcomeEmail(User $user): void;
}

// 3. Выносим логирование в стандартный PSR-3 Logger
use Psr\Log\LoggerInterface;

class UserService
{
    public function __construct(
        private UserRepositoryInterface $userRepository,
        private NotificationServiceInterface $notificationService,
        private LoggerInterface $logger
    ) {}

    public function register(UserDto $userDto): void
    {
        // Валидация теперь инкапсулирована в DTO или отдельном Validator
        $user = new User($userDto->email, $userDto->password);

        // Каждый компонент делает только свою работу
        $this->userRepository->save($user);
        $this->notificationService->sendWelcomeEmail($user);
        $this->logger->info("User registered", ['email' => $user->getEmail()]);
    }
}
```

**Что изменилось?**
1. **Single Responsibility:** `UserService` теперь отвечает только за *оркестрацию* процесса регистрации. Он не знает, *как* сохраняется пользователь или *как* отправляется письмо.
2. **Тестируемость:** Теперь я могу легко написать Unit-тест для `UserService`, создав Mock-объекты для репозитория, почты и логгера. Мне не нужно трогать реальную БД или отправлять реальные письма.
3. **Гибкость:** Если мы решим заменить `mail()` на `SendGrid`, мы просто создадим новую реализацию `NotificationServiceInterface`, не меняя ни одной строчки в `UserService`.

**Вывод:** Рефакторинг SRP — это переход от модели «Я делаю всё сам» к модели «Я делегирую задачи специалистам». Это делает систему предсказуемой и масштабируемой.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

### Рассуждение

Этот вопрос — ловушка для тех, кто считает, что принципы SOLID являются священным писанием. Опытный инженер знает: **SOLID — это не цель, это инструмент.** Цель разработки — решение бизнес-задачи с оптимальным соотношением стоимости, скорости и качества.

Если слепо следовать всем принципам в каждом месте, проект превратится в «архитектурный музей», где для создания одной кнопки нужно создать 15 классов и 3 интерфейса. Это называется **Overengineering** (избыточное проектирование).

Я рассматриваю это через призму **Trade-offs (компромиссов)**. Мы всегда выбираем между:
1. **Гибкостью** (сложная архитектура, готовая к изменениям).
2. **Скоростью доставки** (простой код, который можно быстро написать и выкатить).
3. **Сложностью поддержки** (насколько легко новому разработчику понять код).

Нарушение принципов оправдано, если цена следования принципу (в виде времени разработки или сложности) превышает потенциальную выгоду от гибкости, которую он дает.

---

### Ответ

Да, нарушать принципы SOLID не только можно, но иногда и **нужно**. Главный критерий здесь — **преждевременная оптимизация архитектуры**.

#### Когда нарушение оправдано?

1.  **Прототипирование и MVP (Minimum Viable Product):** Когда нужно проверить гипотезу на рынке за неделю. Здесь важнее скорость, чем идеальная абстракция. Мы сознательно идем на нарушение SRP и OCP, чтобы быстро получить фидбек.
2.  **Малые, изолированные скрипты:** Если вы пишете консольную команду для разовой миграции данных или простой скрипт для парсинга файла, внедрение интерфейсов и DI-контейнеров — это пустая трата времени.
3.  **Очень простая логика, которая вряд ли изменится:** Если у вас есть класс, который просто форматирует дату, создание интерфейса `DateFormatterInterface` будет избыточным (нарушение ISP/DIP), так как вероятность того, что вы подмените этот форматировщик на другой, стремится к нулю.

#### Пример оправданного нарушения (Нарушение SRP и DIP)

Представь, что нам нужно написать микросервис, который раз в сутки делает бэкап одного конкретного файла в локальную папку.

**Вариант «По SOLID» (Overengineering):**
Создаем `BackupManager`, `FileSystemInterface`, `LocalFileSystemImplementation`, `BackupTask`, `CronSchedulerInterface`... Мы потратим 2 дня на написание архитектуры, которая просто копирует файл.

**Вариант «Оправданное нарушение»:**

```php
class SimpleBackupScript
{
    public function run(string $source, string $destination): void
    {
        if (!file_exists($source)) {
            throw new \Exception("Source not found");
        }
        
        // Мы нарушаем SRP: скрипт и проверяет, и копирует, и логирует в файл
        // Мы нарушаем DIP: мы жестко привязаны к функции copy() и файловой системе
        if (copy($source, $destination)) {
            file_put_contents('backup.log', "Success: $source -> $destination\n", FILE_APPEND);
        } else {
            file_put_contents('backup.log', "Failed: $source\n", FILE_APPEND);
        }
    }
}
```

**Почему это оправдано?**
*   **Риск минимален:** Этот код не является ядром системы.
*   **Стоимость ошибки низка:** Если завтра понадобится бэкапить в S3, мы просто перепишем этот скрипт за 10 минут. Нам не нужно поддерживать сложную иерархию интерфейсов для этой задачи.
*   **Скорость:** Мы написали это за 5 минут, протестировали и забыли.

#### Мой золотой стандарт:
Я использую правило **"Rule of Three"**: если я вижу, что какой-то кусок кода приходится менять или расширять в третий раз, именно тогда я провожу рефакторинг и применяю SOLID. До этого момента я оставляю код максимально простым, пока сложность не станет реально обоснованной.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

### Рассуждение

Когда говорят об Open/Closed Principle (OCP), первой ассоциацией часто становится наследование: «Мы открыты для расширения через подклассы, но закрыты для модификации через базовый класс». Однако в современном объектно-ориентированном программировании (и особенно в PHP) наследование считается «сильной» и часто хрупкой связью. 

Инженерный подход требует искать более гибкие способы реализации OCP. Наследование создает жесткую иерархию, которая может привести к проблеме «хрупкого базового класса» (Fragile Base Class), когда изменение в родителе ломает десятки наследников.

Для реализации OCP я рассматриваю три основных альтернативных пути:
1. **Композиция (Composition over Inheritance):** использование паттерна «Стратегия». Это самый чистый способ.
2. **Делегирование (Delegation):** когда объект не сам реализует логику, а перенаправляет её другому объекту.
3. **Метапрограммирование и динамические механизмы:** использование атрибутов (Attributes) или магических методов (хотя к последним я отношусь осторожно из-за потери типизации).

Также стоит упомянуть использование **плагинов/расширений** через систему событий (Event Dispatcher), что является стандартом в Symfony.

---

### Ответ

Наследование — это лишь один из способов реализации OCP. Более гибкие и современные способы — это **композиция**, **интерфейсы** и **событийная модель**.

#### 1. Композиция и паттерн «Стратегия» (Strategy)
Это «золотой стандарт» реализации OCP. Вместо того чтобы расширять класс через наследование, мы инкапсулируем изменяемое поведение в отдельный объект и внедряем его через конструктор.

**Пример:** Система расчета стоимости доставки.

```php
// Вместо создания ShippingServiceDelivery(Inheritance)
interface ShippingStrategy {
    public function calculate(float $weight): float;
}

class GroundShipping implements ShippingStrategy {
    public function calculate(float $weight): float { return $weight * 1.5; }
}

class AirShipping implements ShippingStrategy {
    public function calculate(float $weight): float { return $weight * 5.0; }
}

class ShippingService {
    // Сервис закрыт для модификации (OCP), 
    // но открыт для новых стратегий через композицию.
    public function __construct(private ShippingStrategy $strategy) {}

    public function getCost(float $weight): float {
        return $this->strategy->calculate($weight);
    }
}
```
*Здесь мы добавим любой новый вид доставки, просто создав новый класс стратегии, не меняя `ShippingService`.*

#### 2. Паттерн «Декоратор» (Decorator)
Декоратор позволяет расширять функциональность объекта, не меняя его исходный код и не используя наследование. Это позволяет «наслаивать» поведение.

**Пример:** Логирование или кэширование.

```php
interface DataProvider {
    public function getData(): string;
}

class SimpleDataProvider implements DataProvider {
    public function getData(): string { return "Some data"; }
}

// Декоратор расширяет поведение, не меняя базовый класс
class LoggingDataProvider implements DataProvider {
    public function __construct(private DataProvider $inner) {}

    public function getData(): string {
        echo "Logging start...\n";
        $data = $this->inner->getData();
        echo "Logging end.\n";
        return $data;
    }
}
```

#### 3. Событийная модель (Observer / Event Dispatcher)
Это способ реализации OCP на уровне архитектуры приложения. Основной компонент «выстреливает» событие, а другие компоненты (слушатели) реагируют на него. Основной код остается закрытым для изменений, но система становится открытой для новых реакций.

**Пример (в стиле Symfony):**

```php
// Основной сервис не знает о существовании Emailer или Logger
class UserRegistrationService {
    public function __construct(private EventDispatcher $dispatcher) {}

    public function register(User $user): void {
        // ... логика регистрации ...
        
        // Мы просто уведомляем мир, что произошло событие.
        // Мы не меняем этот код, если захотим добавить SMS-уведомление.
        $this->dispatcher->dispatch(new UserRegisteredEvent($user));
    }
}
```

#### 4. Использование Атрибутов (Attributes) — современный PHP-way
С появлением PHP 8 мы можем использовать атрибуты для изменения поведения кода без его модификации. Это своего рода метапрограммирование.

**Пример:** Мы можем пометить метод атрибутом `#[Cacheable]`, и специальный оберточный компонент (через прокси или middleware) будет расширять его поведение, реализуя OCP на уровне инфраструктуры.

**Итог:**
Если вам нужно изменить **алгоритм** — используйте **Стратегию**.
Если нужно добавить **обертку/дополнительное действие** — используйте **Декоратор**.
Если нужно позволить **внешним модулям реагировать** на действия — используйте **События**.
Наследование оставляйте только для случаев, когда у вас есть жесткая связь "is-a" (является чем-то), и вы уверены в стабильности иерархии.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

### Рассуждение

Это отличный вопрос, который вскрывает разницу между «академическим» пониманием SOLID и реальным проектированием систем.

Если отвечать кратко: **нет, не только к классам.** Но в контекine SOLID — да, это первый уровень, с которого всё начинается.

Я разделяю ответственность на несколько уровней абстракции. Если инженер думает только категориями «классов», он рискует построить систему из идеально разрозненных, но абсолютно хаотичных компонентов. Чтобы SRP работал на полную мощность, его нужно масштабировать вверх по иерархии архитектуры.

Я выделяю три основных уровня, где применяется SRP:
1. **Уровень кода (классы и функции):** то, что мы привыкли называть SOLID.
2. **Уровень модулей/пакетов:** ответственность за объединение связанных функций.
3. **Уровень сервисов/микросервисов (Bounded Contexts):** ответственность за бизнес-домен.

Если мы проигнорируем SRP на уровне микросервисов, мы получим «распределенный монолит», где одна ошибка в одном сервисе вызывает лавину проблем во всей системе.

---

### Ответ

Нет, SRP не ограничивается классами. Принцип «одна единица не должна отвечать за слишком многое» применим к любому уровню архитектуры.

Вот как это выглядит на разных уровнях:

#### 1. Уровень кода (Классы и Функции)
Это базовый уровень. 
* **Класс** должен отвечать за одну сущность или одну область ответственности (например, `UserRepository` только за сохранение).
* **Функция/Метод** должен делать одну вещь. Если метод называется `validateAndSaveUser()`, он уже нарушает SRP. Его нужно разделить на `validate()` и `save()`.

#### 2. Уровень модулей и компонентов (Packages/Libraries)
В больших проектах код делится на пакеты или модули. 
* **Нарушение:** Если ваш модуль `PaymentModule` не только обрабатывает платежи, но и управляет генерацией PDF-инвойсов, отправкой SMS и управлением складскими запасами — вы нарушили SRP на уровне модуля.
* **Последствие:** Такой модуль становится огромным, его сложно обновлять, и его невозможно использовать в другом проекте без «прицепом» тянуть кучу ненужного кода.

#### 3. Уровень архитектурных контекстов (Bounded Contexts в DDD)
Это самый высокий уровень, где SRP превращается в принцип разделения доменов. В Domain-Driven Design это реализуется через понятие **Bounded Context**.
* **Нарушение:** Попытка создать один гигантский «Core Service», который содержит в себе всю логику бизнеса (и заказы, и логистику, и маркетинговую аналитику, и склад). Это «Божественный Модуль».
* **Правильное применение:** Мы разделяем систему на контексты. Контекст «Заказы» (Ordering) отвечает только за создание и статус заказа. Контекст «Доставка» (Shipping) отвечает только за логистику. Они общаются через события (Events), но не знают о внутреннем устройстве друг друга.

#### 4. Уровень микросервисов
На уровне инфраструктуры SRP диктует, что один микросервис должен решать одну бизнес-задачу.
* **Нарушение:** Микросервис `User-Service`, который одновременно управляет профилями, занимается рассылкой маркетинговых писем и анализирует поведение пользователей.
* **Последствие:** Вы теряете все преимущества микросервисов (масштабируемость, независимое развертывание). Если упадет модуль рассылки, упадет и авторизация пользователей.

### Резюме

| Уровень | Объект ответственности | Как проверить (симптом нарушения) |
| :--- | :--- | :--- |
| **Код** | Класс / Функция | Слишком длинный файл, слишком много аргументов, методы делают "и то, и другое". |
| **Модуль** | Пакет / Компонент | При установке модуля подтягивается слишком много зависимостей, которые вам не нужны. |
| **Домен** | Bounded Context | Сложно понять, где заканчивается логика одного процесса и начинается другой. |
| **Система** | Микросервис | Один сервис должен быть переписан или масштабирован из-за нагрузки, вызванной другой функцией. |

**Мой вывод как инженера:** Если вы соблюдаете SRP только на уровне классов, но игнорируете его на уровне сервисов, вы построите «чистый» внутри, но абсолютно неуправляемый и хрупкий снаружи проект.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

### Рассуждение

Этот вопрос проверяет, понимает ли разработчик разницу между «магией», которая происходит во время выполнения (runtime), и тяжелой работой, которая происходит на этапе сборки (build time). Многие думают, что DI-контейнер — это просто огромный массив объектов, который создается при каждом запросе. Это не так.

Чтобы ответить глубоко, я разделю процесс на три четких фазы:
1. **Этап сборки (Compilation Phase):** Это сердце Symfony. Здесь происходит парсинг YAML/XML/PHP конфигов, разрешение зависимостей и оптимизация. Важно подчеркнуть, что это происходит **один раз** (при очистке кэша), а не при каждом запросе.
2. **Этап Autowiring:** Это не магия, а результат работы рефлексии на этапе компиляции. Я должен объяснить, как Symfony сопоставляет типы аргументов с имеющимися в контейнере сервисами.
3. **Этап выполнения (Runtime/Instantiation):** Что происходит, когда мы вызываем `$container->get()`. Здесь важно упомянуть **Lazy Loading** и то, как объекты создаются по требованию.

Я также добавлю нюанс про `CompiledContainer` — это оптимизированный PHP-класс, который генерируется по итогам компиляции, что делает работу контейнера невероятно быстрой.

---

### Ответ

DI-контейнер в Symfony — это не просто «склад объектов», это мощный компилятор, который превращает декларативное описание ваших сервисов в высокооптимизированный, плоский PHP-код.

#### 1. Этап компиляции (Compilation Phase)
Когда вы запускаете приложение (или очищаете кэш), Symfony запускает процесс сборки контейнера. Это происходит не в runtime, а на этапе подготовки.

* **Загрузка конфигурации:** Контейнер собирает все определения сервисов из всех файлов (`services.yaml`, атрибуты, конфиги бандлов).
* **Dependency Graph:** Symfony строит граф зависимостей. Она понимает, что для создания `ServiceA` нужен `ServiceB`, а для `ServiceB` — `ParameterX`.
* **Compiler Passes (Компиляционные проходы):** Это важнейшая часть. Symfony прогоняет через граф набор правил. Например:
    * *Removal Pass:* удаляет неиспользуемые сервисы.
    * *Definition Pass:* заменяет алиасы.
    * *Tagging Pass:* собирает все сервисы с определенным тегом (например, `kernel.event_listener`) и регистрирует их в соответствующем менеджере.
* **Генерация кода:** Итог компиляции — это **PHP-файл** (обычно в `var/cache/.../App_KernelDevDebugContainer.php`). В этом файле вместо сложной логики поиска прописаны прямые вызовы: `$container->setServiceA(new ServiceA($container->getServiceB()))`. Это превращает поиск в быстрый доступ к свойствам объекта.

#### 2. Как работает Autowiring
Autowiring — это не «магия рефлексии в runtime». Это **рефлексия на этапе компиляции**.

Когда Symfony видит конструктор:
```php
public function __construct(UserRepository $repository) {}
```
Она использует PHP `ReflectionClass`, чтобы прочитать тип аргумента (`UserRepository`). Затем она ищет в своем графе сервисов тот, который является экземпляром этого типа. Если находит — она автоматически добавляет этот сервис в определение (definition) этого класса. 

**Важно:** Если в контейнере два сервиса реализуют один интерфейс, автовайринг сломается (будет `AmbiguousServiceException`), и вам придется явно указать, какой именно сервис нужен, через алиас или именованный аргумент.

#### 3. Момент запроса сервиса (Runtime/Instantiation)
Когда в коде вызывается `$container->get(MyService::class)` (или сервис внедряется через конструктор контроллера), происходит следующее:

1. **Проверка наличия:** Контейнер проверяет, создан ли уже этот экземпляр. По умолчанию все сервисы в Symfony — **Shared (Singleton)**. Это значит, что первый запрос создаст объект, а все последующие будут получать тот же самый экземпляр.
2. **Instantiating (Создание):** Если объекта еще нет, контейнер берет уже скомпилированную инструкцию. Он видит список зависимостей, рекурсивно вызывает `get()` для каждой из них и, наконец, вызывает `new MyService(...)`.
3. **Lazy Loading (Ленивая загрузка):** Если сервис помечен как `lazy`, Symfony не создает его сразу. Вместо него она подставляет **Proxy-объект**. Реальный объект будет создан только в тот момент, когда вы впервые вызовете у этого прокси какой-либо метод. Это критично для тяжелых сервисов, которые могут не понадобиться в текущем запросе.

**Итог:** Благодаря тому, что вся тяжелая работа (парсинг, рефлексия, построение графа) вынесена в этап компиляции, в runtime мы имеем практически «голый» PHP-код, который просто создает объекты, что делает Symfony одной из самых быстрых систем в своем классе.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

### Рассуждение

Когда я слышу вопрос о циклических зависимостях, я сразу понимаю: это не просто техническая проблема, это **симптом архитектурной болезни**. 

Циклическая зависимость (Service A требует Service B, а Service B требует Service A) — это признак того, что границы ответственности (SRP) размыты. Два сервиса слишком сильно связаны друг с другом, и их логика неразрывно переплетена.

Прежде чем предлагать «костыли», я всегда рассматриваю решение в три этапа:
1. **Архитектурное исправление (Best Practice):** Как это исправить правильно, чтобы убрать корень проблемы.
2. **Техническое решение (Workaround):** Как это разрулить средствами фреймворка, если рефакторинг сейчас невозможен.
3. **Предотвращение:** Как не допустить этого в будущем.

Я не буду просто предлагать использовать `Lazy` или `Setter Injection`. Сначала я должен спросить: «Почему они зависят друг от друга?». Часто это значит, что нам нужен третий сервис.

---

### Ответ

Я подхожу к этой проблеме иерархически: от исправления архитектуры до использования инструментов контейнера.

#### 1. Архитектурное исправление (Первый приоритет)

Если у меня возник цикл, я ищу способ разорвать его через рефакторинг. Обычно есть два пути:

*   **Выделение третьего сервиса (Extraction):** Если `ServiceA` и `ServiceB` зависят друг от друга, скорее всего, есть часть логики, которая принадлежит обоим. Я выделяю эту логику в `ServiceC` и заставляю оба сервиса зависеть от него.
    *   *Пример:* `OrderService` нужен `PaymentService` для оплаты, а `PaymentService` нужен `OrderService`, чтобы обновить статус заказа. Решение: выделить `OrderStateManager`, который умеет менять статусы, и использовать его в обоих сервисах.

*   **Перенос логики (Relocation):** Иногда один из сервисов на самом деле является частью другого. Возможно, `ServiceB` — это не самостоятельный сервис, а вспомогательный компонент, который должен быть внутри `ServiceA`.

#### 2. Техническое решение (Если рефакторинг невозможен прямо сейчас)

Если я работаю с legacy-кодом или внешними библиотеками, которые я не могу менять, я использую инструменты Symfony DI:

*   **Lazy Services (Proxy):** Это самый чистый способ «обмануть» контейнер. Я помечаю один из сервисов как `lazy`. В итоге контейнер внедрит не сам объект, а его прокси. Цикл в конструкторах разрывается, так как реальный объект будет создан только при первом обращении к его методам.
    ```yaml
    # services.yaml
    App\Service\ServiceB:
        lazy: true
    ```

*   **Setter Injection (Внедрение через сеттер):** Вместо того чтобы требовать зависимость в `__construct`, я позволяю контейнеру внедрить её позже через метод. Это позволяет сначала создать оба объекта, а затем связать их.
    *   *Примечание:* Я не люблю этот метод, так как он делает объект «неполноценным» в момент создания (объект может находиться в нестабильном состоянии до вызова сеттера).

*   **Внедрение Container (Anti-pattern):** Я никогда не внедряю сам контейнер (`ContainerInterface`) в сервис, чтобы вызывать `$container->get()`. Это превращает сервис в «черный ящик», скрывает зависимости и делает тестирование невозможным. Это — тупиковый путь.

#### 3. Профилактика

Чтобы не возвращаться к этой проблеме, я:
1.  **Соблюдаю SRP:** Чем меньше ответственности у класса, тем меньше шансов, что он понадобится кому-то в качестве зависимости для выполнения его же собственной задачи.
2.  **Использую интерфейсы:** Это помогает проектировать зависимости на уровне контрактов, а не реализаций.
3.  **Провожу Code Review:** Я всегда обращаю внимание на конструкторы. Если я вижу, что в конструкторе становится слишком много аргументов — это первый звоночек, что класс нарушает SRP и скоро создаст цикл.

**Итог:** Циклическая зависимость — это сигнал архитектора. Мой подход: **сначала лечить причину (рефакторинг), и только потом снимать симптомы (lazy/setter injection).**

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

### Рассуждение

Эта задача — классический пример разделения **синхронного** и **асинхронного** исполнения. 

Основная бизнес-задача (регистрация пользователя) должна быть завершена максимально быстро. Отправка почты и обновление поискового индекса — это побочные эффекты (side effects). Они важны, но их задержка (например, если почтовый сервер тормозит или API поисковика недоступно) не должна приводить к ошибке регистрации или долгому ожиданию пользователя.

Я рассмотрю три варианта реализации, от самого простого до самого надежного (enterprise-grade), и оценю их через призму сложности, надежности и стоимости поддержки.

---

### Ответ

Я буду использовать событийную модель для отделения основной логики от побочных эффектов, а затем вынесу эти эффекты в фоновые задачи.

#### Вариант 1: Event Dispatcher (Синхронный) — «Плохой вариант»
Я могу вызвать `EventDispatcher`, который запустит слушателей `SendEmailListener` и `UpdateSearchIndexListener`.

*   **Как работает:** В контроллере вызывается `$dispatcher->dispatch(new UserRegisteredEvent($user))`. Слушатели выполняются в том же PHP-процессе.
*   **Trade-offs:**
    *   **Плюсы:** Очень легко реализовать, нет сторонних зависимостей.
    *   **Минусы:** **Это не решает задачу.** Пользователь всё равно будет ждать, пока отправится письмо. Если API поиска упадет, пользователь получит 500 ошибку при регистрации. Это нарушает требование «не замедлять ответ».

#### Вариант 2: Messenger + Message Bus (Асинхронный) — «Золотой стандарт»
Это наиболее правильный путь для Symfony-приложения. Я использую компонент **Symfony Messenger**.

*   **Как работает:**
    1.  В `UserService` после сохранения пользователя я отправляю сообщение в шину: `$bus->dispatch(new UserRegisteredMessage($userId))`.
    2.  Это сообщение попадает в **Transport** (например, RabbitMQ, Redis или даже база данных PostgreSQL через Doctrine).
    3.  Контроллер мгновенно возвращает ответ пользователю.
    4.  В фоне работает отдельный процесс (**Worker**), который слушает очередь, забирает сообщение и выполняет обработчики (`MessageHandler`).
*   **Trade-offs:**
    *   **Плюсы:** 
        *   **Скорость:** Пользователь получает ответ мгновенно.
        *   **Отказоустойчивость:** Если почтовый сервис недоступен, Messenger может автоматически перезапустить задачу (retry strategy) через 5, 10, 60 минут.
        *   **Масштабируемость:** Можно запустить 10 воркеров, если очередь растет.
    *   **Минусы:** Требует инфраструктуру (RabbitMQ/Redis) и управления процессами (Supervisor).

#### Вариант 3: Outbox Pattern (Самый надежный) — «Enterprise-уровень»
Если нам критически важно, чтобы письмо *обязательно* ушло и мы не могли потерять сообщение при сбое очереди (например, если RabbitMQ упал в момент отправки сообщения), я применю паттерн **Transactional Outbox**.

*   **Как работает:**
    1.  В рамках одной транзакции БД я сохраняю `User` и записываю событие в специальную таблицу `outbox_messages` в той же базе.
    2.  Поскольку это одна транзакция, либо сохранятся оба, либо ни одного. Мы гарантируем консистентность.
    3.  Отдельный процесс (Relay) читает таблицу `outbox_messages`, отправляет их в брокер сообщений (RabbitMQ) или обрабатывает напрямую.
*   **Trade-offs:**
    *   **Плюсы:** Гарантированная доставка (At-least-once delivery). Нет риска потерять событие, если брокер сообщений временно недоступен.
    *   **Минусы:** Высокая сложность реализации и дополнительная нагрузка на базу данных.

---

### Мой итоговый выбор

Для типичного современного проекта я выберу **Вариант 2 (Symfony Messenger + RabbitMQ/Redis)**. 

**Моя архитектурная схема будет такой:**
1.  **Domain Layer:** `UserService` сохраняет пользователя и вызывает `eventDispatcher->dispatch(new UserRegisteredEvent($user))`.
2.  **Infrastructure Layer (Listener):** Слушатель этого события не делает работу сам, а делает только одну вещь: перекладывает данные в шину сообщений: `$messageBus->dispatch(new SendWelcomeEmailMessage($userId))`.
3.  **Async Layer:** Воркеры обрабатывают `SendWelcomeEmailMessage` и `UpdateSearchIndexMessage` независимо друг от друга.

Это дает идеальный баланс: **быстрый ответ пользователю**, **изоляция ошибок** (ошибка в поиске не мешает отправке почты) и **автоматические повторы** при сбоях.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

### Рассуждение

Вопрос затрагивает три фундаментально разных уровня безопасности. Чтобы не превратить ответ в кашу, я разделю их по принципу: **«Кто ты?»** (Authentication), **«Что тебе разрешено в принципе?»** (Roles) и **«Можно ли тебе это сделать прямо сейчас с этим конкретным объектом?»** (Authorization/Voters).

Частая ошибка разработчиков — пытаться запихнуть сложную логику проверки прав в проверку ролей. Это приводит к тому, что в контроллере появляются огромные `if`-блоки, которые проверяют не только роль, но и владельца ресурса, статус документа и т.д.

Я рассматриваю это как многослойный пирог:
1. **Authenticator** — проверяет «паспорт».
2. **Role Hierarchy** — проверяет «статус».
3. **Voter** — проверяет «ситуацию».

---

### Ответ

В Symfony контроль доступа строится на двух китах: **Security Component** (для аутентификации) и **Access Decision Manager** (для авторизации).

#### 1. Аутентификация (Authentication): "Кто ты?"
Это процесс идентификации пользователя. Symfony использует систему **Authenticators**.
* **Как это работает:** Когда приходит запрос, `Authenticator` перехватывает его и проверяет учетные данные (токен JWT, сессию, логин/пароль). Если данные верны, создается объект `User` и помещается в `TokenStorage`.
* **Результат:** Мы теперь знаем, что текущий пользователь — это `User` с ID 123.

#### 2. Роли (Roles): "К какой группе ты принадлежишь?"
Роли — это самый простой уровень авторизации. Это статические метки (например, `ROLE_USER`, `ROLE_ADMIN`).
* **Role Hierarchy:** В Symfony можно настроить иерархию (например, `ROLE_ADMIN` включает в себя `ROLE_USER`).
* **Применение:** Используется для глобальных ограничений. Например, доступ к админ-панели (`/admin`) разрешен только тем, у кого есть `ROLE_ADMIN`.

#### 3. Voters: "Можешь ли ты совершить это конкретное действие?"
Voters — это наиболее гибкий и мощный инструмент. Это классы, которые реализуют логику проверки прав на уровне **бизнес-объектов**.
* **Как это работает:** Когда вы вызываете `$this->denyAccessUnlessGranted('EDIT', $article)`, Symfony опрашивает все зарегистрированные **Voters**. Каждый вотер говорит: «Я могу решить этот вопрос» или «Это не моя компетенция». Если вотер берет на себя решение, он возвращает `ACCESS_GRANTED`, `ACCESS_DENIED` или `ACCESS_ABSTAIN`.

---

### Когда выбирать Roles, а когда Voters?

Это ключевой архитектурный вопрос.

#### Используй Роли (Roles), когда:
* **Проверка глобальная и статичная.** 
* *Пример:* «Доступ к разделу управления пользователями разрешен только администраторам». Тут не важно, какой именно пользователь — это просто проверка наличия ярлыка `ROLE_ADMIN`.
* **Пример:** Доступ к API-методам для `ROLE_API_CLIENT`.

#### Используй Voters, когда:
* **Проверка динамическая и зависит от состояния данных (объекта).**
* **Проверка зависит от отношений (владение ресурсом).**
* *Пример:* «Пользователь может редактировать статью, только если он её автор». Роль `ROLE_USER` тут не поможет, потому что редактировать могут разные пользователи. Нужен Voter, который сравнит `$user->getId()` и `$article->getAuthorId()`.
* **Проверка зависит от бизнес-контекста.** 
* *Пример:* «Статью нельзя редактировать, если у неё статус `PUBLISHED`». Это чистая бизнес-логика, которая должна жить в Voter, а не в проверке ролей.

#### Резюме (шпаргалка):

| Ситуация | Инструмент | Почему? |
| :--- | :--- | :--- |
| Доступ к `/admin` | **Roles** | Это глобальный доступ по статусу. |
| Доступ к кнопке "Удалить" | **Voter** | Нужно проверить, является ли текущий юзер владельцем объекта. |
| Доступ к методу API | **Roles** | Это проверка прав доступа к функционалу. |
| Редактирование закрытого заказа | **Voter** | Это проверка состояния бизнес-объекта. |

**Мой принцип:** Если в условии проверки появляется слово **"конкретный"** (этот конкретный пост, этот конкретный заказ, этот конкретный счет) — это 100% работа для **Voter**.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

### Рассуждение

Это фундаментальный вопрос проектирования доменного слоя. В DDD (Domain-Driven Design) **Value Object** должен обладать двумя свойствами: **Immutability** (неизменяемость) и **Self-validation** (самовалидация).

Проблема в том, что Doctrine ORM по своей природе «заточена» под работу с сущностями (Entities), которые имеют жизненный цикл, идентичность и изменяемое состояние. Entity — это то, что меняется; Value Object — это то, что заменяется целиком.

Когда мы пытаемся сохранить Value Object, мы сталкиваемся с конфликтом: Doctrine хочет управлять полями объекта через сеттеры или рефлексию, а наш доменный объект запрещает любые изменения после создания.

Я выделяю три основных спосома решения этой задачи, которые эволюционировали вместе с развитием PHP и Doctrine:
1. **Embeddables (встроенные объекты):** Стандартный путь Doctrine.
2. **Custom Types (пользовательские типы):** Путь через преобразование в примитив (string/int/json).
3. **Специальные реализации через жизненный цикл (Lifecycle Callbacks/Listeners):** Для более сложных случаев.

---

### Ответ

Для реализации Value Objects в Doctrine я использую два основных подхода в зависимости от того, насколько сложен объект.

#### 1. Doctrine Embeddables (Рекомендуемый способ для структурированных объектов)
Это встроенный механизм, который позволяет маппить объект как набор колонок в той же таблице, где лежит основная сущность.

**Пример:**
```php
#[ORM\Embeddable]
readonly class Money 
{
    public function __construct(
        #[ORM\Column(type: 'decimal', precision: 10, scale: 2)]
        public float $amount,
        
        #[ORM\Column(type: 'string', length: 3)]
        public string $currency,
    ) {
        if ($amount < 0) throw new \InvalidArgumentException("Amount cannot be negative");
        if (strlen($currency) !== 3) throw new \InvalidArgumentException("Invalid currency");
    }
}

#[ORM\Entity]
class Product {
    #[ORM\Embedded(class: Money::class)]
    private Money $price;
}
```

*   **Плюсы:**
    *   **Нативная поддержка:** Работает «из коробки».
    *   **Структура в БД:** В таблице `product` будут колонки `price_amount` и `price_currency`. Это позволяет делать выборки и агрегации (SUM, AVG) средствами SQL.
    *   **Валидация:** Объект создается через конструктор, поэтому гарантирует валидность.
*   **Минусы:**
    *   **Зависимость от структуры:** Если вы захотите изменить структуру Value Object, придется делать миграцию по колонкам.
*   **Подводный камень:** Помните, что Embeddable — это не отдельная таблица. Это часть родительской сущности.

#### 2. Custom Doctrine Types (Для атомарных или сложных объектов)
Если Value Object — это что-то вроде `Email`, `Color` (HEX) или сложного массива данных, который в БД должен лежать в одной колонке (например, `JSON` или `STRING`).

**Пример:**
Вы создаете класс `EmailValueObject`, а в Doctrine маппите его через тип `email_type`. Внутри типа вы реализуете `convertToDatabaseValue` (превращаете объект в строку) и `convertToPHPValue` (превращаете строку обратно в объект).

*   **Плюсы:**
    *   **Чистота БД:** Один объект = одна колонка.
    *   **Инкапсуляция:** Вся логика преобразования скрыта внутри типа.
*   **Минусы:**
    *   **Невозможность поиска по полям:** Если вы храните объект как JSON, вы не сможете эффективно сделать SQL-запрос `WHERE email_part_domain = 'gmail.com'`.
    *   **Сложность реализации:** Нужно писать свой класс типа и регистрировать его.
*   **Подводный камень:** При использовании JSON-типов легко потерять строгую типизацию при чтении, если не добавить проверку в `convertToPHPValue`.

#### 3. Сводная таблица сравнения

| Метод | Когда использовать | Хранение в БД | Поиск (SQL) | Сложность |
| :--- | :--- | :--- | :--- | :--- |
| **Embeddable** | Когда у объекта есть несколько полей (Money, Address) | Несколько колонок | **Отлично** | Низкая |
| **Custom Type** | Когда объект — это один примитив (Email, Color) или JSON | Одна колонка | **Плохо** (для JSON) | Средняя |

---

### Мои рекомендации и "Best Practices"

1.  **Всегда используйте `readonly` (PHP 8.2+):** Это гарантирует неизменяемость на уровне языка. Value Object не должен иметь сеттеров.
2.  **Валидация в конструкторе:** Никогда не позволяйте создать объект в невалидном состоянии. `throw new InvalidArgumentException` в конструкторе — это ваш единственный рубеж обороны.
3.  **Избегайте "Anemic Domain Model":** Не превращайте Value Object в простые DTO. У него должна быть логика (например, метод `Money::add(Money $other): Money`), которая возвращает **новый** экземпляр.
4.  **Подводный камень с Identity Map:** Помните, что Doctrine не отслеживает изменения внутри объекта, если вы изменили его внутреннее состояние (что невозможно с `readonly`, но возможно, если вы забыли про `readonly`). Если вы заменили объект целиком (`$entity->setPrice(new Money(...))`), Doctrine увидит это через UnitOfWork. Если же вы попытаетесь изменить поле внутри — Doctrine об этом не узнает. **Всегда заменяйте объект целиком.**

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

### Рассуждение

Это один из самых сложных вопросов стыка DDD и ORM. Проблема в том, что Doctrine — это **Data Mapper**, который работает с графом объектов, а DDD требует, чтобы мы работали с **Агрегатом** как с единой границей консистентности.

Главный риск здесь — «протекание» агрегата. Если мы разрешим изменять дочерние сущности напрямую через репозиторий, минуя корень (Aggregate Root), мы нарушим инварианты (бизнес-правила), которые агрегат обязан защищать.

Я разделю ответ на три уровня:
1.  **Маппинг:** Как связать корень и коллекцию так, чтобы они выглядели как единое целое.
2.  **Управление состоянием:** Как обеспечить, чтобы изменения проходили только через корень.
3.  **Транзакционность:** Кто управляет `flush` и как обеспечить атомарность.

Возьмем для примера агрегат **Order (Заказ)**, где корнем является `Order`, а дочерней сущностью — `OrderItem` (позиция заказа). Инвариант: *«Сумма заказа должна всегда соответствовать сумме всех позиций»*.

---

### Ответ

#### 1. Маппинг коллекции (Encapsulation)

Чтобы соблюсти границы агрегата, мы не должны давать доступ к коллекции в обход методов корня. В Doctrine это делается через `orphanRemoval` и правильную настройку `cascade`.

```php
// Aggregate Root
#[ORM\Entity]
class Order 
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    /**
     * @var Collection<int, OrderItem>
     */
    #[ORM\OneToMany(
        mappedBy: 'order', 
        targetEntity: OrderItem::class, 
        cascade: ['persist', 'remove'], 
        orphanRemoval: true // Важно: удаляет элементы из БД, если они удалены из коллекции
    )]
    private Collection $items;

    public function __construct() {
        $this->items = new ArrayCollection();
    }

    // ЗАПРЕЩАЕМ прямой доступ к коллекции (getItems возвращает только для чтения)
    /** @return Collection<int, OrderItem> */
    public function getItems(): Collection {
        return $this->items->slice(); // Возвращаем копию или ReadOnly обертку
    }

    // ЕДИНСТВЕННЫЙ способ изменить состояние — через методы корня
    public function addProduct(Product $product, int $quantity): void {
        $item = new OrderItem($this, $product, $quantity);
        $this->items->add($item);
        $this->recalculateTotal(); // Поддерживаем инвариант
    }

    private function recalculateTotal(): void {
        // Логика пересчета суммы заказа
    }
}

// Child Entity
#[ORM\Entity]
class OrderItem 
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'items')]
    #[ORM\JoinColumn(nullable: false)]
    private Order $order;

    public function __construct(Order $order, Product $product, int $quantity) {
        $this->order = $order;
        // ...
    }
}
```

**Ключевые моменты маппинга:**
*   **`orphanRemoval: true`**: Если мы удалим `OrderItem` из коллекции `$items`, Doctrine сама удалит соответствующую строку из таблицы `order_item`. Без этого объект останется в базе как «сирота».
*   **`cascade: ['persist']`**: Позволяет нам вызвать `$entityManager->persist($order)`, и Doctrine автоматически сохранит все новые `OrderItem`.

#### 2. Границы транзакции и управление изменениями

В DDD изменения агрегата должны быть атомарными. Либо весь агрегат обновился, либо ничего.

**Кто вызывает `flush`?**
В чистой архитектуре **Domain Layer и Application Layer не должны знать о существовании EntityManager**. 
*   **Плохо:** Вызывать `$em->flush()` внутри метода `Order::addProduct()`. Это смешивает бизнес-логику с инфраструктурой.
*   **Хорошо:** `flush()` вызывается в **Application Service** (или Command Handler), который управляет транзакцией.

```php
// Application Layer
class PlaceOrderHandler 
{
    public function __construct(
        private OrderRepository $orderRepository,
        private EntityManagerInterface $entityManager
    ) {}

    public function handle(AddProductCommand $command): void 
    {
        // 1. Загружаем агрегат через репозиторий
        $order = $this->orderRepository->find($command->orderId);

        // 2. Выполняем бизнес-операцию (внутри агрегата)
        $order->addProduct($command->product, $command->quantity);

        // 3. Сохраняем изменения (Unit of Work)
        // EntityManager увидит изменения и внутри транзакции выполнит все SQL-запросы
        $this->entityManager->flush(); 
    }
}
```

#### 3. Подводные камни и правила

1.  **Запрет на прямой доступ к дочерним сущностям:** Никогда не делайте `OrderItemRepository`. Если вы хотите изменить количество товара в заказе, вы должны вызвать `$order->updateItemQuantity(...)`. Если вы будете менять `OrderItem` напрямую через его репозиторий, вы можете нарушить инвариант суммы заказа в `Order`.
2.  **Проблема больших коллекций:** Если в агрегате тысячи элементов (например, `Order` с 10 000 позиций), `OneToMany` через `Collection` станет тормозить, так как Doctrine загрузит их все в память. В этом случае агрегат нужно разбивать или использовать паттерн «Pagination через репозиторий» (но это уже выход за пределы классического агрегата).
3.  **Транзакционность:** Всегда используйте `EntityManager::wrapInTransaction()` или `@Transactional` (в некоторых фреймворках), чтобы гарантировать, что если `flush()` упадет на середине, база не останется в промежуточном состоянии.

**Итог:** Агрегат — это «черный ящик». Вы взаимодействуете только с корнем, а Doctrine через `cascade` и `orphanRemoval` берет на себя задачу синхронизации этого черного ящика с таблицами базы данных.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

### Рассуждение

Проблема N+1 — это классическая ловушка ORM. Она возникает, когда мы загружаем список основных сущностей (1 запрос), а затем, итерируясь по ним, обращаемся к их связанным объектам (N запросов), которые Doctrine подгружает лениво (Lazy Loading).

Для меня, как для инженера, диагностика — это не гадание, а использование инструментов профилирования. Я не буду пытаться «угадать» запрос в коде; я пойду туда, где видны реальные SQL-логи.

При поиске решения я разделяю их на три категории: **превентивные** (загрузка данных), **структурные** (изменение маппинга) и **архитектурные** (изменение подхода к данным). Каждый из них имеет свои цену (trade-offs).

---

### Ответ

#### 1. Диагностика

Первым делом я должен подтвердить гипотезу. Я использую три основных инструмента:

1.  **Symfony Profiler (Web Debug Toolbar):** Самый быстрый способ. Я открываю вкладку "Doctrine" и смотрю на количество запросов. Если я вижу 50 одинаковых запросов к таблице `comments` для 50 разных `posts` — это N+1.
2.  **SQL Logging:** Включение логирования всех SQL-запросов в консоль или лог-файл. Это позволяет увидеть "пулеметную очередь" из однотипных запросов.
3.  **Blackfire.io или Tideways:** Если проблема сложнее и запросов слишком много, я использую эти профилировщики, чтобы увидеть дерево вызовов и понять, какой именно метод в коде триггерит ленивую загрузку.

#### 2. Способы решения и их Trade-offs

Когда проблема найдена, я выбираю один из следующих путей:

##### А. Eager Loading через Join (Fetch Join) в DQL/QueryBuilder
Это самый эффективный способ. Мы явно говорим Doctrine: «При загрузке сущностей сразу подтяни и их связи одним `JOIN`.»

```php
// Вместо $repo->findAll()
$query = $em->createQuery('SELECT p, c FROM App\Entity\Post p JOIN p.comments c');
$posts = $query->getResult();
```

*   **Плюсы:** Решает проблему за 1 запрос. Очень высокая производительность.
*   **Минусы:** 
    *   **Cartesian Product (Декартово произведение):** Если у вас несколько `OneToMany` связей, загружаемых через `JOIN`, количество строк в результирующем наборе данных растет экспоненциально, что может «убить» память сервера.
    *   **Сложность:** Нужно писать кастомные репозитории вместо использования стандартных методов.

##### Б. Изменение маппинга на `fetch="EAGER"`
Мы можем прописать в аннотациях/атрибутах сущности, что связь всегда должна грузиться сразу.

*   **Плюсы:** Решает проблему автоматически для всех мест, где используется эта сущность.
*   **Минусы:** 
    *   **Огромный риск Overfetching:** Это "пушка по воробьям". Теперь, даже когда вам нужен просто `Post` без комментариев, Doctrine будет всегда тянуть и комментарии. Это замедлит *все* части приложения.
    *   **Негибкость:** Вы не можете отключить это поведение в конкретном запросе.

##### В. Использование Partial Objects или DTO (Data Transfer Objects)
Вместо того чтобы загружать тяжелые сущности со всеми их связями, мы делаем запрос, который выбирает только нужные поля и упаковывает их в простой PHP-объект (DTO).

```php
// QueryBuilder выбирает только конкретные поля
$query = $em->createQuery('SELECT NEW App\Dto\PostSummaryDto(p.id, p.title, c.content) 
                           FROM App\Entity\Post p JOIN p.comments c');
```

*   **Плюсы:** 
    *   **Минимальное потребление памяти:** Мы не создаем тяжелые объекты Entity и не нагружаем Identity Map.
    *   **Максимальная скорость:** Выбираем только то, что реально нужно для отображения страницы.
*   **Минусы:** 
    *   **ReadOnly:** DTO нельзя сохранить через `$em->flush()`. Это только для чтения.
    *   **Дублирование логики:** Нужно создавать специальные классы для каждого вида вывода.

##### Г. Использование Second-Level Cache (L2 Cache)
Если данные редко меняются, можно включить кэширование на уровне Doctrine.

*   **Плюсы:** Снижает нагрузку на БД, так как связанные объекты берутся из кэша (Redis/Memcached).
*   **Минусы:** 
    *   **Сложность инвалидации:** Самая большая проблема — сделать так, чтобы кэш всегда был актуальным.
    *   **Риск несогласованности:** Пользователь может увидеть старые данные.

#### Итоговая стратегия выбора:

1.  Если это **список сущностей** для отображения (Read Model) $\rightarrow$ использую **DTO** или **Fetch Join**.
2.  Если это **конкретный объект** в контексте редактирования $\rightarrow$ использую стандартный Lazy Loading (он здесь уместен).
3.  Если связь используется **везде и всегда** (например, `User` и его `Role`) $\rightarrow$ использую **Eager Loading** в маппинге.
4.  Если данных **огромное количество** и они только для чтения $\rightarrow$ использую **чистый SQL** или **DQL с проекцией в DTO**.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

### Рассуждение

Этот вопрос проверяет понимание концепции **«Defense in Depth» (эшелонированная оборона)**. 

Многие разработчики попадают в ловушку, полагая, что если в приложении есть валидация (четкие типы, Symfony Validator, проверки в доменных моделях), то база данных — это просто «мешок для хранения данных». Это опасное заблуждение. 

Я разделяю ответственность следующим образом:
1. **Приложение (Application/Domain Layer):** отвечает за **бизнес-валидацию**. Это правила, которые могут меняться, зависят от контекста и часто требуют сложной логики (например: «пользователь может купить товар, только если у него есть промокод и баланс больше X»). Это «мягкая» защита.
2. **База данных (PostgreSQL):** отвечает за **целостность данных (Data Integrity)**. Это фундаментальные правила, которые не должны быть нарушены ни при каких обстоятельствах, независимо от того, какой код (PHP, Python, ручной SQL-запрос администратора) пытается изменить данные. Это «жесткая» защита.

Если мы полагаемся только на код, мы уязвимы перед:
* Ошибками в коде (багами).
* Race conditions (состоянием гонки), когда два параллельных запроса обходят проверку в PHP, но конфликтуют в БД.
* Прямыми манипуляциями с БД (миграции, отладка, скрипты импорта).

---

### Ответ

Я использую ограничения на уровне PostgreSQL как **последний рубеж обороны**, гарантирующий, что база данных никогда не перейдет в невалидное состояние. 

#### Какие средства я использую и когда:

**1. Primary Keys и Unique Constraints (Уникальность)**
Это база. Я всегда использую `PRIMARY KEY` и `UNIQUE` индексы.
* **Когда:** Чтобы гарантировать, что у пользователя один email, а у заказа — один уникальный номер.
* **Зачем:** Даже если в PHP-коде проверка `if (userExists($email))` вернет `false` из-за race condition (два запроса пришли одновременно), база данных выбросит `UniqueViolationException`, и мы не получим дубликат.

**2. Foreign Key Constraints (Ссылочная целостность)**
Я всегда использую `FOREIGN KEY` с четко определенным поведением (`ON DELETE CASCADE` или `ON DELETE RESTRICT`).
* **Когда:** Связь `Order` $\rightarrow$ `User`.
* **Зачем:** Чтобы избежать появления «сирот» (orphan records). Если мы удалим пользователя, БД не позволит оставить его заказы «в никуда», если мы не разрешили каскадное удаление. Это предотвращает разрыв связей в данных.

**3. Not Null Constraints (Обязательность)**
Все колонки, которые не могут быть пустыми по логике системы, должны иметь `NOT NULL`.
* **Когда:** `user_id` в таблице заказов, `amount` в таблице транзакций.
* **Зачем:** Чтобы предотвратить появление `NULL`, который в SQL ведет к непредсказуемому поведению при сравнениях и агрегациях.

**4. Check Constraints (Бизнес-инварианты на уровне данных)**
Это мощный инструмент PostgreSQL, который я использую для защиты фундаментальных правил.
* **Когда:** 
    * `CHECK (price >= 0)` — цена не может быть отрицательной.
    * `CHECK (status IN ('pending', 'paid', 'cancelled'))` — статус может быть только из этого списка.
    * `CHECK (end_date > start_date)` — временные интервалы не могут быть вывернуты.
* **Зачем:** Это защищает от «битых» данных, которые могли просочиться через баги в логике или прямые SQL-запросы.

**5. Database Transactions (Атомарность)**
Хотя это не «ограничение», это механизм обеспечения целостности.
* **Когда:** При любых операциях, затрагивающих несколько таблиц (например, перевод денег: минус со счета А, плюс на счет Б).
* **Зачем:** Гарантировать принцип ACID. Либо всё применится, либо всё откатится.

#### Итоговая стратегия:

| Тип проверки | Где реализуется | Цель | Пример |
| :--- | :--- | :--- | :--- |
| **Бизнес-правила** | PHP (Domain/Service) | Комфорт пользователя, сложная логика | "Скидка не может быть больше 50%" |
| **Целостность данных** | PostgreSQL (Constraints) | Защита от коррупции данных | `CHECK (discount <= 0.5)` |
| **Связи и уникальность** | PostgreSQL (FK, Unique) | Структурная корректность | `UNIQUE(email)` |

**Мой вывод:** Приложение — это "умная" оболочка, которая помогает пользователю, а база данных — это "непреклонный страж", который гарантирует, что даже если оболочка сойдет с ума, данные останутся верными.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

### Рассуждение

Когда я слышу «запрос выполняется медленно», я не начинаю сразу ставить индексы. Это классическая ошибка — «лечение симптомов вместо болезни». Неправильный индекс может не только не помочь, но и замедлить вставку (INSERT/UPDATE), а еще хуже — запутать планировщик запросов.

Мой подход базируется на принципе: **«Не оптимизируй то, что не измерил»**. 

Процесс я разделяю на три фазы:
1. **Локализация:** Понять, *где именно* тормозит (БД, сеть, PHP, или сама логика запроса).
2. **Анализ плана выполнения:** Понять, *почему* база выбрала именно такой путь.
3. **Применение стратегий оптимизации:** Исправление плана, структуры или инфраструктуры.

---

### Ответ

#### 1. Диагностика и инструменты

Первым дего я иду в базу, чтобы получить «правду» от планировщика.

*   **EXPLAIN (ANALYZE, BUFFERS):** Мой главный инструмент. 
    *   `EXPLAIN` показывает план, который *собирается* выполнить база.
    *   `EXPLAIN ANALYZE` выполняет запрос на самом деле и показывает реальное время и количество строк.
    *   `BUFFERS` показывает, сколько данных было прочитано из памяти (shared buffers), а сколько — с диска (I/O). Это критично для понимания, упираемся мы в CPU или в медленный диск.
*   **pg_stat_statements:** Если проблема плавающая и происходит на проде, я подключаю этот модуль. Он собирает статистику по всем запросам: среднее время, количество вызовов, максимальная нагрузка. Это позволяет найти «самые тяжелые» запросы в системе.
*   **pgBadger:** Если нужно проанализировать логи PostgreSQL целиком и увидеть общую картину (slow queries, ошибки, нагрузку).

#### 2. На что я смотю в плане (Explain Plan)

Когда я вижу план, я ищу «красные флаги»:

*   **Seq Scan (Sequential Scan):** База читает всю таблицу целиком. Если таблица большая — это почти всегда проблема отсутствия индекса.
*   **Index Scan vs Bitmap Index Scan:** Я смотрю, эффективно ли используется индекс. Если база делает `Bitmap Heap Scan`, это может значить, что данных слишком много для эффективного использования индекса.
*   **Nested Loop:** Если в плане много вложенных циклов на больших объемах данных — это признак того, что джойны (joins) работают неэффективно.
*   **Cost & Actual Time:** Я сравниваю ожидаемую стоимость (`cost`) с реальным временем (`actual time`). Если разрыв огромный — значит, статистика базы устарела.
*   **Disk Read (Read from disk):** Если `Buffers: read=...` показывает большое число, значит, данных не хватает в RAM, и мы упираемся в дисковую подсистему.

#### 3. Типовые причины и способы решения

Я группирую решения по типам проблем:

**А. Проблема: Отсутствие или плохой индекс**
*   **Решение:** Добавление B-tree индекса на колонки в `WHERE`, `JOIN` или `ORDER BY`.
*   **Продвинутое решение:** 
    *   **Partial Index:** Если мы часто ищем только «активные» заказы, создаем индекс `WHERE status = 'active'`. Он будет маленьким и быстрым.
    *   **Composite Index:** Если запрос фильтрует по двум полям сразу, один составной индекс лучше двух отдельных.
    *   **Covering Index (INCLUDE):** Чтобы база вообще не ходила в таблицу, а брала все данные прямо из индекса.

**Б. Проблема: Устаревшая статистика (Stale Statistics)**
*   **Симптом:** Планировщик выбирает `Seq Scan` там, где явно нужен индекс.
*   **Решение:** Запуск `ANALYZE table_name`. Это обновит гистограммы распределения данных, и планировщик примет верное решение.

**В. Проблема: Неэффективный запрос (Sargability)**
*   **Симптом:** Использование функций над колонками в `WHERE`.
    *   *Плохо:* `WHERE DATE(created_at) = '2023-01-01'` (индекс по `created_at` не сработает).
    *   *Хорошо:* `WHERE created_at >= '2023-01-01 00:00:00' AND created_at < '2023-01-02 00:00:00'`.
*   **Решение:** Переписывание запроса так, чтобы он мог использовать индексы.

**Г. Проблема: Избыточность данных (Overfetching)**
*   **Симптом:** `SELECT *` тянет огромные текстовые поля или JSONB, которые не нужны для текущей задачи.
*   **Решение:** Явное указание колонок в `SELECT`.

**Д. Проблема: Проблема архитектуры (N+1)**
*   **Симптом:** Множество мелких запросов в логах.
*   **Решение:** Исправление на уровне приложения (Eager loading в Doctrine) или использование `JOIN` в SQL.

**Резюме моей стратегии:**
1. Найти тяжелый запрос через `pg_stat_statements`.
2. Прогнать его через `EXPLAIN (ANALYZE, BUFFERS)`.
3. Проверить: индекс есть? Индекс работает? Статистика актуальна? Запрос «индексно-дружелюбный»?
4. Если всё ок, но всё равно медленно — смотрим в сторону кэширования, шардирования или оптимизации железа (RAM/IOPS).

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

### Рассуждение

Когда мы говорим об агрегатах в DDD, мы переходим от мышления «таблицами в БД» к мышлению «бизнес-правилами». Главная проблема начинающих архитекторов в том, что они пытаются либо сделать агрегат слишком маленьким (что ведет к потере консистентности), либо слишком большим (что ведет к конфликтам при конкурентном доступе и падению производительности).

Для меня **Агрегат** — это не просто группа объектов, это **единица обеспечения консистентности (Consistency Boundary)**. Если внутри агрегата есть правило, которое должно соблюдаться *всегда* и *мгновенно*, то все элементы, участвующие в этом правиле, должны находиться внутри одного агрегата.

При определении границ я опираюсь на два критерила:
1. **Инварианты:** Какие бизнес-правила должны соблюдаться атомарно?
2. **Жизненный цикл:** Живут ли эти объекты вместе и умирают ли они вместе?

---

### Ответ

**Агрегат** — это кластер связанных объектов (сущностей и Value Objects), которые рассматриваются как единое целое для изменения данных. У агрегата есть только один «вход» — **Корень Агрегата (Aggregate Root)**. Весь внешний мир взаимодействует только с корнем. Никто не имеет права менять дочерние элементы агрегата, не пройдя через корень.

#### Пример: Система управления заказами

Представим процесс оформления заказа.

*   **Aggregate Root:** `Order` (Заказ).
*   **Дочерние сущности/объекты:** `OrderItem` (Позиция заказа), `ShippingAddress` (Адрес доставки — Value Object), `Money` (Сумма — Value Object).

**Как работают границы:**
Если клиент хочет добавить товар в заказ, он вызывает метод `$order->addItem($product, $quantity)`.
Внутри этого метода `Order` (Корень) делает две вещи:
1. Проверяет инвариант: «Не превышен ли лимит товаров в заказе?».
2. Проверяет инвариант: «Общая сумма заказа не превышает кредитный лимит клиента?».
3. Добавляет `OrderItem`.

Все эти действия происходят внутри одной транзакции. Если что-то пойдет не так, весь агрегат откатится.

#### Типовая ошибка: "Слишком большой агрегат" (The Fat Aggregate)

Это самая частая ошибка. Разработчик решает, что раз всё связано, то нужно объединить всё в один огромный агрегат.

**Ошибка:** Попытка включить `Product` (Товар) внутрь агрегата `Order`.

**Почему это плохо:**
1. **Нарушение производительности:** Чтобы изменить количество товаров в одном заказе, вам придется заблокировать (через БД) не только заказ, но и объект `Product`. Если в этот же момент другой клиент пытается купить этот же товар, он будет ждать, пока первый клиент завершит транзакцию. Это убивает конкурентность (Concurrency).
2. **Проблема консистентности:** `Product` — это самостоятельная сущность с огромным жизненным циклом (цена, остатки, описание). Он не должен зависеть от того, существует конкретный заказ или нет.
3. **Сложность:** Агрегат становится гигантским, его трудно тестировать, и его состояние становится непредсказуемым.

**Как правильно:**
`Order` должен ссылаться на `Product` только через его **Identity** (например, `productId`), а не через прямую ссылку на объект. Это разрывает жесткую связь и позволяет `Product` жить своей жизнью.

#### Резюме: как я определяю границы

Когда я проектирую границы, я задаю себе три вопроса:

1.  **Нужно ли мне соблюдать это правило атомарно?** Если я меняю А, должен ли Б измениться *в ту же миллисекунду* в рамках той же транзакции? Если да — они в одном агрегате.
2.  **Является ли этот объект частью жизненного цикла корня?** Если я удалю Корень, должен ли этот объект исчезнуть? Если да — это часть агрегата.
3.  **Как часто эти объекты будут конкурировать за доступ?** Если я объединяю объекты, которые часто меняются разными пользователями одновременно, я создам "бутылочное горлышко" в БД. В этом случае их нужно разделить.

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

### Рассуждение

Этот вопрос переводит дискуссию из области чистого дизайна (DDD) в область реализации на уровне базы данных и инфраструктуры. Здесь мы сталкиваемся с проблемой **Concurrency Control** (контроль конкурентного доступа).

Если два процесса одновременно прочитали один и тот тот же агрегат, изменили его и попытались сохранить, возникает состояние **Race Condition** (состояние гонки). Без механизмов контроля один из процессов либо перезапишет изменения другого (**Lost Update**), либо мы получим некорректные данные, нарушающие инварианты.

В проектировании я рассматриваю два основных стратегии:
1. **Optimistic Concurrency Control (Пессимистичный подход к данным, но оптимистичный к коду):** Мы предполагаем, что конфликтов будет мало.
2. **Pessimistic Concurrency Control (Пессимистичный подход к доступу):** Мы блокируем данные на время работы.

Я также должен упомянуть, что выбор стратегии зависит от бизнес-контекста: насколько критична потеря данных и насколько высока частота конфликтов.

---

### Ответ

Когда два процесса одновременно изменяют один и тот же агрегат, результат зависит от выбранной стратегии управления конкурентностью.

#### 1. Optimistic Concurrency Control (OCC) — Оптимистичная блокировка
Это мой стандартный выбор для большинства веб-приложений. Мы не блокируем строки в БД, пока работаем с ними. Вместо этого мы проверяем, не изменился ли агрегат с момента его чтения.

**Как это реализуется в Doctrine:**
Используется механизм **Versioning**. В сущность добавляется поле `version` (обычно `integer`).

* **Процесс:**
    1. Процесс А читает `Order` (version = 1).
    2. Процесс Б читает `Order` (version = 1).
    3. Процесс А сохраняет изменения. Doctrine делает: `UPDATE orders SET ..., version = 2 WHERE id = 1 AND version = 1`. Успех.
    4. Процесс Б пытается сохранить изменения. Doctrine делает: `UPDATE orders SET ..., version = 2 WHERE id = 1 AND version = 1`.
    5. **Результат:** База возвращает "0 строк изменено", так как `version` уже равна 2. Doctrine выбрасывает `OptimisticLockException`.

**Trade-offs:**
* **Плюсы:** Высокая производительность, нет долгоживущих блокировок в БД, система масштабируема.
* **Минусы:** При высокой конкурентности (когда много людей одновременно правят один объект) пользователи будут постоянно получать ошибки. Нужно продумывать стратегию обработки: повторить попытку (retry) или сообщить пользователю, что данные устарели.

#### 2. Pessimistic Concurrency Control — Пессимистичная блокировка
Если конфликты случаются постоянно и цена ошибки — огромные деньги (например, в высоконагруженных финансовых транзакциях), я использую блокировки на уровне БД.

**Как это реализуется:**
Использование `SELECT ... FOR UPDATE`.

* **Процесс:**
    1. Процесс А читает `Order` с инструкцией `FOR UPDATE`. БД ставит эксклюзивную блокировку на эту строку.
    2. Процесс Б пытается прочитать этот же `Order` с `FOR UPDATE`. Он **замирает** и ждет, пока Процесс А не завершит транзакцию (commit или rollback).
    3. Процесс А завершает работу.
    4. Процесс Б "просыпается", читает уже обновленные данные и продолжает работу.

**Trade-offs:**
* **Плюсы:** Гарантированная консистентность, пользователь никогда не получит ошибку "данные изменились", конфликты разрешаются очередью на уровне БД.
* **Минусы:** 
    * **Низкая производительность:** Процессы стоят в очереди.
    * **Риск Deadlocks (взаимных блокировок):** Если Процесс А заблокировал Объект 1 и хочет Объект 2, а Процесс Б заблокировал Объект 2 и хочет Объект 1 — система зависнет.

#### Моя стратегия проектирования

При проектировании я следую этим правилам:

1.  **По умолчанию — Optimistic Locking.** В 95% случаев (профили пользователей, заказы, статьи) это лучшее решение. Я настраиваю обработку `OptimisticLockException` на уровне Application Layer (например, через автоматический retry в Command Bus или уведомление пользователя).
2.  **Для критических финансовых операций — Pessimistic Locking.** Если речь идет о списании денег со счета, где конкуренция может быть высокой, я использую `Pessimistic Write`.
3.  **Минимизация размера агрегата.** Чем меньше агрегат, тем меньше вероятность, что два процесса наткнутся на него одновременно. Это лучший способ снизить конкуренцию на архитектурном уровне.
4.  **Использование Idempotency Keys.** При работе с внешними API или асинхронными сообщениями я всегда добавляю ключи идемпотентности, чтобы повторная попытка (retry) после ошибки оптимистичной блокировки не создала дублирующий эффект.

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

### Рассуждение

Вопрос о доменных событиях (Domain Events) — это вопрос о переходе от **командной модели** (когда мы говорим «сделай это») к **реактивной модели** (когда мы говорим «это произошло»). 

Многие путают доменные события с интеграционными событиями (которые улетают в RabbitMQ для других микросервисов). Это разные уровни. Доменное событие — это факт, который произошел внутри границ одного агрегата или между ними, и который другие части системы должны узнать, чтобы среагировать.

Главная проблема, которую я решаю с помощью событий — это **декаплинг (развязка)**. Без событий мой `OrderService` превращается в «бога», который знает обо всем: и о почте, и о складе, и о бонусах. С событиями `OrderService` просто говорит: «Заказ создан», а все остальные подписываются на это.

Я разделяю процесс на три аспекта: **возникновение**, **публикация** и **обработка**. И самый важный момент здесь — **атомарность**.

---

### Ответ

#### 1. Когда и как публиковать события

Доменное событие должно создаваться **внутри агрегата** в момент изменения его состояния, но публиковаться оно должно **после** того, как транзакция будет успешно зафиксирована в базе.

**Как я это реализую:**
Я не вызываю `EventDispatcher` прямо внутри метода агрегата (это нарушит чистоту домена, так как агрегат начнет зависеть от инфраструктуры). Вместо этого:
1. Агрегат накапливает события во внутреннем массиве `$recordedEvents`.
2. После того как `OrderService` вызвал `$entityManager->flush()`, я извлекаю эти события из агрегата и отправляю их в шину событий.

#### 2. Связь с транзакциями (Самый критичный момент)

Это главная ловушка. Существует два сценария:

**Сценарий А: Публикация внутри транзакции (Опасно)**
Если я отправлю событие (например, в RabbitMQ) *до* того, как `flush()` завершится, может случиться так: сообщение улетело, воркер его подхватил и начал обрабатывать, но в этот момент БД упала и транзакция откатилась. 
**Результат:** Мы отправили письмо о заказе, которого не существует в базе. Это нарушение консистентности.

**Сценарий Б: Публикация после транзакции (Transactional Outbox)**
Чтобы гарантировать, что событие будет опубликовано **только если транзакция прошла успешно**, я использую один из двух подходов:
1. **Post-Flush Dispatching:** Я собираю все события из измененных сущностей после успешного `flush()` и только тогда пускаю их в шину.
2. **Outbox Pattern (самый надежный):** Я записываю событие в ту же базу данных в ту же транзакцию, где меняется агрегат (в таблицу `outbox_messages`). Отдельный процесс (Relay) читает эту таблицу и перекладывает сообщения в брокер. Это гарантирует **at-least-once delivery**.

#### 3. Проблемы, которые это решает

*   **Слабая связность (Low Coupling):** `OrderService` больше не знает о существовании `EmailService` или `InventoryService`. Он просто сообщает о факте.
*   **Расширяемость (Extensibility):** Чтобы добавить новую реакцию на создание заказа (например, отправку SMS), мне не нужно менять код `OrderService`. Я просто создаю новый `Listener`.
*   **Single Responsibility:** Каждый сервис занимается только своей узкой задачей.

#### 4. Проблемы, которые это создаёт

*   **Сложность отладки (Observability):** Поток управления становится нелинейным. Когда я читаю код `OrderService`, я не вижу, что после его завершения запускается еще 5 процессов. Нужно использовать инструменты трассировки (Jaeger, Zipkin), чтобы понять цепочку событий.
*   **Eventual Consistency (Согласованность в конечном счете):** Система перестает быть мгновенно согласованной. В момент создания заказа склад еще может не знать о нем. Приложению нужно уметь работать с этим состоянием (например, показывать пользователю статус «Обрабатывается»).
*   **Дублирование событий:** Из-за механизмов повторных попыток (retry) обработчик может получить одно и то же событие дважды. Это заставляет меня делать обработчики **идемпотентными**.

**Итог:** Я использую доменные события для развязки компонентов, но всегда слежу за тем, чтобы их публикация была жестко привязана к успешному завершению транзакции (через Outbox или Post-Flush), и всегда проектирую обработчики как идемпотентные функции.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

### Рассуждение

Этот вопрос затрагивает фундамент проектирования сложных систем. Здесь важно не просто дать определения, а показать разницу в **мышлении**. 

Многие разработчики путают эти понятия, потомую что на уровне SQL и Entity (в Doctrine) всё кажется похожим — это просто строки в таблицах. Но в DDD разница не в том, *как это хранится*, а в том, *как это живет и как мы о нем думаем*.

Я разделяю ответ на три части:
1. **Сущность vs Value Object:** Сравнение через призму идентичности и жизненного цикла.
2. **Методология принятия решения:** Мой алгоритм классификации концепций.
3. **Ubiquitous Language:** Как слова из разговора с бизнесом превращаются в названия классов и методов.

---

### Ответ

#### 1. Entity vs Value Object

Главное различие заключается в **идентичности (Identity)**.

* **Entity (Сущность):**
    * Имеет уникальный идентификатор (ID), который не меняется на протяжении всей жизни объекта.
    * Важна её **личность**, а не её свойства. Если у двух пользователей одинаковые имена и фамилии, они всё равно разные люди, потому что у них разные ID.
    * Обладает жизненным циклом: она рождается, меняет состояние (свойства) и умирает.
    * *Пример:* `User`, `Order`, `Product`.

* **Value Object (Объект-значение):**
    * Не имеет идентификатора. Его уникальность определяется исключительно его **значениями**.
    * Важна его **составная часть**, а не личность. Если у двух денег одинаковое количество и валюта, это «одни и те же деньги».
    * Он **неизменяем (Immutable)**. Если вы хотите изменить возраст пользователя, вы не меняете поле в существующем объекте, а заменяете старый Value Object новым.
    * *Пример:* `Money`, `Address`, `Email`, `Color`.

**Краткая шпаргалка:** Если я заменю все свойства объекта на точно такие же — это всё еще тот же объект? Если **да** — это Entity. Если **нет** (это фактически новый объект) — это Value Object.

#### 2. Как я определяю границы (Алгоритм классификации)

Когда я встречаю новую концепцию в домене, я задаю себе три вопроса:

1.  **Есть ли у этого объекта уникальный жизненный путь?** Если объект «движется» по системе, меняет статусы и имеет ID — это **Entity**.
2.  **Является ли этот объект просто описанием чего-то другого?** Если это просто атрибут (например, цвет или цена), который не имеет смысла без владельца — это **Value Object**.
3.  **Нужно ли мне отслеживать изменения в этом объекте по отдельности?** Если я хочу знать, что «адрес изменился», но мне не важно, какой именно это был адрес, а важен только факт изменения — адрес может быть Value Object.

#### 3. Единый язык (Ubiquitous Language)

**Ubiquitous Language** — это общий язык, который используют разработчики, эксперты предметной области (бизнес), менеджеры и тестировщики. Это не «перевод» с бизнес-языка на программистский, это **один и тот тот же язык для всех**.

**Как он влияет на код:**

*   **Имена классов и методов:** Если бизнес говорит: «Мы *аннулируем* заказ», то в коде не должно быть метода `deleteOrder()` или `setStatus(CANCELLED)`. Там должен быть метод `cancel()`. Если бизнес говорит «заказ *отменен*», метод должен называться `isCancelled()`.
*   **Устранение когнитивного диссонанса:** Когда разработчик читает код, он должен видеть бизнес-процесс, а не алгоритм. Код должен читаться как текст на языке бизнеса.
*   **Предотвращение ошибок:** Большинство багов возникает из-за того, что разработчик понял термин не так, как бизнес. Если у нас есть общий язык, этот разрыв сокращается.

**Пример влияния:**
*   *Плохо (технический язык):* `updateUserStatus(int statusId)`
*   *Хорошо (Ubiquitous Language):* `promoteUserToPremium()`

**Итог:** Моя задача как инженера — сделать так, чтобы структура кода (классы, методы, связи) была зеркальным отражением бизнес-модели, описанной на языке экспертов. Если код и бизнес-язык расходятся — архитектура начинает разрушаться.

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

### Рассуждение

Когда мы говорим о Чистой Архитектуре (Clean Architecture), мы говорим о **разделении ответственности** и **инверсии зависимостей**. Главная цель — сделать так, чтобы бизнес-логика (сердце системы) не знала о том, какая база данных используется, какой фреймворк выбран или как данные приходят (HTTP или CLI).

Многие совершают ошибку, смешивая слои, превращая их в «слоеный пирог», где каждый слой знает о следующем. В чистой архитектуре всё работает наоборот: **зависимости направлены внутрь, к центру (к бизнес-логике).**

Я разделяю приложение на четыре основных уровня (слоя), которые я называю:
1. **Domain (Ядро)** — правила бизнеса.
2. **Application (Use Cases)** — сценарии использования.
3. **Infrastructure (Implementation Details)** — инструменты.
4. **Interfaces/Presentation (Entry Points)** — точки входа.

---

### Ответ

#### 1. Структура слоев

**Слой 1: Domain (Самый внутренний)**
Здесь живет «чистая» логика, не зависящая ни от чего.
* **Что внутри:** Сущности (Entities), Value Objects, Доменные исключения, интерфейсы репозиториев, доменные сервисы.
* **Зависимости:** **Ноль**. Этот слой не импортирует ничего из внешних библиотек (кроме, возможно, базовых PHP-типов).

**Слой 2: Application (Use Cases)**
Здесь описываются сценарии, которые пользователь хочет выполнить.
* **Что внутри:** Команды (Commands), Запросы (Queries), Обработчики (Handlers), DTO (Data Transfer Objects), интерфейсы внешних сервисов (например, `EmailServiceInterface`).
* **Зависимости:** Только на слой **Domain**.

**Слой 3: Infrastructure**
Здесь реализуются технические детали.
* **Что внутри:** Реализация репозиториев (SQL/Doctrine), реализации почтовых сервисов (Mailgun/Symfony Mailer), работа с очередями, кэширование.
* **Зависимости:** На слой **Application** (чтобы реализовать его интерфейсы) и на слой **Domain** (чтобы работать с его сущностями).

**Слой 4: Presentation / Interfaces (Внешний слой)**
Точки входа в приложение.
* **Что внутри:** Контроллеры, CLI-команды, консольные обработчики, API-ресурсы.
* **Зависимости:** На слой **Application** (чтобы вызвать нужный сценарий).

---

#### 2. Куда попадут компоненты?

Важно понимать: компоненты не «живут» в слоях, они **реализуют** слои.

* **Symfony-контроллер:** Попадает в слой **Presentation**. Его задача — принять HTTP-запрос, превратить его в DTO и передать в слой Application. Он не должен содержать никакой бизнес-логики.
* **Doctrine (ORM/Repository Implementation):** Попадает в слой **Infrastructure**. В слое Domain лежит только интерфейс `UserRepositoryInterface`. Реализация `DoctrineUserRepository` лежит в Infrastructure и импортирует Doctrine.
* **Обработчик очереди (Message Handler):** Попадает в слой **Application** (если он просто выполняет сценарий) или в **Infrastructure** (если он является механизмом запуска). Обычно это "входная точка", аналогичная контроллеру, поэтому он находится на границе Presentation/Infrastructure.

---

#### 3. Правило зависимостей (Dependency Rule)

**Зависимости всегда направлены к центру.**
* `Presentation` $\rightarrow$ `Application` $\rightarrow$ `Domain`
* `Infrastructure` $\rightarrow$ `Application` $\rightarrow$ `Domain`

Никогда не должно быть ситуации, когда класс из `Domain` импортирует класс из `Infrastructure`. Если `Order` должен быть сохранен, он не вызывает `EntityManager->persist()`. Он просто меняет свое состояние, а `Application Service` вызывает репозиторий, который (через интерфейс) делает это в инфраструктуре.

---

#### 4. Как следить за соблюдением границ?

Чтобы архитектура не превратилась в "спагетти", я использую три метода:

1. **Статический анализ (PHPStan / Psalm):** Я настраиваю правила, которые запрещают определенные импорты. Например, можно настроить правило: «Классы в папке `Domain` не могут использовать пространства имен `Doctrine\*` или `Symfony\*`».
2. **Архитектурные тесты (Deptrac):** Это инструмент, специально созданный для проверки слоев. Я пишу конфигурацию, которая явно описывает правила: «Слой Application может зависеть от Domain, но не может зависеть от Infrastructure». Если кто-то нарушит правило, CI/CD упадет.
3. **Code Review:** Это последний, но важнейший рубеж. Я смотрю не только на то, *что* делает код, но и на то, *где* он это делает. Если я вижу в контроллере запрос к базе через `EntityManager` — это архитектурный дефект, который должен быть возвращен на доработку.

**Итог:** Чистая архитектура — это не про то, как разложить файлы по папкам, а про то, как **направить стрелки зависимостей** так, чтобы бизнес-логика была защищена от изменений во внешнем мире.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

### Рассуждение

Вопрос тестирования — это вопрос о **стоимости и уверенности**. Если тестов слишком мало — мы боимся деплоить. Если их слишком много и они медленные — разработчики перестают их запускать, и они превращаются в «мертвый груз».

Я не сторонник слепого следования «пирамиде тестов», так как в реальных проектах она часто превращается в «ромб» или «гексагон» (слишком много интеграционных тестов). Я выбираю стратегию, основанную на **ценности каждого типа теста** и **скорости обратной связи**.

Мой подход строится на трех столпах:
1. **Специфика тестового слоя:** Разделение на Unit, Integration и Functional.
2.**Управление внешними зависимостями:** Что мы подменяем (Mock), а что оставляем «настоящим».
3.**Инфраструктурная оптимизация:** Как сделать так, чтобы тесты не превратились в многочасовой процесс.

---

### Ответ

#### 1. Стратегия: Сбалансированная пирамида

Я придерживаюсь классической пирамиды, но с поправкой на специфику Symfony:

*   **Unit-тесты (Основание):** 
    *   **Что тестируем:** Доменную логику (Entities, Value Objects, Domain Services). 
    *   **Как:** Изолированно, без загрузки контейнера Symfony. Это максимально быстрые тесты.
    *   **Mocking:** Здесь мы мокаем абсолютно всё, что не является чистым PHP-объектом (репозитории, внешние API).

*   **Integration-тесты (Середина):** 
    *   **Что тестируем:** Взаимодействие с инфраструктурой. Работа репозитория с PostgreSQL, работа с очередями, интеграция сервисов.
    *   **Как:** Здесь мы загружаем `Kernel`, используем реальную базу данных (в контейнере/Docker).
    *   **Mocking:** Мы **не мокаем** базу данных. Мы используем реальную PostgreSQL. Мокаем только внешние HTTP-сервисы (четрез `MockHttpClient`).

*   **Functional / End-to-End тесты (Вершина):**
    *   **Что тестируем:** Полный цикл запроса. От контроллера до ответа и записи в БД.
    *   **Как:** Используем `WebTestCase` в Symfony. Проверяем статус ответа, JSON-структуру и состояние БД после запроса.

#### 2. Что мокаем, а что нет?

Это самый важный вопрос для стабильности.

*   **НЕ мокаем (используем реальные):**
    *   **Базу данных (PostgreSQL):** Мокать репозитории в интеграционных тестах — это «тестировать мок, а не код». Мы должны знать, что наш SQL или DQL действительно работает.
    *   **Value Objects и Entities:** Они часть домена.
*   **МОКАЕМ (через Mock/Stub/Spy):**
    *   **Внешние API:** Чтобы тесты не зависели от интернета и сторонних сервисов (Stripe, Twilio). Используем `MockHttpClient` или `WireMock`.
    *   **Файловая система:** Чтобы не мусорить на диске и не зависеть от прав доступа.
    *   **Случайные факторы:** `ClockInterface` (чтобы тесты времени были детерминированными) и `Random`.

#### 3. Как поддерживать тесты быстрыми и стабильными?

Медленные тесты — это смерть продуктивности. Я использую следующие приемы:

**Для скорости:**
1.  **Database Transactions:** В тестах я не делаю `TRUNCATE` или `DROP/CREATE` после каждого теста. Я оборачиваю каждый тест в транзакцию и делаю `rollback` в конце (`$em->beginTransaction()` / `$em->rollback()`). Это на порядок быстрее.
2.__________________**Parallel Testing:** Использую `Paratest` для запуска тестов в несколько потоков. Для этого у каждого потока должна быть своя база данных (например, `db_test_1`, `db_test_2`).
3.  **In-memory SQLite (Осторожно!):** Иногда используют SQLite в памяти, но я **не рекомендую** это для серьезных проектов, так because PostgreSQL и SQLite ведут себя по-разному (особенно в части типов данных и JSONB). Это создает «ложное чувство безопасности».

**Для стабильности (избегаем Flaky Tests):**
1.  **Deterministic Data:** Никаких `rand()` или `now()`. Всегда использую фиксированные значения или мокаю `ClockInterface`.
2.  **Isolation:** Каждый тест должен быть независим. Я слежу, чтобы один тест не оставлял «хвостов» в базе, которые могут повлиять на следующий (решается через транзакции или очистку).
3.  **Wait-and-retry для асинхронности:** Если мы тестируем Messenger, я не использую `sleep()`. Я использую циклы с коротким ожиданием (polling), проверяя состояние БД, пока условие не будет выполнено или не выйдет таймаут.

**Итог:** Моя стратегия — **максимум Unit-тестов для логики, реальная база для интеграции и строгая изоляция внешних систем через моки.** Это дает баланс между скоростью разработки и уверенностью в качестве кода.

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Это классическая проблема конкурентного доступа в многопользовательских системах. Если два процесса одновременно прочитают состояние $A$, изменят его локально до $A_1$ и $A_2$ и попытаются записать обратно, мы столкнемся с проблемой **Lost Update (Потерянное обновление)**: изменения одного из пользователей просто «затрут» изменения другого без предупреждения.

Я разделяю стратегии защиты на две категории: **Optimistic (Оптимистичная)** и **Pessimistic (Пессимистичная)**.

---

### 1. Optimistic Concurrency Control (OCC) — Оптимистичный подход

Мы исходим из предположения, что конфликты случаются редко. Мы не блокируем запись, а проверяем версию данных в момент сохранения.

**Механизм:**
В таблицу добавляется колонка `version` (обычно `INT`). При каждом `UPDATE` мы добавляем условие: `WHERE id = :id AND version = :old_version`. Если за это время кто-то другой изменил запись, версия в базе уже не совпадает с нашей, `UPDATE` затронет 0 строк, и система поймет, что произошел конфликт.

**В Symfony/Doctrine:**
Это реализуется одной аннотацией `#[ORM\Version]` над полем. Doctrine сама будет проверять версию и выбрасывать `OptimisticLockException`.

*   **Плюсы:**
    *   **Высокая производительность:** Нет реальных блокировок в БД, транзакции проходят быстро.
    *   **Масштабируемость:** Идеально для высоконагруженных систем с редкими конфликтами.
*   **Минусы:**
    *   **Необходимость обработки ошибок:** Приложение должно уметь реагировать на исключение (например, предложить пользователю обновить страницу и попробовать снова).
*   **Когда выбираю:** В 90% случаев в Web-приложениях (редактирование профиля, изменение настроек, создание заказов).

---

### 2. Pessimistic Concurrency Control — Пессимистичный подход

Мы предполагаем, что конфликт может произойти, и блокируем доступ к записи в момент её чтения.

**Механизм:**
Используется SQL-команда `SELECT ... FOR UPDATE`. Когда Процесс А читает запись, база данных накладывает на неё эксклюзивную блокировку. Процесс Б, попытавшись прочитать эту же запись с `FOR UPDATE`, будет вынужден ждать, пока Процесс А не завершит транзакцию (`COMMIT` или `ROLLBACK`).

**В Symfony/Doctrine:**
Реализуется через метод `$em->find(Entity::class, $id, LockMode::PESSIMISTIC_WRITE)`.

*   **Плюсы:**
    *   **Гарантия консистентности:** Конфликты физически невозможны, так чтение заблокировано.
    *   **Простота для пользователя:** Пользователь не получает ошибок «версия изменилась», он просто ждет чуть дольше.
*   **Минусы:**
    *   **Низкая производительность:** Блокировки держат соединения и ресурсы БД.
    *   **Риск Deadlocks:** Если два процесса заблокируют разные записи и попытаются захватить те, что держат другие, возникнет взаимная блокировка.
*   **Когда выбираю:** В критически важных финансовых операциях (списание денег со счета, инвентаризация склада), где цена потери данных или ошибки выше, чем цена ожидания пользователя.

---

### Сравнительная таблица

| Критерий | Optimistic (Версионность) | Pessimistic (Блокировка) |
| :--- | :--- | :--- |
| **Основная идея** | "Проверь, не изменилось ли за время моей работы" | "Я занял эту строку, никто не трогайте" |
| **Производительность** | Очень высокая | Низкая (зависит от длительности транзакции) |
| **Риск Deadlock** | Отсутствует | Высокий |
| **Опыт пользователя** | Может получить ошибку "Конфликт версий" | Может столкнуться с долгой загрузкой (таймаутом) |
| **Типичный кейс** | CMS, соцсети, CRM | Банковские транзакции, бронирование билетов |

---

### Мой финальный выбор

Мой алгоритм принятия решения таков:

1.  **Если конфликт — это редкое исключение** (например, два админа одновременно правят один пост в блоге) $\rightarrow$ **Optimistic Locking**. Это сохранит отзывчивость системы.
2.  **Если конфликт — это ожидаемая часть бизнес-процесса** (например, два процесса пытаются одновременно забронировать последнее место на рейсе) $\rightarrow$ **Pessimistic Locking**. Здесь мы не можем позволить пользователю «попробовать еще раз», мы должны гарантировать результат при первой попытке.
3.  **Если мы боимся Deadlocks** при использовании пессимистичных блокировок $\rightarrow$ я всегда слежу за **строгим порядком захвата ресурсов** (всегда блокируем объекты в одном и том же порядке, например, всегда сначала `User`, потом `Account`).

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

### Рассуждение

Когда меня спрашивают о процессе, я не хочу рассказывать про «правила из учебника». Я хочу рассказать о том, как выстроить **предсказуемый конвейер поставки ценности (Delivery Pipeline)**, который минимизирует риск поломки продакшена и максимизирует скорость работы команды.

Мой подход базируется на трех принципах:
1. **Изоляция изменений:** Каждая задача — это отдельный изолированный контекст.
2. **Автоматизация контроля:** Человек не должен проверять синтаксис или тесты, это делает CI. Человек должен проверять только логику и архитектуру.
3. **Малые и частые релизы:** Чем меньше изменений в одном релизе, тем проще найти причину ошибки, если что-то пойдет не так.

Я не сторонник жесткого GitFlow с его бесконечными ветками `develop` и `release`, так как он создает «интеграционный ад» в конце спринта. Я предпочитаю вариацию **GitHub Flow** с элементами **Trunk-based Development**.

---

### Ответ

Мой процесс разбит на пять четких этапов.

#### 1. Ветвление (Branching Strategy)
Я использую **Short-lived Feature Branches**.

* **Как это работает:** Каждая задача (Jira/Linear/Trello) порождает ветку от `main`. Ветка живет недолго — от нескольких часов до пары дней.
* **Почему так:** Я избегаю долгоживущих веток. Чем дольше ветка живет отдельно от `main`, тем сложнее будет её влить (Merge Hell). Мы стремимся к тому, чтобы `main` всегда был в состоянии "ready to deploy". Если задача большая — мы разбиваем её на маленькие подзадачи, каждая из которых — отдельная ветка.

#### 2. Формат коммитов (Commit Message Convention)
Я придерживаюсь стандарта **Conventional Commates**.

* **Формат:** `type(scope): description` (например, `feat(auth): add JWT authentication` или `fix(order): resolve race condition in payment`).
* **Почему так:** Это позволяет нам:
    1. Автоматически генерировать **Changelog**.
    2. Автоматически определять версию (SemVer) при релизе.
    3. Быстро фильтровать историю (например, найти все `fix` в конкретном модуле).

#### 3. Pull Request (PR) и Code Review
PR — это не просто «проверка кода», это инструмент обмена знаниями.

* **Процесс:** 
    1. Я создаю PR, как только у меня есть минимально работающий код.
    2. **Автоматический этап:** Перед тем как человек откроет PR, **CI (Continuous Integration)** должен пройти: линтеры (PHP_CodeSniffer), статический анализ (PHPStan), тесты (PHPUnit). Если CI упал — ревьюер даже не смотрит код.
    3. **Ручной этап:** Ревьюер смотрит на:
        * Соответствие архитектуре (не нарушен ли SRP/DIP?).
        * Читаемость и именование.
        * Покрытие тестами.
        * Потенциальные побочные эффекты.
* **Почему так:** Мы не тратим время человека на проверку пробелов или пропущенных тестов. Мы фокусируемся на проектировании.

#### 4. Релизы (Deployment & Release)
Я сторонник **Continuous Deployment (CD)** или, как минимум, **Continuous Delivery**.

* **Как это работает:** После апрува в PR и успешного прохождения всех тестов в CI, ветка вливается в `main`. После этого автоматически запускается процесс деплоя на стейджинг, а после финального тестирования — на продакшен.
* **Версионирование:** Используется **Semantic Versioning (SemVer)**. Версия обновляется автоматически на основе типов коммитов (`feat` $\rightarrow$ minor, `fix` $\rightarrow$ patch).
* **Почему так:** Маленькие релизы снижают риск. Если мы выкатили одну маленькую фичу и всё упало — мы откатываемся за секунды. Если мы выкатили релиз с 50 фичами — мы не знаем, кто виноват.

#### 5. Обработка инцидентов (Rollback)
Если на продакшене что-то сломалось, мой приоритет — **быстрый откат (Rollback)**, а не "быстрое исправление" (Hotfix) прямо на лету. Мы откатываем версию в Git/Kubernetes, а потом спокойно разбираем баг в локальной среде.

---

### Резюме процесса

1. **Задача** $\rightarrow$ Создание ветки `feature/issue-123`.
2. **Разработка** $\rightarrow$ Коммиты по `Conventional Commits`.
3. **Push** $\rightarrow$ Запуск CI (Linter, PHPStan, Tests).
4. **PR** $\rightarrow$ Ревью архитектуры + Апрув.
5. **Merge** $\rightarrow$ Вливание в `main`.
6. **Deploy** $\rightarrow$ Автоматический деплой на Prod.

**Это позволяет команде двигаться быстро, не боясь сломать систему, потомут каждый шаг защищен автоматикой и четким регламентом.**

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

### Рассуждение

Вопрос о код-ревью — это вопрос не о поиске ошибок, а о **культуре команды**. Если ревью превращается в «полицейский надзор» или «битву эго», команда замедляется, а разработчики начинают писать код так, чтобы он просто «прошел проверку», а не так, чтобы он был качественным.

Для меня хороший ревью — это **диалог**. Моя цель как ревьюера — не «поймать» автора на ошибке, а помочь ему сделать систему лучше и подтянуть его уровень. 

Я разделяю процесс на три составляющие: **приоритеты (что смотрим)**, **коммуникация (как пишем)** и **разрешение конфликтов (как договариваемся)**.

---

### Ответ

#### 1. На что я смотрю в первую очередь (Приоритеты)

Я не трачу время на обсуждение того, где должна стоять открывающая скобка (это задача линтера). Я иду по иерархии:

1.  **Архитектура и дизайн (High Priority):**
    *   Не нарушены ли границы слоев? (Например, не уплыла ли бизнес-логика в контроллер).
    *   Соблюден ли SRP? Не превращается ли этот класс в «бога»?
    *   Правильно ли выбраны паттерны? (Не является ли этот класс избыточным или, наоборот, слишком упрощенным).
2.  **Корректность и надежность (Medium Priority):**
    *   Обработаны ли крайние случаи (edge cases)? Что будет, если придет `null` или пустой массив?
    *   Неты ли здесь гонок данных (race conditions) или проблем с транзакциями?
    *   Покрыт ли новый код тестами?
3.  **Читаемость и поддерживаемость (Low Priority):**
    *   Понятно ли из имен переменных, что происходит?
    *   Не слишком ли сложен этот метод? Можно ли его упростить?
    *   *Это важная часть, но я никогда не блокирую PR только из-за стиля, если он не нарушает стандарты команды.*

#### 2. Как я маркирую замечания (Коммуникация)

Чтобы ревью не выглядело как поток критики, я использую систему уровней важности. Это позволяет автору понять, что критично, а что — лишь моё мнение.

*   **`[BLOCKER]` (или `Critical`):** Ошибка, которая приведет к багу в проде или нарушит архитектуру. Требует обязательного исправления.
*   **`[SUGGESTION]` (или `Nitpick`):** Моё мнение. «Мне кажется, здесь лучше использовать `match` вместо `switch`». Это не обязательно исправлять, но стоит обдумать.
*   **`[QUESTION]`:** Я не уверен, что здесь происходит. «Почему здесь используется этот цикл вместо `array_map`?». Это призыв к объяснению, а не к исправлению.
*   **`[CHALLENGE]`:** Когда я предлагаю альтернативный подход, который может быть лучше.

**Золотое правило:** Я критикую **код**, а не **человека**. Вместо «Ты сделал ошибку здесь» я пишу «Этот подход может привести к потере данных, если...».

#### 3. Как поступаю при разногласии

Разногласия — это нормально. Это признак того, что команда думает.

1.  **Аргументируй через последствия:** Я никогда не говорю «мне не нравится». Я говорю: «Если мы сделаем так, то при расширении системы нам придется переписывать этот модуль, потому что...». Я апеллирую к стоимости поддержки и рискам.
2.  **Выходи из текстового поля:** Если мы ходим вокруг да около в комментариях более 3-4 реплик — я предлагаю созвониться или подойти к столу. Текст не передает интонацию и часто порождает недопонимание.
3.  **Принцип "Disagree and Commit":** Если мы зашли в тупик, и аргументы сторон равны, я не буду стоять на своем до последнего. 
    *   Если автор — Junior, я могу уступить, если это не критическая ошибка, чтобы не демотивировать его.
    *   Если спор серьезный, мы выносим его на обсуждение с техлидом или архитектором.
    *   Если решение принято (даже если я с ним не согласен), я принимаю его и работаю дальше.

**Итог:** Хорошее ревью — это когда после него автор не чувствует себя «разгромленным», а чувствует, что его код стал чище, а он сам — сильнее.

## Q21 · Работа с задачами

**Интервьюер:** Вот сырая проблема от бизнеса: «Пользователи жалуются, что не могут найти свои заказы из прошлого, поддержка завалена обращениями». Сформулируй из неё задачу для исполнителя — так, чтобы её можно было выполнить без уточнений. Что обязательно включишь в формулировку и почему?

**Кандидат:**

### Рассуждение

Когда бизнес приходит с фразой «всё плохо, пользователи жалуются», это не задача. Это **симптом**. ## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

### Рассуждение

Сразу сделаю важное уточнение: в PostgreSQL **не существует синтаксиса `FORCE INDEX`**, как это реализовано в MySQL. Если вы попробуете написать `SELECT * FROM table FORCE INDEX (idx_name)`, вы получите синтаксическую ошибку.

Однако в PostgreSQL есть концепция, которая выполняет ту же задачу — **управление планом выполнения запроса**. Когда разработчик хочет «заставить» базу использовать конкретный индекс, он сталкивается с тем, что планировщик (Planner) может его игнорировать.

Почему планировщик может игнорировать индекс?
1. **Низкая селективность:** Если индекс вернет 50% всей таблицы, планировщику дешевле прочитать таблицу целиком (`Seq Scan`), чем прыгать по индексу и затем лезть в кучу страниц данных (Random I/O).
2. **Устаревшая статистика:** Планировщик думает, что данных мало или они распределены иначе, чем на самом деле.
3. **Неправильная стоимость (Cost):** Стоимость чтения индекса в расчетах планировщика кажется выше, чем чтение таблицы.

Когда говорят о «принуждении» к индексу в Postgres, обычно имеют в виду либо **изменение параметров сессии**, либо **переписывание запроса**.

---

### Ответ

Поскольку прямого аналога `FORCE INDEX` нет, в PostgreSQL для решения этой проблемы применяются следующие стратегии:

#### 1. Использование `SET enable_seqscan = off` (Временное принуждение)
Это самый близкий аналог. Мы можем на уровне текущей сессии запретить планировщику использовать последовательное сканирование.

```sql
BEGIN;
SET LOCAL enable_seqscan = off; -- Запрещаем Seq Scan только для этой транзакции
SELECT * FROM orders WHERE customer_id = 123;
COMMIT;
```

*   **Когда применять:** Только для **диагностики**. Если запрос с `enable_seqscan = off` работает быстро, значит, проблема в том, что планировщик считает индекс «дорогим». Если и так работает медленно — индекс не поможет.
*   **Почему это опасно:** Это не «лечит» причину. Если вы сделаете это в продакшене, вы можете сломать другие запросы, которые *должны* использовать `Seq Scan`.

#### 2. Исправление статистики (`ANALYZE`)
Часто планировщик игнорирует индекс, потому потому что он «думает», что в таблице всего 100 строк, хотя их миллион.

*   **Когда применять:** Если вы недавно загрузили много данных или провели массовое обновление.
*   **Действие:** Выполнить `ANALYZE table_name;`. Это обновит гистограммы распределения данных, и планировщик увидит реальную селективность индекса.

#### 3. Переписывание запроса (Query Refactoring)
Вместо того чтобы заставлять базу использовать индекс, мы пишем запрос так, чтобы у планировщика не было выбора, кроме как его использовать.

*   **Пример:** Использование функциональных индексов. Если вы ищете `WHERE lower(email) = 'test@test.com'`, обычный индекс по `email` не сработает. Нужно создать индекс `CREATE INDEX idx_email_lower ON users (lower(email));`.
*   **Использование CTE или Subqueries:** Иногда можно «спрятать» часть логики, чтобы планировщик сначала выполнил фильтрацию по индексу в подзапросе.

#### 4. Создание более подходящих индексов
Если индекс игнорируется, возможно, он просто не подходит под задачу.

*   **Covering Indexes (Index Only Scan):** Если запрос выбирает только `id` и `status`, создайте индекс `CREATE INDEX idx_status_id ON orders (status, id);`. Тогда Postgres вообще не будет заглядывать в саму таблицу (Heap), а возьмет всё из индекса. Это максимально быстро.
*   **Partial Indexes:** Если вы часто ищете только «активные» заказы, создайте индекс `CREATE INDEX idx_active_orders ON orders (id) WHERE status = 'active';`. Он будет крошечным и очень быстрым.

### Резюме: когда и что использовать?

| Ситуация | Что делать | Почему |
| :--- | :--- | :--- |
| **Нужно проверить, поможет ли индекс** | `SET enable_seqscan = off` | Диагностика без изменения структуры. |
| **Данные только что загружены** | `ANALYZE` | Обновление «мозгов» планировщика. |
| **Нужен сверхбыстрый поиск по полям** | `Covering Index` | Избегаем лишних чтений с диска (Heap). |
| **Поиск по части поля (напр. `lower()`)** | `Functional Index` | Позволяем индексу соответствовать условию. |
| **Постоянная проблема с селективностью** | `Partial Index` | Делаем индекс максимально узким и эффективным. |

**Мой совет:** Никогда не пытайтесь «зафорсить» индекс в коде приложения. Если планировщик его игнорирует — значит, он делает это по какой-то математической причине. Ваша задача — либо дать ему актуальную статистику (`ANALYZE`), либо создать более эффективный индекс, либо переписать запрос.

## Q25 · Провокации

**Интервьюер:** По твоему опыту, на сколько процентов strict_types=1 замедляет выполнение PHP-кода и почему?

**Кандидат:**

### Рассуждение

Это вопрос с подвохом. Если отвечать поверхностно: «на ноль процентов», потому что проверки происходят во время выполнения. Но если отвечать как инженер, который понимает, как работает Zend Engine, ответ будет: **«Влияние на производительность ничтожно, а в некоторых случаях оно может даже ускорить код»**.

Я не буду давать абстрактное число в процентах (например, «на 2%»), потомую что производительность зависит от профиля нагрузки: сколько у вас преобразований типов (coercion) и насколько много логики в коде.

Чтобы ответить глубоко, я разберу, что происходит «под капотом» при включении `strict_types=1`.

---

### Ответ

Короткий ответ: **Влияние `strict_types=1` на производительность практически незаметно (менее 0.1–1%) и зачастую оно даже положительно.**

Вот почему это так, исходя из внутренней механики PHP:

#### 1. Стоимость проверок (The Cost of Checks)
Многие думают, что `strict_types` заставляет PHP выполнять дополнительные, тяжелые проверки. На самом деле, проверка типов — это встроенная часть работы Zend Engine при вызове любой функции. 

*   **В режиме Coercive (по умолчанию):** Когда вы передаете `string` в функцию, ожидающую `int`, PHP **обязан** выполнить операцию преобразования (casting). Это операция: `(int) $value`. Она требует процессорного времени.
*   **В режиме Strict:** PHP просто проверяет: `if (gettype($value) !== 'integer') throw TypeError`. 

**Парадокс:** Проверка типа (простой `if`) технически может быть даже быстрее, чем выполнение логики приведения типов (особенно если это сложные преобразования строк в числа или даты). Таким образом, в некоторых сценариях `strict_types` может даже **ускорить** выполнение, так как мы избегаем неявных преобразований.

#### 2. Оптимизация JIT (Just-In-Time Compiler)
С появлением PHP 8 и JIT-компилятора роль типизации стала еще важнее.
*   JIT работает максимально эффективно, когда он точно знает типы данных. Чем более предсказуемы типы, тем лучше JИТ может генерировать машинный код без лишних проверок типов во время выполнения (type guards).
*   `strict_types=1` делает намерения разработчика максимально явными, что помогает оптимизатору компилятора лучше понимать поток данных.

#### 3. Где реально может быть замедление?
Замедление может возникнуть не из-за самого режима, а из-ло **изменения логики кода** под этот режим. 

Если раньше ваш код «проглатывал» неверные типы (например, передавая строку `"10"` туда, где нужен `int`), а теперь вы вынуждены везде писать явные приведения типов: `$func((int)$val)`, то эти явные преобразования добавят микроскопическую нагрузку. Но эта нагрузка была бы в любом случае, если бы вы хотели сделать код надежным.

#### 4. Реальный профиль нагрузки
В реальном приложении (Symfony, Laravel) узким местом всегда являются:
1.  **I/O операции** (Запросы к БД, к Redis, к API).
2.  **Аллокация памяти** (Создание тяжелых объектов).
3.  **Сериализация/Десериализация** (JSON, XML).

На фоне этих операций микросекунды, затраченные на проверку `strict_types`, составляют статистическую погрешность.

### Итог

Я никогда не использую `strict_types=1` с оглядкой на производительность. Я использую его ради **надежности (Reliability)** и **предсказуемости (Predictability)**. 

**Мой вердикт:** 
Риск получить `TypeError` во время выполнения — это цена, которую мы платим за чистоту кода. Но цена в плане производительности настолько мала, что она не должна быть фактором при принятии решения. Если ваш код замедлился после включения `strict_types`, значит, проблема не в режиме, а в том, что вы начали делать слишком много лишних преобразований типов вручную.

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

### Рассуждение

Этот вопрос — отличный тест на понимание философии инструментов. Сначала важно сделать критическую поправку: **утверждение, что Doctrine не поддерживает составные ключи, неверно.** Она их поддерживает через аннотации/атрибуты `#[Id]` на нескольких свойствах.

Однако, когда опытные разработчики говорят, что «Doctrine не поддерживает составные ключи», они имеют в виду **проблему их удобства и сложности интеграции с паттернами проектирования**.

Проблема не в невозможности технической реализации, а в том, что составные ключи ломают концепцию **Identity Map** и делают работу с **Entity Manager** крайне неудобной. В Doctrine сущность должна иметь один уникальный идентификатор, который можно легко передать в `find($id)`. Если у вас составной ключ, то вместо одного аргумента `$id` вам нужно передавать массив или объект, что усложняет все слои приложения.

Я разделяю решение этой проблемы на три стратегии: от «правильной с точки зрения DDD» до «прагматичной с точки зрения БД».

---

### Ответ

#### 1. Почему составные ключи — это «боль» для Doctrine?

Основная причина — архитектурная чистота. Doctrine спроектирована вокруг идеи, что у каждой сущности есть **Surrogate Key** (суррогатный ключ, например, `id` `AUTO_INCREMENT`).

*   **Сложность навигации:** Методы вроде `$em->find(User::class, $id)` работают идеально с одним значением. С составным ключом вам приходится передавать массив: `$em->find(User::class, ['userId' => 1, 'tenantId' => 5])`. Это размывает типизацию и усложняет API.
*   **Связи (Associations):** Создание связей между сущностями с составными ключами превращается в кошмар. Вам нужно маппить не одну колонку, а несколько, что делает конфигурацию огромной и хрупкой.
*   **Нарушение паттерна Identity Map:** Внутренний механизм отслеживания изменений в Doctrine заточен под поиск по единственному идентификатору.

#### 2. Как с этим живут в реальных проектах?

В индустрии принято использовать три основных подхода:

**Подход А: Использование суррогатного ключа (Best Practice для Doctrine)**
Это самый распространенный способ. Даже если в базе данных есть логический составной ключ (например, `user_id` + `product_id` в таблице `cart_items`), мы добавляем в таблицу техническую колонку `id` (Primary Key).

*   **Как это выглядит:** В БД у нас `id` (PK) и `UNIQUE(user_id, product_id)`.
*   **Плюсы:** Идеальная работа с Doctrine, легкие связи, простая навигация.
*   **Минусы:** Лишняя колонка в базе данных (но это ничтожная цена за удобство разработки).
*   **Когда использовать:** В 99% случаев. Это стандарт для современной разработки.

**Подход Б: Принятие составного ключа (Когда нельзя менять схему)**
Если вы работаете с Legacy-базой или существующей схемой, где составной ключ — это закон, вы используете возможности Doctrine.

*   **Как это выглядит:**
    ```php
    #[ORM\Entity]
    class OrderItem {
        #[ORM\Id, ORM\Column]
        private int $orderId;

        #[ORM\Id, ORM\Column]
        private int $productId;
    }
    ```
*   **Плюсы:** Полное соответствие существующей схеме БД.
*   **Минусы:** Сложность при использовании `$em->find()`, сложности с генерацией ID (вы не можете использовать `AUTO_INCREMENT` для одного из ключей в составе составного ключа в некоторых БД).
*   **Когда использовать:** Только при работе с существующими базами данных, которые вы не можете менять.

**Подход В: Использование Value Objects для ключей (DDD Way)**
Если составной ключ — это не просто набор ID, а осмысленная сущность (например, `CompositeId`), мы можем попробовать обернуть его. Но в Doctrine это все равно потребует маппинга каждой части ключа в Entity.

#### 3. Резюме и мой выбор

Если бы я проектировал систему с нуля, я бы **никогда не использовал составные первичные ключи**. 

**Мой выбор:**
Я всегда использую **Surrogate Key** (`id` `bigint auto_increment`) как первичный ключ. А для обеспечения уникальности бизнес-логики (например, чтобы у пользователя не было двух одинаковых заказов) я вешаю **Unique Constraint** на набор колонок.

Это дает нам:
1.  **Простоту в коде:** Мы всегда работаем с одним `int $id`.
2.  **Производительность:** Индексы по одиночным ключам работают максимально эффективно.
3.  **Целостность:** База данных все равно защитит нас от дубликатов благодаря `UNIQUE constraint`.

**Вывод:** Не бойтесь «лишней» колонки `id`. В долгосрочной перспективе удобство работы с чистыми сущностями и предсказуемостью ORM стоит гораздо дороже, чем пара байт в хранилище.

1.  **Domain Layer:** Создадим сущность `Order` (Entity) и интерфейс `OrderRepositoryInterface`.
2.  **Application Layer:** Создадим `PayOrderHandler`, который оркеструет процесс.
3.  **Infrastructure Layer:** Реализуем `SqlOrderRepository` и `SmtpMailer`.

#### Шаг 2: Реализация (Refactored Code)

**Domain Layer:**
```php
readonly class Order 
{
    public function __construct(
        public int $id,
        public string $email,
        public string $status,
    ) {}

    public function markAsPaid(): self 
    {
        // Возвращаем новый экземпляр (Immutability)
        return new self($this->id, $this->email, 'paid');
```

**Application Layer:**
```php
class PayOrderService 
{
    public function __construct(
        private OrderRepositoryInterface $repository,
        private MailerInterface $mailer,
        private LoggerInterface $logger,
        private EntityManagerInterface $transactionManager // Для управления транзакциями
    ) {}

    public function execute(int $orderId): void 
    {
        // Оборачиваем всё в транзакцию для обеспечения атомарности
        $this->transactionManager->transactional(function() use ($orderId) {
            $order = $this->repository->find($orderId);
            
            if (!$order) {
                throw new OrderNotFoundException($orderId);
            }

            $updatedOrder = $order->markAsPaid();
            $this->repository->save($updatedOrder);

            // В идеале здесь должен быть Event Dispatcher, 
            // но для простоты оставим так
            $this->mailer->send($updatedOrder->email, 'Ваш заказ оплачен');
            $this->logger->info("Order paid: " . $order->id);
        });
    }
}
```

```php
class OrderController extends AbstractController
{
    public function __construct(
        private PayOrderService $payOrderService
    ) {}

    public function pay(Request $request): Response
    {
        $id = (int) $request->get('order_id'); // Приведение к типу

            $this->payOrderService->execute($id);
            return new Response('ok', 200);

        } catch (\Exception $e) {

    }
}
```

#### Что изменилось и почему это лучше:

2.  **Тестируемость:** Теперь я могу написать Unit-тест на `PayOrderService`, подставив моки для `OrderRepository`, `Mailer` и `Logger`. Мне не нужна база данных или реальный SMTP-сервер.

4.  **Чистота (SRP):** Контроллер теперь только принимает запрос и возвращает ответ. Вся «грязная» работа скрыта в сервисе.
5.  **Типизация:** Мы работаем с объектом `Order`, а не с массивом. Если поле `email` в сущности будет переименовано, IDE и статический анализ сразу укажут на ошибку.

Этот код — классический пример того, как разработчики пытаются «упростить» себе жизнь, но в итоге создают архитектурный кошмар. Здесь нарушены все ключевые принципы, которые мы обсуждали ранее: **SRP**, **DIP (Dependency Inversion Principle)** и сама суть **Domain-Driven Design**.

Основная проблема здесь в том, что **сущность (Entity) перестала быть частью домена и стала частью инфраструктуры**.

**Что именно здесь не так:**

1.  **Нарушение SRP (Single Responsibility Principle):** Сущность `User` теперь отвечает не только за хранение данных пользователя и его бизнес-правила, но и за **сохранение самой себя в базу данных**. Это смешивание ответственности.
2.  **Нарушение DIP (Dependency Inversion Principle):** Доменная сущность зависит от `EntityManagerInterface`. Это инфраструктурный компонент. Теперь ваш домен «пропитан» деталями реализации вашей БД. Вы не можете протестировать `User` без поднятия тяжелого контейнера Symfony и настройки базы данных.

4.  **Проблема прозрачности изменений (Side Effects):** Метод `changeEmail` вызывает `flush()`. Это скрытый побочный эффект. 5.  **Проблема тестируемости:** Чтобы написать простой Unit-тест на смену email, мне нужно создать мок для `EntityManagerInterface`. Это избыточно и усложняет тесты.

Я бы полностью пересмотрел подход, разделив сущность и механизм сохранения.

#### Как это должно выглядеть (Исправленный вариант)

**1. Чистая доменная сущность (Domain Layer):**
Она ничего не знает о базе данных. Она только меняет свое состояние.

```php
#[ORM\Entity]
class User
{
    #[ORM\Id, ORM\GeneratedValue, ORM\Column]
    private ?int $id = null;

    #[ORM\Column(type: 'string', unique: true)]
    private string $email;

    public function __construct(string $email) 
    {
        // Здесь может быть валидация email
        $this->email = $email;
    }

    public function changeEmail(string $newEmail): void
    {
        // Бизнес-валидация (например, проверка формата или запрещенных доменов)
        if (!filter_var($newEmail, FILTER_VALIDATE_EMAIL)) {
            throw new \InvalidArgumentException("Invalid email format");
        }

        $this->email = $newEmail;
    }

    public function getEmail(): string
    {
        return $this->email;
    }

    public function getId(): ?int
    {
        return $this->id;
    }
}
```

**2. Применение в Application Layer (Use Case):**
Управление жизненным циклом и сохранением переносится в сервис.

```php
class ChangeEmailHandler
{
    public function __construct(
        private UserRepositoryInterface $repository, // Интерфейс, а не EntityManager
        private EntityManagerInterface $entityManager // Для управления транзакцией
    ) {}

    public function execute(int $userId, string $newEmail): void
    {
        $user = $this->repository->find($userId);
        
        if (!$user) {
            throw new UserNotFoundException($userId);
        }

        // 1. Меняем состояние сущности
        $user->changeEmail($newEmail);

        // 2. Сохраняем изменения через репозиторий/EM
        // Мы явно контролируем момент записи в БД
        $this->entityManager->flush();
    }
}
```

#### Что мы получили в итоге:

1.  **Тестируемость:** Теперь я могу написать Unit-тест на `User` за миллисекунды, создав просто `new User('test@test.com')`. Мне не нужны моки для БД.
2.  **Чистота:** `User` — это чистый PHP-объект. Он не зависит от Symfony или Doctrine. Его можно перенести в другой проект или даже в другой язык, и логика останется прежней.
3.  **Предсказуемость:** Я точно знаю, когда данные попадут в базу — только тогда, когда вызван `flush()` в сервисном слое. Никаких скрытых запросов внутри методов сущности.
4.  **Соблюдение границ:** Мы разделили **что** происходит (бизнес-логика в `User`) и **как** это сохраняется (инфраструктура в `Repository/EntityManager`).

**Интервьюер:** Тебе нужно решить техническую проблему на незнакомых тебе технологии или стеке. Опиши последовательность своих действий от первого взгляда на задачу до уверенного ответа о сроках решения. Когда, по-твоему, нужно просить помощи у команды, а когда разбираться самому?

Это один из самых важных вопросов, касающихся не навыков кодинга, а **инженерной зрелости**. Незнакомый стек — это не препятствие, а неизбежная часть работы Senior-разработчика. Моя задача — минимизировать риск того, что я «уйду в кроличью нору» на три дня, не принеся пользы.

Я разделяю свой процесс на четыре четких этапа.

---

### 1. Этап исследования (Investigation & Spike)
Когда задача прилетает, я не начинаю писать основной код. Я создаю **Spike** — исследовательскую задачу.

*   **Понимание контекста:** Я читаю документацию не «от корки до корки», а целенаправленно. Что это за технология? Каков её жизненный цикл? Как она взаимодействует с текущей архитектурой?
*   **Создание песочницы (Sandbox):** Я создаю минимальный, изолированный проект (PoC — Proof of Concept) на этом стеке. Если мне нужно разобраться с новым типом БД, я не лезу в основной проект, а поднимаю чистый Docker-контейнер.
*   **Метод проб и ошибок:** В песочнице я пытаюсь воспроизвести проблему или реализовать прототип функции. Я смотрю на ошибки, читаю логи и Stack Overflow/GitHub Issues. Моя цель — понять «ментальную модель» этой технологии.

### 2. Этап оценки (Estimation)
Только после того, как я «потрогал» технологию руками в песочнице, я могу давать сроки.

*   **Декомпозиция:** Я разбиваю задачу на мелкие технические шаги.
*   **Запас на неопределенность (Buffer):** Я всегда закладываю коэффициент сложности. Если я думаю, что задача займет 4 часа, я скажу команде «около одного рабочего дня». Это время на непредвиденные нюансы новой технологии.
*   **Формулировка ответа:** Мой ответ звучит не как «я сделаю это к среде», а как «после исследования я оцениваю задачу в X часов, с учетом рисков изучения [название технологии]».

### 3. Когда разбираться самому, а когда просить помощи?

Это вопрос баланса между **автономностью** и **эффективностью команды**.

#### Разбираться самому, если:
*   **Проблема в синтаксисе или документации:** Это базовый уровень, который я обязан преодолеть сам.
*   **Это «проблема поиска»:** Я просто не знаю, где лежит нужный метод или как настроить конфиг.
*   **У меня есть гипотеза, но нет подтверждения:** Я пробую разные подходы в песочнице, и это занимает разумное время (обычно до 1-2 часов на конкретный подвопрос).

#### Просить помощи (Escalation), если:
*   **Я уперся в «стену» (Time-box):** У меня есть правило: если я бьюсь над одной и той же ошибкой более 2 часов без прогресса — я иду к коллегам. Это не признак слабости, это экономия денег компании.
*   **Проблема в архитектурном противоречии:** Если технология работает так, что она конфликтует с нашими принятыми стандартами (например, как в примере с `EntityManager` внутри сущности), я не пытаюсь «пробить стену», а иду обсуждать это с командой.
*   **Проблема в инфраструктуре/окружении:** Если проблема не в коде, а в том, что «у меня не поднимается Docker» или «не работает VPN» — я не трачу часы на дебаг инфраструктуры, а иду к DevOps/админам.

### Резюме моего подхода:

Мой алгоритм: **Исследую в изоляции $\rightarrow$ Проверяю гипотезы в песочнице $\rightarrow$ Если застрял на фиксированное время — иду за советом $\rightarrow$ Выдаю оценку с учетом рисков.**

Я считаю, что **лучше задать «глупый» вопрос через 2 часа, чем просидеть 2 дня, создавая неверное решение, которое потом придется переписывать всей команде.**

## Q30 · Процесс и рассуждение

**Интервьюер:** Ты пообещал сделать задачу к завтрашнему дню, но по ходу работы понял, что это два дня работы. Что делаешь?

**Кандидат:**

Это ситуация, которая проверяет не твои навыки программирования, а твою **надежность (reliability)** и **профессиональную честность**. 

Самая большая ошибка здесь — продолжать молчать, надеясь «героически» доделать задачу ночью. Это путь к выгоранию, багам и, в конечном итоге, к потере доверия со стороны команды и бизнеса.

Мой алгоритм действий в такой ситуации:

### 1. Немедленная коммуникация (Fail Fast)
Как только я осознал, что не укладываюсь в срок, я **немедленно** сообщаю об этом. Я не жду завтрашнего утра или дедлайна. Чем раньше я скажу, тем больше у команды будет времени перестроить свои планы.

### 2. Структура сообщения (Принцип "Проблема — Причина — Решение")
Я не прихожу с фразой «Я не успеваю». Это бесполезная информация. Я прихожу с полной картиной. Мой отчет (в Slack, Jira или на Daily) будет выглядеть так:

1.  **Статус:** «Я не смогу завершить задачу [Название] к завтрашнему дню, как планировал».
2.  **Причина (Root Cause):** Я объясняю, *почему* это произошло. Важно разделять «я плохо оценил» и «возникли непредвиденные технические сложности».
    *   *Плохо:* «Я не успел».
    *   *Хорошо:* «В процессе реализации выяснилось, что API стороннего сервиса работает не так, как в документации, и мне нужно реализовать дополнительный слой трансформации данных».
3.  **Новый прогноз (New Estimate):** Я даю новую, более реалистичную дату. Причем я добавляю небольшой буфер, чтобы не пришлось просить переноса во второй раз.
4.  **Предложение по компромиссу (Mitigation):** Я предлагаю варианты, как минимизировать ущерб для проекта.

### 3. Примеры подходов

В зависимости от ситуации, я предложу один из трех вариантов:

*   **Вариант А: Смена приоритетов (Scope Reduction).**
    «Я могу успеть сделать основную функцию (MVP) к завтрашнему дню, но дополнительные фичи (например, логирование или расширенные тесты) я доделаю послезавтра. Как нам лучше поступить?»
*   **Вариант Б: Декомпозиция (Incremental Delivery).**
    «Я не успею выкатить всю задачу, но завтра я смогу отдать готовую и протестированную часть [Функционал X], чтобы вы могли начать интеграцию».
*   **Вариант В: Помощь (Resource Allocation).**
    «Задача оказалась сложнее из-за [Причина]. Если это критично сделать завтра, мне может понадобиться помощь [Имя коллеги] для парного программирования или ревью».

---

### Почему я делаю именно так?

1.  **Управление ожиданиями (Expectation Management):** Бизнес может простить задержку, если он узнал о ней заранее. Бизнес никогда не прощает «сюрпризов» в день дедлайна.
2.  **Прозрачность (Transparency):** Я показываю, что я контролирую ситуацию, понимаю причины задержки и предлагаю варианты решения, а не просто констатирую факт поражения.
3.  **Профессиональная репутация:** Человек, который умеет честно говорить о рисках и предлагать пути их минимизации, ценится гораздо выше, чем «герой», который постоянно срывает сроки.

**Мой итог:** Моя цель — не «выполнить задачу любой ценой», а **«обеспечить предсказуемость процесса разработки»**.

## Q31 · Процесс и рассуждение

**Интервьюер:** Как ты решаешь, когда код «достаточно хорош» и его пора отдавать, а когда стоит продолжать улучшать качество? Опиши, как ты соблюдаешь баланс между качеством и скоростью в реальном проекте.

**Кандидат:**

Это один из самых сложных вопросов, потому Because в разработке ПО нет понятия «идеальный код». Есть только **«приемлемый компромисс»**. Если ты будешь стремиться к идеалу, ты никогда не выйдешь в релиз. Если будешь гнаться только за скоростью — ты создашь технический долг, который похоронит проект через полгода.

Мой подход к балансу между качеством и скоростью строится на трех принципах: **определение «линии смерти»**, **управление техническим долгом** и **анализ стоимости изменений**.

---

### 1. Определение «достаточно хорошего» кода (Definition of Done)

Для меня код считается «достаточно хорошим», когда он соответствует трем критериям:

1.  **Он решает бизнес-задачу:** Он выполняет то, что от него ожидалось, и покрывает все описанные в задаче сценарии (Acceptance Criteria).
2.  **Он безопасен и предсказуем:** Он проходит все автоматические тесты, не имеет уязвимостей (SQLi, XSS) и не ломает существующий функционал (регрессия).
3.  **Он поддерживаем (Maintainable):** Он не является «спагетти-кодом». Его можно прочитать, понять и изменить без страха, что всё упадет. Если код требует написания инструкции на 10 страниц, чтобы в нем разобраться — он **не** достаточно хорош.

**Когда я останавливаюсь:** Если я вижу, что дальнейшие улучшения (например, внедрение еще более сложного паттерна проектирования) не принесут прямой пользы для текущей задачи, а лишь увеличат время разработки — я останавливаюсь.

---

###  Boy, когда стоит продолжать улучшать?

Я продолжаю рефакторинг в двух случаях:

1.  **Нарушение инвариантов (Технический долг, который «жжет»):** Если текущее решение создает риск критического сбоя, нарушает безопасность или делает невозможным выполнение следующей запланированной задачи.
2.  **Правило бойскаута (Boy Scout Rule):** Если я нахожу мелкий беспорядок (плохое имя переменной, дублирование кода) в том месте, где я уже работаю. Это маленькие вложения, которые не тормозят задачу, но держат кодовую базу в чистоте.

---

### 2. Как я соблюдаю баланс в реальном проекте

В реальной работе я использую три инструмента для управления этим балансом:

#### А. Управление техническим долгом (Debt Management)
Я не считаю техдолг злом. Техдолг — это **финансовый инструмент**. Иногда мы осознанно берем «кредит» (пишем быстрый, менее идеальный код), чтобы быстрее захватить рынок.
*   **Моя практика:** Если я принимаю решение сделать «быстро и грязно» (например, из-за горящего дедлайна), я **обязательно** создаю задачу в бэклоге на рефакторинг этого места. Мы не должны «забывать» про долги, мы должны их «планировать».

#### Б. Оценка стоимости изменений (Cost of Change)
Перед тем как начать глубокий рефакторинг, я задаю себе вопрос: **«Какова цена этого улучшения?»**
*   Если я потрачу 3 дня на рефакторинг модуля, который меняется раз в год — это **плохая инвестиция**.
*   Если я потрачу 3 дня на рефакторинг ядра системы, которое мы будем расширять каждый день — это **инвестиция в скорость**.

#### В. Процесс CI/CD и автоматизация
Баланс между качеством и скоростью поддерживается автоматикой. 
*   Если у нас есть строгие линтеры, статический анализ (PHPStan) и высокая культура Unit-тестирования, я могу позволить себе двигаться быстрее, зная, что автоматика поймает грубые ошибки. Это снижает «цену» высокой скорости.

---

### Итоговая формула моего подхода:

**Качество = (Корректность + Безопасность + Тестируемость) / Скорость разработки.**

Я не стремлюсь к бесконечному росту качества. Я стремлюю к **оптимальной скорости поставки ценности при соблюдении минимально допустимого порога надежности.** 

Если бизнес просит «быстрее» — я говорю, какой риск мы принимаем. Если бизнес просит «лучше» — я объясняю, сколько это будет стоить в деньгах и времени. Моя роль — быть **честным навигатором** между амбициями бизнеса и реальностью кода.
