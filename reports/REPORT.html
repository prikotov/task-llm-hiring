2Методика

Скриптованное интервью, одинаковые условия для всех, судейство с проверкой фактов.

Интервью

Собеседование сделано в виде скриптованного интервью из 35 открытых вопросов: PHP 8, типы и ловушки (3 вопроса), ООП (1), Symfony (3), Doctrine (3), PostgreSQL (2), DDD и чистая архитектура (4), тестирование и конкурентность (2), процесс работы, включая git (8), плюс разминка с самооценкой знаний (1), три провокации с ложной предпосылкой, два мини-код-ревью и финал собеса (3). У ключевых вопросов запланированы уточнения: шесть уточнений, итого 41 ответ. Вопросы зафиксированы в вопроснике backend-роли и одинаковы для всех кандидатов и прогонов.

Ведёт интервью только скрипт-раннер (runner.py): один собес это один чат, раннер читает вопросник и шлёт вопросы по одному в API модели, каждый ответ дописывается в историю чата. Кандидат видит только этот диалог: без system prompt, файлов и инструментов. Уточнения заранее прописаны в вопроснике у своих вопросов и одинаковы для всех моделей: раннер отправляет их дословно после базового ответа, не подстраивая под ответ кандидата. Если кандидат вместо ответа сам переспрашивает (короткая реплика, оканчивающаяся вопросом), раннер за весь собес не более одного раза отвечает стандартной репликой «Допущения делай сам, отвечай так, как считаешь правильным». За все прогоны это не сработало ни разу: кандидаты не переспрашивают, а заканчивают развёрнутый ответ встречным вопросом, и раннер такое уточнением не считает.

Каждый прогон сохраняется в два файла: человекочитаемый транскрипт и сырая сессия session.json с полным массивом сообщений, ходом мышления и таймингами (пример транскрипта, пример сессии); судейство идёт по протоколам постфактум. Отдельного выбора роли нет: роль это имя папки вопросника. Вопросник interview/roles/backend/questions.json задаёт роль backend, прогоны складываются в папку модели <модель>/backend/run-NN, существующие прогоны не перезаписываются.

Транспорт и изоляция прогонов: локальные модели опрашиваются с сервера ollama с выгрузкой из памяти до и после каждого прогона, чтобы кэш одного собеса не грел следующий; параметры генерации дефолтные, seed не фиксируется. Облачные SOTA ходят через OpenRouter (runner_openrouter.py) с reasoning effort low (сопоставимо с выключенным мышлением локальных), DeepSeek, GigaChat и YandexGPT через родные API провайдеров (runner_ru_cloud.py). Для каждой модели делается несколько независимых прогонов (до пяти на серию).

Оценка

Ответы оцениваются по протоколам постфактум, каждый ответ отдельно. У каждого вопроса есть чек-лист якорей: 🟢 зелёный свет (2–4 признака сильного ответа) и 🚩 красный флаг (1–2 признака слабого) (чек-листы всех вопросов); полные карточки эталона с зелёным светом, красными флагами, образцом ответа и шкалой 0–4 написаны вручную для двух вопросов как калибровка судейства (пример карточки). Сама оценка идёт в два яруса, от дешёвого судьи к дорогому.

Ярус 1: clef, decision-модельлокально, дёшево и быстро: балл, вероятность галлюцинаций, самоотчёт о зоне незнания (need_review).

Самооценка против итоговых баллов

В разминке (вопрос Q00) модель сама оценивает свои знания по восьми разделам шкалой 0–10; итоговые баллы конвейера приведены к той же 10-балльной шкале: ■ пунктир это самооценка, ■ сплошная, итоговый балл: судьи где проверял, иначе clef (тёмно-зелёные точки ● отмечают оси, взятые у судьи: полный прогон каждой серии). Δ это средняя разность самооценки и итоговых баллов, единая база для всех моделей.

Эффект Даннинга-Крюгера воспроизводится почти идеально: корреляция силы модели (clef) с перекосом самооценки, Пирсон r = −0.90 и Спирмен ρ = −0.90 (n = 17). Сильные модели себя недооценивают (Opus −1.5, Haiku −1.6, Sol −1.2), слабые переоценивают (YandexGPT Pro 5 +2.7 при худшем знании стека, gemma4-e2b +2.2), середина откалибрована в ноль (Ultra, qwen3.8, muse, 9B). Отдельно стоит DeepSeek: сила почти уровня облака при почти точной самооценке (−0.4). Подробнее об эффекте у больших языковых моделей читайте в блоге автора.

Низкий балл по разделу не приговор, а сигнал для постановки задачи. Радар показывает, где модели нужна опора: в слабых разделах давать больше контекста (документацию, примеры, конвенции проекта), усиливать гвард-рейлы проверками на детерминированных инструментах (Psalm, PHPStan, PHPCS, тесты в CI) и закладывать более плотное ревью другими агентами и человеком. Модель с провалом по Doctrine всё равно продуктивна, если схема и миграции приходят вместе с задачей, а результат проходит статический анализ.   2. Семь вероятностных признаков (код, структура, глубина, имена API, точные числа, сомнение, противоречия): каждый слабее одного явного вопроса об эскалации.

  5. Чек-листы хороших/плохих пунктов: интегральный балл слаб, но «плохие» детекторы ловят семантические ошибки, невидимые clef. Правило формулировок: «предлагает X как решение», а не «упоминает X».

Токены и стоимость это фактические данные API. Различаем кэш сессии (префикс одного собеса кэшируется между его вопросами, транспортная оптимизация, модель видит тот же контекст) и кэш прогонов (один собес греет следующий; он запрещён: модель выгружается после каждого прогона, каждый собес стартует с холодным контекстом).
Кэш: доля входных токенов сессии, покрытых кэшем: процент и абсолютное число токенов (чт это чтение из кэша, зп запись в кэш); полное число входных токенов видно в соседней колонке. Высокие проценты (Haiku run-03, 96% чтения) это норма для одного чата с явными cache_control-метками: каждый следующий запрос повторяет весь предыдущий контекст, из кэша берётся повторная часть, а новые вопрос-ответ пишутся в кэш один раз (зп). Живая разбивка пишется с 9 октября; кэш-чтение более ранних облачных прогонов восстановлено из журнала OpenRouter (записи в журнале нет, поэтому процент по чтению чуть занижен): у Sol точное значение, у Luna/Haiku/Opus доля дневного агрегата пропорционально токенам сессии, помечено ~. Новые облачные прогоны стартуют с холодным кэшем: раннер выдерживает паузу больше TTL кэша провайдера (у провайдеров нет session id или выключателя кэша; сам кэш бит-идентичен пересчёту и на содержание ответов не влияет). У локальных ollama кэш-токены отдельно не отчитываются: тёплая сессия видна по скорости (muse-glimmer: 9.2 мин с холодным пересчётом префикса против 4.9 мин с кэшем сессии). Стоимость локальных сессий считается по методике из §8 «Экономика» (₽35.85/ч: электричество + амортизация минус остаточная стоимость), отнесено ко времени чистой генерации; входные токены уточнений в ранних прогонах не сохранялись (учтены основные вопросы).
