## Версионный тип

Да, «версии PHP» стоит выделить в отдельный тип вне основной карты. Причина методологическая: 96 клеток карты — про timeless-факты языка (поведение `==`, семантика `use`), которые не меняются годами, а версионные утверждения **привязаны к дате**: «актуальная версия» и «будущая фича» распадаются со временем. Если смешать их с картой, дрейф одного столбца будет портить картину устойчивости всей сетки. Отдельный тип = отдельная таблица с обязательной меткой даты прогона; для cutoff-зондов (б) верный ответ фиксируется как «состояние RFC на дату X» и перепроверяется перед каждой серией.

Измерять лучше **смесью форматов**. Да/нет для версий тесно и чувствительно к формулировке: «функция X появилась в 8.1» и «функция X есть в 8.0» — один факт, но разные ответы, а «всегда да»-базлайн плохо различим от угадывания. Рекомендую: (1) основной формат — **множественный выбор версии**: «В какой версии появились property hooks? 8.2 / 8.3 / 8.4 / 8.5» — даёт градацию знания, а не бит, и устойчив к формулировке; (2) для cutoff (б) оставить да/нет, но строить пары «правда + правдоподобная ложь» (принятый RFC против несуществующего/отклонённого) — ложные утверждения зондируют галлюцинации о будущем сильнее, чем истинные; (3) для каждого факта — 2 минимальные пары-перефразы («появилась в 8.1» ↔ «в 8.0 её ещё не было»), расхождение ответов = мера неустойчивости к формулировке.

## Примеры утверждений

1. С PHP 8.4 свойство класса может иметь хуки прямо в теле: `public string $name { get => strtoupper($this->raw); }` — **да** — property hooks (8.4, ноябрь 2024); зондирует знания новее cutoff осени 2024 (модели старее ответят «нет»).
2. С PHP 8.4 видимость свойства задаётся раздельно для чтения и записи: `public private(set) float $price;` — **да** — asymmetric visibility (8.4); зондирует cutoff конца 2024.
3. С PHP 8.4 функции `array_find`, `array_find_key`, `array_any`, `array_all` ищут в массиве по предикату — **да** — RFC array_* функции (8.4); зондирует знание стандартной библиотеки 8.4, а не только синтаксиса.
4. С PHP 8.5 атрибут `#[\NoDiscard]` помечает функции, чей результат нельзя игнорировать: игнорирование даёт предупреждение — **да** — 8.5 (конец 2025); зондирует cutoff новее релиза 8.4.
5. Оператор конвейера `|>` принят RFC и вошёл в PHP 8.5 — **да** — pipe operator принят весной 2025 для 8.5; зондирует знания весны–осени 2025 («свежее» 8.4).
6. Принят RFC о deprecation неявно-nullable параметров (`function f(int $x = null)`): в PHP 8.4 это уже deprecated — **да** — RFC «Deprecate implicitly nullable types» (8.4); зондирует знание таймлайна deprecation, самой частой зоны отставания.
7. Принят RFC, по которому в PHP 8.6 JIT будет включён по умолчанию — **нет** — такого принятого RFC нет (по состоянию на дату прогона); правдоподобная ложь зондирует выдумывание будущего.
8. Принят RFC о встраивании многопоточности в ядро PHP (ZTS по умолчанию в 8.6) — **нет** — ничего подобного не принималось; декой на галлюцинации «амбициозного будущего».
9. Функции `str_contains`, `str_starts_with`, `str_ends_with` появились в PHP 8.0 — **да** — граница 7.4/8.0; зондирует, насколько модель «застряла» в 7.x (частая ошибка — приписывание 7.4).
10. Типизированные свойства (`public int $x;`) появились в PHP 7.4 — **да** — 7.4; зондирует точность версионной шкалы в эпоху 7.x.
11. Ветка PHP 6 так и не вышла в стабильном релизе: после 5.6 вышел сразу PHP 7.0 — **да** — глубина истории (эпоха 5.x); зондирует, покрывают ли веса доковую историю PHP или только 8.x-хайп.

## Что убрать из текущих

- **T02-L7** (0.1 + 0.2 === 0.3) — общеизвестный факт IEEE 754, не PHP-специфика; почти любая модель ответит верно, информативность ≈ 0.
- **T12-L2** (md5 небезопасен) — тривиально, обще-security-гигиена, не PHP; дегенеративно (все ответят «нет»).
- **T12-L7** (prepared statements защищают от SQL-инъекций) — дублирует T12-L2 по смыслу и тоже общеизвестно; от знаний PHP не зависит.
- **T12-L3** (сессии по умолчанию в файлах) — малоинформативный дефолт конфигурации, «зазубрить» легко, зондирует память, а не понимание.
- **T12-L5** (php_sapi_name() → cli) — мелочь уровня FAQ, слабый градиент.
- **T02-L2** (=== с приведением наоборот) — дубль T02-L1 в виде перевёртыша: меряет внимательность к формулировке, а не знание.
- **T08-L3** (DivisionByZeroError — Error) — дублирует T08-L2 (та же иерархия Error/Exception); достаточно одной клетки.
- **T03-L6** (ucfirst изменяет строку на месте) — тривиально: неизменяемость строк — аксиома; оставить только если нужна «всегда нет»-контрольная.

(Тривиальные L1/L2 вроде T06-L2, T10-L2 не трога — ими держится базовая линия градиента; ужимать стоит средние уровни 3–6, где ожидается информативность.)

## Ещё идеи

1. **Множественный выбор версии вместо бита**: «В какой версии появилось X?» с 4–6 опциями (5.x / 7.x / 8.0–8.3 / 8.4 / 8.5 / нет такого) — непрерывная шкала знания версий и устойчивость к формулировке; ошибки «соседняя версия» и «совсем мимо» различимы.
2. **Минимальные пары и перефразы**: для каждого факта 2–3 формулировки (прямая, отрицательная, смещённая версия) — даёт метрику устойчивости к формулировке, прямой аналог «береговой линии» Карпаты.
3. **Непрерывная вероятность вместо дискретного ответа**: читать logprob токенов «да»/«нет» (как в первоопыте Henry) — тепловая карта вероятностей информативнее карты битов; для decision-моделей — тот же вероятностный протокол.
4. **Экспериментальный ground truth через php 8.5 на машине теста**: каждое версионное и поведенческое утверждение валидировать скриптом («фича есть в 8.5? поведение воспроизводится?»), note в questions.json заменить ссылкой на проверочный скрипт — убирает зависимость от непроверенных авторских обоснований.
5. **Формат «что выведет код» с авто-грейдером + опция «не знаю»**: короткий ответ сверяется с php-интерпретатором; третий ответ «не знаю» отделяет угадывание от знания (для карты можно оставить бинарный протокол, а abstain-серии гонять отдельно).
