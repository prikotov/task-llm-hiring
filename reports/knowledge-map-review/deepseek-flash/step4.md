## Версионный тип

Да, согласен — и лучше не просто «добавить блок», а вынести версионные вопросы в отдельный тип с собственным снимком (`as_of`) и собственной метрикой. Основная карта меряет семантику языка в текущем 8.x; версионные факты стареют скачками (8.4 → 8.5 → 8.6), коррелируют внутри одного релиза (десять вопросов про 8.4 — это почти один вопрос) и начинают мерить дату обучения, а не знание PHP. Если оставить их в 96, cutoff модели будет доминировать в карте и портить сравнение тем/уровней; кроме того, в текущем наборе уже есть версионно-якорные клетки вроде `T08-L7`, которым место именно там.

Для устойчивости к формулировке да/нет не должен быть основным форматом. Надёжнее: «какая минимальная версия» с вариантами 7.0/7.4/8.0/8.1/8.4/8.5/«нет в PHP»; сопоставление «фича → версия»; multi-select «выбери все фичи, появившиеся в 8.4/8.5»; обратная задача «что из этого ещё не принято». Полезно задавать один факт в двух направлениях (фича→версия и версия→набор фич) и в парафразах: расхождение — это и есть неустойчивость. Обязательно добавлять «не знаю»/вероятность и считать score с поправкой на угадывание; отделять «существует ли фича» от «в какой версии появилась», иначе «нет» смешивает незнание фичи с ошибкой версии. Версия — это не дата обучения: модель может знать фичу по RFC до релиза, поэтому вопрос «в какой версии» точнее, чем «знаешь ли фичу». Версии — только minor (8.4, 8.5), «появилась» = первый стабильный релиз; для будущих/trunk-пунктов хранить дату снимка и перепроверять при каждом релизе.

## Примеры утверждений

1. «В PHP 8.4 появились property hooks — get/set-хуки прямо в объявлении свойства.» — ДА — cutoff 8.4 (11.2024); модель до 8.4 обычно отвечает НЕТ или путает с 8.3.
2. «В PHP 8.4 добавлена асимметричная видимость: `public private(set) string $name`.» — ДА — cutoff 8.4; проверяет не только фичу, но и синтаксис.
3. «В PHP 8.5 появился оператор конвейера `|>`.» — ДА — cutoff 8.5 (11.2025); ключевой маркер «знает ли 8.5».
4. «В PHP 8.5 разрешено клонировать объект с изменением свойств: `clone($obj, ['x' => 1])`.» — ДА — cutoff 8.5; проверяет RFC clone with.
5. «В PHP 8.5 добавлены функции `array_first()` и `array_last()`.» — ДА — recent cutoff 8.5; модели до 8.5 обычно говорят, что таких функций нет.
6. «По состоянию на PHP 8.5 generics (параметризованные типы) в PHP отсутствуют.» — ДА — зонд «будущее/обсуждаемое» и отрицательный контроль: не путает PHP с C#/Java.
7. «В PHP 8.6 (trunk) уже принят RFC на generics.» — НЕТ — зонд будущего/trunk; ответ ДА будет сигналом либо более позднего cutoff, либо галлюцинации (перепроверять при выпуске 8.6).
8. «На момент снимка 8.5.11 (сентябрь 2026) текущая стабильная ветка PHP — 8.5, а 8.6 ещё не выпущен.» — ДА — прямой cutoff/дата-зонд; обновлять `as_of` при новом релизе.
9. «Оператор `??` появился в PHP 7.0.» — ДА — старый cutoff 7.0; ловит путаницу с 5.6/7.1.
10. «Скалярные type hints для параметров (`int`, `string`) были уже в PHP 5.6.» — НЕТ — старый cutoff 5.x vs 7.0: скалярные типы появились в 7.0.
11. «Типизированные свойства класса появились в PHP 7.4.» — ДА — старый cutoff 7.4; проверяет, где модель путает 7.3/7.4/8.0.

## Что убрать из текущих

Сразу оговорка: это кандидаты на замену/переформулировку, а не призыв вычеркнуть 10 клеток — иначе поедет сетка 12×8 и баланс 48/48.

- `T01-L7` — сломанный ключ: посылка «приоритет `.` выше арифметики» ложна, но вывод «даст `сумма: 5`» в PHP 8.5 истинен (проверено: `php -r 'var_dump("сумма: " . 2 + 3);'` → `"сумма: 5"`); note про `TypeError` неверен. Не убирать, а переписать/заменить.
- `T02-L2` — определение `===` vs `==` дублирует `T02-L1` и почти не различает модели.
- `T02-L6` — хрупкая формулировка: `(int)"42abc"` = 42 без `TypeError`, а `"42abc" + 1` даёт Warning + 43; `TypeError` только для полностью нечисловой строки. Note смешивает случаи.
- `T06-L2` — «нельзя наследоваться от нескольких классов» — тривиальный миф, низкая дискриминативность.
- `T06-L4` — private родителя недоступен — тривиально и перекрывается `T06-L7`.
- `T07-L2` — трейт нельзя `new` — тривиально.
- `T08-L7` — это версионный факт (8.4), ему место в новом типе, а не в основной карте; заменить на вневерсионное утверждение.
- `T10-L3` — глобальные переменные не видны без `global` — тривиально.
- `T11-L6` — `SplStack`/`SplQueue` — справочная trivia, мало говорит о знаниях.
- `T12-L5` — `php_sapi_name()` для CLI возвращает `cli` — функция-тривиальность, почти нулевая информация.

## Ещё идеи

1. **Пары «факт — парафраз — контрфактическая версия».** Один и тот же факт в 2–3 формулировках, включая замену версии/темы/отрицания; считать не только точность, но и flip-rate/consistency. Это отделяет знание от угадывания по формулировке.
2. **Абстенция и калибровка.** Разрешить «не знаю» или просить вероятность/уверенность; считать Brier/ECE и долю абстенций на трудных клетках. Модель, которая честно говорит «не знаю», информативнее той, которая всегда угадывает.
3. **Исполняемые мини-задачи на php 8.5.** «Что выведет?», «найди баг», «допиши сигнатуру» с автопроверкой через локальный php; 10–15 детерминированных сниппетов. Это ловит разницу между узнаванием факта и применением.
4. **Матрица «факт × формат».** Один факт спрашивать в да/нет, выборе версии, multi-select, «объясни одной фразой»; сравнивать форматную устойчивость. Если факт зелёный только в да/нет — он, вероятно, выучен как паттерн.
5. **Дискриминативность и адаптивность.** По пилоту выкидывать клетки, которые проходят все или не проходит никто; оставлять вопросы с максимальным разбросом между моделями/уровнями; строить «границу знаний» по темам. Это делает тест короче и злее.
