Скелет задания

Модель получает каркас Symfony-проекта (composer.json: symfony/framework-bundle 8.0, console/yaml, doctrine-bundle 3.2, doctrine/migrations 3.3, PHP ≥ 8.4; docker-compose с PostgreSQL 17; заготовка src/ и мigrations/; в require-dev — phpunit, psalm 6 и phpcs PSR12 — инструменты самопроверки кандидата) и два документа:

  • TASK.md — само тестовое задание: требования к «биллингу LLM-токенов», по которым работает кандидат — импорт тарифов и событий, тарификация с effective dating, оф-пик-окно 16:30–00:30 UTC через полночь ×0.5, идемпотентность по (provider, provider_request_id), unrated-события, деньги на bcmath без float с одним округлением HALF_UP 6 знаков на событие, эксклюзивный --to, бонус — ретро-пересчёт после коррекции цен;
  • AGENTS.md — базовые агентские инструкции проекта тестового задания: код в src/, самопроверка приёмки, артефакты COMMIT_MESSAGE.md/PR_DESCRIPTION.md с обоснованием отступлений, русский язык. Харнес pi подхватывает его сам — как любому агенту в этом репозитории. Практики (миграции или schema:update, офлайн или онлайн, менять ли файлы каркаса) модель выбирает сама — чекер наблюдает выбор.

Как запускается

Задание передаётся одним сырым сообщением без system prompt и подсказок. Единственный промпт прогона — дословно, константа TASK_PROMPT в runner_pi.py:

# runner_pi.py, константа TASK_PROMPT — единственный промпт прогона
Прочитай TASK.md в корне репозитория и выполни задание.

Раннер разворачивает свежую копию скелета (без var/, .env — из .env.example) во временный каталог и запускает pi одной командой:

pi -p --session-dir <run>/pi-session --model <тег> --thinking <уровень> "<промпт>"

Реальный вызов из сетки (run-02 qwen3.8, после перевода thinking на честный xhigh):

python3 test-assignment/backend/billing/runner_pi.py \
  --model qwen3.8:27b-pi-100k \
  --results models/qwen3.8-27b-pi-100k/backend/test-assignment/run-02 \
  --thinking max

Облачная модель — тот же раннер с провайдером (ключи и прокси — из env, в git не хранятся; thinking — уровень шкалы провайдера):

python3 test-assignment/backend/billing/runner_pi.py \
  --model openai/gpt-6.1-sol --provider openrouter \
  --results models/openai-gpt-6.1-sol/backend/test-assignment/run-02 \
  --thinking max

cwd — копия скелета; окружение: PI_CODING_AGENT_DIR — одноразовый каталог (никаких глобальных конфигов и сессий pi), PI_OFFLINE=1; провайдер — ollama /v1 (openai-completions) внутреннего сервера, models.json раннера задаёт contextWindow=102400, maxTokens (8192; для xhigh/max — 32768, иначе thinking выжигает лимит вывода в пустой ответ) и thinkingLevelMap из фактической шкалы модели (/api/show). Бюджет — 90 минут на прогон, каждый с нуля. Фактический бюджет выхода каждой группы прогонов — в шапке её таблицы в разделе 7: 8192 у большинства облачных, 16000 у DeepSeek (родной API режет короче), 32768 у локальных на xhigh/max и Anthropic-моделей (высокие уровни размышлений съедают бюджет выхода; первый запуск Haiku с 8192 обрывался по лимиту — см. журнал прогонов). Облачные модели OpenRouter с 2026-10-22 идут нативным провайдером pi (anthropic-messages к openrouter.ai/api, нативные окно и бюджет выхода из каталога, шкала мышления с xhigh/max, ключ через OPENROUTER_API_KEY): кастомная запись openai-completions с переопределениями, которой они шли раньше, на Haiku 5.5 max дала два прогона подряд stop=length посреди размышлений — в этом протоколе reasoning и ответ делят один бюджет выхода (оба прогона вне метрик). Opus 5.5 дополнительно заведён через OrcaRouter (orcarouter.ai): тот же нативный anthropic-messages (/v1/messages, Bearer-ключ), прайс Anthropic без наценки, из домашней сети ходит без прокси; Haiku 5.5 в каталоге OrcaRouter нет (2026-10-22). Мышление через OrcaRouter — классическими бюджетами pi (low 2048 / medium 8192 / high и max 16384 reasoning-токенов на вызов): adaptive-режим, включавшийся compat-флагами из каталога pi, не имеет потолка — первый «low»-прогон в нём потратил 70.8K reasoning и $4.38 (прерван лимитом ключа, вне метрик; разбор в model.md). Полный след сессии (сообщения, tool-вызовы, размышления, токены) остаётся в <run>/pi-session/*.jsonl.

Контур 1 — чекер: детерминированный, без LLM.

Чекер поднимает чистую базу PostgreSQL в docker на свободном порту, фиксирует способ разворота схемы (миграции или schema:update), гоняет команды кандидата и сравнивает вывод с golden-эталонами. Эталоны посчитаны дважды независимо — Python Decimal и PHP-референс судьи, совпадение байт-в-байт.
11 обязательных сценариев: создание БД, разворот схемы, импорт цен, импорт событий, тарификация (RATED/UNRATED), unrated в stderr, базовый отчёт, повторный импорт дублей (идемпотентность), тарификация после дублей, отчёт после дублей, вывод ретро-пересчёта, отчёт после ретро-коррекции; плюс информационный skeleton_changes (что изменено в каркасе). Сценарии построены на граничных нюансах: valid_from включительно, границы оф-пик-окна 16:29:59/16:30:00 и 00:29:59/00:30:00, unified-тариф, cache-цены, коллизия id между провайдерами, округление HALF_UP на уровне события.

Контур 2 — метрики: детерминированные, сравнительные. 
python3 test-assignment/backend/billing/checker/metrics.py --repo <репозиторий кандидата>
Инструменты — phar-кэш, без сети в окружении судьи, в порядке приоритета: phpcs PSR12 — стиль; psalm 6 (errorLevel 1, src/) — типы и логика; phpstan level 8 — строгий статанализ; phpunit 11 — тесты кандидата: количество, ассерты, LOC тестов и покрытие строк (pcov); phpmd — нарушения порогов сложности/чистоты — наблюдение, в сравнение моделей не входит; scc — размер (files, LOC); AST-сборщик coding-standard — WMC, cyclomatic complexity, LCOM4, afferent/efferent coupling и превышения порогов (method cc > 10, method loc > 50, class loc > 300, wmc > 50). Сырые выводы инструментов — полные отчёты phpcs/psalm/phpstan/phpunit, scc.json и collector.json — сохраняются рядом, в <run>/metrics-raw/, имена файлов продублированы в metrics.json в полях raw: агрегаты проверяемы по сырью, за деталями есть куда сходить.
Метрики сравнивают модели между собой, проходного порога нет: у эталонного решения судьи phpstan ≠ 0.

Системный промпт ревьюера — дословно (SYSTEM в checker/judge_tier3.py; на вход подаются TASK.md, дифф решения и факты ярусов 1–2):
Ты — изолированный ревьюер (ярус 3) тестового задания «биллинг LLM-токенов» (PHP/Symfony/Doctrine). Тебе дают текст задания (TASK.md), дифф решения против каркаса, результат детерминированного чекера и метрики качества. Оцени решение по ДВУМ осям рубрики.

Ось A «код и архитектура» (0–4):
0 — решение нерабочее/отсутствует;
1 — частично работает; домен не смоделирован; деньги или время на float;
2 — обязательная часть в целом работает; сущности есть, границы слоёв условные; edge-case'ы (границы окон, unrated, дубли) поверхностно;
3 — корректная доменная модель (тарификация отделена от приёма и отчёта); точные деньги (bcmath, одно округление) и время; схема воспроизводима; edge-case'ы покрыты;
4 — то же + бонус; «дешёвые» решения где можно, явность где нужно; тесты добавляют уверенность.

Ось B «процесс и коммуникация» (0–4):
0 — нет артефактов, самопроверок, след хаотичен;
1 — артефакты формальные; самопроверок нет; commit/PR без обоснования;
2 — самопроверки точечные (прогнал команды, не проверил вывод); артефакты шаблонные;
3 — систематическая самопроверка (тесты, приёмка по шагам, статанализ); commit/PR объясняют решения; отступления от задания осознанны;
4 — то же + самопроверка на границах условий (граничные значения, дубли, ретро-бонус); артефакты читаются как отчёт инженера.

Правила: верь чекеру, а не внешнему виду кода; находи дефекты, которых не видно в диффе (float в деньгах, N+1, мёртвый код) — citируй строки диффа как доказательства; не наказывай за стиль, который не оговорён заданием.

Контур 4 — судья: слепое второе мнение.
Зачем. Ревьюер яруса 3 знает результат чекера и волей-неволей опирается на него — может пропустить дефект, который не виден в функциональных проверках, но виден в коде. 4.1.2. Распределение имён: общие и уникальные

По оси X — скольким прогонам встречено имя (путь каталога или имя файла-класса), по оси Y — сколько таких имён; панель каталогов включает src/ и tests/. Например, левый столбик: 61 путь каталога и 191 имя класса существуют ровно в одном прогоне. Медиана у обеих панелей — тот же один прогон: 61% путей каталогов и 64% имён классов — уникальные имена. Но есть и общие: Provider.php — во всех прогонах, UsageEvent.php — в 24, Model.php — в 20. Полные пути файлов переменчивее самих имён: 81% путей — одиночные против 64% у имён — класс переиспользуется чаще, чем его расположение. Выборка — успешные прогоны, как и во всей подсекции.

4.1.3. Размер решения: классы и строки

По оси X — размер решения (диапазон файлов или строк), по оси Y — число успешных прогонов с размером из диапазона. Это другой счёт, чем на гистограмме имён выше: там класс учтён один раз — как имя (297 разных имён), здесь — каждый файл каждого прогона (677 файлов src в сумме); классы переиспользуются между прогонами, поэтому экземпляров больше, чем имён. Типовой объём успешного решения — 26 файлов и 1431 строк (разброс 12–39 файлов, 466–2018 строк); в отличие от частоты имён, распределение одновершинное. 4.4.2. Архитектура: связность, связанность, сложность

Как читать метрики. Все шесть считаются по src/ каждого прогона AST-коллектором яруса 2; в таблице — медианы по прогонам режима, а размер, связанность и нестабильность (LOC, Ce, Ca, I) — распределением значений по классам: каждый столбик — один класс, прогоны режима объединены, поэтому число прогонов роли не играет; наведение на столбик — значение показателя.

Классов. Число классов в src/ — грубая мера масштаба и степени декомпозиции решения. Само по себе значение не бывает хорошим или плохим: 13 классов у Sol low и 38 у DeepSeek max — одинаково полноценные решения. Подозрительны только крайности: единичные «божьи классы», тянущие всю логику, или, наоборот, дробление до пустых обёрток. Успешные прогоны укладываются в 13–40; крайности показывает колонка «LOC классов» — форма распределения и максимум сразу отличают ровный ряд от одного класса-гиганта.

Ce — исходящая связанность (efferent coupling). Обозначение Ce — из связки метрик Роберта Мартина: C — coupling (связанность), нижний индекс e — efferent (исходящая). Смысл: число зависимостей класса на другие классы проекта — только внутренние App→App, вызовы vendor и глобальных функций не считаются. Показывает, насколько плотно классы переплетены: чем ниже, тем легче менять и тестировать класс изолированно. Хорошо — единицы; тревога — когда у многих классов по десять и больше связей. Пример: RepriceService у DeepSeek (max) зависит от восьми внутренних классов (Money, PricingCalculator, UsageEvent…) — это верхний сервис-оркестратор, широкий кругозор для него нормален. В таблице — распределение по всем классам решения, включая ни с кем не связанные (нулевой хвост у основания).

Ca — входящая связанность (afferent coupling). Сколько классов проекта использует данный. В таблице — распределение по всем классам решения: у большинства входящих связей нет вовсе (нулевой хвост у основания). Заметный ненулевой массив — «популярное» ядро: класс, на который смотрит много кода, менять его больно, зато он хорошо проверен употреблением.

I — нестабильность (instability). Выводится из пары: I = Ce / (Ca + Ce); 0 — максимально стабильный класс, 1 — максимально нестабильный. По всем классам «хороших» прогонов картина textbook: медиана I 0.50; полюса ровно как учит принцип стабильных зависимостей — I = 1 у console-команд (точки входа, обязаны меняться часто), I = 0 у примитивов домена (Decimal, Timestamp, enum-статусы — менять их больно, и они ни на кого не смотрят). В таблице — распределение по классам с зависимостями.

Циклические зависимости (circular dependency). Класс A использует B, а B — A, напрямую или через цепочку. Цикл означает, что классы нельзя вынуть и тестировать по одному, а изменения в одном тянут за собой другой; в слоистой архитектуре это почти всегда протечка абстракции. Хорошо — ноль: это принцип ациклических зависимостей (Acyclic Dependencies Principle) Мартина. Каждый найденный цикл — кандидат на разрыв (вынести интерфейс или событие). Из этих 25 прогонов у 13 циклов нет вовсе; у остальных — одна-две пары, реже четыре-пять. Пример — Sol max: цикл PriceAdjustment ↔ UsageEvent.

LCOM4>1 (связность класса). LCOM4 разбивает методы класса на группы: методы попадают в одну группу, если используют общее свойство; число групп и есть значение. LCOM4 = 1 — класс про одно дело; LCOM4 больше 1 — внутри класса несколько независимых обязанностей, кандидат на разделение. В колонке — число таких классов. Важная оговорка: у сущностей и console-команд метрика даёт ложные срабатывания — UsageEvent у DeepSeek (max) хранит четыре вида токенов и выдаёт по геттеру на каждый, получая LCOM4 10, хотя это нормальная богатая сущность, а не два класса в одном.

Max CC метода (цикломатическая сложность). Число независимых путей исполнения метода — единица плюс количество ветвлений. Показывает, сколько тест-кейсов нужно на покрытие ветвей и насколько метод труден для чтения и правки. Хорошо — до 10; выше 15–20 метод опасно менять без полного прогона тестов. Рекорд — readAndValidate у orca (run-06): 32 пути.

>50 стр. методов. Число методов длиннее 50 строк — грубый датчик «метод делает всё сразу»: такие методы тяжело ревьюить, переиспользовать и покрывать тестами. Хорошо — ноль-единицы на решение. Рекорд — метод apply у qwen3.8 (run-02): 136 строк.

Про «нормальные значения». У Мартина Фаулера — автора знаменитого каталога запахов кода, на котором стоит сам жанр этого подраздела, — нормальных значений нет, и это принципиальная позиция: запах — качественный сигнал без точных порогов, он сознательно не даёт чисел вида «столько — нормально»: решение за ревьюером, который видит контекст. «Нормальные значения» для наших метрик живут у других авторов. Связанность и нестабильность (Ce, Ca, I) — у Роберта Мартина, и это не таблица норм, а принципы: стабильных зависимостей и стабильных абстракций — доменное ядро должно быть стабильным и абстрактным, точки входа — нестабильными; конкретно-стабильное — «зона боли», абстрактно-нестабильное — «зона бесполезности». Цикломатика — Томас Мак-Кейб (1976) с классическим ориентиром «до 10». Граница LCOM4 = 1 — Хитц и Монтазери. Длину методов никто не канонизировал — это фольклор и эвристики Clean Code дяди Боба. Поэтому и наш ориентир здесь — не порог, а форма распределений: смотреть на запах, как учит Фаулер. И напрашивается практический шаг: отдать эти метрики агенту-ревьюеру кода — он покажет места в коде, где стоит уделить внимание: не случайное блуждание по решению, а точное определение пахнущих мест ещё до того, как код увидит человек. Это и качество ревью архитектуры поднимает, и, кажется, экономит токены.

4.5.3. Поиски готового решения на диске

Отдельный вопрос контроля: не пыталась ли модель найти решение вне своего каталога — в каталогах чужих прогонов, глобальным поиском по диску, на хост-машине. У каждой сессии свой cwd (заголовок её jsonl), команды разбираются без тел heredoc'ов; проверки окружения (which, ls /usr/lib/…) поиском не считаются.

  • Чужой каталог прогона: 0 обращений.
