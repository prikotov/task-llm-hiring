Общий вердикт: **эталоны и грейдеры существующих клеток не трогать по существу, но план mimo с массовыми перевесами и переписыванием всего подряд принимать не стоит**. Нужны точечные исправления постановок и отдельная калибровочная ревизия.

## 1. Перевесы L9 ↔ L10 — только частично

**Правильный принцип: сначала семантический уровень, затем эмпирическая калибровка.**

- **L9** — то, что опытный разработчик должен знать стабильно.
- **L10** — тонкое взаимодействие правил, версионная особенность или редко используемая семантика, где ошибка опытного разработчика правдоподобна.
- Процент у моделей — сигнал о неправильной калибровке, утечке или контаминации, но **не самостоятельное определение уровня**.
- 100% у 4.6B означает отсутствие дискриминации в текущем наборе, но не доказывает, что клетка семантически проста: возможны узнавание и угадывание по видимым литералам.

### Согласен с переводом в L9

| Клетки | Почему |
|---|---|
| **T05-L10** | Захват `$this` first-class callable — стандартная семантика PHP 8.1. |
| **T08-L10** | Подмена исключения из `finally` — сложный, но общий control flow, а не версионная экзотика. |
| **T14-L10** | `persist → remove → flush` — базовая работа Unit of Work. |
| **T15-L10** | Running frame при `ORDER BY` — классическая оконная семантика, которую опытный SQL-разработчик должен знать. |
| **T23-L10** | Резолв параметров при компиляции контейнера — обычная семантика Symfony DI. |
| **T26-L10** | Инвариант явно написан в коротком коде; это скорее внимательное чтение, чем «береговая линия». |

### Оставить в L10, несмотря на высокие проценты

- **T06-L10** — property hooks и запись в backing store: новая версионная семантика PHP 8.4, типичный источник ошибки даже у опытного разработчика.
- **T17-L10** — `DEFERRABLE INITIALLY DEFERRED`: специфичное взаимодействие ограничений и транзакций PostgreSQL.
- **T18-L10** — поведение не-static provider именно в PHPUnit 10 версионно-зависимо; это не общий обязательный минимум L9. Но постановку стоит усилить против утечки.
- **T19-L10** — пограничная клетка. Я бы оставил в L10: проверяется не отдельный флаг `-G`, а его взаимодействие с `-d`. Перевод в L9 допустим, но не обязателен.

### T12-L9 и T21-L9

- **T12-L9 не просто переводить в L10, а заменять**. Ручной base64 — преимущественно арифметика и узнавание головоломки, а не глубокая семантика PHP или безопасности. Перенос сохранит дефект конструкта.
- **T21-L9 → L10: да**, одновременно убрав утечку. Пустота/falsy в `default` регулярно понимается неправильно; после исправления постановки это разумная клетка L10.

Важное следствие: **перевесы сами по себе не приблизят оба уровня к целям**. Удаление двух самых трудных клеток из L9 и добавление нескольких 100%-ных клеток из L10 сделает L9 ещё легче. Для L9 нужны новые варианты средней трудности, ориентиром могут служить T03-L9 и T11-L9.

Также надо решить, обязательна ли структура «одна L9 и одна L10 на каждую тему». Если да, перенос одиночной клетки недопустим без замены парной: иначе матрица 28 тем × 2 уровня разрушается.

## 2. Утечки яруса A — пять переписать, VC-L9 оставить

### VC-L9 — оставить

Аргумент из вопроса верен: клетка проверяет прежде всего **допустимость `new C()->hi()`**, а не трудность получения строки `hi`. Ответы `parse error` и `hi` различают знание синтаксиса PHP 8.4. Это простая anchor-клетка L9, но не сломанная.

### T13-L9 — дёшево усилить

Сейчас можно просто повторить `abc`, не зная преобразования server parameters в headers.

```php
$r = Request::create('/demo', 'GET', [], [], [], ['HTTP_X_TOKEN' => 'abc']);
echo $r->headers->get('X-Token') === 'abc' ? 'mapped' : 'missing';
```

Эталон: **`mapped`**.

Остаётся бинарный выбор, но уже требуется именно проверка семантики маппинга.

### T18-L10 — проверять не только количество, но и выполнение тестов

Изменить провайдер:

```php
public function prov(): array
{
    return [[1], [-1]];
}
```

Оставить:

```php
#[DataProvider('prov')]
public function test_x(int $x): void
{
    $this->assertTrue($x > 0);
}
```

Вопрос:

> Ответь двумя числами через запятую: сколько тестов будет выполнено и сколько завершится failure.

Эталон: **`2,1`**, accept также `2, 1`. PHPUnit deprecation не считается failure теста.

Теперь ответ зависит от того, что провайдер всё же выполняется, а не только от подсчёта элементов массива глазами.

### T21 — вычисляемый результат вместо литерала

```twig
{{ 0|default(2) * 3 }}
```

Эталон: **`6`**.

- Правильное понимание `default`: `0` заменяется на `2`, результат `6`.
- Ошибочное «default работает только на undefined»: результат `0`.

Это чистая замена без дополнительной версионной двусмысленности.

### T23-L10 — транзитивный резолв вместо одной очевидной подстановки

```php
$c = new ContainerBuilder();
$c->setParameter('name', 'Bob');
$c->setParameter('greeting', 'hi %name%');
$c->setParameter('message', '%greeting%!');
$c->compile();
echo $c->getParameter('message');
```

Эталон: **`hi Bob!`**.

Для сохранения клетки в L10 можно дополнительно проверять escaping `%%`, но для минимальной правки я бы не добавлял вторую ловушку: транзитивного резолва достаточно, а клетку разумнее перевести в L9.

### T26-L10 — проверять состояние после инварианта

Добавить в `Order`:

```php
public function count(): int
{
    return count($this->items);
}
```

Заменить конец сценария:

```php
$o = new Order;
$o->add('a');

try {
    $o->remove('a');
} catch (DomainException) {
}

echo $o->count();
```

Эталон: **`1`**, грейдер можно оставить исполняемым PHP.

Теперь проверяется не способность прочитать имя исключения, а понимание того, что неудачное удаление последнего элемента **не изменило состояние агрегата**.

## 3. «Край берега»: T11-L10 оставить, T12-L10 заменить

### T11-L10 — оставить как трудную содержательную клетку

Это настоящая композиция семантик:

1. `yield from` возвращает return-значение;
2. внешний авто-ключ не продвигается;
3. `iterator_to_array()` сохраняет ключи;
4. значение с ключом `0` перезаписывается.

То, что клетку не проходит никто, само по себе не дефект. Цель 40–60% относится к **среднему уровня**, а не к каждой клетке. Несколько содержательных крайних клеток допустимы.

Но оставлять её нужно не ради искусственного «антисатуратора», а потому что она измеряет реальную семантику. При результатах huihui 71–89% признаков насыщения шкалы сверху всё равно нет.

Текущее RU-пояснение уже правильно описывает перезапись ключа; EN/ZH должны говорить то же самое, без «last/最后».

Если владелец всё же хочет более умеренную клетку про `yield from`, замена:

```php
function inner(): Generator
{
    yield 1;
    yield 2;
    return 'ok';
}

function outer(): Generator
{
    $r = yield from inner();
    yield $r;
    yield 4;
}

echo implode(',', iterator_to_array(outer(), false));
```

Эталон: **`1,2,ok,4`**. Это проверяет return-значение и продолжение внешнего генератора без крайней ловушки перезаписи ключей.

### T12-L10 — заменить числовую экзотику

Не стоит сохранять клетку только потому, что она даёт 0%. Запоминание `E_ALL = 30719` и вычитание `8` — слабый прокси глубокого знания.

Минимальная замена, проверяющая тот же версионный факт без десятичной арифметики:

```php
echo (E_ALL & 2048) === 0 ? 'strict-out' : 'strict-in';
```

Промпт обязательно с **PHP 8.5**, эталон: **`strict-out`**.

Здесь `2048` — исторический бит `E_STRICT`. Литерал использован намеренно, чтобы не зависеть от возможного deprecation при обращении к константе `E_STRICT`. Это всё ещё трудная версионная клетка, но уже не требование помнить точное десятичное значение `E_ALL`.

## 4. Узнаваемые квизы — массово не переписывать

Для целей этой карты узнавание классики **является частью измеряемого знания**, особенно на L9.

Модель, которая знает поведение `foreach` по ссылке или `return` в `finally`, в том числе потому что видела примеры в документации, действительно лучше подготовлена к PHP-проекту. Это не «читерство», а ожидаемый результат обучения.

Поэтому:

- **T10-L9, T08-L9, T02-L9, T01-L10, T03-L9, T15-L9, T17-L9, T24-L9, T20-*** — оставить.
- Не заменять их только ради оригинальности: новые постановки добавят риск двусмысленности, но не обязательно улучшат измерение.
- Для будущих клеток L10 предпочитать новые композиции правил, а не ещё один известный квиз дословно.
- Переписывать классику стоит только при конкретном дефекте: утечка, неверный уровень, версионная неоднозначность или проверка арифметики вместо семантики.

Если нужен отдельный тест незашоренного reasoning на незнакомых задачах, это должна быть другая методика, а не скрытая замена назначения зоны «Глубина».

## 5. Минимальный набор правок

### P0 — обязательно до следующих серий

1. **Ничего не менять в проверенных эталонах существующих клеток.**
2. Версии в промптах уже исправлены в приложенном v3:
   - T06-L10 и T12-L10 содержат PHP 8.5;
   - T18-L9/L10 содержат PHPUnit 10.5.  
   Повторно это исправлять не нужно.
3. Исправить инфраструктурный баг отчёта: deep определять по `kind: "deep"`/штампу, а не по `level >= 9`, иначе версионная панель искажает метрики «Глубины».
4. Синхронизировать note T11-L10 во всех языках; в ZH T28-L10 заменить `特性加载器` на `属性加载器`.

### P1 — содержательная ревизия

1. Переписать **T13-L9, T18-L10, T21, T23, T26** по вариантам выше; **VC-L9 оставить**.
2. **T12-L10 заменить**, T11-L10 оставить.
3. T12-L9 заменить, а не механически переносить. Например, клеткой о семантике `password_needs_rehash`:

   ```php
   $hash = password_hash('x', PASSWORD_BCRYPT, ['cost' => 4]);
   echo password_needs_rehash($hash, PASSWORD_BCRYPT, ['cost' => 4]) ? 'yes' : 'no';
   echo password_needs_rehash($hash, PASSWORD_BCRYPT, ['cost' => 5]) ? 'yes' : 'no';
   ```

   Эталон: **`noyes`**. Это знание поведения security API, а не ручное кодирование байтов.
4. Перевесить только очевидные семантические промахи: **T05, T08, T14, T15, T23, T26 → L9; T21 → L10**. Остальные пограничные не двигать по одним процентам.
5. Не проводить массовый переспрос вслепую: сначала машинно проверить новые эталоны и сделать небольшой пилот на huihui/e2b. После этого заморозить новую deep-версию и допросить изменённые клетки на всех прогонах.

### P2 — не делать сейчас

- Не переписывать весь узнаваемый квизовый корпус.
- Не переписывать T11-L10 из-за одних 0%.
- Не подгонять каждую клетку под 50–75% или 40–60%: калибровать следует распределение уровня в целом, сохраняя лёгкие anchors и несколько содержательных крайних клеток.
