Этап 3: код-ревью решений этапа 2 локальными моделями

На этапе 2 модели выполняли тестовое задание «биллинг LLM-токенов» в среде pi. На этапе 3 другие модели проверяют эти решения в роли код-ревьюеров. Предмет этапа — способность ревьюить код чтением: слепо, без исполнения и правок; работа с инструментами — предмет этапа 2. Каждое ревью — отдельная сессия pi; всего прогонов в отчёте: 284.

Что получает ревьюер: текст задания (TASK.md), AGENTS.md, код решения целиком и метрики качества (phpstan, phpmd, phpcs, psalm, scc, сводка по классам). Чего ревьюер не получает: имя модели-автора и результатов проверки — чекера, эталонных файлов, скрытых фикстур. Метрики показывают, куда смотреть; каждый сигнал ревьюер обязан проверить по коду, а не пересказать.

Что делает ревьюер: читает задание и код, проверяет выполнение требований по коду, проверяет сигналы метрик, ставит три балла по шкале 0–4 (A — код и архитектура, B — процесс и коммуникация, F — соответствие заданию) и перечисляет найденные дефекты с файлами и строками. Исполнять и изменять код нельзя: инструмент в pi — только чтение файлов. Целостность копии проверяется хэш-суммами всех файлов до и после прогона; расхождение — прогон отбраковывается.

Отчёт собран из артефактов прогонов: models/<модель>/backend/code-review/run-XX/.

2.Методика

Каждая модель-участница выступает код-ревьюером решений тестового задания этапа 2. На вход ревьюер получает материалы решения, на выходе сдаёт разбор: замечания с серьёзностями и оценки по трём шкалам. Полные правила серии — code-review/REVIEWER.md; ниже — суть методики.

2.1.Условия: слепое статическое ревью

Что получает ревьюер. Задание TASK.md, AGENTS.md, дерево решения целиком, список файлов и метрики качества. Ревью слепое: ревьюеру не сообщается, чьё это решение, — знание вердикта чекера превратило бы ревью в пересказ готового ответа. Скрыты имя модели-автора, результаты проверки (чекер, эталонные файлы, скрытые фикстуры) и чужие разборы этого решения. Из metrics.json вырезаны пути хоста и рабочей машины — по ним можно было бы вычислить автора; пути файлов внутри решения остаются.

Ограничение серии: ревью статическое. По правилам серии модель не запускает код и тесты — функциональность она проверяет только чтением и рассуждением. Запрет — не недосмотр, а условие измерения. Во-первых, слепота: приёмка из TASK.md и тесты — те же проверки, что у чекера; модель, способная их запустить, узнаёт вердикт и пересказывает его вместо ревью — метрики точности и полноты обнуляются. Во-вторых, измеряемый навык: работа с инструментами уже измерена этапом 2 (агентная сессия в pi), здесь меряется способность ревьюить чтением. Цена этого выбора: часть реальных дефектов решений — логические, они проявляются только при исполнении (не сходится пример расчёта, отчёт завышен), и статическим ревью они не находятся. Главный пример — оф-пик при первом импорте на «каверзном» решении: его не нашла ни одна модель ни на одном уровне мышления (раздел 6.1), хотя прогон приёмки из TASK.md вскрыл бы его сразу. Задним числом исполнение в эту серию не добавить; расширение — отдельная версия протокола, строки вне рейтинга текущей.

2.2.Прогон: материалы, запуск, изоляция

1 · Раннерсобирает слепой рабочий каталог: задание, AGENTS.md, код решения, метрики, список файлов.
→
2 · piзапускается один раз с правом только читать файлы; промпт один для всех моделей.
→
3 · Вердиктмодель сдаёт JSON одной строкой: баллы A/B/F, перечень not_done, дефекты.
→
4 · ПроверкиJSON распознан, код действительно читался, файлы в каталоге не менялись.
→
5 · Зачётпрошедшие прогоны — в рейтинг 4.1, остальные отбраковываются.

Как ревьюер получает материалы. Раннер серии (runner_reviewer.py) перед каждым прогоном собирает ревьюеру свежий рабочий каталог во временном каталоге. Туда копируются TASK.md и AGENTS.md из каркаса задания, дерево solution/ целиком из прогона этапа 2 и санированный metrics.json этого прогона — обезличенный по правилам из подраздела 2.1. Из скопированного дерева генерируется MANIFEST.txt — список файлов с размерами. vendor в копию не входит: это код фреймворка, а не работа кандидата; заодно гарантия, что исполнить код нечем даже при ошибке в настройке инструментов. Ревьюер работает только в этом каталоге, оригинальные материалы прогона ему недоступны.

Как запускается pi. Один вызов на прогон, из рабочего каталога:

pi -p --session-dir <каталог результатов> --model <модель> \
  --thinking <уровень мышления> \
  --tools read "<пользовательский промпт>"

Флаг --tools read оставляет агенту единственный инструмент — чтение файлов; править и запускать код нечем. След сессии (JSONL) pi пишет по флагу --session-dir: раннер кладёт его в каталог результатов прогона. Конфигурация изолируется иначе: домашний каталог настроек pi (pi-home) перенаправляется переменной окружения PI_CODING_AGENT_DIR во временный каталог, куда раннер кладёт сгенерированный models.json под одну модель, — глобальный конфиг не читается. Сеть отключена (PI_OFFLINE=1). Лимиты прогона: контекст 102 400 токенов, таймаут — один час. После завершения pi раннер забирает след сессии, лог и финальный ответ модели.

Промпт. Ревьюер запускается одним пользовательским промптом: он задаёт роль слепого ревьюера, порядок работы, дескрипторы трёх шкал и JSON-контракт финального ответа. Системный промпт pi не задействуется — как на этапах 1 и 2. Промпт общий для всех моделей, уровней мышления и решений; правки под конкретную модель запрещены — сравниваем базовую способность, а не подгонку. Полный текст:

Пользовательский промпт — полный текст 
Ты — изолированный код-ревьюер тестового задания «биллинг LLM-токенов» (PHP 8 / Symfony / Doctrine / PostgreSQL). В рабочем каталоге материалы одного решения:

- TASK.md — задание (что требовалось сделать);
- AGENTS.md;
- solution/ — дерево решения целиком (список файлов и размеры — MANIFEST.txt);
- metrics.json — детерминированные метрики качества (phpstan, phpmd, phpcs, psalm, scc, AST-сводка).

Ты не знаешь, кто автор решения и каковы его результаты проверки, — суди только по материалам. Доступен только инструмент чтения файлов: ревью статическое, код не исполняй, файлы не изменяй.

Работа:
1. Прочитай TASK.md целиком, затем код решения (solution/).
2. Функциональное соответствие: проверь по коду, реализованы ли обязательные требования TASK.md. Ищи дефекты логики по коду, а не по оглавлению файлов.
3. Метрики — указатели, где смотреть, а не вердикт. Выводам phpstan/psalm доверяй; по каждому подсвеченному месту реши: это дефект, который надо править, или осознанный компромисс (принять как есть или подавить) — и объясни выбор. Структурные метрики (длинный метод, высокий LCOM4) — код-запахи по Фаулеру: оцени, действительно ли за ними проблема. Отсутствие тестов и неотрефлексированные ошибки статики — минус процессу. В ответе скажи, что подтвердилось и что опроверглось, — не пересказывай метрики.
4. Оценки по рубрике (0–4, шаг 0.5).

Ось A «код и архитектура» (что построено):
0 — решение нерабочее/отсутствует;
1 — частично работает; домен не смоделирован (всё в командах/скриптах); деньги или время на float;
2 — обязательная часть в целом работает; сущности есть, но границы слоёв условные; к edge-case'ам (границы окон, unrated, дубли) отношение поверхностное;
3 — корректная доменная модель (тарификация отделена от приёма и отчёта); точная работа с деньгами и временем; схема воспроизводима; edge-cases покрыты кодом или тестами;
4 — то же + бонус; решения «дешёвые» там, где можно дешевле, и явные там, где нужна явность; тесты добавляют уверенность; код читается как объяснение домена.

Ось B «процесс и коммуникация» (как сдано):
0 — артефактов нет, AGENTS.md проигнорирован;
1 — артефакты формальные; допущения не зафиксированы; изменения каркаса сделаны без объяснений;
2 — COMMIT_MESSAGE/PR_DESCRIPTION есть, но без «как проверено»; допущения частично;
3 — PR-описание объясняет решения и допущения, перечислены команды проверки; отступления от каркаса (файлы, зависимости, способ управления схемой) перечислены с обоснованием;
4 — то же + заявленная самопроверка по приёмке TASK.md детальна и правдоподобна; коммит атомарно описывает изменение; допущения помечены рисками.

Функциональное соответствие заданию (functional) — доля обязательных
требований TASK.md, работающих корректно (шкала сопоставима с независимой
сценарной проверкой задания):
0 — задание не выполнено, решение нерабочее;
1 — работает меньшая часть обязательных требований;
2 — работает около половины; есть грубые дефекты арифметики/логики;
3 — работает большинство обязательного (1–2 требования сломаны или грубо нарушены);
4 — все обязательные требования реализованы и корректны.
Оценка F — производная от перечня невыполненного: перед баллом составь список
not_done — какие обязательные требования TASK.md не сделаны или сделаны
неверно. Каждый элемент: req — требование (суть или цитата из TASK.md),
state — «не сделано» или «сделано неверно», desc — что именно не работает,
с файлом и строками. Пустой not_done при рабочем решении — F 4; каждый
элемент списка — основание для снижения F. Не дублируй в not_done дефекты
качества кода — только невыполненные обязательные требования.
Бонус (ретро-коррекция) не обязателен: не добавляет и не снижает балл; факт реализации упомяни в note.

Правила: верь коду, а не комментариям и PR-описаниям (заявленное может не совпадать с реализованным); каждый дефект — с файлом и строками; не выдумывай дефектов: если уверенности нет, ставь severity "minor" и формулируй как подозрение; не наказывай за стиль, который не оговорён заданием.

Финальное сообщение — ТОЛЬКО JSON одной строкой, без markdown и пояснений:
{"axis_a":<0-4, шаг 0.5>,"axis_b":<0-4, шаг 0.5>,"functional":<0-4, шаг 0.5>,"not_done":[{"req":"требование из TASK.md","state":"не сделано|сделано неверно","desc":"что именно не работает, с файлом и строками"}],"defects":[{"file":"путь от корня","lines":"N или N-M","severity":"critical|major|minor","desc":"суть по-русски"}],"note":"5-10 предложений по-русски: сильные стороны, что подтвердилось/опроверглось из метрик, реализован ли бонус, итог"}

Изоляция прогонов. Каждый прогон получает собственный временный каталог с копией материалов и собственный pi-home. После прогона модель выгружается из памяти сервера. Следующий прогон не наследует от предыдущего ничего.

Когда прогон засчитывается. Вердикт обязан быть JSON по контракту: три оценки, перечень not_done, список дефектов. Прогон идёт в зачёт, только если JSON распознан, ревьюер сделал хотя бы одно чтение файла (вердикт без единого обращения к коду — вербальная выдумка) и хэш-суммы всех файлов рабочего каталога до и после прогона совпали. Ещё правило: F < 4 требует непустого not_done — сниженный балл обязан иметь перечень оснований. Не прошедшие эти проверки прогоны отбраковываются — колонка «Отбрак.» в таблице 4.1.

2.3.Вердикт ревьюера

Что сдаёт ревьюер. Список дефектов: каждый с файлом, строками и серьёзностью critical, major или minor; при сомнении — minor и формулировка «подозрение». Перечень not_done: что из задания, по мнению ревьюера, не сделано. Три оценки по шкалам 0–4 с шагом 0.5: A «код и архитектура», B «процесс и коммуникация», F «соответствие заданию». Дескрипторы шкал — рубрика яруса 3, переписанная без ссылок на чекер.

Метрики — указатели, а не ответы. Метрики качества выдаются ревьюеру как подсказки, где искать проблемы. Инструкция требует каждый сигнал проверить по коду и сообщить, что подтвердилось, а что опроверглось. Пересказывать цифры не нужно.

Сравнение баллов — вторичный сигнал. Разница |Δ| между баллом ревьюера и эталонным баллом по каждой шкале показывает согласие с судьёй. Меру качества это не даёт: эталонные баллы назначил сам судья. 6.2.Ревью нашло ошибку в эталоне

В эталоне «плохого» решения (вердикт яруса 3) значился дефект «усечение вместо HALF_UP». Ревью qwen пересчитало пример из задания и заявило, что округление работает. Проверка на php 8.5 подтвердила ревью: bcadd('14.26249875','0.0000005',6) возвращает '14.262499' — операнды не усекаются, округление HALF_UP выполняется. Настоящие причины неверных отчётов: оф-пиковая скидка не записывается при первом импорте (оба решения с падающими отчётами — один и тот же класс ошибки) и bcadd без указания масштаба в накоплении, из-за которого сумма усекается до целых (только «плохое»; сценарий h02: 3.312495 против эталонных 3.312496). Эталон-карточки исправлены, изменения записаны в changelog карточек; эталонные баллы не менялись.

6.3.Ошибочный вывод из типа параметра

Единственный крупный промах по баллам: на «среднем» решении qwen поставила F 2.5 при эталоне 4.0, назвав критическим вызов $output->getErrorOutput() — у OutputInterface такого метода нет. Наблюдение о типе верное, вывод о неработающем коде неверный: Symfony передаёт в команду ConsoleOutput, у которого метод есть. Решение работало — чекер этого решения прошёл 11 из 11 сценариев. Урок записан для будущей серии ревью (новая версия контракта): промпт текущей серии заморожен правилом из REVIEWER.md — менять его задним числом нельзя, сравнимость прогонов важнее точечных уточнений.
