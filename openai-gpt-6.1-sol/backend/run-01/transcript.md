## Q01 · PHP 8

**Интервьюер:** Какие возможности современных версий PHP — с 8.0 и новее — ты считаешь самыми важными для написания чистого и надёжного кода? Покажи на коротких примерах кода.

**Кандидат:**

Я бы выделил возможности, которые **делают контракты явными, сокращают некорректные состояния и упрощают чтение кода**. При этом важно учитывать минимальную версию PHP в проекте.

### 1. Более выразительная система типов — PHP 8.0+

Union types позволяют явно описать несколько допустимых типов, а `mixed` — осознанно обозначить отсутствие ограничений:

```php
declare(strict_types=1);

function normalizeId(int|string $id): string
{
    return (string) $id;
}
```

Но для бизнес-кода я предпочитаю конкретный тип, если это возможно: union не должен маскировать неопределённый контракт.

В PHP 8.1 появились intersection types — объект должен реализовывать **оба** интерфейса:

```php
function consume(Iterator&Countable $items): void
{
    printf("Items: %d\n", count($items));

    foreach ($items as $item) {
        // ...
    }
}
```

А PHP 8.2 поддерживает DNF-типы, например `(Iterator&Countable)|null`.

### 2. Constructor property promotion — PHP 8.0, `readonly` — PHP 8.1

Promotion убирает повторение при объявлении зависимостей, а `readonly` защищает свойства от изменения после инициализации:

```php
final class CreateOrderHandler
{
    public function __construct(
        private readonly OrderRepository $orders,
        private readonly PaymentGateway $payments,
    ) {}
}
```

Для DTO и value objects удобно использовать `readonly class`, доступный с PHP 8.2:

```php
final readonly class Money
{
    public function __construct(
        public int $amountInMinorUnits,
        public string $currency,
    ) {
        if ($amountInMinorUnits < 0) {
            throw new InvalidArgumentException('Amount must be non-negative');
        }
    }
}
```

Важная оговорка: **`readonly` не означает глубокую неизменяемость** — объект, хранящийся в readonly-свойстве, всё ещё может быть изменяемым.

### 3. Enums — PHP 8.1

Они заменяют строки и наборы констант там, где есть конечный набор допустимых значений:

```php
enum OrderStatus: string
{
    case Draft = 'draft';
    case Paid = 'paid';
    case Cancelled = 'cancelled';
}

function canShip(OrderStatus $status): bool
{
    return $status === OrderStatus::Paid;
}
```

На границе системы входное значение можно безопасно разобрать:

```php
$status = OrderStatus::tryFrom($requestStatus);

if ($status === null) {
    throw new InvalidArgumentException('Unknown order status');
}
```

Так произвольная строка не попадёт внутрь бизнес-логики.

### 4. `match` — PHP 8.0

В отличие от `switch`, `match` возвращает значение, использует строгое сравнение и не допускает случайного перехода к следующей ветке:

```php
function label(OrderStatus $status): string
{
    return match ($status) {
        OrderStatus::Draft => 'Черновик',
        OrderStatus::Paid => 'Оплачен',
        OrderStatus::Cancelled => 'Отменён',
    };
}
```

Здесь я намеренно не добавляю `default`: если появится новый статус, забытая ветка проявится через `UnhandledMatchError` при выполнении, а статический анализатор может предупредить раньше.

### 5. Nullsafe operator — PHP 8.0

Полезен для цепочек, где отсутствие значения действительно допустимо:

```php
$city = $user->getAddress()?->getCity() ?? 'Не указан';
```

Но я не использую `?->`, чтобы скрывать нарушение инварианта: если адрес обязателен для доставки, его отсутствие нужно обработать явно.

### 6. Атрибуты — PHP 8.0

Они дают структурированные метаданные вместо специальных комментариев. Например, в Symfony:

```php
use Symfony\Component\Routing\Attribute\Route;

#[Route('/orders/{id}', methods: ['GET'])]
public function show(string $id): Response
{
    // ...
}
```

Сами атрибуты — механизм языка; маршрутизацию, валидацию или ORM-маппинг обеспечивает библиотека, которая их читает.

### 7. `#[Override]` — PHP 8.3

Особенно полезен при рефакторинге наследования: PHP проверяет, что метод действительно переопределяет метод родителя или реализует метод интерфейса.

```php
interface Handler
{
    public function handle(): void;
}

final class ImportHandler implements Handler
{
    #[\Override]
    public function handle(): void
    {
        // ...
    }
}
```

Если контракт изменится и метод перестанет что-либо переопределять, это не останется незаметным.

**Если выбирать самое важное**, я бы поставил на первое место типы, enums и `readonly`: они помогают предотвращать ошибки через устройство кода. А максимальную пользу эти возможности дают вместе со статическим анализом PHPStan/Psalm и тестами — один только синтаксис надёжность не гарантирует.

## Q02 · PHP 8

**Интервьюер:** Как устроена система типов в PHP: что даёт strict_types, как ведут себя приведения типов, какие типичные ловушки встречаются на практике? Приведи примеры, где типизация спасает, а где удивляет.

**Кандидат:**

PHP — динамически типизированный язык, но с проверяемыми объявлениями типов. Тип принадлежит значению, а переменная без объявления типа может хранить разные значения. Типы параметров, возвращаемых значений и свойств позволяют закрепить контракт и получить `TypeError`, если он нарушен.

## 1. Что даёт `strict_types`

```php
declare(strict_types=1);

function sum(int $a, int $b): int
{
    return $a + $b;
}

sum(2, 3);       // 5
sum('2', '3');   // TypeError
```

Без строгого режима PHP допускает некоторые неявные преобразования скалярных аргументов:

```php
// strict_types не включён

function sum(int $a, int $b): int
{
    return $a + $b;
}

sum('2', '3'); // 5: строки преобразованы в int
```

**Главная тонкость: для аргументов режим определяется файлом, из которого вызывается функция**, а не файлом, где она объявлена.

```php
// functions.php
<?php
declare(strict_types=1);

function acceptId(int $id): void {}
```

```php
// caller.php — без strict_types
<?php
require 'functions.php';

acceptId('42'); // Допустимо: аргумент преобразуется в int
```

Для возвращаемого значения действует режим файла, где определена функция:

```php
declare(strict_types=1);

function getId(): int
{
    return '42'; // TypeError при вызове
}
```

Есть и предусмотренное исключение: **`int` допускается для параметра `float` даже в строгом режиме**.

```php
declare(strict_types=1);

function half(float $value): float
{
    return $value / 2;
}

half(5); // 2.5
```

`strict_types` не меняет правила операторов, сравнений и явных приведений. Вызовы из внутреннего кода PHP, например callback через `array_map`, также не всегда ведут себя как прямой вызов из строгого файла.

## 2. Явное приведение — не валидация

Явный cast выполняется и при включённом `strict_types`:

```php
declare(strict_types=1);

var_dump((int) '42');      // int(42)
var_dump((int) '42abc');   // int(42)
var_dump((int) 'abc');     // int(0)
var_dump((int) 3.9);       // int(3)
```

Поэтому так обрабатывать пользовательский ввод опасно:

```php
$id = (int) ($_GET['id'] ?? '');
// Некорректное значение может превратиться в 0 или другое число.
```

Лучше отдельно проверить формат и диапазон, а затем передать значение в типизированную бизнес-логику:

```php
$rawId = $_GET['id'] ?? null;

if (!is_string($rawId)) {
    throw new InvalidArgumentException('ID must be a string');
}

$id = filter_var(
    $rawId,
    FILTER_VALIDATE_INT,
    ['options' => ['min_range' => 1]],
);

if ($id === false) {
    throw new InvalidArgumentException('Invalid ID');
}
```

Здесь сравнение именно `=== false`: при других ограничениях валидным результатом мог бы быть `0`.

## 3. Операторы тоже преобразуют значения

Строгий режим не запрещает арифметику с числовыми строками:

```php
declare(strict_types=1);

var_dump('10' + 2); // int(12)
```

В PHP 8 нечисловая строка в арифметике вызывает `TypeError`:

```php
$result = 'hello' + 2; // TypeError
```

Но строка с числовым префиксом может дать результат с предупреждением:

```php
$result = '10 apples' + 2; // 12 и Warning
```

То есть арифметика — тоже не способ валидировать входные данные.

## 4. `==` и `===` — одна из главных ловушек

`==` сравнивает с преобразованием типов, `===` — проверяет и значение, и тип:

```php
var_dump(0 == '0');     // true
var_dump(0 === '0');    // false
var_dump(false == '0'); // true
```

В PHP 8 сравнение числа с нечисловой строкой изменилось:

```php
var_dump(0 == 'hello'); // false в PHP 8; в PHP 7 было true
```

Но сравнение числовых строк по-прежнему может удивлять:

```php
var_dump('0e123' == '0e456');  // true: обе строки трактуются как число 0
var_dump('0e123' === '0e456'); // false
```

Для обычных сравнений я предпочитаю `===`, а для сравнения секретов или вычисленных MAC — `hash_equals()`.

Похожая ловушка есть у `in_array`:

```php
var_dump(in_array('1', [1, 2]));       // true
var_dump(in_array('1', [1, 2], true)); // false
```

## 5. Приведение к `bool` не понимает смысл строки

```php
var_dump((bool) 'false'); // true
var_dump((bool) '0');     // false
var_dump((bool) '');      // false
```

Поэтому флаг из переменной окружения нельзя надёжно прочитать через `(bool)`:

```php
$enabled = filter_var(
    'false',
    FILTER_VALIDATE_BOOLEAN,
    FILTER_NULL_ON_FAILURE,
);

var_dump($enabled); // false; неизвестное значение даст null
```

Также `empty()` объединяет несколько разных состояний:

```php
empty('0'); // true
empty(0);   // true
empty(null); // true
```

Если важно отличать отсутствие значения от нуля, проверяю их явно.

## 6. Где типизация действительно спасает

Типизированное свойство не позволит записать значение неподходящего типа; в строгом файле скалярное преобразование тоже не пройдёт:

```php
declare(strict_types=1);

final class Order
{
    public int $quantity;
}

$order = new Order();
$order->quantity = '3'; // TypeError
```

Однако типизированное свойство без начального значения имеет состояние **«не инициализировано»**, а не `null`:

```php
$order = new Order();

echo $order->quantity; // Error: свойство не инициализировано
```

Даже nullable-свойство нужно явно инициализировать:

```php
public ?int $quantity = null;
```

Ещё сильнее защищают отдельные доменные типы:

```php
final readonly class UserId
{
    public function __construct(public int $value)
    {
        if ($value <= 0) {
            throw new InvalidArgumentException('ID must be positive');
        }
    }
}

function loadUser(UserId $id): void
{
    // ...
}

loadUser(42); // TypeError независимо от strict_types
```

Теперь контракт проверяет не просто «это число», а «это идентификатор пользователя», а конструктор обеспечивает инвариант.

## 7. Что объявления типов не проверяют

`array` не задаёт тип элементов:

```php
function total(array $amounts): int
{
    // Здесь могут быть строки, объекты и вложенные массивы.
    return array_sum($amounts);
}
```

PHPDoc вроде `@param list<int> $amounts` помогает PHPStan/Psalm, но **не выполняет runtime-проверку**. Также тип `int` сам по себе не гарантирует положительность, а `string` — корректность email.

Мой практический подход: **`strict_types` во всех файлах проекта, явная валидация на границах, конкретные типы и value objects внутри, строгие сравнения и статический анализ**. Это разделяет преобразование внешних данных и выполнение бизнес-логики, где значения уже должны быть корректными.

## Q03 · PHP 8

**Интервьюер:** Как ты проектируешь работу с исключениями в PHP-приложении: свои иерархии исключений, оборачивание чужих исключений, что считается контрактом метода? Какие антипаттерны здесь встречаются?

**Кандидат:**

Я проектирую исключения как часть поведения приложения: **что вызывающий код может обработать, что нужно перевести на границе системы и что означает дефект или инфраструктурный сбой**.

## 1. Разделяю категории ошибок

Обычно выделяю:

- **Ожидаемый отрицательный результат**: пользователь не найден при поиске, данные не прошли валидацию. Иногда удобнее вернуть `null` или объект результата.
- **Нарушение бизнес-правила**: заказ нельзя отменить после отгрузки.
- **Инфраструктурный сбой**: недоступна БД, тайм-аут платёжного сервиса.
- **Ошибка программирования**: `TypeError`, нарушение внутреннего инварианта.

Не делаю общую иерархию ради самой иерархии. Базовый класс или интерфейс нужен, когда вызывающий код действительно обрабатывает группу ошибок одинаково.

```php
abstract class OrderException extends \DomainException {}

final class OrderCannotBeCancelled extends OrderException
{
    public function __construct(public readonly string $orderId)
    {
        parent::__construct('Shipped order cannot be cancelled');
    }
}
```

Доменные исключения не содержат HTTP-статусов, объектов Symfony или деталей Doctrine: домен не должен знать, каким транспортом его вызывают.

## 2. Выбираю между результатом и исключением

Например, различаю два контракта репозитория:

```php
interface OrderRepository
{
    public function find(OrderId $id): ?Order;

    /** @throws OrderNotFound */
    public function get(OrderId $id): Order;
}
```

`find()` подходит, когда отсутствие заказа — нормальный вариант. `get()` — когда сценарий требует существующий заказ и должен прекратиться, если его нет.

При этом `get()` не гарантирует, что никаких других ошибок быть не может: например, хранилище может оказаться недоступным. Значимые инфраструктурные ошибки я тоже документирую на уровне порта.

Для проверки формы с десятками ошибок обычно лучше вернуть список нарушений, чем выбрасывать исключение на первом поле.

## 3. Оборачиваю чужие исключения на границе адаптера

Если прикладной код работает через интерфейс платёжного шлюза, он не должен зависеть от исключений конкретного HTTP-клиента:

```php
interface PaymentGateway
{
    /** @throws PaymentServiceUnavailable */
    public function charge(PaymentRequest $request): PaymentReceipt;
}

final class PaymentServiceUnavailable extends \RuntimeException {}
```

Адаптер переводит техническую ошибку в понятный контракт порта:

```php
try {
    return $this->client->charge($request);
} catch (TransportExceptionInterface $e) {
    throw new PaymentServiceUnavailable(
        'Payment service is unavailable',
        previous: $e,
    );
}
```

Здесь важно:

- **Сохранять `previous`**, чтобы не потерять исходную причину и цепочку диагностики.
- Ловить конкретные ошибки, а не любой `Throwable`: программный дефект нельзя выдавать за недоступность сервиса.
- Не превращать все ответы провайдера в одну ошибку: отказ в оплате и сетевой тайм-аут требуют разных действий.

Особенно важно: **тайм-аут платежа не означает, что платёж не выполнен**. Повторная попытка требует идемпотентного ключа или проверки статуса.

## 4. Что считаю контрактом метода

Контракт — это не только типы параметров и результата. Он включает:

- допустимые входные значения и предусловия;
- результат и постусловия;
- побочные эффекты;
- ожидаемые исключения и условия их возникновения;
- гарантии при ошибке: что могло уже измениться;
- при необходимости — идемпотентность и возможность повторного вызова.

Например:

```php
/**
 * Отменяет заказ и сохраняет изменения атомарно в БД.
 *
 * @throws OrderNotFound
 * @throws OrderCannotBeCancelled
 * @throws OrderStorageUnavailable
 */
public function cancel(OrderId $id): void;
```

В PHP нет checked exceptions: `@throws` документирует контракт и помогает инструментам, но движок не заставляет вызывающий код делать `catch`.

Я документирую **значимые для потребителя ошибки**, а не перечисляю все теоретически возможные `Error`. Изменение семантики исключений тоже может быть несовместимым изменением API.

## 5. Обрабатываю там, где есть решение

Хорошая причина для `catch` — возможность:

- восстановиться;
- выполнить ограниченный безопасный retry;
- перевести исключение на другой уровень абстракции;
- сформировать HTTP-ответ;
- завершить обработку сообщения по правилам очереди.

В HTTP-приложении обычно есть централизованный обработчик:

| Ошибка | Возможное представление |
|---|---|
| Ресурс не найден | `404` |
| Конфликт бизнес-состояния | `409` |
| Некорректные данные | `422` |
| Временная недоступность зависимости | `503` |
| Неожиданная ошибка | `500` |

Это не универсальная таблица: статус зависит от семантики конкретного API. Клиенту возвращаю стабильный код ошибки и безопасное сообщение, а стек и технические детали оставляю в логах.

Не каждое доменное исключение стоит логировать как `error`: например, ожидаемый отказ отменить отгруженный заказ может вообще не требовать аварийного лога.

## 6. Транзакции и очистка ресурсов

`catch (\Throwable)` оправдан, например, для отката и последующего проброса:

```php
$connection->beginTransaction();

try {
    $this->executeUseCase();
    $connection->commit();
} catch (\Throwable $e) {
    $connection->rollBack();
    throw $e;
}
```

На практике предпочитаю штатный transaction helper библиотеки, учитываю состояние транзакции и возможность ошибки самого rollback. Откат БД не отменяет уже выполненный внешний HTTP-запрос.

Освобождение ресурсов делаю через `finally`, но не возвращаю из него значения: это может подавить исходное исключение.

## 7. Основные антипаттерны

**Проглатывание ошибки:**

```php
try {
    $this->save($order);
} catch (\Throwable $e) {
    return true; // Ложный успех
}
```

**Потеря причины:**

```php
catch (TransportExceptionInterface $e) {
    throw new \RuntimeException($e->getMessage()); // Нет previous
}
```

**Логирование на каждом уровне с повторным пробросом** — одна ошибка превращается в несколько одинаковых событий.

**Перехват по тексту сообщения** — текст нестабилен; нужны типы или документированные коды.

**Исключения для обычного ветвления**, когда естественнее `null`, enum или объект результата.

**Безусловный retry** любой ошибки — особенно опасен для платежей и других неидемпотентных операций.

**Оборачивание всех ошибок в `ApplicationException`** — уничтожает полезные различия.

Мой основной принцип: **бросать исключение там, где обнаружено нарушение, переводить его на границе абстракции и обрабатывать только там, где есть осмысленное действие**.

## Q04 · ООП и принципы

**Интервьюер:** Какой из принципов SOLID, по твоему опыту, чаще всего нарушается в реальном коде и почему? Покажи типовой пример нарушения и его рефакторинг.

**Кандидат:**

В рамках нашего условного профиля кандидата я бы выбрал **SRP — принцип единственной ответственности**. Это не статистическое утверждение, но в прикладном PHP-коде такой тип нарушения особенно легко встретить.

SRP означает не «класс должен иметь один метод», а **«у класса должна быть одна причина для изменения»**. Нарушения часто появляются постепенно: к сценарию добавляют SQL, потом отправку письма, затем форматирование ответа — потому что всё это нужно «при создании заказа».

### Пример нарушения

```php
final class OrderController
{
    public function __construct(
        private \PDO $db,
        private MailerInterface $mailer,
    ) {}

    public function create(Request $request): JsonResponse
    {
        $data = $request->toArray();
        $email = $data['email'] ?? null;

        if (!is_string($email)
            || filter_var($email, FILTER_VALIDATE_EMAIL) === false
        ) {
            return new JsonResponse(['error' => 'Invalid email'], 422);
        }

        $statement = $this->db->prepare(
            'INSERT INTO orders (email, status)
             VALUES (:email, :status) RETURNING id'
        );
        $statement->execute([
            'email' => $email,
            'status' => 'draft',
        ]);

        $id = (int) $statement->fetchColumn();

        $this->mailer->send(
            (new Email())
                ->to($email)
                ->subject('Заказ создан')
                ->text("Номер заказа: {$id}")
        );

        return new JsonResponse(['id' => $id], 201);
    }
}
```

У контроллера несколько независимых причин измениться:

- поменялся HTTP-контракт;
- изменились правила создания заказа;
- изменилась схема хранения;
- изменились канал или содержание уведомления.

Кроме того, сбой отправки письма произойдёт **после сохранения заказа**: клиент получит ошибку и может повторить запрос.

### Рефакторинг

Разделяю транспорт, прикладной сценарий и инфраструктуру. Ниже — сокращённый пример; реализация валидации и адаптеров опущена.

**Контроллер отвечает за HTTP:**

```php
final class OrderController
{
    public function __construct(
        private CreateOrderRequestMapper $mapper,
        private CreateOrderHandler $handler,
    ) {}

    public function create(Request $request): JsonResponse
    {
        // Mapper проверяет структуру и значения входных данных.
        $command = $this->mapper->map($request->toArray());
        $id = $this->handler->handle($command);

        return new JsonResponse(['id' => $id->value], 201);
    }
}
```

**Прикладной обработчик координирует сценарий:**

```php
final readonly class CreateOrderCommand
{
    public function __construct(public EmailAddress $email) {}
}

final class CreateOrderHandler
{
    public function __construct(
        private OrderRepository $orders,
        private Outbox $outbox,
        private TransactionManager $transactions,
    ) {}

    public function handle(CreateOrderCommand $command): OrderId
    {
        return $this->transactions->run(function () use ($command): OrderId {
            $order = Order::create($command->email);

            $this->orders->save($order);

            $this->outbox->append(
                new OrderCreated($order->id(), $order->email())
            );

            return $order->id();
        });
    }
}
```

Здесь доменная модель обеспечивает бизнес-инварианты, репозиторий отвечает за сохранение, а **заказ и запись outbox сохраняются в одной транзакции БД**.

**Отдельный потребитель отвечает за уведомление:**

```php
final class SendOrderCreatedEmail
{
    public function __construct(
        private OrderNotificationSender $notifications,
    ) {}

    public function __invoke(OrderCreated $event): void
    {
        $this->notifications->sendCreated(
            $event->orderId,
            $event->email,
        );
    }
}
```

Фоновый процесс доставляет события из outbox; повторные доставки нужно учитывать отдельно. Это не обязательная часть SRP, а решение проблемы надёжности уведомлений в данном сценарии.

### Что изменилось

Теперь изменение SQL не затрагивает контроллер, изменение шаблона письма — сценарий создания заказа, а бизнес-правила можно тестировать без HTTP и почтового сервиса.

При этом обработчик не нарушает SRP только потому, что вызывает несколько зависимостей: **его единая ответственность — координация создания заказа**.

Я бы не дробил каждый класс механически. Критерий рефакторинга — независимые причины изменений и сложность тестирования, а не количество методов или строк.

### ↳ Углубление

**Интервьюер:** Можно ли нарушать принципы SOLID? Приведи пример оправданного нарушения.

**Кандидат:**

Да. **SOLID — ориентиры проектирования, а не требования, которые нужно выполнять любой ценой.** Отступление оправдано, если оно заметно упрощает решение, а последствия понятны и ограничены.

Например, можно сознательно отступить от **DIP — принципа инверсии зависимостей**: прикладной код напрямую зависит от конкретной инфраструктурной библиотеки.

### Пример: небольшая одноразовая CLI-команда

Нужно выгрузить email активных пользователей в CSV:

```php
final class ExportActiveUsers
{
    public function __construct(private \PDO $db) {}

    public function run(string $path): void
    {
        $file = fopen($path, 'wb');

        if ($file === false) {
            throw new \RuntimeException('Cannot open output file');
        }

        try {
            $rows = $this->db->query(
                'SELECT email FROM users WHERE active = true'
            );

            foreach ($rows as $row) {
                if (fputcsv($file, [$row['email']], ',', '"', '') === false) {
                    throw new \RuntimeException('Cannot write CSV row');
                }
            }
        } finally {
            fclose($file);
        }
    }
}
```

Здесь предполагается, что PDO настроен на `PDO::ERRMODE_EXCEPTION`. Команда напрямую знает о SQL, PDO и формате CSV — вместо собственных портов для чтения пользователей и записи результата.

**Почему это может быть оправдано:**

- команда действительно одноразовая или имеет узкое назначение;
- источник данных и формат выгрузки заранее известны;
- поведение можно проверить интеграционным тестом;
- отдельные интерфейсы и адаптеры пока добавили бы больше кода, чем пользы.

Внедрение PDO через конструктор облегчает тестирование, но **само по себе не означает соблюдения DIP**: зависимость всё равно направлена на конкретный инфраструктурный механизм.

### Когда я пересмотрю решение

Если выгрузка станет регулярной, появятся другие источники данных, форматы или бизнес-правила, выделю, например, `ActiveUserReader` и `UserExportWriter`. Тогда абстракции будут отражать реальную вариативность, а не гипотетическое будущее.

Мой критерий: **отступление должно быть локальным, осознанным и недорогим для последующего исправления**. «Так проще» — аргумент только тогда, когда мы учитываем не только скорость написания, но и стоимость поддержки.

### ↳ Углубление

**Интервьюер:** OCP можно реализовать способами, кроме наследования — какими?

**Кандидат:**

Да. **OCP — это возможность добавлять новое поведение без изменения стабильного кода**, а не требование использовать наследование. В PHP я чаще реализую его через композицию и полиморфизм.

### 1. Стратегии через интерфейс и композицию

Например, стоимость доставки зависит от способа доставки:

```php
interface ShippingCalculator
{
    public function calculate(Order $order): Money;
}

final class CourierShipping implements ShippingCalculator
{
    public function calculate(Order $order): Money
    {
        // Расчёт курьерской доставки.
    }
}

final class Checkout
{
    public function __construct(
        private ShippingCalculator $shipping,
    ) {}

    public function total(Order $order): Money
    {
        return $order->subtotal()->add(
            $this->shipping->calculate($order)
        );
    }
}
```

Чтобы добавить самовывоз, создаю новую реализацию `ShippingCalculator`, не меняя `Checkout`.

Это **реализация интерфейса, а не наследование реализации**. Выбор стратегии происходит в конфигурации DI или отдельной фабрике.

### 2. Реестр обработчиков

Подходит, когда реализацию нужно выбирать во время выполнения:

```php
interface Exporter
{
    public function export(array $rows): string;
}

final class ExportService
{
    /** @param array<string, Exporter> $exporters */
    public function __construct(private array $exporters) {}

    public function export(string $format, array $rows): string
    {
        $exporter = $this->exporters[$format]
            ?? throw new \InvalidArgumentException('Unsupported format');

        return $exporter->export($rows);
    }
}
```

Новый формат добавляется отдельным экспортёром и регистрацией в контейнере. В Symfony реализации можно собирать через теги сервисов.

**Важно:** изменение конфигурации подключения не означает, что OCP нарушен — стабильный алгоритм сервиса остаётся прежним.

### 3. Декораторы и middleware

Позволяют добавлять поведение вокруг существующей операции:

```php
final class LoggingExporter implements Exporter
{
    public function __construct(
        private Exporter $inner,
        private LoggerInterface $logger,
    ) {}

    public function export(array $rows): string
    {
        $this->logger->info('Export started');

        return $this->inner->export($rows);
    }
}
```

Аналогично добавляются метрики, кеширование или контроль доступа без изменения исходного экспортёра. Нужно сохранять контракт: например, кеширование не должно менять смысл результата.

### 4. Передача функции или замыкания

Для небольшого расширяемого алгоритма интерфейс иногда избыточен:

```php
function filterOrders(array $orders, callable $predicate): array
{
    return array_values(array_filter($orders, $predicate));
}

$paidOrders = filterOrders(
    $orders,
    static fn (Order $order): bool =>
        $order->status() === OrderStatus::Paid,
);
```

Добавляем новые условия, не меняя механизм фильтрации. Для сложных контрактов предпочту интерфейс; для локального поведения достаточно функции.

### 5. События и подписчики

Сценарий публикует `OrderCreated`, а независимые подписчики отправляют уведомления, обновляют аналитику и выполняют другие дополнительные действия.

Новый подписчик не требует изменения издателя. Но **обязательные шаги бизнес-сценария не стоит прятать в событиях** без явных гарантий порядка, транзакционности и обработки ошибок.

### 6. Правила, выраженные данными

Если вариативность заранее ограничена, поведение можно расширять конфигурацией: таблицей тарифов, набором правил или маршрутов. Тогда добавляется запись, а не новая ветка `if`.

При этом конфигурацию нужно валидировать; если она превращается в собственный язык программирования, простота может исчезнуть.

**Главная оговорка:** невозможно закрыть код от любых изменений. Я выбираю конкретную ось расширения — новый способ доставки, формат экспорта или обработчик события — и делаю стабильным код вокруг неё. Абстракции под все мыслимые изменения обычно лишь усложняют систему.

### ↳ Углубление

**Интервьюер:** SRP применяется только к классам?

**Кандидат:**

Нет. **SRP применим не только к классам, но и к функциям, модулям, пакетам и сервисам** — на каждом уровне полезно группировать код, который меняется по одной причине, и разделять то, что меняется независимо.

При этом «одна ответственность» — не обязательно «одно действие».

### Пример на уровне функции

```php
function registerUser(array $data): void
{
    // Проверить HTTP-данные.
    // Применить правила регистрации.
    // Выполнить SQL-запрос.
    // Сформировать и отправить email.
}
```

Здесь смешаны причины изменения: формат запроса, бизнес-правила, схема БД и шаблон письма.

После разделения прикладной сценарий может выглядеть так:

```php
function registerUser(
    RegisterUserCommand $command,
    UserRepository $users,
): UserId {
    $user = User::register($command->email);
    $users->save($user);

    return $user->id();
}
```

Функция выполняет несколько действий, но её ответственность одна — **координация регистрации пользователя**. Проверка HTTP-запроса остаётся на транспортной границе, детали SQL — в реализации репозитория.

### На других уровнях

- **Модуль:** расчёт тарифов не должен одновременно управлять шаблонами уведомлений.
- **Пакет:** библиотека доменной модели не должна требовать Symfony только ради маршрутизации.
- **Сервис:** сервис платежей не должен владеть ещё и каталогом товаров, если эти области развиваются независимо.

Однако SRP сам по себе не требует выносить каждую ответственность в отдельный микросервис: логического разделения внутри приложения часто достаточно.

Мой практический вопрос при проверке SRP: **«Какие независимые требования заставляют менять этот код?»** Если таких причин несколько, стоит рассмотреть разделение — но не дробить код только ради количества классов.

## Q05 · Symfony

**Интервьюер:** Объясни, как устроен контейнер внедрения зависимостей в Symfony: что происходит при компиляции контейнера, как работает autowiring и что происходит в момент, когда сервис запрошен впервые.

**Кандидат:**

В Symfony DI-контейнер — это **описание графа объектов, которое при сборке превращается в PHP-код для их создания**. Поэтому важно разделять компиляцию контейнера и получение сервиса во время выполнения.

## 1. Что происходит при компиляции

Сначала Symfony загружает конфигурацию сервисов: YAML, XML, PHP-конфигурацию, определения из bundles и зарегистрированные классы.

Например:

```yaml
services:
    _defaults:
        autowire: true
        autoconfigure: true

    App\:
        resource: '../src/'

    App\Contracts\OrderRepository:
        alias: App\Infrastructure\DoctrineOrderRepository
```

На этой стадии `ContainerBuilder` хранит не готовые объекты, а **definitions** — инструкции:

- какой класс или фабрику использовать;
- какие аргументы передать;
- какие вызовы методов выполнить;
- является ли сервис public, shared или lazy;
- какие у него теги.

Затем выполняются **compiler passes**. Они, в частности:

- разрешают зависимости и autowiring;
- обрабатывают autoconfiguration, теги и декораторы;
- проверяют корректность ссылок и графа зависимостей;
- оптимизируют контейнер: удаляют неиспользуемые private-сервисы, встраивают некоторые определения.

Пользовательский compiler pass тоже может изменить definitions, например собрать все обработчики с определённым тегом.

После этого контейнер выгружается в кеш как PHP-код. В production он обычно создаётся при прогреве кеша и используется повторно; в debug-режиме Symfony следит за изменениями ресурсов и при необходимости пересобирает его.

**Компиляция обычно не создаёт экземпляры прикладных сервисов** — она готовит код их создания.

## 2. Как работает autowiring

Autowiring анализирует типы аргументов конструктора и подставляет ссылки на подходящие сервисы:

```php
final class CreateOrderHandler
{
    public function __construct(
        private OrderRepository $orders,
        private LoggerInterface $logger,
    ) {}
}
```

Для каждого аргумента контейнер должен определить конкретный сервис:

- по зарегистрированному классу;
- по alias интерфейса;
- по явно заданному аргументу или binding;
- в поддерживаемых случаях — по единственной подходящей реализации.

Если подходящих реализаций несколько и выбор не задан, сборка завершится ошибкой. Обычно я явно задаю alias:

```yaml
App\Contracts\OrderRepository:
    alias: App\Infrastructure\DoctrineOrderRepository
```

Для скаляров одного типа недостаточно:

```php
final class ApiClient
{
    public function __construct(private string $baseUrl) {}
}
```

Значение нужно настроить:

```yaml
App\ApiClient:
    arguments:
        $baseUrl: '%env(API_BASE_URL)%'
```

**Autowiring происходит при сборке**, а не через reflection при каждом получении сервиса. При этом сами значения environment variables могут разрешаться уже во время выполнения.

Отдельно: **autoconfigure — не autowire**. Autoconfigure автоматически добавляет теги и другую конфигурацию по интерфейсам или атрибутам, а autowire разрешает зависимости.

## 3. Что происходит при первом запросе сервиса

Предположим, Symfony понадобился `CreateOrderHandler`. Скомпилированный контейнер выполняет код, концептуально похожий на такой:

```php
return $this->services[CreateOrderHandler::class]
    ??= new CreateOrderHandler(
        $this->getOrderRepository(),
        $this->getLogger(),
    );
```

Это иллюстрация: реальный сгенерированный код может использовать отдельные файлы, фабрики и встроенные определения.

При первом получении:

1. Контейнер проверяет, создан ли сервис.
2. Если нет — получает или создаёт его зависимости.
3. Вызывает конструктор либо фабрику.
4. Выполняет настроенные вызовы методов.
5. Сохраняет экземпляр, если сервис **shared**.

По умолчанию сервисы shared: последующие получения возвращают тот же экземпляр **в рамках данного контейнера**, а не глобальный singleton на всё приложение.

Для `shared: false` каждое получение создаёт новый экземпляр.

### Private и lazy — отдельные свойства

- **Private-сервис** нельзя напрямую получить через обычный `$container->get()`, но его можно внедрить в другой сервис. Он может быть встроен или удалён при оптимизации.
- **Lazy-сервис** при получении может быть представлен lazy-объектом или прокси: реальная инициализация откладывается до использования. Конкретный механизм зависит от версии Symfony и PHP.

То есть по умолчанию сервисы создаются **по необходимости**, но зависимости запрошенного сервиса обычно создаются сразу. `lazy` позволяет отложить и их инициализацию.

Итого: **при компиляции Symfony решает, что и как создавать; при выполнении сгенерированный контейнер создаёт нужные объекты и управляет повторным использованием экземпляров**.

### ↳ Углубление

**Интервьюер:** Как разруливаешь циклические зависимости между сервисами?

**Кандидат:**

Сначала выясняю, **это архитектурный цикл или действительно необходимая отложенная связь**. Обычно цикл — сигнал, что ответственности смешаны:

```text
OrderService → PaymentService → OrderService
```

Symfony обычно обнаруживает цикл прямых зависимостей при компиляции контейнера. Но если связь отложена через lazy-сервис или locator, ошибка может проявиться позже — либо превратиться в бесконечную рекурсию вызовов.

## 1. Выношу координацию в отдельный сценарий

Например, `OrderService` вызывает оплату, а `PaymentService` обращается обратно к нему, чтобы изменить заказ.

Вместо взаимной зависимости делаю отдельный обработчик:

```php
final class PayOrderHandler
{
    public function __construct(
        private OrderRepository $orders,
        private PaymentGateway $payments,
    ) {}

    public function handle(OrderId $id): void
    {
        $order = $this->orders->get($id);
        $order->assertCanBePaid();

        $receipt = $this->payments->charge(
            PaymentRequest::fromOrder($order)
        );

        $order->markPaid($receipt->id);
        $this->orders->save($order);
    }
}
```

Теперь граф направлен в одну сторону:

```text
PayOrderHandler → OrderRepository
                → PaymentGateway
```

Платёжный адаптер не управляет заказом, а возвращает результат. В реальном платёжном сценарии отдельно решаю вопросы идемпотентности и согласования состояния: транзакция БД не откатит внешний платёж.

## 2. Выделяю более узкую зависимость

Иногда сервису нужен не весь другой сервис, а только данные или общая политика.

Например:

```text
OrderService → PaymentService → OrderService
```

Если оплате нужна лишь информация о заказе, можно передать её аргументом:

```php
$payments->charge($order->id(), $order->total());
```

Либо выделить независимый `OrderReader` или `PricingPolicy`, если это действительно отдельная ответственность.

**Замена класса интерфейсом сама по себе цикл не устраняет**: если интерфейс разрешается в тот же сервис, граф остаётся прежним.

## 3. Использую события для независимой реакции

Если обратная связь нужна для дополнительного действия, например уведомления после оплаты:

```text
Оплата → PaymentSucceeded → Отправка уведомления
```

Издатель не зависит напрямую от подписчика. Но события не являются автоматическим лекарством:

- синхронные обработчики могут сохранить скрытую связанность;
- события могут образовать логический цикл;
- асинхронная обработка требует учёта повторных доставок и согласованности данных.

Обязательные шаги одного сценария предпочитаю оставлять явными.

## 4. Отложенное получение — только при обоснованной необходимости

В инфраструктурных механизмах, например реестрах обработчиков, допустим **узкий service locator**, фабрика или lazy-зависимость. Они позволяют отложить получение объекта.

Но это **разрыв цепочки создания, а не исправление архитектурного цикла**. Если `A` вызывает `B`, а `B` снова вызывает `A`, lazy-прокси не решит проблему.

Поэтому я не использую как стандартный обход:

- внедрение всего контейнера;
- setter injection только ради устранения ошибки компиляции;
- `lazy: true` без понимания последовательности вызовов.

**Мой порядок действий:** сначала вынести координацию, затем сузить зависимости или передать данные аргументами; события и отложенное получение применять только там, где они соответствуют смыслу взаимодействия.

## Q06 · Symfony

**Интервьюер:** Представь: после успешной регистрации пользователя нужно отправить письмо и обновить поисковый индекс, и это не должно замедлять ответ пользователю. Как организуешь это в Symfony-приложении? Опиши возможные варианты и их trade-offs.

**Кандидат:**

Я бы отделил **успешную регистрацию** от **побочных действий**: пользователя сохраняем синхронно, письмо и индексирование выполняем фоновыми воркерами через Symfony Messenger.

Главный вопрос здесь не только скорость: **допустимо ли потерять задачу между сохранением пользователя и отправкой сообщения в очередь?**

## 1. Базовый вариант: Messenger с асинхронным transport

После сохранения пользователя отправляем два сообщения:

```php
final readonly class SendWelcomeEmail
{
    public function __construct(public string $userId) {}
}

final readonly class IndexUser
{
    public function __construct(public string $userId) {}
}
```

```php
$user = User::register($command->email);
$this->users->save($user); // Предполагаем, что изменения уже закоммичены.

$this->bus->dispatch(new SendWelcomeEmail($user->id()->value));
$this->bus->dispatch(new IndexUser($user->id()->value));
```

Важно настроить routing: **сам по себе `dispatch()` не означает асинхронное выполнение**.

```yaml
framework:
    messenger:
        failure_transport: failed

        transports:
            notifications:
                dsn: '%env(MESSENGER_NOTIFICATIONS_DSN)%'
                retry_strategy:
                    max_retries: 5
                    delay: 1000
                    multiplier: 2

            search:
                dsn: '%env(MESSENGER_SEARCH_DSN)%'
                retry_strategy:
                    max_retries: 5
                    delay: 1000
                    multiplier: 2

            failed: 'doctrine://default?queue_name=failed'

        routing:
            App\Message\SendWelcomeEmail: notifications
            App\Message\IndexUser: search
```

Обработчик выполняется отдельным процессом:

```php
#[AsMessageHandler]
final class IndexUserHandler
{
    public function __construct(
        private UserRepository $users,
        private UserSearchIndex $index,
    ) {}

    public function __invoke(IndexUser $message): void
    {
        $user = $this->users->get(new UserId($message->userId));

        $this->index->upsert($user);
    }
}
```

Воркеры запускаются через Supervisor, systemd или оркестратор:

```bash
php bin/console messenger:consume notifications search
```

**Плюсы:** простота, быстрый ответ, независимые retries для письма и индекса.

**Минус:** есть окно потери сообщения:

```text
Пользователь сохранён → процесс упал → сообщение не отправлено
```

Если брокер недоступен, регистрация уже состоялась, но `dispatch()` может завершиться ошибкой. Просто вернуть клиенту `500` опасно: он может повторить регистрацию.

## 2. Надёжный вариант: transactional outbox

Для production-сценария с требованием не терять задачи я обычно выбираю outbox:

```php
$this->transactions->run(function () use ($command): void {
    $user = User::register($command->email);

    $this->users->save($user);

    $this->outbox->append(
        new UserRegistered(
            eventId: $this->ids->generate(),
            userId: $user->id()->value,
        )
    );
});
```

**Пользователь и событие сохраняются в одной транзакции одной БД.** После commit возвращаем ответ. Отдельный relay читает outbox и публикует задачи в Messenger.

Далее можно получить две независимые задачи: отправку письма и обновление индекса.

**Плюсы:**
- нет разрыва между сохранением пользователя и фиксацией намерения выполнить фоновые действия;
- недоступность брокера не мешает регистрации;
- события можно доставить позже.

**Минусы:**
- дополнительная таблица и процесс доставки;
- нужны очистка outbox, мониторинг задержек и безопасная конкурентная обработка;
- возможны дубликаты: relay может опубликовать сообщение и упасть до отметки об отправке.

Outbox даёт надёжную фиксацию события, но не гарантирует «ровно один раз» для внешних эффектов.

## 3. Практичный компромисс: Doctrine transport

Если отдельный брокер пока не нужен, можно хранить сообщения Messenger в PostgreSQL.

При правильной настройке **на том же DBAL connection и внутри той же транзакции** запись пользователя и постановка сообщений могут быть атомарными. Важно проверить это явно: использование одной БД само по себе ещё не означает общую транзакцию.

**Плюсы:** меньше инфраструктуры, надёжная постановка задач вместе с регистрацией.

**Минусы:** очередь нагружает основную БД, требует polling и обслуживания; для больших потоков внешний брокер может быть удобнее.

## 4. События Symfony — не замена очереди

Обычный `EventDispatcher` вызывает подписчиков синхронно. Если подписчик отправляет письмо или обращается к поиску, ответ всё равно замедляется.

Подписчик может **поставить задачу в Messenger**, но тогда гарантии определяются способом постановки: прямой dispatch, общая транзакция или outbox.

Также я не считаю `kernel.terminate` надёжным фоновым механизмом: ответ иногда уже отправлен клиенту, но PHP-процесс продолжает работу, занимает worker и может упасть без сохранённой задачи и retries.

## Что обязательно учесть

- **Повторная доставка.** Для индекса — `upsert` по ID пользователя; при конкурирующих обновлениях может понадобиться версия документа.
- **Дубли писем.** ID события и журнал отправок помогают, но между отправкой письма и записью результата остаётся окно сбоя; лучше использовать idempotency key провайдера, если он поддерживается.
- **Отдельные задачи.** Ошибка поиска не должна приводить к повторной отправке уже отправленного письма.
- **Retries и failed transport.** Временные ошибки повторяем с backoff, постоянные — отправляем на разбор.
- **Eventual consistency.** Пользователь зарегистрирован сразу, но появится в поиске чуть позже.
- **Наблюдаемость.** Контролируем возраст сообщений, размер очереди, число повторов и ошибки.
- **Состав сообщения.** Обычно передаю ID и необходимые стабильные данные, а не Doctrine entity; чувствительные данные минимизирую.

**Итого:** для небольшого приложения — Messenger с Doctrine transport и общей транзакцией; при внешнем брокере и требовании не терять действия — transactional outbox плюс Messenger. Прямой dispatch после commit допустим, только если риск потери задач принят или предусмотрено восстановление.

## Q07 · Symfony

**Интервьюер:** Как в Symfony устроен контроль доступа: аутентификация, роли, voters? В каких случаях выбираешь voter, а в каких достаточно ролей?

**Кандидат:**

В Symfony я разделяю **аутентификацию — кто пользователь** и **авторизацию — что ему разрешено**.

## 1. Аутентификация

За неё отвечает firewall и настроенные для него механизмы: `form_login`, `json_login`, access token или собственный authenticator.

Упрощённо процесс такой:

1. Symfony выбирает подходящий firewall — обычно первый совпавший по запросу.
2. Authenticator извлекает credentials.
3. Через `Passport`, `UserBadge` и механизм проверки credentials определяется пользователь.
4. После успешной проверки создаётся security token с пользователем и его ролями.

Для обычного веб-приложения аутентификация может сохраняться в сессии. Для API часто используют `stateless: true`: каждый запрос должен самостоятельно предоставить credentials.

**Firewall сам по себе не означает запрет доступа:** ограничения задаются отдельно.

## 2. Роли и `access_control`

Роли удобны для крупных категорий доступа: администратор, оператор, пользователь.

```yaml
security:
    role_hierarchy:
        ROLE_ADMIN: ROLE_USER

    access_control:
        - { path: ^/login$, roles: PUBLIC_ACCESS }
        - { path: ^/admin, roles: ROLE_ADMIN }
        - { path: ^/account, roles: ROLE_USER }
```

В `access_control` действует **первое совпавшее правило**, поэтому порядок важен.

Доступ можно проверить и в контроллере:

```php
#[IsGranted('ROLE_ADMIN')]
public function dashboard(): Response
{
    // ...
}
```

Или программно:

```php
$this->denyAccessUnlessGranted('ROLE_ADMIN');
```

Проверку через Security предпочитаю ручному:

```php
in_array('ROLE_ADMIN', $user->getRoles(), true);
```

Ручная проверка не учитывает иерархию ролей.

## 3. Voters: доступ к конкретному объекту

Когда разрешение зависит не только от роли, но и от ресурса или контекста, использую voter.

Например: редактировать заказ может его владелец, если заказ ещё черновик.

```php
final class OrderVoter extends Voter
{
    public const EDIT = 'ORDER_EDIT';

    protected function supports(
        string $attribute,
        mixed $subject,
    ): bool {
        return $attribute === self::EDIT
            && $subject instanceof Order;
    }

    protected function voteOnAttribute(
        string $attribute,
        mixed $subject,
        TokenInterface $token,
    ): bool {
        $user = $token->getUser();

        if (!$user instanceof User) {
            return false;
        }

        return $subject->ownerId()->equals($user->id())
            && $subject->status() === OrderStatus::Draft;
    }
}
```

Проверка в контроллере:

```php
$order = $orders->get($id);

$this->denyAccessUnlessGranted(OrderVoter::EDIT, $order);
```

Voter регистрируется как сервис; при включённом autoconfiguration Symfony добавляет необходимый тег.

### Как принимается решение

Проверка `isGranted()` поступает в **AccessDecisionManager**, который опрашивает voters. Каждый может:

- разрешить;
- запретить;
- воздержаться, если атрибут или объект ему не подходят.

Результат объединяется выбранной стратегией. По умолчанию обычно используется `affirmative`: хотя бы одного разрешающего голоса достаточно. Есть также `unanimous`, `consensus` и `priority`.

Это важно: **запрет одного voter не обязательно перекрывает разрешение другого**. Поэтому я стараюсь не создавать несколько независимых voters с пересекающимися атрибутами без явно продуманной стратегии.

Проверка ролей, кстати, тоже реализована через voters — роли и объектные voters не являются двумя изолированными механизмами.

## Когда чего достаточно

| Ситуация | Выбор |
|---|---|
| Админ-панель доступна только администраторам | Роль |
| Endpoint доступен всем аутентифицированным пользователям | `IS_AUTHENTICATED` |
| Редактирование только собственных заказов | Voter |
| Доступ зависит от tenant, членства в проекте или ACL | Voter |
| Действие зависит от сочетания роли и состояния объекта | Voter |

**Роли дают грубый уровень доступа, voter — контекстное решение о конкретном действии.** Часто использую оба: роль допускает пользователя в раздел, voter проверяет выбранный ресурс.

## Практические нюансы

- Скрыть кнопку в Twig через `is_granted()` недостаточно — проверка обязательно должна быть на сервере.
- Voter не заменяет доменные инварианты: даже авторизованный пользователь не должен обходить бизнес-правила.
- Voters желательно оставлять без побочных эффектов и дорогих запросов.
- Для списков лучше фильтровать доступные записи в запросе, а не загружать тысячи объектов и проверять каждый voter.
- Для неаутентифицированного пользователя отказ может привести к запуску authentication entry point — например, редиректу на login или ответу `401`; для аутентифицированного без прав обычно возвращается `403`.

Мой критерий простой: **если решение можно принять по категории пользователя — роли; если нужно посмотреть на объект и отношения пользователя с ним — voter**.

## Q08 · Doctrine

**Интервьюер:** Как в Doctrine хранить Value Object, если домен требует от него неизменяемости и всегда валидного состояния? Какие есть способы маппинга, их плюсы, минусы и подводные камни?

**Кандидат:**

Я разделяю два требования:

1. **Доменное:** Value Object создаётся только валидным и не меняется после создания.
2. **Инфраструктурное:** Doctrine должна восстановить его из данных БД и заметить замену значения.

Главная ловушка: **обычная ORM-гидратация не вызывает конструктор объекта**, поэтому инварианты, проверяемые только конструктором, не обязательно проверяются при загрузке.

Возьмём VO:

```php
final readonly class Money
{
    public function __construct(
        public int $amountInMinorUnits,
        public string $currency,
    ) {
        if ($amountInMinorUnits < 0) {
            throw new \InvalidArgumentException('Negative amount');
        }

        if (!in_array($currency, ['EUR', 'USD'], true)) {
            throw new \InvalidArgumentException('Unsupported currency');
        }
    }
}
```

Владелец заменяет значение целиком, а не изменяет его части:

```php
public function changePrice(Money $price): void
{
    $this->price = $price;
}
```

## 1. Embeddable: несколько колонок

Естественный вариант для структурного VO:

```php
#[ORM\Embeddable]
final readonly class Money
{
    public function __construct(
        #[ORM\Column(type: 'integer')]
        public int $amountInMinorUnits,

        #[ORM\Column(type: 'string', length: 3)]
        public string $currency,
    ) {
        // Проверка инвариантов.
    }
}
```

```php
#[ORM\Entity]
class Product
{
    #[ORM\Embedded(class: Money::class, columnPrefix: 'price_')]
    private Money $price;
}
```

В таблице получатся `price_amountInMinorUnits` и `price_currency` — имена лучше задать явно, если важна стабильная схема.

**Плюсы:**
- нормальные типизированные колонки;
- удобно фильтровать, сортировать и индексировать;
- VO остаётся частью владельца, без собственной идентичности.

**Минусы и нюансы:**
- Doctrine восстанавливает объект через механизм гидратации, **не через валидирующий конструктор**;
- поддержка конкретных сценариев с `readonly` зависит от версии ORM и PHP — проверяю интеграционными тестами;
- nullable embeddable и частично заполненные колонки требуют отдельного внимания;
- маппинг связывает доменную модель с ORM, если атрибуты размещены непосредственно в ней.

Поэтому добавляю ограничения в БД:

```sql
CHECK (price_amount >= 0),
CHECK (price_currency IN ('EUR', 'USD'))
```

Это защищает от некорректных записей, но не отменяет проверку доменных инвариантов.

**Вывод:** embeddable удобен, но сам по себе не гарантирует создание VO через его публичный контракт.

## 2. Собственный DBAL Type: одна колонка

Подходит для VO, который естественно представляется одним значением: email, UUID, артикул.

```php
final readonly class EmailAddress
{
    public function __construct(public string $value)
    {
        if (filter_var($value, FILTER_VALIDATE_EMAIL) === false) {
            throw new \InvalidArgumentException('Invalid email');
        }
    }
}
```

В собственном типе реализую преобразования, концептуально:

```php
public function convertToPHPValue(
    mixed $value,
    AbstractPlatform $platform,
): ?EmailAddress {
    if ($value === null) {
        return null;
    }

    return new EmailAddress((string) $value);
}

public function convertToDatabaseValue(
    mixed $value,
    AbstractPlatform $platform,
): ?string {
    if ($value === null) {
        return null;
    }

    if (!$value instanceof EmailAddress) {
        throw new \InvalidArgumentException('Expected EmailAddress');
    }

    return $value->value;
}
```

Остальная реализация типа и его регистрация зависят от версии DBAL.

**Плюсы:**
- при загрузке вызывается конструктор VO;
- преобразование централизовано;
- доменный объект не обязан знать о Doctrine.

**Минусы:**
- custom type отображает значение в **одну колонку**, а не раскладывает его по нескольким;
- для составного VO приходится выбирать JSON или другой формат, что усложняет запросы;
- при использовании VO в параметрах запросов иногда нужно явно указывать DBAL type;
- тип не должен зависеть от сервисов или контекста текущего пользователя.

Если в БД лежит невалидное значение, загрузка завершится ошибкой. Я считаю это правильным: лучше явно обнаружить повреждённые данные, чем создать невалидный доменный объект.

## 3. Скалярные поля в ORM-модели, VO на доменной границе

Можно хранить сумму и валюту как скаляры, а VO собирать вручную:

```php
public function price(): Money
{
    return new Money(
        $this->priceAmount,
        $this->priceCurrency,
    );
}

public function changePrice(Money $price): void
{
    $this->priceAmount = $price->amountInMinorUnits;
    $this->priceCurrency = $price->currency;
}
```

**Плюсы:** простой маппинг, удобные SQL-запросы, конструктор проверяет VO.

**Минусы:** сама ORM-сущность может содержать некорректные скаляры до вызова `price()`. Поэтому это компромисс, а не полная гарантия всегда валидного состояния доменной сущности.

Если требование строгое, я разделяю **persistence-модель и доменную модель**. Репозиторий читает скаляры и явно реконструирует домен через конструкторы или фабрики.

Это даёт наиболее явный контроль, но требует больше кода преобразования.

## 4. JSON как формат хранения

Для сложного значения, по которому почти не нужно искать, возможен JSON. Но стандартный Doctrine `json` возвращает массивы и скаляры, **не экземпляр VO**.

Для восстановления объекта нужен custom type или явный mapper.

**Trade-offs:**
- гибкая структура;
- сложнее ограничения и индексы;
- нужны правила версионирования формата;
- изменение доменного класса не должно автоматически ломать старые записи.

Нативную сериализацию PHP для долговременного хранения обычно не выбираю: она слишком сильно связывает данные со структурой классов.

## Подводные камни неизменяемости

- **`readonly` — не валидация:** он запрещает повторное присваивание, но не проверяет смысл значения.
- **`readonly` не обеспечивает глубокую неизменяемость:** вложенные объекты тоже должны быть неизменяемыми.
- **Изменения делаем заменой VO:** это особенно важно для custom types, где нельзя рассчитывать на отслеживание внутренних мутаций объекта.
- При ужесточении инвариантов старые записи могут перестать загружаться — нужна миграция данных.
- `PostLoad`-валидация возможна, но я не использую её как основной способ обеспечить корректность модели: ошибка обнаруживается уже после гидратации.

**Мой выбор:** одноколоночный VO — custom DBAL Type; составной и активно используемый в запросах — embeddable с ограничениями БД. Если обязательно, чтобы любой восстановленный доменный объект прошёл валидирующее создание, — явный mapper и отдельная persistence-модель.

## Q09 · Doctrine

**Интервьюер:** Доменный агрегат состоит из корня и коллекции дочерних сущностей. Как организовать его хранение через Doctrine: маппинг коллекций, границы транзакции, кто и когда вызывает flush? Разбери на примере по твоему выбору.

**Кандидат:**

Возьму агрегат **Order → OrderLine**: заказ — корень, строки заказа — дочерние сущности. Инвариант: оплаченный заказ нельзя менять, количество в строке должно быть положительным.

Основной принцип: **все изменения строк проходят через корень, сохраняется агрегат через репозиторий заказа, а транзакцией управляет прикладной сценарий**.

## 1. Маппинг коллекции

```php
#[ORM\Entity]
#[ORM\Table(name: 'orders')]
class Order
{
    #[ORM\Id]
    #[ORM\Column(type: 'guid')]
    private string $id;

    #[ORM\Column(enumType: OrderStatus::class)]
    private OrderStatus $status = OrderStatus::Draft;

    /** @var Collection<int, OrderLine> */
    #[ORM\OneToMany(
        mappedBy: 'order',
        targetEntity: OrderLine::class,
        cascade: ['persist'],
        orphanRemoval: true,
    )]
    private Collection $lines;

    public function __construct(string $id)
    {
        $this->id = $id;
        $this->lines = new ArrayCollection();
    }

    public function addLine(string $productId, int $quantity): void
    {
        $this->assertEditable();

        $this->lines->add(
            new OrderLine($this, $productId, $quantity)
        );
    }

    public function removeLine(string $lineId): void
    {
        $this->assertEditable();

        foreach ($this->lines as $line) {
            if ($line->id() === $lineId) {
                $this->lines->removeElement($line);

                return;
            }
        }

        throw new OrderLineNotFound($lineId);
    }

    private function assertEditable(): void
    {
        if ($this->status !== OrderStatus::Draft) {
            throw new OrderCannotBeChanged();
        }
    }
}
```

```php
#[ORM\Entity]
class OrderLine
{
    #[ORM\Id]
    #[ORM\Column(type: 'guid')]
    private string $id;

    #[ORM\ManyToOne(targetEntity: Order::class, inversedBy: 'lines')]
    #[ORM\JoinColumn(nullable: false)]
    private Order $order;

    #[ORM\Column]
    private string $productId;

    #[ORM\Column]
    private int $quantity;

    public function __construct(
        Order $order,
        string $productId,
        int $quantity,
    ) {
        if ($quantity <= 0) {
            throw new \InvalidArgumentException('Quantity must be positive');
        }

        $this->id = Uuid::v7()->toRfc4122();
        $this->order = $order;
        $this->productId = $productId;
        $this->quantity = $quantity;
    }

    public function id(): string
    {
        return $this->id;
    }
}
```

Импорты и часть методов здесь опущены.

### Что важно в этом маппинге

- `Order::$lines` — **inverse side**, `OrderLine::$order` — **owning side**. Именно owning side определяет значение внешнего ключа.
- При добавлении строки устанавливаю обе стороны связи: строка получает заказ в конструкторе, заказ добавляет её в коллекцию.
- `cascade: ['persist']` позволяет сохранять новые строки через корень.
- `orphanRemoval: true` удаляет строку из БД после исключения из коллекции. Это подходит, потому что строка принадлежит только одному заказу и не переносится между агрегатами.
- Удаление всего заказа — отдельное решение: ORM cascade remove или `ON DELETE CASCADE` в БД, с учётом того, нужны ли callbacks дочерних сущностей.

В примере удалённая строка не используется повторно. Если модель допускает отвязку или перенос дочерних сущностей, нужны другие правила и корректная синхронизация обеих сторон.

**Изменяемую Doctrine-коллекцию наружу не отдаю**, иначе вызывающий код сможет обойти инварианты корня. Для чтения можно вернуть массив или отдельное представление.

## 2. Репозиторий — только для корня

```php
interface OrderRepository
{
    public function get(string $id): Order;

    public function add(Order $order): void;
}
```

```php
final class DoctrineOrderRepository implements OrderRepository
{
    public function __construct(private EntityManagerInterface $em) {}

    public function add(Order $order): void
    {
        $this->em->persist($order);
    }

    public function get(string $id): Order
    {
        return $this->em->find(Order::class, $id)
            ?? throw new OrderNotFound($id);
    }
}
```

Отдельного репозитория `OrderLineRepository` для изменения строк обычно нет: он позволил бы обойти корень.

Для уже загруженного managed-заказа повторный `persist()` не нужен: Unit of Work отслеживает изменения, а новые строки обнаруживаются через cascade persist.

## 3. Кто вызывает `flush()`

**Не сущность и обычно не отдельный метод репозитория.** `flush()` вызывается на границе прикладного сценария — через transaction manager, middleware или явный orchestration-код.

Например, с Doctrine:

```php
$this->em->wrapInTransaction(function () use ($command): void {
    $order = $this->orders->get($command->orderId);

    $order->addLine(
        $command->productId,
        $command->quantity,
    );
});
```

`EntityManager::wrapInTransaction()` открывает транзакцию, выполняет callback, вызывает `flush()` и затем commit. В прикладном слое я обычно скрываю этот механизм за своим `TransactionManager`.

Это отличается от DBAL transaction helper: **DBAL сам по себе ORM `flush()` не делает**.

При `flush()` Doctrine:

1. Вычисляет изменения managed-сущностей и коллекций.
2. Находит новые сущности через cascade persist.
3. Формирует `INSERT`, `UPDATE`, `DELETE`.
4. Выполняет SQL.

Важно: `flush()` синхронизирует **весь текущий Unit of Work**, а не только один заказ. Поэтому EntityManager не должен бесконтрольно накапливать изменения из независимых сценариев.

## 4. Граница транзакции

Обычно один command handler — одна транзакция:

```text
Загрузить заказ → проверить правила → изменить → flush → commit
```

Нельзя делать `flush()` после каждой добавленной строки: это дробит атомарность и создаёт лишние запросы.

Сам `flush()` способен выполнить накопленные изменения в транзакции, но если нужно включить в неё чтение, блокировку и другие действия, транзакцию открываю явно.

Внешний HTTP-вызов не становится атомарным вместе с БД. Для публикации событий после изменений использую outbox, записанный в той же транзакции.

## 5. Конкурентные изменения

Одна транзакция не защищает автоматически от двух параллельных изменений агрегата.

Возможные решения:

- **Optimistic lock** с version-полем.
- **Pessimistic lock** корня внутри транзакции.
- Ограничения БД для правил, которые можно выразить декларативно.

Тонкость: **изменение только дочерней строки не обязательно вызывает `UPDATE` корня**, поэтому version-поле на `Order` само по себе не гарантирует контроль всех изменений агрегата. Нужно обеспечить изменение версии корня при каждой агрегатной операции либо выбрать другую стратегию блокировки.

## 6. Размер коллекции

Lazy loading помогает отложить загрузку, но не отменяет цену проверки инвариантов: обход `lines` обычно загрузит коллекцию.

Если у корня сотни тысяч дочерних объектов, я пересматриваю границу агрегата. `EXTRA_LAZY` ускоряет отдельные операции вроде `count()`, но не делает огромный агрегат дешёвым для произвольных изменений.

**Итого:** корень контролирует дочерние сущности, owning side корректно задаёт связь, каскады сохраняют граф, а один `flush()` на границе сценария фиксирует изменения. Отдельно проектируются удаление, конкурентный доступ и размер агрегата.

## Q10 · Doctrine

**Интервьюер:** Страница приложения тормозит, есть подозрение на проблему N+1 запросов в Doctrine. Как ты диагностируешь проблему и какие способы решения знаешь? Опиши trade-offs каждого способа.

**Кандидат:**

Я бы сначала подтвердил, что проблема именно в N+1, а не в одном тяжёлом запросе, отсутствии индекса или внешнем сервисе.

**N+1** — это когда один запрос получает список сущностей, а затем обращение к связи для каждой сущности вызывает дополнительный запрос:

```php
$orders = $orderRepository->findBy([], limit: 50);

foreach ($orders as $order) {
    echo $order->customer()->name(); // Возможны ещё 50 SELECT.
}
```

Это может происходить незаметно в Twig, сериализаторе или getter, который обходит коллекцию.

## 1. Диагностика

В dev-окружении использую **Symfony Profiler → Doctrine**:

- количество запросов и суммарное время;
- повторяющиеся SQL с разными параметрами;
- место выполнения — через сбор backtrace, если он включён;
- запросы, появившиеся именно во время рендеринга или сериализации.

Характерный рисунок:

```sql
SELECT ... FROM orders LIMIT 50;
SELECT ... FROM customers WHERE id = ?;
SELECT ... FROM customers WHERE id = ?;
-- ...
```

Проверяю, как количество запросов меняется при размере страницы 10, 20, 50. Если растёт примерно линейно — это хороший признак N+1.

При этом **identity map может уменьшить число запросов**: если несколько заказов ссылаются на одного клиента, Doctrine обычно не загружает его заново в рамках одного EntityManager.

В production использую APM, трассировку и выборочное логирование SQL. Подробный SQL-лог постоянно включать не стоит: это накладные расходы и риск утечки данных.

После устранения N+1 отдельно проверяю тяжёлые запросы через `EXPLAIN ANALYZE`: меньше запросов не всегда означает быстрее.

## 2. Fetch join

Для списка заказов с клиентами:

```php
return $this->createQueryBuilder('o')
    ->leftJoin('o.customer', 'c')
    ->addSelect('c')
    ->setMaxResults(50)
    ->getQuery()
    ->getResult();
```

**Важно:** просто `join()` не обязательно загрузит связанную сущность. `addSelect('c')` делает этот join fetch join.

### Trade-offs

Для связи **to-one** это обычно хорошее решение:

- один запрос;
- связь уже загружена;
- корневые строки не размножаются.

Для **to-many** сложнее:

```php
->leftJoin('o.lines', 'l')
->addSelect('l')
```

- заказ повторяется в SQL-результате для каждой строки;
- растут объём передачи и стоимость гидратации;
- несколько коллекций могут дать декартово произведение;
- обычный `LIMIT` ограничивает SQL-строки, а не число заказов.

Для пагинации с collection fetch join использую Doctrine `Paginator` с подходящими настройками либо двухэтапную загрузку: сначала ID страницы, затем данные этих заказов. `Paginator` обеспечивает корректность во многих типовых случаях, но может выполнять дополнительные запросы и требует проверки на сложных DQL.

## 3. Пакетная загрузка

Вместо запроса на каждую сущность делаю несколько запросов:

```text
1. Получить страницу заказов.
2. Получить клиентов по списку customer_id.
3. Получить строки по списку order_id.
```

Затем собираю результат по ID либо использую второй fetch-join запрос для выбранных корней.

**Плюсы:**
- фиксированное число запросов;
- нет огромного произведения нескольких коллекций;
- удобно сочетать с пагинацией.

**Минусы:**
- больше кода;
- большие `IN (...)` нужно разбивать на части;
- запросы могут увидеть разные состояния данных;
- важно понимать гидратацию: **загрузка дочерних сущностей отдельным запросом не гарантирует инициализацию коллекций у родителей**. Для read model проще явно сгруппировать данные.

## 4. DTO или скалярная проекция

Для страницы часто не нужен полный доменный граф:

```php
$rows = $this->createQueryBuilder('o')
    ->select('o.id AS id', 'c.name AS customerName')
    ->leftJoin('o.customer', 'c')
    ->setMaxResults(50)
    ->getQuery()
    ->getArrayResult();
```

Для числа строк заказа можно добавить агрегатный запрос, вместо загрузки всей коллекции.

**Плюсы:**
- получаем только нужные поля;
- меньше памяти и стоимости гидратации;
- Twig и сериализатор не смогут случайно инициировать lazy loading.

**Минусы:**
- отдельная модель чтения и запрос;
- результат не предназначен для изменения через Unit of Work;
- усложнение запросов при множестве агрегатов.

Для насыщенных списковых страниц это часто мой основной выбор.

## 5. EAGER loading

Можно настроить eager fetch в маппинге или для конкретного запроса.

**Плюс:** связь загружается заранее.

**Минусы:**
- поведение затрагивает места, где связь не нужна;
- возможна избыточная загрузка;
- **EAGER не гарантирует один SQL-запрос** — стратегия зависит от связи и способа загрузки.

Поэтому глобальный `fetch: 'EAGER'` не использую как универсальное лекарство. Предпочитаю выбирать граф загрузки под конкретный сценарий.

## 6. EXTRA_LAZY для больших коллекций

Если странице нужны только количество элементов или ограниченный срез, `EXTRA_LAZY` позволяет некоторым операциям обходиться без полной загрузки коллекции.

**Плюсы:** меньше объектов и памяти.

**Минусы:** если вызвать `count()` для каждого из 50 заказов, можно получить те же 50 отдельных запросов. Для списка обычно лучше один агрегатный запрос. А обычный обход коллекции всё равно её загрузит.

## 7. Кеширование

Result cache, second-level cache или кеш готовой read model могут уменьшить число обращений к БД.

Но это **дополнение, а не исправление плохого графа загрузки**:

- холодный кеш сохраняет проблему;
- нужна инвалидация;
- возможны устаревшие данные;
- query cache Doctrine кеширует разбор запроса, а не его результат.

## Как выбираю

- Список с несколькими **to-one** связями → fetch join.
- Пагинация и несколько **to-many** коллекций → пакетная загрузка или read model.
- Только счётчики и суммы → агрегатные запросы.
- Полноценный доменный сценарий → загрузка необходимого графа агрегата, без лишних связей.

После исправления сравниваю **число запросов, общее время, память и размер результата** на реалистичных данных. И добавляю регрессионную проверку: например, число запросов не должно расти линейно с числом элементов страницы.

## Q11 · PostgreSQL

**Интервьюер:** Вся бизнес-валидация делается в коде приложения. Зачем тогда ограничения целостности на уровне базы данных в PostgreSQL? Какие средства для этого используешь и в каких случаях?

**Кандидат:**

Потому что **проверка в приложении и гарантия целостности в БД решают разные задачи**.

Приложение проверяет правила и даёт понятную ошибку пользователю. База гарантирует, что недопустимое состояние не сохранится — независимо от конкурентных запросов, багов, миграций, импорта или другого приложения.

## Главный пример — конкурентная регистрация

Проверка в коде:

```php
if ($users->existsByEmail($email)) {
    throw new EmailAlreadyUsed();
}

$users->add(User::register($email));
```

Не гарантирует уникальность:

```text
Запрос A: email свободен
Запрос B: email свободен
Запрос A: INSERT
Запрос B: INSERT
```

Нужен уникальный constraint или индекс. Проверку в приложении можно оставить для удобства, но **окончательное решение принимает БД**.

## Какие средства использую

### 1. `NOT NULL` — обязательность значения

```sql
email text NOT NULL
```

Применяю, когда отсутствие значения недопустимо в сохранённом состоянии.

Но `NOT NULL` не запрещает пустую строку — это отдельное правило.

### 2. `CHECK` — условия внутри строки

```sql
CREATE TABLE order_lines (
    id uuid PRIMARY KEY,
    quantity integer NOT NULL CHECK (quantity > 0),
    unit_price_minor bigint NOT NULL CHECK (unit_price_minor >= 0)
);
```

Также подходит для взаимосвязанных полей:

```sql
CHECK (finished_at IS NULL OR finished_at >= started_at)
```

**Ловушка:** `CHECK` запрещает результат `false`, но пропускает `NULL`. Поэтому:

```sql
quantity integer CHECK (quantity > 0)
```

всё ещё допускает `NULL`.

`CHECK` не использую для проверки других строк или таблиц: PostgreSQL не обеспечивает через него корректную поддержку таких межстрочных правил.

### 3. `UNIQUE` и уникальные индексы — отсутствие дублей

```sql
ALTER TABLE users
    ADD CONSTRAINT users_email_unique UNIQUE (email);
```

Если email по правилам проекта сравнивается без учёта регистра:

```sql
CREATE UNIQUE INDEX users_email_ci_unique
    ON users (lower(email));
```

Правила нормализации в приложении должны соответствовать правилам индекса.

Для условной уникальности использую partial index:

```sql
CREATE UNIQUE INDEX one_active_subscription_per_user
    ON subscriptions (user_id)
    WHERE status = 'active';
```

По умолчанию `UNIQUE` допускает несколько `NULL`. В PostgreSQL 15+ можно использовать `UNIQUE NULLS NOT DISTINCT`, если `NULL` должен считаться одинаковым значением.

### 4. `FOREIGN KEY` — существование связанного объекта

```sql
ALTER TABLE order_lines
    ADD CONSTRAINT order_lines_order_fk
    FOREIGN KEY (order_id)
    REFERENCES orders (id)
    ON DELETE CASCADE;
```

Действие при удалении выбираю по смыслу:

- `CASCADE` — дочерняя запись не имеет смысла без владельца;
- `RESTRICT` / `NO ACTION` — удаление необходимо запретить;
- `SET NULL` — связь необязательная, её потеря допустима.

**PostgreSQL не создаёт индекс на ссылающемся столбце автоматически.** Часто добавляю его отдельно для join и проверок при удалении родителя.

### 5. `EXCLUDE` — отсутствие пересекающихся значений

Например, бронирования одного помещения не должны пересекаться по времени:

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE bookings
    ADD CONSTRAINT no_overlapping_bookings
    EXCLUDE USING gist (
        room_id WITH =,
        period WITH &&
    );
```

Здесь `period` — диапазон, например `tstzrange`. Обязательность полей и непустоту диапазона задаю отдельно.

Это надёжнее проверки «сначала найти пересечения, потом вставить», которая без дополнительной синхронизации подвержена гонке.

### 6. Отложенные constraints

`DEFERRABLE` полезен, если внутри транзакции допустимо временно нарушить ограничение, но к commit состояние должно стать корректным.

Например, при перестановке уникальных порядковых номеров. Использую точечно: не все виды ограничений поддерживают откладывание.

## А сложные бизнес-правила?

Не всё нужно переносить в БД.

Правило «сумма всех резервов не превышает остаток» затрагивает несколько строк. Для него могут понадобиться:

- атомарный условный `UPDATE`;
- блокировка строки, представляющей общий ресурс;
- `SERIALIZABLE` с повтором транзакций;
- в обоснованных случаях — trigger.

Trigger использую осторожно: он скрывает часть поведения от прикладного кода и усложняет сопровождение. Constraints предпочтительнее, когда правило можно выразить декларативно.

## Как обрабатываю нарушения

На инфраструктурной границе перевожу известное нарушение в понятную прикладную ошибку:

```php
try {
    $this->em->flush();
} catch (UniqueConstraintViolationException $e) {
    // После определения конкретного нарушенного ограничения:
    throw new EmailAlreadyUsed(previous: $e);
}
```

Нельзя считать **любую** unique violation дубликатом email: нужно определить конкретное ограничение, не полагаясь на произвольный текст ошибки.

После SQL-ошибки транзакция PostgreSQL требует rollback; после ошибки ORM `flush()` нужно также учитывать состояние EntityManager.

**Итого:** в приложении — бизнес-сценарии и удобная валидация; в БД — последняя, конкурентно безопасная защита устойчивых инвариантов данных. Это не лишнее дублирование, а защита на разных уровнях.

## Q12 · PostgreSQL

**Интервьюер:** Запрос в PostgreSQL выполняется медленно. Опиши свой процесс диагностики и оптимизации: какие инструменты применяешь, что смотришь, какие типовые причины встречаются.

**Кандидат:**

Я начинаю не с добавления индекса, а с вопроса: **где именно уходит время — в выполнение SQL, ожидание блокировки, передачу данных или обработку результата приложением?**

## 1. Нахожу конкретный запрос и условия воспроизведения

Собираю:

- SQL и реальные параметры;
- частоту вызовов;
- среднее время и высокие перцентили;
- число возвращаемых строк;
- размер таблиц и распределение данных;
- различия между быстрым и медленным выполнением.

Инструменты:

- Symfony Profiler / APM — связь SQL с конкретным запросом приложения;
- `pg_stat_statements` — часто вызываемые и суммарно дорогие запросы;
- `log_min_duration_statement` — логирование медленных запросов;
- `auto_explain` — выборочный сбор планов медленных запросов.

В `pg_stat_statements` смотрю не только среднее время, но и **число вызовов и суммарное время**: запрос на 20 мс, выполняемый тысячи раз, может быть важнее редкого запроса на секунду.

Логирование включаю с учётом нагрузки и чувствительности параметров.

## 2. Проверяю ожидания и блокировки

```sql
SELECT
    pid,
    state,
    now() - query_start AS duration,
    wait_event_type,
    wait_event,
    pg_blocking_pids(pid) AS blockers,
    query
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;
```

Если запрос ждёт lock, оптимизация его плана может не помочь. Ищу блокирующую транзакцию, долгие транзакции и `idle in transaction`.

Для подробностей использую `pg_locks`. Завершать блокирующую сессию без выяснения её назначения не стоит.

## 3. Изучаю план выполнения

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...
```

**`ANALYZE` действительно выполняет запрос.** На production применяю осторожно, особенно для тяжёлых запросов и изменений данных. Даже выполнение с последующим rollback не устраняет нагрузку и все возможные побочные эффекты.

В плане смотрю:

- **estimated rows против actual rows** — насколько точны оценки;
- `loops` — сколько раз выполняется узел;
- `Rows Removed by Filter` — сколько данных прочитано впустую;
- способы соединения: Nested Loop, Hash Join, Merge Join;
- сортировки и запись временных данных на диск;
- `BUFFERS`: попадания в кеш и чтения;
- объём результирующих строк;
- planning time и execution time.

Время узлов включает работу их потомков, поэтому его нельзя просто суммировать. Значения `actual rows` и времени при нескольких `loops` нужно интерпретировать с учётом повторений.

**Seq Scan сам по себе не проблема**: если запрос читает большую часть таблицы, он может быть дешевле индексного доступа.

## 4. Типовые причины и решения

### Неподходящий или отсутствующий индекс

Например:

```sql
SELECT id, created_at
FROM orders
WHERE tenant_id = $1
  AND status = 'paid'
ORDER BY created_at DESC
LIMIT 50;
```

Кандидат:

```sql
CREATE INDEX CONCURRENTLY orders_tenant_status_created_idx
    ON orders (tenant_id, status, created_at DESC);
```

Проверяю, используется ли он и насколько сокращает работу.

**Цена:** место, дополнительные расходы на запись и обслуживание. Индекс выбираю под реальные запросы, а не на каждый столбец.

Partial index может быть компактнее:

```sql
CREATE INDEX CONCURRENTLY orders_paid_tenant_created_idx
    ON orders (tenant_id, created_at DESC)
    WHERE status = 'paid';
```

Но планировщик должен доказать соответствие условию индекса; с параметризованными условиями и generic plans это не всегда возможно.

### Выражение не соответствует индексу

```sql
WHERE date(created_at) = $1
```

Вместо преобразования каждой строки часто лучше диапазон:

```sql
WHERE created_at >= $1
  AND created_at < $2
```

Границы рассчитываю с правильной временной зоной.

Для `lower(email)` может понадобиться expression index. Также проверяю неявные приведения типов и то, на какой стороне выполняется преобразование.

### Плохие оценки количества строк

Если планировщик ожидал 10 строк, а получил миллион, он мог выбрать неподходящий join.

Действия:

- проверить работу autovacuum / autoanalyze;
- выполнить `ANALYZE`, если статистика устарела;
- увеличить statistics target для проблемного столбца;
- добавить extended statistics для коррелированных условий.

```sql
CREATE STATISTICS orders_tenant_status_stats
    (dependencies, mcv)
    ON tenant_id, status
    FROM orders;

ANALYZE orders;
```

### Слишком много читаемых или возвращаемых данных

Проверяю:

- нужен ли `SELECT *`;
- не размножают ли join строки;
- не маскирует ли `DISTINCT` ошибку запроса;
- можно ли раньше ограничить выборку;
- не используется ли глубокий `OFFSET`.

Для больших страниц часто выбираю keyset pagination:

```sql
WHERE (created_at, id) < ($cursor_time, $cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT 50
```

Нужен подходящий индекс и однозначный порядок. Trade-off: переход к произвольному номеру страницы становится сложнее.

### Сортировки и hash-операции уходят на диск

В плане видны external sort, временные чтения/записи, несколько batches у hash join.

Сначала уменьшаю объём данных или улучшаю запрос. Затем при необходимости тестирую локальное увеличение `work_mem`.

**Не повышаю его глобально вслепую:** память расходуется на отдельные операции, параллельные workers и конкурентные запросы.

### Много мёртвых строк и проблемы обслуживания

Проверяю `pg_stat_user_tables`, работу autovacuum, долгие транзакции и возможный bloat.

Долгая транзакция может мешать очистке старых версий строк. `VACUUM FULL` — не обычный первый шаг: он переписывает таблицу и требует сильной блокировки.

### Неудачный план для разных параметров

У одного tenant десять записей, у другого — миллионы. Общий план prepared statement может быть плох для одного из них.

Сравниваю планы и выполнение с разными параметрами, проверяю custom и generic plans. Настройки вроде `plan_cache_mode` использую для диагностики, а не как универсальное исправление.

## 5. Проверяю результат

После изменения сравниваю на репрезентативных данных:

- время и перцентили;
- число прочитанных строк и buffers;
- память и временные файлы;
- влияние на запись и другие запросы;
- планы для разных параметров.

Учитываю холодный и прогретый кеш. Если SQL выполняется быстро, а страница всё ещё медленная, возвращаюсь к сети, размеру ответа, Doctrine-гидратации и N+1.

**Мой принцип: сначала измерить и понять причину, затем изменить минимально необходимое и проверить эффект. Не «заставить PostgreSQL использовать индекс», а уменьшить общую стоимость работы.**

## Q13 · DDD

**Интервьюер:** Что такое агрегат в DDD и как ты определяешь его границы? Приведи пример с объяснением и типовую ошибку при выборе границ.

**Кандидат:**

**Агрегат в DDD — это группа доменных объектов, которая образует границу согласованности и изменяется через один вход — корень агрегата.** Корень отвечает за соблюдение инвариантов всей группы.

Это не просто дерево объектов или набор связанных таблиц.

## Как определяю границы

Начинаю с бизнес-операций и задаю вопросы:

1. **Какие правила должны выполняться сразу после каждой операции?**
2. Какие данные нужно изменить атомарно, чтобы эти правила сохранить?
3. Какие объекты имеют общий жизненный цикл?
4. Что может изменяться независимо?
5. Не станет ли агрегат слишком большим или конфликтным при конкурентных изменениях?

Обычно одна транзакция изменяет один агрегат. Это ориентир, а не абсолютный запрет: если постоянно приходится атомарно менять несколько агрегатов, стоит пересмотреть модель или явно обосновать такую координацию.

## Пример: заказ и его строки

```text
Order — корень
 ├── OrderLine
 ├── OrderLine
 └── ShippingAddress — Value Object
```

Правила:

- нельзя изменить строки оплаченного заказа;
- количество товара должно быть положительным;
- нельзя подтвердить пустой заказ.

Поэтому операции идут через корень:

```php
$order->addLine($productId, $quantity, $unitPrice);
$order->removeLine($lineId);
$order->confirm();
```

Например:

```php
public function confirm(): void
{
    if ($this->status !== OrderStatus::Draft) {
        throw new OrderCannotBeConfirmed();
    }

    if ($this->lines->isEmpty()) {
        throw new EmptyOrderCannotBeConfirmed();
    }

    $this->status = OrderStatus::Confirmed;
}
```

Внешний код не должен получать изменяемую коллекцию и удалять строку напрямую: иначе можно обойти проверку состояния заказа.

### Что остаётся за границей

**Product** и **Customer** — отдельные агрегаты. Заказ хранит их идентификаторы, а также нужные исторические значения: например, цену на момент покупки и адрес доставки.

Изменение цены в каталоге не должно менять уже оформленный заказ. Сам факт наличия связи или внешнего ключа не делает объекты одним агрегатом.

Резервирование товара на складе тоже обычно относится к другой границе. Тогда нужно определить процесс согласования: например, заказ находится в состоянии ожидания резерва, а после результата подтверждается или отклоняется. Нельзя просто заменить требование строгой согласованности событиями, не согласовав это с бизнесом.

## Типовая ошибка: агрегат «Клиент со всем его миром»

```text
Customer
 ├── Все заказы
 │    ├── Все строки
 │    └── Все платежи
 ├── Все обращения в поддержку
 └── Все уведомления
```

Такую границу часто выбирают по связям в БД: «всё принадлежит клиенту».

Последствия:

- коллекции растут без ограничения;
- независимые операции начинают конкурировать за один корень;
- увеличиваются стоимость загрузки и сложность сохранения;
- разные бизнес-процессы оказываются искусственно связаны.

Обычно клиент, заказ, платёж и обращение — отдельные агрегаты, связанные идентификаторами. Для экрана «всё о клиенте» можно собрать отдельную read model — **форма чтения не определяет границы изменения**.

**Мой критерий: в агрегат включаю минимальный набор объектов, который нужен для защиты конкретных инвариантов, а не всё, что связано с корнем.**

### ↳ Углубление

**Интервьюер:** Два процесса одновременно изменяют один и тот же агрегат. Что произойдёт и как ты проектируешь с учётом этого?

**Кандидат:**

Без специальной защиты возможны **потерянное обновление или нарушение инварианта агрегата**. Транзакция сама по себе этого не предотвращает.

Например, в заказе разрешено не более десяти строк:

```text
В БД: 9 строк.

Процесс A загружает заказ: 9 строк.
Процесс B загружает заказ: 9 строк.

A проверяет лимит и добавляет строку.
B проверяет лимит и добавляет строку.

Оба сохраняют → 11 строк.
```

На стандартном для PostgreSQL уровне `READ COMMITTED` оба процесса могут успешно завершиться: они вставляют разные дочерние записи, прямого конфликта записи нет.

Я выбираю защиту исходя из инварианта и характера конкуренции.

## 1. Optimistic locking

Подходит, если конфликты редки: разрешаем параллельную работу, но при сохранении проверяем, что агрегат не изменился.

В Doctrine:

```php
#[ORM\Version]
#[ORM\Column(type: 'integer')]
private int $version;
```

Концептуально обновление выглядит так:

```sql
UPDATE orders
SET status = :status,
    version = version + 1
WHERE id = :id
  AND version = :expected_version;
```

Если запись уже изменилась, обновление не затронет строку и Doctrine выбросит `OptimisticLockException`.

**Важная тонкость:** изменение только дочерней сущности или коллекции не обязательно вызывает `UPDATE` корня. Поэтому version-поле корня не защищает автоматически весь агрегат. Нужно обеспечить изменение корня при каждой агрегатной операции либо реализовать явную проверку и повышение версии в persistence-слое.

**Trade-offs:**
- не держим блокировку во время работы;
- удобно для форм редактирования и редких конфликтов;
- конфликт обнаруживается поздно;
- повтор операции требует загрузить актуальный агрегат и заново проверить правила.

После конфликта откатываю транзакцию и учитываю состояние EntityManager — нельзя просто повторить `flush()` со старым объектом.

Для пользовательской формы передаю версию, которую пользователь видел при чтении. Иначе загрузка свежего объекта непосредственно перед сохранением не обнаружит, что пользователь редактировал устаревшие данные.

## 2. Pessimistic locking

Если конкуренция высока или операция требует эксклюзивного изменения, блокирую корень:

```php
$this->em->wrapInTransaction(function () use ($orderId): void {
    $order = $this->em->find(
        Order::class,
        $orderId,
        LockMode::PESSIMISTIC_WRITE,
    );

    $order->addLine(/* ... */);
});
```

В PostgreSQL это обычно приводит к `SELECT ... FOR UPDATE`. Второй процесс ждёт завершения первого, затем работает с актуальным состоянием.

**Но блокировка корня защищает агрегат только при общей дисциплине:** все операции изменения должны сначала блокировать корень, а уже затем читать необходимое состояние дочерних объектов.

**Trade-offs:**
- последовательная проверка и изменение инварианта;
- ожидание блокировок снижает пропускную способность;
- возможны deadlock и lock timeout;
- нужны короткие транзакции и одинаковый порядок захвата нескольких блокировок.

Внешний HTTP-вызов внутри такой транзакции стараюсь не делать.

## 3. Атомарные операции и ограничения БД

Для простого инварианта это часто эффективнее загрузки агрегата.

Например, резервирование остатка:

```sql
UPDATE stock
SET available = available - :quantity
WHERE product_id = :id
  AND available >= :quantity
RETURNING available;
```

Если строка не возвращена — резервирование не состоялось. Предварительная проверка в PHP не нужна для гарантии корректности.

Дополнительно использую `UNIQUE`, `CHECK`, `EXCLUDE` там, где ими можно выразить правило.

**Trade-off:** SQL становится частью реализации доменной операции; при прямом обновлении нужно учитывать устаревшее состояние объектов в Doctrine Unit of Work.

## 4. `SERIALIZABLE`

Для сложных правил, зависящих от нескольких чтений и записей, можно использовать сериализуемые транзакции.

PostgreSQL не просто заставит всё выполняться последовательно: он может завершить одну из конфликтующих транзакций ошибкой сериализации.

**Trade-offs:**
- защищает от широкого класса аномалий;
- требует ограниченного retry **всей транзакции**;
- при высокой конкуренции растёт число отмен;
- внешние эффекты нельзя бездумно повторять.

Для уведомлений и публикации событий здесь полезен transactional outbox.

## Как выбираю

- **Редкие конфликты, редактирование пользователем** → optimistic locking, конфликт обычно возвращаю как `409` или предлагаю обновить данные.
- **Короткая операция с высокой конкуренцией** → pessimistic locking.
- **Счётчики, остатки, уникальность** → атомарный SQL и constraints.
- **Сложные межстрочные инварианты** → явная блокировка общего ресурса или `SERIALIZABLE`.

И отдельно различаю **конкурентный конфликт** и **повтор одной команды**: блокировка не защищает от повторного платежа после сетевого тайм-аута. Для этого нужны идемпотентные ключи.

**Главный принцип: инвариант должен оставаться истинным не только при последовательном исполнении методов, но и при реальном параллельном выполнении транзакций.**

## Q14 · DDD

**Интервьюер:** Как ты применяешь доменные события: когда публикуешь, как обрабатываешь, какие проблемы этот подход решает и какие создаёт? Как доменные события связаны с транзакциями базы данных?

**Кандидат:**

Я использую доменные события, чтобы выразить **свершившийся бизнес-факт** и отделить его от реакций других частей системы: `OrderConfirmed`, `PaymentReceived`, `UserRegistered`.

Это не команда: `SendWelcomeEmail` просит выполнить действие, а `UserRegistered` сообщает, что уже произошло.

## 1. Где событие возникает

Событие создаёт доменная модель после успешной операции:

```php
public function confirm(): void
{
    $this->assertCanBeConfirmed();

    $this->status = OrderStatus::Confirmed;

    $this->events[] = new OrderConfirmed(
        eventId: Uuid::v7()->toRfc4122(),
        orderId: $this->id,
    );
}
```

Агрегат **не обращается к Messenger, брокеру или EventDispatcher**. Он только накапливает события, которые прикладной слой затем извлекает.

В событие обычно включаю ID события, ID агрегата, необходимые данные факта, а при необходимости — время и версию агрегата. Doctrine entity туда не передаю.

Важно: событие создано в памяти, но операция ещё может откатиться. Поэтому для внешнего мира факт становится подтверждённым только после commit.

## 2. Когда и как обрабатываю

Разделяю два случая.

### Синхронно, внутри транзакции

Обработчик может изменить данные в той же БД, если эти изменения действительно должны быть атомарными.

```text
Изменение агрегата
→ обработка внутренних событий
→ сохранение всех изменений
→ commit
```

Если обработчик выбросит исключение, транзакция откатывается.

**Плюсы:** атомарность, немедленный результат.

**Минусы:** скрытый граф вызовов, более длинная транзакция, возможные циклы и каскады событий.

Если действие обязательно для основного сценария, часто предпочитаю **явный вызов из application handler**, а не скрытую реакцию подписчика. Внутри такой транзакции не отправляю письма и не вызываю внешние API: rollback БД их не отменит.

### Асинхронно, после commit

Для уведомлений, поиска, аналитики и интеграции с другими системами использую очередь.

```text
Commit регистрации
→ обработка события воркерами
→ письмо и обновление индекса
```

**Плюсы:** быстрый ответ, независимые retries, изоляция сбоев.

**Минусы:** eventual consistency, задержки, дубликаты, возможное нарушение порядка.

Обычный Symfony EventDispatcher работает синхронно. Для фоновой обработки нужен Messenger с асинхронным routing или другой механизм очередей.

## 3. Связь с транзакцией: проблема двойной записи

Нельзя надёжно решить задачу простой перестановкой двух действий.

**Публикация до commit:**

```text
Сообщение отправлено → транзакция откатилась
```

Получатель увидит факт, которого в БД нет. Он также может начать обработку до появления данных.

**Публикация после commit:**

```text
Commit выполнен → процесс упал → сообщение не отправлено
```

Данные сохранены, но событие потеряно.

Для внешнего брокера я обычно использую **transactional outbox**:

```php
$this->transactions->run(function () use ($orderId): void {
    $order = $this->orders->get($orderId);
    $order->confirm();

    foreach ($order->releaseEvents() as $event) {
        $this->outbox->append($event);
    }
});
```

Изменения агрегата и записи outbox фиксируются **в одной транзакции одной БД**. Отдельный relay публикует события в очередь.

Это даёт гарантию: либо сохранены и изменения, и намерение опубликовать событие, либо не сохранено ничего.

Но доставка обычно остаётся **at least once**: relay может отправить событие и упасть до отметки об отправке. Поэтому обработчики должны учитывать повторы.

Если Messenger использует Doctrine transport на том же соединении и в той же транзакции, постановку сообщения также можно сделать атомарной с изменением данных. Это нужно проверить в конкретной конфигурации.

## 4. Что решают события

- Уменьшают прямую связанность издателя и независимых потребителей.
- Позволяют добавлять реакции без изменения основного сценария.
- Делают бизнес-факты явными.
- Помогают строить асинхронные процессы и read models.

При этом **доменные события не означают event sourcing**. Можно хранить текущее состояние агрегатов обычным образом, а события использовать только для реакций.

## 5. Какие проблемы создают

**Повторная доставка.**  
Использую ID события и дедупликацию. Для изменения данных потребителя запись «событие обработано» и сами изменения фиксирую в одной транзакции. Для внешних эффектов, например платежа, нужен idempotency key провайдера: локальная отметка сама по себе не закрывает окно сбоя.

**Порядок.**  
События одного агрегата могут прийти не по порядку. При необходимости использую версию, упорядоченную доставку по ключу агрегата или логику обработки устаревших событий.

**Изменение схемы.**  
В очереди могут лежать старые сообщения. Поэтому формат событий версионирую и поддерживаю совместимость. Внутреннее доменное событие не обязательно публикую наружу напрямую — часто преобразую его в стабильное integration event.

**Скрытый control flow.**  
Нужно видеть, какие подписчики реагируют на факт, и не допускать бесконечных цепочек.

**Состояние после rollback.**  
Если события уже извлечены из объекта, а транзакция упала, нельзя продолжать работу с тем же агрегатом как ни в чём не бывало. Retry выполняю с заново загруженным состоянием.

**Наблюдаемость.**  
Нужны correlation ID, мониторинг задержек outbox и очереди, retries, failed transport и возможность повторной обработки.

**Итого:** событие возникает в домене, но его надёжная публикация — задача прикладного и инфраструктурного слоёв. Для внешних реакций мой обычный выбор — outbox и идемпотентные потребители; обязательные атомарные шаги сценария стараюсь оставлять явными.

## Q15 · DDD

**Интервьюер:** Чем Value Object отличается от Entity в DDD? Как решаешь, к чему отнести ту или иную концепцию домена? Что такое единый язык (ubiquitous language) и как он влияет на код?

**Кандидат:**

**Entity определяется идентичностью, а Value Object — значением.** Главное различие не в наличии поля `id` или отдельной таблицы, а в том, как бизнес понимает равенство и изменение объекта.

## Entity

У сущности есть идентичность, сохраняющаяся на протяжении жизненного цикла.

Например, заказ остаётся тем же заказом, даже если изменились адрес доставки или статус. Два заказа с одинаковыми товарами и суммой — всё равно разные заказы.

```php
final class Order
{
    public function __construct(
        private readonly OrderId $id,
        private OrderStatus $status,
    ) {}

    public function sameIdentityAs(self $other): bool
    {
        return $this->id->equals($other->id);
    }
}
```

Сущность может быть изменяемой, но **изменяемость сама по себе не определяет Entity**.

## Value Object

VO описывает значение и не имеет собственной доменной идентичности. Два экземпляра с одинаковыми значимыми компонентами считаются равными.

```php
final readonly class Money
{
    public function __construct(
        public int $amountInMinorUnits,
        public string $currency,
    ) {
        if ($amountInMinorUnits < 0) {
            throw new \InvalidArgumentException('Negative amount');
        }

        if (!in_array($currency, ['EUR', 'USD'], true)) {
            throw new \InvalidArgumentException('Unsupported currency');
        }
    }

    public function equals(self $other): bool
    {
        return $this->amountInMinorUnits === $other->amountInMinorUnits
            && $this->currency === $other->currency;
    }

    public function add(self $other): self
    {
        if ($this->currency !== $other->currency) {
            throw new \DomainException('Currency mismatch');
        }

        return new self(
            $this->amountInMinorUnits + $other->amountInMinorUnits,
            $this->currency,
        );
    }
}
```

VO обычно делаю неизменяемым: операция возвращает новое значение. Это упрощает рассуждение о коде и позволяет безопасно передавать значение между объектами.

При этом правило «сумма неотрицательная» зависит от контекста: для задолженности или бухгалтерской проводки отрицательное значение может быть допустимо.

## Как выбираю

Задаю вопросы бизнесу:

- Нужно ли отличать два объекта с одинаковыми свойствами?
- Должен ли объект оставаться «тем же самым» после изменения свойств?
- Важны ли его индивидуальная история и жизненный цикл?
- Или нам важно только текущее значение?

### Пример: адрес

**Адрес доставки в оформленном заказе** обычно VO: это снимок значения на момент покупки. Исправление адреса в профиле не должно менять старые заказы.

**Сохранённый адрес в адресной книге пользователя** может быть Entity: пользователь редактирует конкретную запись, делает её основной или удаляет. У записи есть идентичность, а внутри неё может находиться VO `PostalAddress`.

Одна и та же концепция может моделироваться по-разному в разных bounded contexts.

Также:

- `OrderId` может быть VO, хотя идентифицирует Entity.
- Наличие технического первичного ключа в БД не превращает концепцию в доменную Entity.
- Entity не обязательно является корнем агрегата: строка заказа может быть дочерней сущностью.

## Единый язык — ubiquitous language

Это **общий, согласованный язык бизнеса и команды разработки внутри конкретного bounded context**. Его используют в обсуждениях, требованиях, коде и тестах.

Он влияет не только на имена классов, но и на сами операции модели.

Вместо технического:

```php
$order->setStatus('confirmed');
```

используем бизнес-действие:

```php
$order->confirm();
```

Метод выражает смысл операции и защищает её правила: например, нельзя подтвердить пустой заказ.

Аналогично тест называется:

```text
Нельзя подтвердить заказ без строк
```

а не «setter присваивает status».

**Единый язык не обязан быть одинаковым для всей компании.** «Клиент» в продажах и «плательщик» в биллинге могут обозначать разные модели. На границе контекстов я явно перевожу понятия, а не пытаюсь объединить их в универсальный класс `User`.

Итого: **Entity отвечает на вопрос «кто именно это?», VO — «какое это значение?», а единый язык помогает сделать это различие и бизнес-поведение понятными прямо из кода.**

## Q16 · Чистая архитектура

**Интервьюер:** Опиши структуру типичного PHP-приложения по принципам чистой архитектуры: какие слои, что в каждом лежит, каково правило зависимостей между ними. Куда попадут Doctrine, Symfony-контроллер и обработчик очереди? Как следить, что границы слоёв не нарушаются?

**Кандидат:**

Я строю структуру вокруг **бизнес-сценариев и правила зависимостей**, а не вокруг обязательного набора папок. Основное правило чистой архитектуры: **зависимости исходного кода направлены внутрь — к бизнес-логике**. Домен не знает о Symfony, Doctrine, HTTP или очереди.

## 1. Слои и их содержимое

### Domain — бизнес-модель

Здесь находятся:

- агрегаты и сущности;
- Value Objects;
- доменные сервисы и политики;
- доменные события;
- бизнес-исключения.

Например, `Order::confirm()` проверяет, что заказ не пуст и находится в допустимом состоянии.

Домен не получает `Request`, `EntityManagerInterface` или `MessageBusInterface`.

### Application — сценарии использования

Здесь находятся:

- use cases / прикладные обработчики;
- команды и результаты сценариев;
- координация работы доменных объектов;
- порты для необходимых внешних возможностей.

Например:

```php
final class ConfirmOrderHandler
{
    public function __construct(
        private OrderRepository $orders,
        private TransactionManager $transactions,
    ) {}

    public function handle(ConfirmOrder $command): void
    {
        $this->transactions->run(function () use ($command): void {
            $order = $this->orders->get($command->orderId);
            $order->confirm();
        });
    }
}
```

Обработчик знает, **что нужно сохранить атомарно**, но не знает, как Doctrine открывает транзакцию и выполняет `flush()`.

Интерфейс репозитория может находиться в Domain, если представляет коллекцию агрегатов, либо в Application, если является портом конкретного сценария. Важно не название папки, а направление зависимости.

### Внешние адаптеры

В классическом описании их можно разделить на interface adapters и frameworks/drivers. В PHP-проектах я часто группирую их как `Presentation` и `Infrastructure`.

**Presentation / входные адаптеры:**

- Symfony-контроллеры;
- CLI-команды;
- обработчики сообщений очереди;
- преобразование внешнего ввода в команды приложения;
- преобразование результата и ошибок в ответ транспорта.

**Infrastructure / выходные адаптеры:**

- реализации репозиториев на Doctrine;
- DBAL types и ORM mapping;
- HTTP-клиенты внешних сервисов;
- отправка писем;
- реализации outbox, кеша и transaction manager.

```text
src/Order/
├── Domain/
│   ├── Order.php
│   ├── OrderId.php
│   └── OrderRepository.php
├── Application/
│   ├── ConfirmOrder.php

├── Presentation/

│   └── Messenger/ConfirmOrderConsumer.php
└── Infrastructure/

    └── DoctrineTransactionManager.php
```

Здесь организация сначала по бизнес-модулю, затем по слоям. Это не единственно допустимый вариант.

## 3. Куда попадают конкретные технологии

### Doctrine

**Во внешний слой.** Реализация репозитория зависит от Doctrine и от внутреннего интерфейса:

```php
final class DoctrineOrderRepository implements OrderRepository
{
    public function __construct(private EntityManagerInterface $em) {}

    // ...
}
```

При строгом разделении ORM mapping размещаю отдельно от доменных классов, например в XML. Атрибуты Doctrine в домене — осознанный компромисс, а не полная независимость.

То же относится к `Doctrine\Common\Collections\Collection`: его использование в доменной модели тоже создаёт внешнюю зависимость.

### Symfony-контроллер

Это **входной HTTP-адаптер**. Он разбирает запрос, выполняет транспортную валидацию, вызывает сценарий и формирует ответ. Бизнес-правила остаются внутри.

### Обработчик очереди

Это **входной адаптер**, если он принимает сообщение Messenger:

```php
#[AsMessageHandler]
final class ConfirmOrderConsumer
{
    public function __construct(private ConfirmOrderHandler $handler) {}

    public function __invoke(ConfirmOrderMessage $message): void
    {
        $this->handler->handle(
            new ConfirmOrder(new OrderId($message->orderId))
        );
    }
}
```

Прикладной обработчик при этом не зависит от Messenger.

Можно напрямую зарегистрировать application handler в Messenger через внешнюю конфигурацию, без атрибутов в нём. Отдельная обёртка особенно полезна, если формат транспортного сообщения отличается от команды сценария.

## 4. Направление зависимостей и выполнения — разные вещи

Во время выполнения application handler вызывает репозиторий Doctrine. Но в исходном коде он зависит только от внутреннего интерфейса:

```text
Application → OrderRepository ← DoctrineOrderRepository
```

Связывает интерфейс с реализацией **composition root** — конфигурация DI-контейнера Symfony. Именно здесь допустимо знать обо всех слоях.

## 5. Как контролирую границы

- **Deptrac в CI:** запрещаю зависимости Domain от Application и внешних слоёв, Application — от инфраструктуры и транспорта.
- **PHPStan / Psalm:** проверяю типы и при необходимости добавляю правила для запрещённых зависимостей.
- **Тесты:** доменные и прикладные тесты должны запускаться без Symfony Kernel и реальной БД; адаптеры проверяются интеграционными тестами.
- **Code review:** ищу утечки `Request`, `Response`, Doctrine QueryBuilder и транспортных сообщений во внутренние контракты.
- **Явные DTO и порты:** наружу не возвращаю ORM-запросы или lazy-коллекции, требующие работающего EntityManager.

При этом интерфейс на каждый класс не нужен. Абстракции создаю на значимых границах, а не ради формального количества слоёв.

**Итого:** Symfony и Doctrine подключаются к приложению снаружи; бизнес-модель и сценарии не должны зависеть от способов доставки запросов и хранения данных. Правильность этого разделения подтверждается не папками, а зависимостями кода и возможностью тестировать внутренние слои отдельно.

## Q17 · Тестирование

**Интервьюер:** Какую стратегию тестирования выберешь для Symfony-приложения с PostgreSQL: пирамида тестов, типы тестов, что мокаешь, а что нет? Как поддерживать тесты быстрыми и стабильными?

**Кандидат:**

Я выберу **пирамиду тестов с существенным интеграционным слоем**: много быстрых тестов бизнес-логики, достаточное число проверок Doctrine и PostgreSQL, меньше HTTP-тестов и совсем немного сквозных сценариев. Проценты заранее не фиксирую — покрываю риски, а не форму пирамиды.

## 1. Unit-тесты: домен и прикладные сценарии

### Домен

Без Symfony Kernel и БД проверяю:

- инварианты агрегатов;
- операции Value Objects;
- переходы состояний;
- доменные события.

```php
public function testEmptyOrderCannotBeConfirmed(): void
{
    $order = new Order(OrderId::generate());

    $this->expectException(EmptyOrderCannotBeConfirmed::class);

    $order->confirm();
}
```

**Доменные объекты не мокаю:** именно их поведение проверяем.

### Application

Проверяю координацию сценария, подменяя внешние порты:

- репозиторий — fake или mock;
- платёжный шлюз — stub;
- часы и генератор ID — детерминированные реализации;
- отправку сообщений — записывающий fake.

Предпочитаю проверять результат и значимые эффекты, а не каждый внутренний вызов. Например, «сохранён подтверждённый заказ», а не «метод X вызван строго перед Y», если порядок не является частью контракта.

Fake transaction manager помогает unit-тесту, но **не доказывает атомарность** — её проверяю отдельно.

## 2. Интеграционные тесты: реальная PostgreSQL

Использую `KernelTestCase` и отдельную тестовую БД PostgreSQL, обычно в Docker.

Здесь **не мокаю Doctrine и SQL**. Проверяю:

- сохранение и восстановление агрегатов;
- маппинг VO и custom DBAL types;
- каскады и `orphanRemoval`;
- запросы репозиториев;
- constraints, блокировки и optimistic locking;
- атомарность outbox.

SQLite не использую как замену PostgreSQL для этих проверок: различаются SQL, типы, ограничения и конкурентное поведение.

В round-trip тесте обязательно очищаю EntityManager:

```php
$repository->add($order);
$em->flush();
$em->clear();

$restored = $repository->get($order->id());

self::assertTrue($restored->id()->equals($order->id()));
```

Иначе можно получить тот же объект из identity map и не проверить гидратацию вообще.

Для конкуренции нужны **разные соединения и настоящие границы транзакций**: обычный последовательный тест на одном EntityManager гонку не воспроизводит.

## 3. Функциональные HTTP-тесты

Через `WebTestCase` проверяю связку:

```text
HTTP → routing → security → validation → application → persistence
```

Основные сценарии:

- успешный запрос;
- некорректный ввод;
- `401` / `403`;
- доступ к чужому объекту;
- бизнес-конфликт;
- формат ответа.

Использую реальную БД, но внешние сервисы заменяю адаптерами тестового окружения. Для писем проверяю содержимое и факт отправки через тестовый transport, а не обращаюсь к настоящему SMTP.

## 4. Очереди и внешние интеграции

Для Messenger разделяю проверки:

- handler — обычный unit- или интеграционный тест;
- постановка сообщения — проверка через in-memory transport;
- сериализация, routing, retries и реальная доставка — небольшой набор тестов с настоящим transport.

**Синхронный test transport не подтверждает корректность асинхронной обработки.** Для outbox отдельно проверяю rollback, доставку и повторную обработку.

HTTP-адаптеры внешних сервисов проверяю на контролируемых ответах: успех, timeout, ошибки, некорректный payload. Небольшие contract-тесты с sandbox поставщика запускаю отдельно, а не делаю весь CI зависимым от его доступности.

## 5. Немного E2E

Через Panther или другой браузерный инструмент покрываю несколько критичных пользовательских путей, например регистрацию и вход.

Они проверяют взаимодействие компонентов, но дороги и сложнее диагностируются. Все бизнес-варианты в браузере не дублирую.

## Как сохраняю скорость и стабильность

### Изоляция данных

- Отдельная БД на параллельный worker.
- Небольшие фабрики данных вместо огромных общих fixtures.
- Миграции применяются при подготовке окружения, а не перед каждым тестом.
- Для большинства DB-тестов — rollback транзакции, например через DAMA DoctrineTestBundle.

Но тесты commit, очередей, нескольких соединений и блокировок запускаю без такой обёртки, с отдельной очисткой: внешняя тестовая транзакция может скрыть реальное поведение.

### Детерминизм

- Управляемые часы вместо зависимости от текущего времени.
- Фиксированная timezone.
- Явный `ORDER BY`, если тест проверяет порядок.
- Никаких произвольных `sleep()` для ожидания воркера: ожидание конкретного условия с ограниченным timeout.
- Очистка кеша, файлов и других общих ресурсов, которые тест изменяет.

### Организация CI

Быстрые unit-тесты и статический анализ запускаю первыми. Интеграционные и HTTP — параллельно в изолированных окружениях. Более дорогие E2E и проверки реальных интеграций выделяю в отдельные наборы, но критичные проверки оставляю обязательными перед выпуском.

Flaky-тесты не «лечу» бесконечными retries: ищу общий ресурс, гонку или недетерминированное ожидание.

**Итого:** мокаю внешние границы там, где проверяю бизнес-поведение; Doctrine и PostgreSQL проверяю настоящими интеграционными тестами. Скорость достигается не заменой всего моками, а правильным уровнем проверки, малыми данными и изоляцией.

## Q18 · Конкурентность

**Интервьюер:** Два пользователя одновременно изменяют одну и ту же запись в базе. Какие проблемы могут возникнуть и какие способы защиты от них ты знаешь? Сравни подходы и опиши, когда какой выбираешь.

**Кандидат:**

Главное — различать **параллельные транзакции** и **редактирование устаревших данных**. Пользователь мог открыть форму час назад: даже если два сохранения выполнятся последовательно, второе может затереть изменения первого.

## Какие проблемы возникают

### Потерянное обновление

```text
Исходная цена: 100.

A читает 100 и устанавливает 110.
B читает 100 и устанавливает 120.

A сохраняет, затем B сохраняет → 120.
```

База успешно выполнила оба запроса, но изменение A потеряно. Для операции «увеличить на 10 и на 20» ожидалось бы 130.

### Нарушение бизнес-инварианта

Два процесса проверяют, что остаток товара достаточен, и оба оформляют покупку. Предварительные проверки прошли, но итоговый резерв превышает остаток.

### Конфликт разных полей

A меняет телефон, B — адрес. Если приложение сохраняет весь устаревший объект, B может вернуть старый телефон. Если обновляются только изменённые поля, оба изменения могут сохраниться — но это не гарантирует соблюдение правил, связывающих эти поля.

PostgreSQL блокирует конфликтующие записи при `UPDATE`, однако **блокировка записи сама по себе не защищает от сохранения устаревшего значения**.

## 1. Optimistic locking — проверка версии

У записи есть версия:

```sql
UPDATE documents
SET title = :title,
    version = version + 1
WHERE id = :id
  AND version = :expected_version
RETURNING version;
```

Если строка не возвращена, её уже изменили или удалили.

В Doctrine для этого используется version-поле:

```php
#[ORM\Version]
#[ORM\Column(type: 'integer')]
private int $version;
```

Для формы или API важно проверять **версию, которую пользователь получил при чтении**, а не только версию свежезагруженного перед сохранением объекта. В HTTP аналогичную семантику можно выразить через `ETag` и `If-Match`.

**Плюсы:** нет долгих блокировок; хорошо подходит для пользовательского редактирования.

**Минусы:** нужно обработать конфликт — предложить обновить данные, сравнить изменения или выполнить merge. Автоматический retry не всегда корректен: он может молча перезаписать чужую работу.

**Выбираю:** конфликты редки, пользователь долго редактирует данные.

## 2. Pessimistic locking — блокировка на время операции

```sql
BEGIN;

SELECT *
FROM stock
WHERE product_id = :id
FOR UPDATE;

-- Проверка и изменение состояния.

COMMIT;
```

Второй процесс ждёт освобождения блокировки. В Doctrine — `LockMode::PESSIMISTIC_WRITE` внутри транзакции.

**Плюсы:** удобно последовательно выполнить проверку и изменение.

**Минусы:** ожидания, deadlocks, снижение пропускной способности. Нужны короткие транзакции, timeout и одинаковый порядок захвата блокировок.

**Выбираю:** короткие серверные операции с высокой конкуренцией.

Блокировку БД нельзя держать всё время, пока пользователь заполняет форму. И блокировка непосредственно перед сохранением не обнаружит, что форма устарела — для этого всё равно нужна версия.

## 3. Атомарный SQL

Для счётчиков не делаю read–modify–write в PHP:

```sql
UPDATE counters
SET value = value + :delta
WHERE id = :id;
```

Для остатка совмещаю условие и изменение:

```sql
UPDATE stock
SET available = available - :quantity
WHERE product_id = :id
  AND available >= :quantity
RETURNING available;
```

При условии, что `quantity > 0`, это позволяет безопасно конкурировать за остаток. Отсутствие результата означает, что операция не состоялась.

**Плюсы:** коротко, эффективно, нет отдельного окна между проверкой и записью.

**Минусы:** подходит не для каждого сложного сценария; прямой SQL требует учитывать состояние Doctrine identity map.

**Выбираю:** счётчики, остатки, условные переходы состояния.

## 4. Ограничения БД

Использую:

- `UNIQUE` — уникальность;
- `CHECK` — допустимые значения строки;
- `FOREIGN KEY` — корректные ссылки;
- `EXCLUDE` — например, отсутствие пересекающихся бронирований.

**Плюсы:** защита действует для всех путей записи и при конкуренции.

**Минусы:** не все бизнес-правила выразимы декларативно; нарушения нужно переводить в понятные ошибки.

**Выбираю:** всегда, когда устойчивый инвариант можно выразить constraint. Это дополнение к другим подходам, а не замена проверки версии.

## 5. Уровни изоляции

- **`READ COMMITTED`** — стандартный в PostgreSQL; часто достаточен вместе с атомарными операциями и явными блокировками.
- **`REPEATABLE READ`** — стабильный снимок; в PostgreSQL конфликтующее обновление может закончиться ошибкой сериализации, но возможны аномалии вроде write skew.
- **`SERIALIZABLE`** — обеспечивает результат, эквивалентный последовательному выполнению успешно завершённых транзакций, но может отменить одну из них.

Для `SERIALIZABLE` нужен ограниченный retry **всей транзакции**. Внешние эффекты должны быть идемпотентными либо вынесены через outbox.

**Выбираю:** сложные правила, основанные на нескольких чтениях и записях, когда явная блокировка общего ресурса неудобна.

## Краткий выбор

| Сценарий | Основной подход |
|---|---|
| Два пользователя редактируют документ | Версия / optimistic locking |
| Увеличение счётчика | Атомарный `UPDATE` |
| Покупка последней единицы товара | Условный `UPDATE` или короткая блокировка |
| Уникальный email | Уникальный индекс |
| Сложный межстрочный инвариант | Явная блокировка или `SERIALIZABLE` |

**И отдельно:** повтор одной команды после сетевого тайм-аута — не тот же случай, что конкурентное редактирование. Для защиты от двойного платежа или повторного создания нужны идемпотентные ключи.

## Q19 · Git и процесс

**Интервьюер:** Опиши свой git-процесс от постановки задачи до продакшена: ветвление, формат коммитов, pull request, ревью, релизы. Объясни, почему так, а не иначе.

**Кандидат:**

В рамках нашего условного профиля я бы выбрал **trunk-based development с короткоживущими ветками и защищённой `main`**. Для команды, которая регулярно выпускает изменения, это обычно проще Git Flow: меньше долгих расхождений и интеграционных конфликтов.

## 1. Постановка задачи

До написания кода уточняю:

- критерии приёмки;
- изменения API и схемы БД;
- требования к совместимости;
- способ проверки и выкладки;
- риски и план отката.

Большую задачу разбиваю на небольшие, независимо интегрируемые шаги. Незавершённое поведение при необходимости скрываю feature flag.

**Почему:** маленькое изменение проще проверить, выпустить и отменить.

## 2. Ветка

Создаю ветку от актуальной `main`:

```bash
git switch main
git pull --ff-only
git switch -c feat/APP-123-order-cancellation
```

Примеры имён:

```text
feat/APP-123-order-cancellation
fix/APP-456-payment-timeout
```

Ветка живёт желательно несколько дней, а не недель. Общие долгоживущие feature-ветки стараюсь избегать.

Локальную ветку могу обновлять через rebase. **Общую историю не переписываю без согласования**; если нужно обновить свою опубликованную ветку после rebase, использую `--force-with-lease`, а не обычный `--force`.

## 3. Коммиты

Делаю небольшие логические коммиты, не смешивая бизнес-изменение с массовым форматированием.

Использую Conventional Commits, если команда поддерживает этот формат:

```text
feat(order): add cancellation for draft orders
fix(payment): preserve idempotency key on retry
refactor(order): extract pricing policy
```

В теле объясняю **почему**, если причина не очевидна, и указываю задачу:

```text
fix(payment): preserve idempotency key on retry

A timeout does not guarantee that the provider rejected the payment.
Reuse the key to prevent a duplicate charge.

Refs: APP-456
```

**Почему:** понятная история облегчает расследование ошибок, `bisect`, revert и составление release notes.

Перед публикацией проверяю diff, запускаю доступные тесты и статический анализ. Секреты и локальные конфиги в git не попадают.

## 4. Pull request

Открываю небольшой PR; для раннего обсуждения — draft.

В описании:

- что и зачем изменено;
- ссылка на задачу;
- как проверено;
- изменения контрактов и миграции;
- особенности выкладки;
- план отката.

CI проверяет форматирование, PHPStan/Psalm, unit- и интеграционные тесты с PostgreSQL. Для значимых изменений — HTTP-тесты и другие необходимые проверки.

**Почему:** PR должен давать ревьюеру контекст, а CI — снимать механические проверки.

## 5. Ревью и merge

На ревью смотрю прежде всего на:

- корректность бизнес-правил;
- конкурентность и транзакции;
- безопасность;
- совместимость;
- запросы к БД;
- достаточность тестов;
- понятность решения.

Отделяю обязательные замечания от предложений и стилистических предпочтений. Если решение спорное, проще коротко обсудить его, чем вести длинную переписку.

`main` защищена: обязательны успешный CI и одобрение ревью. Для обычных PR предпочитаю **squash merge**, чтобы одна задача соответствовала одному понятному коммиту. Если промежуточные коммиты имеют самостоятельную ценность, можно сохранить их — главное, единая политика команды.

## 6. Релиз и продакшен

После merge CI собирает **неизменяемый артефакт**, привязанный к commit SHA. Один и тот же артефакт проходит staging и выкладывается в production — на сервере не делаем `git pull` и не собираем приложение заново.

Релиз помечаем тегом, например:

```text
v1.14.0
```

SemVer использую, если команда действительно определила правила совместимости; для внутреннего приложения возможна другая схема.

Перед выкладкой проверяем миграции и совместимость версий приложения. Для изменений БД предпочитаю **expand–migrate–contract**:

1. Добавить совместимую структуру.
2. Выпустить код и перенести данные.
3. Позже удалить старую структуру.

После выкладки — smoke tests, метрики ошибок, latency, состояние очередей и БД.

**Почему:** откат кода не обязательно откатывает данные. Автоматический `down` для миграций может быть опаснее исправления вперёд.

## 7. Hotfix и откат

Если `main` пригодна для выпуска, исправление проходит обычный короткий PR-процесс. Если в ней есть ещё неготовые к релизу изменения, hotfix делаю от production-тега и затем переношу исправление в `main`.

В production при проблеме:

- отключаю feature flag, если это возможно;
- возвращаю предыдущий артефакт, если схема совместима;
- либо выпускаю исправление вперёд.

В git отменяю изменение через `revert`, а не переписываю опубликованную историю через `reset`.

**Итого:** короткие ветки, небольшие PR, защищённая `main`, автоматические проверки и воспроизводимый выпуск. Git Flow выбрал бы скорее для нескольких одновременно поддерживаемых версий и редких пакетных релизов — там дополнительные release-ветки могут оправдать свою стоимость.

## Q20 · Git и процесс

**Интервьюер:** Что для тебя хороший код-ревью: как маркируешь замечания, на что смотришь в первую очередь, как поступаешь при разногласии с автором?

**Кандидат:**

Для меня хорошее код-ревью — это **проверка корректности и рисков изменения плюс обмен знаниями**, а не поиск повода переписать код в своём стиле. После него решение должно стать надёжнее, а автор — понимать причины замечаний.

### Как маркирую замечания

Я явно обозначаю, требуется ли изменение:

- **`blocker`** — нельзя мержить: ошибка, уязвимость, потеря данных, нарушение контракта.
- **`required`** — нужно исправить до merge: например, не покрыт критичный сценарий или нарушено согласованное правило архитектуры.
- **`suggestion`** — необязательное улучшение; автор может предложить альтернативу.
- **`question`** — уточнение: возможно, я не понимаю контекст.
- **`nit`** — мелочь, не блокирует merge.

Например:

> **blocker:** Проверка остатка и списание выполняются отдельно. Два запроса могут одновременно пройти проверку. Предлагаю условный `UPDATE` или блокировку строки внутри транзакции.

Или:

> **suggestion:** Здесь можно выделить именованный метод, чтобы бизнес-условие читалось без разбора выражения.

Сам ярлык не заменяет объяснение: **указываю проблему, последствия и по возможности вариант решения**, но не требую именно свою реализацию.

### На что смотрю в первую очередь

1. **Соответствие задаче:** реализовано ли нужное поведение, учтены ли пограничные случаи?
2. **Корректность и безопасность:** права доступа, валидация, конкурентные изменения, транзакции, идемпотентность.
3. **Совместимость и эксплуатация:** миграции, API, очереди, возможность безопасной выкладки и отката.
4. **Доступ к данным и производительность:** N+1, объём загрузки, индексы, внешние вызовы.
5. **Тесты:** проверяют ли поведение и риски, а не только внутренние вызовы?
6. **Читаемость и архитектура:** ясные имена, границы ответственности, отсутствие лишних абстракций.

Форматирование и простые правила оставляю линтерам. Вручную важнее проверить то, чего CI не понимает.

### Если не согласен с автором

Сначала проверяю, не упустил ли я требования или ограничения. Затем обсуждаем **конкретный риск и trade-offs**, а не «правильный стиль».

Если спор можно проверить, использую факт: тест, план запроса, небольшой эксперимент или документацию. Если это равноценные варианты без существенного риска, не блокирую PR из-за личного предпочтения.

Когда переписка затягивается, предлагаю короткий созвон и фиксирую итог в PR. Для существенного архитектурного решения — краткий ADR. Если согласия нет по блокирующему вопросу, привлекаем владельца области или техлида согласно правилам команды.

Важно не превращать ревью в расширение задачи: независимый рефакторинг можно вынести отдельно. Но реальную проблему безопасности или целостности нельзя отложить только ради срока.

**Критерий хорошего ревью для меня: замечания понятны, приоритеты явны, решение обосновано, а обсуждение остаётся уважительным к автору.**

## а) Нашёл попутный баг

1. Проверяю, действительно ли это баг: фиксирую воспроизведение, ожидаемое и фактическое поведение.
2. Оцениваю влияние: затронутые пользователи, безопасность, потеря данных, наличие обходного пути.
3. Завожу отдельную задачу и связываю её с текущей.

Дальше — по ситуации:

- **Не мешает текущей задаче:** продолжаю работу, исправление — отдельным PR.
- **Блокирует реализацию или проверку:** обозначаю зависимость и согласовываю включение исправления либо изменение плана.
- **Критичный баг, например утечка данных:** немедленно эскалирую по процессу инцидентов; при необходимости приостанавливаю текущую работу.

## б) Критерий приёмки противоречит цели

Не игнорирую критерий, но и не реализую его вслепую.

1. Показываю противоречие на конкретном сценарии.
2. Описываю последствия выполнения критерия.
3. Предлагаю исправленную формулировку и варианты решения с влиянием на сроки.
4. Согласовываю решение с владельцем требований, при необходимости подключаю QA.

## Q24 · Провокации

**Интервьюер:** Для чего в PostgreSQL используется FORCE INDEX и в каких случаях его применяют?

**Кандидат:**

В PostgreSQL **нет штатной конструкции `FORCE INDEX`**. Она есть, например, в MySQL, поэтому сначала уточнил бы, о какой СУБД или расширении идёт речь.

В PostgreSQL планировщик сам выбирает способ доступа на основе статистики и оценки стоимости. Если он не использует ожидаемый индекс, я проверяю:

- селективность условия — возможно, последовательное чтение действительно дешевле;
- актуальность статистики (`ANALYZE`);
- соответствие индекса условиям, сортировке и типам;
- функции и приведения над индексированным столбцом;
- различия между estimated и actual rows в `EXPLAIN (ANALYZE, BUFFERS)`.

### Как проверить альтернативный план

Для диагностики можно временно снизить привлекательность последовательного сканирования:

```sql
BEGIN;

SET LOCAL enable_seqscan = off;

EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE customer_id = 123;

ROLLBACK;
```

Но это **не принудительный выбор конкретного индекса** и не абсолютный запрет Seq Scan. Настройка лишь заставляет планировщик по возможности избегать такого способа доступа.

Применяю её для эксперимента: сравнить планы и выяснить, почему оценка стоимости расходится с реальным выполнением. Глобально отключать Seq Scan как «оптимизацию» не стал бы.

Если нужны явные подсказки, существует стороннее расширение **`pg_hint_plan`**, позволяющее влиять на выбор индекса и другие решения планировщика. Использовал бы его точечно, при подтверждённой необходимости: подсказки требуют сопровождения и могут стать неэффективными при изменении данных.

**Обычное решение — исправить запрос, индекс или статистику, а не принуждать PostgreSQL к заранее выбранному плану.**

## Q26 · Провокации

**Интервьюер:** Почему Doctrine ORM не поддерживает составные первичные ключи и как с этим живут в реальных проектах?

**Кандидат:**

Здесь поправлю предпосылку: **Doctrine ORM поддерживает составные первичные ключи**, в том числе ключи, включающие внешние ключи. Но у них есть ограничения и дополнительная сложность.

### Как это выглядит

Например, позиция товара на конкретном складе идентифицируется парой `warehouse_id + product_id`:

```php
#[ORM\Entity]
class StockItem
{
    #[ORM\Id]
    #[ORM\ManyToOne(targetEntity: Warehouse::class)]
    #[ORM\JoinColumn(nullable: false)]
    private Warehouse $warehouse;

    #[ORM\Id]
    #[ORM\ManyToOne(targetEntity: Product::class)]
    #[ORM\JoinColumn(nullable: false)]
    private Product $product;

    #[ORM\Column]
    private int $quantity;

    public function __construct(
        Warehouse $warehouse,
        Product $product,
        int $quantity,
    ) {
        $this->warehouse = $warehouse;
        $this->product = $product;
        $this->quantity = $quantity;
    }
}
```

Оба поля с `#[ORM\Id]` образуют первичный ключ.

### Ограничения и подводные камни

- **Для составного ключа нельзя использовать автоматическую генерацию ID через `GeneratedValue`.** Компоненты идентификатора должны быть заданы до `persist()`.
- Идентичность после сохранения не следует менять: замена склада или товара здесь означает создание другой сущности.
- Ссылки на такую сущность могут потребовать нескольких join columns.
- Запросы, маршруты, DTO и интеграции должны передавать весь идентификатор.
- Поддержка конкретного маппинга в сторонних пакетах и инструментах может быть ограничена.

То есть проблема не в отсутствии поддержки, а в стоимости использования.

### Как выбираю в реальном проекте

**Вариант 1 — оставить составной PK.**  
Подходит для существующей схемы или сущности, чья идентичность действительно задаётся комбинацией значений. Маппинг, загрузку и связи проверяю интеграционными тестами.

**Вариант 2 — отдельный технический ID плюс уникальность пары.**

```sql
CREATE TABLE stock_items (
    id uuid PRIMARY KEY,
    warehouse_id uuid NOT NULL REFERENCES warehouses(id),
    product_id uuid NOT NULL REFERENCES products(id),
    quantity integer NOT NULL,
    UNIQUE (warehouse_id, product_id)
);
```

Это упрощает ссылки и работу инструментов, но добавляет ещё один идентификатор и индекс. **`UNIQUE` на бизнес-комбинацию обязательно сохраняю** — технический ID не предотвращает дубли.

**Вариант 3 — DBAL или SQL для отдельных участков.**  
Если таблица служит для массовых операций или сложный legacy-маппинг не даёт пользы от ORM, не обязательно превращать её в ORM-сущность.

**Итого:** составные ключи в Doctrine допустимы. Отдельный ID часто удобнее, но это проектное решение, а не обход несуществующего запрета.

## Q27 · Мини-код-ревью

**Интервьюер:** Посмотри на этот код:

```php
class OrderController
{
    public function pay(Request $req): Response
    {
        $id = $req->get('order_id');
        $pdo = DB::connect();
        $order = $pdo->query("SELECT * FROM orders WHERE id = $id")->fetch();
        if (!$order) {
            return new Response('not found', 404);
        }
        $order['status'] = 'paid';
        $pdo->exec("UPDATE orders SET status = 'paid' WHERE id = $id");
        Mailer::send($order['email'], 'Ваш заказ оплачен');
        (new Logger())->log('paid ' . $id);
        return new Response('ok');
    }
}
```

Какие проблемы ты видишь и как бы ты этот код переделал? С чего начал бы и почему?

**Кандидат:**

Я бы начал **не с разбиения класса, а с безопасности и смысла операции**. Сейчас endpoint позволяет пометить заказ оплаченным, но в коде нет подтверждения платежа.

## Проблемы

### Критичные

- **SQL injection:** `$id` напрямую вставляется в оба SQL-запроса.
- **Нет аутентификации и проверки доступа:** можно попытаться оплатить чужой заказ.
- **Нет проверки факта оплаты:** запрос пользователя сам по себе не доказывает получение денег. Нужен результат платёжного провайдера или проверенный webhook.
- **Не определены HTTP-метод и CSRF-защита:** изменение состояния не должно выполняться через GET; для cookie-based аутентификации нужна защита от CSRF.

### Корректность и надёжность

- Нет проверки перехода состояния: отменённый заказ тоже станет `paid`.
- Нет защиты от конкурентных и повторных запросов.
- `SELECT` и `UPDATE` не образуют единую защищённую операцию.
- Если письмо не отправится, заказ уже оплачен, но клиент может получить ошибку и повторить запрос.
- Повторный запрос повторно отправит письмо.
- Не обработаны ошибки БД и внешних сервисов.

### Структура

Контроллер одновременно отвечает за HTTP, SQL, бизнес-правила, письмо и логирование. Статические вызовы и `new Logger()` затрудняют подмену зависимостей и тестирование. `SELECT *` загружает лишние данные, `$order['status'] = 'paid'` лишь меняет локальный массив.

## С чего начал бы

1. **Уточнил контракт:** это инициирование платежа или подтверждение уже выполненного?
2. Закрыл SQL injection, доступ и небезопасный способ вызова.
3. Добавил проверки переходов, повторов и конкуренции.
4. Затем выделил сценарий и инфраструктуру, вынес письмо в фон.

Это важнее косметического рефакторинга: красиво разделённый код может оставаться финансово небезопасным.

## Как переделал бы

Для пользовательского endpoint `POST /orders/{id}/pay` контроллер только инициирует платёж:

```php
final class OrderController extends AbstractController
{
    public function __construct(
        private OrderRepository $orders,
        private InitiatePaymentHandler $handler,
    ) {}

    public function pay(string $id): JsonResponse
    {
        $orderId = OrderId::fromString($id);
        $order = $this->orders->get($orderId);

        $this->denyAccessUnlessGranted(OrderVoter::PAY, $order);

        $result = $this->handler->handle(
            new InitiatePayment($orderId)
        );

        return $this->json([
            'paymentId' => $result->paymentId,
            'status' => $result->status,
        ]);
    }
}
```

Маршрут, валидация, CSRF при необходимости и преобразование исключений в HTTP-ответы настраиваются отдельно. Прикладной сценарий получает проверенную идентичность пользователя, если должен самостоятельно обеспечивать авторизацию при других способах вызова.

**Инициирование оплаты** использует стабильный idempotency key платёжной попытки. Сетевой вызов не держит долгую блокировку БД; тайм-аут не считается доказательством отказа платежа.

**Подтверждение оплаты** — отдельный сценарий. Его вызывает адаптер webhook после проверки подписи и данных провайдера, либо процесс сверки платежей:

```php
final class ConfirmPaymentHandler
{
    public function __construct(
        private OrderRepository $orders,
        private ProcessedPayments $processed,
        private Outbox $outbox,
        private TransactionManager $transactions,
    ) {}

    public function handle(VerifiedPayment $payment): void
    {
        $this->transactions->run(function () use ($payment): void {
            $order = $this->orders->getForUpdate($payment->orderId);

            if ($this->processed->contains($payment->paymentId)) {
                return;
            }

            // Проверяет сумму, валюту и допустимость перехода.
            $order->recordPayment(
                $payment->paymentId,
                $payment->amount,
            );

            $this->processed->add($payment->paymentId);

            foreach ($order->releaseEvents() as $event) {
                $this->outbox->append($event);
            }
        });
    }
}
```

Здесь:

- `getForUpdate()` блокирует корень внутри короткой транзакции;
- уникальность идентификатора платежа дополнительно защищена constraint в БД;
- изменение заказа, запись обработки платежа и outbox сохраняются атомарно;
- повторное подтверждение не создаёт повторного события;
- воркер отправляет письмо, обрабатывая возможные повторы доставки.

Репозиторий использует Doctrine или параметризованный SQL, но не конкатенацию:

```php
$stmt = $pdo->prepare(
    'SELECT id, status FROM orders WHERE id = :id'
);
$stmt->execute(['id' => $id]);
```

Логгер внедряется через `LoggerInterface`; пишутся структурированные данные — ID заказа, платежа и correlation ID, без лишних персональных данных.

## Что проверю тестами

- нельзя оплатить чужой заказ;
- неподтверждённый запрос не меняет статус на `paid`;
- неправильная сумма или валюта отклоняются;
- повторное и конкурентное подтверждения обрабатываются безопасно;
- rollback не оставляет событие в outbox;
- сбой отправки письма не отменяет зафиксированную оплату.

**Итог:** контроллер — транспортная граница, оплата — явный бизнес-процесс, БД защищает атомарность и уникальность, а письмо отправляется независимо после фиксации результата.

## Q28 · Мини-код-ревью

**Интервьюер:** Посмотри на эту доменную сущность:

```php
#[ORM\Entity]
class User
{
    public function __construct(
        private EntityManagerInterface $em,
        private string $email,
    ) {}

    public function changeEmail(string $email): void
    {
        $this->email = $email;
        $this->em->flush();
    }

    public function email(): string
    {
        return $this->email;
    }
}
```

Что не так с этой сущностью с точки зрения DDD и чистой архитектуры? Как бы ты её исправил?

**Кандидат:**

Главная проблема — **сущность управляет persistence-механизмом вместо того, чтобы только выражать бизнес-поведение**.

## Что не так

1. **Зависимость домена от Doctrine.**  
   `EntityManagerInterface` нарушает направление зависимостей чистой архитектуры. Чтобы проверить смену email, теперь нужен инфраструктурный объект.

2. **`flush()` внутри сущности.**  
   Он сохраняет изменения всего Unit of Work, а не только этого пользователя. Вызов `changeEmail()` неожиданно может записать изменения других сущностей и нарушить границу прикладной транзакции.

3. **Проблема гидратации.**  
   Doctrine обычно восстанавливает сущности без вызова конструктора. Поле `$em` не является маппируемым и после загрузки может остаться неинициализированным.

4. **Не защищены инварианты.**  
   Любая строка принимается как email. Не определено, требует ли смена подтверждения и что происходит при повторном присваивании того же адреса.

5. **Не показана идентичность.**  
   Если это полный код, отсутствуют ORM-идентификатор и маппинг email. Для Entity нужна доменная идентичность.

Атрибут `#[ORM\Entity]` — отдельный вопрос: при строгой чистой архитектуре маппинг выносится наружу; в более прагматичном варианте атрибуты допустимы как осознанный компромисс. Но внедрение EntityManager и `flush()` внутри сущности я бы убрал в любом случае.

## Доменная модель

Email делаю Value Object:

```php
final readonly class EmailAddress
{
    public function __construct(public string $value)
    {
        if (filter_var($value, FILTER_VALIDATE_EMAIL) === false) {
            throw new \InvalidArgumentException('Invalid email');
        }
    }

    public function equals(self $other): bool
    {
        return $this->value === $other->value;
    }
}
```

Правила нормализации и равенства адресов согласуются отдельно.

Сущность отвечает только за своё состояние:

```php
final class User
{
    public function __construct(
        private readonly UserId $id,
        private EmailAddress $email,
    ) {}

    public function changeEmail(EmailAddress $email): void
    {
        if ($this->email->equals($email)) {
            return;
        }

        $this->email = $email;
    }

    public function email(): EmailAddress
    {
        return $this->email;
    }
}
```

Если бизнес требует подтверждения нового адреса, вместо немедленной замены моделирую `requestEmailChange()` и `confirmEmailChange()`. При необходимости сущность записывает доменное событие, но не отправляет письмо самостоятельно.

## Прикладной сценарий и сохранение

```php
final class ChangeEmailHandler
{
    public function __construct(
        private UserRepository $users,
        private TransactionManager $transactions,
    ) {}

    public function handle(ChangeEmail $command): void
    {
        $this->transactions->run(function () use ($command): void {
            $user = $this->users->get($command->userId);

            $user->changeEmail(
                new EmailAddress($command->email)
            );
        });
    }
}
```

Здесь:

- репозиторий загружает пользователя;
- сущность проверяет локальные бизнес-правила;
- инфраструктурная реализация transaction manager вызывает `flush()` и commit;
- авторизация проверяется на соответствующей границе сценария;
- уникальность email, если она требуется, гарантируется БД, а известное нарушение переводится в прикладную ошибку.

ORM-маппинг размещаю отдельно, например в XML, а `EmailAddress` сохраняю через custom DBAL type, который восстанавливает VO через его конструктор.

**Итого: сущность меняет доменное состояние; прикладной слой определяет сценарий и границу транзакции; Doctrine отвечает за хранение.**

Согласовываю timebox исследования — например, несколько часов для небольшой задачи или отдельный день для сложной интеграции.

После проверки подхода разбиваю работу на:

- реализацию;
- тестирование;
- интеграцию и ревью;
- миграцию или выкладку;
- наблюдение после выпуска.

Даю **диапазон с условиями и уровнем уверенности**, а не обещание без оснований:

> Основной подход проверен. Оценка — 2–3 рабочих дня, включая тесты и ревью, при условии доступа к тестовому API. Если потребуется поддержка старого формата данных, это отдельный объём. Срок получения доступа в оценку разработки не входит.

- тесты нестабильны;

## Мой базовый выбор

Для бизнес-приложения с API, личным кабинетом, интеграциями и фоновой обработкой:

| Компонент | Выбор и причина |
|---|---|
| **Язык** | Поддерживаемая версия PHP 8.x: выразительные типы, зрелая экосистема, удобство разработки прикладного бэкенда |
| **Фреймворк** | Symfony поддерживаемой, при необходимости LTS-ветки: DI, Security, Messenger и предсказуемый жизненный цикл |
| **БД** | PostgreSQL: транзакции, ограничения целостности, развитый SQL и хорошие средства диагностики |
| **Хранение** | Doctrine ORM для агрегатов и обычных операций; DBAL/SQL для read models и массовой обработки |
| **Фоновые задачи** | Symfony Messenger; сначала Doctrine transport, если объём небольшой, внешний брокер — при обоснованной потребности |
| **Тесты и анализ** | PHPUnit, PHPStan или Psalm, интеграционные тесты с настоящей PostgreSQL |
| **Сборка и доставка** | Composer, Docker, CI/CD с неизменяемыми артефактами |

**Redis, поисковый движок и Kubernetes не включал бы автоматически.** Для каждого дополнительного компонента нужна конкретная задача и готовность его обслуживать.

## Архитектура — модульный монолит

Начал бы с модульного монолита с явными границами бизнес-модулей.

Почему:

- проще разработка, локальный запуск и диагностика;
- меньше инфраструктурных отказов;
- проще обеспечить транзакционную согласованность;
- границы предметной области можно уточнять без дорогих изменений распределённой системы.

Микросервисы рассматривал бы при реальной необходимости независимого масштабирования, выпуска или владения отдельными частями системы — не как признак «современности».

## Как защищал бы выбор

Аргументация была бы такой:

> Для наших сценариев этот стек закрывает основную функциональность стандартными средствами. Команда сможет быстро выпускать изменения и поддерживать их без большого числа собственных инфраструктурных решений. При этом мы сохраняем возможность использовать SQL напрямую и выделять отдельные компоненты там, где это действительно потребуется.

Обязательно обозначил бы ограничения:

- ORM может создавать дорогую гидратацию и неэффективные запросы — нужны профилирование и отдельные модели чтения.
- PHP не был бы моим первым выбором для тяжёлых вычислений или некоторых сценариев с огромным числом долгоживущих соединений.
- Добавление очереди требует мониторинга, идемпотентности и процессов обработки ошибок.
- Если команда уже эффективно работает на другом подходящем стеке, переход на Symfony может стоить больше, чем даст.

Для спорного технического требования предложил бы небольшой прототип или нагрузочный тест, а итог зафиксировал в ADR: требования, альтернативы, причины выбора и условия пересмотра.

**Мой выбор — знакомый, зрелый и достаточно простой стек, который команда сможет уверенно эксплуатировать. Не максимум технологий, а минимум необходимых компонентов с понятным запасом развития.**
